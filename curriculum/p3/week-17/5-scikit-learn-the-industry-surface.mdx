## The mental model

scikit-learn has exactly one interface. An **estimator** learns from data with `fit(X, y)`. If it produces predictions it has `predict`; if it produces new features it has `transform`. That is it. Because everything obeys the same contract, objects compose: a `Pipeline` is an estimator made of estimators, `GridSearchCV` is an estimator that fits many copies of an estimator, and `ColumnTransformer` is an estimator that applies different estimators to different columns. The payoff is not tidiness. It is that **`fit` is called in exactly one place**, so the "this transformer must only see training data" rule is enforced by the object graph rather than by you remembering.

```python
# pip install "scikit-learn==1.9.0" "numpy==2.5.2"
from sklearn.datasets import load_breast_cancer

```

### The estimator contract

Every scikit-learn object obeys one of two shapes.

| Method | Present on | Promise |
| --- | --- | --- |
| `fit(X, y=None)` | everything | learn from data; store what it learned in attributes ending with an underscore (`coef_`, `mean_`, `classes_`); return `self` |
| `predict(X)` | models | a prediction per row |
| `predict_proba(X)` | classifiers that can | a probability per class per row |
| `transform(X)` | preprocessors | new features per row |
| `fit_transform(X, y=None)` | preprocessors | `fit` then `transform`, sometimes faster than doing both |
| `score(X, y)` | models | one default metric — accuracy for classifiers, R² for regressors |
| `get_params()` / `set_params()` | everything | read and write the constructor arguments, which is how grid search works |

Two conventions worth knowing on day one:

- **Constructor arguments are stored verbatim and never validated in `__init__`.** All checking happens in `fit`. This is so `clone()` can copy an estimator by reading its params, which is what cross-validation does for every fold.
- **Anything learned from data ends with an underscore.** `scaler.mean_` exists only after `fit`. If you see an attribute without a trailing underscore, it came from you, not from the data. This single naming rule tells you what a serialised model actually contains.

### `fit_transform` on the training set only — the rule

A `StandardScaler` learns two numbers per column: the mean and the standard deviation. Those numbers must come from training data only.

```python
scaler = StandardScaler()
X_tr_s = scaler.fit_transform(X_tr)   # LEARN mean/std here, and apply
X_te_s = scaler.transform(X_te)       # only APPLY. never fit_transform on test.
```

If you write `scaler.fit_transform(X)` on the whole dataset before splitting, the test rows contributed to the mean and standard deviation that the training used. That is **data leakage**: information flowed backwards across the wall from Module 1. Week 19 Module 4 measures exactly how much damage each kind of leak does; Layer 2 below measures one of them right now.

### `Pipeline`: the fix that cannot be forgotten

```python
from sklearn.pipeline import Pipeline

model = Pipeline([
    ("scale", StandardScaler()),
    ("clf",   LogisticRegression(max_iter=5000)),
])
model.fit(X_tr, y_tr)     # calls scale.fit_transform then clf.fit
model.predict(X_te)       # calls scale.transform then clf.predict
```

Read the two comments. On `fit`, the scaler is *fitted*. On `predict`, it is only *applied*. You cannot get this wrong, because `Pipeline` decides, not you. And when a `Pipeline` goes into `cross_val_score`, the whole thing is refitted inside each fold — so the scaler only ever sees that fold's training rows.

`make_pipeline(...)` is the same thing with the step names generated for you (lowercased class names: `standardscaler`, `logisticregression`).

### Line-by-line: what `fit` did

```python
model = make_pipeline(StandardScaler(), LogisticRegression(C=1.0, max_iter=5000))
model.fit(X_tr, y_tr)

print(model[0].mean_[:3])          # [1.40e+01 1.93e+01 9.15e+01]  learned from X_tr
print(model[0].scale_[:3])         # [3.50e+00 4.35e+00 2.40e+01]
print(model[-1].coef_.shape)       # (1, 30)   one weight per feature
print(model[-1].intercept_)        # [0.325...]
print(model[-1].n_iter_)           # how many lbfgs iterations were used
print(model.named_steps["logisticregression"].C)   # 1.0 — you set this, no underscore
```

- `model[0]` and `model[-1]` index the steps. `model.named_steps["..."]` is the same by name.
- `mean_` and `scale_` are the 30 means and 30 standard deviations computed from `X_tr`. These travel with the model, which is why a serialised pipeline can preprocess a single row at serving time identically to training.
- `coef_` is the 30 weights from Module 3, now fitted by `lbfgs` rather than your gradient loop.
- `n_iter_` is the honest convergence report. If it equals `max_iter`, the fit did not converge and any number you report is provisional.

### Checkpoint

<AccordionGroup>
  <Accordion title="1. Why does fit() return self?">
  So calls can chain: `model.fit(X, y).predict(X_te)`. It is also part of the contract that `clone` and `Pipeline` rely on.
  </Accordion>
  <Accordion title="2. What is the difference between a parameter and an attribute here?">
  Parameters are constructor arguments you chose (`C`, `max_iter`) and have no underscore. Attributes are learned from data (`coef_`, `mean_`) and end with one. `get_params()` returns the first kind only.
  </Accordion>
  <Accordion title="3. Can you call transform before fit?">
  No — you get `NotFittedError`. That check is `sklearn.utils.validation.check_is_fitted`, and you should call it in your own transformers too.
  </Accordion>
  <Accordion title="4. What does random_state actually control?">
  Any randomness inside the estimator: the shuffle in `train_test_split`, the bootstrap samples in a forest, the mini-batch order in `SGDClassifier`. Setting it makes a run reproducible. Leaving it as `None` means your reported number is one draw from a distribution you never measured.
  </Accordion>
  <Accordion title="5. Why is fit_transform sometimes faster than fit then transform?">
  Because some estimators compute the transformed output as a by-product of fitting. `PCA.fit_transform` gets the projected data out of the SVD it already ran. For `StandardScaler` there is no saving; the method exists for interface uniformity.
  </Accordion>
</AccordionGroup>

### Leakage, measured: +30.5 accuracy points on data with no signal

This is the experiment that changes behaviour. Generate 200 rows of pure Gaussian noise with 10,000 features and a coin-flip label. There is **no signal**. The true accuracy of any model is 0.50.

```python
# scikit-learn 1.9.0, numpy 2.5.2
import numpy as np
from sklearn.feature_selection import SelectKBest, f_classif
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score
from sklearn.pipeline import make_pipeline

leaky, correct = [], []
for seed in range(20):
    rng = np.random.default_rng(seed)
    X = rng.normal(size=(200, 10_000))
    y = rng.integers(0, 2, 200)

    # WRONG: select the best 20 features using ALL the labels, then cross-validate
    X_sel = SelectKBest(f_classif, k=20).fit_transform(X, y)
    leaky.append(cross_val_score(LogisticRegression(max_iter=5000), X_sel, y, cv=5).mean())

    # RIGHT: selection happens inside each fold, on that fold's training rows only
    pipe = make_pipeline(SelectKBest(f_classif, k=20), LogisticRegression(max_iter=5000))
    correct.append(cross_val_score(pipe, X, y, cv=5).mean())

print("leaky  : %.3f (sd %.3f)" % (np.mean(leaky), np.std(leaky)))
print("correct: %.3f (sd %.3f)" % (np.mean(correct), np.std(correct)))
print("inflation: %.1f accuracy points" % ((np.mean(leaky) - np.mean(correct)) * 100))
```

```
leaky  : 0.815 (sd 0.026)
correct: 0.510 (sd 0.048)
inflation: 30.5 accuracy points
```

Sit with that. **81.5% cross-validated accuracy on random noise.** And the standard deviation across 20 seeds is only 0.026, so it looks *stable* — it would survive a "we ran it five times" sanity check. The correct pipeline gives 0.510, which is 0.5 plus the noise you expect from 200 rows.

The mechanism: with 10,000 noise features and 200 rows, some features will correlate with the labels by chance. `SelectKBest` finds the 20 luckiest ones *using the labels of every row, including the rows that will later be a validation fold*. Cross-validation then measures how well the model predicts labels that were already used to choose the features.

The `Pipeline` version is immune, not because it is careful, but because `cross_val_score` clones the whole pipeline per fold, so `SelectKBest.fit` never sees the validation rows.

<Warning>
This generalises to every transformer that uses `y`, and to several that do not: feature selection, target encoding, oversampling (Week 20 Module 4), dimensionality reduction fitted on all data, and any imputation whose statistic comes from the full set. **If a transformer has a `fit`, it belongs inside the pipeline.**
</Warning>

### `ColumnTransformer`: different columns, different treatment

Real tables are not one dtype. `ColumnTransformer` routes column subsets to different pipelines and concatenates the results.

```python
# scikit-learn 1.9.0, pandas 3.0.5
import sklearn
from sklearn.compose import ColumnTransformer
from sklearn.pipeline import Pipeline
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import StandardScaler, OneHotEncoder
from sklearn.linear_model import LogisticRegression

sklearn.set_config(transform_output="pandas")     # keep names all the way through

numeric     = ["age", "income", "tenure_days"]
categorical = ["plan", "region"]

pre = ColumnTransformer(
    transformers=[
        ("num", Pipeline([("imp", SimpleImputer(strategy="median")),
                          ("sc",  StandardScaler())]), numeric),
        ("cat", OneHotEncoder(handle_unknown="infrequent_if_exist",
                              min_frequency=0.02, sparse_output=False), categorical),
    ],
    remainder="drop",
    verbose_feature_names_out=True,
)
model = Pipeline([("pre", pre), ("clf", LogisticRegression(max_iter=3000))])
```

Four choices in there that are load-bearing:

- **`remainder="drop"`** (the default) means a column you forgot silently disappears. `remainder="passthrough"` means a new upstream column silently arrives untransformed. Neither is safe by accident — pick one deliberately and assert your expected output width after `fit`.
- **`handle_unknown="infrequent_if_exist"`** maps a category never seen in training into the "infrequent" bucket rather than raising. Without it, one new `region` value takes your serving endpoint down at 3 a.m.
- **`min_frequency=0.02`** groups categories appearing in under 2% of rows into that same bucket, which is the rare-category handling from Week 20 Module 1 available for free.
- **`sparse_output=False`** because mixing sparse one-hot output with dense scaled output forces a densification anyway; be explicit rather than surprised.

### Custom transformers

Anything you can write as `fit` then `transform` can join a pipeline. The contract is short but every clause matters.

```python
import numpy as np, pandas as pd
from sklearn.base import BaseEstimator, TransformerMixin

class RatioFeatures(TransformerMixin, BaseEstimator):
    """Derive log income and income per year of tenure.

    Mixin order matters: TransformerMixin FIRST, BaseEstimator last. scikit-learn
    1.9's check_estimator hard-fails the other way round with
    "inheriting from mixins in the wrong order". TransformerMixin gives you
    fit_transform and set_output; BaseEstimator gives get_params/set_params
    (so GridSearchCV can reach your parameters) and a readable __repr__.
    """

    def fit(self, X, y=None):
        self.feature_names_in_ = np.asarray(X.columns)
        self.n_features_in_ = X.shape[1]
        return self                       # ALWAYS return self

    def transform(self, X):
        out = pd.DataFrame(index=X.index)
        out["log_income"] = np.log1p(X["income"])
        out["income_per_tenure_year"] = X["income"] / (X["tenure_days"] / 365.25 + 1e-9)
        return out

    def get_feature_names_out(self, input_features=None):
        return np.array(["log_income", "income_per_tenure_year"])
```

The rules, in order of how often they are broken:

0. **Mixin order: specialised first, `BaseEstimator` last.** `class T(TransformerMixin, BaseEstimator)`. Writing it the other way round raises `AssertionError: WinsorizingScaler is inheriting from mixins in the wrong order` from `check_estimator` in scikit-learn 1.9 — measured, not hypothetical.
1. **Do no work in `__init__`.** Store arguments unchanged, under the same names. `clone()` calls `type(est)(**est.get_params())` and expects an equivalent object; if you transform an argument in `__init__`, cloning silently produces a different estimator, and every cross-validation fold quietly differs from what you think you fitted.
2. **`fit` must return `self`.** Otherwise `fit_transform` from the mixin returns `None`.
3. **Implement `get_feature_names_out`** or your column names vanish at this step and every downstream name becomes `x0`, `x1`.
4. **Do not use `y` in `transform`.** If you need `y`, you need it in `fit` — and then you have a leakage-sensitive transformer that *must* live inside the pipeline.
5. **Set `n_features_in_` and `feature_names_in_`** in `fit` so scikit-learn's schema checks can catch a column-order change at serving time.

### Trade-offs

| Decision | Choose the first when… | Choose the second when… |
| --- | --- | --- |
| **`Pipeline`** vs **loose transformers in a script** | always, for anything that will be cross-validated, tuned or served | never — the only legitimate case is one-off exploratory analysis you will delete |
| **`set_output("pandas")`** vs **numpy arrays** | you have named columns, mixed dtypes, and want debuggable intermediates and working `get_feature_names_out` | throughput matters and you have measured the DataFrame overhead: on the pipeline above it is most of the 2.84 ms per row |
| **`GridSearchCV`** vs **`RandomizedSearchCV`** | the grid is under a few hundred fits, or the parameters are genuinely discrete | more than 3 hyperparameters, or continuous ranges — random search finds a comparable optimum in far fewer fits (Bergstra & Bengio 2012) |
| **`HalvingGridSearchCV`** vs **plain grid** | fits are expensive and most configurations are clearly bad early | fits are cheap, or performance at small `n` does not predict performance at full `n` |
| **`joblib.dump`** vs **`skops` / ONNX** | internal use, same environment pinned, short lifetime | the artifact crosses a trust or version boundary — Week 20 Module 5 breaks a pickle on purpose |

### Reproducibility

Three sources of non-determinism, in the order they bite:

1. **`random_state=None`.** `train_test_split`, `RandomForestClassifier`, `SGDClassifier`, `KMeans` and `RandomizedSearchCV` all draw from the global numpy RNG when it is unset. Set it explicitly at every call site. Do not rely on `np.random.seed()`; scikit-learn's newer code paths use `Generator` objects that ignore it.
2. **Thread-count-dependent floating-point summation.** BLAS reduces in a different order with a different thread count, so `OMP_NUM_THREADS=1` and `OMP_NUM_THREADS=8` can give results differing at the 1e-12 level, which can flip a tie-break in a tree. Pin the thread count in CI if you need bit-identical results.
3. **Library version.** Default parameter values change between minor releases. Pin `scikit-learn==1.9.0` exactly in `requirements.txt`, not `>=`.

### War story: the `ConvergenceWarning` everyone filtered

A team's credit-risk model had a notebook that began with `warnings.filterwarnings("ignore")` — added years earlier because a deprecation notice was noisy. Their monthly refit used `LogisticRegression(max_iter=100)` (the default at the time) on 180 unscaled features.

For eighteen months the model never converged. `n_iter_` was pinned at `max_iter` every single run. The coefficients were wherever lbfgs happened to be after 100 iterations, which depended on the data ordering, so the "top risk drivers" report changed every month and was quietly explained away as "the market moving".

It surfaced when a new hire added `StandardScaler` to the pipeline for unrelated reasons and the model's Gini jumped by 4.1 points overnight. The investigation found `n_iter_ = [100]` in every archived model object.

Two fixes, both cheap. `StandardScaler` in the pipeline, which made lbfgs converge in 23 iterations. And a post-fit assertion in the training job: `assert model[-1].n_iter_.max() < model[-1].max_iter`, promoted to a hard failure. The general lesson: **`ConvergenceWarning` is not a style complaint. It means the object you serialised is not the model you specified.** Never blanket-filter warnings in a training path; filter the specific category you have understood.

### Design checkpoint

> You need to tune an imputation strategy, a one-hot encoder's `min_frequency`, a feature-selection `k`, and a model's `C`, and report an honest score. Sketch the object graph.

<Accordion title="Model answer">
One `Pipeline` containing a `ColumnTransformer` (numeric branch: `SimpleImputer` then `StandardScaler`; categorical branch: `OneHotEncoder`), then `SelectKBest`, then `LogisticRegression`. Every tunable is reachable by a double-underscore path: `pre__num__imp__strategy`, `pre__cat__min_frequency`, `select__k`, `clf__C`. Wrap that in `RandomizedSearchCV` (four parameters is past where grid search is efficient) with an inner `StratifiedKFold`. Then — this is the part people skip — wrap *that* in an outer `cross_val_score` with its own `StratifiedKFold` to get the reported number, because the inner search's best score is optimistically biased by the selection itself. That is nested CV, it costs `outer x inner` fits, and Week 19 Module 3 measures how large the bias is when you skip it. If the cost is prohibitive, the honest alternative is a single untouched holdout scored exactly once, and you say so in the report.
</Accordion>

### Which solver is actually running

`LogisticRegression` dispatches to one of five solvers, and they are genuinely different algorithms with different asymptotics. Measured on 50,000 x 200 dense standardised data, `C=1.0`, `tol=1e-4`, single process, Apple M3 Pro, scikit-learn 1.9.0:

| `solver` | penalty | wall clock | `n_iter_` | train accuracy | what it is |
| --- | --- | --- | --- | --- | --- |
| `lbfgs` (default) | L2 | **0.11 s** | 10 | 0.8833 | limited-memory quasi-Newton; stores `m` past updates, `O(mp)` memory |
| `newton-cholesky` | L2 | 1.05 s | 5 | 0.8833 | forms the full `p x p` Hessian, one Cholesky per step |
| `liblinear` | L2 | 1.79 s | 6 | 0.8833 | coordinate descent on the dual; one-vs-rest only |
| `saga` | L2 | 2.31 s | 18 | 0.8833 | variance-reduced SGD; supports L1 and elastic net |
| `saga` | L1 | 19.18 s | 82 | 0.8833 | as above, with the non-smooth penalty |

All five reach the same optimum to four decimals. They must: the objective is convex with a unique minimum. The spread is **174x in wall clock**, and that is the entire content of the choice.

The selection rule, from the asymptotics rather than the folklore:

- **`lbfgs`**: cost per iteration `O(np)`, memory `O(mp)` with `m = 10` by default. Best general default. Needs standardised features — its line search assumes comparable scales.
- **`newton-cholesky`**: cost per iteration `O(np^2 + p^3)`. Superb when `n >> p` and `p` is at most a few hundred; catastrophic beyond that. Added in 1.2 precisely for the wide-data-poor-in-features case.
- **`liblinear`**: the old default. Coordinate descent, `O(np)` per pass, no true multinomial support (it does one-vs-rest even if you ask for multinomial). Still competitive on small sparse problems.
- **`saga`**: the only route to L1 or elastic net on large data, and the only one supporting sparse input with all penalties. Pay the 8-20x tax when you need the sparsity.

You can check what ran: `model.n_iter_` is the iteration count, and if it equals `max_iter` you did not converge, whatever the score says.

### Why your from-scratch answer differs

In Module 3, our hand-rolled gradient descent and `lbfgs` produced objective values `0.0663602356` and `0.0663601862` — a gap of `4.9e-08` — with coefficients differing by `2.6e-3`. Four distinct reasons, and all four appear in real debugging:

1. **Different stopping criteria.** Ours stopped on change-in-objective below `1e-10` after 4,680 iterations with gradient norm `1.0e-05`. `lbfgs` stops on the gradient's infinity norm below `tol` and reached `2.6e-08`. Comparing two optimisers means first agreeing what "converged" means.
2. **Flat directions.** `mean radius`, `mean perimeter` and `mean area` in this dataset correlate above 0.99. The objective is nearly flat along the direction that trades them, so coefficients can differ by `1e-3` while the objective differs by `1e-8`. **Compare objectives and predictions, never coefficients**, unless the design matrix is well conditioned.
3. **The regularization convention.** scikit-learn minimises `C * sum_i loss_i + 0.5 ||w||^2`; most textbooks minimise `mean_i loss_i + (lambda/2) ||w||^2`. They have the same minimiser only if you set `lambda = 1/(n*C)`. Getting this wrong is the single most common cause of "my implementation does not match sklearn".
4. **The intercept.** scikit-learn does not penalise it. A naive implementation that appends a column of ones and penalises the whole vector produces a genuinely different model, and the difference grows as `alpha` grows.

### `n_jobs`: two measurements that point in opposite directions

`n_jobs=-1` is not free. `joblib` spawns worker processes (the `loky` backend), pickles the estimator and the data to each, and collects results. Measured on the same 11-core M3 Pro, scikit-learn 1.9.0:

**Cheap fits — a 5-point `C` grid, 5-fold, logistic regression on 8,000 x 60:**

| `n_jobs` | wall clock |
| --- | --- |
| 1 | **0.51 s** |
| 4 | 6.66 s |
| −1 | 12.27 s |

**Expensive fits — a 4-point `n_estimators` grid, 3-fold, random forest on 8,000 x 40:**

| `n_jobs` | wall clock | speed-up |
| --- | --- | --- |
| 1 | 25.36 s | 1.0x |
| 4 | 13.39 s | 1.9x |
| −1 | 12.67 s | **2.0x** |

Two lessons that are easy to state and constantly ignored.

- **`n_jobs=-1` made the cheap grid 24x slower.** Each of the 25 fits takes about 20 ms; process startup plus data pickling is far more than that. The rule of thumb that matches this measurement: parallelise only when a single fit exceeds roughly **1 second**.
- **Even on expensive fits, 11 cores bought 2.0x, not 11x.** Random forests are already internally threaded, so the outer processes fight the inner threads for the same cores and the same memory bandwidth. Setting `n_jobs=-1` on *both* the search and the estimator is the classic oversubscription bug; scikit-learn's `threadpoolctl` integration limits the damage but does not eliminate it. Parallelise at **one** level and measure.

Memory is the other half: with the process backend, each worker gets a copy of the data. `loky` uses memory-mapping for numpy arrays above `max_nbytes` (1 MB by default) which avoids copying those, but a pandas DataFrame is pickled in full to every worker. An 8-worker search on a 2 GB DataFrame needs 16 GB it did not ask for.

### What `Pipeline.fit` actually does

The implementation is worth reading — it is about 40 lines in `sklearn/pipeline.py`.

```
Pipeline.fit(X, y):
    Xt = X
    for name, transformer in self.steps[:-1]:
        # _fit_transform_one, memoised through self.memory if set
        Xt = clone(transformer).fit_transform(Xt, y)   # <- fitted copy stored in the pipeline
    self.steps[-1][1].fit(Xt, y)
```

Three consequences that matter:

- **Cloning.** Each step is cloned before fitting, so calling `fit` twice does not accumulate state — and so the estimator objects you passed in are untouched. This is why `clone()` correctness (the "no work in `__init__`" rule) is load-bearing.
- **`memory=`.** Pass a directory and `Pipeline` caches fitted transformers on disk keyed by the step's parameters and the input data hash. On a grid that varies only `clf__C`, this skips refitting the preprocessing entirely. On the 40-fit grid above, caching cuts the preprocessing work to 5 fits instead of 40.
- **Only the last step keeps `y`-consuming semantics.** Intermediate steps get `y` passed to `fit_transform`, which is exactly how `SelectKBest` and target encoders work — and exactly why they must live inside.

### Failure modes

| Failure | Signature | Detector |
| --- | --- | --- |
| Transformer fitted outside CV | CV score far above what production shows; the gap grows with feature count | grep for `fit_transform` outside a `Pipeline`; re-run through a pipeline and diff |
| Non-converged model shipped | `ConvergenceWarning` (often filtered); unstable coefficients between refits | `assert est.n_iter_.max() < est.max_iter` in the training job |
| `clone` produces a different estimator | CV folds disagree wildly with a manual refit | `sklearn.utils.estimator_checks.check_estimator(YourTransformer())` in CI |
| Oversubscription | more cores makes it slower | set `n_jobs` at exactly one level; check `threadpoolctl.threadpool_info()` |
| Worker memory blow-up | OOM only when `n_jobs > 1` | pass numpy arrays not DataFrames to the search, or lower `max_nbytes` |
| Unseen category at serving | `ValueError: Found unknown categories` in the request path | `handle_unknown="infrequent_if_exist"`; add a serving test with a novel category |
| Column order changed upstream | silently wrong predictions, no error | `feature_names_in_` is checked for DataFrames — so pass DataFrames, not arrays, at serving time |
| Default changed on upgrade | scores shift after a dependency bump | pin exact versions; keep a golden-prediction regression test (Week 20 Module 5) |

### Papers

- **Pedregosa, F. et al. (2011), "Scikit-learn: Machine Learning in Python," JMLR 12.** *Takeaway:* the estimator/transformer contract is the library's actual contribution — a uniform interface is what makes `Pipeline`, `GridSearchCV` and every third-party estimator compose.
- **Buitinck, L. et al. (2013), "API design for machine learning software: experiences from the scikit-learn project," ECML PKDD workshop.** *Takeaway:* the "no logic in `__init__`, learned attributes end with an underscore, `fit` returns self" rules exist to make `clone` sound, which is what makes cross-validation correct.
- **Bergstra, J. & Bengio, Y. (2012), "Random Search for Hyper-Parameter Optimization," JMLR 13.** *Takeaway:* with more than a handful of hyperparameters, random search finds equal or better configurations than grid search for a fraction of the budget, because only a few dimensions usually matter.
- **Kaufman, S., Rosset, S., Perlich, C. (2011), "Leakage in Data Mining: Formulation, Detection, and Avoidance," KDD.** *Takeaway:* leakage is a property of the *process* that produced the evaluation, not of any single feature — which is precisely why a structural fix like `Pipeline` beats a checklist. Week 19 Module 4 builds on this.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| CV accuracy 0.82 on pure noise | selection or encoding fitted before cross-validation | put every fitted step in a `Pipeline` |
| Coefficients differ from a hand implementation | scikit-learn uses `C` not `lambda`, and does not penalise the intercept | set `lambda = 1/(n*C)`; exclude the intercept |
| `ConvergenceWarning` ignored for months | blanket `warnings.filterwarnings("ignore")` | filter specific categories only; assert on `n_iter_` |
| `n_jobs=-1` is slower than `n_jobs=1` | process startup dominates cheap fits | parallelise only when one fit exceeds ~1 s |
| OOM only under parallel search | each worker gets a full copy of a DataFrame | pass numpy arrays; rely on `loky` memory-mapping |
| `ValueError: Found unknown categories` in production | `OneHotEncoder(handle_unknown="error")` default | `handle_unknown="infrequent_if_exist"` plus a serving test |
| Feature names become `x0, x1, x2` | a custom transformer without `get_feature_names_out` | implement it; add `sklearn.set_config(transform_output="pandas")` |
| CV folds disagree with a manual refit | logic in `__init__` breaks `clone` | move all work to `fit`; run `check_estimator` |
| Grid search tunes nothing inside the preprocessor | wrong parameter path | use `step__substep__param`; print `model.get_params().keys()` to find it |
