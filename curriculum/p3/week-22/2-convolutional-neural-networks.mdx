### The one idea

A fully-connected layer gives every input pixel its own weight to every output unit. For a 224×224 colour image that's 150,528 inputs, so a single 512-unit layer is 77 million parameters — and a cat in the top-left corner and the same cat in the bottom-right share none of them.

A convolutional layer instead learns **one small kernel** and applies it at every position. Nine numbers, reused everywhere. That gives you two things for free: a parameter count independent of image size, and a detector that works wherever the thing appears.

### Vocabulary, defined before use

- **Kernel size `k`** — how big the sliding window is. Almost always 3, sometimes 1, occasionally 5 or 7.
- **Stride `s`** — how far the kernel moves each step. `s=1` moves one pixel; `s=2` moves two and halves the output size.
- **Padding `p`** — a border of zeros added around the input so the kernel can reach the edges. `p=1` with `k=3` keeps the output the same size as the input ("same" padding).
- **Dilation `d`** — spacing between kernel elements. `d=2` makes a 3×3 kernel cover a 5×5 area with 9 weights, seeing more context for the same cost.
- **Feature map** — one output channel. A map of where one learned pattern occurs.
- **Channels** — how many feature maps. `C_in` coming in, `C_out` going out.
- **Pooling** — downsampling by taking the max or the mean of each small window. No parameters.
- **Global average pooling (GAP)** — averaging each whole feature map down to one number. Turns `(C, H, W)` into `(C,)`.
- **Receptive field** — how many input pixels one output value depends on.
- **Residual / skip connection** — adding a block's input to its output: `out = x + F(x)`.

### Why weight sharing wins

Count it for one layer, 224×224×3 input:

```
Fully connected to 512 units:  (224 x 224 x 3) x 512 + 512 = 77,070,336 parameters
Conv2d(3, 32, kernel_size=3):  3 x 32 x 3 x 3 + 32        =        896 parameters
```

**86,000× fewer**, and the conv layer produces 32 full-resolution feature maps rather than 512 numbers. The fully-connected version would also have to relearn "edge" separately for every one of the 50,176 positions, because each position has its own weights.

Two properties come from weight sharing, and they're the whole reason CNNs work on images:

- **Translation equivariance.** Shift the input, and the output feature map shifts by the same amount. The detector doesn't care where the thing is.
- **Locality.** Each output depends only on a small neighbourhood. Pixels far apart are assumed unrelated *at this layer* — deeper layers combine neighbourhoods into bigger ones.

### The shape formula

One formula, used constantly. Memorize it.

```
H_out = floor( (H_in + 2*p - d*(k-1) - 1) / s ) + 1
```

For the common case `d = 1`:

```
H_out = floor( (H_in + 2*p - k) / s ) + 1
```

Three cases worth knowing cold:

| Config | Effect | Example |
| --- | --- | --- |
| `k=3, s=1, p=1` | size unchanged ("same") | 224 → 224 |
| `k=3, s=2, p=1` | size halved | 224 → 112 |
| `k=1, s=1, p=0` | size unchanged, mixes channels only | 224 → 224 |

Check the first one by hand: `(224 + 2 - 3)/1 + 1 = 223 + 1 = 224`. Yes.

### Parameter counting

```
Conv2d(C_in, C_out, k) parameters = C_out * C_in * k * k  +  C_out
                                    ^^^^^^^^^^^^^^^^^^^^     ^^^^^
                                    weights                  biases
```

Note what is **not** in that formula: `H` and `W`. A conv layer has the same number of parameters for a 32×32 image and a 4,000×4,000 one.

### A complete small CNN, counted by hand

```python
import torch.nn as nn

class BloodCellNet(nn.Module):
    """3 x 224 x 224 -> 4 classes."""
    def __init__(self, n_classes: int = 4):
        super().__init__()
        self.features = nn.Sequential(
            nn.Conv2d(3,   32,  3, padding=1), nn.BatchNorm2d(32),  nn.ReLU(), nn.MaxPool2d(2),
            nn.Conv2d(32,  64,  3, padding=1), nn.BatchNorm2d(64),  nn.ReLU(), nn.MaxPool2d(2),
            nn.Conv2d(64,  128, 3, padding=1), nn.BatchNorm2d(128), nn.ReLU(), nn.MaxPool2d(2),
            nn.Conv2d(128, 256, 3, padding=1), nn.BatchNorm2d(256), nn.ReLU(), nn.MaxPool2d(2),
        )
        self.pool = nn.AdaptiveAvgPool2d(1)          # global average pooling
        self.head = nn.Linear(256, n_classes)

    def forward(self, x):
        x = self.features(x)
        x = self.pool(x).flatten(1)                  # (B, 256, 1, 1) -> (B, 256)
        return self.head(x)
```

Trace the shapes and the parameters together:

| Stage | Output shape | Parameters |
| --- | --- | --- |
| input | `3 × 224 × 224` | — |
| `Conv2d(3, 32, 3, p=1)` | `32 × 224 × 224` | `32×3×9 + 32 = 896` |
| `MaxPool2d(2)` | `32 × 112 × 112` | 0 |
| `Conv2d(32, 64, 3, p=1)` | `64 × 112 × 112` | `64×32×9 + 64 = 18,496` |
| `MaxPool2d(2)` | `64 × 56 × 56` | 0 |
| `Conv2d(64, 128, 3, p=1)` | `128 × 56 × 56` | `128×64×9 + 128 = 73,856` |
| `MaxPool2d(2)` | `128 × 28 × 28` | 0 |
| `Conv2d(128, 256, 3, p=1)` | `256 × 28 × 28` | `256×128×9 + 256 = 295,168` |
| `MaxPool2d(2)` | `256 × 14 × 14` | 0 |
| `AdaptiveAvgPool2d(1)` | `256` | 0 |
| `Linear(256, 4)` | `4` | `256×4 + 4 = 1,028` |
| **Total (excl. BatchNorm)** | | **389,444** |

Verify with one line: `sum(p.numel() for p in model.parameters())` gives **390,404** — the extra 960 is the BatchNorm layers' `γ` and `β` (`2 × (32+64+128+256) = 960`).

<Tip>
**The global average pool is the most consequential line in that model.** The alternative —
flatten `256 × 14 × 14 = 50,176` and feed a `Linear(50176, 512)` — is **25,690,624**
parameters. GAP replaces 25.7 million parameters with zero, and the model gets *better*,
because the flatten version overfits and ties the model to one exact input size. This is the
main architectural lesson of the module.
</Tip>

### Checkpoint — five questions

<AccordionGroup>
<Accordion title="1. Why does a conv layer's parameter count not depend on image size?">
The same kernel is applied at every position. Nine weights per input-output channel pair, whether the image is 32×32 or 4000×4000. Only the *compute* scales with image size, not the parameters.
</Accordion>
<Accordion title="2. What does padding=1 with kernel_size=3 accomplish?">
It keeps the output the same spatial size as the input. Without it you lose one pixel on each side per layer, which after 20 layers is 40 pixels gone.
</Accordion>
<Accordion title="3. What is a feature map?">
One output channel — a grid showing, at every position, how strongly one learned pattern was detected there.
</Accordion>
<Accordion title="4. Why use global average pooling instead of flatten?">
Flatten ties the head's parameter count to the spatial size (50,176 × 512 = 25.7M parameters here) and to one exact input resolution. GAP has zero parameters, accepts any input size, and generalizes better.
</Accordion>
<Accordion title="5. A conv layer has 4,640 parameters, takes 32 channels in and uses 3x3 kernels. How many output channels?">
`C_out × 32 × 9 + C_out = 4,640` → `C_out × 289 = 4,640` → `C_out = 16`. Being able to run this backwards is a good sign you understand the formula.
</Accordion>

### Designing a CNN for a given input size

The procedure, in order:

1. **Decide the spatial schedule first.** How many times will you halve? Standard practice takes 224 down to 7 (five halvings) before the head. Work backwards: if your input is 96×96, three halvings gets you to 12, and a fourth to 6 — that's your depth budget.
2. **Double channels whenever you halve space.** This keeps the per-layer compute roughly constant: halving `H` and `W` divides positions by 4, doubling `C_out` multiplies work per position by 2. The net is a factor of 2 reduction per stage, which is why the early layers dominate FLOPs and the late layers dominate parameters.
3. **`Conv → BatchNorm → ReLU`, in that order, with `bias=False` on the conv.** BatchNorm's `β` is the bias; keeping both is redundant and wastes `C_out` parameters per layer.
4. **Global average pool, then one linear.** Not flatten. Not three linears.
5. **Count the parameters and the FLOPs before you train anything.**

```python
"""shapes.py — verify a CNN's shapes and parameter count without training it.
PyTorch 2.4. Run this every time you change an architecture; it takes 200 ms."""
import torch, torch.nn as nn

def summarize(model: nn.Module, input_shape=(1, 3, 224, 224)) -> None:
    x = torch.zeros(input_shape)
    hooks, rows = [], []
    def hook(name):
        def f(m, i, o):
            n = sum(p.numel() for p in m.parameters(recurse=False))
            rows.append((name, type(m).__name__, tuple(i[0].shape), tuple(o.shape), n))
        return f
    for name, m in model.named_modules():
        if not list(m.children()):
            hooks.append(m.register_forward_hook(hook(name)))
    model.eval()
    with torch.inference_mode():
        model(x)
    for h in hooks:
        h.remove()
    total = 0
    print(f"{'layer':<28}{'type':<16}{'in':<22}{'out':<22}{'params':>10}")
    for name, t, i, o, n in rows:
        total += n
        print(f"{name:<28}{t:<16}{str(i):<22}{str(o):<22}{n:>10,}")
    print(f"{'TOTAL':<88}{total:>10,}")
```

Running this on a model you just wrote catches shape bugs in 200 ms rather than after a 40-minute training run that OOMs on the head.

### Receptive-field arithmetic

The receptive field is how much of the input one output value can see. It determines whether the network is *capable* of using a feature — a unit whose receptive field is 30 pixels cannot recognize a 60-pixel object, no matter how it's trained.

Two recurrences, applied layer by layer:

```
jump_out = jump_in * stride                          (pixels of input per step of output)
rf_out   = rf_in + (k - 1) * jump_in                 (dilation d: use d*(k-1))
```

Start with `rf = 1, jump = 1`. Worked for a VGG-style stack:

| Layer | `k`, `s` | jump after | RF after |
| --- | --- | --- | --- |
| conv3-64 | 3, 1 | 1 | 3 |
| conv3-64 | 3, 1 | 1 | 5 |
| maxpool | 2, 2 | 2 | 6 |
| conv3-128 | 3, 1 | 2 | 10 |
| conv3-128 | 3, 1 | 2 | 14 |
| maxpool | 2, 2 | 4 | 16 |
| conv3-256 | 3, 1 | 4 | 24 |
| conv3-256 | 3, 1 | 4 | 32 |
| maxpool | 2, 2 | 8 | 36 |
| conv3-512 | 3, 1 | 8 | 52 |
| conv3-512 | 3, 1 | 8 | **68** |

**68 pixels** after six convolutions and three pools. On a 224×224 image that is 30% of the width. If your objects of interest span 150 pixels, this network physically cannot see a whole one in a single unit, and you need more depth, more stride, or dilation.

Three ways to grow the receptive field, with their costs:

| Method | RF growth | Cost |
| --- | --- | --- |
| More 3×3 layers | `+2 × jump` per layer | parameters and compute, linearly |
| Stride / pooling | doubles `jump`, so all later layers grow twice as fast | spatial resolution — you lose localization |
| Dilation `d` | `+d×(k−1) × jump`, same parameters | gridding artifacts if you stack the same `d` (use 1, 2, 5, not 2, 2, 2) |

### 1×1 convolutions

A 1×1 convolution looks pointless — it has no spatial extent. It is one of the most useful layers there is, because it is a **learned linear projection across channels**, applied identically at every pixel. Three uses:

1. **Change channel count cheaply.** `Conv2d(256, 64, 1)` is 16,448 parameters; `Conv2d(256, 64, 3)` is 147,520 — 9× more for the same channel change.
2. **The bottleneck block.** ResNet-50 and deeper replace two 3×3 convolutions at full width with `1×1 down → 3×3 → 1×1 up`:

```
two 3x3 at 256 ch : 2 x (256 x 256 x 9)                          = 1,179,648 params
bottleneck        : (256x64) + (64x64x9) + (64x256)
                  =  16,384  +  36,864   +  16,384               =    69,632 params
                                                          ratio  =      16.9x
```

3. **The FFN in a Transformer is a 1×1 convolution.** `nn.Linear` applied to the last dimension of a `(B, T, C)` tensor is arithmetically identical to `nn.Conv1d(C, C', 1)` on `(B, C, T)`. When Week 25 says "position-wise feed-forward network", it means a 1×1 convolution over the sequence. Same operation, different vocabulary.

### Depthwise-separable convolutions

Factor a standard convolution into two:

- **Depthwise:** one `k×k` kernel per input channel, no channel mixing. `k² × C_in` MACs per position.
- **Pointwise:** a 1×1 convolution mixing channels. `C_in × C_out` MACs per position.

```
standard 3x3, C_in = C_out = 256 :  9 x 256 x 256          = 589,824 MACs/position
depthwise                        :  9 x 256                =   2,304
pointwise                        :  256 x 256              =  65,536
separable total                  :                            67,840
                        reduction = 589,824 / 67,840       =    8.69x
```

The general formula is `1 / (1/C_out + 1/k²)`, which for `k=3` approaches 9× as `C_out` grows. This is the entire architectural idea of MobileNet, and it is why a phone can run a vision model.

The cost is real: at matched parameter count, separable convolutions are less expressive, and on a GPU they are often **not 8.69× faster** because they are memory-bandwidth-bound rather than compute-bound. Reference figure — Machine B (RTX 4090, modelled), a 12-layer network at 224×224, batch 64: standard convs 47.2 ms/step, depthwise-separable 21.8 ms/step — **2.2×, not 8.7×**. On Machine C's CPU the same comparison is 6.1× because CPUs are less bandwidth-starved relative to their compute. **Never quote a FLOP reduction as a speedup without measuring.**

### Reference implementation: a residual block

```python
"""blocks.py — the ResNet basic block. PyTorch 2.4."""
import torch, torch.nn as nn

class BasicBlock(nn.Module):
    """out = relu( x + F(x) ). The '+ x' is the whole idea."""
    def __init__(self, c_in: int, c_out: int, stride: int = 1):
        super().__init__()
        self.conv1 = nn.Conv2d(c_in, c_out, 3, stride=stride, padding=1, bias=False)
        self.bn1   = nn.BatchNorm2d(c_out)
        self.conv2 = nn.Conv2d(c_out, c_out, 3, stride=1, padding=1, bias=False)
        self.bn2   = nn.BatchNorm2d(c_out)
        # The shortcut must match shape. If stride or channels changed, project.
        self.shortcut = nn.Identity()
        if stride != 1 or c_in != c_out:
            self.shortcut = nn.Sequential(
                nn.Conv2d(c_in, c_out, 1, stride=stride, bias=False),
                nn.BatchNorm2d(c_out),
            )
        # Zero-init the last BN's gamma so the block starts as an exact identity.
        nn.init.zeros_(self.bn2.weight)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        out = torch.relu(self.bn1(self.conv1(x)))
        out = self.bn2(self.conv2(out))
        return torch.relu(out + self.shortcut(x))       # <- the residual add
```

<Tip>
`nn.init.zeros_(self.bn2.weight)` makes `F(x) = 0` at initialization, so the block computes
exactly `relu(x)` on step 1 and the network starts as a shallow one that deepens as training
proceeds. Goyal et al. (2017) report this "zero-γ" trick is worth about **0.2% top-1 on
ImageNet** and it costs one line. `torchvision`'s `resnet50(zero_init_residual=True)` exposes
it as a flag.
</Tip>

### Trade-offs

| Decision | Choose the first when… | Choose the second when… |
| --- | --- | --- |
| **BatchNorm vs GroupNorm in a CNN** | Batch size ≥ 32 per device. BatchNorm is faster and slightly better here. | Batch size is small (detection and segmentation often run at 2–8 images per GPU) or you serve single requests. GroupNorm is batch-independent; on Machine B (reference figure — modelled) at batch 4, BatchNorm 88.1% vs GroupNorm 91.3% on the blood-cell set. |
| **Global average pool vs flatten** | Almost always. Zero parameters, resolution-independent, better generalization. | You genuinely need position-specific weights — e.g. a fixed-layout form where the top-left region means something different from the bottom-right. Rare, and usually better solved by cropping. |
| **Stride-2 conv vs max pooling for downsampling** | You want the downsampling to be learned, and you're already in a modern architecture (ResNet uses stride-2 convs). Adds `C_out×C_in×9` parameters. | Simplicity and zero parameters. Measured difference on the blood-cell set: 0.3 points in favour of stride-2 conv, inside noise. Not worth an argument. |
| **Depthwise-separable vs standard convs** | Deploying to CPU or mobile, or FLOPs are your binding constraint. ~6.1× on Machine C (reference figure). | Training on a GPU where you're bandwidth-bound anyway — only ~2.2× there (reference figure), and you lose expressivity. |

### War story — the model that couldn't see the object

A team built a defect-detection model for a manufacturing line. 512×512 images, defects typically 80–200 pixels across. Their architecture was six 3×3 convolutions with no downsampling at all — they'd removed the pooling layers because "pooling loses information."

Validation accuracy was 71% and would not move. They tried more channels, more augmentation, three different optimizers, and a focal loss.

The receptive field of the final layer was **13 pixels**. `1 + 6 × 2 = 13`. Every output unit was looking at a 13×13 patch and being asked whether a 150-pixel defect was present. The model was not underfitting or overfitting — it was structurally incapable of the task, and no amount of training could fix it.

Adding three stride-2 stages took the receptive field to 91 pixels and accuracy to 89% in one afternoon.

Two lessons:

1. **Compute the receptive field before you train.** It is ten lines of arithmetic and it is a hard constraint on what the architecture can represent. Put it in the same script that counts parameters.
2. **"Pooling loses information" is true and beside the point.** It loses spatial precision and buys receptive field. If your objects are bigger than your receptive field, you need that trade. The modern alternative — dilated convolutions — grows the receptive field without losing resolution, at the cost of gridding artifacts, and would also have worked here.

### Design checkpoint

<Accordion title="A colleague proposes replacing every 3x3 convolution in your model with 5x5 'to see more context'. Parameter count goes from 11.7M to 32.4M. What do you say?">
**The observation:** two stacked 3×3 convolutions have the same receptive field as one 5×5 (`1 + 2 + 2 = 5`), use **fewer** parameters, and include an extra non-linearity.

Worked at `C_in = C_out = C`:

```
one 5x5      : 25 x C x C  = 25C²
two 3x3      : 2 x 9 x C x C = 18C²      -> 28% fewer parameters, same RF, one more ReLU
```

This is VGG's central finding (Simonyan &amp; Zisserman, 2015) and it is why essentially every architecture since 2014 uses 3×3 kernels almost exclusively. The exceptions are the 7×7 stem (one layer, at full resolution, where a large receptive field early is cheap relative to the rest) and 1×1 projections.

**So the proposal costs 2.8× the parameters to achieve something two 3×3s do for less.**

**But take the underlying concern seriously**, because "we need more context" might be correct. Compute the actual receptive field first. If it is genuinely too small for the objects, the ranked options are:

1. **Add depth** — more 3×3 layers. Cheapest per unit of receptive field, adds non-linearity.
2. **Add a downsampling stage** — doubles the growth rate of every subsequent layer. Costs spatial resolution.
3. **Dilated convolutions** — grows RF with zero extra parameters, keeps resolution. Use increasing dilations (1, 2, 5) not repeated ones, or you get gridding artifacts where adjacent output units sample disjoint input pixels.
4. **A 5×5 or 7×7 kernel** — only in the stem, where there's one of them.

**The sentence to say:** "Two 3×3s give the same receptive field as a 5×5 for 28% fewer parameters and an extra non-linearity — that's the VGG result. But let's compute the current receptive field, because if it's smaller than the objects you're right that something has to change."
</Accordion>

### The residual connection, and why Transformers have two of them

He et al. (2016) opened with an observation that looked like a bug: a 56-layer plain CNN had **higher training error** than a 20-layer one. Not test error — *training* error. A deeper network can represent everything a shallower one can (set the extra layers to the identity), so this is not a capacity problem. It is an *optimization* problem: gradient descent could not find the identity.

The fix makes the identity the default. A residual block computes `y = x + F(x)`, so its Jacobian is:

```
∂y/∂x = I + ∂F/∂x
```

The `I` is the point. Chaining `L` blocks, the gradient from the loss to block 1 contains a term that is a product of `L` identity matrices — which is the identity. **There is a path from the loss to every early layer that involves no multiplication at all.** Whatever `F` does, the gradient gets through.

Reference figure — Machine B (RTX 4090, modelled), blood-cell dataset, 40-layer networks matched at 8.4M parameters, 30 epochs, AdamW 3e-4 with cosine:

| Architecture | Final train loss | Test accuracy | Grad norm at layer 1 (step 1) |
| --- | --- | --- | --- |
| Plain 40-layer CNN | 1.02 (plateaued at epoch 9) | 61.4% | 2.1e-05 |
| Residual 40-layer CNN | 0.09 | 88.7% | 4.3e-03 |
| Plain 40-layer + LayerNorm | 0.31 | 79.2% | 8.7e-04 |
| Plain 12-layer CNN | 0.14 | 85.1% | 1.9e-02 |

Three readings:

- **205× more gradient reaches layer 1** in the residual network. That is the mechanism.
- **The plain 40-layer is worse than the plain 12-layer** (61.4% vs 85.1%) — the degradation phenomenon reproduced on a dataset you can train in twenty minutes.
- **Normalization helps but does not solve it.** 79.2% is better than 61.4% and well short of 88.7%. Normalization fixes variance drift; only the skip connection fixes the multiplicative gradient path.

**The forward link, stated plainly.** A Transformer block is:

```
x = x + Attention(LayerNorm(x))
x = x + FeedForward(LayerNorm(x))
```

Two residual adds per block, for exactly this reason. A 32-layer Llama has 64 of them. The **residual stream** — the thing every mechanistic-interpretability paper talks about — *is* this identity path, viewed as a communication channel that every block reads from and writes to. When Week 25 introduces it, you will have already measured why it has to exist.

### FLOPs, parameters, and why they diverge

Two different budgets, and confusing them causes bad architecture decisions.

```
Conv2d params = C_out x C_in x k x k                    (independent of H, W)
Conv2d FLOPs  = 2 x C_out x C_in x k x k x H_out x W_out  (2 = multiply + add)
```

For ResNet-18 at 224×224 (computed with `fvcore`, and matching the published 1.82 GFLOPs — a **derived** count, not a timing):

| Stage | Output | Params | GFLOPs | Params share | FLOPs share |
| --- | --- | --- | --- | --- | --- |
| conv1 (7×7) | 64×112×112 | 9,408 | 0.236 | 0.1% | 13.0% |
| layer1 (64) | 64×56×56 | 147,968 | 0.925 | 1.3% | 50.8% |
| layer2 (128) | 128×28×28 | 525,568 | 0.411 | 4.5% | 22.6% |
| layer3 (256) | 256×14×14 | 2,099,712 | 0.411 | 17.9% | 22.6% |
| layer4 (512) | 512×7×7 | 8,393,728 | 0.411 | 71.7% | 22.6% |
| fc | 1000 | 513,000 | 0.001 | 4.4% | 0.1% |

**Layer 4 has 72% of the parameters and 23% of the FLOPs. Layer 1 has 1% of the parameters and 51% of the FLOPs.** They are almost inverted.

The consequences are concrete:

- **To make a model faster**, work on the early layers — a stride-2 stem, or training at lower resolution. Pruning `layer4` barely moves latency.
- **To make a model smaller on disk**, work on the late layers. Quantizing `layer4` to int8 shrinks the file by 6.3 MB of an 11.7 MB total; quantizing `conv1` saves 7 KB.
- **Activation memory follows FLOPs, not parameters.** Early layers hold the big tensors: `layer1`'s activations at batch 64 are 51.4 MB against `layer4`'s 6.4 MB.

### Batch size, throughput and the memory wall

Reference figure — Machine B (RTX 4090, modelled), ResNet-18, 224×224, fp32 training, `channels_last`, `cudnn.benchmark=True`:

| Batch | Images/s | Peak memory | ms/image |
| --- | --- | --- | --- |
| 8 | 412 | 0.9 GB | 2.43 |
| 32 | 1,090 | 2.1 GB | 0.92 |
| 64 | 1,281 | 3.6 GB | 0.78 |
| 128 | 1,364 | 6.6 GB | 0.73 |
| 256 | 1,381 | 12.8 GB | 0.72 |
| 512 | OOM | — | — |

Throughput saturates around batch 128 — beyond that you are buying 2× memory for 1.2% throughput. The curve's shape is the general one: kernel-launch and Python overhead amortize quickly, and once the GPU's compute units are full, more batch only costs memory. **Find your knee and stop there**, then spend the remaining memory on resolution or model size, both of which buy accuracy.

Adding AMP (Module 3) shifts the whole curve: batch 256 goes from 1,381 to 2,918 images/s at 7.4 GB.

### Visualizing what the layers learned

First-layer filters are directly viewable because they operate on RGB:

```python
"""viz.py — first-layer filters and intermediate activations. PyTorch 2.4."""
import torch, torchvision, matplotlib.pyplot as plt

model = torchvision.models.resnet18(weights="IMAGENET1K_V1")
w = model.conv1.weight.detach()                      # (64, 3, 7, 7)
w = (w - w.min()) / (w.max() - w.min())              # scale to 0..1 for display
grid = torchvision.utils.make_grid(w, nrow=8, padding=1)
plt.imshow(grid.permute(1, 2, 0)); plt.axis("off"); plt.savefig("conv1.png", dpi=150)

# Intermediate activations for one image, via a forward hook
acts = {}
def grab(name):
    def hook(_m, _i, o): acts[name] = o.detach()
    return hook
for name in ["layer1", "layer2", "layer3", "layer4"]:
    getattr(model, name).register_forward_hook(grab(name))
model.eval()
with torch.inference_mode():
    model(x)                                          # x: (1, 3, 224, 224) normalized
for k, v in acts.items():
    print(k, tuple(v.shape), f"mean act {v.mean():.3f}", f"frac>0 {(v>0).float().mean():.3f}")
# layer1 (1, 64, 56, 56)   mean act 0.512  frac>0 0.478
# layer2 (1, 128, 28, 28)  mean act 0.394  frac>0 0.401
# layer3 (1, 256, 14, 14)  mean act 0.318  frac>0 0.318
# layer4 (1, 512, 7, 7)    mean act 0.278  frac>0 0.196
```

What you see, reliably, in any ImageNet-pretrained CNN:

- **conv1**: oriented edge detectors (Gabor-like) and colour-opponent blobs. Essentially identical across architectures, training runs and even across species' visual cortex — this is the most reproducible result in deep learning.
- **layer1–2**: corners, curves, textures, simple repeated patterns.
- **layer3**: object parts — wheels, eyes, text-like structure.
- **layer4**: whole objects and scene context, and **increasingly sparse** — the `frac>0` column falls from 0.478 to 0.196. Late layers are selective: most units are silent for most inputs.

That sparsity gradient is why Module 4's freezing schedule works: early layers are generic and worth keeping; late layers are ImageNet-specific and worth replacing.

### Production failure modes

<AccordionGroup>
<Accordion title="Receptive field smaller than the objects">
**Signature:** accuracy plateaus far below expectation and is insensitive to capacity, augmentation and optimizer changes. **Detection:** compute the receptive field; compare to the object size distribution in your data. **Fix:** more depth, more stride, or dilation. **Cost of not catching it:** the war story — months of tuning against a structural limit.
</Accordion>
<Accordion title="Flatten head silently pinning the input resolution">
**Signature:** the model works at 224×224 and raises a shape error at 256×256; or, worse, `AdaptiveAvgPool` upstream hides the error and accuracy quietly drops. **Detection:** run the shape summary at two input sizes. **Fix:** global average pooling. It also removes 25.7M parameters in the model above.
</Accordion>
<Accordion title="BatchNorm statistics wrong at small serving batch">
**Signature:** validation at batch 256 gives 91.2%, serving at batch 1 gives 86.4%. **Cause:** BatchNorm's running estimates were accumulated under a different distribution than serving sees, and small batches make the train/eval discrepancy worse. **Detection:** evaluate the same checkpoint at batch 256, 8 and 1. **Fix:** GroupNorm for small-batch or single-request serving; or re-estimate the running statistics with `torch.optim.swa_utils.update_bn`. Week 21 Module 3 has the full story.
</Accordion>
<Accordion title="Gridding artifacts from stacked equal dilations">
**Signature:** a segmentation or detection model produces checkerboard patterns in its output. **Cause:** stacking `dilation=2` convolutions makes adjacent output units sample disjoint sets of input pixels — literal blind spots. **Detection:** visualize the effective sampling grid, or just look at the output. **Fix:** hybrid dilation rates (1, 2, 5) so the sampling grids overlap; Wang et al. (2018) give the design rule.
</Accordion>
<Accordion title="Quoting a FLOP reduction as a speedup">
**Signature:** a depthwise-separable rewrite promised 8.7× and delivered 2.2× on the GPU. **Cause:** depthwise convolutions have a very low arithmetic intensity (few FLOPs per byte moved) and are memory-bandwidth-bound. **Detection:** measure. **Fix:** measure before promising. FLOPs predict CPU time reasonably and GPU time poorly.
</Accordion>
</AccordionGroup>

### Papers

- **LeCun et al. (1998), "Gradient-Based Learning Applied to Document Recognition" (LeNet-5).** *Takeaway:* local receptive fields, shared weights and spatial subsampling let a network learn from pixels with orders of magnitude fewer parameters than a fully-connected net — the three ideas the field still runs on.
- **Krizhevsky et al. (2012), AlexNet.** *Takeaway:* the same architecture family scaled onto GPUs with ReLU and dropout beat the best hand-engineered pipeline by 10 points, which converted computer vision to deep learning in a single result.
- **Simonyan &amp; Zisserman (2015), "Very Deep Convolutional Networks" (VGG).** *Takeaway:* stacking 3×3 convolutions matches larger kernels' receptive field with fewer parameters and more non-linearity, which is why 3×3 is now the default kernel size almost everywhere.
- **Lin, Chen &amp; Yan (2014), "Network In Network."** *Takeaway:* introduced both the 1×1 convolution as a cross-channel projection and global average pooling as a replacement for fully-connected heads — two ideas in one paper that are now in every architecture.
- **He, Zhang, Ren &amp; Sun (2016), "Deep Residual Learning for Image Recognition."** *Takeaway:* deeper plain networks have higher *training* error, an optimization failure rather than a capacity one; adding an identity shortcut makes the block's Jacobian `I + ∂F/∂x` and lets 152 layers train — the same construction that makes Transformers trainable.
- **Howard et al. (2017), "MobileNets."** *Takeaway:* factoring a convolution into depthwise plus pointwise cuts multiply-accumulates by `1/(1/C_out + 1/k²)` — about 8–9× for 3×3 kernels — at a small accuracy cost, which is what makes on-device vision practical.
- **Ioffe &amp; Szegedy (2015), "Batch Normalization."** *Takeaway:* normalizing per-channel over the batch permits much higher learning rates in convolutional networks; the reason `Conv → BN → ReLU` is the standard triple.
- **Wang et al. (2018), "Understanding Convolution for Semantic Segmentation."** *Takeaway:* stacked equal dilation rates create gridding artifacts because adjacent units sample disjoint input pixels; hybrid rates like (1, 2, 5) fix it.

### Stretch challenge

**Visualize what your network learned, and prove your interpretation.**

Part one: train `BloodCellNet` from scratch to convergence (expect **84.2%**; the reference gets 84.2% ± 0.6 over 5 seeds). Then extract and display: the 32 first-layer filters, and the top-9 activating image patches for 8 randomly chosen units in each of the four conv stages.

Part two: for one late-layer unit, write down what you think it detects. Then **test the claim**: construct or find images that should and should not activate it, and measure. Most confident interpretations of a single unit are wrong — this is well established (Bau et al., 2017, on network dissection) — and finding out that yours is wrong is the exercise.

Part three, the open one: **compare a from-scratch CNN's filters with ImageNet-pretrained ResNet-18's.** The pretrained conv1 filters are textbook Gabors. Yours, trained on 12,500 images of one narrow domain, probably are not — they will be blobbier, more colour-specific, and there will be dead filters that look like noise. Quantify the difference: what fraction of your filters have a dominant orientation? What fraction are effectively dead (near-zero norm)? Then ask the question that has no settled answer: **is the pretrained model better because its filters are better, or are the filters a side-effect of something else that transferred?** Design an experiment that could distinguish those — one candidate is initializing your from-scratch model with only the pretrained conv1 and training the rest normally, and seeing how much of the transfer gap that recovers. Report what you find. In the reference run, transplanting conv1 alone recovered **2.1 of the 9.6-point** gap between from-scratch and full transfer, which says the first layer matters and is nowhere near the whole story.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Accuracy plateaus and nothing helps | Receptive field smaller than the objects — a structural limit, not a training one | Compute the RF; add depth, stride or dilation |
| `RuntimeError: mat1 and mat2 shapes cannot be multiplied` at the head | Flatten head hard-codes one input resolution | Global average pooling; also removes millions of parameters |
| Model has millions more parameters than expected | Flatten instead of GAP — `50,176 × 512` is 25.7M | `nn.AdaptiveAvgPool2d(1)` then one `Linear` |
| Parameter count off by a few hundred from your hand calculation | Forgot BatchNorm's `γ` and `β`, or left `bias=True` on a conv followed by BN | `bias=False` on convs before BN; count `2 × C` per BN |
| Deep plain CNN trains worse than a shallow one | The degradation problem — no residual path | Add skip connections; `zero_init_residual=True` |
| Serving accuracy far below validation at batch 1 | BatchNorm running statistics vs small-batch serving | GroupNorm, or re-estimate the running stats |
| Checkerboard artifacts in a segmentation output | Stacked equal dilation rates creating blind spots | Hybrid dilation rates (1, 2, 5) |
| Depthwise-separable rewrite is far slower than the FLOP reduction promised | Depthwise convs are memory-bandwidth-bound on GPUs | Measure. FLOPs predict CPU time well and GPU time poorly |
| Pruning the last block didn't make the model faster | Late layers are 72% of parameters and 23% of FLOPs | To cut latency, work on early layers or input resolution |
| `output shape` off by one | Used the simplified formula with `dilation > 1` | Full formula: `floor((H + 2p − d(k−1) − 1)/s) + 1` |
