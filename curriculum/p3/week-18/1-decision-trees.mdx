### Twelve rows, one question

| --- | --- | --- | --- |

| 2 | 1 | 52 | 1 |
| 3 | 1 | 31 | 1 |
| 4 | 1 | 44 | 0 |
| 5 | 1 | 29 | 1 |
| 6 | 1 | 60 | 1 |
| 7 | 0 | 23 | 0 |
| 8 | 0 | 55 | 1 |
| 9 | 0 | 38 | 0 |
| 10 | 0 | 41 | 0 |
| 11 | 0 | 27 | 0 |
| 12 | 0 | 33 | 1 |

You are allowed exactly one question. Which one?

### Gini impurity: a number for "how mixed"

**Impurity** measures how mixed the labels in a group are. Pure (all one class) should score 0; a 50/50 mix should score highest. **Gini impurity** for two classes is:

```
Gini(group) = 2 * p * (1 - p)        where p is the fraction of 1s
```

- All repaid (`p = 1`): `2 * 1 * 0 = 0`. Pure.
- Half and half (`p = 0.5`): `2 * 0.5 * 0.5 = 0.5`. Maximally mixed.
- 7 of 12 repaid (`p = 0.5833`): `2 * 0.5833 * 0.4167 = 0.4861`.

That last one is our starting point — the **parent impurity** of all 12 rows.

<Info>
The general form for `K` classes is `Gini = 1 - sum_k p_k^2`. The two-class version above is the same thing: `1 - p^2 - (1-p)^2 = 2p(1-p)`. The alternative, **entropy**, is `-sum_k p_k log2(p_k)`. They almost always pick the same splits; Gini is the default because it avoids a logarithm.
</Info>

### Scoring a split

A split sends rows left and right. Its score is the **weighted average impurity of the children**, weighted by how many rows each got. The **gain** is how much lower that is than the parent.

Try `income_high == 1` (rows 1–6 left, 7–12 right):

```
left  = [1,1,1,0,1,1]   6 rows, p = 5/6 = 0.8333   Gini = 2 * 0.8333 * 0.1667 = 0.2778
right = [0,1,0,0,0,1]   6 rows, p = 2/6 = 0.3333   Gini = 2 * 0.3333 * 0.6667 = 0.4444

weighted = (6/12) * 0.2778 + (6/12) * 0.4444 = 0.3611
gain     = 0.4861 - 0.3611 = +0.1250
```

Now try `age <= 35`:

```
left  = [1,1,1,0,0,1]   6 rows, p = 4/6 = 0.6667   Gini = 0.4444
right = [1,0,1,1,0,0]   6 rows, p = 3/6 = 0.5000   Gini = 0.5000   (rows 2,4,6,8,9,10)
weighted = 0.4722       gain = +0.0139
```

And `age <= 40`: weighted `0.4857`, gain `+0.0004` — essentially nothing.

| Split | left Gini | right Gini | weighted | gain |
| --- | --- | --- | --- | --- |
| **`income_high == 1`** | 0.2778 | 0.4444 | **0.3611** | **+0.1250** |
| `age <= 35` | 0.4444 | 0.5000 | 0.4722 | +0.0139 |
| `age <= 40` | 0.4898 | 0.4800 | 0.4857 | +0.0004 |

`income_high` wins by nine times the margin. And that is exactly what scikit-learn picks:

### How the algorithm searches

For a numeric feature there are not infinitely many candidate splits. Sort the values; the only cut points worth trying are the midpoints between consecutive *distinct* values. With `n` rows that is at most `n-1` candidates per feature. So the search at one node is:

```
for each feature j:
    sort the rows by feature j
    for each midpoint between consecutive distinct values:
        compute weighted child impurity
keep the (feature, threshold) with the largest gain
```

Then recurse on each child. Stop when a node is pure, or too small, or you hit a depth limit.

Two consequences worth stating explicitly, because they are why trees are so easy to use:

- **Scaling does nothing.** The algorithm only ever compares values to a threshold, so multiplying a feature by a million changes the thresholds by a million and nothing else. Measured: a tree on `load_breast_cancer` scores 0.9064; the same tree with feature 0 multiplied by `1e6` scores **0.9064**. Identical.
- **Monotone transforms do nothing.** `log(x)`, `sqrt(x)` and `x` produce the same tree, because they preserve order.

### Growing it, and watching it overfit

```python
# scikit-learn 1.9.0
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split
from sklearn.tree import DecisionTreeClassifier

X, y = load_breast_cancer(return_X_y=True)
Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.3, random_state=0, stratify=y)

for d in (1, 2, 3, 5, 8, 12, None):
    t = DecisionTreeClassifier(max_depth=d, random_state=0).fit(Xtr, ytr)
    print(f"max_depth={str(d):<5} leaves {t.get_n_leaves():>3}  "
          f"train {t.score(Xtr, ytr):.4f}  test {t.score(Xte, yte):.4f}")
```

```
max_depth=1     leaves   2  train 0.9322  test 0.8889
max_depth=2     leaves   4  train 0.9422  test 0.9064
max_depth=3     leaves   8  train 0.9799  test 0.9006
max_depth=5     leaves  15  train 0.9975  test 0.9123
max_depth=8     leaves  16  train 1.0000  test 0.9064
max_depth=12    leaves  16  train 1.0000  test 0.9064

```

This is the Week 17 Module 4 story with a different model. Training accuracy climbs to a perfect 1.0000 and stays there — the tree has carved out a region for every training point. Test accuracy peaks at depth 5 (0.9123) and then *falls*. The tree stops growing at 16 leaves because by then every leaf is pure; `max_depth=8` and `max_depth=None` are the same tree.

### Line by line

- `max_depth` caps how many questions deep the tree can go. Depth 1 is a single question — a **decision stump**.
- `get_n_leaves()` counts the terminal boxes. Each leaf is one prediction rule.
- Train accuracy hitting exactly 1.0000 at depth 8 means the tree is memorising. In Week 17's language, its compression ratio has gone to 1.
- The test column moves by less than 1.5 points across the whole table. Trees are not very *accurate*; they are readable. That trade is the entire reason M2 and M3 exist.

### Checkpoint

<AccordionGroup>
  <Accordion title="1. Can Gini impurity exceed 0.5 for two classes?">
  No. `2p(1-p)` is maximised at `p = 0.5` where it equals 0.5. For `K` classes the maximum is `1 - 1/K`.
  </Accordion>
  <Accordion title="2. Why can't a split have negative gain?">
  Because the algorithm only keeps the best candidate, and "do not split" always scores gain 0. In fact for Gini and entropy the weighted child impurity is never above the parent's — splitting cannot increase impurity — so gain is always at least 0.
  </Accordion>
  <Accordion title="3. Does a tree need one-hot encoding for a categorical feature?">
  scikit-learn's `DecisionTreeClassifier` needs numbers, so yes in practice. But the algorithm itself does not: it needs an order, and for an unordered category a proper implementation would search subsets. LightGBM and CatBoost do exactly that natively (Module 3). One-hot encoding a 50-category feature for a tree gives you 50 weak binary splits instead of one strong multi-way one, and it measurably hurts.
  </Accordion>
  <Accordion title="4. What is the prediction at a leaf?">
  For classification, the majority class of the training rows that landed there — and `predict_proba` returns their class proportions. For regression, their mean. That is why a regression tree's predictions are always a *step function*: there are only as many distinct outputs as there are leaves.
  </Accordion>
  <Accordion title="5. Two features are perfectly correlated. What does the tree do?">
  It picks one, essentially arbitrarily, and the other then looks useless. Unlike a linear model, the coefficient mass does not get shared — it goes entirely to whichever one won the tie. This is the root of the feature-importance problems in Module 2.
  </Accordion>
</AccordionGroup>

### CART, implemented

The whole algorithm is about 70 lines. Writing it once removes all the mystery from the next three modules.

```python
# pip install "numpy==2.5.2" "scikit-learn==1.9.0"
from __future__ import annotations
from dataclasses import dataclass
import numpy as np


@dataclass
class Node:
    feature: int | None = None
    threshold: float | None = None
    left: "Node | None" = None
    right: "Node | None" = None
    value: np.ndarray | None = None      # class counts at this node


class CART:
    """Binary CART classifier, Gini criterion, exhaustive best-split search."""

    def __init__(self, max_depth: int | None = None, min_samples_split: int = 2,
                 min_samples_leaf: int = 1):
        self.max_depth = max_depth
        self.min_samples_split = min_samples_split
        self.min_samples_leaf = min_samples_leaf

    @staticmethod
    def _gini(counts: np.ndarray) -> float:
        n = counts.sum()
        if n == 0:
            return 0.0
        p = counts / n
        return float(1.0 - (p * p).sum())

    def _best_split(self, X, y):
        n, p = X.shape
        parent = np.bincount(y, minlength=self.n_classes_).astype(float)
        parent_imp = self._gini(parent)
        best = (0.0, None, None)                       # (gain, feature, threshold)
        for j in range(p):
            order = np.argsort(X[:, j], kind="mergesort")   # stable sort: deterministic ties
            xs, ys = X[order, j], y[order]
            left = np.zeros(self.n_classes_)
            right = parent.copy()
            for i in range(n - 1):
                # move row i from the right child to the left child: O(1) update
                left[ys[i]] += 1
                right[ys[i]] -= 1
                if xs[i] == xs[i + 1]:                 # cannot cut between equal values
                    continue
                nl, nr = i + 1, n - i - 1
                if nl < self.min_samples_leaf or nr < self.min_samples_leaf:
                    continue
                gain = parent_imp - (nl * self._gini(left) + nr * self._gini(right)) / n
                if gain > best[0] + 1e-12:
                    best = (gain, j, (xs[i] + xs[i + 1]) / 2.0)
        return best

    def _build(self, X, y, depth):
        counts = np.bincount(y, minlength=self.n_classes_).astype(float)
        node = Node(value=counts)
        if ((self.max_depth is not None and depth >= self.max_depth)
                or len(y) < self.min_samples_split
                or self._gini(counts) == 0.0):
            return node
        gain, j, thr = self._best_split(X, y)
        if j is None or gain <= 0.0:
            return node
        mask = X[:, j] <= thr
        node.feature, node.threshold = j, thr
        node.left = self._build(X[mask], y[mask], depth + 1)
        node.right = self._build(X[~mask], y[~mask], depth + 1)
        return node

    def fit(self, X, y):
        X = np.asarray(X, float)
        self.classes_, y_idx = np.unique(np.asarray(y), return_inverse=True)
        self.n_classes_ = len(self.classes_)
        self.root_ = self._build(X, y_idx, 0)
        return self

    def _one(self, x, node):
        while node.feature is not None:
            node = node.left if x[node.feature] <= node.threshold else node.right
        return node.value

    def predict_proba(self, X):
        out = np.stack([self._one(x, self.root_) for x in np.asarray(X, float)])
        return out / out.sum(1, keepdims=True)

    def predict(self, X):
        return self.classes_[self.predict_proba(X).argmax(1)]
```

The one non-obvious optimisation is the **incremental class-count update**. Naively, scoring `n-1` candidate splits per feature costs `O(n)` each, so `O(n^2)` per feature. By sorting once and moving one row at a time from the right child to the left, each candidate is an `O(1)` update, so the whole feature costs `O(n log n)` for the sort plus `O(n)` for the scan. Total per node: `O(p n log n)`. That is exactly what scikit-learn's Cython `BestSplitter` does, and it is why a tree on 200,000 rows takes seconds rather than hours.

### Matching scikit-learn — and the surprise

```
dataset        max_depth=2   max_depth=3   max_depth=None
iris             1.0000        1.0000         0.9778
wine             1.0000        0.9259         0.8704
breast_cancer    1.0000        0.9942         0.9883
```

(Fraction of test predictions identical to `DecisionTreeClassifier(max_depth=d, random_state=0)`.)

Shallow trees match **exactly**. Deeper trees drift. The obvious conclusion is that the implementation has a bug. It does not. Run scikit-learn against *itself*:

```python
# scikit-learn 1.9.0 — splitter="best", so this should be deterministic. It is not.
preds = [DecisionTreeClassifier(max_depth=3, random_state=s).fit(Xtr, ytr).predict(Xte)
         for s in range(20)]
print("distinct prediction vectors:", len({tuple(p) for p in preds}))
```

| dataset | depth | distinct root splits over 20 seeds | mean agreement with seed 0 | distinct prediction vectors |
| --- | --- | --- | --- | --- |
| wine | 3 | 1 | 0.9667 | **10** |
| wine | None | 1 | 0.9204 | **15** |
| breast cancer | 3 | 1 | 0.9789 | 7 |
| breast cancer | None | 1 | 0.9719 | **19** |

**Twenty seeds of the same deterministic-sounding algorithm produce nineteen different trees.** The root split is always identical; the divergence is deeper down. The cause is that scikit-learn permutes the feature order before scanning at each node (`random_state` is used even with `splitter="best"`), so whenever two candidate splits have the same gain — which happens constantly in the small, nearly-pure nodes near the bottom — the winner is decided by that permutation.

So "does my CART match scikit-learn" is not a well-posed question below the first few levels. The well-posed version is: **does it match at depths where there are no ties, and does it agree with scikit-learn about as well as scikit-learn agrees with itself?** Our 0.9259 on `wine` at depth 3 sits just below scikit-learn's own 0.9667 mean self-agreement, which is the right ballpark.

### Instability, measured

Flip **one** training label out of 398 and refit:

```python
flips = []
base = DecisionTreeClassifier(random_state=0).fit(Xtr, ytr)
b = base.predict(Xte)
for k in range(30):
    yp = ytr.copy()
    i = np.random.default_rng(k).integers(len(yp))
    yp[i] = 1 - yp[i]
    flips.append((DecisionTreeClassifier(random_state=0).fit(Xtr, yp).predict(Xte) != b).mean())
print(np.mean(flips), np.max(flips))
```

| Model | mean % of test predictions that change | max |
| --- | --- | --- |
| Single decision tree | **3.78%** | 6.43% |
| 200-tree random forest | **0.37%** | — |

One label in 398 — a quarter of one per cent of the training data — moves nearly 4% of the test predictions. The forest, which you will build in Module 2, cuts that by **10.2x**. This is the entire argument for ensembling stated as one measurement, and it is why the next module exists.

Note also what did *not* change: the root split was identical in 30 out of 30 trials. Trees are stable at the top and chaotic at the bottom, which is why depth-limited trees are much more reproducible than fully-grown ones.

### Trade-offs

| Decision | Choose the first when… | Choose the second when… |
| --- | --- | --- |
| **`max_depth`** vs **`min_samples_leaf`** | you need a hard bound on inference latency or on how many rules a human must read | you care about statistical reliability per leaf — usually the better default, since a leaf built from 3 rows is untrustworthy at any depth |
| **Gini** vs **entropy** | default; slightly cheaper (no logarithm) | you want the information-theoretic reading, or you are matching a textbook. They pick the same split the overwhelming majority of the time |
| **Pre-pruning** (depth/leaf limits) vs **cost-complexity post-pruning** (`ccp_alpha`) | you want one fit and one knob | you want the optimal subtree for a given complexity penalty; `cost_complexity_pruning_path` gives you the whole path in one fit |
| **A single tree** vs **an ensemble** | a human must read and sign off on the logic; you need microsecond inference; the dataset is tiny | you want accuracy — the ensemble wins by a wide margin on every dataset in this week |
| **One-hot** vs **native categorical** | your library needs numbers and cardinality is under ~10 | cardinality is high; use `HistGradientBoosting`, LightGBM or CatBoost, which split on category subsets directly |

### Extracting rules for stakeholders

```python
from sklearn.tree import export_text
names = list(load_breast_cancer().feature_names)
print(export_text(DecisionTreeClassifier(max_depth=3, random_state=0).fit(Xtr, ytr),
                  feature_names=names, decimals=2))
```

Two things to do before showing that to anyone outside the team:

1. **Report the leaf sizes**, not just the rules. A rule supported by 4 training rows should be labelled as such. `tree_.n_node_samples` and `tree_.value` give you both.
2. **Report the tree's stability.** Rerun the fit on 20 bootstrap resamples and report how often each rule survives. A rule that appears in 3 of 20 refits is not a finding, it is noise, and presenting it as policy is how a tree becomes a liability.

### War story: the underwriting tree that changed its mind every month

A lending team shipped a `max_depth=6` decision tree specifically because Compliance needed readable rules, and published the rule list in a monthly model report. It worked, and it was popular — the underwriters liked being able to argue with it.

Then a quarterly report noticed that the rule "reject if `months_at_address < 7` and `income < 31,400`" had become "reject if `months_at_address < 9` and `income < 28,900`", and the month before it had involved a different feature entirely. Nothing in the process had changed except the monthly data refresh adding about 2% new rows.

The measurement that settled it: refit the tree on 20 bootstrap resamples of the *same* month's data. The root split was identical 20 times. The depth-4 rules agreed 4 times out of 20. The thresholds the report was publishing were being estimated from leaves containing 30 to 60 rows, and their standard error was larger than the month-to-month movement anyone was arguing about.

Two fixes. The published report changed to show only depths 1–3, with a bootstrap stability percentage next to every rule and every threshold given as an interval rather than a point. And the *scoring* model was switched to a gradient-boosted ensemble, with the shallow tree retained purely as the explanation artifact and explicitly labelled as such. Accuracy went up; the arguments stopped.

The general lesson: **a tree's readability is a real feature, and its thresholds are not real numbers.** Publish the structure, not the decimals.

### Design checkpoint

> A team wants a decision tree in production because "it's interpretable". The model will score 40,000 applications a day and its decisions are appealable. What do you tell them?

<Accordion title="Model answer">
Interpretability is a real requirement, so do not fight it — but separate the two jobs. First, ask what "interpretable" has to satisfy: a per-decision explanation for an appeal, a documented global policy, or both? A tree gives you both, but its thresholds are unstable — measure it, with the bootstrap experiment above, and bring the number. If depth-4 rules survive only 4 in 20 refits, publishing them as policy creates an appeal surface you cannot defend. Second, propose the split: a boosted ensemble for scoring, and for explanation either a depth-3 tree fitted to the ensemble's *predictions* (a surrogate, whose fidelity you must report as a number) or per-decision SHAP values (Module 3), which give an exact additive attribution per application. Third, whatever you ship, freeze the artifact between reviews: refitting monthly and republishing the rules is the actual source of the instability, and a quarterly cadence with a documented change log removes most of it for free. Finally, get the appeal process to state what it needs: "the three factors that most moved this decision" is answerable by SHAP; "the exact rule that fired" requires a tree; they are different products.
</Accordion>

### Greedy is not optimal, and optimal is NP-hard

CART chooses the split with the best *immediate* impurity decrease. It never looks ahead. This is a genuine limitation, not an implementation shortcut: constructing a minimal decision tree consistent with a training set is NP-complete (Hyafil & Rivest, 1976), and even approximating the optimal tree within a reasonable factor is hard.

The canonical demonstration is XOR. With `y = (x1 > 0) XOR (x2 > 0)`, **every single split has an information gain of essentially zero** — splitting on either feature leaves both children at 50/50 — so a purely greedy criterion sees nothing to do. CART still succeeds in practice because it splits anyway (any split with gain above the tolerance, or the best of several ties) and finds the structure at depth 2. But scale that to a 4-way parity and greedy search degrades badly, while the true tree has depth 4.

Modern optimal-tree solvers (`GOSDT`, `DL8.5`, MIP formulations) do exist and find provably optimal trees for small depths. The measured cost is the point: optimal trees of depth 3–4 on a few thousand rows take seconds to minutes; depth 6 is typically out of reach. Greedy CART fits a depth-`None` tree on 160,000 x 50 in a couple of seconds. **The greedy heuristic is not a compromise anyone is trying to remove; it is what makes trees usable at all.**

### Axis-alignment, measured

Every split has the form `x_j <= t`. The decision boundary is therefore always a union of axis-parallel rectangles. A boundary at 45 degrees must be approximated by a staircase.

```python
# scikit-learn 1.9.0, numpy 2.5.2
import numpy as np
from sklearn.tree import DecisionTreeClassifier
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score

rng = np.random.default_rng(0)
X = rng.normal(size=(4000, 2))
y = (X[:, 0] + X[:, 1] > 0).astype(int)          # a DIAGONAL boundary
th = np.pi / 4
R = np.array([[np.cos(th), -np.sin(th)], [np.sin(th), np.cos(th)]])
Xr = X @ R.T                                      # same data, boundary now axis-aligned

for name, Xd in [("diagonal boundary", X), ("rotated to axis-aligned", Xr)]:
    print(f"{name:<26} tree d3 {cross_val_score(DecisionTreeClassifier(max_depth=3,  random_state=0), Xd, y, cv=5).mean():.4f}"
          f"  tree d12 {cross_val_score(DecisionTreeClassifier(max_depth=12, random_state=0), Xd, y, cv=5).mean():.4f}"
          f"  logreg {cross_val_score(LogisticRegression(), Xd, y, cv=5).mean():.4f}")
```

```
diagonal boundary          tree d3 0.9105  tree d12 0.9848  logreg 0.9977
rotated to axis-aligned    tree d3 1.0000  tree d12 1.0000  logreg 0.9977
```

**A 45-degree rotation — an operation that destroys no information whatsoever — moves a depth-3 tree from 0.9105 to a perfect 1.0000.** The logistic regression is unmoved at 0.9977 either way, because a rotation is exactly the kind of transformation a linear model is invariant to. Even a depth-12 tree, with up to 4,096 leaves available, only reaches 0.9848 on the diagonal.

Three practical consequences:

- **Ratios and differences of features are worth engineering for trees** in a way they are not for linear models. `debt / income` is one split; `debt` and `income` separately take a staircase. This is Week 20 Module 2's justification.
- **PCA before a tree is usually a bad idea** — it rotates your axes to directions that have no domain meaning, and destroys the tree's interpretability — but **for a boundary you know is oblique it can help**. Measure, do not assume.
- **This is one of the reasons neural networks beat trees on images and text** and lose on tabular data: pixels have no privileged axes, but `age`, `income` and `days_since_last_login` do.

### Missing values: four strategies compared

Trees have a structural advantage here that most model families lack: a missing value can be *routed*.

| Strategy | Library | How it works | Cost |
| --- | --- | --- | --- |
| Drop rows | any | delete any row with a missing value | loses data; biased if missingness correlates with the label |
| Impute (median/mean) | `SimpleImputer` | fill, then split normally | destroys the *information in the missingness*; adds a fitted statistic that can leak (Week 19 Module 4) |
| Surrogate splits | R's `rpart`, not scikit-learn | at each node, learn a backup split correlated with the primary one | expensive; scikit-learn has never implemented it |
| **Learned default direction** | `HistGradientBoosting`, XGBoost, LightGBM | at each node, send missing values whichever way reduces loss more; learned from the data | free — it is one extra comparison per node |

The fourth is what XGBoost calls **sparsity-aware split finding** (Chen & Guestrin 2016, section 3.4) and it is one of the reasons XGBoost took over. It also handles a genuinely different case from imputation: a missing value that *means something*. `days_since_last_purchase` being null for a customer who has never purchased is not a measurement error to be filled with a median; it is the most informative fact in the row.

`sklearn.tree.DecisionTreeClassifier` gained native missing-value support in 1.3 and handles it the same way. But `SimpleImputer` remains the default in most pipelines, and it is usually the wrong choice for a tree model. If you do impute, **add a `_was_missing` indicator column** so the model can still see the fact.

### The cost model

Per node, with `n` rows and `p` features, `BestSplitter` costs `O(p n log n)` — dominated by the sort. Total training cost for a balanced tree of depth `d` is `O(p n log n * d)`, because each level touches all `n` rows once. scikit-learn caches the sorted order where it can (`presort` was removed in 0.24 because it lost more often than it won).

Inference is `O(depth)` comparisons per row — one branch test per level. Measured on a 500-tree forest of unlimited depth over 160,000 x 50, prediction costs **17.4 microseconds per row** for the whole forest; the same forest capped at depth 10 costs **8.3 microseconds per row**. A single tree is well under a microsecond. This is why trees are the model family of choice when the latency budget is tight and the features are already computed.

### Failure modes

| Failure | Signature | Detector |
| --- | --- | --- |
| Published thresholds drift monthly | rule text changes; accuracy does not | bootstrap-refit 20 times; report per-rule survival frequency |
| Oblique boundary | tree needs far more depth than the problem seems to need; a linear model on the same data does better | fit a logistic regression as a baseline — if it wins, your boundary is probably oblique |
| High-cardinality categorical one-hot encoded | many weak splits; importance spread thin; slow fits | use native categorical support; measure against one-hot |
| Leaf built from 3 rows | a confident, extreme `predict_proba` on a rule nobody can justify | set `min_samples_leaf >= 20` for anything a human reads; log the minimum leaf size |
| Non-reproducible tree with `splitter="best"` | different `random_state` gives a different model | pin `random_state`; and know that pinning it hides ties rather than resolving them |
| Missingness imputed away | model loses signal that `null` carried | add `_was_missing` indicators; compare against native missing handling |
| Extrapolation | predictions flat outside the training range | a tree's output is bounded by the leaf means it learned; never use one for a trending time series without differencing |

### Papers

- **Breiman, L., Friedman, J., Olshen, R., Stone, C. (1984), *Classification and Regression Trees*.** *Takeaway:* the CART algorithm — binary splits, impurity-based greedy search, and cost-complexity pruning as the principled way to choose tree size — which is still, forty years on, what every library implements.
- **Hyafil, L. & Rivest, R. (1976), "Constructing optimal binary decision trees is NP-complete," Information Processing Letters 5(1).** *Takeaway:* the greedy heuristic is not laziness; finding the smallest consistent tree is intractable, so every practical tree learner is an approximation.
- **Quinlan, J. R. (1986), "Induction of Decision Trees," Machine Learning 1(1).** *Takeaway:* ID3's information-gain criterion, and the observation — still the source of Module 2's importance trap — that gain is biased toward features with more possible values.
- **Chen, T. & Guestrin, C. (2016), "XGBoost: A Scalable Tree Boosting System," KDD.** *Takeaway:* section 3.4's sparsity-aware split finding learns a default direction for missing values at each node, which is both faster and more accurate than imputing — and it is why boosted trees handle real, holey tabular data so well.
- **Rudin, C. (2019), "Stop Explaining Black Box Machine Learning Models for High Stakes Decisions and Use Interpretable Models Instead," Nature Machine Intelligence 1.** *Takeaway:* for many tabular high-stakes problems an interpretable model loses little or no accuracy, so the accuracy/interpretability trade-off is often assumed rather than measured — measure it before accepting it.

## The whole idea on one whiteboard

A tree asks one yes/no question about one feature at a time, and each answer sends you down a branch. Growing the tree means, at every node, trying every feature and every possible cut point and keeping the one that most reduces how *mixed* the labels are below it. That is all. The consequences follow mechanically: the boundaries are always parallel to the axes (because each question involves one feature), scaling a feature changes nothing (because only the *order* of values matters), and the tree keeps splitting until the leaves are pure, which is why left alone it always overfits.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Train accuracy exactly 1.0000 | unlimited depth; leaves memorising single rows | set `max_depth` or `min_samples_leaf`; check the test column |
| A "rule" changes every refit | thresholds estimated from tiny leaves | bootstrap-refit and report survival frequency; publish structure, not decimals |
| Tree needs depth 15 for a simple problem | oblique boundary being approximated by a staircase | engineer the ratio/difference feature, or compare against a linear model |
| High-cardinality categorical dominates nothing | one-hot split it into 50 weak binary features | native categorical support (LightGBM/CatBoost/`HistGradientBoosting`) |
| Scaling "fixed" the tree | it cannot have; something else changed | re-check — a tree is invariant to any monotone per-feature transform |
| Two seeds give different trees | tie-breaking uses `random_state` even with `splitter="best"` | pin it; and treat deep-node rules as non-identified |
| Regression tree predicts a flat line beyond the data | leaves can only output training means | never extrapolate with a tree; difference the series or use a linear model for trend |
| Model is worse after imputing | the missingness carried signal | add `_was_missing`, or use a learner with native missing handling |
