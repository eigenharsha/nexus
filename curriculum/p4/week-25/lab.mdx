>

>

>

  <Tab title="basic">
    **Scaffolded. About 60% is written for you; every gap is marked `# TODO`.**

    1. **BPE encode/decode against a provided merge table.** `starter/bpe.py` ships with a trained

       `[0.384, 0.726]` for the token `slept` — to three decimal places.
    3. **Read the parameter count.** Run the provided `count_params.py` on three configs and
       reconcile each against your own hand arithmetic in `ANSWERS.md`. Any discrepancy must be
       explained, not rounded away.

    <Info>
    Acceptance: `make verify TRACK=basic` is green. Roughly 40 lines of your own code.
    </Info>

  <Tab title="standard">
    **Spec and tests only. You write the implementation.**

    Build the whole path. Every component must be unit-tested against a PyTorch equivalent — "it
    ran" is not evidence.

    <Steps>
      <Step title="Train your own BPE tokenizer">
        Train on `data/input.txt` at `vocab_size=1024`. Required: a `train/encode/decode` API,
        deterministic tie-breaking, correct earliest-merge-first encoding order, and special-token
        registration such that a special token's spelling appearing in *user input* encodes to
        ordinary tokens rather than the reserved ID. Report bytes-per-token against `gpt2` on a
        held-out slice.
      </Step>
      <Step title="Implement the model">
        `CausalSelfAttention` (multi-head, masked), `MLP`, `Block` (pre-norm, residual), `GPT`
        (embeddings, stack, final norm, LM head, optional weight tying). Config-driven. Must be
        shape-preserving per block and must assert `d_model % n_heads == 0` with a message naming
        both values.
      </Step>
      <Step title="Test every component against PyTorch">
        Attention must agree with `nn.MultiheadAttention` (weights copied across) to
        `&lt; 1e-5` max absolute difference. The causality perturbation test must pass: change the
        last token, assert no earlier output moves. Your analytic `count_params(config)` must match
        the instantiated model exactly, to the parameter.
      </Step>
      <Step title="Train it">
        5,000 steps, `AdamW` at `lr=3e-4`, `weight_decay=0.1`, `betas=(0.9, 0.95)`, gradient
        clipping at 1.0. Log train and val loss every 500 steps. Target: val loss ≤ 1.55 on
        tinyshakespeare with the default 10.7M config.
      </Step>
      <Step title="Generate, with a KV cache you wrote">
        Implement caching in your own attention module. Support temperature, top-k, top-p and a
        repetition penalty. `is_causal` must be conditional on sequence length — verify by
        asserting cached decode matches full recompute exactly for 8 steps.
      </Step>
      <Step title="Measure">
        Tokens/sec with and without the cache at 32/128/256 output tokens. Verify your
        KV-cache-size arithmetic against the real `past_key_values` byte count — they must match
        exactly, not approximately.
      </Step>
    </Steps>

    <Info>
    Acceptance: `make verify` green (all four test modules), `val_loss.json` shows ≤ 1.55, and
    `MEASUREMENTS.md` contains the cache speedup table and the byte-count verification.
    </Info>
  </Tab>

  <Tab title="hard">
    **A constraint the `standard` solution fails.**

    The `standard` model uses learned absolute positions, full multi-head attention, and a
    hand-written attention kernel. All three break at longer context. Fix all three and prove it.

    1. **RoPE.** Replace learned positions. Verify the relative-distance property numerically: the
       score for `(q at m, k at n)` must equal the score for the same vectors at `(m+δ, n+δ)` to
       1e-4.
    2. **GQA.** Parameterise `n_kv_heads`. Show the KV cache shrinks by exactly `n_heads/n_kv_heads`
       — measured in bytes, not asserted.
    3. **FlashAttention via `F.scaled_dot_product_attention`.** And prove you are actually on the
       flash backend rather than the math fallback.
    4. **The constraint:** run at context lengths 1,024 / 4,096 / 16,384 and report tokens/sec and
       peak memory at each. The `standard` implementation must OOM or exceed a 10× slowdown at
       16,384; yours must not. Include the failing baseline run in your report — a constraint you
       cannot demonstrate the old code failing is not a constraint.
    5. **The attention visualiser.** A tool that takes a sentence and a trained model and renders
       the per-head attention grids, with the causal triangle visible. Use it to identify one
       previous-token head and one attention-sink head in your own trained model, and say how you
       identified each.

    <Warning>
    The 16,384-context run is the gate. If your implementation completes it without OOM but you
    cannot show the baseline failing, you have not demonstrated the point of the exercise.
    </Warning>
  </Tab>

## Stuck? Open these in order

Each reveals a little more than the last. Try the level above before opening the next — a hint you
did not need costs you nothing, but an answer taken too early costs you the lesson.

<AccordionGroup>
<Accordion title="Nudge — I don't know where to start" icon="lightbulb">
Find the **first** failing test and implement only what that one test needs. Ignore the rest of the
lab until it is green. If you cannot tell which test fails first, run
`make verify TRACK=basic` and read the top of the output, not the bottom.
</Accordion>

<Accordion title="Hint — my BPE tokenizer produces different merges than the reference" icon="lightbulb">
Tie-breaking. When two pairs have the same frequency, the order you pick them changes every merge after it, so the vocabularies diverge and never reconverge.

**What to do instead:** Break ties deterministically — lowest pair index wins — and check your counts after each merge rather than only at the end. One wrong tie at merge 12 explains a completely different vocabulary at merge 500.
</Accordion>

<Accordion title="Hint — my attention output has the wrong shape" icon="lightbulb">
The head split is the usual culprit. You reshape `(B, T, C)` into `(B, T, heads, head_dim)` and must transpose to `(B, heads, T, head_dim)` before the matmul, then transpose back and reshape after.

**What to do instead:** Write the expected shape as a comment on every line and assert it. `assert x.shape == (B, heads, T, head_dim)` costs nothing and finds this in seconds.
</Accordion>

<Accordion title="Hint — my model generates repetitive nonsense" icon="lightbulb">
If loss is falling, this is a sampling problem, not a training one. Greedy decoding on a small undertrained model loops almost immediately.

**What to do instead:** Check the loss first: at a vocabulary of 65 characters, random is about 4.17 nats. If loss is near that, it has learned nothing and the bug is in training. If loss is around 1.5, the model is fine — raise the temperature and use top-k.
</Accordion>

<Accordion title="Hint — my KV cache makes generation slower, not faster" icon="lightbulb">
You are probably rebuilding the cache each step rather than appending to it, so you pay the copy plus the original compute.

**What to do instead:** Preallocate the cache to the maximum sequence length and write into a slice. Then confirm the cached run produces token-identical output to the uncached one before you trust the timing.
</Accordion>

<Accordion title="I have a real attempt that fails — show me the full solution" icon="lock">
Open the [reference solution](/solutions/p4/week-25/lab).

Use it properly: read only far enough to get unstuck, then close it and return to your own code.
Afterwards, diff your version against it — the differences are the lesson, and yours is not

</Accordion>
</AccordionGroup>

## Rubric

Score yourself honestly, then have a peer score you. The gap between the two scores is the useful
signal.

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| **Correctness** | tests fail | `basic` passes | `standard` passes, all reference comparisons under tolerance | `hard` passes including the 16,384 run, with the baseline failure demonstrated |
| **Code quality** | works | readable, named sensibly | typed, tested, config-driven, no magic constants | a reviewer would approve unchanged; the assertions carry diagnostic messages |
| **Performance** | untested | timed once | cache speedup and KV byte count measured and verified against the formula | roofline percentage computed, and the gap between predicted and measured explained |
| **Explanation** | none | a README | reasoning documented per component | the explainer teaches it — own diagrams, own numbers, the wrong turns kept in |

**What a 3/3 on Explanation looks like:** you kept the mistake. If your first attention
implementation had the mask off by one, the explainer shows the too-good loss curve, names the bug,
and shows the perturbation test that would have caught it. That is worth more than a clean
write-up, and it is the house style of this entire course.

## If you get stuck

<AccordionGroup>
  <Accordion title="Loss goes to NaN in the first 100 steps">
    In order of likelihood: no gradient clipping; normalisation computed in half precision;
    learning rate too high for your batch size; a `-inf` mask row that is entirely masked (which
    makes softmax produce NaN — a fully-masked row is always a bug, and worth asserting against).
  </Accordion>
  <Accordion title="Loss falls beautifully but samples are gibberish">
    Almost certainly the causal mask. Run `test_causality_perturbation`. If your validation loss is
    below about 1.2 on tinyshakespeare at 10.7M parameters, it is not a great model, it is a
    leaking mask.
  </Accordion>
  <Accordion title="Attention does not match nn.MultiheadAttention">
    Check, in this order: `in_proj_weight` packs q, k, v in that order and you copied it in that
    order; `bias=False` on both sides; you are comparing in `eval()` mode with dropout off; your
    mask is boolean-with-True-meaning-masked, which is the opposite convention from an additive
    float mask.
  </Accordion>
  <Accordion title="Cached generation differs from uncached">
    `is_causal` must be `False` when the input is a single token. Then check that you append the
    new K/V to the cache *before* computing attention, not after, and that you are slicing
    `logits[:, -1, :]` rather than `logits[:, 0, :]`.
  </Accordion>
</AccordionGroup>
