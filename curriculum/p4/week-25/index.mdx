## The through-line

Five modules, one narrative, each one answering the question the previous one raised:

1. **Text → tokens.** A model never sees text; it sees integers. Which integers, and who decided?
2. **Embeddings & position.** Those integers become vectors by table lookup — and a stack of
   vectors has no order, so order must be injected.
3. **Self-attention.** Each vector pulls information from the others, weighted by learned
   relevance. **This is the module that matters most.**
4. **The block & the decoder.** Wrap attention in residuals, norms and a feed-forward network,
   stack it 32 times, count the parameters.
5. **Generation & cost.** Sample from the output distribution in a loop — and discover that the
   loop has two completely different performance regimes.

## The five numbers you should leave with

If someone stops you in a corridor in six months, these are the ones that should still be there.
All five are **derived** — shape algebra, parameter counts and bandwidth arithmetic — so they are
true on any hardware. The GPU throughput figures inside the modules are **reference figures**
modelled for an A10G the authors did not have; see [About the numbers](/start/about-the-numbers).

| Number | What it is |
| --- | --- |
| `(B, T, D)` → `(B, H, T, Dh)` → `(B, H, T, T)` | The shape chain. Nearly every Transformer bug is a disagreement between two of these. |
| `√d_k = 11.31` for `d_k = 128` | The attention scale factor. Without it, softmax saturates and the gradient falls to 3e-7. |
| `218.1M` per Llama-3-8B layer, 80.8% of it FFN | Where the parameters actually are, which decides where LoRA goes. |
| `512 KiB` per token (Llama-2-7B), `4 GiB` at 8k | The KV cache. It is why your GPU runs out of memory. |
| `13.5 GB ÷ 600 GB/s = 44 tok/s` | Decode speed from weight size and memory bandwidth. Predicts reality to within 10%. |
