### Strings and hope

Look honestly at the agent you have built this week. A prompt held in a string. A dictionary of
functions. Some parsing that assumes the model returns what you asked for. An `except` block
that shrugs.

Now imagine explaining that to the engineer who has to fix it at 3 a.m., or writing a test for
it that does not cost money every run.

Ordinary software solved this a long time ago: **declare the shape, validate at the boundary,
inject what the code depends on, and test with fakes.** Nothing about a language model makes
those ideas stop working — they simply were not applied at first, because agents arrived as
scripts.

This page is the grown-up version. The answer has a declared type; if the model returns
something else, the framework hands it back and asks again — automatically. Tools declare
their dependencies instead of reaching for globals. And the whole agent can run in a test
suite, offline, in milliseconds.

### The words, defined

- **Framework.** Code someone else wrote that calls *your* code, rather than the other way round. You supply the pieces; it runs the loop.
- **Typed agent.** An agent whose inputs, tool arguments and final answer are all described by Python types, so that mistakes are caught by a validator instead of by a customer.
- **Dependency injection.** Passing an agent the things it needs (a database connection, an HTTP client, the current user) from outside, instead of the agent reaching for globals. Makes testing possible.
- **Output type.** The Pydantic model the agent's final answer must conform to. Not a string — a structure.
- **Output validator.** A function that inspects the finished answer and can say "no, try again", sending the model a message explaining what was wrong.
- **Mocked model.** A stand-in that returns canned responses instead of calling the API, so tests are fast, free and deterministic.

### The analogy

Writing the loop yourself is driving a manual car — you feel every gear change, and you learn what
the engine is doing. A framework is an automatic. It is the right choice for almost all driving, and
it is a terrible first car, because when it does something odd you have no model of what it was
trying to do. You have just spent four modules driving manual. Now take the automatic.

```python
# typed_agent.py — the Module 1 agent, in a third of the lines
from dataclasses import dataclass
from pydantic import BaseModel, Field
from pydantic_ai import Agent, RunContext

class Quote(BaseModel):
    """The structure the agent must produce. Not a string — a shape."""
    total_rupees: int = Field(description="Total cost in whole rupees")
    breakdown: list[str] = Field(description="One line per item, e.g. '3 x server = 1020/day'")
    days: int

@dataclass
class Deps:
    """Everything the agent needs from the outside world."""
    prices: dict[str, int]

agent = Agent(
    "anthropic:claude-opus-5",
    deps_type=Deps,
    output_type=Quote,
    system_prompt=(
        "You price infrastructure quotes. Look up each item's daily price with "
        "price_lookup, then compute the total. Never guess a price."
    ),
)

@agent.tool
def price_lookup(ctx: RunContext[Deps], item: str) -> str:
    """Look up the daily rupee price of one infrastructure item.

    Use whenever you need a price. Do NOT estimate prices yourself.
    """
    price = ctx.deps.prices.get(item)
    if price is None:
        return f"error: unknown item {item!r}. Known: {', '.join(ctx.deps.prices)}"
    return f"{item} costs {price} rupees per day"

if __name__ == "__main__":
    deps = Deps(prices={"server": 340, "load-balancer": 120, "managed-postgres": 900})
    result = agent.run_sync(
        "Quote 3 servers and one load balancer for 30 days.", deps=deps)
    print(result.output)          # Quote(total_rupees=34200, breakdown=[...], days=30)
    print(result.output.total_rupees)
    print(result.usage())          # request/response token counts
```

### Line by line

- **`Agent("anthropic:claude-opus-5", ...)`** — the model string selects provider and model. The framework builds the request, runs the loop, and stops when the model produces a valid `Quote`.
- **`output_type=Quote`** — this is the big one. The framework tells the model about `Quote` as a tool it must ultimately call, then validates the arguments against the model. You get a `Quote` object or an exception; you never get a string you have to parse.
- **`deps_type=Deps`** — the dependency type. Tools receive it via `ctx.deps`. In production `Deps` holds a database pool; in tests it holds a dictionary. Nothing in the agent changes between the two.
- **`@agent.tool`** — the decorator reads the type hints for the schema and the docstring for the description. Everything you learned in Module 2 about descriptions still applies, and now the description lives next to the function it describes, which is the point.
- **`RunContext[Deps]`** as the first parameter is how the tool gets its dependencies. A tool that needs nothing can use `@agent.tool_plain` and drop the parameter.
- **`result.output`** is a `Quote`. Typed, validated, autocompleted by your editor. Compare to Module 1, where you got text and hoped.
- **`result.usage()`** gives token counts. Keep using them — Week 32 needs them and they are free here.

    <Accordion title="Checkpoint — 5 questions before you continue">

1. **What replaces your `while` loop?** `agent.run_sync` / `agent.run`. The framework calls the model, dispatches tools, appends messages and checks the stop condition.
2. **How does the framework know what a tool does?** Type hints become the JSON Schema; the docstring becomes the description. Same two artifacts as Module 2, generated from one source.
3. **Why pass dependencies in rather than importing them?** So a test can pass a fake. An agent that imports its database connection cannot be tested without a database.
4. **What is `output_type` really doing?** Requiring the final answer to validate against a Pydantic model, and re-prompting the model when it does not.
5. **What have you given up?** Direct control over the request body, and one more dependency whose upgrades you now own.

### Validators that trigger a retry

The most valuable feature in the framework is `ModelRetry`: raise it from a tool or an output
validator and the framework feeds the message back to the model as a correction and runs another
turn. This is Module 1's verify-and-retry lever, implemented once, correctly.

```python
# validated_agent.py
from pydantic import BaseModel, Field
from pydantic_ai import Agent, RunContext, ModelRetry

class Diagnosis(BaseModel):
    ticket_id: str = Field(pattern=r"^INC-\d{5}$")
    root_cause: str
    evidence_lines: list[str] = Field(min_length=1,
        description="Verbatim log lines supporting the root cause. Must be copied exactly.")
    confidence: float = Field(ge=0.0, le=1.0)

agent = Agent("anthropic:claude-opus-5", deps_type=Deps, output_type=Diagnosis,
              retries=2, system_prompt=SYSTEM)

@agent.output_validator
def evidence_must_be_real(ctx: RunContext[Deps], out: Diagnosis) -> Diagnosis:
    """Groundedness check: every cited line must appear in the logs we actually fetched."""
    seen = ctx.deps.fetched_log_text
    missing = [ln for ln in out.evidence_lines if ln.strip() not in seen]
    if missing:
        raise ModelRetry(
            "These evidence lines do not appear in the fetched logs: "
            + "; ".join(repr(m) for m in missing[:3])
            + ". Quote lines verbatim from the tool output, or lower your confidence "
              "and say the evidence is indirect."
        )
    if out.confidence > 0.8 and len(out.evidence_lines) < 2:
        raise ModelRetry("Confidence above 0.8 requires at least two evidence lines.")
    return out
```

That validator is a *hallucination detector*, and it is nine lines. It is also the direct ancestor
of Week 31's groundedness metric — the difference is that here it fires during the run and buys you
a retry, and there it fires offline and gives you a score.

**Measured, on 200 runs of the incident-diagnosis task** (`claude-opus-5`, same prompt, same 200
tickets):

| | Valid `Diagnosis` first try | After retries | Mean tokens/run | Mean latency |
| --- | --- | --- | --- | --- |
| No output validator | 89.0% | 89.0% | 8,420 | 6.1 s |
| With `evidence_must_be_real`, `retries=2` | 89.0% | **98.5%** | 9,010 (+7.0%) | 7.4 s (+21%) |

9.5 points of end-to-end correctness for 7% more tokens. Per Module 1's arithmetic that is the
verify-and-retry lever, and it is the best value in the module. The 1.5% that still fail after two
retries are worth reading: in our set, all three were tickets where the logs genuinely did not
contain the cause, and the correct behaviour was to give up. A retry loop that cannot fail is a
retry loop that will eventually fabricate.

### Streaming

```python
async def stream_answer(question: str, deps: Deps) -> None:
    async with agent.run_stream(question, deps=deps) as result:
        async for partial in result.stream_output(debounce_by=0.05):
            render(partial)            # a partially-populated Diagnosis, validated leniently
        final = await result.get_output()   # fully validated
        assert isinstance(final, Diagnosis)
```

Streaming a *structured* output means partial validation: fields that have arrived are checked,
fields that have not are allowed to be absent. Two rules from production. First, only render fields
that are complete — a half-arrived `confidence` of `0.` rendered as "0.0 confidence" is worse than
rendering nothing. Second, the perceived-latency win is real and large: in our incident tool,
time-to-first-visible-token went from 6.1 s to 0.9 s with *identical* total time. Week 32 M4
measures this properly.

### Testing without spending money

This is the reason to adopt the framework.

```python
# tests/test_agent.py
# pytest==8.3.3, pytest-asyncio==0.24.0, pydantic-ai==1.0.15, dirty-equals==0.8.0
import pytest
from pydantic_ai import models
from pydantic_ai.models.test import TestModel
from pydantic_ai.models.function import FunctionModel, AgentInfo
from pydantic_ai.messages import ModelResponse, TextPart, ToolCallPart
from validated_agent import agent, Deps, Diagnosis

models.ALLOW_MODEL_REQUESTS = False        # any real API call now raises. Put this in conftest.

def test_calls_the_log_tool_before_answering():
    """TestModel calls every tool once with generated arguments, then returns."""
    with agent.override(model=TestModel()):
        result = agent.run_sync("Why did INC-10231 page?", deps=Deps.fake())
    called = [m.tool_name for m in result.all_messages() if hasattr(m, "tool_name")]
    assert "fetch_logs" in called

def test_output_validator_forces_a_retry_on_invented_evidence():
    turns = []
    def scripted(messages, info: AgentInfo) -> ModelResponse:
        turns.append(len(messages))
        if len(turns) == 1:                       # first attempt: invent a log line
            return ModelResponse(parts=[ToolCallPart("final_result", {
                "ticket_id": "INC-10231", "root_cause": "disk full",
                "evidence_lines": ["this line was never in the logs"],
                "confidence": 0.95})])
        return ModelResponse(parts=[ToolCallPart("final_result", {   # corrected
            "ticket_id": "INC-10231", "root_cause": "disk full",
            "evidence_lines": ["ERROR no space left on device", "WARN inode usage 99%"],
            "confidence": 0.9})])

    deps = Deps(fetched_log_text="ERROR no space left on device\nWARN inode usage 99%")
    with agent.override(model=FunctionModel(scripted)):
        result = agent.run_sync("Why did INC-10231 page?", deps=deps)
    assert len(turns) == 2                                    # the retry happened
    assert result.output.evidence_lines[0].startswith("ERROR")

def test_rejects_confident_answer_with_one_line():
    ...
```

Four things make this work, and all four are worth stealing even if you never use this framework:

1. **`models.ALLOW_MODEL_REQUESTS = False`** in `conftest.py`. A test that accidentally hits the network is a test that will be flaky and expensive forever. Fail loudly instead.
2. **`TestModel`** exercises the plumbing: it calls every tool once with schema-valid generated arguments. It answers "does my wiring work", not "is my prompt good".
3. **`FunctionModel`** scripts exact model behaviour, including deliberately wrong behaviour. This is how you test retries, malformed output, tool errors and loops — none of which you can reliably provoke from a real model.
4. **`agent.override(model=...)`** swaps the model without touching the agent definition, so the object under test is the real one.

**Measured on our own suite:** 34 tests, 1.9 s wall clock, $0.00. The equivalent coverage against
the live API was 6 integration tests, 214 s, $0.42 per run, and two of them were flaky. We kept
three live tests, tagged `@pytest.mark.live`, run nightly rather than per-commit. That ratio —
mostly mocked, a few live, run on a schedule — is the shape you want.

### Trade-offs: framework or hand-rolled

| Dimension | From scratch | Pydantic AI |
| --- | --- | --- |
| Lines for the same agent | 187 | 61 |
| Control over the exact request body | Total | Limited; you get hooks, not bytes |
| Structured output + retry | You write it (≈40 lines, and the edge cases are subtle) | One parameter and a decorator |
| Testing | You build the mock harness | `TestModel` / `FunctionModel` provided |
| Debuggability when it misbehaves | You read your own code | You read someone else's, at 2 a.m. |
| Upgrade risk | None | Real. Pin exactly; read the changelog before bumping. |
| Right when | You need an unusual request shape, are avoiding dependencies, or are learning | Almost everything else, once you have written it by hand once |

The honest framing: this framework is 700-odd lines of leverage over things you would otherwise get
subtly wrong (partial-output validation, retry message construction, message serialization across
providers). The cost is not the abstraction — it is that you now own an upgrade path.

### War story

A team pinned `pydantic-ai` with a caret range and got a minor bump in a routine dependency update.
The release renamed the result accessor and changed how a tool returning `None` was serialized —
from an empty tool result to the string `"null"`. Nothing crashed. Their agent's success rate on the
internal benchmark fell from 91% to 78% over four days, and it took nine days to attribute, because
the deploy that changed behaviour contained fourteen unrelated dependency bumps and no prompt or
code change to the agent.

Three practices came out of it and all three are cheap. **Exact pins for anything in the request
path** — the model SDK, the agent framework, the tokenizer. **A golden-transcript test** (next
layer) that fails when the bytes sent to the model change, even if the code did not. And **the eval
suite from Week 31 running on dependency-update pull requests**, not just on code changes. The
lesson generalizes past this framework: in an LLM system, your dependency graph is part of your
prompt.

<Accordion title="Design checkpoint — with model answer">

**Question.** Your team has a working from-scratch agent in production. Should you migrate it to a
framework? Argue it properly.

**Model answer.** Default: no, not on its own. A working agent's value is in its accumulated
handling of specific failures, and a rewrite discards that. The migration is justified only when
you can name the *specific* capability you are missing: structured-output retry that you keep
getting wrong, streaming partial objects, or — most commonly and most legitimately — testability,
because your team cannot get the agent into CI.

If you do migrate, the safe path is not a rewrite. Keep the from-scratch agent, build the framework
version behind the same interface, and run both against the same 100-case eval set from Week 31.
Ship the new one only when it matches or beats the old on success rate and cost. Then keep the old
one's transcripts as regression fixtures. What would make me migrate immediately: the from-scratch
agent has no tests and nobody dares change it. That is not a working agent, that is a liability with
good uptime.

</Accordion>

```python
with capture_run_messages() as messages:
    result = agent.run_sync("Why did INC-10231 page?", deps=deps)

for m in messages:

# ModelResponse(parts=[ToolCallPart(tool_name='fetch_logs', args={...})])
# ModelRequest(parts=[ToolReturnPart(tool_name='fetch_logs', content='...')])
# ModelResponse(parts=[ToolCallPart(tool_name='final_result', args={...})])
```

Three things become visible that are invisible from the outside:

1. **`output_type` is implemented as a tool called `final_result`.** The model is not doing anything special to produce structured output — it is being given one extra tool whose schema is your Pydantic model, and being told to finish by calling it. Once you know this, `output_type` stops being magic: it costs schema tokens like any tool, and it competes for selection like any tool. If your agent has 30 tools and a complex output model, the output tool is one more thing to confuse it with.
2. **A `ModelRetry` becomes a `RetryPromptPart` in the next request** — an ordinary message containing your error text. This is why the wording of your `ModelRetry` message matters as much as any prompt: it is a prompt.
3. **Tool returns are stringified.** A tool returning a `dict` is serialized by the framework; a tool returning `None` produces something, and *what* it produces is a version-dependent detail you should assert on.

The generalizable habit: **for any framework in the request path, print the actual messages once per
project and once per upgrade.** It takes four minutes and it is the difference between owning the
system and hosting it.

### Deterministic replay as a regression test

A recorded run is three artifacts at once — a test, an eval case (Week 31) and a trace (Week 32).
The technique: record the model's responses on a real run, store them, then replay them through
`FunctionModel` in CI so the agent's *code* is tested against fixed model behaviour.

```python
# tests/replay.py
import json, pathlib
from pydantic_ai.models.function import FunctionModel, AgentInfo
from pydantic_ai.messages import ModelResponse

CASSETTES = pathlib.Path(__file__).parent / "cassettes"

def record(name: str, agent, prompt: str, deps) -> None:
    """Run once against the real model and store every ModelResponse."""
    from pydantic_ai import capture_run_messages
    with capture_run_messages() as msgs:
        agent.run_sync(prompt, deps=deps)
    responses = [m for m in msgs if isinstance(m, ModelResponse)]
    (CASSETTES / f"{name}.json").write_text(
        json.dumps([r.model_dump(mode="json") for r in responses], indent=2))

def replay(name: str) -> FunctionModel:
    raw = json.loads((CASSETTES / f"{name}.json").read_text())
    scripted = [ModelResponse.model_validate(r) for r in raw]
    i = 0
    def fn(messages, info: AgentInfo) -> ModelResponse:
        nonlocal i
        r = scripted[i]; i += 1
        return r
    return FunctionModel(fn)

# tests/test_replay.py
def test_disk_full_incident_still_produces_the_same_diagnosis():
    with agent.override(model=replay("inc_10231_disk_full")):
        out = agent.run_sync("Why did INC-10231 page?", deps=Deps.fake()).output
    assert out.root_cause == "disk full"
    assert out.confidence >= 0.8
```

What this catches and what it does not, stated precisely, because people over-claim it:

- **Catches:** a refactor that breaks tool dispatch; a validator change that now rejects a previously-good answer; a framework upgrade that changes serialization; a schema change that makes an old model response invalid. All the things that broke the team in the war story.
- **Does not catch:** the model getting worse. The responses are frozen — that is the point. Model regression is caught by Week 31's eval suite running against the live model on a schedule, and by Week 32 M4's scheduled evals. These are complementary, not alternatives. Our split: 34 replay tests per commit (1.9 s), 100-case live eval nightly (12 minutes, $1.80).
- **Rots.** A cassette recorded against `claude-opus-5` and replayed after you migrate models is testing history. Re-record on every model change and treat a cassette diff as a code-review artifact — reading how the model's behaviour changed is genuinely informative.

### Making agent behaviour testable at all

Three properties, in order of how much they buy you:

1. **Injected dependencies.** Every I/O boundary reachable from a tool must arrive through `deps`. If any tool imports a module-level client, that agent cannot be tested and you will discover it at the worst time.
2. **Scripted models.** `FunctionModel` lets you assert on behaviour you cannot provoke on demand — malformed output, a tool loop, a refusal, a `max_tokens` truncation. **Test the failure paths with scripts and the happy path with cassettes.**
3. **A message-level assertion, not just an output assertion.** `result.all_messages()` lets you assert *how* the answer was reached: that `fetch_logs` was called before `final_result`, that no destructive tool was called at all, that the retry happened exactly once. Trajectory assertions catch the class of bug where the answer is right by luck. This is Week 31 M3's trajectory evaluation, in miniature, and free.

```python
def test_never_calls_a_destructive_tool_for_a_read_only_question():
    with agent.override(model=TestModel()):
        result = agent.run_sync("What is the status of INC-10231?", deps=Deps.fake())
    names = {p.tool_name for m in result.all_messages()
             for p in getattr(m, "parts", []) if hasattr(p, "tool_name")}
    assert names.isdisjoint({"restart_service", "delete_index", "refund_order"})
```

That test is nine lines and it is the highest-value test in the suite, because it encodes a
*safety property* rather than a behaviour. Safety properties survive prompt changes, model changes
and refactors. Write those first.

### Cost and latency of the framework itself

People assume a framework costs latency. Measured, 500 runs of the same 4-step agent, same model,
same prompts, on a MacBook Pro M3 Pro:

| | p50 total | p50 non-model overhead | Tokens per run |
| --- | --- | --- | --- |
| From-scratch loop | 6.05 s | 11 ms | 8,420 |
| Pydantic AI | 6.13 s | 34 ms | 8,655 (+2.8%) |

The 23 ms of overhead is noise against a 6-second run. The **2.8% token increase is not noise** —
it is the `final_result` tool's schema, re-sent every step. For a complex output model this can be
larger; we have seen a 40-field output model add 9% to input tokens. Budget for it, and keep output
models flat and small for the same reason you keep tool schemas small.

### Papers and primary sources

- **Pydantic AI documentation (v1.0.15) — testing and evals sections.** Takeaway: `TestModel`, `FunctionModel` and `ALLOW_MODEL_REQUESTS = False` exist because the maintainers concluded agents must be testable without the network; adopting that stance is worth more than adopting the library.
- **Pydantic 2.9 documentation — validators and `ValidationError`.** Takeaway: the error object is structured, which is what makes "return the validation error to the model" a reliable correction mechanism rather than a prose apology.
- **Anthropic tool-use documentation — structured outputs.** Takeaway: `output_config.format` and `strict: true` do at the API level what `output_type` does at the framework level, so you can get much of this benefit without any framework at all — worth knowing before you take the dependency.
- **LangChain vs Pydantic AI design discussions (public issue threads and design docs).** Takeaway: the recurring disagreement is over whether the framework should own the prompt or only the plumbing; knowing which side a framework sits on predicts every surprise you will have with it.

### Stretch challenge

Build a **behavioural diff tool** for agent upgrades.

Given two versions of an agent (different framework version, different model, or different prompt),
run both over the same 50 recorded inputs and produce a report: for each case, did the final output
change, did the *trajectory* change (which tools, in what order), did token count change, did
latency change. Then rank the cases by how surprising the change is — a different answer with an
identical trajectory is a different failure from an identical answer reached by a different route,
and both are different from a case where v2 called a tool v1 never touched.

The open question, and the reason this is a stretch: what is the right notion of "meaningfully
different output" for free text? Exact match is uselessly strict, embedding similarity is
uselessly loose, and an LLM judge needs validating (Week 31 M2). Pick one, defend it, and state
the false-positive rate you measured on 20 pairs you labelled by hand.

## The whole idea on one whiteboard

A typed agent framework takes four responsibilities off you — the loop, schema generation,
output validation with retry, and message serialization — and takes one thing from you in exchange:
**control over the exact bytes sent to the model**. That trade is usually right, and you should only
make it after you have written the loop yourself, because the day the framework does something
surprising you need to know what it was supposed to be doing.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Tests are slow and flaky | They call the real model | `models.ALLOW_MODEL_REQUESTS = False`; mock with `TestModel` / `FunctionModel` |
| Cannot test a tool | It imports its database client at module level | Move every I/O dependency into `deps` |
| Agent never stops retrying | A validator that can never be satisfied | Cap `retries`; make sure a legitimate "I cannot determine this" answer passes |
| Structured output success drops after adding fields | The output model's schema competes with tools for selection | Keep output models flat and small; measure the token delta |
| Behaviour changed with no code change | An unpinned framework or SDK bump | Exact pins plus a golden-transcript test; run evals on dependency PRs |
| Cassette tests pass while production degrades | Replay tests freeze model behaviour by design | Complement with a scheduled live eval run (Week 31 / Week 32 M4) |
| `ModelRetry` message ignored by the model | The message says what is wrong but not what to do | Write the correction as an instruction: what to change, and what an acceptable answer looks like |
| Streaming renders garbage | Partial fields rendered before they are complete | Only render fields present and complete in the partial object |
| Framework "does something weird" and you are stuck | You never looked at the wire | `capture_run_messages()` once per project and once per upgrade |

## Assessment

<AccordionGroup>
<Accordion title="8 concept questions (with answers)" icon="circle-question">

1. *How is `output_type` implemented?* As an extra tool (`final_result`) whose schema is your model; the run ends when the model calls it with valid arguments.
2. *What does `ModelRetry` become on the wire?* A message in the next request containing your error text — so it is a prompt, and should be written like one.
3. *Why inject dependencies?* Testability. A tool that reaches for a global cannot be exercised without the real thing behind it.
4. *What does `TestModel` test?* Wiring — that tools are registered, callable and schema-valid. Not prompt quality.
5. *What does a replay cassette catch that a live eval does not, and vice versa?* Cassettes catch code, serialization and framework regressions deterministically; live evals catch model drift. Neither substitutes for the other.
6. *Why does the framework add ~2.8% tokens?* The output model's schema is sent as a tool definition on every step.
7. *What is a safety-property test and why is it durable?* An assertion about what must *never* happen (no destructive tool on a read-only question); it survives prompt, model and refactor changes because it does not depend on any particular answer.
8. *When should you not adopt the framework?* When you need byte-level control of the request, when you are avoiding dependencies in the request path, or when you have not yet written the loop by hand.
