All week you learned to say what you mean and to choose what the model sees. This lab turns that
into something a team could rely on — and the ticket below is how the job actually arrives.

## The ticket

> **NEX-4188 · Support platform · P1**
>
> Our triage assistant has three prompts, all pasted into the admin dashboard by different people
> over eight months. Last week someone edited one to fix a complaint and our escalation rate went
> up 20% — we think. Nobody can say what the previous text was, which prompt handled which
> escalation, or whether the change actually caused it.
>
> Move the prompts into the codebase, versioned. Build a way to compare two versions on real
> tickets before anything ships. Give us a rollback that takes a minute. And tell us, with
> evidence, whether last week's change should be kept.
>
> Deliverable: the prompt package, the comparison harness, a context budget for the triage
> endpoint, and a one-page report on the disputed change.

**Time box, honestly:** `basic` 4–5 hours. `standard` 10–12 hours. `hard` a further 6–8 hours.

## Tracks

<AccordionGroup>
  <Accordion title="🟢 basic — scaffolded" icon="circle">
  Given: a starter repository with two prompt versions and twenty labelled tickets.

  1. Render both prompts safely — user text in a fenced slot, braces surviving.
  2. Write the three rendering tests from Module 5 (fence order, brace safety, version pinned).
  3. Run both versions on the twenty tickets and print wins / losses / ties.
  4. State which version you would ship, and why — including if the answer is "neither".
  </Accordion>

  <Accordion title="🔵 standard — spec and tests only" icon="circle-dot">
  Build the whole package yourself:

  - `Prompt` objects: name, version, system, template, model; frozen; `id` for traces.
  - A registry selected by environment variable, so rollback needs no deploy.
  - `compare(a, b, cases)` implementing the strict rule: ship only if wins > losses **and**
    losses = 0.
  - `assemble()` from Module 4 with per-section budgets and a `dropped` report.
  - Rendering tests that run with no network; behavioural tests that run on demand.

  **Acceptance:** a hostile ticket ("ignore previous instructions…") cannot escape its fence; a
  ticket containing `{braces}` does not raise; the comparison refuses to ship a change with any
  regression; and every result record carries the prompt id.
  </Accordion>

  <Accordion title="🟣 hard — one more constraint" icon="circle-check">
  Everything in `standard`, plus:

  - **Ablation.** Report the accuracy and tile cost of the prompt with each technique removed in
    turn, and delete whatever is not load-bearing.
  - **Constraint scoring.** Measure obedience to length and format separately from correctness,
    and report all three rates.
  - **A model change.** Re-run the whole suite on a second model. Report what moved, and whether
    you would need a per-model variant.
  </Accordion>
</AccordionGroup>

## Verify yourself

```bash
make verify      # rendering tests, then the twenty-case comparison
```

Your run should show: 0 fence escapes, 0 render exceptions, a printed win/loss/tie table, a
context budget summing to less than the window minus the answer reservation, and a stated
ship / do-not-ship decision.

## Ship it

Push the package with a `README` that answers the ticket's last question in three sentences:
should last week's change be kept, on what evidence, and what you would do next.

## Rubric

| Points | Criterion |
| --- | --- |
| 25 | Prompts versioned, templated, fenced; rendering tests pass |
| 25 | Comparison harness with the strict ship rule, run on twenty real cases |
| 20 | Context budget with an explicit `dropped` report |
| 20 | Evidence-based verdict on the disputed change |
| 10 | Rollback demonstrated in under a minute |

## If you get stuck

- **Braces exploding your template** → Module 5, brace safety test.
- **The comparison always says ship** → check the strict rule; any loss blocks.
- **Budgets never trigger** → your tile counter is probably counting characters.
- **Both versions score identically** → your twenty cases are too easy; add the ones that
  actually generated complaints.
