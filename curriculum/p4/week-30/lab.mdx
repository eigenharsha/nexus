## The ticket

> **PLAT-2038 · Platform Engineering · P1**
>
> Median time to resolution on our checkout-latency alerts is 41 minutes, of which roughly 19 is
> one engineer opening five dashboards and finding the right runbook. We want that 19 minutes back.
>
> Build an assistant that, when an alert fires: confirms it is real, gathers deploy history,
> connection-pool state and cache metrics in parallel, retrieves the relevant runbook, proposes a
> remediation with its evidence, and — **only after a human approves** — executes it and verifies
> recovery.
>
> Hard requirements from the platform review:
> it must survive a pod eviction mid-run without losing work or repeating a side effect; it must
> stop itself if it stops making progress; it must never execute anything a human has not seen the
> resolved arguments for; and every action must be reconstructable from an audit log twelve months
> later.
>
> Deliverable: the system, an architecture document with a blast-radius table, and a recorded demo
> of it being killed and resuming.

**Time box, honestly:** `basic` 4 hours · `standard` 14–18 hours · `hard` a further 10–12 hours.

<Tabs>
<Tab title="basic">

### What you build

A three-node LangGraph — plan → analyze → report — with in-memory state.

**Given to you** (`labs/p4/week-30/starter/basic/`): a seeded Postgres with 200 synthetic incidents,
a fake metrics API, a 40-document runbook corpus, and `test_basic.py`. About 60% written.

**You write:**

<Steps>
<Step title="The state schema">
A `TypedDict` with at least: `ticket_id`, `severity`, `evidence` (with an **append** reducer), `hypothesis`, `attempts`, `node_trail`. Getting the reducer right is most of this track.
</Step>
<Step title="Three nodes">
`plan` classifies the incident; `analyze` fetches evidence from two sources; `report` formats the output. Each returns only the keys it changes.
</Step>
<Step title="One conditional edge">
After `analyze`: enough evidence goes to `report`, otherwise back to `analyze`, with an attempt cap of 3 and an explicit give-up path.
</Step>
<Step title="Prove the shape">
`app.get_graph().draw_mermaid()` output committed, and matching a snapshot test.
</Step>
</Steps>

**Acceptance:** `make verify TRACK=basic` — 11 tests, mocked model, ~3 s. Two of them check that
evidence accumulates rather than being replaced; that is the reducer test and it is the point of
the track.

<Info>~60% of the code is written for you. TODOs are marked.</Info>

</Tab>
<Tab title="standard">

### What you build

The real system.

**Part A — the graph**

<Steps>
<Step title="Typed state with real reducers">
Decisions as fields. Evidence merged with de-duplication on `(source, query)` — not a plain append, because a replayed node must not double-add.
</Step>
<Step title="Planner, analyst, executor">
Three roles with explicit contracts between them (Pydantic models, `must_return` fields, a `could_not_determine` channel). Parallel evidence gathering.
</Step>
<Step title="RAG over runbooks">
Hybrid BM25 + dense on pgvector with reciprocal-rank fusion and a cross-encoder re-rank (Week 28). Report recall@5 on a labelled alert-to-runbook set of at least 60 pairs.
</Step>
<Step title="MCP-served access">
Two servers: read (metrics, deploys, logs, database — read-only roles) and write (three verbs only, reachable only from `execute`). Separate credentials. Week 29 M4's sandbox rules apply.
</Step>
</Steps>

**Part B — durability**

<Steps>
<Step title="Postgres checkpointing">
Connection pool, autocommit, namespaced thread ids. Prove resume with a test that kills and restarts the process.
</Step>
<Step title="Human approval">
`interrupt()` before any remediation, showing the resolved arguments and the blast radius. `approved_by` recorded in state. Decline is a routed outcome, not an exception.
</Step>
<Step title="Idempotent effects">
Derived idempotency keys (`uuid5` over thread and intent), an outbox, and a worker using `FOR UPDATE SKIP LOCKED`. Rollback command recorded before execution.
</Step>
</Steps>

**Part C — guards**

Four budgets set from your own p99. Circuit breakers on all three dependencies with
model-actionable error messages. A novelty-based livelock detector with its recall and
false-positive rate measured against hand-labelled runs. Structured escalation with the five
required fields.

**Part D — the document**

Architecture doc: autonomy per node, blast-radius table (six columns, "what stops it" naming code),
staged rollout with numeric gates, never-automate list, data and trust boundaries.

<Info>Spec and tests only. `make verify TRACK=standard` runs 38 tests in under 12 seconds, no API calls.</Info>

</Tab>
<Tab title="hard">

### The constraints the standard solution fails

<Steps>
<Step title="Survive 20 randomly-timed process kills">
`SIGKILL` at a uniformly random point in each of 20 runs. Assert: no lost work (every run completes after restart), **no duplicated side effects** (exactly one settled action per thread), and total cost within 15% of the crash-free baseline. Report the replay overhead — ours was 11.3%.
</Step>
<Step title="Add a critic and prove it helped">
A critic agent on the proposed remediation, with a rubric and a stopping rule. Measure quality against the no-critic baseline on the same 40 incidents, scored by two humans, with inter-rater agreement reported. **You are permitted to conclude it did not help** — but you must show the numbers either way.
</Step>
<Step title="Full failure-injection suite green">
Six injected failures — tool timeout, malformed output, livelock, budget exhaustion, dependency returning 200 with an empty body, contradictory instructions — each asserting the correct halt reason, the detection step, and the escalation contents.
</Step>
<Step title="Kill the worker too">
The nastiest case: kill the outbox worker between its API call and its status update. Show how the system recovers, and if it cannot fully recover, show the reconciliation query that detects it and say honestly what a human has to do.
</Step>
</Steps>

<Warning>
There is a constraint here that the `standard` solution fails: a standard-track charge path with a
per-process idempotency key produces duplicates under random kills. So does a livelock detector
tuned on identical strings when the injected failure paraphrases itself. Both have to be engineered.
</Warning>

</Tab>
</Tabs>

## Verify yourself

```bash
cd labs/p4/week-30
make verify TRACK=basic       # 11 tests, mocked model, ~3 s
make verify TRACK=standard    # 38 tests, mocked model, ~12 s
make verify TRACK=hard        # 38 + chaos + failure injection

make chaos N=20               # 20 SIGKILLs at random points; writes chaos/report.md
make inject                   # the six failure injections; asserts halt reasons
make bench                    # 40 incidents, with and without the critic
make recall                   # runbook retrieval recall@5, four configurations
```

`make chaos` must report `duplicate_effects: 0` and `lost_runs: 0`. Any other value is a fail
regardless of what the unit tests say.

## Start here — your first 30 minutes

The requirements above are the *finished* picture. Do not try to hold all of it at once. Do these in
order; each step ends somewhere you can stop and still be making progress.

<Steps>
<Step title="Run the starter and expect RED (5 min)">
```bash
cd labs/p4/week-30
make verify TRACK=basic
```
A red result is success here — it means the harness runs and the tests can see your code. If you get
something that is *not* a test failure (a missing command, an import error), fix that first; it is an
environment problem, not a lab problem.
</Step>

<Step title="Read one test before writing any code (5 min)">
The tests are the real specification — everything written above is prose describing them. Where the
prose and a test disagree, **the test wins**. Open the first one and read it properly.
</Step>

<Step title="Make ONE test pass (15 min)">
Implement the smallest thing the first failing test needs. Run `make verify` again. One more test
passing is the whole goal of your first half hour.

That is the loop for the entire lab: one test, one function, run, repeat. Do not write five functions
and then run for the first time — when it fails you will not know which one broke it.
</Step>

<Step title="Finish the basic track">
Work the `TODO`s in the order they appear. They are in dependency order, not alphabetical.
</Step>

<Step title="Only then read the standard requirements">
With `basic` green you have something that works. `standard` extends it; it does not replace it.
</Step>

<Step title="Ship it">
Push to a public repo with the README. That artifact is what you link from a CV — it outlasts the grade.
</Step>
</Steps>

<Tip>
**Are you on track?** After 30 minutes you should have: a red run, one test read properly, and one
test passing. If you have read for 30 minutes and run nothing, you are reading too much — go run the
starter.
</Tip>

## Stuck? Open these in order

Each reveals a little more than the last. Try the level above before opening the next — a hint you
did not need costs you nothing, but an answer taken too early costs you the lesson.

<AccordionGroup>
<Accordion title="Nudge — I don't know where to start" icon="lightbulb">
Find the **first** failing test and implement only what that one test needs. Ignore the rest of the
lab until it is green. If you cannot tell which test fails first, run
`make verify TRACK=basic` and read the top of the output, not the bottom.
</Accordion>

<Accordion title="Hint — my graph resumes after a crash but repeats a side effect" icon="lightbulb">
Checkpointing restores state, not the outside world. If the node charged a card before the crash, resuming charges it again.

**What to do instead:** Make side-effecting tools idempotent with a key derived from the intent — `uuid5(thread_id, intent)`, not `uuid4()`. A random key is a new key every attempt, which is exactly the bug. The week measures 6 double charges in 20 kills with random keys, and 0 with derived ones.
</Accordion>

<Accordion title="Hint — my multi-agent system is slower and worse than one agent" icon="lightbulb">
That is a real and common result, not a failure of your implementation. Coordination costs tokens and multiplies the places an error can enter.

**What to do instead:** Benchmark against a single strong agent on the same tasks and report cost per *successful* task. The week's own head-to-head has the single agent winning; be willing to conclude the same.
</Accordion>

<Accordion title="Hint — my agent burns the token budget on one run" icon="lightbulb">
No budget enforcement, or enforcement only at the end. A stuck agent will happily spend everything before anyone notices.

**What to do instead:** Track tokens, dollars, wall-clock and step count in graph state, and check them at every node boundary. Fail loudly at the limit rather than silently continuing.
</Accordion>

<Accordion title="I have a real attempt that fails — show me the full solution" icon="lock">
Open the [reference solution](/solutions/p4/week-30/lab).

Use it properly: read only far enough to get unstuck, then close it and return to your own code.
Afterwards, diff your version against it — the differences are the lesson, and yours is not
automatically the worse one.

If you have not yet written code that fails, do not open it. Reading a solution before struggling
with the problem feels exactly like learning, and is the most reliable way to finish this course
having learned nothing.
</Accordion>
</AccordionGroup>

## Rubric

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Correctness | fails tests | happy path | branches, bounded cycles, give-up paths all exercised | six injected failures each handled with the right halt reason |
| Durability | no checkpointer | checkpoints, resume untested | resume tested by hand | 20 random kills, zero duplicate effects, replay overhead measured |
| Code quality | works | readable | typed state, reducers documented, dependencies injected | reducers de-duplicate; safety-property tests; graph diagram diffed in CI |
| Measurement | none | some numbers | benchmark table with cost per successful task | head-to-head with two scorers and agreement reported; detector recall and FP rate |
| Design | no document | a README | architecture doc with autonomy levels | blast-radius table where "what stops it" names code, plus a never-automate list |

Score 12+/15 before you call it done. **Durability below 2 is a fail regardless of total** — a
system that loses work or repeats side effects is not a system, and this lab exists to prove you can
build one that does not.
