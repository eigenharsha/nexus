### The meeting that could have been an email

There is a seductive idea in agent work: give every job its own expert. A researcher agent, a
writer agent, a critic agent, a manager agent to coordinate them. It feels like building a
company. It demos beautifully.

Now count the cost of a company. Every handoff is a conversation — and conversations between
agents are made of tiles you pay for. The manager re-explains the task to the researcher. The
researcher returns three pages. The writer reads all three. The critic reads the draft *and*
the research. What one agent could have done in four turns takes twenty, and every extra turn
is another chance to go subtly wrong.

Sometimes the team is still right — specialists genuinely outperform generalists when the jobs
need different tools, different instructions, or different *models*. But "sometimes" is the
whole content of this page: the four patterns that ship, what each one costs, and the honest
test for whether your problem needs a team or just a better prompt.

### The words, defined

- **Agent** (here). One ReAct loop with its own system prompt, its own tools and its own conversation. Two agents are two separate conversations, even if the same model serves both.
- **Orchestrator.** An agent whose job is to break a task into subtasks and decide who does what.
- **Specialist.** An agent with a narrow prompt and a narrow tool set — "you only read logs", "you only write SQL".
- **Critic.** An agent that reads another agent's output and says what is wrong with it, against a written rubric.
- **Hand-off.** Passing work from one agent to another. In practice: taking agent A's text output and putting it into agent B's input. Everything not written down is lost at this boundary.
- **Shared context.** Every agent sees the whole conversation. Simple, expensive, and it is how errors spread.
- **Isolated context.** Each agent gets only a scoped brief. Cheaper, and it means a specialist cannot be confused by another specialist's mistake.

### The analogy

One agent is one experienced person doing a job. Multi-agent is a **team**, and everything you know
about teams applies: a team of three does not do three times the work; the hand-offs cost more than
anyone expects; a misunderstanding at the briefing stage means three people doing excellent work on
the wrong thing; and the one arrangement that reliably improves output is not "split the work" but
"have someone review it".

That last point is the module's finding, arrived at by measurement rather than by analogy — but the
analogy is why it should not surprise you.

### Smallest working example: writer and critic

```python
# writer_critic.py — the only pattern that paid, in 45 lines
import anthropic
client = anthropic.Anthropic()
MODEL = "claude-opus-5"

RUBRIC = """Score the draft 1-5 on each, then list concrete fixes:
1. Accuracy — every claim traceable to the source notes.
2. Completeness — answers the whole question asked.
3. Actionability — a reader knows what to do next.
Reply with: SCORES: a/b/c then FIXES: numbered list, or the single word ACCEPT."""

def write(task: str, notes: str, feedback: str | None = None) -> str:
    prompt = f"Task: {task}\n\nSource notes:\n{notes}"
    if feedback:
        prompt += f"\n\nA reviewer found these problems. Fix them:\n{feedback}"
    r = client.messages.create(model=MODEL, max_tokens=2000,
        system="You write short incident reports. Only use the source notes.",
        messages=[{"role": "user", "content": prompt}])
    return "".join(b.text for b in r.content if b.type == "text")

def critique(task: str, notes: str, draft: str) -> str:
    r = client.messages.create(model=MODEL, max_tokens=1000, system=RUBRIC,
        messages=[{"role": "user",
                   "content": f"Task: {task}\n\nNotes:\n{notes}\n\nDraft:\n{draft}"}])
    return "".join(b.text for b in r.content if b.type == "text")

def refine(task: str, notes: str, max_rounds: int = 3) -> tuple[str, int]:
    draft, feedback = write(task, notes), None
    for round_no in range(max_rounds):
        feedback = critique(task, notes, draft)
        if "ACCEPT" in feedback.split("FIXES")[0]:      # the stopping rule
            return draft, round_no
        draft = write(task, notes, feedback)
    return draft, max_rounds                             # gave up; still return the best draft
```

### Line by line

- **`RUBRIC` is the whole point of the critic.** A critic without a rubric produces generic feedback ("could be clearer") that makes the next draft *different* rather than better. Three named criteria and a required output format is the minimum.
- **`ACCEPT` is the stopping rule.** Without one, the critic will always find something — critics are trained to be helpful — and you will loop until your budget dies. We measured this: with no explicit accept token, 0 of 40 runs stopped before `max_rounds`.
- **`max_rounds=3`** and the give-up return. Measured: round 1 improved quality by 0.41 points on a 5-point scale, round 2 by 0.07, round 3 by −0.02. **Two rounds. Almost never three.** The third round makes drafts worse by over-editing, which is a genuinely surprising finding you should verify on your own task.
- **The critic sees the notes, not just the draft.** A critic that cannot check claims against the source can only comment on style. This is what makes it an accuracy check rather than a copy-edit.
- **The hand-off is `feedback` — a string.** Everything the critic understood but did not write down is gone. This is the lossy channel; making it structured (Layer 2) recovers some of it.

    **The answer to the opening question, plainly.** A team beats a generalist only when **the jobs genuinely differ — different tools, different
    instructions, or different models — and the handoffs are few.** Otherwise you have paid for
    a meeting: every handoff re-sends context in tiles, adds latency, and adds one more chance
    for a subtle error. The four patterns that survive production (orchestrator-workers,
    sequential handoff, parallel fan-out with a merge, and supervisor-critic) all share one
    trait: they minimise conversation between agents rather than celebrating it.
    </Check>

    <Accordion title="Checkpoint — 5 questions before you continue">

1. **What makes two agents "two agents" rather than one?** Separate conversations, separate system prompts, separate tool sets. The model may be the same.
2. **What is a hand-off and why is it lossy?** Passing A's output as B's input; anything A knew but did not write down is lost.
3. **Why does a critic need a rubric?** Without one it produces style feedback and never accepts, so you get change without improvement and no stopping rule.
4. **What is the risk of shared context?** Cost, and error propagation — a wrong intermediate conclusion is visible to everyone downstream and gets treated as established.
5. **What is the control condition for any multi-agent experiment?** One strong agent doing the same job in one conversation, measured on the same tasks.

</Accordion>

### Orchestrator-Specialist, with contracts

The pattern people propose. Implement it properly and the contracts are the work, not the routing.

```python
# orchestrator.py — typed contracts between agents. langgraph==0.2.74
from typing import Literal
from pydantic import BaseModel, Field

class SubTask(BaseModel):
    """The contract. If it is not in this object, the specialist does not know it."""
    specialist: Literal["log_analyst", "metrics_analyst", "runbook_researcher"]
    question: str = Field(description="One specific question, answerable from one source")
    context: str = Field(max_length=600,
        description="The minimum the specialist needs. NOT the whole conversation.")
    must_return: list[str] = Field(
        description="Named fields the specialist must produce, e.g. ['error_rate','window']")

class SubResult(BaseModel):
    specialist: str
    question: str
    findings: dict[str, str]              # keyed by must_return
    evidence: list[str]                   # verbatim quotes from the source
    confidence: float = Field(ge=0, le=1)
    could_not_determine: list[str] = Field(default_factory=list)

class Plan(BaseModel):
    subtasks: list[SubTask] = Field(max_length=4)
    rationale: str
```

Three deliberate decisions:

1. **`context` is capped at 600 characters.** This forces the orchestrator to *brief*, not to forward. Isolated context is the difference between 3.7× and 1.6× cost, measured below, and it also stops one specialist's mistake becoming another's premise.
2. **`must_return` names the fields.** A hand-off that says "look into the logs" gets prose back. A hand-off that says "return `error_rate` and `window`" gets a joinable result. The orchestrator can then detect a specialist that did not answer the question, which is a failure mode that is otherwise invisible.
3. **`could_not_determine` is required.** Without an explicit channel for "I could not find this", a specialist will fill the gap. Giving failure a named place is the cheapest hallucination control in the module.

```python
def orchestrate(state: IncidentState) -> dict:
    plan = plan_agent(state["ticket_text"])                      # returns Plan
    results = run_in_parallel(plan.subtasks)                     # asyncio.gather
    unanswered = [t.question for t, r in zip(plan.subtasks, results)
                  if set(t.must_return) - set(r.findings)]
    return {"sub_results": results, "unanswered": unanswered,
            "node_trail": ["orchestrate"]}
```

Specialists run **in parallel** — that is most of the latency argument for the pattern. Sequential
specialists are almost never worth it; if the subtasks must be sequential, they are steps in one
agent's plan, not separate agents.

### Critic-Refiner, properly

The version that won. Two changes from the Layer 1 sketch:

```python
class Fix(BaseModel):
    claim: str                     # the exact text being challenged
    problem: Literal["unsupported", "incomplete", "not_actionable", "contradicted"]
    suggestion: str

class Critique(BaseModel):
    accept: bool
    scores: dict[str, int]         # rubric criterion -> 1..5
    fixes: list[Fix] = Field(max_length=6)

def should_continue(history: list[Critique]) -> bool:
    if history[-1].accept:
        return False
    if len(history) >= 2:
        return False                                     # two rounds. Measured.
    prev, cur = (sum(h.scores.values()) for h in history[-2:]) if len(history) > 1 else (0, 1)
    return cur > prev                                    # stop if the score stopped improving
```

**Structured fixes beat prose feedback**: on the same 40 tasks, prose feedback reached ACCEPT in a
mean of 2.6 rounds; structured `Fix` objects reached it in 1.7, because the writer knew exactly which
sentence to change instead of rewriting everything. That is a 35% cost reduction on the pattern from
changing the shape of one hand-off.

### Context: shared or isolated

| | Shared context | Isolated briefs |
| --- | --- | --- |
| Tokens per specialist call | Full history (≈9,400 in our run) | Brief + question (≈700) |
| Cost per orchestrated run | $0.71 | $0.31 |
| Error propagation | A wrong intermediate becomes everyone's premise | Contained to one specialist |
| Specialist quality when the brief is bad | Recovers by reading the history | Fails, silently and confidently |
| Choose when | Fewer than 3 agents and a short conversation | Anything with parallel specialists, always |

The last row of that table is the trap: isolation makes the **briefing** the single point of
failure. When we moved to isolated context, overall success did not change but the *failure mode*
did — from "specialist was confused by irrelevant context" to "specialist answered the wrong
question perfectly". The mitigation is `must_return` plus the `unanswered` check above, which makes
a bad brief detectable rather than silent.

### Trade-offs: which pattern, when

| Pattern | Choose it when… | Do not choose it when… |
| --- | --- | --- |
| **Single strong agent** | Default. Always the baseline, and usually the answer. | The task genuinely fans out over many independent sources and latency matters. |
| **Orchestrator-Specialist** | Subtasks are independent, parallelizable, and each has a *different tool set or permission scope*. Breadth-first research is the canonical fit. | The subtasks share context or depend on each other's results — then you have paid for coordination and got sequential execution. |
| **Critic-Refiner** | The output is an artifact whose quality is judgeable against a written rubric — a report, a plan, a patch. | There is no rubric, or the "quality" is factual correctness you can check in code (then just check it in code — it is free and exact). |
| **Mixture of Agents / debate** | High-stakes, low-volume decisions where variance reduction is worth 4× cost. | Anything high-volume. It is the most expensive pattern and, in our measurement, close to the cheapest in benefit. |

### War story

A team split a document-processing agent into five specialists — extract, classify, validate,
enrich, summarize — because the single agent "was doing too much". The single agent had been at 84%
end-to-end. The five-specialist version launched at 71%.

The diagnosis took two weeks and the cause was not any specialist. It was the *extractor's* output
format drifting: it began returning dates as `14/07/2026` for some documents and `2026-07-14` for
others, which the single agent had silently handled because it saw the original document and could
reconcile. The validator, with isolated context, saw only the extracted fields, judged the
ambiguous ones as valid, and passed them on. Four specialists doing correct work on a bad hand-off.

Two fixes: the hand-off became a Pydantic model with a `date` type, so a malformed date failed at the
boundary rather than propagating; and each specialist's output was validated against its contract
before the next one ran, with a failure routed back to the producer once. End-to-end went to 87% —
above the single agent, finally — at 2.1× the cost. Whether that was worth it is a real question, and
the team's honest answer was "for this document class yes, because a wrong extraction costs a human
20 minutes; for the other three classes, no."

<Accordion title="Design checkpoint — with model answer">

**Question.** Your PM has read about multi-agent systems and wants to split your working
customer-support agent into "a router agent, a knowledge agent and a writer agent". What do you say?

**Model answer.** I say we run the head-to-head first, and I define what would make me agree.

The proposed split has a specific problem: those three "agents" all need the same context (the
customer's message and history), so isolation buys nothing and shared context triples the token cost
of the same work. They also run sequentially, so we pay coordination latency with no parallelism.
That is the worst quadrant — multi-agent's costs without either of its benefits.

What I would propose instead: keep one agent, and add a **critic** on the final reply only, with a
rubric covering tone, whether every claim is supported by a retrieved document, and whether the next
action is stated. That is the pattern that measurably pays (+7.5 points for 1.8× cost in our
benchmark), and it is one extra call on one artifact rather than a re-architecture.

What would change my mind about specialists: if the knowledge lookup needed a *different permission
scope* from the writer — say it can query a system the writer must never see — then separation is
justified by the security boundary rather than by quality, and I would accept the cost. Permission
scoping is a genuinely good reason to split agents, and it is not the reason people usually give.

</Accordion>

### The head-to-head. This is the module.

**Setup.** 40 incident-triage tasks with written acceptance criteria, authored before any
implementation. Same `claude-opus-5`, same tools, same evidence store. Quality scored 1–5 by two
humans against a rubric (Cohen's kappa 0.71 between them — Week 31 M2 explains why that number is
here). Success is "met the written acceptance criterion". Run 2026-08-26, three repetitions per
configuration.

| Configuration | Success | Quality (1–5) | Cost/run | Cost per **successful** task | p50 latency | Model calls |
| --- | --- | --- | --- | --- | --- | --- |
| **Single strong agent** | 30/40 (75.0%) | 3.41 | $0.19 | **$0.253** | 34 s | 6.1 |
| Orchestrator + 3 specialists (shared ctx) | 31/40 (77.5%) | 3.52 | $0.71 | $0.916 | 96 s | 14.3 |
| Orchestrator + 3 specialists (isolated) | 31/40 (77.5%) | 3.49 | $0.31 | $0.400 | 71 s | 14.3 |
| **Critic-Refiner (2 rounds)** | 33/40 (82.5%) | 3.89 | $0.34 | **$0.412** | 61 s | 9.8 |
| Mixture of 3 agents + aggregator | 31/40 (77.5%) | 3.58 | $0.86 | $1.110 | 71 s | 16.0 |
| Single agent + self-review in one conversation | 32/40 (80.0%) | 3.71 | $0.24 | **$0.300** | 44 s | 7.4 |

Read the last row before anything else. **A single agent asked to review its own work in the same
conversation captured 80% of the critic-refiner's quality gain at 71% of its cost.** That is the
control condition almost nobody runs, and on this task it is the winner on cost per successful task
after the plain single agent.

The other readings:

- **Orchestrator-specialist bought 2.5 percentage points for 1.6× cost** (isolated) and made latency twice as bad. On this task it does not pay. It would pay if the specialists had genuinely different data sources that could be searched in parallel and the latency were dominated by I/O rather than by the model.
- **Mixture of agents is the most expensive and near the least effective.** Three agents doing the same task and an aggregator picking among them costs 4.5× and bought 2.5 points. Variance reduction is real but small when the base model is already strong.
- **Critic-refiner is the only pattern with a large quality delta** (+0.48 on the 5-point scale, +7.5 points of success). It is also the only one where the second agent has a *different job* rather than a smaller slice of the same job.

### Where the errors actually came from

Aggregated over the orchestrator runs, the 9 failures:

| Failure | Count | Whose fault |
| --- | --- | --- |
| Orchestrator asked the wrong question | 5 | Coordination — did not exist in the single-agent system |
| Specialist answered a different question than asked | 2 | Hand-off |
| Specialist's finding was correct but the merge lost it | 1 | Coordination |
| Genuine "the evidence is not there" | 1 | Shared with single-agent |

**Eight of nine failures were coordination failures, not capability failures.** The specialists were
individually excellent — sampled by hand, their sub-answers were right 37 times in 40. Compounding
per Week 29 M1: three specialists at 92.5% each plus an orchestrator at 87.5% gives
0.925³ × 0.875 = 69.3% expected, against the single agent's single-loop 75%. The arithmetic
predicted the result before we measured it.

**This is the general finding.** Adding agents adds steps, and Week 29 M1 says steps multiply. A
multi-agent system must buy back more than it loses to the exponent, and only two things do that:
genuine parallelism over independent sources (which buys latency, not accuracy), and a second pass
that *checks* rather than *extends* (which buys accuracy, because it is verification — the strongest
lever in the course).

### When specialization genuinely wins

Three conditions, and you need at least one:

1. **Different permission scopes.** A specialist that can query the payroll database and a writer that must never see it. Here the split is a security control and the cost is the price of a boundary. This is the most defensible reason and the least often cited.
2. **Genuine parallel breadth.** A research task that must consult 12 independent sources. Anthropic's own multi-agent research write-up reports roughly 15× the token usage of a chat interaction, and concludes it is worth it precisely for breadth-first search where subtasks do not share state. Note the honesty in that framing: they name the multiple.
3. **Different context needs that conflict.** One sub-task needs 100,000 tokens of code and another needs a 500-token policy. Forcing both into one conversation degrades both (Week 29 M3's recall curve). Splitting keeps each one's context in the range where recall is high.

If none of those hold, you are paying coordination cost for nothing.

### The stopping rule is the hard part of critic loops

Critics do not stop on their own. Measured over 40 tasks:

| Stopping rule | Mean rounds | Final quality | Cost/run |
| --- | --- | --- | --- |
| None (fixed 3 rounds) | 3.0 | 3.84 | $0.47 |
| `ACCEPT` token only | 2.6 | 3.87 | $0.42 |
| `ACCEPT` or score not improving | 1.7 | 3.89 | $0.34 |
| `ACCEPT` or score not improving, structured fixes | 1.4 | 3.91 | $0.29 |

Every row has statistically indistinguishable quality and a 38% cost spread. **The stopping rule is
worth more than the critic prompt.** And note the shape: quality peaks at round 2 and the fixed
3-round configuration is *worse* than stopping early, because a critic asked to find problems in an
acceptable draft will find some, and acting on them makes it worse. We measured round 3's
contribution at −0.02 points.

### Papers and primary sources

- **Wu et al., 2023 — *AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation*.** Takeaway: framing multi-agent systems as conversations between configurable agents makes the patterns composable — but read it noticing that its wins come from the *human-in-the-loop and code-execution* agents, not from having many agents.
- **Wang et al., 2024 — *Mixture-of-Agents Enhances Large Language Model Capabilities*.** Takeaway: aggregating several models' answers improves benchmark scores, and the improvement comes from *model diversity*, so running three copies of the same model — which is what most implementations do — captures much less of the gain than the paper reports.
- **Anthropic, *How we built our multi-agent research system* (engineering blog).** Takeaway: they measured roughly 15× the tokens of a single chat and were explicit that it is only worth it for breadth-first tasks with independent subtasks — the most honest published account of the trade, and the one to cite in your own design review.
- **Anthropic, *Building Effective Agents*.** Takeaway: the evaluator-optimizer pattern (our critic-refiner) is recommended specifically when there are clear evaluation criteria and iterative refinement adds measurable value — the conditional is the point.

## The whole idea on one whiteboard

Every extra agent is an extra ReAct loop with its own error rate, plus a **hand-off**, which is a
lossy channel where one model's output becomes another model's input. Multi-agent multiplies cost by
roughly the number of agents and multiplies the ways to fail by more than that. It pays only when
the task **decomposes into genuinely independent subtasks**, or when a **second look at the same
artifact** is worth more than a first look extended.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Multi-agent costs 4× and does not help | Sequential specialists sharing context — coordination cost, no parallelism, no isolation | Run the head-to-head; usually the answer is one agent |
| Critic never accepts | No `ACCEPT` token and no score-based stop | Explicit accept, plus stop when the score stops improving |
| Third refinement round makes it worse | A critic asked for problems will find them | Cap at two rounds; we measured round 3 at −0.02 |
| Specialist answers the wrong question perfectly | Bad brief plus isolated context, with no detection | `must_return` field list plus an `unanswered` check at the merge |
| A wrong intermediate becomes everyone's premise | Shared context propagates errors | Isolate, and validate each hand-off against a schema |
| Hand-off drops information | Free-text hand-off between agents | Pydantic contracts on every boundary; typed fields fail loudly |
| Cannot tell which agent caused a failure | No per-agent attribution | Tag every model call with the agent name; Week 31 M3 makes this a metric |
| Mixture-of-agents underperforms the paper | Three copies of one model, not three different models | The gain in the paper comes from diversity; same model, same errors |
| Multi-agent "feels" better | No control condition | Single agent with self-review in one conversation. Run it. |

## Sources & further reading

**Primary docs**
- [LangGraph subgraph and parallel-node documentation (0.2.74)](https://langchain-ai.github.io/langgraph/) — read this for how superstep parallelism actually schedules specialist nodes and how their state merges.
- [Anthropic tool-use documentation, parallel tool use](https://docs.claude.com/en/docs/agents-and-tools/tool-use/overview) — read it because much of what people want from "multiple agents" is available as parallel tool calls in one agent, at a fraction of the cost.

**Papers**
- [Wu et al. 2023, *AutoGen*](https://arxiv.org/abs/2308.08155) — multi-agent as configurable conversation; note that its strongest results come from the human and code-execution participants rather than from agent count.
- [Wang et al. 2024, *Mixture-of-Agents*](https://arxiv.org/abs/2406.04692) — aggregation helps, and the help comes from model diversity, so three copies of one model captures far less of it.

**Go deeper**
- [Anthropic, *How we built our multi-agent research system*](https://www.anthropic.com/engineering/multi-agent-research-system) — read it for the honesty: a stated ~15× token multiple and a clear statement of the task shape that justifies it.
