## The mental model

An embedding model is trained so that **text that answers a question lands near that question** in
vector space. Not "similar text lands near similar text" — that is a different objective and it
produces a different model. Retrieval quality is entirely about whether that training objective
matches your queries and your documents.

    ### What an embedding model is trained to do

    Week 25 introduced embeddings as the lookup table inside a language model. A **retrieval
    embedding model** is a different object with a different job: given a piece of text, produce one
    fixed-length vector such that **texts about the same thing land close together**.

    The training objective is worth knowing because it explains the failures. These models are
    trained with **contrastive learning**: show the model a query and its correct passage (a
    *positive pair*), plus a batch of unrelated passages (*negatives*), and adjust the weights so the
    positive pair's vectors move together and the negatives move apart. Do that over hundreds of
    millions of pairs — questions and their answers, titles and their articles, code and its
    docstrings — and the geometry emerges.

    Two consequences follow directly:

    - **The model is only good at the kinds of pairs it was trained on.** A model trained mostly on
      web question-answer pairs will do well on questions and less well on "find the clause similar
      to this clause".
    - **"Similar" means similar *in the training objective's sense*.** For most retrieval models
      that means "answers this", not "shares vocabulary" and not "same topic".

    ### Bi-encoders

    The architecture used for retrieval is a **bi-encoder**: the query and the document go through
    the model *separately* and produce two independent vectors, which are then compared with a
    single cheap operation.

    That separation is the entire reason retrieval is possible at scale. Because a document's vector
    does not depend on the query, you compute all 47,300 of them once, at ingest, and at query time
    you only embed the query and do 47,300 dot products.

    The alternative — a **cross-encoder**, which feeds query and document *together* into one model
    and outputs a relevance score — is more accurate and cannot be precomputed. Week 28 Module 4
    uses it as a re-ranker over the top 50 candidates, which is the only way it is affordable.

    ### Similarity: cosine, dot product, Euclidean

    **Cosine similarity** is the cosine of the angle between two vectors: 1.0 for the same
    direction, 0.0 for perpendicular, −1.0 for opposite. It ignores magnitude, which is what you
    want — a long passage and a short one about the same thing should match.

    ```
    cos(a, b) = (a · b) / (|a| · |b|)
    ```

    **If you normalise every vector to length 1 first, cosine similarity is just the dot product.**
    That is why every retrieval pipeline normalises: it turns the similarity computation into one
    matrix multiply, which is the fastest operation a computer does.

    Euclidean (L2) distance also works, and on normalised vectors it is *monotonically related* to
    cosine — ranking by one gives the same order as ranking by the other. So on normalised vectors
    the choice does not matter for ranking. On un-normalised vectors it matters enormously, and
    mixing the two is a real bug: normalise at ingest, normalise at query, assert it.

    ### The analogy

    A library where every book has been assigned a spot on a very large field, and books about the
    same thing are placed near each other. Nobody wrote the coordinates down by hand; a librarian
    walked around for years moving books that people looked for together closer together.

    A bi-encoder is that field. When you have a question, you work out where in the field your
    question *belongs*, walk to that spot, and pick up what is nearby. You never compare your
    question to each book individually — you compare positions.

    ### Smallest working example


    ```python
    # similarity_matrix.py
    from sentence_transformers import SentenceTransformer
    import numpy as np

    model = SentenceTransformer("BAAI/bge-small-en-v1.5")     # 33.4M params, 384 dims

    texts = [
        "How do I return a faulty product?",                       # a question
        "Returns of defective goods must be reported within 14 days.",   # its answer
        "Returns of non-defective goods are accepted within 45 days.",   # a near-miss
        "Our warehouse operates Monday to Friday, 8am to 6pm.",          # unrelated
        "How do I reset my password?",                                   # another question
        "Click 'Forgot password' on the sign-in page to receive a reset link.",
    ]

    E = model.encode(texts, normalize_embeddings=True)      # (6, 384)
    S = E @ E.T                                             # cosine, because normalised

    print("      " + "".join(f"{i:>7}" for i in range(6)))
    for i, row in enumerate(S):
        print(f"{i:>4}  " + "".join(f"{v:7.2f}" for v in row))
    ```

    ### Line-by-line walkthrough

    - `normalize_embeddings=True` — scales each vector to length 1. Without it, `E @ E.T` is a raw
      dot product and the diagonal is not 1.00, which is your check that normalisation happened.
    - `E @ E.T` — 6×384 times 384×6 gives 6×6, every pair at once. This is the same operation as
      Week 25's attention scores, and at Module 4's scale it is the same operation a vector index
      is trying to avoid doing exhaustively.
    - **Read row 0.** The question "how do I return a faulty product?" scores 0.78 against its
      correct answer (row 1) and 0.71 against the *wrong* answer about non-defective goods (row 2).
      Only 0.07 apart. That gap is what your whole retrieval system is trying to widen, and it is
      why Week 28's re-ranking exists.
    - **Read the 1–2 pair: 0.83.** The two answers score higher against *each other* than either
      does against the question. That is the model doing what it was trained to do — those two
      sentences are extremely similar text. It is also a warning: your top-k will fill up with
      near-duplicate passages unless you handle it (Week 28 M4's MMR).
    - Rows 4 and 5 at 0.74 confirm the model handles a completely different topic cleanly. Row 3 is
      unrelated to everything and sits at 0.28–0.36, which is roughly this model's floor. **Note
      that the floor is not 0.** Cosine similarities from these models live in a narrow band, and a
      raw threshold like "above 0.5 is relevant" is meaningless without calibration on your corpus.

    <Accordion title="Checkpoint — 5 questions before you continue">
    1. **What is a bi-encoder and why does retrieval need one?** Query and document are embedded independently, so document vectors are precomputed once at ingest.
    2. **Why normalise embeddings?** So cosine similarity becomes a plain dot product — one matrix multiply for all pairs.
    3. **What are these models actually trained to do?** Contrastive learning on positive pairs (query, correct passage) against in-batch negatives.
    4. **Why is a raw similarity threshold like 0.7 meaningless without calibration?** Unrelated English passages already score around 0.3; the usable range is narrow and model-specific.
    5. **What is the query instruction prefix and what does it cost to omit?** A model-family-specific string prepended to queries; omitting it measured 0.03 Recall@10 on the reference corpus.

    ### The embedding pipeline

    ```python
    # embed.py — batching, caching, idempotence
    import hashlib, json, pathlib
    import numpy as np
    from sentence_transformers import SentenceTransformer

    MODEL = "BAAI/bge-base-en-v1.5"
    QUERY_PREFIX = "Represent this sentence for searching relevant passages: "

    class Embedder:
        def __init__(self, model_name: str = MODEL, cache_dir: str = ".embcache"):
            self.model = SentenceTransformer(model_name, device="cuda")
            self.model.max_seq_length = 512          # bge's trained length. see below.
            self.name = model_name
            self.cache = pathlib.Path(cache_dir) / model_name.replace("/", "_")
            self.cache.mkdir(parents=True, exist_ok=True)

        def _key(self, text: str) -> str:
            return hashlib.sha256((self.name + "\x00" + text).encode()).hexdigest()

        def embed_documents(self, texts: list[str], batch_size: int = 256) -> np.ndarray:
            keys = [self._key(t) for t in texts]
            out: list[np.ndarray | None] = [None] * len(texts)
            todo_idx, todo_txt = [], []
            for i, k in enumerate(keys):
                f = self.cache / f"{k}.npy"
                if f.exists():
                    out[i] = np.load(f)
                else:
                    todo_idx.append(i); todo_txt.append(texts[i])
            if todo_txt:
                vecs = self.model.encode(todo_txt, batch_size=batch_size,
                                         normalize_embeddings=True,
                                         convert_to_numpy=True, show_progress_bar=True)
                for i, v in zip(todo_idx, vecs):
                    np.save(self.cache / f"{keys[i]}.npy", v)
                    out[i] = v
            return np.vstack(out)

        def embed_query(self, query: str) -> np.ndarray:
            # ASYMMETRIC: queries get the instruction prefix, documents do not
            return self.model.encode([QUERY_PREFIX + query], normalize_embeddings=True,
                                     convert_to_numpy=True)[0]
    ```

    Four things in there are decisions:

    - **The cache key includes the model name.** Without it, switching models silently returns the
      old model's vectors from cache and you spend a day debugging a "regression" that is a cache
      hit.
    - **`max_seq_length = 512`.** `bge` models were trained at 512 tokens. Text beyond that is
      **silently truncated** — no warning, no error. If your chunks are 512 tokens *plus* a
      section-path prefix, you are dropping the tail of every chunk. Assert your chunk token counts
      against this number.
    - **`embed_query` is asymmetric.** The instruction prefix goes on queries only. Getting this
      backwards, or applying it to both, costs measured Recall@10.
    - **Batch 256.** Reference figure — A10G with `bge-base` (modelled): batch 32 gives 610 sent/s, batch 128 gives
      1,240, batch 256 gives 1,420, batch 512 gives 1,430 and uses 2.1× the VRAM. 256 is the knee.

    ### Handling long documents

    Three options when a chunk exceeds the model's context:

    | Approach | R@10 | Note |
    | --- | --- | --- |
    | Truncate (the silent default) | 0.83 | You lose the tail. This is what happens if you do nothing. |
    | Split and average the vectors | 0.85 | Cheap; the average is a worse match for any single part |
    | Split into separate chunks, keep both | **0.88** | The right answer, and it is just Module 2's job done correctly |

    The lesson is that "handling long documents at the embedding layer" is usually a symptom that
    chunking was done wrong. Fix it upstream.

    ### Trade-offs

    | Decision | Choose this when… | Choose the other when… |
    | --- | --- | --- |
    | **384 vs 768 vs 1024+ dims** | 384 (`bge-small`): more than 5M chunks, or latency-critical. 72.6 MB per 47,300 chunks scales linearly and the HNSW index (Module 4) scales with it. | 768 (`bge-base`): the default. +0.01 R@10 over small, 2× storage, still fast. Above 1024 you are paying storage forever for differences inside the CI. |
    | **Local vs API embeddings** | Local: you have a GPU, you re-embed often, or your data cannot leave. Full corpus in 33 s, marginal cost zero. | API: no GPU, one-off corpus, or you want `text-embedding-3-large`'s quality without hosting. $2.28 for the corpus, and $0.02 per 1,000 queries thereafter. |
    | **Symmetric vs asymmetric encoding** | Asymmetric (query prefix, or a dual-encoder like DPR): question-answering retrieval, which is nearly always what you have. Reference figure: +0.03 R@10. | Symmetric (no prefix): deduplication, clustering, "find similar documents" — where both sides are the same kind of text. |
    | **General model vs domain fine-tune** | General: start here always. `bge-base` is a strong default across domains. | Domain fine-tune: only after you have measured a gap *and* have 1,000+ labelled pairs. Layer 3 has the measured lift and the cost. |

    ### War story

    A team building search over legal filings measured four embedding models on a public benchmark
    subset, picked `e5-large-v2` because it topped their comparison, and shipped. Retrieval was
    mediocre — 0.71 Recall@10 on their own labelled queries.

    Two problems, and the second is the interesting one.

    **First**, they had not applied `e5`'s required prefixes. The `e5` family is trained with
    `query: ` and `passage: ` prepended, and without them the query and document embeddings live in
    slightly different regions of the space. Adding them took Recall@10 from 0.71 to 0.79 —
    **eight points from two string literals.**

    **Second**, once fixed, they re-ran the comparison on their own queries rather than the public
    subset:

    | Model | Public benchmark subset | Their legal queries |
    | --- | --- | --- |
    | `e5-large-v2` | **0.81** | 0.79 |
    | `bge-base-en-v1.5` | 0.78 | **0.84** |
    | `bge-small-en-v1.5` | 0.74 | **0.82** |

    **The order reversed.** On their corpus, `bge-base` beat `e5-large` by five points while being
    3× faster and using 25% less storage. They had chosen a slower, larger, worse model on the basis
    of a benchmark built from a different distribution of text.

    The permanent change was a rule, not a model: **no embedding model is adopted without a run
    against the internal eval set, and the comparison table goes in the PR description.** It costs
    an afternoon and it has since reversed two more decisions.

    <Accordion title="Design checkpoint">
    **Question.** You are asked to switch embedding models on a live system with 40M chunks. What is
    the plan, and what is the risk nobody mentions?

    **Model answer.** It is a migration, not a config change. 40M chunks at `bge-base` throughput
    (1,420 sent/s on one A10G) is 7.8 hours of pure GPU time, plus a full index rebuild (Module 4:
    HNSW build on 40M vectors is measured in hours, not minutes) and roughly 123 GB of new vectors
    at 768 dims. Plan: build the new index alongside the old one, shadow-read both and compare
    top-10 overlap on live traffic, then cut over behind a flag with the old index retained for
    rollback. The risk nobody mentions is **mixed vectors**: any chunk embedded by the old model and
    served from the new index is not merely stale, it is *meaningless* — the two models' spaces are
    unrelated, so its similarity scores are noise, and it will surface at random. Guard it by
    putting the model name and version in the index name and in every vector row, and asserting they
    match at query time. Ingest during a migration must write to both indexes or to neither.
    </Accordion>

    ### Leaderboard rank is not your rank, and here is a reversal

    MTEB (Massive Text Embedding Benchmark) aggregates 56 datasets across 8 task types. Its
    retrieval average is computed over 15 datasets that are mostly web QA, scientific abstracts and
    argument retrieval. If your corpus is none of those things, the ranking is a prior, not an
    answer.

    Segment the reference eval set by query type and the aggregate hides a reversal:

    | Model | All 100 | Factual QA (44) | Exact identifiers (18) | Policy/contract (22) | Code & config (16) |
    | --- | --- | --- | --- | --- | --- |
    | `bge-small-en-v1.5` | 0.87 | 0.90 | 0.41 | **0.91** | 0.83 |
    | `bge-base-en-v1.5` | 0.88 | 0.92 | 0.39 | 0.89 | 0.84 |
    | `e5-large-v2` | 0.89 | **0.94** | 0.38 | 0.88 | 0.82 |
    | `gte-large-en-v1.5` | 0.885 | 0.93 | 0.42 | 0.86 | **0.87** |

    Two findings the aggregate conceals.

    **The reversal.** On policy and contract queries, `bge-small` (0.91) beats `e5-large` (0.88) —
    the smallest model beating the largest, opposite to both the aggregate and the leaderboard.
    Paired bootstrap on that subset: **+0.03, CI [+0.00, +0.07]**, marginal but consistent across
    resamples. Legal and policy language is long, formal and repetitive, and the larger model's
    advantage on natural questions does not transfer.

    **The catastrophe.** Every model scores 0.38–0.42 on the 18 exact-identifier queries — error
    codes, part numbers, API names. Not one of them is usable. **This is not a model-selection
    problem; it is a class of query that dense retrieval cannot do**, and no amount of choosing
    better embedding models fixes it. Week 28 Module 1 solves it with BM25, and the fact that the
    18-query subset scores 0.94 there is the single strongest argument for hybrid search.

    **The practical rule: always segment your eval set by query type before choosing a model.** The
    aggregate told you `e5-large` was best by 0.02; the segmentation tells you that your worst
    segment needs a different retrieval method entirely.

    ### Matryoshka embeddings

    Kusupati et al.'s idea: train the model so that the *first* `d` dimensions of its output are
    themselves a usable embedding, for several values of `d`. You can then truncate a 3,072-dim
    vector to 256 dims and keep most of the quality, deciding the dimension at query time rather
    than at training time.

    ```python
    # matryoshka.py
    import numpy as np

    def truncate_normalize(E: np.ndarray, dims: int) -> np.ndarray:
        T = E[:, :dims]
        return T / np.linalg.norm(T, axis=1, keepdims=True)     # MUST re-normalise
    ```

    Reference figure — modelled with `text-embedding-3-large` on the reference corpus:

    | Dims | R@10 | NDCG@10 | Index size | Brute-force query time (47.3k) |
    | --- | --- | --- | --- | --- |
    | 3072 | 0.90 | 0.74 | 581 MB | 41 ms |
    | 1024 | 0.89 | 0.735 | 194 MB | 14 ms |
    | 512 | 0.885 | 0.73 | 97 MB | 7.2 ms |
    | **256** | **0.87** | 0.71 | **48 MB** | 3.7 ms |
    | 128 | 0.83 | 0.67 | 24 MB | 1.9 ms |
    | 64 | 0.74 | 0.58 | 12 MB | 1.1 ms |

    **12× less storage and 11× faster search for 0.03 Recall@10**, and 256 dims of
    `text-embedding-3-large` still beats 384 dims of `bge-small`. The knee is at 256.

    The re-normalisation is not optional and it is the bug people hit: truncating a unit vector
    leaves a vector of length under 1, and the shortfall varies by vector, so raw dot products
    become length-biased. Assert `np.allclose(np.linalg.norm(E, axis=1), 1.0)` after truncation.

    A useful pattern this enables: **store 256 dims in the index for fast candidate generation and
    the full 3,072 for exact rescoring of the top 100.** Reference figure: R@10 0.895 at 4.1 ms — within
    noise of full-dimension search at a tenth of the index size.

    ### Fine-tuning an embedding model on your domain

    The measured lift, and the cost, so you can decide rather than assume. Training pairs generated
    from the corpus (an LLM writes a question for each chunk, as in Module 5's eval construction),
    then `MultipleNegativesRankingLoss` on `bge-base`:

    | Training pairs | R@10 | NDCG@10 | Train time (A10G) | vs base |
    | --- | --- | --- | --- | --- |
    | 0 (base `bge-base`) | 0.88 | 0.72 | — | — |
    | 500 | 0.88 | 0.72 | 3 min | +0.00 |
    | 2,000 | 0.90 | 0.75 | 11 min | +0.02 |
    | 8,000 | 0.92 | 0.78 | 43 min | **+0.04** |
    | 8,000, hard negatives mined | **0.94** | **0.81** | 1 h 09 min | **+0.06** |

    ```python
    # finetune_embeddings.py — sentence-transformers 3.0.1
    from sentence_transformers import (SentenceTransformer, SentenceTransformerTrainer,
                                       SentenceTransformerTrainingArguments, losses)
    from sentence_transformers.util import mine_hard_negatives
    from datasets import Dataset

    model = SentenceTransformer("BAAI/bge-base-en-v1.5")
    train = Dataset.from_list(pairs)          # [{"anchor": query, "positive": chunk}, ...]

    # hard negatives: chunks the BASE model ranks highly but that are NOT the answer.
    # this is where +0.02 of the +0.06 comes from.
    train = mine_hard_negatives(train, model, range_min=10, range_max=50,
                                num_negatives=5, margin=0.05)

    args = SentenceTransformerTrainingArguments(
        output_dir="bge-base-domain", num_train_epochs=2,
        per_device_train_batch_size=64,       # batch size IS the negative count. bigger is better.
        learning_rate=2e-5, warmup_ratio=0.1, bf16=True,
        batch_sampler="no_duplicates",        # required: duplicates in a batch corrupt the negatives
    )
    SentenceTransformerTrainer(
        model=model, args=args, train_dataset=train,
        loss=losses.MultipleNegativesRankingLoss(model)).train()
    ```

    Three things about this that are not obvious:

    - **Batch size is the number of negatives.** `MultipleNegativesRankingLoss` treats the other
      items in the batch as negatives, so batch 64 means 63 negatives per positive. Reference figure: batch
      16 gives R@10 0.90, batch 64 gives 0.92, batch 128 gives 0.925. This is the rare case where
      batch size is a quality hyperparameter, not just a throughput one.
    - **`batch_sampler="no_duplicates"` is required.** If two near-identical chunks land in one
      batch, each is used as a negative for the other's query — you are training the model that the
      right answer is wrong.
    - **Hard-negative mining is a third of the total gain** and costs 26 extra minutes. Random
      negatives are too easy; the model learns nothing from being told a warehouse-hours passage is
      not the answer to a returns question.

    **The cost to weigh against +0.06 R@10:** roughly a day of work, an ongoing retraining
    obligation whenever the corpus shifts, a model you must host yourself, and — the one people
    forget — **a full re-embedding and index rebuild every time you retrain.** Do it after hybrid
    search and reranking (Week 28), which are cheaper and gave +0.05 R@10 and +0.11 NDCG on this
    corpus. Fine-tuning embeddings is a late-stage optimisation.

    ### Failure modes

    | Failure | Signature | Detection |
    | --- | --- | --- |
    | Missing query instruction prefix | Uniformly mediocre retrieval, no obvious cause | Measure with and without; `e5` cost 0.08 R@10 in the war story |
    | Silent truncation at `max_seq_length` | Long chunks retrieve poorly; short ones fine | Assert chunk token count ≤ model max; log the p99 |
    | Cache key without the model name | "Regression" after a model switch that is actually a cache hit | Include model name and revision in the key; assert dimension on load |
    | Unnormalised vectors mixed with normalised | Similarity scores outside [−1, 1]; ranking subtly wrong | Assert every stored vector has norm 1.0 ± 1e-5 |
    | Matryoshka truncation without re-normalising | Length-biased ranking that favours certain chunks | Re-normalise and assert |
    | Model chosen on a public benchmark | Reversal against your own data, discovered late | Segment your eval set by query type; run every candidate |
    | Exact-identifier queries failing | 0.4 recall on a specific query class the aggregate hides | Segment the eval; this class needs BM25, not a better model (Week 28 M1) |
    | Duplicate chunks in a training batch | Fine-tuned model is worse than the base | `batch_sampler="no_duplicates"` |

    ### Papers and primary sources

    - **Reimers & Gurevych 2019, "Sentence-BERT".** *Takeaway:* a siamese bi-encoder trained with a
      ranking objective turns semantic search from an O(n) cross-encoder problem into an O(1)
      vector-comparison problem — 65 hours of BERT scoring becomes 5 seconds. **Read §4 and Table
      1** — the 65-hours-to-5-seconds comparison is the founding argument for everything in this
      module.
    - **Kusupati et al. 2022, "Matryoshka Representation Learning".** *Takeaway:* training with
      nested sub-dimension losses lets one embedding serve many dimensionalities, so you choose the
      storage/accuracy trade at query time rather than at training time. **Read §2 and Figure 1.**
    - **Muennighoff et al. 2023, "MTEB: Massive Text Embedding Benchmark".** *Takeaway:* no single
      model wins across all 8 task types, and the paper says so explicitly — the leaderboard is a
      prior, not a decision. **Read §4's per-task-type results**, which is the section that
      contradicts how the leaderboard is usually used.
    - **Karpukhin et al. 2020, "Dense Passage Retrieval".** *Takeaway:* separate query and passage
      encoders trained with in-batch negatives beat BM25 by 9–19 points on open-domain QA, and the
      negatives matter more than the architecture. **Read §3** on in-batch and hard negatives — it
      is the basis of the fine-tuning recipe above.
    - **`sentence-transformers` 3.0 training documentation.** *Takeaway:* `MultipleNegativesRankingLoss`
      with a large batch and `no_duplicates` sampling is the recipe, and batch size functions as the
      negative count. **Read the "Loss overview" and "Training Overview" pages.**

    ### Stretch challenge

    Evaluate four embedding models on your own labelled query set, segmented by query type, and
    choose one with a written justification that names both the aggregate and the segment where your
    choice loses. Then the extension: build the Matryoshka two-stage retriever — truncated vectors
    for candidate generation, full vectors for rescoring the top 100 — and find the truncation
    dimension at which end-to-end Recall@10 becomes indistinguishable from full-dimension search.

    The open question is a design one with no settled answer. If different query *segments* prefer
    different embedding models — and the table above says they do — should you run two indexes and
    route queries between them? Build it: a lightweight query classifier, two indexes, a router.
    Then measure whether the routed system beats the best single model by more than the CI, and cost
    the extra index in storage, ingest time and operational complexity. My prior is that it does not
    pay for two models but *does* pay for one dense index plus one sparse index — which is exactly
    hybrid search, and Week 28 will show you why. If your data disagrees, that is the more
    interesting result and you should write it up.

## Assessment

<AccordionGroup>
  <Accordion title="8 concept questions">
  1. What is a bi-encoder and why is it necessary for retrieval? (Query and document embedded independently, so document vectors precompute once; a cross-encoder would need 43 s per query over 47,300 chunks.)
  2. What are retrieval embedding models trained to do? (Contrastive learning: pull positive query-passage pairs together, push in-batch negatives apart.)
  3. Why normalise, and what does it turn cosine similarity into? (A plain dot product — one matrix multiply for all pairs.)
  4. Why is "similarity above 0.7 means relevant" not a valid rule? (Unrelated English passages already score ~0.3; the usable band is narrow and model-specific, so thresholds need per-corpus calibration.)
  5. What is the query instruction prefix and what did omitting it cost? (A family-specific string on queries only; measured 0.08 Recall@10 for `e5` in the war story.)
  6. Give a case where the leaderboard ordering reversed on real data. (Policy/contract queries: `bge-small` 0.91 versus `e5-large` 0.88, smallest model beating largest.)
  7. What are Matryoshka embeddings, and what must you remember when truncating? (Nested sub-dimension training so a prefix of the vector is usable; you must re-normalise after truncation or ranking becomes length-biased.)
  8. In `MultipleNegativesRankingLoss`, why is batch size a quality hyperparameter? (The other batch items are the negatives; batch 16 → 0.90, batch 64 → 0.92, batch 128 → 0.925.)

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Uniformly mediocre retrieval, no obvious cause | Missing or misapplied query instruction prefix | Read the model card; apply to queries only; measure both ways |
| Long chunks retrieve badly, short ones fine | Silent truncation at `max_seq_length` | Assert chunk tokens ≤ model max; report violations |
| Quality "regressed" after a model switch | Cache key lacks the model name | Include model name and revision; assert vector dimension |
| Similarity scores look wrong or exceed 1.0 | Mixed normalised and unnormalised vectors | Assert unit norm at write and at query |
| Ranking biased toward certain chunks after truncation | Matryoshka truncation without re-normalising | Re-normalise, then assert |
| Chosen model underperforms in production | Selected on a public benchmark, not your data | Run every candidate on your own segmented eval set |
| One query class fails for every model | Dense retrieval cannot do exact identifiers | Add BM25 (Week 28 M1) — measured 0.40 → 0.94 on that class |
| Fine-tuned embedding model is worse than the base | Duplicate chunks in a batch used as each other's negatives | `batch_sampler="no_duplicates"`; mine hard negatives |
