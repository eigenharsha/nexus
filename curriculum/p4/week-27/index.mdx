The measurement is the point. Anyone can wire an embedding model to a vector store in an afternoon.
This week is about being able to say *how well it works* and *why*, with numbers you can defend.

## The through-line

1. **Why RAG, and the ingestion problem.** Facts belong in the prompt, not the weights. Then the
   unglamorous discovery: parsing is where most RAG systems actually lose their quality, and it is
   the stage nobody instruments.
2. **Chunking strategies.** Chunk size is a hyperparameter with an inverted-U curve. Small chunks
   split the answer; large ones dilute the embedding.
3. **Embeddings for retrieval.** Bi-encoders, why they are what makes retrieval possible at all,
   and why the leaderboard's ranking is a prior rather than an answer.
4. **Vector indexes.** Why a B-tree cannot do this, and HNSW derived from first principles —
   Week 13's skip list over Week 14's heaps.
5. **Building and evaluating.** The eval set, the ablation table, and the diagnosis that separates
   retrieval failures from generation failures.

## Read the modules in this order, but build in this order

The modules teach in pipeline order. **Build in a different order**, because Module 5's eval set is
what makes every other module's claims measurable:

<Steps>
  <Step title="Module 5's eval set, first">
    100 queries with human-verified relevant chunks. Two days. Nothing before this produces a number
    you can trust.
  </Step>
  <Step title="Module 1's ingestion, second">
    Parse, scorecard, fix the worst. This is the largest single quality lever in the week
    (+0.11 Recall@10) and it is measurable the moment the eval set exists.
  </Step>
  <Step title="Modules 2 and 3, third">
    Chunking sweep, then embedding-model comparison. Both are afternoon experiments once the
    harness exists.
  </Step>
  <Step title="Module 4's index, last">
    You do not need an index below ~100,000 chunks. Add it when brute force stops being fast enough,
    and measure its recall against exact search when you do.
  </Step>
</Steps>

## The five numbers you should leave with

| Number | What it is |
| --- | --- |
| `0.72 → 0.83` Recall@10 | Parsing fixes alone, before touching anything glamorous. |
| Inverted U, peak at **512 tokens** | Chunk size. 31% of answers split at 128; 4% signal at 2,048. |
| `2,180` vs `1,000,000` distance computations | HNSW at `ef_search=40` versus brute force on 1M vectors. |
| `0.95 → 0.31` filtered recall | The post-filter trap at 3.1% selectivity. Silent, and the query does not error. |
| **68 / 24 / 8** | Failure attribution: retrieval / generation / both. Most debugging goes to the 24. |

## Cost and hardware

<Note>
**Where this week's numbers come from.** Almost everything in this week is a **reference figure**.
The 1,000-PDF corpus, the chunk store and the 100-query eval set are not in this repository and the
eval was never run here, so the quality numbers — Recall@k, NDCG, citation precision — are modelled
alongside the throughputs, which assume an A10G and an `m6i.2xlarge` the authors did not have.

What *is* solid: the index memory footprints, the `O(N·d)` scan arithmetic and the Matryoshka
truncation maths are **derived** and exact, and the *method* — build a corpus, define an eval set,
ablate one variable at a time, report a confidence interval — is the actual deliverable of the
week. Run it on your own documents and every number below becomes yours. See [About the numbers](/start/about-the-numbers).
</Note>

<Info>
**Everything this week runs for under $3.** Postgres and pgvector run in Docker on a laptop.
Embedding 47,300 chunks with `bge-base` takes 33 seconds on a GPU or about 22 minutes on an M2 Pro
CPU — both fine. The `hard` track's 10M-vector index needs a 32 GB machine for about 3 hours
(roughly $1.20 on an `m6i.2xlarge`), and there is a documented 1M-vector fallback.
</Info>
