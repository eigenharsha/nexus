ticket below is how the job actually arrives.

## The ticket

> **NEX-4203 · Internal tools · P1**
>
> Our support agent prototype works in the demo and is unusable in the team channel. It sometimes
> loops until it times out, it once tried to issue a refund it was not asked for, tool failures
> surface as stack traces, and nobody can say what any given run actually did. Two engineers want
> to adopt a framework; one wants to keep the hand-rolled version.
>
> Make it something we would put on call. We need it to fail cleanly and explain itself, to have a
> budget it cannot exceed, to never attempt a destructive action without an explicit gate, and to
> come with numbers showing whether it is getting better.
>
> Deliverable: the agent with its harness, the tool catalogue with justifications, a trajectory
> eval suite over twenty real tickets, and a framework recommendation supported by measurements.

**Time box, honestly:** `basic` 5–6 hours. `standard` 12–16 hours. `hard` a further 8–10 hours.

## Tracks

<AccordionGroup>
  <Accordion title="🟢 basic — scaffolded" icon="circle">
  Given: a working ReAct loop, three tools, and twenty labelled tickets.

  1. Add turn, tile and wall-clock budgets, each returning a distinct status.
  2. Turn tool exceptions into observations with *useful* error text.
  3. Add repeated-call detection with a corrective observation.
  4. Print a readable trace for every run.
  5. Deliberately break each tool in turn and confirm the agent recovers or fails cleanly.
  </Accordion>

  <Accordion title="🔵 standard — spec and tests only" icon="circle-dot">
  Build the whole thing:

  - The harness with all six responsibilities from Module 3, budgets passed per request.
  - A tool catalogue of at most six tools, each with a description stating what, when and returns;
    data tools and action tools clearly separated.
  - Any destructive tool behind an idempotency key and an explicit confirm step.
  - Context curation from Module 4: recent verbatim, older summarised, durable facts stored.
  - A trajectory eval suite: twenty cases with expected tools and turn budgets, reporting task
    success, path validity, cost per successful run and unsafe attempts.

  **Acceptance:** no tool exception escapes the loop; no destructive tool executes without confirm;
  a 10,000-row result never enters the transcript whole; an identical repeated call never executes
  twice; and every run ends with one of the defined statuses plus a trace.
  </Accordion>

  <Accordion title="🟣 hard — one more constraint" icon="circle-check">
  Everything in `standard`, plus:

  - **The bake-off.** Rebuild the same agent in one framework from Module 5. Report the five
    columns, including time to debug the first deliberate failure.
  - **Near-miss reporting.** Count blocked destructive attempts, refusals and budget terminations
    per hundred runs, and chart them.
  - **One improvement, measured.** Change exactly one thing — error messages, or the tool catalogue,
    or repeat detection — and report which eval column moved.
  </Accordion>
</AccordionGroup>

## Verify yourself

```bash
make verify     # sabotage suite, then the twenty-case trajectory eval
```

Your run should show: every sabotage handled with a clean status, zero unconfirmed destructive
executions, a trajectory report with four columns, and a stated framework recommendation with the
numbers behind it.

## Ship it

Push with a `README` answering the ticket's real question in three sentences: hand-rolled or
framework, on what evidence, and what you would do next.

## If you get stuck

- **The agent loops forever** → repeated-call detection, then turn budget (Module 3).
- **Stack traces reach the user** → exceptions must become observations, not crashes.
- **Every framework looks the same** → you have not broken anything yet; sabotage is the comparison.
- **Eval says nothing changed** → your twenty cases are too easy; use the tickets that caused complaints.
