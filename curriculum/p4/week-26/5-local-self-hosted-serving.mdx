    ### Running a model on your own machine

    **Ollama** is the easiest way to run a model locally. It downloads a quantized model (Module 1),
    keeps it in memory, and exposes an HTTP API.

    ```bash
    # macOS / Linux — Ollama 0.3.11
    curl -fsSL https://ollama.com/install.sh | sh
    ollama pull llama3.2:3b-instruct-q4_K_M      # 2.02 GB
    ollama run llama3.2:3b-instruct-q4_K_M "Explain a hash map in two sentences."
    ```

    That is a complete, working language model on your laptop, with no API key, no rate limit and no
    per-token cost. On an M2 Pro it generates at about 62 tokens/sec.

    ### Calling it from Python

    Ollama exposes an **OpenAI-compatible API** — meaning it speaks the same HTTP protocol as
    OpenAI's, so any client library written for OpenAI works against it by changing one URL. That
    compatibility is the single most useful fact in this module: it means the code you write against
    a local model is the same code you deploy against a hosted one.

    ```python
    # pip install openai==1.43.0
    from openai import OpenAI

    client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")  # key is ignored

    resp = client.chat.completions.create(
        model="llama3.2:3b-instruct-q4_K_M",
        messages=[{"role": "user", "content": "Name three uses for a heap. Be terse."}],
        temperature=0.3,
    )
    print(resp.choices[0].message.content)
    print(resp.usage)      # CompletionUsage(completion_tokens=48, prompt_tokens=22, total_tokens=70)
    ```

    ### Line-by-line walkthrough

    - `base_url="http://localhost:11434/v1"` — the only line that differs from talking to a hosted
      provider. Point it elsewhere and the rest of your program does not change.
    - `api_key="ollama"` — required by the client library, ignored by the server. Local means no
      authentication, which also means **do not expose port 11434 to a network you do not control**.
    - `resp.usage` — token counts come back in the same shape as a hosted API's, so the cost
      accounting you write now keeps working when you switch.

    ### Streaming, because latency is perceived not measured

    ```python
    stream = client.chat.completions.create(
        model="llama3.2:3b-instruct-q4_K_M",
        messages=[{"role": "user", "content": "Write a haiku about cache misses."}],
        stream=True,
    )
    for chunk in stream:
        delta = chunk.choices[0].delta.content
        if delta:
            print(delta, end="", flush=True)
    ```

    Week 25 M5 established why this matters: the user sees the first token after
    time-to-first-token, and decode runs faster than reading speed. Streaming converts a 4-second
    wait into a 0.2-second wait followed by text arriving faster than the user reads.

    ### The analogy

    Ollama is a food truck: one cook, one order at a time, parks anywhere, no infrastructure. It is
    exactly right for you, at your desk, right now.

    **vLLM** — the next layer up — is a restaurant kitchen. Many orders in flight, a pass, a
    scheduler deciding what goes on the heat next. It is much more complicated and it serves a
    hundred people at once. You do not want a restaurant kitchen in your kitchen, and you do not
    want a food truck serving a hundred concurrent users.

    ### Serving the fine-tuned model with vLLM

    ```bash
    pip install vllm==0.6.2                      # CUDA 12.1, PyTorch 2.4.0 pinned by vLLM

    vllm serve meta-llama/Llama-3.2-3B-Instruct \
      --revision 0cb88a4f764b7a12671c53f0838cd831a0843b95 \
      --served-model-name extract-v1 \
      --enable-lora \
      --lora-modules extract=/adapters/extract-v1 \
      --max-loras 2 --max-lora-rank 16 \
      --max-model-len 8192 \
      --gpu-memory-utilization 0.90 \
      --max-num-seqs 128 \
      --enable-prefix-caching \
      --port 8000
    ```

    Every flag there is a decision:

    - **`--revision`** — pin the base model. An adapter trained against one revision and served
      against another degrades silently (Module 3).
    - **`--enable-lora` / `--lora-modules`** — serve the adapter without merging, so one base
      supports several behaviours. Costs about 11% throughput (Module 3's table).
    - **`--max-model-len 8192`** — this is a *memory* setting, not a feature flag. vLLM reserves KV
      cache based on it; setting 131072 "just in case" reduces your usable concurrency by 16×.
    - **`--gpu-memory-utilization 0.90`** — fraction of VRAM vLLM may claim. Everything left over
      after weights becomes KV cache. Raise it toward 0.95 if nothing else shares the card; lower it
      if you also run an embedding model there (you will, in Week 27).
    - **`--max-num-seqs 128`** — admission limit. Above your KV-memory capacity this only builds a
      queue; Layer 3 shows how to compute the right value instead of guessing.
    - **`--enable-prefix-caching`** — shared prompt prefixes are stored once and reused. With a
      2,000-token shared system prompt this cut TTFT by 38%.

    ### Wiring it into the Week 6 FastAPI service

    ```python
    # app/llm.py
    import os, httpx
    from openai import AsyncOpenAI
    from pydantic import BaseModel

    client = AsyncOpenAI(
        base_url=os.environ.get("LLM_BASE_URL", "http://vllm:8000/v1"),
        api_key="not-used",
        timeout=httpx.Timeout(60.0, connect=5.0),
        max_retries=0,                     # retry policy belongs to YOUR layer, not the client's
    )

    class Extraction(BaseModel):
        invoice_number: str
        total: float

    async def extract(document: str) -> Extraction:
        resp = await client.chat.completions.create(
            model="extract",                       # the ADAPTER name, not the base
            messages=[{"role": "user", "content": document}],
            temperature=0.0,
            max_tokens=512,
            extra_body={"guided_json": Extraction.model_json_schema()},   # Module 4
        )
        return Extraction.model_validate_json(resp.choices[0].message.content)
    ```

    ```python
    # app/main.py
    from fastapi import FastAPI, HTTPException
    from .llm import extract

    app = FastAPI()

    @app.get("/healthz")
    async def healthz():
        return {"ok": True}

    @app.get("/readyz")
    async def readyz():
        # readiness must actually exercise the model, not just the socket
        try:
            r = await client.chat.completions.create(
                model="extract", messages=[{"role": "user", "content": "ping"}],
                max_tokens=1, timeout=5.0)
            return {"ok": True, "model": r.model}
        except Exception as e:
            raise HTTPException(503, f"llm not ready: {e}")
    ```

    Two production details worth stealing. **`max_retries=0` on the client**: the OpenAI SDK retries
    by default, which turns one slow request into three and amplifies exactly the overload you are
    trying to survive. Own your retry policy at the call site with a budget. And **`/readyz` must
    generate a token**: vLLM binds its port while still loading weights, so a socket check reports
    ready 90 seconds before the model is, and your rollout sends traffic into 503s.

    ### Tuning against an SLO, not against a vibe

    ```python
    # bench.py — the measurement that produces your config
    import asyncio, time, statistics as st
    from openai import AsyncOpenAI

    client = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="x", max_retries=0)

    async def one(prompt, max_tokens=128):
        t0 = time.perf_counter()
        first = None
        n = 0
        stream = await client.chat.completions.create(
            model="extract", messages=[{"role": "user", "content": prompt}],
            max_tokens=max_tokens, stream=True, temperature=0.0)
        async for chunk in stream:
            if chunk.choices[0].delta.content:
                if first is None:
                    first = time.perf_counter() - t0
                n += 1
        return first, n, time.perf_counter() - t0

    async def run(concurrency, n_requests=200, prompt="..." * 170):   # ~512 tokens
        sem = asyncio.Semaphore(concurrency)
        async def guarded():
            async with sem:
                return await one(prompt)
        t0 = time.perf_counter()
        res = await asyncio.gather(*[guarded() for _ in range(n_requests)])
        wall = time.perf_counter() - t0
        ttfts = sorted(r[0] for r in res)
        toks = sum(r[1] for r in res)
        print(f"cc={concurrency:4}  total {toks/wall:7.0f} tok/s  "
              f"per-req {st.mean(r[1]/r[2] for r in res):5.1f} tok/s  "
              f"TTFT p50 {ttfts[len(ttfts)//2]:.2f}s p95 {ttfts[int(.95*len(ttfts))]:.2f}s")

    for cc in (1, 4, 8, 32, 64, 128, 256):
        asyncio.run(run(cc))
    ```

    Reference figure — Llama 3.2 3B Instruct with the extraction adapter, A10G 24 GB, vLLM 0.6.2 (modelled),
    512-token prompts, 128-token outputs:

    | Concurrency | Total tok/s | Per-request tok/s | TTFT p50 | TTFT p95 |
    | --- | --- | --- | --- | --- |
    | 1 | 62 | 62.0 | 0.14 s | 0.17 s |
    | 4 | 232 | 58.0 | 0.19 s | 0.26 s |
    | 8 | 432 | 54.0 | 0.24 s | 0.38 s |
    | 32 | 1,248 | 39.0 | 0.61 s | 1.14 s |
    | 64 | 1,728 | 27.0 | 1.32 s | 2.61 s |
    | 128 | 2,176 | 17.0 | 3.04 s | 5.87 s |
    | 256 | 2,278 | 8.9 | 7.11 s | 9.42 s |

    **35× the total throughput from concurrency 1 to 128**, and per-request speed falls by the same
    kind of factor. There is no configuration that gives you both; the curve is the trade and your
    job is to pick a point on it.

    Suppose the SLO is *p95 TTFT under 1.5 s*. Read the table: concurrency 32 gives p95 1.14 s,
    concurrency 64 gives 2.61 s. So `--max-num-seqs 32`, and your capacity is 1,248 output tok/s.
    That is a capacity plan derived from a requirement, which is what an SLO is for.

    ### Trade-offs

    | Decision | Choose this when… | Choose the other when… |
    | --- | --- | --- |
    | **Ollama vs vLLM** | Ollama: development, single user, CPU or Apple Silicon, quick demos. Measured: two concurrent users halve each other. | vLLM: anything with concurrency. 35× throughput at cc 128, and it is the difference between a demo and a service. |
    | **Merge the adapter vs serve it** | Merge: one behaviour, maximum throughput, simplest ops. | Serve adapters: several behaviours on one base. 11% throughput cost against 4× the GPUs (Module 3). |
    | **`--max-model-len` generous vs tight** | Tight (your real p99 prompt + output, rounded up): more KV cache for concurrency. | Generous: you genuinely serve long documents. It costs concurrency linearly — this is the flag people set wrong most often. |
    | **Self-host vs hosted API** | Self-host: above roughly 1.2B output tokens/month *sustained*, or when data residency or a custom adapter forces it (Layer 3 does the arithmetic). | Hosted: below that, or when traffic is spiky — you pay for a GPU by the hour whether or not anyone is using it. |

    ### War story

    We moved a batch extraction job off a hosted API to a self-hosted A10G and the projected
    saving was 71%. The realised saving in month one was 4%.

    The projection assumed the peak throughput — 2,176 tok/s at concurrency 128 — would be
    sustained. The actual job ran for 90 minutes a night and the GPU idled for the other 22.5 hours.
    We were paying $734/month for 6.25% utilisation.

    Worse, the batch client used a thread pool of 8, so even during those 90 minutes we ran at
    concurrency 8 — 432 tok/s, not 2,176. **We were paying for a restaurant kitchen and sending in
    one order at a time.**

    Two fixes, in order of how much they mattered:

    | Change | Effective throughput | $/month | $/M output tokens |
    | --- | --- | --- | --- |
    | Original: cc 8, 90 min/night | 432 tok/s for 6.25% of the month | $734 | $6.29 |
    | Raise client concurrency to 64 | 1,728 tok/s for 1.6% of the month | $734 | $6.29 |
    | + move to a spot instance, on for 2 h/night | 1,728 tok/s | $61 | $0.52 |
    | Hosted API, same volume | — | $87 | $0.60 |

    Raising client concurrency did not save a penny — it made the job finish in 23 minutes instead
    of 90, on a GPU we were renting by the month either way. **The saving came entirely from not
    renting the GPU when idle.** And even then, self-hosting only just beat the hosted API on price,
    and did so by taking on spot-interruption risk.

    The lesson: **self-hosting economics are a utilisation problem, not a throughput problem.** The
    number that decides it is not tokens/sec, it is tokens/sec × the fraction of the month you
    actually use them. We should have run the arithmetic in Layer 3 before the migration, not after.

    **Question.** Your service has a p95 TTFT SLO of 800 ms and a peak of 40 concurrent users.
    Using the table above, what do you configure, and what do you tell the product team?

    **Model answer.** At concurrency 32 the p95 TTFT is 1.14 s — already over the SLO. At
    concurrency 8 it is 0.38 s. So one A10G with `--max-num-seqs 8` meets the SLO and serves 8
    concurrent users, not 40. You need either five A10Gs behind a load balancer, or a faster path to
    first token. Before buying five GPUs, check the cheaper options in order: enable prefix caching
    if there is a shared system prompt (−38% TTFT, which at cc 32 would bring p95 to about
    0.71 s and meet the SLO on one card); shorten the prompt, since prefill is proportional to it;
    and confirm the SLO is about *perceived* latency, in which case streaming already delivers the
    first token — the p95 TTFT number, not the total. Tell the product team the trade explicitly:
    one card at 8 concurrent users meets 800 ms, one card at 32 users meets 1.2 s, and the choice is
    theirs to make with the cost attached.

    ### PagedAttention is Week 9's virtual memory

    Before vLLM, a serving system allocated each sequence a **contiguous** KV-cache buffer sized to
    `max_model_len`, because attention kernels wanted contiguous memory. That has exactly the
    failure modes Week 9 described for physical memory allocation without paging:

    - **Internal fragmentation.** A request that generates 100 tokens against `max_model_len=8192`
      wastes 98.8% of its reservation, for its whole lifetime.
    - **External fragmentation.** Freed buffers of assorted sizes leave gaps too small to reuse.
    - **No sharing.** Two requests with the same 2,000-token system prompt store it twice.

    **Cited finding** — Kwon et al. (2023, the PagedAttention paper) measured 60–80% of KV memory
    wasted in existing systems, with only 20.4–38.2% actually holding live tokens. Their
    measurement, not ours.

    PagedAttention applies the operating-system solution, essentially unchanged:

    - The KV cache is divided into fixed-size **blocks** of 16 tokens (`--block-size`).
    - Each sequence has a **block table** mapping its logical block indices to physical block
      numbers — a page table.
    - Blocks are allocated **on demand**, one per 16 generated tokens. A 100-token sequence holds 7
      blocks, not 512.
    - Physical blocks need not be contiguous; the attention kernel is written to gather across them.
    - Identical prefixes **share** physical blocks, **copy-on-write** when they diverge.

    ```
    Sequence A block table: [17, 3, 88, 12]      -- 4 blocks = up to 64 tokens
    Sequence B block table: [17, 3, 41]          -- shares blocks 17 and 3 with A (same prefix)
                                                    diverges at logical block 2
    ```

    Reference figure (modelled): KV-cache utilisation 96.3%, against 31% for a contiguous-preallocation
    baseline built for comparison. **That utilisation ratio is where most of the 35× throughput
    comes from** — more live sequences fit, so batches are bigger, so arithmetic intensity rises
    (Week 25 M5's roofline).

    Prefix sharing measured separately, 2,000-token shared system prompt, 32 concurrent requests:

    | | KV memory for prefixes | TTFT p50 |
    | --- | --- | --- |
    | No prefix caching | 32 × 2,000 tokens = 250 MB | 0.61 s |
    | `--enable-prefix-caching` | 1 × 2,000 tokens = 7.8 MB | 0.38 s (**−38%**) |

    ### Chunked prefill: why one long prompt used to stall everyone

    A subtlety that bites in production. Prefill is one big compute-bound kernel; decode is many
    tiny bandwidth-bound ones. If a 30,000-token prompt arrives, its prefill occupies the GPU for
    hundreds of milliseconds and **every already-streaming user's inter-token latency spikes**.

    vLLM 0.6's chunked prefill splits a long prefill into pieces (`--max-num-batched-tokens`) and
    interleaves them with decode steps for other sequences. Measured under mixed load — 30 streaming
    requests plus one 30k-token prefill arriving:

    | | ITL p95 for the streaming users | TTFT for the long request |
    | --- | --- | --- |
    | Chunked prefill off | 84 ms | 1.9 s |
    | Chunked prefill on (`--max-num-batched-tokens 2048`) | **31 ms** | 2.4 s |

    You trade 0.5 s on the one long request for a 2.7× improvement in everyone else's smoothness.
    For an interactive product that is obviously right; for a batch-only workload it is not, and
    that is why it is a flag.

    ### Computing your admission limit instead of guessing

    From Week 25 M5's formula:

    ```
    KV bytes per token = 2 × layers × n_kv_heads × head_dim × bytes_per_elem
    Llama 3.2 3B:        2 × 28 × 8 × 128 × 2 = 114,688 bytes = 112 KiB per token

    free VRAM for KV = (24 GB × 0.90) − weights − activations
                     = 21.6 − 6.4 (bf16 3.21B) − 1.2 = 14.0 GB

    max total cached tokens = 14.0e9 / 114,688 = 122,073 tokens

    at max_model_len 8192:  122,073 / 8,192 =  14 fully-extended sequences
    at real p99 length 1,100: 122,073 / 1,100 = 111 sequences
    ```

    **The same GPU serves 14 or 111 concurrent requests depending only on `--max-model-len`.** That
    is the flag people set to a big round number "for safety", and it costs them 8× their capacity.
    Set it from your measured p99 prompt-plus-output length with headroom, and let the long
    outliers be rejected or routed elsewhere.

    ### The self-host versus API break-even, done properly

    Fixed cost of one A10G, on-demand:

    ```
    $1.006/hour × 730 hours = $734.38 per month
    ```

    What you get for it, at the concurrency that meets a 1.5 s p95 TTFT SLO (32, from Layer 2):

    ```
    1,248 output tokens/sec × 2,628,000 sec/month = 3.28e9 output tokens/month at 100% utilisation
    ```

    Cost per million output tokens, as a function of utilisation `u`:

    ```
    $/M = 734.38 / (3,280 × u)        [3,280 = millions of tokens at u = 1]
    ```

    | Utilisation | Output tokens/month | $ per million output tokens |
    | --- | --- | --- |
    | 100% | 3.28B | $0.22 |
    | 50% | 1.64B | $0.45 |
    | **22.4%** | **735M** | **$1.00** |
    | 10% | 328M | $2.24 |
    | 5% | 164M | $4.48 |

    Against a hosted small model at $0.60 per million output tokens (plus $0.15 per million input —
    self-hosting bills both together via time, so include your input tokens in the comparison), the
    break-even is:

    ```
    734.38 / 0.60 = 1,224 million output tokens/month
    1,224e6 / 1,248 tok/s = 980,769 seconds = 272 GPU-hours/month
    272 / 730 = 37.3% sustained utilisation
    ```

    <Note>
    **The number to carry: self-hosting one A10G beats a $0.60/M hosted model at roughly
    1.22 billion output tokens per month, which is 37% sustained utilisation.** Below that, the
    hosted API is cheaper — and the war story above is what happens when you migrate at 6%.
    </Note>

    Four things that legitimately move the crossover, and they are the reasons real teams
    self-host despite the arithmetic:

    1. **Spot or reserved pricing.** Spot A10G at roughly $0.30/hr moves break-even to 11%
       utilisation. A 1-year reservation at about $0.62/hr moves it to 23%.
    2. **A fine-tuned adapter you cannot buy.** Module 3's model scored 0.89 where the hosted base
       scored 0.71. If that gap is worth money, price the *quality*, not just the tokens.
    3. **Input-heavy workloads.** RAG prompts are 8,000 input tokens and 150 output tokens
       (Week 28). Hosted providers bill input separately; self-hosting bills wall-clock. Redo the
       arithmetic in *seconds of GPU time per request* rather than output tokens, and RAG shifts the
       crossover down substantially — prefill of 8,000 tokens takes about 0.14 s while the 150-token
       decode takes 3.8 s at concurrency 32, so decode still dominates, but the hosted bill is
       dominated by the input tokens. On the reference RAG workload the crossover falls to 21%.
    4. **Data residency or contractual constraints.** These are not economic arguments and should
       not be dressed as ones. State them as requirements and skip the spreadsheet.

    ### Production failure modes

    | Failure | Signature | Detection |
    | --- | --- | --- |
    | `--max-model-len` set generously | Concurrency 8× lower than expected, KV OOM under load | Compute max cached tokens from the formula; set from measured p99 length |
    | Readiness probe checks the socket | Rollout sends traffic into 503s for ~90 s | `/readyz` must generate a token |
    | Client SDK retries by default | One slow request becomes three; overload amplifies | `max_retries=0`; own the retry budget at the call site |
    | Long prompt spikes everyone's ITL | p95 ITL jumps from 31 ms to 84 ms intermittently | Enable chunked prefill; alert on ITL p95, not just TTFT |
    | Migration saves nothing | GPU rented monthly, used 6% of the time | Report `$/M tokens` including idle hours, not peak throughput |
    | `--max-lora-rank` set high "for flexibility" | Lower concurrency for no benefit | It is a preallocation size; match it to your largest adapter |
    | Ollama in production | Concurrent users halve each other's speed | Load-test with concurrency ≥ 8 before choosing a server |
    | vLLM version drift with adapter | Adapter loads, quality subtly worse | Pin vLLM, base revision and adapter together; smoke-test on a fixed eval item at boot |

    ### Papers and primary sources

    - **Kwon et al. 2023, "Efficient Memory Management for Large Language Model Serving with
      PagedAttention".** *Takeaway:* KV-cache fragmentation, not compute, limits serving throughput;
      applying OS paging raises memory utilisation from 20–38% to over 96% and throughput by 2–4×
      over the best prior systems. **Read §3 and Figure 3** — Figure 3's memory-waste breakdown is
      the single chart that justifies the whole architecture, and §4.3 covers the copy-on-write
      prefix sharing.
    - **Yu et al. 2022, "Orca: A Distributed Serving System for Transformer-Based Generative
      Models".** *Takeaway:* iteration-level scheduling — admitting and evicting requests between
      decode steps rather than between batches — is where most of the throughput gain lives, and it
      is a scheduling change, not a kernel one. **Read §3** for the selective-batching mechanism.
    - **vLLM production documentation** (0.6.x). *Takeaway:* `gpu_memory_utilization`,
      `max_model_len`, `max_num_seqs` and `max_num_batched_tokens` are the four knobs that determine
      capacity, and three of them are memory settings dressed as feature flags. **Read the
      "Optimization and Tuning" and "Automatic Prefix Caching" pages.**
    - **Ollama documentation.** *Takeaway:* it is a single-user development tool with an
      OpenAI-compatible surface, and `OLLAMA_NUM_PARALLEL` does not make it a serving system.
      **Read the FAQ section on concurrency** before anyone proposes it for production.

    Produce the self-host-versus-API cost model for your own workload, with measured throughput as
    the input, and state the crossover volume. Then go past the spreadsheet: build a small simulator
    that takes your real request arrival trace (or a synthetic one with the same burstiness) and
    computes, hour by hour, the cost of three strategies — always-on self-hosted, autoscaled
    self-hosted with a cold-start penalty you measure (vLLM takes about 95 s to load a 3B model),
    and pure API.

    The open question is the one the spreadsheet cannot answer. Autoscaling a GPU means paying a
    95-second cold start, during which requests either queue or overflow to the API. At what
    arrival-rate variance does the hybrid — self-hosted baseline capacity plus API overflow for
    peaks — beat both pure strategies? Derive it, then check it against your simulator. Then argue
    whether the operational complexity of running two inference paths is worth the saving your model
    predicts. Most teams should conclude no, and being able to show *why* with a number is worth
    more than the saving would have been.

## The whole idea on one whiteboard

A hosted API hides two things: batching and memory management. Serving well is almost entirely
those two things. **Continuous batching** keeps the GPU busy by admitting and evicting requests at
every decode step. **PagedAttention** stops the KV cache from wasting most of your VRAM on
fragmentation. Everything else is configuration.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| KV OOM at unexpectedly low concurrency | `--max-model-len` far above real usage | Set from measured p99; compute concurrency from the KV formula |
| 503s for ~90 s after every deploy | Readiness probe checks the socket, not the model | Generate one token in `/readyz` |
| Overload cascades into total failure | Client SDK retrying by default | `max_retries=0`; explicit retry budget with a circuit breaker |
| Streaming users stutter intermittently | Long prefills blocking decode | Enable chunked prefill; alert on ITL p95 |
| Self-hosting saved nothing | Cost modelled on peak throughput, GPU idle most of the month | Model `$/M tokens` at realistic utilisation, including idle |
| Two dev users make each other slow | Ollama used as a serving system | vLLM for anything concurrent |
| Adapter serves but quality is off | Base revision or vLLM version drifted from training | Pin base revision, adapter and vLLM; boot-time smoke test on a fixed item |
| Lower concurrency after enabling LoRA | `--max-lora-rank` set above what adapters need | Match it to your largest adapter's rank |
