## The mental model

An A/B test is a machine for answering one question: **if I had shipped this change to everyone,
what would have happened?**

It works because of **randomisation**. Assign users to variants at random and the two groups are, in
expectation, identical in every respect — known and unknown, measured and unmeasured. Any difference in
outcome must then be caused by the treatment, because nothing else systematically differs.

That is the entire logical foundation, and it is why the two most damaging failures are both attacks
on it:

- **SRM (sample ratio mismatch)** — the split is not what you asked for, so the randomisation is
  broken, so the groups are not comparable.
- **Peeking** — you stop when the result looks good, which converts a 5% false-positive rate into
  something much larger.

Everything else is arithmetic.

### The words, defined

- **Variant** — one version being tested. Control (A) is the current behaviour; treatment (B) is the
  change.
- **Randomisation unit** — what gets assigned: a user, a session, a request, a device.
- **Primary metric** — the one number that decides the outcome. There is exactly one.
- **Guardrail metric** — a metric that must *not* get worse, even if the primary improves.
- **MDE (minimum detectable effect)** — the smallest change your test is designed to detect.
- **Power** — the probability of detecting a real effect of MDE size. Conventionally 0.80.
- **SRM (sample ratio mismatch)** — the observed split differs from the intended one by more than
  chance.

### Designing a test, end to end

The example: does changing the checkout button from grey to green increase purchases?

**1. Pick the randomisation unit.** User, not session or request.

Why user matters: if you randomise per *session*, a single person sees green on Monday and grey on
Tuesday. Their behaviour is contaminated by both, and — worse — heavy users appear in the data many
times, which breaks the independence assumption behind every test in Module 3 and makes your
confidence intervals too narrow.

**Rule: randomise at the level at which the user experiences the change, and at which you want to
measure the outcome.**

**2. Choose the primary metric.** *Purchase conversion rate: purchasers ÷ users.*

Not "clicks on the button" — a proxy that can improve while purchases do not. Not "revenue" as the
primary — it is high-variance and needs far more data (though it should be a secondary).

**3. Choose guardrails.** Metrics that must not degrade: page load time, error rate, refund rate,
support-contact rate. A conversion win bought with a doubled refund rate is not a win.

**4. Compute the sample size.** You need three inputs: baseline rate, the MDE, and the power.

```python
import numpy as np
from scipy import stats

def n_per_arm(p, mde_rel, alpha=0.05, power=0.80):
    """p: baseline rate. mde_rel: relative lift you want to detect, e.g. 0.10 for +10%."""
    p2 = p * (1 + mde_rel)
    za, zb = stats.norm.ppf(1 - alpha / 2), stats.norm.ppf(power)
    pbar = (p + p2) / 2
    num = (za * np.sqrt(2 * pbar * (1 - pbar)) + zb * np.sqrt(p*(1-p) + p2*(1-p2))) ** 2
    return int(np.ceil(num / (p2 - p) ** 2))

print(n_per_arm(0.05, 0.10))     # baseline 5%, want to detect a 10% relative lift
```

Measured table:

| Baseline | Relative MDE | n per arm | Total |
|---|---|---|---|
| 5% | 20% | 8,158 | 16,316 |
| 5% | 10% | 31,234 | 62,468 |
| 5% | 5% | 122,124 | 244,248 |
| 5% | 2% | 752,703 | 1,505,406 |
| 2% | 10% | 80,682 | 161,364 |
| 10% | 10% | 14,751 | 29,502 |
| 30% | 10% | 3,763 | 7,526 |

Two patterns worth extracting:

- **Sample size scales as `1/MDE²`.** Halving the effect you want to detect quadruples the users
  needed: 10% MDE needs 31,234 per arm, 5% needs 122,124 — almost exactly 4×.
- **Rarer events need more data.** At a 2% baseline you need 80,682 per arm for a 10% lift; at 30%
  baseline, 3,763. That is a **21× difference** for the same relative effect.

**5. Write the decision rule before launching.** Literally write it down:

> Primary: purchase conversion. MDE: +5% relative. n = 122,124 per arm. Run for 14 days minimum
> (two full weekly cycles) or until n is reached, whichever is later. Ship if the 95% CI on the
> relative lift excludes zero and no guardrail degrades by more than 1%. Do not look at the primary
> metric before day 14.

That paragraph is the difference between an experiment and a search for a favourable number.

### Randomisation, and why it is the whole argument

The assignment must be:

- **Deterministic** — the same user always gets the same variant. Use `hash(user_id + experiment_id)`,
  not a random number generator at request time.
- **Independent across experiments** — include the experiment id in the hash, or experiment 2's
  assignment will correlate with experiment 1's.
- **Uniform** — the hash must spread evenly.

```python
import hashlib

def assign(user_id: str, experiment_id: str, split=0.5) -> str:
    h = hashlib.sha256(f"{experiment_id}:{user_id}".encode()).digest()
    x = int.from_bytes(h[:8], "big") / 2**64        # uniform in [0, 1)
    return "treatment" if x < split else "control"

from collections import Counter
c = Counter(assign(f"user{i}", "exp_button_colour") for i in range(100_000))
print(c)          # Counter(&#123;'control': 50241, 'treatment': 49759&#125;) -- close to 50/50
```

Using `hashlib` rather than Python's built-in `hash()` is not fussiness: `hash()` on strings is
**randomly salted per process** by default, so the same user gets different variants on different
servers and after every restart. This is a real and very common bug.

### The SRM check: four lines that save you

You asked for 50/50. You got 50,000 and 48,000. Is that a problem?

```python
import numpy as np
from scipy import stats

def srm_check(counts, expected_ratio=(0.5, 0.5)):
    obs = np.array(counts, dtype=float)
    exp = obs.sum() * np.array(expected_ratio)
    chi2 = ((obs - exp) ** 2 / exp).sum()
    p = 1 - stats.chi2.cdf(chi2, len(obs) - 1)
    return chi2, p

for a, b, label in [(50000, 50000, "clean 50/50"), (50000, 49900, "0.1% short"),
                    (50000, 49500, "0.5% short"), (50000, 48000, "4% short")]:
    chi2, p = srm_check([a, b])
    print(f"{label:<14} {a:,}/{b:,}  chi2={chi2:8.2f}  p={p:.3e}  "
          f"{'SRM - do not trust this test' if p < 0.001 else 'ok'}")
```

Measured:

```
clean 50/50    50,000/50,000  chi2=    0.00  p=1.000e+00  ok
0.1% short     50,000/49,900  chi2=    0.10  p=7.517e-01  ok
0.5% short     50,000/49,500  chi2=    2.51  p=1.129e-01  ok
4% short       50,000/48,000  chi2=   40.82  p=1.672e-10  SRM - do not trust this test
```

**Why a failed SRM invalidates everything.** You designed a 50/50 split. If you got 51/49, *something
non-random selected which users went where*. Common causes: the treatment crashes on old browsers so
those users drop out of B; a redirect loses slow connections; a bot filter is applied to one arm only;
an assignment bug.

Whatever the cause, the two groups now differ in a way you did not control, so **the difference in
your metric is confounded** and cannot be attributed to the treatment. The result is not "slightly
biased" — it is uninterpretable.

Use a strict threshold: **p &lt; 0.001**, not 0.05. You will run many experiments and you do not want
to chase false SRM alarms. But when it fires, stop, find the cause, and re-run.

### Peeking: the measured cost

Everyone wants to look at the result early. Here is what it costs, simulated on data with **no real
effect at all**:

```python
import numpy as np
from scipy import stats
rng = np.random.default_rng(7)

def run_peeking(n_final, peeks, trials=4000):
    false_pos = 0
    checks = np.linspace(n_final // peeks, n_final, peeks).astype(int)
    for _ in range(trials):
        a = rng.normal(0, 1, n_final)
        b = rng.normal(0, 1, n_final)          # identical distributions: NO effect
        for n in checks:
            if stats.ttest_ind(a[:n], b[:n])[1] < 0.05:
                false_pos += 1
                break                           # "we stopped early because it was significant"
    return false_pos / trials

for peeks in (1, 2, 5, 10, 20):
    print(f"peeking {peeks:>2} time(s): false-positive rate = {run_peeking(2000, peeks):.4f}")
```

Measured:

| Number of looks | False-positive rate | Inflation |
|---|---|---|
| 1 (correct) | 0.0512 | 1.0× |
| 2 | 0.0815 | 1.6× |
| 5 | 0.1363 | 2.7× |
| 10 | 0.1883 | 3.7× |
| **20** | **0.2507** | **5.0×** |

**Checking your dashboard 20 times gives you a one-in-four chance of declaring a win when nothing
happened.** And 20 looks is not paranoid — it is one look per weekday for a four-week test, which is
exactly what everybody does.

The mechanism is simple. The p-value wanders randomly over time. Given enough looks, it will dip below
0.05 at some point by chance, and the practice of "stop when significant" guarantees you catch it when
it does.

The fixes, in order of practicality:

1. **Fix the sample size in advance and look once.** Free, correct, unpopular.
2. **Sequential testing with a correction.** O'Brien-Fleming or Pocock boundaries adjust the threshold
   at each interim look so the overall `α` stays at 0.05. O'Brien-Fleming is strict early and near-
   nominal at the end, which is usually what you want.
3. **Always-valid inference.** Mixture sequential probability ratio tests and confidence sequences give
   intervals valid at *every* moment, so you may look continuously. This is what modern
   experimentation platforms (Optimizely's Stats Engine, Statsig, Eppo) implement. The cost is roughly
   20–50% more data for the same power — a real price, paid for the ability to stop whenever you like.

**Whichever you choose, choose it before launch.** Deciding to apply a sequential correction after you
have already peeked does not undo the peeking.

### CUPED: getting the same answer with less data

**CUPED** (Controlled-experiment Using Pre-Existing Data) uses a pre-experiment covariate — usually the
same metric measured before the experiment started — to remove variance that has nothing to do with
the treatment.

The idea: a user who spent a lot last month will probably spend a lot this month, in either arm. That
variation is noise for your purposes. Subtract the predictable part.

```
Y_adjusted = Y − θ(X − X̄)        where θ = Cov(Y, X) / Var(X)
```

`θ` is the least-squares slope of `Y` on `X`. The adjustment is **unbiased** — it does not change the
expected treatment effect — and it reduces variance by a factor of `1 − ρ²`.

```python
import numpy as np
rng = np.random.default_rng(7)
N = 20_000

for rho in (0.0, 0.3, 0.5, 0.7, 0.9):
    pre = rng.normal(100, 20, N)
    post = 100 + rho*(pre - 100) + rng.normal(0, 20*np.sqrt(1 - rho**2), N)
    assign = rng.integers(0, 2, N)
    post = post + assign * 2.0                       # true treatment effect: +2.0

    theta = np.cov(post, pre)[0, 1] / np.var(pre)
    cuped = post - theta * (pre - pre.mean())

    def eff(y):
        a, b = y[assign == 0], y[assign == 1]
        se = np.sqrt(a.var(ddof=1)/len(a) + b.var(ddof=1)/len(b))
        return b.mean() - a.mean(), se

    d0, se0 = eff(post); d1, se1 = eff(cuped)
    print(f"corr={np.corrcoef(pre, post)[0,1]:.3f}  plain {d0:+.4f}+/-{1.96*se0:.4f}  "
          f"CUPED {d1:+.4f}+/-{1.96*se1:.4f}  variance -{1-(se1/se0)**2:.1%}  "
          f"n needed x{(se1/se0)**2:.3f}")
```

Measured (true effect is +2.0 in every row):

| corr(pre, post) | Plain estimate ± CI | CUPED estimate ± CI | Variance reduction | Sample size needed |
|---|---|---|---|---|
| 0.010 | +2.4554 ± 0.5538 | +2.4554 ± 0.5538 | 0.0% | ×1.000 |
| 0.296 | +2.5113 ± 0.5540 | +2.4919 ± 0.5290 | 8.8% | ×0.912 |
| 0.502 | +2.1887 ± 0.5583 | +2.1393 ± 0.4825 | 25.3% | ×0.747 |
| 0.696 | +1.6375 ± 0.5511 | +1.9137 ± 0.3952 | 48.6% | ×0.514 |
| **0.899** | +1.6805 ± 0.5543 | **+2.0173 ± 0.2417** | **81.0%** | **×0.190** |

Read the bottom row. With a covariate correlated 0.9 with the outcome, CUPED **cuts the required
sample size to 19%** — a 5.3× speedup, or equivalently the same test in a fifth of the time. And note
the estimate itself: plain gives +1.68 against a true +2.0, while CUPED gives +2.02. The variance
reduction is not just narrower intervals, it is a more accurate point estimate.

The variance reduction is exactly `ρ²`: at ρ = 0.9 that is 0.81, matching the measured 81.0%.

**Two conditions that must hold:**

1. **The covariate must be measured entirely before the experiment starts.** Using anything measured
   during the experiment can be affected by the treatment, which biases the estimate. This is the one
   way to get CUPED wrong, and it is silent.
2. **The covariate must correlate with the outcome.** At ρ = 0.01 the measured reduction was 0.0% —
   CUPED did nothing, harmlessly. It never hurts; it just sometimes does not help.

The best covariate is almost always **the same metric from the pre-period**, which typically correlates
0.4–0.8 for user-level engagement metrics — worth a 16–64% variance reduction for essentially free.

### Novelty and primacy effects

**Novelty:** users engage with anything new simply because it is new. A UI change can show a large lift
in week 1 that decays to zero by week 3.

**Primacy:** the opposite — users are slowed by an unfamiliar interface and the treatment looks worse
initially, then recovers.

Both mean **the effect measured on day 1 is not the effect you will get in steady state**. Detect them
by plotting the treatment effect *by day since first exposure*, not just cumulatively. A monotone decay
towards zero is novelty; a rise from negative is primacy.

The practical rule: **run for at least two full weekly cycles.** Weekday and weekend users behave
differently, so a test running Tuesday to Friday is measuring a non-representative population. Two
weeks is the usual minimum, and longer for anything touching habitual behaviour.

### Trade-offs

| Decision | Choose this when… | Choose the other when… | The number |
|---|---|---|---|
| **Fixed horizon, one look** | You can wait; you want maximum power per user | You need to stop early for bad results | Correct 5% false-positive rate versus 25% with 20 looks |
| **Sequential / always-valid** | You must monitor continuously; stopping early matters | Data is plentiful and patience is available | Roughly 20–50% more data for the same power |
| **CUPED** | You have a pre-period covariate correlated with the outcome | No pre-period data (new users) | Measured: ρ = 0.9 cuts required `n` to 19% |
| **User-level randomisation** | Almost always | The unit genuinely is a request (infrastructure tests) | Session-level randomisation contaminates users and breaks independence |
| **Strict SRM threshold (p &lt; 0.001)** | You run many experiments | You run few and can investigate every alert | At `p < 0.05` you would investigate 1 in 20 healthy experiments |

### What breaks in the real world

A team ran a recommendation-algorithm test for three weeks. The treatment showed a **+3.2% lift in
click-through, p = 0.008**. They shipped it. Post-launch metrics showed no improvement at all.

The post-mortem found an SRM: 1,043,221 users in control against 1,009,887 in treatment — a 1.6% gap,
`p < 1e-100`. Nobody had checked.

The cause was mundane. The new recommendation service had a 400 ms p99 that occasionally exceeded the
page's 500 ms client-side timeout. When it timed out, the client fell back to the control experience
**and logged the user as control**. So the treatment arm systematically lost its slowest sessions —
slow connections, older devices, congested networks — and those users click less.

**The 3.2% "lift" was a healthier population, not a better algorithm.**

Three fixes, and the third is the one that generalises: check SRM automatically on every experiment,
before anyone sees the metrics; log assignment at the point of *assignment*, never at the point of
*rendering*; and treat any fallback path as a potential source of differential attrition, because it
almost always is.

### Design checkpoint

<Accordion title="You must test a change to a marketplace's search ranking. Sellers and buyers both use it. What breaks, and how do you design around it?">

The randomisation assumption breaks, and this is the most important thing to recognise: **units are not
independent.** This is **interference**, or SUTVA violation (Stable Unit Treatment Value Assumption).

Concretely, in a marketplace:

- If treatment buyers get better search results, they buy more of a **finite inventory**. Control
  buyers now face a depleted marketplace and convert *worse*. The measured difference is inflated: it
  includes both the treatment's benefit and the harm it inflicted on control.
- Sellers respond to demand. A seller who gets more views from treatment buyers restocks or raises
  prices, which affects everyone.

The consequence is that a naive A/B test **overestimates the effect**, sometimes enormously, and the
overestimate is largest exactly when the change is most effective. Shipping to 100% then produces a
much smaller lift than the test promised — which is precisely the pattern of "our experiments always
overpromise" that marketplace teams report.

Designs that handle it, in increasing order of cost:

1. **Cluster randomisation.** Randomise geographic markets, product categories, or time-zone regions
   rather than users. Interference happens *within* a cluster and clusters are roughly independent.
   The cost is severe: your effective sample size becomes the number of *clusters*, not users. Forty
   cities means `n = 40`, and the MDE goes up correspondingly.
2. **Switchback tests.** Randomise *time periods* — the whole marketplace runs treatment for 30
   minutes, then control for 30 minutes, alternating. Every unit sees both, so cross-unit interference
   within a period is captured. Used heavily by ride-hailing and delivery platforms. Requires
   careful handling of carryover (a period is contaminated by the previous one) and of time-of-day
   effects.
3. **Two-sided / bipartite randomisation.** Randomise supply and demand separately and estimate both
   effects. Complex, and the right answer when you genuinely need to separate them.
4. **Budget-split designs.** Split the *inventory* as well as the users, so each arm has its own pool.
   Clean but expensive and often infeasible.

**What to actually do**, and this is the honest answer: run the user-level test to get a fast directional
read, and treat the number as an **upper bound**. Then validate with a switchback or a
market-level holdout before committing to the headline figure. State the interference explicitly in
the readout so that nobody quotes the inflated number in a planning document.

The answer that gets you hired names SUTVA, explains the mechanism (finite inventory), states the
direction of the bias (overestimate), and proposes switchback as the practical validation.

### Sequential testing, properly

The problem with peeking is that a fixed threshold of 0.05 applied `k` times has a family-wise error
rate far above 0.05 — measured at **0.2507 for 20 looks**.

Three principled solutions:

**Group sequential boundaries.** Pre-specify `k` interim analyses and adjust the threshold at each.

- **Pocock**: the same, stricter, threshold at every look (about 0.0158 for 5 looks at overall
  α = 0.05). Simple; loses power at the final analysis.
- **O'Brien-Fleming**: very strict early (around 5e-6 at the first of 5 looks), nearly nominal at the
  end (about 0.041). This is usually what you want — early stopping only for overwhelming evidence,
  and almost no power sacrificed at the planned end.

**Always-valid inference.** Confidence sequences (Howard et al., 2021) and mixture SPRTs give
intervals valid at *every* sample size simultaneously, so continuous monitoring is legitimate. This is
what Optimizely's Stats Engine, Statsig and Eppo implement. The price is roughly 20–50% more data for
the same power at the fixed horizon.

**Bayesian monitoring.** Report `P(treatment > control | data)` and stop when it exceeds a threshold.
Legitimate under a Bayesian interpretation and *not* immune to optional stopping if you then interpret
it in frequentist terms — a widely misunderstood point. Deng, Lu and Chen's work on Bayesian A/B
testing addresses exactly this.

### The false-discovery arithmetic of an experiment programme

Here is the calculation almost nobody does. Suppose:

- You run 100 experiments a year.
- **10%** of your ideas are genuinely good (a realistic figure — large programmes report win rates
  from 10% to 30%).
- α = 0.05, power = 0.80.

Then among the tests that come back significant:

```
true positives  = 100 × 0.10 × 0.80 = 8
false positives = 100 × 0.90 × 0.05 = 4.5
```

**36% of your "wins" are false.** And that is with perfect methodology — no peeking, no segment
fishing, no SRM.

With peeking 20 times, the false-positive rate becomes 0.25:

```
false positives = 100 × 0.90 × 0.25 = 22.5   ->  74% of "wins" are false
```

Three quarters of your shipped wins are noise. This is the arithmetic behind the well-documented
phenomenon that large experimentation programmes see their aggregate metric improve far less than the
sum of their individual "wins" predicts.

The levers: raise the prior (better ideas, from research rather than brainstorming), raise power (more
data per test, or CUPED), lower α for irreversible changes, and — the most effective — **replicate the
important wins**. A replication at α = 0.05 takes the false-positive rate on that decision to 0.0025.

### Metric selection and the OEC

The **Overall Evaluation Criterion** is the single metric a test is decided on. Getting it right is the
hardest part of experimentation and the least statistical.

| Metric type | Example | Problem |
|---|---|---|
| **Proxy** | Clicks | Easy to move, weakly related to value. Clickbait improves it |
| **Direct** | Purchases | Sparser, higher variance, longer horizon |
| **Long-term** | Retention at 90 days | Cannot be measured within an experiment's lifetime |
| **Guardrail** | Latency, error rate, refunds | Must not degrade; not what you are optimising |

The structural problem is that **the metric you can measure quickly is rarely the one you care about**.
Kohavi's canonical example: at Bing, a bug that *degraded* search relevance *increased* both revenue
per search and queries per user — because users searched more when the first results failed them. Any
short-term revenue OEC would have shipped a change that harmed the product.

Two defences:

- **A surrogate validated against long-term outcomes.** Establish, from historical experiments, which
  short-term metrics actually predict the long-term one you care about, and use those.
- **Long-term holdouts.** Keep 1–5% of users out of all changes for 6–12 months and measure the
  cumulative effect. This is the only way to catch slow degradation from a series of individually
  positive changes, and every large experimentation programme that has run one has found surprises.

### Interference and network effects

A/B testing assumes **SUTVA**: one unit's outcome depends only on its own treatment. Violations are
common and produce biased estimates in a *predictable direction*:

| Setting | Mechanism | Bias direction |
|---|---|---|
| Social network | Treated users influence untreated friends | **Underestimate** (control is partially treated) |
| Marketplace | Treated buyers deplete shared inventory | **Overestimate** (control is harmed) |
| Ad auction | Treated advertisers bid up prices | Overestimate |
| Shared cache | Treatment warms the cache for control | Underestimate |
| Rate limits / capacity | Treatment consumes shared capacity | Overestimate |

Designs: **cluster randomisation** (independent groups; effective `n` becomes the number of clusters),
**switchback** (randomise time periods; every unit sees both), **ego-cluster** (randomise a user and
their close neighbourhood together), and **two-sided randomisation** for marketplaces.

The cost of clustering is severe and is the thing people underestimate: with 40 markets, your effective
sample size is 40, not four million users, and the MDE rises by roughly `sqrt(n_users/n_clusters)`
adjusted by the intra-cluster correlation. A design that is unbiased and cannot detect anything is not
better than a biased one — you have to state both.

### Production failure modes

| Failure | Signature | Detection |
|---|---|---|
| **SRM** | Split differs from intended by more than chance | Chi-square at `p < 0.001`, automatically, on every experiment, before metrics are shown |
| **Differential attrition via a fallback path** | SRM plus a plausible-looking lift | Log assignment at assignment time, never at render time; audit every fallback |
| **Peeking** | "It reached significance on day 3" | Measured 25% false-positive rate at 20 looks. Fixed horizon or a sequential correction chosen in advance |
| **Segment fishing** | "It didn't work overall but it worked for iOS users in Germany" | Pre-declare segments; correct for multiplicity; treat post-hoc segments as hypothesis-generating only |
| **Novelty effect** | Large day-1 lift decaying towards zero | Plot the effect by days since first exposure; run at least two weekly cycles |
| **Interference** | Test lift far exceeds the post-launch lift | Name the mechanism; validate with a switchback or market holdout; treat the A/B number as an upper bound |
| **Underpowered test read as "no effect"** | `p = 0.3` on a real 4% effect | State the MDE before launch; a null result below the MDE is uninformative |
| **CUPED covariate from the experiment period** | Estimate biased, silently | The covariate must be measured entirely before assignment |
| **Multiple metrics, no correction** | Every experiment "wins" on something | One pre-declared primary metric; everything else exploratory |

- **S. R. Howard, A. Ramdas, J. McAuliffe and J. Sekhon, "Time-uniform, nonparametric,

- **D. Eckles, B. Karrer and J. Ugander, "Design and Analysis of Experiments in Networks: Reducing

- **R. Kohavi, A. Deng, B. Frasca, T. Walker, Y. Xu and N. Pohlmann, "Online controlled experiments at
  large scale," KDD 2013.** Takeaway: the Bing case where degraded relevance increased short-term

### Stretch challenge

Build an experiment analyser that refuses to give you a number you should not trust.

1. Implement, as blocking checks that run *before* any metric is displayed: SRM (chi-square,
   `p < 0.001`), pre-period balance on 5–10 covariates, and an outlier/bot filter applied identically
   to both arms.
2. Implement the analysis: primary metric with a bootstrap CI on the difference, guardrails with
   one-sided checks, and CUPED using a pre-period covariate. Report the variance reduction achieved.
3. Implement **sequential correction**: O'Brien-Fleming boundaries for a stated number of interim
   looks. Verify by simulation that the family-wise false-positive rate stays at 0.05 across those
   looks — this is the test that proves your implementation is correct.
4. Add a **novelty detector**: estimate the treatment effect by day since first exposure, fit a trend,
   and flag a significant decay.
5. Feed it the deliberately broken dataset from the lab — the one with a subtle SRM — and confirm it
   refuses to report a result. Then write the readout: what happened, why the result cannot be used,
   and what would have to change to re-run it.

There is no single right answer for step 4 — separating novelty from a genuine time trend requires
assumptions, and stating yours explicitly is the deliverable.

## Common mistakes

| Symptom | Cause | Fix |
|---|---|---|
| A significant, plausible lift that does not replicate post-launch | SRM from differential attrition (a fallback path) | Automatic chi-square SRM check at `p < 0.001` before any metric is shown |
| "It reached significance on day 3" | Peeking with a fixed 0.05 threshold | Measured 25% false-positive rate at 20 looks. Fixed horizon, or sequential boundaries chosen in advance |
| Same user sees both variants | Randomised by session or request | Randomise by user with a stable hash including the experiment id |
| Assignment differs across servers | Python's `hash()` is salted per process | Use SHA-256 or another stable hash |
| "It worked for iOS users in Germany" | Post-hoc segment fishing | Pre-declare segments; correct for multiplicity; post-hoc findings are hypotheses |
| Large day-1 lift that fades | Novelty effect | Plot the effect by days since exposure; run at least two weekly cycles |
| Test lift much larger than post-launch lift | Interference (shared inventory, capacity, network) | Name the mechanism; validate with a switchback or market holdout |
| CUPED result biased | Covariate measured during the experiment | The covariate must predate assignment entirely |
| "No effect" from an underpowered test | MDE never stated | State the MDE before launch; a null below the MDE is uninformative |

<Accordion title="Concept questions (8)">
1. Why randomise by user rather than session? *(Sessions from one user are dependent, the user is contaminated by both variants, and heavy users would be over-represented — breaking the independence assumption.)*

4. Measured false-positive rate when peeking 20 times? *(0.2507, a 5× inflation over the nominal 0.05.)*

6. Why must the CUPED covariate predate the experiment? *(Anything measured during the experiment can be affected by the treatment, which biases the estimate silently.)*
7. With a 10% idea-success rate, α = 0.05 and 80% power, what fraction of "wins" are false? *(4.5 false against 8 true — about 36%, with perfect methodology.)*
8. Give one interference mechanism and the direction of its bias. *(Marketplace inventory depletion: treatment harms control, so the estimate is inflated. Or social spillover: control is partially treated, so the estimate is deflated.)*
