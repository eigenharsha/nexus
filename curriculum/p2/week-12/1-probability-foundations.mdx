### The words, defined

- **Experiment** — anything with an uncertain outcome: a coin flip, a user visit, an email arriving.
- **Sample space** — the set of all possible outcomes. For one die, `{1,2,3,4,5,6}`.
- **Event** — a subset of the sample space. "The die shows an even number" is `{2,4,6}`.
- **Probability** — a number between 0 and 1 assigned to an event. For equally likely outcomes it is
  just "favourable outcomes divided by total outcomes".
- **Conditional probability** — `P(A | B)`, read "probability of A given B": the probability of A once
  you know B happened.
- **Independent** — A and B are independent if knowing B tells you nothing about A:
  `P(A | B) = P(A)`.
- **Random variable** — a number determined by the outcome. "The number shown on the die" is one.
- **Expectation** — the long-run average value of a random variable, written `E[X]`.

### Start with dice

One fair six-sided die. `P(even) = 3/6 = 0.5`. `P(> 4) = 2/6 = 1/3`.

Now the conditional version. **Given that the die shows an even number**, what is `P(> 4)`? The
possible worlds have shrunk to `{2, 4, 6}`, and one of those three is greater than 4. So
`P(>4 | even) = 1/3`.

Interesting: `P(>4) = 1/3` too. Knowing it was even told you nothing. Those two events are
**independent** — for this die, coincidentally.

The general formula:

```
P(A | B) = P(A and B) / P(B)
```

Check it: `P(>4 and even) = P({6}) = 1/6`. `P(even) = 1/2`. So `(1/6)/(1/2) = 1/3`. ✓

**Simulate it, always.** The single most useful habit in this module is checking every probability
answer by simulation. It takes four lines and it catches errors that reasoning does not.

```python
import random
rng = random.Random(0)
trials = 1_000_000
even = 0; even_and_big = 0
for _ in range(trials):
    d = rng.randint(1, 6)
    if d % 2 == 0:
        even += 1
        if d > 4:
            even_and_big += 1
print(even_and_big / even)      # 0.3327184477674052  -> 1/3. Confirmed.
```

### The medical test paradox, slowly

This is the most important example in Week 12. Read it twice.

A disease affects **1 in 1,000** people. A test is **99% accurate**, meaning:

- If you have the disease, it says positive 99% of the time (**sensitivity** = 0.99).
- If you do not, it says negative 99% of the time (**specificity** = 0.99).

You test positive. **What is the probability you have the disease?**

Most people say about 99%. Take a moment and commit to an answer before reading on.

Now count. Imagine **100,000 people**:

```
                        have it (100)      don't have it (99,900)
test positive            99                       999
test negative             1                    98,901
```

- Of the 100 who have it, 99 test positive (99% sensitivity).
- Of the 99,900 who do not, 1% test positive anyway — that is **999 false positives**.

Total positives: `99 + 999 = 1,098`. Of those, 99 actually have the disease.

```
P(disease | positive) = 99 / 1098 = 0.0902 = 9.0%
```

**Nine percent.** A 99%-accurate test, and a positive result means a 9% chance you are ill. There are
**ten false positives for every true one**.

The reason is not the test. It is that healthy people vastly outnumber sick ones, so even a small
error rate applied to a huge group produces more errors than the small group produces correct hits.
`1% of 99,900 = 999` beats `99% of 100 = 99`.

**This is the single most important fact in applied machine learning**, and the module's Layer 2 shows
it happening to a real classifier.

### Bayes' theorem

That counting argument, written as a formula:

```
P(A | B) = P(B | A) × P(A) / P(B)
```

- `P(A)` is the **prior** — what you believed before the evidence. Here, 0.001.
- `P(B | A)` is the **likelihood** — how likely the evidence is if A is true. Here, 0.99.
- `P(B)` is the total probability of the evidence, from all causes:
  `P(B) = P(B|A)P(A) + P(B|not A)P(not A) = 0.99 × 0.001 + 0.01 × 0.999 = 0.01098`.
- `P(A | B)` is the **posterior** — your updated belief. `0.99 × 0.001 / 0.01098 = 0.0902`. ✓

```python
def bayes(prior, sensitivity, false_positive_rate):
    p_evidence = sensitivity * prior + false_positive_rate * (1 - prior)
    return sensitivity * prior / p_evidence

print(bayes(0.001, 0.99, 0.01))     # 0.09016...
```

### The odds form, which is easier

There is a version that avoids the denominator entirely and is much easier to reason with:

```
posterior odds = prior odds × likelihood ratio
```

where the **likelihood ratio** is `P(evidence | A) / P(evidence | not A)`.

For the medical test:

- Prior odds: `1 : 999` (one sick person per 999 healthy).
- Likelihood ratio: `0.99 / 0.01 = 99`.
- Posterior odds: `99 : 999`, which is about `1 : 10`.
- As a probability: `99/(99+999) = 0.090`. ✓

**Read that as: the evidence multiplied your belief by 99, and it still was not enough**, because you
started 999-to-1 against. That framing — evidence multiplies, priors matter — is the intuition worth
carrying.

Now test yourself: what if you test positive **twice**, with two independent tests?

<Accordion title="Answer">

Multiply the likelihood ratios: `99 × 99 = 9,801`.

Posterior odds: `1 × 9801 : 999`, i.e. `9801 : 999`, which is about `9.8 : 1` in favour.
As a probability: `9801/(9801+999) = 0.907` — **90.7%**.

Two positives take you from 9% to 91%. That is why real diagnostic protocols retest, and why an
ensemble of independent weak signals can beat one strong one.

The essential caveat: **"independent" is doing a lot of work.** If both tests fail for the same
underlying reason — the same reagent batch, the same confounding condition, the same feature in a
model — the likelihood ratios do not multiply, and assuming they do is how confidently wrong systems
get built.

</Accordion>

### Expectation and variance

The **expectation** of a random variable is the probability-weighted average:

```
E[X] = Σ x · P(X = x)
```

For a fair die: `(1+2+3+4+5+6)/6 = 3.5`. Note that 3.5 is not a possible outcome — an expectation is
an average, not a prediction.

**Variance** measures spread: the expected squared distance from the mean.

```
Var(X) = E[(X − E[X])²] = E[X²] − (E[X])²
```

For a fair die: `E[X²] = (1+4+9+16+25+36)/6 = 15.167`, so `Var = 15.167 − 3.5² = 2.917`, and the
**standard deviation** (the square root) is 1.708.

```python
import statistics
outcomes = [1,2,3,4,5,6]
print(statistics.mean(outcomes))    # 3.5
print(statistics.pvariance(outcomes))  # 2.9166666666666665
print(statistics.pstdev(outcomes))     # 1.707825127659933
```

Two properties you will use constantly:

- **`E[X + Y] = E[X] + E[Y]`** — always, even if X and Y are related.
- **`Var(X + Y) = Var(X) + Var(Y)`** — **only if X and Y are independent.** This is why the standard
  error of a mean is `σ/sqrt(n)` (Module 3), and why correlated observations make your confidence
  intervals too narrow.

<Accordion title="1. What is the difference between P(A|B) and P(B|A)?">
They answer different questions and are rarely equal. `P(positive | sick)` is a property of the test;
`P(sick | positive)` also depends on how common the disease is. Confusing them is the base-rate
fallacy.
</Accordion>
<Accordion title="2. State Bayes' theorem in odds form.">
`posterior odds = prior odds × likelihood ratio`, where the likelihood ratio is
`P(evidence|A) / P(evidence|not A)`.
</Accordion>
<Accordion title="3. A 99% accurate test on a 1-in-1000 disease. Precision of a positive?">
About 9%. 99 true positives against 999 false ones per 100,000 people — ten false alarms per real case.
</Accordion>
<Accordion title="4. Why does Var(X+Y) = Var(X)+Var(Y) require independence?">
The general formula is `Var(X+Y) = Var(X) + Var(Y) + 2·Cov(X,Y)`, and the covariance term is zero only
when they are uncorrelated. Correlated data has more variance than the independent formula predicts,
which makes naive confidence intervals too narrow.
</Accordion>
<Accordion title="5. Two independent positive tests: 9% becomes what?">
Multiply the likelihood ratios: `99 × 99 = 9801`, giving odds of `9801:999` ≈ 90.7%. But check that
the tests really are independent — shared failure modes break the multiplication.
</Accordion>

### Naive Bayes, and why "naive"

Naive Bayes classifies by computing, for each class, `P(class | features)` via Bayes' theorem — and
making one deliberately false assumption: **that the features are conditionally independent given the
class.**

```
P(class | x₁,…,xₙ) ∝ P(class) × Π P(xᵢ | class)
```

For text, "free" and "money" appearing in a message are obviously not independent. The assumption is
wrong. It works anyway, and the reason is that classification only needs the *ranking* of class
scores to be right, not the probabilities themselves — the dependencies distort the magnitudes
without usually flipping the order.

Work in **log space**, always: multiplying a thousand probabilities each around 1e-4 underflows to
zero in float64 within about 80 terms.

```python
import re, math
from collections import Counter

TOKEN = re.compile(r"[a-z0-9$£!']+")
def tokenise(text): return TOKEN.findall(text.lower())

class NaiveBayes:
    """Bernoulli-style naive Bayes on token presence, with Laplace smoothing."""
    def __init__(self, alpha=1.0):
        self.alpha = alpha

    def fit(self, rows):                       # rows: list of (label 0/1, text)
        self.counts = [Counter(), Counter()]
        self.docs = [0, 0]
        vocab = set()
        for y, text in rows:
            self.docs[y] += 1
            for t in set(tokenise(text)):      # presence, not count
                self.counts[y][t] += 1
                vocab.add(t)
        self.vocab = vocab
        self.total = [sum(self.counts[0].values()), sum(self.counts[1].values())]
        n = self.docs[0] + self.docs[1]
        self.log_prior = [math.log(self.docs[0] / n), math.log(self.docs[1] / n)]
        return self

    def log_ratio(self, text):
        """log P(x|spam) - log P(x|ham): the EVIDENCE, with no prior."""
        V = len(self.vocab); s = 0.0
        for t in set(tokenise(text)):
            if t not in self.vocab:
                continue                        # unseen tokens carry no information
            p_spam = (self.counts[1][t] + self.alpha) / (self.total[1] + self.alpha * V)
            p_ham  = (self.counts[0][t] + self.alpha) / (self.total[0] + self.alpha * V)
            s += math.log(p_spam) - math.log(p_ham)
        return s

    def predict_logodds(self, text, prior_log_odds=None):
        if prior_log_odds is None:
            prior_log_odds = self.log_prior[1] - self.log_prior[0]
        return prior_log_odds + self.log_ratio(text)
```

**Two design decisions worth defending.**

`log_ratio` is separated from the prior. That is not stylistic: it lets you *change the prior at
prediction time without retraining*. If your training set is 13% spam and production traffic is 0.5%
spam, you substitute the production prior and the classifier is correctly calibrated. Almost no
tutorial implementation supports this, and it is the difference between a model that works in
production and one that does not.

**Laplace smoothing** (`alpha`) exists because a token seen only in ham gives `P(token | spam) = 0`,
which makes the whole product zero regardless of every other word. One unseen word would veto the
classification. Adding `alpha` to every count prevents it, and `alpha` is a real hyperparameter — the
lab measures the difference between 1.0 and 0.1.

### Measured: a real spam classifier

Trained on the **UCI SMS Spam Collection** (5,574 real SMS messages, 13.4% spam), 80/20 split with
`random.Random(42)`, vocabulary 8,262 tokens:

| | Value |
|---|---|
| Test set | 1,115 messages (14.3% spam) |
| Confusion matrix | TP 138, FP 2, FN 21, TN 954 |
| Accuracy | **0.9794** |
| Precision | **0.9857** |
| Recall (sensitivity) | **0.8679** |
| Specificity | **0.9979** |
| F1 | **0.9231** |

98% accuracy, 99% precision. A good classifier.

Now the point of the module. **Sensitivity and specificity are properties of the classifier and do not
change with prevalence. Precision does.** Applying Bayes' theorem with the measured sensitivity
(0.8679) and specificity (0.9979) at different base rates:

| Base rate (prevalence) | Precision | False positives per true positive |
|---|---|---|
| 50% | 0.9976 | 0.00 |
| **13.4%** (this dataset) | **0.9847** | 0.02 |
| 5% | 0.9562 | 0.05 |
| 1% | 0.8073 | 0.24 |
| **0.1%** | **0.2934** | **2.41** |
| **0.01%** | **0.0398** | **24.10** |

**The same classifier**, unchanged, goes from 98.5% precision to 4.0% precision. At a 0.01% base rate,
every genuine detection comes with 24 false alarms.

This is the arithmetic behind every "our fraud model has 99% accuracy" claim you will ever hear, and
it is why the first question about any detector is **"at what prevalence?"**

### Trade-offs

| Decision | Choose this when… | Choose the other when… | The number |
|---|---|---|---|
| **Naive Bayes** | Text classification, small data, you need speed and interpretability | Feature dependencies carry real signal | Trains on 4,459 messages in well under a second; F1 0.92 with no tuning |
| **Report precision/recall** | The classes are imbalanced | The classes are balanced and errors are symmetric | Accuracy was 0.979 while precision at 0.01% prevalence is 0.040 — accuracy hid a 25× problem |
| **Train-set prior** vs **production prior** | The training distribution matches production | It does not (almost always, for rare events) | Substituting the prior is free and re-calibrates the classifier without retraining |
| **Laplace `alpha = 1`** vs **smaller** | Small vocabulary, little data | Large vocabulary; you want sharper evidence | Measured F1: 0.9231 at `alpha = 1.0`, 0.9518 at `alpha = 0.1` |
| **Log space** | Always | Never | ~80 multiplications of 1e-4 underflows float64 to exactly zero |

### What breaks in the real world

A payments team shipped a fraud model with a validation AUC of 0.94 and precision of 0.91 on their
held-out set. In production the review queue was 94% false positives, and the operations team stopped
looking at it within three weeks.

The validation set had been **rebalanced to 50/50** to "help the model learn" — a defensible training
choice, applied by mistake to the *evaluation* set as well. Production fraud prevalence was about
0.2%. Recomputing precision at the true base rate from the measured sensitivity and specificity gave
0.07, which is what the queue actually showed.

The model was fine. The evaluation was not. Two fixes shipped: evaluate on a set with the **production
class balance**, always; and report *precision at a fixed alert volume* ("of the 500 cases we can
review per day, how many are fraud?") rather than precision at an arbitrary threshold, because that is
the number the operations team experiences.

**The general rule: rebalancing is a training technique, never an evaluation technique.** If you
rebalance to train, you must un-rebalance to evaluate, and the correction is exactly the Bayes
arithmetic in the table above.

### Design checkpoint

<Accordion title="You must detect a defect that occurs in 1 in 5,000 units. Your classifier has 95% sensitivity and 99% specificity. Is this shippable?">

Compute before opining.

Per 1,000,000 units: 200 defective, 999,800 good.

- True positives: `0.95 × 200 = 190`
- False positives: `0.01 × 999,800 = 9,998`
- Precision: `190 / 10,188 = 1.9%`

**52 false alarms per real defect.** If a human inspects each alert, that is 10,188 inspections to
catch 190 defects. Whether that is shippable depends entirely on the cost ratio, and now you can
compute it: if an inspection costs £2 and a missed defect costs £5,000, then the alerting system costs
£20,376 and saves `190 × £5,000 = £950,000`. **Ship it.** If an inspection costs £200 and a missed
defect costs £300, do not.

**The lever that actually matters is specificity, not sensitivity.** Going from 99% to 99.9%
specificity cuts false positives from 9,998 to 1,000 and raises precision from 1.9% to **16%** — an
8.4× improvement. Going from 95% to 99% *sensitivity* only takes true positives from 190 to 198 and
precision to 2.0%. **When the negative class is 5,000× larger, the false-positive rate is multiplied
by 5,000 and the false-negative rate is not.**

Three further moves worth naming:

1. **Cascade.** A cheap high-recall filter followed by an expensive high-precision one. The second
   stage only sees the ~1% that passed the first, where the effective base rate is now much higher —
   you have engineered the prevalence upward.
2. **Change the operating point deliberately.** Report precision at a fixed alert budget, not at
   threshold 0.5. "The top 500 alerts contain 180 of the 200 defects" is a statement a factory manager
   can act on.
3. **Reduce the population.** If defects concentrate in one production line or one supplier, run the
   detector only there. Halving the population halves the false positives at no cost to recall.

</Accordion>

### Base-rate neglect, in production terms

The relationship between precision, prevalence and the classifier's two rates:

```
precision = (TPR × π) / (TPR × π + FPR × (1 − π))
```

where `π` is prevalence, TPR is sensitivity and FPR is `1 − specificity`.

Differentiate the intuition rather than the formula: **as `π → 0`, precision → `TPR·π / (FPR·(1−π))`,
which is proportional to `π/FPR`.** Precision falls linearly with prevalence and is inversely
proportional to the false-positive rate. That is why:

- Halving prevalence halves precision (in the low-prevalence regime).
- Halving FPR doubles precision.
- Improving TPR does essentially nothing.

The measured curve for the real spam classifier (TPR 0.8679, FPR 0.0021):

| π | Precision | FP per TP |
|---|---|---|
| 50% | 0.9976 | 0.00 |
| 13.4% | 0.9847 | 0.02 |
| 1% | 0.8073 | 0.24 |
| 0.1% | 0.2934 | 2.41 |
| 0.01% | 0.0398 | 24.10 |

Note the shape: from 13.4% to 1% precision only falls from 0.985 to 0.807, and then it collapses.
**The cliff is between 1% and 0.1%**, which is exactly where most interesting production detection
problems live — fraud, abuse, security alerts, rare defects, model regressions.

### The same arithmetic in three other places you will meet

**1. Model evaluation (Week 31).** You have 200 eval prompts and your model fails on 0.5% of
production traffic. The probability that at least one of your 200 prompts triggers the failure is
`1 − 0.995²⁰⁰ = 63%`. So a third of the time you ship the bug and your eval suite is green. To be 95%
confident of catching a 0.5% failure mode you need `log(0.05)/log(0.995) ≈ 598` samples — and to catch
a 0.05% failure mode, about 5,990.

```python
import math
for rate in (0.05, 0.01, 0.005, 0.001):
    n = math.log(0.05) / math.log(1 - rate)
    print(f"failure rate {rate:>7.3%}: need {math.ceil(n):>6,} samples for 95% detection")
```

```
failure rate  5.000%: need     59 samples for 95% detection
failure rate  1.000%: need    299 samples for 95% detection
failure rate  0.500%: need    598 samples for 95% detection
failure rate  0.100%: need  2,995 samples for 95% detection
```

This is the identical structure to the Pentium FDIV argument in Week 9 Module 3 — sampling cannot
bound a rate much below `3/n`.

**2. A/B testing.** A test with 80% power will miss a real effect 20% of the time. If only 1 in 10 of
your ideas actually works, then among tests that come back significant at `α = 0.05`, the fraction
that are real is `0.8 × 0.1 / (0.8 × 0.1 + 0.05 × 0.9) = 64%`. **A third of your "wins" are noise**,
before any p-hacking. Module 4 develops this.

**3. Security alerting.** An IDS with a 0.1% false-positive rate on 10 million daily events generates
10,000 alerts a day. If genuine intrusions occur once a week, precision is about
`1/70,000`. This is the arithmetic behind alert fatigue, and it is why security teams tune for
specificity to an extent that looks paranoid from outside.

### Calibration: probabilities that mean something

A classifier is **calibrated** if, among the cases it assigns probability 0.7, about 70% are positive.
Accuracy does not imply calibration and calibration does not imply accuracy.

Naive Bayes is famously **badly calibrated**: because it multiplies dependent features as if they were
independent, the evidence is double-counted and the scores are pushed towards 0 and 1. It ranks well
and its probabilities are close to meaningless.

Measure it with a **reliability diagram** (bin by predicted probability, plot observed frequency) or
summarise with **Expected Calibration Error**:

```python
import numpy as np
def ece(probs, labels, bins=10):
    edges = np.linspace(0, 1, bins + 1)
    total = 0.0
    for lo, hi in zip(edges[:-1], edges[1:]):
        m = (probs > lo) & (probs <= hi)
        if m.sum() == 0: continue
        total += m.mean() * abs(labels[m].mean() - probs[m].mean())
    return total
```

Fixes: **Platt scaling** (fit a logistic regression on the scores) or **isotonic regression** (fit a
monotone step function). Both need a held-out calibration set. Isotonic is more flexible and needs
more data; Platt is nearly free and usually sufficient.

This matters whenever a downstream decision uses the probability as a number rather than as a rank —
expected-value calculations, thresholding on cost, or feeding a score into another model.

### Production failure modes

| Failure | Signature | Detection |
|---|---|---|
| **Evaluated on a rebalanced set** | Validation precision far above production precision | Evaluate at the production class balance; or recompute precision from TPR/FPR at the true prevalence |
| **Prevalence drift** | Precision degrades with no model or code change | Monitor the positive rate of the *input* stream, not just of predictions |
| **Reported accuracy on imbalanced data** | A model that predicts "negative" always scores 99.9% | Report precision, recall and the confusion matrix; never accuracy alone |
| **Numerical underflow** | Probabilities become exactly 0; ties everywhere | Work in log space |
| **Zero-probability veto** | One unseen word flips a confident classification | Laplace or Lidstone smoothing; measure `alpha` |
| **Assumed independence of correlated signals** | An ensemble is far more confident than it should be | Likelihood ratios only multiply for genuinely independent evidence; check for shared failure modes |
| **Uncalibrated scores used as probabilities** | Expected-value decisions are systematically wrong | Reliability diagram and ECE; Platt or isotonic calibration |
| **Train/serve prior mismatch** | Model is systematically over- or under-confident | Separate the prior from the evidence, as `log_ratio` does, and substitute the production prior |

### Frontier and further pointers

- **A. Tversky and D. Kahneman, "Judgment under Uncertainty: Heuristics and Biases," *Science* 185,
  1974.** Takeaway: people systematically ignore base rates when given individuating evidence, which
  is a stable cognitive bias rather than a lapse — so the arithmetic must be done explicitly, every
  time, by everyone.
- **D. Eddy, "Probabilistic reasoning in clinical medicine" (1982), and G. Gigerenzer and U. Hoffrage,
  "How to improve Bayesian reasoning without instruction: frequency formats," *Psychological Review*
  102(4), 1995.** Takeaway: when the medical-test problem is posed in percentages most physicians get
  it badly wrong; posed as natural frequencies ("of 1,000 people…") accuracy improves dramatically —
  which is why this module counts people rather than manipulating percentages.
- **A. Y. Ng and M. I. Jordan, "On Discriminative vs. Generative Classifiers: A comparison of logistic
  regression and naive Bayes," NeurIPS 2001.** Takeaway: naive Bayes converges to its (higher)
  asymptotic error much faster than logistic regression, so it wins on small datasets and loses on
  large ones — a precise statement of when the wrong independence assumption is worth making.
- **C. Guo, G. Pleiss, Y. Sun and K. Q. Weinberger, "On Calibration of Modern Neural Networks,"
  ICML 2017.** Takeaway: modern deep networks are systematically *overconfident* despite being more
  accurate than older ones, and temperature scaling — a single parameter — largely fixes it.

### Stretch challenge

Build a decision system where the base rate is the design variable.

1. Take the spam classifier and construct an **operating-point table**: for thresholds spanning the
   score range, compute TPR, FPR, precision and alerts-per-day at a stated traffic volume and
   prevalence. This is the table a product owner can actually make a decision from.
2. Add a **cost model**: cost per false positive (a user's real message blocked), cost per false
   negative (spam delivered). Find the threshold minimising expected cost, and show how it moves as
   prevalence changes from 13% to 0.1%.
3. Build a **two-stage cascade**: a cheap high-recall stage followed by an expensive high-precision
   one. Measure the end-to-end precision, recall and cost against the single-stage system at the same
   recall. Quantify how much of the gain comes from raising the effective prevalence entering stage 2.
4. Now **calibrate**: fit Platt scaling on a held-out set, measure ECE before and after, and check
   whether the cost-optimal threshold from step 2 changes. It usually does, and by more than people
   expect.
5. Write the one-page memo a product owner would actually read: what the system will do, how many
   false alarms per day, what it costs, and what the number is that would make you change the
   threshold.

There is no single right answer — the cost ratio is a business decision, not a statistical one, and
making that separation explicit is the point.

## The whole idea on one whiteboard

Probability is bookkeeping about a set of possible worlds.

**Conditional probability** narrows the set: `P(A | B)` means "of the worlds where B happened, what
fraction also have A?" Everything difficult in this module comes from confusing `P(A | B)` with
`P(B | A)`, which are almost never equal.

**Bayes' theorem** is the rule for flipping between them:

```
P(A | B) = P(B | A) × P(A) / P(B)
```

And the version you will actually use, in words:

```
posterior odds  =  prior odds  ×  likelihood ratio
```

Your belief after seeing evidence is your belief before, multiplied by how much more likely the
evidence is under one hypothesis than the other. **If the prior is tiny, strong evidence still leaves
you uncertain** — and that one sentence is the whole module.

**The interview question this answers:** "a test is 99% accurate for a 1-in-1000 disease; you test
positive; what is your probability?" Answer 9%, and *count people out loud* rather than reciting a
formula — 100 sick, 99 detected; 99,900 healthy, 999 false positives.

**The follow-up that gets you hired:** "so what would you change?" Specificity, not sensitivity —
because the negative class is 1,000× larger, so its error rate is multiplied by 1,000 and the positive
class's is not.
</Accordion>
<Accordion title="If you're working" icon="briefcase">
**1. Check whether any model in your organisation is evaluated on a rebalanced set.** Ask "what is the
positive rate in the evaluation set, and what is it in production?" If they differ, the reported
precision is wrong and you can compute the correct one from sensitivity, specificity and the true
prevalence in thirty seconds.

**2. Replace "accuracy" with "precision at a fixed alert budget" in one dashboard.** "Of the 500 cases
we can review daily, how many are real?" is a number an operations team can act on. Accuracy on an
imbalanced problem is not.

**3. Before building any rare-event detector, compute the false-positive load first.** Prevalence times
volume gives true positives; false-positive rate times volume gives the alerts. If the ratio is worse
than about 10:1, the humans downstream will stop reading them — that is an empirical regularity worth
respecting, and it is cheaper to discover on a whiteboard.
</Accordion>

## Common mistakes

| Symptom | Cause | Fix |
|---|---|---|
| Model "99% accurate", useless in production | Accuracy reported on imbalanced data | Precision, recall and the confusion matrix at the production base rate |
| Validation precision far above production | Evaluated on a rebalanced set | Rebalance to train, never to evaluate; correct with the Bayes formula |
| Precision degrades with no code change | Prevalence drifted | Monitor the input positive rate, not just the prediction rate |
| Classifier scores are all 0.0 or 1.0 | Underflow from multiplying many small probabilities | Work in log space |
| One rare word flips a confident prediction | Zero probability vetoing the product | Laplace smoothing; tune `alpha` |
| An ensemble is far more confident than warranted | Assumed independence of correlated signals | Likelihood ratios multiply only for independent evidence |
| Expected-value decisions systematically wrong | Uncalibrated scores treated as probabilities | Reliability diagram, ECE, then Platt or isotonic calibration |
| Confidence intervals too narrow | Correlated observations treated as independent | `Var(X+Y) = Var(X)+Var(Y)+2Cov(X,Y)` — the covariance term is not optional |
