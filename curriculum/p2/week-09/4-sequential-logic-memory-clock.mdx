### The words, defined

- **Combinational** — a circuit whose output depends only on its current inputs. Everything in
  Modules 1–3.
- **Sequential** — a circuit whose output depends on its inputs *and* on what happened before. It
  has state.
- **Feedback** — wiring an output back to an input, so the circuit can influence itself.
- **Clock** — a signal that alternates 0, 1, 0, 1 forever at a fixed rate. One 0→1→0 round is a
  **cycle**. The moment it goes 0→1 is the **rising edge**.
- **Flip-flop** — a one-bit memory that copies its input to its output only at the clock edge, and
  holds that value for the rest of the cycle.
- **Register** — `n` flip-flops side by side, storing an `n`-bit value.
- **RAM** — many registers plus an **address**: wires that select which one you mean.

### Why remembering needs feedback and a clock

Take a NOT gate and connect its output to its own input. What happens? If the input is 0, the output
becomes 1, which makes the input 1, which makes the output 0, forever. It oscillates. Useless.

Now take *two* NOT gates in a loop. If the first input is 0, the first output is 1, which makes the
second output 0, which feeds back as 0 to the first input. Consistent. It sits there. Set it to 1
instead and it also sits there. **Two stable states — that is one bit of memory.** This is the
cross-coupled inverter pair, and it is the heart of every SRAM cell on your CPU.

The problem: you cannot *write* to it easily, and if you build big circuits out of loops like this,
signals arriving at slightly different times cause the loop to flip unpredictably. That is a **race
condition**, in hardware, literally.

The fix is the clock. Add a gate on the input path that only opens at the rising edge. Then:

- Between edges, the loop is sealed. It holds its value, and combinational logic downstream has the
  whole cycle to settle.
- At the edge, the new value goes in, all at once, everywhere on the chip.

This gives you a discrete notion of time. "State at cycle `t+1` is a function of state at cycle `t`."
That is the entire model of computation for a synchronous digital system, and it is why hardware
people draw waveforms instead of flowcharts.

### The building sequence

You will build these in order, each from the previous one:

1. **DFF** (D flip-flop) — given to you as a primitive. `out(t) = in(t−1)`. It outputs, this cycle,
   whatever it saw last cycle.
2. **Bit** — a DFF that only changes when you tell it to. Put a MUX in front: if `load` is 1 take
   the new input, if `load` is 0 take the DFF's own output. That feedback path is what makes it
   remember across cycles.
3. **Register** — 16 Bits, sharing one `load` line.
4. **RAM8** — 8 Registers. To write, use a `DMux8Way` to route `load` to exactly one register. To
   read, use a `Mux8Way16` to select one register's output.
5. **RAM64, RAM512, RAM4K, RAM16K** — each is 8 of the previous one, with 3 more address bits.

### The smallest working example

```python
# seq.py — a clocked bit, a register, and a tiny RAM. Python 3.13, no dependencies.

class DFF:
    """Primitive: outputs, this cycle, whatever it was given last cycle."""
    def __init__(self):
        self.state = 0      # what the world sees now
        self.next = 0       # what it will see after the next clock edge
    def set_input(self, v):  self.next = v & 1
    def tick(self):          self.state = self.next     # the clock edge

class Bit:
    """A DFF with a load line. load=0 -> hold, load=1 -> take in."""
    def __init__(self):      self.dff = DFF()
    def out(self):           return self.dff.state
    def set_input(self, in_, load):
        # This is a MUX: select between the fed-back old value and the new one.
        self.dff.set_input(in_ if load else self.dff.state)
    def tick(self):          self.dff.tick()

class Register:
    def __init__(self, width=16): self.bits = [Bit() for _ in range(width)]
    def out(self):                return sum(b.out() << i for i, b in enumerate(self.bits))
    def set_input(self, value, load):
        for i, b in enumerate(self.bits):
            b.set_input((value >> i) & 1, load)
    def tick(self):
        for b in self.bits: b.tick()

r = Register()
print("cycle 0, out =", r.out())          # 0
r.set_input(42, load=1); r.tick()
print("after loading 42, out =", r.out()) # 42
r.set_input(99, load=0); r.tick()
print("after 'loading' 99 with load=0 =", r.out())   # still 42
r.set_input(99, load=1); r.tick()
print("after loading 99, out =", r.out()) # 99
```

Output:

```
cycle 0, out = 0
after loading 42, out = 42
after 'loading' 99 with load=0 = 42
after loading 99, out = 99
```

### Line-by-line

- `DFF` has **two** fields, `state` and `next`. That split is the whole point: the outside world only
  ever reads `state`, and writes only land on `next`. `tick()` copies one to the other. That is a
  clock edge, modelled honestly.
- `Bit.set_input` contains the MUX: `in_ if load else self.dff.state`. When `load` is 0 the flip-flop
  is fed its own current output — the feedback loop — so it holds. This one line is why a register
  remembers.
- `Register` is 16 `Bit`s with a shared `load`. There is no extra idea here, just width.
- Every object has `tick()`, and you must call *all* of them before reading any of them, otherwise
  you have simulated a clock that reaches different parts of the chip at different times. That bug
  is called **clock skew** and it is real.

### The memory hierarchy, and why it exists

You could imagine one big flat memory. Nobody builds that, because fast memory is expensive and
dense memory is slow. So machines have layers, and a memory request falls through them until it
hits:

| Level | Typical size | Typical latency | Roughly, in "if L1 were 1 second" |
|---|---|---|---|
| Register | ~1 KB total | 0 cycles (it *is* the input) | instant |
| L1 cache | 32–192 KB per core | ~1 ns (3–5 cycles) | 1 second |
| L2 cache | 0.5–16 MB per core | ~3–5 ns (12–20 cycles) | 4 seconds |
| L3 / SLC | 8–128 MB shared | ~15–25 ns | 20 seconds |
| DRAM | 8–512 GB | ~80–100 ns | 1.5 minutes |
| NVMe SSD | 0.5–8 TB | ~50–150 µs | ~1.5 days |
| Network (same datacentre) | — | ~200–500 µs | ~4 days |
| Spinning disk seek | — | ~5–10 ms | ~4 months |

Copy that table into your notes. It is the most reusable thing in Week 9. The right-hand column is
the one that changes behaviour: once you feel that a DRAM miss is "a minute and a half" while an L1
hit is "a second", you stop writing code that misses.

### The one rule: cache lines

Memory does not move one byte at a time. It moves **cache lines** — 64 bytes on x86-64, 128 bytes on
Apple silicon. Touch one byte and you pay for the whole line. So:

- If you read bytes in order, the first read costs a full miss and the next 15 or 31 are nearly
  free. This is **spatial locality**.
- If you read every 4096th byte, every single read is a full miss, and you throw away 60 of the 64
  bytes you paid for.

That is the entire explanation for the benchmark in Layer 2, which measures a **66.7× slowdown**
from nothing but the order of two nested loops.

### Guided practice

Build a `PC` (program counter): a 16-bit register with three extra behaviours, checked in priority
order — reset beats load, load beats increment.

    def __init__(self): self.reg = Register(16)
    def out(self): return self.reg.out()
    def set_input(self, in_, load, inc, reset):
        cur = self.reg.out()
        if reset:   nxt = 0
        elif load:  nxt = ____              # TODO
        elif inc:   nxt = ____              # TODO
        else:       nxt = cur

Two things to notice. First, `& 0xFFFF` — the counter wraps at 65535, exactly as the hardware

priority logic is a chain of MUXes selecting the *value*, not a decision about whether to write.
In hardware you cannot "skip" a write; you write the old value back. That is the same insight as
`Bit`'s feedback path.

### Checkpoint

<AccordionGroup>
<Accordion title="1. Why does a single inverter with feedback oscillate but two do not?">
One inversion around the loop means the value must differ from itself — no consistent state exists,
so it flips forever. Two inversions mean the value must equal itself, which has two solutions (0 and
1); both are stable.
</Accordion>
<Accordion title="2. What does the clock actually buy you?">
A guaranteed quiet interval. Between edges nothing stored changes, so combinational logic has a full
cycle to settle before anything samples it. It converts a continuous, racy physical system into a
discrete state machine.
</Accordion>
<Accordion title="3. How many address bits does RAM16K need?">
14, because `2^14 = 16384`. Each level of the hierarchy in the lab adds 3 bits (a factor of 8):
RAM8 → 3, RAM64 → 6, RAM512 → 9, RAM4K → 12, RAM16K → 14 (the last stage is 4-way, not 8-way).
</Accordion>
<Accordion title="4. Which is bigger: the latency gap from L1 to DRAM, or from DRAM to NVMe?">
DRAM to NVMe, by far. L1 (~1 ns) to DRAM (~90 ns) is about 90×. DRAM to NVMe (~100 µs) is about
1,100×. The hierarchy's steps are not evenly spaced, and the storage step is the cliff.
</Accordion>
<Accordion title="5. You iterate a 4096x4096 float array column-first. What fraction of each fetched cache line do you use?">
On a 64-byte line holding 16 floats, you use 1 of 16 — about 6%. On Apple silicon's 128-byte lines
it is 1 of 32, about 3%. That waste is what the measured 66.7× slowdown is made of.
</Accordion>
</AccordionGroup>

### The real theory: timing, not logic

The logic of a register is trivial. The engineering is entirely in timing, and it is governed by
three parameters of the flip-flop:

- **`t_setup`** — the input must be stable for this long *before* the clock edge.
- **`t_hold`** — the input must remain stable for this long *after* the edge.
- **`t_cq`** (clock-to-Q) — the delay from the edge to the output actually changing.

For a path from one register through combinational logic to another register:

```
Setup constraint:  t_cq + t_logic_max + t_setup  <=  T_clock - t_skew
Hold  constraint:  t_cq + t_logic_min           >=  t_hold + t_skew
```

The first sets your maximum frequency and is what Modules 1–3 were really about. The second is
nastier: **it cannot be fixed by slowing the clock**. A hold violation means a signal raced through
short logic and arrived at the next flip-flop before the old value had been safely captured, and it
is fixed by *adding* delay (buffers) or fixing clock distribution. A design that fails hold is
broken at every frequency.

Then there is **metastability**. If an input changes exactly during the setup/hold window, the
flip-flop's internal loop can sit balanced between 0 and 1 for an unbounded time before resolving.
It is not a bug you can eliminate, only make improbable. The standard measure is MTBF:

```
MTBF  =  exp(t_resolve / tau)  /  (T_w  x  f_clock  x  f_data)
```

For a typical modern flip-flop with `tau ≈ 20 ps` and `T_w ≈ 20 ps`, a 1 GHz clock and a 10 MHz
asynchronous data rate, allowing one full cycle (1 ns) to resolve gives an MTBF on the order of
10¹³ seconds — hundreds of thousands of years. Allowing only 200 ps drops it to well under a second.
This is why every asynchronous input crosses a **two-flop synchroniser**, and it is why "just sample
it" is a bug report waiting to happen.

### The production API surface

In SystemVerilog, a register is an `always_ff` block. The template, with the two variants you will
actually write:

```systemverilog
// Synchronous reset (preferred for FPGA and most ASIC flows)
always_ff @(posedge clk) begin
  if (rst)        q <= '0;
  else if (load)  q <= d;
end

// A program counter: reset > load > increment, exactly the Hack PC
always_ff @(posedge clk) begin
  if      (reset) pc <= 16'd0;
  else if (load)  pc <= d;
  else if (inc)   pc <= pc + 16'd1;
end
```

Three rules that are not optional:

1. **`<=` (non-blocking) in `always_ff`, `=` (blocking) in `always_comb`.** Mixing them produces
   simulation/synthesis mismatch — code that works in the simulator and not in silicon.
2. **Every signal assigned in an `always_ff` gets a value on every path, or you have inferred a
   latch.** Latches are level-sensitive, not edge-sensitive, and they break static timing analysis.
   `verilator --lint-only -Wall` will tell you.
3. **One clock domain per module where possible.** Crossing domains requires an explicit
   synchroniser or an async FIFO, and it must be reviewed as a separate artefact.

Verify with **Verilator 5.030** (`verilator --binary --timing --assert`) or **Icarus Verilog 12.0**,
and lint clock-domain crossings with Yosys 0.47 plus a CDC pass before you believe anything.

### SRAM vs DRAM: why the hierarchy has the shape it has

| | SRAM (caches) | DRAM (main memory) |
|---|---|---|
| Cell | 6 transistors (cross-coupled pair + 2 access) | 1 transistor + 1 capacitor |
| Density | ~6× worse per bit | the reference |
| Latency | ~1–20 ns | ~80–100 ns (including row activation) |
| Refresh | none — static | every row every ~32–64 ms, or the charge leaks away |
| Cost per bit | roughly 20–100× DRAM | the reference |
| Where | on the CPU die | separate chips on a bus |

The 6T-vs-1T cell count is the entire reason your L1 is kilobytes and your DRAM is gigabytes. And
"refresh" is not free: a DRAM device spends a low single-digit percentage of its time refreshing and
unavailable, which is one of several reasons DRAM latency has barely improved in twenty years while
bandwidth has grown enormously. **Latency is the thing that did not scale.** That asymmetry —
plentiful bandwidth, stubborn latency — is why prefetching, larger cache lines, and batching
dominate modern performance work.

### Measured: the cost of getting memory order wrong

Same arithmetic, same data, same compiler, same machine. Only the loop order differs.

```c
// loc.c — sum a NxN float matrix row-major vs column-major.
// clang -O2 -ffast-math -o loc loc.c && ./loc 4096 5
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
static double now(void){ struct timespec t; clock_gettime(CLOCK_MONOTONIC,&t);
  return t.tv_sec + t.tv_nsec/1e9; }
int main(int argc, char **argv){
  int N = argc>1 ? atoi(argv[1]) : 2048;
  int REP = argc>2 ? atoi(argv[2]) : 5;
  size_t n = (size_t)N*N;
  float *a = aligned_alloc(64, n*sizeof(float));
  for (size_t i=0;i<n;i++) a[i]=1.0f;
  double best_r=1e9, best_c=1e9; volatile float sink=0;
  for (int r=0;r<REP;r++){
    double t0=now(); float s=0;
    for (int i=0;i<N;i++) for (int j=0;j<N;j++) s += a[(size_t)i*N+j];   /* stride 1 */
    double t1=now(); sink=s; if (t1-t0<best_r) best_r=t1-t0;
    t0=now(); float s2=0;
    for (int j=0;j<N;j++) for (int i=0;i<N;i++) s2 += a[(size_t)i*N+j];  /* stride N */
    t1=now(); sink=s2; if (t1-t0<best_c) best_c=t1-t0;
  }
  printf("N=%d  %.1f MiB  row=%.4fs  col=%.4fs  slowdown=%.2fx  "
         "ns/elem row=%.2f col=%.2f\n", N, (double)n*4/1048576.0,
         best_r, best_c, best_c/best_r, best_r/n*1e9, best_c/n*1e9);
  free(a); (void)sink; return 0;
}
```

Measured on an Apple M3 Pro, macOS 26.2, Apple clang 17 (`-O2 -ffast-math`), best of 5 runs:

| N | Working set | Row-major | Column-major | Slowdown | ns/element (row → col) |
|---|---|---|---|---|---|
| 256 | 0.2 MiB | 0.03 ms | 0.28 ms | **9.3×** | 0.05 → 0.43 |
| 512 | 1.0 MiB | 0.13 ms | 1.65 ms | **12.7×** | 0.05 → 0.63 |
| 1024 | 4.0 MiB | 0.05 ms | 1.40 ms | **28.0×** | 0.05 → 1.34 |
| 2048 | 16.0 MiB | 0.34 ms | 12.8 ms | **38.2×** | 0.08 → 3.06 |
| 4096 | 64.0 MiB | 1.04 ms | 69.6 ms | **66.7×** | 0.06 → 4.15 |

Read the shape, not just the peak. At 0.2 MiB the whole matrix fits in L2, so the penalty is only
9.3×. As the working set grows past the caches, the column-major version degenerates to one DRAM
access per element and the gap widens monotonically to 66.7×. Across repeated runs on a loaded
machine the 4096 figure ranged from 56× to 81×; the *shape* is stable, the exact peak is not.

One more measurement that changes how you read the first one. Compiled **without** `-ffast-math`,
both loops took the same time. Strict IEEE semantics forbid reordering a floating-point sum, so the
row-major loop cannot be vectorised and becomes a serial chain of dependent `fadd` instructions —
about 1.17 ns per element, slow enough that memory is no longer the bottleneck. The 66.7× gap only
appears once the fast path is actually fast. **A memory optimisation is invisible while something
else is the bottleneck**, which is the most common reason people conclude "cache locality doesn't
matter".

### Trade-offs

| Decision | Choose this when… | Choose the other when… | The number |
|---|---|---|---|
| **Row-major (C) traversal** vs **column-major (Fortran) traversal** | Your language stores rows contiguously (C, Python/NumPy default, PyTorch) | Your library is column-major (Fortran, R, Julia, BLAS internals) | Getting it backwards costs 9×–67× depending on working-set size |
| **Array of structs** vs **struct of arrays** | You touch most fields of a record together | You sweep one field across many records | SoA turns a 1-of-16-fields-used line into 16-of-16; up to a 16× reduction in bytes fetched |
| **Synchronous reset** vs **asynchronous reset** | FPGA; you want clean timing analysis and no reset-tree timing closure problem | You must guarantee a known state before the clock is running | Async reset needs a *synchronised de-assert* or you get a metastable release across the whole chip |
| **Bigger cache line** vs **smaller** | Sequential access dominates | Random pointer-chasing dominates | 128 B lines (Apple silicon) double the useful prefetch for sequential code and double the waste for random access |

### What breaks in the real world

A team migrated an image-preprocessing service from NumPy to a hand-written C++ inner loop expecting
a speedup. It got 4× *slower*. The NumPy version had been calling into a routine that iterated
rows; the C++ rewrite iterated columns because the author transcribed the loop bounds from a maths
paper where the sum index was written outermost. The arithmetic was identical, the tests all passed
— the output was bit-for-bit the same — and the profiler showed all the time inside the loop with no
obvious culprit. The fix was swapping two lines. The diagnosis came from `perf stat` showing
`LLC-load-misses` about 30× higher than the NumPy version.

The reusable lesson: **when the same computation is unexpectedly slow, measure cache misses before
you read the code.** On Linux, `perf stat -e cache-references,cache-misses,LLC-load-misses`. On
macOS, Instruments' *Counters* template. The ratio tells you in ten seconds what an hour of reading
might not.

### Design checkpoint

<Accordion title="You must store 10 million records and scan one 4-byte field of each, once per request. Array-of-structs with 200-byte records, or struct-of-arrays?">

Struct of arrays, and the arithmetic is decisive.

**AoS:** each record is 200 bytes. Scanning one 4-byte field touches one cache line per record (the
records are bigger than a line, so no sharing). 10M records × 64 B = **640 MB of memory traffic**
for 40 MB of useful data — you use 6% of what you fetch. At ~40 GB/s of achievable streaming
bandwidth, that is about 16 ms per scan, and it will not fit in any cache.

**SoA:** the field lives in its own contiguous 40 MB array. 10M × 4 B = **40 MB of traffic**, every
byte of it useful, fully prefetchable, and it fits inside a large L3/SLC on a modern server part.
About 1 ms at the same bandwidth — a **16× reduction in bytes moved**.

The counter-argument, which you must state: if a *different* request path touches ten fields of one
record, SoA now costs ten separate streams and ten times the TLB pressure. Real systems answer this
with hybrid layouts — column groups, or "AoSoA" tiles of 8–16 records — which is exactly what
columnar formats like Apache Parquet and Arrow do. You will meet them again in Week 15.

### Under the hood: what a cache actually does with an address

A physical address is split into three fields:

```
| tag | index | offset |
```

- **offset** — which byte within the line. 6 bits for a 64-byte line, 7 for 128.
- **index** — which *set* of the cache to look in. For a 32 KB, 8-way, 64-byte-line L1:
  32768 / 64 / 8 = 64 sets, so 6 index bits.
- **tag** — everything above, compared against the tags of the 8 lines in that set.

Three consequences that show up in real profiles:

1. **Conflict misses.** Addresses that share index bits map to the same set. With 8-way
   associativity, nine hot arrays whose base addresses differ by an exact multiple of
   `sets × line_size` (4 KB here) will evict each other endlessly, even though the cache is 99%
   empty. This is why matrix sizes that are exact powers of two are often *slower* than sizes
   padded by one row — the classic fix is to allocate `N × (N + 1)` and stride by `N + 1`.
2. **The TLB is a second, independent cache.** It maps virtual page numbers to physical ones, and it
   is small — order 64–3000 entries. A column-major sweep of a 64 MiB matrix with 16 KB pages
   touches 4,096 pages per column pass, blowing any L1 TLB. Part of the measured 66.7× is TLB
   misses, not just data misses. Huge pages (2 MB) reduce entries needed by 128×.
3. **Prefetchers only help patterns they recognise.** Hardware stride prefetchers detect constant
   strides, usually up to a page boundary. A stride of `N × 4` bytes that crosses pages every access
   defeats them. This is why the column-major penalty grows with `N`: at small `N` the stride stays
   within a page and prefetch still works.

### At scale: the numbers that govern the rest of the course

The single most useful derived quantity is **arithmetic intensity** — FLOPs performed per byte moved
from memory. Compare it against the machine's ratio of peak FLOP/s to peak memory bandwidth
(the "machine balance"), and you know instantly whether a kernel is compute-bound or memory-bound.
This is the Roofline model.

Peak compute and bandwidth below are **vendor specifications** (reference figures — the authors
had no A100 or H100); the balance column is **derived** by dividing one by the other. See
[About the numbers](/start/about-the-numbers).

| Machine | Peak compute | Peak memory BW | Balance (FLOP/byte) |
|---|---|---|---|
| Apple M3 Pro (CPU, FP32 vector) | ~1–2 TFLOP/s | ~150 GB/s | ~10 |
| NVIDIA A100 80 GB (FP16 tensor) | ~312 TFLOP/s | ~2039 GB/s | ~153 |
| NVIDIA H100 SXM (FP16 tensor) | ~990 TFLOP/s | ~3350 GB/s | ~295 |

Read the last column as: on an H100, a kernel must do about **295 floating-point operations per byte
it reads** to keep the tensor cores busy. Almost nothing does. A dense matrix multiply of size `n`
does `2n³` FLOPs on `3n²` elements, so intensity grows with `n` — which is why big matmuls are the
only thing that reaches peak, and why every Transformer optimisation you will meet in Phase 4
(FlashAttention, KV-cache layout, fused kernels, quantisation) is fundamentally about moving fewer
bytes, not doing fewer FLOPs. FlashAttention's entire contribution is tiling attention so the
intermediate `n × n` matrix never leaves SRAM.

You now have the vocabulary for that argument, and you got it from a nested loop.

### DRAM: why latency stopped improving

DRAM access is not one operation. It is:

1. **ACTIVATE** a row — the row's ~8192 bits are read destructively into the sense amplifiers.
   `tRCD`, typically ~13–18 ns.
2. **READ/WRITE** a column from the open row. `CL`, typically ~13–18 ns.
3. **PRECHARGE** to close the row before opening another. `tRP`, ~13–18 ns.

A **row hit** (next access is in the already-open row) costs only step 2. A **row miss** costs all
three, roughly `tRP + tRCD + CL` ≈ 45 ns of device latency, before controller queueing, bus transfer
and on-chip interconnect — which is how you get to 80–100 ns end to end.

Those three timings have barely moved since DDR2 in 2004. What has grown is *bandwidth*: wider
buses, more channels, higher transfer rates, more banks to overlap. DDR5-6400 moves roughly 51 GB/s
per channel against DDR2-800's 6.4 GB/s — about 8× — while `CL` in nanoseconds is essentially
unchanged. **This is the central fact of modern performance engineering:** you can move a lot of
bytes, but you must ask for them early. Every technique — prefetching, out-of-order execution,
hyperthreading, GPU warp scheduling, async I/O — exists to find work to do during those 80 ns.

### Production failure modes

| Failure | Signature | Detection |
|---|---|---|
| **False sharing** | Two threads write different variables; throughput drops 5–10× as core count rises | The variables share a cache line. `perf c2c` on Linux. Fix by padding to 64/128 B or `alignas(64)` |
| **Cache-set thrashing on power-of-two strides** | A matrix kernel is slower at N=1024 than at N=1025 | Conflict misses. Pad the leading dimension: allocate `N×(N+8)` |
| **TLB thrashing** | High `dTLB-load-misses`, poor scaling with data size, unaffected by cache-friendly rewrites | Enable huge pages (`madvise(MADV_HUGEPAGE)`), or restructure to touch fewer pages per pass |
| **Metastability at a CDC boundary** | Rare, unreproducible corruption; often temperature-dependent | Two-flop synchroniser on every async input; CDC lint as a gate in CI |
| **Inferred latch in RTL** | Simulation passes, hardware behaves differently; timing analysis reports unconstrained paths | `verilator --lint-only -Wall`; assign every output on every path in `always_comb` |
| **Hold violation** | Design fails at *all* frequencies, including slow ones | Static timing analysis hold check; fix with buffer insertion, never with a slower clock |

### Frontier and further pointers

- **Wulf & McKee (1995), "Hitting the Memory Wall: Implications of the Obvious."** Takeaway: if
  processor speed improves faster than memory latency, average access time is eventually dominated
  entirely by memory, no matter how good the cache hit rate — the paper that named the problem this
  module is about.
- **Williams, Waterman & Patterson (2009), "Roofline: An Insightful Visual Performance Model for
  Multicore Architectures," *CACM* 52(4).** Takeaway: plotting attainable FLOP/s against arithmetic
  intensity gives a single picture that tells you whether to optimise compute or memory traffic —
  the model behind the machine-balance table above.
- **Drepper (2007), "What Every Programmer Should Know About Memory."** Takeaway: a 114-page,
  measurement-driven tour of cache associativity, prefetching, NUMA and TLBs that remains the best
  single document on the subject; the numbers are dated, the mechanisms are not.
- **Dao et al. (2022), "FlashAttention: Fast and Memory-Efficient Exact Attention with
  IO-Awareness."** Takeaway: attention was memory-bound, not compute-bound, and tiling it so the
  intermediate matrix stays in SRAM gives a 2–4× speedup with identical mathematics — this module's
  lesson, applied to the most important kernel in modern AI. You will implement the idea in Phase 4.

## The whole idea on one whiteboard

Combinational logic has no memory because information only flows forwards. Feed the output back
into the input and you get memory — but you also get a race: the output changes, which changes the
input, which changes the output, forever.

The **clock** resolves the race by adding a referee. A clocked memory element accepts a new value
only at one instant per cycle (the clock edge) and holds it steady for the rest of the cycle. That
gives combinational logic a whole cycle of quiet to settle in.

So: **combinational logic computes; clocked elements remember; the clock decides when "now" ends.**
Everything above — registers, RAM, the program counter, the whole CPU — is those three sentences,
repeated at scale.

## Common mistakes

| Symptom | Cause | Fix |
|---|---|---|
| Register "forgets" when `load=0` | No feedback path — the DFF was fed 0 or the raw input instead of its own output | `Bit` is a MUX selecting between `in` and the DFF's current output |
| Simulation gives different results depending on iteration order | Called `tick()` on some components before reading others | Two-phase update: compute all next-states, then commit all of them |
| RAM8 writes to every register | Used a plain AND on `load` instead of routing it through `DMux8Way` | Exactly one register's `load` may be high per write |
| PC increments when it should load | Priority order implemented wrong | Reset beats load beats increment. Test all eight combinations |
| Cache benchmark shows no difference | Compiled without optimisation, or the fast loop is FP-dependency-bound | Use `-O2 -ffast-math`; verify the row-major loop vectorised before believing a null result |
| Threaded code stops scaling past 4 cores | False sharing on adjacent counters | Pad each per-thread counter to 64 (or 128) bytes |
| Matrix kernel slower at N=1024 than N=1025 | Cache-set conflict misses on a power-of-two stride | Pad the leading dimension |

1. Why does memory require feedback? *(Without a path from output back to input the circuit has no way to depend on its own past — output is a pure function of current inputs.)*
