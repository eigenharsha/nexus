## Outcome

<Note>
By Sunday you will have a pipeline that pulls from a REST API and a scraped page, normalizes nested
JSON into relational tables, deduplicates and merges incrementally into DuckDB, survives a schema
change and a mid-run crash, and runs on a schedule with data-quality assertions and a run report.
It will be safe to re-run. That last property is the one that makes it a pipeline rather than a
script.
</Note>

## Why this week is the one that pays for the course

<Info>
**For Meera specifically.** Weeks 15 and 16 are the most directly job-applicable pair in Phase 2.
The pipeline you build this week is a thing you can point at on Monday morning. Most companies have
at least one "someone runs a notebook and pastes the output into a spreadsheet" process, and
replacing one of those with an automated, tested, re-runnable pipeline is a visible, attributable
win that does not require anyone's permission to start.
</Info>

The skills here are not exotic. They are: pull data reliably from a source you do not control,
land it somewhere queryable, make the process idempotent, and notice when it breaks. Almost nobody
does all four, which is why data teams spend most of their time on incidents rather than analysis.

## The measurement environment

Every number in weeks 15 and 16 comes from the same dataset and the same machine, so the figures
across modules are directly comparable.

| | |
| --- | --- |
| Machine | Apple M3 Pro, 18 GB unified memory, macOS 15 |
| Dataset | 10,000,000 synthetic card transactions: 8 columns, 2,000 merchants, 8 categories, 4 regions |
| On disk | 186 MB Parquet (snappy), 663 MB CSV, 142 MB Parquet (zstd) |
| Timing | best-of-3, each engine in its own process |
| Memory | `resource.getrusage(RUSAGE_SELF).ru_maxrss` — whole-process peak, not Python-heap |

<Warning>
Measuring each engine in its own process matters more than it sounds. Peak memory measured with
`tracemalloc` only counts Python-level allocations, so it reports near zero for DuckDB and Polars —
both of which do their work in native code. `ru_maxrss` in a fresh process is the honest number, and
it is the one that determines whether your job fits in its container.
</Warning>

## The headline number

The same group-by aggregation over 10 million rows:

| Engine | Time | Peak RSS |
| --- | --- | --- |
| DuckDB 1.1.3 | **0.117 s** | **96 MB** |
| Polars 1.17.1 (lazy) | 0.299 s | 1,023 MB |
| Polars 1.17.1 (eager) | 0.637 s | 934 MB |
| pandas 2.2.3 | 1.510 s | 878 MB |

DuckDB is **12.9× faster than pandas and uses 9.1× less memory**, on a query neither engine was
tuned for. Module 5 has the full table across five query shapes and explains why.

## Exit checks

1. Explain ETL versus ELT and say which one the pipeline you built is, and why.
2. Quote, from your own measurement, the Parquet-versus-CSV ratio for a single-column aggregate.
3. Kill your pipeline mid-run and restart it. It must produce the identical final table.
4. Add a field, change a field's type, and remove a field upstream. Say what `dlt` did in each case.
5. State the row count at which you would stop using pandas, with your own numbers behind it.
