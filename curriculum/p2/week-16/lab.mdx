## The ticket

> **DATA-204 — Every new dataset costs us two days before anyone can say anything about it**
>
> *Reported by: Analytics, priority P2*
>
> We onboard a new data source roughly monthly. Each time, an analyst spends one to two days in a
> notebook working out what is in it: what the columns are, how much is missing, what the
> distributions look like, whether anything is obviously broken. The notebooks are inconsistent —
> different people check different things — they are not kept, and the same questions get asked
> again three months later.
>
> Twice this year we have shipped a model that turned out to be reading a column populated after the
> outcome. Both times somebody would have caught it in the first hour with the right check.
>
> Build us a tool. Point it at a file, get a report. It must be the same report every time, it must
> run in CI so we can re-run it when data changes, and **it must warn us about leakage**.

<Info>
**Time box.** `basic` 4–5 hours. `standard` 12–16 hours. `hard` a further 8–10 hours.
</Info>

<Tabs>
  <Tab title="basic">
    **A guided notebook producing eight required plots on a provided dataset.**

    The dataset is `labs/p2/week-16/data/transactions.parquet` — 500,000 rows, 12 columns, with
    deliberate problems: one constant column, one identifier, two columns over 40% missing, a
    right-skewed amount, a class-imbalanced target, and **one leaky feature**.

    | # | Plot | What it must show |
    | --- | --- | --- |
    | 1 | Missingness bar chart | percentage missing per column, sorted descending |
    | 2 | Numeric distributions | a histogram grid, with log scale where skew exceeds 3 |
    | 3 | ECDF of the amount column | with p50 and p95 annotated |
    | 4 | Categorical frequencies | top 10 levels per categorical, with cardinality in the title |
    | 5 | Target distribution | with the class balance stated as a percentage |
    | 6 | Feature vs target | grouped distributions for the five most associated features |
    | 7 | Correlation heatmap | diverging colormap **centred on zero** |
    | 8 | Single-feature AUC | a horizontal bar chart, with a line marking the 0.95 leakage threshold |

    **Acceptance criteria**

    - `pytest labs/p2/week-16/tests/test_basic.py` green.
    - **Every axis labelled**, every plot with a title stating the sample size.
    - Plot 7 uses `TwoSlopeNorm(vcenter=0)` — a diverging colormap that is not centred silently
      makes "white means zero correlation" false.
    - Plot 8 identifies the leaky column. **Name it in a markdown cell and say how you know.**
    - Plot 2 uses log-spaced bins where it uses a log axis, not linear bins on a log axis.

    <Info>~60% of the code is written for you. TODOs are marked. Answers provided.</Info>

    <Warning>
    Plot 8 is the point of the whole track. A depth-3 decision tree on one feature reaching 0.95+ AUC
    means that feature nearly determines the target — which, for a hard problem, means it contains
    the answer rather than predicting it. When you find it, ask **when that column is populated
    relative to the outcome**. That question is the entire lesson.
    </Warning>
  </Tab>

  <Tab title="standard">
    **A CLI tool: point it at any CSV or Parquet and get an HTML report.**

    ```
    eda report data/txns.parquet --target is_refund --out report.html
    eda report data/txns.csv --target churned --sample 100000
    eda compare data/jan.parquet data/feb.parquet --out drift.html
    ```

    ### What the report must contain

    | Section | Content |
    | --- | --- |
    | **Overview** | rows, columns, memory (`deep=True`), dtypes, duplicate row count |
    | **Schema** | per column: dtype, missing %, cardinality, sample values, and a flag for identifier / constant / high-cardinality |
    | **Missingness** | per column, plus **whether missingness correlates with the target** — that is the MNAR signal |
    | **Distributions** | histogram + ECDF per numeric column; frequency table per categorical |
    | **Outliers** | IQR and modified z-score counts per numeric column, **not** plain z-score |
    | **Correlations** | Pearson **and** mutual information, side by side, with the disagreements highlighted |
    | **Target relationships** | each feature against the target, ranked by mutual information |
    | **Leakage warnings** | single-feature AUC; near-perfect predictors; duplicate rows; candidate grouping keys |
    | **Written summary** | a generated prose paragraph naming the three things a human should look at first |

    ### Acceptance criteria

    - `make verify` green: `pytest`, `ruff check`, `mypy --strict`.
    - **Tested on three genuinely different datasets** — a wide one, a tall one, and one that is
      mostly categorical. Different shapes break different assumptions, which is the point.
    - **A single self-contained HTML file** with embedded figures. It must survive being emailed.
    - `--target` is optional; without it, the target sections are skipped rather than crashing.
    - **The correlation section must flag disagreements**: any pair where Pearson is below 0.1 and
      mutual information is high. That is a non-linear relationship your correlation matrix missed,
      and it is the finding module 4 measured at r = −0.02 with MI = 0.98.
    - `eda compare` produces a drift report gated on **both** significance and effect size.
    - The written summary is generated from the findings, not hard-coded, and it names columns.

    <Info>Spec and tests only. You write the implementation.</Info>

    <Warning>
    **The drift comparison must not use a p-value threshold alone.** Module 4 measured that at a
    million rows per side, a KS test flags a shift of 0.01 standard deviations **100% of the time**.
    A report that flags everything gets ignored, and then it is not there when something real
    happens. Gate on the KS statistic (or Wasserstein distance) as well, and fix the sample size so
    sensitivity does not drift as the data grows.
    </Warning>
  </Tab>

  <Tab title="hard">
    **A 10-million-row file, a fixed memory budget, drift comparison with statistical tests, and a
    sub-60-second runtime.**

    ### The constraints

    | Constraint | Why the `standard` solution fails |
    | --- | --- |
    | **10,000,000 rows** | `pd.read_parquet` on a wide 10M-row file is several gigabytes; module 2 measured 404 MB for 5M rows and 5 columns |
    | **Peak RSS under 2 GB**, asserted | the memory budget is the actual constraint, not the runtime |
    | **Under 60 seconds** end to end | the correlation matrix alone is 0.46 s at 21 columns; mutual information over 40 columns is not |
    | **Drift between two 10M-row files** | you cannot hold both |
    | **Same output as the `standard` tool** on a small file | correctness must not depend on the size path |

    ### What this forces you to change

    1. **Push the aggregations into DuckDB.** Week 15 module 5 measured DuckDB at 12.9× faster than
       pandas with 9.1× less memory on a group-by over 10 million rows. Counts, nulls, quantiles,
       distinct counts and histograms are all single SQL queries that never materialise a DataFrame.
    2. **Compute histograms in SQL**, not by loading the column:
       ```sql
       SELECT width_bucket(amount, 0, 1000, 50) AS bin, count(*) FROM 'f.parquet' GROUP BY 1
       ```
    3. **Sample for the expensive parts.** Mutual information and single-feature AUC are `O(n log n)`
       or worse per feature. **Sample 100,000 rows for those**, use the full data for the exact
       aggregates, and **state in the report which figures are sampled.** An unlabelled sampled
       statistic is a lie by omission.
    4. **Approximate quantiles.** `approx_quantile` in DuckDB (a t-digest) instead of an exact sort.
       Report the approximation.
    5. **Stream the drift comparison.** Compute a summary per file — histograms on a shared binning,
       plus quantiles — and compare the summaries. **Never hold both files.**

    ### Acceptance criteria

    - A test asserting **peak RSS under 2 GB**, measured with `resource.getrusage(RUSAGE_SELF).ru_maxrss`
      in a subprocess. Not `tracemalloc`, which does not see DuckDB's native allocations.
    - A test asserting **runtime under 60 seconds** on the 10M-row fixture.
    - **A test asserting the small-file output is identical** between the pandas path and the DuckDB
      path, for every exact statistic. Approximate statistics get a documented tolerance.
    - The drift comparison works on two 10M-row files without loading either.
    - **Every sampled or approximated figure is labelled as such in the report.**

    <Warning>
    The trap in this track is producing a *different* report on the fast path. If your DuckDB
    implementation computes the median differently from your pandas one, you have two tools, and the
    one you trust depends on which file you pointed it at. **The identical-output test is the
    hardest requirement here and it is the one that matters** — and where they legitimately cannot
    be identical (approximate quantiles), the report must say so rather than the tolerance being
    hidden in a test.
    </Warning>
  </Tab>
</Tabs>

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
A published tool — `pip install`-able or a documented CLI — plus example reports for three different
datasets, plus a `FINDINGS.md` for one of them written as a memo to a stakeholder.
</Card>

The tool is the engineering. **`FINDINGS.md` is what demonstrates judgement**, and it is what a
hiring manager reads. Two pages, for someone who will not open your code:

<Steps>
  <Step title="Open with the recommendation">
    "This dataset can support a churn model, with three caveats." Not "the dataset has 47 columns".
    The reader is deciding something; lead with the decision.
  </Step>
  <Step title="Then the three things that matter">
    Not everything you found. The three findings that change what someone does. Everything else is
    an appendix.
  </Step>
  <Step title="Then the risks, explicitly including leakage">
    "`days_to_followup` is populated after discharge and must not be used." Naming a specific column
    and a specific reason is worth more than a paragraph about data quality in general.
  </Step>
  <Step title="Close with what the data cannot tell them">
    The most valuable paragraph in any analysis memo, and the one people leave out because it feels
    like admitting failure. It is the opposite: it is the part only someone who understood the data
    could write.
  </Step>
</Steps>

<Tip>
`make datasets` running the tool over three differently-shaped files is the target that finds real
bugs. A tool written against one dataset encodes assumptions about it — every column is numeric,
there is always a target, cardinality is always low. **A wide frame, a tall frame and a
mostly-categorical frame break different assumptions**, and a tool that survives all three is
actually reusable.
</Tip>

## Start here — your first 30 minutes

The requirements above are the *finished* picture. Do not try to hold all of it at once. Do these in
order; each step ends somewhere you can stop and still be making progress.

<Steps>
<Step title="Run the starter and expect RED (5 min)">
```bash
cd labs/p2/week-16
make verify TRACK=basic
```
A red result is success here — it means the harness runs and the tests can see your code. If you get
something that is *not* a test failure (a missing command, an import error), fix that first; it is an
environment problem, not a lab problem.
</Step>

<Step title="Read one test before writing any code (5 min)">
The tests are the real specification — everything written above is prose describing them. Where the
prose and a test disagree, **the test wins**. Open the first one and read it properly.
</Step>

<Step title="Make ONE test pass (15 min)">
Implement the smallest thing the first failing test needs. Run `make verify` again. One more test
passing is the whole goal of your first half hour.

That is the loop for the entire lab: one test, one function, run, repeat. Do not write five functions
and then run for the first time — when it fails you will not know which one broke it.
</Step>

<Step title="Finish the basic track">
Work the `TODO`s in the order they appear. They are in dependency order, not alphabetical.
</Step>

<Step title="Only then read the standard requirements">
With `basic` green you have something that works. `standard` extends it; it does not replace it.
</Step>

<Step title="Ship it">
Push to a public repo with the README. That artifact is what you link from a CV — it outlasts the grade.
</Step>
</Steps>

<Tip>
**Are you on track?** After 30 minutes you should have: a red run, one test read properly, and one
test passing. If you have read for 30 minutes and run nothing, you are reading too much — go run the

## Rubric

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Correctness | fails tests | produces a report | correct on three different dataset shapes | leakage detection finds the planted leak and reports *why* |
| Code quality | works | readable | `mypy --strict` clean, plotting separated from analysis | reusable as a library; every figure has labelled axes and a stated n |
| Performance | untested | timed | handles 10M rows | under 2 GB and 60 s, with an identical-output test against the small path |
| Explanation | none | a README | report is readable by a non-analyst | `FINDINGS.md` names specific risks and states what the data cannot answer |

**What a 3 in Explanation actually requires.** Not "the data has missing values". Something like:
*"`credit_score` is 43% missing, and missingness correlates with the target at r = 0.31 — this is
MNAR, so mean imputation will bias the model. I recommend keeping the missingness indicator, which
by single-feature AUC is more predictive (0.68) than any imputed value would be. But check when that
field is populated: if it is only requested for applicants who have already been flagged, the
indicator is leakage rather than signal, and that is a question for the credit team, not one I can
answer from this file."*

## Common ways submissions lose points

| What happens | Why it costs marks | What to do instead |
| --- | --- | --- |
| Drift gated on p-value alone | Flags everything at large n — measured 100% on a 0.01 SD shift | Gate on the KS statistic or Wasserstein distance too; fix the sample size |
| Only Pearson correlation reported | Blind to non-linear relationships — measured r = −0.02 where MI = 0.98 | Report both; flag the disagreements |
| Diverging heatmap not centred | "White means zero" is silently false | `TwoSlopeNorm(vcenter=0)` |
| Plain z-score for outliers | Masking: the outlier inflates the std it is judged against | IQR, or modified z-score with median and MAD |
| Tool tested on one dataset | Encodes assumptions about that dataset's shape | Three shapes: wide, tall, mostly categorical |
| No leakage section | The thing the ticket explicitly asked for | Single-feature AUC, duplicate rows, candidate grouping keys |
| Sampled statistics not labelled | The reader believes an exact figure | Mark every sampled or approximate number in the report |
| Memory measured with `tracemalloc` | Does not see DuckDB's or NumPy's native allocations | `ru_maxrss` in a subprocess |
| Fast path gives different numbers | Two tools; trust depends on which file you used | Identical-output test, with documented tolerances for approximations |
| Unlabelled axes in generated plots | The report makes claims the reader cannot check | Assert labels in a test — figure metadata is cheap to test |
| `FINDINGS.md` lists everything found | The reader wanted a decision, not an inventory | Three findings, the risks, and what the data cannot answer |
