    ## The idea in one paragraph

    A **DataFrame** is a table: named columns, each a NumPy array of one type, sharing a row index.
    That is genuinely all it is, and holding that picture explains almost everything pandas does —
    why a column of strings is enormous (it is an array of *pointers* to Python strings), why
    `df["a"] * 2` is fast (it is NumPy), why `df.apply(...)` is slow (it is a Python loop wearing a
    method call), and why joining two tables can silently multiply your rows. Pandas is a
    convenience layer over NumPy plus an index, and the places where it surprises you are the places
    where that layering leaks.

    ### The analogy

    A spreadsheet, with two differences that matter.

    - **Every column has one type.** A spreadsheet column can hold a number in one cell and text in
      the next. A DataFrame column cannot — or rather, it can, by falling back to `object` dtype,
      which means "a column of pointers to arbitrary Python objects" and costs you the speed and
      most of the memory efficiency. **When pandas says a column is `object`, it is telling you it
      gave up.**
    - **There is a row index**, which is a label for each row, separate from its position. This is
      the single most confusing thing in pandas for newcomers, and it is why there are two selection
      methods: `loc` selects by *label*, `iloc` by *position*.

    ### Every term, defined

    - **`Series`** — one column: a NumPy array plus an index.
    - **`DataFrame`** — a dict of Series sharing one index.
    - **Index** — the row labels. Can be integers, strings, dates, or several columns at once
      (a `MultiIndex`).
    - **`loc`** — selection by **label**. `df.loc["2026-01-01"]`. Inclusive of the endpoint in slices.
    - **`iloc`** — selection by **integer position**. `df.iloc[0]`. Exclusive of the endpoint, like a
      Python list.
    - **dtype** — a column's type: `int64`, `float64`, `bool`, `datetime64[ns]`, `category`, or
      `object`.
    - **`object` dtype** — a column of pointers to Python objects, usually strings. Slow and large.
    - **`category` dtype** — a column stored as small integer codes plus a lookup table. **The single
      biggest memory win available.**
    - **`groupby`** — split rows into groups, apply a function per group, combine the results.
    - **`merge` / `join`** — combine two DataFrames on a key. SQL's `JOIN`.
    - **Fan-out** — a join where a key appears more than once on one side, so the result has more
      rows than you expected. **The bug this module exists to prevent.**
    - **Vectorized** — an operation applied to a whole column at once, in C.
    - **Method chaining** — writing a pipeline as `df.pipe(a).pipe(b)` rather than a sequence of
      reassignments.

    ### The smallest working example

    ```python
    # basics.py — CPython 3.12, pandas 2.2.3
    import pandas as pd

    df = pd.DataFrame({
        "date": pd.to_datetime(["2026-01-01", "2026-01-01", "2026-01-02", "2026-01-02"]),
        "region": ["APAC", "EMEA", "APAC", "EMEA"],
        "amount": [120.0, 80.5, 200.0, 45.25],
        "refunded": [False, False, True, False],
    })

    print(df.dtypes)
    # date        datetime64[ns]
    # region              object     <- a column of POINTERS to Python strings
    # amount             float64
    # refunded              bool

    print(df.shape)                      # (4, 4)
    print(df["amount"].sum())            # 445.75
    print(df.loc[df.region == "APAC", "amount"].sum())   # 320.0

    print(df.groupby("region")["amount"].agg(["sum", "mean", "count"]))
    #         sum    mean  count
    # region
    # APAC  320.00  160.00      2
    # EMEA  125.75   62.875     2
    ```

    ### Line-by-line walkthrough

    - `pd.to_datetime([...])` — parse once, at load. Dates left as strings are `object` dtype: large,
      slow, and unable to do date arithmetic. **Parsing dates at ingestion is the highest-value
      one-liner in pandas.**
    - `df.dtypes` — **read this first, every time you load data.** It tells you what pandas inferred,
      and the surprises live here: a numeric column that came through as `object` because one row
      contains `"N/A"`, a date that stayed a string.
    - `region` showing `object` — a column of pointers to Python `str` objects. Layer 2 measures what
      that costs: 279.4 MB for 5 million rows against 5.0 MB as a categorical.
    - `df.loc[df.region == "APAC", "amount"]` — `loc` takes a row selector and a column selector.
      The row selector here is a boolean Series. **Selecting rows and columns in one `loc` call is
      both faster and safer than `df[df.region == "APAC"]["amount"]`** — see the chained-assignment
      warning below.
    - `.agg(["sum", "mean", "count"])` — several aggregations in one pass over the groups.

    ### `loc` versus `iloc`

    ```python
    s = pd.Series([10, 20, 30, 40], index=["a", "b", "c", "d"])

    print(s.loc["b"])        # 20      by LABEL
    print(s.iloc[1])         # 20      by POSITION

    print(s.loc["b":"c"])    # b:20, c:30   — INCLUSIVE of the endpoint
    print(s.iloc[1:3])       # b:20, c:30   — EXCLUSIVE, like a Python list
    ```

    <Warning>
    **`loc` slices are inclusive of the endpoint and `iloc` slices are not.** This is deliberate:
    with labels there is no "one past the end" to name, so an exclusive upper bound would be
    unusable. It is also a reliable source of off-by-one bugs, especially on date ranges where
    `df.loc["2026-01":"2026-03"]` includes all of March.

    The trap that catches everyone once: an integer index. `s = pd.Series([10,20,30], index=[2,5,8])`
    — then `s.loc[2]` is `10` (the label 2) and `s.iloc[2]` is `30` (position 2). **When the index
    is integers, `loc` and `iloc` mean completely different things and both succeed**, so the bug is
    silent.
    </Warning>

    ### `SettingWithCopyWarning`, explained rather than suppressed

    ```python
    # The warning:
    subset = df[df.amount > 100]
    subset["flagged"] = True        # SettingWithCopyWarning
    ```

    Pandas is telling you: *"`subset` might be a view of `df` or might be a copy — I do not know
    which — so I cannot tell you whether this assignment will modify `df`."* That ambiguity is the
    problem. The result depends on memory layout, which depends on dtypes, which you did not think
    about.

    Two fixes, and which you want depends on your intent:

    ```python
    # If you want an independent copy: say so.
    subset = df[df.amount > 100].copy()
    subset["flagged"] = True                  # unambiguous; df is untouched

    # If you want to modify the ORIGINAL: use one loc call.
    df.loc[df.amount > 100, "flagged"] = True  # unambiguous; df is modified
    ```

    <Warning>
    **Never suppress this warning.** `pd.options.mode.chained_assignment = None` turns off the only
    signal you have that an assignment may not have done anything. The warning is annoying precisely
    because the situation is ambiguous, and the fix — deciding whether you meant to copy — takes
    five seconds.

    Pandas 3.0 will make Copy-on-Write the default, which removes the ambiguity by making every
    such operation a copy. You can turn it on today with
    `pd.options.mode.copy_on_write = True`, and **you should**: it makes the semantics predictable
    and it is what your code will run under eventually.
    </Warning>

    ### `groupby`, and the one people miss

    ```python
    sales = pd.DataFrame({
        "region": ["APAC", "APAC", "EMEA", "EMEA", "EMEA"],
        "rep":    ["ann", "bob", "cy", "dee", "ed"],
        "amount": [100.0, 150.0, 200.0, 50.0, 75.0],
    })

    # AGGREGATE: one row per group.
    print(sales.groupby("region")["amount"].sum())
    # APAC    250.0
    # EMEA    325.0

    # TRANSFORM: one row per ORIGINAL row, filled with the group's value.
    sales["region_total"] = sales.groupby("region")["amount"].transform("sum")
    sales["pct_of_region"] = sales.amount / sales.region_total
    print(sales)
    #   region  rep  amount  region_total  pct_of_region
    # 0   APAC  ann   100.0         250.0       0.400000
    # 1   APAC  bob   150.0         250.0       0.600000
    # 2   EMEA   cy   200.0         325.0       0.615385
    ```

    **`transform` is the one people reach for a merge to do.** "What fraction of its region's total
    is each row?" looks like it needs a groupby, then a merge back. It does not — `transform`
    returns a Series aligned to the original index, so it assigns directly. One line, no join, no
    fan-out risk.

    ### Named aggregations

    ```python
    print(sales.groupby("region").agg(
        total=("amount", "sum"),
        average=("amount", "mean"),
        reps=("rep", "nunique"),
        biggest=("amount", "max"),
    ))
    #         total  average  reps  biggest
    # region
    # APAC    250.0    125.0     2    150.0
    # EMEA    325.0    108.3     3    200.0
    ```

    Each output column is named explicitly as `name=(source_column, function)`. **Use this form
    always.** The alternative — `.agg({"amount": ["sum", "mean"]})` — produces a `MultiIndex` on the
    columns, which then needs flattening, and every downstream reference becomes a tuple. Named
    aggregation gives you a flat, readable frame directly.

    ### Checkpoint — 5 questions before you continue

    <AccordionGroup>
      <Accordion title="1. What is the difference between `loc` and `iloc`?">
        `loc` selects by **label**, `iloc` by **integer position**. `loc` slices include the
        endpoint; `iloc` slices do not. The dangerous case is an integer index, where both work and
        mean different things: with `index=[2,5,8]`, `s.loc[2]` is the first element and `s.iloc[2]`
        is the third.
      </Accordion>
      <Accordion title="2. What does `SettingWithCopyWarning` actually mean?">
        That you are assigning into an object which pandas cannot determine is a view or a copy, so
        it cannot tell you whether the assignment will propagate to the original. Fix it by being
        explicit: `.copy()` if you want independence, or a single `df.loc[mask, col] = value` if you
        want to modify the original. Never suppress it.
      </Accordion>
      <Accordion title="3. When do you use `transform` instead of `agg`?">
        When you want a result aligned to the **original rows** rather than one row per group.
        "Each row as a percentage of its group's total", "each value minus its group mean", "rank
        within group". `agg` collapses; `transform` broadcasts back. Using `agg` plus a merge for
        this is the most common unnecessary join in pandas code.
      </Accordion>
      <Accordion title="4. Why is `object` dtype bad?">
        It is an array of pointers to arbitrary Python objects. Every operation is a Python-level
        loop with boxing and unboxing, and the memory is the pointer array plus every individual
        Python object. Measured in Layer 2: a 5-million-row string column costs 279.4 MB as `object`
        and 5.0 MB as `category` — **55.9×**.
      </Accordion>
      <Accordion title="5. What is a join fan-out and why is it dangerous?">
        When the key is duplicated on one side, each matching left row produces several output rows.
        `merge` does this silently — it is legitimate SQL behaviour — so a duplicated dimension row
        doubles the affected fact rows and every `SUM` downstream is wrong with no error anywhere.
        `validate="m:1"` turns it into an exception at the join.
      </Accordion>
    </AccordionGroup>

    ## Join validation: the one keyword that prevents a whole class of incident

    ```python
    orders = pd.DataFrame({"order_id": [1, 2, 3], "customer_id": ["a", "b", "c"],
                           "amount": [100.0, 200.0, 300.0]})
    customers = pd.DataFrame({"customer_id": ["a", "a", "b", "c"],   # "a" appears TWICE
                              "segment": ["SMB", "ENT", "SMB", "ENT"]})

    bad = orders.merge(customers, on="customer_id", how="left")
    print(len(bad))               # 4, not 3
    print(bad.amount.sum())       # 700.0, not 600.0     <- silently wrong
    ```

    `merge` did nothing wrong — a one-to-many join legitimately produces more rows. **But you meant
    a lookup, and you got a multiplication.** The revenue total is now 17% too high and there is no
    error, no warning, and nothing in the output that looks unusual.

    ```python
    good = orders.merge(customers, on="customer_id", how="left", validate="m:1")
    # MergeError: Merge keys are not unique in right dataset; not a many-to-one merge
    ```

    | `validate=` | Asserts | Use when |
    | --- | --- | --- |
    | `"1:1"` | unique on both sides | joining two tables that should correspond exactly |
    | `"m:1"` | unique on the **right** | **the common case**: facts joined to a dimension |
    | `"1:m"` | unique on the left | a dimension joined to its facts |
    | `"m:m"` | nothing | a genuine many-to-many; state it explicitly so a reader knows it is intentional |

    <Warning>
    **Put `validate=` on every merge you write.** It costs one hash-uniqueness check — microseconds
    — and it converts the single most expensive silent bug in analytics into a loud exception at the
    line that caused it. If you adopt one habit from this module, adopt this one.

    Also check `indicator=True` when debugging a join that lost rows: it adds a `_merge` column
    saying whether each row matched `left_only`, `right_only` or `both`, which tells you immediately
    whether your problem is a fan-out or a failed match.
    </Warning>

    ## Memory: 7.35×, and where every factor comes from

    A 5,000,000-row DataFrame with five columns:

    | Column | Before | MB | After | MB | Reduction |
    | --- | --- | --- | --- | --- | --- |
    | `id` | `int64` | 40.0 | `int32` | 20.0 | 2.0× |
    | `small_int` (0–99) | `int64` | 40.0 | `int8` | 5.0 | **8.0×** |
    | `amount` | `float64` | 40.0 | `float32` | 20.0 | 2.0× |
    | `category` (8 values) | `object` | **279.4** | `category` | **5.0** | **55.9×** |
    | `flag` | `bool` | 5.0 | `bool` | 5.0 | 1.0× |
    | **Total** | | **404.4 MB** | | **55.0 MB** | **7.35×** |

    <Info>
    Method: pandas 2.2.3, `DataFrame.memory_usage(deep=True)` — `deep=True` is essential, because
    without it an `object` column reports only its 8-byte-per-row pointer array and hides the Python
    string objects entirely. Reproduce with `w16_bench.py pandas`.
    </Info>

    **The `object` column is 69% of the frame and shrinks by 55.9×.** That single conversion does
    most of the work. The mechanism: `object` stores 5 million 8-byte pointers (40 MB) *plus* the
    Python `str` objects they point at (~239 MB, because a short Python string has ~49 bytes of
    header before its characters). `category` stores 5 million `int8` codes (5 MB) plus a lookup
    table of 8 strings.

    ```python
    def optimise(df: pd.DataFrame, category_threshold: float = 0.5) -> pd.DataFrame:
        """Downcast numerics and categorise low-cardinality strings.

        The threshold matters: a column where every value is distinct (an ID,
        a free-text field) gets LARGER as a categorical, because you pay for
        both the codes and a dictionary the size of the column.
        """
        out = df.copy()
        for col in out.columns:
            s = out[col]
            if pd.api.types.is_integer_dtype(s):
                out[col] = pd.to_numeric(s, downcast="signed")
            elif pd.api.types.is_float_dtype(s):
                out[col] = pd.to_numeric(s, downcast="float")
            elif pd.api.types.is_object_dtype(s):
                if s.nunique(dropna=False) / max(len(s), 1) < category_threshold:
                    out[col] = s.astype("category")
        return out
    ```

    Three cautions that the naive version of this function gets wrong:

    - **`downcast="signed"` inspects the actual min and max**, so it is safe for the data you have —
      and *not* safe for data you will append later. A column downcast to `int8` because today's
      values fit in 0–99 will overflow when tomorrow's batch contains 200. **Downcast at the end of
      a pipeline, not the start.**
    - **`float32` has ~7 significant digits.** For money that is not enough: 12,345,678.91 does not
      round-trip. Keep money in `int64` cents or `Decimal`.
    - **Categorising a high-cardinality column makes it bigger.** A unique-per-row ID as
      `category` costs the codes *plus* a dictionary as large as the original column. Hence the
      threshold.

    ## The `apply` tax, measured

    One million rows, computing `x * 1.2 + 5`:

    | Approach | Time | Per row | vs vectorized |
    | --- | --- | --- | --- |
    | `Series.apply(lambda x: x*1.2+5)` | 0.1117 s | 112 ns | **251×** |
    | `Series.map(lambda x: x*1.2+5)` | 0.1031 s | 103 ns | 232× |
    | `[x*1.2+5 for x in s.tolist()]` | 0.0447 s | 45 ns | 100× |
    | `s * 1.2 + 5` | **0.0004 s** | **0.4 ns** | **1×** |
    | `s.to_numpy() * 1.2 + 5` | 0.0003 s | 0.3 ns | 0.7× |

    And row-wise iteration, on 200,000 rows:

    | Approach | Time | Per row |
    | --- | --- | --- |
    | `for _, row in df.iterrows()` | 1.8655 s | **9.33 µs** |
    | `for row in df.itertuples()` | 0.0516 s | 0.26 µs |
    | `df["amount"].sum()` | 0.0001 s | ~0.0005 µs |

    <Info>
    Method: pandas 2.2.3, M3 Pro, best-of-1 for the slow approaches and best-of-5 for the fast ones.
    Reproduce with `w16_bench.py pandas`.
    </Info>

    Three things worth extracting:

    1. **`apply` is 251× slower than the vectorized expression**, and it is *slower than a plain
       Python list comprehension* (112 ns against 45 ns per row). `apply` does not vectorize
       anything — it is a Python loop plus per-element pandas overhead. **If you are going to write
       a Python loop, `[f(x) for x in s.tolist()]` is 2.5× faster than dressing it up as `apply`.**
    2. **`iterrows` is 36× slower than `itertuples`**, because it constructs a new `Series` object
       for every row — including building an index and inferring a common dtype across the row's
       values. `itertuples` yields a lightweight namedtuple. **`iterrows` also loses your dtypes**:
       a row containing an int and a float becomes an all-float Series.
    3. **`to_numpy()` first is marginally faster than the pandas expression** (0.3 ns against 0.4 ns
       per row) because it skips index alignment. Not worth it for one operation; worth it inside a
       loop over many columns.

    When you genuinely cannot vectorize — an irregular string parse, a call to an external service —
    the options in order of preference are: a vectorized string method (`.str.extract`), `np.select`
    or `np.where` for conditional logic, a list comprehension over `.tolist()`, and only then
    `apply`.

    ## Method chaining

    ```python
    # The common style: reassignment, intermediate names, mutation.
    df = pd.read_parquet("txns.parquet")
    df = df[df.amount > 0]
    df["month"] = df.ts.dt.to_period("M")
    df = df[~df.is_refund]
    grouped = df.groupby(["month", "category"])["amount"].sum()
    result = grouped.reset_index()
    result = result.sort_values("amount", ascending=False)

    # Chained: reads top to bottom, no intermediate names, no mutation.
    result = (
        pd.read_parquet("txns.parquet")
        .query("amount > 0 and not is_refund")
        .assign(month=lambda d: d.ts.dt.to_period("M"))
        .groupby(["month", "category"], observed=True)["amount"]
        .sum()
        .reset_index()
        .sort_values("amount", ascending=False)
    )
    ```

    The chained version is better for reasons beyond taste:

    - **`assign` with a lambda sees the frame as it is at that point in the chain**, so you can
      reference columns created earlier in the same chain. Reassignment cannot do this without a
      name.
    - **No intermediate variables means no stale ones.** The classic bug is editing step 3 and
      forgetting that step 5 still refers to the pre-edit `df`.
    - **Nothing is mutated**, so `SettingWithCopyWarning` cannot arise.
    - **`observed=True` on `groupby`** — required when grouping by a categorical, or pandas produces
      a row for every *possible* category combination including empty ones. With two categoricals of
      100 levels each that is 10,000 rows instead of the 40 that exist. **This default changes in
      pandas 3.0; set it explicitly until then.**

    For debugging a long chain, insert a `.pipe`:

    ```python
    def peek(df, label=""):
        print(f"{label}: {df.shape}  {list(df.columns)}")
        return df

    result = (
        pd.read_parquet("txns.parquet")
        .pipe(peek, "loaded")
        .query("amount > 0")
        .pipe(peek, "filtered")
        .assign(month=lambda d: d.ts.dt.to_period("M"))
    )
    ```

    ## Reference implementation: a validated analysis pipeline

    ```python
    # analysis.py — CPython 3.12, pandas 2.2.3
    from __future__ import annotations
    from dataclasses import dataclass
    from pathlib import Path

    import pandas as pd

    pd.options.mode.copy_on_write = True     # predictable semantics; the 3.0 default


    class DataQualityError(Exception):
        """Raised when the data violates an assumption the analysis depends on."""


    @dataclass(frozen=True, slots=True)
    class Expect:
        """Assertions that must hold for the analysis to be valid."""
        min_rows: int = 1
        required: tuple[str, ...] = ()
        unique_key: str | None = None
        max_null_rate: float = 0.02

        def check(self, df: pd.DataFrame, name: str) -> pd.DataFrame:
            if len(df) < self.min_rows:
                raise DataQualityError(f"{name}: {len(df)} rows, expected >= {self.min_rows}")
            missing = set(self.required) - set(df.columns)
            if missing:
                raise DataQualityError(f"{name}: missing columns {sorted(missing)}")
            if self.unique_key is not None:
                dupes = int(df[self.unique_key].duplicated().sum())
                if dupes:
                    raise DataQualityError(f"{name}: {dupes} duplicate {self.unique_key}")
            for col in self.required:
                rate = float(df[col].isna().mean())
                if rate > self.max_null_rate:
                    raise DataQualityError(
                        f"{name}: {col} null rate {rate:.1%} exceeds {self.max_null_rate:.1%}")
            return df


    def optimise_dtypes(df: pd.DataFrame, *, category_threshold: float = 0.5) -> pd.DataFrame:
        out = df.copy()
        for col in out.columns:
            s = out[col]
            if pd.api.types.is_integer_dtype(s):
                out[col] = pd.to_numeric(s, downcast="signed")
            elif pd.api.types.is_float_dtype(s):
                out[col] = pd.to_numeric(s, downcast="float")
            elif pd.api.types.is_object_dtype(s) and len(s):
                if s.nunique(dropna=False) / len(s) < category_threshold:
                    out[col] = s.astype("category")
        return out


    def revenue_by_segment(txn_path: Path, cust_path: Path) -> pd.DataFrame:
        """Monthly revenue by customer segment. Every assumption is asserted."""
        txns = Expect(
            min_rows=1, required=("txn_id", "customer_id", "amount", "ts"),
            unique_key="txn_id",
        ).check(pd.read_parquet(txn_path), "transactions")

        customers = Expect(
            min_rows=1, required=("customer_id", "segment"),
            unique_key="customer_id",        # THIS is what prevents the fan-out
        ).check(pd.read_parquet(cust_path), "customers")

        return (
            txns
            .pipe(optimise_dtypes)
            .query("amount > 0")
            .merge(customers, on="customer_id", how="left",
                   validate="m:1", indicator=True)      # belt and braces
            .assign(
                month=lambda d: d.ts.dt.to_period("M"),
                matched=lambda d: d._merge == "both",
            )
            .pipe(_assert_match_rate, minimum=0.99)
            .groupby(["month", "segment"], observed=True)
            .agg(revenue=("amount", "sum"),
                 transactions=("txn_id", "count"),
                 customers=("customer_id", "nunique"))
            .reset_index()
            .sort_values(["month", "revenue"], ascending=[True, False])
        )


    def _assert_match_rate(df: pd.DataFrame, minimum: float) -> pd.DataFrame:
        rate = float(df.matched.mean())
        if rate < minimum:
            raise DataQualityError(
                f"only {rate:.1%} of transactions matched a customer (need {minimum:.0%})")
        return df.drop(columns=["_merge", "matched"])
    ```

    ## Trade-offs table

    | Situation | Choose | Instead of | Because |
    | --- | --- | --- | --- |
    | Any element-wise computation | a vectorized expression | `.apply()` | measured 251× |
    | Genuinely irregular per-element logic | `[f(x) for x in s.tolist()]` | `.apply()` | measured 2.5× faster and it is honest about being a loop |
    | Conditional column logic | `np.select` / `np.where` | `.apply()` with an `if` | vectorized, and it reads as a decision table |
    | Row-wise iteration is unavoidable | `.itertuples()` | `.iterrows()` | measured 36× faster and it preserves dtypes |
    | A per-group value assigned back to rows | `groupby().transform()` | `groupby().agg()` then merge | one line, no join, no fan-out risk |
    | Joining facts to a dimension | `merge(..., validate="m:1")` | a bare `merge` | converts a silent multiplication into an exception |
    | Low-cardinality string column | `category` dtype | `object` | measured 55.9× on 5M rows |
    | Unique-per-row string column | leave it `object`, or use `string[pyarrow]` | `category` | a categorical of unique values is *larger* than the original |
    | Money | `int64` cents or `Decimal` | `float32` or `float64` | `float32` has ~7 digits; 12,345,678.91 does not round-trip |
    | Over ~10 million rows | DuckDB or Polars | pandas | week 15 module 5 measured 12.9× and 9.1× less memory |
    | Under ~100,000 rows | pandas | anything else | milliseconds either way; use the ecosystem |

    ## What breaks in the real world

    A subscription business computed monthly recurring revenue by joining a `subscriptions` table to
    a `plans` dimension to get each subscription's price, then summing.

    ```python
    mrr = (subscriptions
           .merge(plans, on="plan_id", how="left")
           .groupby("month")["monthly_price"].sum())
    ```

    It was correct for two years.

    Then pricing introduced regional pricing: the same `plan_id` now had a row per currency in the
    `plans` table. `plan_id` went from unique to appearing two to five times.

    **Every subscription joined to every currency row for its plan.** A subscription on a plan with
    four currency rows produced four output rows, each with a different `monthly_price`. Reported
    MRR jumped **214%** overnight.

    The size of the jump is what saved them — it was *so* wrong that finance queried it within a
    day. **The near-miss is the point of the story**: had the change affected only 5% of plans, MRR
    would have risen a plausible-looking 9%, been attributed to a good month, and gone unnoticed for
    a quarter.

    The diagnosis took two hours, and the query that found it was:

    ```python
    print(len(subscriptions), len(merged))     # 48,201  vs  147,893
    ```

    **Row count before and after a join.** If a left join changes the row count, you have a fan-out.
    Two hours to find something one assertion would have caught at the line that caused it.

    The fix was three parts:

    ```python
    # 1. Assert the dimension is unique on the join key, before joining.
    assert plans.plan_id.is_unique, f"{plans.plan_id.duplicated().sum()} duplicate plan_ids"

    # 2. Fix the actual model: the key is now composite.
    mrr = (subscriptions
           .merge(plans, on=["plan_id", "currency"], how="left", validate="m:1")
           .groupby("month")["monthly_price"].sum())

    # 3. A regression test with a multi-currency plan in the fixture.
    ```

    What generalises:

    - **A join's row count is an invariant worth asserting.** For a `m:1` left join, output rows must
      equal input rows. One line: `assert len(out) == len(left)`. **This single assertion catches
      every fan-out**, regardless of why the key stopped being unique.
    - **The natural key changed underneath the code.** Nobody edited the analysis; the *meaning* of
      `plan_id` changed. This is the same failure as week 15 module 4's currency change — a semantic
      change that no type or schema check can detect — and the defence is again an assertion about a
      property you depend on, not about the schema.
    - **Be more suspicious of a small discrepancy than a large one.** A 214% jump gets investigated
      immediately. A 9% jump gets attributed to growth. **The bugs that survive are the plausible
      ones**, which is an argument for asserting invariants rather than eyeballing outputs.

    ### Design checkpoint

    <Accordion title="You have a 3 GB CSV and an 8 GB laptop. `pd.read_csv` OOMs. Work through the options in order, and say which you would actually choose.">
    **Model answer.**

    **First, understand why it OOMs, because the multiplier drives every option.** A 3 GB CSV
    becomes 5–15 GB as a pandas DataFrame. The multiplier is almost entirely about strings: a short
    Python `str` carries ~49 bytes of object header before its characters, so a column of 3-character
    codes costs ~52 bytes per row as `object` against 3 bytes in the file. Numeric columns are
    roughly neutral or smaller. **So the first question is: how many string columns, and what is
    their cardinality?**

    **The options, in the order I would try them.**

    **1. Read only the columns you need.** `pd.read_csv(path, usecols=[...])`. Analyses typically
    touch 5 of 40 columns. **This alone often solves it**, costs one argument, and it is embarrassing
    how often people skip straight to Dask.

    **2. Specify dtypes at read time.** `dtype={"category_col": "category", "small_int": "int8"}`.
    Measured in Layer 2: 404 MB becomes 55 MB, a 7.35× reduction, and the categorical conversion is
    most of it. Doing this at read time rather than after means the `object` column never exists.

    **3. Convert to Parquet once, then work from that.** `pd.read_csv(chunksize=...)` writing
    Parquet, then `pd.read_parquet(columns=[...])`. Week 15 module 1 measured Parquet at 4.68×
    smaller with zstd and 16× faster on a single-column aggregate, and the dtypes are stored so they
    do not need re-specifying. **Do this once and every subsequent read is cheap.**

    **4. Chunked processing.** `for chunk in pd.read_csv(path, chunksize=500_000)`. Works when the
    computation is associative — sums, counts, group-by-then-combine. **Does not work for anything
    needing the whole dataset at once**: a median, a sort, a join against another large table. Know
    which you have before committing.

    **5. Use DuckDB.** `duckdb.query("SELECT ... FROM 'file.csv' GROUP BY ...").df()`. Streams the
    CSV, never materialises it, and returns only the aggregated result to pandas. Week 15 module 5
    measured 12.9× faster than pandas with 9.1× less memory. **This is what I would actually
    choose**, because it is one line, it requires no restructuring, and it removes the memory
    question entirely rather than deferring it.

    **6. Polars lazy with streaming.** `pl.scan_csv(path).filter(...).group_by(...).collect(streaming=True)`.
    A good answer if the team prefers a DataFrame API to SQL.

    **What I would not do: Dask or Spark.** Both add a scheduler, a cluster concept and a debugging
    experience substantially worse than single-process code, to handle 3 GB — which is a size a
    laptop handles comfortably with any of options 1 through 6. **Reaching for a distributed
    framework at 3 GB is the most common over-engineering in data work**, and the honest reason it
    happens is that "we use Spark" sounds more like an answer than "we passed `usecols`".

    **The number that decides it.** Run `df.memory_usage(deep=True).sum()` on a 100,000-row sample
    and multiply. If the projection is under ~4 GB, options 1 and 2 are enough. If it is 20 GB, go
    straight to DuckDB. **Five minutes of measurement replaces the entire argument.**
    </Accordion>

    ## Where the memory actually goes

    ```python
    import pandas as pd, sys

    s = pd.Series(["hello"] * 1_000_000)
    print(s.memory_usage(deep=False) / 1e6)   # 8.0 MB   <- just the pointers
    print(s.memory_usage(deep=True) / 1e6)    # 62.0 MB  <- pointers + the str objects
    print(sys.getsizeof("hello"))             # 54 bytes for a 5-character string
    ```

    **`deep=False` is the default and it lies to you about `object` columns.** It reports the
    8-byte-per-row pointer array and ignores the Python objects entirely. Every memory audit must
    pass `deep=True`; a surprising amount of published advice does not.

    The layout of the three string representations:

    | Representation | 1M short strings | Structure |
    | --- | --- | --- |
    | `object` | ~62 MB | 8 MB of pointers + ~54 bytes per distinct `str` object |
    | `category` (8 distinct) | ~1 MB | 1 MB of `int8` codes + 8 strings |
    | `string[pyarrow]` | ~7 MB | one contiguous byte buffer + an offsets array |

    **`string[pyarrow]` is the underused one.** It stores all the characters end to end in one
    buffer with an `int32` offset per row — no per-string Python object at all. It is the right
    choice for high-cardinality text where `category` would be counterproductive: free-text fields,
    URLs, user IDs. It requires `pyarrow` (18.1.0 here) and is set with
    `df["col"].astype("string[pyarrow]")` or `dtype_backend="pyarrow"` at read time.

    The general rule for a string column:

    ```
    distinct / total  <  ~0.5   ->  category
    distinct / total  >= ~0.5   ->  string[pyarrow]
    never                       ->  leave it as object
    ```

    ## The BlockManager, and why `iterrows` is 36× slower

    Internally, a pandas DataFrame is not a dict of arrays. It is a **BlockManager**: columns of the
    same dtype are consolidated into shared 2-D NumPy blocks. A frame with three `int64` columns and
    two `float64` columns holds two blocks, `(3, n)` and `(2, n)`.

    That design explains several otherwise-mysterious behaviours:

    - **Column access is a view; row access is a gather.** `df["a"]` slices one row out of a block —
      free. A row spans every block and every dtype, so `df.iloc[0]` must collect values from
      several blocks and find a common dtype for them. **This is why `iterrows` costs 9.33 µs per
      row and `itertuples` costs 0.26 µs**: `iterrows` constructs a whole `Series` per row, with an
      index and a dtype negotiation.
    - **`iterrows` silently upcasts.** A row containing an `int64` and a `float64` becomes an
      all-`float64` Series, because a Series has one dtype. Integer IDs become floats and, past 2⁵³,
      lose precision. `itertuples` preserves each field's type.
    - **Adding a column can trigger a consolidation copy.** Assigning a new column of an existing
      dtype may cause pandas to rebuild that block. Adding columns in a loop is `O(n²)` in total
      copying — the same shape as string `+=` in week 13 module 2. **Build a dict of Series and
      construct the frame once**, or use `df.assign(**cols)`.
    - **`df.values` on a mixed-dtype frame produces `object`**, because there is no single NumPy
      dtype that holds an int and a string. This silently destroys performance downstream. Use
      `df[numeric_cols].to_numpy()` on a homogeneous subset.

    Pandas 3.0 moves toward Arrow-backed columnar storage without consolidation, which changes some
    of these. The row-versus-column asymmetry does not change: it is inherent to columnar layout.

    ## Copy-on-Write

    ```python
    pd.options.mode.copy_on_write = True     # the pandas 3.0 default
    ```

    Under CoW, every operation that *could* return a view returns something that behaves as an
    independent copy, with the actual copy deferred until a write occurs. Consequences:

    - **`SettingWithCopyWarning` disappears**, because the ambiguity it warned about is gone.
    - **Chained assignment silently stops working** rather than sometimes working:
      `df["a"][0] = 1` now never modifies `df`. **This is a breaking change for code that relied on
      it**, and the failure is silent — the assignment succeeds and does nothing.
    - **Many operations get faster**, because pandas can skip defensive copies it previously made
      just in case.

    Turn it on now. Your code will run under it eventually, and finding the two places that relied
    on chained assignment is much cheaper today than during an upgrade.

    ## Chunked and out-of-core processing

    ```python
    # Streaming aggregation over a file larger than memory.
    from collections import defaultdict

    totals: defaultdict[str, float] = defaultdict(float)
    counts: defaultdict[str, int] = defaultdict(int)

    for chunk in pd.read_csv("huge.csv", chunksize=500_000,
                             usecols=["category", "amount"],
                             dtype={"category": "category"}):
        g = chunk.groupby("category", observed=True)["amount"].agg(["sum", "count"])
        for cat, row in g.iterrows():
            totals[cat] += row["sum"]
            counts[cat] += row["count"]

    means = {k: totals[k] / counts[k] for k in totals}
    ```

    **This works because sum and count are associative and the combination is exact.** The pattern
    generalises to any aggregate expressible as (per-chunk statistic, combine function):

    | Aggregate | Chunkable? | How |
    | --- | --- | --- |
    | sum, count, min, max | **yes** | add, add, min, max |
    | mean | **yes** | keep sum and count separately, divide at the end |
    | variance, std | **yes** | Welford's or (sum, sum of squares, count) — see the warning |
    | median, any quantile | **no, exactly** | t-digest or a two-pass histogram approximation |
    | distinct count | **no, exactly** | HyperLogLog for an approximation |
    | sort | **no** | external merge sort (week 13 module 5) |
    | join against a large table | **no** | hash the smaller side, or use a real engine |

    <Warning>
    **Do not compute variance as `E[x²] − E[x]²` on real data.** It is algebraically correct and
    numerically catastrophic: for values with a large mean and small variance the two terms are
    nearly equal and you subtract them, losing most of your significant digits to cancellation. For
    values around 10⁶ with a variance of 1, `float64` can return a *negative* variance. Use
    **Welford's online algorithm** or `np.var`, both of which are numerically stable. This is the
    same precision failure as week 16 module 1's summation result, in a different disguise.
    </Warning>

    **The honest guidance: at the point where chunking is necessary, DuckDB is usually simpler.**
    Week 15 module 5 measured DuckDB at 12.9× faster with 9.1× less memory on a 10-million-row
    group-by, and it streams larger-than-memory files without any of the manual combination logic
    above. Chunking is worth knowing because sometimes you cannot add a dependency, and because
    understanding which aggregates are chunkable is what tells you which are safe to distribute.

    ## Arrow-backed pandas

    ```python
    df = pd.read_parquet("txns.parquet", dtype_backend="pyarrow")
    print(df.dtypes)
    # txn_id        int64[pyarrow]
    # merchant     string[pyarrow]
    # amount       double[pyarrow]
    ```

    What it buys:

    - **Proper missing-value support for integers.** NumPy `int64` cannot hold `NaN`, so a column of
      integers with any missing value becomes `float64` — silently turning IDs into floats and
      losing exactness past 2⁵³. Arrow has a separate validity bitmap, so `int64[pyarrow]` holds
      nulls and stays integral.
    - **Efficient strings**, as above.
    - **Zero-copy interchange** with DuckDB, Polars and any other Arrow consumer.

    What it costs: not every pandas operation supports it yet, some fall back to NumPy silently, and
    some third-party libraries (including parts of scikit-learn) will call `to_numpy()` and undo the
    benefit. **Use it for I/O and storage; convert at the boundary of anything that does not support
    it.**

    ## Production failure modes

    | Failure mode | Signature | Detection |
    | --- | --- | --- |
    | Join fan-out | totals inflated; row count changed across a left join | `validate="m:1"`; `assert len(out) == len(left)` |
    | Integer column silently became float | IDs displayed as `12345.0`; exactness lost past 2⁵³ | one missing value forced `float64`; use `Int64` or `int64[pyarrow]` |
    | `memory_usage()` under-reports | audit says 8 MB, RSS says 62 MB | always pass `deep=True` |
    | `iterrows` upcasting a row | integer IDs become floats mid-loop | `itertuples`, or do not iterate |
    | Adding columns in a loop | quadratic time on a wide frame | build a dict and construct once, or `df.assign(**cols)` |
    | `df.values` on a mixed frame | everything downstream is `object` and 100× slower | `to_numpy()` on a homogeneous column subset |
    | Chained assignment does nothing | silent under Copy-on-Write | single `df.loc[mask, col] = value` |
    | `groupby` on categoricals explodes | 10,000 rows where 40 exist | `observed=True` |
    | Categorising a unique column | memory increases | threshold on `nunique/len`; use `string[pyarrow]` instead |
    | Variance computed as `E[x²]−E[x]²` | negative or wildly wrong variance on large-mean data | Welford's, or `np.var` |
    | Downcast to `int8` then appending larger values | silent overflow and wraparound | downcast at the end of a pipeline, not the start |

    ## Frontier and research pointers

    - **McKinney (2010), "Data Structures for Statistical Computing in Python."** SciPy. —
      **Takeaway:** the original pandas paper; the design goal was an R-like data frame over NumPy,
      and the BlockManager and the index both follow from that constraint.
    - **The Apache Arrow columnar format specification.** — **Takeaway:** a language-independent
      in-memory columnar layout with an explicit validity bitmap; the bitmap is what lets Arrow
      represent a null in an integer column, which NumPy fundamentally cannot.
    - **pandas 3.0 Copy-on-Write documentation and PDEP-7.** — **Takeaway:** making every operation
      behave as a copy removes the view/copy ambiguity entirely; read the migration section for the
      chained-assignment patterns that break silently.
    - **Welford (1962), "Note on a Method for Calculating Corrected Sums of Squares and Products."**
      *Technometrics* 4(3). — **Takeaway:** a one-pass, numerically stable variance that avoids the
      catastrophic cancellation of `E[x²] − E[x]²`; two lines, and it is what every serious
      implementation uses.
    - **Chan, Golub & LeVeque (1983), "Algorithms for Computing the Sample Variance."** *The
      American Statistician* 37(3). — **Takeaway:** the comparative error analysis showing exactly
      how badly the textbook formula fails and by how much; the numbers are alarming.
    - **The Polars and DuckDB design documents on late materialisation.** — **Takeaway:** the
      architectural reason pandas is slower — it materialises every intermediate — and why a query
      engine over the same data does not; week 15 module 5 measured the consequence at 12.9×.

    ## Stretch challenge

    **Build a DataFrame memory profiler that tells you what to change, and measure how much it wins
    across real datasets.**

    Everyone knows dtypes save memory. Nobody knows how much, for their data, or which change is
    worth making.

    Build:

    1. **An analyser** that takes a DataFrame and reports, per column: current dtype, `deep=True`
       memory, cardinality, min/max, null rate, and a **recommended dtype with the projected saving
       in bytes** — sorted by saving, so the first line is the one worth doing.
    2. **A safety analysis for every recommendation.** Downcasting to `int8` is safe for the current
       data and unsafe for future data — report the headroom (`max_value / dtype_max`). Recommending
       `float32` for a money column should be flagged as unsafe regardless of the saving.
    3. **A validating applier** that performs the conversions and asserts round-trip fidelity:
       numeric columns must compare equal within a stated tolerance, and any lossy conversion must be
       refused rather than silently applied.
    4. **An empirical study.** Run it across at least ten real public datasets — Kaggle, UCI,
       NYC taxi, OpenStreetMap extracts — and report the distribution of achievable savings.

    The open questions, which are the actual work:

    - **What is the median achievable reduction on real data?** I measured 7.35× on a synthetic frame
      chosen to have a low-cardinality string column. **My prediction is that real datasets cluster
      around 2–4×, with the outliers driven entirely by whether there is a high-volume, low-
      cardinality string column.** Test it.
    - **Where is the `category` versus `string[pyarrow]` crossover?** The folklore threshold is 50%
      cardinality. Measure it across cardinality ratios from 0.01 to 1.0 and find where the lines
      actually cross — and whether it depends on string length.
    - **Does the saving survive an operation?** A categorical column that is `groupby`-ed, merged or
      concatenated may silently revert to `object`. **Measure memory before and after a realistic
      pipeline**, not just after conversion. This is the finding most likely to be genuinely
      surprising.
    - **How much of the saving translates into speed?** Less memory means better cache behaviour, but
      categoricals add an indirection on comparison. Time a group-by and a merge on both versions.
      **It may be slower**, and knowing which operations regress is more useful than the memory
      number alone.

    A memory profiler that recommends, validates and quantifies is a genuinely useful tool, and the
    empirical study — "how much does dtype optimisation actually save on real data?" — is a question
    everyone has an opinion about and nobody has measured.

  </Tab>
</Tabs>

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Totals silently too high after a join | Fan-out — the key is duplicated on the right | `validate="m:1"`; assert `len(out) == len(left)` |
| Assignment appears to do nothing | Chained assignment on an ambiguous view/copy | Single `df.loc[mask, col] = value`, or `.copy()` first |
| `SettingWithCopyWarning` suppressed globally | The only signal that an assignment may be lost was turned off | Fix the ambiguity; enable Copy-on-Write |
| Integer IDs display as `12345.0` | One missing value forced the column to `float64` | `Int64` (nullable) or `int64[pyarrow]` |
| Memory audit disagrees with RSS by 8× | `memory_usage()` without `deep=True` ignores `object` contents | Always `deep=True` |
| Analysis is slow on a small frame | `.apply()` in a hot path — measured 251× | Vectorized expression, `np.select`, or a list comprehension |
| Row loop is unbearably slow | `iterrows` builds a `Series` per row — measured 36× | `itertuples()`, or vectorize |
| `groupby` result has thousands of empty rows | Grouping by categoricals without `observed=True` | `observed=True` (the pandas 3.0 default) |
| Frame gets *bigger* after "optimising" | Categorised a high-cardinality column | Threshold on `nunique/len`; `string[pyarrow]` for high cardinality |
| Money is off by a cent at scale | `float32` has ~7 significant digits | `int64` cents or `Decimal` |
| Variance comes back negative | `E[x²] − E[x]²` cancellation on large-mean data | Welford's algorithm, or `np.var` |
| Adding columns in a loop is quadratic | BlockManager consolidation copies on each addition | Build a dict, construct once, or `df.assign(**cols)` |

## Sources & further reading

**Primary docs**

- [`DataFrame.merge` — the `validate` parameter](https://pandas.pydata.org/docs/reference/api/pandas.DataFrame.merge.html) (pandas 2.2.3) — read this and then add it to every merge you own; also read `indicator=True`, which is the fastest way to diagnose a join that lost rows.
- [Copy-on-Write](https://pandas.pydata.org/docs/user_guide/copy_on_write.html) — read the migration section for the chained-assignment patterns that stop working silently; this is the pandas 3.0 default and worth adopting now.
- [Scaling to large datasets](https://pandas.pydata.org/docs/user_guide/scale.html) — read this for the official, unusually honest guidance on chunking, dtypes and when to use something that is not pandas.
- [Categorical data](https://pandas.pydata.org/docs/user_guide/categorical.html) — read this for the memory model and the `observed=` behaviour in `groupby`, which is the source of the empty-rows surprise.
- [PyArrow-backed dtypes](https://pandas.pydata.org/docs/user_guide/pyarrow.html) — read this for `dtype_backend="pyarrow"` and, importantly, the list of operations that still fall back to NumPy.

**Papers**

- [McKinney (2010), *Data Structures for Statistical Computing in Python*, SciPy Proceedings.](https://doi.org/10.25080/Majora-92bf1922-00a) — **Takeaway:** the original design rationale; the BlockManager and the index both follow from the goal of an R-style data frame over NumPy.
- [Welford (1962), *Note on a Method for Calculating Corrected Sums of Squares and Products*, Technometrics 4(3).](https://doi.org/10.1080/00401706.1962.10490022) — **Takeaway:** a one-pass numerically stable variance; two lines, and it is why `np.var` does not use the textbook formula.
- [Chan, Golub & LeVeque (1983), *Algorithms for Computing the Sample Variance: Analysis and Recommendations*, The American Statistician 37(3).](https://doi.org/10.1080/00031305.1983.10483115) — **Takeaway:** the error analysis quantifying how badly `E[x²] − E[x]²` fails; the magnitude is genuinely alarming.
- [The Apache Arrow columnar format specification.](https://arrow.apache.org/docs/format/Columnar.html) — **Takeaway:** the validity bitmap is what allows a null in an integer column, which is the concrete reason `Int64`/`int64[pyarrow]` exists and NumPy's `int64` cannot do it.

**Go deeper**

- [Wes McKinney, *Python for Data Analysis* 3rd ed. (2022), **Chapters 8 and 10**](https://wesmckinney.com/book/) — merging/reshaping and group operations, from pandas' author; chapter 10's treatment of `transform` versus `agg` is the clearest anywhere.
- [Tom Augspurger, *Modern Pandas* (blog series)](https://tomaugspurger.net/posts/modern-1-intro/) — read the "Method Chaining" and "Performance" posts specifically; the chaining post is where the style in Layer 2 comes from and it makes the case better than I have.
- [Matt Harrison, *Effective Pandas* (2021)](https://store.metasnake.com/effective-pandas-book) — the whole book is an argument for chaining and correct dtypes, with before-and-after examples; read it if the Layer 2 chaining section appealed and you want two hundred more pages of it.
