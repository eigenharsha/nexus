## Outcome

<Note>
By Sunday you will have a CLI that takes any CSV or Parquet file and produces an HTML report:
schema, missingness, distributions, outliers, correlations, target relationships, **leakage
warnings**, and a written summary. It will run on a 10-million-row file inside a fixed memory budget.
And you will be able to defend every number in it.
</Note>

## Why this week matters more than it looks

<Info>
**For Meera specifically.** Week 15 built the pipeline; this week is what you do with what it
loaded. Together they are one system — raw source to defensible analysis — and that system is the
artifact you point at. The EDA tool in particular is something you will genuinely use every week
afterwards, on your own job's data, which is not true of most course projects.
</Info>

And for everyone: **this is the week that decides whether Phase 3 works.** Every model you build
from week 17 onward is a function of the features you feed it. The single most common reason a
beginner's model scores 0.95 in a notebook and 0.61 in production is a mistake made in this week —
a transform fitted on the whole dataset, a duplicated row spanning the train/test split, a feature
that encodes the answer. Week 19 pays that off; **week 16 is where the debt is incurred or avoided.**

## The three numbers to carry out of this week

| Claim | Measured |
| --- | --- |
| Vectorization beats a Python loop | **156×** on a 1M-element dot product |
| dtype optimisation cuts DataFrame memory | **7.35×** on a 5M-row frame (404 MB → 55 MB) |
| `Series.apply` costs you | **251×** versus the vectorized expression |

And the one that matters most, which is a **negative** result:

| Folklore | What the measurement says |
| --- | --- |
| "Imputing before the train/test split inflates your score" | **It does not, measurably.** Across mean, KNN and iterative imputers at n = 100 to 5,000, the inflation was within ±0.02 AUC and usually negative. |
| The leaks that *do* inflate your score | **Target encoding: +0.275 AUC on a pure-noise feature. Feature selection before CV: +0.356 accuracy at 20,000 features. Duplicate rows spanning the split: +0.200 AUC at 50% duplication.** |

Module 3 works through why, and the principle that predicts which transforms leak and which do not.

<Warning>
The task specification for this week asked for a demonstration that imputing before splitting
inflates test accuracy. **I built it, measured it thirty times across three imputers and four sample
sizes, and it does not.** Rather than manufacture a scenario that produces the expected number, the
module reports what actually happened and replaces the folklore with a rule that predicts the
measured results. That is a more useful lesson and it is the honest one.
</Warning>

## Exit checks

1. Replace a Python loop with a vectorized expression and quote your own speedup.
2. Take a DataFrame and cut its memory by 5× or more with dtypes, and say where each factor came from.
3. State which data transforms leak across a train/test split and which do not, with the rule that
   distinguishes them.
4. Run a full EDA checklist on an unfamiliar dataset and produce a two-page memo with findings, risks
   and a recommended modelling approach.
5. Take a misleading chart, rebuild it honestly, and write the critique.
