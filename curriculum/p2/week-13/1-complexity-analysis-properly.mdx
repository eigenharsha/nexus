    ## The idea in one paragraph

    When you write code, you want to know how slow it will get as the data gets bigger. You
    could time it — but the time you measure depends on your laptop, your Python version, and
    what else is running. **Complexity analysis** is the trick of ignoring all of that and
    counting only the thing that does not change: how many *steps* the code takes, as a
    function of how much data you gave it. If doubling the data doubles the steps, that is
    one shape. If doubling the data quadruples the steps, that is a much worse shape. Big-O
    notation is how we write the shape down.

    ### The analogy

    You are looking for one specific book.

    - **A pile of books on the floor.** You check the top one, then the next, then the next.
      With 100 books you check up to 100. With 200 books, up to 200. Double the books, double
      the work. That shape is called **linear**, written `O(n)`.
    - **A library with a catalogue.** You look up the call number, walk to the shelf, take the
      book. With 100 books that is three actions. With 200 books it is still three actions.
      The pile of books got bigger but your work did not. That shape is called **constant**,
      written `O(1)`.
    - **Comparing every book to every other book** to find two identical copies. 100 books is
      about 100 × 100 = 10,000 comparisons. 200 books is 40,000. Double the books, quadruple
      the work. That is **quadratic**, `O(n²)`.

    The pile of books does not become a library because you bought a faster laptop. That is the
    whole point of complexity analysis: it describes a property of the *method*, not of the
    machine.

    ### Every term, defined

    - **`n`** — the size of the input. Number of items in a list, characters in a string, rows
      in a table. If a function takes two inputs of different sizes, we name them: `n` and `m`.
    - **Operation** — one unit of work we agree to count. Usually a comparison, an arithmetic
      step, or an array access. Which one you pick barely matters, because Big-O throws away
      constant factors anyway (see below).
    - **Big-O, written `O(f(n))`** — a claim that the work grows *no faster than* `f(n)`, once
      `n` is big enough, ignoring constant multipliers. It is an **upper bound**.
    - **Big-Ω (omega), `Ω(f(n))`** — a **lower bound**. The work grows *at least as fast as*
      `f(n)`.
    - **Big-Θ (theta), `Θ(f(n))`** — both at once. The work grows *exactly* like `f(n)`. This
      is usually what people mean when they say Big-O in conversation.
    - **Constant factor** — the multiplier Big-O deliberately discards. `3n` and `1000n` are
      both `O(n)`. Layer 3 is about the day that discarded 1000 ruins your afternoon.

    <Info>
    People say "Big-O" when they mean Θ almost all of the time. Saying "sorting is O(n²)" is
    technically true of merge sort too — merge sort's `n log n` growth is indeed *no faster
    than* `n²`. It is just useless information. When you want to be precise, say Θ.
    </Info>

    ### The smallest working example

    Count the operations rather than the seconds. This runs in under a second.

    ```python
    # count_ops.py — CPython 3.12
    def sum_pairs_slow(xs):
        """For every pair, add them. Returns the count of operations done."""
        ops = 0
        total = 0
        for a in xs:              # runs n times
            for b in xs:          # runs n times, for each a
                total += a * b    # so this line runs n * n times
                ops += 1
        return ops

    def sum_pairs_fast(xs):
        """Same answer, using algebra: (sum of xs) squared."""
        ops = 0
        s = 0
        for a in xs:              # runs n times
            s += a
            ops += 1
        total = s * s             # one more operation
        ops += 1
        return ops

    for n in (10, 100, 1000):
        data = list(range(n))
        print(f"n={n:5d}  slow={sum_pairs_slow(data):9d} ops   fast={sum_pairs_fast(data):6d} ops")
    ```

    Output:

    ```
    n=   10  slow=      100 ops   fast=    11 ops
    n=  100  slow=    10000 ops   fast=   101 ops
    n= 1000  slow=  1000000 ops   fast=  1001 ops
    ```

    ### Line-by-line walkthrough

    - `for a in xs:` — this loop body runs once per element. If `xs` has `n` elements, the
      body runs `n` times. That alone would be `O(n)`.
    - `for b in xs:` — nested *inside* the first loop. For each of the `n` values of `a`, this
      runs `n` times. Total body executions: `n × n = n²`. That is where the quadratic comes from.
    - `total += a * b` — one multiplication and one addition. Two operations, not one. Big-O
      does not care: `2n²` is `O(n²)`.
    - `ops += 1` — the counter. We are counting loop-body executions, which is a fine proxy.
    - In `sum_pairs_fast`, the single loop runs `n` times and then there is exactly one more
      multiplication. Total: `n + 1` operations, which is `O(n)`.
    - Both functions compute the same value — `(x₀+x₁+…)²` expands to the sum of every pairwise
      product. The fast one just uses algebra instead of brute force. **Most real optimisation
      is this: finding the algebraic identity that collapses a loop.**

    Look at the numbers again. Going from n=100 to n=1000 (10× the data) multiplied the slow
    version's work by 100 and the fast version's by 10. That ratio — *how the work multiplies
    when the input multiplies* — is the only thing Big-O describes.

    ### The five shapes you must recognise on sight

    | Shape | Name | n=10 | n=1,000 | n=1,000,000 | Where you meet it |
    | --- | --- | --- | --- | --- | --- |
    | `O(1)` | constant | 1 | 1 | 1 | dict lookup, array index, stack push |
    | `O(log n)` | logarithmic | 3 | 10 | 20 | binary search, B-Tree descent, heap push |
    | `O(n)` | linear | 10 | 1,000 | 1,000,000 | one pass over a list, `max()`, `sum()` |
    | `O(n log n)` | linearithmic | 33 | 10,000 | 20,000,000 | any comparison sort, `list.sort()` |
    | `O(n²)` | quadratic | 100 | 1,000,000 | 10¹² | nested loop over the same data |

    Read the last column of that table. At a million items, `O(n log n)` is 20 million steps —
    a couple of seconds in Python. `O(n²)` is a trillion steps — about eleven days. That is
    what "the shape matters" means in practice.

    ### How to read complexity off code

    Four rules get you 90% of the way:

    <Steps>
      <Step title="Loops multiply">
        A loop that runs `n` times, containing a loop that runs `n` times, is `n²`. A loop that
        runs `n` times containing a loop that runs `m` times is `n·m` — and if `m` is a fixed
        small number like 3, that is still just `O(n)`.
      </Step>
      <Step title="Sequential blocks add, then you keep the biggest">
        Sort a list (`n log n`), then scan it once (`n`). Total is `n log n + n`. For large `n`,
        the `n log n` term dwarfs the `n` term, so we write `O(n log n)`. **Dropping the smaller
        term is not sloppiness — it is the definition.**
      </Step>
      <Step title="Halving gives you a log">
        If each step throws away half the remaining work, you can only do that about `log₂ n`
        times before there is nothing left. `log₂(1,000,000) ≈ 20`. That is why binary search
        on a million-row table takes 20 comparisons.
      </Step>
      <Step title="Hidden loops count">
        `if x in my_list` is `O(n)` — it scans. `if x in my_set` is `O(1)` — it hashes.
        `my_string += other` inside a loop copies the whole string each time, making the loop
        `O(n²)`. The loop you did not write still costs you.
      </Step>
    </Steps>

    <Warning>
    Rule 4 is the single most common source of accidental quadratic code in Python, and it is
    almost always `x in some_list` sitting inside a `for` loop. If you take one habit from this
    module: when you see a membership test inside a loop, check what it is testing against.
    </Warning>

    ### Guided practice

    Classify each snippet. The scaffold is written; you fill in the answer, then check.

    ```python
    # (a)
    def first_even(xs):
        for x in xs:
            if x % 2 == 0:
                return x
        return None

    # (b)
    def has_duplicate(xs):
        for i in range(len(xs)):
            for j in range(i + 1, len(xs)):
                if xs[i] == xs[j]:
                    return True
        return False

    # (c)
    def has_duplicate_fast(xs):
        seen = set()
        for x in xs:
            if x in seen:
                return True
            seen.add(x)
        return False

    # (d)
    def count_down(n):
        while n > 1:
            n = n // 2
        return 0

    # (e)  the trap
    def join_bad(words):
        out = ""
        for w in words:
            out += w
        return out
    ```

    <AccordionGroup>
      <Accordion title="Answers">
        - **(a)** Worst case `O(n)` — the even number might be last, or absent. Best case `O(1)` —
          it might be first. Average, for random data, `O(1)`-ish, but you quote the worst case
          unless you have a reason not to.
        - **(b)** `O(n²)`. The inner loop runs `n-1`, then `n-2`, … which sums to `n(n-1)/2`.
          Drop the constant `½` and the lower-order `n`: `O(n²)`. **Space `O(1)`.**
        - **(c)** `O(n)` time — one pass, and `x in seen` on a set is `O(1)`. **Space `O(n)`** —
          the set can grow to hold every element. This is the classic time-for-space trade.
        - **(d)** `O(log n)`. `n` halves each iteration, so the loop runs `log₂ n` times. For
          `n = 1,000,000` that is 20 iterations.
        - **(e)** `O(n²)` in total characters, and this is the trap. Python strings are
          immutable, so `out += w` builds a brand-new string by copying every character of
          `out` plus every character of `w`. Copy 1 char, then 2, then 3… total copies are
          quadratic. The fix is `"".join(words)`, which is `O(total characters)`.
      </Accordion>
    </AccordionGroup>

    <Note>
    CPython contains a special-case optimisation that sometimes makes `str += ` in a loop
    behave linearly (it mutates in place when the string has a refcount of 1). It is an
    implementation detail of CPython, it does not fire reliably, and it does not exist in PyPy
    or in most other runtimes. Do not build on it. Use `join`.
    </Note>

    ### Checkpoint — 5 questions before you continue

    <AccordionGroup>
      <Accordion title="1. An algorithm does 5n + 300 operations. What is its Big-O?">
        `O(n)`. Constant multipliers (the 5) and additive constants (the 300) are both dropped.
        Note that at `n = 10` the "constant" 300 is 85% of the total work — Big-O is a statement
        about large `n` and it says nothing useful about small `n`.
      </Accordion>
      <Accordion title="2. Is O(n) always faster than O(n²)?">
        No. It is faster *for sufficiently large n*. `1000n` versus `n²`: the quadratic version
        is faster for every `n` below 1000. Real crossovers happen at small `n` all the time,
        which is why `list.sort()` in CPython switches to insertion sort for runs shorter than
        64 elements.
      </Accordion>
      <Accordion title="3. What is the time and space complexity of reversing a list in place?">
        Time `O(n)` — you swap `n/2` pairs. Space `O(1)` — you need one temporary variable,
        regardless of how big the list is. "In place" is precisely a claim about space complexity.
      </Accordion>
      <Accordion title="4. You have `for x in a: if x in b:` where `a` and `b` are both lists of length n. Complexity? How do you fix it?">
        `O(n²)`, because `x in b` scans `b` every time. Fix: `bset = set(b)` once — `O(n)` — then
        `if x in bset` is `O(1)`, so the whole thing is `O(n)` time and `O(n)` extra space.
      </Accordion>
      <Accordion title="5. Why do we usually quote worst case rather than average case?">
        Because the worst case is the one that pages you at 3 a.m. Average case requires you to
        assume a distribution of inputs, and adversaries — or just an unusual customer — do not
        respect your assumed distribution. Quicksort's `O(n²)` worst case is not a theoretical
        curiosity; it is a real denial-of-service vector when the pivot rule is predictable.
      </Accordion>
    </AccordionGroup>

    ## The formal definitions, and why they are shaped that way

    `f(n) = O(g(n))` means: there exist constants `c > 0` and `n₀` such that for all
    `n ≥ n₀`, `f(n) ≤ c · g(n)`.

    Read that again with the two quantifiers in mind, because they are the whole content:

    - **`n ≥ n₀`** — the claim is only about large inputs. Everything below `n₀` is exempt. This
      is why an algorithm's Big-O tells you nothing about how it behaves on your 20-element test.
    - **`c`** — you are allowed to pick any constant multiplier you like. This is why constant
      factors vanish, and why two implementations with a 20× performance gap can be honestly
      described by the same symbol.

    `Ω` flips the inequality (`f(n) ≥ c · g(n)`), and `Θ(g(n))` means both `O(g(n))` and
    `Ω(g(n))` hold — with possibly different constants.

    | Notation | Claim | Analogy |
    | --- | --- | --- |
    | `O(g)` | grows no faster than `g` | "at most" — like `≤` |
    | `Ω(g)` | grows at least as fast as `g` | "at least" — like `≥` |
    | `Θ(g)` | grows exactly like `g` | "the same as" — like `=` |
    | `o(g)` (little-o) | grows *strictly* slower than `g` | "less than" — like `&lt;` |

    Little-o shows up in one place you will care about: `n log n` is `o(n²)`, which is the
    formal way of saying the gap between merge sort and bubble sort widens without bound.

    ## Amortized analysis: deriving the doubling result

    Python's `list.append` is documented as O(1). That cannot be literally true — a list is a
    contiguous block of memory, and when it fills, appending requires allocating a bigger block
    and copying everything across, which is `O(n)`. The resolution is **amortized analysis**:
    the average cost per operation *over a sequence of operations*, which is a stronger and more
    useful claim than "average case over random inputs".

    ### The aggregate method

    Start with capacity 1 and double whenever full. Insert `n` items. The resizes happen at
    sizes 1, 2, 4, 8, …, up to the largest power of two `≤ n`. The total copying work is:

    ```
    1 + 2 + 4 + 8 + ... + 2^k    where 2^k ≤ n < 2^(k+1)
    = 2^(k+1) - 1
    < 2n
    ```

    So `n` appends do fewer than `2n` copies in total, plus `n` writes. Total work `&lt; 3n`,
    divided by `n` operations, is a constant. **Amortized O(1)**, proven, in four lines.

    The key move is the geometric series: because the resize sizes double, the *last* resize
    costs more than all previous resizes combined. Everything before it is a rounding error.

    ### The accounting method (the one to use in an interview)

    Charge 3 tokens for every append. One token pays for writing the new element. The other two
    go into a bank account attached to that element. When the array is full at size `n`, the
    `n/2` elements added since the last resize each have 2 banked tokens — that is `n` tokens,
    exactly enough to pay for copying all `n` elements. The bank never goes negative, therefore
    the real cost never exceeds 3 per operation, therefore amortized O(1). ∎

    ### Why the growth factor must be greater than 1

    ```python
    # growth_factor.py — how many total element-copies for n appends?
    def total_copies(n: int, factor: float, start: int = 1) -> int:
        cap, size, copies = start, 0, 0
        while size < n:
            if size == cap:
                cap = max(cap + 1, int(cap * factor))
                copies += size          # copy every existing element
            size += 1
        return copies

    for f in (1.0000001, 1.125, 1.25, 1.5, 2.0, 4.0):
        c = total_copies(1_000_000, f)
        print(f"factor {f:>9}:  {c:>12,} copies  ({c/1_000_000:.2f} per append)")
    ```

    ```
    factor 1.0000001:  499,999,500,000 copies  (499999.50 per append)
    factor     1.125:      8,681,481 copies  (8.68 per append)
    factor      1.25:      4,489,047 copies  (4.49 per append)
    factor       1.5:      2,099,753 copies  (2.10 per append)
    factor       2.0:      1,048,575 copies  (1.05 per append)
    factor       4.0:        349,525 copies  (0.35 per append)
    ```

    Growing by a *constant amount* (factor 1.0, i.e. `cap += 1`) gives 500 billion copies —
    quadratic. Any factor strictly greater than 1 gives a constant amortized cost. Larger
    factors do fewer copies but waste more memory: at factor 4 you can be holding 4× the memory
    you need. **CPython's `listobject.c` uses roughly 1.125** (`new_allocated = (newsize +
    (newsize >> 3) + 6) & ~3`), tuned for memory frugality on the many small lists a Python
    program creates. **Java's `ArrayList` uses 1.5. Go's slices use 2× below 256 elements, then
    decay toward 1.25.** Three good engineering teams, three different answers, because the
    trade-off is memory-versus-copies and the right point depends on your workload.

    ## Recurrence relations

    When an algorithm calls itself, write the cost as an equation in terms of itself.

    Merge sort: split in half, sort each half, merge in linear time.

    ```
    T(n) = 2·T(n/2) + Θ(n)
    ```

    ### Recursion tree method

    Draw the calls as a tree. At the root you do `n` work. Level 2 has two calls each doing
    `n/2` — total `n`. Level 3 has four calls each doing `n/4` — total `n`. **Every level does
    `n` work.** The tree has `log₂ n` levels because the problem halves each time. Total:
    `n · log₂ n`. Therefore `Θ(n log n)`.

    That "every level does n work" is the entire proof, and it is why the recursion tree method
    is worth 30 seconds on a whiteboard: you can see the answer before you compute it.

    ### The Master theorem

    For `T(n) = a·T(n/b) + f(n)` with `a ≥ 1`, `b > 1`, compare `f(n)` against
    `n^(log_b a)` — the total leaf work:

    | Case | Condition | Result | Reading |
    | --- | --- | --- | --- |
    | 1 | `f(n) = O(n^(log_b a − ε))` | `Θ(n^(log_b a))` | leaves dominate |
    | 2 | `f(n) = Θ(n^(log_b a))` | `Θ(n^(log_b a) · log n)` | every level equal |
    | 3 | `f(n) = Ω(n^(log_b a + ε))` and regularity holds | `Θ(f(n))` | root dominates |

    Worked, quickly:

    | Algorithm | Recurrence | `log_b a` | Case | Result |
    | --- | --- | --- | --- | --- |
    | Binary search | `T(n) = T(n/2) + Θ(1)` | `log₂1 = 0` | 2 | `Θ(log n)` |
    | Merge sort | `T(n) = 2T(n/2) + Θ(n)` | `log₂2 = 1` | 2 | `Θ(n log n)` |
    | Naive matrix multiply (blocked) | `T(n) = 8T(n/2) + Θ(n²)` | `log₂8 = 3` | 1 | `Θ(n³)` |
    | Strassen | `T(n) = 7T(n/2) + Θ(n²)` | `log₂7 ≈ 2.807` | 1 | `Θ(n^2.807)` |
    | Karatsuba multiply | `T(n) = 3T(n/2) + Θ(n)` | `log₂3 ≈ 1.585` | 1 | `Θ(n^1.585)` |

    The Strassen row is the one worth staring at. Reducing `a` from 8 to 7 — seven
    multiplications instead of eight, at the cost of more additions — changes the exponent from
    3.000 to 2.807. On a 4096×4096 matrix that is a factor of about 4.6 in theoretical
    operations. **This is the same structural move you will see in week 26 when a low-rank
    adapter replaces a full weight update: reduce the count of expensive sub-problems, accept
    more cheap arithmetic.**

    ## Trade-offs table

    | Situation | Choose | Instead of | Because |
    | --- | --- | --- | --- |
    | `n` is bounded and small (under ~50), code runs constantly | the simple `O(n²)` scan | a hash-based `O(n)` structure | building the hash set costs more than the scan saves; measure the crossover, don't assume it |
    | `n` is unbounded or user-controlled | the better asymptotic complexity, always | "it's fine at our current size" | user-controlled `n` is an availability risk, not a performance one |
    | Memory is the binding constraint | `O(n log n)` in-place (heapsort, introsort) | `O(n)` counting sort | counting sort's space is `O(range)`, which can be enormous for sparse keys |
    | You need worst-case guarantees (SLA, real-time) | merge sort / heapsort — `Θ(n log n)` always | quicksort — `O(n²)` worst case | a p99.9 latency SLA is a statement about the worst case, not the average |
    | Data is nearly sorted | Timsort (`list.sort()`) — `O(n)` on sorted runs | any textbook sort | Timsort detects existing runs; on already-sorted input it is linear |
    | You are inside a tight loop over a NumPy array | a vectorized expression | any Python-level algorithm | the constant factor difference is 50–200× (measured in week 16 M1), which beats most asymptotic wins at realistic `n` |

    ## Reference implementation: an empirical complexity classifier

    Theory tells you the shape. This tells you whether your code actually has that shape.

    ```python
    # empirical_complexity.py — CPython 3.12
    """Fit measured runtimes to a power law and report the observed exponent.

    If your code is O(n^k), then log(time) = k*log(n) + c, so the slope of a
    log-log fit IS the exponent. No numpy needed.
    """
    from __future__ import annotations
    import gc
    import math
    import time
    from typing import Callable, Sequence


    def measure(fn: Callable[[int], None], n: int, reps: int = 5) -> float:
        """Best-of-reps wall time in seconds. Best-of, not mean: see the note below."""
        best = math.inf
        for _ in range(reps):
            gc.collect()
            t0 = time.perf_counter()
            fn(n)
            best = min(best, time.perf_counter() - t0)
        return best


    def fit_exponent(sizes: Sequence[int], times: Sequence[float]) -> tuple[float, float]:
        """Least-squares slope and intercept of log(time) vs log(n)."""
        xs = [math.log(n) for n in sizes]
        ys = [math.log(t) for t in times]
        k = len(xs)
        mx, my = sum(xs) / k, sum(ys) / k
        num = sum((x - mx) * (y - my) for x, y in zip(xs, ys))
        den = sum((x - mx) ** 2 for x in xs)
        slope = num / den
        return slope, my - slope * mx


    def classify(slope: float) -> str:
        """Map an observed exponent to the nearest familiar shape."""
        for bound, name in ((0.15, "O(1) or O(log n)"),
                            (0.75, "sub-linear"),
                            (1.15, "O(n)"),
                            (1.45, "O(n log n)"),
                            (2.30, "O(n^2)"),
                            (3.30, "O(n^3)")):
            if slope < bound:
                return name
        return f"worse than cubic (exponent {slope:.2f})"


    def profile(name: str, fn: Callable[[int], None], sizes: Sequence[int]) -> None:
        times = [measure(fn, n) for n in sizes]
        slope, _ = fit_exponent(sizes, times)
        print(f"{name:<28} exponent={slope:5.2f}  ->  {classify(slope)}")
        for n, t in zip(sizes, times):
            print(f"    n={n:>8,}  {t * 1e3:9.3f} ms")


    if __name__ == "__main__":
        SIZES = (1_000, 4_000, 16_000, 64_000)

        def linear_scan(n: int) -> None:
            data = list(range(n))
            _ = sum(data)

        def quadratic_membership(n: int) -> None:
            a = list(range(n))
            b = list(range(n))
            _ = sum(1 for x in a if x in b)     # x in b is a scan: n * n

        def linear_membership(n: int) -> None:
            a = list(range(n))
            b = set(range(n))
            _ = sum(1 for x in a if x in b)     # x in b is a hash: n * 1

        def sort_it(n: int) -> None:
            import random
            data = [random.random() for _ in range(n)]
            data.sort()

        profile("linear scan", linear_scan, SIZES)
        profile("membership in list", quadratic_membership, SIZES)
        profile("membership in set", linear_membership, SIZES)
        profile("list.sort (Timsort)", sort_it, SIZES)
    ```

    Measured output on the reference machine (M3 Pro, CPython 3.12.9):

    ```
    linear scan                  exponent= 1.21  ->  O(n log n)
        n=   1,000      0.012 ms
        n=   4,000      0.043 ms
        n=  16,000      0.285 ms
        n=  64,000      1.644 ms
    membership in list           exponent= 1.91  ->  O(n^2)
        n=   1,000      2.945 ms
        n=   4,000     50.319 ms
        n=  16,000    574.165 ms
        n=  64,000   9010.628 ms
    membership in set            exponent= 1.04  ->  O(n)
        n=   1,000      0.045 ms
        n=   4,000      0.173 ms
        n=  16,000      0.724 ms
        n=  64,000      3.438 ms
    list.sort (Timsort)          exponent= 1.16  ->  O(n log n)
        n=   1,000      0.095 ms
        n=   4,000      0.486 ms
        n=  16,000      2.376 ms
        n=  64,000     11.675 ms
    ```

    Four things to notice, and the **first one is that the tool got an answer wrong**.

    1. **`linear scan` — a `sum()` over a list — is reported as `O(n log n)`.** It is `O(n)`. The
       fitted exponent came back as 1.21 because the measurement is contaminated: at n = 1,000 the
       list is 8 KB and lives in L1, at n = 64,000 it is 512 KB plus a million-odd int objects
       scattered across the heap, so the per-element cost genuinely rises with `n`. The algorithm
       is linear; the *machine* is not. **A tool that classifies complexity from wall-clock time is
       measuring the algorithm and the memory hierarchy together and cannot separate them.**
       I am leaving the wrong answer in rather than widening the sweep until it looks right,
       because this is the honest limitation and it is more useful than a clean table.
    2. **The quadratic version comes back as 1.91, not 2.00.** Close enough to be unambiguous —
       and note that if 1.21 can mean "linear", the classifier's thresholds are doing a lot of
       work. Treat the exponent as evidence, not as a verdict.
    3. **At n = 64,000, list membership takes 9.01 seconds and set membership takes 3.44
       milliseconds — a factor of 2,621×.** That is a one-line change: `b = set(b)`.
    4. **Timsort measures 1.16, which lands in the `O(n log n)` bucket, but partly by luck.**
       Over a 64× range of `n`, `log₂ n` only moves from 10 to 16 — a factor of 1.6 while `n` moves
       by 64. A log factor is nearly invisible in a log-log fit over a narrow range. Given that a
       genuinely linear scan measured 1.21 here, you should not trust this tool to distinguish
       `O(n)` from `O(n log n)` at all. **That is the honest limitation of empirical complexity
       fitting, and it is why you still need the theory.**

    ## War story: the `in` that cost a quarter of a million dollars

    A telemetry ingestion service at a mid-size SaaS company received batches of up to 50,000
    events. Each batch was deduplicated against the IDs already seen in that batch:

    ```python
    seen = []
    for event in batch:
        if event.id not in seen:      # O(len(seen)) — a list scan
            seen.append(event.id)
            emit(event)
    ```

    This shipped and ran fine for fourteen months. Typical batches were 200–400 events, so
    `seen` was small, the scan was cheap, and nothing showed up in any dashboard.

    Then a customer onboarded a fleet of IoT devices that buffered while offline and flushed on
    reconnect. Batch sizes jumped to 45,000. The dedup loop went from ~80,000 comparisons to
    ~1.01 *billion*. Per-batch processing went from 12 ms to 41 seconds. The consumer's poll
    interval was 30 seconds, so Kafka rebalanced the consumer group mid-batch; the batch was
    redelivered to a different consumer, which also took 41 seconds, and also got rebalanced.
    **The system never made forward progress.** Four hours of downtime, a stuck partition, and
    a duplicate-billing incident downstream because some events were emitted before each
    rebalance.

    The fix was `seen = set()`. One word. It went out in a hotfix eleven minutes after the
    engineer looked at the loop.

    The lessons that generalise:

    - **The bug was written in a code review that passed.** `if x not in seen` reads like
      English. Big-O is invisible in readable code, which is exactly why you have to look for it
      deliberately.
    - **The failure was in the tail, not the mean.** p50 batch size never changed. The dashboard
      that mattered would have been p99 batch size, and nobody had it.
    - **The blast radius was not the slow function.** It was the consumer-group rebalance loop
      the slow function triggered. Quadratic code inside a system with a timeout does not
      degrade — it collapses.

    <Warning>
    Add this to your review checklist: **any membership test inside a loop, and any string
    concatenation inside a loop.** Those two patterns account for most accidentally-quadratic
    Python I have seen in production.
    </Warning>

    ### Design checkpoint

    <Accordion title="You maintain a service that assembles a response from up to N upstream items. Product wants to raise the per-request cap from 100 to 10,000. What do you check before saying yes?">
    **Model answer.** Find every place where `N` appears in a loop bound, and the complexity of
    each.

    1. **Grep for nested iteration over the item collection.** A 100× increase in `N` is a
       10,000× increase in any `O(N²)` section. At `N=100`, a quadratic section doing 10,000
       cheap operations is invisible (sub-millisecond). At `N=10,000` it is 100 million
       operations — tens of seconds in Python.
    2. **Check membership tests, `list.remove`, `list.index`, `del list[0]`, `list.insert(0, x)`
       and string `+=`.** All of these are `O(N)` in a place that looks `O(1)`.
    3. **Check space, not just time.** If each item holds a 4 KB payload, `N=10,000` is 40 MB
       per in-flight request. At 50 concurrent requests that is 2 GB, and your container limit
       is probably 1 GB. **The complexity bug that kills you here is space, and it presents as
       an OOMKill, not as latency.**
    4. **Check the serialization boundary.** JSON-encoding 10,000 items is linear but with a
       large constant, and it happens on the event loop thread.
    5. **Then measure, don't argue.** Run the real handler at N = 100, 1,000, 10,000 and fit the
       exponent with the tool above. If the exponent is above 1.3, you have a specific thing to
       fix before you can say yes.

    The answer to give product is not "no". It is: "yes at 10,000 once the dedup path is
    hash-based and we've raised the memory limit — here are the two numbers."

    ## Where Big-O lies: three distinct failures

    Big-O is a statement about the limit as `n → ∞`, made in a model where every operation costs
    the same. Both halves of that sentence are false about real computers, in three separate ways.

    ### Lie 1: the memory hierarchy makes operations cost wildly different amounts

    The RAM model that Big-O assumes says accessing `a[0]` and `a[999999]` cost the same. On the
    M3 Pro reference machine they differ by roughly 80×, because one is an L1 hit (~4 cycles,
    about 1 ns) and one may be a DRAM access (~80–100 ns). Week 9's memory-hierarchy module
    measured this directly; here is what it does to an algorithm with an *identical* Big-O.

    Traversing `n` elements, three ways, all `Θ(n)`:

    | `n` | Python list (contiguous) | Linked list, nodes allocated in order | Linked list, nodes shuffled | shuffled ÷ list |
    | --- | --- | --- | --- | --- |
    | 1,000 | 0.016 ms | 0.015 ms | 0.022 ms | **1.3×** |
    | 10,000 | 0.129 ms | 0.290 ms | 0.185 ms | **1.4×** |
    | 100,000 | 2.203 ms | 2.811 ms | 32.930 ms | **14.9×** |
    | 1,000,000 | 32.577 ms | 111.785 ms | 661.008 ms | **20.3×** |

    <Info>
    Method: CPython 3.12.9, M3 Pro, best-of-5, `gc.disable()` during each timed section and each
    structure built and freed in isolation so the three cases never coexist in memory. Nodes use
    `__slots__` (56 bytes each) so the linked list is as favourable as pure Python allows.
    Reproduce with `dsa_suite.py w13m1` from the lab repo.
    </Info>

    Read the table carefully, including the row that misbehaves.

    - **At n=1,000 all three are identical.** 1,000 nodes × 56 bytes is 56 KB; the M3 Pro's L2 is
      16 MB. Everything is in cache, so pointer-chasing is free. **Below the cache size, Big-O is
      the whole truth.**
    - **At n=10,000 the sequential linked list measures *slower* than the shuffled one** (0.290
      vs 0.185 ms). That is backwards, and it is noise — the two allocations landed differently
      and the gap is under 0.1 ms on a shared machine. I am leaving it in the table rather than
      re-rolling until it looks tidy, because this is what real measurement looks like and the
      instinct to quietly delete the inconvenient row is the instinct that produces fraudulent
      benchmarks. The signal starts at 100,000 and is unambiguous at 1,000,000.
    - **At n=1,000,000 the shuffled list is 20.3× slower than the array** for the same `Θ(n)`
      work. 1M nodes × 56 bytes = 56 MB, comfortably past L2, so nearly every `c = c.nxt`
      is a cache miss with no possible prefetch — the address of the next node is only known
      after the current one arrives.
    - **The sequentially-allocated list is still 3.4× slower than the array** at 1M. Even in
      allocation order, each node is a separate object with a header, so you touch 56 bytes of
      cache line to read 8 bytes of payload, and CPython's pointer indirection defeats the
      hardware prefetcher's stride detection.

    The practical rule: **`Θ(n)` over contiguous memory and `Θ(n)` over pointers are different
    algorithms**, and the gap grows with `n` rather than staying constant. This is the single
    biggest reason `collections.deque` (an array of 64-element blocks) beats a textbook doubly
    linked list, and it is why `numpy` exists.

    ### Lie 2: the crossover point is often inside the range you care about

    Big-O guarantees the better algorithm wins *eventually*. Production systems live at specific
    finite `n`, and "eventually" can be past your entire input range.

    CPython's `list.sort()` is Timsort, and `Objects/listobject.c` contains this:

    ```c
    /* If the list is small, just do a binary insertion sort. */
    #define MIN_GALLOP 7
    /* ... */
    if (nremaining < MIN_MERGE) {          /* MIN_MERGE == 64 */
        Py_ssize_t force = nremaining;
        binarysort(&ms, &lo, force);
        ...
    }
    ```

    Below 64 elements, CPython does not use merge sort at all. It uses binary insertion sort —
    `O(n²)` in the number of *moves*. The authors of the standard library measured the crossover
    and chose the asymptotically worse algorithm below it, because insertion sort has no
    recursion, no merge buffer allocation and perfect locality. Introsort in libstdc++ makes the
    same call at a threshold of 16.

    Where else this bites, with the thresholds:

    | Pair | Crossover (order of magnitude) | Why |
    | --- | --- | --- |
    | Insertion sort vs merge sort | ~16–64 elements | recursion + allocation overhead |
    | Linear scan vs hash set | ~15–30 elements | hashing a key costs 30–80 ns; comparing an int costs ~5 ns |
    | Naive `n³` matmul vs Strassen | ~500–1000 per dimension | Strassen's 18 additions and temporaries |
    | Brute-force k-NN vs an HNSW index | ~10⁴–10⁵ vectors | index build cost + graph traversal overhead; **you will measure this exact crossover in week 27** |
    | `dict` vs a sorted list + bisect | ~8–16 keys | hash table has a fixed allocation and per-lookup hashing cost |

    That HNSW row is the one to remember. In week 27 you will be tempted to reach for a vector
    index on a 5,000-document corpus. Brute-force cosine similarity over 5,000 × 768-dim float32
    vectors is a single 15 MB matrix multiply — roughly 3 ms with NumPy on this machine. An HNSW
    index over the same corpus costs seconds to build, adds a dependency, and gives approximate
    answers. **The `O(log n)` structure is the wrong choice, and you will only know that because
    you learned to look for the crossover here.**

    ### Lie 3: amortized is not worst-case, and sometimes the worst case is what ships

    `list.append` is amortized `O(1)`, and the *individual* append that triggers a resize of a
    1-million-element list copies 1 million pointers — about 8 MB of memcpy, a few milliseconds.
    Amortized analysis says this averages out. Your p99.9 latency SLA does not average out.

    This is a real class of production incident:

    - **Go's map growth** is incremental precisely to avoid this — Go rehashes a few buckets per
      operation rather than all at once, trading throughput for tail latency.
    - **Redis** rehashes its dict incrementally for the same reason, moving one bucket per command.
    - **The JVM's `ArrayList`** does not, so a single `add()` on a large list can pause.

    If you are writing a latency-sensitive path, pre-size your containers. `[None] * n` and
    `dict` comprehension from a known-size iterable both skip the growth sequence entirely.

    ## Cost and latency math

    Turn complexity into money. Take a request handler doing an `O(n²)` dedup on `n` items,
    at 5 ns per comparison (a realistic optimistic figure for an int comparison in a tight
    CPython loop it is closer to 40 ns, but use 5 ns for the C-speed case):

    | `n` | comparisons `n²/2` | time at 40 ns/cmp | at 1,000 req/s, CPU-seconds/s | vCPUs needed |
    | --- | --- | --- | --- | --- |
    | 100 | 5,000 | 0.2 ms | 0.2 | 1 |
    | 1,000 | 500,000 | 20 ms | 20 | 20 |
    | 10,000 | 50,000,000 | 2.0 s | 2,000 | 2,000 |

    At `n = 10,000` you would need roughly 2,000 vCPUs to hold 1,000 req/s. On AWS at roughly
    $0.04 per vCPU-hour for c7g on-demand, that is about **$58,000/month** to run a loop that
    the hash-set version runs on **one** vCPU for about $29/month. The `O(n)` version's arithmetic:
    10,000 hash operations at 60 ns is 0.6 ms per request, 0.6 CPU-seconds per second at 1,000
    req/s — one core with headroom.

    **Complexity analysis is capacity planning.** That is the sentence to take into a design review.

    ## Production failure modes and their signatures

    | Failure mode | Signature in your telemetry | How to detect before it fires |
    | --- | --- | --- |
    | Accidental quadratic in a request path | latency vs input-size plot bends upward; p99 diverges from p50 while p50 stays flat | plot latency against payload size, not against time. This one chart finds most of them. |
    | Amortized resize spike | periodic latency spikes at powers of two of the collection size | histogram of latency, not average; look for a small mode far to the right |
    | Algorithmic complexity DoS | a small number of requests consume most CPU; attacker-controlled input size or structure | fuzz with adversarial inputs (sorted, all-equal, collision-crafted keys) in CI |
    | Space complexity blowup | OOMKill with no memory leak; RSS proportional to concurrent requests × input size | load-test at max documented input size × max concurrency, not at typical values |
    | Cache-hostile data layout | CPU-bound with low IPC (below 1.0) and high cache-miss rate in `perf stat` | measure IPC; a pointer-chasing loop shows IPC around 0.3 |

    <Tip>
    The single highest-value dashboard in this list is **latency against input size** as a
    scatter plot. Time-series latency graphs hide quadratic behaviour completely, because they
    average over a mix of input sizes. A scatter of (payload size, duration) makes the curve
    visible immediately, and the shape of the cloud tells you the exponent.
    </Tip>

    ## Frontier and research pointers

    - **Bentley, Haken & Saxe (1980), "A general method for solving divide-and-conquer
      recurrences."** *SIGACT News* 12(3). — **Takeaway:** the Master theorem as you use it today,
      including the regularity condition in case 3 that most textbook summaries silently drop.
    - **Crosby & Wallach (2003), "Denial of Service via Algorithmic Complexity Attacks."**
      USENIX Security. — **Takeaway:** an attacker who can choose your hash keys can force every
      insert into one bucket, turning an `O(1)` hash table into an `O(n)` list and a web server
      into a brick with a few kilobytes of traffic; this paper is why Python 3.3+ randomises
      `str` hashing by default.
    - **Aggarwal & Vitter (1988), "The Input/Output Complexity of Sorting and Related Problems."**
      *CACM* 31(9). — **Takeaway:** when data does not fit in memory, the right cost model counts
      block transfers rather than comparisons, giving the `Θ((N/B)·log_{M/B}(N/B))` bound that
      external merge sort achieves — the reason database sorts and Spark shuffles are designed
      the way they are.
    - **Frigo, Leiserson, Prokop & Ramachandran (1999), "Cache-Oblivious Algorithms."** FOCS. —
      **Takeaway:** you can design algorithms that are asymptotically optimal for *every* level
      of an unknown memory hierarchy simultaneously, without ever naming a cache size; this is
      why recursive blocked layouts (van Emde Boas trees, recursive matmul) beat flat ones.
    - **Peters (2002), the Timsort listsort.txt design note** in CPython's source tree. —
      **Takeaway:** the best sorting algorithm for real data is the one that exploits the runs
      real data already contains, and the write-up is a masterclass in choosing an algorithm by
      measuring your actual inputs rather than by reading an asymptotic table.

    ## Stretch challenge

    Build a **regression detector for algorithmic complexity** and wire it into CI.

    The target: given a function and a size-generator, it runs the function across a geometric
    sweep of `n`, fits the exponent, and fails the build if the exponent has moved by more than
    a threshold since the recorded baseline. This is a real and underused piece of engineering —
    it catches the class of bug in the war story above *at the pull request*, not in production.

    Hard parts you will have to make decisions about, none of which have one right answer:

    1. **Noise.** Best-of-N helps but CI runners are noisy neighbours on shared hardware. Do you
       use operation *counts* (via `sys.settrace` or a counting wrapper — deterministic but slow
       and intrusive) instead of wall time? Do you measure both and require them to agree?
    2. **Range.** You saw that a log-log fit cannot separate `O(n)` from `O(n log n)` over a 64×
       range. How wide does the sweep have to be, and how long can a CI job afford to run?
    3. **What counts as a regression?** An exponent moving 1.02 → 1.09 is noise. 1.02 → 1.55 is
       a real change. Where do you draw the line, and how do you avoid a flaky test that
       everyone learns to re-run?
    4. **Superlinear-but-not-power-law.** `O(n log n)` and `O(n^1.1)` are nearly indistinguishable
       empirically. Is fitting `a·n^k` the right model, or should you fit `a·n·log(n) + b·n + c`
       and compare residuals across candidate models by AIC?
    5. **Reporting.** A failed build that says "exponent regressed" is useless. What does the
       failure message have to contain for the author to fix it in five minutes?

    Ship it as a `pytest` plugin. If you get it working, it belongs on your GitHub profile — very
    few engineers have written one and every team that has a performance incident wishes they had.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Function is "O(n)" but latency quadruples when input doubles | `x in some_list` or `list.index()` inside the loop — a hidden `O(n)` scan | Build a `set` or `dict` once outside the loop; membership becomes `O(1)` |
| Building a string in a loop is fast in tests, slow in prod | CPython's in-place `str +=` optimisation fires when refcount is 1, and stops firing when the string is also referenced elsewhere | Use `"".join(parts)` or `io.StringIO`; never rely on the refcount optimisation |
| Periodic latency spikes with no matching traffic spike | Amortized container resize copying the whole backing array | Pre-size: `[None] * n`, `dict.fromkeys(...)`, or `set(iterable)` in one call |
| Empirical exponent comes back as 1.05 for code you know is `O(n log n)` | The log factor moves by 1.6× while `n` moves by 64× — invisible in a narrow log-log fit | Widen the sweep by 3+ orders of magnitude, or fit and compare candidate models rather than a single power law |
| Algorithm with better Big-O is slower in production | You are below the crossover point; the constant factor dominates at your real `n` | Measure at your actual `n`. Keep both implementations and switch on size, the way `list.sort()` does at 64 |
| OOMKill under load with no memory leak | Space complexity is `O(n)` per request and concurrency multiplies it | Load-test at documented max input × max concurrency; bound `n` at the edge |
| `O(n²)` code passes all tests and all load tests | Tests use realistic-median inputs; the quadratic only shows at the tail | Property-test with adversarial sizes; assert on the *shape*, not on a fixed latency threshold |
| Recursion is `O(log n)` in time but crashes | Space complexity of the call stack was never analysed; CPython's default limit is 1000 frames | Analyse stack depth as space; convert to iteration or raise the limit deliberately with a comment |

## Sources & further reading

**Primary docs**

- [CPython `Objects/listobject.c`](https://github.com/python/cpython/blob/v3.12.9/Objects/listobject.c) (tag `v3.12.9`) — read this for the actual growth formula (`newsize + (newsize >> 3) + 6`) and the `MIN_MERGE == 64` threshold below which Timsort abandons merge sort for binary insertion sort.
- [CPython `Objects/listsort.txt`](https://github.com/python/cpython/blob/v3.12.9/Objects/listsort.txt) — Tim Peters' design note for Timsort. Read this for how an algorithm gets chosen by measuring real inputs rather than by consulting an asymptotic table.
- [Python `TimeComplexity` wiki page](https://wiki.python.org/moin/TimeComplexity) — read this for the per-operation table of `list`, `deque`, `dict` and `set` costs; it is the reference you will actually reach for, and it is where you confirm that `list.pop(0)` is `O(n)`.
- [`time.perf_counter` documentation](https://docs.python.org/3.12/library/time.html#time.perf_counter) — read this for why it, not `time.time()`, is the correct clock for benchmarking (monotonic, highest available resolution, includes sleep).

**Papers**

- [Bentley, Haken & Saxe (1980), *A general method for solving divide-and-conquer recurrences*, SIGACT News 12(3), 36–44.](https://doi.org/10.1145/1008861.1008865) — **Takeaway:** the Master theorem in its original form, including the regularity condition in case 3 that popular summaries drop and that is exactly the condition a real recurrence tends to violate.
- [Crosby & Wallach (2003), *Denial of Service via Algorithmic Complexity Attacks*, USENIX Security Symposium.](https://www.usenix.org/conference/12th-usenix-security-symposium/denial-service-algorithmic-complexity-attacks) — **Takeaway:** worst-case complexity is a security property, not a performance footnote; an attacker choosing inputs can move you from your average case to your worst case at will.
- [Aggarwal & Vitter (1988), *The Input/Output Complexity of Sorting and Related Problems*, CACM 31(9), 1116–1127.](https://doi.org/10.1145/48529.48535) — **Takeaway:** once data exceeds memory the correct unit of cost is the block transfer, not the comparison, and the optimal bound changes shape entirely.
- [Frigo, Leiserson, Prokop & Ramachandran (1999), *Cache-Oblivious Algorithms*, FOCS.](https://doi.org/10.1109/SFFCS.1999.814600) — **Takeaway:** recursive divide-and-conquer layouts achieve optimal cache behaviour at every level of the hierarchy without knowing any cache's size, which is why recursive blocking beats hand-tuned tiling across machines you have never seen.

**Go deeper**

- Cormen, Leiserson, Rivest & Stein, *Introduction to Algorithms*, 4th ed., **Chapter 4 (Divide-and-Conquer)** — the substitution, recursion-tree and master methods worked properly, with the proofs. Read chapter 4 specifically; it is the one chapter of CLRS that pays for itself immediately.
- [Sedgewick & Wayne, *Algorithms*, 4th ed., **Section 1.4 (Analysis of Algorithms)**](https://algs4.cs.princeton.edu/home/) — the doubling-ratio experiment, which is the empirical technique in this module's reference implementation, explained better than I have explained it.

Read it for the mechanism behind Lie 1: it is the document that turns "cache miss" from a phrase into a model you can predict with.
