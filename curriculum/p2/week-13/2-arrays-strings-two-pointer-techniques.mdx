    ## The idea in one paragraph

    An **array** stores items side by side in one block of memory. Because they are side by side,
    the computer can jump to item number `i` with one multiplication — that is why `lst[500000]`
    is instant. Most array problems that look like they need two nested loops actually need one
    loop plus a bit of bookkeeping. The three techniques in this module — **prefix sums**, **two
    pointers**, and the **sliding window** — are all the same underlying trick: *do not recompute
    what you already know*. They turn O(n²) into O(n), and they cover a startling fraction of the
    array and string problems you will ever be asked.

    ### The analogy

    You are a shopkeeper and someone asks: "how much did we take between Tuesday and Friday?"

    - **Naive.** Get the ledger, find Tuesday, add up every day until Friday. If they ask a
      hundred such questions, you do a hundred additions-from-scratch.
    - **Prefix sums.** Once, at the start of the day, you write a second column: "total taken from
      the start of the year up to and including this day." Now "Tuesday to Friday" is
      `total_through_Friday − total_through_Monday`. **One subtraction, any range.** You paid a
      single pass through the ledger to make every future question free.

    That is the entire idea. Precompute once, answer forever.

    ### Every term, defined

    - **Array** — a fixed block of memory holding items of the same size, side by side. Python's
      `list` is a *dynamic array*: an array plus automatic resizing.
    - **Index** — the position of an item, counting from 0. `lst[0]` is the first item.
    - **Contiguous** — stored with no gaps. This is what makes `lst[i]` a single address
      calculation: `start + i × 8` for a Python list of pointers.
    - **In place** — modifying the original array rather than building a new one. Uses O(1) extra
      space.
    - **Prefix sum** — an array `P` where `P[i]` is the sum of the first `i` items of the original.
      Note `P` has length `n+1`, with `P[0] = 0`; that extra zero is what removes every
      off-by-one.
    - **Two pointers** — two indices moving through the array under some rule, usually toward each
      other or both forward.
    - **Sliding window** — a contiguous stretch of the array, `arr[left:right+1]`, that you grow
      and shrink instead of rebuilding.
    - **Immutable** — cannot be changed after creation. Python strings are immutable; every
      "modification" builds a brand-new string.

    ### The smallest working example

    ```python
    # prefix.py — CPython 3.12
    sales = [120, 80, 200, 50, 300, 90, 60]   # Mon..Sun

    # Build the prefix array. P[i] = sum of the first i days.
    P = [0] * (len(sales) + 1)
    for i, amount in enumerate(sales):
        P[i + 1] = P[i] + amount
    print(P)          # [0, 120, 200, 400, 450, 750, 840, 900]

    # Any range sum, in one subtraction. Days i..j inclusive:
    def range_sum(i, j):
        return P[j + 1] - P[i]

    print(range_sum(1, 4))    # Tue..Fri: 80+200+50+300 = 630
    print(P[5] - P[1])        # the same subtraction, written out: 750 - 120 = 630
    print(range_sum(0, 6))    # the whole week: 900
    print(range_sum(3, 3))    # one single day: 50
    ```

    ### Line-by-line walkthrough

    - `P = [0] * (len(sales) + 1)` — one longer than the data, and starting with a zero. That
      leading zero is not decoration: it is what makes `range_sum(0, j)` work without a special
      case for "the range starts at the beginning".
    - `P[i + 1] = P[i] + amount` — each entry is the previous total plus today. One pass, O(n).
      **This is the only loop in the whole technique.**
    - `return P[j + 1] - P[i]` — `P[j+1]` is everything through day `j`; `P[i]` is everything
      before day `i`. Subtract and the overlap cancels, leaving exactly days `i` through `j`.
    - `range_sum(3, 3)` returns 50 — a single-element range works, which is the case that breaks
      most hand-written off-by-one versions. Test it first, every time.

    Cost: **O(n) once to build, then O(1) per query, forever.** With 2,000 queries on a
    100,000-element array, measured on the reference machine: recomputing each sum takes 503.8 ms;
    building the prefix array takes 8.1 ms and then answering all 2,000 queries takes 2.16 ms.
    That is **233× faster**, and the gap widens with the array size.

    ### Two pointers

    Problem: given a **sorted** array, find two numbers that add to a target.

    ```python
    def two_sum_sorted(nums: list[int], target: int) -> tuple[int, int] | None:
        """nums must be sorted ascending. Returns the two INDICES, or None."""
        left, right = 0, len(nums) - 1
        while left < right:
            current = nums[left] + nums[right]
            if current == target:
                return (left, right)
            elif current < target:
                left += 1        # need a bigger sum -> move the small end up
            else:
                right -= 1       # need a smaller sum -> move the big end down
        return None

    print(two_sum_sorted([1, 3, 4, 6, 8, 11], 10))   # (1, 4)  -> 3 + 8
    print(two_sum_sorted([1, 3, 4, 6, 8, 11], 100))  # None
    ```

    **Why it is correct**, which is the part that matters: because the array is sorted, if
    `nums[left] + nums[right]` is too small, then `nums[left]` paired with *anything* at or below
    `right` is also too small — so `left` can never be part of the answer with any remaining
    partner, and discarding it loses nothing. Symmetrically for `right`. Each step eliminates a
    whole row or column of the possibility space, and the pointers meet after at most `n` steps.
    O(n) time, O(1) space, versus O(n²) for the double loop.

    ### The sliding window template

    This one template, memorised, solves a whole class of problems:

    ```python
    def longest_substring_without_repeats(s: str) -> int:
        """Length of the longest stretch with no repeated character."""
        last_seen: dict[str, int] = {}
        left = 0
        best = 0
        for right, ch in enumerate(s):
            # If ch is already inside the window, jump left past its last position.
            if ch in last_seen and last_seen[ch] >= left:
                left = last_seen[ch] + 1
            last_seen[ch] = right
            best = max(best, right - left + 1)
        return best

    print(longest_substring_without_repeats("abcabcbb"))   # 3  ("abc")
    print(longest_substring_without_repeats("bbbbb"))      # 1  ("b")
    print(longest_substring_without_repeats("pwwkew"))     # 3  ("wke")
    ```

    The shape is always: **`right` advances every iteration; `left` advances only when the window
    becomes invalid; neither ever moves backward.** Because each pointer moves at most `n` times
    total, the whole thing is O(n) even though there is a loop inside a loop in the general
    version. That argument — "each pointer only moves forward, so total work is 2n" — is the one
    to say out loud in an interview.

    <Warning>
    `last_seen[ch] >= left` is the condition that beginners drop, and the code still passes the
    easy tests. Without it, a character seen *before* the current window drags `left` backward,
    which both gives wrong answers and breaks the O(n) argument. Test with `"abba"` — the correct
    answer is 2, and the buggy version returns 3.
    </Warning>

    ### In-place manipulation

    ```python
    def reverse_in_place(a: list) -> None:
        """O(1) extra space. Modifies a; returns nothing (like list.sort)."""
        i, j = 0, len(a) - 1
        while i < j:
            a[i], a[j] = a[j], a[i]
            i += 1
            j -= 1

    xs = [1, 2, 3, 4, 5]
    reverse_in_place(xs)
    print(xs)          # [5, 4, 3, 2, 1]
    ```

    `a[i], a[j] = a[j], a[i]` swaps without a temporary variable because Python evaluates the
    entire right-hand side into a tuple first, *then* unpacks it. Two pointers again: they start
    at the ends and walk toward each other, and the loop ends when they meet.

    ### The string trap

    ```python
    # SLOW — O(n^2) in total characters
    out = ""
    for word in words:
        out += word          # builds a whole new string each time

    # FAST — O(total characters)
    out = "".join(words)
    ```

    Python strings are **immutable**. `out += word` cannot extend `out`; it allocates a new string
    and copies both operands into it. Doing that `n` times copies 1, then 2, then 3… characters —
    quadratic. `"".join` computes the total length once, allocates once, and copies each character
    exactly once.

    ### Checkpoint — 5 questions before you continue

    <AccordionGroup>
      <Accordion title="1. Why is the prefix array length n+1 instead of n?">
        So `P[0] = 0` can mean "the sum of nothing". That lets `sum(i..j) = P[j+1] - P[i]` work for
        every `i` including 0, with no special case. If you make it length `n` you will write an
        `if i == 0` branch, and that branch is where the off-by-one lives.
      </Accordion>
      <Accordion title="2. Why does the two-pointer two-sum require a sorted array?">
        Because the decision "move left up or move right down" depends on knowing that everything
        left of `left` is smaller and everything right of `right` is larger. Without sorted order
        that inference is invalid and you can discard the actual answer. On unsorted data, use a
        hash set instead: one pass, O(n) time and O(n) space.
      </Accordion>
      <Accordion title="3. A sliding window has a loop inside a loop. Why is it O(n) and not O(n²)?">
        Because `left` never moves backward. Across the entire run, `right` advances exactly `n`
        times and `left` advances at most `n` times, so the total number of pointer moves is at
        most `2n` regardless of how the inner loop is nested. Amortized argument, not a
        loop-counting argument — which is why loop-counting gives the wrong answer here.
      </Accordion>
      <Accordion title="4. What does `a[i], a[j] = a[j], a[i]` actually do?">
        Python evaluates the right-hand side completely first, building the tuple `(a[j], a[i])`
        from the current values, and only then assigns to the targets left to right. So no
        temporary variable is needed and the order of assignment cannot corrupt the values.
      </Accordion>
      <Accordion title="5. `len('café') == len('café')` is False in some editors. Why?">
        One is the single code point U+00E9 (é), the other is `e` followed by the combining acute
        accent U+0301 — two code points that *render* identically. Python compares code points, so
        the strings are unequal and their lengths differ. `unicodedata.normalize("NFC", s)` puts
        both into the same canonical form. This is the bug that makes a user's name fail to match
        itself, and it is three lines to prevent.
      </Accordion>

    ## Dynamic arrays: what `list` actually is

    A CPython `list` is a `PyListObject` holding a pointer to a separately-allocated array of
    `PyObject*`, plus `ob_size` (how many are used) and `allocated` (how many slots exist). Two
    consequences you will feel:

    - **The list stores pointers, not values.** `[1, 2, 3]` is three 8-byte pointers to three
      separately allocated int objects. That is 8 bytes per slot plus 28 bytes per small int, and
      it is why a NumPy array of a million int64s is 8 MB while a Python list of the same is about
      36 MB.
    - **`ob_size < allocated` most of the time.** The spare capacity is what makes `append` O(1),
      and `sys.getsizeof` shows you the allocated size, not the used one.

    ```python
    import sys
    xs = []
    prev = None
    for i in range(20):
        size = sys.getsizeof(xs)
        if size != prev:
            print(f"len={len(xs):3d}  {size} bytes")
            prev = size
        xs.append(i)
    ```

    ```
    len=  0  56 bytes
    len=  1  88 bytes
    len=  5  120 bytes
    len=  9  184 bytes
    len= 17  248 bytes
    ```

    The jumps are the reallocations. CPython's `list_resize` in `Objects/listobject.c`:

    ```c
    new_allocated = ((size_t)newsize + (newsize >> 3) + 6) & ~(size_t)3;
    ```

    That is roughly **1.125×** growth (`newsize >> 3` is `newsize / 8`), plus 6, rounded down to a
    multiple of 4. Compare: Java's `ArrayList` grows 1.5×, Go's slices grow 2× under 256 elements
    then decay toward 1.25×, and C++ `std::vector` is 2× on libstdc++ and 1.5× on MSVC. A smaller
    factor wastes less memory and does more copies; CPython optimises for memory because Python
    programs create enormous numbers of small lists.

    <Tip>
    If you know the final size, pre-allocate. `[None] * n` does one allocation instead of ~`log_1.125(n)`
    reallocations plus copies. For `n = 1,000,000` that is 1 allocation instead of roughly 60, and
    about 1.05 element-copies per append avoided.
    </Tip>

    ## The sliding-window template, generalised

    Almost every window problem is one of two shapes. Learn both and you stop re-deriving them.

    **Shape A — fixed size `k`.** The window never changes size; you add one and drop one.

    ```python
    window = initial_state(nums[:k])
    best = evaluate(window)
    for right in range(k, len(nums)):
        add(window, nums[right])
        remove(window, nums[right - k])
        best = better(best, evaluate(window))
    ```

    **Shape B — variable size, "longest/shortest window satisfying P".** `right` always advances;
    `left` advances only while the window violates the condition.

    ```python
    left = 0
    window = empty_state()
    best = identity()
    for right in range(len(nums)):
        add(window, nums[right])
        while not is_valid(window):          # shrink until valid again
            remove(window, nums[left])
            left += 1
        best = better(best, right - left + 1)
    return best
    ```

    Swap `while not is_valid` for `while is_valid` and record inside the loop, and you get
    "shortest window satisfying P" instead. Those two templates plus a correct `add`/`remove` pair
    cover: longest substring with at most K distinct characters, minimum window substring,
    subarrays with product less than K, longest repeating character replacement, and maximum
    consecutive ones after K flips.

    **The part people get wrong** is `remove`. It must exactly undo `add`, including deleting a
    dictionary key when its count reaches zero — because `len(counter)` is usually how `is_valid`
    counts distinct elements, and a lingering zero-count key makes it wrong.

    ```python
    def longest_with_at_most_k_distinct(s: str, k: int) -> int:
        from collections import defaultdict
        count: dict[str, int] = defaultdict(int)
        left = best = 0
        for right, ch in enumerate(s):
            count[ch] += 1
            while len(count) > k:
                out = s[left]
                count[out] -= 1
                if count[out] == 0:
                    del count[out]        # <-- delete, do not leave a zero
                left += 1
            best = max(best, right - left + 1)
        return best

    assert longest_with_at_most_k_distinct("eceba", 2) == 3      # "ece"
    assert longest_with_at_most_k_distinct("aa", 1) == 2
    assert longest_with_at_most_k_distinct("abcdef", 0) == 0
    ```

    ### What the window is worth, measured

    Sliding-window maximum — for every window of `k` consecutive elements, report the largest —
    computed naively as `max(a[i:i+k])` per position, versus the monotonic-deque version that keeps
    a decreasing deque of candidate indices:

    | Elements | Window `k` | Naive `max()` per window | Monotonic deque | Speedup |
    | --- | --- | --- | --- | --- |
    | 100,000 | 1,000 | 737.4 ms | 14.0 ms | **53×** |
    | 1,000,000 | 1,000 | 9,108.5 ms | 134.5 ms | **68×** |

    <Info>
    Method: CPython 3.12.9, M3 Pro, best-of-3 (best-of-1 for the 1M naive case), both verified to
    return identical output at n = 100,000. Reproduce with `extra_dsa.py w13m2x`.
    </Info>

    The naive version is `O(n·k)` — and note that it is not a Python-slowness artifact, because
    `max()` on a slice is a C-level loop. The window version is `O(n)` because each index enters
    and leaves the deque exactly once. **The speedup tracks `k`**: at `k = 1,000` you would predict
    something in the low hundreds and measure 53–68×, the gap being the deque's per-element
    bookkeeping in Python against `max()`'s tight C loop. Larger `k` widens it; `k` of 5 or 10 would
    make the naive version win outright.

    ## Reference implementation: a chunker with overlap

    Not a toy. This is the function you will import in week 27, and it is a sliding window with a
    fixed stride.

    ```python
    # chunker.py — CPython 3.12. No dependencies.
    from __future__ import annotations
    import re
    import unicodedata
    from dataclasses import dataclass


    @dataclass(frozen=True, slots=True)
    class Chunk:
        text: str
        start: int          # character offset into the normalized source
        end: int            # exclusive
        index: int


    _WS = re.compile(r"\s+")


    def normalize(text: str) -> str:
        """Canonicalize before you do anything else with user text.

        NFC composes 'e' + combining-acute into the single code point 'e-acute',
        so two visually identical strings compare equal, hash equal, and produce
        the same embedding. Do this at the ingestion boundary, exactly once.
        """
        return _WS.sub(" ", unicodedata.normalize("NFC", text)).strip()


    def chunk_by_words(
        text: str,
        size: int = 200,
        overlap: int = 40,
    ) -> list[Chunk]:
        """Split into windows of `size` words that overlap by `overlap` words.

        Overlap exists so a sentence straddling a boundary appears whole in at
        least one chunk. Stride = size - overlap; a stride of zero would loop
        forever, which is why it is checked rather than assumed.
        """
        if size <= 0:
            raise ValueError("size must be positive")
        if not 0 <= overlap < size:
            raise ValueError("overlap must satisfy 0 <= overlap < size")

        text = normalize(text)
        if not text:
            return []

        # Keep character offsets so a chunk can be traced back to the source.
        words: list[tuple[str, int, int]] = [
            (m.group(0), m.start(), m.end()) for m in re.finditer(r"\S+", text)
        ]
        if not words:
            return []

        stride = size - overlap
        chunks: list[Chunk] = []
        for idx, start_w in enumerate(range(0, len(words), stride)):
            window = words[start_w : start_w + size]
            if not window:
                break
            chunks.append(
                Chunk(
                    text=" ".join(w for w, _, _ in window),
                    start=window[0][1],
                    end=window[-1][2],
                    index=idx,
                )
            )
            if start_w + size >= len(words):
                break          # this window already reached the end
        return chunks
    ```

    ```python
    # test_chunker.py — pytest 8.x
    import pytest
    from chunker import chunk_by_words, normalize, Chunk


    def test_covers_every_word():
        text = " ".join(f"w{i}" for i in range(1000))
        chunks = chunk_by_words(text, size=200, overlap=40)
        seen = set()
        for c in chunks:
            seen.update(c.text.split())
        assert len(seen) == 1000          # nothing dropped


    def test_overlap_is_exact():
        text = " ".join(f"w{i}" for i in range(1000))
        chunks = chunk_by_words(text, size=200, overlap=40)
        a, b = chunks[0].text.split(), chunks[1].text.split()
        assert a[-40:] == b[:40]


    def test_offsets_slice_back_to_source():
        text = normalize("alpha beta gamma delta epsilon zeta")
        chunks = chunk_by_words(text, size=3, overlap=1)
        for c in chunks:
            assert text[c.start : c.end] == c.text


    def test_terminates_on_short_input():
        assert len(chunk_by_words("one two", size=200, overlap=40)) == 1


    def test_empty_input():
        assert chunk_by_words("") == []
        assert chunk_by_words("   \n\t  ") == []


    def test_rejects_overlap_equal_to_size():
        with pytest.raises(ValueError):
            chunk_by_words("a b c", size=10, overlap=10)   # stride 0 = infinite loop


    def test_normalization_makes_equal_strings_equal():
        precomposed = "café"          # é as one code point
        decomposed  = "café"         # e + combining acute
        assert precomposed != decomposed
        assert normalize(precomposed) == normalize(decomposed)
    ```

    <Check>
    `test_rejects_overlap_equal_to_size` is the test that earns its keep. `overlap == size` makes
    `stride == 0`, and `range(0, n, 0)` raises `ValueError` in Python — but if you had written the
    loop with a `while` and a manual increment, it would hang forever in production with no error
    and no log line. Validate the stride, do not discover it.
    </Check>

    ## Trade-offs table

    | Situation | Choose | Instead of | Because |
    | --- | --- | --- | --- |
    | Many range-sum queries over static data | prefix sums | recomputing per query | O(n) build then O(1) per query; measured 233× at n=100,000 with 2,000 queries |
    | Range queries over data that also *changes* | Fenwick tree (BIT) or segment tree | prefix sums | a prefix array is O(n) to update; a Fenwick tree is O(log n) for both update and query |
    | Find a pair summing to a target, array sorted | two pointers | hash set | O(1) space instead of O(n), and you already paid for the sort |
    | Same, array unsorted, one query | hash set | sort then two pointers | O(n) beats O(n log n); only sort if you need sorted order anyway |
    | Substring search in Python | `str.find` / the `in` operator | your own KMP | CPython uses a two-way + Crochemore-Perrin algorithm in C; measured 170× faster than a Python KMP (Layer 3) |
    | Substring search in C/Rust over huge corpora, many patterns | Aho-Corasick | repeated single-pattern search | one pass finds all patterns simultaneously; this is what a real BM25 tokenizer does |
    | Building a string from many pieces | `"".join(parts)` | `s += piece` in a loop | one allocation instead of n; the `+=` version is quadratic in total characters |
    | Numeric arrays over ~10,000 elements | `numpy.ndarray` | `list` | 4.5× less memory (8 vs 36 bytes/element) and a 50–200× faster inner loop (week 16) |
    | Fixed-size numeric buffer, no NumPy dependency wanted | `array.array` | `list` | same 8 bytes/element packing, standard library only |

    ## What breaks in the real world

    A document-ingestion service chunked PDFs for a retrieval index using a word window of 512
    with 64 overlap, and deduplicated chunks by exact string hash before embedding — a sensible
    optimisation, since embedding is the expensive step and legal documents repeat boilerplate.

    Six weeks in, the embedding bill was 2.7× the forecast and the dedup hit rate was 4% instead
    of the ~35% seen in the prototype. Same code, same documents.

    The difference was the PDF text extractor. The prototype used `pdftotext`, which emits
    precomposed characters (NFC). Production had switched to a different library that emits
    decomposed characters (NFD) for accented text — and the corpus was European contracts, full of
    accented names and place names. Every chunk containing "Zürich" or "société" hashed differently
    from its NFC-identical twin. **The strings rendered identically in every log line and every
    debugging session**, which is why it took three weeks to find: the two chunks looked the same
    on screen, in the terminal, and in the database viewer.

    The fix was one line at the ingestion boundary:

    ```python
    text = unicodedata.normalize("NFC", raw_text)
    ```

    What generalises:

    - **Normalize at the boundary, exactly once, and never again.** If normalization is scattered
      through the codebase, some paths will miss it. One function at ingestion, and everything
      downstream can assume NFC.
    - **`len()` is not a safe equality proxy for text**, and neither is visual inspection. When
      debugging string mismatches, print `[hex(ord(c)) for c in s]` or
      `s.encode('unicode_escape')`. Both strings above are five characters on screen; one is 5
      code points and one is 6.
    - **The symptom was a cost anomaly, not an error.** Nothing threw. Nothing logged. The only
      signal was a dedup rate that had quietly halved, and nobody had a graph of it. If you have a
      dedup or cache step, graph its hit rate — that ratio is your canary for an entire class of
      silent data bugs.

    ### Design checkpoint

    <Accordion title="You must support range-sum queries over a 50-million-row table where rows are also being appended and occasionally corrected. Queries must be under 10 ms. What do you build?">
    **Model answer.**

    A flat prefix array is wrong here: a correction to row 1,000 invalidates 49,999,000 entries,
    so an update is O(n) — about 50 ms of pure memcpy at best, and far worse in Python.

    **Option 1 — Fenwick tree (binary indexed tree).** O(log n) update, O(log n) prefix query.
    At n = 50M, log₂ n ≈ 26, so a query is 26 array reads — well under a microsecond in C, a few
    microseconds in Python. Memory is one number per row: 400 MB as int64, or 200 MB as int32 if
    the values fit. This is the textbook answer and it is right if the data fits in memory on one
    machine.

    **Option 2 — the one I would actually ship: a columnar store with zone maps.** Keep the data
    in Parquet or DuckDB partitioned by time. Each row group carries min/max/sum statistics, so a
    range sum reads only the row groups that overlap the range, and for fully-contained groups it
    reads the precomputed sum instead of the rows. A correction rewrites one row group, not the
    world. **You will build exactly this in week 15**, and it wins here because it also solves
    durability, concurrent readers and the fact that 50M rows do not belong in one process's heap.

    **The deciding question is the update-to-query ratio.** Heavy queries and rare updates: prefix
    array, rebuilt nightly. Balanced: Fenwick. Updates arriving continuously with a durability
    requirement: columnar store with statistics.

    **The trap to name explicitly:** floating-point prefix sums lose precision. Summing 50 million
    float32 values naively accumulates error proportional to `n × ε`; by row 50 million a
    `float32` accumulator has drifted enough that `P[j] - P[i]` for a narrow range near the end can
    be visibly wrong. Accumulate in `float64` (or in integer cents), or use pairwise/Kahan
    summation. **You will measure this exact error in week 16 module 1.**
    </Accordion>

    ## KMP is asymptotically better and measurably slower, and that is the most useful benchmark in this week

    Knuth–Morris–Pratt searches for a pattern in `Θ(n + m)` with no backtracking. The naive
    algorithm is `O(n·m)` in the worst case. Textbook conclusion: use KMP.

    Adversarial input — a 2,000,001-character text of `"aaa…aab"`, pattern `"aa…ab"` of 201
    characters, the exact case constructed to make naive backtrack maximally:

    | Implementation | Time | vs naive |
    | --- | --- | --- |
    | Naive `t[i:i+m] == p`, pure Python | 374.4 ms | 1.00× |
    | KMP, pure Python | **391.5 ms** | **0.96× — slower** |
    | `str.find`, CPython's C implementation | **2.301 ms** | **163×** |

    <Info>
    Method: CPython 3.12.9, M3 Pro, best-of-2 for the Python implementations and best-of-5 for
    `str.find`, all three verified to return the same index. Reproduce with `dsa_suite.py w13m2`.
    </Info>

    Two separate lessons, and both are worth more than the algorithm itself.

    **1. The naive version is not doing naive work.** `t[i:i+m] == p` looks like an O(m) inner
    loop, but CPython executes it as a slice (one C-level `memcpy` of 201 bytes) followed by a
    string comparison (one C-level `memcmp`). Both run at memory bandwidth. Meanwhile KMP's inner
    loop is `while k and ch != p[k]: k = f[k-1]` — a Python-level comparison, index and assignment
    per character, at roughly 40–60 ns each. **KMP does asymptotically less work in a language
    that is 100× slower per unit of work.** The asymptotic win is real and the constant factor
    eats it whole.

    **2. `str.find` beats both by two orders of magnitude** because CPython implements a hybrid:
    Crochemore–Perrin two-way matching with a Bloom-filter-style bad-character skip table, in C,
    over raw bytes (`Objects/stringlib/fastsearch.h`). It is a better algorithm *and* it is in C.

    The rule this generalises to, and it governs the rest of your Python career: **an algorithmic
    improvement that keeps you in the interpreter must beat a ~100× constant-factor handicap
    before it wins.** In practice that means: reach for the C-implemented standard library first,
    and reserve hand-written algorithms for cases where no C implementation of the *right shape*
    exists. When you write KMP for real it will be inside a C extension, a Rust module, or as
    Aho-Corasick over many patterns at once — because *that* shape has no standard-library
    equivalent.

    ## When the better algorithm does win: Rabin-Karp and Aho-Corasick

    Single-pattern search in Python: use `str.find`, always. The two rolling-hash-family
    algorithms earn their place at a different shape of problem:

    - **Rabin-Karp** hashes a rolling window and compares hashes, falling back to a full
      comparison on a hash match. Its win is **multiple patterns of the same length**: hash all
      `k` patterns into a set, roll once through the text, and you find all of them in `O(n + k·m)`
      instead of `O(k·n)`. Its risk is hash collisions — with a weak modulus, an attacker can
      craft input that collides every window and forces the O(n·m) fallback, which is an
      algorithmic-complexity DoS.
    - **Aho-Corasick** builds a trie of all patterns with failure links (the same idea as KMP's
      failure function, generalised to a trie) and finds every occurrence of every pattern in one
      pass, `O(n + total pattern length + occurrences)`. **This is what a production keyword
      matcher, a profanity filter, or a BM25 tokenizer with a stopword list actually uses.** You
      will build the trie half of it in week 14 module 1.

    ## Unicode: three things that will cost you a day each

    ```python
    >>> a, b = "café", "café"          # NFC (4 code points), NFD (5 code points)
    >>> len(a), len(b)
    (4, 5)
    >>> a == b
    False
    >>> import unicodedata
    >>> unicodedata.normalize("NFC", a) == unicodedata.normalize("NFC", b)
    True

    >>> family = "👨‍👩‍👧‍👦"
    >>> len(family)                     # Python characters (code points)
    7
    >>> len(family.encode("utf-8"))     # bytes
    25
    ```

    Three distinct failure modes:

    1. **Composition.** NFC composes, NFD decomposes. Different byte sequences, identical
       rendering. Normalize at ingestion. **Which form?** NFC for storage and comparison (it is
       the web's default and what `unicodedata` prefers); NFD only when you need to strip
       diacritics, where decomposing and dropping the combining marks is the clean way to do it.
    2. **Grapheme clusters.** The family emoji is *one* thing a human sees, 7 code points, and 25
       UTF-8 bytes. `s[0]` on it gives you a lone man emoji; truncating a string at a code-point
       boundary can split a grapheme and produce mojibake. Any "truncate to 100 characters" that
       runs on user text needs the `regex` module's `\X` (grapheme cluster) or an explicit
       segmentation pass.
    **What normalization costs.** Over a 2,000,000-character corpus:

    | Input | `unicodedata.normalize("NFC", s)` |
    | --- | --- |
    | Pure ASCII | ~0.00 ms (quick-check short-circuits immediately) |
    | Already NFC, accented | 2.22 ms |
    | NFD (needs real composition work) | **61.37 ms** |
    | `s.lower()` on the same corpus, for scale | 10.06 ms |

    Normalizing text that is already normalized is **27.6× cheaper** than normalizing text that is
    not, because `unicodedata` runs a quick-check pass that bails out early when the string is
    already in the target form. Two consequences: normalizing at the boundary is nearly free once
    your corpus is clean, and it is **idempotent and cheap to call defensively** — so there is no
    performance argument for skipping it.

    3. **Case folding is not lowercasing.** `"ß".lower()` is `"ß"`; `"ß".casefold()` is `"ss"`.
       For case-insensitive *comparison* use `casefold()`. For display use `lower()`. Turkish
       dotless ı breaks the naive assumption in the other direction, which is the reason
       `"I".lower()` being locale-dependent has taken down real login systems.

    In your text pipelines the boundary function is always the same three lines, and they belong
    at ingestion, once:

    ```python
    def canonical(s: str) -> str:
        s = unicodedata.normalize("NFC", s)
        s = "".join(ch for ch in s if unicodedata.category(ch) != "Cf")  # drop zero-width/format
        return re.sub(r"\s+", " ", s).strip()
    ```

    Dropping category `Cf` removes zero-width joiners, zero-width spaces and bidirectional
    overrides. Those are invisible, they survive copy-paste out of PDFs and web pages, they break
    exact matching, and — because a right-to-left override can make `moc.liame@resu` render as
    `user@email.com` — they are also a phishing vector. **You will care about this again in week 31
    when a hidden instruction inside a retrieved document is the attack.**

    ## Memory layout: the array you should be using

    | Container | Bytes per int64 element | 1M elements | Access cost |
    | --- | --- | --- | --- |
    | `list` of ints | 8 (pointer) + 28 (int object) = ~36 | ~36 MB | pointer dereference + unbox |
    | `array.array('q')` | 8 | 8 MB | direct, boxes on read |
    | `numpy.ndarray(dtype=int64)` | 8 | 8 MB | direct, vectorized ops stay unboxed |
    | `bytes` / `memoryview` | 1 (uint8) | 1 MB | direct, zero-copy slicing |

    A `list` of a million small ints is **4.5× the memory** of the equivalent NumPy array, and
    every element access dereferences a pointer to a heap object and unboxes an integer. Small
    ints from −5 to 256 are interned and shared, which is why `[0] * 1_000_000` measures far
    smaller than `list(range(1_000_000))` — a fact that has produced many wrong memory benchmarks.

    `memoryview` is the underused one. It gives you zero-copy slices of a buffer:

    ```python
    data = bytearray(10_000_000)
    mv = memoryview(data)
    chunk = mv[1_000_000:2_000_000]     # no copy: 0 bytes allocated
    slow  = data[1_000_000:2_000_000]   # copies 1 MB
    ```

    In an ingestion pipeline that slices multi-megabyte payloads per request, that difference is
    the whole memory profile.

    ## Production failure modes

    | Failure mode | Signature | Detection |
    | --- | --- | --- |
    | Quadratic string building | CPU-bound; profile shows `str.__add__` or `unicode_concatenate` | grep for `+=` on a string inside a loop; use `join` or `io.StringIO` |
    | Silent Unicode mismatch | dedup/cache hit rate drops with no error; strings look identical in logs | normalize at ingestion; when debugging print `s.encode('unicode_escape')`, never the string |
    | Grapheme split on truncation | mojibake in the UI, usually only for emoji or Indic scripts | truncate on grapheme clusters (`regex` module `\X`), and test with the family emoji |
    | Rabin-Karp collision DoS | pathological slowdown on attacker-supplied input only | use a randomized modulus per process, or use `str.find` |
    | `list` used as a numeric buffer | RSS ~4.5× the expected size; GC pauses proportional to element count | `array.array` or NumPy; both remove the per-element object entirely |
    | Prefix sums over float32 at scale | range sums near the end of the array are subtly wrong; error grows with index | accumulate in float64 or integers; use pairwise summation (week 16 M1 measures the error) |
    | Slicing large buffers per request | RSS proportional to concurrency × payload size | `memoryview` for zero-copy slices |

    ## Frontier and research pointers

    - **Knuth, Morris & Pratt (1977), "Fast Pattern Matching in Strings."** *SIAM J. Comput.* 6(2).
      — **Takeaway:** the failure function lets you never re-examine a text character, giving
      `Θ(n+m)` worst case; also read it as the origin of the "precompute a table from the pattern"
      idea that Aho-Corasick and Boyer-Moore both generalise.
    - **Crochemore & Perrin (1991), "Two-Way String-Matching."** *JACM* 38(3). — **Takeaway:**
      splitting the pattern at its critical factorization gives `O(n)` worst case with `O(1)`
      extra space; this is the algorithm behind CPython's `str.find` and glibc's `strstr`, which
      is why it beat your KMP by 163×.
    - **Aho & Corasick (1975), "Efficient String Matching: An Aid to Bibliographic Search."**
      *CACM* 18(6). — **Takeaway:** a trie with failure links finds every occurrence of every
      pattern in a single pass, independent of how many patterns there are; this is the right
      structure whenever you have a dictionary rather than a single needle.
    - **Karp & Rabin (1987), "Efficient randomized pattern-matching algorithms."** *IBM J. Res.
      Dev.* 31(2). — **Takeaway:** a rolling hash makes multi-pattern and 2-D matching cheap, at
      the cost of a probabilistic guarantee you must not let an adversary control.
    - **Unicode Standard Annex #15, Unicode Normalization Forms**, and **UAX #29, Text Segmentation.**
      — **Takeaway:** NFC/NFD/NFKC/NFKD are four different canonicalizations with genuinely
      different use cases (NFKC folds ligatures and full-width forms, which you want for search
      and do not want for storage), and grapheme cluster boundaries — not code points — are what
      "a character" means to a user.

    ## Stretch challenge

    **Build a text-normalization contract test suite and run it against three real extractors.**

    Take the war story seriously: pick three ways to get text out of a PDF (`pdftotext`,
    `pypdf`, `pdfplumber` — all free) and one HTML extractor, then build a suite that measures,
    for the same source documents:

    1. **Normalization form distribution.** What fraction of output is already NFC? Does the
       extractor emit NFD, or a mix within one document?
    2. **Invisible character contamination.** Count `Cf`-category code points, non-breaking
       spaces, soft hyphens and zero-width joiners per 1,000 characters.
    3. **Round-trip stability.** Extract the same PDF twice — is the output byte-identical? Some
       extractors are not deterministic, which quietly destroys content-hash-based deduplication.
    4. **The downstream consequence, measured.** Chunk and hash the output of each extractor and
       report the dedup rate on a corpus with known duplicates. Then normalize and report it
       again. The delta is the cost of skipping normalization, in a number.

    The open questions:

    - **Is NFC always right?** NFKC would also fold "ﬁ" to "fi" and full-width Latin to ASCII,
      which helps search recall and destroys information you might need to render. Where is the
      line, and does it move depending on whether the text is going into an index or into a
      display?
    - **Should normalization be lossy at ingestion or at query time?** Storing NFC and normalizing
      queries to NFC is one design; storing raw and normalizing both sides at comparison time is
      another. One is cheaper; the other is reversible. Argue for one, with the storage and
      latency numbers.
    - **How do you detect the failure in production?** You cannot diff every document. What single
      metric would have caught the war story in week one rather than week six?

    Publish it. A test suite that quantifies "which PDF extractor will hurt me least" is a thing
    every RAG team needs and nobody has written down.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Sliding window returns a too-large answer on `"abba"` | Missing the `last_seen[ch] >= left` guard, so `left` jumps backward | Guard the jump; `left` must be monotonically non-decreasing |
| Window with distinct-count condition is off by one | Zero-count keys left in the counter, so `len(counter)` overcounts | `del counter[k]` when the count reaches 0 |
| Max-sum-window returns 0 on all-negative input | `best` initialised to 0 instead of the first window's sum | Initialise `best` from the first window, never from a literal |
| Range-sum off by one at the array start | Prefix array of length `n` with no leading zero | Length `n+1`, `P[0] = 0`, `sum(i..j) = P[j+1] - P[i]` |
| Report generation is fast in dev, minutes in prod | String `+=` in a loop — quadratic in total output size | `"".join(parts)` or `io.StringIO` |
| Two identical-looking strings compare unequal | NFC vs NFD composition | `unicodedata.normalize("NFC", s)` at ingestion; debug with `s.encode('unicode_escape')` |
| Truncating user text produces mojibake | Cut in the middle of a grapheme cluster | Segment on `\X` with the `regex` module before truncating |
| Case-insensitive comparison misses German or Turkish text | `.lower()` instead of `.casefold()` | `casefold()` for comparison, `lower()` for display |
| RSS 4× the expected size for a numeric buffer | `list` of ints — 8-byte pointer plus 28-byte int object each | `array.array` or `numpy.ndarray` |
| Chunker hangs on a specific document | `overlap == size`, so stride is 0 | Validate `0 <= overlap < size` at the entry point |

- [`unicodedata`](https://docs.python.org/3.12/library/unicodedata.html) — read this for `normalize`, and for `category`, which is how you find and strip invisible format characters.
- [`array` module](https://docs.python.org/3.12/library/array.html) — read this for the typecode table; `'q'` is int64 and `'d'` is float64, and this is the zero-dependency way to stop paying 36 bytes per integer.
- [`memoryview`](https://docs.python.org/3.12/library/stdtypes.html#memoryview) — read this for zero-copy slicing of buffers, and for the `release()` semantics that matter when the underlying object must be resized.

**Papers**

- [Knuth, Morris & Pratt (1977), *Fast Pattern Matching in Strings*, SIAM J. Comput. 6(2), 323–350.](https://doi.org/10.1137/0206024) — **Takeaway:** precomputing a failure function from the pattern means the text pointer never moves backward, giving linear worst-case time.
- [Crochemore & Perrin (1991), *Two-Way String-Matching*, JACM 38(3), 651–675.](https://doi.org/10.1145/116825.116845) — **Takeaway:** critical factorization gives linear time in constant space, and it is what your standard library actually runs.
- [Aho & Corasick (1975), *Efficient String Matching: An Aid to Bibliographic Search*, CACM 18(6), 333–340.](https://doi.org/10.1145/360825.360855) — **Takeaway:** one pass finds every occurrence of every pattern in a dictionary, which is the shape real keyword and tokenizer problems have.
- [Karp & Rabin (1987), *Efficient randomized pattern-matching algorithms*, IBM J. Res. Dev. 31(2).](https://doi.org/10.1147/rd.312.0249) — **Takeaway:** rolling hashes generalise cheaply to multiple patterns and to 2-D, at the price of a collision probability an adversary must not be able to exploit.
- [Unicode Consortium, *UAX #15: Unicode Normalization Forms* and *UAX #29: Unicode Text Segmentation*.](https://www.unicode.org/reports/tr15/) — **Takeaway:** canonical equivalence is a defined relation with four normal forms, and "a character" to a user is a grapheme cluster, not a code point.

**Go deeper**

- [Sedgewick & Wayne, *Algorithms* 4th ed., **Chapter 5.3 (Substring Search)**](https://algs4.cs.princeton.edu/home/) — the clearest side-by-side of brute force, KMP, Boyer-Moore and Rabin-Karp, with the automaton view of KMP that makes the failure function obvious.
- [Ned Batchelder, *Pragmatic Unicode* (PyCon 2012 talk and write-up)](https://nedbatchelder.com/text/unipain.html) — 40 minutes that will save you a day. Read it for the "Unicode sandwich" rule: decode at input, work in `str`, encode at output.
- [Skiena, *The Algorithm Design Manual* 3rd ed., **Chapter 3**](https://www.algorist.com/) — the war stories are the point; the section on when a fancy data structure is not worth it is the counterweight to everything else you read this week.
