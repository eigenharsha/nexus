    ## The idea in one paragraph

    A Python list keeps its items **next to each other in memory**, like books on one shelf. That
    makes reading item number 5,000 instant — the computer can calculate exactly where it is. But
    inserting a book in the middle means physically shifting every book after it. A **linked
    list** solves the opposite problem: each item is stored wherever there is room, and each one
    holds the *address* of the next item, like a treasure hunt where each clue tells you where the
    next clue is. Inserting is free — you just rewrite two clues. But finding item number 5,000
    means following 5,000 clues. **Stacks** and **queues** are not new structures; they are rules
    about *which end* you are allowed to touch.

    ### The analogy

    - **Array (Python `list`)** — a row of numbered lockers, bolted to the wall. Locker 5,000 is
      exactly 5,000 locker-widths from the start, so you walk straight to it. But to add a locker
      in the middle you have to unbolt and re-bolt everything after it.
    - **Linked list** — a scavenger hunt. Each clue is on a scrap of paper somewhere in the
      building, and each scrap tells you where the next scrap is. Adding a new clue in the middle
      is trivial: change one scrap to point at the new one, and point the new one at the old next.
      But there is no way to get to the 5,000th clue except by reading the first 4,999.
    - **Stack** — a pile of plates. You add on top, you take from the top. Last one in is the
      first one out. This is called **LIFO** (last-in, first-out).
    - **Queue** — the line at a coffee shop. You join at the back, you get served from the front.
      First one in is the first one out: **FIFO**.

    ### Every term, defined

    - **Node** — one box holding a value plus at least one pointer to another box.
    - **Pointer / reference** — a value that says *where* something else lives, rather than being
      the thing itself. In Python every variable is a reference; `a = b` copies the address, not
      the object.
    - **Head** — the first node. If you lose the head, you lose the whole list.
    - **Tail** — the last node. Its "next" pointer is `None`.
    - **Singly linked** — each node points only forward.
    - **Doubly linked** — each node points forward *and* backward. Costs 8 more bytes per node,
      and buys you the ability to remove a node in O(1) when you already have it.
    - **Sentinel** — a fake node at the head and tail that never holds real data. It exists so
      that your insert and delete code never needs an `if node is None` special case. This is a
      real technique, not a trick — it removes roughly half the bugs from linked-list code.
    - **LIFO / FIFO** — last-in-first-out (stack) and first-in-first-out (queue).
    - **Cache** — a small, fast store of results you already computed, so you do not compute them
      twice.
    - **Eviction** — deciding what to throw out of a full cache. **LRU** = throw out the
      Least Recently Used item.

    ### The smallest working example

    ```python
    # tiny_list.py — CPython 3.12
    class Node:
        """One box: a value, and where to find the next box."""
        def __init__(self, value):
            self.value = value
            self.next = None

    # Build:  10 -> 20 -> 30 -> None
    head = Node(10)
    head.next = Node(20)
    head.next.next = Node(30)

    # Traverse: follow the pointers until there is no next.
    current = head
    while current is not None:
        print(current.value)
        current = current.next
    # 10
    # 20
    # 30

    # Insert 15 between 10 and 20 — two pointer writes, no shifting.
    new = Node(15)
    new.next = head.next        # 15 -> 20
    head.next = new             # 10 -> 15
    # now:  10 -> 15 -> 20 -> 30 -> None

    # Delete 20 — one pointer write. (We had to walk here to find it.)
    prev = head.next            # the node holding 15
    prev.next = prev.next.next  # 15 -> 30, skipping 20
    # now:  10 -> 15 -> 30 -> None
    ```

    ### Line-by-line walkthrough

    - `self.next = None` — a fresh node points nowhere. `None` is the marker for "end of list".
    - `head.next.next = Node(30)` — read it left to right: from head, go next (that's 20), and set
      *its* next to a new node. This is why the chain works: each node only knows about the next one.
    - `while current is not None:` — the traversal loop. `current` is a *cursor*, not a copy;
      moving it does not change the list.
    - `current = current.next` — the single most important line in linked-list code. Forget it and
      you have an infinite loop. Put it before the work and you skip the first element.
    - `new.next = head.next` then `head.next = new` — **the order matters and this is where
      beginners lose an hour.** If you write `head.next = new` first, you have destroyed the only
      reference to the node holding 20, and Python garbage-collects the rest of your list.
      **Always attach the new node's pointers before you rewrite the old ones.**
    - `prev.next = prev.next.next` — deletion is just "point around it". The skipped node has no
      references left, so Python frees it. In C you would `free()` it yourself; in Python the
      refcount hits zero and it goes away.

    ### Stacks and queues in Python — what to actually use

    You will almost never write your own stack in Python. A `list` already is one:

    ```python
    stack = []
    stack.append("a")     # push — amortized O(1)
    stack.append("b")
    top = stack.pop()     # pop  — O(1), returns "b"
    ```

    A queue is where people go wrong:

    ```python
    # WRONG — works, but it is O(n) per removal
    queue = []
    queue.append("a")
    first = queue.pop(0)      # every remaining element shifts left one slot

    # RIGHT
    from collections import deque
    queue = deque()
    queue.append("a")         # O(1)
    first = queue.popleft()   # O(1)
    ```

    `list.pop(0)` removes the first element and then moves every other element one slot to the
    left, because a Python list is a contiguous block. Removing from a 100,000-element list moves
    99,999 pointers. Doing that 100,000 times is 5 billion pointer moves. Here is what that costs,
    measured:

    | Elements drained | `list.pop(0)` | `deque.popleft()` | ratio |
    | --- | --- | --- | --- |
    | 1,000 | 0.17 ms | 0.02 ms | **7×** |
    | 10,000 | 13.20 ms | 0.57 ms | **23×** |
    | 50,000 | 650.79 ms | 4.58 ms | **142×** |
    | 100,000 | 2,884.32 ms | 5.09 ms | **567×** |

    Look at the two columns separately. The `deque` column roughly multiplies by 10 when `n`
    multiplies by 10 — that is linear, as expected for `n` removals of O(1) each. The `list`
    column multiplies by about 100 — that is quadratic, `n` removals of O(n) each. **At 100,000
    items, draining a list-as-queue takes 2.9 seconds and draining a deque takes 5 milliseconds.**

    ### Checkpoint — 5 questions before you continue

    <AccordionGroup>
      <Accordion title="1. Why can't you index a linked list like `lst[5000]`?">
        Because nodes are scattered in memory with no arithmetic relationship between them. An
        array can compute `base_address + 5000 * item_size` in one instruction. A linked list has
        no such formula — the only way to node 5,000 is to follow 5,000 pointers, which is O(n).
      </Accordion>
      <Accordion title="2. You have a reference to a node in the middle of a singly linked list and want to delete it. Why is that O(n)?">
        Because you need to change the *previous* node's `next` pointer, and a singly linked node
        has no way to reach its predecessor. You have to walk from the head to find it. In a
        doubly linked list the node holds `prev`, so deletion is two pointer writes — O(1). This
        is the entire reason an LRU cache needs a doubly linked list.
      </Accordion>
      <Accordion title="3. Why is `list.append` O(1) but `list.insert(0, x)` O(n)?">
        `append` writes into the next free slot at the end (and occasionally reallocates, which
        amortizes away). `insert(0, x)` must shift every existing element one position right to
        make room at the front — `n` moves.
      </Accordion>
      <Accordion title="4. What is a sentinel node and what bug does it prevent?">
        A dummy node at the head (and usually the tail) that never holds data. Without it, every
        insert and delete needs a special case for "am I at the head?" — because updating the head
        means writing to a variable rather than to a node's pointer. With sentinels, every node
        has a real `prev` and a real `next`, so one code path handles every position. It removes
        the `if node is head` branch, which is where most linked-list bugs live.
      </Accordion>
      <Accordion title="5. When would you use a linked list over a Python list in real code?">
        Almost never, on its own — measure before you reach for one. The real use is as a
        *component*: the recency ordering inside an LRU cache, an intrusive free-list inside an
        allocator, or a wait queue inside a scheduler where nodes are removed from arbitrary
        positions and you already hold a pointer to the node. If your access pattern is "iterate"
        or "index", an array wins on every axis including cache behaviour.
      </Accordion>
    </AccordionGroup>

    ## The LRU cache, properly

    An LRU cache answers two questions in O(1):

    1. **"Do I have key K, and what is its value?"** — a hash map does this and a list cannot.
    2. **"What is the least recently used entry, so I can evict it?"** — an ordered list does this
       and a hash map cannot.

    Neither structure can do both. **So you use both, wired together: the map's values are
    pointers into the list's nodes.** That sentence is the whole design, and it is the answer to
    the interview question.

    Why the list must be **doubly** linked: on a cache hit you must move that node to the front.
    Moving it means unlinking it from where it currently is, which means writing to its
    predecessor's `next` pointer. A singly linked node cannot find its predecessor without a scan,
    which would make `get` O(n) and defeat the whole design.

    Why there must be **sentinels**: without them, "unlink a node" needs three special cases (it
    is the head, it is the tail, it is both). With a permanent `head` and `tail` sentinel, every
    real node is guaranteed to have a non-null `prev` and `next`, and unlink is unconditionally:

    ```python
    node.prev.next = node.next
    node.next.prev = node.prev
    ```

    ### Reference implementation

    ```python
    # lru.py — CPython 3.12. Complete, tested, no dependencies.
    from __future__ import annotations
    from typing import Any, Hashable, Iterator, Optional


    class _Node:
        """A doubly linked node. __slots__ drops the per-instance __dict__,
        taking each node from 152 bytes to 72 on CPython 3.12/arm64."""
        __slots__ = ("key", "value", "prev", "next")

        def __init__(self, key: Hashable = None, value: Any = None) -> None:
            self.key = key
            self.value = value
            self.prev: Optional[_Node] = None
            self.next: Optional[_Node] = None


    class LRUCache:
        """Least-recently-used cache with O(1) get and put.

        Invariants (assert these in tests):
          - len(self._map) == number of real nodes strictly between the sentinels
          - the node after _head is the most recently used
          - the node before _tail is the least recently used
          - every value in _map is a node currently linked into the list
        """

        def __init__(self, capacity: int) -> None:
            if capacity <= 0:
                raise ValueError("capacity must be positive")
            self.capacity = capacity
            self._map: dict[Hashable, _Node] = {}
            # Two sentinels that always exist. No node is ever at a boundary.
            self._head = _Node()
            self._tail = _Node()
            self._head.next = self._tail
            self._tail.prev = self._head
            self.hits = 0
            self.misses = 0
            self.evictions = 0

        # ---- private list surgery -------------------------------------------
        def _unlink(self, node: _Node) -> None:
            node.prev.next = node.next
            node.next.prev = node.prev

        def _push_front(self, node: _Node) -> None:
            node.prev = self._head
            node.next = self._head.next
            self._head.next.prev = node
            self._head.next = node

        # ---- public API ------------------------------------------------------
        def get(self, key: Hashable, default: Any = None) -> Any:
            node = self._map.get(key)
            if node is None:
                self.misses += 1
                return default
            self.hits += 1
            self._unlink(node)
            self._push_front(node)
            return node.value

        def put(self, key: Hashable, value: Any) -> None:
            node = self._map.get(key)
            if node is not None:
                node.value = value
                self._unlink(node)
                self._push_front(node)
                return
            if len(self._map) >= self.capacity:
                victim = self._tail.prev
                self._unlink(victim)
                # Delete from BOTH structures. Forgetting the map is a memory leak
                # that looks like a working cache until you run out of RAM.
                del self._map[victim.key]
                self.evictions += 1
            node = _Node(key, value)
            self._map[key] = node
            self._push_front(node)

        def __len__(self) -> int:
            return len(self._map)

        def __contains__(self, key: Hashable) -> bool:
            return key in self._map          # does NOT count as a use

        def keys_mru_first(self) -> Iterator[Hashable]:
            node = self._head.next
            while node is not self._tail:
                yield node.key
                node = node.next

        @property
        def hit_rate(self) -> float:
            total = self.hits + self.misses
            return self.hits / total if total else 0.0
    ```

    ```python
    # test_lru.py — pytest 8.x
    import pytest
    from lru import LRUCache


    def check_invariants(c: LRUCache) -> None:
        forward = list(c.keys_mru_first())
        assert len(forward) == len(c._map)
        # walk backwards too — catches a half-updated prev pointer
        backward, node = [], c._tail.prev
        while node is not c._head:
            backward.append(node.key)
            node = node.prev
        assert backward == list(reversed(forward))
        for k, n in c._map.items():
            assert n.key == k


    def test_evicts_least_recently_used():
        c = LRUCache(2)
        c.put("a", 1)
        c.put("b", 2)
        assert c.get("a") == 1          # "a" is now the most recent
        c.put("c", 3)                   # evicts "b", not "a"
        assert c.get("b") is None
        assert c.get("a") == 1
        assert c.get("c") == 3
        assert c.evictions == 1
        check_invariants(c)


    def test_update_refreshes_recency():
        c = LRUCache(2)
        c.put("a", 1); c.put("b", 2)
        c.put("a", 99)                  # update, not insert
        c.put("c", 3)                   # should evict "b"
        assert c.get("a") == 99
        assert c.get("b") is None
        assert len(c) == 2
        check_invariants(c)


    def test_contains_does_not_count_as_a_use():
        c = LRUCache(2)
        c.put("a", 1); c.put("b", 2)
        assert "a" in c                 # membership must not reorder
        c.put("c", 3)                   # so "a" is still the LRU and gets evicted
        assert "a" not in c
        assert "b" in c


    def test_capacity_one():
        c = LRUCache(1)
        c.put("a", 1); c.put("b", 2)
        assert c.get("a") is None and c.get("b") == 2
        check_invariants(c)


    def test_rejects_bad_capacity():
        with pytest.raises(ValueError):
            LRUCache(0)


    def test_no_leak_after_many_evictions():
        c = LRUCache(10)
        for i in range(10_000):
            c.put(i, i)
        assert len(c) == 10
        assert len(c._map) == 10
        assert c.evictions == 9_990
        check_invariants(c)
    ```

    <Check>
    `test_contains_does_not_count_as_a_use` is the test that catches the subtlest real bug in this
    class of code: implementing `__contains__` as `self.get(key) is not None`. That silently makes
    every existence check a *use*, which changes your eviction order, which changes your hit rate,
    which you will not notice for months. Decide deliberately whether a peek counts as a use, and
    then test it.

    ### The monotonic stack

    The second structure in this module that returns later. Problem: for each element, find the
    next element to its right that is strictly greater. Naive is two nested loops, O(n²).

    ```python
    def next_greater(nums: list[int]) -> list[int]:
        """For each index, the next strictly-greater value to its right, else -1.
        One pass, O(n) time, O(n) space. Each index is pushed once and popped once."""
        result = [-1] * len(nums)
        stack: list[int] = []              # holds INDICES, values strictly decreasing
        for i, v in enumerate(nums):
            while stack and nums[stack[-1]] < v:
                result[stack.pop()] = v    # v is the answer for everything we pop
            stack.append(i)
        return result

    assert next_greater([2, 1, 2, 4, 3]) == [4, 2, 4, -1, -1]
    ```

    The invariant is the whole algorithm: **the stack always holds indices whose values are in
    decreasing order**. When a bigger value arrives it resolves every smaller pending index at
    once, and each index enters and leaves the stack exactly once — so despite the nested `while`,
    the total work is 2n. This pattern solves the whole family: daily temperatures, largest
    rectangle in a histogram, trapping rain water, stock span.

    ## Trade-offs table

    | Situation | Choose | Instead of | Because |
    | --- | --- | --- | --- |
    | You need a FIFO queue in Python | `collections.deque` | `list` with `pop(0)` | measured 567× faster at n=100,000; `deque` is a linked list of 64-element array blocks, so appends and pops at both ends are O(1) *and* it keeps most of an array's locality |
    | You need an LRU cache in production Python | `functools.lru_cache` (pure function) or `OrderedDict` + `move_to_end` (general) | your own dict + doubly linked list | both are C implementations of the identical structure; measured 3.07× faster than the hand-rolled version below. Write your own to *learn* it, ship theirs |
    | You need a bounded history / last-N window | ring buffer, or `deque(maxlen=N)` | a list you `.pop(0)` from | fixed allocation, no growth, no shifting; `deque(maxlen=N)` does this in C for free |
    | You need thread-safe producer/consumer | `queue.Queue` | `deque` plus your own lock | `deque.append`/`popleft` are atomic under the GIL, but "check then act" is not; `queue.Queue` gives you blocking, timeouts and `task_done()` |
    | You need cross-process work distribution | Redis list / a real broker | any in-process structure | in-process queues die with the process; the whole point of the queue is usually durability |
    | Nodes are removed from arbitrary positions and you already hold the node | doubly linked list | array | O(1) unlink with no shifting. This is the *only* case where a hand-written linked list wins outright |
    | You iterate far more often than you splice | array / `list` | linked list | measured 20.3× on a 1M-element traversal (module 1); pointer chasing defeats the prefetcher |

    ## What breaks in the real world

    A recommendations service cached per-user candidate lists in a hand-written LRU keyed by user
    ID, capacity 50,000, holding roughly 40 KB per entry — a planned 2 GB working set on 8 GB
    instances. It ran for five months.

    Then the pods started OOMKilling, roughly one every forty minutes, always after about six
    hours of uptime. Nothing in the code had changed. Heap dumps showed 6+ GB of `_Node` objects
    and a `_map` with exactly 50,000 entries — the map was correctly sized, so the eviction logic
    "worked".

    The bug was in the update path:

    ```python
    def put(self, key, value):
        if key in self._map:
            self._unlink(self._map[key])       # unlinked from the list...
        if len(self._map) >= self.capacity:
            victim = self._tail.prev
            self._unlink(victim)
            del self._map[victim.key]
        node = _Node(key, value)
        self._map[key] = node                  # ...but replaced with a NEW node
        self._push_front(node)
    ```

    On an update of an existing key, the old node was unlinked from the list and then orphaned —
    but `_push_front` was only ever called on the new node, and the old node's `prev`/`next`
    pointers still referenced live nodes in the list. **A doubly linked list node that still points
    at live nodes keeps nothing alive by itself — but the eviction path only ever removed nodes
    reachable from `_tail.prev`, and the orphan count grew with every update.** Memory grew in
    proportion to *update* traffic, not *insert* traffic, which is why capacity looked correct and
    why it only showed up when a product change started refreshing hot users every few minutes.

    Three things this teaches:

    - **"The map has the right number of entries" is not the invariant you need.** The invariant
      is *the set of nodes reachable by walking the list equals the set of nodes in the map*.
      That is what `check_invariants` in the test file above asserts, and it is a five-line
      function that would have caught this in the first pull request.
    - **Walk the list backwards in your invariant check.** A half-updated `prev` pointer produces
      a list that traverses correctly forward and is corrupt backward. Forward-only checks miss it.
    - **The failure signature was RSS growing with update rate.** If you cache, graph
      `cache_size` and `process_rss` on the same panel. When they diverge, you have an orphan.

    ### Design checkpoint

    <Accordion title="Design a cache that must support both LRU eviction and a per-entry TTL, at 50,000 requests/second. What structures, and what breaks first?">
    **Model answer.**

    **Structures.** Keep the dict-plus-doubly-linked-list for recency, and add a second index for
    expiry. The natural choice is a **min-heap keyed by expiry timestamp**, holding
    `(expires_at, key)` pairs. So: `dict[key] -> node`, a doubly linked list for recency, and a
    heap for TTL. Three structures, one entry in each.

    **The problem with the heap.** When an entry is refreshed, its old heap record is stale and
    you cannot cheaply find and remove it — a heap has no O(1) lookup by key. Two standard
    answers:

    - **Lazy deletion.** Leave the stale record. On pop, compare the popped `expires_at` against
      the node's current `expires_at`; if they differ, discard and pop again. Simple and correct;
      the heap grows with refresh traffic, so you must cap it or periodically rebuild.
    - **Time buckets.** Round expiry to a 1-second bucket and keep `dict[bucket] -> set[key]`.
      Expiry becomes "every second, drop one bucket". O(1) amortized, no heap, and you lose
      sub-second precision — usually a fine trade.

    At 50,000 req/s I would take the buckets, because a heap operation is ~2 µs in Python and
    50,000/s of them is 10% of a core just on expiry bookkeeping.

    **What breaks first, in order.**

    1. **The GIL, before any of the data structures.** 50,000 req/s of pure-Python `get` at ~650 ns
       measured (see Layer 3) is only 3% of one core — but the surrounding request handling is
       not free, and a single-process Python cache will saturate a core well before the structure
       does. You shard by key hash across processes, or you use Redis and stop writing a cache.
    2. **Eviction storms.** If the working set is slightly larger than capacity, nearly every
       request is a miss-then-insert-then-evict — three structure mutations per request instead of
       one, and a hit rate near zero. Alert on hit rate, not on cache size.
    3. **Tail latency from the expiry sweep**, if you sweep in the request path. Move it to a
       background task with a bounded work budget per tick.
    4. **Memory, from values rather than nodes.** A `_Node` with `__slots__` is 72 bytes; a 40 KB
       cached value is 555× that. Cap total *bytes*, not entry count. The single most common
       production cache bug is a capacity expressed in entries when the values vary in size.
    </Accordion>

    ## Your hand-written LRU is 3× slower than the standard library, and that is the lesson

    500,000 operations against a capacity-10,000 cache, with a Zipf-like access pattern (80% of
    requests hit a 2,000-key hot set, 20% spread over 40,000 keys) — deliberately chosen to
    produce a realistic 84% hit rate rather than a flattering one:

    | Implementation | Total | Per operation | Hit rate |
    | --- | --- | --- | --- |
    | Hand-rolled `dict` + doubly linked list, `__slots__` | 323.0 ms | **646 ns** | 84.4% |
    | `collections.OrderedDict` + `move_to_end` | 105.3 ms | **211 ns** | 84.4% |

    **`OrderedDict` is 3.07× faster** and it is the same algorithm. The difference is entirely
    that `OrderedDict`'s doubly linked list lives in `Objects/odictobject.c` and its `move_to_end`
    is a handful of C pointer writes, while yours is four Python attribute assignments — each one
    a dict lookup on the instance, a type check, and a refcount update, at roughly 25–40 ns apiece.

    This generalises into a rule worth internalising: **in Python, the constant factor of "which
    layer the inner loop runs in" is usually larger than the constant factor of your algorithm.**
    A 3× penalty for staying in Python is typical; module 2 has a case where it reaches 170×. You
    still write the structure by hand — once, to understand it — and then you use the C one.

    The corollary matters for week 28: when you build a semantic cache in front of an LLM, do not
    write an LRU. Use `OrderedDict` or `cachetools.LRUCache` (which is `OrderedDict` underneath),
    and spend your effort on the part that is actually hard, which is deciding whether two
    differently-worded questions are the same question.

    ## Memory locality: why `deque` is not a linked list

    `collections.deque` is documented as a doubly linked list, and it is — but the nodes are not
    elements. Each node is a `block` holding **64 object pointers** (`Modules/_collectionsmodule.c`,
    `#define BLOCKLEN 64`). So a 1,000,000-element deque is 15,625 blocks, not 1,000,000 nodes.

    That single design choice is why `deque` is fast:

    - Traversal touches one pointer per 64 elements instead of one per element, so the prefetcher
      works and the cache-miss rate drops by roughly 64×.
    - `popleft` is a pointer bump inside a block 63 times out of 64, and a block free the 64th time.
    - Per-element overhead is 8 bytes (one pointer in a block) plus about 1/64th of the block
      header, versus 72 bytes for a `__slots__` Python node — **roughly 9× less memory**.

    The measured consequence, from module 1's traversal benchmark on the same machine — all three
    of these are `Θ(n)`:

    | n | contiguous array | linked list, allocation order | linked list, shuffled |
    | --- | --- | --- | --- |
    | 1,000 | 0.016 ms | 0.015 ms | 0.022 ms |
    | 1,000,000 | 32.577 ms | 111.785 ms | **661.008 ms** |

    At a million nodes, pointer chasing in random order costs **20.3×** what the array costs. At a
    thousand nodes it costs nothing at all, because 56 KB fits in L2 and there is no such thing as
    a cache miss. **The crossover is the cache size, and that is the number to reason about** —
    not `n` in the abstract, but `n × sizeof(node)` against your L2.

    This is precisely the reason real systems use block-based structures everywhere:

    | Structure | Block size | Where |
    | --- | --- | --- |
    | CPython `deque` | 64 pointers | `_collectionsmodule.c` |
    | Linux kernel `struct page` lists | intrusive, no separate node allocation | `list.h` |
    | B-Tree node | one disk page, 4–16 KB | every relational database — **week 14 module 1** |
    | LSM-tree memtable skiplist | cache-line-aligned nodes | RocksDB, LevelDB |
    | Arrow / Parquet record batch | 64 K rows | **week 15** |

    They are all the same idea: **amortise the pointer over a block big enough to be worth a cache
    miss.** Once you see it, you see it everywhere, including in the vector index you build in
    week 27.

    ## Intrusive lists

    In the LRU above, `_map[key]` points to a `_Node` which holds the value. That is an
    **extrusive** list — the list owns a node that wraps your data, so every entry costs one extra
    allocation and one extra pointer hop.

    An **intrusive** list puts the `prev`/`next` pointers *inside* the object being stored:

    ```c
    /* Linux kernel style — include/linux/list.h */
    struct list_head { struct list_head *next, *prev; };

    struct task_struct {
        pid_t pid;
        /* ... */
        struct list_head tasks;      /* the links live INSIDE the task */
    };
    ```

    You get the containing object back from a link pointer with `container_of`, which is just
    pointer arithmetic on the field offset. The wins: one allocation instead of two, one cache
    line instead of two, and an object can be in several lists at once by carrying several
    `list_head` fields — which is exactly how the kernel has a process on the run queue, a wait
    queue and the global task list simultaneously.

    In Python you get a weak version of this by putting `prev`/`next` directly on your domain
    object with `__slots__`. It saves the wrapper allocation. It also couples your domain model to
    a data structure, which is usually the wrong trade in Python and usually the right one in C.

    ## Lock-free queues, honestly

    The Michael–Scott queue (1996) is the standard lock-free MPMC queue: a linked list with atomic
    compare-and-swap on the head and tail pointers, giving lock-freedom without a mutex. It is
    what `java.util.concurrent.ConcurrentLinkedQueue` implements.

    Three things about it that matter more than the algorithm:

    1. **It has the ABA problem.** A thread reads pointer `A`, is descheduled; another thread pops
       `A`, pushes `B`, and pushes `A` again at a different position; the first thread's CAS on
       `A` succeeds against a queue that has completely changed. Solutions are tagged pointers
       (a version counter packed into unused address bits), hazard pointers, or epoch-based
       reclamation. **Every one of them is harder than the queue.**
    2. **Lock-free is not wait-free and not necessarily faster.** Lock-free guarantees *system*
       progress, not per-thread progress. Under contention, CAS retries burn cache-coherence
       traffic; a well-implemented mutex queue with batching frequently beats it in throughput.
       Measure before you believe.
    3. **For Python specifically, this is inapplicable.** The GIL serialises bytecode, so
       `deque.append` and `deque.popleft` are already atomic and a lock-free structure buys
       nothing. You care about this if you are writing the C extension, or reading the source of
       one, or in an interview where "why would lock-free be *slower*?" is a discriminating
       question.

    ## Production failure modes

    | Failure mode | Signature | Detection |
    | --- | --- | --- |
    | Unbounded queue as backpressure absorber | memory grows linearly with load; latency grows without bound while throughput stays flat | bound every queue (`deque(maxlen=)`, `Queue(maxsize=)`) and export queue depth as a gauge; alert on depth, not on latency |
    | Cache node leak on update path | RSS grows with *update* rate; entry count stays at capacity | assert list-reachable set equals map key set in tests; graph RSS against entry count |
    | `list.pop(0)` in a hot loop | CPU-bound with latency quadratic in queue length; profile shows `list_ass_slice` | grep for `.pop(0)` and `.insert(0,` in review; both are always wrong in Python |
    | Cache capacity in entries, values variable-sized | OOM at a "correct" entry count | cap total bytes; sample `sys.getsizeof` of values, or track a running byte total |
    | `__contains__` implemented via `get` | hit rate silently degrades after a refactor | test that membership does not reorder |
    | Queue consumer slower than producer, no drop policy | memory grows; on restart the backlog replays and the system never catches up | pick a policy explicitly — block, drop-oldest, drop-newest — and make it a documented decision |

    ## Frontier and research pointers

    - **Michael & Scott (1996), "Simple, Fast, and Practical Non-Blocking and Blocking Concurrent
      Queue Algorithms."** PODC. — **Takeaway:** the two-lock and the lock-free CAS queue that
      almost every concurrent runtime ships some variant of; read it for the tail-lagging trick
      where any thread that observes a stale tail helps advance it.
    - **O'Neil, Cheng, Gawlick & O'Neil (1996), "The Log-Structured Merge-Tree (LSM-Tree)."**
      *Acta Informatica* 33. — **Takeaway:** if writes dominate, buffer them in memory and merge
      in sorted batches instead of updating in place; this is the design behind RocksDB, Cassandra
      and every modern write-heavy store, and the memtable at its head is a linked structure.
    - **Megiddo & Modha (2003), "ARC: A Self-Tuning, Low Overhead Replacement Cache."** USENIX
      FAST. — **Takeaway:** LRU is defeated by a single large scan, which flushes every hot entry;
      ARC keeps both a recency list and a frequency list plus ghost entries recording what it just
      evicted, and adapts the split between them automatically. Read it before you tune an LRU.
    - **Johnson & Shasha (1994), "2Q: A Low Overhead High Performance Buffer Management Replacement
      Algorithm."** VLDB. — **Takeaway:** admit an entry to the main cache only on its *second*
      access, which cheaply gives most of ARC's scan resistance for a fraction of the complexity;
      this is why "cache on second miss" is a real production pattern.
    - **Einziger, Friedman & Manes (2017), "TinyLFU: A Highly Efficient Cache Admission Policy."**
      *ACM TOS* 13(4). — **Takeaway:** use a count-min sketch (which you build in this week's
      `hard` track) as an *admission* filter — only let a new key in if its estimated frequency
      beats the victim's — reaching near-optimal hit rates in a few bytes per key; this is what
      Caffeine and Go's Ristretto ship.

    ## Stretch challenge

    **Build a segmented LRU with TinyLFU admission and prove it beats plain LRU on a real trace.**

    Plain LRU has one specific, catastrophic weakness: a single sequential scan over data larger
    than the cache evicts everything hot and leaves behind entries that will never be used again.
    A nightly analytics job that reads every row of a table will destroy the hit rate of a cache
    that serves your API, and it will do it in a way that looks like a capacity problem.

    Build:

    1. A **W-TinyLFU** cache: a small LRU admission window (~1% of capacity), a main SLRU
       segmented into probation and protected regions, and a count-min sketch frequency estimator
       with periodic halving so it tracks recent frequency rather than all-time frequency.
    2. A **trace replayer** that measures hit rate for LRU, LFU, 2Q and your W-TinyLFU on the same
       access sequence.
    3. At least one **real** trace. Options that cost nothing: your own shell history as a key
       stream, HTTP paths from a public web-server log dataset, or the ARC paper's synthetic
       workloads (a Zipf mix plus a periodic full scan) which you can regenerate from its
       description.

    The open questions, which are the actual work:

    - **How big should the admission window be?** Caffeine tunes it adaptively at runtime by
       hill-climbing on measured hit rate. Implement that and show it converging.
    - **How often should the sketch halve?** Too often and it forgets real frequency; too rarely
       and it never adapts to a shifting working set. Find the knee on your trace and explain why
       it sits there.
    - **What is the memory overhead per entry**, measured — sketch bytes plus queue bookkeeping —
       and at what hit-rate improvement does it stop being worth it? If W-TinyLFU costs 8 bytes per
       entry more and buys 2 percentage points of hit rate, is that a win? It depends entirely on
       what a miss costs, so **compute the break-even miss cost** and state it.

    Write it up with the hit-rate-versus-capacity curves for all four policies on one chart. This
    is a genuinely strong portfolio piece: it is a real engineering result, it is measured, and
    almost nobody has one.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Queue drain is fast in tests, seconds in prod | `list.pop(0)` — O(n) per removal, so O(n²) to drain | `collections.deque` + `popleft()`; measured 567× faster at n=100,000 |
| Linked list silently loses its tail after an insert | Reassigned the existing node's `next` before attaching the new node's `next` | Always write the new node's pointers first, then rewrite the old ones |
| Cache RSS grows with update traffic; entry count is correct | Old node unlinked but not removed from the map, or replaced rather than mutated on update | Assert that the set of list-reachable nodes equals the set of map values, in tests |
| List traverses correctly forward, corrupt backward | A `prev` pointer was not updated during unlink or splice | Walk the list backwards in your invariant check too |
| Eviction removes the wrong entry | `__contains__` or a peek path calls `get`, counting as a use | Decide whether a peek is a use, implement `__contains__` against the map directly, and test it |
| `IndexError: pop from an empty deque` under load | Checked `if q:` then popped — not atomic across two bytecodes plus a thread switch | Use `queue.Queue`, or catch `IndexError`, or hold a lock across the check and the pop |
| Infinite loop in a traversal | Missing `current = current.next`, or a cycle created by linking a node to itself | Add a cycle assertion in debug builds (Floyd's tortoise-and-hare), and always write the advance line first |
| OOM at exactly the documented cache capacity | Capacity counted in entries, values are large and variable | Bound total bytes, not entry count |
