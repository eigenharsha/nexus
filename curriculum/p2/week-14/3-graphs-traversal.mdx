    ## The idea in one paragraph

    A **graph** is just "things, and connections between things". Cities and roads. People and
    friendships. Tasks and their prerequisites. Web pages and links. Once you notice that a problem
    is a graph, you get a large toolbox for free — because the same two traversal algorithms answer
    an enormous range of questions, and they differ by a single word. **Breadth-first search**
    explores outward in rings, so it finds the *shortest* route. **Depth-first search** follows one
    path as far as it goes before backing up, so it is the right shape for "is there any path?",
    "is there a cycle?", and "what order must these run in?".

    ### The analogy

    You are in a building looking for the exit.

    - **BFS.** Check every room one door away. Then every room two doors away. Then three. You need
      to remember a growing list of rooms to visit, but **the first exit you find is the closest
      one**, guaranteed, because you never looked at anything farther before finding it.
    - **DFS.** Pick a corridor and follow it. Follow the next. Keep going until you hit a dead end,
      then back up to the last junction and try a different corridor. Uses far less memory — you
      only remember the path you are on — but the first exit you find might be the farthest one in
      the building.

    **BFS uses a queue** (first in, first out — the oldest room is explored next, keeping you at the
    current ring). **DFS uses a stack** (last in, first out — the newest room is explored next,
    driving you deeper). That is the whole difference.

    ### Every term, defined

    - **Graph** — a set of **nodes** (also called vertices) and **edges** connecting them.
    - **Directed** — edges have a direction. "A follows B" does not imply "B follows A". Drawn with
      arrows.
    - **Undirected** — edges go both ways. "A is friends with B" implies the reverse.
    - **Weighted** — edges carry a number (distance, cost, time). Module 4 handles these.
    - **Neighbour** — a node you can reach in one edge.
    - **Degree** — how many edges touch a node. In a directed graph: **in-degree** (arrows coming
      in) and **out-degree** (arrows going out).
    - **Path** — a sequence of nodes each connected to the next.
    - **Cycle** — a path that returns to where it started.
    - **DAG** — Directed Acyclic Graph: directed, with no cycles. Dependencies, build steps, task
      workflows, and git history are all DAGs.
    - **Connected component** — a group of nodes all reachable from one another.
    - **Adjacency list** — for each node, a list of its neighbours. The default representation.
    - **Adjacency matrix** — an `n × n` grid where cell `(i,j)` says whether an edge exists.
    - **Topological sort** — an ordering of a DAG's nodes such that every edge points forward. "Do
      these tasks in an order that respects every prerequisite."

    ### Representations

    ```python
    # Adjacency list — a dict of node -> list of neighbours.
    graph = {
        "A": ["B", "C"],
        "B": ["D"],
        "C": ["D", "E"],
        "D": ["E"],
        "E": [],
    }

    # The same graph as an adjacency matrix.
    #      A  B  C  D  E
    # A [  0  1  1  0  0 ]
    # B [  0  0  0  1  0 ]
    # C [  0  0  0  1  1 ]
    # D [  0  0  0  0  1 ]
    # E [  0  0  0  0  0 ]
    ```

    | | Adjacency list | Adjacency matrix |
    | --- | --- | --- |
    | Memory | O(V + E) | O(V²) |
    | "Are A and B connected?" | O(degree of A) | **O(1)** |
    | "List A's neighbours" | **O(degree of A)** | O(V) — scan a whole row |
    | Good for | sparse graphs (most real ones) | dense graphs, and small ones |

    **Almost every real graph is sparse**, so the adjacency list is the default and the matrix is
    the exception. A social network with 100 million users where each has 200 friends has
    2×10¹⁰ edges as a list, and 10¹⁶ cells as a matrix. Layer 3 has the measured numbers at a
    scale you can actually run.

    ### The smallest working example

    ```python
    # traverse.py — CPython 3.12
    from collections import deque

    graph = {
        "A": ["B", "C"],
        "B": ["D"],
        "C": ["D", "E"],
        "D": ["E"],
        "E": [],
    }

    def bfs(graph, start):
        """Explore in rings. Uses a QUEUE."""
        visited = {start}
        order = []
        frontier = deque([start])
        while frontier:
            node = frontier.popleft()        # <-- oldest first
            order.append(node)
            for nb in graph[node]:
                if nb not in visited:
                    visited.add(nb)          # mark when ENQUEUED, not when dequeued
                    frontier.append(nb)
        return order

    def dfs(graph, start):
        """Follow one path as deep as it goes. Uses a STACK."""
        visited = set()
        order = []
        frontier = [start]
        while frontier:
            node = frontier.pop()            # <-- newest first
            if node in visited:
                continue
            visited.add(node)
            order.append(node)
            for nb in reversed(graph[node]):  # reversed so we pop in original order
                if nb not in visited:
                    frontier.append(nb)
        return order

    print(bfs(graph, "A"))   # ['A', 'B', 'C', 'D', 'E']
    print(dfs(graph, "A"))   # ['A', 'B', 'D', 'E', 'C']
    ```

    ### Line-by-line walkthrough

    - `frontier = deque([start])` versus `frontier = [start]` — a deque for BFS (O(1) `popleft`; a
      list would be O(n), and week 13 measured that at 567× slower) and a plain list for DFS, where
      `pop()` from the end is already O(1).
    - **`node = frontier.popleft()` versus `node = frontier.pop()` is the entire algorithmic
      difference.** Everything else is identical. Read those two functions side by side until that
      is obvious, because it is the most reusable fact in this module.
    - **In BFS, mark visited when you *enqueue*, not when you dequeue.** If you mark on dequeue, a
      node with three incoming edges gets enqueued three times before it is ever processed. On a
      dense graph that is a memory blowup, and it is the classic BFS bug.
    - **In DFS, check visited when you *pop*.** A node can legitimately be pushed several times
      before it is first popped; skipping it on pop is the simplest correct handling.
    - `reversed(graph[node])` — cosmetic. A stack reverses order, so reversing on push restores the
      natural order in the output. Correctness does not depend on it.
    - `bfs` gives `A, B, C, D, E` — A first, then everything one step away (B, C), then two steps
      (D, E). `dfs` gives `A, B, D, E, C` — it dives A→B→D→E, hits a dead end, then backs all the
      way up to try C.

    ### BFS gives shortest paths on unweighted graphs

    ```python
    def shortest_path(graph, start, goal):
        """Fewest edges from start to goal. Returns the path, or None."""
        if start == goal:
            return [start]
        parent = {start: None}
        frontier = deque([start])
        while frontier:
            node = frontier.popleft()
            for nb in graph[node]:
                if nb not in parent:
                    parent[nb] = node
                    if nb == goal:
                        # Walk the parent chain back and reverse it.
                        path = [goal]
                        while parent[path[-1]] is not None:
                            path.append(parent[path[-1]])
                        return path[::-1]
                    frontier.append(nb)
        return None

    print(shortest_path(graph, "A", "E"))   # ['A', 'C', 'E']
    ```

    **Why BFS is correct here and DFS is not.** BFS visits nodes strictly in order of distance from
    the start: everything at distance 1, then everything at distance 2, and so on. So the first time
    you reach the goal, you reached it by a shortest route — there is no shorter one, because you
    would have found it in an earlier ring. DFS has no such guarantee; it might reach the goal down
    a 40-hop detour while a 2-hop route exists.

    <Warning>
    **This holds only for unweighted graphs** — or, equivalently, when every edge costs the same.
    The moment edges have different weights, "fewest edges" and "lowest total cost" diverge, and you
    need Dijkstra (module 4). Using BFS on a weighted graph is a correctness bug that produces a
    plausible-looking wrong answer, which is the worst kind.
    </Warning>

    ### Checkpoint — 5 questions before you continue

    <AccordionGroup>
      <Accordion title="1. What is the only difference between BFS and DFS in code?">
        Whether the frontier is a queue or a stack — `popleft()` versus `pop()`. Everything else
        is identical. That one word determines whether you explore in rings or dive down branches,
        and therefore whether the first path you find is the shortest.
      </Accordion>
      <Accordion title="2. Why does BFS find shortest paths but DFS doesn't?">
        Because BFS visits nodes in non-decreasing order of distance from the start — all of
        distance 1, then all of distance 2, and so on. The first time it reaches the goal, no
        shorter path can exist, because a shorter one would have been found in an earlier ring. DFS
        visits in an order determined by the graph's structure and may reach the goal by a long
        route first.
      </Accordion>
      <Accordion title="3. When should you use an adjacency matrix?">
        When the graph is **dense** (E close to V²), when V is small enough that V² is affordable,
        or when you need O(1) "is there an edge between A and B?" queries. Also when you want to do
        linear algebra on it — a matrix representation lets you compute path counts by matrix
        powers, and it is how PageRank is expressed. Otherwise, adjacency list.
      </Accordion>
      <Accordion title="4. How do you detect a cycle in a DIRECTED graph?">
        Two standard ways. **Kahn's algorithm:** repeatedly remove nodes with in-degree 0; if you
        cannot place every node, the leftovers form the cycle. **DFS with three colours:** white
        (unvisited), grey (on the current recursion stack), black (finished) — finding a grey node
        means you have found a back edge, and that is a cycle. Both are O(V + E). Kahn's gives you a
        topological order for free; the DFS version gives you the cycle path more directly.
      </Accordion>
      <Accordion title="5. Why can't you use the directed cycle-detection method on an undirected graph?">
        Because in an undirected graph every edge A–B is reachable in both directions, so the trivial
        "walk to B then back to A" looks like a cycle to a naive algorithm. For undirected graphs
        you track the *parent* you came from and ignore it: seeing any already-visited node that is
        not your immediate parent means a real cycle. Union-find also works and is often cleaner.
      </Accordion>

    ## Topological sort, and why it is cycle detection

    **Kahn's algorithm** in full:

    ```python
    from collections import deque

    def topological_sort(graph: dict) -> list | None:
        """Return an order where every edge points forward, or None if a cycle exists.

        This is simultaneously a topological sort AND a cycle detector, because
        the exact condition for a topological order to exist is acyclicity.
        """
        in_degree = {node: 0 for node in graph}
        for node in graph:
            for nb in graph[node]:
                in_degree[nb] += 1

        # Everything with no prerequisites can start immediately.
        ready = deque(n for n in graph if in_degree[n] == 0)
        order = []
        while ready:
            node = ready.popleft()
            order.append(node)
            for nb in graph[node]:
                in_degree[nb] -= 1        # one prerequisite satisfied
                if in_degree[nb] == 0:
                    ready.append(nb)      # all prerequisites satisfied

        # If we could not place every node, the leftovers are in (or downstream of) a cycle.
        return order if len(order) == len(graph) else None

    build = {
        "app":    ["bundle"],
        "styles": ["bundle"],
        "bundle": ["deploy"],
        "tests":  ["deploy"],
        "deploy": [],
    }
    print(topological_sort(build))   # ['app', 'styles', 'tests', 'bundle', 'deploy']

    cyclic = {"a": ["b"], "b": ["c"], "c": ["a"]}
    print(topological_sort(cyclic))  # None
    ```

    **The two algorithms are the same algorithm.** A topological order exists if and only if the
    graph is acyclic. Kahn's produces the order when there is one and fails when there is not, and
    the failure is informative: the nodes it could not place are exactly the nodes in cycles, plus
    everything downstream of them.

    ### Printing the actual cycle

    "There is a cycle" is a useless error message. Users need "`auth` → `db` → `cache` → `auth`".
    The three-colour DFS gives you the path directly:

    ```python
    def find_cycle(graph: dict) -> list | None:
        """Return one cycle as a list of nodes, or None. O(V + E)."""
        WHITE, GREY, BLACK = 0, 1, 2
        colour = {n: WHITE for n in graph}
        parent: dict = {}

        def walk(start):
            # Iterative DFS: a recursive version dies at ~1,000 nodes deep.
            stack = [(start, iter(graph.get(start, ())))]
            colour[start] = GREY
            while stack:
                node, children = stack[-1]
                advanced = False
                for nb in children:
                    if colour.get(nb, WHITE) == GREY:
                        # Back edge into a node on the current path: cycle found.
                        cycle = [nb]
                        cur = node
                        while cur != nb:
                            cycle.append(cur)
                            cur = parent[cur]
                        cycle.append(nb)
                        return list(reversed(cycle))
                    if colour.get(nb, WHITE) == WHITE:
                        parent[nb] = node
                        colour[nb] = GREY
                        stack.append((nb, iter(graph.get(nb, ()))))
                        advanced = True
                        break
                if not advanced:
                    colour[node] = BLACK
                    stack.pop()
            return None

        for n in graph:
            if colour[n] == WHITE:
                c = walk(n)
                if c:
                    return c
        return None

    deps = {"auth": ["db"], "db": ["cache"], "cache": ["auth"], "web": ["auth"]}
    print(find_cycle(deps))     # ['auth', 'db', 'cache', 'auth']
    ```

    **Grey means "on the current path".** Reaching a grey node is a back edge, and the cycle is the
    portion of the current path from that node onward. Reaching a *black* node is fine — you have
    fully explored it and it led nowhere back — which is exactly why two colours are insufficient
    and everyone's first attempt reports false cycles on diamond-shaped DAGs.

    <Warning>
    The recursive version of this is four lines shorter and will crash. CPython's default recursion
    limit is 1,000, so a dependency chain 1,000 deep raises `RecursionError`. A `node_modules` tree
    or a deeply nested workflow easily exceeds that. **Write graph traversals iteratively when the
    depth is data-dependent**, which for graphs it always is.
    </Warning>

    ## Union-find (disjoint set union)

    For "are these two things in the same group?" and "merge these two groups", union-find beats
    traversal.

    ```python
    class UnionFind:
        """Path compression + union by rank => near-constant amortized operations.

        Formally O(alpha(n)) where alpha is the inverse Ackermann function.
        alpha(n) <= 4 for every n that fits in the universe, so: constant.
        """

        __slots__ = ("parent", "rank", "count")

        def __init__(self, n: int) -> None:
            self.parent = list(range(n))    # each element is its own root
            self.rank = [0] * n             # upper bound on tree height
            self.count = n                  # number of disjoint sets

        def find(self, x: int) -> int:
            # Path compression: re-point every node on the path directly at the root.
            root = x
            while self.parent[root] != root:
                root = self.parent[root]
            while self.parent[x] != root:
                self.parent[x], x = root, self.parent[x]
            return root

        def union(self, a: int, b: int) -> bool:
            """Returns False if they were already connected — which is a cycle."""
            ra, rb = self.find(a), self.find(b)
            if ra == rb:
                return False
            # Union by rank: attach the shorter tree under the taller one.
            if self.rank[ra] < self.rank[rb]:
                ra, rb = rb, ra
            self.parent[rb] = ra
            if self.rank[ra] == self.rank[rb]:
                self.rank[ra] += 1
            self.count -= 1
            return True

        def connected(self, a: int, b: int) -> bool:
            return self.find(a) == self.find(b)
    ```

    **Both optimisations are required.** Path compression alone gives `O(log n)`. Union by rank
    alone gives `O(log n)`. Together they give `O(α(n))`, effectively constant — a genuinely
    surprising result (Tarjan, 1975) and one of the few places where two independent tricks combine
    to beat either.

    `union` returning `False` is the cycle detector for undirected graphs: if two nodes are already
    connected and you are adding an edge between them, that edge closes a cycle. This is exactly how
    Kruskal's minimum-spanning-tree algorithm works, which you will meet in module 4.

    | Problem | Union-find | BFS/DFS |
    | --- | --- | --- |
    | Static connectivity, one query | either | simpler |
    | **Many** connectivity queries | **O(α) each** | O(V+E) each |
    | Edges arriving incrementally | **natural** | rebuild every time |
    | Edges being *removed* | **cannot do it** | fine |
    | Need the actual path | cannot | **yes** |

    **Union-find cannot handle deletion.** If your edges can disappear, you need a different
    structure (or to rebuild). This is the constraint that decides the choice more often than
    performance does.

    ## Trade-offs table

    | Situation | Choose | Instead of | Because |
    | --- | --- | --- | --- |
    | Sparse graph (E much less than V²) | adjacency list | matrix | O(V+E) vs O(V²); measured 23.9× less memory at 100k nodes / 1M edges |
    | Dense graph, or V under ~5,000 | matrix (bitset) | list | O(1) edge queries, and V² bits is small when V is small |
    | Shortest path, unweighted | BFS | DFS or Dijkstra | correct by construction, and simpler than Dijkstra with no heap |
    | Shortest path, weighted, non-negative | Dijkstra (module 4) | BFS | BFS counts edges, not cost — a plausible-looking wrong answer |
    | "Does any path exist?" | DFS | BFS | uses O(depth) memory instead of O(width); on a wide graph BFS's frontier can be most of the graph |
    | Cycle detection with the path needed | 3-colour DFS | Kahn's | Kahn's tells you *that* there is a cycle; DFS hands you the node sequence |
    | Cycle detection plus an execution order | Kahn's | 3-colour DFS | one pass gives both, and it is iterative by nature |
    | Incremental connectivity | union-find | re-running BFS | O(α) per operation versus O(V+E) per query |
    | Connectivity with edge removal | BFS/DFS, or a link-cut tree | union-find | union-find has no un-union operation |
    | Very deep graphs | iterative traversal | recursion | CPython raises `RecursionError` at ~1,000 frames |

    ## Reference implementation: a dependency-cycle detector

    ```python
    # depcycle.py — CPython 3.12. Find cycles in a real package dependency tree.
    from __future__ import annotations
    import json
    import sys
    from collections import deque
    from pathlib import Path


    def load_lockfile(path: Path) -> dict[str, list[str]]:
        """Build a dependency graph from a package-lock.json (lockfileVersion 2/3)."""
        data = json.loads(path.read_text())
        graph: dict[str, list[str]] = {}
        for name, meta in data.get("packages", {}).items():
            key = name or "<root>"
            deps = list(meta.get("dependencies", {}))
            deps += list(meta.get("peerDependencies", {}))
            graph[key] = deps
        # Any package that is only ever a target must still be a node.
        for deps in list(graph.values()):
            for d in deps:
                graph.setdefault(d, [])
        return graph


    def find_all_cycles(graph: dict[str, list[str]], limit: int = 20) -> list[list[str]]:
        """Report up to `limit` distinct cycles. Iterative three-colour DFS."""
        WHITE, GREY, BLACK = 0, 1, 2
        colour: dict[str, int] = {n: WHITE for n in graph}
        parent: dict[str, str] = {}
        cycles: list[list[str]] = []
        seen_signatures: set[frozenset[str]] = set()

        for root in graph:
            if colour[root] != WHITE:
                continue
            colour[root] = GREY
            stack: list[tuple[str, object]] = [(root, iter(graph.get(root, ())))]
            while stack:
                node, children = stack[-1]
                advanced = False
                for nb in children:
                    c = colour.get(nb, WHITE)
                    if c == GREY:
                        cycle = [nb]
                        cur = node
                        while cur != nb:
                            cycle.append(cur)
                            cur = parent[cur]
                        cycle.reverse()
                        sig = frozenset(cycle)
                        if sig not in seen_signatures:
                            seen_signatures.add(sig)
                            cycles.append(cycle + [nb])
                            if len(cycles) >= limit:
                                return cycles
                    elif c == WHITE:
                        parent[nb] = node
                        colour[nb] = GREY
                        stack.append((nb, iter(graph.get(nb, ()))))
                        advanced = True
                        break
                if not advanced:
                    colour[node] = BLACK
                    stack.pop()
        return cycles


    def build_order(graph: dict[str, list[str]]) -> list[str] | None:
        """Kahn's algorithm. Returns None if the graph is cyclic."""
        indeg = {n: 0 for n in graph}
        for n in graph:
            for nb in graph[n]:
                indeg[nb] += 1
        ready = deque(sorted(n for n in graph if indeg[n] == 0))  # sorted => deterministic
        order: list[str] = []
        while ready:
            n = ready.popleft()
            order.append(n)
            for nb in graph[n]:
                indeg[nb] -= 1
                if indeg[nb] == 0:
                    ready.append(nb)
        return order if len(order) == len(graph) else None


    if __name__ == "__main__":
        g = load_lockfile(Path(sys.argv[1]))
        print(f"{len(g)} packages, {sum(len(v) for v in g.values())} edges")
        cycles = find_all_cycles(g)
        if not cycles:
            order = build_order(g)
            print(f"acyclic; install order has {len(order)} steps")
        else:
            print(f"{len(cycles)} cycle(s) found:")
            for c in cycles:
                print("  " + " -> ".join(c))
            sys.exit(1)
    ```

    ## What breaks in the real world

    A data platform ran nightly transformation jobs described in YAML: each job listed the tables it
    read and the table it wrote. The scheduler built a graph and ran jobs in dependency order.

    An engineer added a job that enriched `customers` using an aggregate over `orders` — and
    `orders` already had a job that joined against `customers` for currency conversion. A cycle:
    `customers → orders → customers`.

    The scheduler used Kahn's algorithm and correctly failed to produce an order. Its error handling
    was:

    ```python
    order = topological_sort(graph)
    if order is None:
        logger.error("dependency cycle detected")
        order = list(graph)          # <-- fall back to declaration order and hope
    ```

    **The fallback is the bug.** It ran the jobs in YAML file order, which was alphabetical. Jobs
    read stale upstream tables. The output was not an error — it was *plausible numbers*, computed
    from the previous night's data for one table and today's for another. Finance reported the
    discrepancy eleven days later, and the reconciliation cost more engineering time than the
    original feature.

    The error message did not help either. `dependency cycle detected` — with 340 jobs, nobody knew
    which two. Finding the cycle by hand took most of a day.

    The fix was three things, and all three matter:

    1. **Fail the build, do not fall back.** A cycle is a configuration error. Refusing to run is
       the correct behaviour; running in an arbitrary order and producing wrong numbers is not.
    2. **Print the cycle path.** `customers -> orders -> customers` turns a day of investigation
       into thirty seconds. This is the whole reason to use the three-colour DFS alongside Kahn's.
    3. **Move the check into CI.** The graph is built from files in the repo, so the cycle is
       detectable at pull-request time. It became a required check and the class of bug disappeared.

    What generalises: **an error message naming the specific entities is worth an order of magnitude
    more than one naming the category.** "Dependency cycle detected" is a category. "`customers →
    orders → customers`, introduced in `orders_currency.yml`" is an entity, and the difference is a
    day of someone's life. **You will make this exact decision in week 30** when validating an
    agent's step graph.

    ### Design checkpoint

    <Accordion title="You are building a workflow engine where users define step graphs in a UI. 50,000 workflows, up to 500 steps each, edited constantly. How do you guarantee no workflow ever executes a cycle?">
    **Model answer.**

    **Validate on write, not on execute.** Every save runs a cycle check on that workflow's graph.
    500 nodes is `O(V+E)` — microseconds. The API returns 400 with the cycle path, and the UI
    highlights those edges in red. **A cycle should be impossible to save**, which is a far stronger
    guarantee than "impossible to run" and it puts the error in front of the person who caused it,
    while they are still looking at it.

    **But validate on execute too.** Two reasons. First, the graph may reference *other* workflows —
    a step that invokes workflow B, which invokes C, which invokes A. That cross-workflow cycle is
    not visible when saving A. Second, workflows saved before you shipped the check exist in the
    database. Defence in depth: cheap check on write for good errors, cheap check on execute for
    safety.

    **The cross-workflow graph is the real problem.** With 50,000 workflows that can invoke each
    other, saving one workflow can create a cycle in the *global* invocation graph. Options:

    - **Recompute the global graph on every save.** 50,000 nodes, `O(V+E)` — still milliseconds.
      Viable, and I would start here because it is simple and obviously correct.
    - **Incremental check.** A new edge `A → B` creates a cycle if and only if `A` is already
      reachable from `B`. So run one DFS from `B` looking for `A`, which touches only `B`'s
      descendants. Faster in the common case, worse in the worst case, more code. **Do this only
      when the simple version is measurably too slow**, and it will not be at this scale.
    - **Maintain a topological order incrementally** (Pearce & Kelly, 2006). Genuinely clever,
      genuinely more code, and unnecessary below millions of edges.

    **Runtime guards regardless of static validation**, because static analysis cannot see
    everything:

    - **A step budget per execution.** Even an acyclic graph can be huge, and a conditional edge or
      a dynamic step target can create a runtime loop the static check never saw. Hard-cap total
      steps and fail with a clear error.
    - **A depth budget** for nested workflow invocations.
    - **Idempotency keys** so a retried execution does not double-apply effects.

    **The thing I would fight for in the design review:** the API must return the cycle *path*, and
    the UI must highlight it. This is the difference between a feature users can debug themselves
    and one that generates support tickets. It costs one extra function — the three-colour DFS —
    that you have already written.

    **Where the analogy to week 30 lands:** an agent's step graph has exactly this shape, and a
    cycle there means the agent loops, calling tools and burning tokens until a budget stops it.
    Static validation before execution is much cheaper than a token budget discovering it at
    runtime.
    </Accordion>

    ## Representation memory at scale

    Measured with a recursive `sys.getsizeof` walk over the Python objects, against the theoretical
    matrix sizes:

    | Nodes | Edges | Adjacency list (Python dict of lists) | Bitset matrix (V²/8 bytes) | Dense byte matrix (V²) | list advantage |
    | --- | --- | --- | --- | --- | --- |
    | 10,000 | 100,000 | 4.9 MB | 12.5 MB | 100.0 MB | **2.53×** |
    | 100,000 | 1,000,000 | 52.3 MB | **1,250.0 MB** | 10,000.0 MB | **23.89×** |

    <Info>
    Method: CPython 3.12.9, adjacency list as `dict[int, list[int]]` measured by recursive
    `sys.getsizeof` with cycle detection; matrix figures computed as `V²/8` and `V²` bytes since
    allocating them was not feasible. Reproduce with `extra_dsa.py w14m3`.
    </Info>

    **The advantage grows with V, not with E.** The list is `O(V + E)` and the matrix is `O(V²)`, so
    a 10× increase in nodes at constant density multiplies the gap by 10. At a million nodes the
    bitset matrix would be 125 GB and the list around 500 MB.

    **When the matrix wins**, and it genuinely does sometimes:

    - **V is small.** A 1,000-node matrix is 125 KB as a bitset — it fits in L2, and edge queries
      are a single bit test. For all-pairs shortest paths (Floyd–Warshall, `O(V³)`) on 1,000 nodes,
      the matrix is unambiguously right.
    - **The graph is dense.** At E ≈ V²/2 the list stores two integers per edge (16+ bytes) where
      the matrix stores one bit.
    - **You want linear algebra.** PageRank, spectral clustering and graph neural networks are all
      matrix operations. A `scipy.sparse` CSR matrix is the middle ground: adjacency-list memory
      with matrix-operation semantics, and it is what you should reach for in practice.

    **The Python overhead is the hidden cost of the list.** 52.3 MB for 1M edges is ~52 bytes per
    edge — a `list` object header plus an 8-byte pointer plus a 28-byte `int` object. The same graph
    as two NumPy arrays in CSR form (`indptr` int32, `indices` int32) is 4 MB + 0.4 MB = **4.4 MB,
    about 12× smaller than the dict-of-lists.** If your graph is large, the representation decision
    that matters most is not list-versus-matrix, it is Python-objects-versus-flat-arrays.

    ## Traversal throughput

    | Operation | Scale | Time | Per edge |
    | --- | --- | --- | --- |
    | BFS from one source, full traversal | 100,000 nodes, 1,000,000 undirected edges (2M directed) | 159.4 ms | **80 ns** |
    | Kahn's topological sort, acyclic | 200,000 nodes, 599,998 edges | 135.1 ms | 225 ns |
    | Kahn's with a cycle injected (detects and reports) | same graph + 1 back edge | 179.5 ms | 299 ns |

    <Info>
    Method: CPython 3.12.9, M3 Pro, best-of-3, adjacency list as `list[list[int]]`, `collections.deque`
    frontier. The BFS reached all 100,000 nodes. Reproduce with `extra_dsa.py w14m3`.
    </Info>

    **80 ns per edge is the number to carry.** It tells you that a million-edge traversal is ~160 ms
    in Python — fine for a request-scoped operation, too slow for a per-request hot path, and
    hopeless for a 100-million-edge graph (13 seconds). Above roughly 10 million edges you want
    `scipy.sparse.csgraph`, `rustworkx`, or to keep the graph in a database that traverses for you.

    **Cycle detection costs 33% more than a clean topological sort**, not 2×. Kahn's does the same
    in-degree pass either way; the extra time is the failed `len(order) == len(graph)` path plus the
    slightly different memory access pattern. **Cycle detection is essentially free** — which
    removes the last excuse for the war story's "log it and continue".

    ## Traversal order and cache behaviour

    Both BFS and DFS are `O(V + E)`, and they are not equally fast on the same graph.

    - **BFS's frontier can be enormous.** On a graph with high branching factor, the queue holds an
      entire level. For a social graph with average degree 200, level 3 is roughly 8 million nodes —
      the frontier alone is hundreds of megabytes and every `popleft` touches a cache-cold node.
    - **DFS's stack is O(depth)**, typically far smaller. But DFS's *access pattern* jumps around the
      graph arbitrarily, so it has poor locality too.
    - **Neither has good locality on a graph stored as scattered Python objects.** The 80 ns/edge
      above is dominated by pointer chasing — this is week 13 module 1's 20.3× result, appearing
      again.

    The production answer for large graphs is to **renumber nodes so that neighbours are numerically
    close**, then store the graph in CSR arrays. A breadth-first or Cuthill–McKee relabelling
    clusters each node's neighbours into a contiguous slice of the `indices` array, so expanding a
    node reads one or two cache lines instead of `degree` scattered ones. Reported speedups in the
    graph-processing literature are 2–5× on large graphs from relabelling alone, with no change to
    the algorithm. This is the same "make the data contiguous" move as B-Tree pages and `deque`
    blocks.

    ## Union-find: why α(n) is genuinely constant

    Tarjan (1975) proved that `m` union-find operations on `n` elements with path compression and
    union by rank cost `O(m · α(n))`, where α is the inverse Ackermann function.

    ```
    α(n) = 1   for n ≤ 2
    α(n) = 2   for n ≤ 4
    α(n) = 3   for n ≤ 16
    α(n) = 4   for n ≤ 2^65536
    ```

    There are roughly 10⁸⁰ atoms in the observable universe. `2^65536` is unimaginably larger.
    **α(n) ≤ 4 for any input that can physically exist**, so treating union-find as constant-time is
    correct in every practical sense — while remaining, strictly, not constant. Fredman & Saks
    (1989) proved the α bound is optimal for any pointer-based structure, so this is not a gap
    waiting to be closed.

    **Both optimisations are required.** Path compression alone: `O(log n)` amortized. Union by rank
    alone: `O(log n)` worst case. Together: `O(α(n))`. Neither result predicts the other, which is
    what makes the combined proof famous.

    A practical note: **union by *size* is usually better than union by rank** in real code. Rank is
    an upper bound on height that becomes stale after path compression, whereas size is always
    exact, and size is often independently useful ("how big is this component?"). The asymptotics
    are identical.

    ## Production failure modes

    | Failure mode | Signature | Detection |
    | --- | --- | --- |
    | `RecursionError` in a graph traversal | crashes on deep inputs only; passes every small test | write traversals iteratively; test with a 10,000-deep chain |
    | Two-colour cycle detection | false cycles reported on diamond-shaped DAGs | use three colours; test the diamond `a→b→d`, `a→c→d` |
    | Cycle detected but not reported by path | hours of manual investigation per incident | three-colour DFS alongside Kahn's; print the node sequence |
    | Cycle detected, then falling back to an arbitrary order | silently wrong output, discovered days later | fail closed; a cycle is a configuration error, not a warning |
    | BFS marking visited on dequeue | memory grows to O(E) instead of O(V); duplicates in the frontier | mark on enqueue; assert `len(frontier) <= V` |
    | Grid traversal with negative indices | islands on opposite edges merge; wrong answer, no error | bounds-check before indexing; test with land on the first and last rows |
    | Adjacency matrix on a sparse graph | O(V²) memory; OOM as V grows | measured 23.9× at 100k nodes; use a list or `scipy.sparse` |
    | Union-find without path compression | operations degrade to O(log n) or worse | assert the tree depth stays under a small constant in tests |
    | Union-find where edges must be removed | there is no `un-union`; the model is simply wrong | use BFS/DFS, or rebuild, or a link-cut tree |
    | Traversal of a huge graph in Python | 80 ns/edge means 100M edges is 13 s | `scipy.sparse.csgraph` or `rustworkx`; or push it into the database |

    ## Frontier and research pointers

    - **Kahn (1962), "Topological sorting of large networks."** *CACM* 5(11). — **Takeaway:**
      repeatedly emitting zero-in-degree nodes both produces a topological order and detects
      acyclicity, because the two properties are equivalent; the leftovers are the cycle.
    - **Tarjan (1972), "Depth-First Search and Linear Graph Algorithms."** *SIAM J. Comput.* 1(2). —
      **Takeaway:** DFS with discovery/low-link numbers computes strongly connected components,
      bridges and articulation points in a single `O(V+E)` pass; this is the paper that made DFS a
      general technique rather than a traversal.
    - **Tarjan (1975), "Efficiency of a Good But Not Linear Set Union Algorithm."** *JACM* 22(2). —
      **Takeaway:** path compression plus union by rank gives `O(m·α(n))`, and α is bounded by 4 for
      any conceivable input — the definitive "not technically constant, constant in practice" result.
    - **Fredman & Saks (1989), "The cell probe complexity of dynamic data structures."** STOC. —
      **Takeaway:** the α(n) bound is optimal — no pointer-based union-find can do better, so this
      is not a gap awaiting a cleverer algorithm.
    - **Pearce & Kelly (2006), "A Dynamic Topological Sort Algorithm for Directed Acyclic Graphs."**
      *ACM JEA* 11. — **Takeaway:** you can maintain a topological order incrementally as edges
      arrive, touching only the affected region rather than resorting — the right algorithm for a
      workflow engine at very large scale, and overkill below it.
    - **Beamer, Asanović & Patterson (2012), "Direction-Optimizing Breadth-First Search."** SC12. —
      **Takeaway:** on graphs with a large frontier, switching BFS from top-down (expand the
      frontier) to bottom-up (have unvisited nodes look for a visited parent) gives multi-fold
      speedups; it is the algorithm behind the Graph500 benchmark leaders and a lovely example of an
      optimisation that only exists once you think about the *frontier size* rather than the
      asymptotics.

    **Build a cycle detector for a real dependency ecosystem and quantify how common cycles are.**

    Cycles in dependency graphs are widely assumed to be rare. Find out whether that is true.

    Build:

    1. A loader for at least two ecosystems: `package-lock.json` (npm), `poetry.lock` or
       `uv.lock` (Python), `Cargo.lock` (Rust), or the Go module graph from `go mod graph`. Each has
       a different notion of a dependency edge — dev, peer, optional, build — and **which edges you
       include changes the answer**, which is itself part of the finding.
    2. Three-colour DFS reporting every distinct cycle, plus Tarjan's SCC algorithm, which gives you
       all strongly connected components in one pass and is the more general tool. Compare them.
    3. A survey harness that runs across many real lockfiles — the top 500 npm packages, or every
       lockfile in your own organisation.

    The open questions:

    - **How common are cycles, really?** npm's peer-dependency graph is notoriously cyclic; Cargo
      forbids cycles in normal dependencies but allows them via dev-dependencies. Get numbers.
    - **Which edge types create them?** If 95% of cycles come from peer or dev dependencies, then
      "no cycles in the runtime graph" may be true while "no cycles in the full graph" is false —
      and package managers exploit exactly this distinction.
    - **How large are the SCCs?** A 2-node cycle is a design smell. A 40-node strongly connected
      component means forty packages that cannot be built, versioned or reasoned about
      independently. Plot the SCC size distribution.
    - **Does it scale?** At 80 ns per edge, a 10-million-edge graph is 0.8 seconds in Python.
      Compare against `rustworkx` (pin `rustworkx==0.15.1`) and `scipy.sparse.csgraph` and report
      the speedup — this is the practical question of whether Python is the right tool for graph
      work at your scale.

    The write-up — "how cyclic is the npm dependency graph, and which edge types cause it" — is a
    genuinely original empirical result, it is cheap to produce, and it is exactly the kind of thing
    that gets read.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| `RecursionError` on real data, never in tests | Recursive DFS on a graph deeper than ~1,000 | Iterative traversal with an explicit stack; test a 10,000-deep chain |
| Cycle reported on a diamond-shaped DAG | Two-colour DFS: "already visited" conflated with "on the current path" | Three colours — white, grey, black; grey means on the stack |
| BFS memory blows up on a dense graph | Marking visited on dequeue rather than enqueue | Mark when you enqueue; a node then enters the frontier exactly once |
| Islands on opposite grid edges merge | Negative indices are valid in Python and wrap to the far side | Bounds-check `0 <= r < rows and 0 <= c < cols` before indexing |
| Shortest path is not shortest | DFS used, or BFS used on a *weighted* graph | BFS for unweighted; Dijkstra the moment weights differ |
| Only one component gets traversed | Traversal started from a single node, not looped over all unvisited nodes | Outer loop over every node whose colour is still white |
| Union-find is slow | Missing path compression, or missing union by rank/size | Both are required for O(α(n)); each alone gives O(log n) |
| Topological sort output differs between runs | Iteration order of a set, or of a dict populated in varying order | Sort the ready queue if determinism matters; test that two runs agree |
| Cycle detected, pipeline runs anyway | Error handling falls back to an arbitrary order | Fail closed; report the cycle path |
| Graph traversal is too slow at scale | 80 ns/edge in Python means 100M edges is 13 s | `scipy.sparse.csgraph`, `rustworkx`, or the database |

**Primary docs**

- [`collections.deque`](https://docs.python.org/3.12/library/collections.html#collections.deque) — read this for the O(1) `popleft` that makes BFS's frontier viable; a `list` here is O(n) per removal and was measured 567× slower in week 13.
- [`scipy.sparse.csgraph`](https://docs.scipy.org/doc/scipy-1.14.1/reference/sparse.csgraph.html) (SciPy 1.14.1) — read this for `connected_components`, `breadth_first_order` and `shortest_path` over a CSR matrix; it is the right answer once your graph exceeds a few million edges and it is already installed.
- [`rustworkx` 0.15.1](https://www.rustworkx.org/) — read the migration notes from NetworkX; it implements the same API surface in Rust and is 10–100× faster on large graphs, which is the practical alternative when SciPy's shape does not fit.
- [`sys.setrecursionlimit`](https://docs.python.org/3.12/library/sys.html#sys.setrecursionlimit) — read this to understand why raising the limit is *not* the fix: the real constraint is the C stack, and a high limit converts a `RecursionError` into a segfault.
- [npm `package-lock.json` format](https://docs.npmjs.com/cli/v10/configuring-npm/package-lock-json) — read this for the `packages` map in lockfileVersion 2/3 and the distinction between `dependencies`, `devDependencies`, `peerDependencies` and `optionalDependencies`; which of these you treat as edges changes the graph.

**Papers**

- [Kahn (1962), *Topological sorting of large networks*, CACM 5(11), 558–562.](https://doi.org/10.1145/368996.369025) — **Takeaway:** peeling zero-in-degree nodes yields a topological order, and failing to place every node is exactly the condition for a cycle — one algorithm, two answers.
- [Tarjan (1972), *Depth-First Search and Linear Graph Algorithms*, SIAM J. Comput. 1(2), 146–160.](https://doi.org/10.1137/0201010) — **Takeaway:** DFS annotated with discovery and low-link numbers yields SCCs, bridges and articulation points in a single linear pass.
- [Tarjan (1975), *Efficiency of a Good But Not Linear Set Union Algorithm*, JACM 22(2), 215–225.](https://doi.org/10.1145/321879.321884) — **Takeaway:** path compression and union by rank together give `O(m·α(n))`, and α(n) ≤ 4 for any input that can exist.
- [Fredman & Saks (1989), *The cell probe complexity of dynamic data structures*, STOC.](https://doi.org/10.1145/73007.73040) — **Takeaway:** the inverse-Ackermann bound is optimal, so union-find is as fast as any pointer-based structure can be.
- [Pearce & Kelly (2006), *A Dynamic Topological Sort Algorithm for Directed Acyclic Graphs*, ACM JEA 11.](https://doi.org/10.1145/1187436.1210590) — **Takeaway:** maintaining a topological order incrementally touches only the affected region, which is what a large workflow engine needs and what a small one does not.
- [Beamer, Asanović & Patterson (2012), *Direction-Optimizing Breadth-First Search*, SC12.](https://doi.org/10.1109/SC.2012.50) — **Takeaway:** when the frontier is large, having unvisited vertices search for a visited parent beats expanding the frontier; the insight comes from thinking about frontier size rather than asymptotic cost.

**Go deeper**

- [Sedgewick & Wayne, *Algorithms* 4th ed., **Chapter 4 (Graphs)**](https://algs4.cs.princeton.edu/home/) — the best-organised treatment of graph algorithms for practitioners; sections 4.1–4.2 cover exactly this module and the API design is worth stealing.
- [Skiena, *The Algorithm Design Manual* 3rd ed., **Chapters 5–6**](https://www.algorist.com/) — read this specifically for the "graph modelling" section, which is a catalogue of how real problems map onto graph formulations; it is the skill this module is actually teaching.
- [Tim Roughgarden, *Algorithms Illuminated Part 2: Graph Algorithms and Data Structures*](https://www.algorithmsilluminated.org/) — read chapter 8 for the clearest available explanation of why BFS gives shortest paths, with the layer-by-layer invariant stated properly.
