    ## The idea in one paragraph

    Sometimes you do not need everything in order — you only need to know **what comes next**. A
    hospital triage desk does not rank all 200 waiting patients; it needs the most urgent one, right
    now, and it needs that to stay true as new patients arrive. A **heap** is the structure for
    exactly this. It keeps one guarantee — the smallest (or largest) item is at a known position —
    and it deliberately keeps everything else only loosely arranged, because maintaining a *loose*
    arrangement is far cheaper than maintaining a *sorted* one. That trade is the entire idea:
    give up full order, keep the extreme, and both insert and remove cost `log n` instead of `n`.

    ### The analogy

    A pyramid of people where the rule is: **everyone must be shorter than the people below them.**

    - The shortest person in the whole pyramid is necessarily at the top. You can see them instantly.
    - Nobody claims the second row is sorted, or that the left side is shorter than the right. The
      rule is only ever about a person and the people directly below them.
    - **A new person arrives.** Put them at the bottom, then let them climb: compare with the person
      above, swap if they are shorter, repeat. They rise at most as many times as the pyramid is
      tall — about `log₂ n` swaps.
    - **The top person leaves.** Move the very last person up to the top (they are almost certainly
      too tall), then let them sink: compare with the two below, swap with the *shorter* of them,
      repeat. Again at most `log₂ n` swaps.

    Keeping this loose rule is cheap. Keeping everyone fully sorted would mean shuffling half the
    pyramid on every arrival.

    ### Every term, defined

    - **Heap** — a binary tree where every parent satisfies an ordering rule against its children.
    - **Min-heap** — every parent is `≤` both children. The minimum is at the root.
    - **Max-heap** — every parent is `≥` both children. The maximum is at the root.
    - **Heap property** — that parent/child rule. Note what it does *not* say: nothing about
      siblings, and nothing about non-adjacent nodes. `[1, 5, 2, 8, 9, 3]` is a valid min-heap.
    - **Complete binary tree** — every level is full except possibly the last, which fills left to
      right. Heaps are always complete, and that is what lets them live in an array with no gaps.
    - **Sift up (bubble up)** — move a too-small node toward the root by swapping with its parent.
    - **Sift down (heapify down)** — move a too-large node toward the leaves by swapping with its
      smaller child.
    - **Heapify** — turn an arbitrary array into a heap. Done bottom-up it is O(n).
    - **Priority queue** — the *interface*: `push(item, priority)` and `pop_highest_priority()`.
      A heap is the usual implementation, but not the only one.

    ### The array trick

    This is the part that surprises people. **A heap needs no pointers at all.** Because the tree is
    complete, you can number the nodes level by level, left to right, and store them in a flat array:

    ```
                  1                     index:  0  1  2  3  4  5  6
                /   \                   array: [1, 3, 2, 7, 5, 4, 6]
               3     2
              / \   / \
             7   5 4   6
    ```

    And then the tree structure is pure arithmetic:

    ```
    left child of i  = 2*i + 1
    right child of i = 2*i + 2
    parent of i      = (i - 1) // 2
    ```

    Check it: node at index 1 (value 3) has children at 3 and 4, which hold 7 and 5. Correct. Node
    at index 4 has parent at `(4-1)//2 = 1`. Correct.

    **Why this matters beyond elegance:** no pointer means no per-node allocation, no 16 bytes of
    child pointers, and — the big one — **the whole structure is contiguous in memory**. After
    week 13 module 1, you know what that is worth: the same `Θ(n)` traversal over contiguous memory
    was measured 20.3× faster than over scattered nodes. A heap gets that for free.

    ### The smallest working example

    ```python
    # tiny_heap.py — CPython 3.12
    def sift_up(heap, i):
        """Move heap[i] up until its parent is <= it."""
        while i > 0:
            parent = (i - 1) // 2
            if heap[parent] <= heap[i]:
                break                                    # property restored
            heap[parent], heap[i] = heap[i], heap[parent]
            i = parent

    def sift_down(heap, i):
        """Move heap[i] down until both children are >= it."""
        n = len(heap)
        while True:
            smallest = i
            left, right = 2 * i + 1, 2 * i + 2
            if left < n and heap[left] < heap[smallest]:
                smallest = left
            if right < n and heap[right] < heap[smallest]:
                smallest = right
            if smallest == i:
                break                                    # property restored
            heap[i], heap[smallest] = heap[smallest], heap[i]
            i = smallest

    def push(heap, item):
        heap.append(item)              # put it at the end (the next free leaf)
        sift_up(heap, len(heap) - 1)   # let it climb

    def pop(heap):
        smallest = heap[0]             # the answer is always at index 0
        last = heap.pop()              # remove the final leaf
        if heap:                       # (if the heap is not now empty)
            heap[0] = last             # move it to the root
            sift_down(heap, 0)         # let it sink
        return smallest


    h = []
    for v in [5, 3, 8, 1, 9, 2]:
        push(h, v)
    print(h)                            # [1, 3, 2, 5, 9, 8]  <- a valid heap, NOT sorted
    print([pop(h) for _ in range(6)])   # [1, 2, 3, 5, 8, 9]  <- sorted, one pop at a time
    ```

    ### Line-by-line walkthrough

    - `parent = (i - 1) // 2` — integer division. For `i = 1` and `i = 2` this gives 0, which is
      correct: both are children of the root.
    - `if heap[parent] <= heap[i]: break` — the moment the property holds, stop. On average a pushed
      item rises only a level or two, which is why push is fast in practice despite the `log n`
      bound.
    - **`sift_down` must compare against both children and swap with the smaller.** If you swap with
      the larger, you place a bigger value above a smaller sibling and break the property on the
      other side. This is the single most common heap bug.
    - `if left < n` — the bounds check. In a complete tree stored in an array, a node has children
      only if the computed indices are inside the array. Omit this and you get `IndexError` on
      every leaf.
    - `last = heap.pop()` then `heap[0] = last` — removing the *root* directly would leave a hole
      in the middle of the array. Instead you remove the *last* element (free, no shifting) and put
      it at the root, then let it sink. The array stays gap-free, which is what keeps the index
      arithmetic valid.
    - `print(h)` shows `[1, 3, 2, 5, 9, 8]` — **not sorted**, and correctly so. 9 sits before 8.
      The heap only ever promises index 0.

    ### In real code: use `heapq`

    ```python
    import heapq

    h = []
    heapq.heappush(h, 5)
    heapq.heappush(h, 1)
    print(heapq.heappop(h))          # 1

    data = [9, 4, 7, 1, 8, 2]
    heapq.heapify(data)              # in place, O(n)
    print(data[0])                   # 1

    print(heapq.nsmallest(3, data))  # [1, 2, 4]
    print(heapq.nlargest(3, data))   # [9, 8, 7]
    ```

    `heapq` is a **min-heap only.** For a max-heap, negate the priorities:

    ```python
    heapq.heappush(h, (-priority, item))     # highest priority pops first
    ```

    ### Priorities and payloads

    A common need is "store an item, ordered by a separate priority". Use a tuple — Python compares
    tuples element by element:

    ```python
    import heapq, itertools

    tasks = []
    counter = itertools.count()          # a unique, always-increasing tiebreaker

    def add(priority, name):
        heapq.heappush(tasks, (priority, next(counter), name))

    add(3, "write tests")
    add(1, "fix the outage")
    add(2, "review PR")
    add(1, "call the customer")          # SAME priority as the outage

    while tasks:
        pri, _, name = heapq.heappop(tasks)
        print(pri, name)
    # 1 fix the outage
    # 1 call the customer
    # 2 review PR
    # 3 write tests
    ```

    <Warning>
    **The counter is not optional.** Without it, two tasks with equal priority make Python fall
    through to comparing the third element — the name. For strings that happens to work. For a
    dict, a custom object, or anything without `__lt__`, it raises `TypeError`. And this only fires
    on an exact priority tie, so it passes every test and then breaks in production the first time
    two things are equally urgent. The counter also gives you FIFO ordering within a priority level,
    which is almost always what you want anyway.
    </Warning>

    ### Guided practice

    ```python
    def merge_intervals(intervals: list[list[int]]) -> list[list[int]]:
        """Merge all overlapping intervals. [[1,3],[2,6],[8,10]] -> [[1,6],[8,10]]

        The whole algorithm is: sort by start, then walk once, extending the
        last kept interval whenever the next one starts before it ends.
        """
        if not intervals:
            return []
        intervals = sorted(intervals, key=lambda x: x[0])
        merged = [intervals[0][:]]
        for start, end in intervals[1:]:
            last = merged[-1]
            # TODO 1: if this interval starts at or before last's end, they overlap:
            #         extend last's end to the max of the two ends
            # TODO 2: otherwise, there is a gap: start a new interval
            pass
        return merged

    print(merge_intervals([[1,3],[2,6],[8,10],[15,18]]))  # [[1,6],[8,10],[15,18]]
    print(merge_intervals([[1,4],[4,5]]))                  # [[1,5]]  — touching counts
    print(merge_intervals([[1,4],[2,3]]))                  # [[1,4]]  — fully contained
    print(merge_intervals([]))                             # []
    ```

    <AccordionGroup>
      <Accordion title="Answers">
      ```python
      if start <= last[1]:            # TODO 1
          last[1] = max(last[1], end)
      else:                           # TODO 2
          merged.append([start, end])
      ```

      **`max(last[1], end)` and not just `end`.** The case that breaks the naive version is a fully
      contained interval: `[[1,10],[2,3]]`. After sorting, `last` is `[1,10]` and the next is
      `[2,3]`. Writing `last[1] = end` would *shrink* the merged interval to `[1,3]`, silently
      losing coverage. `max` is what keeps it correct. This is the single most common bug in
      interval merging and it is invisible unless a test contains a contained interval.

      **`start <= last[1]` and not `<`.** Whether `[1,4]` and `[4,5]` merge into `[1,5]` depends on
      whether intervals are closed or half-open, which is a *domain* question, not a coding one. For
      meeting rooms, a meeting ending at 4:00 and one starting at 4:00 do not conflict, so you want
      `<`. For merging coverage ranges, they are contiguous and should merge, so you want `<=`.
      **Decide deliberately and write it in the docstring**, because the reviewer cannot tell which
      you meant.

      **The complexity** is `O(n log n)` for the sort and then `O(n)` for the single pass. The sort
      dominates. And notice the shape: *sort, then one pass* is the answer to almost every interval
      problem, because sorting by start time makes "does it overlap the previous one?" a purely
      local question.
      </Accordion>

    ### Checkpoint — 5 questions before you continue

    <AccordionGroup>
      <Accordion title="1. Is a heap sorted?">
        No. Only the root is guaranteed. `[1, 5, 2, 8, 9, 3]` is a valid min-heap and 5 comes before
        2. Sorted order costs `n` pops at `log n` each — that is heapsort, `O(n log n)`.
      </Accordion>
      <Accordion title="2. Why does a heap need no pointers?">
        Because a heap is always a *complete* binary tree, so numbering nodes level by level leaves
        no gaps, and the parent/child relationships become arithmetic: children of `i` are `2i+1`
        and `2i+2`. The tree is implicit in the indices. This also makes the whole structure
        contiguous in memory, which is worth a large constant factor.
      </Accordion>
      <Accordion title="3. In sift_down, why must you swap with the SMALLER child?">
        Because after the swap, the value you moved up becomes the parent of the other child too. If
        you swap with the larger child, the value now at the parent position is larger than the
        remaining sibling, and you have broken the heap property on that side. Swapping with the
        smaller child guarantees the new parent is `≤` both.
      </Accordion>
      <Accordion title="4. How do you get a max-heap out of Python's `heapq`?">
        Negate the priority: `heappush(h, (-p, count, item))`. For floats be careful with `NaN`
        (which compares False with everything and silently corrupts the heap) and `-0.0`. If you
        only need the top K, `heapq.nlargest` avoids the whole issue.
      </Accordion>
      <Accordion title="5. When would a heap be the wrong choice for a priority queue?">
        When you need to **change or cancel** a priority already in the queue. A binary heap has no
        O(1) way to find an arbitrary item, so `decrease_key` requires either an external index map
        or lazy deletion. It is also wrong when priorities are a small fixed set — with 8 priority
        levels, 8 FIFO queues plus a bitmask is O(1) for everything and is what real OS schedulers
        use.
      </Accordion>
    </AccordionGroup>

    ## Why bottom-up heapify is O(n)

    Building a heap by pushing `n` items one at a time is `O(n log n)`. Building it bottom-up is
    `O(n)`. The proof is a two-line counting argument and it is worth being able to produce.

    `heapify` sifts *down* from the last internal node backwards to the root:

    ```python
    def heapify(a):
        # Everything from len(a)//2 onward is a leaf — already a valid heap of size 1.
        for i in range(len(a) // 2 - 1, -1, -1):
            sift_down(a, i)
    ```

    Count the work by level, from the bottom:

    | Level from the bottom | Number of nodes | Max sift distance | Work |
    | --- | --- | --- | --- |
    | 0 (leaves) | n/2 | 0 | 0 |
    | 1 | n/4 | 1 | n/4 |
    | 2 | n/8 | 2 | 2n/8 |
    | h | n/2^(h+1) | h | h·n/2^(h+1) |

    ```
    Total = Σ (h from 0 to log n) of  h · n / 2^(h+1)
          = (n/2) · Σ h/2^h
          = (n/2) · 2                     [the series Σ h/2^h converges to 2]
          = n
    ```

    **The intuition is better than the algebra: half the nodes are leaves and do zero work.** Only
    one node — the root — can sift the full `log n` distance. The expensive nodes are rare and the
    cheap nodes are everywhere. Pushing one at a time inverts this: every pushed item starts at the
    bottom, which is where the tree is *deepest*, so the expensive case is the common case.

    Measured on the reference machine:

    | n | `heapq.heapify` | n successive `heappush` | Speedup |
    | --- | --- | --- | --- |
    | 100,000 | 2.0 ms (20 ns/element) | 6.5 ms (65 ns/element) | **3.23×** |
    | 1,000,000 | 22.7 ms (23 ns/element) | 42.0 ms (42 ns/element) | **1.85×** |

    <Info>
    Method: CPython 3.12.9, M3 Pro, best-of-3, identical input data. Both are C implementations, so
    this measures the algorithms rather than the interpreter. Reproduce with `extra_dsa.py w14m2`.
    </Info>

    The theoretical ratio at n = 10⁶ is `log₂(10⁶)/1 ≈ 20`, and the measured ratio is 1.85. **The
    theory is right and the measurement is right; they are answering different questions.** `heapify`
    is `O(n)` in *comparisons*, but both versions must touch all `n` elements, and at a million
    elements memory bandwidth dominates the comparison count. The 3.23× at 100,000 (where everything
    fits in L2) versus 1.85× at 1,000,000 (where it does not) shows the effect directly: **the
    algorithmic win shrinks as the data leaves cache.** Use `heapify` when you have all the data —
    it is free and strictly better — but do not expect a 20× win.

    ## The stale-entry problem in a real scheduler

    Priority queues in production need to change or cancel entries. A binary heap cannot find an
    arbitrary item, so there are two standard answers.

    **Lazy deletion** — mark the entry dead and skip it on pop:

    ```python
    import heapq, itertools

    class ScheduledQueue:
        """Priorities can be updated or cancelled. Stale entries are skipped on pop."""

        _REMOVED = object()

        def __init__(self) -> None:
            self._heap: list[list] = []
            self._entries: dict[object, list] = {}   # task -> its heap entry
            self._counter = itertools.count()

        def add(self, task, priority: float) -> None:
            if task in self._entries:
                self.remove(task)
            entry = [priority, next(self._counter), task]
            self._entries[task] = entry
            heapq.heappush(self._heap, entry)

        def remove(self, task) -> None:
            entry = self._entries.pop(task)
            entry[2] = self._REMOVED       # mutate in place: the heap still holds this list

        def pop(self):
            while self._heap:
                priority, _, task = heapq.heappop(self._heap)
                if task is not self._REMOVED:
                    del self._entries[task]
                    return task
            raise KeyError("pop from an empty priority queue")

        def __len__(self) -> int:
            return len(self._entries)      # LIVE entries, not heap size
    ```

    <Warning>
    `len(self._entries)` is the live count; `len(self._heap)` includes tombstones. **Export both.**
    If the heap grows without the live count growing, you have a churn problem and the heap will
    consume memory proportional to your total update volume rather than your working set. The fix
    is a periodic rebuild when `len(heap) > 2 * len(entries)` — the same live-versus-total decision
    as the tombstone bug in week 13 module 4, in a different structure.
    </Warning>

    **Indexed heap (`decrease_key`)** — keep a `task -> heap position` map, updated on every swap.
    Then updating a priority is `O(log n)` with no garbage. It is what a textbook Dijkstra assumes.
    It is also more code, and every swap must update two structures atomically, which is a bug
    surface. **In practice almost everyone uses lazy deletion**, including most real Dijkstra
    implementations — module 4 does exactly this.

    ## The sweep line

    Every interval problem is the same algorithm: turn each interval into two *events*, sort the
    events, sweep.

    ```python
    def max_concurrent_meetings(intervals: list[tuple[int, int]]) -> int:
        """Minimum number of rooms needed. O(n log n)."""
        events: list[tuple[int, int]] = []
        for start, end in intervals:
            events.append((start, +1))     # a meeting begins
            events.append((end, -1))       # a meeting ends
        # Critical: at the same timestamp, process ENDS before STARTS, so a room
        # freed at 10:00 is reused by a meeting starting at 10:00. -1 sorts before
        # +1 automatically, which is why the delta is the second tuple element.
        events.sort()
        current = best = 0
        for _, delta in events:
            current += delta
            best = max(best, current)
        return best

    assert max_concurrent_meetings([(0, 30), (5, 10), (15, 20)]) == 2
    assert max_concurrent_meetings([(7, 10), (2, 4)]) == 1
    assert max_concurrent_meetings([(1, 5), (5, 9)]) == 1      # touching, not overlapping
    ```

    The tie-break comment is the whole subtlety. `(10, -1)` sorts before `(10, +1)` because `-1`
    is less than `+1`, so ends are processed first and the room is reused. Flip that and
    `[(1,5),(5,9)]` reports 2 rooms instead of 1. **Whether that is a bug depends on your domain** — for CPU reservations
    you may genuinely need the resource held through the boundary — so make it explicit and test it.

    The same sweep, with different accumulators, answers: minimum meeting rooms, maximum concurrent
    connections, peak memory in an allocation trace, and "how many servers do I need at peak".

    ## Reference implementation: bounded priority queue for k-NN

    ```python
    # bounded_pq.py — CPython 3.12. The week-27 brute-force baseline.
    from __future__ import annotations
    import heapq
    import itertools
    from typing import Any, Iterator


    class BoundedPriorityQueue:
        """Keep the K items with the HIGHEST score, in O(K) memory.

        Internally a MIN-heap of size <= K: the root is the worst item kept,
        which is exactly the admission threshold. This is the structure HNSW
        uses for its result set during graph traversal.
        """

        __slots__ = ("_k", "_heap", "_counter", "seen", "admitted")

        def __init__(self, k: int) -> None:
            if k <= 0:
                raise ValueError("k must be positive")
            self._k = k
            self._heap: list[tuple[float, int, Any]] = []
            self._counter = itertools.count()
            self.seen = 0
            self.admitted = 0

        def offer(self, score: float, item: Any) -> bool:
            """Returns True if the item was kept. False means it did not clear the bar."""
            self.seen += 1
            if len(self._heap) < self._k:
                heapq.heappush(self._heap, (score, next(self._counter), item))
                self.admitted += 1
                return True
            if score > self._heap[0][0]:
                heapq.heapreplace(self._heap, (score, next(self._counter), item))
                self.admitted += 1
                return True
            return False

        @property
        def threshold(self) -> float:
            """Nothing scoring below this can be admitted. HNSW uses exactly this
            value to decide when to stop expanding the graph frontier."""
            return self._heap[0][0] if len(self._heap) == self._k else float("-inf")

        @property
        def is_full(self) -> bool:
            return len(self._heap) == self._k

        def best_first(self) -> list[tuple[float, Any]]:
            return [(s, it) for s, _, it in sorted(self._heap, reverse=True)]

        def __len__(self) -> int:
            return len(self._heap)

        def __iter__(self) -> Iterator[tuple[float, Any]]:
            return iter(self.best_first())
    ```

    ```python
    # test_bounded_pq.py — pytest 8.x
    import random
    import pytest
    from bounded_pq import BoundedPriorityQueue


    def test_keeps_exactly_the_top_k():
        data = [(random.random(), i) for i in range(10_000)]
        q = BoundedPriorityQueue(50)
        for s, i in data:
            q.offer(s, i)
        assert q.best_first() == sorted(data, reverse=True)[:50]


    def test_memory_is_bounded():
        q = BoundedPriorityQueue(10)
        for i in range(1_000_000):
            q.offer(float(i), i)
        assert len(q) == 10


    def test_threshold_is_the_worst_kept():
    ```

    when the best remaining candidate is worse than the result set's threshold. If `threshold`
    returned a real value before the queue was full, the search would terminate early and silently
    return fewer than K neighbours — a **recall** bug, not a crash, and therefore one you would

    ## Trade-offs table

    | Situation | Choose | Instead of | Because |
    | --- | --- | --- | --- |
    | You have all the data up front | `heapq.heapify` | n successive pushes | O(n) vs O(n log n); measured 3.23× at 100k, 1.85× at 1M |
    | You need the top K of a large stream | bounded heap / `heapq.nlargest` | sort then slice | O(K) memory instead of O(n); measured 27.8× less memory at n = 10⁷ (week 13 M5) |
    | Priorities are a small fixed set (say 8 levels) | array of FIFO queues + bitmask | a heap | O(1) for everything; this is what OS schedulers do |
    | You must update or cancel queued items | lazy deletion with a `task -> entry` map | an indexed heap with `decrease_key` | far less code and no invariant to maintain across swaps; rebuild when tombstones exceed live entries |
    | You need the median or an arbitrary quantile continuously | two heaps (max-heap of the lower half, min-heap of the upper) | sorting repeatedly | O(log n) per insert, O(1) to read the median |
    | You need `merge` of two queues in O(log n) | pairing heap or Fibonacci heap | binary heap | binary heap merge is O(n); in practice measure first, because Fibonacci heaps rarely win |
    | Interval overlap, count or capacity questions | sweep line over sorted events | nested comparison of every pair | O(n log n) vs O(n²), and the same code shape answers the whole family |
    | Priority queue across processes | Redis sorted set / a real broker | any in-process heap | durability and multiple consumers are the actual requirements |

    ## What breaks in the real world

    A job runner scheduled retries with a `heapq` keyed on `(next_attempt_at, job_id)`. When a job
    was cancelled, the code removed it from the jobs table but left the heap entry — the classic
    lazy-deletion design, and the pop loop correctly skipped entries whose job no longer existed.

    The bug was in the *retry* path. On failure, a job was rescheduled with a new backoff:

    ```python
    heapq.heappush(self._heap, (next_attempt_at, job_id))
    ```

    The **old** entry was never removed or marked. A job that failed 12 times had 12 entries in the
    heap, 11 of them stale. Correctness was fine — the pop loop skipped stale entries by checking
    the job's current `next_attempt_at` against the popped one.

    Then an upstream dependency started failing, and roughly 400,000 jobs entered exponential
    backoff. Each retry pushed a new entry without removing the old. Over six hours the heap grew
    to **19 million entries** for about 400,000 live jobs. Memory went from 200 MB to 4.1 GB.

    The failure was not the memory. It was that **the pop loop had to skip an average of 47 stale
    entries to find one live job**, and each skip is a `heappop` — a `log n` sift-down over a
    19-million-element heap. Scheduling throughput fell from 8,000 jobs/second to 170. **The
    scheduler became the bottleneck during the incident it was supposed to help recover from**,
    and the retry storm could not drain.

    The fix was two changes:

    ```python
    # 1. Mark the previous entry dead when rescheduling.
    if job_id in self._entries:
        self._entries[job_id][-1] = self._REMOVED

    # 2. Rebuild when the heap is mostly garbage.
    if len(self._heap) > 2 * len(self._entries):
        self._heap = [e for e in self._heap if e[-1] is not self._REMOVED]
        heapq.heapify(self._heap)          # O(n), which is why this is cheap
    ```

    What generalises:

    - **Lazy deletion needs a compaction policy, always.** The technique is fine; the technique
      *without a rebuild trigger* is an unbounded memory leak whose growth rate is your update rate.
      This is the same shape as the tombstone bug in week 13 module 4, and recognising it as the
      same shape is the point.
    - **The rebuild is cheap precisely because `heapify` is O(n).** Filtering and re-heapifying 19
      million entries is about 400 ms. Doing it once an hour is nothing. Not doing it cost an outage.
    - **The metric that would have caught it is `len(heap) / len(live)`.** Export the ratio for
      every structure that uses lazy deletion. Alert above 2.

    ### Design checkpoint

    <Accordion title="Design the rate limiter for an API with 50,000 tenants, each with their own limit, at 200,000 requests/second total. Where does a heap belong, and where does it not?">
    **Model answer.**

    **Where a heap does not belong: the request path.** The obvious design is a min-heap of
    `(next_refill_time, tenant)` so a background sweeper refills buckets in order. At 200,000 req/s
    that heap is being mutated 200,000 times a second, each mutation is `O(log 50,000) ≈ 16` swaps,
    and every one takes a lock. **The heap becomes a single contended structure on the hot path,
    which is the thing you are least allowed to have.**

    **What to build instead: lazy token buckets with no timer at all.** Store per tenant
    `(tokens: float, last_refill: float)` in a flat hash map. On a request, compute the refill
    *arithmetically*:

    ```python
    now = time.monotonic()
    elapsed = now - state.last_refill
    state.tokens = min(capacity, state.tokens + elapsed * rate)
    state.last_refill = now
    allowed = state.tokens >= 1.0
    if allowed:
        state.tokens -= 1.0
    ```

    No heap, no sweeper, no timers, no background thread. **The refill is a multiplication.** A
    tenant idle for an hour is refilled correctly on its next request, in O(1), the first time
    anyone asks. This is what every production rate limiter does, and the insight is that a
    continuous process does not need discrete events to model it.

    **Where a heap does belong here: eviction of idle tenant state.** With 50,000 active tenants
    but potentially millions of tenant IDs over time, you need to drop cold state. A bounded LRU
    (week 13 module 3) is the better fit; a heap keyed by `last_seen` would need `decrease_key` on
    every request, which is exactly the contention you just avoided.

    **What breaks first, in order.**

    1. **Lock contention on the hash map.** 200,000 req/s of read-modify-write on shared state. In
       Python the GIL serialises it anyway, so you shard by tenant hash across processes — but note
       that sharding means a tenant's limit is enforced per shard unless you route consistently by
       tenant, which is a **routing** requirement, not a data-structure one, and it is the real
       design decision in this problem.
    2. **Clock. Use `time.monotonic()`, never `time.time()`.** An NTP step backward makes `elapsed`
       negative and, with the `min(capacity, ...)`, silently grants a burst — or with a naive
       implementation, permanently corrupts the bucket. This is a real outage class.
    3. **Memory.** 50,000 tenants × (float, float, key) is a few megabytes. Not the constraint.
       Cold-tenant accumulation is, hence the LRU.
    4. **Fairness at the boundary.** A fixed-window limiter lets a tenant send 2× the limit across a
       window boundary. Token buckets do not have this problem, which is the main reason to prefer
       them over the simpler counter.

    **The summary line for a design review:** "a heap is the right structure when you must repeatedly
    ask *what is next*; it is the wrong structure when the answer can be computed from a timestamp."
    </Accordion>

    ## The brute-force k-NN baseline for week 27

    In week 27 you will build an HNSW index and be asked whether it was worth it. That question is
    only answerable against a measured brute-force baseline, so here it is: **1,000,000 vectors of
    dimension 64, float32, find the top 10 by dot product.**

    | Stage | Time | Note |
    | --- | --- | --- |
    | Matrix–vector product (`mat @ q`), NumPy | **7.9 ms** | 256 MB of float32, one BLAS call |
    | Then: full `np.sort` of all 1M scores, take last 10 | 21.9 ms | O(n log n) |
    | Then: `np.argpartition(scores, -10)[-10:]` | **3.1 ms** | O(n), **7.0× faster than sorting** |
    | Then: `heapq.nlargest(10, scores.tolist())` | 23.4 ms | leaves NumPy, pays boxing |
    | **Total query: score + argpartition** | **11.0 ms** | |

    And for contrast, the same scoring done in pure Python:

    | Approach | Time for 1M vectors |
    | --- | --- |
    | Pure Python dot products (measured on 50,000, extrapolated) | **3.4 s** |
    | NumPy `mat @ q` | 7.9 ms |
    | | **434× faster** |

    <Info>
    Method: CPython 3.12.9, NumPy 2.1.3, M3 Pro (Accelerate BLAS), best-of-3, seeded RNG,
    `argpartition` and `sort` verified to return the same top-10 set. Reproduce with
    `fixups.py vectors`.
    </Info>

    Three things to carry into week 27.

    **1. Brute force over a million vectors is 11 ms.** That is a perfectly serviceable latency for
    many products. **Before you add an approximate index, a dependency, an index build step and a
    recall regression, check whether 11 ms was already fine.** The honest crossover for HNSW is
    somewhere in the 10⁵–10⁷ vector range depending on dimension and latency budget, and below it
    the index is strictly worse on every axis including correctness.

    **2. `argpartition` beats `sort` by 7.0× and this is the same lesson as the bounded heap.**
    Both are "you asked for the top K, do not produce a total order". `np.argpartition` is
    introselect (quickselect with a median-of-medians fallback) — `O(n)` average, and it rearranges
    the array only enough to guarantee that position `-K` is correct with everything larger to its
    right. It does not sort those K, which is why you sort the 10 survivors afterwards if you need
    them ordered — `O(K log K)` on ten elements is free.

    **3. `heapq.nlargest` on `.tolist()` is 7.5× slower than `argpartition`**, despite being the
    right algorithm, because `.tolist()` boxes a million floats into Python objects. **Once your
    data is in NumPy, leaving NumPy is the expensive operation** — more expensive than most
    algorithmic choices you could make inside it. This is the single most common performance mistake
    in numerical Python, and you will meet it again in week 16.

    ## Where the bounded heap actually goes in HNSW

    HNSW search maintains two priority queues, and understanding why there are two is most of
    understanding the algorithm:

    - **The candidate queue** — a *min*-heap by distance (closest first). "Which node do I explore
      next?" This is unbounded in principle and drains as the search proceeds.
    - **The result set** — a *max*-heap by distance of size at most `ef` (equivalently, the
      bounded-top-K queue above, with score = negative distance). "What is the best I have found?"

    The termination condition is the interesting part:

    ```
    while candidates is not empty:
        c = closest candidate
        if distance(c) > threshold(results):   # the worst thing I am keeping
            break                              # nothing left can improve the result set
        ... expand c's neighbours ...
    ```

    **`threshold(results)` is exactly the `threshold` property on the `BoundedPriorityQueue`
    above.** The search stops when the nearest unexplored candidate is farther than the worst kept
    result — because the graph is (approximately) navigable, so nothing beyond it can be closer.
    That is the entire pruning rule, and it is why `ef` trades recall against latency: a larger `ef`
    means a looser threshold, more expansion, better recall, more time.

    **The bug that this creates**, and which you will hit in week 27: if `threshold` returns a real
    value before the result set is full, the loop breaks early and returns fewer than `k` neighbours
    with silently degraded recall. Hence `float("-inf")` until full, and hence the test.

    ## Fibonacci heaps: the theory that mostly does not pay

    | Operation | Binary heap | Binomial | Fibonacci | Pairing |
    | --- | --- | --- | --- | --- |
    | `find_min` | O(1) | O(log n) | **O(1)** | O(1) |
    | `insert` | O(log n) | O(log n) | **O(1)** am. | O(1) |
    | `extract_min` | O(log n) | O(log n) | O(log n) am. | O(log n) am. |
    | `decrease_key` | O(log n) | O(log n) | **O(1)** am. | O(log n) am. (conjectured better) |
    | `merge` | O(n) | O(log n) | **O(1)** | O(1) |

    Fibonacci heaps give Dijkstra `O(E + V log V)` instead of `O((V+E) log V)`, which for a dense
    graph is a genuine asymptotic improvement. **They are almost never used.** The reasons are worth
    knowing because they are the standard reasons a theoretically-better structure loses:

    - **Constant factors.** Each node carries a parent pointer, a child pointer, two sibling
      pointers, a degree and a mark bit — roughly 5× the memory of a heap array entry, all of it
      pointer-chasing (week 13 module 1: 20.3×).
    - **Amortized, not worst-case.** The `O(1)` `decrease_key` is amortized; individual operations
      can trigger a long cascading-cut sequence. Unusable where tail latency matters.
    - **`decrease_key` has to be *reachable*.** You need a handle to the node, which means
      maintaining an external map — and once you have that map, the binary heap's `O(log n)`
      `decrease_key` is available too.
    - **Measured comparisons consistently favour binary or pairing heaps** on real graph sizes.
      Larkin, Sen & Tarjan's 2014 experimental study is the standard reference and its conclusion
      is blunt: the simple structures win.

    **The one place they earn their keep** is a dense graph where `decrease_key` dominates and `E`
    is close to `V²`. That is rare, and if you are there you should measure both.

    **d-ary heaps** are the practical tuning knob instead. A 4-ary heap has depth `log₄ n` (half
    that of binary), so `decrease_key` and `sift_up` are twice as fast, at the cost of 4 comparisons
    per level instead of 2 in `sift_down`. Since Dijkstra does far more `decrease_key` than
    `extract_min` on a sparse graph, 4-ary heaps measurably win there — and the children of node `i`
    being `4i+1 .. 4i+4` means all four are usually in the same cache line, which is the real
    reason.

    ## Production failure modes

    | Failure mode | Signature | Detection |
    | --- | --- | --- |
    | Lazy deletion with no compaction | heap size grows with update volume, not working-set size; pop latency rises | export `len(heap) / len(live)`; rebuild with `heapify` above 2 |
    | Missing tiebreaker in the heap tuple | intermittent `TypeError`, frequency rises with load | `next(itertools.count())` as the second element, always |
    | `NaN` in a heap of floats | heap property silently violated; `pop` returns wrong values, no error | filter `NaN` at ingestion; `NaN` compares False with everything |
    | Max-heap by negation with mixed int/float | subtle ordering errors around `-0.0` | keep the sign convention in one place; prefer `nlargest` |
    | Unbounded priority queue as a work buffer | memory grows under load; latency unbounded | bound it and apply backpressure; export queue depth |
    | Sweep-line tie-break wrong | off-by-one in "rooms needed", only when intervals touch exactly | test the touching case explicitly; document closed vs half-open |
    | Priority inversion / starvation | low-priority items never run under sustained load | age priorities over time, or reserve a fraction of capacity per class |
    | Heap of large objects | memory proportional to queue depth × object size | store IDs and look values up; the queue holds keys, not payloads |

    ## Frontier and research pointers

    - **Williams (1964), "Algorithm 232: Heapsort."** *CACM* 7(6). — **Takeaway:** the original
      implicit-array binary heap; the insight that a complete tree needs no pointers is the reason
      heaps are still the default sixty years later.
    - **Floyd (1964), "Algorithm 245: Treesort 3."** *CACM* 7(12). — **Takeaway:** the bottom-up
      O(n) heapify; the counting argument is that half the nodes are leaves and the expensive nodes
      are rare.
    - **Fredman & Tarjan (1987), "Fibonacci Heaps and Their Uses in Improved Network Optimization
      Algorithms."** *JACM* 34(3). — **Takeaway:** amortized O(1) `decrease_key` improves Dijkstra
      to `O(E + V log V)`; read it for the potential-function argument, which is the cleanest
      introduction to amortized analysis in the literature.
    - **Larkin, Sen & Tarjan (2014), "A Back-to-Basics Empirical Study of Priority Queues."**
      ALENEX. — **Takeaway:** measured across many workloads, simple binary and pairing heaps beat
      Fibonacci heaps in practice; the paper is the standard citation for "the asymptotically better
      structure lost".
    - **Malkov & Yashunin (2018), "Efficient and Robust Approximate Nearest Neighbor Search Using
      Hierarchical Navigable Small World Graphs."** *IEEE TPAMI* 42(4). — **Takeaway:** the
      candidate and result priority queues, and the "stop when the closest candidate is worse than
      the worst result" rule, are the whole search algorithm; `ef` is the size of the bounded
      result queue and is the single knob trading recall against latency. **Read section 4 now**
      — you will implement this in week 27 and the queues will already be familiar.
    - **Brodal (1996), "Worst-Case Efficient Priority Queues."** SODA. — **Takeaway:** the amortized
      Fibonacci bounds can be made worst-case, which matters for real-time systems and essentially
      nowhere else; a good example of a result that is important theoretically and irrelevant
      practically.

      than the scoring?

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Heap returns values out of order | `sift_down` swapped with the larger child instead of the smaller | Compare against both children, swap with the smaller |
| `IndexError` when popping near the end | Missing `if left < n` bounds check in `sift_down` | Check both child indices against the array length |
| Intermittent `TypeError: '<' not supported` | Equal priorities fell through to comparing payloads | Add `next(itertools.count())` as the second tuple element |
| Scheduler memory grows with retry volume | Lazy deletion with no compaction | Mark old entries dead; rebuild with `heapify` when heap size exceeds 2× live count |
| Building a heap is slower than expected | `n` successive pushes instead of `heapify` | `heapq.heapify(all_data)`; measured 1.85–3.23× faster |
| Heap of floats returns nonsense | A `NaN` got in; it compares False with everything | Filter `NaN` at ingestion, or use a sentinel priority |
| Interval merge loses coverage | `last[1] = end` instead of `max(last[1], end)` | Test with a fully contained interval like `[[1,10],[2,3]]` |
| "Meeting rooms" off by one on touching intervals | Sweep-line tie-break processes starts before ends | Encode as `(time, -1)` for end and `(time, +1)` for start so ends sort first; document the convention |
| Top-K over NumPy data is slow | `.tolist()` before `heapq.nlargest`, boxing a million floats | `np.argpartition`; measured 7.5× faster than the heapq route |
| Low-priority work never runs | Priority inversion under sustained high-priority load | Age priorities upward with wait time, or reserve capacity per class |

## Sources & further reading

**Primary docs**

- [`heapq`](https://docs.python.org/3.12/library/heapq.html) — read the module docstring's "Theory" section, which is a genuinely good short explanation of the array representation; and note `heapreplace` (one sift instead of two) and `heappushpop` (which differ in *order* and therefore in result).
- [CPython `Modules/_heapqmodule.c`](https://github.com/python/cpython/blob/v3.12.9/Modules/_heapqmodule.c) (tag `v3.12.9`) — read `siftup` and note that CPython's version moves the hole down to a leaf first and then sifts the value up, which halves the comparisons versus the textbook algorithm.
- [`numpy.argpartition`](https://numpy.org/doc/2.1/reference/generated/numpy.argpartition.html) (NumPy 2.1.3) — read this for the introselect guarantee: element at position `kth` is in its final sorted position and everything before it is smaller, with no ordering promised within either side.
- [`queue.PriorityQueue`](https://docs.python.org/3.12/library/queue.html#queue.PriorityQueue) — read this for the thread-safe wrapper and the explicit documentation note recommending the `(priority, count, task)` tuple pattern.

**Papers**

- [Williams (1964), *Algorithm 232: Heapsort*, CACM 7(6), 347–348.](https://doi.org/10.1145/512274.3734138) — **Takeaway:** a complete binary tree can be stored in a flat array with children at `2i+1` and `2i+2`, eliminating pointers entirely.
- [Floyd (1964), *Algorithm 245: Treesort 3*, CACM 7(12), 701.](https://doi.org/10.1145/355588.365103) — **Takeaway:** building a heap bottom-up is O(n), not O(n log n), because half the nodes are leaves that require zero work.
- [Fredman & Tarjan (1987), *Fibonacci Heaps and Their Uses in Improved Network Optimization Algorithms*, JACM 34(3), 596–615.](https://doi.org/10.1145/28869.28874) — **Takeaway:** amortized O(1) `decrease_key` improves Dijkstra's bound; the potential-function proof is the best introduction to amortized analysis anywhere.
- [Larkin, Sen & Tarjan (2014), *A Back-to-Basics Empirical Study of Priority Queues*, ALENEX.](https://doi.org/10.1137/1.9781611973198.7) — **Takeaway:** on real workloads, simple binary and pairing heaps outperform Fibonacci heaps; the asymptotically superior structure loses on constants and cache behaviour.
- [Malkov & Yashunin (2018), *Efficient and Robust Approximate Nearest Neighbor Search Using Hierarchical Navigable Small World Graphs*, IEEE TPAMI 42(4).](https://doi.org/10.1109/TPAMI.2018.2889473) — **Takeaway:** the search is two priority queues plus one termination rule; `ef` is the bounded result queue's size and is the recall-versus-latency knob.

**Go deeper**

- [Sedgewick & Wayne, *Algorithms* 4th ed., **Section 2.4 (Priority Queues)**](https://algs4.cs.princeton.edu/home/) — the derivation of the `Σ h/2^h = 2` sum that makes heapify linear, done properly and briefly.
- Cormen et al., *Introduction to Algorithms* 4th ed., **Chapter 6 (Heapsort)** — the formal `BUILD-MAX-HEAP` analysis, including the tighter bound that makes the O(n) result rigorous rather than hand-wavy.
- [Erik Demaine, *MIT 6.006 lecture on heaps and heapsort*](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2020/) — read/watch it for the visual level-by-level accounting; it is the clearest presentation of the linear heapify argument in any lecture I know of.
