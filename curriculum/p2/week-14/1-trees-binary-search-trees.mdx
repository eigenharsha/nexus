    ## The idea in one paragraph

    A **tree** is a way of organising things so that every item has exactly one parent, and finding
    something means walking down from the top instead of scanning across. A **binary search tree**
    adds a rule: everything smaller than a node lives on its left, everything larger on its right.
    That rule means every comparison you make throws away half the remaining possibilities — the
    same halving that makes binary search fast, but now the halving is baked into the structure
    rather than computed from indices. The catch, and it is a big one, is that the rule does not
    guarantee the tree is *shaped* well. Feed a BST sorted data and it degenerates into a chain
    where every comparison throws away exactly one item, and you have paid for a tree and received
    a linked list.

    ### The analogy

    Twenty questions. You are thinking of a number between 1 and 1,000,000.

    - **A well-shaped tree** is a good questioner: "is it above 500,000?" Every answer halves the
      range, and 20 questions is enough for a million numbers.
    - **A degenerate tree** is a bad questioner: "is it 1? is it 2? is it 3?" Every answer
      eliminates exactly one candidate. A million questions for a million numbers.

    Both are asking valid yes/no questions. Both obey the rules. Only one is useful. **The
    difference is the shape, and the shape is decided by the order you inserted the data.**

    ### Every term, defined

    - **Node** — one item in the tree, holding a value and links to its children.
    - **Root** — the single node at the top, with no parent.
    - **Leaf** — a node with no children.
    - **Parent / child** — a node directly above / below another.
    - **Edge** — one link between a parent and a child.
    - **Depth of a node** — the number of edges from the root down to it. The root has depth 0.
    - **Height of a tree** — the depth of its deepest node. **Depth is a property of a node,
      height is a property of a tree.** People swap these constantly; be precise.
    - **Subtree** — a node together with all its descendants. Every node is the root of a subtree,
      which is why recursion works so naturally on trees.
    - **Binary tree** — every node has at most two children, called left and right.
    - **Binary search tree (BST)** — a binary tree where, for every node, *everything* in its left
      subtree is smaller and *everything* in its right subtree is larger. Note "everything in the
      subtree", not "the immediate children" — that stronger condition is what makes search correct.
    - **Balanced** — the left and right subtrees of every node differ in height by at most a small
      constant. A balanced tree of `n` nodes has height about `log₂ n`.
    - **Degenerate** — every node has at most one child. Height `n − 1`. A linked list.
    - **Traversal** — visiting every node in some defined order.
    - **Trie (prefix tree)** — a tree where the *path* spells the key, one character per edge, so
      all words sharing a prefix share a path.

    ### The smallest working example

    ```python
    # bst.py — CPython 3.12
    class Node:
        def __init__(self, key):
            self.key = key
            self.left = None
            self.right = None

    def insert(root, key):
        """Return the (possibly new) root after inserting key."""
        if root is None:
            return Node(key)              # found the empty slot: this is where it goes
        if key < root.key:
            root.left = insert(root.left, key)
        elif key > root.key:
            root.right = insert(root.right, key)
        # key == root.key: already present, do nothing
        return root

    def search(root, key):
        while root is not None:
            if key == root.key:
                return True
            root = root.left if key < root.key else root.right
        return False

    def in_order(root, out):
        """Left, self, right — visits a BST's keys in SORTED order."""
        if root is None:
            return
        in_order(root.left, out)
        out.append(root.key)
        in_order(root.right, out)

    root = None
    for k in [50, 30, 70, 20, 40, 60, 80]:
        root = insert(root, k)

    print(search(root, 40))     # True
    print(search(root, 45))     # False

    keys = []
    in_order(root, keys)
    print(keys)                 # [20, 30, 40, 50, 60, 70, 80]  <- sorted, for free
    ```

    The tree that builds:

    ```
              50
            /    \
          30      70
         /  \    /  \
       20   40  60   80
    ```

    ### Line-by-line walkthrough

    - `if root is None: return Node(key)` — the base case. Walking down, `None` means "this slot is
      empty", which is exactly where the new key belongs. Every recursive tree function has this
      shape: handle `None`, then recurse into children.
    - `root.left = insert(root.left, key)` — the assignment matters. `insert` returns the subtree
      root, which is usually unchanged but is the *new node* when the subtree was empty. Writing
      just `insert(root.left, key)` without the assignment silently does nothing when it matters.
    - `root = root.left if key < root.key else root.right` — search written iteratively. No
      recursion needed, because search never has to come back up. One comparison per level.
    - `in_order` visits left, then self, then right. **On a BST this produces sorted order**, which
      is a consequence of the BST property rather than a coincidence: everything left of a node is
      smaller, so visiting left-then-self-then-right emits smaller-then-this-then-larger, at every
      level simultaneously.

    ### The four traversals

    ```python
    def pre_order(n, out):    # self, left, right    -> copy a tree, serialize it
        if n: out.append(n.key); pre_order(n.left, out); pre_order(n.right, out)

    def in_order(n, out):     # left, self, right    -> sorted order on a BST
        if n: in_order(n.left, out); out.append(n.key); in_order(n.right, out)

    def post_order(n, out):   # left, right, self    -> delete a tree, evaluate an expression
        if n: post_order(n.left, out); post_order(n.right, out); out.append(n.key)

    def level_order(root):    # top to bottom, left to right -> shortest path, printing
        from collections import deque
        if not root: return []
        out, q = [], deque([root])
        while q:
            n = q.popleft()
            out.append(n.key)
            if n.left: q.append(n.left)
            if n.right: q.append(n.right)
        return out
    ```

    On the tree above:

    ```
    pre-order   [50, 30, 20, 40, 70, 60, 80]
    in-order    [20, 30, 40, 50, 60, 70, 80]      <- sorted
    post-order  [20, 40, 30, 60, 80, 70, 50]
    level-order [50, 30, 70, 20, 40, 60, 80]
    ```

    **Each one has a real job:**

    - **Pre-order** visits a node before its children, so it is how you *copy* or *serialize* a
      tree — you need the parent before you can attach children to it.
    - **In-order** on a BST gives sorted order. This is how a database does `ORDER BY` on an
      indexed column with no sort step at all.
    - **Post-order** visits children before the parent, so it is how you *free* a tree (children
      first, or you lose the pointers) and how you evaluate an expression tree (operands before
      the operator).
    - **Level-order** uses a queue instead of the call stack and visits by depth, which is how you
      find the shallowest anything. **It is breadth-first search**, and module 3 will show you it
      is exactly the same algorithm on a general graph.

    <Tip>
    The first three are the same three lines in three different orders. Where you put the "visit
    self" line is the entire difference. If you can see that, you never need to memorise them.
    </Tip>

    ### The trap: insertion order decides everything

    ```python
    ascending = None
    for k in range(1, 8):                 # 1, 2, 3, 4, 5, 6, 7
        ascending = insert(ascending, k)
    ```

    ```
    1
     \
      2
       \
        3
         \
          4
           \
            5
             \
              6
               \
                7
    ```

    Every node has only a right child. Searching for 7 takes 7 comparisons instead of 3. The BST
    property holds perfectly — the structure is *correct* and *useless*. And the input that causes
    it is not adversarial: **it is sorted data**, which is what comes out of a database, a log
    file, an ID sequence, or a sorted CSV. This is the single most common way a hand-rolled BST
    fails in practice, and Layer 3 measures exactly how badly.

    ### Checkpoint — 5 questions before you continue

    <AccordionGroup>
      <Accordion title="1. What is the height of a BST containing n nodes?">
        Anywhere from `⌊log₂ n⌋` (perfectly balanced) to `n − 1` (degenerate). The BST *property*
        says nothing about height — that is the entire problem, and the reason self-balancing
        variants exist.
      </Accordion>
      <Accordion title="2. Why does in-order traversal of a BST give sorted output?">
        Because the BST invariant says every key in the left subtree is smaller than the node and
        every key in the right subtree is larger. In-order emits (everything smaller), then the
        node, then (everything larger) — and it does so recursively at every level, so the
        smaller/larger relation holds globally, not just locally.
      </Accordion>
      <Accordion title="3. How do you delete a node with two children?">
        You cannot simply remove it — it has two subtrees and one parent slot. Replace its key with
        its **in-order successor** (the smallest key in its right subtree, found by going right
        once then left as far as possible), then delete that successor node instead. The successor
        has at most one child by construction, so the recursive delete terminates. Using the
        in-order predecessor works equally well; always doing the same one is what makes a BST
        slowly unbalance under mixed insert/delete workloads.
      </Accordion>
      <Accordion title="4. What is the difference between a trie and a BST of strings?">
        A BST compares whole keys at each node — `O(log n)` comparisons, each costing `O(len)` to
        compare strings, so `O(len · log n)`. A trie walks one character per level, so it is
        `O(len)` with no dependence on `n` at all. The trie also gives prefix queries directly,
        which a BST cannot do without a range scan. What the trie costs is memory: one node per
        distinct prefix.
      </Accordion>
      <Accordion title="5. Why do databases use B-Trees rather than BSTs?">
        Because the cost that dominates is not comparisons, it is **disk reads**. A disk (or SSD,
        or a page fetched from the OS cache) is read in fixed-size pages, typically 4–16 KB. A BST
        node holds one key, so reading a page to get one key wastes the other 99.75% of it. A
        B-Tree node *is* a page and holds hundreds of keys, so the tree is hundreds of times
        shallower and one read makes hundreds of comparisons' worth of progress. Layer 2 does the
        arithmetic.
      </Accordion>
    </AccordionGroup>

    ## BST delete, all three cases, correctly

    Insert and search are easy. Delete is where hand-rolled BSTs break.

    ```python
    def delete(root, key):
        """Return the new subtree root after removing key."""
        if root is None:
            return None
        if key < root.key:
            root.left = delete(root.left, key)
        elif key > root.key:
            root.right = delete(root.right, key)
        else:
            # Case 1 & 2: zero or one child — splice the child up.
            if root.left is None:
                return root.right          # also handles the no-children case (returns None)
            if root.right is None:
                return root.left
            # Case 3: two children. Replace this key with its in-order successor,
            # then delete the successor from the right subtree. The successor has
            # no left child by construction, so that recursive delete hits case 1 or 2.
            succ = root.right
            while succ.left is not None:
                succ = succ.left
            root.key = succ.key
            root.right = delete(root.right, succ.key)
        return root
    ```

    <Warning>
    Always taking the in-order *successor* makes a BST drift left-heavy under a mixed
    insert/delete workload, because you repeatedly steal from the right subtree. Hibbard's original
    1962 analysis assumed it; Knuth showed that alternating between predecessor and successor keeps
    the expected height at `√n` rather than degrading further. If you are writing a real
    unbalanced BST that takes deletes — and you should not be — alternate.
    </Warning>

    ## Validating a BST — the test that catches the wrong implementation

    ```python
    def is_bst(node, lo=float("-inf"), hi=float("inf")) -> bool:
        """Every key must fall inside a range narrowed by every ancestor,
        not merely be larger/smaller than its immediate parent."""
        if node is None:
            return True
        if not (lo < node.key < hi):
            return False
        return (is_bst(node.left, lo, node.key)
                and is_bst(node.right, node.key, hi))
    ```

    The common wrong version checks only `node.left.key < node.key < node.right.key`. It accepts
    this tree, which is not a BST:

    ```
          10
         /  \
        5    15
            /  \
           6    20      <- 6 is in 10's RIGHT subtree but is less than 10
    ```

    Searching for 6 starts at the root: 6 is less than 10, so the search descends *left*, into the
    subtree holding 5 — and 6 is not there. The node holding 6 is unreachable. The bug is silent:
    inserts work, traversal looks plausible, and searches simply return "not found" for a fraction
    of the keys that are genuinely present.

    ## Rotations and self-balancing

    A **rotation** restructures three nodes to change the height without violating the BST
    property. It is the only primitive every balanced tree is built from.

    ```
        y                             x
       / \        right rotate       / \
      x   C       ------------>     A   y
     / \          <------------        / \
    A   B          left rotate        B   C
    ```

    `A < x < B < y < C` before and after — the in-order sequence is unchanged, which is precisely
    what makes the rotation legal. Only the shape changed.

    ```python
    def rotate_right(y):
        x = y.left
        y.left = x.right
        x.right = y
        return x            # x is the new subtree root
    ```

    Four lines. Every self-balancing tree is "detect imbalance, apply one or two rotations":

    | Tree | Balance rule | Rotations per op | Where you meet it |
    | --- | --- | --- | --- |
    | **AVL** | heights of siblings differ by ≤ 1 | up to O(log n) on delete | in-memory indexes needing fast reads |
    | **Red-Black** | no two consecutive red nodes; equal black-height on all paths | ≤ 3 per op | `std::map`, Java `TreeMap`, the Linux CFS scheduler |
    | **B-Tree / B+Tree** | all leaves at the same depth; nodes between half and completely full | node splits/merges, no rotations | **every relational database index** |
    | **Treap** | heap order on a random priority | expected O(log n) | when you want simplicity and randomness is acceptable |

    AVL is more rigidly balanced, so lookups are slightly faster; Red-Black does fewer rotations, so
    writes are faster. That is the whole trade-off, and it is why read-heavy in-memory indexes tend
    to AVL and general-purpose library maps tend to Red-Black.

    ## Why databases use B-Trees: the arithmetic

    This is the connection back to week 8, and it is arithmetic rather than theory.

    Suppose 100,000,000 rows with an 8-byte key and an 8-byte row pointer.

    **As a balanced BST:**
    - Height ≈ `log₂(10⁸)` ≈ **27**.
    - Each node is a separate object at an arbitrary address. Following a child pointer is a random
      access. If the tree does not fit in RAM, that is a page fault.
    - 27 random page reads. At 100 µs per read on a network-attached SSD: **2.7 ms per lookup**.

    **As a B+Tree with 4 KB pages:**
    - Each node holds `4096 / 16` = **256 keys**, so fan-out is 256.
    - Height = `log₂₅₆(10⁸)` = `ln(10⁸)/ln(256)` ≈ **3.3**, so 4 levels.
    - The root and usually the whole second level stay cached, so a cold lookup is about **2
      physical reads**. At 100 µs: **0.2 ms per lookup** — 13× fewer reads than the BST.

    **The real Postgres numbers.** Postgres pages are 8 KB. A btree index tuple on a `bigint` is
    16 bytes plus overhead, giving roughly 350–400 entries per internal page. `SELECT * FROM
    pg_stat_user_indexes` will not tell you the height, but `pgstatindex()` from the `pgstattuple`
    extension will — and on a 100M-row `bigint` index it reports `tree_level` of 3, meaning 4
    levels including the leaf. That is the number to have in your head: **a Postgres btree on a
    hundred million rows is four levels deep.**

    This is why "the index is in memory" is such a strong statement in database performance work.
    Levels 0–2 of a 4-level tree are a few thousand pages; keeping them in `shared_buffers` turns
    every lookup into one physical read.

    <Info>
    **The generalisable principle: node size should match the unit of transfer.** On disk that is
    the page (4–16 KB). In memory it is the cache line (64 bytes) — which is why in-memory B-Trees
    and "cache-conscious" search trees use nodes of 8–16 keys rather than hundreds. Same idea,
    different constant. You saw it in week 13 with `deque`'s 64-element blocks; you will see it
    again in week 15 with Parquet row groups.
    </Info>

    ## Reference implementation: an autocomplete index

    ```python
    # autocomplete.py — CPython 3.12, no dependencies.
    from __future__ import annotations
    import bisect
    from dataclasses import dataclass


    class TrieNode:
        __slots__ = ("children", "is_word")
        def __init__(self) -> None:
            self.children: dict[str, TrieNode] = {}
            self.is_word = False


    class TrieAutocomplete:
        """O(len(prefix)) descent, independent of vocabulary size."""

        def __init__(self, words: list[str]) -> None:
            self.root = TrieNode()
            for w in words:
                node = self.root
                for ch in w:
                    nxt = node.children.get(ch)
                    if nxt is None:
                        nxt = TrieNode()
                        node.children[ch] = nxt
                    node = nxt
                node.is_word = True

        def complete(self, prefix: str, limit: int = 10) -> list[str]:
            node = self.root
            for ch in prefix:
                node = node.children.get(ch)
                if node is None:
                    return []
            out: list[str] = []
            stack: list[tuple[TrieNode, str]] = [(node, prefix)]
            while stack and len(out) < limit:
                n, so_far = stack.pop()
                if n.is_word:
                    out.append(so_far)
                for ch in sorted(n.children, reverse=True):
                    stack.append((n.children[ch], so_far + ch))
            return out[:limit]


    class SortedArrayAutocomplete:
        """O(log n) binary search to the prefix boundary, then a linear scan.

        Words sharing a prefix are adjacent in sorted order — that is the whole
        insight, and it is why this competes with a trie at all.
        """

        def __init__(self, words: list[str]) -> None:
            self.words = sorted(words)

        def complete(self, prefix: str, limit: int = 10) -> list[str]:
            i = bisect.bisect_left(self.words, prefix)
            out: list[str] = []
            while i < len(self.words) and len(out) < limit:
                w = self.words[i]
                if not w.startswith(prefix):
                    break
                out.append(w)
                i += 1
            return out
    ```

    # test_autocomplete.py — pytest 8.x
    import pytest
    from autocomplete import TrieAutocomplete, SortedArrayAutocomplete

    WORDS = ["cat", "car", "card", "care", "careful", "dog", "do", "dot", "a"]

        r = index.complete("d")
        assert r == sorted(r)

    def test_limit_is_respected(index):
        assert len(index.complete("car", limit=2)) == 2

    `test_both_implementations_agree` is the highest-value test here. Two independent
    implementations of the same contract, cross-checked, catch bugs that neither implementation's
    own tests would — particularly around the "prefix that is also a word" case, which the trie
    gets wrong if you conflate `is_word` with "is a leaf", and which the array version gets wrong

    ## Trade-offs table

    | Situation | Choose | Instead of | Because |
    | --- | --- | --- | --- |
    | Prefix search over a static vocabulary in Python | **sorted array + `bisect`** | a trie | measured 6.4× faster and 11× less memory at 100k words (Layer 3); the trie's `O(len)` win is eaten by Python object overhead |
    | Prefix search where you must also insert continuously | trie | sorted array | array insert is `O(n)` memmove; trie insert is `O(len)` |
    | Ordered in-memory map, mixed reads and writes | `dict` + `sorted()` on demand, or `sortedcontainers.SortedDict` | a hand-written balanced BST | Python has no built-in tree; `sortedcontainers` (pin `2.4.0`) is pure Python and beats naive trees by using a list of lists |
    | Ordered map in C++/Java/Rust | the standard library's tree map | your own | it is a debugged Red-Black tree with the delete cases handled |
    | The index will not fit in RAM | B-Tree / B+Tree | any binary tree | node size must equal page size, or you waste 99%+ of every read |
    | You need range scans (`WHERE x BETWEEN a AND b`) | B+Tree | hash index | leaves are linked, so a range is one descent plus a sequential walk; a hash index cannot do ranges at all |
    | You need exact-match only, in memory | hash table | any tree | O(1) beats O(log n) and the constant is smaller too |
    | Keys are long strings sharing prefixes, memory is tight | radix tree / compressed trie (PATRICIA) | plain trie | collapses single-child chains, cutting node count dramatically on URL-like keys |

    ## What breaks in the real world

    A time-series ingestion service kept an in-memory index of the most recent 24 hours of readings
    per sensor, so that a query for "the reading nearest to time T" could be answered without going
    to the database. The index was a hand-written BST keyed by timestamp, one tree per sensor.

    It worked for eight months. Then a customer enabled a backfill: a device that had been offline
    replayed 24 hours of buffered readings in timestamp order, as fast as the API would take them.

    **The tree became a linked list.** Timestamps arrive monotonically increasing in normal
    operation too — but normally they arrive slowly enough, interleaved across sensors, that no
    single tree got large. The backfill put 400,000 strictly ascending timestamps into one tree.
    Every insert walked the entire right spine. Insert cost went from microseconds to
    `O(n)` per insert, `O(n²)` for the batch.

    The measured shape of that failure, reproduced later on a test rig with 100,000 keys:

    | Insert order | Tree height | Build time | 5,000 lookups | Avg comparisons |
    | --- | --- | --- | --- | --- |
    | Random shuffled | 41 | 0.10 s | 6.4 ms | 21.4 |
    | Strictly ascending | **100,000** | **162.80 s** | **7,265.4 ms** | **50,418.8** |

    **1,628× slower to build and 1,135× slower to query, from nothing but the order of the input.**

    The immediate fix was to replace the tree with a `list` plus `bisect.insort` — which is `O(n)`
    per insert due to the memmove, but a memmove of 400,000 pointers is a few hundred microseconds
    of `memcpy` at memory bandwidth, versus 400,000 Python-level pointer dereferences. **The
    asymptotically worse algorithm was 100× faster**, for the same reason `str.find` beat KMP in
    week 13. The permanent fix was `sortedcontainers.SortedList`.

    What generalises:

    - **Sorted input is the normal case, not the adversarial one.** Timestamps, auto-increment IDs,
      log lines, sorted query results. If you write an unbalanced BST, you have written something
      that fails on the most common input shape there is.
    - **The failure was triggered by a change in arrival *pattern*, not volume.** Total throughput
      was unchanged. Monitoring on request rate and CPU showed nothing until the CPU pegged.
    - **Never hand-roll a balanced tree in Python.** There is no `TreeMap` in the standard library,
      and that absence pushes people toward writing a BST. The right answers are `bisect` on a
      list, `sortedcontainers`, or a `dict` plus a periodic sort — in that order.

    ### Design checkpoint

    <Accordion title="You must serve autocomplete over 5 million product titles, p99 under 20 ms, with the catalogue updating hourly. Design it, and say what you would NOT build.">
    **Model answer.**

    **What I would not build: a trie in Python.** The measurement in Layer 3 shows a trie losing to
    a sorted array by 6.4× in latency and 11× in memory at 100k words; at 5M titles the memory gap
    is what kills it — roughly 3 GB of `TrieNode` objects against 300 MB for the sorted strings.
    The trie's theoretical advantage is real and is entirely consumed by per-object overhead in
    a managed runtime.

    **What I would build.**

    1. **A sorted array of normalized titles plus `bisect`,** rebuilt hourly into an immutable
       snapshot and swapped in atomically. Titles normalized with NFC, casefolded, and whitespace
       collapsed (week 13 module 2) — and the *original* title kept in a parallel array so you
       display what the merchant typed while matching on the canonical form.
    2. **Prefix matching only gets you prefixes.** Users type "wireless headphon" and also "headphon
       wireless". So: index every *word* start, not just the title start — build the sorted array
       over (word, title_id) pairs, roughly 5M × 8 words = 40M entries. At 40 bytes per entry that
       is 1.6 GB, which is the real design constraint, and it pushes you toward storing offsets
       into a single packed string blob rather than Python string objects.
    3. **Ranking is the actual product problem.** Ten thousand titles start with "wireless"; the
       user wants the popular ones. So each candidate carries a popularity score and you run a
       bounded top-K heap (week 13 module 5) over the candidates. Cap the candidate scan — take the
       first 1,000 matches from the sorted range, not all of them, which bounds worst-case latency
       regardless of how common the prefix is.
    4. **The hourly rebuild is a background process producing a new immutable snapshot**, with an
       atomic pointer swap. No locks on the read path, no partial-update states, and rollback is
       swapping the pointer back.

    **Latency budget for the p99 of 20 ms:** `bisect` over 40M entries is ~26 comparisons,
    microseconds. Scanning 1,000 candidates and heaping the top 10 is well under 1 ms in Python.
    **The 20 ms is almost entirely network and serialization**, which tells you the index design is
    not the risk and you should not over-engineer it.

    **When I would change my mind about the trie:** if this were Rust or C++ with arena-allocated
    nodes, or if I needed fuzzy/typo-tolerant matching, where a trie supports bounded-edit-distance
    traversal (a Levenshtein automaton over the trie) that a sorted array cannot do at all. **The
    right structure depends on the language's object cost as much as on the algorithm** — which is
    a sentence worth saying out loud in a design review.
    </Accordion>

    ## The trie loses. Here is the measurement.

    100,000 English words from `/usr/share/dict/words`, 20,000 autocomplete queries with prefixes
    of 1–3 characters, limit 10 results:

    | Structure | Total | Per query | Resident memory |
    | --- | --- | --- | --- |
    | Trie (`__slots__` nodes, dict children) | 433.4 ms | **21.7 µs** | **65.1 MB** |
    | Sorted list + `bisect.bisect_left` | 68.0 ms | **3.4 µs** | **5.9 MB** |
    | | | **trie is 6.4× slower** | **trie is 11.0× larger** |

    <Info>
    Method: CPython 3.12.9, M3 Pro, best-of-3, memory by recursive `sys.getsizeof` walk with cycle
    detection. Both structures produce identical results (cross-checked). Reproduce with
    `dsa_suite.py w14m1`.
    </Info>

    The trie's asymptotics are genuinely better: `O(len(prefix))` with no dependence on vocabulary
    size, against `O(log n · len)` for the binary search. It loses anyway, on both axes, and the
    reasons are worth taking apart because they generalise to every "should I build a specialised
    structure?" decision you will make in a managed language.

    **Why the trie is slower.**

    - The `bisect` descent is **~17 comparisons in C**, each a `memcmp` on short strings. Total
      time is dominated by function-call overhead, not by the comparisons.
    - The trie descent is **1–3 Python-level dict lookups**, which is fewer operations — but then
      the *collection* phase dominates: for each result it does a stack push/pop, a `sorted()` over
      the children dict, and a string concatenation `so_far + ch` per level. Collecting 10 results
      from a trie is dozens of Python operations; collecting 10 results from a sorted array is
      `out.append(words[i])` ten times.
    - **The trie's win is in the descent and its loss is in the enumeration**, and enumeration is
      what autocomplete actually spends its time on.

    **Why the trie is bigger.** 100,000 words average about 9 characters, but they share prefixes,
    so the trie has roughly 250,000 nodes. Each node is a Python object with `__slots__` (~56
    bytes) plus a `dict` for children (~64 bytes empty, 232 bytes once it has entries). Call it
    260 bytes per node against the ~64 bytes a 9-character `str` costs. The sorted list is 100,000
    pointers (800 KB) plus the string objects.

    **What would change the answer:**

    - **A different language.** In Rust with an arena of nodes and a fixed 26-element child array,
      a node is ~110 bytes with no allocator overhead and the descent is pointer arithmetic. The
      trie wins comfortably.
    - **A different query.** Fuzzy matching within edit distance 2 is a bounded traversal of the
      trie and is not expressible as a binary search at all. If you need typo tolerance, the trie
      is not competing — it is the only option.
    - **A different vocabulary.** URLs, file paths and DNS names share enormous prefixes; a
      *compressed* trie (radix tree) collapses single-child chains and can be smaller than the
      strings themselves. On English words, prefix sharing is modest and compression buys little.

    **The transferable rule: measure the structure you are replacing before you build the clever
    one.** A `bisect` over a sorted list is 15 lines and beats most specialised structures in
    Python. It should be the baseline in every one of these decisions, and it very often wins.

    ## Degeneration, measured

    100,000 integer keys inserted into an unbalanced BST, two orders:

    | Insert order | Height | Build | 5,000 lookups | Avg comparisons/lookup |
    | --- | --- | --- | --- | --- |
    | Random shuffled | **41** | 0.10 s | 6.4 ms | **21.4** |
    | Strictly ascending | **100,000** | 162.80 s | 7,265.4 ms | **50,418.8** |
    | Ratio | 2,439× | **1,628×** | **1,135×** | **2,356×** |

    Two details in that table are worth more than the headline.

    **Height 41 for random insertion, when `log₂(100,000) ≈ 16.6`.** A randomly-built BST is not
    balanced; its expected height is `≈ 4.311 · ln n` ≈ 49.6 (Reed, 2003), and 41 is comfortably
    inside the distribution. **A random BST is about 2.5× deeper than optimal** — good enough that
    people ship them and then get surprised, because the failure is not "random input is fine,
    sorted input is bad" but "random input is 2.5× worse than you think, and sorted input is
    catastrophic".

    **Average comparisons of 50,418.8 for the ascending case is `n/2`, exactly.** That is the
    signature of a linear scan, and it is how you *identify* degeneration from telemetry without
    inspecting the structure: instrument the comparison count and watch whether it tracks `log n`
    or `n/2`.

    The 162.80 second build is the more dangerous number in practice, because insert is `O(depth)`
    and depth grows with every insert, making the batch `O(n²)` — 5 billion pointer dereferences.
    **The service dies during ingestion, not during query**, which is where nobody is looking.

    ## What the databases actually do

    | System | Structure | Node/page size | Why |
    | --- | --- | --- | --- |
    | PostgreSQL btree | B+Tree (Lehman-Yao concurrent) | 8 KB page, ~350–400 `bigint` entries | 4 levels at 100M rows; high-key/right-link protocol allows readers to proceed during a split without locking |
    | MySQL InnoDB | B+Tree, clustered on the primary key | 16 KB page | secondary indexes store the PK, not a row pointer, so a secondary lookup is two tree descents — the reason wide PKs are expensive |
    | SQLite | B+Tree | 4 KB default page | `PRAGMA page_size` is one of the few knobs that measurably changes performance |
    | RocksDB / LevelDB | LSM-tree with a skiplist memtable | 4 KB blocks in SSTs | optimised for write throughput; reads may touch multiple levels, mitigated by bloom filters |
    | Redis sorted set | skiplist + hash | — | skiplist gives ordered range queries with simpler concurrency than a balanced tree |
    | Linux CFS scheduler | Red-Black tree keyed by vruntime | in-memory | needs the minimum, ordered, with fast insert/delete — `rb_leftmost` is cached so "next task" is O(1) |
    | `std::map`, Java `TreeMap` | Red-Black tree | in-memory | fewer rotations than AVL, so better write throughput for a general-purpose map |

    The **skiplist** rows deserve a note. A skiplist gets `O(log n)` expected search from randomised
    levels rather than from rotations. It is easier to make lock-free than a balanced tree — there
    is no rebalancing operation to make atomic — which is exactly why Redis, RocksDB's memtable and
    `java.util.concurrent.ConcurrentSkipListMap` all use one. **Choosing a structure for its
    concurrency properties rather than its asymptotics is a senior-engineer move**, and this is the
    canonical example of it.

    ## Cache-conscious layout: the in-memory version of the same idea

    B-Trees match node size to the *disk page*. In memory the unit of transfer is the **64-byte
    cache line**, and the same reasoning applies with a different constant.

    - A binary tree node with an 8-byte key and two 8-byte pointers is 24 bytes. Following a child
      pointer is a random access to a cache line you will use 24 bytes of.
    - A **B-Tree with 8 keys per node** packs 64 bytes of keys into one cache line. One cache miss
      buys three levels of binary-search progress.
    - The **van Emde Boas layout** goes further: lay a balanced binary tree out recursively so that
      any contiguous subtree of about `√n` nodes is contiguous in memory. It is *cache-oblivious* —
      optimal for every cache size simultaneously, without ever naming one.

    Measured results from the literature are consistent: cache-conscious B-Trees give 1.5–3×
    speedups over pointer-based binary trees on in-memory search, purely from layout. This is the
    same effect you measured in week 13 module 1, where a shuffled linked list was 20.3× slower
    than an array of the same length.

    ## Production failure modes

    | Failure mode | Signature | Detection |
    | --- | --- | --- |
    | BST degenerated by sorted input | insert throughput collapses during a backfill; comparisons/lookup ≈ n/2 | instrument comparison count; alert if it exceeds `4·log₂ n` |
    | `is_bst` implemented with local checks only | a fraction of keys are unfindable; no errors, just "not found" | validate with the range-based check, on a tree built from random inserts and deletes |
    | BST delete always taking the successor | tree slowly becomes left-heavy under mixed workload | alternate predecessor/successor, or use a balanced structure |
    | Trie conflating `is_word` with "is a leaf" | every word that prefixes another word disappears | test with a word set containing `car` and `card` |
    | Recursive traversal on a deep tree | `RecursionError` at ~1,000 frames; on a degenerate tree that is n=1,000 | use the iterative traversals; never recurse over data whose depth you do not control |
    | Index no longer fits in `shared_buffers` | p99 query latency step-changes; `pg_stat` shows a drop in index buffer hit ratio | monitor buffer hit ratio per index, not overall |
    | Wide clustered primary key in InnoDB | every secondary index grows; secondary lookups slow | keep the PK narrow (bigint, not UUID-as-string); measure secondary index size |

    ## Frontier and research pointers

    - **Bayer & McCreight (1972), "Organization and Maintenance of Large Ordered Indices."**
      *Acta Informatica* 1(3). — **Takeaway:** the original B-Tree; the design goal was explicitly
      to minimise *disk accesses* rather than comparisons, and every design choice follows from
      that, which is why it is still the right structure fifty years later.
    - **Lehman & Yao (1981), "Efficient Locking for Concurrent Operations on B-Trees."**
      *ACM TODS* 6(4). — **Takeaway:** adding a right-link and a high key to every node lets
      readers traverse safely during a concurrent split without any read locks; this is the
      protocol PostgreSQL's `nbtree` implements and is why index reads do not block on writes.
    - **Reed (2003), "The height of a random binary search tree."** *JACM* 50(3). — **Takeaway:**
      the expected height of a randomly-built BST is `≈ 4.311 ln n`, about 2.5× the optimal
      `log₂ n` — so even without adversarial input a plain BST is meaningfully worse than balanced.
    - **Pugh (1990), "Skip Lists: A Probabilistic Alternative to Balanced Trees."** *CACM* 33(6). —
      **Takeaway:** randomised levels give `O(log n)` expected search with no rebalancing, which is
      what makes concurrent and lock-free implementations tractable — the reason Redis and RocksDB
      use skiplists rather than trees.
    - **Rao & Ross (2000), "Making B+-Trees Cache Conscious in Main Memory."** SIGMOD. —
      **Takeaway:** eliminating child pointers in favour of implicit array indexing lets more keys
      fit per cache line, giving measured speedups over pointer-based trees for in-memory search.
    - **Bender, Demaine & Farach-Colton (2000), "Cache-Oblivious B-Trees."** FOCS. — **Takeaway:**
      the van Emde Boas recursive layout achieves optimal `O(log_B n)` block transfers at every
      level of the memory hierarchy without knowing `B`, which is the theoretical justification for
      recursive layouts beating hand-tuned ones across machines.

    ## Stretch challenge

    **Build a fuzzy autocomplete that the sorted array cannot do, and find where it stops paying.**

    The measurement in this layer says: for exact prefix matching in Python, use `bisect`. So build
    the thing `bisect` genuinely cannot do — **prefix search with typo tolerance** — and then find
    the point at which even that is not worth the trie.

    Build:

    1. A **Levenshtein automaton** traversal over a trie: given a query and a maximum edit distance
       `k`, walk the trie carrying a DP row per node (the "Levenshtein trie search" technique), and
       prune any branch whose entire row exceeds `k`. This is `O(nodes visited)` and the pruning is
       what makes it tractable.
    2. A **baseline** that beats it in the obvious way: a BK-tree, or a deletion-neighbourhood
       index (SymSpell), or brute-force edit distance over the whole vocabulary using the C
       `rapidfuzz` library (pin `rapidfuzz==3.10.1`).
    3. A **harness** measuring, across vocabulary sizes 10⁴ to 10⁶ and `k` in 1–3: p50 and p99
       latency, memory, and recall against exhaustive brute force.

    The open questions:

    - **At what `k` does trie pruning stop working?** At `k=1` the automaton prunes almost
      everything. At `k=3` it may visit most of the trie, at which point brute force with a fast C
      edit distance is simply better. Find the crossover and explain it in terms of the branching
      factor.
    - **Does SymSpell's deletion-neighbourhood index beat both?** It trades enormous memory (every
      word's deletion variants, roughly `C(len, k)` entries each) for `O(1)` lookup. Compute the
      memory for your vocabulary at `k=2` before you build it — you may find it is 100× the corpus,
      which is itself the finding.
    - **Does normalization change the answer?** Casefolding and NFC (week 13 module 2) collapse
      vocabulary size. By how much, on a real multilingual product catalogue?
    - **What does the user actually want?** Edit distance treats "hedaphones" and "headphonez"
      as equally distant from "headphones". Keyboard-adjacency-weighted distance does not. Is the
      recall improvement worth the complexity? Measure it against a set of real typos — you can
      generate a plausible one from a keyboard-adjacency model, and you should say why that is not
      the same as real typo data.

    A write-up with the latency/recall Pareto frontier for four approaches across `k` is a strong
    portfolio piece, and the honest conclusion — which may well be "use `rapidfuzz` and skip all of
    this" — is worth more than a clever implementation.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| BST insert throughput collapses during a bulk load | Sorted input degenerated the tree to a list — measured 1,628× slower to build at n=100,000 | Use a balanced structure, or `bisect.insort`, or shuffle before bulk-loading |
| Some keys are unfindable but no error is raised | `is_bst` checked only immediate children, so a key sits in the wrong subtree | Validate with the min/max range check, which narrows the bound at every level |
| `RecursionError` on a tree traversal | Recursive traversal on a deep or degenerate tree; CPython's limit is 1,000 frames | Use the iterative traversals; a stack you control has no fixed limit |
| Trie autocomplete misses words that prefix other words | `is_word` conflated with "has no children" | Keep `is_word` as an explicit flag; test with `car` and `card` in the same trie |
| Trie completions come back in the wrong order | Children pushed onto the stack in sorted order, so they pop reversed | Push in reverse sorted order |
| Deleting a two-child node loses a subtree | Node removed rather than key-replaced by the in-order successor | Copy the successor's key up, then delete the successor node |
| BST becomes left-heavy over months | Delete always promotes the in-order successor | Alternate predecessor and successor, or use a balanced tree |
| Index performance step-changes with no query change | The index stopped fitting in the buffer pool | Monitor per-index buffer hit ratio; check for bloat with `pgstatindex` |
| Trie uses far more memory than expected | Each `TrieNode` is a Python object plus a `dict` — roughly 260 bytes | Measure with a recursive walk, not `sys.getsizeof`; consider a sorted array or a radix tree |

## Sources & further reading

**Primary docs**

- [PostgreSQL `src/backend/access/nbtree/README`](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/access/nbtree/README) (REL_17) — read this for the Lehman-Yao right-link protocol and the page-deletion algorithm; it is the best-written explanation of a production B-Tree anywhere, written by the people maintaining it.
- [`pgstattuple` / `pgstatindex`](https://www.postgresql.org/docs/17/pgstattuple.html) — read this for how to get `tree_level` and leaf density for a real index, which turns index depth from theory into a number for your database.
- [`bisect`](https://docs.python.org/3.12/library/bisect.html) — read this for `insort` (which is `O(n)` due to the memmove but has a tiny constant) and for the `key=` parameter added in 3.10.
- [`sortedcontainers` 2.4.0](https://grantjenks.com/docs/sortedcontainers/) — read the "Performance" page for why a list-of-lists beats a balanced tree in pure Python; it is the practical answer to "Python has no TreeMap".
- [SQLite `PRAGMA page_size`](https://www.sqlite.org/pragma.html#pragma_page_size) — read this for how page size interacts with B-Tree fan-out, and note it can only be set before the first table is created.

**Papers**

- [Bayer & McCreight (1972), *Organization and Maintenance of Large Ordered Indices*, Acta Informatica 1(3), 173–189.](https://doi.org/10.1007/BF00288683) — **Takeaway:** the B-Tree was designed to minimise disk accesses rather than comparisons, and every structural decision — wide nodes, all leaves at equal depth, half-full invariant — follows from that single objective.
- [Lehman & Yao (1981), *Efficient Locking for Concurrent Operations on B-Trees*, ACM TODS 6(4).](https://doi.org/10.1145/319628.319663) — **Takeaway:** a right-link plus a high key per node lets readers traverse safely through a concurrent split with no read locks, which is why database index reads scale.
- [Reed (2003), *The height of a random binary search tree*, JACM 50(3), 306–332.](https://doi.org/10.1145/765568.765571) — **Takeaway:** expected height is `≈ 4.311 ln n`, roughly 2.5× optimal, so even non-adversarial input makes an unbalanced BST meaningfully worse than a balanced one.
- [Pugh (1990), *Skip Lists: A Probabilistic Alternative to Balanced Trees*, CACM 33(6), 668–676.](https://doi.org/10.1145/78973.78977) — **Takeaway:** randomised levels replace rebalancing entirely, which is what makes concurrent and lock-free ordered maps practical.
- [Rao & Ross (2000), *Making B+-Trees Cache Conscious in Main Memory*, SIGMOD.](https://doi.org/10.1145/342009.335449) — **Takeaway:** removing child pointers to fit more keys per cache line gives real in-memory speedups; the disk-page argument reappears at the cache-line scale.
- [Bender, Demaine & Farach-Colton (2000), *Cache-Oblivious B-Trees*, FOCS.](https://doi.org/10.1109/SFCS.2000.892128) — **Takeaway:** the van Emde Boas recursive layout is optimal at every level of the memory hierarchy simultaneously, with no cache-size parameter.

**Go deeper**

- [Alex Petrov, *Database Internals* (2019), **Part I, chapters 2–4**](https://www.databass.dev/) — the clearest modern treatment of B-Trees, page layout, splits and merges, written for engineers rather than researchers. Read chapters 2–4 and you will understand your database's index better than most of the people using it.
- [Sedgewick & Wayne, *Algorithms* 4th ed., **Section 3.3 (Balanced Search Trees)**](https://algs4.cs.princeton.edu/home/) — the left-leaning red-black tree presentation, which is the only version of red-black insertion that fits on one page and is comprehensible.
- [Knuth, *TAOCP* Vol 3, **Section 6.2.2**](https://www-cs-faculty.stanford.edu/~knuth/taocp.html) — the original analysis of BST behaviour under random insertion and the asymmetric-delete problem; dense, and the source everyone else is paraphrasing.
