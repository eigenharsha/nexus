    ## The idea in one paragraph

    Some problems break into smaller versions of themselves — and the smaller versions **repeat**.
    A plain recursive solution solves each repeat from scratch, so the work explodes exponentially
    even though there are only a handful of genuinely distinct subproblems. **Dynamic programming**
    is the observation that you should write each answer down the first time you compute it, and
    look it up afterwards. That is the entire technique. Everything else — memoization, tabulation,
    the recipe, the space tricks — is bookkeeping around that one idea.

    ### The analogy

    You are climbing a staircase and someone asks how many distinct ways there are to reach step 30,
    taking 1 or 2 steps at a time.

    - **The naive approach.** "Ways to reach 30 = ways to reach 29 + ways to reach 28." To work out
      29 you compute 28 and 27. To work out 28 you compute 27 and 26 — **and you already computed 28
      and 27 a moment ago, but you threw the answers away.** By step 30 you have recomputed the same
      handful of numbers millions of times.
    - **Dynamic programming.** Keep a notepad. Every time you work out "ways to reach step k", write
      it down. Next time it comes up, read it off the pad. **30 numbers, computed once each.**

    The staircase has only 30 distinct questions in it. The naive approach asks them 2.7 million
    times. That gap is not an optimisation — it is the difference between a program that finishes and
    one that does not.

    ### Every term, defined

    - **Subproblem** — a smaller instance of the same problem. "Ways to reach step 28" is a
      subproblem of "ways to reach step 30".
    - **Overlapping subproblems** — the same subproblem is needed more than once. **This is the
      condition that makes DP worth doing.** Merge sort's subproblems never overlap, which is why
      merge sort is divide-and-conquer, not DP.
    - **Optimal substructure** — an optimal solution is built from optimal solutions to
      subproblems. **This is the condition that makes DP correct.** It is why shortest paths have DP
      solutions and longest *simple* paths do not.
    - **Memoization** — top-down: write the recursion naturally, cache the results. "Memo" as in
      memorandum, not memorise.
    - **Tabulation** — bottom-up: fill a table from the base cases upward, no recursion.
    - **State** — the set of values that identify one subproblem. Choosing the state is the whole
      design.
    - **Transition (recurrence)** — the formula giving one state's answer from smaller states.
    - **Base case** — the states you know without computing.

    ### The smallest working example

    ```python
    # fib.py — CPython 3.12
    calls = {"naive": 0, "memo": 0}

    def fib_naive(n):
        calls["naive"] += 1
        if n < 2:
            return n
        return fib_naive(n - 1) + fib_naive(n - 2)

    def fib_memo(n, seen=None):
        if seen is None:
            seen = {}
        calls["memo"] += 1
        if n < 2:
            return n
        if n in seen:
            return seen[n]
        seen[n] = fib_memo(n - 1, seen) + fib_memo(n - 2, seen)
        return seen[n]

    def fib_table(n):
        """Bottom-up. No recursion, no dictionary, no call overhead."""
        if n < 2:
            return n
        prev, cur = 0, 1
        for _ in range(n - 1):
            prev, cur = cur, prev + cur
        return cur
    ```

    | 30 | 2,692,537 | 59 | 31 | 0.1566 s |
    | 35 | **29,860,703** | **69** | 36 | **2.6146 s** |

    with `time.perf_counter`. Reproduce with `extra_dsa.py w14m5`.

    **At n = 35 the naive version makes 432,764× more calls than the memoized one.** Extrapolate:
    the call count roughly multiplies by 1.618 (the golden ratio) per increment of `n`, so `fib(50)`
    naive is about 40 billion calls — around an hour. `fib(50)` memoized is 99 calls, instantly.

    Notice that **memoized calls are almost exactly `2n − 1`**, and table steps are `n + 1`. The
    memoized version still pays for a function call and a dict lookup per state; the table pays for
    neither.

    ### Line-by-line walkthrough

    - `if n < 2: return n` — the base case. `fib(0) = 0`, `fib(1) = 1`. Every DP needs base cases,
      and getting them wrong is the most common source of off-by-one answers.
    - `return fib_naive(n-1) + fib_naive(n-2)` — the recurrence. Correct, and catastrophically
      wasteful: the two branches recompute enormous overlapping subtrees.
    - `if n in seen: return seen[n]` — **the entire DP.** One line. Everything above and below it is
      the same recursion.
    - `seen[n] = ...` before `return seen[n]` — store, then return. Storing after the return
      statement (a real bug people write) means nothing is ever cached and you have the naive
      version with extra steps.
    - `prev, cur = cur, prev + cur` — the tabulated version, which notices that computing `fib(n)`
      only ever needs the previous two values. **Space `O(1)` instead of `O(n)`.** This is the same
      space-reduction move that Layer 2 applies to edit distance, in its simplest possible form.

    <Warning>
    `def fib_memo(n, seen={})` — a mutable default argument — is a real Python trap. The dictionary
    is created **once, when the function is defined**, and shared across every call for the lifetime
    of the process. For pure Fibonacci that happens to work as a global cache. For anything whose
    answers depend on other inputs, it silently returns results computed for a *different* problem.
    Use `seen=None` and create it inside, as above.
    </Warning>

    ### Climbing stairs, the canonical first DP

    ```python
    def climb_stairs(n: int) -> int:
        """Ways to reach step n taking 1 or 2 steps at a time."""
        if n <= 2:
            return n
        dp = [0] * (n + 1)
        dp[1], dp[2] = 1, 2            # base cases
        for i in range(3, n + 1):
            dp[i] = dp[i - 1] + dp[i - 2]     # arrive from one below, or two below
        return dp[n]

    assert climb_stairs(1) == 1
    assert climb_stairs(2) == 2      # (1,1) or (2)
    assert climb_stairs(3) == 3      # (1,1,1), (1,2), (2,1)
    assert climb_stairs(45) == 1836311903
    ```

    The recurrence is `dp[i] = dp[i-1] + dp[i-2]` because the *last* move to reach step `i` was
    either a 1-step from `i−1` or a 2-step from `i−2`, and those two sets of routes are disjoint and
    cover everything. **Reasoning about "what was the last move?" is the single most reliable way to
    find a DP recurrence** — more reliable than looking for a pattern.

    ### Guided practice: the grid

    ```python
    def unique_paths(rows: int, cols: int, blocked: set[tuple[int, int]]) -> int:
        """Paths from top-left to bottom-right moving only right or down,
        avoiding blocked cells."""
        if (0, 0) in blocked or (rows - 1, cols - 1) in blocked:
            return 0
        dp = [[0] * cols for _ in range(rows)]
        dp[0][0] = 1
        for r in range(rows):
            for c in range(cols):
                if (r, c) in blocked:
                    dp[r][c] = 0
                    continue
                if r == 0 and c == 0:
                    continue                 # already seeded
                # TODO 1: add the ways that arrive from above (if r > 0)
                # TODO 2: add the ways that arrive from the left (if c > 0)
                pass
        return dp[rows - 1][cols - 1]

    print(unique_paths(3, 3, set()))            # expected 6
    print(unique_paths(3, 3, {(1, 1)}))         # expected 2
    print(unique_paths(1, 5, set()))            # expected 1
    print(unique_paths(3, 3, {(0, 1), (1, 0)})) # expected 0
    ```

    <AccordionGroup>
      <Accordion title="Answers">
      ```python
      total = 0
      if r > 0:
          total += dp[r - 1][c]      # TODO 1: arrived by moving down
      if c > 0:
          total += dp[r][c - 1]      # TODO 2: arrived by moving right
      dp[r][c] = total
      ```

      **Why the loop order works.** When you compute `dp[r][c]`, you need `dp[r-1][c]` (previous
      row, already complete) and `dp[r][c-1]` (same row, already computed this iteration). Row-major
      order satisfies both. **Choosing an evaluation order in which every dependency is already
      computed is step 4 of the recipe**, and getting it wrong produces zeros rather than an error.

      **Why `dp[r][c] = 0` for a blocked cell.** Zero ways to be there means zero ways propagate
      onward. Setting it to 0 and continuing is cleaner than special-casing every neighbour, and it
      is why `unique_paths(3, 3, {(0,1),(1,0)})` correctly returns 0 — both routes out of the start
      are walled off.

      **Complexity:** `O(rows × cols)` time and space. The space is reducible to `O(cols)` — you
      only ever read the previous row — which is exactly the trick Layer 2 applies to edit distance.
      </Accordion>

    ### Checkpoint — 5 questions before you continue

    <AccordionGroup>
      <Accordion title="1. What two properties must a problem have for DP to apply?">
        **Overlapping subproblems** (the same subproblem recurs, so caching pays) and **optimal
        substructure** (an optimal solution is composed of optimal sub-solutions, so caching is
        correct). Missing the first means DP is pointless; missing the second means DP is wrong.
      </Accordion>
      <Accordion title="2. Memoization or tabulation?">
        Memoization is top-down: write the natural recursion, add a cache. Easier to derive, and it
        only computes the states you actually need. Tabulation is bottom-up: fill a table in
        dependency order. No recursion limit, no call overhead, and it enables space optimisation
        because you control the fill order. **Derive with memoization, ship tabulation.**
      </Accordion>
      <Accordion title="3. Why is `fib` with memoization O(n) rather than O(2^n)?">
        Because there are only `n+1` distinct subproblems — `fib(0)` through `fib(n)` — and each is
        computed once. Every other call is a cache hit costing O(1). **The complexity of a DP is
        (number of states) × (cost per transition)**, and that formula answers this question for
        every DP you will ever write.
      </Accordion>
      <Accordion title="4. What is 'state' in dynamic programming?">
        The minimal set of values that uniquely identify a subproblem. For Fibonacci, `n`. For edit
        distance, `(i, j)` — the prefix lengths. For knapsack, `(item_index, remaining_capacity)`.
        **Choosing the state is 90% of solving a DP problem.** If your recurrence needs information
        your state does not carry, the state is wrong.
      </Accordion>
      <Accordion title="5. Why does DP not solve the longest simple path problem?">
        Because it lacks optimal substructure. The longest simple path from A to C does not
        decompose into the longest simple path from A to B plus B to C — those two might reuse a
        node, making the combination not simple. Shortest paths *do* have the property (a shortest
        path's subpaths are shortest), which is why Dijkstra and Bellman-Ford exist and no
        polynomial longest-path algorithm does. Longest simple path is NP-hard.
      </Accordion>
    </AccordionGroup>

    ## The five-step recipe

    Applied identically to every problem below. Write these five lines before writing code, every
    time.

    <Steps>
      <Step title="1. State — what identifies a subproblem?">
        Name it precisely: "`dp[i][j]` = the edit distance between the first `i` characters of `a`
        and the first `j` characters of `b`". If you cannot write this sentence, you do not have a
        DP yet. **This step is where the difficulty is.**
      </Step>
      <Step title="2. Transition — how does one state follow from smaller ones?">
        The recurrence. Derive it by asking *"what was the last decision?"* and enumerating the
        possibilities. Each possibility becomes a term.
      </Step>
      <Step title="3. Base case — which states do you know for free?">
        Usually the empty case. Edit distance from an empty string to a length-`j` string is `j`.
        Get these wrong and every answer is off by a constant.
      </Step>
      <Step title="4. Evaluation order — in what order can you fill it?">
        Every state's dependencies must already be computed. For a 2-D table with dependencies above
        and to the left, row-major order works. Memoization sidesteps this step entirely, which is
        why it is easier to derive with.
      </Step>
      <Step title="5. Answer — which cell is the result?">
        Usually the last one, but not always. "Longest increasing subsequence" is `max(dp)`, not
        `dp[-1]`, because the best subsequence need not end at the last element.
      </Step>
    </Steps>

    ## Edit distance, derived with the recipe

    **1. State.** `dp[i][j]` = minimum edits to turn `a[:i]` into `b[:j]`.

    **2. Transition.** What was the last operation?

    - If `a[i-1] == b[j-1]`, the characters already match: `dp[i][j] = dp[i-1][j-1]`, cost 0.
    - Otherwise, one of three things happened:
      - **Delete** `a[i-1]`: `dp[i-1][j] + 1`
      - **Insert** `b[j-1]`: `dp[i][j-1] + 1`
      - **Substitute** `a[i-1]` with `b[j-1]`: `dp[i-1][j-1] + 1`

      Take the minimum.

    **3. Base case.** `dp[i][0] = i` (delete everything), `dp[0][j] = j` (insert everything).

    **4. Order.** Row-major: each cell needs up, left and up-left, all already filled.

    **5. Answer.** `dp[n][m]`.

    ```python
    def edit_distance(a: str, b: str) -> int:
        n, m = len(a), len(b)
        dp = [[0] * (m + 1) for _ in range(n + 1)]
        for i in range(n + 1):
            dp[i][0] = i
        for j in range(m + 1):
            dp[0][j] = j
        for i in range(1, n + 1):
            for j in range(1, m + 1):
                cost = 0 if a[i - 1] == b[j - 1] else 1
                dp[i][j] = min(
                    dp[i - 1][j] + 1,          # delete a[i-1]
                    dp[i][j - 1] + 1,          # insert b[j-1]
                    dp[i - 1][j - 1] + cost,   # substitute (or match, cost 0)
                )
        return dp[n][m]

    assert edit_distance("kitten", "sitting") == 3
    assert edit_distance("", "abc") == 3
    assert edit_distance("abc", "abc") == 0
    ```

    `kitten → sitting` is 3: substitute k→s, substitute e→i, insert g.

    ## Space optimisation, and what it costs

    Look at the recurrence: `dp[i][j]` depends only on row `i` and row `i−1`. **Rows 0 through
    `i−2` are never read again.** So keep two rows:

    ```python
    def edit_distance_two_rows(a: str, b: str) -> int:
        """O(min(n, m)) space instead of O(n*m)."""
        if len(b) > len(a):
            a, b = b, a                    # iterate over the SHORTER string
        n, m = len(a), len(b)
        prev = list(range(m + 1))
        for i in range(1, n + 1):
            cur = [i] + [0] * m
            ai = a[i - 1]
            for j in range(1, m + 1):
                cur[j] = min(prev[j] + 1, cur[j - 1] + 1,
                             prev[j - 1] + (ai != b[j - 1]))
            prev = cur
        return prev[m]
    ```

    Measured, on random DNA-like strings (alphabet `acgt`):

    | Length (both) | Full matrix time | Two-row time | Full matrix peak | Two-row peak | Memory ratio |
    | --- | --- | --- | --- | --- | --- |
    | 500 | 490.6 ms | 410.2 ms | 4.41 MB | 0.045 MB | **97×** |
    | 2,000 | 17,749.1 ms | 14,837.4 ms | 154.54 MB | 0.165 MB | **936×** |
    | 4,000 | 81,741.1 ms | 87,132.6 ms | **634.67 MB** | **0.325 MB** | **1,952×** |

    <Info>
    Method: CPython 3.12.9, M3 Pro, `tracemalloc` peak for the Python heap, both implementations
    verified to return identical distances at every size. Reproduce with `extra_dsa.py w14m5`.
    </Info>

    Three things to read out of that table.

    1. **The memory reduction is enormous and grows with `n`** — 1,952× at length 4,000. The full
       matrix is `O(nm)`; two rows is `O(m)`. At length 4,000 the full matrix is 634 MB, and at
       10,000 it would be ~4 GB. **The space optimisation is what makes the algorithm usable at
       all**, not a micro-optimisation.
    2. **The time is essentially unchanged**, and at 4,000 the two-row version is *slightly slower*
       (87.1 s vs 81.7 s). Both do the same `n×m` cell computations. The two-row version allocates a
       fresh list per row, which costs a little; the full-matrix version pays more for cache misses
       on a 634 MB structure. **They roughly cancel**, and which wins depends on the size — the
       two-row version wins at 500 and 2,000 and loses at 4,000.
    3. **The pure-Python cost is brutal.** 4,000 × 4,000 is 16 million cell computations in 82
       seconds — about 5 µs per cell. In C this is roughly 20 ns per cell. **If you need edit
       distance on real data, use `rapidfuzz` (pin `rapidfuzz==3.10.1`)**, which implements the
       bit-parallel Myers algorithm in C++ and is thousands of times faster. Write it yourself to
       understand it; import it to ship it. This is the same conclusion as week 13's LRU and KMP.

    <Warning>
    **The two-row version cannot reconstruct the alignment.** Backtracking requires walking the full
    table from `dp[n][m]` back to `dp[0][0]`, following which of the three predecessors produced
    each value — and you threw those rows away. So: **need the number, use two rows; need the
    alignment, keep the matrix** (or use Hirschberg's algorithm, which gets the alignment in
    `O(min(n,m))` space by divide-and-conquer at 2× the time — see Layer 3).
    </Warning>

    ## Reference implementation: a mini `diff`

    ```python
    # minidiff.py — CPython 3.12. Edit distance with backtracking, over lines.
    from __future__ import annotations
    from dataclasses import dataclass
    from enum import Enum


    class Op(Enum):
        EQUAL = " "
        DELETE = "-"
        INSERT = "+"
        REPLACE = "~"


    @dataclass(frozen=True, slots=True)
    class Edit:
        op: Op
        old_index: int | None
        new_index: int | None
        text: str


    def align(a: list[str], b: list[str]) -> tuple[int, list[Edit]]:
        """Levenshtein distance over sequences, with the alignment path.

        Keeps the full (n+1) x (m+1) matrix because backtracking requires it.
        Memory is O(n*m) ints; for line-diffing two 10,000-line files that is
        10^8 cells, which is why real diff tools use Myers' algorithm instead.
        """
        n, m = len(a), len(b)
        dp = [[0] * (m + 1) for _ in range(n + 1)]
        for i in range(n + 1):
            dp[i][0] = i
        for j in range(m + 1):
            dp[0][j] = j
        for i in range(1, n + 1):
            ai = a[i - 1]
            row, prev = dp[i], dp[i - 1]
            for j in range(1, m + 1):
                row[j] = min(prev[j] + 1, row[j - 1] + 1,
                             prev[j - 1] + (ai != b[j - 1]))

        # Backtrack from the bottom-right. At each cell, work out which
        # predecessor produced this value and emit the corresponding edit.
        edits: list[Edit] = []
        i, j = n, m
        while i > 0 or j > 0:
            if i > 0 and j > 0 and a[i - 1] == b[j - 1] and dp[i][j] == dp[i - 1][j - 1]:
                edits.append(Edit(Op.EQUAL, i - 1, j - 1, a[i - 1]))
                i, j = i - 1, j - 1
            elif i > 0 and j > 0 and dp[i][j] == dp[i - 1][j - 1] + 1:
                edits.append(Edit(Op.REPLACE, i - 1, j - 1, b[j - 1]))
                i, j = i - 1, j - 1
            elif i > 0 and dp[i][j] == dp[i - 1][j] + 1:
                edits.append(Edit(Op.DELETE, i - 1, None, a[i - 1]))
                i -= 1
            else:
                edits.append(Edit(Op.INSERT, None, j - 1, b[j - 1]))
                j -= 1
        edits.reverse()
        return dp[n][m], edits


    def unified(a: list[str], b: list[str], context: int = 3) -> str:
        """Render the alignment as a unified-diff-like output."""
        _, edits = align(a, b)
        keep = set()
        for idx, e in enumerate(edits):
            if e.op is not Op.EQUAL:
                for k in range(max(0, idx - context), min(len(edits), idx + context + 1)):
                    keep.add(k)
        out, last_shown = [], -2
        for idx, e in enumerate(edits):
            if idx not in keep:
                continue
            if idx != last_shown + 1:
                out.append("@@")
            out.append(f"{e.op.value} {e.text}")
            last_shown = idx
        return "\n".join(out)
    ```

    ```python
    # test_minidiff.py — pytest 8.x
    import pytest
    from minidiff import align, unified, Op


    def test_distance_matches_known_values():
        assert align(list("kitten"), list("sitting"))[0] == 3
        assert align(list("flaw"), list("lawn"))[0] == 2
        assert align([], list("abc"))[0] == 3
        assert align(list("abc"), list("abc"))[0] == 0


    def test_alignment_length_equals_distance():
        """Every non-EQUAL edit costs exactly 1, so they must sum to the distance."""
        for a, b in [("kitten", "sitting"), ("", "abc"), ("abc", ""), ("sunday", "saturday")]:
            d, edits = align(list(a), list(b))
            assert sum(1 for e in edits if e.op is not Op.EQUAL) == d


    def test_alignment_reconstructs_the_target():
        """Applying the edits to `a` must produce `b`. This is the real test."""
        for a, b in [("kitten", "sitting"), ("abcdef", "azced"), ("", "xyz"), ("xyz", "")]:
            _, edits = align(list(a), list(b))
            rebuilt = []
            for e in edits:
                if e.op in (Op.EQUAL, Op.REPLACE, Op.INSERT):
                    rebuilt.append(e.text)
            assert "".join(rebuilt) == b


    def test_identical_input_produces_no_edits():
        d, edits = align(list("same"), list("same"))
        assert d == 0
        assert all(e.op is Op.EQUAL for e in edits)


    def test_empty_both_sides():
        assert align([], []) == (0, [])


    def test_line_diff():
        a = ["def f():", "    return 1", "", "print(f())"]
        b = ["def f():", "    return 2", "", "print(f())"]
        out = unified(a, b)
        assert "- " in out and "+ " in out or "~ " in out
    ```

    <Check>
    `test_alignment_reconstructs_the_target` is the test that matters. The distance is easy to get
    right and the *path* is easy to get wrong — an off-by-one in the backtrack, or checking the
    three predecessors in the wrong order, produces a plausible-looking edit list that does not
    actually transform `a` into `b`. Applying the edits and comparing against `b` is the only check
    that catches it, and it catches everything.
    </Check>

    ## Trade-offs table

    | Situation | Choose | Instead of | Because |
    | --- | --- | --- | --- |
    | Deriving a solution for the first time | memoization | tabulation | write the natural recursion and add `@lru_cache`; you can convert later |
    | Shipping it | tabulation | memoization | no recursion limit, no call overhead, and it enables space optimisation |
    | You need only the answer value | two-row / rolling array | full table | measured 1,952× less memory at n = 4,000 |
    | You need the path or alignment | full table, or Hirschberg | two rows | backtracking needs the table; Hirschberg gets the path in O(min(n,m)) space at 2× time |
    | Only a few states are reachable | memoization | tabulation | tabulation fills every cell whether needed or not; sparse state spaces waste most of it |
    | Recursion would go deeper than ~1,000 | tabulation | memoization | CPython raises `RecursionError`; raising the limit risks a segfault |
    | Edit distance on real data at scale | `rapidfuzz` (`3.10.1`) | your own | bit-parallel Myers in C++; pure Python is ~5 µs/cell |
    | The state space is exponential (TSP, subset-sum with large values) | branch and bound, or approximation | DP | bitmask DP over `n` cities is `O(2ⁿ·n²)` — fine at n=20, hopeless at n=40 |
    | The greedy choice is provably safe | greedy | DP | if the greedy-choice property holds, greedy is faster and simpler; check before reaching for DP |

    ## What breaks in the real world

    A content-moderation service compared each incoming message against a blocklist of ~8,000
    banned phrases, using Levenshtein distance so that "sp4m" and "s p a m" would still match. The
    implementation used the full-matrix edit distance, one comparison per phrase per message.

    Messages averaged 80 characters and phrases averaged 12, so each comparison was a 80 × 12 = 960-
    cell table. 8,000 phrases meant 7.7 million cells per message. At roughly 5 µs per cell in pure
    Python that is 38 seconds per message — obviously untenable — so the original author had used
    `python-Levenshtein` (a C extension), bringing it to about 40 ms per message. Acceptable.

    Then a product change allowed users to paste longer content, and the message length cap went
    from 500 to 50,000 characters.

    **The cost is `O(n·m)` per phrase, so a 100× increase in `n` is a 100× increase in cost.**
    Per-message time went from 40 ms to about 4 seconds. Worse, the service held the full matrix per
    comparison: a 50,000 × 12 int matrix is 600,000 cells, and with 16 worker threads each holding
    one, memory spiked. Requests queued, the health check timed out, and the pod was killed and
    restarted — repeatedly, because the queued messages replayed on restart.

    Three things were wrong, and only the first is about DP:

    1. **Edit distance was the wrong tool for the job.** The question was "does this 50,000-character
       message *contain* something close to this phrase?", which is **approximate substring
       matching**, not whole-string edit distance. The fix is a windowed comparison, or better, the
       `partial_ratio` family in `rapidfuzz` — which is `O(n·m)` in the *phrase* length, not the
       message length, because it slides a window of the phrase's size. That alone is a ~4,000×
       reduction for a 50,000-character message.
    2. **No input bound.** The complexity was `O(message_length × phrase_length × phrase_count)` and
       exactly one of those three was user-controlled and uncapped. **Any user-controlled term in a
       product of complexities is an availability risk** — the same lesson as week 13 module 1's
       war story, in a different algorithm.
    3. **Restart replay made it self-sustaining.** The pod died, the messages requeued, the new pod
       died on the same messages. **A slow path plus a restart-on-timeout plus at-least-once
       delivery is a system that cannot recover on its own**, and that combination is what turned a
       latency regression into an outage.

    The eventual design: a fast exact-match pass with Aho-Corasick (week 13 module 2) to narrow
    8,000 phrases to a handful of candidates, then `rapidfuzz.partial_ratio` on only those, with a
    hard cap on message length for the fuzzy pass. Per-message time became 3 ms at any input size.

    ### Design checkpoint

    <Accordion title="You must deduplicate 5,000,000 product listings where the same product is described differently by different sellers. Edit distance is O(n*m) per pair and there are 1.25 x 10^13 pairs. Design it.">
    **Model answer.**

    **Name the real problem: it is not the distance function, it is the number of pairs.** 1.25 ×
    10¹³ comparisons at even 1 µs each is 145 days. Making the distance function 100× faster still
    leaves you with 1.5 days. **You must avoid computing most of the pairs**, which means blocking
    or hashing, not a better metric.

    **The design, in three stages.**

    **1. Blocking (the essential step).** Only compare listings that could plausibly match.

    - **MinHash + LSH** on character 3-grams or word shingles. Jaccard similarity above a threshold
      lands in the same LSH bucket with high probability. With 128 permutations and 16 bands of 8
      rows, pairs with Jaccard above ~0.7 collide with probability above 0.99, while dissimilar
      pairs almost never do. **This reduces 1.25 × 10¹³ pairs to perhaps 10⁷–10⁸ candidate pairs** —
      five or six orders of magnitude, which is the whole game.
    - Cheaper alternatives worth measuring first: block by exact brand, by category, or by a
      normalised numeric attribute like model number. Often a domain key gets you 90% of the
      reduction for 5% of the effort, and it is embarrassing to build LSH when `GROUP BY brand`
      would have done.

    **2. Fuzzy scoring on candidates only.** `rapidfuzz.process.cdist` on the candidate pairs, which
    is SIMD-accelerated bit-parallel Myers. At roughly 1 µs per pair for short strings, 10⁸ pairs is
    about 100 seconds on one core and trivially parallel across cores.

    **3. Clustering, and this is where the subtlety is.** Similarity is **not transitive**: A
    matches B, B matches C, A does not match C. Options:

    - **Connected components via union-find** (week 14 module 3). Simple, fast, and it produces
      *chains* — a long ladder of pairwise-similar listings merges into one giant cluster containing
      genuinely different products. **This is the failure mode to watch for**, and you detect it by
      looking at the cluster size distribution: if your largest cluster has 40,000 members, you have
      it.
    - **Correlation clustering or a threshold on average intra-cluster similarity.** More expensive,
      resistant to chaining.
    - **The pragmatic answer: union-find, then split any cluster above a size threshold** by
      re-clustering it with a higher similarity threshold. Ugly, effective, and it bounds the damage.

    **Normalisation before any of this.** Lowercase, NFC-normalise (week 13 module 2), strip
    punctuation, expand common abbreviations, sort tokens. **This is worth more than any algorithm
    choice** — normalisation turns many fuzzy matches into exact matches, which are free.

    **What I would not do: embeddings, at first.** Semantic similarity via a sentence embedding plus
    a vector index is genuinely better at "the same product described completely differently", and
    it is what you will build in week 27. But it costs an embedding pass over 5M listings, a vector
    index, and a recall/precision tuning exercise. **Start with normalisation plus LSH plus
    rapidfuzz, measure the residual error, and add embeddings only for the cases that survive** —
    which will be the interesting ones, and by then you will know how many there are.
    </Accordion>

    ## The DP complexity formula, and when it fails you

    **Time = (number of states) × (cost per transition). Space = (number of states), unless you can
    roll it.** That formula answers every complexity question about a DP, and it is also the tool
    for deciding whether DP is viable at all.

    | Problem | States | Per transition | Time | Practical limit |
    | --- | --- | --- | --- | --- |
    | Fibonacci | `n` | O(1) | O(n) | unbounded |
    | Edit distance | `n·m` | O(1) | O(nm) | ~10⁸ cells in C, ~10⁷ in Python |
    | 0/1 knapsack | `n·W` | O(1) | O(nW) | **pseudo-polynomial** — see below |
    | Longest increasing subsequence (DP) | `n` | O(n) | O(n²) | n ≈ 10⁴ |
    | LIS (patience sorting) | `n` | O(log n) | **O(n log n)** | n ≈ 10⁸ |
    | Travelling salesman (bitmask) | `2ⁿ·n` | O(n) | O(2ⁿ·n²) | **n ≈ 20** |
    | Matrix chain multiplication | `n²` | O(n) | O(n³) | n ≈ 10³ |

    **The knapsack row is the trap.** `O(nW)` looks polynomial. It is not — `W` is a *value*, and its
    encoding length is `log W` bits, so the algorithm is exponential in the input *size*. With
    `n = 100` items and `W = 10⁹` (capacity in grams, or a budget in cents), the table has 10¹¹
    cells. **The algorithm you were taught in an interview is unusable on real data with fine-grained
    weights**, and the standard escape is to scale the weights down and accept an approximation —
    which is exactly what an FPTAS does.

    **The TSP row is the other trap.** Held-Karp turns `O(n!)` into `O(2ⁿ·n²)`, which is a genuine
    triumph — and `2⁴⁰` is 10¹² states, each needing a table entry. **The exponential is still
    exponential.** DP made the constant enormously better and changed nothing structural. Being able
    to say that is what separates understanding DP from having memorised it.

    ## Hirschberg: the alignment in linear space

    The Layer 2 trade — "two rows gives the number but not the path" — is not actually forced.
    Hirschberg (1975) gets the alignment in `O(min(n,m))` space at 2× the time, by divide and conquer:

    1. Split `a` in half at index `n/2`.
    2. Compute the last DP row of `a[:n/2]` against `b`, forward, in two rows.
    3. Compute the last DP row of `reversed(a[n/2:])` against `reversed(b)`, in two rows.
    4. Add the two rows element-wise. **The index `k` minimising the sum is where the optimal
       alignment crosses the midpoint of `a`.** That single index is the only thing you keep.
    5. Recurse on `(a[:n/2], b[:k])` and `(a[n/2:], b[k:])`.

    The recurrence is `T(n,m) = O(nm) + T(n/2, k) + T(n/2, m−k)`, and the two subproblems together
    have half the total area, so the total work is `nm + nm/2 + nm/4 + … = 2nm`. **Exactly 2× the
    time, and `O(min(n,m))` space instead of `O(nm)`.**

    Applied to the measured numbers: at length 4,000 the full matrix needs 634.67 MB and Hirschberg
    needs about 0.33 MB while still producing the alignment. **This is what makes `diff` on large
    files possible**, and it is one of the most elegant space-time trades in algorithms — worth
    implementing once for the pleasure of it.

    ## Myers' diff: why `git diff` is not edit distance

    `git diff` does not compute Levenshtein distance. It computes the **shortest edit script** under
    insertions and deletions only (no substitutions), using Myers (1986), which runs in
    `O((n+m)·D)` where `D` is the size of the edit script.

    **The insight is to change what you index.** Instead of a table indexed by `(i, j)`, index by
    `(d, k)` — the number of edits `d` so far, and the diagonal `k = i − j`. For each `d`, you only
    track the furthest-reaching point on each diagonal, which is `O(d)` values. Since real diffs are
    usually small relative to file size, `D` is small and the algorithm is nearly linear.

    | Files | Full DP `O(nm)` | Myers `O((n+m)·D)` |
    | --- | --- | --- |
    | 10,000 lines, 10 lines changed | 10⁸ cells | ~2 × 10⁵ operations, **500× less** |
    | 10,000 lines, 5,000 lines changed | 10⁸ cells | ~10⁸, no better |

    **Myers is fast exactly when the diff is small, which is the common case for source control and
    the whole reason it was chosen.** Git additionally caps the work with a heuristic and falls back
    to a coarser diff on pathological inputs — `diff --minimal` disables that fallback, which is why
    it can be dramatically slower.

    ## DP on trees, and the LIS speed-up

    **DP on trees** works because a subtree is a natural subproblem and a tree has no cycles, so the
    dependency order is just post-order traversal.

    ```python
    def max_independent_set(tree: dict[int, list[int]], root: int) -> int:
        """Largest set of nodes with no two adjacent. O(V), one post-order pass.
        dp[node] = (best if node EXCLUDED, best if node INCLUDED)"""
        # Iterative post-order, because a 10,000-deep tree kills recursion.
        order, stack, parent = [], [(root, None)], {root: None}
        while stack:
            n, p = stack.pop()
            order.append(n)
            for c in tree.get(n, ()):
                if c != p:
                    parent[c] = n
                    stack.append((c, n))
        dp: dict[int, tuple[int, int]] = {}
        for n in reversed(order):                 # children before parents
            excl = incl = 0
            for c in tree.get(n, ()):
                if c == parent[n]:
                    continue
                ce, ci = dp[c]
                excl += max(ce, ci)               # child free to do either
                incl += ce                        # child must be excluded
            dp[n] = (excl, incl + 1)
        return max(dp[root])
    ```

    **Longest increasing subsequence** is the classic example of a DP that a better algorithm
    replaces. The `O(n²)` DP is `dp[i] = 1 + max(dp[j] for j < i if a[j] < a[i])`. Patience sorting
    gets `O(n log n)`:

    ```python
    import bisect

    def lis_length(a: list[int]) -> int:
        """tails[k] = smallest possible tail of an increasing subsequence of length k+1."""
        tails: list[int] = []
        for x in a:
            i = bisect.bisect_left(tails, x)
            if i == len(tails):
                tails.append(x)
            else:
                tails[i] = x
        return len(tails)
    ```

    `tails` is **not** the LIS — it is a list of the best possible tails at each length, and its
    length happens to equal the LIS length. Reconstructing the actual subsequence needs a parallel
    predecessor array. **The `O(n log n)` version exists because `bisect` replaces the linear scan
    over previous states**, which is a general move: *when a DP transition is "find the best among
    all previous states satisfying a predicate", a search structure may replace the scan.* Segment
    trees and monotonic deques do this for other DP families.

    ## Production failure modes

    | Failure mode | Signature | Detection |
    | --- | --- | --- |
    | Mutable default `seen={}` as a memo | wrong answers that depend on call history; works in isolated tests | `seen=None` and create inside; or `functools.lru_cache` |
    | `@lru_cache` on a method | the cache holds `self`, so instances are never garbage collected | `lru_cache` on a module-level function, or `cached_property`, or an explicit dict |
    | `RecursionError` on real input | memoized DP whose depth is data-dependent | convert to tabulation; test with the largest realistic input |
    | Full DP matrix on large inputs | OOM; measured 634 MB at n = 4,000 and ~4 GB at 10,000 | roll to two rows, or Hirschberg if the path is needed |
    | Two-row version, then someone needs the path | rewrite under deadline | decide up front whether the path is needed; use Hirschberg to have both |
    | Knapsack with a large capacity | table of `n·W` cells is unallocatable | it is pseudo-polynomial; scale weights and accept an FPTAS approximation |
    | User-controlled dimension in an `O(nm)` DP | latency quadratic in payload size | cap the input at the API edge; the complexity is a product and one term is uncapped |
    | Wrong evaluation order | zeros or wrong answers, no error | assert dependencies are filled; test against a brute-force oracle on small inputs |
    | Float DP with accumulated error | answers off by tiny amounts; comparisons flip | use integers where possible; DP over probabilities should use log-space sums |

    ## Frontier and research pointers

    - **Bellman (1954), "The Theory of Dynamic Programming."** *Bull. AMS* 60(6). — **Takeaway:** the
      Principle of Optimality — an optimal policy's remaining decisions form an optimal policy for
      the resulting state — is exactly the optimal-substructure condition, stated first for control
      problems rather than algorithms. (The name "dynamic programming" was chosen partly to sound
      unobjectionable to a defence-department budget reviewer, which Bellman cheerfully admits in his
      autobiography.)
    - **Wagner & Fischer (1974), "The String-to-String Correction Problem."** *JACM* 21(1). —
      **Takeaway:** the `O(nm)` edit-distance table with insert, delete and substitute — the
      algorithm in Layer 2, in its original form, with the proof of optimality.
    - **Hirschberg (1975), "A Linear Space Algorithm for Computing Maximal Common Subsequences."**
      *CACM* 18(6). — **Takeaway:** divide-and-conquer over the DP table recovers the alignment path
      in `O(min(n,m))` space at exactly 2× the time; one of the most elegant space-time trades in the
      literature.
    - **Myers (1986), "An O(ND) Difference Algorithm and Its Variations."** *Algorithmica* 1(2). —
      **Takeaway:** indexing by (edit count, diagonal) instead of (i, j) gives `O((n+m)D)`, which is
      near-linear when the diff is small; this is what `git diff` runs.
    - **Masek & Paterson (1980), "A Faster Algorithm Computing String Edit Distances."** *JCSS* 20(1).
      — **Takeaway:** the Four Russians technique precomputes all possible `t × t` blocks of the DP
      table, giving `O(nm / log² n)` — a rare sub-quadratic result, and the ancestor of the
      bit-parallel methods that `rapidfuzz` actually uses.
    - **Backurs & Indyk (2015), "Edit Distance Cannot Be Computed in Strongly Subquadratic Time
      (unless SETH is false)."** STOC. — **Takeaway:** the `O(nm)` bound is essentially optimal under
      a standard complexity assumption, so **stop looking for a fundamentally faster exact
      algorithm** — the wins available are constant-factor (bit-parallelism) or approximate.

    2. **Hirschberg** — the alignment in linear space at 2× time.

    The open questions, which are the actual research:

    - **What is the distribution of `D/n` in real commits?** Myers is `O((n+m)D)`, so its advantage
      depends entirely on `D` being small. Plot `D` against file size across thousands of real
      commits. Is the "diffs are small" assumption true? **My guess is that it is overwhelmingly
      true for source files and badly false for generated files, lockfiles and minified assets** —
      confirm or refute it with data.
    - **Where does Myers lose to full DP?** There must be a `D/n` ratio above which the constant
      factors favour the simpler algorithm. Find it.
    - **Is Hirschberg's 2× time penalty real?** Measure it. The theory says exactly 2×; cache
      behaviour may make it better or worse, since Hirschberg's working set is tiny and the full
      matrix's is enormous. **Predict which way before you measure.**
    - **How does line-level compare to character-level?** `git` diffs lines. Hashing each line to an
      integer first makes `n` and `m` far smaller and comparisons `O(1)` instead of `O(line length)`.
      Quantify the speedup, and find a case where line-level gives a much worse diff than
      character-level would.
    - **What about the patience diff algorithm** (`git diff --patience`)? It anchors on lines that

      human-readable diffs that Myers sometimes mangles on refactored code. Implement it and find a
      real commit where it is visibly better.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Memoized function returns stale or wrong answers | Mutable default argument `seen={}` shared across all calls | `seen=None`, create inside; or `functools.lru_cache` |
| Memory grows and objects are never collected | `@lru_cache` on a method, holding `self` forever | Module-level function, `cached_property`, or an explicit per-instance dict |
| `RecursionError` on production input | Memoized DP whose recursion depth is data-dependent | Convert to tabulation; do not just raise the recursion limit |
| DP table full of zeros | Evaluation order wrong — cells read before their dependencies were written | Check that every dependency is filled; test against a brute-force oracle |
| Answer off by one | Base cases wrong, usually the empty-prefix row or column | `dp[i][0] = i` and `dp[0][j] = j`; test with empty strings on both sides |
| Backtracked alignment does not reconstruct the target | Predecessor checks in the wrong order, or an off-by-one in the walk | Apply the edits and assert they produce the target — this catches everything |
| OOM on large inputs | Full `O(nm)` matrix; 634 MB at n = 4,000, ~4 GB at 10,000 | Two rows if you need the value; Hirschberg if you need the path |
| Knapsack DP will not allocate | `O(nW)` is pseudo-polynomial and `W` is a value, not a size | Scale the weights and accept an approximation (FPTAS) |
| Fuzzy matching is fine in tests, times out in production | A user-controlled length in the `O(nm)` product | Cap the input at the edge; use approximate substring matching, not whole-string distance |
| Answer is `dp[-1]` but should be `max(dp)` | The optimum need not end at the last state (e.g. LIS) | Step 5 of the recipe: state explicitly which cell is the answer |

## Sources & further reading

**Primary docs**

- [`functools.lru_cache`](https://docs.python.org/3.12/library/functools.html#functools.lru_cache) — read this for `maxsize=None` (which makes it a pure memoizer with no eviction), `cache_info()` for free hit/miss stats, and the explicit warning about keeping references alive.
- [`functools.cache`](https://docs.python.org/3.12/library/functools.html#functools.cache) — `lru_cache(maxsize=None)` under a shorter name, added in 3.9; this is what you want for DP memoization.
- [`rapidfuzz` 3.10.1](https://rapidfuzz.github.io/RapidFuzz/) — read the `process.cdist` docs for batch comparison, and `fuzz.partial_ratio` for approximate *substring* matching, which is the function the war story needed and did not use.
- [`difflib`](https://docs.python.org/3.12/library/difflib.html) — read this for `SequenceMatcher`'s "autojunk" heuristic, which silently ignores elements appearing in more than 1% of a long sequence and produces surprising diffs; it is on by default and catches everyone once.
- [Git `diff` documentation](https://git-scm.com/docs/git-diff) — read the `--diff-algorithm` section for `myers`, `minimal`, `patience` and `histogram`, and note that the default falls back to a heuristic on large inputs.

**Papers**

- [Bellman (1954), *The Theory of Dynamic Programming*, Bulletin of the AMS 60(6), 503–515.](https://doi.org/10.1090/S0002-9904-1954-09848-8) — **Takeaway:** the Principle of Optimality is the optimal-substructure condition, stated originally for sequential decision processes rather than for algorithms.
- [Wagner & Fischer (1974), *The String-to-String Correction Problem*, JACM 21(1), 168–173.](https://doi.org/10.1145/321796.321811) — **Takeaway:** the `O(nm)` edit-distance recurrence with a proof of optimality; the algorithm in Layer 2 is this paper.
- [Hirschberg (1975), *A Linear Space Algorithm for Computing Maximal Common Subsequences*, CACM 18(6), 341–343.](https://doi.org/10.1145/360825.360861) — **Takeaway:** divide-and-conquer on the DP table recovers the alignment in linear space at exactly 2× the time; two pages, and worth reading in full.
- [Myers (1986), *An O(ND) Difference Algorithm and Its Variations*, Algorithmica 1(2), 251–266.](https://doi.org/10.1007/BF01840446) — **Takeaway:** indexing by edit count and diagonal makes the cost depend on the *diff size* rather than the file size, which is why `git diff` is fast.
- [Masek & Paterson (1980), *A Faster Algorithm Computing String Edit Distances*, JCSS 20(1).](https://doi.org/10.1016/0022-0000(80)90002-1) — **Takeaway:** precomputing all small blocks of the DP table gives `O(nm/log² n)`; the ancestor of the bit-parallel implementations in modern libraries.
- [Backurs & Indyk (2015), *Edit Distance Cannot Be Computed in Strongly Subquadratic Time (unless SETH is false)*, STOC.](https://doi.org/10.1145/2746539.2746612) — **Takeaway:** the quadratic bound is essentially tight, so the only available wins are constant-factor or approximate — which tells you where to spend effort.

**Go deeper**

- Cormen et al., *Introduction to Algorithms* 4th ed., **Chapter 14 (Dynamic Programming)** — the rod-cutting and matrix-chain examples are the clearest derivations of "state, then transition" anywhere, and the section on reconstructing the solution is the part most treatments skip.
- [Erik Demaine, *MIT 6.006 lectures 15–22 (Dynamic Programming)*](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2020/) — the five-step framing in this module is essentially Demaine's; his "what are the subproblems?" framing is the most teachable version of DP I have encountered.
- [Skiena, *The Algorithm Design Manual* 3rd ed., **Chapter 10**](https://www.algorist.com/) — read this for the honest discussion of when DP is *not* the answer, and the war stories about problems that look like DP and are not.
