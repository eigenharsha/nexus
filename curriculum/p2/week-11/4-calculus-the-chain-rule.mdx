## The mental model

A derivative answers one question: **if I nudge the input a little, how much does the output move?**

That is it. `df/dx = 3` means "increase `x` by a tiny amount `h`, and `f` increases by about `3h`".

The **chain rule** answers the same question for a chain of functions. If `x` affects `y` and `y`
affects `z`, then the effect of `x` on `z` is the *product* of the two effects:

```
dz/dx = dz/dy × dy/dx
```

Nudges multiply along a chain. That is the entire content of the chain rule, and it is the entire
content of backpropagation.

The only remaining question is *bookkeeping*: in what order do you evaluate the products so that you
do the least work? The answer — start from the output and work backwards — is called reverse mode,
and it is why training a billion-parameter model is possible at all.

### A derivative is a slope

Draw a straight line on paper. Pick two points on it. The **slope** is "how much it went up" divided
by "how much it went across":

```
slope = (y₂ − y₁) / (x₂ − x₁)
```

That is the whole idea, and it is the same idea you used in school for `y = mx + c`.

Now draw a **curve** instead. A curve does not have one slope — it is steeper in some places than
others. So we ask a narrower question: **what is the slope at this particular point?**

Take your point, take another point very close to it, and compute the slope between them. As the
second point gets closer, that slope settles down to a specific number. That number is the
**derivative** at that point, written `f'(x)` or `df/dx`.

In symbols:

```
f'(x) = (f(x + h) − f(x)) / h        as h gets very small
```

### Compute one, right now

```python
def derivative(f, x, h=1e-5):
    return (f(x + h) - f(x - h)) / (2 * h)     # centred difference: see below

f = lambda x: x ** 2
print(derivative(f, 3.0))       # 6.000000000039306
print(derivative(f, 5.0))       # 9.999999999621423
```

For `f(x) = x²` the exact derivative is `2x`, so at `x = 3` it should be 6. We got
6.000000000039306 — correct to about 11 decimal places.

**Why `(f(x+h) − f(x−h)) / (2h)` rather than `(f(x+h) − f(x)) / h`?** Both are valid. The centred
version looks at the same distance either side and cancels more of the error. Layer 2 quantifies the
difference — it is roughly `h²` versus `h`, which at `h = 1e-5` is the difference between an error
around 1e-10 and one around 1e-5.

### The rules you need (there are five)

You could compute every derivative numerically, but the exact rules are short and you will need them
to check your work.

| Function | Derivative | In words |
|---|---|---|
| `c` (a constant) | `0` | Flat things do not change |
| `x^n` | `n·x^(n−1)` | Bring the power down, reduce it by one |
| `e^x` | `e^x` | The one function that is its own slope |
| `ln(x)` | `1/x` | |
| `f(x) + g(x)` | `f'(x) + g'(x)` | Slopes add |
| `f(x) · g(x)` | `f'·g + f·g'` | The **product rule** |
| `f(g(x))` | `f'(g(x)) · g'(x)` | The **chain rule** — the important one |

Check one numerically so you trust it:

```python
import math
print(derivative(lambda x: x ** 3, 2.0))   # 12.00000000021184  (exact: 3*2^2 = 12)
print(derivative(math.exp, 1.0))           # 2.718281828517632  (exact: e = 2.718281828459045)
print(derivative(math.log, 4.0))           # 0.24999999999053554 (exact: 1/4)
```

### The chain rule, slowly

Suppose you have two steps: `y = g(x)`, then `z = f(y)`. Nudge `x` by a tiny amount. Two things
happen in sequence:

1. `y` changes by `g'(x)` times as much as `x` did.
2. `z` changes by `f'(y)` times as much as `y` did.

So `z` changes by `f'(y) × g'(x)` times as much as `x` did. **The effects multiply.**

```
dz/dx = dz/dy × dy/dx
```

That fraction-like notation is deliberately suggestive: it looks like the `dy` terms cancel, and while
that is not a proof, it is a reliable way to remember it.

**A concrete example.** Let `z = (3x + 1)²`.

Break it into steps: `y = 3x + 1`, then `z = y²`.

- `dy/dx = 3`
- `dz/dy = 2y = 2(3x + 1)`
- So `dz/dx = 2(3x + 1) × 3 = 6(3x + 1)`

At `x = 2`: `6 × 7 = 42`. Check it:

```python
print(derivative(lambda x: (3 * x + 1) ** 2, 2.0))     # 42.000000000896875
```

**Longer chains just multiply more terms.** For `x → a → b → L`:

```
dL/dx = dL/db × db/a × da/dx
```

A neural network with 50 layers is a chain of 50 functions, and its gradient is a product of 50 local
derivatives. That is literally all backpropagation computes.

### Partial derivatives and the gradient

Most real functions have more than one input. `f(x, y) = x² + 3y` has two.

A **partial derivative** asks the same nudge question about *one* input while holding the others
fixed. It is written with a curly `∂` instead of `d`:

```
∂f/∂x = 2x        (treat y as a constant)
∂f/∂y = 3         (treat x as a constant)
```

Collect all the partials into a vector and you have the **gradient**, written `∇f` ("nabla f" or
"grad f"):

```
∇f = [∂f/∂x, ∂f/∂y] = [2x, 3]
```

```python
def numeric_gradient(f, x, h=1e-5):
    """x is a list. Returns the gradient as a list."""
    g = []
    for i in range(len(x)):
        xp = list(x); xp[i] += h
        xm = list(x); xm[i] -= h
        g.append((f(xp) - f(xm)) / (2 * h))
    return g

f = lambda v: v[0] ** 2 + 3 * v[1]
print(numeric_gradient(f, [2.0, 5.0]))      # [4.000000000026205, 2.9999999998864264]
```

`[4, 3]` as expected: `2x = 4` at `x = 2`, and `3` always.

**What does the gradient mean geometrically?** Imagine `f` as a landscape, with height at each `(x, y)`.
The gradient at a point is an arrow pointing **directly uphill, in the steepest direction**, and its
length is how steep that is.

That single fact is the whole of Module 5: to go *downhill* — to reduce a loss — step in the direction
`−∇f`. That is gradient descent.

### The functions you will actually differentiate

These five appear in every neural network. Derive them once and you have them forever.

**1. Mean squared error.** `L = (y − t)²` where `y` is the prediction and `t` the target.

```
dL/dy = 2(y − t)
```

Simple, and note the shape of it: the gradient is proportional to the error. Big error, big
correction.

**2. Sigmoid.** `σ(x) = 1 / (1 + e^(−x))`. It squashes any number into `(0, 1)`.

```
σ'(x) = σ(x) · (1 − σ(x))
```

That is a remarkable result: the derivative is expressible in terms of the output alone, so you can
compute it without re-deriving anything. Note also its maximum: at `σ(x) = 0.5` the derivative is
`0.25`. **The sigmoid's slope never exceeds 0.25.** Chain 10 of them and the product of gradients is
at most `0.25¹⁰ ≈ 1e-6`. That is the vanishing-gradient problem, visible in one line of arithmetic.

**3. ReLU.** `relu(x) = max(0, x)`.

```
relu'(x) = 1 if x > 0, else 0
```

The derivative is 1 or 0 — no shrinking. Chain a hundred of them and the gradient is still 1 wherever
the units are active. **That is why ReLU replaced sigmoid in deep networks**, and it is a one-line
argument.

(At exactly `x = 0` the derivative does not exist. Every framework picks 0 by convention and it
makes no practical difference, because hitting exactly 0.0 has probability zero in floating point.)

**4. Softmax.** Turns a vector of scores into probabilities:
`softmax(x)ᵢ = e^(xᵢ) / Σⱼ e^(xⱼ)`.

**5. Cross-entropy after softmax.** This is the pair you will actually use, and together they are
beautiful:

```
L = −log(softmax(x)_target)

dL/dxᵢ = softmax(x)ᵢ − 1[i == target]
```

In words: **the gradient is the predicted probability minus the true probability.** If the model
says 0.7 for the right class, the gradient on that logit is `0.7 − 1 = −0.3`. If it says 0.2 for a
wrong class, the gradient is `0.2 − 0 = 0.2`. Nothing could be more interpretable.

This simplicity is exactly why frameworks provide a fused `softmax_cross_entropy` rather than making
you compose them: the combined gradient is one subtraction, while composing them separately computes
a Jacobian and then cancels most of it.

### Deriving the five gradients properly

**Sigmoid.** Write `σ = (1 + e^(−x))⁻¹`. Chain rule with `u = 1 + e^(−x)`:

```
dσ/dx = −u⁻² · du/dx = −(1 + e^(−x))⁻² · (−e^(−x)) = e^(−x) / (1 + e^(−x))²
```

Now the trick: `e^(−x)/(1+e^(−x))² = [1/(1+e^(−x))] × [e^(−x)/(1+e^(−x))] = σ × (1 − σ)`, because
`1 − σ = e^(−x)/(1 + e^(−x))`.

**Softmax Jacobian.** With `p = softmax(x)`:

```
∂pᵢ/∂xⱼ = pᵢ(δᵢⱼ − pⱼ)          where δᵢⱼ is 1 if i == j else 0
```

That is a full `n × n` Jacobian matrix, and materialising it is wasteful.

**Softmax + cross-entropy, fused.** With `L = −log p_t` for target class `t`:

```
∂L/∂xᵢ = Σⱼ (∂L/∂pⱼ)(∂pⱼ/∂xᵢ) = pᵢ − δᵢₜ
```

The Jacobian's off-diagonal terms cancel completely. This is why every framework has a fused op —
`torch.nn.CrossEntropyLoss` takes **logits, not probabilities**, precisely so it can use this
simplification and avoid the numerical hazard of computing `log(softmax(x))` in two steps.

**The numerical hazard is worth naming.** `softmax` then `log` computes `exp` of possibly large
numbers and then takes a log of a possibly tiny one. The fused **log-sum-exp** form is stable:

```
log softmax(x)ᵢ = xᵢ − max(x) − log Σⱼ exp(xⱼ − max(x))
```

Subtracting the max before exponentiating bounds everything. This is the same trick as Module 2's
`softmax_rows`, and it is the reason passing probabilities to `CrossEntropyLoss` (a common bug)
produces silently worse training rather than an error.

### `gradcheck`: the technique that finds the bug

Any analytic gradient can be checked against a numerical one. This is not optional discipline for
custom layers and custom losses — it is the difference between a five-minute fix and a week of
tuning learning rates.

```python
def numeric_grad(f, xs, i, h=1e-6):
    orig = xs[i]
    xs = list(xs)
    xs[i] = orig + h; fp = f(xs)
    xs[i] = orig - h; fm = f(xs)
    return (fp - fm) / (2 * h)

def relative_error(a, b):
    return abs(a - b) / max(1e-12, abs(a) + abs(b))
```

**Use relative error, not absolute.** A gradient of magnitude 10,000 with absolute error 0.01 is fine;
a gradient of 1e-8 with absolute error 0.01 is catastrophically wrong. The conventional thresholds:

| Relative error | Verdict |
|---|---|
| `> 1e-2` | Definitely wrong |
| `1e-2` to `1e-4` | Probably wrong, unless there is a kink (ReLU at 0, abs, max) |
| `1e-4` to `1e-7` | Fine for a deep network with kinks |
| `< 1e-7` | Correct |

Measured on the reverse-mode engine below, worst relative error over 200 random inputs per function:

| Function | Worst relative error |
|---|---|
| MSE `(y − t)²` | **1.831e-10** |
| sigmoid | 3.731e-10 |
| `tanh(w·x + b)` | 1.940e-07 |
| `relu(w·x + b)²` | 4.815e-10 |
| binary cross-entropy | 3.608e-10 |
| 5-deep `tanh` chain | 2.938e-09 |
| softmax + cross-entropy over 3 classes | 3.970e-09 |

Every one is comfortably under 1e-6. If yours are not, your gradient is wrong.

**Three practical rules for gradchecking real models.** Use `float64` — in `float32` the numerical
gradient's noise floor is around 1e-3 and the check is meaningless. Check a few random parameters, not
all of them, because each one costs two forward passes. And avoid kinks: perturbing a ReLU input
across zero makes the numerical and analytic gradients legitimately disagree, so either use `tanh`
for the check or pick points away from the kink.

### Forward mode versus reverse mode

Both compute exact derivatives (not approximations) by applying the chain rule mechanically. They
differ in *the order of multiplication*, and that difference is everything.

Consider `f: ℝⁿ → ℝᵐ` — `n` inputs, `m` outputs. The full derivative is the `m × n` **Jacobian**.

**Forward mode** carries derivatives alongside values, forwards. One pass gives you the derivative of
*all outputs* with respect to *one input*. To get the whole Jacobian: **`n` passes.**

**Reverse mode** does a forward pass storing intermediate values, then a backward pass propagating
derivatives from the output. One backward pass gives you the derivative of *one output* with respect
to *all inputs*. Whole Jacobian: **`m` passes.**

| | Cost | Best when |
|---|---|---|
| Forward mode | `n` × forward | `n ≪ m` (few inputs, many outputs) |
| Reverse mode | `m` × forward + memory for the graph | `m ≪ n` (many inputs, few outputs) |

**Neural network training has `m = 1`** — the loss is a single scalar — **and `n` = the number of
parameters**, which for a 7 B model is 7,000,000,000. Reverse mode costs one backward pass. Forward
mode would cost seven billion.

That single asymmetry is why reverse-mode autodiff exists, why it is called backpropagation in this
context, and why the field cares about it at all. It is not a subtle optimisation; it is a factor of
`n`.

**The price of reverse mode is memory.** You must store every intermediate activation from the forward
pass, because the backward pass needs them. For a Transformer this is the dominant training memory
cost after the optimizer state, and it is what **gradient checkpointing** trades away: recompute
activations during the backward pass instead of storing them, typically saving ~50–70% of activation
memory for roughly 30% more compute.

**And forward mode is not useless.** When you genuinely have few inputs and many outputs — sensitivity
of a whole simulation to two physical parameters — forward mode wins. `torch.func.jvp` implements it,
and `jacfwd` versus `jacrev` in JAX is exactly this choice, exposed.

### Trade-offs

| Decision | Choose this when… | Choose the other when… | The number |
|---|---|---|---|
| **Reverse mode** | Training anything — one scalar loss, many parameters | Few inputs, many outputs | 1 backward pass vs `n` forward passes; `n = 7e9` for a 7B model |
| **Analytic gradients** | Production; anything in a hot loop | One-off analysis; verifying | Numerical gradients cost `2n` forward passes and have ~1e-8 accuracy at best |
| **Fused softmax+CE** | Always, for classification | Never | The gradient is one subtraction instead of an `n × n` Jacobian, and it is numerically stable |
| **Gradient checkpointing** | Activation memory is the binding constraint | Compute is the constraint | Roughly 50–70% less activation memory for about 30% more compute |
| **`float64` for gradcheck** | Always, when gradchecking | Never | In fp32 the numerical gradient's noise floor is ~1e-3, so the check cannot distinguish right from wrong |

### Reference implementation: a 100-line autodiff engine

This is the direct precursor to Week 21. It is a scalar version of what PyTorch does with tensors.

```python
# micrograd_style.py — reverse-mode automatic differentiation in ~90 lines.
import math

class Value:
    """A scalar that remembers how it was computed."""
    __slots__ = ("data", "grad", "_backward", "_prev", "_op")

    def __init__(self, data, _children=(), _op=""):
        self.data = float(data)
        self.grad = 0.0                 # dL/d(self), filled in by backward()
        self._backward = lambda: None   # how to push gradient to my children
        self._prev = set(_children)
        self._op = _op

    def __add__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data + other.data, (self, other), "+")
        def _b():
            self.grad  += out.grad      # d(a+b)/da = 1
            other.grad += out.grad
        out._backward = _b
        return out

    def __mul__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data * other.data, (self, other), "*")
        def _b():
            self.grad  += other.data * out.grad     # d(ab)/da = b
            other.grad += self.data  * out.grad
        out._backward = _b
        return out

    def __pow__(self, k):
        out = Value(self.data ** k, (self,), f"**{k}")
        def _b(): self.grad += k * self.data ** (k - 1) * out.grad
        out._backward = _b
        return out

    def relu(self):
        out = Value(self.data if self.data > 0 else 0.0, (self,), "relu")
        def _b(): self.grad += (out.data > 0) * out.grad
        out._backward = _b
        return out

    def exp(self):
        out = Value(math.exp(self.data), (self,), "exp")
        def _b(): self.grad += out.data * out.grad          # d(e^x)/dx = e^x
        out._backward = _b
        return out

    def log(self):
        out = Value(math.log(self.data), (self,), "log")
        def _b(): self.grad += (1.0 / self.data) * out.grad
        out._backward = _b
        return out

    def tanh(self):
        t = math.tanh(self.data)
        out = Value(t, (self,), "tanh")
        def _b(): self.grad += (1 - t * t) * out.grad
        out._backward = _b
        return out

    def __neg__(self):        return self * -1
    def __sub__(self, o):     return self + (-o if isinstance(o, Value) else Value(-o))
    def __rsub__(self, o):    return Value(o) + (-self)
    def __truediv__(self, o): return self * (o ** -1 if isinstance(o, Value) else Value(o) ** -1)
    def __rtruediv__(self, o): return Value(o) * (self ** -1)
    __radd__ = __add__
    __rmul__ = __mul__

    def backward(self):
        """Topologically sort the graph, then apply the chain rule in reverse."""
        topo, seen = [], set()
        def build(v):
            if v in seen: return
            seen.add(v)
            for c in v._prev: build(c)
            topo.append(v)
        build(self)
        self.grad = 1.0                 # dL/dL = 1
        for v in reversed(topo):
            v._backward()
```

Note how small those gradients are. The input to `tanh` is `2*3 + e^2 ≈ 13.4`, where `tanh` has
completely saturated at 1.0, so its local derivative `1 − tanh²` is about `9.4e-12`. Every gradient
upstream is multiplied by that. **A saturated activation kills the gradient for everything behind
it** — this is the vanishing-gradient problem, appearing in a three-line example.

**The three ideas that make it work**, and they are the same three in PyTorch:

1. **Every operation records its children and a closure that knows its local derivative.** The graph
   is built as a side effect of the forward computation — this is "define-by-run", and it is why you
   can use Python control flow inside a model.
2. **Gradients accumulate with `+=`, never `=`.** If a value is used twice, both paths contribute.
   Getting this wrong gives you the gradient of only the last use, and the bug is subtle. (It is also
   why you must call `optimizer.zero_grad()` in PyTorch — accumulation is the default.)
3. **Topological sort, then reverse.** A node's gradient is only complete once every node that uses it
   has been processed. The topological order guarantees that.

Verify it:

```python
x = Value(2.0); y = Value(3.0)
z = (x * y + x.exp()).tanh()
z.backward()
print(z.data)              # 0.9999999999953071
print(x.grad, y.grad)      # 9.75e-11  1.88e-11

# and gradcheck it
def f(v): return (v[0] * v[1] + v[0].exp()).tanh()
# ... compare against numeric_grad as in the table above
```

### What breaks in the real world

A team implemented a custom ranking loss — a margin-based objective with a learned temperature —
directly in PyTorch. Training ran. The loss decreased. Validation NDCG did not move for three weeks.

They tried: three learning rates, two optimizers, warmup, gradient clipping, a bigger model, more
data. Nothing.

The bug was a missing factor. The analytic gradient of their temperature parameter was off by a factor
of `1/T` because a term had been dropped when the expression was simplified by hand. The gradient
pointed in approximately the right direction — enough for the loss to decrease — but scaled wrongly
relative to every other parameter, so the temperature effectively never moved.

`torch.autograd.gradcheck` on the loss with `float64` inputs found it in under a minute. The relative
error was 0.4.

**The rule that came out of it, and it is worth adopting verbatim: any custom autograd function, any
hand-derived gradient, and any custom loss gets a `gradcheck` test in CI before it gets a training
run.** It costs ten lines and it prevents the failure mode that is most expensive to diagnose,
because a wrong gradient produces a *plausible* training curve rather than an obvious error.

### Design checkpoint

<Accordion title="You need the gradient of a 50-parameter simulation with respect to its 3 physical inputs, and the simulation involves a loop that runs a data-dependent number of times. Forward or reverse mode?">

**Count the inputs and outputs first — that is the whole decision.**

Here `n = 3` inputs and `m = 50` outputs, so the Jacobian is 50 × 3. Forward mode costs 3 passes;
reverse mode costs 50. **Forward mode wins by roughly 17×.** This is the opposite of the neural-network
case and it is the situation people get wrong by habit, because "autodiff" has become synonymous with
backprop.

**The data-dependent loop reinforces the choice.** Reverse mode must store the entire tape, and a loop
whose trip count depends on the data means the memory is unbounded and unpredictable. Forward mode
carries a fixed-size dual number alongside each value and uses `O(1)` extra memory regardless of how
long the loop runs.

**In practice:**

```python
import torch
# forward mode: 3 jvp calls, one per input direction
jac = torch.func.jacfwd(simulate)(params)     # picks forward mode
# reverse mode would be:
jac = torch.func.jacrev(simulate)(params)     # 50 backward passes
```

JAX exposes the same choice as `jax.jacfwd` and `jax.jacrev`, and the documentation states the rule
directly: `jacfwd` when the output dimension exceeds the input dimension, `jacrev` otherwise.

**The composition worth knowing:** for a Hessian (second derivatives) of a scalar function of many
inputs, the right answer is `jacfwd(jacrev(f))` — reverse mode for the inner gradient (one output,
many inputs) and forward mode for the outer Jacobian of that gradient. Getting this the wrong way
round costs a factor of `n`, and it is the standard trick behind efficient Hessian-vector products.

### The finite-difference error curve, measured

A numerical derivative has two error sources pulling in opposite directions:

- **Truncation error** — the difference quotient is not the limit. For the centred difference this is
  `O(h²)`; it *shrinks* as `h` shrinks.
- **Roundoff error** — `f(x+h)` and `f(x−h)` are nearly equal, so subtracting them cancels significant
  digits. This is `O(ε/h)` where `ε ≈ 2.2e-16` is machine epsilon; it *grows* as `h` shrinks.

Total error is roughly `C·h² + ε/h`, minimised at `h ≈ (ε)^(1/3) ≈ 6e-6`, with a minimum error around
`ε^(2/3) ≈ 4e-11`.

Measured, sweeping `h` on `tanh(w·x + b)`:

| h | worst relative error |
|---|---|
| 1e-1 | 1.284e-02 |
| 1e-2 | 1.291e-04 |
| **1e-4** | **1.325e-08** |
| 1e-6 | 1.940e-07 |
| 1e-8 | 1.219e-05 |
| 1e-10 | 9.314e-04 |
| 1e-12 | 1.143e-01 |

A clean U-curve with the optimum near `h = 1e-4`, and the error at `h = 1e-12` is **eight orders of
magnitude worse** than at the optimum. Choosing `h` too small is the more common mistake, and it looks
like a broken gradient.

Two consequences you can act on. **`h = 1e-5` is a good default in float64** and is what most
`gradcheck` implementations use. And **numerical gradients are useless in float32**, where `ε ≈ 1.2e-7`
puts the best achievable error around `ε^(2/3) ≈ 2.4e-5` — you cannot distinguish a correct gradient
from one that is 0.01% wrong.

**Complex-step differentiation** escapes the trade-off entirely for real-analytic functions:

```
f'(x) ≈ Im( f(x + ih) ) / h
```

Because there is no subtraction of nearly equal numbers, there is no cancellation, and you can take
`h = 1e-200` and get machine-precision accuracy. It requires the function to accept complex inputs,
which rules out most real code, but where it applies it is exact and it is a genuinely useful trick
for validating an analytic derivative.

### What autodiff costs, precisely

The **cheap gradient principle** (Baur–Strassen, 1983): reverse-mode differentiation of a function
computes the gradient in at most a small constant multiple of the cost of evaluating the function
itself. The classical bound is a factor of about 5; in practice, for neural networks, the backward
pass costs roughly **2× the forward pass**, giving `forward + backward ≈ 3 × forward`.

That is where the familiar training-cost estimate comes from:

```
training FLOPs ≈ 6 × N × D          for N parameters and D tokens
```

`2N` per token for the forward pass (one multiply and one add per parameter), times 3 for
forward-plus-backward. You now know both factors.

**Memory is the real cost.** Reverse mode must retain every intermediate value the backward pass needs.
For a Transformer:

| Component | Memory |
|---|---|
| Parameters (bf16) | `2N` bytes |
| Gradients (bf16) | `2N` bytes |
| Adam state (fp32 `m` and `v`) | `8N` bytes |
| fp32 master weights | `4N` bytes |
| **Activations** | `O(L · B · S · D)` — depends on batch and sequence, often the largest term |

Module 5 completes this table with the measured GB figures. The activation term is the one autodiff is
responsible for, and it is why **gradient checkpointing** exists: store activations only at layer
boundaries and recompute the rest during the backward pass. With `sqrt(L)` checkpoints the memory goes
from `O(L)` to `O(sqrt(L))` for one extra forward pass of compute — Chen et al. (2016) report
training substantially deeper networks on fixed memory this way, at roughly 30% extra compute.

### Where the chain rule goes wrong at depth

The gradient at layer `k` of an `L`-layer network is a product of `L − k` local Jacobians. Products of
many terms behave badly:

- **Vanishing.** If each factor has magnitude around 0.25 (sigmoid's maximum), the product at depth 10
  is at most `0.25¹⁰ ≈ 9.5e-7`, and at depth 20 it is `9e-13` — below fp32's resolution near 1. Early
  layers receive no signal.
- **Exploding.** If each factor has magnitude 1.5, depth 20 gives `1.5²⁰ ≈ 3,325`, and the update
  blows the weights apart in one step.

The fixes, and what each actually does to the product:

| Fix | Mechanism |
|---|---|
| **ReLU** | Local derivative is exactly 1 where active, so it contributes no shrinkage |
| **Residual connections** | `y = x + f(x)` gives `dy/dx = 1 + f'(x)` — there is always a path with derivative 1, so the product cannot vanish along it |
| **Normalisation (batch/layer)** | Keeps activations in the regime where derivatives are `O(1)` |
| **Careful initialisation (He, Xavier)** | Sets weight variance so the *forward* activations neither grow nor shrink, which keeps the backward Jacobians near unit scale |
| **Gradient clipping** | Bounds the exploding case directly, by global norm |

Residual connections are the one to internalise: `1 + f'(x)` is why networks went from about 20 layers
to over 1,000, and it is a one-line consequence of the chain rule.

### Numerical hazards in the standard operations

| Operation | Hazard | Standard fix |
|---|---|---|
| `softmax` | `exp` of large logits overflows to `inf` | Subtract the row max first |
| `log(softmax(x))` | `log` of an underflowed 0 gives `−inf` | Fused `log_softmax` via log-sum-exp |
| `log(p)` in cross-entropy | `p = 0` gives `−inf`, then `nan` gradients | Pass logits to a fused loss; never compute probabilities first |
| `sqrt(x)` at `x = 0` | Derivative is `1/(2√x)` = infinity | Add epsilon inside the sqrt, not outside: `sqrt(x + eps)` |
| `x / y` with tiny `y` | Gradient is `−x/y²`, which explodes | Clamp the denominator, or reformulate |
| `pow(x, n)` with `x < 0` and fractional `n` | `nan` in the forward pass | Guard the domain |
| Division by a norm | `nan` when the norm is 0 | `x / (‖x‖ + eps)` |

Note the `sqrt` detail: writing `sqrt(x) + eps` does nothing to fix the infinite gradient at zero,
while `sqrt(x + eps)` fixes it. This is exactly why layer normalisation's epsilon is *inside* the
square root, and it is a distinction that produces real `nan` bugs.

### Production failure modes

| Failure | Signature | Detection |
|---|---|---|
| **Wrong hand-derived gradient** | Loss decreases, target metric never moves | `torch.autograd.gradcheck` in float64, in CI, for every custom function |
| **Gradients not zeroed** | Loss behaves erratically; effective LR grows over time | PyTorch accumulates by default. `optimizer.zero_grad()` every step |
| **Probabilities passed to `CrossEntropyLoss`** | Trains, but noticeably worse; no error | The API takes logits. Check what your model's last layer returns |
| **`nan` after N steps** | Loss becomes `nan` and never recovers | Usually `log(0)`, `0/0`, or `sqrt(0)`'s gradient. Add `torch.autograd.set_detect_anomaly(True)` to localise it |
| **Vanishing gradients** | Early-layer gradient norms are orders of magnitude below late-layer ones | Log per-layer gradient norms every N steps. Residuals, normalisation and ReLU-family activations |
| **Exploding gradients** | Loss spikes; weights become `inf` | Clip by global norm; check initialisation scale |
| **In-place op breaks autograd** | `RuntimeError: a variable needed for gradient computation has been modified` | An in-place operation overwrote a value the backward pass needed. Avoid `x += y` on tensors that require grad |
| **`detach()` in the wrong place** | A parameter never updates and there is no error | Print `param.grad` after `backward()`. `None` means it is not in the graph |

4. Now break things on purpose and observe: (a) change `+=` to `=` in a `_backward` and find an input

mapping that curve for your own implementation is the point.

## Common mistakes

| Symptom | Cause | Fix |
|---|---|---|
| Loss falls, metric never improves | Wrong hand-derived gradient — right direction, wrong scale | `gradcheck` in float64; relative error above 1e-2 means wrong |
| Numerical gradient disagrees badly | `h` too small (roundoff) or too large (truncation), or float32 | Use float64 and `h ≈ 1e-5`; measured optimum at 1e-4 |
| Gradients grow across steps for no reason | Not zeroed — PyTorch accumulates by design | `optimizer.zero_grad()` every step |
| Only the last use of a value gets gradient | Used `=` instead of `+=` in a backward function | Accumulate always: a value used twice gets contributions from both paths |
| `nan` appears after some steps | `log(0)`, `0/0`, or `sqrt(0)`'s infinite derivative | Fused stable ops; epsilon *inside* the sqrt, not outside |
| Early layers do not learn | Vanishing gradients through saturating activations | ReLU family, residual connections, normalisation, better init |
| `RuntimeError: variable needed for gradient has been modified` | In-place operation on a tensor the backward pass needs | Avoid in-place ops on tensors requiring grad |
| A parameter never updates, no error | It is detached from the graph | Print `param.grad` after `backward()`; `None` means it is not connected |
