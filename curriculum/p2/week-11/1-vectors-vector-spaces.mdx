## The mental model

A vector is a list of numbers. That is all it is.

What makes it powerful is that a list of numbers can be read **two ways at once**:

- as a **point** in space — `[3, 4]` is the location three steps right and four steps up;
- as an **arrow** from the origin to that point — a direction with a length.

Everything in this module comes from switching between those two readings. "How similar are these two
things?" becomes "how close are these two points?" or "how aligned are these two arrows?" — and those
are different questions with different answers, which is the entire cosine-versus-Euclidean debate.

### Start with two numbers

Draw a pair of axes on paper. Mark the point 3 across and 4 up. Write `[3, 4]` next to it.

That is a **vector**. Two numbers, in a fixed order. The order matters: `[4, 3]` is a different point.

Now draw an arrow from the origin (where the axes cross, the point `[0, 0]`) to your dot. Same
object, second reading: an arrow pointing up and to the right.

**Why two readings?** Because different questions want different pictures. "Where is this document
in meaning-space?" wants the point. "Do these two documents point the same way?" wants the arrow.

### How long is the arrow?

Drop a vertical line from your point down to the horizontal axis. You now have a right-angled
triangle with sides 3 and 4. Pythagoras gives the hypotenuse:

```
length = sqrt(3² + 4²) = sqrt(9 + 16) = sqrt(25) = 5
```

That length has a name: the **norm**, written with vertical bars, `|v|` or `‖v‖`. In `n` dimensions
you do the same thing — square every component, add them up, take the square root:

```
‖v‖ = sqrt(v₁² + v₂² + ... + vₙ²)
```

This particular one is the **L2 norm** or **Euclidean norm**, because there are others (we meet them
in Layer 2). When someone says "the norm" with no qualifier, they mean this one.

```python
import math
v = [3, 4]
norm = math.sqrt(sum(x * x for x in v))
print(norm)          # 5.0
```

### Adding vectors, and scaling them

Two operations, both of which you can see:

**Addition** — add matching components. `[3, 4] + [1, 2] = [4, 6]`. Geometrically: put the tail of the
second arrow at the head of the first, and the result is the arrow from the origin to where you end
up. Draw it. It is the "walk 3 right and 4 up, then 1 right and 2 up" picture.

**Scaling** — multiply every component by a single number (a **scalar**). `2 × [3, 4] = [6, 8]`.
Geometrically: same direction, twice as long. And `-1 × [3, 4] = [-3, -4]` is the same length pointing
exactly backwards.

That is the whole definition of a **vector space**: a set of things you can add together and scale,
where the results stay in the set. Lists of numbers qualify. So, it turns out, do many other things —
but for this course, vector space means "lists of numbers of a fixed length".

### The dot product: the most important operation in this course

Take two vectors of the same length. Multiply them component by component, then add up the results.

```
u = [3, 4]        v = [1, 2]
u · v = (3 × 1) + (4 × 2) = 3 + 8 = 11
```

```python
def dot(u, v):
    return sum(a * b for a, b in zip(u, v))

print(dot([3, 4], [1, 2]))     # 11
```

One line. Now: **what does 11 mean?**

Here is the fact that makes the whole thing work:

```
u · v  =  ‖u‖ × ‖v‖ × cos(θ)
```

where θ (theta) is the angle between the two arrows. So the dot product is *the product of the two
lengths, scaled by how aligned they are.*

`cos(θ)` — cosine — is a number between −1 and 1 that measures alignment:

| The arrows are… | angle θ | cos(θ) |
|---|---|---|
| pointing the same way | 0° | **1** |
| at right angles ("orthogonal") | 90° | **0** |
| pointing opposite ways | 180° | **−1** |

You do not need to remember trigonometry. You need to remember those three rows: **1 means same
direction, 0 means unrelated, −1 means opposite.**

Check it yourself with a case you can see:

```python
print(dot([1, 0], [1, 0]))    # 1   -- same direction
print(dot([1, 0], [0, 1]))    # 0   -- right angles
print(dot([1, 0], [-1, 0]))   # -1  -- opposite
```

Draw those three pairs on paper. The middle one is the important one: **two arrows at right angles
have a dot product of exactly zero.** That is what "unrelated" looks like in arithmetic.

### Cosine similarity, which is the thing you will actually use

The dot product mixes two things: how aligned the arrows are, *and* how long they are. Usually you
only want the alignment. So divide the lengths out:

```
cosine_similarity(u, v)  =  (u · v) / (‖u‖ × ‖v‖)  =  cos(θ)
```

```python
import math

def norm(v):    return math.sqrt(sum(x * x for x in v))
def cosine(u, v):
    return dot(u, v) / (norm(u) * norm(v))

print(cosine([3, 4], [6, 8]))      # 1.0    -- same direction, different length
print(cosine([1, 0], [0, 1]))      # 0.0    -- right angles
print(cosine([1, 1], [1, 0]))      # 0.7071 -- 45 degrees
```

**`cosine([3, 4], [6, 8]) = 1.0`** is the line to stare at. Those are different vectors — one is twice
as long as the other — and cosine says they are *identical*. It has thrown the length away entirely
and kept only the direction.

### Why that matters, concretely

Suppose you turn documents into vectors (this is what an **embedding model** does, and you will use
one in Week 27; for now, take it as given that some function turns text into a list of, say, 768
numbers, arranged so that similar meanings give similar directions).

Now consider three documents:

- **A:** a 200-word blog post about cats
- **B:** a 5,000-word encyclopaedia article about cats
- **C:** a 200-word blog post about tax law

If length affects the embedding at all — and with many models it does — then B's vector is *longer*
than A's, simply because there is more text. Measure straight-line (Euclidean) distance and B looks
far from A, possibly further than C is. Measure the angle and A and B point almost the same way, while
C points somewhere else entirely.

**Direction is what the document is about. Length is how much of it there is.** In search you almost
always want the first, which is why cosine similarity is the default in essentially every vector
database you will meet.

### The trick everyone uses: normalise first

If you divide a vector by its own length, you get a vector of length exactly 1 pointing the same way.
That is called a **unit vector**, and doing it is called **normalising**.

```python
def normalise(v):
    n = norm(v)
    return [x / n for x in v]

print(normalise([3, 4]))          # [0.6, 0.8]
print(norm(normalise([3, 4])))    # 1.0
```

And now the useful part: **if both vectors are already normalised, the dot product IS the cosine
similarity**, because you are dividing by 1 × 1.

```python
a, b = normalise([3, 4]), normalise([6, 8])
print(dot(a, b))     # 0.9999999999999999  (1.0, up to floating-point rounding)
```

This is not a cute observation. It is why production retrieval systems normalise every embedding
once, at write time, and then use plain dot product at query time — a dot product is a single fused
multiply-add loop that hardware is extremely good at, while cosine similarity needs two square roots
and a division per comparison. Over a million vectors per query, that difference is the whole
latency budget. **Week 27 will assume you know this.**

### Projection: "how much of u points along v?"

One more picture. Shine a light straight down onto the arrow `v`. The shadow that `u` casts on `v` is
the **projection** of `u` onto `v`.

Its length is `(u · v) / ‖v‖`, and the projection vector itself is:

```
proj_v(u) = ((u · v) / (v · v)) × v
```

```python
def project(u, v):
    scale = dot(u, v) / dot(v, v)
    return [scale * x for x in v]

print(project([3, 4], [1, 0]))     # [3.0, 0.0]  -- the shadow on the x-axis is just the x-component
```

That result should feel obvious once you see it: projecting onto the x-axis keeps the x-component and
discards the rest. Projection is "keep only the part that points this way". It reappears in Module 3
(PCA is projection onto the most informative directions) and in Week 21 (a gradient update is a step
along a direction).

### Span, basis, independence — in pictures

Three words that sound abstract and are not.

**Span** — everything you can reach by scaling and adding a given set of vectors. One arrow in 2-D
spans a line (scale it up, down, backwards — you stay on the line). Two arrows pointing in different
directions span the whole plane.

**Linearly independent** — none of the vectors is reachable from the others. `[1,0]` and `[0,1]` are
independent. `[1,0]` and `[2,0]` are *not*, because the second is just the first, doubled — it adds no
new direction.

**Basis** — a set of independent vectors that spans the whole space. In 2-D you need exactly 2; in
768-D you need exactly 768. `[1,0]` and `[0,1]` are the standard basis for 2-D, and the components of
a vector are exactly "how much of each basis direction".

Why this matters later: an embedding with 768 numbers lives in a 768-dimensional space, but the
vectors an actual model produces usually cluster near a much lower-dimensional surface inside it —
they do not use all 768 independent directions. That observation is the whole idea behind PCA
(Module 3) and behind LoRA (Week 26).

### The norms you will actually meet

The L2 norm is one of a family. For a vector `v`:

```
L1:   ‖v‖₁ = Σ |vᵢ|                 "Manhattan" -- walk along the grid
L2:   ‖v‖₂ = sqrt(Σ vᵢ²)            "Euclidean" -- straight line
L∞:   ‖v‖∞ = max |vᵢ|               "Chebyshev" -- the largest single component
Lp:   ‖v‖ₚ = (Σ |vᵢ|^p)^(1/p)       the general family
```

```python
import numpy as np
v = np.array([3.0, -4.0, 0.0])
np.linalg.norm(v, 1)        # 7.0
np.linalg.norm(v)           # 5.0     (ord=2 is the default)
np.linalg.norm(v, np.inf)   # 4.0
```

Where each one shows up, concretely:

- **L2** — the default everywhere: embedding normalisation, weight decay (which is L2 regularisation),
  gradient clipping by global norm, and MSE loss (which is squared L2 error).
- **L1** — Lasso regression, and any time you want **sparsity**. The reason L1 produces exact zeros
  while L2 does not is geometric: the L1 unit ball is a diamond with corners *on the axes*, so the
  first point of contact with a loss contour tends to be a corner, and a corner has zero components.
  The L2 ball is a sphere with no corners. Draw both in 2-D and you will never forget it.
- **L∞** — adversarial robustness (the standard threat model is "change every pixel by at most ε"),
  and per-element gradient clipping.

### Vectorising: never write the loop

```python
import numpy as np

def cosine_numpy(A, b):
    """Cosine similarity of every row of A (n x d) against a single vector b (d,)."""
    A_n = A / np.linalg.norm(A, axis=1, keepdims=True)
    b_n = b / np.linalg.norm(b)
    return A_n @ b_n                                     # (n,)

def cosine_prenormalised(A_unit, b_unit):
    """If you normalised at write time, this is the whole query."""
    return A_unit @ b_unit
```

`keepdims=True` is the detail that trips people: `np.linalg.norm(A, axis=1)` returns shape `(n,)`,
and dividing `(n, d)` by `(n,)` fails or broadcasts wrongly. With `keepdims=True` you get `(n, 1)`,
which broadcasts correctly across columns. **Shape bugs are the number-one source of silent
wrongness in numerical Python**, and Module 2 makes shape discipline a formal practice.

### Cosine vs Euclidean vs dot: the actual decision

These three are related but not interchangeable, and the relationship is worth memorising:

```
For unit vectors:   ‖u − v‖² = 2 − 2(u · v)
```

So **for normalised vectors, ranking by Euclidean distance and ranking by cosine similarity give
identical orderings.** If you have normalised, the choice does not matter for ranking (it matters for
thresholds and for scores you display).

If you have *not* normalised, they differ, and so does raw dot product:

| Metric | Sensitive to magnitude? | Use when |
|---|---|---|
| **Dot product** | Yes — a longer vector scores higher against everything | Your model was trained with dot-product objectives, or magnitude encodes something you want (e.g. confidence, term frequency) |
| **Cosine** | No | You want "about the same thing" regardless of length. The default for text retrieval |
| **Euclidean (L2)** | Yes | Coordinates in a real geometric space; clustering where scale is meaningful |

The trap: **some embedding models are trained with a dot-product objective and some with cosine.**
OpenAI's `text-embedding-3-*` return normalised vectors, so all three agree. Many open models
(including several sentence-transformers checkpoints) do not, and using dot product on unnormalised
output silently biases retrieval towards longer documents. Check `model.encode(..., normalize_embeddings=True)`
or normalise yourself, and write down which you did.

### Measured: the shape of high-dimensional space

This is the experiment that changes how you think about embeddings. Generate random unit vectors in
`d` dimensions and measure two things: the cosine between random pairs, and the spread of distances
from a query to a set of points.

```python
# concentration.py — run it. numpy 2.5.2, Python 3.13.
import numpy as np
rng = np.random.default_rng(0)
for d in (2, 3, 5, 10, 50, 100, 500, 1000, 4096):
    n = 2000
    X = rng.standard_normal((n, d))
    Xn = X / np.linalg.norm(X, axis=1, keepdims=True)
    idx = rng.integers(0, n, size=(20000, 2)); idx = idx[idx[:, 0] != idx[:, 1]]
    cos = np.einsum('ij,ij->i', Xn[idx[:, 0]], Xn[idx[:, 1]])
    dist = np.linalg.norm(Xn[1:] - Xn[0], axis=1)
    print(f"d={d:<5} mean|cos|={np.abs(cos).mean():.4f}  max|cos|={np.abs(cos).max():.4f}  "
          f"dist std/mean={dist.std()/dist.mean():.4f}  (max-min)/min={(dist.max()-dist.min())/dist.min():.4f}")
```

Measured output:

| d | mean \|cos\| | max \|cos\| | dist spread (std/mean) | (max−min)/min |
|---|---|---|---|---|
| 2 | 0.6333 | 1.0000 | 0.4898 | 2837.7 |
| 3 | 0.5032 | 1.0000 | 0.3451 | 47.65 |
| 5 | 0.3749 | 0.9970 | 0.2456 | 6.961 |
| 10 | 0.2580 | 0.9027 | 0.1665 | 2.087 |
| 50 | 0.1129 | 0.5761 | 0.0716 | 0.6585 |
| 100 | 0.0802 | 0.3970 | 0.0499 | 0.4071 |
| 500 | 0.0357 | 0.1869 | 0.0225 | 0.1841 |
| 1000 | 0.0251 | 0.1356 | 0.0158 | 0.1013 |
| 4096 | 0.0125 | 0.0611 | 0.0077 | 0.0599 |

Two effects, both dramatic:

**1. Random vectors become orthogonal.** At d = 2 the average absolute cosine between two random
directions is 0.63 — random vectors mostly point somewhat similarly. At d = 1000 it is **0.025**, and
the *maximum over 20,000 random pairs* is only 0.136. In a thousand dimensions, nothing is
accidentally similar to anything.

That is good news for embeddings: it means there is enormous room to place concepts so that unrelated
ones are near-orthogonal, and any similarity you measure is signal rather than coincidence.

**2. Distances concentrate.** At d = 2 the furthest of 2,000 random points is 2,838× further away than
the nearest. At d = 1000 it is **1.10× further** — a 10% difference between the nearest and the
furthest point in the entire set. The standard deviation of distances falls to **1.6% of the mean**.

That is bad news for search. "Find the nearest neighbour" is a question about the *smallest* distance,
and if all distances are within 10% of each other, small perturbations reorder the results and any
approximate method has almost no margin for error.

### Trade-offs

| Decision | Choose this when… | Choose the other when… | The number |
|---|---|---|---|
| **Normalise at write time + dot product** | You are doing similarity search at any scale | You need raw magnitudes for another purpose | Removes two `sqrt` and a division per comparison; at 1 M vectors/query that is the difference between one BLAS call and a Python-visible loop |
| **Cosine** | Text retrieval, where length means "how much text" | Coordinates where scale is real (geo, sensor readings) | On the worked example: cosine 1.0 vs 0.02 correctly; Euclidean ranked the wrong pair 2.8× closer |
| **L1 penalty** | You want feature selection / exact zeros | You want small-but-nonzero weights | L1's unit ball has corners on the axes; L2's does not |
| **Higher-dimensional embeddings** | You need more capacity to separate concepts | Storage, memory bandwidth or ANN recall matters | 4096-D at fp32 is 16 KB/vector; 1 M vectors is 16 GB. Distances also concentrate further: spread falls from 1.58% at d=1000 to 0.77% at d=4096 |

### Reference implementation

A small, tested similarity search you will extend in Week 27:

```python
# vecsearch.py — exact nearest-neighbour search, done correctly.
import numpy as np

class ExactIndex:
    """Brute-force cosine search. Correct by construction; the baseline every ANN index is measured against."""

    def __init__(self, dim: int):
        self.dim = dim
        self._vecs = np.empty((0, dim), dtype=np.float32)
        self._ids: list[str] = []

    def add(self, ids: list[str], vecs: np.ndarray) -> None:
        vecs = np.asarray(vecs, dtype=np.float32)
        if vecs.ndim != 2 or vecs.shape[1] != self.dim:
            raise ValueError(f"expected (n, {self.dim}), got {vecs.shape}")
        norms = np.linalg.norm(vecs, axis=1, keepdims=True)
        if np.any(norms == 0):
            raise ValueError("zero vector cannot be normalised")
        self._vecs = np.vstack([self._vecs, vecs / norms])    # normalise ONCE, at write time
        self._ids.extend(ids)

    def search(self, q: np.ndarray, k: int = 5) -> list[tuple[str, float]]:
        q = np.asarray(q, dtype=np.float32).ravel()
        q = q / np.linalg.norm(q)
        scores = self._vecs @ q                               # dot == cosine, because both are unit
        k = min(k, len(self._ids))
        top = np.argpartition(-scores, k - 1)[:k]              # O(n), not O(n log n)
        top = top[np.argsort(-scores[top])]
        return [(self._ids[i], float(scores[i])) for i in top]

if __name__ == "__main__":
    rng = np.random.default_rng(0)
    idx = ExactIndex(128)
    idx.add([f"doc{i}" for i in range(10_000)], rng.standard_normal((10_000, 128)))
    target = rng.standard_normal(128)
    idx.add(["needle"], (target * 3.0)[None, :])               # same direction, 3x the length
    hits = idx.search(target, k=3)
    assert hits[0][0] == "needle" and hits[0][1] > 0.999, hits
    print(hits)
```

The assertion is the point: a vector three times longer but pointing the same way scores 1.0, because
normalisation removed the length. That is the behaviour you want, and it is worth having a test that
would fail if someone "optimised" the normalisation away.

`np.argpartition` rather than `np.argsort` is a real optimisation: partial selection is O(n) against
O(n log n), and at n = 1,000,000 and k = 10 that is roughly a 20× reduction in the sorting work.

### What breaks in the real world

A support-search feature was rebuilt on embeddings and shipped with visibly worse results than the
keyword search it replaced. The complaint was consistent: searching for a specific error message
returned long "getting started" guides instead of the short troubleshooting page that contained the
exact string.

The embedding model was a sentence-transformers checkpoint that does not return normalised vectors,
and the retrieval code used raw dot product because a blog post said dot product was faster. Long
documents have larger-magnitude embeddings, so **every long document outscored every short one on
every query**, regardless of topic. The system had accidentally implemented "return the longest
document".

The fix was one line — `normalize_embeddings=True` on the encoder — and recall@5 on their evaluation
set went from 0.34 to 0.71. Two weeks of prompt-tuning and reranking experiments had preceded it.

The diagnosis is available to anyone who checks: `print(np.linalg.norm(embeddings, axis=1))`. If those
numbers are not all 1.0, and you are using dot product, you have this bug.

### Design checkpoint

<Accordion title="You must serve nearest-neighbour search over 50 million 1024-dimensional embeddings with p99 under 50 ms. What is the arithmetic, and what does it force?">

**Storage first.** 50 M × 1024 × 4 bytes (fp32) = **204.8 GB**. That does not fit in the RAM of a
normal machine, so the first decision is forced before any algorithm is chosen:

- **fp16:** 102.4 GB — fits on a large memory-optimised instance.
- **int8 scalar quantisation:** 51.2 GB — comfortable, with a small recall cost.
- **Product quantisation** at, say, 64 bytes/vector: 3.2 GB — fits in cache-friendly memory, with a
  larger recall cost that you must measure rather than assume.

**Then the compute.** A brute-force scan is 50 M × 1024 multiply-adds = 51.2 GFLOP *per query*. At a
realistic 380 GFLOP/s of achieved fp64 BLAS throughput on a laptop-class CPU (measured in Module 2),
that is about 135 ms per query for one query, single-threaded — already over budget before any
concurrency. And it is memory-bandwidth-bound in practice, not compute-bound: you must stream 204.8 GB
per query, which at 150 GB/s takes 1.4 seconds.

**So brute force is out by roughly 30×, and the gap is bandwidth.** That forces an approximate index —
HNSW or IVF-PQ — which is exactly Week 27's subject.

**Now the part this module contributes.** From the concentration table, at d = 1024 the spread of
distances is on the order of 1.5% of the mean. An approximate index that gets "close enough" in
distance may be returning a completely different item, because *many items are close enough*. This is
why ANN systems are evaluated on **recall@k against the exact answer**, not on distance error — and
why you must build the exact index (the reference implementation above) before you build the
approximate one, to have ground truth to measure against.

The complete answer has four numbers: storage per precision, bytes streamed per brute-force query,
the resulting speedup requirement, and the recall target. A candidate who says "use a vector database"
without any of them has not done the design.

### The curse of dimensionality, quantified

Three separate phenomena travel under that name, and they have different consequences.

**1. Concentration of distances.** For i.i.d. random points, the ratio of the maximum to the minimum
distance from a query tends to 1 as `d → ∞`. Measured:

| d | (max − min)/min | dist std/mean |
|---|---|---|
| 2 | 2837.7 | 48.98% |
| 10 | 2.087 | 16.65% |
| 100 | 0.4071 | 4.99% |
| 1000 | 0.1013 | 1.58% |
| 4096 | 0.0599 | 0.77% |

Beyer, Goldstein, Ramakrishnan and Shaft's 1999 result is the formal statement: under broad
conditions, the nearest neighbour becomes indistinguishable from the farthest as dimension grows, and
so "nearest neighbour" stops being a meaningful query.

**Why embeddings work anyway** — and this is the crucial caveat — is that **real embeddings are not
i.i.d. random points.** They lie on a low-dimensional manifold inside the high-dimensional space; the
*intrinsic* dimension is far below the ambient dimension. Empirically, estimates of intrinsic
dimension for text-embedding spaces are typically an order of magnitude below the ambient dimension.
The measurement above is the worst case, and it tells you what you are relying on: you are relying on
your data having structure. When your embeddings *do* behave like the table above, your retrieval has
stopped working and you should check whether the encoder is producing anything meaningful.

**2. Volume concentrates in the shell.** The volume of a `d`-ball scales as `r^d`, so the fraction of
a unit ball's volume lying within radius `0.9` is `0.9^d`. At d = 100 that is 0.0027 — **99.7% of the
volume is in the outer 10% shell.** At d = 1000 it is `10^-46`. "Interior" ceases to exist in any
useful sense, which is why intuitions built in 2-D and 3-D mislead so reliably.

**3. Sampling requirements explode.** To cover a `d`-dimensional unit cube at resolution 0.1 per axis
requires `10^d` samples. At d = 10 that is 10 billion. This is the reason non-parametric methods (kNN
regression, kernel density estimation) degrade in high dimension while parametric models do not, and
it is the reason deep learning works at all: it imposes structure rather than filling space.

### Near-orthogonality and the Johnson-Lindenstrauss lemma

The mean absolute cosine measured above falls as roughly `1/sqrt(d)`: 0.0802 at d = 100 and 0.0251 at
d = 1000, and `sqrt(1000/100) = 3.16` against a measured ratio of 3.19. That is the theoretical rate,
confirmed.

The consequence is the **Johnson-Lindenstrauss lemma**: any `n` points in any dimension can be
projected into `O(log n / ε²)` dimensions while preserving all pairwise distances to within a factor
of `1 ± ε`. Concretely, one million points can be embedded in a few thousand dimensions with 10%
distortion, *regardless of the original dimension*.

Two practical consequences:

- **Random projection is a legitimate dimensionality reduction technique**, requires no training, and
  costs one matrix multiply. It is the basis of several LSH schemes and a reasonable baseline before
  reaching for PCA.
- **The number of "almost orthogonal" directions in `d` dimensions is exponential in `d`**, not linear.
  In 768 dimensions you can pack an enormous number of directions that are pairwise near-orthogonal.
  This is the mathematical basis of the **superposition** hypothesis in mechanistic interpretability:
  a network with 768 neurons can represent far more than 768 features by assigning each an
  almost-orthogonal direction and tolerating small interference. Elhage et al.'s "Toy Models of
  Superposition" (2022) makes this precise, and the arithmetic starts with the table above.

### Memory and bandwidth: what a vector actually costs

| Precision | Bytes/dim | 1024-D vector | 1 M vectors | 1 B vectors |
|---|---|---|---|---|
| fp32 | 4 | 4.10 KB | 4.10 GB | 4.10 TB |
| fp16 / bf16 | 2 | 2.05 KB | 2.05 GB | 2.05 TB |
| int8 | 1 | 1.02 KB | 1.02 GB | 1.02 TB |
| PQ (64 subquantisers, 8 bits) | 0.0625 | 64 B | 64 MB | 64 GB |

Brute-force search is **memory-bandwidth-bound, not compute-bound.** One query against 1 M fp32
1024-D vectors reads 4.1 GB. At ~150 GB/s of achievable memory bandwidth on a laptop-class machine
that is a 27 ms floor from bandwidth alone, regardless of how fast your FLOPs are. Compare against
the compute: 2 × 10⁶ × 1024 = 2.05 GFLOP, which at the ~1,550 GFLOP/s fp32 BLAS rate measured in
Module 2 is 1.3 ms. **Bandwidth is 20× the bottleneck.**

That single ratio explains the whole design of modern vector search: quantisation is not primarily
about storage, it is about **bytes moved per query**. Cutting fp32 to int8 cuts the bandwidth floor
4×, and product quantisation cuts it 64×. You are buying bandwidth, and you pay in recall.

### Production failure modes

| Failure | Signature | Detection |
|---|---|---|
| **Unnormalised vectors with dot-product scoring** | Long documents dominate every result set | `np.linalg.norm(embs, axis=1)` — if not all 1.0, and you use dot, you have it |
| **Mixed normalisation between index and query** | Scores outside [−1, 1]; ranking subtly wrong | Assert `abs(score) <= 1.0 + 1e-5` in the search path |
| **Different embedding model versions in one index** | Recall collapses for a subset of documents | Store the model id and version with every vector; refuse mixed queries |
| **fp16 overflow during normalisation** | NaNs for a small fraction of vectors | Norm computed in fp16 overflows above ~65,504. Compute norms in fp32, then cast |
| **Zero vectors** | Division by zero → NaN → that document matches nothing, silently | Validate at write time; an empty or all-stopword document embeds near zero for some models |
| **Cosine on features with different units** | Nonsense neighbours | Cosine on raw mixed-unit features is meaningless. Standardise first, or use a learned metric |
| **ANN recall degraded after a data-distribution shift** | Quality drops with no code change | Recall@k against the exact index, measured on a fixed probe set, on a schedule |

### Frontier and further pointers

- **K. Beyer, J. Goldstein, R. Ramakrishnan and U. Shaft, "When Is 'Nearest Neighbor' Meaningful?",
  ICDT 1999.** Takeaway: under broad conditions the ratio of farthest to nearest distance converges to
  1 as dimension grows, so nearest-neighbour queries lose meaning — unless the data has low intrinsic
  dimension, which is exactly what real embeddings provide.
- **W. B. Johnson and J. Lindenstrauss (1984), and the modern treatments of random projection.**
  Takeaway: `n` points embed into `O(log n / ε²)` dimensions with `1 ± ε` distance distortion
  independent of the source dimension, which makes random projection a training-free baseline for
  dimensionality reduction.
- **N. Elhage et al., "Toy Models of Superposition," Transformer Circuits, 2022.** Takeaway: because
  the number of near-orthogonal directions grows exponentially with dimension, a layer can represent
  many more features than it has neurons by tolerating small interference — the near-orthogonality
  measured in this module is the mechanism.
- **J. Johnson, M. Douze and H. Jégou, "Billion-scale similarity search with GPUs" (FAISS), IEEE Big
  Data 2019.** Takeaway: at scale the binding constraint is memory bandwidth rather than FLOPs, which
  is why product quantisation and GPU-resident compressed codes, not faster distance kernels, are what
  make billion-scale search possible.

### Stretch challenge

Measure the **intrinsic dimension** of a real embedding space and connect it to retrieval quality.

1. Take 20,000 embeddings from a real model (any sentence-transformers checkpoint, or a cached set).
   Reproduce the concentration table on them: mean absolute cosine, distance spread, (max−min)/min.
2. Compare against random Gaussian vectors of the same ambient dimension. The real embeddings will be
   *much* less concentrated. Quantify the gap.
3. Estimate intrinsic dimension two ways: (a) PCA — how many components explain 95% of variance
   (Module 3 gives you this); (b) a two-nearest-neighbour maximum-likelihood estimator. Do they agree?
4. Now the experiment that matters: **randomly project** the embeddings to `k` dimensions for
   `k = 8, 16, 32, 64, 128, 256, 512` and measure recall@10 against the exact full-dimension answer at
   each `k`. Plot recall against `k` and against bytes per vector.
5. Find the knee. Compare it against your intrinsic-dimension estimates. Then write the paragraph:
   how many dimensions does this embedding model actually need, and what did the extra ones buy?

There is no single right answer — models differ, and the knee moves with the corpus. The valuable
output is the recall-versus-bytes curve, because that is the axis a real system is optimised on.

## Common mistakes

| Symptom | Cause | Fix |
|---|---|---|
| Long documents dominate every search result | Unnormalised vectors scored by dot product | Normalise at write time; then dot product *is* cosine |
| Similarity scores outside [−1, 1] | Index normalised, query not (or vice versa) | Normalise in one place; assert the score range in the search path |
| `ValueError` or wrong broadcast when normalising a matrix | `np.linalg.norm(A, axis=1)` returns `(n,)`, not `(n, 1)` | `keepdims=True` |
| NaNs for a few documents | Zero-norm vector (empty or all-stopword input), or fp16 norm overflow | Validate at write time; compute norms in fp32 |
| Euclidean and cosine disagree on ranking | Vectors are not normalised | For unit vectors `‖u−v‖² = 2 − 2(u·v)`, so the rankings must agree; if they differ, you did not normalise |
| Cosine gives nonsense on tabular features | Mixed units and scales | Standardise features first; cosine on raw mixed units is meaningless |
| Recall drops after a model upgrade | Index contains vectors from two model versions | Store model id and version per vector; rebuild on upgrade |
