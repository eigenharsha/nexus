## The mental model

A matrix is a **function that takes a vector and returns a vector**, with one restriction: it must be
*linear*, which means it does exactly two things — it can stretch space and it can rotate or shear it,
but it always keeps the origin fixed and always keeps parallel lines parallel.

The single most useful fact: **the columns of a matrix tell you where the basis vectors land.**

If `M` is 2×2, then column 1 is where `[1, 0]` goes and column 2 is where `[0, 1]` goes. Everything
else follows, because every other vector is a combination of those two, and linearity means
combinations are preserved.

That one sentence turns matrix multiplication from a rule you memorise into something you can predict
by looking.

### A matrix is a grid, and the grid is a function

A **matrix** is a rectangular grid of numbers. We write its size as rows × columns, so

```
M = [ 2  0 ]        is a 2x2 matrix
    [ 0  3 ]
```

To apply a matrix to a vector, you take the dot product of each *row* with the vector:

```
M v  where  M = [ 2  0 ]   and   v = [ 1 ]
                [ 0  3 ]             [ 1 ]

row 1 · v = (2 × 1) + (0 × 1) = 2
row 2 · v = (0 × 1) + (3 × 1) = 3

so  M v = [ 2 ]
          [ 3 ]
```

The vector `[1, 1]` went to `[2, 3]`. Draw both arrows. The matrix stretched space by 2 horizontally
and 3 vertically.

```python
def matvec(M, v):
    return [sum(m_ij * v_j for m_ij, v_j in zip(row, v)) for row in M]

print(matvec([[2, 0], [0, 3]], [1, 1]))     # [2, 3]
```

### The columns are where the basis vectors land

Apply that same matrix to `[1, 0]`:

```
M [1, 0] = [2, 0]      <- that is exactly column 1 of M
M [0, 1] = [0, 3]      <- that is exactly column 2 of M
```

This is not a coincidence, it is arithmetic: multiplying by `[1, 0]` picks out the first entry of
each row, which *is* the first column.

So here is the whole trick. **To see what a matrix does, look at where its columns are.** You do not
need to compute anything.

Try it on four matrices. Draw the unit square (corners at `[0,0]`, `[1,0]`, `[1,1]`, `[0,1]`) and then
draw where each corner goes.

| Matrix | Column 1 (where `[1,0]` goes) | Column 2 (where `[0,1]` goes) | What it does |
|---|---|---|---|
| `[[2,0],[0,2]]` | `[2,0]` | `[0,2]` | **scale** everything by 2 |
| `[[1,1],[0,1]]` | `[1,0]` (unmoved) | `[1,1]` (tilted right) | **shear** — pushes the top sideways |
| `[[0,-1],[1,0]]` | `[0,1]` | `[-1,0]` | **rotate** 90° anticlockwise |
| `[[1,2],[2,4]]` | `[1,2]` | `[2,4]` | **squash** — both columns lie on the same line! |

That last one deserves attention. Column 2 is exactly 2 × column 1. Both basis vectors land on the
*same line*, so **every** vector lands on that line. The whole plane has been flattened into a line.
Information has been destroyed: many different inputs now give the same output, and there is no way
to undo it.

That property has a name — **rank** — and we come back to it below.

### Matrix times matrix: doing one transformation after another

If `A` and `B` are both transformations, then `AB` means "**do B first, then A**". (Yes, right to left.
It is the same order as function notation `f(g(x))`, and it is the source of a lot of confusion.)

The rule for computing it: entry `(i, j)` of `AB` is the dot product of row `i` of `A` with column `j`
of `B`.

```
A = [ 2  0 ]      B = [ 1  1 ]
    [ 0  3 ]          [ 0  1 ]

AB[0][0] = (2,0) · (1,0) = 2
AB[0][1] = (2,0) · (1,1) = 2
AB[1][0] = (0,3) · (1,0) = 0
AB[1][1] = (0,3) · (1,1) = 3

AB = [ 2  2 ]
     [ 0  3 ]
```

```python
def matmul(A, B):
    n, k, m = len(A), len(B), len(B[0])
    return [[sum(A[i][p] * B[p][j] for p in range(k)) for j in range(m)]
            for i in range(n)]

print(matmul([[2, 0], [0, 3]], [[1, 1], [0, 1]]))    # [[2, 2], [0, 3]]
```

**Shapes:** an `(n × k)` matrix times a `(k × m)` matrix gives an `(n × m)` matrix. The two inner
numbers must match, and then they disappear. Write it out every time:

```
(n x k) @ (k x m) -> (n x m)
      ^     ^
      these must match, and then they vanish
```

That habit will save you hours in Week 21. It is the whole shape-debugging method.

**Order matters.** `AB` is generally not `BA`:

```python
print(matmul([[1, 1], [0, 1]], [[2, 0], [0, 3]]))    # [[2, 3], [0, 3]]  -- different!
```

Which makes sense from the picture: rotating then stretching is not the same as stretching then
rotating.

### Transpose: flip it over the diagonal

The **transpose** of `M`, written `Mᵀ`, swaps rows and columns. Element `(i, j)` becomes `(j, i)`.

```
M  = [ 1  2  3 ]         Mᵀ = [ 1  4 ]
     [ 4  5  6 ]              [ 2  5 ]
                              [ 3  6 ]
```

A 2×3 becomes a 3×2. In practice you will use transpose constantly, for one reason: **to make shapes
line up.** If you have `A` of shape `(n, d)` and `B` of shape `(m, d)` and you want all pairwise dot
products, `A @ B.T` gives you `(n, m)`. That single expression is the core of an attention layer and
of the similarity search in Module 1.

### Identity and inverse

The **identity matrix** `I` has 1s down the diagonal and 0s elsewhere. It is the transformation that
does nothing:

```
I = [ 1  0 ]        I v = v   for every v
    [ 0  1 ]
```

The **inverse** of `M`, written `M⁻¹`, is the transformation that undoes `M`: `M⁻¹ M = I`. If `M`
rotates by 90°, `M⁻¹` rotates by −90°. If `M` scales by 2, `M⁻¹` scales by ½.

**Not every matrix has an inverse.** The squash matrix `[[1,2],[2,4]]` does not, because it flattened
the plane onto a line — many inputs map to the same output, so there is no way to run it backwards.

### Determinant: how much area changed

The **determinant** of a 2×2 matrix is a single number telling you how much the transformation scales
area. For

```
M = [ a  b ]        det(M) = ad − bc
    [ c  d ]
```

- `det = 2` means areas double.
- `det = 1` means area is preserved (a rotation, for instance).
- `det = −1` means area preserved but space was *flipped* (mirrored).
- **`det = 0` means area collapsed to zero** — the transformation squashed space into a lower
  dimension, and there is no inverse.

Check the squash: `det([[1,2],[2,4]]) = 1×4 − 2×2 = 0`. Confirmed.

**`det = 0` ⟺ no inverse.** That is the connection worth remembering, and it is why "the matrix is
singular" and "the determinant is zero" mean the same thing.

### Rank: how many dimensions survive

The **rank** of a matrix is the number of dimensions its output actually occupies.

- `[[2,0],[0,3]]` has rank 2 — the output fills the whole plane.
- `[[1,2],[2,4]]` has rank 1 — the output is a line.
- The all-zeros matrix has rank 0 — everything goes to the origin.

A matrix is **full rank** when its rank equals the smaller of its two dimensions. Full rank means
nothing was thrown away. Low rank means the matrix has *less information in it than its size
suggests* — which is the entire idea behind Module 3, image compression, and LoRA.

```python
import numpy as np
print(np.linalg.matrix_rank(np.array([[2, 0], [0, 3]])))   # 2
print(np.linalg.matrix_rank(np.array([[1, 2], [2, 4]])))   # 1
print(np.linalg.det(np.array([[1., 2.], [2., 4.]])))       # 0.0
```

```python
import numpy as np
square = np.array([[0, 1, 1, 0],       # x-coordinates of the 4 corners
                   [0, 0, 1, 1]])      # y-coordinates

mats = {
    "A": np.array([[3, 0], [0, 1]]),
    "B": np.array([[1, 0], [0.5, 1]]),
    "C": np.array([[0, 1], [1, 0]]),
    "D": np.array([[2, 4], [1, 2]]),
}
for name, M in mats.items():
    out = M @ square
    print(name, "corners ->", out.T.tolist(),
          " det =", round(float(np.linalg.det(M)), 3),
          " rank =", np.linalg.matrix_rank(M))
```

Before running: which one has determinant 0? Which one is a reflection?

<Accordion title="Answers">

- **A** `[[3,0],[0,1]]` — stretches by 3 horizontally, leaves vertical alone. `det = 3`, rank 2. The
  square becomes a 3×1 rectangle.
- **B** `[[1,0],[0.5,1]]` — a vertical shear: `[1,0]` goes to `[1, 0.5]`, so the bottom edge tilts up.
  `det = 1`, rank 2. **Area is unchanged** — shears never change area, which surprises people the
  first time.
- **C** `[[0,1],[1,0]]` — swaps the coordinates, which is a **reflection** in the line `y = x`.
  `det = −1`. The negative sign is exactly the "space was flipped" signal.
- **D** `[[2,4],[1,2]]` — column 2 is 2 × column 1, so both basis vectors land on the same line.
  `det = 2×2 − 4×1 = 0`, **rank 1**. The square collapses to a line segment. No inverse exists.

The general rule you should extract: **look at the columns first.** If one column is a multiple of
another, the determinant is zero and you have lost a dimension, and no amount of computing will
recover it.

### Three readings of matrix multiplication

The same operation, three interpretations. You need all three because different situations make
different ones obvious.

**1. Rows dot columns.** `C[i,j] = A[i,:] · B[:,j]`. The definition. Best for hand computation and for
understanding shape rules.

**2. Columns of the output are transformed columns of B.** `C[:,j] = A @ B[:,j]`. Best for thinking
about a matrix as a *function applied to many inputs at once*. This is the right reading for
`X @ W` in a neural network: each row of `X` is an example, and `W` transforms it.

**3. Sum of outer products.** `C = Σₚ A[:,p] ⊗ B[p,:]`, where each term is a rank-1 matrix. Best for
understanding **low-rank approximation** — if you keep only the largest few terms of that sum, you
have compressed the matrix. This is exactly what Module 3's SVD does and exactly what LoRA
(Week 26) exploits.

```python
import numpy as np
A = np.random.default_rng(0).standard_normal((4, 3))
B = np.random.default_rng(1).standard_normal((3, 5))

C1 = np.array([[A[i] @ B[:, j] for j in range(5)] for i in range(4)])   # reading 1
C2 = np.column_stack([A @ B[:, j] for j in range(5)])                   # reading 2
C3 = sum(np.outer(A[:, p], B[p, :]) for p in range(3))                  # reading 3
assert np.allclose(C1, C2) and np.allclose(C2, C3) and np.allclose(C3, A @ B)
```

Reading 3 is the one that pays off later. `A @ B` where the inner dimension is 3 is *a sum of three
rank-1 matrices*. If the inner dimension were 8 and the outer dimensions 4096, you would be describing
a 4096×4096 matrix with 8 rank-1 pieces — 65,536 numbers instead of 16.8 million. That is LoRA, and
you have just written it.

### Shape discipline: the practice that eliminates the bug class

Shape errors are the dominant bug in numerical Python, and the standard "fix" — permuting arguments
and adding `.T` until the error goes away — produces code that runs and computes the wrong thing.
Replace it with a mechanical process.

**Rule 1: annotate every array with its shape, in a comment, using names not numbers.**

```python
# x:      (B, S, D)      batch, sequence, model dim
# W_qkv:  (D, 3 * H * Dh)
# qkv:    (B, S, 3, H, Dh)
```

**Rule 2: assert shapes at function boundaries.**

```python
def attention(q, k, v):
    B, H, S, Dh = q.shape
    assert k.shape == (B, H, S, Dh), f"k {k.shape} != q {q.shape}"
    assert v.shape == (B, H, S, Dh), f"v {v.shape} != q {q.shape}"
    scores = q @ k.transpose(-2, -1)          # (B,H,S,Dh) @ (B,H,Dh,S) -> (B,H,S,S)
    assert scores.shape == (B, H, S, S)
    return (scores.softmax(-1) @ v)           # (B,H,S,S) @ (B,H,S,Dh) -> (B,H,S,Dh)
```

**Rule 3: use `einsum` when the index bookkeeping gets hard.** It makes the contraction explicit and
self-documenting:

```python
scores = np.einsum('bhqd,bhkd->bhqk', q, k)     # unmistakable: contract over d
```

**Rule 4: make the batch dimension always first, and never squeeze it.** A batch of 1 that gets
silently squeezed to a 2-D array is the classic source of "works in the test, breaks in production".

**Rule 5: when a shape error appears, write both shapes down and find the mismatched axis before
touching the code.** The transformation you need is then obvious, and it is usually a `transpose`, not
a `reshape`. **`reshape` reinterprets memory and `transpose` reorders axes** — using `reshape` where
you meant `transpose` silently scrambles data and produces no error at all.

### Broadcasting, precisely

NumPy aligns shapes from the **right**. Two dimensions are compatible if they are equal, or one of
them is 1.

```
(3, 4)   +  (4,)      -> (3, 4)     row vector added to every row
(3, 4)   +  (3, 1)    -> (3, 4)     column vector added to every column
(3, 4)   +  (3,)      -> ERROR      4 vs 3, and neither is 1
(2, 1, 4) + (3, 4)    -> (2, 3, 4)  the middle 1 stretches
```

The trap that appears in real code:

```python
scores = np.array([[1.0, 2.0], [3.0, 4.0]])        # (2, 2)
row_sums = scores.sum(axis=1)                       # (2,)   -- NOT (2, 1)
probs = scores / row_sums                           # broadcasts along the WRONG axis, no error
probs_ok = scores / row_sums[:, None]               # (2, 2) / (2, 1) -- correct
print(probs)      # [[0.333, 0.286], [1.0, 0.571]]  rows do not sum to 1
print(probs_ok)   # [[0.333, 0.667], [0.429, 0.571]] correct
```

No exception is raised. The output has the right shape and the wrong values. **`keepdims=True` on
every reduction that feeds a broadcast** is the habit that prevents this, and it costs nothing.

### Measured: the cost of writing the loop yourself

```python
# matmul.py — the same C = A @ B, four ways.
import numpy as np, time

def naive(A, B):                      # pure Python triple loop
    n, k = A.shape; m = B.shape[1]
    C = np.zeros((n, m))
    for i in range(n):
        for j in range(m):
            s = 0.0
            for p in range(k): s += A[i, p] * B[p, j]
            C[i, j] = s
    return C

def rows(A, B):                       # loop over rows, vectorised inner product
    C = np.empty((A.shape[0], B.shape[1]))
    for i in range(A.shape[0]): C[i] = A[i] @ B
    return C

def tiled(A, B, T=64):                # blocked, to fit tiles in cache
    n, k = A.shape; m = B.shape[1]
    C = np.zeros((n, m))
    for i0 in range(0, n, T):
        for j0 in range(0, m, T):
            acc = C[i0:i0+T, j0:j0+T]
            for p0 in range(0, k, T):
                acc += A[i0:i0+T, p0:p0+T] @ B[p0:p0+T, j0:j0+T]
    return C
```

Measured on numpy 2.5.2, Python 3.13.2, Apple M3 Pro (Accelerate BLAS), best of several runs:

| n | naive Python | row-vectorised | tiled | BLAS (`A @ B`) | naive / BLAS |
|---|---|---|---|---|---|
| 128 | 321.3 ms (0.013 GFLOP/s) | 0.23 ms (17.9) | 0.06 ms (66.1) | **0.013 ms (313.6)** | **24,025×** |
| 256 | 2410.3 ms (0.014 GFLOP/s) | 0.70 ms (48.2) | 0.47 ms (71.2) | **0.086 ms (389.2)** | **27,959×** |

And precision, at BLAS speed:

| n | fp64 | fp32 | speedup |
|---|---|---|---|
| 512 | 0.68 ms (396 GFLOP/s) | 0.17 ms (**1,579 GFLOP/s**) | 3.98× |
| 1024 | 5.66 ms (380 GFLOP/s) | 1.38 ms (**1,551 GFLOP/s**) | 4.09× |
| 2048 | 47.83 ms (359 GFLOP/s) | 11.78 ms (**1,458 GFLOP/s**) | 4.06× |

Four things to take from that table.

1. **The pure-Python loop is ~28,000× slower than BLAS.** Not 28×. Twenty-eight thousand. Every
   interpreter operation — bounds check, type dispatch, object allocation — happens per multiply.
2. **Just vectorising the inner loop gets you to within ~10× of BLAS** at n = 256 (48 vs 389
   GFLOP/s). Most of the win is available for almost no effort.
3. **fp32 is ~4× faster than fp64**, consistently. Vector registers hold twice as many fp32 values and
   the memory traffic halves. This is why deep learning is fp32 or lower by default, and it is the
   first step on the road to fp16, bf16 and int8 in Week 26.
4. **The naive GFLOP/s figure barely changes with n** (0.013 → 0.014) because it is interpreter-bound,
   while BLAS *falls* slightly with n (396 → 359 fp64) because it becomes memory-bound. Those are
   different regimes and the crossover is Module 9's Roofline argument from Week 9.

### Trade-offs

| Decision | Choose this when… | Choose the other when… | The number |
|---|---|---|---|
| **`A @ B`** | Always, for dense matmul | Never, unless you are learning | 28,000× faster than the Python equivalent |
| **fp32** | Training and inference of neural networks | Numerical linear algebra where conditioning matters (solving, inversion, eigenvalues) | 4× the throughput, half the memory; ~7 decimal digits versus ~16 |
| **`einsum`** | Complex multi-axis contractions where index bookkeeping is the risk | Simple 2-D matmul | Same BLAS underneath for common cases; the win is readability, not speed |
| **`reshape`** vs **`transpose`** | Reinterpreting the same memory layout | Reordering axes | Confusing them scrambles data silently and raises no error |
| **Explicit tiling in Python** | Teaching; or when you cannot call BLAS | Any real workload | Tiled NumPy reached 71 GFLOP/s against BLAS's 389 — better than naive, still 5.5× off |

### Reference implementation

Shape-safe linear algebra helpers with the assertions that catch real bugs:

```python
# shapes.py — utilities that make shape bugs loud instead of silent.
import numpy as np

def matmul_checked(A: np.ndarray, B: np.ndarray) -> np.ndarray:
    if A.ndim != 2 or B.ndim != 2:
        raise ValueError(f"expected 2-D, got {A.ndim}-D and {B.ndim}-D")
    if A.shape[1] != B.shape[0]:
        raise ValueError(
            f"inner dimensions do not match: {A.shape} @ {B.shape}. "
            f"Did you mean A @ B.T ({A.shape} @ {B.T.shape})?"
        )
    return A @ B

def softmax_rows(x: np.ndarray) -> np.ndarray:
    """Numerically stable row-wise softmax. keepdims is load-bearing, twice."""
    x = np.asarray(x, dtype=np.float64)
    m = x.max(axis=-1, keepdims=True)          # subtract the max: prevents exp overflow
    e = np.exp(x - m)
    return e / e.sum(axis=-1, keepdims=True)   # keepdims -> correct broadcast

def pairwise_dots(A: np.ndarray, B: np.ndarray) -> np.ndarray:
    """All pairwise dot products: (n, d) x (m, d) -> (n, m)."""
    if A.shape[1] != B.shape[1]:
        raise ValueError(f"feature dims differ: {A.shape[1]} vs {B.shape[1]}")
    return A @ B.T

if __name__ == "__main__":
    rng = np.random.default_rng(0)
    x = rng.standard_normal((5, 7)) * 100
    p = softmax_rows(x)
    assert np.allclose(p.sum(axis=1), 1.0), p.sum(axis=1)
    assert np.all(np.isfinite(p))
    big = np.array([[1000.0, 1001.0, 1002.0]])       # would overflow without the max trick
    assert np.allclose(softmax_rows(big).sum(), 1.0)
    print("ok")
```

Two details worth stealing. The error message in `matmul_checked` **suggests the fix** — nine times
out of ten the intended operation was `A @ B.T`, and saying so turns a two-minute debug into a
five-second one. And `softmax_rows` subtracts the row maximum before exponentiating: without it,
`exp(1000)` overflows to `inf` and the result is `nan`. Every softmax in every framework does this,
and it is worth knowing why.

### What breaks in the real world

A team fine-tuning a classifier saw training loss decrease normally and validation accuracy sit at
exactly chance. Everything looked right: the loss curve, the gradient norms, the learning-rate
schedule.

The bug was one line in the data pipeline. Images arrived as `(batch, height, width, channels)` from
the loader and the model wanted `(batch, channels, height, width)`. The author wrote
`x.reshape(B, C, H, W)` instead of `x.permute(0, 3, 1, 2)`. `reshape` accepted it without complaint —
the total number of elements is identical — and produced tensors in which each "channel" was a
horizontal stripe of the original image, interleaved.

The model trained happily on the scrambled data, learned the training set, and generalised to nothing.
Three days were spent on learning rates and augmentation before someone saved a batch to disk and
looked at it.

**Two rules came out of that incident, and they are worth adopting.** First: `reshape` only when you
are certain the memory order is what you want; `permute`/`transpose` when you are reordering meaning.
Second, and more useful: **look at the data after every transformation in the pipeline, once.** Save
five images to PNG. Print five rows of the tensor. Ten minutes of looking would have replaced three
days of hypothesising.

### Design checkpoint

<Accordion title="You have a (32, 512, 768) activation tensor and a (768, 3072) weight matrix. Write the multiply, state the output shape, and compute the FLOPs and memory traffic.">

**The multiply.** NumPy and PyTorch both broadcast matmul over leading dimensions:

```python
out = x @ W          # (32, 512, 768) @ (768, 3072) -> (32, 512, 3072)
```

The last axis of `x` (768) contracts with the first axis of `W` (768). Everything to the left of that
is treated as batch.

**FLOPs.** Each output element is a dot product of length 768, which is 768 multiplies and 767 adds —
conventionally counted as `2 × 768` FLOPs.

```
output elements = 32 × 512 × 3072 = 50,331,648
FLOPs           = 2 × 768 × 50,331,648 = 77.3 GFLOP
```

**Memory traffic** (fp32, if nothing is cached):

```
x:   32 × 512 × 768  × 4 B =  50.3 MB
W:   768 × 3072      × 4 B =   9.4 MB
out: 32 × 512 × 3072 × 4 B = 201.3 MB
total                       ≈ 261 MB
```

**Arithmetic intensity** = 77.3 GFLOP / 0.261 GB ≈ **296 FLOP/byte**. Compare against machine balance
from Week 9: roughly 10 FLOP/byte for a laptop CPU and ~295 for an H100's tensor cores. So this
operation is **compute-bound on a CPU and right at the balance point on an H100** — which is exactly
why large matmuls are the only thing that reaches peak on modern accelerators, and why every
Transformer optimisation is about making the matmuls bigger rather than fewer.

**And the practical follow-up:** at the measured 1,551 GFLOP/s fp32 rate on an M3 Pro, 77.3 GFLOP is
about 50 ms. In fp16 on an H100 at ~990 TFLOP/s it is about 78 µs. That four-order-of-magnitude gap,
for one layer of one batch, is the entire reason GPU training exists.

A complete answer states the shape, the FLOPs, the bytes, the intensity, and which side of machine
balance it falls on. That is the calculation you will do repeatedly in Phase 3 and 4.

### Why BLAS is 28,000× your loop

The gap decomposes into four factors, and it is worth knowing which contributes what.

**1. Interpreter overhead (~100–1000×).** A CPython bytecode operation costs on the order of 20–50 ns.
A hardware fused multiply-add costs about 0.25 ns. The naive loop measured **0.013 GFLOP/s**, which
is about 77 ns per multiply-add — entirely interpreter.

**2. Vectorisation (4–16×).** BLAS uses SIMD: NEON on ARM gives 4 fp32 lanes, AVX-512 gives 16. Each
instruction does 4–16 multiply-adds. This is the same mechanism as Week 9 Module 5's measured 4.79×.

**3. Cache blocking (2–10×).** A naive `i, j, p` loop over an `n × n` matmul reads `B` column-wise,
striding by `n` — exactly the pathological pattern measured in Week 9 Module 4 at up to **66.7×**
slower. BLAS tiles the computation so each tile fits in L1/L2 and is reused `O(T)` times before being
evicted. The measured tiled NumPy version reached 71 GFLOP/s against 48 for the row-vectorised one, a
1.5× gain from blocking alone even with NumPy already doing the inner work.

**4. Instruction-level parallelism and register blocking (2–4×).** Hand-tuned microkernels keep 8–16
accumulators live in registers so the multiply-add pipeline never stalls on a dependency — the same
"break the dependency chain" idea from Week 9 Module 5.

Multiply them: `500 × 8 × 4 × 3 ≈ 48,000`, in the right neighbourhood of the measured 28,000×.

The practical rule that falls out: **matmul is one of maybe five operations that have been optimised
by specialists for forty years.** Your job is to express your computation as one, not to implement one.

### Precision: what fp32, fp16 and bf16 actually cost you

| Format | Bits (sign/exp/mantissa) | Decimal digits | Max | Min normal |
|---|---|---|---|---|
| fp64 | 1/11/52 | ~15.9 | 1.8e308 | 2.2e-308 |
| fp32 | 1/8/23 | ~7.2 | 3.4e38 | 1.2e-38 |
| **fp16** | 1/5/10 | ~3.3 | **65,504** | 6.1e-5 |
| **bf16** | 1/8/7 | ~2.4 | 3.4e38 | 1.2e-38 |
| fp8 (E4M3) | 1/4/3 | ~1.2 | 448 | 1.5e-3 |

Measured throughput on the M3 Pro: fp32 is **~4.06× faster than fp64** consistently across n = 512,
1024 and 2048.

The fp16-versus-bf16 distinction is the one that matters in practice. **bf16 has the same exponent
range as fp32 and fewer mantissa bits; fp16 has more mantissa bits and a drastically smaller range.**
Gradients in deep networks routinely fall below fp16's smallest normal value of 6.1e-5 and flush to
zero, which is why fp16 training requires **loss scaling** (multiply the loss by ~2¹⁵ before the
backward pass, divide the gradients afterwards) and bf16 does not. Every accelerator since the A100
supports bf16 for exactly this reason.

Matmul in low precision is usually done with **fp32 accumulation**: the multiplies are fp16/bf16, the
running sum is fp32. Without that, accumulating thousands of terms in fp16 loses catastrophically —
once the accumulator exceeds about 2048, adding 1 to it is a no-op in fp16, because the gap between
representable values exceeds 1.

### Numerical stability: condition number

The **condition number** of a matrix, `κ(A) = σ_max / σ_min` (the ratio of largest to smallest
singular value — Module 3 defines these), tells you how much a relative error in the input is
amplified in the output of a solve.

Rule of thumb: **you lose about `log₁₀(κ)` decimal digits of accuracy.**

```python
import numpy as np
def hilbert(n): return 1.0 / (np.arange(1, n+1)[:, None] + np.arange(n) )
for n in (5, 10, 15):
    H = hilbert(n)
    x = np.ones(n); b = H @ x
    x_hat = np.linalg.solve(H, b)
    print(f"n={n:2d}  kappa={np.linalg.cond(H):.3e}  max error={np.abs(x_hat-x).max():.3e}")
```

Measured output:

```
n= 5  kappa=4.766e+05  max error=1.718e-11
n=10  kappa=1.603e+13  max error=8.469e-04
n=15  kappa=4.239e+17  max error=1.087e+01
```

The true answer is all ones. At n = 15 the computed "solution" is off by **10.87** — it is not
approximately right, it is noise. And the rule of thumb holds precisely: at n = 10, `log₁₀(1.6e13) ≈
13.2`, and fp64's ~15.9 digits minus 13.2 leaves about 2.7 — the measured error of 8.5e-4 is right
there.

The same matrix shows why explicit inversion is worse. At n = 12:

```
solve :  0.1435
inv@b :  8.6563
```

**Inverting and multiplying is 60× less accurate than solving**, on identical input, for the same
reason: forming the inverse performs extra arithmetic on an already ill-conditioned problem.

Three practical consequences:

- **Never invert a matrix to solve a system.** `np.linalg.solve(A, b)` is both faster and more
  accurate than `np.linalg.inv(A) @ b`, because it uses LU factorisation and avoids forming the
  inverse at all. Explicit inversion is a red flag in a code review.
- **Prefer `lstsq` or a QR-based solve for least squares.** Forming the normal equations `AᵀA` squares
  the condition number, which halves your remaining digits.
- **In fp32 you have ~7 digits, so anything with `κ > 10⁵` is dangerous.** In deep learning this shows
  up as batch-norm and layer-norm statistics, and as the reason the epsilon in the denominator of a
  normalisation layer is not optional.

### At scale: the shape of every Transformer layer

A Transformer layer is entirely matrix multiplication. For batch `B`, sequence `S`, model dimension
`D`, feedforward dimension `F = 4D`, heads `H`:

| Operation | Shapes | FLOPs |
|---|---|---|
| QKV projection | `(B,S,D) @ (D,3D)` | `6·B·S·D²` |
| Attention scores | `(B,H,S,Dh) @ (B,H,Dh,S)` | `2·B·S²·D` |
| Attention × V | `(B,H,S,S) @ (B,H,S,Dh)` | `2·B·S²·D` |
| Output projection | `(B,S,D) @ (D,D)` | `2·B·S·D²` |
| MLP up | `(B,S,D) @ (D,4D)` | `8·B·S·D²` |
| MLP down | `(B,S,4D) @ (4D,D)` | `8·B·S·D²` |
| **Total per layer** | | `24·B·S·D² + 4·B·S²·D` |

The two terms behave differently and the crossover matters. The `S²` term overtakes the `D²` term when
`S > 6D`. For `D = 4096` that is `S > 24,576` tokens. So **for ordinary context lengths, a Transformer
is dominated by the feedforward and projection matmuls, not by attention** — which is why "attention
is quadratic" is true and often not the binding constraint, and why FlashAttention's contribution was
memory traffic rather than FLOPs.

Sanity-check it against a known number: Llama-2-7B has `D = 4096`, 32 layers. Forward FLOPs per token
≈ `2 × 7e9 = 14 GFLOP` (the standard `2 × params` estimate). Training is roughly 3× forward
(forward + backward), giving `6 × params` per token — the well-known `C ≈ 6ND` scaling-law formula
from Kaplan et al. You now know where that 6 comes from.

### Production failure modes

| Failure | Signature | Detection |
|---|---|---|
| **`reshape` used where `permute` was meant** | Model trains, generalises to nothing; no error at any point | Visualise the data after every pipeline stage. Assert shapes *and* look at values |
| **Broadcast along the wrong axis** | Wrong values, correct shape, no exception | `keepdims=True` on every reduction feeding a broadcast; assert row sums where they should be 1 |
| **fp16 overflow in softmax or norm** | `nan` appearing after a few hundred steps | Subtract the max before `exp`; compute norms and reductions in fp32; prefer bf16 |
| **fp16 gradient underflow** | Loss plateaus; gradient norms are exactly 0 for some layers | Loss scaling, or switch to bf16 (same exponent range as fp32) |
| **Explicit matrix inversion** | Results drift as the problem becomes ill-conditioned | `np.linalg.solve` / `lstsq`; check `np.linalg.cond` |
| **Non-contiguous tensors after transpose** | Silent 2–5× slowdown; some ops raise | `.contiguous()` after a permute that precedes a reshape; check `.flags['C_CONTIGUOUS']` |
| **Accumulation in low precision** | Sums silently stop growing past ~2048 in fp16 | Ensure fp32 accumulation; in PyTorch check the autocast dtype policy for your op |

- **K. Goto and R. van de Geijn, "Anatomy of High-Performance Matrix Multiplication," ACM TOMS 34(3),

  the default training format.
- **N. J. Higham, *Accuracy and Stability of Numerical Algorithms* (2nd ed., 2002), Chapters 1–3.**
  Takeaway: the condition number bounds the accuracy achievable by *any* algorithm on a problem, so

- **J. Kaplan et al., "Scaling Laws for Neural Language Models," 2020.** Takeaway: training compute is
  approximately `6ND` FLOPs for `N` parameters and `D` tokens — a number that falls directly out of
  the per-layer FLOP table above, and the basis of every training-budget decision in Phase 4.

## Common mistakes

| Symptom | Cause | Fix |
|---|---|---|
| Model trains but generalises to nothing | `reshape` used where `permute`/`transpose` was meant | `reshape` reinterprets memory; `transpose` reorders axes. Visualise the data after every stage |
| Rows of a "probability" matrix do not sum to 1 | Broadcast along the wrong axis after a reduction | `keepdims=True` on every reduction that feeds a broadcast |
| `ValueError: matmul: Input operand 1 has a mismatch` | Inner dimensions do not match | Write both shapes down; the answer is usually `A @ B.T`, not a reshape |
| `nan` after a few hundred training steps | `exp` overflow in softmax, or fp16 range exceeded | Subtract the row max before `exp`; use bf16 or fp32 accumulation |
| Gradients exactly zero for some layers in fp16 | Underflow below fp16's 6.1e-5 minimum normal | Loss scaling, or switch to bf16 |
| Numerical solution drifts or is nonsense | Ill-conditioned system, or explicit inversion | `np.linalg.solve`; check `np.linalg.cond`; expect to lose `log10(κ)` digits |
| Unexpected 2–5× slowdown after a transpose | Tensor is no longer contiguous | `.contiguous()` before an op that needs it; check the flags |
| "NumPy is slow" | Looping over rows in Python and calling NumPy inside | Express the whole operation as one array op; the measured cost of the loop is 3–4 orders of magnitude |
