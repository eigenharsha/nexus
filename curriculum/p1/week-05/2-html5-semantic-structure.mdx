## Why you should care

### For Aarav (student)

- Accessibility is the cheapest way to look senior in a code review. Almost nobody your age does it, and it takes ten minutes to learn the rules that matter.
- A Lighthouse accessibility score of 100 on your portfolio site is a screenshot you can put in the README. It is objective, verifiable, and rare.
- Interviewers ask "what is the difference between `div` and `section`?" to find out whether you have ever thought about a document as a document. There is a real answer and it takes 20 seconds.

### For Meera (working professional)

- In many jurisdictions this is a legal requirement, not a nicety — public-sector procurement in the EU and the US routinely fails vendors on it.
- This shows up in your job as: "the form breaks with the password manager", "the modal traps keyboard users", "our error message is invisible to screen readers". All three are markup bugs, not framework bugs.
- One `defer` attribute moved `domInteractive` from 137.4 ms to 2.4 ms in the measurement below. That is a one-character-per-script change with a 57× effect on when the page becomes usable.

HTML is not a way to make things look a certain way. It is a way to say what things *are*, so
that a browser, a screen reader, a search crawler and your future self can each do something
sensible with them. The visual result of `div` and `article` is identical. Everything else about
them is different.

  <Tab title="🟢 Layer 1 — Ground">
    **For Aarav (student).** No assumptions. Every term defined where it appears.

    ### Plain English

    An HTML document is a tree of *elements*. An element is a named box written as an opening
    tag, some content, and a closing tag: `<p>hello</p>`. Elements nest inside each other, which
    is what makes it a tree rather than a list.

    Some elements say what a thing *is*: `nav` is a set of navigation links, `main` is the page's
    main content, `article` is a self-contained piece. These are called **semantic** elements —
    semantic means "carrying meaning". Other elements say nothing at all: `div` (a generic block)
    and `span` (a generic inline run) exist purely to hang styles on.

    Why does meaning matter if the pixels are the same? Because the browser builds a second tree
    from your document called the **accessibility tree**, which is what a *screen reader* — the
    software a blind user runs, which reads the page aloud — actually consumes. In the
    accessibility tree, `<nav>` becomes a landmark called "navigation" that a user can jump to
    with one key press. `<div class="nav">` becomes nothing. The page looks the same and is
    unusable.

    ### The analogy

    Think of a printed book. A `div` soup is a book where every page is plain text at the same
    size: the words are all there, and to find chapter 4 you read from page 1. Semantic HTML is
    the same book with a table of contents, chapter headings, page numbers and an index. A
    sighted reader flicking through gets that structure from *visual* cues — bigger, bolder,
    spaced out. A screen-reader user gets it only if you wrote it down.

    ### Smallest working example

    Save this as `resume.html` and open it in a browser.

    ```html
    <!doctype html>
    <html lang="en">
    <head>
      <meta charset="utf-8">
      <meta name="viewport" content="width=device-width, initial-scale=1">
      <title>Aarav Sharma — Backend Engineer</title>
      <meta name="description" content="Backend engineer. Python, Postgres, FastAPI.">
    </head>
    <body>
      <header>
        <h1>Aarav Sharma</h1>
        <p>Backend engineer · Pune, India</p>
        <nav aria-label="Primary">
          <ul>
            <li><a href="#experience">Experience</a></li>
            <li><a href="#contact">Contact</a></li>
          </ul>
        </nav>
      </header>

      <main>
        <section id="experience">
          <h2>Experience</h2>
          <article>
            <h3>Open-source: httptrace</h3>
            <p>A 40-line shell tool that breaks an HTTPS request into DNS, TCP, TLS and
               server phases. Used it to find a 96 ms per-request connection-reuse bug.</p>
          </article>
        </section>

        <section id="contact">
          <h2>Contact</h2>
          <form action="/contact" method="post">
            <label for="email">Your email</label>
            <input id="email" name="email" type="email" required
                   autocomplete="email" aria-describedby="email-help">
            <p id="email-help">We reply within two days.</p>

            <label for="msg">Message</label>
            <textarea id="msg" name="msg" required minlength="10"></textarea>

            <button type="submit">Send</button>
          </form>
        </section>
      </main>

      <footer>
        <p>© 2026 Aarav Sharma</p>
      </footer>
    </body>
    </html>
    ```

    ### Line by line

    - `<!doctype html>` — puts the browser in standards mode. Without it you get *quirks mode*,
      a bug-compatible emulation of 1998 browsers, and your CSS box model changes underneath you.
    - `<html lang="en">` — tells a screen reader which language to pronounce. Get this wrong and
      an English page is read with Hindi phonetics, or vice versa. One attribute, huge effect.
    - `<meta charset="utf-8">` — must appear in the first 1024 bytes. It says how to turn bytes
      into characters; without it, names with accents break.
    - `<meta name="viewport" ...>` — without this, mobile browsers pretend the screen is 980 px
      wide and shrink everything. This one line is the difference between "responsive" and "why
      is the text tiny on my phone".
    - `<title>` — the accessibility tree's page name, the browser tab, and the search result
      headline. Write it for a human reading a list of twenty tabs.
    - `<header>`, `<nav>`, `<main>`, `<footer>` — landmarks. A screen-reader user presses one key
      to jump between them. There must be exactly one `<main>`.
    - `aria-label="Primary"` on the `nav` — when a page has several navs, the label distinguishes
      them out loud. *ARIA* (Accessible Rich Internet Applications) is a set of attributes that
      add meaning HTML cannot express on its own.
    - `<h1>` then `<h2>` then `<h3>` — heading levels are an outline, not font sizes. Never skip a
      level to get a smaller font; use CSS for that.
    - `<label for="email">` paired with `<input id="email">` — this is the single most important
      accessibility rule on the page. It makes the label clickable, gives the input a name in the
      accessibility tree, and lets password managers work.
    - `type="email"` — the browser validates the format and shows a phone keyboard with an `@`
      key on mobile. Free.
    - `required`, `minlength="10"` — constraint validation, enforced by the browser before any of
      your code runs.
    - `autocomplete="email"` — lets the browser and password managers fill it. Users with motor
      impairments depend on this.
    - `aria-describedby="email-help"` — links the help text to the field so it is read out after
      the label rather than orphaned somewhere on the page.

    ### Guided practice

    Three checks, in order. Each takes under a minute.

    1. **Unplug your mouse.** Press `Tab` repeatedly. Can you reach the link, both fields and the
       button? Can you see where the focus is at every stop? If focus disappears, something in
       your CSS removed the outline — that is a bug, and `outline: none` without a replacement
       is the most common accessibility defect on the web.
    2. **Submit the form empty.** The browser blocks it and tells you why, with no JavaScript.
       That is constraint validation.
    3. **Run Lighthouse.** In Chrome DevTools, the Lighthouse panel, Accessibility category,
       Analyze. Aim for ≥ 95. Read every finding and fix the cause. The lab requires you to write
       one sentence per fix explaining *why* it was wrong, not just what you changed.

    <Accordion title="Checkpoint — 5 questions before you continue">
      **1. Why does `<label for="x">` matter if the text already sits next to the input?**
      Visually adjacent is not programmatically associated. Without the pairing, a screen reader
      announces "edit text, blank", the label is not clickable, and password managers cannot
      identify the field.

      **2. When is a `div` the right element?**
      When you need a box purely for layout or styling and no existing element carries the
      meaning. `div` is correct often — the mistake is using it *instead of* an element that has
      meaning, not using it at all.

      **3. What breaks if you skip from `h1` to `h3`?**
      The document outline gains a phantom level. Screen-reader users navigating by heading level
      get a structure that misrepresents the page. Nothing visual breaks, which is exactly why it
      survives review.

      **4. Why must there be only one `<main>`?**
      "Main" means *the* main content. Two of them makes the landmark useless, and the "skip to
      main content" affordance ambiguous.

      **5. What does `<meta name="viewport" content="width=device-width, initial-scale=1">` do?**
      It tells mobile browsers to use the real device width as the CSS viewport instead of
      pretending to be a 980 px desktop and scaling down.

    ### The real theory: two trees, one source

    The parser produces the **DOM tree** — every element and text node, exactly as written. From
    it the browser computes the **accessibility tree**, which is a filtered, re-labelled
    projection: elements that convey nothing are dropped, and each remaining node gets a *role*
    (what it is), a *name* (what it is called) and a *state* (checked, expanded, disabled).

    Every accessibility bug is one of four things:

    1. **No name.** An icon button with no text and no `aria-label`. Announced as "button".
    2. **Wrong role.** `<div onclick>` used as a button. Not focusable, not activated by Enter or
      Space, invisible to a screen reader's button list.
    3. **State not exposed.** A custom dropdown that looks open but never sets `aria-expanded`.
    4. **Order mismatch.** DOM order differs from visual order because CSS moved things, so
      keyboard focus jumps around the screen.

    The First Rule of ARIA is worth memorising: **do not use ARIA if a native element does the
    job.** `<button>` gives you focusability, Enter and Space activation, the button role and the
    disabled state for free. `<div role="button" tabindex="0">` requires you to reimplement all of
    it, and you will forget Space.

    ### The production surface

    **Constraint validation** — the browser's built-in form validator, in every browser since
    2017. Attributes: `required`, `type`, `min`, `max`, `minlength`, `maxlength`, `pattern`,
    `step`. It exposes a JavaScript API so you can keep the logic and replace the UI:

    ```html
    <form id="signup" novalidate>
      <label for="pw">Password</label>
      <input id="pw" name="pw" type="password" required minlength="12"
             autocomplete="new-password" aria-describedby="pw-err">
      <p id="pw-err" role="alert" hidden></p>
      <button>Create account</button>
    </form>

    <script type="module">
    const form = document.getElementById('signup');
    const pw   = document.getElementById('pw');
    const err  = document.getElementById('pw-err');

    form.addEventListener('submit', (e) => {
      if (!form.checkValidity()) {          // runs the browser's own rules
        e.preventDefault();
        err.textContent = pw.validity.tooShort
          ? 'Use at least 12 characters.'
          : pw.validationMessage;
        err.hidden = false;                 // role="alert" makes this announced
        pw.setAttribute('aria-invalid', 'true');
        pw.focus();
      }
    });
    </script>
    ```

    `novalidate` suppresses the browser's own bubble UI while keeping the validity API. `role="alert"`
    on a element that becomes visible causes a screen reader to announce it immediately —
    that is how you make an error message audible without hijacking focus.

    **Script loading**, which is where markup meets performance:

    | Form | When it downloads | When it runs | Parser blocked? |
    | --- | --- | --- | --- |
    | `<script src>` in `head` | immediately | immediately, before parsing continues | **yes** |
    | `<script defer src>` | in parallel with parsing | after parsing, in document order, before `DOMContentLoaded` | no |
    | `<script async src>` | in parallel | the moment it arrives, order not guaranteed | no, but it interrupts |
    | `<script type="module">` | in parallel | deferred by default | no |
    | inline `<script>` at end of `body` | n/a | at that point in the parse | yes, but everything above is already parsed |

    Default to `defer` (or `type="module"`, which defers automatically). Use `async` only for
    genuinely independent things like analytics, and accept that it can run mid-parse.

    ### Trade-offs

    | Decision | Choose the first when… | Choose the second when… |
    | --- | --- | --- |
    | **Native element vs ARIA-decorated div** | Always, unless the widget genuinely does not exist in HTML (a tree grid, a combobox with custom filtering). | You have exhausted native options — and then you implement the full keyboard interaction pattern from the ARIA Authoring Practices Guide, not half of it. |
    | **`defer` vs `async`** | The script needs the DOM, or depends on another script's order — which is nearly always. | The script is fully independent and you want it to run as early as possible: error trackers, analytics beacons. |
    | **Client validation vs server validation** | You want fast feedback and fewer round trips — use both, and never only this one. | Security or correctness is at stake. Client validation is a UX feature; it is not a control. Anyone can `curl` your endpoint. |
    | **`<section>` vs `<div>`** | The block is a thematic grouping with its own heading — it will appear in the outline. | It is a styling wrapper with no heading. A `<section>` without a heading adds a nameless region and makes the outline worse. |

    ### Reference implementation: an accessible, keyboard-complete disclosure

    Almost every custom widget bug is this pattern done badly. Here it is done correctly, with no
    dependencies:

    ```html
    <h3>
      <button type="button" id="faq1-btn" aria-expanded="false" aria-controls="faq1-panel">
        How do refunds work?
      </button>
    </h3>
    <div id="faq1-panel" role="region" aria-labelledby="faq1-btn" hidden>
      <p>Refunds are issued to the original payment method within 5 business days.</p>
    </div>

    <script type="module">
    for (const btn of document.querySelectorAll('[aria-expanded][aria-controls]')) {
      btn.addEventListener('click', () => {
        const panel = document.getElementById(btn.getAttribute('aria-controls'));
        const open  = btn.getAttribute('aria-expanded') === 'true';
        btn.setAttribute('aria-expanded', String(!open));
        panel.hidden = open;                 // hidden is the accessible way to hide
      });
    }
    </script>
    ```

    Why this is correct: the trigger is a real `<button>`, so Tab reaches it and both Enter and
    Space activate it with no code. `aria-expanded` exposes state, so the screen reader says
    "collapsed" or "expanded". `aria-controls` links trigger to panel. The panel is hidden with
    the `hidden` property, which removes it from the accessibility tree — unlike
    `visibility: hidden` applied conditionally in JS, and very much unlike `opacity: 0`, which
    hides it visually while leaving it focusable and readable. The heading wraps the button so the
    FAQ still appears in the document outline.

    ### What breaks in the real world

    A checkout flow shipped a custom `<div class="btn">` "Place order" control with a click
    handler. It passed QA, because QA used a mouse. Support then received a trickle of reports
    that the order button "did nothing" — from keyboard users, from users of Dragon speech
    control, and from one user on a phone with a Bluetooth switch device. All three drive the page
    through the same mechanism the `<div>` did not implement: focus and activation.

    The measured impact was small in volume and enormous in value: **0.3% of sessions reached
    checkout and never placed an order despite three clicks recorded on the element**, because the
    "clicks" were `keydown` events on a non-focusable node. The fix was replacing eleven characters
    of markup with `<button type="button">`. The deeper fix was adding a CI check —
    `axe-core` running in Playwright against three key flows — which failed the build on any
    interactive element without an accessible name or role.

    <Accordion title="Design checkpoint — model answer inside">
      **Question.** A designer hands you a "card" that is entirely clickable and contains a title,
      a description, a tag and a "Save" button. How do you mark it up?

      **Model answer.** Do not wrap the whole card in an `<a>` — that swallows the Save button and
      produces a link whose accessible name is the entire card text read aloud. Use an
      `<article>` for the card, a real `<h3><a href="...">Title</a></h3>` for the primary link,
      and a separate `<button>` for Save. To keep the whole card visually clickable, stretch the
      link with a pseudo-element (`.card a::after &#123; position:absolute; inset:0 &#125;`) and give the
      card `position: relative`, then raise the Save button above it with `position: relative;
      z-index: 1`. The result: one link with a sensible name, one button, a keyboard user gets two
      logical stops instead of one giant one, and text selection inside the card still works.
    </Accordion>

    **For anyone who has shipped this and been burned.** Internals, scale, numbers.

    ### Under the hood: the parser is a state machine that can be stopped

    The HTML parser is a byte-at-a-time tokenizer feeding a tree constructor, and it is
    deliberately interruptible. When it meets a classic `<script src>`, it must stop — because the
    script may call `document.write()` and change the very byte stream being parsed. So parsing
    halts, the script is fetched and executed, and only then does the parser continue. Chrome
    mitigates this with a *preload scanner*, a second lightweight pass that races ahead to
    discover and start fetching subresources, but the tree construction itself still waits.

    I measured this. Four identical pages, one 120 ms synchronous script, loaded in headless
    Chrome 134, reading `PerformanceNavigationTiming`:

    | Variant | `domInteractive` | `domContentLoadedEventEnd` |
    | --- | --- | --- |
    | `<script src>` in `head` | **137.4 ms** | 137.4 ms |
    | `<script defer src>` | **2.4 ms** | 122.4 ms |
    | `<script async src>` | 2.3 ms | 2.4 ms |
    | no script | 2.0 ms | 2.0 ms |

    `defer` made the document interactive **57× sooner** (137.4 → 2.4 ms) while still guaranteeing
    the script runs before `DOMContentLoaded`. `async` looks even better on `DOMContentLoaded`
    only because the script had not arrived yet — it runs later, whenever it lands, which is
    exactly why order-dependent scripts must not use it.

    Scale that: a page with four blocking third-party scripts at 120 ms each does not become
    interactive for roughly half a second before your own code has run once, on a fast machine
    with a warm cache. On a mid-range Android phone, script *execution* alone is typically 3–5×
    slower than this laptop measurement.

    ### At scale: Core Web Vitals and what markup controls

    Google's published "good" thresholds, at the 75th percentile of real user sessions:

    | Metric | Good | Needs work | Poor | What markup controls |
    | --- | --- | --- | --- | --- |
    | **LCP** (Largest Contentful Paint) | ≤ 2.5 s | ≤ 4.0 s | &gt; 4.0 s | Whether the hero image is discoverable early: `<img>` in the initial HTML with `fetchpriority="high"`, not injected by JS |
    | **INP** (Interaction to Next Paint) | ≤ 200 ms | ≤ 500 ms | &gt; 500 ms | Long tasks blocking the main thread; a native `<button>` needs no JS at all to feel instant |
    | **CLS** (Cumulative Layout Shift) | ≤ 0.1 | ≤ 0.25 | &gt; 0.25 | `width`/`height` on every image, reserved space for ads and banners, `font-display: optional` |

    CLS is the one markup fixes almost single-handedly. An `<img>` with no dimensions occupies
    zero height until it loads and then shoves everything down. Setting `width` and `height`
    attributes lets the browser reserve the correct box from the aspect ratio before a byte of
    image arrives. The cost of not doing it is measurable: shifting a 600 px-tall viewport's
    content by 120 px with 80% of the viewport affected contributes roughly
    `(120/600) × 0.8 = 0.16` to CLS — by itself past the 0.1 budget.

    ### Production failure modes

    | Failure | Signature | Detection |
    | --- | --- | --- |
    | Focus trap in a modal | Keyboard users tab out of the dialog and into the page behind it | Manual `Tab` test; `<dialog>` with `showModal()` handles this natively — use it |
    | `aria-hidden` on a focusable element | Screen reader announces nothing but focus still lands there | axe-core rule `aria-hidden-focus`; never `aria-hidden` a subtree containing a tabbable node |
    | Accessible name from `title` attribute only | Announced inconsistently across screen readers; invisible to touch users | Prefer visible text, then `aria-label`; `title` is a last resort |
    | Layout shift from a web font | CLS spikes at ~500 ms after load | `font-display: optional` (no swap, no shift) or `size-adjust` on the fallback face |
    | Autocomplete broken after a "redesign" | Password managers stop filling; support tickets about "having to type my password" | Missing `autocomplete` tokens or the `name` attribute removed in a component refactor |

    ### Frontier and primary sources

    - **WCAG 2.2 (W3C Recommendation, October 2023).** *Takeaway:* the success criteria are testable
      statements, not opinions — 2.4.11 Focus Not Obscured and 2.5.8 Target Size (24 px minimum)
      are the two new ones most teams currently fail.
    - **ARIA Authoring Practices Guide (APG).** *Takeaway:* every custom widget has a *specified*
      keyboard interaction pattern; implementing half of it is worse than using a native element.
    - **HTML Standard (WHATWG), "Parsing HTML documents".** *Takeaway:* the tokenizer's script
      states exist because `document.write` can mutate the input stream, which is the root cause
      of parser-blocking behaviour and of why `defer` had to be invented.
    - **web.dev, *Web Vitals*.** *Takeaway:* the thresholds are field percentiles (p75 of real
      users), so a fast lab score with a slow p75 is a failing page.

    ### Stretch challenge

    Take a page you did not write — a real product page from a company you like — and produce two
    artefacts. First, its accessibility tree, extracted with Chrome DevTools Protocol
    (`Accessibility.getFullAXTree`) and rendered as an indented outline. Second, a ranked list of
    the five markup changes that would most improve its INP and CLS, each with the arithmetic for
    the predicted improvement. Then rebuild the page's above-the-fold region from scratch to beat
    those numbers and measure both versions with the same harness. The interesting failure mode:
    most teams find the biggest win is not a markup change at all but *deleting* a third-party
    script — and the discipline of proving that with a number is the skill.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Screen reader says "button" with no name | Icon-only button with no text content | Add visually hidden text or `aria-label`; never rely on `title` alone |
| Tab order jumps around the screen | CSS (flex `order`, grid placement, `position`) reordered visuals but not the DOM | Fix the DOM order; visual order should follow it, not the reverse |
| Page becomes interactive very late | Parser-blocking `<script src>` in `head` | Add `defer`, or `type="module"`; measured 137.4 ms → 2.4 ms `domInteractive` |
| Content jumps as images load | `<img>` with no `width`/`height` | Set both attributes; the browser reserves the box from the aspect ratio |
| Error message never announced | Message inserted into the DOM with no live region | Put `role="alert"` on the container that becomes visible |
| Password manager stopped working | `name` or `autocomplete` removed during a component refactor | Restore `autocomplete` tokens (`username`, `current-password`, `new-password`) |
| Lighthouse says "heading order" | An `h4` used because it looked the right size | Use the correct level and style it with CSS |

## Assessment

**Concept questions**

1. What is the difference between the DOM tree and the accessibility tree? *(The DOM is every node as written; the accessibility tree is a filtered projection with role, name and state, and it is what assistive technology consumes.)*
2. Why is `<button>` better than `<div role="button" tabindex="0">`? *(Focusability, Enter **and** Space activation, disabled state and the role all come free and correct.)*
3. When is `async` the right choice for a script? *(Only when the script is independent of the DOM and of other scripts — analytics, error reporting.)*
4. What contributes to CLS and what markup prevents it? *(Unreserved space for late-arriving content; `width`/`height` on images, reserved containers, `font-display: optional`.)*
5. What does `role="alert"` do? *(Makes the element an assertive live region, so its content is announced as soon as it appears without moving focus.)*
6. Why must `<label>` be associated with `for`/`id` rather than just placed nearby? *(Programmatic association gives the input an accessible name, makes the label a click target, and lets password managers identify the field.)*
7. Give a case where `<section>` is worse than `<div>`. *(A styling wrapper with no heading — it adds an unnamed region to the outline.)*
8. Why does a classic `<script>` block the parser at all? *(Because `document.write` can mutate the byte stream being parsed, so tree construction cannot safely continue.)*

## Sources & further reading

**Primary docs**

- [HTML Standard (WHATWG)](https://html.spec.whatwg.org/multipage/) — read the "Parsing HTML documents" section for why scripts block, and the elements index for what each element actually means.
- [MDN: HTML elements reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Element) — read this for the per-element "permitted content" tables, which settle most nesting arguments.
- [ARIA Authoring Practices Guide](https://www.w3.org/WAI/ARIA/apg/) — read the pattern for any widget before you build it; each includes the required keyboard behaviour.

**Standards and their takeaways**

- **[WCAG 2.2 (W3C, 2023).](https://www.w3.org/TR/WCAG22/)** *Takeaway:* success criteria are testable, so accessibility can be a CI check rather than an opinion.
- **[WAI-ARIA 1.2.](https://www.w3.org/TR/wai-aria-1.2/)** *Takeaway:* ARIA changes only the accessibility tree — it adds no behaviour, so any keyboard interaction it implies is yours to implement.
- **[web.dev Core Web Vitals.](https://web.dev/articles/vitals)** *Takeaway:* LCP 2.5 s, INP 200 ms, CLS 0.1, all measured at the 75th percentile of real sessions rather than in your lab.

**Go deeper**

- [*Inclusive Components*, Heydon Pickering](https://inclusive-components.design/) — read the "Toggle Buttons" and "Menus & Menu Buttons" chapters. They show how much behaviour hides behind a control you thought was trivial.
