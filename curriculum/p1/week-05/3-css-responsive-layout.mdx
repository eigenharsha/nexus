## Why you should care

### For Aarav (student)

- Layout is where beginners lose the most hours. Two rules — the cascade and the box model — remove most of that loss permanently.
- A page that works on a phone is a hiring signal. Most student portfolios still overflow horizontally at 360 px, which is the width of a very common Android device.
- "Centre a div" is a real interview question because the three answers reveal exactly how much CSS you understand.

### For Meera (working professional)

- This shows up in your job as: "the table breaks on mobile", "the modal is behind the header", "the page jumps when the font loads". All three are cascade or stacking-context problems with deterministic answers.
- Design tokens as CSS custom properties are how you ship dark mode in an afternoon instead of a sprint, and how you stop hard-coded hex values spreading through a codebase.
- Layout cost is real and measurable: laying out 5,000 items took **80.2 ms with flex-wrap and 20.5 ms with Grid** in the measurement below. On a 60 fps budget of 16.7 ms per frame, one of those is a dropped frame and the other is five.

Three ideas carry all of CSS. **The cascade** decides which rule wins. **The box model** decides
how big a thing is. **The formatting context** — flow, flex, or grid — decides where it goes.
Everything else, including every framework you will ever use, is a convenience layer over those
three.

  <Tab title="🟢 Layer 1 — Ground">
    **For Aarav (student).** No assumptions. Every term defined where it appears.

    ### Plain English

    A CSS rule has a *selector* (which elements it applies to) and a *declaration block* (the
    properties to set). When two rules set the same property on the same element, one has to win.
    The browser decides in this order:

    1. **Origin and importance.** Your stylesheet beats the browser's defaults. A declaration
       marked `!important` beats a normal one. (`!important` is a bug report about your
       selectors; more on that in Layer 2.)
    2. **Specificity.** A three-part score: how many `#id` selectors, how many `.class`,
       `[attribute]` and `:pseudo-class` selectors, and how many element names. Compare left to
       right. `#nav .item a` scores 1-1-1 and beats `.item a`, which scores 0-1-1. One `#id`
       outranks any number of classes.
    3. **Source order.** If specificity ties, the rule written later wins.

    The **box model** is how the browser computes an element's size. Every box has *content*,
    then *padding* (space inside the border), then a *border*, then *margin* (space outside).
    By default `width` sets only the content width, so padding and border are *added on top* —
    which is why a 300 px box with 20 px padding is 340 px wide. That default is a historical
    mistake. Fix it once, globally, and never think about it again:

    ```css
    *, *::before, *::after { box-sizing: border-box; }
    ```

    Now `width: 300px` means the whole box is 300 px, padding and border included.

    ### The analogy

    Specificity is a courtroom. The element name is a witness, a class is a signed statement, an
    ID is a video recording. More video beats any amount of testimony. `!important` is shouting
    over the judge: it works, and everyone in the room now has to shout to be heard, and after
    three months nobody can hear anything at all.

    ### Smallest working example: centre a box three ways

    ```html
    <!doctype html>
    <html lang="en"><meta charset="utf-8"><title>Centring</title>
    <style>
      *, *::before, *::after { box-sizing: border-box; }
      body { font: 16px/1.5 system-ui, sans-serif; margin: 0; }
      section { height: 30vh; border: 2px solid #ccc; margin-bottom: 1rem; }
      .box { background: #ffec99; padding: 1rem; width: 200px; }

      /* 1. Flexbox: the container distributes its children */
      .flex { display: flex; justify-content: center; align-items: center; }

      /* 2. Grid: place the child in the middle cell */
      .grid { display: grid; place-items: center; }

      /* 3. Auto margins in flow: margin:auto absorbs leftover space */
      .auto { display: flow-root; }
      .auto .box { margin: 0 auto; }
    </style>
    <section class="flex"><div class="box">flex</div></section>
    <section class="grid"><div class="box">grid</div></section>
    <section class="auto"><div class="box">auto margins</div></section>
    </html>
    ```

    ### Line by line

    - `display: flex` turns the section into a **flex container**; its direct children become flex
      items laid out along one axis (by default, left to right).
    - `justify-content: center` centres along the *main* axis (horizontal here).
    - `align-items: center` centres along the *cross* axis (vertical here). Two properties,
      because a flex container thinks in two named axes, not in "x and y".
    - `display: grid` with `place-items: center` is shorthand for `align-items` plus
      `justify-items`, and centres in both directions with one line.
    - `margin: 0 auto` works because `auto` on a horizontal margin means "take all the leftover
      space". With `auto` on both sides, the leftovers split evenly. It centres horizontally only
      — vertical `margin: auto` does nothing in normal flow, which is precisely why "centre a div
      vertically" was hard for fifteen years.
    - `display: flow-root` creates a new block formatting context so the section contains its
      children's margins instead of letting them escape. This is the modern replacement for the
      `clearfix` hack.

    ### Guided practice: the mobile-first three-column layout

    60% is written for you. Fill in the two `TODO` lines.

    ```css
    /* Mobile first: write the small-screen layout with NO media query. */
    .cards {
      display: grid;
      gap: 1rem;
      grid-template-columns: 1fr;      /* one column on a phone */
      padding: 1rem;
    }

    /* Tablet and up */
    @media (min-width: 48rem) {        /* 48rem = 768px at the default 16px root */
      .cards { grid-template-columns: /* TODO: two equal columns */ ; }
    }

    /* Desktop and up */
    @media (min-width: 64rem) {        /* 1024px */
      .cards { grid-template-columns: /* TODO: three equal columns */ ; }
    }

    .card { background: #fff; border: 1px solid #e5e5e5; border-radius: .5rem; padding: 1rem; }
    ```

    Answers: `repeat(2, 1fr)` and `repeat(3, 1fr)`. `1fr` is one *fraction* of the leftover space,
    so three `1fr` columns split the row evenly whatever the width. Now try replacing all three
    rules with a single line that needs no media query at all:

    ```css
    .cards { grid-template-columns: repeat(auto-fit, minmax(16rem, 1fr)); }
    ```

    That says: as many columns as fit, each at least 16 rem wide, sharing leftover space equally.
    It is responsive with no breakpoints, and it is the single most useful line of CSS in this
    module.

    <Accordion title="Checkpoint — 5 questions before you continue">
      **1. `.card p` and `p.intro` both set colour. Which wins?**
      Both score 0-1-1, so source order decides: whichever is written later.

      **2. Why is `box-sizing: border-box` almost always right?**
      Because you size things by their outer box in a layout, and the default forces you to
      subtract padding and border in your head everywhere.

      **3. What is `1fr`?**
      One fraction of the free space remaining in a grid container after fixed-size tracks and
      gaps are removed.

      **4. Why mobile-first (`min-width`) rather than desktop-first (`max-width`)?**
      The base styles are the simplest case and every override adds complexity progressively. It
      also means an unsupported or failed media query leaves you with a usable narrow layout
      rather than a broken wide one.

      **5. `margin-top` on a child pushes the parent down instead. Why?**
      Margin collapsing: adjacent vertical margins in normal flow merge. `display: flow-root`,
      padding, or a border on the parent stops it. Flex and grid containers never collapse
      margins.

    **For Meera (working professional).** Trade-offs, real tools, real versions.

    ### The real theory: formatting contexts and stacking contexts

    Two independent hierarchies decide where a box lands.

    A **formatting context** decides layout. `display: flex` or `grid` on a parent changes the
    rules for its children: `float` stops applying, margins stop collapsing, `align-items` starts
    working. This is why pasted CSS "does nothing" — it belongs to a formatting context the
    element is not in.

    A **stacking context** decides paint order along z. It is created by, among others: `position`
    other than `static` *with* a `z-index`, `opacity` less than 1, `transform`, `filter`,
    `will-change`, `isolation: isolate`, and `position: fixed`. Inside a stacking context,
    `z-index` values only compete with siblings in that same context. This is the answer to the
    classic bug: **your `z-index: 9999` modal is behind the header because an ancestor with
    `opacity: 0.99` created a stacking context that caps it.** The fix is never a bigger number;
    it is moving the modal out of that ancestor — or using the top layer via `<dialog>`, which
    escapes stacking contexts entirely.

    ### The production surface: design tokens and dark mode

    Custom properties are inherited runtime variables, unlike Sass variables which are compile
    time. That makes theming a matter of re-declaring a few values on a selector:

    ```css
    :root {
      color-scheme: light dark;

      --space-1: .25rem;  --space-2: .5rem;  --space-3: 1rem;  --space-4: 2rem;
      --radius: .5rem;
      --font-sans: system-ui, -apple-system, "Segoe UI", Roboto, sans-serif;

      --bg:        #fffdf7;
      --surface:   #ffffff;
      --ink:       #1e1e1e;
      --ink-muted: #5b5b5b;
      --accent:    #1971c2;
      --danger:    #e03131;
      --border:    #e5e3dd;
    }

    @media (prefers-color-scheme: dark) {
      :root:not([data-theme="light"]) {
        --bg:        #1a1a19;
        --surface:   #232322;
        --ink:       #e8e6e3;
        --ink-muted: #a9a6a1;
        --accent:    #74c0fc;
        --danger:    #ff8787;
        --border:    #34342f;
      }
    }
    :root[data-theme="dark"] { /* same overrides, for the explicit toggle */ }

    body { background: var(--bg); color: var(--ink); font-family: var(--font-sans); }
    .card { background: var(--surface); border: 1px solid var(--border); border-radius: var(--radius); padding: var(--space-3); }
    ```

    Three properties of this that matter in a real codebase: the dark palette is defined by
    *re-declaring tokens*, never by writing a second set of component rules; the
    `:root:not([data-theme="light"])` guard means an explicit user choice beats the OS preference
    in both directions; and `color-scheme: light dark` makes form controls, scrollbars and the
    default canvas follow the theme without any work from you.

    ### Trade-offs

    | Decision | Choose the first when… | Choose the second when… |
    | --- | --- | --- |
    | **Flexbox vs Grid** | The content decides the sizes and you care about one axis: a toolbar, a row of chips, a card's internal stack. | The container decides the structure and you care about both axes: page layout, a card grid, anything where columns must line up across rows. |
    | **Media query vs intrinsic sizing** | You need a genuine layout *change* — sidebar becomes a drawer, table becomes cards. | You only need "as many as fit": `repeat(auto-fit, minmax(...))` and `clamp()` do it with no breakpoints and no viewport assumptions. |
    | **`rem` vs `px`** | Anything typographic or spatial — it scales with the user's font-size preference, which is an accessibility requirement. | Hairlines and borders where 1 device pixel is exactly what you mean. |
    | **CSS custom properties vs a preprocessor variable** | The value must change at runtime: themes, per-component overrides, values set from JS. | The value is a build-time constant you want inlined and dead-code-eliminated. |
    | **`transform`/`opacity` animation vs animating `width`/`top`** | Always, for anything that moves — these skip layout and paint and run on the compositor. | Never by choice; if a layout property must animate, animate it on a small, contained subtree. |

    ### Reference implementation: a responsive page shell with no duplicated markup

    ```css
    /* --- reset --- */
    *, *::before, *::after { box-sizing: border-box; }
    body { margin: 0; font: 100%/1.5 var(--font-sans); background: var(--bg); color: var(--ink); }
    img, svg, video { display: block; max-width: 100%; height: auto; }

    /* --- the shell: single column on mobile, sidebar from 60rem up --- */
    .shell {
      display: grid;
      grid-template-areas: "head" "main" "foot";
      grid-template-columns: 1fr;
      min-height: 100dvh;                 /* dvh accounts for mobile browser chrome */
    }
    @media (min-width: 60rem) {
      .shell {
        grid-template-areas: "head head" "side main" "foot foot";
        grid-template-columns: 16rem 1fr;
      }
    }
    .shell > header { grid-area: head; }
    .shell > nav    { grid-area: side; }
    .shell > main   { grid-area: main; min-width: 0; }   /* min-width:0 stops overflow */
    .shell > footer { grid-area: foot; }

    /* --- fluid type without breakpoints --- */
    h1 { font-size: clamp(1.75rem, 1.2rem + 2.5vw, 3rem); line-height: 1.15; }
    .prose { max-width: 68ch; }           /* ch = width of "0"; ~68 characters reads best */

    /* --- card grid, zero media queries --- */
    .cards { display: grid; gap: var(--space-3);
             grid-template-columns: repeat(auto-fit, minmax(16rem, 1fr)); }

    /* --- respect the user --- */
    @media (prefers-reduced-motion: reduce) {
      *, *::before, *::after { animation-duration: .01ms !important; transition-duration: .01ms !important; }
    }
    ```

    Two lines in there fix bugs you would otherwise spend an afternoon on. `min-width: 0` on the
    grid item: grid and flex items default to `min-width: auto`, meaning "at least as wide as my
    content", so one long unbreakable string (a URL, a code block, a wide table) blows the layout
    out and produces horizontal scroll. And `100dvh` instead of `100vh`: on mobile, `vh` is
    computed against the *largest* viewport, so a `100vh` element is taller than the visible area
    when the browser's URL bar is showing.

    ### What breaks in the real world

    A dashboard team shipped a table inside a CSS grid cell. It looked correct on every developer
    machine and produced horizontal page scroll on every phone. The table had a column of order
    IDs 28 characters long. The grid item's default `min-width: auto` meant the column could not
    shrink below its widest cell, so the grid track grew past the viewport and the whole page
    scrolled sideways — including the header, which was the visible symptom people reported.

    Two hours went into `overflow-x: hidden` on `body`, which hid the symptom and broke
    position-sticky. The actual fix was two declarations: `min-width: 0` on the grid item, and
    `overflow-x: auto` on a wrapper around the table so the *table* scrolls rather than the page.
    The general rule this produced, now in their review checklist: **wide content scrolls inside
    its own container; the page body never scrolls horizontally.**

    <Accordion title="Design checkpoint — model answer inside">
      **Question.** A designer gives you a card grid: 1 column on phones, 2 on tablets, 4 on wide
      desktops, and cards must never be narrower than 260 px. Do you use media queries?

      **Model answer.** No. `grid-template-columns: repeat(auto-fit, minmax(260px, 1fr))` satisfies
      all four requirements with one declaration, and it keeps working at container widths nobody
      specified — including inside a sidebar, which a viewport media query cannot know about. Add
      `gap` and you are done. Reach for a media query only when the layout must genuinely *change
      shape* rather than reflow: for example if at desktop the first card becomes a full-width
      hero. Then the query expresses a real design decision instead of restating arithmetic the
      browser can do.
    </Accordion>

  <Tab title="🟣 Layer 3 — Edge">
    **For anyone who has shipped this and been burned.** Internals, scale, numbers.

    ### Under the hood: the rendering pipeline

    Every visual change goes through some suffix of this pipeline:

    `style` → `layout` (geometry) → `paint` (fill pixels into layers) → `composite` (assemble layers on the GPU)

    Which properties you touch decides how much of it re-runs. Changing `width`, `top`, `margin`
    or `font-size` invalidates layout, so all four stages run. Changing `background-color` skips
    layout but repaints. Changing `transform` or `opacity` skips both and only recomposites,
    which is why every smooth animation on the web is built from those two properties.

    ### At scale: measured layout costs

    Chrome 134, headless, Apple Silicon, 5,000 items of identical markup and content, laid out
    three ways. Time measured as `appendChild` plus a forced layout read:

    | Layout method | Append | Append + forced layout |
    | --- | --- | --- |
    | `display: flex` with `flex-wrap: wrap` | 0.4 ms | **80.2 ms** |
    | `display: grid`, 10 columns | 0.5 ms | **20.5 ms** |
    | `float: left` | 0.4 ms | **18.2 ms** |

    Flex wrapping is **3.9× more expensive** than Grid at this size, because the wrap algorithm
    must measure each item to decide where lines break, whereas Grid's tracks are known up front.
    The frame budget at 60 fps is 16.7 ms, so all three drop frames — but flex drops five and grid
    drops one.

    Now the cost of *changing* something, on the already-laid-out containers:

    | Operation | Cost |
    | --- | --- |
    | Resize one child, force layout (flex, 5,000 children) | 2.8 ms |
    | Resize one child, force layout (grid, 5,000 children) | 3.3 ms |
    | Resize one child inside `contain: strict` | **2.3 ms** |
    | Write an inline style to 5,000 children, then force layout | **12.3 ms** |

    That last row is the one to remember: a loop that touches 5,000 elements' styles costs 12.3 ms
    before you have done anything else in the frame — 74% of the entire 16.7 ms budget.

    ### Layout thrash: the measured disaster

    Interleaving DOM *writes* and layout *reads* forces the browser to recompute layout
    synchronously on every read, because your read must reflect your write. Measured on the same
    machine, appending rows to a list:

    | Pattern | Rows | Time |
    | --- | --- | --- |
    | Append, then read `offsetHeight` **once** at the end | 50,000 | 230.7 ms |
    | Append and read `offsetHeight` **inside the loop** | 5,000 | **2,406.3 ms** |

    Ten times fewer rows, ten times *more* time — roughly a **100× per-row penalty**. The fix is
    always the same shape: batch all reads, then batch all writes. Do not alternate.

    ```js
    // Bad: read, write, read, write... each read forces a synchronous layout
    for (const el of items) { el.style.height = el.offsetHeight + 10 + 'px'; }

    // Good: read everything, then write everything
    const heights = items.map(el => el.offsetHeight);        // all reads
    items.forEach((el, i) => el.style.height = heights[i] + 10 + 'px');  // all writes
    ```

    ### Containment and `will-change` misuse

    `contain: strict` (shorthand for `size layout style paint`) promises the browser that nothing
    inside the element affects anything outside it, so a change inside cannot invalidate the rest
    of the page. In the measurement above it cut a forced relayout from 2.8 ms to 2.3 ms — an 18%
    saving on a synthetic case, and much larger on deep real pages. Its cost is that you must
    genuinely mean it: `contain: size` means the element's size does not depend on its contents,
    so if you are wrong the element collapses.

    `will-change: transform` promotes an element to its own compositor layer *ahead of time*. Used
    on one animating element it removes a paint. Used on a hundred elements it allocates a hundred
    GPU layers, and layer memory is roughly `width × height × 4 bytes` per layer — a full-screen
    layer on a 1440 × 900 display is about 5.2 MB. Twenty of those is 100 MB of GPU memory for an
    animation that has not started. The rule: apply `will-change` immediately before the animation
    and remove it after, or do not use it at all.

    ### Production failure modes

    | Failure | Signature | Detection |
    | --- | --- | --- |
    | Horizontal scroll on mobile only | Whole page shifts; header scrolls too | A grid/flex item without `min-width: 0` containing unbreakable content. Bisect with `* { outline: 1px solid red }` |
    | Modal behind the header | `z-index` increases have no effect | An ancestor with `transform`, `filter` or `opacity` created a stacking context. Use `<dialog>` + `showModal()` or portal the node to `body` |
    | CLS spike at ~500 ms | Text reflows once the web font arrives | `font-display: swap` with a metrically different fallback. Use `size-adjust` and `ascent-override` on the fallback, or `font-display: optional` |
    | Janky scroll on a long list | Frames over 16.7 ms during scroll only | Paint-heavy `box-shadow`/`filter` on many elements; or a scroll handler reading layout. Add `content-visibility: auto` to off-screen sections |
    | `100vh` element taller than the screen | Bottom bar hidden under mobile browser chrome | Use `100dvh`, or `svh`/`lvh` when you mean specifically the small or large viewport |

    ### Frontier and primary sources

    - **CSS Cascade Level 5 (W3C).** *Takeaway:* cascade layers (`@layer`) let you order whole
      buckets of CSS explicitly, which finally solves "our design system loses to a utility class"
      without specificity arms races.
    - **CSS Containment Level 2.** *Takeaway:* `contain` and `content-visibility: auto` let you
      tell the engine which subtrees it may skip, converting a whole-document layout into a
      viewport-sized one.
    - **CSS Grid Layout Level 2 (subgrid).** *Takeaway:* `subgrid` lets a child participate in its
      parent's tracks, which is the only correct way to align content *across* independent cards.
    - **Container Queries (CSS Containment Level 3).** *Takeaway:* components can respond to the
      space they are given rather than to the viewport, which removes the last legitimate reason
      most component libraries had for viewport media queries.

    ### Stretch challenge

    Build a measurement harness that renders the same 5,000-item list under six layout strategies
    — flex-wrap, grid, float, `columns`, absolute positioning, and grid with
    `content-visibility: auto` — and reports append time, forced-layout time, peak layer memory
    and frames dropped during a scripted scroll. Then predict, before running it, which will win
    at 500 items and which at 50,000, and write down why you were wrong. The genuinely open part:
    find a case where flex-wrap beats grid. It exists, and finding it teaches you more about the
    line-breaking algorithm than any article will.

    **Two:** add `min-width: 0` to your grid/flex content items and see how many mobile-overflow
    tickets disappear. **Three:** record a Performance trace during your app's worst interaction
    and look only at the Layout rows — if you find reads and writes alternating, batching them is
    usually a same-day fix worth a measured 10–100× on that path.
  </Accordion>
</AccordionGroup>

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Element is wider than you set | Default `box-sizing: content-box` adds padding and border | Global `box-sizing: border-box` |
| Horizontal scroll on mobile | Grid/flex item default `min-width: auto` plus unbreakable content | `min-width: 0` on the item; `overflow-x: auto` on a wrapper |
| `z-index` has no effect | An ancestor created a stacking context (`transform`, `opacity`, `filter`) | Move the node out, or use `<dialog>`/top layer |
| Parent does not grow with its child's margin | Margin collapsing in normal flow | `display: flow-root` on the parent, or use flex/grid |
| `100vh` overflows on iOS | `vh` uses the largest viewport, not the visible one | Use `100dvh` |
| Animation is janky | Animating `width`, `top` or `left` re-runs layout every frame | Animate `transform` and `opacity` only |
| Style changes are slow on long lists | Reads and writes interleaved, forcing sync layout | Batch reads then writes; measured 230.7 ms vs 2,406.3 ms |
| Dark mode needs a second stylesheet | Colours hard-coded in component rules | Put colours in custom properties; re-declare tokens under `prefers-color-scheme` |

## Assessment

**Concept questions**

1. Compute the specificity of `#app .list li a:hover`. *(1-2-2: one id; `.list` and `:hover` are two class-level; `li` and `a` are two elements.)*
2. Why does `margin: auto` centre horizontally but not vertically in normal flow? *(In block layout, `auto` horizontal margins absorb free space; vertical `auto` margins compute to zero. Flex and grid do not have this restriction.)*
3. Name three things that create a stacking context. *(`position` plus `z-index`, `opacity` &lt; 1, `transform`, `filter`, `will-change`, `isolation: isolate`.)*
4. When is `repeat(auto-fit, minmax(16rem, 1fr))` better than three media queries? *(Whenever the requirement is "as many as fit" — it also works inside containers of unknown width, which viewport queries cannot see.)*
5. Which properties can animate without triggering layout? *(`transform` and `opacity`; also `filter` on the compositor in most engines.)*
6. What does `contain: strict` promise, and what does it cost? *(That the subtree affects nothing outside it — size, layout, style and paint; the cost is that `contain: size` collapses the element if its size really does depend on content.)*
7. Why does `min-width: 0` fix grid overflow? *(Grid and flex items default to `min-width: auto`, which is the item's min-content size; setting 0 allows shrinking below it.)*
8. What is the frame budget at 60 fps, and what did 5,000 inline style writes cost against it? *(16.7 ms; the writes plus forced layout cost 12.3 ms, or 74% of the budget.)*

## Sources & further reading

**Primary docs**

- [MDN: CSS layout guides](https://developer.mozilla.org/en-US/docs/Learn/CSS/CSS_layout) — read the Flexbox and Grid guides end to end once; they are unusually good and cover the algorithms, not just the syntax.
- [CSS Grid Layout Level 1 (W3C)](https://www.w3.org/TR/css-grid-1/) — read §7 for track sizing, which explains why `1fr` and `minmax()` behave as they do.
- [web.dev: Rendering performance](https://web.dev/articles/rendering-performance) — read this for the pipeline diagram and the list of which properties trigger which stage.

**Specs and their takeaways**

- **[CSS Cascade Level 5.](https://www.w3.org/TR/css-cascade-5/)** *Takeaway:* `@layer` orders whole buckets of CSS explicitly, ending specificity arms races between design systems and utilities.
- **[CSS Containment Level 2.](https://www.w3.org/TR/css-contain-2/)** *Takeaway:* `content-visibility: auto` lets the engine skip layout and paint for off-screen subtrees, turning document-sized work into viewport-sized work.
- **[CSS Containment Level 3 (container queries).](https://www.w3.org/TR/css-contain-3/)** *Takeaway:* components sized by their container rather than the viewport are the correct unit of responsive design.

**Go deeper**

- [*Every Layout*, Heydon Pickering and Andy Bell](https://every-layout.dev/) — read the "Stack", "Sidebar" and "Grid" chapters. It reframes layout as a small set of composable primitives instead of a pile of breakpoints, and it will change how you write CSS permanently.
