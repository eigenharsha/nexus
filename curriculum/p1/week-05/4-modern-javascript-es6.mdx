    **New to all of this?** This layer is yours. No assumptions — every term is discovered the moment you need it.

    ### Plain English

    A *function* in JavaScript is a value: you can put it in a variable, pass it to another
    function, and return it. A function passed to another function so it can be run later is
    called a **callback**.

    Some work takes time — fetching a file, waiting for a timer. JavaScript never blocks waiting.
    Instead it hands the work to the browser (or Node), continues running your code, and later
    runs your callback with the result. That "later" is managed by the **event loop**: a loop that
    checks whether the call stack is empty and, if so, takes the next queued function and runs it.

    Three ways to express "do this after that finishes", in historical order:

    - **Callbacks.** Pass a function. Nesting three of them nests three levels deep, and error
      handling has to be repeated at every level.
    - **Promises.** A **promise** is an object representing a value that is not ready yet. It is
      in one of three states: *pending*, *fulfilled* (with a value) or *rejected* (with an error).
      You attach `.then(onFulfilled)` and `.catch(onRejected)`.
    - **`async`/`await`.** Syntax over promises. An `async` function always returns a promise.
      Inside it, `await somePromise` pauses *that function* until the promise settles, while the
      rest of the program keeps running. It reads like normal top-to-bottom code.

    Two more terms you need. `var` declares a variable scoped to the whole enclosing *function*.
    `let` and `const` are scoped to the enclosing *block* — the nearest pair of braces — which is
    almost always what you meant. `const` means the *binding* cannot be reassigned; the object it
    points at can still be mutated.

    ### The analogy

    A restaurant with one waiter. Callbacks are sticky notes: "when table 4's food is ready, do
    this" — and to handle a sequence you write a note that says to write another note. Promises
    are a numbered ticket: you hold something now that will become the food later, and you can
    hand the ticket to someone else. `async`/`await` is the waiter simply saying "I will wait
    here" — except the restaurant secretly rewrites that into tickets, so the waiter can serve
    every other table while "waiting".

    ### Smallest working example: the same program, three ways

    ```js
    // A stand-in for a slow network call. Returns a promise that resolves after `ms`.
    const fetchThing = (name, ms) =>
      new Promise((resolve) => setTimeout(() => resolve(`${name} done`), ms));

    // --- 1. Callbacks -------------------------------------------------
    function withCallbacks(done) {
      setTimeout(() => {
        console.log('a done');
        setTimeout(() => {
          console.log('b done');
          setTimeout(() => { console.log('c done'); done(); }, 90);
        }, 120);
      }, 100);
    }

    // --- 2. Promises --------------------------------------------------
    function withPromises() {
      return fetchThing('a', 100)
        .then((r) => { console.log(r); return fetchThing('b', 120); })
        .then((r) => { console.log(r); return fetchThing('c', 90); })
        .then((r) => console.log(r));
    }

    // --- 3. async/await -----------------------------------------------
    async function withAwait() {
      console.log(await fetchThing('a', 100));
      console.log(await fetchThing('b', 120));
      console.log(await fetchThing('c', 90));
    }
    ```

    All three take the same time, because all three wait for `a` before starting `b`. Only the
    readability changed. Now the version that is actually *faster*:

    ```js
    async function inParallel() {
      const [a, b, c] = await Promise.all([
        fetchThing('a', 100), fetchThing('b', 120), fetchThing('c', 90),
      ]);
      console.log(a, b, c);
    }
    ```

    Measured on Node 24, the three-task workload:

    ```
    sequential awaits : 315 ms
    Promise.all       : 122 ms
    ```

    **2.6× faster**, and 122 ms is exactly the slowest of the three tasks — which is the floor.
    The sequential version is not slow because `await` is slow; it is slow because you told it to
    wait for `a` before even *starting* `b`.

    ### Line by line

    - `new Promise((resolve) => ...)` — the constructor takes a function that receives `resolve`
      (and `reject`). You call `resolve(value)` when the work is done.
    - `` `${name} done` `` — a *template literal*. Backticks allow `${expression}` interpolation.
    - `.then((r) => ...)` — registers a callback for fulfilment and returns a *new* promise, which
      is what makes chaining work.
    - `return fetchThing('b', 120)` inside a `.then` — returning a promise from `then` makes the
      outer chain wait for it. Forgetting this `return` is the single most common promise bug:
      the chain continues immediately and your errors vanish.
    - `async function` — always returns a promise, even if the body returns a plain value.
    - `await` — legal only inside an `async` function or at the top level of an ES module. It
      pauses this function, not the thread.
    - `Promise.all([...])` — takes an array of promises, returns one promise for an array of
      results. It starts all of them immediately because the array is built before `all` is called.
    - `const [a, b, c] = ...` — *destructuring*: pull array elements into named variables.

    ### Guided practice: predict, then verify

    Write down your predicted output order, then run it. No peeking.

    ```js
    console.log('1 sync start');
    setTimeout(() => console.log('7 setTimeout 0'), 0);
    queueMicrotask(() => console.log('4 queueMicrotask'));
    Promise.resolve().then(() => console.log('5 promise.then'));
    (async () => {
      console.log('2 async fn body (sync until first await)');
      await null;
      console.log('6 after await');
    })();
    console.log('3 sync end');
    ```

    Verified output on Node 24.19:

    ```
    1 sync start
    2 async fn body (sync until first await)
    3 sync end
    4 queueMicrotask
    5 promise.then
    6 after await
    7 setTimeout 0
    ```

    Three rules explain all of it. **First:** the body of an `async` function runs *synchronously*
    until it hits the first `await` — which is why 2 comes before 3. **Second:** everything
    queued as a microtask (`queueMicrotask`, `.then`, the continuation after an `await`) runs in
    FIFO order once the synchronous script finishes. **Third:** `setTimeout` is a macrotask and
    gets its turn only after the microtask queue is completely empty — so 7 is last even though it
    was scheduled first with a delay of zero.

    <Accordion title="Checkpoint — 5 questions before you continue">
      **1. Why does `2` print before `3`?**
      An `async` function body executes synchronously up to its first `await`. Calling it does not
      defer anything by itself.

      **2. `setTimeout(fn, 0)` — why is it not "run immediately"?**
      It queues a macrotask. The event loop only takes a macrotask after the current script and
      the entire microtask queue have finished.

      **3. What is the difference between `const x = []` and `let x = []` for mutation?**
      None. `const` blocks reassignment of the binding, not mutation of the object. `x.push(1)`
      works with `const`.

      **4. What does an `async` function return if its body returns `42`?**
      A promise that fulfils with `42`. `async` always wraps the return value in a promise.

      **5. Why was `Promise.all` 122 ms and not 310 ms?**
      Because the three promises were created — and therefore started — before `Promise.all` ran.
      The total is the slowest of them, not their sum.
    </Accordion>

    ### The real theory: one loop, two queues, one checkpoint

    The runtime holds a **call stack**, a **microtask queue**, and a set of **macrotask** (task)
    sources: timers, I/O completions, DOM events, `MessageChannel`. The algorithm:

    1. Run the current task to completion — JavaScript never pre-empts a running function.
    2. Reach a **microtask checkpoint**: drain the microtask queue *entirely*, including
       microtasks enqueued while draining.
    3. In a browser, if it is time, run rendering (style, layout, paint) — this is where
       `requestAnimationFrame` callbacks fire, *before* layout.
    4. Take exactly one macrotask. Go to 1.

    Two consequences that show up in real bugs. An infinite chain of microtasks starves the
    macrotask queue forever, and because step 3 never runs, the tab freezes with no error. And
    `await` inside a loop yields between iterations, so a `for` loop of a million `await null`s is
    a million microtask checkpoints and is dramatically slower than the synchronous version.

    Here is a harder ordering case, verified on Node 24.19:

    ```js
    const out = [];
    setTimeout(() => { out.push('T1'); Promise.resolve().then(() => out.push('T1-micro')); }, 0);
    setTimeout(() => { out.push('T2'); }, 0);
    Promise.resolve().then(() => { out.push('P1'); return Promise.resolve(); })
                     .then(() => out.push('P2'));
    (async () => { out.push('A-sync'); await Promise.resolve(); out.push('A-after-await'); })();
    out.push('MAIN');
    setTimeout(() => console.log(out.join(' -> ')), 20);
    ```

    Actual output:

    ```
    A-sync -> MAIN -> P1 -> A-after-await -> P2 -> T1 -> T1-micro -> T2
    ```

    The subtle part is `P2` landing *after* `A-after-await` even though `P1` was queued first.
    Returning a promise from `.then` costs two extra microtask ticks — the runtime must adopt the
    returned thenable, which takes one tick to call its `then` and another to resolve. And
    `T1-micro` runs between `T1` and `T2`, because the microtask queue is drained after *each*
    macrotask, not after all of them.

    ### The production surface

    | Combinator | Settles when | Rejects when | Use it for |
    | --- | --- | --- | --- |
    | `Promise.all` | all fulfil | **any** rejects, immediately | you need every result; partial data is useless |
    | `Promise.allSettled` | all settle | never | dashboards, fan-out where one dead widget must not kill the page |
    | `Promise.race` | first settles | first *settles* as a rejection | timeouts, first-response-wins |
    | `Promise.any` | first fulfils | only if **all** reject (`AggregateError`) | mirrors, fallbacks |

    Measured on Node 24 with three tasks of 100, 120 and 90 ms:

    ```
    sequential awaits : 315 ms
    Promise.all       : 122 ms
    Promise.allSettled: 102 ms   (fulfilled, rejected, fulfilled)
    Promise.race      :  93 ms
    ```

    `race` returns at 93 ms — the fastest task — and the other two keep running. That matters:
    **`race` does not cancel the losers.** For real cancellation you need `AbortController`:

    ```js
    async function fetchWithTimeout(url, ms = 3000) {
      const ac = new AbortController();
      const timer = setTimeout(() => ac.abort(), ms);
      try {
        const res = await fetch(url, { signal: ac.signal });
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return await res.json();
      } finally {
        clearTimeout(timer);          // always runs, success or failure
      }
    }
    ```

    Measured: an abort scheduled at 50 ms against a 500 ms task rejected at **51 ms** with
    `AbortError`. `AbortSignal.timeout(ms)` is the built-in shorthand, and `AbortSignal.any([...])`
    combines several signals — a per-request timeout plus a component-unmount signal, for example.

    ### Trade-offs

    | Decision | Choose the first when… | Choose the second when… |
    | --- | --- | --- |
    | **`Promise.all` vs `allSettled`** | Every result is required; a partial answer would be wrong or misleading. | The page degrades gracefully — render what returned, show an error state for what did not. |
    | **`race` vs `AbortController`** | You only need the value and the loser is cheap to let finish. | The loser costs money, holds a connection, or would write stale data. Cancel it. |
    | **Sequential `await` vs `Promise.all`** | Step N genuinely needs step N−1's result. | The calls are independent — and if they are, the sequential version is a measured 2.6× bug. |
    | **`for await...of` vs `Promise.all`** | You need backpressure — a stream, or an API that will rate-limit you. | The set is small and bounded and you want maximum concurrency. |
    | **ESM (`import`) vs CommonJS (`require`)** | New code, browsers, tree-shaking, top-level `await`. | You are inside an existing CJS codebase; mixing the two costs more than it saves. |

    ### Reference implementation: a concurrency-limited mapper

    `Promise.all` over 5,000 URLs opens 5,000 sockets and gets you rate-limited. This is the
    utility every codebase eventually writes:

    ```js
    /**
     * Run `fn` over `items` with at most `limit` in flight.
     * Preserves input order in the result. Never rejects early —
     * returns allSettled-shaped entries so one failure cannot lose the rest.
     */
    export async function mapLimit(items, limit, fn, { signal } = {}) {
      const results = new Array(items.length);
      let next = 0;

      async function worker() {
        while (true) {
          if (signal?.aborted) throw signal.reason ?? new DOMException('Aborted', 'AbortError');
          const i = next++;
          if (i >= items.length) return;
          try {
            results[i] = { status: 'fulfilled', value: await fn(items[i], i, signal) };
          } catch (err) {
            results[i] = { status: 'rejected', reason: err };
          }
        }
      }

      const n = Math.max(1, Math.min(limit, items.length));
      await Promise.all(Array.from({ length: n }, worker));
      return results;
    }
    ```

    Why it is shaped this way: a shared `next` index is safe because JavaScript is single-threaded
    — there is no interleaving between `next++` reading and writing. Each worker loops rather than
    recursing, so a 100,000-item list does not build a 100,000-deep chain. Errors are captured per
    item rather than thrown, so one bad URL does not discard 4,999 good results. And the `signal`
    is checked at the top of each iteration, so an abort stops scheduling new work immediately
    instead of after everything drains.

    ### What breaks in the real world

    A search box called the API on every keystroke and rendered whatever came back. It worked in
    development, where the API was 4 ms away. In production, results for "lap" would arrive
    *after* results for "laptop" and overwrite them, so the user saw stale results roughly one
    time in twenty — reported as "search is random".

    The team's first fix was a 300 ms debounce. That reduced the frequency but did not remove the
    race, because two requests can still be in flight when typing pauses briefly and resumes. The
    real fix is two lines: keep the controller for the in-flight request and abort it before
    starting the next one.

    ```js
    let inFlight = null;
    input.addEventListener('input', debounce(async (e) => {
      inFlight?.abort();                              // cancel the previous search
      inFlight = new AbortController();
      try {
        const data = await fetchWithSignal(`/api/search?q=${encodeURIComponent(e.target.value)}`,
                                           inFlight.signal);
        render(data);                                 // only the newest request reaches this line
      } catch (err) {
        if (err.name !== 'AbortError') showError(err); // aborts are expected, not errors
      }
    }, 250));
    ```

    The lesson generalises: **debounce reduces load; cancellation guarantees correctness.** They
    are not substitutes, and shipping only the first one hides the bug instead of fixing it.

    <Accordion title="Design checkpoint — model answer inside">
      **Question.** A dashboard loads six independent widgets from six endpoints. One endpoint is
      flaky and occasionally takes 30 seconds. How do you load the page?

      **Model answer.** `Promise.allSettled` over the six, each wrapped with its own
      `AbortSignal.timeout(2000)`. Render each widget as its result settles rather than waiting for
      the set — so the page is useful at the speed of the fastest endpoint, not the slowest. Widgets
      whose promise rejected render an error state with a retry button that starts a fresh request.
      `Promise.all` would be wrong twice over: one flaky endpoint would reject the whole batch and
      blank the dashboard, and even on the happy path the user would stare at a spinner for 30
      seconds to see five widgets that were ready in 80 ms.
    </Accordion>

  <Tab title="🟣 Layer 3 — Edge">
    **For anyone who has shipped this and been burned.** Internals, scale, numbers.

    ### Under the hood: `await` is a state machine, not a pause

    An `async` function is compiled into a resumable state machine. Each `await` splits the
    function at that point; the continuation is stored as a closure and registered as a *reaction*
    on the awaited promise. When the promise settles, that reaction is enqueued as a **microtask**,
    and the function resumes with its local variables restored from the closure. Nothing blocks:
    the stack unwinds completely at each `await` and is rebuilt on resume.

    This is exactly Python's coroutine model from Week 4 — `await` yields to a scheduler, the
    scheduler resumes you when the future is ready. Two differences worth knowing. JavaScript has
    *one* loop per agent (per tab or per worker), with no equivalent of Python's separate loop
    objects. And JavaScript's microtask checkpoint is a language-level guarantee that runs between
    every macrotask, whereas Python's `asyncio` has no equivalent priority tier — an
    `asyncio.Future` callback is scheduled as a regular loop callback with `call_soon`.

    A useful consequence: `await` on an already-resolved value still costs a microtask tick.
    `await null` in a hot loop of 1,000,000 iterations is 1,000,000 checkpoint round trips. If you
    are awaiting inside a tight loop over data you already have, you have converted a synchronous
    loop into a scheduler stress test.

    ### At scale: the numbers that decide architecture

    From the measured runs on Node 24.19 (three tasks: 100, 120, 90 ms):

    | Pattern | Wall clock | What it tells you |
    | --- | --- | --- |
    | Sequential `await` | 315 ms | The sum. You serialised independent work. |
    | `Promise.all` | 122 ms | The max. The theoretical floor for parallel I/O. |
    | `Promise.allSettled` | 102 ms | The max of the survivors; a rejection settles instantly. |
    | `Promise.race` | 93 ms | The min — and the other two are still running. |
    | `AbortController` at 50 ms | rejects at 51 ms | Cancellation latency is one macrotask, not one task duration. |

    Now the failure mode nobody measures: **an unbounded `Promise.all`**. Mapping
    `Promise.all(urls.map(fetch))` over 5,000 URLs does not create 5,000 parallel connections —
    the browser caps at 6 per origin (HTTP/1.1) or roughly 100 streams (HTTP/2), and Node's default
    agent has its own pool. What you actually create is 5,000 pending promise objects, 5,000
    closures, and a queue the runtime must service. Memory grows linearly and the *last* request
    finishes after everything ahead of it, so p99 latency for any individual item becomes the total
    batch time. `mapLimit(items, 8, fn)` keeps memory flat and p99 proportional to the queue depth
    you chose deliberately.

    ### Closures and the leaks they cause

    A closure keeps its entire enclosing scope alive, not just the variables it reads — engines
    optimise this, but not reliably across all shapes. The classic browser leak:

    ```js
    function attach(node) {
      const bigData = new Array(1_000_000).fill('x');   // ~8 MB of pointers
      node.addEventListener('click', () => console.log('clicked'));  // captures scope
    }
    ```

    The handler never touches `bigData`, but it closes over the same scope, and the listener holds
    a reference from the DOM node. Remove the node and the listener is still registered, so the
    scope — and `bigData` — stays reachable. Detach the listener, use `{ signal }` on
    `addEventListener` so an `AbortController` removes it, or use a `WeakRef`. The diagnostic is a
    heap snapshot in DevTools with the "Detached" filter: detached DOM nodes with retained size
    are always this bug.

    ### Production failure modes

    | Failure | Signature | Detection |
    | --- | --- | --- |
    | Missing `return` in a `.then` | Errors silently swallowed; the chain continues too early | Enable `no-floating-promises` in typescript-eslint; every promise must be awaited, returned or explicitly voided |
    | Unhandled rejection kills the process | Node exits with code 1 and a stack you cannot place | `process.on('unhandledRejection')` to log; but the real fix is attaching handlers at creation |
    | `forEach` with an `async` callback | The loop "finishes" instantly; nothing is awaited | `forEach` ignores the returned promise. Use `for...of` with `await`, or `Promise.all(map(...))` |
    | Microtask starvation | Tab frozen, no error, CPU at 100% | A promise chain that re-enqueues itself. Rendering never runs because step 3 of the loop is never reached |
    | Stale render after fast typing | Results flicker between old and new | No cancellation. `AbortController` per request |
    | `setInterval` drift and pile-up | Handlers overlap when the callback is slower than the interval | Use a self-scheduling `setTimeout` after the work completes, not `setInterval` |

    ### Frontier and primary sources

    - **ECMA-262, *Jobs and Job Queues* (§9.5).** *Takeaway:* the microtask queue is specified by
      the language, not the host, which is why promise ordering is identical in Node, browsers and
      Deno while timer ordering is not.
    - **HTML Standard, *Event loops* (§8.1.7).** *Takeaway:* rendering is a step *inside* the loop,
      between macrotasks, which is why blocking the main thread and starving microtasks both
      produce a frozen frame.
    - **WHATWG DOM, *AbortController*.** *Takeaway:* cancellation is modelled as a signal you pass
      *into* an operation, not as a method on a promise — because a promise is a result, not a task.
    - **V8 blog, "Faster async functions and promises" (2018).** *Takeaway:* `await` was respecified
      to save two microtask ticks per await, which is why old blog posts' predicted orderings are
      now wrong.

JavaScript runs one thing at a time on one thread. Everything asynchronous is a promise to run a
function *later*, and "later" has exactly two priorities: microtasks, which run as soon as the
current script finishes and before anything else, and macrotasks, which get one turn each after
all microtasks are done. Every ordering puzzle you will ever be shown is that one rule.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Loop completes instantly, nothing awaited | `array.forEach(async ...)` — `forEach` discards the returned promise | `for (const x of arr) await f(x)` or `await Promise.all(arr.map(f))` |
| Errors disappear from a promise chain | Missing `return` before a promise inside `.then` | Return it, or use `async`/`await` where the mistake is impossible |
| Three independent calls take the sum of their times | Sequential `await` on independent work | `Promise.all`; measured 315 ms → 122 ms |
| One dead endpoint blanks the whole page | `Promise.all` on independent widgets | `Promise.allSettled` plus per-widget error states |
| Search shows results for an older query | No cancellation; only debouncing | `AbortController`, aborting the previous request |
| Tab frozen, no error, 100% CPU | Microtask starvation — a self-re-enqueueing promise chain | Break the chain with `setTimeout(…, 0)` so macrotasks and rendering get a turn |
| Memory grows on every route change | Listeners keep closures alive on detached nodes | `addEventListener(…, { signal })` and abort on teardown |
| `this` is undefined inside a callback | A regular `function` has its own `this`; arrow functions inherit it | Use an arrow function, or bind explicitly |

## Assessment

**Concept questions**

1. Why does the body of an `async` function run before the next synchronous statement? *(It executes synchronously until the first `await`.)*
2. What is the difference between the microtask and macrotask queues? *(Microtasks are drained entirely at every checkpoint; exactly one macrotask runs per loop turn.)*
3. `Promise.race` resolves. What happens to the losers? *(Nothing — they keep running. `race` is not cancellation.)*
4. When does `Promise.any` reject? *(Only when every input rejects, with an `AggregateError`.)*
5. Why is `await` in a tight loop over in-memory data a bad idea? *(Each `await` costs a microtask checkpoint; a million iterations is a million scheduler round trips.)*
6. What does `const` actually prevent? *(Reassignment of the binding, not mutation of the referenced object.)*
7. Why can a frozen tab show no error? *(Microtask starvation: the loop never reaches the rendering step or the macrotask queue, and nothing throws.)*
8. How do you cancel an in-flight `fetch`? *(Pass an `AbortSignal`; call `abort()`. Measured cancellation latency: 51 ms for an abort scheduled at 50 ms.)*

**Coding challenge.** Implement `mapLimit(items, limit, fn, { signal })` from scratch. Hidden tests: results in input order; concurrency never exceeds `limit` (verified with a counter); one rejection does not lose other results; abort mid-flight leaves no pending work; 100,000 items do not blow the stack.

## Sources & further reading

**Primary docs**

- [MDN: Using promises](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Using_promises) — read the "Common mistakes" section; it is short and every item is a bug you will otherwise ship.
- [MDN: AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController) — read this for `AbortSignal.timeout()` and `AbortSignal.any()`, which remove most hand-rolled timeout code.
- [HTML Standard §8.1.7, Event loops](https://html.spec.whatwg.org/multipage/webappapis.html#event-loops) — read this once for the authoritative loop algorithm, including where rendering fits.

**Specs and their takeaways**

- **[ECMA-262 §9.5, Jobs.](https://tc39.es/ecma262/)** *Takeaway:* promise ordering is a language guarantee, so it is identical across every host; timer ordering is not, so it is not.
- **[V8, "Faster async functions and promises."](https://v8.dev/blog/fast-async)** *Takeaway:* `await` was made two microtask ticks cheaper in 2018, which invalidated a lot of widely-copied ordering explanations.
- **[WHATWG DOM, AbortController.](https://dom.spec.whatwg.org/)** *Takeaway:* cancellation belongs to the operation, not to the promise, which is why there is no `promise.cancel()` and never will be.

**Go deeper**

- Jake Archibald, *In the Loop* (JSConf Asia 2018) — 35 minutes, and it makes the loop, microtasks and `requestAnimationFrame` visible in a way no article manages. Watch it before the assessment.
