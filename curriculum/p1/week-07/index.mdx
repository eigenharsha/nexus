## Outcome

<Note>
By Sunday you have designed a normalized e-commerce schema, seeded it with a million rows, and
answered twenty analytical questions in SQL — each with an `EXPLAIN ANALYZE` plan you can read and
explain.
</Note>

Week 6 gave you an API. This week is what sits behind it. Almost every performance problem and
almost every "the numbers are wrong" incident you will meet in your career starts here: in a schema
that permitted bad data, or a query whose grain was not what the author thought.

The week's spine is one dataset — 200,000 customers, 20,000 products, 1,000,000 orders, 3,000,000
order items — that every module measures against. All the numbers in these pages came from it.

## The numbers this week produced

Every one of these was **measured** on the week's dataset — a real PostgreSQL 16.14 container on
an Apple Silicon laptop, not a modelled figure — and each is explained in the module that produced
it. The reproduction log, including the `EXPLAIN` output and the seed script, is committed at
`evidence/phase-1-w05-08-measurements.md`; see [About the numbers](/start/about-the-numbers) for what "measured" commits us to. Your absolute milliseconds will differ
with disk and cache state; the plan shapes and the ratios should not.

| Fact | Number | Module |
| --- | --- | --- |
| Fan-out join inflating a revenue `SUM` | 3.0× (507,507,500 → 1,522,492,500) | M3 |
| Top-N-per-group: window function versus correlated subquery | 330 ms versus cancelled at 5 min 07 s | M4 |
| Aggregating in SQL versus pulling into Pandas | 127 ms versus 1,826 ms (14.4×) | M4 |
| Bulk load: `COPY` versus auto-committed `INSERT` | 295 ms versus 83,773 ms (284×) | M5 |
| MVCC bloat from five full-table updates | 48 MB → 284 MB, 999,959 dead tuples | M5 |
| Backfilling a column on 1M rows in one statement | 62.7 s | M2 |
| `CREATE INDEX CONCURRENTLY` overhead | +11% wall time, no write lock | M2 |

## What you should be able to say out loud by Sunday

1. "That is an update anomaly — the city is stored per order instead of per customer."
2. "The `SUM` is wrong because the join changed the grain; `count(*)` went from 5,002 to 15,000."
3. "`NOT IN` with a nullable subquery returns zero rows; use `NOT EXISTS`."
4. "Compute the rank in a CTE — you cannot filter on a window function in `WHERE`."
5. "The table is 6× its data because of dead tuples; `VACUUM` makes the space reusable but does not shrink the file."

## Prerequisites check

You need Docker running and about 2 GB of free disk for the seeded dataset. You should be
comfortable in a shell (`P1-W02-M1`) and able to write a Python script that reads a CSV
(`P1-W03-M3`). No prior SQL is assumed — module 3 starts from `SELECT`.

## What this week feeds

Week 8 takes this schema and makes it correct under concurrency and fast under load: the same
tables, the same queries, with transactions, isolation levels, indexes and an ORM on top. The
`EXPLAIN` reading you learn in module 3 is the tool you use for every measurement in `P1-W08-M3`.
Week 15 revisits the analytical queries as incremental pipelines.
