**For Aarav (student).** No assumptions. Every term is defined where it first appears.

### The one idea

`cc hello.c -o hello` looks like one command. It is four programs run back to back, and each one hands a file to the next. You can stop the chain at any point and read what came out. Once you have done that once, "compiler errors" and "linker errors" stop being the same thing in your head — and they are not the same thing, which is why you can fix them.

### The analogy

Think of publishing a book.

1. **Preprocess** — the editor pastes in every chapter you referenced by name. Your 3-page draft becomes a 500-page manuscript because you wrote "see the appendix" and the appendix got pasted in.
2. **Compile** — a translator turns the English manuscript into another language. Still text, still readable, just not by you.
3. **Assemble** — a typesetter turns the translated text into printing plates. Now it is machine-shaped, not human-shaped.
4. **Link** — the binder gathers your plates plus the plates for the standard chapters everyone shares (the index, the glossary), checks that every "see page X" actually points somewhere, and produces one physical book.

If a chapter you referenced does not exist, the *binder* is the one who notices, not the translator. That is exactly why "undefined reference" is a linker error and not a compiler error.

### The vocabulary, defined

- **Source file** — the `.c` file you typed.
- **Preprocessor** — a text-substitution program that runs before the compiler. It handles every line starting with `#`: `#include` pastes a file in, `#define` defines a text replacement, `#ifdef` includes or skips a block.
- **Header file** (`.h`) — a file containing *declarations*: promises that a function or variable exists somewhere, with a given name and shape. It usually contains no actual code.
- **Declaration** — "a function called `printf` exists and takes these arguments." A promise.
- **Definition** — the actual body of the function. The delivery on the promise.
- **Compiler** — turns preprocessed C into **assembly**, a human-readable text form of the machine's instruction set.
- **Assembler** — turns assembly text into an **object file** (`.o`): real machine code, plus a list of names.
- **Symbol** — a name in an object file. Either **defined** here (this file contains the code) or **undefined** (this file uses it, someone else must supply it).
- **Linker** — stitches object files and libraries together, resolves every undefined symbol to a definition, and writes the final **executable**.
- **Library** — a bundle of pre-compiled object files. `libSystem` on macOS, `libc` on Linux.
- **Process** — a running instance of an executable, with its own private view of memory.

### Smallest working example

```c
/* hello.c */
#include <stdio.h>
#define GREETING "hello"
int main(void) { printf("%s, world\n", GREETING); return 0; }
```

Now run each stage by hand and look at what falls out:

```bash
cc -E hello.c -o hello.i    # 1. preprocess only
cc -S hello.c -o hello.s    # 2. compile to assembly
cc -c hello.c -o hello.o    # 3. assemble to an object file
cc    hello.o -o hello      # 4. link
./hello
```

Measured on this machine (Apple clang 15.0.0, macOS 15, arm64):

| Stage | File | Lines | Bytes |
|---|---|---|---|
| source | `hello.c` | 3 | 105 |
| preprocessed | `hello.i` | 557 | 25,076 |
| assembly | `hello.s` | 38 | 1,088 |
| object | `hello.o` | — | 808 |
| executable | `hello` | — | 33,432 |

Your three-line file became 557 lines after preprocessing. `cc -E -H hello.c` shows why: **37 header files** were pulled in, transitively, so that the compiler would know the one line that declares `printf`.

### Line-by-line walkthrough

Open `hello.i` and look at the last four lines:

```c
# 4 "hello.c"
int main(void) { printf("%s, world\n", "hello"); return 0; }
```

Two things happened. `GREETING` was replaced by `"hello"` — the preprocessor does not know or care that it is a string; it substitutes text. And the `#include` line is gone, replaced by 550-odd lines of declarations above. The `# 4 "hello.c"` is a **line marker**: it tells the compiler "the next line came from line 4 of hello.c", which is how error messages point at your file instead of at line 553 of a generated blob.

Now `hello.s`, trimmed to the interesting part:

```asm
_main:
	sub	sp, sp, #32          ; make room on the stack
	adrp	x0, l_.str@PAGE      ; load the address of the format string
	add	x0, x0, l_.str@PAGEOFF
	adrp	x1, l_.str.1@PAGE    ; load the address of "hello"
	add	x1, x1, l_.str.1@PAGEOFF
	bl	_printf              ; branch-and-link: call printf
	mov	w0, #0               ; return value 0
	add	sp, sp, #32
	ret
```

`bl _printf` is a call to an address the compiler does not know yet. It writes a placeholder and records "someone must fill this in".

Now `hello.o`. `nm` lists its symbols:

```bash
nm hello.o
```

```
0000000000000000 T _main
                 U _printf
```

`T` means "defined here, in the text (code) section". `U` means **undefined** — needed, but not supplied by this file. That single `U` is the whole reason the link step exists.

Finally, the executable. `otool -L hello` (use `ldd hello` on Linux) shows what it will load at run time:

```
hello:
	/usr/lib/libSystem.B.dylib (compatibility version 1.0.0, current version 1351.0.0)
```

`printf` is not inside your 33 KB binary. The binary contains a note saying "find it in libSystem when you start."

```c
/* undef.c */
```

<Step title="Confirm with nm">


```
_helper
```

`nm -u` lists undefined symbols only. When you get an "undefined reference", this is the first command to run — it tells you the exact mangled name the linker is looking for, which is often not the name you typed.
</Step>
<Step title="Fix it and watch the U disappear">
Add `void helper(void) &#123; puts("hi"); &#125;` and rebuild. `nm -u` now prints only `_puts`, which libSystem supplies.

<Step title="Write your first Makefile">

```makefile
CC      := cc
CFLAGS  := -std=c17 -Wall -Wextra
hello: hello.o
	$(CC) $(CFLAGS) $< -o $@
hello.o: hello.c
	$(CC) $(CFLAGS) -c $< -o $@

	rm -f hello hello.o
```

Run `make` twice. The second time it prints `make: 'hello' is up to date.` — because `make` compares file modification times and skips work whose inputs have not changed. `touch hello.c && make` rebuilds. That is the entire idea of `make`.

<Accordion title="Checkpoint — 5 questions before you continue">

1. **Which stage reports "undefined reference to `foo`"?** — the linker. The compiler only needed a declaration.
2. **What does `-c` do?** — stop after assembling; produce a `.o` and do not link.
3. **Why did 3 lines become 557?** — `#include` pasted in 37 header files transitively, all so the compiler could see one declaration of `printf`.
4. **What is the difference between a declaration and a definition?** — a declaration promises a name exists with a given shape; a definition supplies the body. A header holds declarations; a `.c` file holds definitions.
5. **Your `hello` is 33 KB but does almost nothing. Where did the bytes go?** — mostly metadata: load commands, the symbol table, unwind info and page alignment. `size -m hello` shows the `__text` section is **68 bytes**.

### The four stages, and the flags that stop at each

| Stage | Program | Flag | Input | Output |
|---|---|---|---|---|
| Preprocess | `clang -cc1` / `cpp` | `-E` | `.c` + headers | `.i` (still C) |
| Compile | `clang -cc1` | `-S` | `.i` | `.s` (assembly text) |
| Assemble | `clang -cc1as` / `as` | `-c` | `.s` | `.o` (ELF on Linux, Mach-O on macOS) |
| Link | `ld64` / `ld.lld` / `GNU ld` | (default) | `.o` + libs | executable or shared library |

Useful diagnostics you should have in muscle memory:

```bash
cc -E -H file.c -o /dev/null    # print the header inclusion tree (37 lines for stdio.h alone)
cc -S -O2 file.c -o -           # assembly to stdout — the fastest way to answer "what did it compile to"
nm -u obj.o                     # undefined symbols: what this object needs
nm -g obj.o                     # global (exported) symbols: what it provides
otool -L bin                    # macOS: dynamic libraries this binary will load
ldd bin                         # Linux: same
size -m bin                     # segment/section sizes
cc -Wl,-t file.c                # trace what the linker actually pulled in
```

### Header guards, and why they exist

Include the same header twice and you get "redefinition of struct X". The fix is a **header guard**:

```c
#ifndef NEXUS_QUEUE_H
#define NEXUS_QUEUE_H
/* declarations */
#endif
```

`#pragma once` does the same thing in one line and is supported by clang, gcc and MSVC, but it is not in the C standard and it identifies files by inode, which breaks across bind mounts and symlinked build trees. In a monorepo with a shared build cache, use the named guard. In a single project, `#pragma once` is fine. Do not use both — that is cargo cult, and the second one is dead code.

### Static vs dynamic linking

| | Static (`libfoo.a`) | Dynamic (`libfoo.so` / `.dylib`) |
|---|---|---|
| When symbols resolve | link time | load time (and lazily, per symbol, on first call) |
| Binary size | large — the code is inside | small — 33,432 bytes for our hello, with `__text` only 68 bytes |
| Security patch to libc | requires relinking and redeploying every binary | replace one file, restart processes |
| Startup cost | zero | dynamic loader work per library and per relocation |
| Deploy story | one file, no runtime deps | needs the right library versions present |

**Choose static when** you are shipping a CLI to machines you do not control, building a container `FROM scratch`, or you need reproducible behaviour independent of the host's libc. Go and Rust default here, and that is why a Go binary "just runs".

**Choose dynamic when** you want a single libc/OpenSSL upgrade to fix every process on the box, when many processes share the same library (the pages are shared physical memory), or when you are on macOS — where you effectively have no choice. Apple does not ship a static `libSystem`, so `clang -static` fails on macOS; on Linux, `gcc -static` works, and Alpine's musl makes fully-static builds small.

### Reading the linker's mind: symbol resolution order

The classic Linux trap:

```bash
gcc -lm main.c -o main      # fails: undefined reference to `sqrt'
gcc main.c -lm -o main      # works
```

`ld` processes its inputs left to right and, for a static archive, pulls in only the members that satisfy symbols *already known to be undefined*. When `-lm` comes first, nothing is undefined yet, so nothing is pulled in. This is not a bug, it is a documented single-pass design, and it is why build systems always put libraries last. `--start-group`/`--end-group` exists for genuine circular dependencies between archives; needing it usually means your module boundaries are wrong.

### A Makefile that does not lie to you

```makefile
# Makefile — debug and release from the same sources
CC       := cc
SRC      := $(wildcard src/*.c)
CFLAGS   := -std=c17 -Wall -Wextra -Wpedantic -MMD -MP
LDFLAGS  :=

BUILD    ?= debug
ifeq ($(BUILD),debug)
  CFLAGS  += -O0 -g3 -fsanitize=address,undefined -fno-omit-frame-pointer
  LDFLAGS += -fsanitize=address,undefined
else
  CFLAGS  += -O2 -DNDEBUG
endif

OBJ := $(SRC:src/%.c=build/$(BUILD)/%.o)
DEP := $(OBJ:.o=.d)
BIN := build/$(BUILD)/app

.PHONY: all clean verify
all: $(BIN)

$(BIN): $(OBJ)
	$(CC) $(OBJ) $(LDFLAGS) -o $@

build/$(BUILD)/%.o: src/%.c | build/$(BUILD)
	$(CC) $(CFLAGS) -c $< -o $@

build/$(BUILD):
	mkdir -p $@

verify: all
	./$(BIN) --selftest

clean:
	rm -rf build

-include $(DEP)
```

Three details that separate this from the Makefile most people write:

- **`-MMD -MP`** makes the compiler emit a `.d` file listing every header each `.o` depends on, and `-include $(DEP)` feeds those back to `make`. Without it, editing a header rebuilds nothing and you debug a stale binary for an hour. `-MP` adds phony targets so a *deleted* header does not break the build.
- **Separate output directories per `BUILD`.** `make BUILD=release` and `make` do not fight over the same `.o` files. Mixing sanitized and non-sanitized objects in one link produces bizarre crashes.
- **Order-only prerequisite `| build/$(BUILD)`.** The directory must exist but its timestamp must not trigger rebuilds. The `|` is what says that.

### What breaks in the real world

A team ships a C extension used from Python. CI is green. In production, one service in ten segfaults inside `memcpy` on startup, and only on the machines that had been running longest.

The cause: `make` had no header dependency tracking. A struct in `session.h` had grown a field. The `.c` file that *allocated* the struct was rebuilt because it had been edited; the `.c` file that only *read* it was not, because its own `.c` had not changed and `make` never knew it included the header. The two objects were linked together with different ideas of `sizeof(struct session)` — 48 bytes in one, 56 in the other. Every field after the insertion point was read at the wrong offset. It only crashed on hosts that had gone through the specific partial-rebuild sequence, which is why CI (which always built clean) never saw it.

The signature of this bug is that a **clean build fixes it**, which teaches everyone the wrong lesson ("just `make clean`") and hides the real fix, which is four characters: `-MMD -MP`. The second-order fix is to build in a container from scratch in CI so "works after clean build" and "works" are the same statement.

<Accordion title="Design checkpoint — one question, with a model answer">

**Question.** Your team's C service takes 6 minutes to build from clean and 40 seconds for an incremental one-file change. Someone proposes switching to a unity build (`#include` every `.c` into one translation unit) because "it compiles the whole thing in 90 seconds." Do you take it?

**Model answer.** Probably not, and the reason is the 40 seconds, not the 6 minutes.

A unity build wins on clean builds because it pays the header-parsing cost once instead of N times — measured on our `hello.c`, one `#include <stdio.h>` costs 37 header files and inflates 105 bytes of source to 25,076 bytes of preprocessed text; multiply that by 200 translation units and most of a clean build is re-parsing the same headers. Unity builds legitimately fix that.

But developers do not do clean builds; they do incremental ones. A unity build makes *every* edit a full rebuild, so the 40-second incremental becomes 90 seconds. You have made the common case 2.25× worse to make the rare case 4× better. It also breaks parallelism — `make -j10` has nothing to parallelise over one translation unit — and it silently changes semantics, because `static` functions and file-scope names from different files now collide in one scope.

The measurement to take before deciding: `cc -E -H` on your three biggest translation units and count the shared headers. If the answer is "most of the cost is our own headers", the fix is precompiled headers (`-include` a prebuilt PCH) or C++20-style modules, both of which keep incremental builds incremental. If the answer is "most of the cost is that we have 200 files each including all 90 of our headers", the fix is to cut the include graph — forward-declare in headers, include in `.c` files. And before any of that, try `ccache`, which is one line in `CC` and typically gets clean-build times close to the incremental case for free on a warm cache.
</Accordion>

### The optimiser deleted your benchmark. Here is the proof.

This is the single most common way a beginner's performance measurement produces a wrong conclusion, and you should be able to demonstrate it in 60 seconds.

```c
long sum_to(long n) { long s = 0; for (long i = 1; i <= n; i++) s += i; return s; }
```

Timed with `clock_gettime(CLOCK_MONOTONIC)` around `sum_to(1000000000)`:

| Build | Wall time | Notes |
|---|---|---|
| `-O0` | ~1.0 s on an idle machine; 9.2–27.2 s on this loaded box (load average 44) | the loop actually runs, one billion iterations |
| `-O1` | 0.000 ms | loop gone |
| `-O2` | 0.000 ms | loop gone |

The `-O2` assembly, in full:

```asm
_sum_to:
	subs	x8, x0, #1
	b.lt	LBB0_2
	sub	x9, x0, #2
	mul	x10, x8, x9
	umulh	x8, x8, x9
	extr	x8, x8, x10, #1
	add	x8, x8, x0, lsl #1
	sub	x0, x8, #1
	ret
```

Nine instructions, no branch backwards, no loop. LLVM's **scalar evolution** pass recognised the induction variable and replaced the loop with the closed form n(n+1)/2 — Gauss's trick, applied by a compiler pass. The `mul`/`umulh` pair is a 128-bit multiply because the intermediate n(n−1) overflows 64 bits for large n, and `extr … #1` is the divide-by-two.

This is why "I timed my loop and it took 0 ms" means "the loop is not in your binary". Defences, in order of preference:

1. **Consume the result.** Print it, or store it through a `volatile` pointer. Our benchmark does print `sum`, which is why the *call* survives — only the loop was replaced.
2. **`asm volatile("" : : "r"(x) : "memory");`** — a compiler barrier that forces `x` into a register and clobbers memory, so nothing can be moved across it. Google Benchmark's `DoNotOptimize` is this.
3. **Put the workload in a separate translation unit** and build without LTO, so the optimiser cannot see through the call.
4. **Check the assembly.** `cc -S -O2 bench.c -o -` costs five seconds and settles the argument. Do this before you publish a number.

Note the honest second row of that table: the same `-O0` binary measured 9.2 s, 12.6 s, 19.3 s and 27.2 s on four consecutive runs while this machine was under load average 44, and ~1.0 s when it was quiet. **Wall-clock benchmarks on a shared machine are worthless.** For the rest of Week 1 we measure with `CLOCK_PROCESS_CPUTIME_ID` and report the *minimum* of N runs, which is the only run that was not stolen from.

### The address space, and the four gigabytes of nothing

`size -m hello` on the linked executable:

```
Segment __PAGEZERO: 4294967296 (zero fill)
Segment __TEXT: 16384
	Section __text: 68
	Section __cstring: 17
	Section __unwind_info: 88
Segment __DATA_CONST: 16384
	Section __got: 8
Segment __LINKEDIT: 16384
```

Three things worth noticing.

**`__PAGEZERO` is 4 GB of deliberately unmapped address space at address 0.** Every 64-bit Mach-O binary starts with it. Its purpose is that any dereference of a null pointer — or of a null pointer plus a 32-bit offset, which is what `p->field` on a null `p` looks like — lands in unmapped memory and faults immediately, instead of silently reading whatever happened to be at low addresses. Linux achieves the same with `vm.mmap_min_addr` (default 65536). This is why a null-pointer dereference is a clean `SIGSEGV` and not a security hole; it is a design decision, not luck.

**`__text` is 68 bytes.** Out of a 33,432-byte file. The rest is Mach-O load commands, the symbol table, unwind information for exception handling and backtraces, code-signature space, and 16 KB page alignment. This is why "my hello world is 33 KB, C is bloated" is a misreading — the marginal cost of the next function is tens of bytes, not tens of kilobytes.

**`__got` is the Global Offset Table**, 8 bytes here — one entry, for `printf`. At load time the dynamic linker writes the real address of `printf` into that slot. On macOS with `dyld`, and on Linux with lazy binding (`ld.so`), the first call goes through a stub that resolves the symbol and patches the table; subsequent calls are a direct indirect jump. `LD_BIND_NOW=1` (Linux) or `DYLD_BIND_AT_LAUNCH=1` (macOS) resolves everything eagerly at startup instead — worth doing for latency-sensitive services where you would rather pay 100% of the cost at boot than a fraction of it in the p99.

### ABI and calling conventions

The **ABI** (Application Binary Interface) is the agreement about how compiled code interoperates: which registers carry arguments, who saves what, how structs are laid out and returned, how the stack is aligned.

On AArch64 (Apple's ABI, a variant of AAPCS64): integer and pointer arguments go in `x0`–`x7`, floating point in `v0`–`v7`, the return value in `x0`, the return address in `x30` (`lr`), and the stack must be 16-byte aligned at every call. You can read all of this straight off `hello.s`: `adrp x0/add x0` then `adrp x1/add x1` load the two arguments, and `bl _printf` puts the return address in `x30`.

Apple's ABI differs from the standard AAPCS64 in a way that bites: **variadic arguments are passed on the stack, not in registers.** Code that calls `printf` through a hand-written wrapper works on Linux/aarch64 and crashes on macOS/arm64. This is documented in Apple's "Writing ARM64 Code for Apple Platforms" and is the reason a surprising amount of JIT and FFI code has an `#ifdef __APPLE__`.

The ABI is also why C is the lingua franca. Python's `ctypes`, Rust's `extern "C"`, Go's cgo, the CUDA driver API and every `.so` plugin system in existence agree on the C ABI, because it is the only thing everyone already implements. When you call a PyTorch kernel in Week 21, the boundary you are crossing is this one.

### `-O0` vs `-O2`: what you actually give up

Compile-time cost, measured as user CPU time compiling a 40-line benchmark file:

| Optimisation level | Compile time |
|---|---|
| `-O0` | 0.04 s |
| `-O2` | 0.08 s |

Two times slower to compile, for a workload where the run-time difference was total loop elimination. On a real 200-file project, `-O2` typically costs 2–4× the compile time of `-O0` — which is why the debug build in the Makefile above uses `-O0 -g3` and the release build uses `-O2 -DNDEBUG`, and why you should never benchmark a debug build or debug a release one.

`-Og` exists specifically for the middle case: optimisations that do not destroy debuggability. Use it when a bug only reproduces under optimisation and `-O2` gives you `<optimized out>` for every variable.

### Production failure modes and how you detect them

| Failure | Signature | Detection |
|---|---|---|
| Stale object linked against a changed header | crash at a plausible-looking offset; `make clean` "fixes" it | add `-MMD -MP` and `-include $(DEP)`; build clean in CI containers |
| Benchmark loop optimised away | a suspiciously round 0.000 ms, or a speedup far beyond memory bandwidth | inspect `cc -S -O2`; consume results; use `DoNotOptimize` |
| Undefined reference only in release | a function was `static inline` in a header and only emitted at `-O0` | give it external linkage or make it `static` in one `.c`; check `nm -u` on both builds |
| Works locally, "GLIBC_2.34 not found" in production | built against a newer glibc than the target | build in a container matching production, or link statically with musl |
| Two libraries define the same symbol | one silently wins; behaviour depends on link order | `nm -g` both; `-Wl,--allow-multiple-definition` is a way to hide the bug, not fix it |
| p99 latency spike on the first request per code path | lazy symbol binding resolving on first call | `LD_BIND_NOW=1` / `DYLD_BIND_AT_LAUNCH=1`, or warm the paths at startup |

### Frontier and research pointers

- **Levine, J. (1999). *Linkers and Loaders*.** One-sentence takeaway: linking is a database join over symbol names, and every "weird linker error" is a failed or ambiguous join you can debug with `nm`.
- **Drepper, U. (2011). "How To Write Shared Libraries."** One-sentence takeaway: symbol visibility, not code size, dominates dynamic library load cost — hiding non-API symbols with `-fvisibility=hidden` measurably cuts relocation work at startup.
- **Lattner & Adve (2004). "LLVM: A Compilation Framework for Lifelong Program Analysis & Transformation." CGO.** One-sentence takeaway: separating the language front end from a typed SSA intermediate representation is what makes one optimiser serve C, Rust, Swift and Julia at once.
- **ARM, "Procedure Call Standard for the Arm 64-bit Architecture (AAPCS64)", 2024 release.** One-sentence takeaway: the register allocation for arguments and returns is a written contract, and reading it is how you debug FFI crashes rather than guessing.
- **Bernstein, D. J., "The death of optimizing compilers" (2015 talk).** One-sentence takeaway: compilers optimise the code you did not need to optimise and cannot fix the algorithm you chose — a useful counterweight before you spend a week on flags.

### Stretch challenge

Take one function from your own code, ideally something with a branch inside a loop. Then:

1. Compile it at `-O0`, `-O1`, `-O2`, `-O3` and `-Os` and record the instruction count of the function body (`objdump -d` and count, or use Godbolt's compiler explorer for a nicer view).
2. Find the exact optimisation level at which the behaviour you care about changes, and use `-fno-<pass>` flags or `-Rpass=` remarks (`clang -O2 -Rpass=loop-vectorize`) to identify *which pass* did it.
3. Now add `-march=native` and re-measure. On this M3, and on any x86 box with AVX-512, this can change the answer dramatically — and it also produces a binary that will `SIGILL` on an older machine.
4. Write down the rule you would put in your team's build file, and the reason. There is no single right answer: `-march=native` is correct for a benchmark rig and wrong for a distributed binary, and the interesting case is a container image that runs on a heterogeneous fleet. What would you actually ship?

## Apply it at work

<AccordionGroup>
<Accordion title="If you're a student" icon="graduation-cap">

**Portfolio line:** *"A build system walkthrough repo: the same 40-line program shown at all four compilation stages, with measured artifact sizes and a Makefile that demonstrates why `-MMD -MP` matters."* It is a teaching artifact, and teaching artifacts read well because they prove you understood rather than copied.

**The interview angle.** "What is the difference between a compiler error and a linker error?" is a screening question at every systems-adjacent company, and the good answer is mechanical, not definitional: *the compiler works on one translation unit and only needs declarations, so it catches syntax and type errors; the linker sees all objects at once and resolves names, so it is the only thing that can know a definition is missing. `nm -u` shows you exactly which symbol it wanted.*

The senior follow-up is "why did adding `-O2` break your code?" — and the answer that lands is undefined behaviour becoming visible, which you will be able to demonstrate with real assembly after Module 5.
</Accordion>
<Accordion title="If you're working" icon="briefcase">

Three places this shows up in a normal engineering week:

1. **A Docker image is 1.2 GB and the app is 8 MB.** Almost always a single-stage build that kept the toolchain. The fix is a multi-stage `Dockerfile` where the build stage compiles and the final stage is `FROM gcr.io/distroless/base` or `scratch` with a statically linked binary. Knowing which symbols the binary actually needs (`ldd` says "not a dynamic executable" when you got it right) is the difference between that working and a mystery `exec format error`.

2. **"Works on my machine", GLIBC edition.** A binary built on Ubuntu 24.04 fails on a 22.04 host with `version 'GLIBC_2.35' not found`. glibc is backward compatible, not forward compatible. Build in a container matching the oldest target, or link musl statically. This costs teams days when nobody knows the rule.

3. **The 40-minute CI build.** Before buying bigger runners, run `cc -E -H` over your worst translation unit and count headers, then turn on `ccache` (or `sccache`) and `make -j$(nproc)`. On a typical C/C++ service both together cut warm-cache builds by more than half, and neither requires touching a line of application code.
</Accordion>

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| `undefined reference to 'sqrt'` even though you `#include <math.h>` | the header declares it, the library defines it; you did not link `-lm` | `gcc main.c -lm` — and note libraries go **after** the objects that need them |
| Adding `-lfoo` before the source file still fails | `ld` is single-pass and only pulls archive members that satisfy already-undefined symbols | put all `-l` flags last on the command line |
| Editing a header changes nothing until `make clean` | no header dependency tracking | add `-MMD -MP` to `CFLAGS` and `-include $(DEP)` to the Makefile |
| Sanitizer build crashes in unrelated code | sanitized and non-sanitized `.o` files linked together | build each configuration into its own output directory; never share `.o`s |
| Benchmark reports 0.000 ms | the optimiser removed the loop | consume the result, add a compiler barrier, and read `cc -S -O2` before believing a number |
| `error: redefinition of 'struct foo'` | header included twice, no guard | add `#ifndef`/`#define`/`#endif` or `#pragma once` — one of them, not both |
| Debug build works, release build crashes | undefined behaviour the optimiser exploited (see Module 5) | run `-fsanitize=undefined` on the debug build; build tests at `-O2` too |
| Binary runs on your laptop, `SIGILL` in production | `-march=native` baked in CPU features the target lacks | use an explicit baseline like `-march=x86-64-v2`, or runtime dispatch |

## Sources & further reading

**Primary docs**

- **[Clang Compiler User's Manual, "Driver Options" (LLVM 17/18).](https://clang.llvm.org/docs/UsersManual.html)** Read this for the exact meaning of `-E`, `-S`, `-c`, `-MMD`, `-MP` and the `-Rpass=` remark flags that tell you which optimisation fired.
- **[GNU Make Manual, Chapter 4 ("Writing Rules") and §4.14 ("Generating Prerequisites Automatically").](https://www.gnu.org/software/make/manual/make.html)** Read this for the canonical `-MMD -MP` pattern and for the difference between normal and order-only prerequisites.
- **[Apple, "Writing ARM64 Code for Apple Platforms".](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms)** Read this for the documented ways Apple's ABI diverges from AAPCS64 — particularly variadic arguments on the stack, which breaks portable FFI code.
- **`man 1 nm`, `man 1 otool`, `man 1 ld` (macOS 15); `man 1 ld.so` (Linux).** Read these for the flags you will use to debug a link failure instead of guessing at it.

**Papers**

- **[Lattner, C. & Adve, V. (2004). "LLVM: A Compilation Framework for Lifelong Program Analysis & Transformation." *CGO*.](https://llvm.org/pubs/2004-01-30-CGO-LLVM.html)** One-sentence takeaway: a typed SSA intermediate representation decoupled from any source language is what lets one optimiser back end serve C, Swift, Rust and Julia.
- **[Drepper, U. (2011). "How To Write Shared Libraries."](https://www.akkadia.org/drepper/dsohowto.pdf)** One-sentence takeaway: default symbol visibility makes the dynamic linker do relocation work proportional to your *whole* symbol table, so `-fvisibility=hidden` plus an explicit export list is the cheapest startup win in a large shared library.

**Go deeper**

- **[Levine, J. R. (1999). *Linkers and Loaders*, Chapters 4–5 (symbols, relocation) and 9 (shared libraries).](https://www.iecc.com/linker/)** The only book that treats linking as a first-class subject; Chapter 9 explains lazy binding and the PLT/GOT well enough that `otool -L` output stops being mysterious.
- **[Godbolt Compiler Explorer (godbolt.org).](https://godbolt.org/)** Not a paper, but the single highest-value tool in this module: paste a function, pick a compiler version, and watch the assembly change as you add flags. Use it to reproduce the `sum_to` result above in 30 seconds.
