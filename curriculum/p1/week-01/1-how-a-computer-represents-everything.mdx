### The one idea

A computer stores exactly one kind of thing: a **bit** — a switch that is either off or on, written `0` or `1`. That is all. There is no "text" inside the machine and no "picture" inside the machine. There are only switches.

Meaning is not a property of the switches. Meaning is an **agreement** — a rule you and the machine share about how to read a group of switches. Change the agreement and the same switches mean something else. The whole of computing is agreements stacked on switches.

### The analogy

Picture a row of eight light switches on a wall. Each switch is off or on. How many different patterns can the wall show? Switch 1 doubles the possibilities of the wall to its right, and so on: 2 × 2 × 2 × 2 × 2 × 2 × 2 × 2 = 256.

Now two people walk in. The first has agreed that the pattern means a number from 0 to 255. The second has agreed that it means a letter. They look at the same wall and read different things, and neither of them is wrong. The wall does not know.

### The vocabulary, defined

- **Bit** — one switch. One binary digit. `0` or `1`.
- **Byte** — eight bits, treated as one unit. 2⁸ = 256 possible patterns.
- **Nibble** — four bits. Exactly one hexadecimal digit. Handy, and the reason hex exists.
- **Word** — the natural chunk size a particular CPU works in. On the Apple M3 and on a modern Intel or AMD chip, that is 64 bits.
- **Base** (or **radix**) — how many digit symbols a number system uses. Decimal is base 10 (digits 0–9). Binary is base 2 (digits 0–1). Hexadecimal is base 16 (digits 0–9 then a–f).
- **Hexadecimal** (**hex**) — base 16, written with a `0x` prefix in C and Python. One hex digit is exactly four bits, so one byte is exactly two hex digits. That clean 1-to-2 mapping is the only reason anyone uses it.
- **ASCII** — a 1963 agreement mapping 128 characters to the numbers 0–127. `A` is 65. `a` is 97. Space is 32.
- **Encoding** — a specific agreement for turning characters into bytes. ASCII is one. UTF-8 is another.

### Counting in binary, by hand

Each position in a binary number is worth twice the position to its right. For eight bits the place values are:

```
place value:  128  64  32  16   8   4   2   1
bit:            0   1   0   0   0   0   0   1
```

Add up the place values where the bit is `1`: 64 + 1 = **65**. And 65 is ASCII `A`. Those eight bits are, at the same time, the number 65 and the letter `A`. Which one they "are" depends entirely on what you tell the program to do with them.

Do these four by hand right now, on paper, before reading on:

| Binary | Place values that are on | Decimal | Hex | ASCII |
|---|---|---|---|---|
| `01000001` | 64 + 1 | 65 | `0x41` | `A` |
| `01100001` | 64 + 32 + 1 | 97 | `0x61` | `a` |
| `00110000` | 32 + 16 | 48 | `0x30` | `0` (the character zero) |
| `11111111` | all eight | 255 | `0xff` | — (not ASCII) |

Notice the last two rows. The *character* `0` is the *number* 48. This trips up every beginner exactly once: `'0'` and `0` are different values, and `'0' - '0'` is how you turn a digit character into the digit it represents.

### Smallest working example

Save this as `bits.c`. It prints the bits of one byte.

```c
#include <stdio.h>

void print_byte(unsigned char b) {
    for (int i = 7; i >= 0; i--) {
        putchar((b >> i) & 1 ? '1' : '0');
    }
    putchar('\n');
}

int main(void) {
    print_byte('A');   /* the character A  */
    print_byte(65);    /* the number 65    */
    print_byte(255);
    return 0;
}
```

Compile and run:

```bash
cc -std=c17 -Wall -Wextra bits.c -o bits && ./bits
```

Output:

```
01000001
01000001
11111111
```

The first two lines are identical. That is the whole lesson, printed.

### Line-by-line walkthrough

- `#include <stdio.h>` — pull in the declarations for `printf` and `putchar` so the compiler knows they exist. Without it you get a warning and, in C17, an error.
- `unsigned char b` — one byte, treated as a number from 0 to 255. We say **unsigned** because we do not want negative values here; see Layer 2 for what "signed" costs you.
- `for (int i = 7; i >= 0; i--)` — walk from the leftmost bit (position 7, worth 128) down to the rightmost (position 0, worth 1). We go left-to-right because that is how humans read numbers.
- `b >> i` — the **right shift** operator. It slides all the bits `i` places to the right, dropping what falls off the end. After shifting, the bit we care about is sitting in position 0.
- `& 1` — the **bitwise AND** operator against the pattern `00000001`. Every position where either side is `0` becomes `0`. So this keeps only the rightmost bit and zeroes everything else. Shift-then-mask is *the* idiom for "give me bit number `i`", and you will see it in every codebase that touches hardware, network packets or compression.
- `? '1' : '0'` — the ternary conditional: if the masked value is 1, use the character `'1'`, else the character `'0'`. Note the quotes: we are printing characters, not numbers.
- `putchar(...)` — write one character to standard output.
- `print_byte('A')` — in C, `'A'` in single quotes *is* the number 65. The compiler substitutes it at compile time.

<Accordion title="Checkpoint — 5 questions before you continue">

1. **How many distinct values fit in 3 bits?** — 2³ = 8, namely 0 through 7.
2. **What decimal number is `00011011`?** — 16 + 8 + 2 + 1 = 27.
3. **Why is one byte exactly two hex digits?** — one hex digit encodes 4 bits (16 possibilities), and a byte is 8 bits, so 8 ÷ 4 = 2.
4. **`'7'` is stored as which number?** — 55. The character `7` is ASCII 55; the digit 7 is the number 7. Subtracting `'0'` (48) converts one to the other.
5. **A file is 5 bytes and shows 4 characters in your editor. What happened?** — at least one character needed more than one byte, so the file is not plain ASCII. It is almost certainly UTF-8.
</Accordion>

### Two's complement, and why signed overflow is a different animal

Eight bits give 256 patterns. If you want negatives you have to spend half of them. **Two's complement** is the agreement every modern CPU uses: the top bit carries a *negative* place value.

```
place value:  -128  64  32  16   8   4   2   1
bit:             1   0   0   0   0   0   0   1     ->  -128 + 1 = -127
bit:             1   1   1   1   1   1   1   1     ->  -128 + 127 = -1
```

Two properties make it the winner over the alternatives (sign-magnitude, ones' complement):

1. **There is exactly one zero.** Sign-magnitude has `+0` and `-0`, and every comparison has to special-case it.
2. **Addition is the same circuit for signed and unsigned.** The adder does not need to know. `0xFF + 0x01 = 0x00` with a carry out, and that is correct both as `255 + 1 = 256 (truncated)` and as `-1 + 1 = 0`.

The range is asymmetric: an *N*-bit two's complement integer holds −2^(N−1) to 2^(N−1) − 1. For `int32_t` that is −2147483648 to 2147483647. There is no positive 2147483648, which is why `abs(INT_MIN)` is undefined and why `-INT_MIN` overflows.

Now the part that bites in production:

| | Unsigned overflow | Signed overflow |
|---|---|---|
| C standard says | Defined. Wraps modulo 2^N. | **Undefined behaviour.** |
| What actually happens at `-O0` | wraps | usually wraps |
| What actually happens at `-O2` | wraps | the optimiser may assume it *cannot happen* and delete your check |
| Sanitizer that catches it | `-fsanitize=unsigned-integer-overflow` (opt-in, off by default) | `-fsanitize=signed-integer-overflow` (part of `-fsanitize=undefined`) |

That last row is the practical takeaway. `if (x + 1 < x)` as an overflow check on a signed `int` is not a check — at `-O2` the compiler is entitled to compile it to `false`, because signed overflow "cannot happen", so `x + 1` is always greater than `x`. Write `if (x > INT_MAX - 1)` instead, which asks the question without performing the overflow. We will watch the compiler delete a security check for exactly this reason in Module 5.

### The signed/unsigned comparison trap

This is the single most common integer bug in C and C++ code review:

```c
#include <stdio.h>
#include <string.h>

/* WRONG */
void copy_bad(char *dst, const char *src, int n) {
    if (n > 1024) return;              /* "bounds check" */
    memcpy(dst, src, (size_t)n);       /* n = -1 becomes 18446744073709551615 */
}
```

If `n` arrives as `-1` — from a length field in a network packet, say, or from a function that returns `-1` on error — the check `n > 1024` passes, and the cast to `size_t` turns `-1` into 2⁶⁴ − 1. `memcpy` then attempts an 18-exabyte copy and you have a remote heap corruption. The fix is to make the type match the domain (`size_t n`) and reject the error return *before* the cast.

The mirror-image bug goes the other way:

```c
size_t len = strlen(s);
for (int i = 0; i <= len - 1; i++) { ... }   /* when s is "", len is 0 */
```

`len - 1` on a `size_t` is not −1; it is 18446744073709551615. The loop runs essentially forever. `gcc`/`clang` warn about this with `-Wsign-compare`, which `-Wextra` turns on. Turn on `-Wall -Wextra` and treat these as errors.

### Endianness, measured

**Endianness** is the agreement about which byte of a multi-byte number goes at the lowest address. Run this:

```c
#include <stdio.h>
#include <stdint.h>
int main(void) {
    uint32_t x = 0x01020304;
    unsigned char *p = (unsigned char *)&x;
    printf("%02x %02x %02x %02x\n", p[0], p[1], p[2], p[3]);
    return 0;
}
```

On this machine (Apple M3 Pro, macOS 15) it prints:

```
04 03 02 01
```

The **least** significant byte is at the lowest address: **little-endian**. x86-64 and ARM in its normal configuration are both little-endian, so in practice you will see this everywhere. But every network protocol from IP onward specifies **big-endian** ("network byte order"), so any code that parses packets or writes a binary file format must convert explicitly with `htonl`/`ntohl`/`htons`/`ntohs` from `<arpa/inet.h>`, or `__builtin_bswap32`. Never memcpy a struct onto the wire and hope.

### Text: ASCII to UTF-8

ASCII covers 128 characters, which is enough for English and nothing else. **Unicode** assigns a number — a **code point**, written `U+00E9` — to every character in every writing system, currently about 155,000 of them. An **encoding** turns code points into bytes. UTF-8 is the encoding that won, and it won for three specific engineering reasons:

1. **ASCII is a subset.** Any valid ASCII file is already valid UTF-8, byte for byte. Thirty years of tooling kept working.
2. **It is self-synchronising.** Continuation bytes always start with the bits `10`, so if you land in the middle of a character you can find the boundary by scanning backwards at most three bytes. UTF-16 has no such property.
3. **No byte-order problem.** It is a byte sequence, so there is no endianness and no BOM needed.

The layout, which is worth memorising:

| Code points | Bytes | Bit pattern |
|---|---|---|
| U+0000 – U+007F | 1 | `0xxxxxxx` |
| U+0080 – U+07FF | 2 | `110xxxxx 10xxxxxx` |
| U+0800 – U+FFFF | 3 | `1110xxxx 10xxxxxx 10xxxxxx` |
| U+10000 – U+10FFFF | 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

**Derived** — these byte counts are fixed by the Unicode and UTF-8 standards, not by any machine, so you will get exactly these on your own (shown with Python 3.13.2):

| Text | Python `len()` | UTF-8 bytes | UTF-16 bytes | Hex (UTF-8) |
|---|---|---|---|---|
| `A` | 1 | 1 | 2 | `41` |
| `é` | 1 | 2 | 2 | `c3 a9` |
| `→` | 1 | 3 | 2 | `e2 86 92` |
| `😀` | 1 | 4 | 4 | `f0 9f 98 80` |
| `👩‍💻` | **3** | **11** | 10 | `f0 9f 91 a9 e2 80 8d f0 9f 92 bb` |
| `नमस्ते` | 6 | 18 | 12 | `e0 a4 a8 …` |

Look at row five. That single visible glyph — the "woman technologist" emoji — is three code points (woman, zero-width joiner U+200D, laptop) and eleven bytes. If your database column is `VARCHAR(10)` and counts bytes, one emoji rejects the row. If it counts code points, a user's "1-character" name is 3. If your UI counts what a human calls a character (a **grapheme cluster**), it is 1. Three different correct answers to "how long is this string", and the bug is always in the mismatch. Pick one definition per boundary and write it down.

### Trade-offs table

| Decision | Choose X when… | Choose Y when… |
|---|---|---|
| `int` vs `int32_t`/`int64_t` | `int` for loop counters and small local arithmetic — it is the CPU's natural size and never smaller than 16 bits | `int32_t`/`int64_t` (from `stdint.h`) whenever the width is part of the contract: file formats, wire protocols, hashes, anything persisted |
| Signed vs unsigned | **Signed** for quantities that can be subtracted and compared — indices, offsets, counts you might difference. Overflow is UB, but that means the sanitizer can catch it | **Unsigned** for bit patterns, hashes, and sizes that come from the platform (`size_t`). Never for a value you will subtract without a guard |
| UTF-8 vs UTF-16 | **UTF-8** for storage, files, wire protocols, and anything Linux touches. 1 byte for ASCII, no BOM, no endianness | **UTF-16** only when an API forces it — Windows `W` APIs, Java/JS/C# in-memory strings, ICU internals |
| `float` (fp32) vs `double` (fp64) | **fp32** for graphics, ML tensors, and any array of millions of values where you are memory-bandwidth-bound — half the bytes means twice the throughput | **fp64** for money-adjacent maths, physics, iterative accumulation, and anything where you cannot afford to reason about error growth (see Layer 3 for the measured error) |

### Reference implementation — `binviz.c`

Complete, compiles clean under `-Wall -Wextra -std=c17`, and verified against `hexdump -C`.

```c
/* binviz.c — show the bits and bytes behind a value.
 * build: cc -std=c17 -Wall -Wextra -O2 binviz.c -o binviz
 * usage: ./binviz int 65
 *        ./binviz float 12.1414223
 *        ./binviz str  "café"
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdint.h>

static void print_bits(const void *obj, size_t nbytes) {
    const unsigned char *p = (const unsigned char *)obj;
    /* walk bytes from most significant DOWN, i.e. reverse memory order
       on a little-endian machine, so the number reads as a human writes it */
    for (size_t i = nbytes; i-- > 0; ) {
        for (int b = 7; b >= 0; b--) putchar((p[i] >> b) & 1 ? '1' : '0');
        putchar(' ');
    }
    putchar('\n');
}

static void print_memory_order(const void *obj, size_t nbytes) {
    const unsigned char *p = (const unsigned char *)obj;
    for (size_t i = 0; i < nbytes; i++) printf("%02x ", p[i]);
    printf("   <- memory order, low address first\n");
}

int main(int argc, char **argv) {
    if (argc != 3) {
        fprintf(stderr, "usage: %s (int|float|str) VALUE\n", argv[0]);
        return 2;
    }
    if (strcmp(argv[1], "int") == 0) {
        int32_t v = (int32_t)strtol(argv[2], NULL, 0);
        printf("int32  %" PRId32 "  (unsigned view: %" PRIu32 ")\n",
               v, (uint32_t)v);
        print_bits(&v, sizeof v);
        print_memory_order(&v, sizeof v);
    } else if (strcmp(argv[1], "float") == 0) {
        float v = strtof(argv[2], NULL);
        uint32_t bits; memcpy(&bits, &v, sizeof bits);
        printf("float32 %.9g\n", (double)v);
        printf("  sign=%u exponent=%u (biased) => 2^%d   mantissa=0x%06x\n",
               bits >> 31, (bits >> 23) & 0xFF, (int)((bits >> 23) & 0xFF) - 127,
               bits & 0x7FFFFF);
        print_bits(&v, sizeof v);
        print_memory_order(&v, sizeof v);
    } else if (strcmp(argv[1], "str") == 0) {
        size_t n = strlen(argv[2]);
        printf("string of %zu bytes\n", n);
        print_memory_order(argv[2], n);
        for (size_t i = 0; i < n; i++) {
            printf("  byte %2zu = 0x%02x  ", i, (unsigned char)argv[2][i]);
            print_bits(&argv[2][i], 1);
        }
    } else {
        fprintf(stderr, "unknown mode %s\n", argv[1]);
        return 2;
    }
    return 0;
}
```

`PRId32`/`PRIu32` need `#include <inttypes.h>` — add it; it is the one line reviewers always catch. Verify against the system tool:

```bash
./binviz str "café"
printf 'café' | hexdump -C     # must show the same bytes: 63 61 66 c3 a9
```

### What breaks in the real world

Three incidents, all public record, all the same bug class.

**Ariane 5, Flight 501, 4 June 1996.** Forty seconds after liftoff the rocket destroyed itself. The inertial reference system carried over from Ariane 4 converted a 64-bit floating-point horizontal-velocity value into a 16-bit signed integer. Ariane 5's trajectory was faster than any Ariane 4 flight, the value exceeded 32767, the conversion trapped, both redundant units failed identically because they ran identical code, and the guidance computer read the diagnostic bit pattern as flight data. Loss was around $370 million. The conversion had been analysed and *deliberately left unprotected* because on Ariane 4 the physical velocity could not reach that value. The lesson is not "check your casts" — it is that a range assumption is part of the interface, and it does not travel with the code when the code is reused.

**Bitcoin value-overflow incident, 15 August 2010 (CVE-2010-5139).** Block 74638 contained a transaction with two outputs of roughly 92.2 billion BTC each. The sum overflowed the signed 64-bit satoshi counter and wrapped to a small positive number, so the "outputs do not exceed inputs" check passed. 184.467 billion BTC — more than 8,000× the 21 million cap — existed for about five hours until a patched client and a chain reorganisation erased it. The check was arithmetically correct and still wrong, because it computed the sum *before* validating that the sum was representable.

**Boeing 787 generator control units, FAA Airworthiness Directive 2015-09-07.** A 32-bit signed counter incremented every 10 ms. After 2³¹ counts the counter overflowed: 2147483648 × 10 ms = 21474836.5 s = **248.55 days**. All four generator control units, powered on continuously and therefore in lockstep, would enter failsafe simultaneously and drop all AC electrical power in flight. The interim fix in the AD was a maintenance procedure to power-cycle the aircraft before 248 days elapsed. Redundancy does not help against a deterministic bug that all replicas share — a point that returns in Week 30 when we talk about correlated failure.

<Accordion title="Design checkpoint — one question, with a model answer">

**Question.** You are designing the wire format for a metrics agent that ships counters from 50,000 hosts to a central collector. Someone proposes: "send each counter as an 8-byte `double`, it handles both integers and floats and we never have to think about types." What do you say?

**Model answer.** Reject it, for three reasons and one concession.

First, `double` has a 53-bit significand, so it represents every integer exactly only up to 2⁵³ ≈ 9.007 × 10¹⁵. A monotonic byte counter on a 100 Gb/s link accumulates 1.25 × 10¹⁰ bytes/s and reaches 2⁵³ in about 8.3 days of continuous saturation. Past that point increments silently round away and the counter appears to stall. A `uint64_t` gives you 1.8 × 10¹⁹, or 46 years on the same link.

Second, `double` is 8 bytes always. Varint-encoded `uint64` costs 1 byte for values under 128, which is what most counters are, and at 50,000 hosts × 200 metrics × 1 Hz that is 10 M values/s — the difference between 80 MB/s and roughly 20 MB/s of collector ingress.

Third, floats do not compare or hash reliably, so deduplication and idempotent replay get harder for no benefit.

The concession: you do need two types, not one, because gauges genuinely are real-valued (CPU fraction, latency seconds). Ship a tagged union — one byte of type tag, then either a varint `uint64` or an fp64 — which is exactly what Prometheus, OpenTelemetry and StatsD all converged on. The right answer to "we do not want to think about types" is a tag byte, not a wider type.
</Accordion>

### IEEE-754 binary64, exactly

A `double` is 64 bits split 1 / 11 / 52: sign, biased exponent, and the fraction of a significand whose leading `1` is implied and not stored. The value is

```
(-1)^sign × 1.fraction × 2^(exponent - 1023)
```

The implied leading `1` is why you get 53 bits of precision from 52 stored bits, and why the format has to reserve `exponent == 0` for numbers that have no leading 1 — the **subnormals**.

Now the famous example — **derived**, not measured: IEEE-754 fixes every bit below, so this is what your machine prints too, exactly:

```
0.1 + 0.2 = 0.30000000000000004441
bits(0.1+0.2) = 3fd3333333333334
bits(0.3)     = 3fd3333333333333
difference    = 1 ULP  (absolute: 5.551e-17)
```

The two values differ in the final bit of the significand. One **ULP** (unit in the last place) at magnitude 0.3 is 2⁻⁵⁴ ≈ 5.55 × 10⁻¹⁷, which is exactly the gap shown. Nothing is broken. `0.1` is not representable in binary at all — it is the repeating fraction `0.0001100110011…` — so both operands were already rounded before the addition happened, and the two roundings did not cancel.

The practical rule: never test floats with `==`. Test `fabs(a - b) <= tol` with an absolute tolerance for values near zero and a relative one otherwise; `math.isclose` in Python and `np.allclose` in NumPy both do the combined form (`rel_tol=1e-9`, `abs_tol=0.0` and `rtol=1e-5, atol=1e-8` respectively — note how different those defaults are, which is its own source of bugs).

### Error accumulation

**Derived.** Summing 10,000,000 copies of `0.1`; exact answer 1,000,000. IEEE-754 arithmetic is
deterministic, so these results are bit-identical on any conforming machine — you should reproduce
the digits, not merely the magnitude. See [About the numbers](/start/about-the-numbers).

| Method | Result | Relative error |
|---|---|---|
| naive `float` (fp32) | 1087937.000000 | **8.794 × 10⁻²** |
| naive `double` (fp64) | 999999.999839 | −1.610 × 10⁻¹⁰ |
| Kahan compensated, fp64 | 1000000.000000 | 0.0 (to printed precision) |

The fp32 number is the one to stare at: **8.8% wrong**, not in the last digit — in the second digit. The mechanism is absorption. Once the running total reaches about 2²⁴ ≈ 1.68 × 10⁷ ULPs above the addend, `total + 0.1` rounds back to `total` and the sum stops moving entirely. fp32 has 24 bits of significand, so this happens once the total exceeds roughly 2²⁴ × 0.1 ≈ 1.68 × 10⁶ — and indeed the fp32 result is stuck near 1.09 × 10⁶.

This is why PyTorch's `tensor.sum()` on a large fp16 tensor accumulates in fp32 by default, why `torch.mean` on a big fp16 tensor without `dtype=torch.float32` is a bug you will hit in Week 26, and why numerical libraries use pairwise or Kahan summation. NumPy's `np.sum` uses pairwise summation, which cuts the error growth from O(n) to O(log n) and costs nothing measurable.

### Subnormals, and the cliff they hide

When the exponent field is all zeros, the leading bit is `0` instead of `1` and the exponent is fixed at the minimum. This buys **gradual underflow**: instead of the smallest positive fp64 being 2.2250738585072014 × 10⁻³⁰⁸ and the next value down being zero, you get another 52 bits of ever-coarser resolution down to 4.94 × 10⁻³²⁴.

The cost is speed. On many x86 microarchitectures, operations on subnormals trap to microcode and run 10×–100× slower than normal arithmetic. This is why audio DSP code and ML inference kernels set FTZ (flush-to-zero) and DAZ (denormals-are-zero) — in PyTorch, `torch.set_flush_denormal(True)`. Apple silicon handles subnormals in hardware without the penalty in most cases, which means a kernel that is fine on your M3 laptop can fall off a cliff on the x86 inference box. Measure on the target.

### The reduced-precision formats, computed exactly

Every one of these is the same layout — sign, exponent, fraction — with a different split. Nothing new is happening. This is the entire content of "quantization" in Week 26, and it is worth being able to derive the ranges cold.

| Format | S/E/M bits | Exponent bias | Max finite | Min normal | Machine epsilon | Decimal digits |
|---|---|---|---|---|---|---|
| fp64 | 1/11/52 | 1023 | 1.7976931 × 10³⁰⁸ | 2.2250739 × 10⁻³⁰⁸ | 2.2204460 × 10⁻¹⁶ | ~15.9 |
| fp32 | 1/8/23 | 127 | 3.4028235 × 10³⁸ | 1.1754944 × 10⁻³⁸ | 1.1920929 × 10⁻⁷ | ~7.2 |
| **bf16** | **1/8/7** | **127** | **3.3895314 × 10³⁸** | **1.1754944 × 10⁻³⁸** | **7.8125 × 10⁻³ (2⁻⁷)** | **~2.4** |
| fp16 | 1/5/10 | 15 | 6.5504 × 10⁴ | 6.1035156 × 10⁻⁵ | 9.765625 × 10⁻⁴ | ~3.3 |
| fp8 E4M3 | 1/4/3 | 7 | 4.48 × 10² | 1.5625 × 10⁻² | 1.25 × 10⁻¹ | ~0.9 |
| fp8 E5M2 | 1/5/2 | 15 | 5.7344 × 10⁴ | 6.1035156 × 10⁻⁵ | 2.5 × 10⁻¹ | ~0.6 |

The bf16 row is the one that explains the last five years of ML hardware. **bf16 has exactly the same 8 exponent bits as fp32**, so it has the same dynamic range — max 3.39 × 10³⁸, min normal 1.18 × 10⁻³⁸, verified above by constructing the bit patterns `0x7F7F0000` and `0x00800000` and reading them back as fp32. Converting fp32 to bf16 is, to a first approximation, *truncating the low 16 bits*. Nothing overflows and nothing underflows.

fp16, by contrast, has 5 exponent bits and a minimum normal of 6.1 × 10⁻⁵. Typical gradient magnitudes in a transformer sit around 10⁻⁷ to 10⁻⁹. In fp16 they flush to zero and training silently stops learning — which is precisely why fp16 mixed-precision training needs *loss scaling* (multiply the loss by ~2¹⁵ before the backward pass, unscale before the optimiser step) and bf16 does not. That single fact is why every TPU, every A100/H100 tensor core path, and every modern LLM training recipe defaults to bf16 rather than fp16, even though bf16 has 3 fewer mantissa bits.

Derivation you should be able to do in an interview: bf16 has 7 stored mantissa bits, so 8 bits of significand, so machine epsilon is 2⁻⁸ = 0.00390625 and the *unit roundoff* is 2⁻⁸ = 0.0078125 depending on convention — measured above as 0.0078125 for the "gap above 1.0" definition, i.e. the smallest x such that `1.0 + x != 1.0` in bf16. Decimal digits: log₁₀(2⁸) = 2.41. bf16 gives you between two and three significant decimal digits. It works for neural network weights because gradient descent is a stochastic process that is already averaging over noise far larger than 0.4%.

### Production failure modes and how you detect them

| Failure | Signature you will actually see | Detection |
|---|---|---|
| fp32 accumulator saturating | a metric that rises and then flatlines at a suspiciously round-in-binary value | assert the sum against an integer accumulator on a sample; use `dtype=` on reductions |
| fp16 gradient underflow | loss goes flat, gradient norm reads exactly `0.0`, no error | log `grad_norm` every step; switch to bf16, or enable `GradScaler` |
| Overflow to `inf` in fp16 attention scores | loss becomes `nan` two steps after a `inf` appears | `torch.autograd.set_detect_anomaly(True)` in a repro run; check for `inf` before the softmax |
| Endianness on the wire | works between two Linux x86 boxes, garbage against a JVM or a network appliance | round-trip test in CI with an explicitly big-endian fixture |
| UTF-8 length mismatch | `VARCHAR(n)` insert fails only for certain users, usually non-Latin names or emoji | test fixtures containing `नमस्ते` and `👩‍💻`; assert on code points, not bytes, at the API boundary |
| Signed overflow deleted by the optimiser | check works at `-O0`, disappears at `-O2` | build the test suite at `-O2` too; run `-fsanitize=undefined` in CI |

### Frontier and research pointers

- **Goldberg, "What Every Computer Scientist Should Know About Floating-Point Arithmetic" (ACM Computing Surveys, 1991).** Takeaway: rounding error is not randomness — it is a deterministic, analysable function of the operation order, and you can bound it.
- **Kahan, "How JAVA's Floating-Point Hurts Everyone Everywhere" (1998).** Takeaway: a language that forbids extended-precision intermediates in the name of reproducibility makes numerically naive code *less* accurate, not more.
- **Micikevicius et al., "Mixed Precision Training" (ICLR 2018, arXiv:1710.03740).** Takeaway: fp16 training works if and only if you keep an fp32 master copy of the weights and scale the loss to move gradients out of the fp16 subnormal range.
- **Kalamkar et al., "A Study of BFLOAT16 for Deep Learning Training" (arXiv:1905.12322, 2019).** Takeaway: matching fp32's *exponent* range matters far more than matching its mantissa, so bf16 trains without loss scaling at fp16's memory cost.
- **Micikevicius et al., "FP8 Formats for Deep Learning" (arXiv:2209.05433, 2022).** Takeaway: two fp8 formats are needed, not one — E4M3 for forward activations and weights, E5M2 for gradients, because the two have different range-versus-precision needs.
- **Unicode Standard Annex #29, "Unicode Text Segmentation" (Unicode 16.0).** Takeaway: "character" is not one concept — code point, code unit and grapheme cluster are three different counts, and your API must state which one it means.

### Stretch challenge

Write `fp32_to_bf16()` two ways: (a) plain truncation of the low 16 bits, and (b) round-to-nearest-even, which adds `0x7FFF + ((bits >> 16) & 1)` before truncating. Then:

1. Download any small model's weight tensor (a 4 MB `.safetensors` file is fine) and convert it both ways.
2. Report the mean and max **relative** error of each method against the fp32 original, and the fraction of weights where the two methods disagree.
3. Predict, before measuring, whether truncation introduces a *bias* (a non-zero mean error) and in which direction. Then check.
4. Now do the same for a tensor of activations after a GELU, which is asymmetric around zero. Does your answer to (3) change?

There is no single right answer to the follow-up: at what point does the bias from truncation actually degrade a downstream benchmark score, and is that point different for weights than for the KV cache? Bring a number and an argument.

## Apply it at work

<AccordionGroup>
<Accordion title="If you're a student" icon="graduation-cap">

**Portfolio line:** *"binviz — a 90-line C tool that shows the bit-level representation of any integer, float or UTF-8 string, verified byte-for-byte against `hexdump`."* Small, but it is a tool, not a homework exercise, and the README can carry the bf16 range table you derived.

**The interview angle.** "Why does `0.1 + 0.2 != 0.3`?" is asked constantly and almost everyone answers "floating point is imprecise", which scores zero. The answer that scores is: *0.1 has no exact binary representation, so both operands are rounded before the addition; the result is one ULP — 5.55 × 10⁻¹⁷ at that magnitude — above the nearest double to 0.3. Here are the two bit patterns; they differ in the last bit.* Being able to say the bit patterns is the difference between "has heard of it" and "has looked".

The follow-up you should prepare for is "so how do you compare floats?" and the follow-up to *that* is "how would you store money?" — answer: integer minor units (cents) or a fixed-point decimal type, never a binary float, because 0.01 is not representable and a million additions will drift.
</Accordion>
<Accordion title="If you're working" icon="briefcase">

Three places this shows up in a normal engineering week:

1. **The `VARCHAR(255)` incident.** A signup form rejects a user in Mumbai or Osaka whose name is well under 255 characters. Cause: the column counts bytes (MySQL `utf8mb4` counts characters, but many ORM-generated Postgres `varchar` limits are applied client-side against a byte length, and Java's `String.length()` counts UTF-16 code units). The fix is a decision, not a patch: state at each boundary whether the limit is bytes, code points or grapheme clusters, and test with `👩‍💻` in your fixtures.

2. **The metric that flatlines.** A Prometheus-style counter or an in-process aggregate stored as fp32 stops moving after a few hours. It has hit the absorption threshold. Search your codebase for `float32` on anything named `total`, `sum`, `count` or `bytes` — those are all integers, and they should be `int64`/`uint64`.

3. **The JSON number that changed.** JavaScript's `Number` is fp64, so any integer above 2⁵³ (9,007,199,254,740,991) loses precision when it passes through a browser or a Node service. Snowflake IDs, Twitter/X IDs, Postgres `bigint` primary keys and nanosecond timestamps are all above that line. The fix is to serialise them as strings — which is exactly why every large API you have used returns `"id": "1234567890123456789"` rather than a bare number.
</Accordion>

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| `if (x + 1 < x)` never fires at `-O2` but fires at `-O0` | signed overflow is UB; the optimiser assumes it cannot occur and folds the test to `false` | test without overflowing: `if (x > INT_MAX - 1)`; build tests at `-O2`; run `-fsanitize=undefined` in CI |
| Loop `for (int i = 0; i <= len - 1; ...)` hangs on an empty string | `len` is `size_t`; `0 - 1` wraps to 18446744073709551615 | use `for (size_t i = 0; i < len; i++)`; enable `-Wsign-compare` (included in `-Wextra`) |
| `memcpy` with a huge length after a passing bounds check | a negative `int` length cast to `size_t` | type the length `size_t` at the boundary and reject error sentinels before casting |
| Binary file written on Linux is garbage on a network appliance | struct written directly to disk/socket in host (little-endian) order | serialise field by field with `htonl`/`htons`, or use a schema format (protobuf, CBOR) |
| Emoji breaks a length check that passes in tests | test fixtures are ASCII-only; byte length vs code point vs grapheme cluster confused | add `é`, `→`, `👩‍💻`, `नमस्ते` to fixtures; decide and document which count each API uses |
| `assert(a == b)` on computed floats fails intermittently | exact equality on values produced by different operation orders | compare with a tolerance: `math.isclose(a, b, rel_tol=1e-9)` or `fabs(a-b) <= 1e-9 * fmax(fabs(a), fabs(b))` |
| fp16 training loss goes flat, no error raised | gradients below fp16 min normal 6.1 × 10⁻⁵ flush to zero | switch to bf16 (same exponent range as fp32), or enable loss scaling with `torch.cuda.amp.GradScaler` |
| `hexdump` shows one more byte than characters typed | shell `echo` appends `\n` (0x0a) | use `printf '%s'` instead of `echo`, or `echo -n` |

- **[Goldberg, D. (1991).
