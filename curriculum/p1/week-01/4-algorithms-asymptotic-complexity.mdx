### The one idea

"Faster" is not a property of an algorithm. It is a property of an algorithm *at a size*. What you want to know is not "how long does this take" but "when I make the input ten times bigger, what happens to the time?" — because that question has an answer that does not depend on your laptop, the weather, or what Chrome is doing.

The answer is a **growth rate**, and there are only about six of them you will meet in practice.

### The analogy

You are looking for a name in a phone book with a million names.

- **Linear search** — start at page 1, read every name. Worst case: a million reads. Double the phone book, double the work.
- **Binary search** — open in the middle. Is the name before or after? Throw away half. Repeat. Twenty steps and you are done, because 2²⁰ ≈ 1,000,000. Double the phone book and it costs you *one extra step*.

That difference — a million versus twenty — is the whole subject. And notice what binary search needed that linear search did not: the book had to be **sorted**. That is why sorting matters.

### The vocabulary, defined

- **Input size (n)** — how much data. Number of array elements, number of rows, length of the string. Say what n *is* before you say anything about complexity.
- **Basic operation** — the thing you count. For sorting, a comparison. For searching, a probe. Choosing one and counting it is the whole method.
- **Growth rate** — how the count of basic operations changes as n grows.
- **Big-O (O)** — an *upper bound* on growth. "O(n²)" means: beyond some size, the count is at most some constant times n². It deliberately ignores constants and small terms, because those depend on your machine and the growth rate does not.
- **Big-Omega (Ω)** — a *lower bound*. "at least this much."
- **Big-Theta (Θ)** — both. "exactly this growth rate." When people say O(n log n) about merge sort they usually mean Θ.
- **Invariant** — a statement that is true before the loop, stays true after every iteration, and is therefore true at the end. It is how you prove a loop is correct instead of hoping.
- **In-place** — uses O(1) extra memory beyond the input.
- **Stable sort** — equal elements keep their original relative order. Matters when you sort by one key after another.
- **Recursion** — a function that calls itself on a smaller version of the problem.
- **Divide and conquer** — split the problem in half, solve both halves, combine.

### Counting by hand: selection sort on n = 8

Selection sort: find the smallest element, swap it to the front, repeat on the rest.

```
pass 1: scan positions 1..7 to find the min  -> 7 comparisons
pass 2: scan positions 2..7                  -> 6 comparisons
pass 3:                                      -> 5
...
pass 7:                                      -> 1
                                          total 28
```

7 + 6 + 5 + 4 + 3 + 2 + 1 = 28. In general it is (n−1) + (n−2) + … + 1 = **n(n−1)/2**. For n = 8 that is 8 × 7 / 2 = 28. ✓

That formula has an n² in it, so we say selection sort is **O(n²)**. And this is not an estimate — the instrumented program below counts exactly 511,984,000 comparisons at n = 32,000, and 32000 × 31999 / 2 = 511,984,000 exactly.

### The growth table you should be able to reproduce

| n | log₂ n | n | n log₂ n | n² |
|---|---|---|---|---|
| 10 | 3.3 | 10 | 33 | 100 |
| 1,000 | 10 | 1,000 | 9,966 | 1,000,000 |
| 1,000,000 | 20 | 1,000,000 | 19,931,569 | 1,000,000,000,000 |

Read the last row slowly. At a million elements, n log n is about 20 million operations — a small fraction of a second. n² is a **trillion** — at a billion operations per second, that is about 17 minutes. Same machine, same data, different algorithm.

### Smallest working example

```c
#include <stdio.h>

/* returns the index of `key`, or -1. Requires a sorted array. */
int binary_search(const int *a, int n, int key) {
    int lo = 0, hi = n;                 /* invariant: answer is in [lo, hi) */
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;   /* not (lo+hi)/2 — see Layer 2 */
        if (a[mid] == key) return mid;
        if (a[mid] <  key) lo = mid + 1;
        else               hi = mid;
    }
    return -1;
}

int main(void) {
    int a[] = {2, 4, 8, 16, 32, 64, 128, 256};
    int n = (int)(sizeof a / sizeof a[0]);
    printf("%d %d %d\n",
           binary_search(a, n, 32),    /* 4  */
           binary_search(a, n, 2),     /* 0  */
           binary_search(a, n, 5));    /* -1 */
    return 0;
}
```

### Line-by-line walkthrough

- `int lo = 0, hi = n;` — the search window is the **half-open interval** `[lo, hi)`: `lo` is included, `hi` is not. Half-open intervals are how you avoid every off-by-one in this algorithm. Note `hi = n`, not `n - 1`.
- `while (lo < hi)` — keep going while the window is non-empty. An empty window means `lo == hi` and the key is not present.
- `int mid = lo + (hi - lo) / 2;` — the midpoint. Written this way instead of `(lo + hi) / 2` because the latter can overflow when `lo` and `hi` are both large. This is a real bug that sat in the Java standard library for nine years; Layer 2 has the story.
- `if (a[mid] == key) return mid;` — found it.
- `if (a[mid] < key) lo = mid + 1;` — the key is bigger than the midpoint, so it is somewhere strictly after `mid`. We can exclude `mid` itself, hence `+ 1`. Forgetting the `+ 1` is the standard infinite loop.
- `else hi = mid;` — the key is smaller, so it is somewhere strictly before `mid`. Since `hi` is exclusive, `hi = mid` already excludes `mid`. **No `- 1` here.** The asymmetry (`mid + 1` on one side, `mid` on the other) is not arbitrary; it falls directly out of the half-open interval.

**The invariant**, stated properly: *if the key is in the array at all, its index is in `[lo, hi)`.* It is true before the loop (`[0, n)` is the whole array). Each branch preserves it. When the loop exits, the window is empty, so the key is not present. That is a proof, and it took three sentences.

<Step title="Break it three ways, then fix each">
Change `lo = mid + 1` to `lo = mid`. Search for 5. The program hangs — `mid` stops moving once the window is two wide. Change `hi = mid` to `hi = mid - 1`. Search for 2. It returns −1 for a key that exists. Change `hi = n` to `hi = n - 1`. Search for 256. It returns −1, because the last element is now excluded from the very first window.

Each of those is a real bug found in real code review. Run all three.
</Step>
<Step title="Write selection sort, with the comparison counter">

```c
static long long comparisons = 0;

void selection_sort(int *a, size_t n) {
    for (size_t i = 0; i + 1 < n; i++) {
        size_t m = i;                        /* index of the smallest so far */
        for (size_t j = i + 1; j < n; j++) {
            comparisons++;
            if (a[j] < a[m]) m = j;
        }
        int t = a[i]; a[i] = a[m]; a[m] = t;
    }
}
```

Invariant: *after pass `i`, positions `0..i` hold the `i+1` smallest elements, in order.*

Run it on n = 8, 80 and 800 and print `comparisons` each time. You should get exactly 28, 3,160 and 319,600 — and n(n−1)/2 gives 28, 3160, 319600. Your counter is now a check on your understanding, not just a number.
</Step>
<Step title="Predict before you measure">
Before running anything at n = 32,000: selection sort will do 32000 × 31999 / 2 = 511,984,000 comparisons. If your machine does roughly 5 × 10⁸ simple operations per second in this loop, predict the time. Then measure. (Measured on this machine: **890 ms**.)
</Step>
</Steps>

<Accordion title="Checkpoint — 5 questions before you continue">

1. **Why does Big-O drop constants?** — because constants depend on the machine and the growth rate does not. An algorithm that is 100× slower per operation but O(n log n) beats an O(n²) one at some n, always.
2. **What is the exact comparison count of selection sort?** — n(n−1)/2, every time, regardless of input order. Selection sort has no best case.
3. **Why is `mid = lo + (hi - lo) / 2` preferred over `(lo + hi) / 2`?** — the sum can overflow when both are near the maximum int; the subtraction form cannot.
4. **What does the binary search invariant buy you?** — a proof of correctness in three sentences, and a mechanical way to decide whether each branch needs a `+ 1`.
5. **Binary search on an unsorted array — what happens?** — it returns a wrong answer, quietly. No crash, no error. The precondition is part of the contract and nothing enforces it.
</Accordion>

### Recurrences: where n log n comes from

Merge sort splits the array in half, sorts both halves, and merges them in linear time. As a recurrence:

```
T(n) = 2·T(n/2) + Θ(n)
T(1) = Θ(1)
```

Unroll it. At depth 0 you do n work in one merge. At depth 1, two merges of n/2 each — still n. At depth k, 2ᵏ merges of n/2ᵏ — still n. The recursion bottoms out at depth log₂ n. So the total is n work per level × log₂ n levels = **Θ(n log n)**.

The **Master Theorem** packages this: for `T(n) = a·T(n/b) + f(n)`, compare f(n) against n^(log_b a). Merge sort has a = 2, b = 2, so n^(log₂ 2) = n, and f(n) = Θ(n) matches, giving Θ(n log n). Binary search has a = 1, b = 2, f(n) = Θ(1), so n^(log₂ 1) = n⁰ = 1, which matches, giving Θ(log n). You should be able to do those two from memory; the third case (f dominating) shows up in Week 14.

|---|---|---|---|---|---|---|
| 1,000 | 1.04 | 0.043 | 0.051 | 499,500 | 8,677 | 9,904 |
| 4,000 | 11.15 | 0.184 | 0.257 | 7,998,000 | 42,803 | 49,490 |
| 16,000 | 203.75 | 0.810 | 1.232 | 127,992,000 | 203,393 | 226,362 |
| 32,000 | 890.35 | 1.888 | 2.793 | 511,984,000 | 438,675 | 489,441 |
| 128,000 | — | 6.879 | 11.988 | — | 2,010,228 | 2,252,352 |
| 1,000,000 | — | 63.05 | 110.06 | — | 18,673,546 | 21,042,240 |

Fitted exponents, from the ratio of the endpoints (slope on log-log axes):

- **selection sort**: ln(890.35 / 1.039) / ln(32) = **1.95**. That is n².
- **merge sort**: ln(63.05 / 0.043) / ln(1000) = **1.06**. That is n log n — slightly above 1, and the excess is the log factor.
- **`qsort`**: ln(110.06 / 0.051) / ln(1000) = **1.11**.

At n = 32,000, selection sort is **471× slower** than merge sort. The comparison counts explain it exactly: 511,984,000 versus 438,675, a ratio of 1,167 — larger than the time ratio because selection sort's inner loop is a tight, perfectly-predicted, cache-friendly scan and merge sort's is not. The algorithm won by three orders of magnitude while losing on constants by a factor of 2.5. That is Big-O in one sentence.

Sanity-check the counts against theory. Merge sort's comparison count is bounded by n·log₂n − n + 1; at n = 1,000,000 that is 19,931,569 − 999,999 = 18,931,570, and we measured **18,673,546**. Within 1.4%. If your instrumented count is not close to the formula, your implementation is wrong, and that is a better test than any unit test.

### Why your merge sort beat the C library

`qsort` did 21,042,240 comparisons to merge sort's 18,673,546 — 12.7% more, which is expected for a randomized-pivot quicksort. But it took **110.06 ms versus 63.05 ms, 1.75× slower**. The extra 12.7% of comparisons cannot explain a 75% time difference.

The reason is the interface. `qsort`'s signature is:

```c
void qsort(void *base, size_t nmemb, size_t size,
           int (*compar)(const void *, const void *));
```

Every single comparison is an **indirect call through a function pointer**, to a function that takes `void *` arguments it must cast and dereference. It cannot be inlined, because the compiler does not know which function it is. Twenty-one million indirect calls, each with argument setup, a call, two dereferences, a subtraction, and a return. Merge sort's comparison is `a[j] < a[i]` — one instruction, inlined, branch-predicted.

This is why C++ `std::sort` (which takes the comparator as a *template parameter*, so it inlines) is typically 2–3× faster than C's `qsort` on the same algorithm, and it is why Rust's `sort_unstable` and Go's `slices.SortFunc` (generic, monomorphised) are fast. **Genericity through function pointers costs; genericity through monomorphisation does not.** You will meet this exact trade again in Week 21 when a Python callback in a training loop turns out to be the bottleneck.

### The crossover: when O(n²) wins

Insertion sort versus merge sort at small n, average over 200,000 iterations each:

| n | insertion (ns) | merge (ns) | winner |
|---|---|---|---|
| 8 | 20.0 | 82.5 | insertion, 4.1× |
| 32 | 199.5 | 434.0 | insertion, 2.2× |
| 64 | 723.0 | 1,187.5 | insertion, 1.6× |
| **96** | **1,699.7** | **1,643.8** | **merge, barely — this is the crossover** |
| 256 | 9,965.3 | 6,038.4 | merge, 1.65× |
| 512 | 37,838.1 | 13,227.1 | merge, 2.9× |

The crossover on this machine is at **n ≈ 96**. Below that, the O(n²) algorithm wins, for three concrete reasons: no recursion overhead, no auxiliary array and therefore no allocation, and a completely sequential memory access pattern that the hardware prefetcher handles perfectly.

Every real sort in every real standard library exploits this:

- **libstdc++ `std::sort`** is introsort: quicksort, switching to insertion sort below 16 elements, and to heapsort if recursion depth exceeds 2·log₂n (which bounds the worst case at O(n log n) instead of quicksort's O(n²)).
- **CPython's `list.sort` and Java's `Arrays.sort` for objects** are Timsort: identify already-sorted "runs", extend short runs to a `minrun` of 32–64 using **binary insertion sort**, then merge. The 32–64 figure is not folklore; it is exactly this crossover, measured.
- **Rust's `slice::sort`** is a Timsort derivative; `sort_unstable` is pattern-defeating quicksort (pdqsort), which adds median-of-three-of-medians pivot selection and a special case for many-duplicates.

### Trade-offs table

| Decision | Choose X when… | Choose Y when… |
|---|---|---|
| Merge sort vs quicksort | **Merge sort** when you need stability (sorting by secondary key first), a guaranteed O(n log n) worst case (adversarial input, SLA), or you are sorting a linked list or an external file where sequential access is all you have | **Quicksort/introsort** when you need in-place O(log n) memory and average-case speed, and you can accept the worst case being bounded by an introsort fallback |
| Sort-then-binary-search vs a hash set | **Sort + binary search** when you need range queries, ordered iteration, or predictable memory; O(n log n) once then O(log n) per query, no hashing cost | **Hash set** when you only need membership and equality; O(1) expected per query. Break-even for pure membership is roughly one query — but sorting also gives you `lower_bound`, which a hash cannot |
| Recursive vs iterative merge sort | **Recursive** for clarity; depth is log₂n, so 20 frames at n = 1,000,000 — trivial | **Iterative (bottom-up)** when the recursion is on untrusted depth, in an embedded context with a 4 KB stack, or when you want to avoid the call overhead at small subarray sizes |
| Hand-rolled sort vs the library | **The library**, essentially always: it is introsort or timsort, it is tested against adversarial inputs, and it handles the small-n case for you | **Hand-rolled** only when you have a measured reason: a fixed small n, a radix-sortable key (integers, fixed-width strings), or an external/streaming constraint the library cannot express |

### Reference implementation — merge sort with a single scratch buffer

```c
/* msort.c — top-down merge sort, one allocation, stable.
 * build: cc -std=c17 -O2 -Wall -Wextra msort.c -o msort */
#include <stdlib.h>
#include <string.h>

static void merge_run(int *a, int *tmp, size_t lo, size_t mid, size_t hi) {
    size_t i = lo, j = mid, k = lo;
    /* `a[j] < a[i]` and not `<=` is what makes this STABLE:
       on a tie we take from the left run first. */
    while (i < mid && j < hi) tmp[k++] = (a[j] < a[i]) ? a[j++] : a[i++];
    while (i < mid) tmp[k++] = a[i++];
    while (j < hi)  tmp[k++] = a[j++];
    memcpy(a + lo, tmp + lo, (hi - lo) * sizeof *a);
}

static void msort_rec(int *a, int *tmp, size_t lo, size_t hi) {
    if (hi - lo < 2) return;
    size_t mid = lo + (hi - lo) / 2;
    msort_rec(a, tmp, lo, mid);
    msort_rec(a, tmp, mid, hi);
    if (a[mid - 1] <= a[mid]) return;   /* already ordered: skip the merge */
    merge_run(a, tmp, lo, mid, hi);
}

int nx_merge_sort(int *a, size_t n) {
    if (n < 2) return 0;
    int *tmp = malloc(n * sizeof *tmp);
    if (!tmp) return -1;                 /* allocation can fail; say so */
    msort_rec(a, tmp, 0, n);
    free(tmp);
    return 0;
}
```

Four decisions worth defending in review:

1. **One allocation for the whole sort**, not one per recursive call. Allocating inside `msort_rec` turns 2n−1 recursive calls into 2n−1 `malloc`/`free` pairs — at the 31.85 ns per pair measured in Module 3, that is 63 ms of pure allocator time at n = 1,000,000, roughly doubling the runtime.
2. **`(a[j] < a[i])`, strictly less than.** On a tie the left element is taken first, which preserves input order among equals. That is stability, and it is a one-character decision.
3. **The `a[mid-1] <= a[mid]` early exit.** If the two halves are already in order, the merge is a no-op. This makes the sort O(n) on already-sorted input for free — one comparison per node.
4. **`nx_merge_sort` returns `int`.** It can fail. A sort that silently does nothing when `malloc` returns `NULL` is worse than one that crashes.

### What breaks in the real world

In 2006, Joshua Bloch published "Extra, Extra — Read All About It: Nearly All Binary Searches and Mergesorts Are Broken". The binary search in `java.util.Arrays`, in the JDK since 1.2 and reviewed by many of the best engineers in the industry, computed the midpoint as:

```java
int mid = (low + high) / 2;
```

For arrays longer than 2³⁰ ≈ 1.07 billion elements, `low + high` overflows a signed 32-bit `int` and becomes negative, so `mid` is negative and the next array access throws `ArrayIndexOutOfBoundsException`. The bug was in Jon Bentley's *Programming Pearls*, in the ACM's canonical reference implementation, and in nearly every textbook — because for twenty years no one had an array that big.

Three things to take from it. First, the fix is `int mid = low + ((high - low) / 2);`, or in Java `(low + high) >>> 1` using the unsigned shift. Second, this is the integer overflow from Module 1 arriving in the most reviewed algorithm in computer science, which should calibrate how much you trust "it's been in production for years". Third, and most usefully: the bug was found by *thinking about the precondition*, not by testing, because the test would have needed a 4 GB array. Some bugs are only reachable by reasoning.

<Accordion title="Design checkpoint — one question, with a model answer">

**Question.** A service holds 2 million records in memory and must answer "give me all records with score between X and Y, sorted by score" thousands of times a second. Records are updated a few hundred times a second. A colleague proposes a hash map from score to record list. What do you propose and why?

**Model answer.** A hash map is the wrong structure because the query is a **range** query, and hashing destroys order by design — answering "between X and Y" would require scanning every bucket, which is O(n) per query on 2 million records. That is the deciding fact, and it is worth stating before any performance argument.

Propose a sorted structure. Two candidates:

**Sorted array plus binary search.** Query is `lower_bound(X)` then a sequential walk to Y: O(log n) to find the start — 21 probes at n = 2,000,000 — then O(k) for k results, with perfect cache locality on the walk. The problem is updates: inserting into a sorted array is O(n) memmove, and at a few hundred updates a second on 2 million 32-byte records that is roughly 64 MB/s of memmove, which is survivable but wasteful.

**A B-tree or a skip list.** O(log n) for both query and update, ordered iteration for free. This is what you actually want, and it is exactly what a database index gives you — which is the point I would make in the design review: we are reimplementing a B-tree index, and if this data is already in Postgres, `CREATE INDEX ON records (score)` plus a range query does this at a level of tuning we will not match. Week 8 measures that.

If it must stay in-process, the pragmatic answer is a sorted array rebuilt periodically plus a small unsorted overlay of recent updates, merged at query time — the LSM-tree idea. Concretely: binary search the sorted base (21 probes), linear scan the overlay (bounded at, say, 10,000 entries), merge the two result streams, and rebuild the base when the overlay exceeds its bound. That trades a bounded amount of query work for O(1) updates, and it is the same structure RocksDB and Lucene use for the same reason.

The measurement that decides between them: read-to-write ratio and the size of k. If k is usually large, the sequential walk dominates and the sorted array's cache locality wins outright. If k is 1–10 and updates are frequent, the tree wins.
</Accordion>

### Big-O counts operations. The machine charges for cache misses.

Binary search is O(log n) probes. Here is what those probes actually cost, measured, on sorted `int` arrays:

| n | array size | linear search (ns) | binary search (ns) | probes | ns per probe |
|---|---|---|---|---|---|
| 1,000 | 4 KB | 211.6 | 28.3 | 10 | 2.8 |
| 10,000 | 40 KB | 1,802.5 | 20.9 | 14 | 1.5 |
| 100,000 | 400 KB | 18,226.5 | 76.9 | 17 | 4.5 |
| 1,000,000 | 4 MB | 192,225 | 120.0 | 20 | 6.0 |
| 10,000,000 | 40 MB | 2,002,740 | 870.0 | 24 | **36.3** |

Linear search scales exactly 10× per decade, as O(n) demands. Binary search's *probe count* grows from 10 to 24 — a factor of 2.4 — but its *time* grows from 28 ns to 870 ns, a factor of 31. The extra factor of 13 is entirely memory hierarchy: at 4 KB the whole array is in L1; at 40 MB every one of the first ~20 probes is a cache miss to DRAM, and 36 ns per probe is close to this machine's DRAM latency.

This is the most important correction to naive Big-O reasoning: **O(log n) with random access can be slower than O(n) with sequential access, up to a surprisingly large n.** At n = 1,000 linear search loses by 7.5×; the reason it does not lose by 100× is that the linear scan is prefetched and branch-predicted while binary search's next address depends on the current load. For a 64-element array, linear scan beats binary search on essentially every modern CPU, which is why small-map implementations in high-performance codebases (Abseil's `flat_hash_map`, LLVM's `SmallVector`) are linear.

The fix, when you genuinely need to search a large sorted array often, is **layout**, not algorithm: an Eytzinger (BFS) layout puts the binary search tree in breadth-first order so the first several probes share cache lines, and published results show 2–3× improvements over the classic layout at sizes above L2. The algorithm is still O(log n). Only the constant moved.

### Merge sort's real cost is memory traffic

Merge sort at n = 1,000,000 moved 18.67 M comparisons but also **copied every element log₂n = 20 times** — once per level, into `tmp` and back. That is 20 × 1,000,000 × 4 bytes × 2 (write to tmp, memcpy back) = **160 MB of memory traffic** for a 4 MB array.

Quicksort, by contrast, partitions in place: it also touches each element once per level, but with no auxiliary array and no copy-back. Its memory traffic is roughly half. That is why in-place algorithms win at sizes above cache even when they lose on comparison count — and it is why the measured `qsort` result (1.75× *slower* despite in-place partitioning) is so interesting: the function-pointer overhead was large enough to swamp a genuine memory-traffic advantage.

You can remove the copy-back entirely by alternating the roles of `a` and `tmp` at each recursion level ("ping-pong" merge sort), which cuts traffic roughly in half at the cost of a slightly more confusing implementation. Implement it and measure; on this machine it is worth measuring whether the win survives at n = 1,000,000 where the array is 4 MB and L2 is 16 MB per performance-core cluster.

### Branch misprediction, measured indirectly

The merge inner loop is `tmp[k++] = (a[j] < a[i]) ? a[j++] : a[i++];`. On random data that branch is unpredictable — roughly 50/50 — so the CPU mispredicts about half the time, and a misprediction on this class of core costs on the order of 12–20 cycles.

At n = 1,000,000 with 18.67 M comparisons, roughly 9.3 M mispredictions × ~15 cycles ≈ 140 M cycles ≈ **35 ms at 4 GHz**. The whole sort took 63 ms. Over half the runtime of merge sort on random data is branch misprediction.

This is why *branchless* merge is a real technique: compute both outcomes and select with a conditional move (`csel` on ARM64, `cmov` on x86) instead of branching. It does strictly more work and is faster on random data because it never mispredicts. The test to run: sort random data and nearly-sorted data with both versions. The branchy version should win on nearly-sorted input (predictable branch, less work) and lose on random. If you see that crossover, you have measured branch prediction directly without a profiler.

### Sorting lower bounds, and how to beat them

Any comparison-based sort needs Ω(n log n) comparisons in the worst case. The proof is a counting argument: there are n! possible orderings, each comparison yields one bit, so you need at least log₂(n!) bits, and by Stirling log₂(n!) ≈ n log₂n − n·log₂e ≈ n log₂n − 1.44n. At n = 1,000,000 that lower bound is **18,488,865 comparisons**. Our merge sort used **18,673,546** — within **1.0% of the information-theoretic optimum.** That is a satisfying thing to be able to compute.

The bound only applies to comparison sorts. **Radix sort** reads the key's digits instead of comparing, and runs in O(d·n) for d-digit keys — for 32-bit integers with 8-bit digits, four passes, O(4n). At n = 1,000,000 that is 4 M operations against 18.7 M comparisons, and radix sort routinely beats introsort by 2–4× on integer keys. It loses on: arbitrary comparators, memory (it needs counting arrays and usually an output buffer), and cache behaviour (scattered writes during the distribution pass). Use it when your keys are fixed-width integers or fixed-length strings and n is large. Do not use it for "sort these objects by a lambda".

### Production failure modes and how you detect them

| Failure | Signature | Detection |
|---|---|---|
| Quicksort worst case on adversarial input | p99 latency 1000× the median; CPU pegged on one request | randomized or median-of-three pivot; introsort depth limit; a hash-flooding-style regression test |
| Accidental O(n²) from a nested `in` check | fine in staging with 1,000 rows, 40× slower at 10,000 | plot time vs n on log-log; a slope near 2 is the whole diagnosis |
| Sort not stable when the code assumes it is | records with equal keys reorder between runs; "flaky" test | check the docs: `qsort` and `std::sort` are **not** stable; `std::stable_sort`, Python's `sorted`, Java object sort are |
| Binary search on a stale or unsorted array | wrong answer, no error, intermittent | assert sortedness in debug builds; make the sorted invariant a type (a `SortedVec` wrapper) |
| Midpoint overflow at 2³⁰ elements | `ArrayIndexOutOfBoundsException` / negative index, only at extreme scale | use `lo + (hi - lo) / 2`; it costs nothing |
| Benchmark measured on a loaded machine | numbers vary 10×+ between runs; conclusions flip | `CLOCK_PROCESS_CPUTIME_ID`, minimum of N, and report the load average you measured under |

### Frontier and research pointers

- **Musser, D. R. (1997). "Introspective Sorting and Selection Algorithms." *Software: Practice and Experience* 27(8).** One-sentence takeaway: cap quicksort's recursion depth at 2·log₂n and fall back to heapsort, and you get quicksort's average case with an O(n log n) worst-case guarantee — which is what `std::sort` has done ever since.
- **Peters, T. (2002). "Timsort" (CPython `listsort.txt`).** One-sentence takeaway: real-world data contains long already-sorted runs, so detecting and merging runs beats sorting from scratch — and the `minrun` of 32–64 exists precisely because insertion sort wins below the crossover we measured at n ≈ 96.
- **Bloch, J. (2006). "Nearly All Binary Searches and Mergesorts Are Broken." Google Research Blog.** One-sentence takeaway: `(low + high) / 2` overflows above 2³⁰ elements, and the bug survived twenty years in the canonical textbook implementation because nobody had an array that large.
- **Khuong, P.-V. & Morin, P. (2017). "Array Layouts for Comparison-Based Searching." *ACM Journal of Experimental Algorithmics* 22.** One-sentence takeaway: changing the memory *layout* of a sorted array (Eytzinger/BFS order) speeds up binary search by 2–3× at large n without changing a single comparison — the algorithm was never the bottleneck.
- **Frigo, M., Leiserson, C., Prokop, H. & Ramachandran, S. (1999). "Cache-Oblivious Algorithms." *FOCS*.** One-sentence takeaway: divide-and-conquer that recurses down to base cases automatically achieves near-optimal cache behaviour at every level of the hierarchy without knowing any cache parameters.
- **Kim, C. et al. (2010). "FAST: Fast Architecture Sensitive Tree Search on Modern CPUs and GPUs." *SIGMOD*.** One-sentence takeaway: once you lay out a search tree to match cache line, SIMD width and page size, search throughput improves by an order of magnitude — the same O(log n) with the constants engineered.

### Stretch challenge

Find your machine's real crossover surface, not just a point.

1. Implement insertion sort, merge sort, and a hybrid merge sort with a tunable `CUTOFF` below which it calls insertion sort.
2. Sweep `CUTOFF` from 1 to 256 at n = 1,000,000 on random data and plot time versus `CUTOFF`. Find the optimum. Is it near the n ≈ 96 crossover we measured, or lower? Explain the difference — the hybrid's base case is a *subarray already in cache*, which is not the same experiment as sorting a fresh 96-element array.
3. Now repeat on three input distributions: random, already sorted, and reverse sorted. Does the optimal `CUTOFF` move? By how much?
4. Add a branchless merge using a conditional move, and repeat step 3. Predict, before measuring, on which distribution the branchless version loses.

The open question with no single right answer: your library ships one `CUTOFF`. You have three optimal values for three distributions, and you cannot see the caller's data. What do you ship, and would you instead detect runs at run time like Timsort — and what does that detection cost on data with no runs? Bring numbers.

## Apply it at work

<AccordionGroup>
<Accordion title="If you're a student" icon="graduation-cap">

**Portfolio line:** *"A sorting benchmark harness in C that instruments comparison counts alongside CPU time, verifies both against the theoretical formulas, and fits the empirical growth exponent — measured 1.95 for selection sort and 1.06 for merge sort."* The verification against theory is the part that makes an interviewer sit up.

**The interview angle.** Everyone can say "merge sort is O(n log n)". The three things that separate a strong answer:

- **State the invariant.** "The answer is in the half-open interval `[lo, hi)`" answers all the off-by-one follow-ups at once.
- **Know where the constant lives.** "My merge sort beat `qsort` by 1.75× because `qsort` makes an indirect call per comparison and cannot inline the comparator" is a systems answer to an algorithms question, and it is what a staff interviewer is fishing for.
- **Know the lower bound.** "log₂(n!) ≈ 18.5 million comparisons at n = 1,000,000, and my implementation used 18.67 million, so I am within 1% of optimal" ends the conversation in your favour.

Prepare the follow-up: "when would you not use O(n log n)?" — radix sort for integer keys, or insertion sort below the crossover, and you have the measured crossover.
</Accordion>
<Accordion title="If you're working" icon="briefcase">

Three places this shows up in a normal engineering week:

1. **The endpoint that got slow after the data grew.** Before profiling, plot response time against row count on log-log axes with three or four data points. A slope near 2 means you have a nested loop or an `in` check on a list, and you can usually find it by grepping for a loop containing a `.filter(` or a lookup. This diagnosis takes ten minutes and skips an afternoon of flame graphs.

2. **The p99 that is 1000× the median.** Sorting is a common cause: a code path that hits quicksort's worst case, or a comparator that is O(k) per comparison (comparing long strings, or deserialising inside the comparator). Check whether your language's sort is introsort-guarded and whether your comparator is cheap. Precompute the sort key — the Schwartzian transform / `key=` argument — rather than computing it inside the comparison.

3. **Reviewing a "we need a faster machine" request.** The measured 471× gap between two correct sorting algorithms at n = 32,000 is a bigger factor than any hardware upgrade you can buy. Ask for the growth curve before approving the instance-size bump; if the slope is 2, hardware buys you a 2× bigger input and nothing more.
</Accordion>

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Binary search hangs | `lo = mid` instead of `lo = mid + 1` when going right | with a half-open window: `lo = mid + 1` on the right branch, `hi = mid` on the left |
| Binary search misses the last element | window initialised as `[0, n-1]` while the loop treats `hi` as exclusive | pick one convention — half-open `[0, n)` — and make every line obey it |
| Negative index at ~1 billion elements | `(lo + hi) / 2` overflowed | `lo + (hi - lo) / 2` |
| Sort result reorders equal elements | `qsort` and `std::sort` are not stable | use `std::stable_sort`, Python `sorted`, or add a tiebreaker field to the comparator |
| Merge sort is slower than expected | allocating the scratch buffer inside the recursion | allocate once in the wrapper; at n = 1e6 this is ~63 ms of allocator time saved |
| "It's O(n log n) so it should be fast" but it is not | the constant is a function-pointer call, a string comparison, or a cache miss per probe | count the operations *and* measure; compare with the theoretical count |
| Benchmark numbers vary 10× run to run | wall-clock timing on a loaded machine | `CLOCK_PROCESS_CPUTIME_ID`, minimum of N runs, report load average |
| Recursion depth crash on a huge sort | recursing on the larger half first, or quicksort worst case | recurse on the smaller half and loop on the larger (tail-call), or use introsort's depth limit |

## Sources & further reading

**Primary docs**

- **`man 3 qsort` (macOS 15) and the glibc `qsort` source (`stdlib/msort.c`).** Read this for the surprise that glibc's `qsort` is actually a merge sort when memory allows, falling back to quicksort only under memory pressure — the name is a lie and the behaviour is documented in the source, not the man page.
- **[CPython `Objects/listsort.txt`.](https://github.com/python/cpython/blob/main/Objects/listsort.txt)** Read this for Tim Peters' own explanation of run detection, `minrun` selection and the merge invariants; it is the best-written design document in any standard library.
- **libstdc++ `bits/stl_algo.h`, `__introsort_loop` and `__final_insertion_sort`.** Read this for the exact 16-element threshold and the `2 * log2(n)` depth limit, in the shipping source rather than in a summary.

**Papers**

- **[Musser, D. R. (1997). "Introspective Sorting and Selection Algorithms." *Software: Practice and Experience* 27(8), 983–993.](https://doi.org/10.1002/%28SICI%291097-024X%28199708%2927:8%3C983::AID-SPE117%3E3.0.CO;2-%23)** One-sentence takeaway: bounding quicksort's recursion depth and switching to heapsort converts a quadratic worst case into a guaranteed O(n log n) at essentially no average-case cost.
- **Bloch, J. (2006). "Nearly All Binary Searches and Mergesorts Are Broken."** One-sentence takeaway: the canonical binary search overflows its midpoint computation above 2³⁰ elements, and the bug survived two decades of review because reaching it required an array nobody had.
- **[Khuong, P.-V. & Morin, P. (2017). "Array Layouts for Comparison-Based Searching." *ACM JEA* 22, 1.3.](https://doi.org/10.1145/3053370)** One-sentence takeaway: reordering a sorted array into Eytzinger (breadth-first) layout makes binary search 2–3× faster at large n purely by improving cache-line utilisation.
- **[Frigo, M., Leiserson, C. E., Prokop, H. & Ramachandran, S. (1999). "Cache-Oblivious Algorithms." *FOCS*, 285–297.](https://doi.org/10.1109/SFFCS.1999.814600)** One-sentence takeaway: recursive divide-and-conquer down to a small base case is automatically within a constant factor of optimal for *every* level of the memory hierarchy, without tuning.

**Go deeper**

- **Cormen, Leiserson, Rivest & Stein, *Introduction to Algorithms*, 4th ed., Chapters 2–4.** The loop-invariant proofs for insertion sort and merge sort in Chapter 2, and the Master Theorem in Chapter 4, are the reference the rest of the field cites; do the exercises on recurrences before Week 14.
- **[Sedgewick & Wayne, *Algorithms*, 4th ed., §2.2–2.3 and the accompanying "doubling test" methodology.](https://algs4.cs.princeton.edu/home/)** The doubling test — run at n, then 2n, and take the ratio — is the fastest way to get an empirical exponent in the field, and it is exactly the method used for the measured table above.
