### The one idea

Four tools turn a script into something a team can maintain: **types** so mistakes are caught before running, **tests** so behaviour is checked automatically, **a linter and formatter** so style is never discussed again, and **a reproducible environment** so it runs the same everywhere.

None of them make your code work. All of them make it *stay* working while other people change it.

### The analogy

A recipe written for yourself is a list of steps. A recipe published in a book needs four extra things: **stated quantities and units** (types — "2 cups", not "some flour"), **a way to check it worked** (tests — "the skewer comes out clean"), **a consistent format** so every recipe reads the same way (formatter), and **a specific ingredient list** so someone in another country buys the right things (dependency pinning).

You do not need any of it to cook dinner tonight. You need all of it for someone else to cook it in two years.

### The vocabulary, defined

- **Type hint (annotation)** — a note in the source saying what type a variable or parameter holds: `def f(x: int) -> str:`. Python **does not enforce** it at runtime.
- **Static type checker** — a program that reads your annotations and finds contradictions without running the code. `mypy` is the standard one.
- **Test** — code that runs your code and asserts the result. If the assertion fails, the test fails.
- **`pytest`** — the standard Python test runner. Finds files named `test_*.py`, runs functions named `test_*`, and reports.
- **Fixture** — reusable test setup, provided by a function decorated `@pytest.fixture` and requested by naming it as a test parameter.
- **Parametrised test** — one test function run several times with different inputs.
- **Mock / monkeypatch** — replacing a real thing (a network call, the clock) with a fake for the duration of a test.
- **Coverage** — the percentage of your lines that ran during the tests. A weak signal; see below.
- **Linter** — a tool that finds suspicious code. `ruff`.
- **Formatter** — a tool that rewrites your code to one canonical style. `ruff format`.
- **Virtual environment (venv)** — a private directory of packages for one project, so two projects can use different versions.
- **`uv`** — a very fast package and environment manager, written in Rust. Replaces `pip` and `venv`.
- **`pyproject.toml`** — the standard configuration file: project metadata, dependencies, and tool settings.
- **Lockfile** — a file recording the **exact** version of every package, including transitive dependencies, so installs are reproducible.
- **Property-based test** — instead of "for this input, expect this output", you state a rule that must hold for *all* inputs and let a tool generate them. `hypothesis`.

### Smallest working example

```python
# money.py
def split_evenly(total_cents: int, parts: int) -> list[int]:
    """Split `total_cents` into `parts` shares that sum to the total."""
    if parts <= 0:
        raise ValueError("parts must be positive")
    share = total_cents // parts
    result = [share] * parts
    result[0] += total_cents - share * parts
    return result
```

```python
# test_money.py
import pytest
from money import split_evenly


def test_exact():
    assert split_evenly(100, 4) == [25, 25, 25, 25]


def test_remainder_sums_correctly():
    assert sum(split_evenly(101, 4)) == 101


def test_one_part():
    assert split_evenly(7, 1) == [7]


def test_zero_parts_raises():
    with pytest.raises(ValueError, match="positive"):
        split_evenly(100, 0)
```

Set up and run:

```bash
uv venv && source .venv/bin/activate
uv pip install pytest
pytest -q
```

```
....                                                    [100%]
4 passed in 0.44s
```

Four tests, all green. **The function has a bug.** Layer 2 finds it.

### Line-by-line walkthrough

- `def split_evenly(total_cents: int, parts: int) -> list[int]:` — the annotations say two ints in, a list of ints out. Python ignores them at runtime; `mypy` uses them; humans read them first.
- `"""Split ..."""` — the docstring. It should say what the function guarantees, and it is the thing your property tests will be derived from.
- `raise ValueError("parts must be positive")` — validate arguments at the boundary.
- `total_cents // parts` — floor division, giving an integer.
- `import pytest` then `def test_exact():` — pytest discovers any function whose name starts with `test_`. No class, no registration.
- `assert split_evenly(100, 4) == [25, 25, 25, 25]` — a plain `assert`. pytest rewrites assertions so a failure shows both sides, which is why you do not need `assertEqual`.
- `with pytest.raises(ValueError, match="positive"):` — asserts that the block raises, **and** that the message matches. Without `match`, the test passes even if a completely different `ValueError` occurs — including one from a typo in your own test.

<Step title="Use a fixture for shared setup">

```python
import pytest
from pathlib import Path


@pytest.fixture
def ledger_file(tmp_path: Path) -> Path:
    """A throwaway file. tmp_path is a pytest builtin: a fresh dir per test."""
    p = tmp_path / "ledger.csv"
    p.write_text("Aarav,100\nMeera,250\n", encoding="utf-8")
    return p


def test_reads_two_rows(ledger_file: Path):
    assert len(ledger_file.read_text().splitlines()) == 2
```

`tmp_path` is provided by pytest and cleaned up automatically. Tests that write into the current directory pollute the repository and fail when run in parallel; `tmp_path` costs nothing and prevents both.
</Step>
<Step title="Replace something you cannot control">

```python
import datetime as dt


def greeting(now: dt.datetime | None = None) -> str:
    now = now or dt.datetime.now(dt.UTC)
    return "good morning" if now.hour < 12 else "good afternoon"


def test_morning():
    assert greeting(dt.datetime(2025, 1, 1, 9, tzinfo=dt.UTC)) == "good morning"


def test_afternoon_via_monkeypatch(monkeypatch):
    class FakeDateTime(dt.datetime):
        @classmethod
        def now(cls, tz=None):
            return dt.datetime(2025, 1, 1, 15, tzinfo=dt.UTC)
    monkeypatch.setattr(dt, "datetime", FakeDateTime)
    assert greeting() == "good afternoon"
```

Two ways to make time testable, and **the first is better**: passing `now` as an optional parameter needs no mocking at all. Reach for `monkeypatch` only when you cannot change the signature — and note that `monkeypatch` undoes itself at the end of the test, which a manual assignment would not.
</Step>

<Accordion title="Checkpoint — 5 questions before you continue">

1. **Does Python enforce type hints at runtime?** — no. They are metadata. `mypy` checks them before you run; at runtime `f("hello")` on `def f(x: int)` runs happily.
2. **What does pytest need to find your test?** — a file named `test_*.py` (or `*_test.py`) and a function named `test_*`. Nothing else.
3. **Why `pytest.raises(ValueError, match="...")` rather than just `pytest.raises(ValueError)`?** — without `match`, any `ValueError` passes, including one caused by a bug in the test itself.
4. **What is `tmp_path`?** — a builtin fixture giving each test a fresh temporary directory, cleaned up afterwards.
5. **Four tests pass. Is the function correct?** — no. They prove it works for four inputs. Layer 2 finds an input that breaks it.
</Accordion>

### The bug the example tests missed

Three example tests passed. Now state the *properties* the docstring implies and let `hypothesis` generate inputs:

```python
from hypothesis import given, settings, strategies as st
from money import split_evenly


@given(total=st.integers(min_value=-10**9, max_value=10**9),
       parts=st.integers(min_value=1, max_value=1000))
@settings(max_examples=500)
def test_sum_is_preserved(total, parts):
    assert sum(split_evenly(total, parts)) == total


@given(total=st.integers(min_value=0, max_value=10**9),
       parts=st.integers(min_value=1, max_value=1000))
@settings(max_examples=500)
def test_shares_differ_by_at_most_one(total, parts):
    shares = split_evenly(total, parts)
    assert max(shares) - min(shares) <= 1
```

```
..F                                                        [100%]
_______________ test_shares_differ_by_at_most_one _______________

total = 2, parts = 3

>       assert max(shares) - min(shares) <= 1
E       assert (2 - 0) <= 1
E        +  where 2 = max([2, 0, 0])
E        +  and   0 = min([2, 0, 0])
E       Failing test case: test_shares_differ_by_at_most_one(total=2, parts=3)

1 failed, 2 passed in 0.57s
```

**`split_evenly(2, 3)` returns `[2, 0, 0]`.** The sum is right — that property passed — but the shares are wildly uneven, because the implementation dumps the entire remainder on the first share. For a payment splitter that means one person owes 2 cents and two owe nothing, which is not what "split evenly" means and which a finance team will notice.

The fix distributes the remainder:

```python
def split_evenly(total_cents: int, parts: int) -> list[int]:
    """Split into `parts` shares differing by at most one cent, summing to the total."""
    if parts <= 0:
        raise ValueError("parts must be positive")
    share, remainder = divmod(total_cents, parts)      # floor division; remainder >= 0
    return [share + 1] * remainder + [share] * (parts - remainder)
```

```
......                                                     [100%]
6 passed in 0.58s
```

Now check the negative case by hand, because `divmod` with a negative numerator surprises people: `split_evenly(-5, 3)` gives `[-1, -2, -2]`, which sums to −5 and has a spread of 1. Correct.

**The lesson is not "hypothesis is clever".** It is that the example tests encoded the three cases the author had in mind, and the bug lived in the fourth. Writing down the *property* — "shares differ by at most one" — is what surfaced it, and that property came straight from the docstring.

### Shrinking is the feature

Hypothesis did not report the first failing input it found; it reported `(2, 3)`. Internally it found something like `(872341, 617)` and then repeatedly simplified while keeping the failure, producing the minimal case. That is **shrinking**, and it is the difference between a usable property-testing tool and a random-input generator.

A minimal failing case is one you can reason about in your head, paste into a debugger, and turn into a permanent regression test. Hypothesis also writes failures to `.hypothesis/examples/` and replays them first on subsequent runs, so a fixed bug stays fixed.

### Typing: what it checks and what it does not

```python
from collections.abc import Iterable, Sequence
from typing import TypedDict, Protocol, TypeVar, Literal, overload

T = TypeVar("T")


def first(items: Sequence[T]) -> T | None:              # generic: preserves the element type
    return items[0] if items else None


class UserRow(TypedDict):                                # a dict with a known shape
    id: int
    email: str
    is_admin: bool


class Repo(Protocol):                                    # structural, no inheritance needed
    def load(self, uid: int) -> UserRow | None: ...


Mode = Literal["r", "w", "a"]                            # only these three strings


def parse(data: str, *, strict: bool = False) -> dict[str, str]: ...
```

Modern syntax notes worth adopting: use `list[int]` not `typing.List[int]` (3.9+), `X | None` not `Optional[X]` (3.10+), and `collections.abc.Iterable` not `typing.Iterable` (deprecated). In 3.12+ you can write generics as `def first[T](items: Sequence[T]) -> T | None:` with no `TypeVar` declaration at all.

**What mypy does not do:**

- **It does not check at runtime.** `parse(123)` runs fine if mypy never saw it, or if the value came from `json.loads` typed as `Any`.
- **`Any` disables checking silently.** Every untyped third-party function returns `Any`, and `Any` propagates: one untyped call can make a whole function unchecked. `mypy --strict` includes `--disallow-any-expr` variants and `warn_return_any` to surface this.
- **It does not validate data.** A `TypedDict` says what you *believe* the JSON contains. If the API returns a string where you declared `int`, mypy is happy and your code fails at runtime. That is Pydantic's job (Week 6), and the boundary rule is: **types inside, validation at the edges.**

Adopt incrementally. On an existing codebase, `mypy --strict` on day one produces thousands of errors and gets switched off. Instead:

```toml
[tool.mypy]
python_version = "3.13"
strict = false
warn_unused_ignores = true
warn_redundant_casts = true

[[tool.mypy.overrides]]        # strict only where you have done the work
module = ["myapp.core.*", "myapp.domain.*"]
strict = true

[[tool.mypy.overrides]]        # silence untyped third-party packages
module = ["untyped_lib.*"]
ignore_missing_imports = true
```

Then widen the strict list one module per week. Layer 3 has the measured migration cost.

### `pytest` beyond the basics

```python
import pytest


@pytest.fixture(scope="session")                 # created ONCE for the whole run
def db_engine():
    engine = create_engine("sqlite:///:memory:")
    yield engine                                  # everything after yield is teardown
    engine.dispose()


@pytest.fixture                                   # default scope="function": fresh per test
def db(db_engine):                                # fixtures compose
    conn = db_engine.connect()
    tx = conn.begin()
    yield conn
    tx.rollback()                                 # each test sees a clean database
    conn.close()


@pytest.mark.parametrize("bad", ["", "  ", None, "a" * 300])
def test_rejects_bad_email(bad):
    with pytest.raises(ValueError):
        validate_email(bad)


def test_slow_path(caplog, monkeypatch, tmp_path):
    monkeypatch.setenv("NEXUS_TIMEOUT", "0.1")
    with caplog.at_level("WARNING"):
        run()
    assert "timeout" in caplog.text
```

The pieces that matter:

- **Fixture scopes** (`function`, `class`, `module`, `session`) trade isolation against speed. The pattern above — a session-scoped engine plus a function-scoped transaction that rolls back — gives per-test isolation at roughly the cost of a `BEGIN`, which is the single biggest speed-up available to a test suite that touches a database.
- **`yield` fixtures** put setup and teardown in one function, and teardown runs even if the test fails.
- **`caplog`** captures log records, so you can assert on logging without touching handlers.
- **`monkeypatch.setenv`/`setattr`/`delitem`** all undo themselves at the end of the test. A manual `os.environ[...] = ...` does not, and leaks into every test that runs after it.
- **`conftest.py`** holds fixtures shared across a directory, discovered automatically with no import.

### Coverage: what it measures and what it does not

```bash
uv pip install pytest-cov
pytest --cov=money --cov-report=term-missing --cov-branch
```

```
Name       Stmts   Miss Branch BrPart  Cover   Missing
------------------------------------------------------
money.py       6      0      2      0   100%
```

**100% coverage, and the original function was wrong.** Coverage measures which lines *executed*, not whether anything meaningful was *asserted*. A test suite of `assert True` after calling every function reaches 100%.

Use coverage as a **floor, not a target**: it reliably tells you which code has *no* test, which is worth knowing. Two settings make it more honest — `--cov-branch` counts both sides of every `if` (a much stronger signal than line coverage), and `--cov-fail-under=80` in CI stops it silently drifting down. Beyond about 85% the marginal test is usually testing generated code or unreachable error paths, and chasing 100% produces tests written for the metric.

The properties that actually indicate a good suite: **it fails when you introduce a bug** (mutation testing, `mutmut`, measures this directly), it runs fast enough that people run it, and it does not break when you refactor internals.

### Tooling: `uv`, `ruff`, and one config file

```toml
# pyproject.toml
[project]
name = "ledger"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["httpx>=0.27,<0.28"]

[project.optional-dependencies]
dev = ["pytest>=8", "pytest-cov", "mypy>=1.10", "ruff>=0.5", "hypothesis>=6.100"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "W", "I", "UP", "B", "SIM", "C4", "G", "RUF", "ARG", "PTH"]
ignore = ["E501"]                       # the formatter handles line length

[tool.pytest.ini_options]

```

The rule sets worth enabling by name: **`B`** (bugbear — catches the mutable default from Module 1), **`I`** (import sorting, replacing isort), **`UP`** (pyupgrade — rewrites `Optional[X]` to `X | None`), **`SIM`** (simplification), **`G`** (logging format — catches the f-string-in-log-call cost from Module 3), and **`PTH`** (prefer `pathlib` over `os.path`).

```bash
uv venv                      # 0.033 s
uv pip install -e ".[dev]"   # 0.135 s warm cache, 4.43 s cold
ruff check . && ruff format --check .
mypy .
pytest
```

Measured on 100 files / 30,100 lines of typed Python:

| Tool | Cold | Warm |
|---|---|---|
| `ruff check` | **0.059 s** | 0.022 s |
| `ruff format --check` | 0.023 s | — |
| `mypy` | **1.335 s** | **0.091 s** (incremental cache) |
| `uv venv` | 0.080 s | 0.033 s |
| `uv pip install` (4 packages) | 4.43 s | **0.135 s** |

**ruff is 22.6× faster than mypy on a cold run** and they are doing different jobs — ruff is a syntactic linter, mypy performs whole-program type inference. The practical consequence is that ruff belongs in a pre-commit hook (60 ms is unnoticeable) and mypy belongs in the editor and in CI with its cache preserved between runs.

**Lockfiles.** `uv lock` writes `uv.lock` pinning every transitive dependency with hashes; `uv sync` installs exactly that. Commit the lockfile for applications; do **not** for libraries, where you want the loosest constraints your users can satisfy. `pyproject.toml` states what you *need*; the lockfile states what you *got*.

### Trade-offs table

| Decision | Choose X when… | Choose Y when… |
|---|---|---|
| Example tests vs property tests | **Examples** for specific known cases, regression tests for fixed bugs, and anything with a hand-computed expected value | **Properties** for invariants: round-trip (`parse(render(x)) == x`), conservation (sums preserved), idempotence, ordering. Hypothesis found `(2, 3)` that four examples missed |
| `mypy --strict` everywhere vs incremental | **Strict from day one** on a new project — it costs nothing when there is no code | **Per-module `strict = true` overrides** on an existing codebase; strict on day one produces thousands of errors and gets turned off, which is worse than none |
| Mock vs real dependency | **Real** where it is fast: SQLite in memory, a local HTTP fixture. Fewer false positives, and it exercises the actual integration | **Mock** for slow, non-deterministic or expensive things: network, clocks, payment providers. Prefer injecting the dependency over patching a module path, which breaks on refactor |
| Coverage target | **A floor** (80–85%) to catch untested modules | **Never a target.** 100% coverage with the original `split_evenly` and its four passing tests is exactly the failure mode; use branch coverage and mutation testing instead |
| `uv` vs `pip`+`venv` | **`uv`** for new work — 0.135 s to install four packages warm, one tool for envs, installs and locking | **`pip`** when a constrained environment forbids new tooling; `pip install -r requirements.txt` with hashes is still reproducible, just slower |

### What breaks in the real world

A data pipeline had 94% test coverage and a green CI badge. A schema change upstream started sending `user_id` as a string (`"1042"`) instead of an integer, for about 3% of records.

The pipeline's type hints said `user_id: int` throughout. `mypy --strict` was clean. Every test passed, because every test fixture had been written by hand with integer IDs.

The string IDs flowed through untouched — Python compared, stored and joined them happily — and landed in the warehouse. Downstream, `user_id = 1042` and `user_id = "1042"` were different keys, so the affected users' events split across two rows in every aggregate. It was noticed eleven days later when someone asked why daily actives had drifted 3% from another source.

Three things went wrong and each has a specific fix:

1. **Type hints are not validation.** `mypy` verified the code was *internally* consistent with the belief that `user_id` is an `int`. Nothing checked the belief. The fix is a validating boundary — Pydantic, or an explicit `int(row["user_id"])` with an error path — at the point data enters the program. **Types inside, validation at the edges.**
2. **Fixtures encoded the same assumption as the code.** Hand-written test data cannot surprise you, because you wrote it. A `hypothesis` strategy generating both `int` and `str` IDs, or a contract test against a captured sample of *real* upstream payloads, would have failed immediately.
3. **94% coverage measured nothing about this.** The parsing line executed on every test. Coverage cannot distinguish "ran with the inputs I imagined" from "ran with the inputs that occur".

<Accordion title="Design checkpoint — one question, with a model answer">

**Question.** Your team's test suite takes 22 minutes and people have started pushing without running it. A colleague proposes deleting the slowest 30 tests, which are integration tests hitting a real Postgres. What do you propose?

**Model answer.** Do not delete them — they are the tests most likely to catch a real bug. Make them fast, and split the suite by feedback loop.

**First, measure.** `pytest --durations=25` names the slow tests in one command. In my experience the distribution is extremely skewed: a handful of tests dominate, and the cause is usually per-test database setup rather than the queries. If 30 tests take 18 of the 22 minutes, that is 36 seconds each, which is almost certainly schema creation per test.

**Fix the fixture pattern.** A session-scoped engine plus a function-scoped transaction that rolls back gives per-test isolation at the cost of a `BEGIN`/`ROLLBACK` rather than a schema rebuild. This routinely takes a database-backed suite from tens of seconds per test to single-digit milliseconds, and it changes nothing about what the tests assert.

**Then parallelise.** `pytest-xdist` with `-n auto` uses every core; on an 11-core machine that is close to a 8–10× wall-clock reduction *if* tests are independent — and if they are not, `-n auto` will find that out, which is itself valuable information.

**Then split by loop.** Unit tests (no I/O) run on every save and in a pre-commit hook; they should be under 10 seconds. Integration tests run in CI on every push. Slow end-to-end tests run on the merge queue. This is not about running fewer tests, it is about which failures you learn about in 10 seconds versus 10 minutes.

**Add ruff and mypy to pre-commit** while you are there: measured at 0.059 s and 0.091 s warm on 30,000 lines, they are free and they catch a category of error before a test ever runs.

**The thing I would push back on hardest** is the framing. People stop running the suite because it is slow, and the response "have fewer tests" trades the symptom for the disease — the next incident is then unprotected. If after all of the above it is still too slow, the honest conversation is about which integration tests overlap and can be merged, not about deleting the coverage of the database layer, which is where the expensive bugs live.
</Accordion>

### Why ruff is 22.6× faster than mypy, and why that is not a criticism

Measured on 100 files, 30,100 lines of annotated Python:

| Tool | Cold | Warm | What it does |
|---|---|---|---|
| `ruff check` | **0.059 s** | 0.022 s | parse each file, walk the AST, apply ~800 syntactic rules |
| `ruff format --check` | 0.023 s | — | parse and re-print |
| `mypy` | **1.335 s** | **0.091 s** | build a whole-program dependency graph, infer types, check consistency |

That is roughly **510,000 lines/second** for ruff and **22,500 lines/second** for mypy cold.

The gap is not "Rust versus Python" alone; it is the problem being solved. Ruff's analysis is **per-file and syntactic** — it can parse all 100 files on 11 cores in parallel and never needs to know what any other file contains. Mypy must build a **module dependency graph**, process modules in topological order, infer types across function boundaries, and resolve every import including typeshed stubs for the standard library. That is inherently a whole-program analysis, and it is why its incremental cache (`.mypy_cache`) matters so much: **1.335 s cold versus 0.091 s warm is a 14.7× difference**, and it is the single most important thing to preserve in CI. A CI job that does not cache `.mypy_cache` is paying the cold cost on every run.

Practical placement: ruff in the editor and in pre-commit (60 ms is below the threshold of noticing); mypy in the editor via the language server and in CI **with its cache restored**. Running mypy in a pre-commit hook on a large repository is where people conclude type checking is not worth it.

`uv`'s numbers come from the same kind of engineering: **0.033 s** to create a venv (it hardlinks rather than copying), **0.135 s** to install four packages from a warm cache (hardlinks from a global content-addressed store), **4.43 s** cold. The warm number is what makes `uv sync` viable at the top of every CI job.

### Gradual typing at scale, and the `Any` leak

The failure mode of a typed codebase is not wrong annotations; it is **`Any` spreading silently**.

```python
import json

def load(path: str) -> dict:            # bare `dict` == dict[Any, Any]
    return json.load(open(path))        # json.load returns Any anyway

cfg = load("c.json")
cfg["timeout"] + "5"                    # mypy: no error. Any absorbs everything.
```

Any expression involving `Any` produces `Any`, and it propagates through returns into callers. A single untyped third-party call at the bottom of a stack can silently un-check everything above it.

The flags that surface it:

```toml
[tool.mypy]
strict = true                     # a bundle; the ones that matter for Any are:
disallow_any_generics = true      # bare `dict` / `list` are errors
disallow_untyped_defs = true      # every function must be annotated
warn_return_any = true            # returning Any from a typed function is an error
warn_unused_ignores = true        # stale `# type: ignore` comments are errors
```

`--strict` is a bundle of about a dozen flags, and its most valuable member is `warn_unused_ignores`: without it, `# type: ignore` comments accumulate and outlive the problems they suppressed, so the codebase looks checked and is not.

The migration strategy that works on a large codebase, in order:

1. **`strict = false` globally, `ignore_missing_imports = true`**, and get to zero errors. This is the baseline that lets CI go green.
2. **Per-module `strict = true` overrides**, starting with leaves (pure domain logic, no I/O) and working toward the edges. Leaves are cheap because they have few dependencies.
3. **Never use bare `# type: ignore`.** Always `# type: ignore[error-code]`, so it stops suppressing only what you meant and `warn_unused_ignores` can retire it.
4. **Add stubs for untyped dependencies** as `.pyi` files in a `stubs/` directory with `mypy_path = "stubs"`, rather than blanket-ignoring the module. Even a 20-line stub for the three functions you use removes an `Any` source.
5. **Track the ratio.** `mypy --html-report` produces a per-module "imprecision" percentage. Watching that number fall is a better progress metric than counting annotated functions.

Dropbox's published account of typing four million lines is the reference experience here: the checker itself had to get faster (incremental mode, then the mypyc-compiled build) before the migration was tolerable, and the biggest wins came from typing the most-imported modules first.

### Property-based testing: how shrinking works

Hypothesis does not generate random inputs and stop. It has two phases.

**Generation.** Strategies produce values from an internal byte stream, so a test case is fundamentally a sequence of bytes interpreted by the strategy. It biases toward "interesting" values — zero, boundary values, empty collections, `NaN`, values that previously failed — rather than sampling uniformly.

**Shrinking.** When a failure is found, hypothesis repeatedly transforms the underlying byte stream toward something lexicographically smaller and re-runs, keeping any transformation that still fails. Because *smaller byte stream* maps to *simpler value* by construction, shrinking works across arbitrary composed strategies with no per-strategy shrinker. That internal representation is the key idea from the Hypothesis paper, and it is why hypothesis shrinks composed and filtered strategies where older tools (QuickCheck derivatives) needed a hand-written shrinker per type.

In our run it reduced a failure to **`split_evenly(total=2, parts=3)`** — the smallest case where a remainder exists and there is more than one share to spread it over.

Two mechanisms worth configuring:

- **The example database.** Failures are stored in `.hypothesis/examples/` and replayed first on the next run. **Commit this directory in CI** (or restore it from cache) so a discovered failure does not need to be rediscovered.
- **`@settings(deadline=...)`** — hypothesis fails a test that takes wildly longer on one example than others, which catches accidental quadratic behaviour. It also causes confusing flakes on slow CI; set `deadline=None` for genuinely slow tests rather than disabling hypothesis.

The properties worth reaching for, in rough order of value:

| Property | Form | Catches |
|---|---|---|
| Round trip | `decode(encode(x)) == x` | serialisation bugs, encoding loss |
| Conservation | `sum(split(x)) == x` | the arithmetic class of bug |
| Idempotence | `f(f(x)) == f(x)` | normalisation, migration, dedup bugs |
| Oracle / differential | `fast(x) == slow_obvious(x)` | optimisation bugs — the highest-value one |
| Metamorphic | `sorted(xs + [y])` contains `y` | when you have no oracle at all |

**Stateful testing** (`RuleBasedStateMachine`) generates *sequences* of operations and checks invariants after each, which is how you find "deposit, withdraw, deposit" ordering bugs that no single-call property reaches. That is exactly what the week's lab asks for on the `hard` track.

### Types are erased, and what Pydantic does about it

At runtime, annotations live in `__annotations__` and nothing checks them:

```python
def f(x: int) -> str:
    return x * 2                       # mypy: error. Runtime: returns 4 for f(2).

print(f(2))                            # 4  — an int, from a function annotated -> str
print(f.__annotations__)               # {'x': <class 'int'>, 'return': <class 'str'>}
```

With `from __future__ import annotations` (and by default from Python 3.14 under PEP 649), annotations are stored as **strings** and only evaluated on demand via `typing.get_type_hints()`. That makes forward references and circular imports painless, and it means any library that inspects annotations must resolve them itself.

Pydantic v2 is the production answer to the erasure gap: it reads the annotations at class-creation time, compiles a **validation schema**, and executes it in Rust (`pydantic-core`). The distinction to hold onto is:

- **`mypy` checks that your code is internally consistent with your beliefs.** Free, static, no runtime cost.
- **Pydantic checks that the data matches your beliefs.** Runtime cost, and the only thing that catches the string-`user_id` incident from Layer 2.

The boundary rule that follows: **validate at the edges (HTTP handlers, message consumers, file parsers, database rows), then trust the types inside.** Validating in the middle of a call chain is wasted work; not validating at the edge is the bug.

### Packaging, in the state it is actually in

`pyproject.toml` (PEP 517/518/621) is now the single source of truth: metadata in `[project]`, build backend in `[build-system]`, tool config in `[tool.*]`. `setup.py` is legacy and `setup.cfg` is fading.

Two distribution formats: a **wheel** (`.whl`) is a pre-built zip that installs by unpacking, and an **sdist** (`.tar.gz`) is source that must be built. Wheels are why `pip install numpy` is fast; without a matching wheel, pip compiles the package on your machine. Wheel filenames encode compatibility: `numpy-2.1.0-cp313-cp313-macosx_11_0_arm64.whl` names the Python version, the ABI and the platform.

**Backend choice:** `hatchling` for pure Python (simple, fast, no `setup.py`); `setuptools` when you have an existing configuration or need its build features; `maturin` for a Rust extension; `scikit-build-core` for CMake/C++.

**Application versus library** is the decision that determines your lockfile policy:

| | Application | Library |
|---|---|---|
| Dependency constraints | pin narrowly | as loose as you can honestly support |
| Lockfile committed | **yes** (`uv.lock`) | **no** — it would constrain your users' resolutions |
| Reproducibility target | this exact deployment | any environment satisfying the constraints |

Upper bounds on library dependencies (`httpx<0.28`) are a known source of unresolvable dependency conflicts downstream: your bound plus another package's bound can produce a graph with no solution. Add an upper bound only when you know a specific version breaks you.

Publish to **TestPyPI first** — it is a real registry with the same API, and it is where you discover that your README does not render or your wheel is missing a subpackage. Then use **trusted publishing** (OIDC from GitHub Actions), which removes the long-lived API token that is otherwise sitting in your CI secrets.

### Production failure modes and how you detect them

| Failure | Signature | Detection |
|---|---|---|
| Type hints trusted as validation | wrong-typed data flows through and corrupts downstream joins | validate at the boundary (Pydantic, explicit conversion); contract tests against captured real payloads |
| `Any` silently un-checks a subsystem | mypy clean, obvious type errors in production | `disallow_any_generics`, `warn_return_any`, `mypy --html-report` imprecision score |
| Stale `# type: ignore` comments | the codebase looks typed and is not | `warn_unused_ignores = true`; always use `# type: ignore[code]` |
| High coverage, low confidence | 94% coverage and a schema bug shipped | branch coverage; mutation testing (`mutmut`); property tests |
| CI mypy takes minutes | cold cache on every run | cache `.mypy_cache` between CI runs — measured 1.335 s vs 0.091 s, a 14.7× difference |
| Test suite too slow to run | 22 minutes; people stop running it | `pytest --durations=25`; session-scoped engine + per-test transaction rollback; `pytest-xdist -n auto` |
| Hypothesis flakes in CI, passes locally | slow CI machine trips the per-example deadline | `@settings(deadline=None)` for genuinely slow tests; do not disable hypothesis |
| A fixed bug reappears | the hypothesis example database was not preserved | commit or cache `.hypothesis/examples/`; add the shrunk case as an explicit `@example` |
| "Works on my machine" after a dependency update | no lockfile, or a lockfile not used in CI | `uv lock` committed for applications; `uv sync --frozen` in CI |
| Package installs but imports fail | a subpackage missing from the wheel | build the wheel, `unzip -l` it, and install it into a clean venv in CI before publishing |

### Frontier and research pointers

- **MacIver, D. R., Hatfield-Dodds, Z. et al. (2019). "Hypothesis: A new approach to property-based testing." *Journal of Open Source Software* 4(43).** One-sentence takeaway: representing test cases as an internal byte stream makes shrinking work for arbitrary composed strategies without a per-type shrinker, which is what makes property testing practical rather than academic.
- **Claessen, K. & Hughes, J. (2000). "QuickCheck: A Lightweight Tool for Random Testing of Haskell Programs." *ICFP*.** One-sentence takeaway: the original property-testing paper — state a law, generate inputs, and the tool finds the counterexample you did not think of.
- **Lehtosalo, J. et al. — PEP 484 ("Type Hints"), PEP 544 ("Protocols"), PEP 561 ("Distributing type information"), PEP 649 ("Deferred annotations").** One-sentence takeaway: Python's gradual typing was designed so that annotations are optional metadata and checking is a separate tool, which is why `Any` interoperates with everything and why erasure is deliberate rather than accidental.
- **Dropbox Engineering, "Our journey to type checking 4 million lines of Python" (2019).** One-sentence takeaway: the blockers to a large typing migration were checker *speed* and third-party stubs, not developer resistance — which is why mypy's incremental mode and the mypyc-compiled build exist.
- **Jia, Y. & Harman, M. (2011). "An Analysis and Survey of the Development of Mutation Testing." *IEEE TSE* 37(5).** One-sentence takeaway: mutation score — the fraction of injected faults your tests detect — measures suite quality in a way coverage cannot, because it asks whether tests *assert* rather than whether lines *ran*.
- **Inozemtseva, L. & Holmes, R. (2014). "Coverage Is Not Strongly Correlated with Test Suite Effectiveness." *ICSE*.** One-sentence takeaway: measured across large Java projects, coverage percentage correlates weakly with the ability to detect faults once suite size is controlled for — the empirical case for treating coverage as a floor.

### Stretch challenge

Find a real bug with property testing that example tests miss, and prove the properties are what did it.

1. Take a function of your own with existing example tests — a parser, a serialiser, a rate limiter, a date-range calculator. Something with arithmetic or state.
2. Write down its properties **from the docstring**, not from the implementation. Round-trip, conservation, idempotence, ordering, bounds. If the docstring does not support any property, that is a finding: rewrite the docstring first.
3. Run hypothesis with `max_examples=1000`. Report the failing case, the **shrunk** case, and how many examples it took to find it. If nothing fails, weaken your properties until one does — you have either a correct function or properties too vague to constrain it, and you should know which.
4. **Measure the coverage of both suites.** Our reference: the example suite achieved 100% line and branch coverage on a function that returned `[2, 0, 0]` for `split_evenly(2, 3)`. Show your own version of that gap.
5. Add a `RuleBasedStateMachine` for a stateful object (an account, a cache, a connection pool) with an invariant checked after every operation. Report the shortest failing operation sequence hypothesis found.
6. Run `mutmut` on the module with each suite. Report the mutation score for the example suite and the property suite separately.

The open question with no single right answer: property tests are slower (500 examples versus 4), they can flake on timing, and a badly chosen property either passes vacuously or duplicates the implementation. Where in your codebase are they worth it, and what would you tell a colleague who says "I'd rather write ten more example tests in that time"? Bring your mutation scores from step 6 — that is the only number that actually answers it.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Type hints did not prevent a runtime type error | annotations are not enforced; the data came from outside | validate at the boundary with Pydantic or explicit conversion; types inside, validation at the edges |
| mypy clean, obvious type bugs in production | `Any` from an untyped dependency propagated | `disallow_any_generics`, `warn_return_any`; write minimal `.pyi` stubs instead of blanket ignores |
| `# type: ignore` comments everywhere, nobody knows why | bare ignores never expire | always `# type: ignore[error-code]`; enable `warn_unused_ignores` |
| High coverage, bugs still ship | coverage measures execution, not assertion | branch coverage; mutation testing; property tests |
| `pytest.raises` passes for the wrong reason | no `match=`, so any instance of that exception passes | `pytest.raises(ValueError, match="expected text")` |
| Tests pass alone, fail together | shared mutable state, or an env var set without `monkeypatch` | function-scoped fixtures; `monkeypatch` (which undoes itself); run with `pytest -p no:randomly` off to find order dependence |
| CI mypy takes minutes | the incremental cache is not preserved | cache `.mypy_cache`; measured 14.7× difference |
| Hypothesis flakes only in CI | the per-example deadline trips on a slower machine | `@settings(deadline=None)` for slow tests |
| A hypothesis-found bug reappears | the example database was not preserved | commit or cache `.hypothesis/examples/`; add the shrunk case as an `@example` |
| Package installs but a submodule is missing | the wheel does not include it | build the wheel, `unzip -l` it, install into a clean venv in CI before publishing |
| Library users hit dependency conflicts | unnecessary upper bounds on your dependencies | pin narrowly in applications, loosely in libraries; upper-bound only a version you know breaks |
