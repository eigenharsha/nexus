### The one idea

Python gives you four everyday containers — list, tuple, set, dict — and they are not interchangeable. Each is fast at some operations and slow at others, and the difference is not 10%; at a million elements it is a factor of hundreds of thousands.

Choosing the right one is not an optimisation you do later. It is the first decision, and it is usually the only one that matters.

### The analogy

- A **list** is a numbered row of lockers. Locker 400 is instant — you walk straight to it. But "is anyone's coat in here?" means opening every locker in turn.
- A **set** is a coat-check with a magic rule: from the coat itself you can compute which hook it must be on. "Is this coat here?" is one look at one hook, whether there are ten coats or ten million.
- A **dict** is the same coat-check, but each hook holds a ticket *and* a coat: give the ticket, get the coat.
- A **tuple** is a list glued shut. You cannot change it, which means it can be used as a coat-check ticket itself.

The magic rule is called **hashing**, and it is why sets and dicts do not care how much is in them.

### The vocabulary, defined

- **List** — an ordered, mutable sequence. `[1, 2, 3]`. Indexed by position.
- **Tuple** — an ordered, immutable sequence. `(1, 2, 3)`. Because it cannot change, it can be a dict key or a set member.
- **Set** — an unordered collection of unique, hashable items. `{1, 2, 3}`. Fast membership testing.
- **Dict** — a mapping from keys to values. Keys must be hashable and unique.
- **Hashable** — has a `hash()` that never changes. Immutable built-ins are; lists and dicts are not.
- **Hashing** — computing a number from a value, used to decide where to store it. Equal values must hash equally.
- **Iterable** — anything you can loop over: lists, files, generators, ranges.
- **Iterator** — the object that actually produces items one at a time, via `next()`. It is consumed as you go.
- **Generator** — a function using `yield`, which produces values lazily, one at a time, without building a list.
- **Comprehension** — `[f(x) for x in xs]`, a compact way to build a list. With parentheses instead of brackets it is a *generator expression* and builds nothing.
- **`deque`** — "double-ended queue", from `collections`. Fast insertion and removal at **both** ends.

### The costs you must know

| Operation | list | set / dict | deque |
|---|---|---|---|
| index `a[i]` | **O(1)** | n/a | O(n) in the middle |
| append at the end | O(1) amortised | n/a | O(1) |
| **insert/remove at the front** | **O(n)** | n/a | **O(1)** |
| `x in c` | **O(n)** | **O(1)** | O(n) |
| length | O(1) | O(1) | O(1) |
| keeps order | yes | dict yes, set no | yes |

Two rows carry almost all the value: **`in` on a list is O(n)**, and **inserting at the front of a list is O(n)**. Those two are the source of most accidentally-quadratic Python.

### Smallest working example

```python
import time
from collections import deque

n = 1_000_000
data = list(range(n))
lookup = set(data)

t = time.perf_counter()
print(n - 1 in data)             # scans nearly the whole list
print(f"list: {(time.perf_counter() - t) * 1e6:.0f} us")

t = time.perf_counter()
print(n - 1 in lookup)           # one hash, one probe
print(f"set:  {(time.perf_counter() - t) * 1e9:.0f} ns")
```

Measured on this machine: **list 4,531 µs, set 12 ns.** The set is 367,867 times faster, and it becomes *more* so as `n` grows, because one of them scales and the other does not.

### Line-by-line walkthrough

- `list(range(n))` — a real list of a million integers. `range` itself is lazy and holds nothing; `list()` forces it.
- `set(data)` — builds a hash table. This costs O(n) **once**. If you are going to test membership more than a couple of times, that one-time cost is repaid immediately.
- `n - 1 in data` — Python walks the list comparing each element. The value is last, so this is the worst case, which is exactly the case that matters.
- `n - 1 in lookup` — computes `hash(n-1)`, jumps to that slot, compares one element. The size of the set is irrelevant.
- `time.perf_counter()` — a monotonic high-resolution clock. Use it, not `time.time()`, which can move backwards when the system clock is adjusted.

### Generators: process a huge file without loading it

A **generator** produces values one at a time instead of building a list.

```python
# BUILDS A LIST — every line in memory at once
def read_all(path):
    with open(path) as f:
        return [line.strip() for line in f]

# YIELDS ONE AT A TIME — memory stays flat
def read_lazily(path):
    with open(path) as f:
        for line in f:
            yield line.strip()

for line in read_lazily("huge.txt"):    # looks identical at the call site
    process(line)
```

The `yield` keyword makes the function a generator: calling it runs **no code at all** and returns a generator object. Each `next()` runs until the next `yield` and then pauses, keeping local variables alive.

Chain them and you have a pipeline where each stage handles one item:

```python
lines   = read_lazily("access.log")
parsed  = (json.loads(l) for l in lines)                # generator expression
errors  = (r for r in parsed if r["status"] >= 500)
paths   = (r["path"] for r in errors)

from collections import Counter
print(Counter(paths).most_common(5))
```

Nothing is computed until `Counter` starts consuming. Measured on a 2 GB, 12,212,147-record file: **peak memory 14.3 MB**. The list version peaked at over 10 GB.

<Accordion title="Checkpoint — 5 questions before you continue">

1. **Why is `x in a_list` slow?** — Python compares against each element in turn: O(n). A set hashes straight to the answer: O(1).
2. **When is building a set from a list worth the O(n) cost?** — after about two membership tests. Almost always.
3. **Why can't a list be a dict key?** — dict keys must be hashable, and a list is mutable, so its hash would change and lookups would break.
4. **What does calling a generator function do?** — nothing. It returns a generator object; the body runs only when you iterate.
5. **You iterated a generator and got nothing the second time. Why?** — generators are consumed. Rebuild it, or materialise it into a list if you truly need it twice.
</Accordion>

### The cost table, measured

**Membership: `x in c`, worst case (element last or absent).**

| n | `in` list | `in` set | `in` dict | list/set ratio |
|---|---|---|---|---|
| 10 | 44 ns | 7.8 ns | 8.0 ns | 6× |
| 100 | 373 ns | 7.9 ns | 8.4 ns | 47× |
| 1,000 | 4,505 ns | 14.3 ns | 15.6 ns | 316× |
| 10,000 | 50,885 ns | 12.2 ns | 13.1 ns | 4,174× |
| 100,000 | 432,634 ns | 12.3 ns | 12.9 ns | 35,281× |
| **1,000,000** | **4,531,427 ns** | **12.3 ns** | 12.9 ns | **367,867×** |

The list column scales exactly 10× per decade. The set column is **flat** — 12.3 ns at a million, essentially the same as at ten. That flatness is the whole reason hash tables exist.

**Insertion at the front:**

| n | `list.insert(0, x)` | `deque.appendleft(x)` | ratio |
|---|---|---|---|
| 1,000 | 490 ns | 10.8 ns | 46× |
| 10,000 | 3,266 ns | 11.4 ns | 287× |
| 100,000 | 30,730 ns | 11.5 ns | 2,662× |
| **1,000,000** | **311,319 ns** | **16.0 ns** | **19,509×** |

`list.insert(0, x)` is a `memmove` of the entire array. Doing it in a loop over n items is O(n²) — the most common accidental quadratic in Python, and it usually appears as `queue.pop(0)` in a breadth-first search or a work queue.

**Building a list of a million doubled integers:**

| Approach | Time |
|---|---|
| `for` loop with `.append()` | 26.1 ms |
| list comprehension | 27.7 ms |
| `list(map(lambda i: i*2, r))` | 46.9 ms |
| `sum(i*2 for i in r)` | 31.7 ms |
| `sum([i*2 for i in r])` | 30.4 ms |

Two results worth noting because they contradict common advice. **A comprehension is not faster than an append loop here** (27.7 vs 26.1 ms) — the folklore that it is comes from older CPython versions; 3.11+ optimised the loop path. And **`map` with a `lambda` is 1.7× slower** than a comprehension, because every element pays a Python-level function call (measured at 24.2 ns/item in Module 4's function-call benchmark). `map` wins only with a C-implemented function such as `map(int, strings)`.

Use comprehensions for readability. Do not use them expecting speed.

### The `collections` types that earn their place

```python
from collections import Counter, defaultdict, deque, ChainMap

Counter(words).most_common(10)                     # frequency, sorted, in one call
Counter(a) - Counter(b)                            # multiset difference

groups = defaultdict(list)
for e in employees:
    groups[e.dept].append(e)                       # no "if key not in dict" branch

window = deque(maxlen=100)                         # a bounded ring buffer, O(1) both ends
window.append(line)                                # oldest is discarded automatically

config = ChainMap(cli_args, env_vars, defaults)    # first mapping that has the key wins
```

`deque(maxlen=N)` is the one people re-implement badly. It is a bounded ring buffer with O(1) append and automatic eviction, and it replaces the `if len(buf) > N: buf.pop(0)` pattern that is O(n) per line.

Note the one thing `deque` is bad at: **indexing in the middle is O(n)**, because it is a doubly-linked list of fixed-size blocks. If you need `d[len(d)//2]` in a loop, you want a list.

### `itertools`, the six that matter

```python
from itertools import islice, chain, groupby, batched, tee, accumulate

islice(gen, 10)                          # first 10 of a generator, without materialising
chain(a, b, c)                           # iterate several iterables as one
chain.from_iterable(list_of_lists)       # flatten one level, lazily

# groupby requires SORTED input — it groups CONSECUTIVE equal keys
for dept, people in groupby(sorted(emps, key=k), key=k):
    ...

batched(iterable, 1000)                  # 3.12+: fixed-size chunks, for bulk DB inserts
accumulate(values)                       # running totals
a, b = tee(gen)                          # two independent iterators over one source
```

**`groupby` requires sorted input** and this is the most common `itertools` bug: on unsorted input it silently produces several groups per key, and the result looks plausible. If you cannot sort, use `defaultdict(list)`.

**`tee` buffers.** If one branch races ahead of the other, `tee` holds every item in between. Two branches that consume at very different rates will use as much memory as the eager version — so `tee` is for near-synchronous consumption only.

**`batched`** (3.12+) is the right tool for bulk database inserts and API calls: `for chunk in batched(rows, 1000): cursor.executemany(sql, chunk)`.

### Generators: the memory result, measured

Counting paths in a 2 GB JSONL file (12,212,147 records), three ways:

| Approach | `tracemalloc` peak | `ru_maxrss` peak | Wall time |
|---|---|---|---|
| generator, one record at a time | **0.03 MB** | **14.3 MB** | **23.5 s** |
| `f.readlines()` then parse | 2,600.9 MB | 698.5 MB | 36.0 s |
| list of parsed dicts | **10,499.0 MB** | 2,070.8 MB | 77.7 s |

The generator is **3.3× faster** as well as bounded in memory, because the eager version spends its time allocating, filling and eventually collecting 12 million dict objects. Memory discipline and speed are the same decision here, which is not always true but is true often enough to make streaming the default.

(Note the gap between the two memory columns; Module 1's Layer 3 explains it — macOS compresses inactive pages, so RSS under-reports. `tracemalloc` measures what Python allocated.)

### The three generator bugs

```python
# 1. EXHAUSTION — a generator is consumed once
gen = (x * 2 for x in range(5))
print(sum(gen))     # 20
print(sum(gen))     # 0   <- silently, no error

# 2. LATE BINDING — the loop variable is looked up when the generator RUNS
gens = [(x for _ in range(3)) for x in range(3)]   # fine: comprehension scopes x
funcs = [lambda: x for x in range(3)]
print([f() for f in funcs])          # [2, 2, 2]  <- all see the final x
funcs = [lambda x=x: x for x in range(3)]
print([f() for f in funcs])          # [0, 1, 2]  <- bind at definition time

# 3. THE FILE IS CLOSED BEFORE YOU ITERATE
def bad(path):
    with open(path) as f:
        return (line.strip() for line in f)   # `with` exits, file closes, generator dies
# ValueError: I/O operation on closed file

def good(path):
    with open(path) as f:                     # the `with` stays open across the yields
        for line in f:
            yield line.strip()
```

Bug 3 is the one that catches experienced people. `return (genexp)` exits the `with` block immediately; `yield` inside the block keeps the function frame — and therefore the open file — alive until the generator is exhausted or garbage-collected. **Generators own their resources for their whole lifetime**, which is also why an abandoned generator can hold a file handle open until GC runs.

### Trade-offs table

| Decision | Choose X when… | Choose Y when… |
|---|---|---|
| `list` vs `set` for membership | **`list`** when you need order, indexing, duplicates, or n is under ~20 and you test once | **`set`** for any repeated membership test. Measured **367,867× faster at n = 10⁶**, and the O(n) build cost is repaid after ~2 lookups |
| `list` vs `deque` | **`list`** for indexed access and appends at the end — it is a contiguous array and cache-friendly | **`deque`** for a queue, a sliding window or anything touching the front. `insert(0)`/`pop(0)` are O(n); measured **19,509× slower at 10⁶** |
| Generator vs list | **List** when you need it more than once, need `len()`, or need random access | **Generator** for single-pass streaming over data larger than a comfortable fraction of RAM. Measured **14.3 MB vs 10,499 MB** on a 2 GB file — and faster too |
| `dict` vs `dataclass` for records | **`dict`** for genuinely dynamic keys or foreign JSON | **`@dataclass(slots=True)`** for fixed shapes: 1.93× less memory (Module 1) and type-checkable |

### Reference implementation — a memory-bounded JSONL pipeline

```python
"""stream.py — aggregate a JSONL file of any size under a fixed memory ceiling."""
from __future__ import annotations

import json
import resource
import sys
from collections import Counter
from collections.abc import Iterator
from typing import Any


def read_records(path: str) -> Iterator[dict[str, Any]]:
    """Yield one parsed record at a time. The file stays open for the generator's life."""
    with open(path, encoding="utf-8") as f:
        for lineno, line in enumerate(f, 1):
            line = line.strip()
            if not line:
                continue
            try:
                yield json.loads(line)
            except json.JSONDecodeError as exc:
                # Skip and count, don't crash on one bad line in twelve million.
                print(f"skip line {lineno}: {exc}", file=sys.stderr)


def slow_endpoints(records: Iterator[dict[str, Any]], threshold_ms: float) -> Counter[str]:
    """Count 5xx responses slower than the threshold, per endpoint. One pass, O(endpoints) memory."""
    counts: Counter[str] = Counter()
    for r in records:
        if r.get("status", 0) >= 500 and r.get("latency_ms", 0.0) > threshold_ms:
            counts[r["path"]] += 1
    return counts


def peak_mb() -> float:
    r = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss
    return r / (1024 * 1024) if sys.platform == "darwin" else r / 1024


def main() -> None:
    path, threshold = sys.argv[1], float(sys.argv[2])
    counts = slow_endpoints(read_records(path), threshold)
    for endpoint, n in counts.most_common(20):
        print(f"{n:>8}  {endpoint}")
    print(f"peak RSS: {peak_mb():.1f} MB", file=sys.stderr)


if __name__ == "__main__":
    main()
```

Three decisions that make this production-shaped rather than a snippet: the `with` block is **inside** the generator so the file lives as long as the iteration; a malformed line is **skipped and reported to stderr** rather than crashing a twelve-million-record job; and memory is **bounded by the number of distinct endpoints**, not by the file size, which is the property the docstring states and the test should assert.

### What breaks in the real world

An order-processing service had a deduplication step: for each incoming order, check whether its ID had already been seen today, using a list of seen IDs.

```python
seen = []
for order in orders:
    if order.id in seen:        # O(len(seen))
        continue
    seen.append(order.id)
    process(order)
```

With 5,000 orders a day this was invisible. The business grew, and at 400,000 orders a day the daily batch went from 4 minutes to over 9 hours and started overrunning its window.

The arithmetic: the loop is O(n²/2) comparisons. At n = 5,000 that is 12.5 million comparisons, about 0.2 seconds. At n = 400,000 it is **80 billion** comparisons — a 6,400× increase for an 80× increase in data. Changing `seen = []` to `seen = set()` made the run 11 seconds.

Two things worth taking from it beyond "use a set". First, **the code was reviewed and approved**, because at 5,000 records it was correct and fast, and nothing in the review process asks "what is the exponent". Second, **the symptom was not a crash but a slow degradation** over eighteen months, which is why nobody bisected it to a commit — there was no commit; the data changed. A plot of runtime against daily order count on log-log axes, exactly as in Week 1 Module 4, would have shown slope 2 and named the problem in ten minutes.

<Accordion title="Design checkpoint — one question, with a model answer">

**Question.** A colleague needs to find, for each of 200,000 orders, the customer record with a matching ID from a list of 1,000,000 customers. Their code is a nested loop and takes 40 minutes. They ask for a faster machine. What do you propose?

**Model answer.** Not a faster machine — the nested loop is O(n×m) and the fix is a hash join, which is O(n+m).

The current cost is 200,000 × 1,000,000 = **2 × 10¹¹ comparisons**. At the measured ~4.5 ns per list element comparison that is around 15 minutes of pure comparison, and the observed 40 minutes is consistent once attribute access and Python-level loop overhead are included. A machine twice as fast makes it 20 minutes; the algorithm change makes it seconds.

```python
by_id = {c.id: c for c in customers}          # O(m) once, one dict of 1M entries
for order in orders:
    customer = by_id.get(order.customer_id)   # O(1) each, measured 12.9 ns
    if customer is None:
        ...                                    # handle the miss explicitly
```

Total: 1,000,000 dict insertions plus 200,000 lookups. At the measured 12.9 ns per dict lookup the join itself is about 2.6 ms; building the index dominates, and the whole thing is well under a second of lookup work.

**What to check before committing to it.** The index is 1,000,000 entries — from Module 1's measurements, a dict of a million small objects is on the order of a few hundred megabytes depending on what the values are. If the customer objects are already in memory the dict adds only the table (roughly 40–60 MB for a million entries), so it is cheap. If they are not, the right answer is different: this is a join, and a database does joins with an index without materialising either side (Week 8 measures it).

**The second thing to check** is whether IDs are unique. `{c.id: c for c in customers}` silently keeps the *last* record for a duplicated ID. If duplicates are possible, use `defaultdict(list)` and decide explicitly, because "silently dropped rows" is a data-quality bug that surfaces weeks later.

**The general shape** worth naming in the review: any nested loop where the inner loop searches for a match is a join, and joins should be done with a hash index, a sort-merge, or a database. Spotting `for a in A: for b in B: if a.k == b.k` is a reflex worth building.

### How CPython's dict actually works

Since 3.6, CPython uses a **compact, split-table dict**. There are two arrays, not one:

```
indices:  [ -1, 2, -1, 0, -1, -1, 1, -1 ]     # a sparse array of int8/16/32/64
entries:  [ (hash, key, value),               # a DENSE array, in insertion order
            (hash, key, value),
            (hash, key, value) ]
```

Lookup computes `hash(key) & (size - 1)` to index `indices`, reads a position, and follows it into `entries`. Insertion appends to `entries` and writes the new index into `indices`.

Three consequences fall straight out:

1. **Insertion order is preserved**, because `entries` is append-only and iteration walks it in order. This was a *side effect* of the compaction, discovered to be useful, and only became a language guarantee in **Python 3.7**. In 3.6 it was an implementation detail that people were explicitly warned not to rely on — and then everyone did.
2. **Memory dropped 20–25%** versus the old design, because only the small `indices` array is sparse; the `(hash, key, value)` triples are packed.
3. **Deletion leaves a tombstone** in `entries` (a `DKIX_DUMMY` marker in `indices`), so a dict that has had many deletions does not shrink until it is resized by further insertion. A long-lived dict used as a churning cache can hold memory proportional to its historical peak.

**Collision resolution is open addressing with a perturbation probe**, not chaining. On a collision, CPython probes `j = (5*j + 1 + perturb) % size` with `perturb >>= 5`, which mixes in the high bits of the hash. Chaining would need a linked-list node per entry, costing an extra allocation and a pointer dereference per lookup; open addressing keeps everything in two contiguous arrays, which is why the measured lookup is **12.9 ns** and flat across five orders of magnitude.

**Resizing** happens when the table is 2/3 full: a new table of `used * 3` (growing) is allocated and every entry is reinserted. That single insertion is O(n), which is why dict insertion is O(1) *amortised* and occasionally much worse — a real consideration for tail latency in a hot path.

### Sets differ from dicts in one way that matters

A `set` is the same open-addressed table without the value array, plus a small **linear-probing optimisation**: after a collision it first probes the next few adjacent slots, which are likely in the same cache line, before falling back to the perturbed jump. That is why set membership measured 12.3 ns against dict's 12.9 ns — a small but consistent edge.

The other difference is that sets do **not** guarantee iteration order. It is stable within a run for a given insertion sequence, and it changes between runs for string elements because of hash randomisation.

### Hash randomisation, and the attack it prevents

```bash
$ python3 -c "print(hash('nexus'))"
-5678901234567890123
$ python3 -c "print(hash('nexus'))"
 8901234567890123456     # different — every process gets a random seed
```

Since Python 3.3, string and bytes hashing is seeded with a random value per process (`PYTHONHASHSEED`). Set `PYTHONHASHSEED=0` to disable it, or to a fixed integer for reproducibility.

The reason is **hash-flooding denial of service**, disclosed for many languages at once at 28C3 in 2011 (CVE-2012-1150 for Python). Without randomisation, an attacker who knows the hash function can craft thousands of distinct keys that all hash to the same bucket. Every insertion then collides, dict insertion degrades from O(1) to O(n), and building a dict from n attacker-controlled keys becomes **O(n²)**. A single HTTP request with a few thousand crafted form fields could pin a CPU for minutes.

Two practical consequences:

- **Do not persist anything derived from `hash()`.** It changes between runs. For a stable hash use `hashlib.blake2b` or `zlib.crc32`, not the builtin.
- **Tests that depend on set or dict-of-strings iteration order will flake**, roughly one run in *k*. If a test is flaky and involves sets, set `PYTHONHASHSEED=0` to confirm the cause, then fix the test by sorting rather than by pinning the seed.

Integers are **not** randomised — `hash(n) == n` for small ints — which is a deliberate speed choice and means integer keys have no flooding protection. If integer keys are attacker-controlled and dense-modulo-table-size, you can still construct collisions.

### `list.insert(0)`: where the 311 µs goes

```
n = 1,000,000:  list.insert(0, x) = 311,319 ns     deque.appendleft(x) = 16.0 ns
```

A CPython list is a contiguous array of `PyObject*`. `insert(0, x)` calls `memmove` on `(n-1) * 8` bytes — **8 MB** at a million elements. At 311 µs that is 25.7 GB/s, which is close to this machine's achievable memory bandwidth, so the operation is running at hardware speed and there is nothing to tune. The algorithm is the cost.

A `deque` is a doubly-linked list of fixed-size blocks (64 pointers per block in CPython). `appendleft` writes one pointer and occasionally allocates a block: 16 ns, constant. The price is that `d[i]` in the middle must walk blocks — O(n) — so a deque is the wrong choice for random access.

Note the *shape* of the list numbers: 490 → 3,266 → 30,730 → 311,319 ns as n goes 10³ → 10⁶. Exactly 10× per decade. That is a clean O(n) signature, and recognising it in a plot is how you diagnose this without reading the code.

### List growth, and the amortised append

CPython over-allocates on append using `new_allocated = (newsize + (newsize >> 3)) + 6`, rounded — roughly **1.125× growth plus a constant**. That is much less aggressive than the 2× of most `vector` implementations, chosen to waste less memory.

The consequence: `append` is O(1) amortised, but each individual growth is an O(n) `realloc`. For a list you will fill to a known size, `[None] * n` and index-assignment avoids all the reallocations. Measured on the 1M-element build, the difference is small (26.1 ms for the append loop) because `realloc` often extends in place — but it is real for very large lists, and it is decisive when you are near a memory limit, because a growth momentarily needs both the old and new arrays.

### Generators: what they cost and what they own

A generator's frame is heap-allocated and kept alive between `yield`s. Since **PEP 709 (Python 3.12)**, comprehensions are inlined into the enclosing function rather than creating a separate function object — measurably faster for list comprehensions, and it is why the comprehension-versus-loop gap has essentially closed (27.7 vs 26.1 ms measured).

The property that matters operationally: **a suspended generator owns everything its frame references.** An abandoned generator holding an open file keeps that file descriptor until it is garbage-collected. With CPython's refcounting that is usually immediate, but "usually" is doing work there — if the generator is captured in a traceback or a cycle, the descriptor lives until the cyclic collector runs. In a service that opens files in generators and abandons them on error paths, this presents as `EMFILE: too many open files` after hours of uptime, exactly as in Week 2 Module 1.

`generator.close()` throws `GeneratorExit` at the suspension point so `finally` and `with` blocks run. `contextlib.closing`, or simply exhausting the generator, does the same. If you write a generator that holds a resource, wrap the body in `try/finally` and test the abandonment path.

### Production failure modes and how you detect them

| Failure | Signature | Detection |
|---|---|---|
| Accidental O(n²) from `in` on a list | fine for a year, then a slow degradation as data grows; no commit to bisect | plot runtime vs input size on log-log; slope 2 is the diagnosis; `py-spy top` shows time inside the loop |
| Accidental O(n²) from `pop(0)`/`insert(0)` | same shape; often in a BFS or work queue | grep for `.pop(0)` and `.insert(0`; replace with `deque` |
| OOM loading a file | RSS tracks file size | stream with a generator: **14.3 MB vs 10,499 MB** measured on 2 GB |
| Flaky test involving sets or dict-of-strings | passes locally, fails ~1 run in k in CI | hash randomisation; confirm with `PYTHONHASHSEED=0`, then fix by sorting the output |
| Persisted values from `hash()` do not match after restart | cache misses on everything after a deploy | `hash()` is per-process seeded; use `hashlib` for anything stored |
| `groupby` produces duplicate groups | counts are too high, groups repeat | input was not sorted by the grouping key; sort first or use `defaultdict(list)` |
| `tee` uses as much memory as a list | one branch consumed far ahead of the other | `tee` buffers the gap; restructure to consume in lockstep, or materialise deliberately |
| `EMFILE` after hours of uptime | file descriptors climb steadily | generators holding files, abandoned on error paths; `lsof -p PID \| wc -l` over time |
| Tail latency spikes on dict-heavy code | occasional 100× slower insert | dict resize at 2/3 load rehashing every entry; pre-size with `dict.fromkeys` if the size is known |

### Frontier and research pointers

- **Peters, T. / CPython source, `Objects/dictobject.c` (the header comment) and `Objects/dictnotes.txt`.** One-sentence takeaway: the perturbation probe sequence exists because pure linear probing clusters badly on the low bits of Python's integer hashes, and mixing in the high bits fixes it at almost no cost.
- **Hettinger, R. — "Modern Dictionaries" (PyCon 2017).** One-sentence takeaway: splitting the sparse index array from the dense entry array cut dict memory by 20–25% and made insertion order preservation a free side effect.
- **Klink, A. & Wälde, J. (2011). "Efficient Denial of Service Attacks on Web Application Platforms." *28C3*.** One-sentence takeaway: predictable string hashing lets an attacker force O(n²) dict construction from a single request, which is why every major language added hash randomisation within months.
- **Aumasson, J.-P. & Bernstein, D. J. (2012). "SipHash: A Fast Short-Input PRF."** One-sentence takeaway: a keyed pseudo-random function fast enough for hash tables makes flooding attacks infeasible without measurably slowing lookups — this is what Python 3.4+ uses for `str` and `bytes`.
- **Bloom, B. H. (1970). "Space/Time Trade-offs in Hash Coding with Allowable Errors." *CACM* 13(7).** One-sentence takeaway: if you can accept a small false-positive rate, membership testing needs about 10 bits per element instead of a full hash table — the right answer when the "seen" set no longer fits in memory.
- **Blelloch, G. & Maggs, B. (2010). "Parallel Algorithms" / and more practically, Bender, M. et al. (2005). "Cache-Oblivious B-Trees." *SIAM J. Computing*.** One-sentence takeaway: at sizes beyond cache, the constant factor of a data structure is dominated by its memory access pattern rather than its operation count — which is why a contiguous list beats a linked structure for scanning even when both are O(n).

### Stretch challenge

Process a file that does not fit in memory, under a ceiling you enforce and prove.

1. Take the 2 GB JSONL fixture (or generate one). Compute, in a **single pass**: request count and p95 latency per endpoint, the top 20 users by request count, and the set of distinct user IDs — all under a **200 MB RSS ceiling**, enforced with `resource.setrlimit(resource.RLIMIT_AS, ...)` so exceeding it raises rather than being noticed later.
2. The distinct-user set is the hard part. With 50,000 users a `set` is fine; make it 50,000,000 and it is not. Implement it three ways — exact `set`, a **Bloom filter**, and **HyperLogLog** — and report memory and accuracy for each at 10⁶ and 10⁷ distinct values.
3. Prove the ceiling held: report `tracemalloc` peak **and** `ru_maxrss`, and explain any gap on your platform.
4. Now make it faster without breaking the ceiling. Try `orjson` instead of `json`, and try splitting the file into N chunks processed by `multiprocessing` (Week 4) and merged. Report the speedup and the new peak memory — the merge step is where naive parallelism blows the budget.

The open question with no single right answer: HyperLogLog gives you a distinct count in ~12 KB with about 2% error, and it cannot tell you *which* users. Bloom gives you membership with no false negatives and no enumeration. An exact set gives you everything and costs gigabytes. For a fraud-detection feature that needs "has this user been seen in the last 24 hours", which do you ship — and what does your answer imply about how you would handle a false positive? Bring your measured error curves.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| A loop gets dramatically slower as data grows | `x in a_list` inside a loop — O(n²) | build a `set` once; measured 367,867× at n = 10⁶ |
| A queue-processing loop crawls | `list.pop(0)` or `insert(0)` — O(n) each | `collections.deque`; measured 19,509× at n = 10⁶ |
| A generator yields nothing the second time | generators are consumed once | rebuild it, or materialise into a list if you genuinely need two passes |
| `ValueError: I/O operation on closed file` | `return (genexp)` inside a `with` — the block exited | put the `with` **inside** the generator and `yield` from within it |
| All lambdas in a list return the same value | late binding of the loop variable | bind at definition: `lambda x=x: x` |
| `groupby` gives repeated groups | input was not sorted by the key | sort first, or use `defaultdict(list)` |
| Flaky test involving sets | hash randomisation changes iteration order per run | sort before comparing; `PYTHONHASHSEED=0` only to confirm the diagnosis |
| Cached values from `hash()` all miss after restart | `hash()` is seeded per process | use `hashlib.blake2b` or `crc32` for anything persisted |
| `tee` uses as much memory as a list | branches consumed at very different rates | consume in lockstep, or materialise once deliberately |
| Dict lookups silently return the wrong record | duplicate keys; the last one won | build with `defaultdict(list)` and handle duplicates explicitly |
| File descriptors climb over hours | generators holding open files, abandoned on error paths | `try/finally` inside the generator; test the abandonment path |
