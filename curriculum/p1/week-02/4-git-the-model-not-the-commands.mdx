<Tab title="🟢 Layer 1 — Ground">

**New to all of this?** This layer is yours. No assumptions — every term is discovered the moment you need it.

### The one idea

Git does not store diffs. It stores **complete snapshots** of your project, each one labelled with a hash of its contents, each one pointing at the snapshot it came from. Everything else — branches, merges, rebases, `git log` — is a way of walking or extending that structure.

Learn the structure and the commands become obvious. Learn the commands first and Git stays magic forever.

### The analogy

Think of a photo album where every page is a complete photograph of your desk, and on the back of each page you have written which page came before it.

- A **commit** is one page: a full picture, plus a note saying "the page before this was #47".
- A **branch** is a sticky note you put on one page saying "main". Moving to a different page means peeling the sticky note off and putting it on another page. That is all a branch is — 41 bytes of text naming one commit.
- **`HEAD`** is a bookmark that says which page you are currently looking at.
- A **merge** adds a new page whose back says "the two pages before this were #47 and #52".
- A **rebase** takes your recent pages, re-photographs them as if the desk had started from a different page, and throws away — well, unreferences — the originals.

The album is append-only. Pages are never edited. That is why Git can be fast and why almost nothing is truly lost.

### The vocabulary, defined

- **Repository (repo)** — a project directory plus the `.git` folder holding its history.
- **Working tree** — the files you can see and edit right now.
- **Staging area (index)** — a holding area between the working tree and a commit. `git add` puts things here; `git commit` turns what is here into a commit.
- **Commit** — an immutable snapshot: the full tree of files, the parent commit(s), author, timestamp, and message. Named by a 40-character SHA-1 hash.
- **Hash / SHA** — the 40 hex characters that name an object. Computed from the content, so identical content always gives an identical hash.
- **Branch** — a movable label pointing at one commit. Literally a file containing a hash.
- **`HEAD`** — a pointer to the branch (or commit) you have checked out.
- **Merge** — combine two branches by creating a commit with two parents.
- **Rebase** — replay your commits on top of a different base, creating *new* commits with new hashes.
- **Conflict** — Git could not automatically combine two changes to the same region, and is asking you to decide.
- **Remote** — another copy of the repository, usually on a server. `origin` is the conventional name.
- **DAG (directed acyclic graph)** — the shape the commits form: arrows point backwards to parents, and there are no cycles.

### Draw the graph after every command

Do this whole sequence and run `git log --oneline --graph --all` after **every** step. Drawing the graph on paper as you go is the exercise; the commands are incidental.

```bash
mkdir demo && cd demo && git init -q
git config user.name "You" && git config user.email you@example.com

echo "line 1" > a.txt && git add a.txt && git commit -qm "A"
echo "line 2" >> a.txt && git commit -qam "B"
git log --oneline --graph --all
```

```
* 8f3c1a2 B
* 1b90ee4 A
```

Two commits, `B` pointing back to `A`. Now branch:

```bash
git switch -c feature          # create a branch AND move HEAD to it
echo "feature work" > f.txt && git add f.txt && git commit -qm "D"
git switch main
echo "line 3" >> a.txt && git commit -qam "C"
git log --oneline --graph --all
```

```
* 7d2e5b1 (HEAD -> main) C
| * 4a1c8f9 (feature) D
|/
* 8f3c1a2 B
* 1b90ee4 A
```

The `|/` is the fork point. Both `C` and `D` have `B` as their parent. **Nothing was copied** — branching created a 41-byte file.

```bash
cat .git/refs/heads/feature
```

```
4a1c8f97cfd4c5b1a3e9e2a0d8f7b6c5e4d3a2b1
```

That is the entire branch: one hash in one file.

### Merge versus rebase, on the same graph

```bash
git merge feature -m "M: merge feature"
git log --oneline --graph --all
```

```
*   c9f0aa3 (HEAD -> main) M: merge feature
|\
| * 4a1c8f9 (feature) D
* | 7d2e5b1 C
|/
* 8f3c1a2 B
```

The merge commit `M` has **two** parents. The history is a true record of what happened: two lines of work existed and were combined here.

Now the other option, from the same starting point:

```bash
git switch feature
git rebase main
git log --oneline --graph --all
```

```
* e51b7c4 (HEAD -> feature) D'
* 7d2e5b1 (main) C
* 8f3c1a2 B
```

Straight line. But look at the hash: `D` was `4a1c8f9` and `D'` is `e51b7c4`. **It is a different commit.** Same changes, different parent, therefore different content, therefore different hash. The original `D` still exists in the object database but nothing points at it — which is what `reflog` is for.

### Line-by-line walkthrough of a commit

```bash
git cat-file -p HEAD
```

```
tree 2e81171448eb9f2ee3821e3d447aa6b2fe3ddba1
author You <you@example.com> 1755000000 +0530
committer You <you@example.com> 1755000000 +0530

B
```

- `tree` — the hash of a **tree object**, which is the directory listing for this snapshot.
- `parent` — absent here because this example is showing the first commit; normally there is one line per parent, and a merge commit has two.
- `author` versus `committer` — the author wrote the change; the committer created this commit object. They differ after a rebase or a `cherry-pick`, which is how you can tell a commit has been replayed.
- The blank line, then the message.

Follow the tree down:

```bash
git cat-file -p HEAD^{tree}
```

```
100644 blob ce013625030ba8dba906f756967f9e9ca394464a	a.txt
```

`100644` is the file mode (regular file, not executable). Then the type, the hash, and the name. Follow it once more:

```bash
git cat-file -p ce013625030ba8dba906f756967f9e9ca394464a
```

```
hello
```

Three levels: commit → tree → blob. That is the whole storage model.

### Guided practice

<Steps>
<Step title="Compute a Git hash by hand">
Git hashes `"<type> <size>\0<content>"`, not the bare content.

```bash
echo "hello" > a.txt        # 6 bytes: h-e-l-l-o-newline
printf 'blob 6\0hello\n' | shasum
git hash-object a.txt
```

Both print:

```
ce013625030ba8dba906f756967f9e9ca394464a
```

You just reproduced Git's naming scheme with two shell commands. This is the moment Git stops being magic.
</Step>
<Step title="Cause a real conflict and resolve it">

```bash
git switch main && echo "shared line - main version" > shared.txt && git add . && git commit -qm "main edit"
git switch -c other HEAD~1 && echo "shared line - other version" > shared.txt && git add . && git commit -qm "other edit"
git switch main && git merge other
```

```
Auto-merging shared.txt
CONFLICT (add/add): Merge conflict in shared.txt
```

```bash
cat shared.txt
```

```
<<<<<<< HEAD
shared line - main version
=======
shared line - other version
>>>>>>> other
```

Between `<<<<<<<` and `=======` is **your** side (`HEAD`, where you are). Between `=======` and `>>>>>>>` is **their** side. Edit the file to what you actually want — usually not either side verbatim — delete all three marker lines, then `git add shared.txt && git commit`.

`git merge --abort` at any point puts everything back. Nothing is at risk.
</Step>
<Step title="Recover a 'lost' commit">

```bash
git switch -c doomed && echo x >> a.txt && git commit -qam "important work"
git rev-parse HEAD                      # note this hash
git switch main && git branch -D doomed # branch deleted!
git reflog | head -3
```

```
6f28172 HEAD@{0}: checkout: moving from doomed to main
a4c071f HEAD@{1}: commit: important work
9da5741 HEAD@{2}: checkout: moving from 9da5741 to doomed
```

```bash
git cat-file -t a4c071f      # commit — still there
git switch -c recovered a4c071f
```

The reflog records every position `HEAD` has held for the last 90 days. **Deleting a branch deletes a 41-byte file, not your work.**
</Step>
<Step title="Write a commit message worth reading">

```
Fix duplicate charge when retry races the webhook

The payment webhook and the client retry could both mark an order
paid, and neither checked whether the other already had. Under load
we saw 0.3% of orders charged twice.

Add a unique constraint on (order_id, idempotency_key) and treat the
constraint violation as success, so whichever arrives second is a
no-op.

Fixes NEXUS-812.
```

Subject line: imperative mood ("Fix", not "Fixed"), under 50 characters, no trailing period. Blank line. Body wrapped at 72 characters explaining **why**, not what — the diff already says what. This is the format `git log --oneline` and every Git tool assumes.
</Step>
</Steps>

<Accordion title="Checkpoint — 5 questions before you continue">

1. **What does Git store in a commit — a diff or a snapshot?** — a snapshot, as a tree of blobs. Diffs are computed on demand when you ask for them.
2. **What is a branch, physically?** — a file under `.git/refs/heads/` containing one 40-character hash. Creating one copies nothing.
3. **Why does a rebased commit have a different hash?** — its parent changed, the parent is part of the commit's content, and the hash is computed from the content.
4. **You deleted a branch with unmerged work. Is it gone?** — no. `git reflog` finds the commit for 90 days by default; `git switch -c name HASH` brings it back.
5. **In a conflict, which side is above `=======`?** — yours (`HEAD`, the branch you are on). Theirs is below.
</Accordion>

### Merge versus rebase: the actual decision

This argument is usually conducted as a matter of taste. It is not; there is a rule.

**Never rebase commits that other people have.** Rebasing rewrites history: the old commits are unreferenced and new ones with new hashes take their place. If a colleague has the old commits, their next `git pull` produces a duplicated, tangled mess, and the fix requires them to reset to your version and lose anything they built on top.

Within that constraint:

| | Merge | Rebase |
|---|---|---|
| History | true record — shows that two lines existed | linear, as if the work happened sequentially |
| `git bisect` | works; merge commits can be skipped | works better — every commit is a clean, testable state |
| Conflict resolution | once, in the merge commit | potentially once **per commit** being replayed |
| Reverting the whole feature | one `git revert -m 1 <merge>` | revert each commit, or revert a range |
| Safe on shared branches | **yes** | **no** |
| `git blame` quality | slightly noisier | cleaner |

The workflow most teams converge on, and the one worth adopting: **rebase your own feature branch onto the latest main before opening a PR** (linear, easy to review, every commit testable), then **merge the PR with a merge commit** (the merge point is a real event; the feature is revertible as a unit). `git pull --rebase` for your own in-progress work; `git config --global pull.rebase true` makes that the default and eliminates the "Merge branch 'main' into main" noise commits that clutter so many repositories.

### Atomic commits, and `add -p`

A commit should be one logical change that leaves the tree in a working state. That property is what makes `git bisect`, `git revert` and `git blame` useful; without it they all degrade.

```bash
git add -p                # interactively stage hunks, not whole files
```

`y` stage this hunk, `n` skip, `s` split into smaller hunks, `e` edit the hunk by hand, `q` quit. This is how you turn an afternoon of mixed work into four clean commits, and it is the single highest-value Git command most people never learn.

```bash
git commit --amend                     # fix the last commit (message or content)
git commit --fixup=<hash>              # mark a commit as a fix for an earlier one
git rebase -i --autosquash main        # ...and squash all fixups automatically
```

The `--fixup` / `--autosquash` pair is the clean way to address review comments: make a fixup commit per comment, then squash them into the right original commits just before merge. The reviewer sees incremental changes; main gets clean history.

### Interactive rebase: the operations

```bash
git rebase -i HEAD~5
```

```
pick 7d2e5b1 Add parser skeleton
squash 4a1c8f9 fix typo
reword 8f3c1a2 Add tokenizer
edit 1b90ee4 Add evaluator
drop e51b7c4 debugging printf
```

- **`pick`** — keep as is.
- **`reword`** — keep the changes, edit the message.
- **`squash`** — fold into the previous commit, combining messages.
- **`fixup`** — like squash but discard this commit's message.
- **`edit`** — stop here so you can amend the content.
- **`drop`** — remove the commit entirely.
- Reordering the lines reorders the commits.

If it goes wrong: `git rebase --abort` during, or `git reset --hard ORIG_HEAD` after. `ORIG_HEAD` is set to where you were before the rebase started, which makes the whole operation reversible.

### `.gitignore`, and the file that is already tracked

```gitignore
# build artifacts
build/
*.o
*.pyc
__pycache__/

# environments and secrets
.env
.env.*
!.env.example        # negation: DO track the template
venv/
.venv/

# editor and OS noise
.DS_Store
.idea/
*.swp
```

The rule everyone hits: **`.gitignore` only affects untracked files.** Adding a pattern for a file Git is already tracking does nothing. To stop tracking it:

```bash
git rm --cached .env       # remove from the index, keep on disk
git commit -m "Stop tracking .env"
```

And the harder truth: this removes it going forward but **the file's contents remain in every historical commit**. If it was a secret, it is compromised — rotate the credential first, then consider `git filter-repo` (the modern replacement for `filter-branch`) to purge it, which rewrites every commit hash in the repository and requires everyone to re-clone. Rotate first. Always rotate first.

### Trade-offs table

| Decision | Choose X when… | Choose Y when… |
|---|---|---|
| Merge vs rebase | **Merge** for shared branches, for integrating a finished feature, and whenever the fact that parallel work existed is information worth keeping | **Rebase** for your own unpushed work, to keep a feature branch current, and to produce a reviewable linear series — never on commits others have |
| Squash-merge vs merge commit | **Squash** when the branch's intermediate commits are noise ("wip", "fix typo") and the unit of meaning is the PR | **Merge commit** when the intermediate commits are meaningful and individually testable — squashing destroys bisect granularity inside the feature |
| Long-lived branches vs trunk-based | **Long-lived release branches** when you must support multiple shipped versions | **Trunk-based with feature flags** otherwise: merge conflicts grow superlinearly with branch age, and a two-week branch is a different problem from a two-day one |
| `revert` vs `reset` | **`revert`** for anything already pushed — it adds a new commit undoing the change, so history stays valid for everyone | **`reset`** only for local, unpushed work. `reset --hard` on a pushed branch forces everyone else to recover |

### The commands worth knowing beyond the basics

```bash
git log --oneline --graph --all --decorate       # the graph, always
git log -S 'functionName'                        # commits that ADDED or REMOVED this string
git log -p -- path/to/file                       # full history of one file, with diffs
git log --follow -- path/to/file                 # ...across renames
git blame -w -C -M file.c                        # ignore whitespace, detect moved/copied code
git stash push -m "wip: parser" -- src/parse.c   # stash specific paths, with a message
git cherry-pick -x <hash>                        # copy one commit; -x records the origin
git range-diff main..old main..new               # diff two versions of a branch — review a force-push
git worktree add ../hotfix main                  # a second working tree, no stashing needed
```

`git log -S` (the "pickaxe") is the one to remember: it answers "when did this string enter the codebase and who put it there" in one command, which is usually the actual question behind "who wrote this".

`git worktree` is the answer to "I need to fix something on main but I have uncommitted work" — it checks out another branch into a separate directory sharing the same object database, so you neither stash nor clone.

### What breaks in the real world

A team ran `git push --force` to clean up a shared feature branch after an interactive rebase. Three colleagues had already pulled the old commits. Over the next two hours, each of them ran `git pull`, which merged the old and new histories together, producing a branch with every commit duplicated — once with its original hash and once with its rebased hash — plus three merge commits nobody intended.

`git log --oneline` showed 47 commits for 22 logical changes. Two of the rebased commits had been dropped in the confusion, so a bug fix that had been reviewed and approved was silently absent from the branch, and it shipped without that fix.

Two things would have prevented it. **`git push --force-with-lease`** instead of `--force`: it refuses the push if the remote has moved since you last fetched, which catches exactly the case where someone else has pushed in the meantime. And a **protected branch rule** on anything shared, which is one checkbox in GitHub/GitLab settings.

The recovery, for the record: each colleague ran `git fetch && git reset --hard origin/feature`, having first checked `git reflog` for any local work they needed to `cherry-pick` back on top. Total cost about three hours across four people, plus a bug in production. The commit that got lost was found by `git log -S` on the fix's distinctive string.

<Accordion title="Design checkpoint — one question, with a model answer">

**Question.** A performance regression appeared somewhere in the last 200 commits on main. Reproducing it takes about 90 seconds. A colleague suggests reading the diffs of the likely-looking commits. What do you do instead, and what do you need in place for it to work?

**Model answer.** `git bisect run`, with a script that exits 0 for good and non-zero for bad.

Bisect does binary search over the commit range, so 200 commits take ⌈log₂ 200⌉ = **8 test runs** — measured on a 200-commit repository, the sequence was 200 → 99 → 49 → 24 → 12 → 5 → 2 → 0 remaining, and it named the exact commit. At 90 seconds per test that is 12 minutes of wall time and roughly zero minutes of human attention. Reading 200 diffs is an afternoon, and it finds the bug only if the cause is visible in a diff — which for a performance regression it often is not.

```bash
cat > /tmp/bisect-test.sh <<'EOF'
#!/bin/sh
make -s build || exit 125          # 125 = SKIP: cannot test this commit
./bench --max-ms 250 || exit 1     # non-zero = bad
exit 0
EOF
chmod +x /tmp/bisect-test.sh
git bisect start HEAD HEAD~200
git bisect run /tmp/bisect-test.sh
git bisect reset
```

**Exit code 125 is the important detail.** It means "skip this commit", for commits that do not build or where the test is not meaningful. Without it, an unbuildable commit is scored "bad" and bisect converges on the wrong answer.

What you need in place for this to work, and this is the real content of the question:

1. **Every commit must build and be testable.** This is what "atomic commits" buys you, and it is the strongest practical argument for the rebase-then-merge workflow: a squashed feature branch bisects to "the whole feature", which tells you much less.
2. **A deterministic test with a threshold.** Performance tests are noisy; run the benchmark several times and compare the *minimum* against a threshold with margin, exactly as in Week 1. A flaky test makes bisect converge confidently on a random commit, which is worse than not bisecting.
3. **The regression must be monotone.** Bisect assumes one transition from good to bad. If the behaviour flaps, bisect will find *a* transition and it may not be the one you want. Verify the endpoints explicitly before starting.

Finally, `git bisect` is not only for regressions: `git log -S 'string'` finds when a string appeared, and `git bisect` with an inverted test finds when a bug was *fixed*, which is how you locate the commit to backport.
</Accordion>

### The object database, verified by hand

Git has exactly four object types, all stored the same way: **blob** (file contents), **tree** (a directory listing), **commit** (a snapshot plus parents and metadata), and **tag** (an annotated tag). Every object is stored as

```
<type> <byte-length>\0<content>
```

zlib-compressed, in a file named after the SHA-1 of that byte string. Verify it:

```bash
$ echo "hello" > a.txt
$ printf 'blob 6\0hello\n' | shasum
ce013625030ba8dba906f756967f9e9ca394464a
$ git hash-object a.txt
ce013625030ba8dba906f756967f9e9ca394464a
$ git rev-parse HEAD:a.txt
ce013625030ba8dba906f756967f9e9ca394464a
```

Three ways to the same 40 characters. The header is why `sha1sum a.txt` alone gives a *different* value — a fact worth knowing before you spend an hour confused.

**Content addressing has consequences that explain most of Git's behaviour:**

- **Deduplication is automatic and global.** The same file content in 500 commits is one blob. Copy a file without changing it and Git stores nothing new; the tree just names the same blob twice.
- **Renames are not stored.** Git records trees, not operations. `git log --follow` and `git blame -M` *detect* renames after the fact by comparing content similarity (default threshold 50%). This is why a rename plus a heavy edit in one commit loses the trail.
- **History is tamper-evident.** A commit's hash covers its tree and its parent hash, so it covers the entire history transitively. Changing an old commit changes every descendant's hash. This is a Merkle DAG — the same structure as a blockchain, and it predates Bitcoin by four years.
- **Every hash change is a new object.** Rebasing 20 commits creates 20 new commit objects; the old ones remain until garbage collection.

On SHA-1: Git has migrated to **SHA-1DC** (collision detection, from the SHAttered work), which detects the known collision-attack patterns and refuses them. Full SHA-256 repository support exists in git 2.29+ but is not interoperable with SHA-1 repositories, so essentially nobody uses it yet. The practical exposure is low — a Git collision attack requires you to accept a crafted object — but the migration is a real, slow, ongoing piece of work.

### Loose objects, packfiles, and where the disk went

Git writes new objects individually ("loose"): one zlib-compressed file each. Periodically it repacks them into a **packfile** with delta compression, storing similar objects as deltas against each other.

Measured on a repository of **201 commits**, each adding one line to a growing text file:

| State | `.git` size |
|---|---|
| Loose objects (201 commits, no gc) | **2.5 MB** |
| After `git gc` | **236 KB** |

**10.6× smaller.** The mechanism is that each of the 201 versions of `data.txt` was stored as a complete compressed blob; after packing, they are stored as deltas against each other, and a one-line difference is a very small delta.

Two operational consequences:

- **`git gc` runs automatically** when loose objects accumulate (`gc.auto`, default 6700 loose objects). If you script Git operations that create many objects, run `git gc` explicitly rather than letting it fire mid-workflow.
- **Delta compression is why `git clone` is fast** relative to the history size, and why a repository with large binary files is slow: binaries do not delta well, so each version is stored nearly in full. That is the entire motivation for Git LFS, which stores a pointer file in Git and the blob elsewhere.

Packfiles also explain a common confusion: `git count-objects -vH` shows both loose and packed counts, and the "size" of a repository depends entirely on when it was last packed.

### Bisect, measured

On a 201-commit repository with a defect introduced at commit 137, `git bisect run` with a shell script that greps for the defect:

```
Bisecting: 99 revisions left to test after this (roughly 7 steps)
Bisecting: 49 revisions left to test after this (roughly 6 steps)
Bisecting: 24 revisions left to test after this (roughly 5 steps)
Bisecting: 12 revisions left to test after this (roughly 4 steps)
Bisecting:  5 revisions left to test after this (roughly 3 steps)
Bisecting:  2 revisions left to test after this (roughly 2 steps)
Bisecting:  0 revisions left to test after this (roughly 1 step)
ca7f288d83503d2ef6fd5d1891c487b85618c2ab is the first bad commit
```

**8 test runs for 200 candidates**, exactly ⌈log₂ 200⌉ = 8. It is Week 1's binary search, running over a commit DAG instead of an array — and like binary search, its correctness depends on a precondition: the property must be **monotone** (good before, bad after). If it flaps, bisect converges confidently on a wrong answer, which is the failure mode to watch for.

For a non-linear history, bisect picks the commit that best splits the remaining DAG by *ancestry*, not by list position, which is why merge commits do not break it.

### Reflog: what is actually recoverable

```
$ git reflog | head -3
6f28172 HEAD@{0}: checkout: moving from lost to main
a4c071f HEAD@{1}: commit: important work
9da5741 HEAD@{2}: checkout: moving from 9da5741 to lost
$ git cat-file -t a4c071f
commit
```

After deleting the branch, the commit is still a valid object. The reflog records every value `HEAD` and each branch has held.

Retention, and this is the part people get wrong: **`gc.reflogExpire` defaults to 90 days for reachable entries and `gc.reflogExpireUnreachable` to 30 days for unreachable ones.** After that, `git gc` prunes them and the objects become genuinely unreachable, then are deleted by `git prune` (default `gc.pruneExpire` of two weeks). So "Git never loses anything" is true for about a month, not forever.

The recovery toolkit, in order:

```bash
git reflog                        # everything HEAD has pointed at
git reflog show <branch>          # everything one branch has pointed at
git fsck --lost-found             # dangling commits and blobs with no reflog entry
git cat-file -p <hash>            # inspect a candidate before restoring
git switch -c recovered <hash>    # bring it back
```

`git fsck --lost-found` is the last resort — it finds objects that exist but are unreachable, including commits whose reflog entry expired but whose objects have not yet been pruned. It writes them to `.git/lost-found/`.

The one thing that genuinely destroys work: **changes that were never committed**. `git checkout -- file`, `git restore file`, `git reset --hard` and `git clean -fd` on uncommitted work are unrecoverable, because the content never entered the object database. `git stash` before anything destructive; a stash is a real commit and appears in the reflog.

### Scale: where Git stops being fast

Git's performance model is dominated by two things: the number of files in the working tree (because status must stat them all) and the total history size.

- **`git status` is O(files in the working tree).** At around 100,000 files, an uncached `status` takes seconds. `core.fsmonitor` (built in since git 2.37, using FSEvents on macOS and a watcher daemon on Linux/Windows) makes it near-constant by tracking changes as they happen. Enable it on any large repo: `git config core.fsmonitor true`.
- **The index is a single file.** `.git/index` holds one entry per tracked file, and it is rewritten on many operations. The **sparse index** (git 2.34+, with `sparse-checkout` in cone mode) collapses whole directories you have not checked out into single entries, and Microsoft reported it taking Office's repository from tens of thousands of index entries to hundreds.
- **`git clone` is O(history)**, which is why `--depth 1` (shallow) and `--filter=blob:none` (partial clone, fetching blobs on demand) exist. Partial clone is the better default for CI: you get full history for `log` and `bisect` but only download the blobs you actually check out.
- **Large binaries do not delta-compress.** A 50 MB binary changed 100 times is 5 GB of packfile, and every clone downloads all of it. Git LFS replaces the blob with a pointer and stores the content in a separate service.

Monorepo tooling worth knowing exists: Microsoft's **VFS for Git** and its successor **Scalar** (now part of Git itself as `scalar clone`) combine partial clone, sparse checkout, fsmonitor and background maintenance into one command.

### Production failure modes and how you detect them

| Failure | Signature | Detection / fix |
|---|---|---|
| Force-push tangles a shared branch | commit count roughly doubles; duplicate messages in `git log` | `--force-with-lease` always; protected branches; recover with `git reset --hard origin/branch` after checking reflog |
| Secret committed | it is in every clone and every fork, forever | **rotate the credential first**; then `git filter-repo` and force everyone to re-clone; add a pre-commit secret scanner (`gitleaks`) |
| Bisect names an innocent commit | the test is flaky or the property is not monotone | verify both endpoints explicitly; run the test N times and use the minimum; use exit 125 to skip unbuildable commits |
| Repository is huge and clones are slow | `.git` much larger than the working tree | `git count-objects -vH`; find big blobs with `git rev-list --objects --all \| git cat-file --batch-check`; move to LFS |
| `git status` takes 8 seconds | very large working tree | `core.fsmonitor true`; `git config core.untrackedCache true`; sparse checkout |
| "Lost" work after `reset --hard` | uncommitted changes gone | unrecoverable if never committed — `git stash` before destructive operations; committed work is in the reflog for 30–90 days |
| `git blame` shows one commit for everything | a whole-file reformat | `git blame -w --ignore-rev <hash>`; commit a `.git-blame-ignore-revs` file and set `blame.ignoreRevsFile` |

### Frontier and research pointers

- **Merkle, R. C. (1987). "A Digital Signature Based on a Conventional Encryption Function." *CRYPTO '87*.** One-sentence takeaway: hashing a tree of hashes makes any change to any leaf detectable at the root, which is exactly what makes Git's history tamper-evident.
- **Torvalds, L. (2007). "Tech Talk: Linus Torvalds on git." Google Talk.** One-sentence takeaway: Git was designed around distribution and content-addressing first and usability second, which explains both its power and its command-line surface.
- **Stevens, M., Bursztein, E., Karpman, P., Albertini, A. & Markov, Y. (2017). "The First Collision for Full SHA-1." *CRYPTO*.** One-sentence takeaway: SHA-1 collisions are practical for a well-resourced attacker, which is why Git ships SHA-1DC collision detection and why the SHA-256 migration exists.
- **Bird, C., Rigby, P. C., Barr, E. T. et al. (2009). "The Promises and Perils of Mining Git." *MSR*.** One-sentence takeaway: rebases, squashes and merge strategies mean the commit history is a *curated artifact*, not a faithful record of development, which limits what you can infer from it.
- **Microsoft, "Scalar" and the sparse-index work (git 2.34+, `sparse-index` design doc).** One-sentence takeaway: making Git's index sparse — collapsing unchecked-out directories to single entries — is what made a 300 GB monorepo usable with ordinary Git commands.

### Stretch challenge

Build the smallest thing that is recognisably Git.

1. Implement `hash-object`, `cat-file`, and a minimal `commit-tree` in Python or C: write blobs and trees into `.git/objects` using Git's exact format (`<type> <len>\0<content>`, zlib-compressed, path `.git/objects/ab/cdef…`). **Verify with real Git**: after your program writes an object, `git cat-file -p <hash>` must print it back correctly.
2. Add `write-tree` for a directory (including nested directories and file modes) and `commit-tree` producing a commit object. Then run `git log` on the repository your program built. If `git log` shows your commits, your format is byte-correct.
3. Now measure: build a repository with 200 commits each changing one line of a 10,000-line file, using your implementation. Compare `.git` size before and after `git gc`. Our reference measured **2.5 MB → 236 KB, 10.6×**. What do you get, and how does the ratio change if the change per commit is a random line versus an appended line?
4. Implement `git bisect` yourself over a linear history, taking a test command. Confirm it converges in ⌈log₂ n⌉ steps and handle the exit-125 skip case correctly.

The open question with no single right answer: Git chose snapshots plus delta-compression-at-rest over storing deltas directly (as SVN and Mercurial's revlog largely do). That makes checkout O(1) in history depth and packing expensive. Where does that trade-off break down — and would you make the same choice for a repository whose dominant content is 200 MB model checkpoints rather than source text? Design the storage layer you would actually want for a repository of model weights, and say what you would give up.

## Apply it at work

<AccordionGroup>
<Accordion title="If you're a student" icon="graduation-cap">

**Portfolio line:** *"A minimal Git implementation — `hash-object`, `write-tree`, `commit-tree` — producing objects that real `git log` reads correctly, plus a measured comparison of loose versus packed storage (2.5 MB → 236 KB)."* Building a tool's format from the spec and having the real tool accept your output is a strong signal.

**The interview angle.** "Explain the difference between merge and rebase" is asked constantly, and the answer that scores is not the definition — it is the rule plus the mechanism: *rebase creates new commits with new hashes because the parent is part of the commit's content; that is fine for your own unpushed work and destructive for anything others have, because their pull will merge the old and new histories into a duplicated mess.*

Then have the recovery answer ready, because it is the natural follow-up: *reflog for 90 days on reachable entries and 30 on unreachable, then `fsck --lost-found`; the only truly unrecoverable thing is work that was never committed.*
</Accordion>
<Accordion title="If you're working" icon="briefcase">

Three places this shows up in a normal engineering week:

1. **The regression nobody can explain.** `git bisect run` with a 30-line test script finds it in ⌈log₂ n⌉ runs while you do something else. The prerequisite is that commits are individually buildable, which is the practical argument for atomic commits — make it in code review, not in the abstract.

2. **"Who wrote this and why."** `git log -S 'distinctive_string'` finds the commit that introduced a line; `git log --follow -p -- path` gives a file's whole story across renames; `git blame -w -C -M` ignores whitespace and follows moved code. These three answer most archaeology questions in seconds, and most engineers know none of them.

3. **Repository hygiene that costs nothing.** Turn on `pull.rebase`, `core.fsmonitor`, `--force-with-lease` as a habit, and a `.git-blame-ignore-revs` file the first time you reformat the codebase. Add `gitleaks` to pre-commit. Each is one line and each prevents a recurring class of pain.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Colleagues' branches tangle after your push | you force-pushed a rebased shared branch | `--force-with-lease`; never rebase commits others have; protect shared branches |
| `.gitignore` does not ignore a file | the file is already tracked | `git rm --cached FILE`, commit; ignore rules apply only to untracked files |
| A secret is in the history | committed once, present in every clone | **rotate the credential first**; then `git filter-repo`; add a pre-commit secret scanner |
| Bisect blames an innocent commit | flaky test, or a commit that would not build was scored bad | exit 125 to skip; run the test N times and take the minimum; verify both endpoints first |
| Merge conflict markers committed | resolved by hand, forgot to delete `<<<<<<<` lines | add a pre-commit hook grepping for conflict markers; `git diff --check` also flags them |
| `git blame` shows one commit everywhere | a repository-wide reformat | `.git-blame-ignore-revs` plus `blame.ignoreRevsFile`; `git blame -w` |
| Deleted a branch with unmerged work | it looks gone | `git reflog`, then `git switch -c name HASH`; 30–90 days of retention |
| Uncommitted work lost to `reset --hard` | it was never in the object database | genuinely unrecoverable; `git stash` before anything destructive |
| `.git` is far bigger than the source | binaries stored in history; they do not delta-compress | find big blobs via `git rev-list --objects --all`; migrate to Git LFS |
| `git status` takes seconds | very large working tree | `git config core.fsmonitor true` and `core.untrackedCache true` |

- **[`git help revisions` (gitrevisions(7)).](https://git-scm.com/docs/gitrevisions)** Read this for the full grammar of `HEAD~3`, `HEAD^2`, `main@{yesterday}`, `HEAD^{tree}` and `branch@{u}` — the notation that makes every other command shorter.
- **[`git help bisect` — the `run` section and exit code 125.](https://git-scm.com/docs/git-bisect)** Read this specifically for the skip semantics, which is the detail that makes automated bisect trustworthy.
- **[Git 2.34+ sparse-index design document (`Documentation/technical/sparse-index.txt`).](https://github.com/git/git/blob/master/Documentation/technical/sparse-index.adoc)** Read this for how Git made very large monorepos workable, and for what `core.fsmonitor` actually does.
- **[`git filter-repo` documentation.](https://github.com/newren/git-filter-repo)** Read this instead of any `filter-branch` tutorial; `filter-branch` is officially discouraged as slow and dangerous, and `filter-repo` is the recommended replacement.

**Papers**

- **[Merkle, R. C. (1987). "A Digital Signature Based on a Conventional Encryption Function." *CRYPTO '87*, 369–378.](https://doi.org/10.1007/3-540-48184-2_32)** One-sentence takeaway: the hash-of-hashes tree structure Git uses for history integrity was formalised twenty years before Git existed.
- **[Stevens, M. et al. (2017). "The First Collision for Full SHA-1." *CRYPTO*, 570–596.](https://doi.org/10.1007/978-3-319-63688-7_19)** One-sentence takeaway: SHA-1 collisions became practical, prompting Git's SHA-1DC collision detection and the long-running SHA-256 migration.
- **[Bird, C., Rigby, P. C., Barr, E. T., Hamilton, D. J., German, D. M. & Devanbu, P. (2009). "The Promises and Perils of Mining Git." *MSR*, 1–10.](https://doi.org/10.1109/MSR.2009.5069475)** One-sentence takeaway: because history can be rewritten, a Git log is a curated narrative rather than a record of what happened, which matters for anyone drawing conclusions from it.

- **[Chacon, S. & Straub, B., *Pro Git*, 2nd ed., Chapters 3 (Branching), 7 (Tools: `add -p`, `bisect`, `rerere`) and 10 (Internals).](https://git-scm.com/book/en/v2)** Chapter 7's `rerere` section is the underrated one — it makes Git remember conflict resolutions and replay them, which pays for itself on any long-lived branch.
