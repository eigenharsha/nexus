**New to all of this?** This layer is yours. No assumptions — every term is discovered the moment you need it.

### The one idea

A shell is a program whose whole job is to read a line of text, turn it into a program launch, and wait. It is not "the terminal" and it is not the operating system. Understanding the six steps it performs on that line explains almost every confusing thing the command line does.

### The analogy

The shell is a **receptionist**. You hand over a request written on a slip. The receptionist expands the shorthand you used ("all the invoices" becomes a list of actual filenames), looks up which department handles it, sends a runner to do the job, tells the runner where to put the output, and waits by the desk for the runner to come back with a yes or a no.

Three consequences fall out immediately. The runner cannot rearrange the receptionist's desk — a child process cannot change its parent's directory or variables. The receptionist expands the shorthand *before* the runner sees it — which is why `rm *.txt` in an empty directory says "no such file: *.txt". And the receptionist learns only one thing when the runner returns: succeeded or failed, as a number.

### The vocabulary, defined

- **Shell** — a program that reads command lines and runs programs. `zsh` is the macOS default since Catalina; `bash` is the Linux default.
- **Terminal emulator** — the window (Terminal.app, iTerm2, GNOME Terminal). It draws characters; the shell interprets them. Two different programs.
- **Process** — a running program, with its own memory, its own open files, and a numeric **PID** (process ID).
- **`fork()`** — a system call that creates a near-copy of the current process. The copy is the **child**; the original is the **parent**.
- **`exec()`** — a system call that replaces the current process's program with a different one, keeping the PID and the open files.
- **System call** — a request from your program to the kernel. Opening files, creating processes and reading from the network are all system calls.
- **File descriptor (fd)** — a small integer naming an open file inside one process. Every process starts with three: **0 = stdin**, **1 = stdout**, **2 = stderr**.
- **Redirection** — attaching a file descriptor to something other than the terminal. `> f` sends fd 1 to `f`; `2> f` sends fd 2.
- **Environment variable** — a named string every process inherits from its parent. `PATH`, `HOME`, `USER`.
- **`PATH`** — a colon-separated list of directories the shell searches, **in order**, for the program you named.
- **Exit code** — a number from 0 to 255 a process returns when it ends. **0 means success**; anything else is failure. Available as `$?`.
- **Signal** — an asynchronous notification sent to a process. `SIGINT` (2) is Ctrl-C, `SIGTERM` (15) is a polite "please stop", `SIGKILL` (9) cannot be caught or ignored.
- **Permission bits** — nine bits on every file: read/write/execute, for user/group/other.

### The six steps, demonstrated

```bash
$ echo hello > out.txt
```

1. **Expand.** The shell processes quotes, `$VARIABLES`, globs (`*.txt`), and command substitution. Nothing has run yet.
2. **Resolve.** Is `echo` a shell builtin, a function, an alias, or a file on `PATH`? Ask the shell directly:

```bash
$ type -a echo
echo is a shell builtin
echo is /bin/echo
```

Two answers, and the **first** one wins. This single command answers most "why is it running the wrong version" questions.

3. **`fork()`.** The shell makes a copy of itself.
4. **Redirect, in the child.** The child points fd 1 at `out.txt`. Crucially this happens in the child, *after* the fork — which is why the shell's own output is unaffected.
5. **`exec()`.** The child replaces itself with the `echo` program.
6. **`wait()`.** The parent blocks until the child exits and collects its exit code.

```bash
$ ls /nonexistent
ls: /nonexistent: No such file or directory
$ echo $?
1
$ ls /
... 
$ echo $?
0
```

### Why `cd` cannot be a program

```bash
$ type -a cd
cd is a shell builtin
```

If `cd` were an external program, the shell would fork a child, the child would change *its own* directory, and then exit — leaving the parent exactly where it was. A child cannot modify its parent's state. That is why `cd`, `export`, `source` and `exit` must all be builtins, and it is why a script that does `cd /somewhere` does not move your interactive shell.

The same rule explains `export`. Environment variables flow **down** into children and never back up.

### The permission grid

```bash
$ ls -l script.sh
-rwxr-x---  1 aarav  staff  120 Aug 12 09:14 script.sh
 ^^^^^^^^^
```

Read it as a 3×3 grid — three groups of three:

| | read (4) | write (2) | execute (1) | octal |
|---|---|---|---|---|
| **user** (owner) | r | w | x | 4+2+1 = **7** |
| **group** | r | − | x | 4+0+1 = **5** |
| **other** | − | − | − | **0** |

So `rwxr-x---` is **750**. `chmod 750 script.sh` sets it. The first character (`-` here, `d` for a directory, `l` for a symlink) is the file type and is not part of the nine bits.

For directories the meanings shift and this trips up everyone: **r** means "list the names inside", **w** means "create or delete entries", and **x** means "traverse into it / access things by name". A directory with `r` but no `x` lets you see the filenames and read nothing. `x` without `r` lets you open `dir/known-file` but not list the directory — which is exactly how `/home` is often configured.

### Smallest working example

```bash
#!/usr/bin/env bash
set -euo pipefail

echo "pid=$$  parent=$PPID"
echo "this goes to stdout"
echo "this goes to stderr" >&2
exit 3
```

```bash
$ chmod 755 demo.sh
$ ./demo.sh > out.txt
this goes to stderr
$ echo $?
3
$ cat out.txt
pid=41297  parent=41288
this goes to stdout
```

The stderr line appeared on the terminal even though we redirected output — because `>` redirects fd 1 only. To capture both: `./demo.sh > out.txt 2>&1` (order matters: this means "point 1 at the file, then point 2 wherever 1 currently points").

### Line-by-line walkthrough

- `#!/usr/bin/env bash` — the **shebang**. The kernel reads the first two bytes of an executable; if they are `#!`, it runs the named interpreter with the script as an argument. Using `env` finds `bash` on `PATH` rather than hard-coding `/bin/bash`, which matters because macOS ships bash 3.2 from 2007 at `/bin/bash` and Homebrew installs bash 5.x elsewhere.
- `set -e` — exit immediately if any command returns non-zero. Without it, a script keeps going after a failure and does the next step on bad data.
- `set -u` — treat an unset variable as an error. This is what turns `rm -rf "$PREFIX/"` from a catastrophe into an error message when `PREFIX` is unset.
- `set -o pipefail` — a pipeline's exit code is the first non-zero one, not the last command's. Without it, `false | true` succeeds.
- `$$` is this process's PID, `$PPID` its parent's.
- `>&2` sends this line to fd 2. Diagnostics go to stderr so that `script > data.csv` produces a clean data file.
- `exit 3` — any number 0–255. Use 0 for success and distinct non-zero values for distinct failures; CI reads this and nothing else.

### Guided practice

<Steps>
<Step title="Find where a command really comes from">

```bash
type -a python3
which -a python3
echo "$PATH" | tr ':' '\n' | nl
```

`PATH` is searched **left to right, first match wins**. If `type -a` lists three `python3`s, the one at the top is what runs. This is the entire explanation for "I installed it but the old one keeps running".
</Step>
<Step title="Watch redirection separate the streams">

```bash
ls / /nonexistent > good.txt 2> bad.txt
cat good.txt      # the listing
cat bad.txt       # the error
ls / /nonexistent > all.txt 2>&1
ls / /nonexistent 2>&1 > wrong.txt   # a classic bug: order matters
```

In the last line, `2>&1` runs first and points stderr at the *terminal* (where fd 1 still is), and only then is fd 1 moved to the file. Errors go to your screen. Always put `2>&1` after the redirect it should follow.
</Step>
<Step title="Kill something on purpose">

```bash
sleep 300 &          # run in the background
jobs                 # [1]+ Running   sleep 300 &
kill %1              # sends SIGTERM (15)
jobs                 # [1]+ Terminated
sleep 300 &
kill -9 %1           # SIGKILL — cannot be caught, no cleanup runs
```

`SIGTERM` is a request the program can catch and clean up after. `SIGKILL` is the kernel removing it. Reach for `-9` only after `SIGTERM` has failed, because a process killed with `-9` cannot flush its files or release its locks — Week 4 covers what that costs you.
</Step>
<Step title="Break permissions and fix them properly">

```bash
echo 'echo hi' > s.sh
./s.sh                    # permission denied — no execute bit
chmod +x s.sh && ./s.sh   # hi
ls -l s.sh                # -rwxr-xr-x  (755)
chmod 700 s.sh            # only you can read, write or run it
```

Note what "permission denied" for a script means: not that the file is unreadable, but that the execute bit is off. `bash s.sh` works even without it, because then bash — not the kernel — is opening the file.
</Step>
</Steps>

<Accordion title="Checkpoint — 5 questions before you continue">

1. **Why can't a script change your shell's current directory?** — it runs in a child process, and a child cannot modify its parent. Use `source script.sh` to run it in the current shell instead.
2. **What does exit code 0 mean?** — success. Every other value means failure. This is inverted from most languages' truthiness and catches everyone once.
3. **`cmd 2>&1 > f` versus `cmd > f 2>&1` — what is the difference?** — the first sends stderr to the terminal and stdout to the file; the second sends both to the file. Redirections are applied left to right.
4. **What is `755` in letters?** — `rwxr-xr-x`: owner can do everything, everyone else can read and execute.
5. **A `.sh` file gives "permission denied" — what is missing?** — the execute bit. `chmod +x`.
</Accordion>

### `PATH` resolution, precisely

The order the shell resolves a bare word is: **alias → function → builtin → hash table → `PATH` search, left to right**. `type -a name` prints the whole chain; `command -v name` prints only the winner; `which` is an external program that does *not* know about your builtins or functions and will lie to you about `echo`, `time` and `[`.

The **hash table** is the part that surprises people. Shells cache the resolved path of each command. Install a newer binary earlier in `PATH` and the shell may keep running the old one until you run `hash -r` (bash) or `rehash` (zsh), or start a new shell. If `type -a` says the right thing and the wrong one still runs, this is why.

### Login shells, interactive shells, and which file gets read

This is the single most common source of "it works in my terminal but not in cron/CI".

| Shell kind | bash reads | zsh reads |
|---|---|---|
| Login (SSH, console) | `/etc/profile`, then the first of `~/.bash_profile`, `~/.bash_login`, `~/.profile` | `/etc/zshenv`, `~/.zshenv`, `/etc/zprofile`, `~/.zprofile`, `/etc/zshrc`, `~/.zshrc`, `~/.zlogin` |
| Interactive non-login (new tab) | `~/.bashrc` | `~/.zshenv`, `~/.zshrc` |
| **Non-interactive** (script, cron, CI) | **only `$BASH_ENV` if set** | **only `~/.zshenv`** |

A cron job or a CI step runs a **non-interactive, non-login** shell, so `~/.bashrc` and `~/.zshrc` are never read. Your `PATH` additions, your `nvm`/`pyenv`/`conda` initialisation and your aliases do not exist there. The correct fixes, in order of preference: use absolute paths in cron entries; set `PATH=` explicitly at the top of the crontab; or, if you must, `source` the specific file you need — but never `source ~/.bashrc` from a script, because most `.bashrc` files begin with a guard that returns immediately when non-interactive.

### The safety preamble, and what each line prevents

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
IFS=$'\n\t'
trap 'echo "FAILED: line $LINENO: $BASH_COMMAND" >&2' ERR
```

- **`-e`** — abort on the first failing command. Prevents "step 3 failed, step 4 ran anyway on missing data".
- **`-u`** — abort on an unset variable. The `rm -rf "$UNSET/"` class of disaster.
- **`-o pipefail`** — a pipeline fails if *any* stage fails. Without it, `curl bad-url | jq .` exits 0 because `jq` succeeded on empty input. This is the one that silently produces empty deployments.
- **`-E`** — make the `ERR` trap inherit into functions and subshells. Without it the trap does not fire where you most want it.
- **`IFS=$'\n\t'`** — remove space from the field separator so unquoted expansion does not split on spaces in filenames. A partial defence; quoting is the real one.
- **The `ERR` trap** — prints the failing line number and the actual command. Turns "the script exited 1" into a diagnosis.

Now the honest part: **`set -e` has real holes**, and you should know them rather than trust it blindly.

```bash
set -e
foo() { false; echo "still here"; }
if foo; then :; fi        # -e is DISABLED inside a condition. "still here" prints.
count=$(grep -c x f) || true   # without || true, a no-match grep (exit 1) kills the script
let i++                        # returns 1 when the result is 0. kills the script.
arr=(); echo "${arr[@]}"       # with -u, an empty array is "unset" in bash < 4.4
```

`set -e` is suppressed in any command that is part of a condition (`if`, `while`, `&&`, `||`, `!`). That is documented and correct, and it means a function called in an `if` will not abort on failure. This is why serious scripts check exit codes explicitly at the points that matter rather than relying on `-e` alone. `shellcheck` (0.10.0) knows all of these and will point at each one.

### Exit codes as an interface

| Code | Meaning |
|---|---|
| 0 | success |
| 1 | general failure |
| 2 | shell/builtin misuse (bad flag) |
| 126 | found but not executable |
| 127 | **command not found** |
| 128 + N | killed by signal N — so **130** is Ctrl-C (SIGINT), **137** is SIGKILL, **143** is SIGTERM |

`137` is the one to memorise: a container that exits 137 was `SIGKILL`ed, and in Kubernetes that almost always means the OOM killer. If you see 137 in CI, you are out of memory, not out of luck.

Define your own codes deliberately and document them: `2` for bad usage, `3` for a missing dependency, `4` for a failed precondition. A script whose only codes are 0 and 1 forces callers to parse stderr.

### Trade-offs table

| Decision | Choose X when… | Choose Y when… |
|---|---|---|
| Background job vs `systemd`/`launchd` service | **`cmd &` plus `nohup`** for an ad-hoc long job on a box you are sitting at | **A service unit** for anything that must survive reboot, restart on failure, or have its logs collected. `nohup ... &` has no restart policy and no log rotation |
| `kill` vs `kill -9` | **`kill` (SIGTERM)** always first — the process can flush buffers, release locks and deregister | **`kill -9`** only after a timeout. It cannot be caught, so temp files, lock files and half-written output all survive |
| `set -e` vs explicit checks | **`set -Eeuo pipefail`** as a baseline for every script — it catches the common cases for free | **Explicit `if ! cmd; then`** at the three or four steps that genuinely matter, because `-e` is disabled in conditions and inside some constructs |
| Shell vs Python for a task | **Shell** when the task is mostly invoking other programs and passing streams between them — that is what it is for | **Python** past roughly 100 lines, or as soon as you need data structures, error types, or tests. The measured threshold is below |

### Reference implementation — a self-diagnosing script preamble

```bash
#!/usr/bin/env bash
# nx-preamble.sh — the boilerplate every operational script should start with.
set -Eeuo pipefail
IFS=$'\n\t'

readonly SCRIPT_NAME="${0##*/}"
readonly SCRIPT_DIR="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd -P)"
readonly LOCKFILE="${TMPDIR:-/tmp}/${SCRIPT_NAME}.lock"

log()  { printf '%s %s %s\n' "$(date -u +%FT%TZ)" "$1" "${*:2}" >&2; }
info() { log INFO  "$@"; }
warn() { log WARN  "$@"; }
die()  { log ERROR "$@"; exit "${EXIT_CODE:-1}"; }

need() { command -v "$1" >/dev/null 2>&1 || { EXIT_CODE=3 die "missing dependency: $1"; }; }

cleanup() {
  local rc=$?
  rm -f -- "${TMPWORK:-}"
  [[ $rc -ne 0 ]] && warn "exiting with status $rc"
  return $rc
}
trap cleanup EXIT
trap 'die "interrupted"' INT TERM
trap 'log ERROR "line $LINENO: $BASH_COMMAND"' ERR

need jq
need curl

# single-instance guard: flock on Linux, mkdir elsewhere (portable)
if command -v flock >/dev/null; then
  exec 9>"$LOCKFILE"
  flock -n 9 || { EXIT_CODE=4 die "another instance is running"; }
else
  mkdir "$LOCKFILE.d" 2>/dev/null || { EXIT_CODE=4 die "another instance is running"; }
  trap 'rmdir "$LOCKFILE.d" 2>/dev/null || true' EXIT
fi

TMPWORK="$(mktemp "${TMPDIR:-/tmp}/${SCRIPT_NAME}.XXXXXX")"
info "starting, workdir=$TMPWORK"
```

Four details that matter and are usually missing:

- **`cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd -P`** resolves the script's own directory through symlinks. `$0` is not reliable when the script is sourced or symlinked.
- **`trap cleanup EXIT`** fires on *every* exit path including `die`, so temp files never leak. The `local rc=$?` on the first line captures the status before anything else clobbers it.
- **`mkdir` as a lock** is atomic on every POSIX filesystem and works on macOS, which has no `flock(1)`. `mkdir` succeeding *is* the acquisition; there is no check-then-act race.
- **`--` before user-controlled arguments** stops a filename beginning with `-` from being parsed as a flag. `rm -- "$f"` is not paranoia; `rm "$f"` where `f` is `-rf` is a real failure mode.

### What breaks in the real world

A deployment script had run nightly for a year. It fetched a manifest, filtered it, and rolled out whatever it found:

```bash
curl -s "$MANIFEST_URL" | jq -r '.services[].name' > services.txt
while read -r svc; do deploy "$svc"; done < services.txt
```

One night the manifest host returned a 502. `curl -s` printed nothing and exited 0 — because without `-f`, curl considers "I successfully received an HTTP error page" a success. `jq` received empty input, produced empty output, and exited 0. `services.txt` was empty, the loop body never ran, and the script exited 0. **CI went green. Nothing was deployed for eleven hours**, and it was only noticed when a customer asked about a feature that had shipped that morning.

Three separate defences would each have caught it: `curl -fsS` (fail on HTTP errors), `set -o pipefail` (which would still not have helped here, since both commands genuinely exited 0), and — the one that actually matters — **asserting the postcondition**: `[[ -s services.txt ]] || die "empty manifest"`. The general rule is that a pipeline of programs that all "succeed" can still produce nothing, and only an explicit check on the *output* catches that. Exit codes tell you a program did not crash. They do not tell you it did the work.

<Accordion title="Design checkpoint — one question, with a model answer">

**Question.** A teammate's data-loading shell script is 400 lines: it parses arguments, retries HTTP calls, builds JSON with `printf`, and maintains a state file it reads and rewrites. It works. They want to add per-record error reporting. Do you extend it or rewrite it in Python?

**Model answer.** Rewrite, and the argument should be made on three specific grounds rather than taste.

**Correctness of data handling.** Building JSON with `printf` has no escaping, so a record containing a quote or a backslash produces invalid JSON, silently. Shell has one data type — the string — so "a list of records, some of which failed, with a reason each" has no natural representation; you end up with parallel arrays or delimiter-separated strings, and the delimiter eventually appears in the data. Per-record error reporting is precisely the requirement that shell handles worst.

**Cost per external command.** Measured on this machine: 10,000 iterations of a pure shell loop take **0.013 s**; the same 10,000 iterations each invoking one external command take **12.863 s** — a **989× difference**, about **1.29 ms per fork+exec**. A script that shells out to `jq`, `date` and `sed` once per record pays roughly 4 ms per record before doing any work. At 100,000 records that is 6.5 minutes of pure process creation. Python's equivalent 10,000-iteration loop is 0.028 s and its JSON handling is in-process.

**Testability.** The state file read-modify-write is the part that will cause a real incident, and there is no reasonable way to unit-test it in shell. In Python it is a function with a temp directory and three test cases.

The threshold I would state as a team rule: **shell is right when the script is a pipeline of other programs and control flow is linear.** As soon as it has data structures, a retry policy, a state machine, or needs tests, it has outgrown shell. This one has all four. The migration is also low-risk here because the shell script is the specification — port it function by function, keeping the same CLI, and diff the outputs on a week of real inputs before switching.
</Accordion>

### What a process costs, measured

The single most useful number in shell engineering is the cost of creating a process.

| Loop, 10,000 iterations | Wall time | Per iteration |
|---|---|---|
| Shell builtin only (`:`) | **0.013 s** | 1.3 µs |
| One external command per iteration (`/bin/echo`) | **12.863 s** | **1.29 ms** |
| Python 3.13 `for i in range(10000): pass` | 0.028 s | 2.8 µs |

**989× between the first two rows.** That gap is `fork()` plus `execve()` plus the dynamic loader resolving the new binary's symbols, plus the shell's `wait()`. It is why a shell loop that calls `date` once per line takes minutes on a file that `awk` processes in seconds — the work is not in the computation, it is in the process creation.

The engineering consequences are concrete:

- **Batch, do not iterate.** `sort file | uniq -c` spawns two processes for the whole file. `while read line; do echo "$line" | ...; done < file` spawns two per *line*.
- **Prefer builtins in loops.** `${var%%.*}` costs microseconds; `$(echo "$var" | cut -d. -f1)` costs 2.6 ms because it is two forks and a pipe.
- **The 1.29 ms is the floor for any CLI tool's startup**, which is why a linter that takes 400 ms to start dominates a pre-commit hook over 50 files, and why tools like `ruff` (Week 3) advertise their startup time.

### File descriptors are the actual interface

Every open file, socket, pipe and device in a process is an integer index into the kernel's per-process file descriptor table. Two things follow that are worth knowing precisely.

**A pipe is a kernel buffer, and it has a size.** On Linux the default pipe capacity is 65,536 bytes (16 pages); on macOS it starts at 16,384 and grows. When the buffer fills, `write()` **blocks**. That is the entire mechanism of back-pressure in a shell pipeline: `producer | slow_consumer` throttles the producer automatically, with no coordination. It is also why a pipeline can deadlock if a process tries to write to and read from the same child without draining — the classic hang in hand-rolled `popen` code, and the reason Python's `subprocess.communicate()` exists.

**Deleting an open file does not free the space.** `unlink` removes the directory entry; the inode survives while any fd refers to it. A log file rotated by `rm` while the writer still has it open keeps consuming disk with no visible file — `df` shows the space used, `du` does not find it. `lsof +L1` lists exactly these (link count 0, still open). The fix is `truncate -s 0` or a proper rotation with `copytruncate`/`SIGHUP`.

Limits, on this machine:

```bash
$ ulimit -n        # soft limit: max open fds per process
256                # macOS default — surprisingly low
$ ulimit -Hn
unlimited
```

macOS ships a soft limit of **256** file descriptors per process. Linux typically ships 1024 soft / 1048576 hard. A server accepting connections, or a build tool opening many files, hits this and reports `EMFILE: too many open files` — which is why `ulimit -n 65536` appears at the top of so many start scripts, and why systemd units carry `LimitNOFILE=`.

### Tracing what a process actually does

**On Linux:** `strace -f -e trace=file,process ./prog` shows every system call. `strace -c` gives a syscall histogram, which is how you discover that your program spent its time in 400,000 `stat()` calls looking for a config file.

**On macOS this is much harder than the textbooks say.** `dtruss` requires `sudo` *and* System Integrity Protection interferes with tracing Apple-signed binaries, so `sudo dtruss ls` frequently produces nothing useful. The practical options are: trace your own unsigned binaries only, use `sudo fs_usage -w -f filesys ./prog` for file activity (which does work), or do the tracing in a Linux container. Any tutorial that says "just run dtruss" has not tried it on a recent macOS.

The portable investigative toolkit that does work everywhere:

```bash
lsof -p PID              # every open file, socket and library
lsof -i :8080            # who has port 8080
ps -o pid,ppid,stat,etime,rss,command -p PID
pstree -p PID            # Linux; `ps -ef` and read PPIDs on macOS
cat /proc/PID/environ | tr '\0' '\n'    # Linux only: the process's environment
cat /proc/PID/limits                     # Linux only: its actual rlimits
```

`/proc` has no macOS equivalent. That asymmetry is a genuine reason to keep a Linux VM or container around for systems work even when you develop on a Mac.

### `sudo`, setuid, and why the environment is scrubbed

A **setuid** binary carries a bit that makes the kernel run it as the file's owner rather than the invoker. `/usr/bin/sudo` is setuid root — that is how an unprivileged user gets root.

Because the invoker controls the environment of a setuid program, the environment is an attack surface. The dynamic loader ignores `LD_PRELOAD` and `LD_LIBRARY_PATH` for setuid binaries (and `DYLD_*` on macOS) precisely because otherwise you could inject a library into a root process. `sudo` additionally scrubs the environment down to a whitelist (`env_reset` in `/etc/sudoers`), which is why `sudo make install` may not see your `PATH` and why `sudo -E` — which preserves it — should make you nervous.

This is also why **`sudo` is not a way to make permission errors go away.** If a file is `640 root:root` and your service user cannot read it, the fix is group membership or the file's mode, not running the service as root. A service running as root turns every future memory-safety bug in it (Week 1, Module 5) into a full machine compromise.

**`umask`** is the complement: it masks off permission bits at creation time. The common default `022` means new files are created `644` and directories `755` — group and other lose write. A shared build directory that needs group-writable output sets `umask 002`. A script that writes credentials should set `umask 077` *before* creating the file, not `chmod 600` after — the `chmod` leaves a window in which the file exists world-readable, and that window is a real, exploited race.

### Production failure modes and how you detect them

| Failure | Signature | Detection |
|---|---|---|
| Works in terminal, fails in cron | `command not found` (exit 127) for something clearly installed | non-interactive shells read no `rc` file; set `PATH` in the crontab, use absolute paths |
| Container exits 137 | no error in logs, restart loop | 128+9 = SIGKILL, almost always the OOM killer; check `dmesg` / pod events, raise limits or fix the leak |
| Disk full, `du` finds nothing | `df` says 95%, `du -sh /` says half that | deleted-but-open files; `lsof +L1` finds them; restart the holder or `truncate` |
| `EMFILE: too many open files` | fails after N hours under load | fd leak; `lsof -p PID \| wc -l` over time; raise `ulimit -n` *and* fix the leak |
| Pipeline hangs at ~64 KB of output | reproducible, always at the same point | pipe buffer full and nobody is reading; drain both streams concurrently |
| Script silently does nothing | exit 0, empty output, CI green | assert postconditions: `[[ -s out ]] \|\| die`; `curl -fsS`; check row counts |
| Credentials file briefly world-readable | never noticed until an audit | `umask 077` before creation, not `chmod` after |

### Frontier and research pointers

- **Ritchie, D. M. & Thompson, K. (1974). "The UNIX Time-Sharing System." *CACM* 17(7).** One-sentence takeaway: the whole design follows from "everything is a file descriptor and processes compose through them", and reading it explains why pipes, redirection and `/dev` all work the same way.
- **Kerrisk, M. (2010). *The Linux Programming Interface*, Chapters 24–27 (process creation, `execve`) and 44 (pipes).** One-sentence takeaway: `fork` + `exec` as two separate calls is what makes redirection possible at all, because the child gets to rearrange its file descriptors in the gap between them.
- **Chen, X., Garfinkel, T. et al. (2008). "Overshadow" / and more directly Wei, J. et al. (2008). "TOCTTOU Vulnerabilities in UNIX-Style File Systems." *FAST*.** One-sentence takeaway: check-then-act on filesystem paths is a race by construction, which is why `mkdir` (atomic) beats "test then create" as a lock and why `O_CREAT|O_EXCL` exists.
- **Rochkind, M. (2004). *Advanced UNIX Programming*, 2nd ed., Chapter 5.** One-sentence takeaway: signal handling has a small set of async-signal-safe functions and everything else is undefined behaviour in a handler — the same rule that made `_exit` rather than `exit` correct in Week 1's lab.
- **POSIX.1-2024 (IEEE Std 1003.1-2024), "Shell Command Language."** One-sentence takeaway: the parts of shell behaviour that are actually portable are far narrower than what bash and zsh accept, and this document is how you tell the difference.

### Stretch challenge

Reconstruct what an unknown program does using only observation.

1. Take any binary you did not write — `git`, `curl`, or better, a tool from your workplace. Do **not** read its source or its `--help`.
2. On Linux: `strace -f -c ./prog args` for a syscall histogram, then `strace -f -e trace=openat,connect,execve` for the detail. On macOS: `sudo fs_usage -w -f filesys ./prog` plus `lsof -p` sampled in a loop, and note in your write-up which questions you could *not* answer because `dtruss` and `/proc` were unavailable.
3. Produce: every file it read or wrote, every network endpoint it contacted, every child process it spawned, and its exit code.
4. Now write a one-paragraph description of what the program does, and only then read its documentation. How wrong were you, and which observation would have corrected you?

The open question with no single right answer: this is exactly the technique used both for incident response and for supply-chain analysis of a suspicious dependency. Given what you just did, what would a *malicious* program do differently to make this analysis fail — and what would you have to add to your method to catch it? Consider timing, environment detection, and the difference between what a program does on its first run and its hundredth.

<Accordion title="If you're a student" icon="graduation-cap">

**Portfolio line:** *"A black-box analysis of an unfamiliar binary using only `strace`, `lsof` and `ps` — every file, socket and child process it touches, reconstructed without reading a line of its source."* This reads as security-adjacent work, which is rarer on a junior resume than another CRUD app.

**The interview angle.** "What happens when you type `ls` and press Enter?" is the classic open-ended systems question and it is scored on how many layers you can go down. The strong answer is the six steps — expand, resolve, fork, redirect in the child, exec, wait — plus one detail that shows you have actually looked: *the redirection happens in the child between fork and exec, which is why the shell's own output is unaffected, and why `cd` has to be a builtin.*

The follow-up to prepare is "why is exit code 137 in my CI logs?" — 128 + 9, SIGKILL, almost always the OOM killer.
</Accordion>
<Accordion title="If you're working" icon="briefcase">

Three places this shows up in a normal engineering week:

1. **"It works locally, fails in CI."** Nine times in ten this is a non-interactive shell not reading your `rc` file, so a tool installed by `nvm`/`pyenv`/`asdf` is not on `PATH`. Check with `type -a tool` inside the CI step, not on your laptop, and fix it by setting `PATH` explicitly rather than sourcing a profile.

2. **The disk that is full with no files.** `df` says 95%, `du` disagrees. Deleted-but-still-open files, usually a log the app holds open after a rotation deleted it. `lsof +L1` finds them in one command, and the permanent fix is `copytruncate` or a `SIGHUP` handler in the app.

3. **Reviewing any shell script that ships.** Look for four things and you will catch most defects: the `set -Eeuo pipefail` preamble, quoted variable expansions, a postcondition assertion on anything downloaded, and a `trap ... EXIT` for temp files. A script fetching a manifest without `curl -fsS` and without an emptiness check is the incident described above waiting to recur.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Errors still on screen after `cmd > out.txt` | `>` redirects fd 1 only | `cmd > out.txt 2>&1`, in that order |
| `cmd 2>&1 > f` puts errors on screen | redirections apply left to right; stderr was pointed at the terminal first | put `2>&1` after the stdout redirect |
| Script's `cd` does not affect your shell | it ran in a child process | `source script.sh` to run it in the current shell |
| `command not found` (127) in cron only | non-interactive shells do not read `~/.bashrc` / `~/.zshrc` | absolute paths, or set `PATH` in the crontab |
| Installed a new version, old one still runs | `PATH` order, or the shell's command hash cache | `type -a cmd`; `hash -r` (bash) / `rehash` (zsh) |
| Pipeline succeeds but produces nothing | every stage exited 0 on empty input | `curl -fsS`; assert the postcondition: `[[ -s out ]] \|\| die` |
| `set -e` did not stop the script | `-e` is disabled inside `if`, `while`, `&&`, `\|\|`, `!` | check exit codes explicitly at the steps that matter; run `shellcheck` |
| Container restarts with exit 137 | 128 + 9 = SIGKILL, usually the OOM killer | check memory limits and actual usage; 143 is a graceful SIGTERM instead |
| `df` full but `du` cannot find it | deleted files still held open | `lsof +L1`; restart the holder or `truncate -s 0` |
| Loop over a large file takes minutes | one or more external commands per line, ~1.29 ms each | use `awk`/`sort` on the whole stream, or move to Python |
| Secrets file readable for a moment after creation | `chmod 600` applied after the file existed | `umask 077` before creating it |

## Sources & further reading

**Primary docs**

- **[`man 1 bash`, sections "INVOCATION" and "SHELL BUILTIN COMMANDS" (bash 5.2).](https://man7.org/linux/man-pages/man1/bash.1.html)** Read INVOCATION in full once — it is the definitive table of which startup file is read for which kind of shell, and it settles most CI mysteries.
- **`man 1 zsh` and `man 1 zshoptions` (zsh 5.9).** Read this for the startup-file order, which differs from bash in ways that matter on macOS where zsh is the default.
- **[POSIX.1-2024, "Shell Command Language" (IEEE Std 1003.1-2024, XCU §2).](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html)** Read this to know which constructs are portable; `[[ ]]`, arrays and `local` are not POSIX, and `#!/bin/sh` scripts using them break on dash.
- **`man 2 fork`, `man 2 execve`, `man 7 pipe` (Linux); `man 2 fork`, `man 1 lsof`, `man 1 fs_usage` (macOS 15).** Read `pipe(7)` specifically for the buffer capacity and the blocking semantics that give shell pipelines their back-pressure.
- **[ShellCheck wiki (0.10.0), the SC2086 and SC2181 pages.](https://www.shellcheck.net/wiki/SC2086)** Read these two; unquoted expansion and `if [ $? -ne 0 ]` are the two most common shell defects and the wiki explains each in a page.

**Papers**

- **[Ritchie, D. M. & Thompson, K. (1974). "The UNIX Time-Sharing System." *Communications of the ACM* 17(7), 365–375.](https://doi.org/10.1145/361011.361061)** One-sentence takeaway: uniform treatment of files, devices and pipes behind a single small syscall interface is the design decision that everything else in this module follows from.
- **[Wei, J. & Pu, C. (2005). "TOCTTOU Vulnerabilities in UNIX-Style File Systems: An Anatomical Study." *USENIX FAST*.](https://www.usenix.org/legacy/event/fast05/tech/full_papers/wei/wei.pdf)** One-sentence takeaway: any "check the file, then act on it" sequence is a race with anyone who can rename the path, which is why atomic primitives (`mkdir`, `O_CREAT|O_EXCL`, `openat`) exist.
- **[Provos, N., Friedl, M. & Honeyman, P. (2003). "Preventing Privilege Escalation." *USENIX Security*.](https://www.usenix.org/legacy/event/sec03/tech/full_papers/provos_et_al/provos_et_al.pdf)** One-sentence takeaway: privilege separation — running the untrusted parsing work in an unprivileged process — contained bugs in OpenSSH that would otherwise have been root compromises, and it is the argument against running services as root.

**Go deeper**

- **[Kerrisk, M. (2010). *The Linux Programming Interface*, Chapters 24–28 and 44–45.](https://man7.org/tlpi/)** The authoritative treatment of process creation, program execution and pipes; Chapter 24's diagram of what `fork` copies and what it shares is worth redrawing by hand.
- **[Greg Wooledge, "BashFAQ" and "BashPitfalls" (mywiki.wooledge.org).](https://mywiki.wooledge.org/BashPitfalls)** Not academic, and the single most useful shell resource on the internet: 60-odd numbered pitfalls, each with the failing case and the fix. Read pitfalls 1–20 in one sitting.
