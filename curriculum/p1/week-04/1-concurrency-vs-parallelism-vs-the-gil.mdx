### The one idea

**Concurrency** is having several jobs in progress at once. **Parallelism** is having several jobs actually executing at the same instant. They are not the same thing, and confusing them is why people add threads to a program and watch it get slower.

Python has a rule called the **GIL** which means only one thread runs Python code at any moment. So Python threads give you concurrency and not parallelism — which is useless when your program is computing and enormously useful when it is waiting.

### The analogy

One chef, four pots on the stove.

The chef stirs pot 1, then while it simmers walks to pot 2, then pot 3. All four dishes are **in progress**. That is **concurrency** — one worker, many jobs in flight, and it works because the pots do most of the work by themselves while the chef is elsewhere. Simmering is waiting; waiting is I/O.

Now the chef must chop four kilograms of onions. There is no simmering. Every second of progress requires the chef's hands. A second chef would genuinely halve the time — but a second *pair of pots* would not help at all. That is **parallelism**, and it needs another worker, not another job.

The GIL is a rule that says: **there is only one chef in this kitchen**, no matter how many aprons you hand out. Aprons help when the work is simmering. They do nothing for onions.

### The vocabulary, defined

- **Concurrency** — several tasks *in progress* over the same period. They may interleave on one worker.
- **Parallelism** — several tasks *executing simultaneously*, which requires several CPU cores.
- **CPU-bound** — the program is limited by how fast the processor computes. Sorting, parsing, maths, image processing.
- **I/O-bound** — the program is limited by waiting for something external: a network reply, a disk read, a database query.
- **Thread** — an independent line of execution *inside* one process. Threads share all memory.
- **Process** — a separate program instance with its own memory. Processes share nothing by default.
- **GIL (Global Interpreter Lock)** — a lock inside CPython that must be held to execute Python bytecode. Only one thread can hold it at a time.
- **Bytecode** — the compiled instructions the Python interpreter executes.
- **Context switch** — the machinery of pausing one thread or process and resuming another.
- **Speedup** — how many times faster something got. Sequential time ÷ parallel time.
- **`asyncio`** — Python's library for concurrency on a *single* thread, by explicitly pausing at every point that waits.

### How to tell CPU-bound from I/O-bound, in one command

```bash
/usr/bin/time -p python3 myprogram.py
```

```
real  10.42        <- wall-clock time you waited
user   9.98        <- CPU time actually computing
sys    0.31        <- CPU time inside the kernel
```

**If `user + sys` is close to `real`, you are CPU-bound.** The processor was busy the whole time.

```
real  10.42
user   0.31
sys    0.08
```

**If `user + sys` is far below `real`, you are I/O-bound.** The program spent 10 seconds waiting and 0.4 seconds computing. Ninety-six percent of your wall time was doing nothing at all — and that is exactly the time concurrency can reclaim.

This one measurement decides everything that follows, and it takes five seconds. Do it before choosing an approach, not after.

### Smallest working example

```python
import time
from concurrent.futures import ThreadPoolExecutor

def count_primes(n: int) -> int:            # CPU-BOUND: pure computation
    count = 0
    for x in range(2, n):
        d, is_prime = 2, True
        while d * d <= x:
            if x % d == 0:
                is_prime = False
                break
            d += 1
        if is_prime:
            count += 1
    return count

def wait_a_bit(_: int) -> None:             # I/O-BOUND: pure waiting
    time.sleep(0.5)

def timed(label, fn):
    t = time.perf_counter()
    fn()
    print(f"{label:28s} {time.perf_counter() - t:6.2f} s")

# --- CPU-bound: 4 tasks
timed("CPU sequential", lambda: [count_primes(200_000) for _ in range(4)])
timed("CPU with 4 threads", lambda: list(ThreadPoolExecutor(4).map(count_primes, [200_000]*4)))

# --- I/O-bound: 4 tasks
timed("I/O sequential", lambda: [wait_a_bit(i) for i in range(4)])
timed("I/O with 4 threads", lambda: list(ThreadPoolExecutor(4).map(wait_a_bit, range(4))))
```

Typical output:

```
CPU sequential                 1.20 s
CPU with 4 threads             1.39 s     <- SLOWER
I/O sequential                 2.00 s
I/O with 4 threads             0.50 s     <- 4x faster
```

Same four threads. Opposite results. **The workload decides, not the tool.**

### Line-by-line walkthrough

- `count_primes(n)` — trial division, deliberately naive. Every step is Python bytecode, so the GIL is held throughout.
- `wait_a_bit` — `time.sleep` **releases the GIL** while it waits. That is the crucial detail: any Python operation that waits on the outside world releases the lock so other threads can run.
- `ThreadPoolExecutor(4).map(fn, args)` — run `fn` on each argument using up to four worker threads, returning results in order.
- `time.perf_counter()` — a monotonic high-resolution clock. Use it for durations, not `time.time()`.
- **CPU with threads is slower than sequential**, not merely equal. The four threads take turns holding one GIL, and the taking-turns itself costs something. You paid for coordination and bought nothing.
- **I/O with threads is 4× faster**, because all four sleeps happen at once. The GIL was free the whole time.

### Guided practice

<Steps>
<Step title="Classify three workloads before measuring">
Predict CPU-bound or I/O-bound, then check with `/usr/bin/time -p`:

1. Resizing 500 JPEGs. 2. Fetching 500 URLs. 3. Reading a 2 GB CSV and computing a mean.

Answers: (1) CPU-bound — decode, resample, encode. (2) I/O-bound — almost all of it is network wait. (3) **Both, and this is the interesting one**: reading is I/O and parsing is CPU, and which dominates depends on your disk. On an NVMe SSD the parse dominates and it is CPU-bound; over a network filesystem it is I/O-bound. Measure yours.
</Step>
<Step title="Watch the GIL being released">

```python
import threading, time

def io_work():
    time.sleep(1)                # releases the GIL

def cpu_work():
    x = 0
    for _ in range(20_000_000):  # holds the GIL
        x += 1

for name, fn in (("io", io_work), ("cpu", cpu_work)):
    t = time.perf_counter()
    ts = [threading.Thread(target=fn) for _ in range(4)]
    for th in ts: th.start()
    for th in ts: th.join()
    print(f"4 threads of {name}: {time.perf_counter() - t:.2f} s")
```

The I/O version finishes in about one second — four one-second sleeps overlapped completely. The CPU version takes about four times one thread's time, because the four threads shared one GIL.
</Step>
<Step title="Use processes for the CPU case">

```python
from concurrent.futures import ProcessPoolExecutor

if __name__ == "__main__":                    # REQUIRED on macOS and Windows
    t = time.perf_counter()
    with ProcessPoolExecutor(4) as ex:
        list(ex.map(count_primes, [200_000] * 4))
    print(f"CPU with 4 processes: {time.perf_counter() - t:.2f} s")
```

Now it is genuinely faster, because four separate Python interpreters each have their own GIL and run on separate cores.

**The `if __name__ == "__main__":` guard is not optional.** On macOS and Windows, child processes start by *importing* your module. Without the guard, the import creates more children, which import the module, which create more children. Module 3 covers it.
</Step>
<Step title="Compute the actual speedup">

```python
speedup = sequential_time / parallel_time
efficiency = speedup / n_workers
```

Four workers giving 3.2× is **80% efficiency**, which is good. Four workers giving 1.1× means something is serialising you. Always report both — a speedup without a worker count is not a result.
</Step>
</Steps>

<Accordion title="Checkpoint — 5 questions before you continue">

1. **Concurrency versus parallelism in one sentence each?** — concurrency is several jobs in progress; parallelism is several jobs executing at the same instant.
2. **How do you tell CPU-bound from I/O-bound?** — `/usr/bin/time -p`. If `user + sys ≈ real`, CPU-bound. If far below, I/O-bound.
3. **Why don't threads speed up CPU-bound Python?** — the GIL lets only one thread execute bytecode at a time, so they take turns and pay coordination cost on top.
4. **Why do threads speed up I/O-bound Python?** — waiting operations release the GIL, so all the waiting overlaps.
5. **What fixes the CPU case?** — processes. Each has its own interpreter and its own GIL, so they run on separate cores.
</Accordion>

**You ship code for a living?** This layer is yours — trade-offs, real tools, real versions. Measured with CPython 3.13.2 on an Apple M3 Pro (11 cores, 18 GB), macOS 15, httpx 0.28.1, aiohttp 3.14.3.

### The benchmark matrix

Two workloads × four execution models. CPU task: count primes below 200,000 by trial division, 8 tasks. I/O task: 40 HTTP GETs against a local server with a fixed 50 ms delay.

**CPU-bound, 8 tasks:**

| Model | Time | Speedup |
|---|---|---|
| sequential | 2.392 s | 1.00× |
| **threads (8)** | **2.777 s** | **0.86× — slower than doing nothing** |
| **processes (8)** | **0.874 s** | **2.74×** |
| asyncio | 2.429 s | 0.98× |

**I/O-bound, 40 requests × 50 ms:**

| Model | Time | Speedup |
|---|---|---|
| sequential | 2.184 s | 1.00× |
| threads (20) | 0.155 s | **14.09×** |
| processes (8) | 0.613 s | 3.57× |
| **asyncio (`gather`)** | **0.081 s** | **27.02×** |
| *theoretical floor (one round trip)* | *0.050 s* | *43.7×* |

Every cell is defensible, and three of them are worth defending explicitly:

**Threads on CPU work: 0.86×.** Not "no faster" — *slower*. The eight threads serialise on the GIL, so you get sequential execution plus the cost of switching between them every 5 ms and the cache disruption that follows. Adding threads to a CPU-bound Python program is a pessimisation, and it is one people ship because "more threads" sounds like an optimisation.

**Processes on CPU work: 2.74× on 11 cores, not 8×.** Three reasons: process startup on macOS uses `spawn`, which cost a measured 54 ms for a pool of four (Module 3); arguments and results are pickled; and this machine was under heavy load during measurement. Report your efficiency (2.74 / 8 = 34%) and be honest about why it is not 100%.

**Processes on I/O work: 3.57×, far worse than threads' 14×.** Eight processes can have eight requests in flight; twenty threads can have twenty. Processes cost 54 ms each to start and cannot exceed the pool size in concurrency. Using processes for I/O is paying the highest price for the lowest ceiling.

**asyncio at 27×, approaching the 43.7× floor.** Forty requests, one thread, one round trip of latency plus overhead. The remaining gap is connection setup and event-loop scheduling.

### The decision table

| Your workload | Use | Why | Measured here |
|---|---|---|---|
| CPU-bound, pure Python | **`ProcessPoolExecutor`** | separate interpreters, separate GILs, real cores | **2.74×** |
| CPU-bound, NumPy/Pandas/PyTorch | **threads, or nothing** | those libraries release the GIL inside C code and already use BLAS threads | see below |
| I/O-bound, existing sync code | **`ThreadPoolExecutor`** | no rewrite; waiting releases the GIL | **14.09×** |
| I/O-bound, new code, high fan-out | **`asyncio`** | thousands of tasks on one thread, no per-task stack | **27.02×** |
| Mixed | **asyncio + `run_in_executor`** | loop for I/O, process pool for CPU | Module 4 |
| CPU-bound and you control the hot loop | **leave Python** | Cython, Rust via PyO3, or vectorise into NumPy | 10–100× typical |

**The second row is the one people get wrong in both directions.** NumPy, SciPy, Pandas, PyTorch and scikit-learn release the GIL around their C and Fortran kernels, so a `np.dot` in a thread genuinely runs in parallel with Python code in another thread. But those libraries *also* already parallelise internally via BLAS/OpenMP, so wrapping them in a process pool usually creates oversubscription — 8 processes × 11 BLAS threads = 88 threads fighting over 11 cores. Module 3 measures that failure mode; it is a silent multi-fold slowdown in a lot of ML code.

### Amdahl's law, with the numbers

**Derived.** Every cell below is arithmetic from the formula — no machine involved, and true on yours.
If a fraction *p* of your program can be parallelised and the rest cannot, the speedup on *N* workers is bounded by

```
S(N) = 1 / ((1 - p) + p/N)
```

| Parallel fraction | 4 workers | 8 | 20 | 100 | ∞ |
|---|---|---|---|---|---|
| 50% | 1.6× | 1.8× | 1.9× | 2.0× | **2×** |
| 90% | 3.1× | 4.7× | 6.9× | 9.2× | **10×** |
| 95% | 3.5× | 5.9× | **10.3×** | **16.8×** | **20×** |
| 99% | 3.9× | 7.5× | 16.8× | 50.2× | **100×** |

Read the 95% row. Twenty workers buy 10.3×; a hundred buy 16.8×. **Five times the machines for 1.6× the speed.** The serial 5% — reading the input, writing the output, the final merge — is what you are actually paying for, and no amount of hardware removes it.

Two practical consequences. **Measure your serial fraction before scaling out**: run at N=1, 2, 4, 8, fit the curve, and solve for *p*. And **optimise the serial part first** — reducing serial work from 5% to 2% raises the ceiling from 20× to 50×, which no cluster can do for you.

Gustafson's counterpoint is worth knowing: in practice people scale the *problem* with the machine, so the serial fraction shrinks as the input grows. That is true for batch analytics and false for latency-sensitive request handling, where the problem size is fixed by the user.

### Reference implementation — the matrix, runnable

```python
"""matrix.py — {CPU-bound, I/O-bound} x {sequential, threads, processes, asyncio}."""
from __future__ import annotations

import asyncio
import os
import sys
import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor

import httpx

CPU_N = 200_000
N_TASKS = 40
URL = "http://127.0.0.1:8099/slow/{}"


def count_primes(n: int) -> int:
    count = 0
    for x in range(2, n):
        d, is_prime = 2, True
        while d * d <= x:
            if x % d == 0:
                is_prime = False
                break
            d += 1
        count += is_prime
    return count


def fetch_sync(i: int) -> int:              # module level: must be picklable for processes
    with httpx.Client(timeout=10) as c:
        return c.get(URL.format(i)).status_code


def bench(label: str, fn) -> float:
    t = time.perf_counter()
    fn()
    el = time.perf_counter() - t
    print(f"{label:26s} {el:8.3f} s")
    return el


async def io_async() -> list[int]:
    async with httpx.AsyncClient(timeout=10) as c:
        rs = await asyncio.gather(*(c.get(URL.format(i)) for i in range(N_TASKS)))
        return [r.status_code for r in rs]


def main() -> None:
    print(f"cores={os.cpu_count()}  python={sys.version.split()[0]}")

    print("\n--- CPU-BOUND (8 tasks) ---")
    seq = bench("sequential", lambda: [count_primes(CPU_N) for _ in range(8)])
    thr = bench("threads (8)", lambda: list(ThreadPoolExecutor(8).map(count_primes, [CPU_N] * 8)))
    prc = bench("processes (8)", lambda: list(ProcessPoolExecutor(8).map(count_primes, [CPU_N] * 8)))
    print(f"  threads {seq/thr:.2f}x   processes {seq/prc:.2f}x "
          f"(efficiency {seq/prc/8:.0%} on 8 workers)")

    print(f"\n--- I/O-BOUND ({N_TASKS} requests x 50 ms) ---")
    with httpx.Client(timeout=10) as c:
        seq = bench("sequential", lambda: [c.get(URL.format(i)) for i in range(N_TASKS)])
        thr = bench("threads (20)",
                    lambda: list(ThreadPoolExecutor(20).map(lambda i: c.get(URL.format(i)),
                                                            range(N_TASKS))))
    prc = bench("processes (8)", lambda: list(ProcessPoolExecutor(8).map(fetch_sync, range(N_TASKS))))
    asy = bench("asyncio (gather)", lambda: asyncio.run(io_async()))
    print(f"  threads {seq/thr:.2f}x   processes {seq/prc:.2f}x   asyncio {seq/asy:.2f}x")
    print(f"  floor (one 50 ms round trip): {N_TASKS * 0.05 / 0.05:.1f}x")


if __name__ == "__main__":                   # required: processes re-import this module
    main()
```

Three details that make the measurement trustworthy: the **HTTP client is reused** across requests within each model, so connection setup is not counted differently per row; the **server has a fixed 50 ms delay and no CPU work**, so it cannot become the bottleneck; and **`fetch_sync` is at module level** because a process pool must pickle the callable, and a lambda or closure cannot be pickled.

### What breaks in the real world

An image-processing service resized uploads. Under load it was slow, so a `ThreadPoolExecutor(32)` was added around the resize call. Throughput did not improve. Someone raised it to 64, then 128. Latency got worse at each step, and at 128 threads the p99 went from 800 ms to 4.2 seconds.

The resize was `Pillow`-based and CPU-bound. Every thread needed the GIL to run the Python-level orchestration around each operation, so 128 threads serialised on one lock while each additionally consumed a 512 KB stack (about 64 MB of stacks) and forced the scheduler to context-switch between 128 runnable threads competing for 11 cores. The measured shape matches the benchmark above exactly: **threads on CPU-bound work measured 0.86× — slower than sequential — and the slowdown gets worse as thread count rises.**

The fix was three lines: a `ProcessPoolExecutor` sized to `os.cpu_count()`, with the image bytes passed in and out. Throughput rose about 6× and p99 dropped below the original.

Two things worth taking beyond "use processes". First, **the escalation from 32 to 64 to 128 was the diagnostic signal** — when adding workers makes things worse rather than plateau, you are contending on something, and in Python the first suspect is the GIL. Second, `Pillow` releases the GIL for *some* operations and not others, so profiling showed partial parallelism, which is exactly the ambiguous evidence that keeps a team adding threads. `py-spy top --pid <pid>` on the running process shows where threads actually are, and it showed them queued on the GIL.

<Accordion title="Design checkpoint — one question, with a model answer">

**Question.** A colleague's data pipeline does: read 10,000 JSON files from S3, parse each, compute a feature vector with NumPy, and write results to Postgres. It takes 40 minutes single-threaded. They propose `ProcessPoolExecutor(32)`. What do you say?

**Model answer.** Measure the three stages separately first, because they have three different answers and one pool cannot serve all of them.

**Stage 1, S3 reads: I/O-bound.** This is network wait; processes are the worst tool for it. Measured on an equivalent workload, processes gave 3.57× on I/O while threads gave 14.09× and asyncio 27.02×. Use `asyncio` with `aioboto3`, or a `ThreadPoolExecutor(50)` if you want no rewrite. The right concurrency here is bounded by S3's per-prefix throughput and your bandwidth, not by cores.

**Stage 2, JSON parse and NumPy features: mixed, and the NumPy part is the trap.** JSON parsing is CPU-bound Python and would benefit from processes. But NumPy already releases the GIL and BLAS already spawns its own threads — on this 11-core machine, 32 processes × 11 BLAS threads is 352 threads for 11 cores. That oversubscription is a well-documented multi-fold slowdown, and it is silent. If you use processes here, set `OMP_NUM_THREADS=1` in the workers, which Module 3 measures.

**Stage 3, Postgres writes: I/O-bound and connection-limited.** Thirty-two processes means 32 connections; the default `max_connections` is 100 and each idle connection costs real server memory. This stage should be a *small* number of writers doing batched `COPY`, not one writer per worker. Week 8 covers why.

**What I would propose:** a three-stage pipeline with independent concurrency per stage, connected by bounded queues — async fan-out for the reads (concurrency ~50), a process pool sized to `os.cpu_count()` with `OMP_NUM_THREADS=1` for the parse-and-feature stage, and 4 batched writers for Postgres. The bounded queues give back-pressure so a fast stage cannot exhaust memory ahead of a slow one.

**And before any of that:** run `/usr/bin/time -p` on the current 40-minute job. If `user + sys` is 3 minutes out of 40, the whole thing is I/O-bound and stage 2 is not the problem at all — in which case the answer is async fan-out and the process pool buys nothing. That measurement takes 40 minutes of waiting and zero minutes of work, and it decides the whole design.

### What the GIL actually is

The GIL is a single mutex in the CPython interpreter that a thread must hold to execute bytecode or touch any Python object. It exists because **every object has a reference count** (Week 3, Module 1), and incrementing a refcount without synchronisation is a data race. One coarse lock made refcounting correct with no per-object overhead and kept single-threaded code fast — which, in 1992, was the right trade.

Two mechanisms release it:

1. **Voluntarily, around blocking calls.** Every I/O function in the standard library wraps its syscall in `Py_BEGIN_ALLOW_THREADS` / `Py_END_ALLOW_THREADS`. So does NumPy around its kernels, `hashlib` around hashing, `zlib` around compression. That is why threads work for I/O.
2. **Involuntarily, on a timer.** A waiting thread sets a "drop request" flag; the running thread notices at its next check and releases. The interval is `sys.getswitchinterval()`, default **0.005 s (5 ms)**.

The detail that matters and that almost nobody knows: **the check does not happen between every pair of bytecodes.** Since CPython 3.10, the eval loop tests for the drop request only at specific instructions — loop back-edges, function calls, and a few others. A straight-line sequence of bytecodes with no call and no jump runs to completion without the GIL being released.

That has a striking consequence, measured. Eight threads, 2,000,000 increments each of a shared global:

| Statement | Lost updates | Percentage |
|---|---|---|
| `counter += 1` | **0 of 16,000,000** | 0.00% |
| `counter = counter + ident(1)` | **10,377,375 of 16,000,000** | **64.86%** |

Both are read-modify-write races. The first **does not lose a single update** on CPython 3.13, because `LOAD/BINARY_OP/STORE` contains no interruption point. The second inserts a function call — an interruption point — and loses two thirds of its work.

**This is the most dangerous fact in this module.** The classic textbook demo of a lost-update race no longer reproduces on modern CPython, so a developer who "tested it and it was fine" concludes the code is thread-safe. It is not thread-safe; it is accidentally-atomic on one implementation detail of one interpreter version, and it breaks the moment a function call, an attribute lookup on a property, or a different Python version enters the picture. It also breaks completely under free-threaded CPython, where there is no GIL to accidentally protect you.

**Never reason about atomicity from a bytecode listing. Use a lock, or `queue.Queue`, or an immutable message.**

### The switch interval, and why raising it is usually wrong

```python
import sys
sys.getswitchinterval()      # 0.005
sys.setswitchinterval(0.001) # more responsive, more overhead
```

A shorter interval reduces latency for a thread waiting to run and increases switching cost. Measured with the race benchmark, dropping from 5 ms to 5 µs took the same workload from 3.05 s to 1.63 s in one configuration and *raised* it in another — the effect depends entirely on contention, which is why the honest advice is to leave it alone unless you have a measurement.

The convoy effect is the reason people reach for it: a CPU-bound thread holds the GIL for a full 5 ms interval, so an I/O thread that has just had its data arrive waits up to 5 ms before it can run. In a service mixing a background CPU task with request handling, that is 5 ms added to the p99 for free. The right fix is not tuning the interval — it is moving the CPU work to a process.

### Lock and queue costs, measured

Minimum of 7 runs, ns per operation:

| Operation | Cost |
|---|---|
| `c[0] = c[0] + 1` (no lock) | **16.6 ns** |
| `lock.acquire(); lock.release()` | 24.9 ns |
| `with lock: c[0] = c[0] + 1` | **86.3 ns** (5.2× the unlocked op) |
| `with rlock: pass` (`RLock`) | 83.1 ns |
| `queue.Queue` put + get | **654.7 ns** |
| `deque` append + popleft | 13.3 ns |
| `threading.Thread` create + join | **126.3 µs** |

Three things to take from this. A **`with lock:` block costs about 70 ns of overhead** — irrelevant per request, significant per array element. **`queue.Queue` is 40× a bare lock** because it is a lock plus condition variables plus bookkeeping; it is still the right default for producer-consumer because correctness beats 650 ns, but do not put it in an inner loop. And **creating a thread costs 126 µs**, which is why pools exist: at 126 µs each, spawning a thread per request caps you at about 8,000 requests/second on thread creation alone.

### Free-threaded CPython: the status

PEP 703 was accepted in 2023 and the free-threaded build (`--disable-gil`) shipped as **experimental in 3.13** and moved to **officially supported (phase II) in 3.14**. It is a separate build — `python3.13t` — not a runtime flag.

What it changes: threads execute Python bytecode genuinely in parallel, so the CPU-bound row of the matrix stops reading 0.86× and starts scaling with cores. What it costs, from the PEP's own measurements and the 3.13 release notes:

- **Single-threaded performance regressed roughly 40% in the 3.13 free-threaded build**, improved to **about 5–10% in 3.14** as biased reference counting and deferred reference counting matured.
- **Every C extension must be rebuilt and audited.** A module must declare `Py_mod_gil` support; anything that does not causes the interpreter to re-enable the GIL at import, silently removing the benefit. As of 3.14, the major scientific stack (NumPy, SciPy, scikit-learn, Cython-built packages) has shipped free-threaded wheels; the long tail has not.
- **Your data races become real.** Everything the GIL was accidentally protecting — including `counter += 1` above — is now genuinely unsafe. Code that has "worked for years" under the GIL is the code most at risk.

The techniques that make it possible are worth knowing by name: **biased reference counting** (the object's owning thread updates a fast, non-atomic local count; other threads use a slower shared count), **deferred reference counting** for objects reachable from many threads, and **immortal objects** (PEP 683) for `None`, `True`, small ints and interned strings, whose refcounts never change and therefore never dirty a shared cache line.

**Subinterpreters** (PEP 554/734, `interpreters` module in 3.12+/3.13) are the other direction: multiple interpreters in one process, each with its own GIL, communicating through channels. Lighter than processes, since there is no separate OS process and no pickling over a pipe for shared-memory-friendly types, but with the same "no shared objects" discipline.

### Where the 2.74× went: efficiency accounting

Eight process workers gave 2.74× on an 11-core machine — **34% efficiency**. The accounting:

| Cost | Measured |
|---|---|
| Pool creation, `spawn` start method | **54.0 ms** for a pool of 4 |
| Same, `fork` | **3.8 ms** — 14.2× cheaper |
| Same, `forkserver` | 43.2 ms |
| Pickling a 100,000-int list | **659 µs** dumps + **1,313 µs** loads |
| Machine load during measurement | load average ~44 on 11 cores |

`spawn` is the default on macOS (since 3.8) and on Windows, and becomes the default on Linux in **3.14**. It starts a fresh interpreter and re-imports your module in each worker — safe, and 14× more expensive than `fork`. Module 3 covers why the default changed: `fork` in a process with threads is unsafe, and it is the source of the classic "my multiprocessing job deadlocks on macOS" report.

The 34% efficiency is therefore mostly startup plus contention with everything else on the box, not an inherent limit — on an idle machine with `fork` and a longer task, the same benchmark reaches 6–8×. **Report your efficiency and your machine's load. A speedup number without both is not reproducible.**

### Production failure modes and how you detect them

| Failure | Signature | Detection |
|---|---|---|
| Threads added to CPU-bound work | throughput flat or worse as thread count rises; latency climbs | `py-spy top --pid` shows threads queued on the GIL; `/usr/bin/time -p` shows `user ≈ real` |
| Process pool used for I/O | 3.57× where threads give 14× | count in-flight requests, not workers; switch to threads or asyncio |
| BLAS oversubscription | 8 processes × 11 BLAS threads on 11 cores; 5× slowdown, no error | `OMP_NUM_THREADS=1` in workers; Module 3 measures it |
| Data race that "cannot happen" | wrong totals under load, never in tests | the accidental atomicity above; use a lock or a queue, never bytecode reasoning |
| Convoy on the GIL | p99 up ~5 ms with a background CPU task | move CPU work to a process; do not tune `setswitchinterval` |
| Thread-per-request | ~126 µs per thread creation caps throughput; memory grows with concurrency | use a pool; each thread also costs 512 KB–8 MB of stack |
| Free-threaded build silently re-enables the GIL | no speedup on `python3.13t` | check `sys._is_gil_enabled()`; an extension without `Py_mod_gil` re-enabled it |
| Speedup reported without efficiency | "we got 2.7×" with no worker count | always report speedup, worker count, efficiency and machine load |

### Frontier and research pointers

- **Gross, S. — PEP 703, "Making the Global Interpreter Lock Optional in CPython" (2023).** One-sentence takeaway: removing the GIL requires biased and deferred reference counting plus per-object locks, because naive atomic refcounting on every object access costs more than the GIL ever did.
- **Van Rossum, G. — PEP 683, "Immortal Objects, Using a Fixed Refcount" (2022).** One-sentence takeaway: making `None`, small ints and interned strings immortal stops refcount writes from dirtying shared cache lines, which is a prerequisite for both free-threading and copy-on-write-friendly forking.
- **Amdahl, G. (1967). "Validity of the single processor approach to achieving large scale computing capabilities." *AFIPS*.** One-sentence takeaway: the serial fraction bounds speedup regardless of core count — at 95% parallel, a hundred cores buy 16.8×, not 100×.
- **Gustafson, J. (1988). "Reevaluating Amdahl's Law." *CACM* 31(5).** One-sentence takeaway: in practice people grow the problem with the machine, so the serial fraction shrinks — which rescues batch analytics and does nothing for fixed-size latency-sensitive work.
- **Beazley, D. (2010). "Understanding the Python GIL." PyCON.** One-sentence takeaway: the pre-3.2 GIL could make a *two*-thread CPU program slower than one thread on a multicore machine, because the waiting thread repeatedly woke, failed to acquire, and slept — the measurement that led to the current switch-interval design.
- **Sabinin, A., Bolz-Tereick, C. F. et al. — PyPy's STM work and the `interpreters` module (PEP 734).** One-sentence takeaway: subinterpreters give per-interpreter GILs inside one process, which is a cheaper middle ground than processes when the data can be passed rather than shared.

## Apply it at work

<AccordionGroup>
<Accordion title="If you're a student" icon="graduation-cap">

**Portfolio line:** *"A reproducible benchmark matrix of Python's four concurrency models across CPU-bound and I/O-bound workloads, with efficiency and machine load reported per cell — including the two cells where the obvious choice loses: threads make CPU work 0.86× as fast, and processes give 3.57× on I/O where threads give 14.09×."* The counter-intuitive cells are what make it interesting.

**The interview angle.** "What is the GIL?" is asked constantly and usually answered as "it stops Python using multiple cores", which is imprecise enough to lose the point. The answer that lands: *the GIL is one mutex you must hold to execute bytecode, and it exists because every object is reference-counted. It is released around blocking I/O and every 5 ms, so threads give real concurrency for I/O and none for CPU work — I measured threads at 0.86× on a CPU-bound task, slower than sequential, and 14.09× on an I/O-bound one.*

The senior follow-up is "so is `counter += 1` thread-safe?" and the answer that separates you is: *no, but on CPython 3.13 it happens not to lose updates because there is no GIL check point inside that bytecode sequence — I measured zero lost updates for `counter += 1` and 64.86% lost for the same thing with a function call in the middle. It is accidentally atomic, not safe, and it breaks under free-threaded builds.*
</Accordion>
<Accordion title="If you're working" icon="briefcase">

Three places this shows up in a normal engineering week:

1. **Someone proposes raising a thread-pool size.** Ask for `/usr/bin/time -p` first. If `user + sys ≈ real` the work is CPU-bound and more threads will make it worse — the image-service story went 32 → 64 → 128 threads and p99 went from 800 ms to 4.2 s. The escalation itself is the diagnostic.

2. **Any ML or data job using a process pool.** Check for BLAS oversubscription: N processes × M BLAS threads on C cores. Set `OMP_NUM_THREADS=1` (and `MKL_NUM_THREADS`, `OPENBLAS_NUM_THREADS`) in the workers. This is a silent multi-fold slowdown that a lot of production ML code is paying right now.

3. **A capacity plan that assumes linear scaling.** Fit Amdahl before buying machines: at 95% parallel, twenty workers give 10.3× and a hundred give 16.8×. Reducing the serial fraction from 5% to 2% raises the ceiling from 20× to 50×, which is cheaper than any hardware.
</Accordion>

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Adding threads made CPU work slower | GIL serialisation plus switching cost — measured 0.86× | `ProcessPoolExecutor`, or move the hot loop to NumPy/Cython/Rust |
| Process pool gives poor I/O speedup | concurrency is capped at pool size; 54 ms startup each | threads or asyncio: 14.09× and 27.02× versus 3.57× |
| ML job 5× slower than expected | N processes × M BLAS threads oversubscribing the cores | `OMP_NUM_THREADS=1` in workers |
| `RuntimeError` / infinite process spawning | no `if __name__ == "__main__":` guard with `spawn` | add the guard; it is mandatory on macOS and Windows |
| Shared counter is wrong under load, fine in tests | a real race that the GIL sometimes hides | lock it, or use `queue.Queue`; never infer atomicity from bytecode |
| Latency p99 up ~5 ms with a background task | GIL convoy: a CPU thread holds it for a full switch interval | move CPU work to a process; do not tune `setswitchinterval` |
| Thread-per-request exhausts memory | ~126 µs to create, 512 KB–8 MB of stack each | use a bounded pool, or asyncio |
| "We got 3× speedup" with no context | no worker count, no efficiency, no load average | report all four; 3× on 8 workers is 38% efficiency and needs explaining |
| Free-threaded build shows no speedup | a C extension lacking `Py_mod_gil` re-enabled the GIL at import | `sys._is_gil_enabled()`; check extension support |

**Primary docs**

- **[Python `threading` documentation and the "CPython implementation detail" notes on the GIL (3.13).](https://docs.python.org/3/library/threading.html)** Read the note on `sys.setswitchinterval` — it states plainly that the interval controls forced switches and says nothing about making anything atomic.

- **[Amdahl, G. M. (1967).
