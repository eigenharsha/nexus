## The ticket

> **NEX-1201 · Data · P1**
>
> Two problems, one root cause: nobody here can tell a real result from a plausible one.
>
> **(a)** Last quarter we shipped a recommendation change on the strength of a +3.2% A/B result. Post-
> launch metrics showed nothing. The post-mortem found a sample ratio mismatch that nobody had checked.
> Build a tool that runs the trust checks *before* it will show anyone a metric.
>
> **(b)** Our fraud model reports 0.91 precision in validation and the review queue is 94% false
> positives. Build a from-scratch classifier and an evaluation that reports precision **at the
> production base rate**, so this cannot happen again.
>
> Deliver both, plus a one-page "how to read an A/B test" guide the rest of the company can use.

<Warning>
Requirement (a) is the whole lab. A tool that computes a p-value is trivial; a tool that *refuses to
compute one* when the randomisation is broken is the deliverable. Build the checks as blocking gates,
not as warnings.
</Warning>

<Tabs>

<Tab title="basic">

**Means, intervals and a t-test on given data.**

1. `describe(data)` — n, mean, median, std, IQR, p50/p90/p95/p99, skewness, and the fraction above the
   mean.
2. `ci_mean(data, conf=0.95)` using the t distribution.
3. `two_sample_test(a, b)` — Welch's t-test (`equal_var=False`), with the effect size (Cohen's d) and a
   confidence interval on the difference.
4. `wilson(k, n)` — a confidence interval for a proportion that behaves correctly at `k = 0`.

**Acceptance criteria**

- `ci_mean` half-width scales as `1/sqrt(n)`: measured on the same population, going from n=100 to
  n=10,000 must shrink it by a factor of 10 ± 5%.
- `two_sample_test` uses Welch, not Student. (SciPy's default is Student. This is the point of the
  exercise.)
- `wilson(0, 100)` returns a non-zero upper bound; the Wald interval would return `(0, 0)`.
- `describe` reports `frac_above_mean` and it is below 0.5 for any right-skewed input.

<Info>About 60% is written for you. The `TODO(you)` markers are on Welch, Wilson and the skewness.</Info>

</Tab>

<Tab title="standard">

**The CLI tool and the classifier. These are the two portfolio artefacts.**

**Part 1 — `abtest` CLI**

1. **Blocking pre-checks**, run before any metric is displayed: SRM (chi-square at `p < 0.001`),
   pre-period covariate balance, and an identical outlier/bot filter applied to both arms. If any fail,
   the tool prints the failure and **exits without reporting the primary metric**.
2. **Sample-size calculator** — `n_per_arm(baseline, relative_mde, alpha, power)` and its inverse
   (given `n`, report the MDE).
3. **Analysis** — primary metric with a bootstrap CI on the difference; guardrails with one-sided
   checks; effect size.
4. **Decision output** — ship / do not ship / inconclusive, against a decision rule supplied on the
   command line, plus the MDE so a null result is interpretable.

**Part 2 — naive Bayes from scratch**

1. Laplace smoothing, log-space scoring, and — the important design decision — **the prior separated
   from the evidence**, so the production prior can be substituted at prediction time without
   retraining.
2. Evaluation reporting the full confusion matrix, precision, recall, specificity and F1 **at the
   production base rate**, not at the training base rate.
3. A **paired bootstrap** comparing two model configurations on the same test set, reporting the
   difference interval and `P(B > A)`.

**Acceptance criteria**

- The analyser refuses to report a primary metric when SRM fires. Verified against the broken dataset.
- The classifier reaches F1 above 0.90 on the SMS Spam Collection.
- The base-rate table matches the Bayes formula: precision at 0.1% prevalence must come out near 0.29
  for a classifier with sensitivity 0.868 and specificity 0.998.
- The paired bootstrap on `alpha=1.0` versus `alpha=0.1` produces a difference interval that excludes
  zero, while the two individual intervals overlap — and your write-up explains why both are true.

<Info>Spec and tests only. The `abtest` CLI is the artefact worth linking from a CV.</Info>

</Tab>

<Tab title="hard">

**Two constraints the standard solution fails.**

1. **Sequential testing.** Add O'Brien-Fleming boundaries for a stated number of interim looks.
   **Constraint: verify by simulation that the family-wise false-positive rate across all looks stays
   at 0.05 ± 0.01.** The `standard` tool, checked repeatedly, measures about 0.25 at 20 looks — you must
   demonstrate both numbers.
2. **CUPED.** Implement variance reduction with a pre-experiment covariate. **Constraint: demonstrate
   numerically that the required sample size falls, and show that the reduction matches `ρ²` to within
   2 percentage points across ρ = 0.3, 0.5, 0.7, 0.9.**
3. **A written report** covering both: the measured false-positive inflation from peeking, the
   sequential correction restoring it, and the CUPED sample-size saving with the arithmetic.

**Acceptance criteria**

- Simulated family-wise error rate with O'Brien-Fleming across 5 looks: 0.05 ± 0.01.
- CUPED variance reduction at ρ = 0.9: 81% ± 2pp, and the estimate must remain unbiased (the point
  estimate's mean across simulations must be within 2% of the true effect).
- The report states, for a specific experiment, how many fewer users CUPED would have required.

<Warning>
The constraint that breaks the standard solution is the *verified* family-wise error rate. Implementing
boundaries is easy; demonstrating by simulation that they actually control the error rate is where the
implementation bugs surface.
</Warning>

</Tab>

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
A public repo with the `abtest` CLI, the classifier, the full test suite, and `HOW-TO-READ-AN-AB-TEST.md`
— one page, written by you, that a product manager could follow.
</Card>

The one-pager is the artefact that gets read. Suggested structure, and keep it to one page:

1. **Before launch:** primary metric, MDE, sample size, guardrails, decision rule, stop date.
2. **Before believing the result:** SRM check, was the sample size fixed in advance, was there peeking,
   is the primary metric the pre-declared one.
3. **Reading it:** effect size with a confidence interval, not a p-value. Is the interval's *lower*
   bound worth shipping for?
4. **The traps:** peeking (5% → 25% at 20 looks), segment fishing, novelty effects, interference.
5. **When to distrust a win:** too good to be true usually is (Twyman's law); check SRM first.

## Common ways submissions lose points

1. **SRM implemented as a warning rather than a gate.** The ticket asks for a tool that refuses. A
   warning is ignored, which is exactly how the incident happened.
2. **Precision reported only at the training base rate.** The whole point of part (b) is the
   re-calibration to production prevalence.
3. **Unpaired bootstrap for the model comparison.** It will fail to detect the difference, and the
   write-up will conclude the models are equivalent — reproducing the error the module is about.
4. **`equal_var=True` left as SciPy's default.** Silent, small, and wrong.
5. **Sequential boundaries implemented but not verified.** The simulation is the deliverable; the
   formula is not.
6. **The one-pager written for statisticians.** It is for a product manager. If it contains the phrase
   "null hypothesis", rewrite it.
