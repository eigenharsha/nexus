**`LAB-P2-W14`** — one lab, three tracks. Beginners start at `basic` and climb.
Working professionals start at `standard`. `hard` is where the interview stories come from.
</Note>

## The ticket

> **Two deliverables, one repo.**
>
> **(a) A problem-solving journal.** Not a solutions folder — a *journal*. For each problem: the
> approach you tried first, why it was wrong or too slow, the approach that worked, and the
> complexity of each. The failed first idea is a required field. This is the artifact that gets
> you through a technical screen, because it is the record of how you think, and it is the thing
> you re-read on the train to the interview.
>
> **(b) A route planner.** A CLI that loads a real OpenStreetMap extract and answers
> origin-to-destination queries with Dijkstra and A*, reporting the path, cost, node expansions and
> runtime for each. It must assert that both algorithms return the same cost — that assertion is
> the test of your heuristic.

<Info>
**Time box.** `basic` 5–6 hours. `standard` 12–15 hours. `hard` a further 8–10 hours. The
`standard` track is 15 problems plus a route planner; if you are new to DSA, budget 20 hours and do
not feel bad about it. The problems get faster as the patterns settle — problems 12–15 usually take
a third of the time problems 1–4 did, and noticing that happen is part of the point.
</Info>

    | 8 | Kth largest element in a stream | heap | "use a bounded min-heap of size k" |

    - Problems 1–3 must have **both a recursive and an iterative** implementation, tested to agree.

  <Tab title="standard">
    **Fifteen medium problems with written complexity analysis, plus the route planner CLI.**

    ### The fifteen

    | # | Problem | Pattern | The thing that makes it medium |
    | --- | --- | --- | --- |
    | 1 | Binary tree right-side view | BFS | you need the *last* node of each level, not the first |
    | 2 | Lowest common ancestor in a BST | tree + BST property | the BST property makes it O(h) with no recursion |
    | 3 | Serialize and deserialize a binary tree | pre-order + sentinels | null markers are what make it unambiguous |
    | 4 | Implement a trie with prefix search | trie | `is_word` is not "is a leaf" |
    | 5 | Kth smallest in a BST | in-order + early exit | stop at k; do not build the whole list |
    | 6 | Course schedule II (return the order) | topological sort | now you must produce the order, not just a boolean |
    | 7 | Clone a graph | DFS + memo | the memo keyed by original node is what prevents infinite recursion |
    | 8 | Word ladder | BFS on an implicit graph | the graph is not given; you generate neighbours on demand |
    | 9 | Pacific-Atlantic water flow | multi-source BFS | search *backwards* from the oceans, not forwards from each cell |
    | 10 | Network delay time | Dijkstra | the answer is the *maximum* of the shortest paths |
    | 11 | Cheapest flights within K stops | Bellman-Ford, bounded | Dijkstra is wrong here — the stop limit breaks its greedy invariant |
    | 12 | Coin change (fewest coins) | unbounded knapsack | greedy fails; construct a coin set where it does |
    | 13 | Longest common subsequence | 2-D string DP | the base case row and column |
    | 14 | Word break | 1-D DP over a string | the state is "is `s[:i]` breakable", not "which words are used" |
    | 15 | Edit distance with the alignment | 2-D DP + backtracking | the path, not just the number |

    **Acceptance criteria**

    - All 15 solved, `make verify` green.
    - **A `JOURNAL.md` entry per problem**, with these four required fields:
      1. *First idea* — what you tried before you found the answer, and its complexity.
      2. *Why it failed* — too slow, wrong on a specific input, or too much memory. **Name the input
         that broke it.**
      3. *Working approach* — the state/transition or the traversal, in two sentences.
      4. *Complexity* — time and space, with a one-line justification.
    - **Problem 11 must include a written explanation of why Dijkstra gives the wrong answer**, with
      a concrete counterexample graph. This is the highest-value paragraph in the journal.
    - **Problem 12 must include a coin set where the greedy algorithm fails** — for example coins
      `[1, 3, 4]` and target 6, where greedy gives 4+1+1 = 3 coins and the optimum is 3+3 = 2.

    ### The route planner

    ```
    route --osm data/city.osm.pbf --from 52.5163,13.3777 --to 52.4862,13.4283 --algo astar
    route ... --compare        # runs both, asserts equal cost, prints the expansion ratio
    ```

    **Acceptance criteria**

    - Loads a real `.osm.pbf` (Geofabrik regional extracts are free; a mid-size city is fine).
    - Dijkstra and A* implemented behind one interface; `--compare` asserts identical cost and
      prints expansions for each.
    - **An admissibility test**: pick a goal, run Dijkstra to get true costs for all nodes, and
      assert `h(n) <= true(n)` for every node. If this fails, your heuristic is wrong and A* is
      returning suboptimal routes silently.
    - Reports expansions and wall time. **Expansions are the primary metric** — they are
      deterministic and reproduce; wall time does not.

    <Info>Spec and tests only. You write the implementation.</Info>

    <Warning>
    The single most common failure on the route planner is a **unit mismatch in the heuristic**. If
    your edge weights are travel *time* and your heuristic is *distance*, `h` overestimates by a
    factor of the speed and A* returns suboptimal routes with no error. Divide by the **maximum**
    speed anywhere in the network — the maximum, not the average. The admissibility test exists to
    catch exactly this.
    </Warning>
  </Tab>

  <Tab title="hard">
    **A\* with a custom heuristic beating Dijkstra by at least 3× on node expansions, plus a written
    proof sketch of admissibility.**

    <Warning>
    **The measured baseline is 1.49×**, not 3×. On a 1,200 × 1,200 grid with 20% obstacles,
    corner-to-corner, plain Manhattan distance reduced expansions from 1,177,499 to 792,399 — a
    1.49× improvement (week 14 module 4, Layer 3). **Plain Manhattan will not get you to 3×.** That
    is the constraint the `standard` solution fails, and finding a way past it is the lab.
    </Warning>

    **Three legitimate routes to 3×, and they are not equivalent:**

    1. **Better tie-breaking.** With unit edge costs, vast numbers of nodes share the same `f`, and
       the default heap ordering fans the search across an entire equal-`f` plateau. Push
       `(f, -g, node_id)` so that among equal `f`, the node deeper along a path pops first. **This
       costs nothing and preserves optimality.** On plateau-heavy grids the reduction is substantial
       on its own.
    2. **A stronger admissible heuristic — ALT (landmarks + triangle inequality).** Precompute exact
       distances from `L` landmark nodes to every node. Then
       `h(n) = max over landmarks of |d(L, goal) − d(L, n)|`, which is admissible by the triangle
       inequality and is much tighter than Manhattan because **it knows about the obstacles**.
       Preprocessing is `L` Dijkstra runs; memory is `L × V` distances. **This preserves optimality
       and is the intellectually satisfying answer.**
    3. **Weighted A\*, `f = g + w·h`.** Guarantees a path at most `w`× optimal. Easiest, largest
       expansion reduction, **and it gives up optimality.** Perfectly legitimate — but you must
       label it as a different guarantee and report the *measured* suboptimality, not just the
       bound.

    **Acceptance criteria**

    - **A measured ≥3× reduction in node expansions** against Dijkstra on the same graph and the
      same origin/destination pairs, averaged over at least 100 random pairs. Single-pair results
      are noise.
    - **A written proof sketch of admissibility** for your heuristic. The shape of the argument is
      always: *identify work that any path must do, and show `h` counts no more than that work.*
      For ALT: state the triangle inequality, show `d(L,goal) ≤ d(L,n) + d(n,goal)`, rearrange to
      `d(n,goal) ≥ d(L,goal) − d(L,n)`, and note the same holds with the roles swapped, giving the
      absolute value. Two paragraphs.
    - **An empirical admissibility check** across at least 1,000 sampled nodes: `h(n) ≤ true(n)`.
      A proof plus a test, because a correct proof of the wrong formula is still wrong code.
    - **If you used weighted A\***, report the measured suboptimality distribution — mean and max
      of `cost_weighted / cost_optimal` across your 100 pairs — and compare it to the theoretical
      `w` bound. It will be far better than the bound, and explaining why is worth marks.

    **The stretch beyond the requirement:** implement **bidirectional A\***, which is genuinely
    subtle. The naive termination condition — stop when the two searches meet — returns suboptimal
    paths, and the bug is invisible without a ground-truth comparison. Find the bug by comparing
    against Dijkstra, then fix it. This is the best single exercise in the week.

    <Warning>There is a constraint here that the `standard` solution fails.</Warning>

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
A public **problem-solving journal** repo. For each problem: the approach, the failed first idea,
and the final complexity. Plus the route planner with its `--compare` output committed as evidence.
</Card>

The journal is the artifact, not the solutions. Anyone can push 15 solved problems — the internet is
full of them and an interviewer discounts them entirely. **A record of fifteen wrong first ideas and
why each was wrong is evidence of how you think**, which is the only thing a technical screen is
actually assessing.

Write each entry in four lines. Do not write essays; write the four fields. The entry for problem 11
should look something like:

> **11. Cheapest flights within K stops.**
> *First idea:* Dijkstra with the stop count carried alongside the cost. O((V+E) log V).
> *Why it failed:* Dijkstra finalises a node the first time it pops it, but a *more expensive* route
> reaching a city in *fewer stops* can be the only viable one — so finalising on cost alone discards
> the answer. Broke on a 4-city graph where the cheap route used 3 stops and the limit was 1.
> *Working approach:* Bellman-Ford bounded to K+1 relaxation rounds. Each round extends every path
> by exactly one edge, so after round `r` you have the best cost using at most `r` edges. Relax from
> a snapshot of the previous round, or one round leaks into the next.
> *Complexity:* O(K·E) time, O(V) space.

That entry is 90 seconds to write and it is exactly what you would say out loud in an interview.

<Tip>
`make journal` fails if any problem's entry is missing the *"failed first idea"* field. That is
deliberate. The field people skip is the field that makes the artifact worth having, and a check
that enforces it is more effective than an instruction that requests it.
</Tip>

## Rubric

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Correctness | fails tests | happy path only | edge cases (empty, single node, disconnected, unreachable) | property-tested against a brute-force oracle |
| Code quality | works | readable | tested + `mypy --strict` clean | iterative where depth is data-dependent; one interface for both algorithms |
| Performance | untested | measured once | expansions and time reported across 100 pairs | ≥3× expansion reduction with admissibility proven and tested |
| Explanation | none | a README | complexity stated per problem | all four journal fields per problem, including the counterexample for problem 11 |

**What a 3 in Explanation actually requires.** Not "this is O(n log n)". Something like: *"My first
attempt used Dijkstra with a stop counter in the priority queue. It failed on a graph where the
cheapest route to the destination used 3 hops and the limit was 1 — Dijkstra finalises a node on
first pop, so it committed to the cheap-but-too-long route and never explored the expensive-but-short
one. Bellman-Ford bounded to K+1 rounds is correct because each round extends paths by exactly one
edge, so the round index *is* the hop count."*

## Common ways submissions lose points

| What happens | Why it costs marks | What to do instead |
| --- | --- | --- |
| Recursive tree/graph traversal | Crashes on deep real input; passes every small test | Iterative with an explicit stack wherever depth is data-dependent |
| Two-colour cycle detection | False positives on diamond-shaped prerequisite graphs | Three colours: white, grey, black; grey means "on the current path" |
| Journal entries with no failed first idea | The field that makes the journal valuable is the one omitted | Write the wrong idea down *while you are having it*, before you fix it |
| Route planner reports only wall time | Wall time is machine-dependent and unreproducible | Report node expansions as the primary metric |
| Heuristic asserted admissible, never tested | A unit mismatch makes A* silently suboptimal | Compute true distances with Dijkstra; assert `h(n) <= true(n)` on 1,000 samples |
| Weighted A* presented as if it were optimal | It is a different guarantee, not a free speedup | Label it, and report measured suboptimality against the `w` bound |
| Problem 12 with no failing greedy example | The whole point of the problem is that greedy is wrong here | Coins `[1,3,4]`, target 6: greedy gives 3 coins, optimum is 2 |
| 3× claimed from a single origin/destination pair | Expansion ratios vary enormously with geometry | Average over ≥100 random pairs and report the distribution |
