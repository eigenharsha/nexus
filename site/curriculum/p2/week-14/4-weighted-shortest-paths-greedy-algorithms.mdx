    ## The idea in one paragraph

    In module 3, BFS found the shortest path by counting *edges*, because every edge cost the same.
    Real problems are not like that: roads have lengths, network links have latencies, tasks have
    durations. Once edges have different costs, "fewest hops" and "cheapest total" are different
    questions, and BFS answers the wrong one. **Dijkstra's algorithm** answers the right one, by
    always expanding the cheapest-so-far node rather than the fewest-hops-so-far node. **A\***
    improves on it by adding one extra number — a guess of how far the goal still is — so the search
    heads toward the target instead of spreading out uniformly in every direction.

    ### The analogy

    You are pouring water at your house and want to know when it reaches the shop.

    - **BFS** is water spreading through corridors where every corridor takes exactly one second.
      The wavefront is a ring of equal hop-count.
    - **Dijkstra** is water spreading through pipes of different lengths. The wavefront is a ring of
      equal *travel time*, which is a strange shape on the map — but it is exactly the right shape,
      because the first moment water reaches the shop is the shortest travel time by definition.
      **The pool grows in every direction, including directly away from the shop**, because the
      water has no idea where the shop is.
    - **A\*** is the same water, but you have a map and can estimate the straight-line distance from
      any point to the shop. Now you pour preferentially toward the shop. You still find the
      shortest route — **provided your estimate never claims the shop is closer than it really is.**

    That proviso is the whole subject of A*. An estimate that never overestimates is called
    **admissible**, and admissibility is exactly what makes A* return the true shortest path rather
    than a confident wrong one.

    ### Every term, defined

    - **Weighted graph** — each edge carries a number: distance, time, cost, latency.
    - **Path cost** — the sum of the weights along a path.
    - **Shortest path** — the path with the smallest total cost. Not necessarily the fewest edges.
    - **Relaxation** — the core operation: if going to `v` via `u` is cheaper than the best known
      route to `v`, record the cheaper one. Every algorithm here is relaxation in a different order.
    - **Frontier** — nodes discovered but not yet finalised, held in a priority queue.
    - **Finalised (settled)** — a node whose shortest distance is known for certain and will never
      change.
    - **Greedy algorithm** — one that makes the locally best choice at each step and never
      reconsiders. Sometimes provably optimal, often not.
    - **Heuristic `h(n)`** — an estimate of the remaining cost from `n` to the goal.
    - **Admissible** — `h(n)` never overestimates the true remaining cost. Required for A* to be
      correct.
    - **Consistent (monotone)** — `h(u) ≤ cost(u,v) + h(v)` for every edge. Stronger than
      admissible, and it means a node is never re-expanded.
    - **MST (minimum spanning tree)** — the cheapest set of edges connecting every node with no
      cycles.

    ### The smallest working example

    ```python
    # dijkstra.py — CPython 3.12
    import heapq

    graph = {
        "A": [("B", 1), ("C", 4)],
        "B": [("C", 2), ("D", 5)],
        "C": [("D", 1)],
        "D": [],
    }

    def dijkstra(graph, start):
        """Shortest cost from start to every reachable node."""
        dist = {start: 0}
        pq = [(0, start)]                 # (cost so far, node)
        while pq:
            d, node = heapq.heappop(pq)   # ALWAYS the cheapest unfinalised node
            if d > dist.get(node, float("inf")):
                continue                  # a stale entry; we already found better
            for nb, weight in graph[node]:
                nd = d + weight
                if nd < dist.get(nb, float("inf")):
                    dist[nb] = nd         # relaxation
                    heapq.heappush(pq, (nd, nb))
        return dist

    print(dijkstra(graph, "A"))
    # {'A': 0, 'B': 1, 'C': 3, 'D': 4}
    ```

    ### Line-by-line walkthrough

    - `pq = [(0, start)]` — a min-heap of `(cost, node)`. Because cost is first, `heappop` always
      returns the cheapest known unfinalised node. **That ordering is the algorithm.**
    - `d, node = heapq.heappop(pq)` — the moment you pop a node, its distance is final. Nothing left
      in the queue is cheaper, and (with non-negative weights) no route through a more expensive
      node can be cheaper. This is the correctness argument, and it is the sentence that breaks with
      negative weights.
    - `if d > dist.get(node, inf): continue` — **lazy deletion**, exactly as in module 2. When a
      node's distance improves we push a new entry rather than trying to find and update the old
      one. The old entry is stale and is skipped here. This is why the heap can hold more entries
      than there are nodes.
    - `nd = d + weight` then `if nd < dist.get(nb, inf)` — relaxation. "Is going via me cheaper than
      whatever you had?"
    - Trace it: A(0) → B is 1, C via A is 4. Pop B(1) → C via B is 1+2 = 3, which beats 4, so C
      improves; D via B is 6. Pop C(3) → D via C is 3+1 = 4, beating 6. Pop D(4). Answer: D costs 4
      by A→B→C→D. **Note that the shortest path has three edges and the two-edge route A→C→D costs
      5.** That is precisely the difference between BFS and Dijkstra.

    ### Why negative weights break it

    ```python
    #  A --1--> B
    #  A --5--> C
    #  C --(-10)--> B
    #
    # True shortest A->B is A->C->B = 5 + (-10) = -5.
    ```

    Dijkstra pops B at cost 1 and marks it final, because 1 is the smallest thing in the queue at
    that moment. Only later does it explore C (cost 5) and discover the −10 edge — but B is already
    finalised and Dijkstra never revisits. **It returns 1. The answer is −5.**

    The failure is not a crash or an exception. It is a wrong number returned with complete
    confidence, and it only appears on inputs that contain a negative edge — so it passes every test
    written by someone who did not think about negative weights.

    <Warning>
    "But my weights are distances, they cannot be negative." Check again. Refunds are negative
    amounts. Time zones and clock adjustments produce negative durations. A cost function of the form
    `price − discount` can go negative. A profit-maximising path is a *cost*-minimising path over
    negated profits. **If any weight can be negative, use Bellman-Ford**, which costs O(V·E) instead
    of O((V+E) log V) and is correct.
    </Warning>

      **Why early-exit at the goal is safe.** When `goal` is popped, its distance is final by the
      same argument that makes Dijkstra correct at all. Continuing would only compute distances to
      nodes you did not ask about. On a large graph this is a large saving and it is free.

      **Why `prev` is written during relaxation, not on pop.** `prev[nb]` must record the predecessor
      on the *best* route found so far, which is exactly the moment you improve `dist[nb]`. Writing
      it on pop would be too late — you would have lost which edge produced the winning distance.

      **The unreachable case matters.** `D` has no outgoing edges, so from `D` the queue empties
      without ever reaching `A`, and the function falls through to `(inf, [])`. Test it: a shortest-
      path function that raises `KeyError` on an unreachable target is a function that crashes the
      first time a road closes.

    ### Checkpoint — 5 questions before you continue

    <AccordionGroup>
      <Accordion title="1. Why does Dijkstra use a priority queue rather than a plain queue?">
        Because it must always expand the *cheapest* unfinalised node, and a plain FIFO queue gives
        you the *oldest*. With uniform weights those coincide, which is exactly why BFS works on
        unweighted graphs — BFS is Dijkstra with all weights equal to 1.
      </Accordion>
      <Accordion title="2. Why is a node's distance final the moment it is popped?">
        Because the heap returns the smallest remaining tentative distance `d`. Any other route to
        that node must pass through some node still in the queue, whose distance is at least `d`,
        and adding a non-negative edge cannot reduce it below `d`. **The words "non-negative" are
        doing all the work** — remove them and the argument collapses, which is precisely why
        negative weights break Dijkstra.
      </Accordion>
      <Accordion title="3. What does 'admissible' mean and why does A* need it?">
        A heuristic is admissible if it never overestimates the true remaining cost. A* expands nodes
        in order of `f = g + h`. If `h` overestimates for the node on the true shortest path, that
        node's `f` is inflated, it sits lower in the queue, and A* pops the goal via a worse route
        first — returning a suboptimal path with no indication anything went wrong.
      </Accordion>
      <Accordion title="4. What is a greedy algorithm, and when is greedy correct?">
        One that takes the locally best option and never reconsiders. It is provably correct when the
        problem has the **greedy-choice property** (a locally optimal choice is part of some global
        optimum) and **optimal substructure** (an optimal solution contains optimal solutions to
        subproblems). Dijkstra, Kruskal and Prim have these. The 0/1 knapsack does not, which is why
        it needs dynamic programming — module 5.
      </Accordion>
      <Accordion title="5. What is a minimum spanning tree and what is it not?">
        The cheapest set of edges that connects every node with no cycles — `V−1` edges. It is **not**
        a shortest-path tree: the MST minimises *total* edge weight, while a shortest-path tree
        minimises distance *from one source* to each node. They are usually different trees, and
        confusing them is a common and expensive modelling error.
      </Accordion>
    </AccordionGroup>

    ## Bellman-Ford: correct with negative weights

    ```python
    def bellman_ford(nodes, edges, start):
        """edges: list of (u, v, weight). O(V*E).
        Returns (dist, None) or (None, negative_cycle_nodes)."""
        dist = {n: float("inf") for n in nodes}
        dist[start] = 0
        prev = {}

        # V-1 rounds: any shortest path has at most V-1 edges, and each round
        # guarantees all paths of one more edge have been relaxed.
        for _ in range(len(nodes) - 1):
            changed = False
            for u, v, w in edges:
                if dist[u] + w < dist[v]:
                    dist[v] = dist[u] + w
                    prev[v] = u
                    changed = True
            if not changed:
                break                 # early exit: converged

        # One more round. If anything still improves, a negative cycle exists.
        affected = [v for u, v, w in edges if dist[u] + w < dist[v]]
        if affected:
            return None, affected
        return dist, None
    ```

    | | Dijkstra | Bellman-Ford |
    | --- | --- | --- |
    | Complexity | O((V+E) log V) | O(V·E) |
    | Negative edges | **wrong answer, silently** | correct |
    | Negative cycles | undefined | **detects them** |
    | Distributed | hard | natural — this is RIP and the basis of distance-vector routing |

    **Negative cycle detection is a feature, not a side effect.** In currency arbitrage you take
    `−log(exchange_rate)` as the weight; a negative cycle is then a sequence of trades that returns
    more than you started with. Bellman-Ford finds it. This is a real production use, and it is the
    one time you *want* the negative cycle.

    ## A*: Dijkstra plus a guess

    ```python
    import heapq

    def astar(neighbours, start, goal, h):
        """neighbours(n) -> iterable of (node, cost). h(n) -> estimated cost to goal.
        Correct iff h is admissible (never overestimates)."""
        g = {start: 0}
        pq = [(h(start), 0, start)]      # (f = g + h, g, node)
        prev = {}
        expansions = 0
        while pq:
            f, gn, node = heapq.heappop(pq)
            if gn > g.get(node, float("inf")):
                continue
            expansions += 1
            if node == goal:
                path = [goal]
                while path[-1] != start:
                    path.append(prev[path[-1]])
                return gn, path[::-1], expansions
            for nb, w in neighbours(node):
                ng = gn + w
                if ng < g.get(nb, float("inf")):
                    g[nb] = ng
                    prev[nb] = node
                    heapq.heappush(pq, (ng + h(nb), ng, nb))
        return float("inf"), [], expansions
    ```

    **`h(n) = 0` makes this exactly Dijkstra.** A* is a strict generalisation, and that is the
    cleanest way to remember it.

    ### Choosing and proving a heuristic

    | Movement allowed | Admissible heuristic | Why it never overestimates |
    | --- | --- | --- |
    | 4-directional grid, unit cost | Manhattan: abs(dx) + abs(dy) | you must make at least abs(dx) horizontal and abs(dy) vertical moves; obstacles can only add |
    | 8-directional, diagonal cost 1 | Chebyshev: max(abs(dx), abs(dy)) | a diagonal move reduces both by one, so you need at least the larger |
    | Any direction, Euclidean cost | Euclidean: `√(dx² + dy²)` | straight line is the shortest distance between two points |
    | Road network, cost = time | `great_circle_distance / max_speed_limit` | you cannot arrive faster than the straight line at the fastest legal speed |
    | Anything | `h(n) = 0` | trivially admissible; this is Dijkstra |

    **The proof pattern is always the same: show that the true remaining cost is at least `h(n)`,
    by identifying work that any path must do.** For Manhattan distance on a grid: any path from
    `n` to the goal must change `x` by `dx` and `y` by `dy`, each move changes exactly one by one,
    so at least abs(dx) + abs(dy) moves are required. Obstacles only add. Therefore `h ≤ true`. ∎

    **The road-network row is the one that bites in practice.** If your cost is *travel time* and
    your heuristic is *distance*, the units do not match and the heuristic is inadmissible by a
    factor of the speed. Dividing by the maximum speed limit anywhere in the graph fixes it — and
    note that the *maximum* is required, not the average, because a path might use only motorways.
    Using the average speed makes the heuristic inadmissible and A* silently returns suboptimal
    routes.

    <Tip>
    **Weighted A\* trades optimality for speed, deliberately.** Use `f = g + w·h` with `w > 1`. The
    result is guaranteed to be at most `w` times optimal — a bounded-suboptimality guarantee — and it
    is typically dramatically faster because the search is pulled much harder toward the goal. In
    routing, `w = 1.2` for a route at most 20% longer than optimal is often an excellent trade, and
    it is how you get the 3× expansion reduction the `hard` track asks for.
    </Tip>

    ## Minimum spanning trees

    ```python
    def kruskal(n, edges):
        """edges: (weight, u, v). Sort, then add any edge that does not close a cycle.
        O(E log E), dominated by the sort."""
        uf = UnionFind(n)                # from module 3
        mst, total = [], 0
        for w, u, v in sorted(edges):
            if uf.union(u, v):           # False means they were already connected
                mst.append((u, v, w))
                total += w
                if len(mst) == n - 1:
                    break                # a spanning tree has exactly n-1 edges
        return mst, total
    ```

    ```python
    import heapq

    def prim(adj, start=0):
        """Grow one tree from a start node, always adding the cheapest edge
        leaving the tree. O(E log V) with a heap."""
        seen = {start}
        pq = [(w, start, v) for v, w in adj[start]]
        heapq.heapify(pq)                # O(n), see module 2
        mst, total = [], 0
        while pq and len(seen) < len(adj):
            w, u, v = heapq.heappop(pq)
            if v in seen:
                continue                 # lazy deletion again
            seen.add(v)
            mst.append((u, v, w))
            total += w
            for nb, nw in adj[v]:
                if nb not in seen:
                    heapq.heappush(pq, (nw, v, nb))
        return mst, total
    ```

    | | Kruskal | Prim |
    | --- | --- | --- |
    | Structure | union-find | priority queue |
    | Complexity | O(E log E) | O(E log V) |
    | Best when | **sparse** graphs; edges already sorted | **dense** graphs; edge list not materialised |
    | Grows | many fragments that merge | one connected tree |
    | Parallelises | reasonably (sort, then merge) | poorly (inherently sequential) |

    **Both are greedy and both are provably optimal**, via the **cut property**: for any partition of
    the nodes into two sets, the minimum-weight edge crossing that partition is in some MST. Kruskal
    applies it globally (the cheapest remaining edge crosses *some* cut); Prim applies it locally
    (the cheapest edge leaving the current tree). That single lemma is the proof for both, and being
    able to state it is what "provably correct greedy" means.

    ## Reference implementation: a route planner CLI

    ```python
    # route.py — CPython 3.12. Dijkstra and A* over an OpenStreetMap extract.
    from __future__ import annotations
    import heapq
    import math
    from dataclasses import dataclass, field


    @dataclass(slots=True)
    class RoadNetwork:
        """Nodes are OSM node ids; coords are (lat, lon) in degrees."""
        coords: dict[int, tuple[float, float]] = field(default_factory=dict)
        adj: dict[int, list[tuple[int, float]]] = field(default_factory=dict)
        max_speed_kmh: float = 130.0          # the fastest legal speed anywhere

        def haversine_km(self, a: int, b: int) -> float:
            lat1, lon1 = self.coords[a]
            lat2, lon2 = self.coords[b]
            R = 6371.0
            p1, p2 = math.radians(lat1), math.radians(lat2)
            dp = math.radians(lat2 - lat1)
            dl = math.radians(lon2 - lon1)
            x = math.sin(dp / 2) ** 2 + math.cos(p1) * math.cos(p2) * math.sin(dl / 2) ** 2
            return 2 * R * math.asin(math.sqrt(x))

        def heuristic_hours(self, node: int, goal: int) -> float:
            """Admissible for a cost measured in HOURS.

            Proof: the great-circle distance is a lower bound on road distance
            (roads cannot be shorter than a straight line), and no legal journey
            exceeds max_speed_kmh, so the true remaining time is at least
            distance / max_speed. Therefore h never overestimates.
            """
            return self.haversine_km(node, goal) / self.max_speed_kmh


    @dataclass(slots=True)
    class SearchResult:
        cost: float
        path: list[int]
        expansions: int
        pushes: int


    def search(net: RoadNetwork, start: int, goal: int,
               weight: float = 1.0, use_heuristic: bool = True) -> SearchResult:
        """weight=1.0 and use_heuristic=True  -> optimal A*
           use_heuristic=False                -> Dijkstra
           weight>1.0                         -> weighted A*, at most `weight` x optimal"""
        def h(n: int) -> float:
            return net.heuristic_hours(n, goal) * weight if use_heuristic else 0.0

        g: dict[int, float] = {start: 0.0}
        prev: dict[int, int] = {}
        pq: list[tuple[float, float, int]] = [(h(start), 0.0, start)]
        expansions = pushes = 0

        while pq:
            _, gn, node = heapq.heappop(pq)
            if gn > g.get(node, math.inf):
                continue                      # stale entry
            expansions += 1
            if node == goal:
                path = [goal]
                while path[-1] != start:
                    path.append(prev[path[-1]])
                path.reverse()
                return SearchResult(gn, path, expansions, pushes)
            for nb, w in net.adj.get(node, ()):
                ng = gn + w
                if ng < g.get(nb, math.inf):
                    g[nb] = ng
                    prev[nb] = node
                    heapq.heappush(pq, (ng + h(nb), ng, nb))
                    pushes += 1
        return SearchResult(math.inf, [], expansions, pushes)
    ```

    ```python
    # test_route.py — pytest 8.x
    import math
    import pytest
    from route import RoadNetwork, search


    @pytest.fixture
    def net():
        n = RoadNetwork(max_speed_kmh=100.0)
        # A tiny synthetic network: a straight chain plus a costly shortcut.
        n.coords = {1: (0.0, 0.0), 2: (0.0, 0.1), 3: (0.0, 0.2), 4: (0.0, 0.3)}
        n.adj = {
            1: [(2, 0.1), (3, 0.5)],
            2: [(3, 0.1), (4, 0.9)],
            3: [(4, 0.1)],
            4: [],
        }
        return n


    def test_astar_and_dijkstra_agree_on_cost(net):

        d = search(net, 1, 4, use_heuristic=False)
        assert a.cost == pytest.approx(d.cost)
        assert a.path == d.path


    def test_astar_expands_no_more_than_dijkstra(net):

        d = search(net, 1, 4, use_heuristic=False)
        assert a.expansions <= d.expansions


    def test_heuristic_is_admissible_on_every_pair(net):
        """The property that makes A* correct — assert it, do not assume it."""
        d_from = {n: search(net, n, 4, use_heuristic=False).cost for n in net.adj}
        for n, true_cost in d_from.items():
            if math.isinf(true_cost):
                continue
            assert net.heuristic_hours(n, 4) <= true_cost + 1e-9


    def test_unreachable_goal(net):
        net.adj[3] = []
        net.adj[2] = [(3, 0.1)]
        net.adj[1] = [(2, 0.1)]
        r = search(net, 1, 4)
        assert math.isinf(r.cost) and r.path == []


    def test_weighted_astar_bound(net):
        optimal = search(net, 1, 4).cost
        w = 1.5
        r = search(net, 1, 4, weight=w)
        assert r.cost <= w * optimal + 1e-9      # the bounded-suboptimality guarantee


    def test_start_equals_goal(net):
        r = search(net, 1, 1)
        assert r.cost == 0.0 and r.path == [1]
    ```

    <Check>
    `test_heuristic_is_admissible_on_every_pair` is the test almost nobody writes, and it is the one
    that matters. Admissibility is a *property of your heuristic against the actual graph*, not
    something you can assert by reading the formula — a unit mismatch, a speed limit above your
    assumed maximum, or a one-way road that makes the straight line unreachable will all break it.
    Compute true distances with Dijkstra and assert `h(n) ≤ true(n)` for every node. On a real graph
    you sample rather than exhaust, but the test is the same shape.
    </Check>

    ## Trade-offs table

    | Situation | Choose | Instead of | Because |
    | --- | --- | --- | --- |
    | Non-negative weights, one source | Dijkstra | Bellman-Ford | O((V+E) log V) vs O(V·E) |
    | Any weight can be negative | Bellman-Ford | Dijkstra | Dijkstra returns a wrong answer silently |
    | You need to *detect* negative cycles | Bellman-Ford | anything else | it is the only one that does; this is currency arbitrage |
    | Single target, and you have a distance metric | A* | Dijkstra | measured 1.49× fewer expansions with plain Manhattan; far more with a better heuristic |
    | Single target, approximate is fine | weighted A* (`w = 1.2`–`2.0`) | A* | bounded `w`× suboptimality, large expansion reduction |
    | All-pairs, dense, V under ~1,000 | Floyd–Warshall | V× Dijkstra | O(V³) with a tiny constant, and it is 5 lines |
    | Road network, millions of queries | contraction hierarchies | A* | heavy preprocessing, then queries in microseconds |
    | Cheapest connecting set, sparse | Kruskal | Prim | sort-dominated; union-find is O(α) |
    | Cheapest connecting set, dense | Prim | Kruskal | O(E log V) and never materialises the edge list |
    | Unweighted graph | BFS | Dijkstra | same answer, no heap, simpler |

    ## What breaks in the real world

    A logistics platform routed delivery vehicles with A*, cost measured in **minutes**, heuristic
    `haversine_km / 80` — dividing by 80 km/h, the average speed observed across their fleet.

    It shipped, routes looked sensible, and drivers were happy for four months.

    Then a customer with a distribution centre beside a motorway complained that the app consistently
    routed around the motorway for long hauls, adding 15–20 minutes. The routes were *legal and
    plausible* — just not optimal — which is why nobody had spotted it.

    **The heuristic was inadmissible.** Motorway segments were traversed at 110 km/h. For a node
    30 km from the goal along a motorway, the true remaining time was `30/110 = 16.4` minutes, while
    `h` claimed `30/80 = 22.5` minutes. **`h` overestimated by 37%.** A* therefore *under*-prioritised
    the motorway route — its `f = g + h` looked worse than it was — and popped the goal via a
    slower arterial route first. A* is only optimal when `h` never overestimates; here it did, and
    the algorithm returned the first path it found rather than the best.

    The symptom set is worth memorising, because it is what an inadmissible heuristic always looks
    like:

    - **No errors, no exceptions, no failed assertions.**
    - **Routes are valid** — they get you there, they obey the graph.
    - **Routes are consistently slightly worse**, and the excess correlates with how badly `h`
      overestimates in that region.
    - **It only shows up when you compare against ground truth**, which nobody was doing.

    The fix was one character's worth of thought: divide by the **maximum** speed anywhere in the
    network (130 km/h), not the average. That made `h` admissible everywhere. It also made the
    heuristic weaker — a weaker heuristic explores more — and expansions rose about 22%, adding
    roughly 4 ms per query. **They accepted the 4 ms.**

    What generalises:

    - **"Average" is almost never the right constant in an admissible heuristic.** Admissibility is
      a statement about the worst case over the whole graph, so the bound must use the extreme.
    - **Test admissibility, do not reason about it.** Run Dijkstra to get true costs on a sample of
      nodes and assert `h ≤ true`. It is a few lines and it would have caught this on day one.
    - **Suboptimality is invisible without a ground-truth comparison.** Add a shadow check: for 0.1%
      of requests, also compute the Dijkstra answer and record the ratio. If the ratio is ever above
      1.0, your heuristic is inadmissible. This costs almost nothing and turns an unobservable bug
      into a metric.

    ### Design checkpoint

    <Accordion title="Your routing service must answer 5,000 queries/second over a 20-million-node road network with p99 under 50 ms. A* takes 800 ms. What do you do?">
    **Model answer.**

    **First, name the actual problem.** A* is `O(E log V)` in the worst case and its expansion count
    grows roughly with the *area* it must explore. On a 20-million-node continental graph a long
    route explores millions of nodes. No amount of heuristic tuning gets 800 ms to 50 ms — you need
    a different algorithm class, not a faster implementation.

    **The answer is preprocessing.** Road networks are static for hours or days; queries are
    constant. That asymmetry is exactly what preprocessing exploits.

    1. **Contraction hierarchies (Geisberger et al., 2008).** Order nodes by "importance"; repeatedly
       remove the least important node and insert *shortcut* edges preserving shortest paths through
       it. Queries then run bidirectional Dijkstra that only ever moves *upward* in the hierarchy.
       Preprocessing on a continental network is tens of minutes; queries drop to **microseconds** —
       a factor of roughly 10⁴–10⁵. This is what OSRM ships and it is the standard answer.
    2. **Bidirectional search** as a cheaper first step. Search forward from the start and backward
       from the goal, meeting in the middle. The explored region is two circles of radius `d/2`
       rather than one of radius `d`, so roughly **half the area** — typically a 2× win. Easy, no
       preprocessing, and worth doing regardless. The termination condition is subtle and is where
       the bugs are: you cannot stop at the first meeting node, you must continue until the best
       forward plus backward distance is no worse than the sum of the two frontiers' minimums.
    3. **ALT (A\*, Landmarks, Triangle inequality).** Precompute distances from ~16 landmark nodes to
       everything; the triangle inequality then gives a much stronger admissible heuristic than
       straight-line distance. Preprocessing is minutes, memory is `16 × V` distances, and the
       expansion reduction is typically 5–20×. **A good middle option** when contraction
       hierarchies are too much machinery.

    **What I would actually do, in order.**

    - **Week 1:** bidirectional A* plus a landmark heuristic. Roughly 10–30× improvement, days of
      work, no new infrastructure. This may well be enough — 800 ms / 20 = 40 ms.
    - **If not: contraction hierarchies**, or adopt OSRM/Valhalla rather than building one. **This is
      a solved problem with good open-source implementations, and writing your own is a multi-month
      project that will be worse.** Saying that in a design review is more valuable than being able
      to implement CH.
    - **Regardless: cache.** Route requests are enormously skewed — the same city pairs, the same
      commutes. An LRU on `(origin_cell, dest_cell, time_bucket)` with coordinates snapped to a
      ~100 m grid will have a high hit rate. **You built this cache in week 13 module 3.**

    **What breaks first at 5,000 req/s:** not the algorithm — memory bandwidth and the fact that a
    20-million-node graph as Python objects is tens of gigabytes. The graph must be flat arrays
    (CSR) in a compiled language or a memory-mapped file. **In Python, at 80 ns per edge (module 3),
    5,000 queries/second each touching 10,000 edges is 4 billion edge-visits per second. That is not
    happening.** The honest answer includes "this service is not written in Python", and knowing
    that before you start is worth more than any optimisation.
    </Accordion>

    ## A* versus Dijkstra, measured — and why the win is smaller than you expect

    A 1,200 × 1,200 grid (1,440,000 cells) with 20% of cells randomly blocked, routing from one
    corner to the opposite corner, 4-directional movement, unit edge cost, Manhattan heuristic:

    | Algorithm | Path cost | Nodes expanded | Wall time |
    | --- | --- | --- | --- |
    | Dijkstra (`h = 0`) | 2,398 | 1,177,499 | 1.04 s |
    | A* with Manhattan `h` | 2,398 | **792,399** | **0.87 s** |
    | | *identical* | **1.49× fewer** | **1.19× faster** |

    <Info>
    Method: CPython 3.12.9, M3 Pro, single run per algorithm (the grid is deterministic given the
    seed), both verified to return the same optimal cost of 2,398. Reproduce with `extra_dsa.py w14m4`.
    </Info>

    **1.49×, not the 10× the textbooks imply.** This is the honest number and the reasons are
    instructive:

    - **The goal is in the far corner, so almost the whole grid lies "between" start and goal in
      Manhattan terms.** A* prunes the region *beyond* the goal and the strips outside the bounding
      rectangle — but for corner-to-corner routing that is a minority of the grid. Route to a nearby
      target instead and the ratio becomes enormous; route to the far corner and it is small. **The
      benefit depends on the geometry of the query, not on the algorithm.**
    - **20% obstacles weaken the heuristic.** Manhattan distance ignores walls, so in a cluttered
      region the true remaining cost substantially exceeds `h`, and a heuristic far below the truth
      provides little guidance. The gap between `h` and reality is exactly the amount of guidance
      you lose.
    - **Ties are everywhere.** With unit costs, huge numbers of nodes share the same `f`. The
      tie-breaking rule then determines expansion order, and the default (whatever the heap returns)
      is not the good one. **Breaking ties toward larger `g`** — preferring nodes deeper along a path
      — typically cuts expansions substantially, because it drives the search to commit to a route
      rather than fanning out across an entire equal-`f` plateau.

    **The time ratio (1.19×) is smaller than the expansion ratio (1.49×)** because A* does more work
    per expansion: computing `h(nb)` for every neighbour, and pushing 3-tuples instead of 2-tuples.
    On this grid `h` is two subtractions and two `abs` calls — cheap — and it still eats 20% of the
    win. **With an expensive heuristic (a landmark lookup, a learned model) the expansion reduction
    must be large to pay for itself**, and that trade is the actual engineering question.

    ### Getting to 3×: what the `hard` track requires

    The lab's `hard` track asks for a ≥3× expansion reduction. Plain Manhattan gives 1.49×, so it is
    genuinely not enough — which is the point of the exercise. Three routes to 3×:

    1. **Weighted A\*, `f = g + w·h` with `w ≈ 1.5–2.0`.** Guarantees a path at most `w`× optimal.
       On this grid `w = 2` typically expands under a third as many nodes. **It is the easiest win
       and it costs optimality**, so the write-up must state the measured suboptimality, not just
       the speedup.
    2. **Tie-breaking toward larger `g`.** Push `(f, -g, node)` so that among equal `f`, deeper nodes
       pop first. Costs nothing, keeps optimality, and on plateau-heavy grids the reduction is large.
    3. **A stronger admissible heuristic.** Precompute exact distances from a handful of landmark
       cells (ALT). The triangle inequality gives `h(n) = max over landmarks of abs(d(L, goal) − d(L, n))`, which is
       admissible and much tighter than Manhattan because it *knows about the obstacles*. This is the
       intellectually satisfying answer and it keeps optimality.

    **Combining 2 and 3 is the correct solution to the hard track**, because it reaches the target
    without giving up optimality. Option 1 reaches it by changing the problem, which is a legitimate
    engineering choice but must be labelled as one.

    ## Consistency versus admissibility

    - **Admissible:** `h(n) ≤ true_cost(n → goal)` for all `n`.
    - **Consistent (monotone):** `h(u) ≤ cost(u,v) + h(v)` for every edge `(u,v)`, and `h(goal) = 0`.

    Consistency implies admissibility, not the reverse. The practical difference:

    - **With a consistent heuristic**, `f` is non-decreasing along any path, a node's `g` is final
      when popped, and **A\* never re-expands a node.** You can use a closed set and skip anything in
      it.
    - **With a merely admissible heuristic**, A* can find a better route to an already-closed node
      and must re-open it. Skipping closed nodes then produces suboptimal results. This is
      **Algorithm A\*\*** and it can, pathologically, re-expand exponentially many times.

    Every standard geometric heuristic — Manhattan, Euclidean, Chebyshev, ALT — is consistent, which
    is why nearly every A* implementation uses a closed set and is nonetheless correct. **If you
    invent a heuristic, check consistency, not just admissibility**, because the closed set in the
    code you copied assumes it.

    ## The beam-search connection

    In week 25 you will generate text with beam search:

    ```
    keep the B best partial sequences
    for each step:
        expand every beam by every plausible next token
        score each candidate: sum of log-probabilities so far
        keep the B highest-scoring candidates
    ```

    Map it onto A*:

    | A* | Beam search |
    | --- | --- |
    | `g(n)` — cost from start, known | sum of log-probs so far, known |
    | `h(n)` — estimated cost to goal | **nothing** (or a length-normalisation term) |
    | priority queue, unbounded | priority queue, **bounded to B** |
    | admissible `h` ⟹ optimal path | **no optimality guarantee at all** |
    | goal test | end-of-sequence token |

    Two differences and both matter enormously.

    **1. Beam search has no admissible heuristic**, because there is no way to lower-bound "how much
    log-probability remains" for an unfinished sentence. So it is **greedy best-first search**, not
    A*, and it has no optimality guarantee. It routinely returns a sequence that is not the highest
    total probability, and the failure is invisible.

    **2. Beam search bounds the frontier to `B`**, discarding everything else. A* keeps all
    candidates. So beam search can permanently discard the prefix of the best sequence at step 3 —
    the prefix that looks bad early and pays off later. **This is exactly the failure mode of
    weighted A\* with a large `w`, and it is why beam search with a large beam sometimes produces
    *worse* text than a small beam** (the "beam search curse"): a larger beam finds higher-probability
    sequences, and higher-probability sequences in a length-biased model are short and generic.

    **The transfer:** when you meet a decoding strategy in week 25, ask the two A* questions. *What
    is the estimate of remaining cost, and is it a lower bound?* (For beam search: there is none.)
    *What is being discarded, and can the discarded thing have been optimal?* (For beam search: yes,
    always.) Those two questions explain most of beam search's observed behaviour, and you now have
    them because you learned A* properly.

    ## Production failure modes

    | Failure mode | Signature | Detection |
    | --- | --- | --- |
    | Inadmissible heuristic | routes valid but consistently 5–20% worse; no errors | shadow-compare 0.1% of queries against Dijkstra; assert the ratio is 1.0 |
    | Unit mismatch in `h` | same as above, worse; e.g. distance heuristic on a time cost | assert `h(n) <= true(n)` on a sample; check units explicitly |
    | Dijkstra on negative weights | plausible wrong answer; only on inputs with negative edges | assert all weights are non-negative at graph construction, and fail loudly |
    | Negative cycle, unnoticed | Bellman-Ford loops or returns garbage | run the extra Vth round and report the affected nodes |
    | Heap without a tiebreaker | intermittent `TypeError` when two nodes share a cost | `(f, -g, node_id)` — the id also gives deterministic output |
    | Stale heap entries unbounded | memory grows with edge relaxations, not with V | lazy deletion is correct; monitor `len(heap)` against V |
    | Float accumulation in path costs | tiny inconsistencies; `dist[u] + w < dist[v]` flips on equal paths | use integers (metres, milliseconds) where possible; otherwise an epsilon |
    | Closed set with an inconsistent heuristic | suboptimal paths that the tests do not catch | verify consistency, not just admissibility |
    | Unreachable target | `KeyError` walking the predecessor chain | return `(inf, [])`; test it |

    ## Frontier and research pointers

    - **Dijkstra (1959), "A note on two problems in connexion with graphs."** *Numerische Mathematik*
      1. — **Takeaway:** two and a half pages; the original has no priority queue at all, and reading
      it shows how much of the modern algorithm is the data structure rather than the idea.
    - **Hart, Nilsson & Raphael (1968), "A Formal Basis for the Heuristic Determination of Minimum
      Cost Paths."** *IEEE Trans. SSC* 4(2). — **Takeaway:** A* is optimal *and* optimally efficient
      — no algorithm with the same heuristic information can expand fewer nodes — and admissibility
      is exactly the condition; the 1972 correction that distinguishes consistency from admissibility
      is essential reading alongside it.
    - **Pohl (1970), "Heuristic search viewed as path finding in a graph."** *Artificial Intelligence*
      1(3). — **Takeaway:** weighted A* with `f = g + w·h` returns a path at most `w`× optimal, which
      is the cleanest speed-for-quality dial in search and reappears everywhere, including decoding.
    - **Geisberger, Sanders, Schultes & Delling (2008), "Contraction Hierarchies."** WEA. —
      **Takeaway:** contracting nodes in importance order and adding shortcut edges turns
      continental-scale routing into microsecond queries after minutes of preprocessing; this is what
      every production router does.
    - **Goldberg & Harrelson (2005), "Computing the Shortest Path: A* Search Meets Graph Theory."**
      SODA. — **Takeaway:** the ALT heuristic — landmarks plus the triangle inequality — gives a much
      tighter admissible bound than straight-line distance, with modest preprocessing; this is the
      practical route to a large expansion reduction while keeping optimality.
    - **Freitag & Al-Onaizan (2017), "Beam Search Strategies for Neural Machine Translation."**
      ACL Workshop on Neural MT. — **Takeaway:** larger beams often produce *worse* output, because
      beam search is best-first search with no admissible heuristic and a length bias; read it right
      before week 25 and the A* framing above will make it obvious rather than surprising.

    ## Stretch challenge

    **Build a route planner on real OSM data and characterise the heuristic's quality, not just its
    speed.**

    Take an OpenStreetMap extract (Geofabrik publishes free regional extracts; pick a city, roughly
    50–200 MB of `.osm.pbf`), build the road graph, and implement Dijkstra, A*, weighted A*, ALT, and
    bidirectional search behind one interface.

    Then measure the thing nobody measures: **how good is the heuristic, as a function of where you
    are in the graph?**

    1. For a sample of 1,000 nodes, compute the true distance to a fixed goal with Dijkstra, and plot
       `h(n) / true(n)` — the **heuristic ratio** — against `true(n)`. A perfect heuristic is 1.0. A
       useless one is 0. **This single plot tells you more about your search performance than any
       benchmark.**
    2. Find where the ratio is worst. It will be near water, mountains, and one-way systems — places
       where the straight line badly underestimates road distance. **This is where A* degenerates to
       Dijkstra**, and it explains region-specific latency outliers that otherwise look like noise.
    3. Compare against ALT with 4, 8, 16 and 32 landmarks. Plot the ratio improvement and the
       preprocessing cost. Find the knee.

    The open questions:

    - **How should landmarks be chosen?** Random is the baseline; farthest-point sampling and
       "avoid" (Goldberg's method) are better. Implement two and measure the ratio improvement per
       landmark. Is 16 well-chosen landmarks better than 64 random ones?
    - **Is the ratio plot predictive?** Fit a model from heuristic ratio to expansion count and see
       whether you can predict query latency from the ratio alone, without running the search. If
       you can, you have a way to route hard queries to a different algorithm.
    - **What does weighted A\* actually cost you?** Sweep `w` from 1.0 to 3.0 and plot both
       expansions and *measured* suboptimality. The theoretical bound is `w`× — how close is reality?
       In routing it is usually far better than the bound, and quantifying that gap tells you how
       aggressive you can safely be.
    - **Does bidirectional search compose with A\*?** Bidirectional A* is genuinely subtle — the
       naive termination condition returns suboptimal paths. Implement it, find the bug by comparing
       against Dijkstra, then fix it. **This is the single best exercise in the module** because the
       bug is real, common, and invisible without a ground-truth comparison.

    The deliverable — a heuristic-quality map of a real city, with the regions where A* fails
    highlighted — is a striking portfolio artifact and it is not something you will find already done.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Shortest path is wrong on some inputs | Dijkstra used on a graph with negative edges | Bellman-Ford; and assert non-negativity at graph construction |
| Routes are valid but consistently 10–20% worse | Inadmissible heuristic — usually a unit mismatch or an average where a maximum was needed | Divide by the *maximum* speed; assert `h(n) <= true(n)` on a sample |
| A* returns suboptimal paths with a "correct" heuristic | Closed set used with a merely admissible (not consistent) heuristic | Verify consistency `h(u) <= cost(u,v) + h(v)`, or allow re-opening nodes |
| `TypeError` comparing nodes in the heap | Two nodes with equal `f`, falling through to compare the payload | `(f, -g, node_id)` — also gives deterministic output and better tie-breaking |
| A* barely beats Dijkstra | Weak heuristic, or every node lies between start and goal | Measure the heuristic ratio `h/true`; consider ALT landmarks or tie-breaking toward larger `g` |
| Heap grows far beyond V | Stale entries from lazy deletion, which is correct | Expected; monitor `len(heap)` and rebuild if it exceeds a few times V |
| `KeyError` when reconstructing a path | Goal unreachable, and the predecessor chain has no entry | Return `(inf, [])` and test the unreachable case |
| Bellman-Ford returns garbage | A negative cycle exists and was not detected | Run the extra Vth relaxation round; report the affected nodes |
| MST used where a shortest-path tree was meant | They minimise different things | MST minimises total edge weight; SPT minimises distance from one source |
| Costs drift over long paths | Float accumulation in `dist[u] + w` | Use integers (metres, milliseconds) where possible |

- [`networkx` shortest paths](https://networkx.org/documentation/stable/reference/algorithms/shortest_paths.html) (pin `networkx==3.4.2`) — read this for `astar_path`'s explicit note that the heuristic must be admissible, and for `negative_edge_cycle` as a ready-made detector.
- [`scipy.sparse.csgraph.dijkstra`](https://docs.scipy.org/doc/scipy-1.14.1/reference/generated/scipy.sparse.csgraph.dijkstra.html) (SciPy 1.14.1) — read this for the CSR input format and the `limit` parameter; it is 50–100× faster than a Python implementation and already installed.
- [OSRM routing engine docs](https://project-osrm.org/docs/v5.24.0/api/) — read the contraction-hierarchies section for what a production router actually does, and note that the preprocessing step is the entire product.
- [`pyrosm` 0.6.2](https://pyrosm.readthedocs.io/) — read this for extracting a drivable road network from a `.osm.pbf` in a few lines; it is the fastest path from "download an extract" to "have a graph".

**Papers**

- [Dijkstra (1959), *A note on two problems in connexion with graphs*, Numerische Mathematik 1, 269–271.](https://doi.org/10.1007/BF01386390) — **Takeaway:** the original is two and a half pages with no priority queue; how much of the modern algorithm is the data structure becomes obvious.
- [Hart, Nilsson & Raphael (1968), *A Formal Basis for the Heuristic Determination of Minimum Cost Paths*, IEEE Trans. SSC 4(2), 100–107.](https://doi.org/10.1109/TSSC.1968.300136) — **Takeaway:** A* is optimally efficient among algorithms with the same heuristic, and admissibility is precisely the condition for optimality; read the 1972 correction on consistency alongside it.
- [Pohl (1970), *Heuristic search viewed as path finding in a graph*, Artificial Intelligence 1(3).](https://doi.org/10.1016/0004-3702(70)90007-X) — **Takeaway:** `f = g + w·h` gives a path at most `w`× optimal — a tunable, bounded speed-for-quality trade that reappears in decoding, planning and scheduling.
- [Geisberger, Sanders, Schultes & Delling (2008), *Contraction Hierarchies: Faster and Simpler Hierarchical Routing in Road Networks*, WEA.](https://doi.org/10.1007/978-3-540-68552-4_24) — **Takeaway:** preprocessing that adds shortcuts in node-importance order converts continental routing from seconds to microseconds; the asymmetry between static graphs and constant queries is what makes it possible.
- Goldberg & Harrelson (2005), *Computing the Shortest Path: A\* Search Meets Graph Theory*, SODA. — **Takeaway:** landmarks plus the triangle inequality give a far tighter admissible heuristic than Euclidean distance, and landmark *selection* matters more than landmark count.
- [Freitag & Al-Onaizan (2017), *Beam Search Strategies for Neural Machine Translation*, ACL WNMT.](https://aclanthology.org/W17-3207/) — **Takeaway:** beam search is best-first search without an admissible heuristic and with a bounded frontier, which is why larger beams can produce worse output — read this just before week 25.

**Go deeper**

- [Amit Patel, *Introduction to A\** (Red Blob Games)](https://www.redblobgames.com/pathfinding/a-star/introduction.html) — the best interactive explanation of A* in existence. Read the sections on heuristics and tie-breaking specifically; the tie-breaking page alone will improve your implementation more than any other single change.
- [Sedgewick & Wayne, *Algorithms* 4th ed., **Section 4.4 (Shortest Paths)**](https://algs4.cs.princeton.edu/home/) — the cleanest presentation of relaxation as the unifying primitive across Dijkstra, Bellman-Ford and topological-order shortest paths.
- Russell & Norvig, *Artificial Intelligence: A Modern Approach* 4th ed., **Chapter 3** — read this for the framing of search as a general problem-solving method; it is where the A*-to-beam-search connection becomes explicit, and it is the chapter that makes week 25 make sense.
