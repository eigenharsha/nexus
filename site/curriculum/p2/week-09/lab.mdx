## The ticket

> **NEX-901 · Hardware · P1**
>
> We are bringing up a 16-bit teaching CPU on an FPGA next quarter and the synthesis team needs a
> reference implementation of the datapath they can diff against. Deliver the combinational and
> sequential blocks — gates, adders, ALU, register file, RAM16K, PC — with (a) all official test
> scripts green, (b) a gate-count and critical-path-depth report per block, and (c) a written
> answer to the question the architecture lead keeps asking: *"at what clock frequency does this
> design stop working, and which block is responsible?"*
>
> Bonus, and the reason this ticket is P1 rather than P2: the software team claims their matrix
> code is "memory bound" but has no measurement. Produce one.

<Warning>
Read that ticket again. It does not ask for working chips — it asks for working chips **plus a
number**. A submission with all tests green and no area/depth report is a 1/3 on this lab, not a 3/3.
</Warning>

## Time box

| Track | Honest estimate |
|---|---|
| `basic` | 3–4 hours |
| `standard` | 8–10 hours |
| `hard` | +5–6 hours on top of `standard` |

If `standard` is taking you more than 12 hours, the usual cause is building each 16-bit chip flat
instead of composing it from the 1-bit version. Stop and refactor; it will be faster.

<Tabs>

<Tab title="basic">

**Gates and adders, with the test scripts provided.**

Build, from NAND only:

1. `Not`, `And`, `Or`, `Xor`, `Mux`, `DMux`
2. `Not16`, `And16`, `Or16`, `Mux16`
3. `Or8Way`, `Mux4Way16`, `Mux8Way16`, `DMux4Way`, `DMux8Way`
4. `HalfAdder`, `FullAdder`, `Add16`, `Inc16`

**Acceptance criteria**

- Every chip passes its supplied `.tst` script with zero comparison failures.
- Your Python simulator prints the gate count and depth for each of the six primitive gates, and the
  numbers match: NOT 1/1, AND 2/2, OR 3/2, XOR 4/3, MUX 4/3, DMUX 5/3 (gates/depth).
- `Inc16` costs strictly fewer gates than `Add16`. If it does not, you instantiated a full adder with
  a constant operand — fix it.

<Info>
About 60% of the code is written for you in `starter/`. TODOs are marked with `// TODO(you)`.
Answers are in `solution/`, but the tests will tell you the truth faster than the answers will.
</Info>

</Tab>

<Tab title="standard">

**The full datapath, plus the report.**

Everything in `basic`, plus:

1. `ALU` — all six control bits, `out`, `zr`, `ng`.
2. `Bit`, `Register`, `RAM8`, `RAM64`, `RAM512`, `RAM4K`, `RAM16K`, `PC`.
3. A Python reference model of the ALU and a randomised verification harness: 18 documented
   operations × 2,000 random 16-bit operand pairs, checking `out`, `zr` and `ng` on every call.
4. `REPORT.md` containing the gate-count and depth table for every block, the resulting `f_max`
   estimate at `t_gate = 10 ps`, and a named answer to "which block is the critical path".

**Acceptance criteria**

- All official test scripts green.
- Verification harness prints `0 failures`.
- `REPORT.md` states an `f_max` and names the responsible block. (It will be the adder inside the
  ALU. You must show the arithmetic, not just assert it.)
- Total ALU gate count under 1,100 NANDs with a ripple adder.

<Info>Spec and tests only. You write the implementation. This is the portfolio artefact for Week 9.</Info>

</Tab>

<Tab title="hard">

**A constraint the standard solution fails.**

1. **Replace the ripple adder with a parallel-prefix adder** (Kogge-Stone or Brent-Kung) inside the
   ALU. Constraint: **ALU critical-path depth must be under 40 NAND levels.** The `standard`
   solution measures around 81 and cannot meet this by tuning.
2. **Written critical-path analysis:** which path is longest before and after, why, and what the new
   area cost is. Include the depth-versus-width table for both adders at n = 4, 8, 16, 32, 64.
3. **The C locality benchmark:** measure row-major versus column-major traversal at
   N = 256, 512, 1024, 2048, 4096, report the slowdown at each size, and explain the *shape* of the
   curve using your machine's actual cache sizes and line size — not just "cache misses".
4. **The negative control:** run the same benchmark compiled without `-ffast-math` and explain why
   the gap collapses. A submission that reports the 60× without noticing this gets 2/3 on
   explanation, not 3/3.

<Warning>
The depth constraint is the real content here. You cannot reach it by micro-optimising gates —
you have to change the algorithm, which is the whole point.
</Warning>

</Tab>

</Tabs>

## Verify yourself

```bash
cd labs/p2/week-09
make verify        # green on a correct solution, red on the starter

# what it runs:
#   1. the official Nand2Tetris .tst comparison scripts for every chip
#   2. pytest tests/  -- the ALU reference-model harness (18 ops x 2000 pairs)
#   3. python tools/report.py  -- regenerates the area/depth table and diffs it
#                                 against the numbers you committed in REPORT.md
#   4. (hard track) asserts ALU depth < 40 and runs the C benchmark
```

`make verify` fails if `REPORT.md` is missing or if its numbers do not match a fresh run. That is
deliberate: a stale performance report is worse than none.

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
A public repo containing every HDL file, the test output, `REPORT.md` with your measured area/depth
table, the benchmark data, and a short explainer post titled "How a computer adds" aimed at someone
who has never seen a logic gate.
</Card>

The explainer post is not filler. Writing "how a computer adds" for a non-expert is the fastest way
to discover which parts you only think you understand, and it is the artefact that will actually get
read when you link this from a CV. Target 800–1,200 words, one diagram you drew yourself, and one
measured number.

## Start here — your first 30 minutes

The requirements above are the *finished* picture. Do not try to hold all of it at once. Do these in
order; each step ends somewhere you can stop and still be making progress.

<Steps>
<Step title="Run the starter and expect RED (5 min)">
```bash
cd labs/p2/week-09
make verify TRACK=basic
```
A red result is success here — it means the harness runs and the tests can see your code. If you get
something that is *not* a test failure (a missing command, an import error), fix that first; it is an
environment problem, not a lab problem.
</Step>

<Step title="Read one test before writing any code (5 min)">
The tests are the real specification — everything written above is prose describing them. Where the
prose and a test disagree, **the test wins**. Open the first one and read it properly.
</Step>

<Step title="Make ONE test pass (15 min)">
Implement the smallest thing the first failing test needs. Run `make verify` again. One more test
passing is the whole goal of your first half hour.

That is the loop for the entire lab: one test, one function, run, repeat. Do not write five functions
and then run for the first time — when it fails you will not know which one broke it.
</Step>

<Step title="Finish the basic track">
Work the `TODO`s in the order they appear. They are in dependency order, not alphabetical.
</Step>

<Step title="Only then read the standard requirements">
With `basic` green you have something that works. `standard` extends it; it does not replace it.
</Step>

<Step title="Ship it">
Push to a public repo with the README. That artifact is what you link from a CV — it outlasts the grade.
</Step>
</Steps>

<Tip>
**Are you on track?** After 30 minutes you should have: a red run, one test read properly, and one
test passing. If you have read for 30 minutes and run nothing, you are reading too much — go run the
starter.
</Tip>

## Stuck? Open these in order

Each reveals a little more than the last. Try the level above before opening the next — a hint you
did not need costs you nothing, but an answer taken too early costs you the lesson.

<AccordionGroup>
<Accordion title="Nudge — I don't know where to start" icon="lightbulb">
Find the **first** failing test and implement only what that one test needs. Ignore the rest of the
lab until it is green. If you cannot tell which test fails first, run
`make verify TRACK=basic` and read the top of the output, not the bottom.
</Accordion>

<Accordion title="Hint — my chip passes some test vectors and fails others" icon="lightbulb">
Almost always an unhandled input combination rather than a wiring error. The failing vectors will share a pattern — read them as a group, not one at a time.

**What to do instead:** Write out the full truth table for the failing cases and compare against what your chip produces. The difference names the missing term.
</Accordion>

<Accordion title="Hint — my ALU works for addition but the zr or ng flag is wrong" icon="lightbulb">
The flags are computed from the *output*, after all the control bits have been applied — including negation. Computing them from an intermediate value gives right answers with wrong flags.

**What to do instead:** Compute `zr` and `ng` from the final `out` bus only. `ng` is simply the most significant bit under two's complement.
</Accordion>

<Accordion title="I have a real attempt that fails — show me the full solution" icon="lock">
Open the [reference solution](/solutions/p2/week-09/lab).

Use it properly: read only far enough to get unstuck, then close it and return to your own code.
Afterwards, diff your version against it — the differences are the lesson, and yours is not
automatically the worse one.

If you have not yet written code that fails, do not open it. Reading a solution before struggling
with the problem feels exactly like learning, and is the most reliable way to finish this course
having learned nothing.
</Accordion>
</AccordionGroup>

## Rubric

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Correctness | tests fail | gates and adders pass | ALU and memory pass too | passes plus randomised verification with 0 failures over 36,000 operand pairs |
| Code quality | works | readable | composed hierarchically, no copy-pasted 16-bit blocks | a reviewer would approve unchanged; every chip built from the previous one |
| Performance | untested | gate counts reported | depth reported too, and `f_max` computed | prefix adder meets the &lt;40-level constraint, with the area cost stated |
| Explanation | none | a README | `REPORT.md` with the critical path named | the locality curve explained by cache sizes, including why it collapses without `-ffast-math` |

**Aim for 3/3 on Explanation before you chase 3/3 on Performance.** The report is what makes this
work legible to anyone else, and it is the part interviewers actually engage with.

## Common ways submissions lose points

1. Gate counts reported, depth omitted. Depth is the number that matters.
2. `Mux16` written as sixteen copy-pasted lines of gates rather than sixteen `Mux` instantiations.
3. The ALU verified only against the supplied `.tst` file, which uses a small fixed set of inputs.
4. `REPORT.md` quoting the numbers from this course rather than the ones the student measured.
5. The benchmark run once, at one size, with no curve — so the cache-capacity story cannot be told.
