## The ticket

> **NEX-1002 · Platform · P1**
>
> Our vendor's chat SDK is being discontinued in 90 days and their protocol is undocumented. We need
> a replacement we own. Build a chat server on raw TCP sockets — no web framework, no message broker
> — supporting multiple rooms, nicknames, join/leave notifications and broadcast, with a documented
> wire protocol other teams can implement clients against.
>
> Hard requirements from the incident review of the current system:
> 1. It must not lose or merge messages under load. The current one does, and nobody can explain why.
> 2. It must detect and clean up clients that vanish without disconnecting. We currently accumulate
>    dead sessions until a restart.
> 3. One slow client must not be able to grow server memory without bound. That is what caused the
>    May outage.
>
> Deliver: the server, `PROTOCOL.md`, a packet capture proving framing works, and a benchmark report.

<Warning>
Requirement 1 is the whole lab. It is Module 2's byte-stream demonstration, wearing a suit. If your
answer does not involve explicit framing, you have not fixed it — you have made it less frequent.
</Warning>

<Tabs>

<Tab title="basic">

**Echo server plus a single client, done properly.**

1. A TCP echo server that handles one client at a time.
2. `recv_exactly(sock, n)` with a test proving it handles a peer that closes mid-message.
3. Length-prefixed framing: `send_msg` / `recv_msg` with a 4-byte big-endian length and a bounded
   maximum.
4. A demonstration script reproducing Module 2's result: 1,000 small sends, counted `recv()` calls,
   with and without `TCP_NODELAY`.

**Acceptance criteria**

- `recv_exactly` returns `None` on a clean close and never returns a short buffer.
- The framing round-trips 10,000 random messages of length 0 to 100,000 bytes.
- A declared length above the maximum is rejected **before** any allocation.
- Your sends-to-recvs ratio is reported. (Reference: 413 and 67 for 1,000 sends.)

<Info>
About 60% is written for you in `starter/`. The `TODO(you)` markers are on `recv_exactly`, the
length bound, and the framing round-trip test.
</Info>

</Tab>

<Tab title="standard">

**The multi-room chat server. This is the portfolio artefact.**

1. **Server:** concurrent clients, rooms, nicknames, `JOIN`/`LEAVE` broadcast, `MSG` fan-out to a
   room, graceful disconnect handling, and per-connection timeouts.
2. **Protocol:** length-prefixed framing with a versioned, type-tagged message format. Heartbeats
   (`PING`/`PONG`) with dead-peer detection. Error codes for every rejectable command.
3. **`PROTOCOL.md`:** the message table (direction, fields, required/optional), the connection state
   machine, the framing spec with byte offsets, the version-negotiation rule, the heartbeat
   parameters, and the complete error-code list. Someone on another team must be able to write a
   client from this document alone, without reading your code.
4. **A packet capture** (`.pcap`) showing your framing working, with an annotation identifying the
   4-byte length prefix of at least three consecutive messages by byte offset.
5. **A client** that reconnects with exponential backoff and full jitter.

**Acceptance criteria**

- 50 concurrent clients across 5 rooms exchange 10,000 messages with zero loss, zero duplication and
  zero merging.
- A client that stops responding to `PING` is disconnected within 3× the heartbeat interval.
- Killing a client process (`SIGKILL`, no clean close) does not leak a session or a file descriptor.
- `PROTOCOL.md` is complete enough that a peer reviewer writes a working client without asking you a
  question. **Actually test this** — swap documents with someone.

<Info>Spec and tests only. This is the Phase 2 project you link from a CV.</Info>

</Tab>

<Tab title="hard">

**1,000 concurrent clients, with the constraints that break the standard solution.**

1. **Rewrite on an event loop** (`selectors` or `asyncio`) and reach **1,000 concurrent
   connections**. The thread-per-connection `standard` solution will run out of memory or scheduler
   headroom before it satisfies the latency budget.
2. **Back-pressure.** A deliberately slow client — one that connects, subscribes to a busy room and
   never reads — must not grow server memory without bound. Bound the per-connection outbound queue,
   pick a drop-or-disconnect policy, and *document the choice*.
3. **Report:** memory per connection, p50 and p99 message latency at 100 / 500 / 1,000 connections,
   and throughput. Compare against your `standard` implementation on the same load.
4. **Survive loss.** Run the client and server across a `tc netem` link with 2% loss and 100 ms
   latency (Linux, or two containers). Messages must still arrive intact and in order; report the
   throughput drop and check it against the Mathis bound (~1.0 Mbit/s per flow at 2% and 100 ms).

**Acceptance criteria**

- p99 message latency under 100 ms at 1,000 connections on a healthy link.
- With one slow client attached and 10,000 messages broadcast, server RSS growth stays bounded and
  the drop policy is visible in the logs.
- The report explains the *shape* of the latency curve as connections increase, not just its values.

<Warning>
The constraint the standard solution fails is memory under back-pressure, not raw connection count.
A threaded server can reach 1,000 connections; it cannot bound its memory when one of them stops
reading, because each thread blocks in `sendall` and the queue is the kernel's.
</Warning>

</Tab>

</Tabs>

## Verify yourself

```bash
cd labs/p2/week-10
make verify        # green on a correct solution, red on the starter

# what it runs:
#   1. pytest tests/test_framing.py     -- round-trip, boundary, oversize-rejection
#   2. pytest tests/test_protocol.py    -- version negotiation, error codes, state machine
#   3. pytest tests/test_chaos.py       -- SIGKILL a client, half-close, slow reader,
#                                          header-then-disconnect, 4 GB declared length
#   4. python tools/loadtest.py --conns 50 --messages 10000  -- zero loss/dup/merge assertion
#   5. tools/check_protocol_md.py       -- fails if PROTOCOL.md lacks any required section
#   6. (hard) tools/bench.py            -- memory/latency table, regenerated and diffed
```

`make verify` fails if `PROTOCOL.md` is missing a required section. The required sections are:
message table, state machine, framing spec, versioning, heartbeats, error codes. That check exists
because the document is the deliverable most likely to be skipped and the one most likely to be read.

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
A public repo with the server, the client, `PROTOCOL.md`, the `.pcap` capture with its annotation,
and `BENCHMARK.md` with your measured numbers. Plus a 60-second terminal recording (asciinema) of
three clients chatting across two rooms.
</Card>

The asciinema recording is worth the ten minutes it takes. A chat server is one of the few systems
projects that is *visually* obvious, and a recording embedded in the README converts a reader in
five seconds where a paragraph does not.

## Rubric

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Correctness | tests fail | echo and framing work | rooms, broadcast, heartbeats, clean disconnects | survives the full chaos suite: SIGKILL, half-close, slow reader, oversize length, 1,000 reconnects |
| Code quality | works | readable | framing, protocol and transport are separate modules | a reviewer would approve unchanged; no exception can escape the accept loop |
| Performance | untested | works with 5 clients | 50 clients, zero loss, latency reported | 1,000 connections with bounded memory under back-pressure and a p99 under 100 ms |
| Explanation | none | a README | `PROTOCOL.md` complete | a peer wrote a working client from `PROTOCOL.md` alone, and the benchmark report explains the curve's shape |

**The `Explanation` column is where this lab is won.** Two submissions with identical code are
distinguished entirely by whether someone else could use the protocol.

## Common ways submissions lose points

1. **Framing "works" because messages are small.** Test with messages that straddle the read buffer —
   at least one of 100,000 bytes — and with several messages arriving in one `recv`.
2. **No heartbeat, or a heartbeat with no timeout.** Sending `PING` and never acting on a missing
   `PONG` is decoration.
3. **`PROTOCOL.md` describes the happy path only.** Every command needs its error cases and the
   ordering constraints. "Invalid input is rejected" is not a specification.
4. **Benchmarks with one data point.** The interesting content is how latency and memory change from
   100 to 1,000 connections, not their value at one point.
5. **The slow-client test not actually run.** Write the adversarial client, attach it, and show the
   memory graph flat. Asserting that back-pressure exists is not the same as demonstrating it.
6. **An exception in one connection killing the server.** `ECONNRESET` and `EPIPE` are normal
   traffic, not bugs.
