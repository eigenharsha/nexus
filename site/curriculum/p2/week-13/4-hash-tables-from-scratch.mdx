    ## The idea in one paragraph

    You have a shelf of numbered boxes and a pile of labelled items. You want to find any item
    instantly. A **hash function** takes the label and turns it into a box number — the same label
    always gives the same number, and different labels are spread evenly across the boxes. To store
    an item, compute its box number and put it there. To find it, compute the box number again and
    look. **You never search.** The catch is that two different labels can produce the same box
    number — that is a **collision**, it is unavoidable, and everything difficult about hash tables
    is about handling it well.

    ### The analogy

    A cloakroom at a theatre with 100 numbered hooks.

    - **Without hashing.** You hang coats wherever there is space and write nothing down. Finding
      a coat means checking every hook. 100 coats, up to 100 checks.
    - **With hashing.** The rule is: hook number = (sum of the letters in your surname) mod 100.
      You hand over "Kapoor", the attendant computes 613 mod 100 = 13, walks to hook 13, done. One
      step, regardless of how many coats are hanging.
    - **The collision.** "Kapoor" and "Roopak" have the same letters, so both map to hook 13. Two
      coats, one hook. You need a plan. Either hang both on hook 13 and check the names (that is
      **chaining**), or put the second one on hook 14 and remember to look there too (that is
      **open addressing**).

    ### Every term, defined

    - **Hash function** — turns a key into an integer. Must be *deterministic* (same key, same
      number, always) and should spread keys evenly across the output range.
    - **Hash code** — the integer a hash function returns. In Python, `hash("abc")`. It can be
      negative and it can be enormous.
    - **Bucket / slot** — one position in the table's underlying array.
    - **Index** — the bucket a key maps to: `hash(key) % capacity`, or `hash(key) & (capacity - 1)`
      when capacity is a power of two (which is faster and is what real tables do).
    - **Collision** — two different keys mapping to the same bucket.
    - **Separate chaining** — each bucket holds a small list of every key that landed there.
    - **Open addressing** — every key lives directly in a bucket; on a collision you *probe* for
      another free bucket by a fixed rule.
    - **Linear probing** — the simplest probe rule: try the next bucket, then the next.
    - **Load factor (α)** — `entries / capacity`. The single most important number about a hash
      table. At α = 0.75, three quarters of the slots are used.
    - **Resize / rehash** — allocating a bigger array and re-inserting every key. Required when
      the load factor gets too high.
    - **Tombstone** — a marker left where a key was deleted from an open-addressed table, meaning
      "empty, but keep probing past me".

    ### Why collisions are guaranteed

    You have 2⁶⁴ possible hash codes and, say, 1,000 buckets. Every key must land somewhere. The
    pigeonhole principle says that with more than 1,000 keys, at least two share a bucket.

    Worse than that, collisions arrive far earlier than intuition suggests. With 1,000 buckets and
    only **38 randomly-hashed keys**, there is a better-than-even chance that two collide. That is
    the birthday paradox: the chance of *no* collision after `k` keys in `m` buckets is
    `m!/((m−k)!·mᵏ)`, which crosses 50% at roughly `k ≈ 1.18·√m`.

    **Design for collisions from the first line of code.** They are not an edge case.

    ### The smallest working example

    ```python
    # tiny_hash.py — CPython 3.12
    class TinyMap:
        def __init__(self, capacity=8):
            self.capacity = capacity
            # Each bucket is a list of (key, value) pairs. Chaining.
            self.buckets = [[] for _ in range(capacity)]

        def _index(self, key):
            # hash() can be negative. Python's % on a negative left operand
            # returns a non-negative result, so this is safe.
            return hash(key) % self.capacity

        def put(self, key, value):
            bucket = self.buckets[self._index(key)]
            for i, (k, v) in enumerate(bucket):
                if k == key:
                    bucket[i] = (key, value)      # key already here: replace
                    return
            bucket.append((key, value))            # new key: append to the chain

        def get(self, key, default=None):
            for k, v in self.buckets[self._index(key)]:
                if k == key:
                    return v
            return default

        def show(self):
            for i, b in enumerate(self.buckets):
                if b:
                    print(f"  bucket {i}: {b}")


    m = TinyMap(capacity=4)
    for name, age in [("ann", 31), ("bob", 25), ("cy", 44), ("dee", 38), ("ed", 52)]:
        m.put(name, age)

    print(m.get("cy"))       # 44
    print(m.get("zoe"))      # None
    m.show()
    ```

    The exact bucket layout depends on Python's randomised string hashing, so **your output will
    differ from mine and that is correct** — see the box below. What will always be true is that
    five keys in four buckets means at least one bucket holds two or more.

    ### Line-by-line walkthrough

    - `self.buckets = [[] for _ in range(capacity)]` — a list of empty lists. Note it is *not*
      `[[]] * capacity`, which would create four references to the *same* list; that is a classic
      Python bug and here it would make every key appear in every bucket.
    - `hash(key) % self.capacity` — squeeze an arbitrary integer into a valid index. Python's
      modulo on a negative number returns a non-negative result (`-7 % 4 == 1`), so this is safe.
      In C or Java, `%` on a negative gives a negative and you must mask or take the absolute value.
    - `for i, (k, v) in enumerate(bucket)` — scanning the chain. **This is the part that is not
      O(1).** It is O(chain length), and the entire art of hash tables is keeping chains short.
    - `if k == key` — comparing the *keys*, not the hashes. Two different keys can hash the same,
      so equality is what actually decides. This is why a key must implement both `__hash__` and
      `__eq__`, and why they must agree: **equal objects must have equal hashes**, or lookups fail
      unpredictably.
    - `bucket.append(...)` — the new key goes on the end of the chain.

    <Warning>
    **Your output really will differ from the printout above, and from run to run.** Since Python
    3.3, `hash()` of a `str` or `bytes` includes a per-process random seed, so bucket assignments
    change every time you start Python. This is a security feature (Layer 3 explains what it
    prevents). It also means **never persist or transmit a Python `hash()` value** — it is not
    stable across processes. Use `hashlib.blake2b` or `zlib.crc32` if you need a stable hash.
    Integers are unaffected: `hash(n) == n` for small ints.
    </Warning>

    ### The load factor and why you resize

    With `n` keys in `m` buckets, the average chain length is `α = n/m`. Every lookup costs about
    `1 + α/2` comparisons on average.

    | Load factor α | Avg chain length | Avg comparisons per lookup |
    | --- | --- | --- |
    | 0.25 | 0.25 | ~1.1 |
    | 0.75 | 0.75 | ~1.4 |
    | 5.0 | 5.0 | ~3.5 |
    | 100 | 100 | ~51 |

    At α = 100 you have written a slow linked list with extra steps. So: **when α exceeds a
    threshold, double the capacity and re-insert everything.** By the amortization argument from
    module 1, doubling makes the total resize cost linear, so the amortized cost per insert stays
    O(1).

    ```python
    def put(self, key, value):
        # ... insert as before, incrementing self.n on a genuinely new key ...
        if self.n / self.capacity > 0.75:
            self._resize(self.capacity * 2)

    def _resize(self, new_capacity):
        old = self.buckets
        self.capacity = new_capacity
        self.buckets = [[] for _ in range(new_capacity)]
        self.n = 0
        for bucket in old:
            for k, v in bucket:
                self.put(k, v)      # re-insert: the index depends on capacity
    ```

    <Warning>
    **You cannot copy buckets across.** `hash(key) % 8` and `hash(key) % 16` give different
    answers for most keys. If you move bucket 3 of the old table to bucket 3 of the new one, most
    of those keys become permanently unfindable — and the bug is invisible until the table happens
    to resize, which in a small test it never does. **Write a test that inserts enough keys to
    force at least two resizes and then asserts every key is still retrievable.** It will fail the
    first time you write it, and that failure is the lesson.
    </Warning>

    ### Checkpoint — 5 questions before you continue

    <AccordionGroup>
      <Accordion title="1. Why must equal objects have equal hashes?">
        Because lookup computes the bucket from the hash and only then compares for equality. If
        `a == b` but `hash(a) != hash(b)`, then `a` and `b` land in different buckets and looking
        up `b` will never find the entry stored under `a`. Python enforces this by making any class
        that defines `__eq__` unhashable by default — you must define `__hash__` too, deliberately.
      </Accordion>
      <Accordion title="2. Why can't a Python list be a dict key?">
        Because lists are mutable. If you used a list as a key and then appended to it, its hash
        would change, and the entry would be sitting in the bucket for its *old* hash. It becomes
        unfindable — the dict still holds it, iteration still shows it, and lookup fails. Python
        prevents this by making `list` unhashable. Tuples of immutables are hashable for exactly
        the same reason.
      </Accordion>
      <Accordion title="3. What is the load factor and what happens when it gets too high?">
        `α = entries / capacity`. As α rises, chains get longer and lookups approach O(n). Real
        tables resize at α between 0.66 and 0.9 (CPython uses 2/3). For open addressing the effect
        is far more violent than for chaining — Layer 3 measures both.
      </Accordion>
      <Accordion title="4. Why is a resize O(n) but appending still amortized O(1)?">
        Same argument as the dynamic array in module 1: because capacity *doubles*, the resizes
        happen at 8, 16, 32, … and the total rehashing work across `n` inserts is `1 + 2 + 4 + …`,
        which stays below `2n`. Divide by `n` inserts and you get a constant. The individual insert that triggers the
        resize is genuinely O(n) — which matters for tail latency.
      </Accordion>
      <Accordion title="5. Why does Python randomise string hashing?">
        To prevent hash-collision denial of service. If an attacker knows your hash function, they
        can craft thousands of keys that all land in one bucket, turning every insert and lookup
        into a linear scan of that bucket. A few kilobytes of crafted POST data then consumes
        seconds of CPU. Layer 3 measures the effect at 4,649×. Randomising the seed per process
        means the attacker cannot predict which keys collide.
      </Accordion>
    </AccordionGroup>

    ## What makes a hash function good enough

    For a hash *table* (not for cryptography) you need three properties:

    1. **Deterministic** within a process. Same key, same code.
    2. **Uniform.** Keys spread evenly across buckets. Non-uniformity means long chains, which
       means the O(1) is a lie.
    3. **Avalanche.** Changing one bit of the input should change about half the output bits. Without
       it, similar keys (`user_1000`, `user_1001`) cluster into adjacent buckets, which is
       catastrophic for linear probing specifically.

    You do **not** need cryptographic strength. SHA-256 is a fine hash and a terrible choice for a
    hash table: it is roughly 100× slower than xxHash or wyhash and buys you nothing the table uses.

    | Hash | Speed (GB/s, order of magnitude) | Use it for |
    | --- | --- | --- |
    | `hash()` (CPython: SipHash-1-3 for `str`/`bytes`) | ~1–2 | in-process dicts; DoS-resistant by design |
    | xxHash3 / wyhash | ~10–30 | high-throughput hash tables, checksums, sharding |
    | CRC32 (hardware instruction) | ~20 | error detection; **not** uniform enough for a hash table on its own |
    | MurmurHash3 | ~5 | the classic; still fine, superseded on speed |
    | BLAKE3 / SHA-256 | ~1–3 / ~0.5 | content addressing, integrity, anything an adversary sees |

    CPython uses **SipHash-1-3** with a per-process random key for `str` and `bytes`
    (`Python/pyhash.c`), chosen specifically because it is a keyed PRF — an attacker who cannot
    guess the key cannot construct collisions. For `int`, `hash(n) == n` for small values, which is
    why integer keys cluster perfectly into consecutive buckets and why CPython's dict handles
    integer keys with a probe sequence designed to cope with that.

    ## Chaining versus open addressing

    ### Separate chaining

    ```python
    # Each bucket holds a list. Simple, forgiving, one extra indirection per lookup.
    buckets: list[list[tuple[K, V]]]
    ```

    - **Load factor can exceed 1.** Nothing breaks at α = 2; lookups just cost ~2 comparisons.
    - **Deletion is trivial:** remove from the list. No tombstones.
    - **Costs:** one pointer per bucket plus a list object per non-empty bucket — in Python, 56
      bytes for the list header alone. Poor cache behaviour, because the chain is a separate
      allocation.

    ### Open addressing with linear probing

    ```python
    # Two parallel flat arrays. Everything lives in the table itself.
    keys: list[K | None]
    vals: list[V | None]
    ```

    - **Load factor must stay below 1** — at α = 1 the table is full and a miss loops forever.
    - **Excellent cache behaviour:** probing walks *forward through contiguous memory*, so the
      next slot is almost always in the cache line you already fetched.
    - **Deletion needs tombstones.** Blanking a slot breaks the probe chain for every key that
      probed past it. Tombstones must count toward the load factor, or a delete-heavy workload
      degrades to a full scan in a table that looks half empty.
    - **Primary clustering:** occupied runs merge into longer runs, and longer runs attract more
      keys. The probe count grows *super-linearly* in α, which is the whole story of Layer 3.

    ### The probe-count formulas

    For a successful search:

    ```
    chaining          ≈  1 + α/2
    linear probing    ≈  (1 + 1/(1−α)) / 2
    double hashing    ≈  −ln(1−α) / α
    ```

    Substituting: at α = 0.5, linear probing costs 1.5 probes; at α = 0.9 it costs 5.5; at α = 0.99
    it costs 50.5. Chaining goes 1.25 → 1.45 → 1.50 over the same range. **Layer 3 measures both
    against these formulas and the agreement is nearly exact**, which is unusual and worth seeing.

    ## Reference implementation

    ```python
    # hashmap.py — CPython 3.12. Both strategies, one interface.
    from __future__ import annotations
    from typing import Any, Hashable, Iterator

    _EMPTY = object()
    _TOMBSTONE = object()


    class ChainedHashMap:
        """Separate chaining. Power-of-two capacity so we can mask instead of modulo."""

        __slots__ = ("_cap", "_n", "_buckets", "max_load")

        def __init__(self, capacity: int = 8, max_load: float = 0.75) -> None:
            if capacity & (capacity - 1):
                raise ValueError("capacity must be a power of two")
            self._cap = capacity
            self._n = 0
            self._buckets: list[list[tuple[Hashable, Any]]] = [[] for _ in range(capacity)]
            self.max_load = max_load

        def _idx(self, key: Hashable) -> int:
            # Masking keeps the LOW bits. For int keys, hash(n) == n, so the low
            # bits are the value itself — which is why consecutive ints spread
            # perfectly and why hash quality matters most for the low bits.
            return hash(key) & (self._cap - 1)

        def __setitem__(self, key: Hashable, value: Any) -> None:
            b = self._buckets[self._idx(key)]
            for i, (k, _) in enumerate(b):
                if k is key or k == key:
                    b[i] = (key, value)
                    return
            b.append((key, value))
            self._n += 1
            if self._n > self.max_load * self._cap:
                self._resize(self._cap * 2)

        def __getitem__(self, key: Hashable) -> Any:
            for k, v in self._buckets[self._idx(key)]:
                if k is key or k == key:
                    return v
            raise KeyError(key)

        def __delitem__(self, key: Hashable) -> None:
            b = self._buckets[self._idx(key)]
            for i, (k, _) in enumerate(b):
                if k is key or k == key:
                    b[i] = b[-1]        # swap with last, then pop: O(1), order-agnostic
                    b.pop()
                    self._n -= 1
                    return
            raise KeyError(key)

        def _resize(self, new_cap: int) -> None:
            old = self._buckets
            self._cap = new_cap
            self._buckets = [[] for _ in range(new_cap)]
            for b in old:
                for k, v in b:
                    self._buckets[self._idx(k)].append((k, v))   # no resize check

        def __contains__(self, key: Hashable) -> bool:
            return any(k is key or k == key for k, _ in self._buckets[self._idx(key)])

        def __len__(self) -> int:
            return self._n

        def __iter__(self) -> Iterator[Hashable]:
            for b in self._buckets:
                for k, _ in b:
                    yield k


    class OpenAddressedHashMap:
        """Linear probing with tombstones. Tombstones count toward the load factor."""

        __slots__ = ("_cap", "_n", "_tombs", "_keys", "_vals", "max_load")

        def __init__(self, capacity: int = 8, max_load: float = 0.70) -> None:
            if capacity & (capacity - 1):
                raise ValueError("capacity must be a power of two")
            if not 0 < max_load < 1:
                raise ValueError("max_load must be strictly between 0 and 1")
            self._cap = capacity
            self._n = 0
            self._tombs = 0
            self._keys: list[Any] = [_EMPTY] * capacity
            self._vals: list[Any] = [None] * capacity
            self.max_load = max_load

        def _probe(self, key: Hashable) -> tuple[int, bool]:
            """Return (slot, found). On a miss, slot is where the key would go —
            the FIRST tombstone seen, if any, else the first empty slot."""
            mask = self._cap - 1
            i = hash(key) & mask
            first_tomb = -1
            while True:
                k = self._keys[i]
                if k is _EMPTY:
                    return (first_tomb if first_tomb >= 0 else i), False
                if k is _TOMBSTONE:
                    if first_tomb < 0:
                        first_tomb = i
                elif k is key or k == key:
                    return i, True
                i = (i + 1) & mask

        def __setitem__(self, key: Hashable, value: Any) -> None:
            i, found = self._probe(key)
            if found:
                self._vals[i] = value
                return
            if self._keys[i] is _TOMBSTONE:
                self._tombs -= 1
            self._keys[i] = key
            self._vals[i] = value
            self._n += 1
            if (self._n + self._tombs) > self.max_load * self._cap:
                self._resize(self._cap * 2 if self._n > self._cap // 2 else self._cap)

        def __getitem__(self, key: Hashable) -> Any:
            i, found = self._probe(key)
            if not found:
                raise KeyError(key)
            return self._vals[i]

        def __delitem__(self, key: Hashable) -> None:
            i, found = self._probe(key)
            if not found:
                raise KeyError(key)
            self._keys[i] = _TOMBSTONE      # NOT _EMPTY — that would break the chain
            self._vals[i] = None
            self._n -= 1
            self._tombs += 1

        def _resize(self, new_cap: int) -> None:
            """Doubling grows; same-size rebuilds compact away tombstones."""
            old_k, old_v = self._keys, self._vals
            self._cap = new_cap
            self._keys = [_EMPTY] * new_cap
            self._vals = [None] * new_cap
            self._n = 0
            self._tombs = 0
            mask = new_cap - 1
            for k, v in zip(old_k, old_v):
                if k is _EMPTY or k is _TOMBSTONE:
                    continue
                i = hash(k) & mask
                while self._keys[i] is not _EMPTY:
                    i = (i + 1) & mask
                self._keys[i] = k
                self._vals[i] = v
                self._n += 1

        def __contains__(self, key: Hashable) -> bool:
            return self._probe(key)[1]

        def __len__(self) -> int:
            return self._n

        def __iter__(self) -> Iterator[Hashable]:
            for k in self._keys:
                if k is not _EMPTY and k is not _TOMBSTONE:
                    yield k

        @property
        def load_factor(self) -> float:
            return (self._n + self._tombs) / self._cap
    ```

    ## Trade-offs table

    | Situation | Choose | Instead of | Because |
    | --- | --- | --- | --- |
    | Load factor will stay below ~0.7 | open addressing | chaining | measured 1.10× faster at α = 0.30 and better cache behaviour; no per-bucket allocation |
    | Load factor will exceed 0.8, or you cannot control it | chaining | open addressing | measured 2.08× faster at α = 0.95; probe count stays flat where open addressing's explodes to 40.99 |
    | Delete-heavy workload | chaining | open addressing | no tombstones, no compaction pass, no invisible degradation |
    | Memory is tight and keys are small | open addressing | chaining | no per-bucket list object (56 bytes each in Python) and no per-entry node |
    | Keys come from users or the network | anything with a **randomly-seeded** hash | a fixed hash function | measured 4,649× slowdown under a collision attack at only 8,000 keys |
    | You need a stable hash across processes or machines | `hashlib.blake2b` or xxHash | Python's `hash()` | `hash()` of a `str` is randomly seeded per process and is not stable |
    | Keys are sequential integers | either, but check the probe rule | naive linear probing on `hash(n) == n` | consecutive ints occupy consecutive slots, creating maximal primary clustering |
    | You need ordered iteration or range queries | a B-Tree or a sorted structure | a hash table | hashing destroys order by design; there is no cheap way back |

    ## What breaks in the real world

    A feature-flag service kept an in-process cache mapping `(user_id, flag_name)` to a boolean,
    with a hand-written open-addressed table because the team had profiled `dict` overhead in a hot
    loop and wanted the flat-array layout. It had tombstones. It counted them. It was, by the
    standards of hand-written hash tables, good.

    The bug was in `_resize`. It doubled capacity when `(n + tombstones) > 0.7 × cap` — but the
    doubling decision looked at `n + tombstones` while the *need* to grow depends on `n` alone:

    ```python
    if (self._n + self._tombs) > self.max_load * self._cap:
        self._resize(self._cap * 2)          # ALWAYS doubles
    ```

    Flags were evaluated per request and evicted on flag config change, so the table churned
    constantly: roughly 200 live entries with millions of insert/delete cycles per hour. Each cycle
    added tombstones; each tombstone threshold crossing **doubled the capacity** even though the
    live entry count never exceeded a few hundred.

    Over eleven days of uptime the table grew to 2²⁶ slots — **67 million slots holding about 200
    live keys**, roughly 1 GB of `None`. RSS grew linearly with uptime. The team spent two weeks
    hunting a memory leak in a service that had no leak: every object was reachable, correctly
    tracked, and doing its job in a table that had grown by a factor of 330,000.

    The fix is the two-line version in the reference implementation above:

    ```python
    self._resize(self._cap * 2 if self._n > self._cap // 2 else self._cap)
    ```

    Grow only if the *live* entries justify it; otherwise rebuild at the same size, which compacts
    tombstones away.

    What generalises:

    - **A tombstone is a deferred cost, and deferred costs need a second policy.** One threshold
      decides *when* to act; a separate decision decides *what action*. Conflating them is the bug.
    - **"Memory grows with uptime, not with load" points at a data structure, not a leak.** A leak
      grows with allocation volume. This grew with *elapsed time* because the churn rate was
      constant. That distinction would have saved a week.
    - **The metric that would have caught it is `capacity / len()`.** Export it. Any container whose
      capacity-to-size ratio exceeds ~4 is telling you something.

    ### Design checkpoint

    <Accordion title="You are sharding 500 million vectors across 12 nodes with `hash(id) % 12`. Ops wants to add 4 nodes. What happens, and what should you have built?">
    **Model answer.**

    **What happens: almost everything moves.** Going from `% 12` to `% 16` changes the destination
    of any key whose `hash % 12` and `hash % 16` differ — which is roughly `1 − 1/lcm`-ish in
    practice and empirically about **75% of all keys**. You must re-transfer roughly 375 million
    vectors. At 768 dimensions in float32 that is 3 KB each, so ~1.1 TB across the network, and the
    cluster is either read-only or serving inconsistent results for the duration.

    **What you should have built: consistent hashing.**

    Map both nodes and keys onto the same circular hash space (say 0 to 2³²−1). A key belongs to
    the first node encountered walking clockwise from the key's position. Adding a node inserts one
    point on the ring and steals only the keys between it and its predecessor — **on average `K/N`
    keys move, not `K·(N−1)/N`.** Going 12 → 16 nodes moves about 25% of keys instead of 75%, and
    critically it moves them from *specific* nodes rather than shuffling everything.

    **The refinement that makes it actually work: virtual nodes.** With one point per physical node,
    the ring is lumpy — random placement of 12 points gives shard sizes varying by 2–3×, so your
    largest node runs out of memory while the smallest is idle. Give each physical node **100–200
    virtual points** on the ring and the load spread tightens to a few percent. This is what
    Cassandra calls `num_tokens` (default 16, commonly raised to 256), what Dynamo introduced, and
    what every sharded cache does.

    **The alternative worth naming: rendezvous hashing (HRW).** For each key compute
    `hash(key, node)` for every node and pick the highest. It gives the same minimal-disruption
    property with no ring and no virtual nodes, at the cost of `O(N)` work per lookup — which is
    nothing for N = 16 and unacceptable for N = 10,000. **For a 16-node cluster, rendezvous hashing
    is simpler and I would probably choose it.**

    **What neither solves.** Consistent hashing minimises *how many* keys move; it does not make
    moving them free, and it does not handle hot keys — a single viral document is on one node
    regardless of your ring. For that you need replication of hot shards, which is a different
    mechanism entirely, and the honest thing to say in the design review is that consistent hashing
    solves the rebalancing problem and not the hotspot problem.

    **You will build this in week 27** when the vector store outgrows one process.

    ## The load-factor sweep: wall time

    Same table, same keys, 200,000 lookups, best-of-5, on a quiet machine:

    | Load factor | Chaining (ns/get) | Open addressing (ns/get) | CPython `dict` (ns/get) | open ÷ chain |
    | --- | --- | --- | --- | --- |
    | 0.30 | 129 | **117** | **25** | 0.91× |
    | 0.50 | 173 | **135** | 25 | 0.78× |
    | 0.70 | 188 | 181 | 24 | 0.96× |
    | 0.80 | 208 | 229 | 24 | 1.10× |
    | 0.90 | 281 | 422 | 26 | 1.50× |
    | 0.95 | **317** | 661 | 27 | **2.08×** |

    **The crossover is at α ≈ 0.75.** Below it, open addressing wins — 1.28× at α = 0.50 — because
    a probe walks forward through contiguous memory while a chain dereferences a separate Python
    list object. Above it, primary clustering takes over and open addressing loses, reaching 2.08×
    slower at α = 0.95.

    **This is why real tables resize at 0.66–0.75 and not higher.** CPython's dict resizes when the
    table is 2/3 full (`Objects/dictobject.c`, `USABLE_FRACTION`). Java's `HashMap` uses 0.75.
    Rust's `hashbrown` uses 7/8 — and can, because SwissTable's SIMD group probing has a completely
    different clustering profile. Go's map uses 6.5 entries per 8-slot bucket, so 0.8125. **Every
    one of those numbers is somebody's version of this table.**

    **The `dict` column is the humbling one.** CPython's dict is flat at 24–27 ns across the whole
    sweep — **5× to 12× faster than either hand-rolled implementation**, and it does not degrade at
    high load factor because it resizes before it gets there. It achieves this with a design worth
    knowing: since 3.6, `dict` is **split into a compact insertion-ordered entries array plus a
    sparse index array of small integers**. Iteration walks the dense array (cache-friendly, and
    incidentally why dicts are insertion-ordered), while the sparse index holds `int8`/`int16`
    indices rather than 8-byte pointers, so a small dict's index table fits in one or two cache
    lines. Combined with a probe sequence that mixes in the *high* bits of the hash
    (`perturb >>= 5; i = (5*i + 1 + perturb) & mask`) rather than pure linear probing, it avoids
    primary clustering entirely.

    ## Hash-collision denial of service

    Force every key into one bucket and measure:

    | Keys | Normal `dict`, all lookups | All keys colliding | Slowdown |
    | --- | --- | --- | --- |
    | 1,000 | 0.03 ms | 18.25 ms | **537×** |
    | 2,000 | 0.07 ms | 75.59 ms | **1,129×** |
    | 4,000 | 0.13 ms | 318.16 ms | **2,411×** |
    | 8,000 | 0.26 ms | 1,196.06 ms | **4,649×** |

    <Info>
    Method: a class whose `__hash__` returns a constant 0, so every key collides. Inserting and then
    looking up all `n` keys. Reproduce with `hash_dos.py`.
    </Info>

    The scaling is the signature: doubling `n` roughly **quadruples** the time — 18.25 → 75.59 →
    318.16 → 1,196.06. That is `O(n²)`, exactly as expected for `n` lookups each scanning an
    `n`-long chain. **8,000 crafted keys consume 1.2 seconds of CPU.** In a JSON body that is maybe
    100 KB. A single modest request can consume more CPU than a thousand normal ones.

    This is the attack from **Crosby & Wallach (2003)**, and it was re-demonstrated against nearly
    every web framework at 28C3 in 2011 (Klink & Wälde), affecting PHP, Python, Java, Ruby, ASP.NET
    and Node simultaneously — because they all parsed POST parameters into a hash table with a
    deterministic, publicly-known hash function.

    **Python's fix** (PEP 456, Python 3.4; the `-R` flag existed from 3.2.3) is SipHash with a
    per-process random key. An attacker cannot compute which keys collide without knowing the key.
    This is why `hash("abc")` differs between runs, and why `PYTHONHASHSEED=0` — which disables it
    — should never be set in production. If you have set it to make tests deterministic, **set it in
    the test runner only**, and know that you have disabled a security control.

    **What is still exposed:** `hash(int)` is *not* randomised (`hash(n) == n` for small `n`).
    Integer-keyed dicts fed attacker-controlled integers can still be attacked — an attacker
    supplying multiples of your table size forces a collision run. In practice this is limited by
    CPython's perturbation-based probe sequence, but if you are building a table on integer keys
    from the network, mix them: `hash(key) ^ process_random_salt`, or hash them properly.

    ## Consistent hashing

    The sharding problem: `hash(key) % N` moves ~`(N−1)/N` of all keys when `N` changes. Consistent
    hashing moves ~`1/N`.

    Map nodes and keys onto a circle of `2³²` positions; a key belongs to the first node clockwise
    from it. Adding a node splits one arc rather than reshuffling everything.

    ```python
    import bisect, hashlib

    class ConsistentHashRing:
        """Virtual nodes are what make this actually balance."""

        def __init__(self, nodes: list[str], vnodes: int = 150) -> None:
            self._vnodes = vnodes
            self._ring: list[int] = []                  # sorted positions
            self._owner: dict[int, str] = {}
            for n in nodes:
                self.add(n)

        @staticmethod
        def _pos(s: str) -> int:
            return int.from_bytes(hashlib.blake2b(s.encode(), digest_size=4).digest(), "big")

        def add(self, node: str) -> None:
            for i in range(self._vnodes):
                p = self._pos(f"{node}#{i}")
                bisect.insort(self._ring, p)
                self._owner[p] = node

        def remove(self, node: str) -> None:
            for i in range(self._vnodes):
                p = self._pos(f"{node}#{i}")
                idx = bisect.bisect_left(self._ring, p)
                if idx < len(self._ring) and self._ring[idx] == p:
                    self._ring.pop(idx)
                    del self._owner[p]

        def node_for(self, key: str) -> str:
            p = self._pos(key)
            idx = bisect.bisect_right(self._ring, p) % len(self._ring)
            return self._owner[self._ring[idx]]
    ```

    **Why `blake2b` and not `hash()`.** The ring must be identical in every process and after every
    restart, or two clients disagree about where a key lives. Python's `hash()` is randomly seeded
    per process and would give each replica a different ring. This is the single most common bug in
    hand-rolled consistent hashing.

    **Why 150 virtual nodes.** With one point per node the arcs are exponentially distributed and
    shard sizes vary by 2–3×. With `v` virtual nodes the standard deviation of load falls as
    `1/√v`; at v = 150 the spread is a few percent. Cassandra's `num_tokens` defaults to 16 (chosen
    to limit repair cost) and is commonly raised; Dynamo used 100–200. **The knob trades load
    balance against ring size and rebalancing granularity**, and 100–200 is the range everyone
    converges on.

    Used in: Amazon Dynamo and DynamoDB, Cassandra, Riak, `memcached` clients (`ketama`), Envoy's
    ring-hash load balancer, and every sharded vector database you will meet in week 27.

    ## Production failure modes

    | Failure mode | Signature | Detection |
    | --- | --- | --- |
    | Tombstone accumulation with unconditional doubling | RSS grows with **uptime**, not with load; `len()` stays small | export `capacity / len()`; alert above ~4 |
    | Tombstones not counted toward load factor | lookups degrade to a full scan in a table that looks empty | the delete-heavy churn test; assert probe count stays bounded |
    | Resize copies buckets instead of rehashing | a fraction of keys become unfindable, only after a resize | test that all keys survive two forced resizes |
    | Hash-collision DoS | a few requests consume most CPU; `O(n²)` in payload size | never disable `PYTHONHASHSEED`; bound the number of keys parsed from a request |
    | Mutable object used as a key | entry becomes unfindable but still iterates | make key types frozen dataclasses or tuples; `__hash__` must depend only on immutable fields |
    | `__eq__` without `__hash__` (or disagreeing) | duplicate entries for equal keys | test `hash(a) == hash(b)` whenever `a == b`, with `hypothesis` |
    | `hash()` persisted or sent over the wire | works in dev, breaks after restart or across replicas | grep for `hash(` near serialization; use `hashlib` for anything durable |
    | `% N` sharding, then a node added | massive rebalancing, cluster read-only for hours | consistent hashing or rendezvous hashing from day one |
    | Poor low-bit avalanche with power-of-two masking | probe counts far above theory; some buckets empty and others huge | measure the probe-count table above and compare to `1 + α/2` |

    ## Frontier and research pointers

    - **Knuth (1963), later *TAOCP* Vol 3 §6.4.** — **Takeaway:** the linear-probing analysis giving
      `(1 + 1/(1−α))/2` for successful and `(1 + 1/(1−α)²)/2` for unsuccessful search; the
      measurements in this module match it to within 3%, sixty years later, which is a reasonable
      argument for reading the primary source.
    - **Crosby & Wallach (2003), "Denial of Service via Algorithmic Complexity Attacks."** USENIX
      Security. — **Takeaway:** worst-case complexity is a security property; an attacker who knows
      your hash function converts your average case into your worst case with a few kilobytes.
    - **Aumasson & Bernstein (2012), "SipHash: A Fast Short-Input PRF."** INDOCRYPT. — **Takeaway:**
      a keyed pseudorandom function fast enough to hash every dict key while making collisions
      unforgeable without the key; this is PEP 456 and the reason `hash("abc")` changes between runs.
    - **Karger et al. (1997), "Consistent Hashing and Random Trees."** STOC. — **Takeaway:** placing
      keys and nodes on one circle makes the expected number of keys that move when a node joins or
      leaves `K/N` rather than `K·(N−1)/N`; the original motivation was web caching, and it became
      the foundation of every distributed store.
    - **DeCandia et al. (2007), "Dynamo: Amazon's Highly Available Key-value Store."** SOSP. —
      **Takeaway:** consistent hashing needs virtual nodes to balance, and the paper is candid that
      the naive one-point-per-node ring was unusable in production — the practical detail the
      theory paper omits.
    - **Thaler & Ravishankar (1998), "Using Name-Based Mappings to Increase Hit Rates."**
      *IEEE/ACM ToN* 6(1). — **Takeaway:** rendezvous (highest-random-weight) hashing gives the same
      minimal-disruption guarantee with no ring and no virtual nodes, at `O(N)` per lookup — simpler
      than consistent hashing whenever `N` is small.
    - **Google's SwissTable / Rust `hashbrown` design notes.** — **Takeaway:** storing a 7-bit hash
      fragment per slot in a separate control byte array lets one SIMD instruction test 16 slots at
      once, which changes the clustering economics enough to make a 7/8 load factor practical.

    ## Stretch challenge

    **Implement a SwissTable-style hash map and find out whether SIMD group probing is reachable
    from Python.**

    The design: alongside the slots, keep a byte array of *control bytes*, one per slot, holding
    either "empty", "deleted", or the top 7 bits of the key's hash. A lookup computes the hash,
    finds the group of 16 control bytes, and compares all 16 against the 7-bit fragment **in one
    SIMD instruction**. Only slots whose fragment matches are candidates for a full key comparison.

    This changes the arithmetic completely: most probes never touch a key at all, so clustering
    costs far less, which is why `hashbrown` can run at a 7/8 load factor where the table in this
    module falls apart at 0.95.

    Build:

    1. A reference implementation in pure Python — control bytes in a `bytearray`, group matching
       with a loop. **This will be slow.** That is expected; it establishes correctness and lets you
       count probes.
    2. A NumPy version where group matching is `np.equal(control[g:g+16], fragment)` — vectorised,
       though the per-call NumPy overhead may swamp a 16-byte comparison. **Measure whether it
       does.** This is the interesting question.
    3. A benchmark against your chained and open-addressed tables and against `dict`, sweeping the
       load factor to 0.95, reporting probe counts (deterministic) and ns/op (noisy) separately.

    The open questions:

    - **Does group probing reduce probe counts as much in your implementation as the theory
      suggests?** Plot avg and max probes against α for all three strategies on one chart. The max
      column is where the story is.
    - **Where does the Python overhead put the crossover?** A `bytearray` slice plus a comparison is
      several hundred nanoseconds; if that exceeds the cost of the key comparisons it saves, the
      technique loses in Python entirely — which is a legitimate and useful finding, and matches
      what you found for tries in week 14.
    - **What load factor could you actually run at?** If your max probe count at 0.95 stays under
      10, you can run at 0.95, and the memory saving over a 0.66 table is 30%. Is that worth it for
      a table holding 500 million entries? Compute the dollar value.
    - **Does a 7-bit fragment collide too often at your table sizes?** 1/128 false-positive rate per
      slot means one spurious full comparison per 128 probed slots. At what table size does that
      start to matter?

    Write it up with the probe-count-versus-load-factor chart for four strategies. Very few people
    have implemented SwissTable outside of C++ and Rust, and the write-up of *why it does or does
    not translate to Python* is the genuinely original part.

    The average hides the entire failure mode. At α = 0.99 open addressing averages 41 probes and
    peaks at 15,832. Your table needs both columns.
  </Step>
  <Step title="Then time it, on a quiet machine">
    Close everything. Best-of-5 minimum. Build one table, measure it, free it, `gc.collect()`, then
    build the next — three tables alive at once evict each other from cache and the last one
    measured looks slowest.
  </Step>
  <Step title="Ship it">
    A chart with load factor on x, probes on y, two curves, the theory curves overlaid as dashed
    lines, and the crossover marked. That single chart is the deliverable.
  </Step>
</Steps>

## Apply it at work

<AccordionGroup>
  <Accordion title="If you're a student" icon="graduation-cap">
    **Portfolio line:** "Implemented separate chaining and open addressing with tombstone
    compaction, measured probe counts against Knuth's 1963 analysis across load factors 0.30–0.99
    (agreement within 3%), and identified the α ≈ 0.75 crossover where open addressing stops
    winning — then demonstrated a 4,649× hash-collision DoS and explained PEP 456."

    **The interview move.** "Implement a hash table" is a common screen. Everyone writes chaining
    and gets it working. Three things separate you:

    1. Say **"power-of-two capacity so I can mask instead of modulo"** as you write `_idx`, and
       mention that this makes low-bit hash quality critical.
    2. When you write delete for open addressing, say **"tombstone, not empty — blanking the slot
       breaks the probe chain"** before you write it. Interviewers wait for this and most
       candidates hit the bug live.
    3. When asked about the load factor, give a number and a reason: **"resize at 0.66 like CPython
       — above about 0.75 linear probing's clustering makes it slower than chaining, and I measured
       the crossover at 0.75."**

    The DoS discussion is a strong closing move if there is time. It reframes complexity as a
    security property, which is a level of thinking most candidates never demonstrate.
  </Accordion>
  <Accordion title="If you're working" icon="briefcase">
    **1. Check whether anything in your stack sets `PYTHONHASHSEED`.** `grep -r PYTHONHASHSEED`
    across your Dockerfiles, CI configs and process managers. People set it to make flaky tests
    deterministic and it leaks into production images. If it is set to a fixed value in anything
    that serves traffic, you have disabled the mitigation for a 4,649× amplification attack. Set it
    in the test runner only.

    **2. Bound the number of keys you will parse from untrusted input.** Most JSON parsers will
    happily build a dict with a million keys from a 10 MB body. Cap it — most frameworks have a
    setting, and if yours does not, check `len()` after parsing and reject. This is the actual
    defence; hash randomisation is the backstop.

    **3. Audit your custom `__eq__` implementations for a matching `__hash__`.** In Python, defining
    `__eq__` sets `__hash__ = None`, so the class is unhashable — which is safe. The dangerous case
    is a class that defines *both*, where `__hash__` includes a mutable field. Then mutating an
    object already in a `set` or used as a `dict` key makes it unfindable while it is still there.
    `@dataclass(frozen=True)` makes this correct by construction, and it is usually a one-line
    change.
  </Accordion>
</AccordionGroup>

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Keys vanish after the table grows | Resize copied buckets instead of rehashing; the mask changed | Re-insert every entry; test that all keys survive two forced resizes |
| Open-addressed lookups degrade to a full scan | Delete wrote `_EMPTY`, breaking the probe chain for keys stored past it | Write a tombstone; treat it as "keep probing" on read and "reusable" on write |
| RSS grows with uptime, `len()` stays small | Tombstone threshold triggers an unconditional doubling | Grow only if live entries justify it; otherwise rebuild at the same capacity to compact |
| Object is in the dict but lookups fail | A field used in `__hash__` was mutated after insertion | `@dataclass(frozen=True)`, or hash only immutable fields |
| Duplicate entries for objects that compare equal | `__eq__` defined without a consistent `__hash__` | Property-test: `a == b` must imply `hash(a) == hash(b)` |
| Works locally, breaks across replicas | Python's `hash()` used for sharding or persistence; it is seeded per process | `hashlib.blake2b` or xxHash for anything crossing a process boundary |
| A few requests consume most CPU | Hash-collision DoS; time grows quadratically in the key count | Never fix `PYTHONHASHSEED` in production; cap keys parsed per request |
| Probe counts far above the theory | Poor low-bit avalanche combined with power-of-two masking | Mix high bits into the index, or use a hash with proper avalanche |
| Adding a shard triggers a full rebalance | `hash(key) % N` sharding | Consistent hashing with 100–200 virtual nodes, or rendezvous hashing for small N |
| `[[]] * capacity` makes every key appear everywhere | All buckets are the *same* list object | `[[] for _ in range(capacity)]` |

## Sources & further reading

**Primary docs**

- [CPython `Objects/dictobject.c`](https://github.com/python/cpython/blob/v3.12.9/Objects/dictobject.c) (tag `v3.12.9`) — read the header comment for the compact-dict layout (dense entries array plus sparse index array) and `USABLE_FRACTION` for the 2/3 resize threshold; then find `perturb >>= PERTURB_SHIFT` to see the probe sequence that mixes high hash bits and avoids primary clustering.
- [CPython `Python/pyhash.c`](https://github.com/python/cpython/blob/v3.12.9/Python/pyhash.c) — read this for the SipHash-1-3 implementation and the per-process key initialisation; it is short and it is what PEP 456 specified.
- [PEP 456 — Secure and interchangeable hash algorithm](https://peps.python.org/pep-0456/) — read this for the threat model and why the fix had to be a *keyed* PRF rather than a better hash.
- [`hashlib`](https://docs.python.org/3.12/library/hashlib.html) — read this for `blake2b(digest_size=...)`, which is what you want for a stable, fast, non-cryptographically-required hash across processes.
- [Rust `hashbrown` design notes](https://github.com/rust-lang/hashbrown) — read the README for the control-byte and SIMD group-probing design that lets a 7/8 load factor work.

**Papers**

- [Knuth (1963), analysis of linear probing, collected in *TAOCP* Vol 3 §6.4.](https://www-cs-faculty.stanford.edu/~knuth/taocp.html) — **Takeaway:** successful search costs `(1 + 1/(1−α))/2` probes and unsuccessful costs `(1 + 1/(1−α)²)/2`; the measurements in Layer 3 match to within 3%.
- [Crosby & Wallach (2003), *Denial of Service via Algorithmic Complexity Attacks*, USENIX Security.](https://www.usenix.org/conference/12th-usenix-security-symposium/denial-service-algorithmic-complexity-attacks) — **Takeaway:** an attacker who can choose your keys forces your worst case at will, turning O(1) into O(n) and a web server into a brick.
- [Aumasson & Bernstein (2012), *SipHash: A Fast Short-Input PRF*, INDOCRYPT.](https://doi.org/10.1007/978-3-642-34931-7_28) — **Takeaway:** a keyed PRF fast enough to run on every dict key makes collisions unforgeable, which is why hash randomisation costs almost nothing.
- [Karger, Lehman, Leighton, Panigrahy, Levine & Lewin (1997), *Consistent Hashing and Random Trees*, STOC.](https://doi.org/10.1145/258533.258660) — **Takeaway:** mapping keys and nodes to one circle reduces the keys that move on a topology change from `K(N−1)/N` to `K/N`.
- [DeCandia et al. (2007), *Dynamo: Amazon's Highly Available Key-value Store*, SOSP.](https://doi.org/10.1145/1294261.1294281) — **Takeaway:** virtual nodes are not an optimisation but a requirement — the one-token-per-node ring was measurably unusable, which the theory paper does not tell you.
- [Thaler & Ravishankar (1998), *Using Name-Based Mappings to Increase Hit Rates*, IEEE/ACM ToN 6(1).](https://doi.org/10.1109/90.663936) — **Takeaway:** rendezvous hashing achieves minimal disruption with no ring state at all, and is the simpler choice whenever the node count is small.

**Go deeper**

- [Sedgewick & Wayne, *Algorithms* 4th ed., **Section 3.4 (Hash Tables)**](https://algs4.cs.princeton.edu/home/) — the clearest side-by-side of chaining and linear probing with the probe-count derivations, and the doubling-ratio experiments that this module's benchmark reproduces.
- Matt Kulukundis, *"Designing a Fast, Efficient, Cache-friendly Hash Table, Step by Step"* (CppCon 2017) — the SwissTable talk. Watch it for how control bytes and SIMD change the load-factor economics; it is the clearest explanation of a modern hash table anywhere.
- Raymond Hettinger, *"Modern Dictionaries"* (PyCon 2017) — how CPython's dict got compact and insertion-ordered, from the person who designed it. Read it for why iteration order became an implementation guarantee almost by accident.
