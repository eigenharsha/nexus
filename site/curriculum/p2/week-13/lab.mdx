## The ticket

> **PLAT-4471 — Our cache layer has no owner and nobody can explain its behaviour**
>
> *Reported by: Platform, priority P2*
>
> We have four different caches across three services. Two are `dict`s that never evict. One is a
> hand-rolled LRU that a departed engineer wrote and which has been OOMKilling `svc-reco` roughly
> once a day for three weeks. One is `functools.lru_cache` on a function whose arguments include a
> `datetime`, so it has a 0.2% hit rate and is pure overhead.
>
> Before we standardise on anything, we want someone who understands the primitives well enough to
> tell us *why* each of these is broken and what the replacement should be. Build the primitives
> from scratch, benchmark them against the standard library, and write up what you learned about
> the gap between complexity classes and measured constants.
>
> Deliverable: a `pycollections` package with tests, a benchmark harness, and a report.

    class HashMap:
        """Open hashing (separate chaining) with power-of-two capacity."""

        _INITIAL_CAPACITY = 8
        _MAX_LOAD = 0.75

        def __init__(self) -> None:
            self._cap = self._INITIAL_CAPACITY
            self._n = 0
            self._buckets: list[list[tuple]] = [[] for _ in range(self._cap)]

        def _index(self, key) -> int:
            # Power-of-two capacity lets us mask instead of taking a modulus.
            # hash() can be negative; masking with cap-1 handles that correctly
            # because it keeps only the low bits of the two's-complement value.
            return hash(key) & (self._cap - 1)

        def __setitem__(self, key, value) -> None:
            bucket = self._buckets[self._index(key)]
            for i, (k, _) in enumerate(bucket):
                if k == key:
                    bucket[i] = (key, value)     # replace in place
                    return
            bucket.append((key, value))
            self._n += 1
            if self._n / self._cap > self._MAX_LOAD:
                self._resize(self._cap * 2)

        def __getitem__(self, key):

  <Tab title="standard">
    **Build the full `pycollections` package plus a benchmark harness.**

    Five structures, all tested, plus a harness that produces an empirical complexity table.

    | Module | Requirement |
    | --- | --- |
    | `hashmap.py` | `HashMap` (chaining) and `OpenAddressingMap` (linear probing with tombstones). Both support get/set/del/len/iter/contains, resize on load factor, and deletion that does not break probe chains. |
    | `dynarray.py` | `DynamicArray` with amortized O(1) append, `__getitem__`/`__setitem__` with negative indexing, `insert`, `pop`, and a `capacity` property. Growth factor configurable. |
    | `dll.py` | `DoublyLinkedList` with sentinels, O(1) `push_front`/`push_back`/`unlink(node)`, and iteration in both directions. |
    | `lru.py` | `LRUCache` built on `dll.py` and a `dict`, O(1) `get`/`put`, hit/miss/eviction counters. |
    | `heap.py` | `MinHeap` with `push`, `pop`, `peek`, `heapify` (bottom-up, O(n)), and a `BoundedMinHeap(k)` that keeps only the k largest items seen. |
    | `bench.py` | The harness: sweeps sizes, times operations best-of-N, fits the log-log exponent, and emits a Markdown table plus a matplotlib PNG. |

    **Acceptance criteria**

    - `make verify` green: `pytest` (all structures), `ruff check`, `mypy --strict`.
    - **Structural invariant tests, not just behavioural ones.** For the DLL: walk forward and
      backward and assert the sequences are reverses of each other. For the LRU: assert
      `set(list-reachable nodes) == set(map.values())`. For the heap: assert the heap property at
      every index after every operation in a randomized 10,000-operation test.
    - **Property tests** using `hypothesis` (pin `hypothesis==6.122.3`): for any sequence of
      random operations, your `HashMap` behaves identically to a `dict`, and your `MinHeap` pops in
      the same order as `sorted()`.
    - `bench.py` produces `RESULTS.md` containing, for each structure, the measured exponent and
      the ns/op at n = 10³, 10⁴, 10⁵, 10⁶, plus your machine and Python version.
    - **Your `RESULTS.md` must contain at least one row where the measurement disagrees with the
      theory, and a paragraph explaining it.** If every row agrees, your sweep is too narrow or
      your timing is wrong.

    **The open-addressing deletion trap.** With linear probing you cannot simply blank a slot on
    delete — that breaks the probe chain for every key that collided past it. You need a
    **tombstone**: a sentinel meaning "empty, but keep probing". Then `get` treats a tombstone as
    "keep going" and `set` treats the first tombstone as a reusable slot. And you must count
    tombstones toward the load factor, or a delete-heavy workload degrades to a full scan with a
    table that looks half empty.

    ```python
    _EMPTY = object()
    _TOMBSTONE = object()

    def __delitem__(self, key):
        i = self._probe_to(key)
        if i is None:
            raise KeyError(key)
        self._keys[i] = _TOMBSTONE      # not _EMPTY
        self._vals[i] = None
        self._n -= 1
        self._tombstones += 1
        if (self._n + self._tombstones) / self._cap > self._MAX_LOAD:
            self._resize(self._cap)      # same size: this is a compaction, not a growth
    ```

    <Info>Spec and tests only. You write the implementation.</Info>

  <Tab title="hard">
    **Beat `dict` on a specialised workload and prove it, then add a count-min sketch.**

    **Part A — beat `dict`.** The constraint that makes this possible: `dict` is general. It
    handles any hashable key, arbitrary insertion order, deletion, and adversarial hash
    distributions. If you give up generality you can win. Pick one:

    - **Integer keys, known maximum, known count.** No hashing at all — direct index, or a
      perfect-hash bucket array. Compare against `dict[int, int]`.
    - **Immutable, build-once, read-many.** Build a **minimal perfect hash function** over the key
      set (CHD or BDZ algorithm), giving exactly one probe per lookup with zero collisions and no
      load-factor slack. This is what `frozen` symbol tables in compilers do.
    - **Small fixed-size keys, cache-conscious layout.** Store keys and values in two parallel
      flat `array.array`s so a probe touches one cache line, and use open addressing with
      Robin Hood displacement to bound the probe distance.

    **Acceptance criteria for Part A**

    - A **measured** win of at least 1.3× on lookup throughput against `dict` for your chosen
      workload, on 1,000,000 keys, best-of-5, with the benchmark script committed.
    - A written statement of **exactly what generality you gave up**, and a test that demonstrates
      the failure mode you accepted (e.g. "inserting after freeze raises", or "collides
      catastrophically on adversarial keys").
    - Memory measured with `ru_maxrss` in a subprocess per implementation, not `sys.getsizeof`.

    <Warning>
    Pure Python will almost certainly lose to `dict`, because `dict`'s probe loop is C and yours is
    bytecode. That is a legitimate finding and you may report it — **but only after you have tried
    `array.array` for the storage and eliminated per-element boxing.** If you want an outright win
    you will likely need NumPy for the key array or a small Cython/C extension. Either is in scope.
    Reporting an honest loss with a profile explaining where the time went is worth full marks;
    reporting a win you did not measure is worth zero.
    </Warning>

    **Part B — count-min sketch with measured error bounds.**

    A count-min sketch estimates the frequency of every item in a stream using a fixed amount of
    memory, with a one-sided error: it never underestimates, and it overestimates by at most
    `ε·N` with probability `1 − δ`, where `width = ⌈e/ε⌉` and `depth = ⌈ln(1/δ)⌉`.

    Requirements:

    - Implement it with `d` independent hash functions over a `d × w` counter array.
    - **Verify the bound empirically.** Stream 10,000,000 items drawn from a Zipf distribution,
      keep exact counts in a `dict` for comparison, and for a range of `(w, d)` report: memory
      used, mean absolute error, p99 error, max error, and the fraction of items whose error
      exceeded the theoretical `ε·N`. That fraction should be under `δ`. **Plot it.**
    - **Find where the theory is pessimistic.** The bound is worst-case. On Zipf data the heavy
      hitters are estimated almost exactly and the error concentrates on the tail. Show this with
      a plot of error against true frequency, and explain why.
    - Use it as the admission filter in a **TinyLFU** cache and measure the hit-rate difference
      against plain LRU on a trace that includes a full scan.

    <Warning>There is a constraint here that the `standard` solution fails.</Warning>

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
A public repo plus `RESULTS.md`: a written report titled **"What I learned about constants versus
Big-O"** containing your benchmark table, at least two rows where measurement disagreed with
theory, and your explanation of each.
</Card>

The report is the deliverable that gets you hired, not the code. Everyone's `HashMap` looks the
same. The paragraph explaining why your open-addressing table beat chaining at load factor 0.5 and
lost at 0.95 — with your own numbers — is the thing an interviewer will actually read and ask
about.

Structure it as:

<Steps>
  <Step title="Machine and versions first">
    CPU, RAM, OS, Python build, and how you timed (best-of-N, GC state). Without this the numbers
    are anecdotes.
  </Step>
  <Step title="The table">
    One row per (structure, operation, n). Include the fitted exponent and the ns/op.
  </Step>
  <Step title="The disagreements">
    Every row where the measurement did not match the textbook, with your explanation. This is the
    section people read.
  </Step>
  <Step title="What you would actually ship">
    For each structure you wrote, state whether you would use it in production and why not. The
    honest answer for most of them is "no, use the standard library" — say so, and say what
    writing it taught you that using it would not have.
  </Step>
</Steps>

## Rubric

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Correctness | fails tests | happy path only | edge cases handled (resize, delete, empty, duplicate keys) | structural invariants asserted + property-tested against `dict`/`sorted` |
| Code quality | works | readable | tested + `mypy --strict` clean | a reviewer would approve unchanged; sentinels and tombstones used deliberately and commented |
| Performance | untested | measured at one size | swept across 4 sizes with fitted exponents | beats a stated baseline with evidence, or documents an honest loss with a profile |
| Explanation | none | a README | reasoning documented | at least two measurement-vs-theory disagreements explained correctly |

**What a 3 in Explanation actually requires.** Not "hash tables are O(1)". Something like: *"My
open-addressing table is 1.9× faster than chaining at load factor 0.30 because a probe stays in
one cache line while a chain dereferences a Python list object per bucket. It is 2.8× slower at
0.95 because the average probe length grows as 1/(1−α)²/2, which is 200 probes at α=0.95 versus 12
at α=0.30. The crossover on my machine is at α≈0.7."*

## Common ways submissions lose points

| What happens | Why it costs marks | What to do instead |
| --- | --- | --- |
| Resize copies buckets instead of rehashing | Keys become unfindable; a test with fewer than `cap` keys will not catch it | Test that all keys survive a forced resize |
| Open-addressing delete writes `_EMPTY` | Breaks the probe chain for later keys; the bug is data-dependent and intermittent | Tombstones, counted toward load factor |
| Benchmark uses `time.time()` | Low resolution and not monotonic; results are unreproducible | `time.perf_counter()`, best-of-N |
| Benchmark reports the mean | The mean folds in every unrelated thing the machine did | Report the minimum, and say so |
| Benchmark holds all structures in memory at once | They evict each other from cache; the last one measured looks slowest | Build, measure, free, `gc.collect()`, then build the next |
| `RESULTS.md` has no machine specs | The numbers cannot be interpreted or reproduced | CPU, RAM, OS, Python version, timing method |
| Every measured row matches theory perfectly | Almost certainly means the sweep is too narrow to show cache effects | Sweep to 10⁶; the interesting behaviour starts past L2 |
