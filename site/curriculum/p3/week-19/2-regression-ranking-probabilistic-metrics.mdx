## Why you should care

**For Aarav (student).**
- Recall@k, MRR and NDCG are taught here and used in Weeks 27 and 28 to grade a real retrieval system. Learn them properly once, now, and eight weeks of RAG work becomes measurable instead of vibes.
- "Why RMSE and not MAE?" is a favourite screening question, and the answer that lands is not "RMSE punishes large errors" — it is "MSE's minimiser is the conditional mean and MAE's is the conditional median, so the choice is a statement about which one the business is paying for."
- Calibration is the fastest way to look senior in a project review. Almost nobody checks whether a 0.8 from their model means 80%, and the check is four lines of code.

**For Meera (professional).**
- This shows up in your job as: a forecasting model reported at "8% MAPE" that is systematically short every month, causing stock-outs, because MAPE's minimiser is far below the mean. Layer 2 measures the bias at **61% low** on lognormal demand.
- If any downstream system multiplies your model's probability by a pound value — expected revenue, expected loss, a bid — then calibration is not an ML nicety, it is a correctness requirement, and Module 1's cost-optimal threshold is wrong without it.
- Conformal prediction gives you a distribution-free interval with a coverage guarantee in about twelve lines and no retraining. It is the highest value-per-line technique in this entire week.

## The mental model

Every metric is a bet about which errors you are willing to trade for which. Squaring the error says a single 10-unit miss is worse than ten 1-unit misses, so its minimiser is the **mean**. Taking absolute value says they are equal, so its minimiser is the **median**. Tilting the absolute value says being under is worse than being over, so its minimiser is a **quantile**. Ranking metrics make the same kind of bet about *positions* rather than magnitudes: Recall@k does not care where in the top k an item landed, NDCG does. And a probabilistic metric asks a different question entirely — not "was the ranking right" but "does 0.8 mean 80%" — which no amount of AUC can answer.

### Ten predictions

A **regression** model predicts a number, not a class, so there is no confusion matrix. There is only the gap between what you said and what happened. Here are ten house prices in thousands, truth and prediction:

```
truth y      120  135  150  160  175  180  195  210  225  240
prediction   125  130  148  165  170  185  190  205  230  235
error e       +5   -5   -2   +5   -5   +5   -5   -5   +5   -5
```

The **error** (or **residual**) is `prediction - truth`. Signed, so a positive means you guessed too high. You cannot just average the errors — the pluses and minuses cancel and a model that is wildly wrong in both directions scores zero. So every regression metric is a different way of making the errors positive first.

**Mean absolute error (MAE)** — make each error positive by dropping the sign, then average.

```
MAE = (5 + 5 + 2 + 5 + 5 + 5 + 5 + 5 + 5 + 5) / 10 = 47/10 = 4.70
```

MAE is in the same units as the label — here, thousands of pounds. "On average we are £4,700 out." That is a sentence a stakeholder understands, which is MAE's main advantage.

**Mean squared error (MSE)** — make each error positive by squaring, then average.

```
MSE = (25 + 25 + 4 + 25 + 25 + 25 + 25 + 25 + 25 + 25) / 10 = 229/10 = 22.90
```

The units are thousands *squared*, which means nothing to anyone. So take the square root:

**Root mean squared error (RMSE)** = `sqrt(22.90)` = **4.7854**. Back in thousands of pounds, and always greater than or equal to MAE.

**Median absolute error** — the middle value of the absolute errors rather than their average. Here every absolute error is 5 except one 2, so the median is **5.00**.

**Mean absolute percentage error (MAPE)** — express each error as a fraction of the truth, then average.

```
MAPE = mean(|e_i| / y_i) * 100 = 2.7214 %
```

### The one thing you must see

Change a single prediction. Row 6 — truth 180 — was predicted 185. Suppose the model instead says **305**: one badly wrong row out of ten. Recompute everything.

| Metric | Before | After | Multiplied by |
| --- | --- | --- | --- |
| MAE | 4.7000 | 16.7000 | **3.55×** |
| MSE | 22.9000 | 1582.9000 | **69.12×** |
| RMSE | 4.7854 | 39.7857 | **8.31×** |
| MAPE | 2.7214% | 9.3881% | 3.45× |
| Median absolute error | 5.0000 | 5.0000 | **1.00×** |

One row out of ten moved MSE by a factor of 69 and moved the median absolute error not at all. **That is not a flaw in either metric — it is the metrics doing their jobs.** MSE is designed to scream about large errors; median absolute error is designed to ignore them. Which behaviour you want depends entirely on whether one very wrong prediction is genuinely much worse than several slightly wrong ones. For a delivery ETA, one prediction that is two hours out is much worse. For a heating-demand forecast summed over a thousand homes, it probably is not.

```python
# pip install "numpy==2.5.2"
import numpy as np

y    = np.array([120., 135., 150., 160., 175., 180., 195., 210., 225., 240.])
yhat = np.array([125., 130., 148., 165., 170., 185., 190., 205., 230., 235.])

def report(y, yhat, label):
    e = yhat - y
    print(f"{label:12s} MAE {np.abs(e).mean():8.4f}  MSE {(e**2).mean():10.4f}  "
          f"RMSE {np.sqrt((e**2).mean()):8.4f}  MAPE {np.abs(e/y).mean()*100:7.4f}%  "
          f"medAE {np.median(np.abs(e)):6.4f}")

report(y, yhat, "clean")
bad = yhat.copy(); bad[5] = 305.0
report(y, bad, "one outlier")
```

```
clean        MAE   4.7000  MSE    22.9000  RMSE   4.7854  MAPE  2.7214%  medAE 5.0000
one outlier  MAE  16.7000  MSE  1582.9000  RMSE  39.7857  MAPE  9.3881%  medAE 5.0000
```

### Line by line

- `e = yhat - y` is a NumPy array of ten signed errors; every metric below is one reduction over it.
- `np.abs(e).mean()` is MAE. `(e**2).mean()` is MSE — note that `**` is elementwise, so this squares each error before averaging, not the other way round.
- `np.median(np.abs(e))` is the robust one. It is the only metric in the row that a single bad prediction cannot move, because the median of eleven-ish numbers ignores their extremes by construction.
- `np.abs(e/y)` divides elementwise. If any `y` is zero this produces `inf`, which is MAPE's central problem and the subject of Layer 2.

### Ranking: a different kind of "wrong"

Some models do not predict a number or a class — they **rank**. A search engine returns ten documents; a recommender returns twenty products; in Week 27 a retriever returns the chunks of text that go into a language model's prompt. What matters is not a value, it is *which items appeared and in what order*.

Say for one query there are three genuinely relevant documents, with IDs 3, 5 and 12, and two systems return ten results each:

```
system A:  7   3  12   5   9   1   4   8   2   6
system B:  3  12   7   9   5   4   1   6   8   2
           ^   ^   ^   ^   ^
          r1  r2  r3  r4  r5
```

**Recall@k** — of the relevant documents, what fraction appeared in the top k?

```
A: relevant in top 5 = {3, 12, 5} -> 3/3 = 1.0000
B: relevant in top 5 = {3, 12, 5} -> 3/3 = 1.0000
```

**Identical.** Both systems put all three relevant documents in the top five. **Precision@5** is also identical: 3 of the 5 shown are relevant, so 0.6000 each. If Recall@5 were your only metric, you would report that these two systems are the same.

**MRR (mean reciprocal rank)** — `1 / (rank of the first relevant hit)`, averaged over queries. System A's first hit is at rank 2, so 1/2 = **0.5000**. System B's is at rank 1, so **1.0000**.

**NDCG@k (normalised discounted cumulative gain)** — give each relevant hit a score that shrinks with its position, add them up, and divide by the best possible total. The discount is `1 / log2(i + 2)` where `i` counts from zero, so the first five positions are worth `1.0000, 0.6309, 0.5000, 0.4307, 0.3869`.

```
A hits at positions 2, 3, 5 (i = 1, 2, 4):  0.6309 + 0.5000 + 0.3869 = 1.5178
B hits at positions 1, 2, 5 (i = 0, 1, 4):  1.0000 + 0.6309 + 0.3869 = 2.0178
ideal: three hits at positions 1, 2, 3   :  1.0000 + 0.6309 + 0.5000 = 2.1309

NDCG@5(A) = 1.5178 / 2.1309 = 0.7328
NDCG@5(B) = 2.0178 / 2.1309 = 0.9469
```

Same recall, same precision, and a 0.21 gap in NDCG. If a human reads the first result, that gap is the whole product.

**These four functions are exactly the ones Week 27 Module 5 uses to grade a retrieval system**, down to the `1 / log2(i + 2)` discount and the `set` intersection. </Note>

<AccordionGroup>
  <Accordion title="1. Why is RMSE always greater than or equal to MAE?">
  Because of Jensen's inequality applied to the convex squaring function: the root-mean-square of a set of non-negative numbers is at least their arithmetic mean, with equality only when every absolute error is identical. In the clean table above, RMSE 4.7854 versus MAE 4.7000 — the small gap tells you the errors are nearly uniform. **A large RMSE/MAE ratio is a free outlier detector**: after the bad row it becomes 39.79/16.70 = 2.38.
  </Accordion>
  <Accordion title="2. If your metric is MAE, what single constant is the best possible prediction?">
  The **median** of the labels. If your metric is MSE, it is the **mean**. This is the fastest way to remember which is which, and it is also the strongest baseline you can build in one line — always report it, exactly as Module 1 reports the majority class.
  </Accordion>
  <Accordion title="3. What does a Recall@10 of 1.0 with an MRR of 0.125 tell you?">
  Everything relevant was found, but the first relevant item was at rank 8. If a person reads the list top-down, they saw seven irrelevant results first. If a language model receives all ten items in its prompt, this system is fine. The metric you report is determined by what consumes the ranking, not by what is easiest to compute.
  </Accordion>
  <Accordion title="4. Why does NDCG need the 'N'?">
  Because raw DCG depends on how many relevant documents exist for that query — a query with eight relevant documents can score a much higher DCG than a query with one, so averaging raw DCG across queries would let easy queries dominate. Dividing by the **ideal** DCG for that query puts every query on a 0-to-1 scale, which is what makes the average meaningful.
  </Accordion>
  <Accordion title="5. Your model's MAPE is 8% and the business is unhappy about persistent shortages. What do you suspect?">
  That MAPE is doing exactly what it is designed to do. Because over-prediction is penalised without bound and under-prediction is capped at 100%, the forecast that minimises MAPE sits well below the mean — measured in Layer 2 at 38.7% of the mean on a lognormal demand distribution. The model is not broken; the objective is asking it to under-forecast.
  </Accordion>

### Losses and their minimisers

The one fact that organises everything here: **the constant that minimises a loss tells you what that loss is asking your model to estimate.**

| Loss | Formula | Minimising constant | Choose it when… |
| --- | --- | --- | --- |
| Squared error | `mean((yhat - y)^2)` | the **mean** | you are summing predictions (total demand, total revenue) and large errors really are disproportionately bad |
| Absolute error | `mean(\|yhat - y\|)` | the **median** | the label is heavy-tailed and a few extreme rows should not dominate |
| Huber (delta) | quadratic within `delta`, linear beyond | between mean and median | you want MSE's smooth gradients with MAE's outlier resistance; `delta` is the crossover in label units |
| Pinball / quantile (q) | `mean(max(q*e, (q-1)*e))` | the **q-th quantile** | the cost of being under differs from the cost of being over, or you want an interval |
| MAPE | `mean(\|e\| / y)` | roughly a low quantile — **measured at the 38.7th percentile of the mean below** | a percentage genuinely is the unit of the business *and* `y` is bounded well away from zero |

The asymmetry knob is the useful one in practice. Retail stock-outs cost more than overstock; cloud capacity under-provisioning costs more than over-provisioning; an ETA that is late annoys more than one that is early. All of those are a pinball loss with `q` above 0.5, and scikit-learn gives it to you directly:

```python
from sklearn.ensemble import GradientBoostingRegressor
model = GradientBoostingRegressor(loss="quantile", alpha=0.90)   # alpha IS q
```

### MAPE's trap, measured

MAPE is the most-requested and least-defensible metric in business forecasting. Two defects, both demonstrable in five lines.

**It is asymmetric.** Under-predicting is bounded — you can never score worse than 100% by predicting zero — while over-predicting is unbounded. Truth 100, predict 50: APE 50%. Truth 100, predict 200: APE 100%. Truth 100, predict 500: APE 400%. Same *ratio* of error in the first pair, twice the penalty for the over-prediction.

**It blows up near zero.** Truth 1, predict 3: APE 200%, from an absolute error of 2. A single low-volume SKU can dominate a whole portfolio's MAPE.

The consequence, measured on 20,000 draws from a lognormal demand distribution (`sigma = 0.8`, `mu = 3.0`):

```python
import numpy as np
rng = np.random.default_rng(0)
d = rng.lognormal(3.0, 0.8, 20_000)
grid = np.linspace(d.min() + 0.01, np.quantile(d, 0.999), 4000)
best = min(grid, key=lambda c: np.mean(np.abs(c - d) / d))
print(f"mean {d.mean():.3f}  median {np.median(d):.3f}  MAPE-optimal constant {best:.3f}")
```

```
mean 27.640  median 19.991  MAPE-optimal constant 10.688
```

The MAPE-minimising forecast is **10.688 — 38.7% of the mean, and 53.5% of the median.** A team that optimises MAPE and ships the result will under-forecast demand by roughly 61% and then be surprised by stock-outs. This is not a subtle statistical effect; it is a two-thirds error caused entirely by the choice of metric.

If a business genuinely thinks in percentages, use **weighted MAPE** (`sum|e| / sum|y|`, which is scale-aware and does not blow up on small rows) or **symmetric MAPE** with its own known problems, or best of all report MAE alongside the mean of `y` so the reader can compute a percentage themselves. Never optimise MAPE.

### R-squared, honestly

R-squared is `1 - SS_res / SS_tot`: the fraction of the label's variance the model explains. It cannot decrease when you add a feature to a training fit, including a column of pure noise. Measured on California housing, 16,512 training rows, adding `k` columns of standard normal noise:

| Noise features added | Train R² | Adjusted train R² | **Test R²** |
| --- | --- | --- | --- |
| 0 | 0.61255 | 0.61236 | **0.57579** |
| 5 | 0.61280 | 0.61249 | 0.57497 |
| 50 | 0.61369 | 0.61233 | 0.57411 |
| 200 | 0.61736 | 0.61248 | 0.57168 |
| 1,000 | **0.63702** | 0.61342 | **0.55377** |

A thousand columns of literal random numbers bought **+0.0245 training R-squared**. Adjusted R-squared, `1 - (1-R²)(n-1)/(n-p-1)`, stayed within 0.001 of its starting value across the whole sweep — it charges you for each parameter and correctly reports "nothing happened". Test R-squared fell by 0.0220, which is the truth.

Rules: report **adjusted R-squared on training data** when comparing models with different feature counts, plain R-squared on held-out data, and never compare R-squared across datasets — an R² of 0.3 can be excellent for human behaviour and 0.95 can mean you leaked.

### Ranking metrics: the production implementation

This is the code Weeks 27 and 28 use, verbatim. Learn it here.

```python
# pip install "numpy==2.5.2"
import numpy as np

def recall_at_k(retrieved: list[int], relevant: set[int], k: int) -> float:
    """Fraction of relevant items that appear anywhere in the top k. Order-blind above k."""
    return len(set(retrieved[:k]) & relevant) / len(relevant)

def precision_at_k(retrieved: list[int], relevant: set[int], k: int) -> float:
    """Fraction of the k shown that were relevant. The denominator is k, not len(relevant)."""
    return len(set(retrieved[:k]) & relevant) / k

def mrr(retrieved: list[int], relevant: set[int]) -> float:
    """Reciprocal rank of the FIRST relevant hit. Nothing after it matters."""
    for i, cid in enumerate(retrieved, start=1):
        if cid in relevant:
            return 1.0 / i
    return 0.0

def ndcg_at_k(retrieved: list[int], relevant: set[int], k: int) -> float:
    """Position-discounted, normalised by the best ranking possible for this query."""
    dcg = sum(1.0 / np.log2(i + 2) for i, cid in enumerate(retrieved[:k]) if cid in relevant)
    ideal = sum(1.0 / np.log2(i + 2) for i in range(min(len(relevant), k)))
    return dcg / ideal if ideal > 0 else 0.0
```

Four implementation details that cause real bugs:

- **`enumerate(retrieved[:k])` starts at zero, so the discount is `1/log2(i+2)`** and position 1 gets a discount of exactly 1.0. If you see `1/log2(i+1)` with a one-based index it is the same thing; mixing the two conventions silently changes every number.
- **`ideal` uses `min(len(relevant), k)`.** A query with 20 relevant documents evaluated at k=10 can only ever place 10, so the ideal DCG must be capped at 10 terms or NDCG can never reach 1.0 and your averages are meaningless.
- **`relevant` is a `set`.** If your retriever can return the same chunk twice — which happens after a hybrid fusion — a list-based intersection double-counts and Recall@k can exceed 1.0.
- **The `ideal > 0` guard.** A query with no relevant documents in your labelled set must be excluded from the average, not scored as zero. Scoring it zero drags every reported number down by the fraction of unlabelled queries, which is one of the more common ways a retrieval eval quietly lies.

| Choose Recall@k as primary when… | Choose NDCG@k when… | Choose MRR when… |
| --- | --- | --- |
| everything in the top k is consumed equally — a language model receives all k chunks in its prompt | ordering inside the top k changes the outcome, e.g. you have a re-ranker whose entire job is order | the consumer looks at exactly one result: a "jump to source" link, a single citation, a voice answer |
| `k` is fixed by a hard budget (context window, page size) | you have **graded** relevance (0–3), which NDCG uses properly and MRR ignores | you want a metric that is brutal about the first position and easy to explain |
| you want the metric that is easiest to explain to a non-specialist | you are comparing systems that all find the same items but order them differently — as A and B did above | latency budgets mean you will show fewer results over time |

### Calibration: does 0.8 mean 80%?

A model can rank perfectly and still produce numbers that mean nothing, because **ROC-AUC is invariant to any monotone transform of the scores** (Module 1, Layer 3). If anything downstream multiplies your probability by a pound value — expected loss, expected revenue, a bid, Module 1's cost-optimal threshold — then the number must be *calibrated*: among all cases scored 0.30, about 30% should be positive.

Two measurements do the job.

- **Brier score** — the mean squared error of the probability: `mean((p - y)^2)`. Lower is better; the baseline is a constant prediction of the prevalence, which scores `pi*(1-pi)`.
- **Reliability diagram** — bin the predictions, plot mean predicted against observed frequency per bin, and compare with the 45-degree line. **Expected calibration error (ECE)** is the support-weighted mean absolute gap.

Measured on the telco churn dataset (7,043 rows, 26.54% churn, `xgboost==2.1.4`), deliberately using an over-confident booster — `max_depth=8`, 600 trees, no subsampling, `reg_lambda=0`:

```
model                AUC      AP      Brier     log-loss   ECE
raw booster        0.8061  0.5935  0.17520     0.66588   0.1366
+ Platt (sigmoid)  0.8061  0.5935  0.15538     0.48087   0.0188
+ isotonic         0.8029  0.5845  0.15017     0.47606   0.0229
constant baseline     —       —    0.19486        —         —
```

Read three things. **AUC does not move under Platt scaling** (0.8061 either way) — it is a monotone transform, so the ranking is untouched and only the *meaning* of the numbers changed. **ECE fell 7.3×**, from 0.1366 to 0.0188. And the raw model's Brier of 0.17520 was only 10.1% better than predicting the constant 0.2654 — which is a much less flattering summary than "AUC 0.81".

The raw model's reliability curve shows the classic over-confidence:

```
predicted  0.013  0.142  0.251  0.346  0.449  0.554  0.648  0.755  0.849  0.964
observed   0.121  0.273  0.339  0.382  0.357  0.333  0.596  0.491  0.643  0.663
```

In the top bin the model says **96.4%** and reality says **66.3%**. Any expected-value calculation using that bin overstates by 45%.

```python
# pip install "xgboost==2.1.4" "scikit-learn==1.9.0"
from sklearn.calibration import CalibratedClassifierCV, calibration_curve
from sklearn.frozen import FrozenEstimator

# X_cal / y_cal is a THIRD split, never used for fitting the booster
cal = CalibratedClassifierCV(FrozenEstimator(model), method="sigmoid").fit(X_cal, y_cal)
p = cal.predict_proba(X_test)[:, 1]
frac_pos, mean_pred = calibration_curve(y_test, p, n_bins=10, strategy="uniform")
```

`FrozenEstimator` (scikit-learn 1.6+) is how you calibrate an already-fitted model without refitting it. Before 1.6 this was `cv="prefit"`, now deprecated. Without it, `CalibratedClassifierCV` refits the base estimator inside its own cross-validation, which is correct but retrains your booster five times.

<Warning>
**The result that matters most in this section is the one that is not in the table.** A properly tuned booster on the same data — `max_depth=3`, `learning_rate=0.05`, early stopping at 112 trees — scores **Brier 0.13424** with **no calibration at all**, beating both calibrated versions of the over-fitted model (0.15538 and 0.15017) and beating the raw over-fitted model by 23.4%. Calibration is a repair, not an upgrade. Fix the model first; calibrate what remains.
</Warning>

### Trade-offs: Platt versus isotonic

| Choose Platt (sigmoid) when… | Choose isotonic when… |
| --- | --- |
| the calibration set is small — under roughly 1,000 rows, or under ~100 positives | you have thousands of calibration rows and can afford a flexible fit |
| the miscalibration looks like a consistent squeeze or stretch (a sigmoid shape) | the distortion is not sigmoid-shaped — common after resampling (Week 20 Module 4) |
| you need the ranking preserved exactly — it is strictly monotone | a slight AUC loss is acceptable: measured **0.8061 → 0.8029** here, because isotonic's step function creates ties |
| you want two parameters and near-zero overfitting risk | you want the lowest achievable Brier: 0.15017 versus 0.15538 here |

### War story: the bid that was 45% too high

*A modelled composite — assembled from recurring patterns rather than one company, with illustrative figures. The mechanism is real and the measured tables elsewhere on this page are unaffected; the incident is not a case study. See [About the numbers](/start/about-the-numbers).*

An ad-tech team ran a click-prediction model whose output was multiplied directly by a conversion value to set a bid. The model's AUC was healthy and stable for months. Spend, however, ran consistently over plan, and the excess was concentrated in the highest-value inventory.

The cause was in the top reliability bin, exactly as in the table above. The model had been retrained with deeper trees during a "quality push", which raised AUC by 0.004 and destroyed calibration at the top of the range: predictions near 0.96 were converting at about 0.66. Because the bid was `p * value`, every bid in the most expensive inventory was inflated by roughly 45%, and because the auction is second-price the team still won those auctions — they just paid more for them. Nothing in the monitoring caught it: AUC was up, log-loss was not on the dashboard, and there was no reliability check.

The fix was fifteen lines: log the mean predicted probability and the realised conversion rate per decile every day, alert when the gap in any decile exceeds 0.05 absolute, and add a Platt layer fitted weekly on a held-out slice. The lasting lesson is the general one: **if a probability is multiplied by money, monitor calibration, not ranking.**

### Design checkpoint

> A demand-forecasting team reports 8.4% MAPE and wants to ship. Warehouses are complaining about stock-outs. What do you check, in what order?

<Accordion title="Model answer">
First, reproduce their metric and compute the **mean signed error**, not the absolute one. If the model is systematically under-forecasting, the signed mean will be clearly negative while MAPE says nothing — MAPE cannot show direction. Second, plot the MAPE-optimal constant against the mean of the label, exactly as measured above: on lognormal demand the MAPE minimiser sits at 38.7% of the mean, so an 8.4% MAPE is entirely consistent with a forecast biased 60% low on the heavy-tailed SKUs.

Then re-frame the objective around the actual asymmetry. A stock-out costs the margin on the lost sale plus a substitution risk; overstock costs holding cost plus markdown. Those are two different numbers, so the right loss is **pinball at a `q` derived from them** — `q = C_understock / (C_understock + C_overstock)`, which is the newsvendor formula and structurally the same derivation as Module 1's cost threshold. Fit `GradientBoostingRegressor(loss="quantile", alpha=q)` and report weighted MAPE plus mean signed error plus achieved service level, and never report plain MAPE again. Finally, check the low-volume SKUs separately: they dominate MAPE and may be better served by a reorder-point rule than a model at all.
</Accordion>

### Proper scoring rules, and why Brier and log-loss are the only two you should use

A **scoring rule** takes a predicted distribution and an outcome and returns a penalty. It is **proper** if the forecaster's expected penalty is minimised by reporting their true belief, and **strictly proper** if that minimum is unique. This is not a technicality — an improper scoring rule pays your model to lie.

Squared error on probabilities (Brier) and negative log-likelihood (log-loss) are both strictly proper. Accuracy is not: if you believe the true probability is 0.6, accuracy is maximised by reporting 1.0, so a model tuned on accuracy is being paid to be over-confident. F1 is not proper either. This is the formal reason that the Module 1 metrics cannot substitute for the ones here.

Brier decomposes (Murphy, 1973) into three interpretable terms:

```
Brier  =  reliability  -  resolution  +  uncertainty
```

- **uncertainty** is `pi*(1-pi)`, a property of the data alone — 0.19486 on telco churn. Nothing you do changes it.
- **reliability** is the calibration error, weighted by bin size. Lower is better. This is the term Platt scaling attacks.
- **resolution** is how far your predictions spread away from the base rate. Higher is better. This is the term more data and better features attack.

Run the numbers from Layer 2 through that lens. Platt scaling took Brier from 0.17520 to 0.15538 — a **reliability** improvement, with AUC unchanged at 0.8061 confirming resolution did not move. Tuning the model took Brier to 0.13424 with AUC rising to 0.8498 — a **resolution** improvement. The decomposition tells you which of the two levers is available, and it is the reason "just calibrate it" is bad advice for a model that is genuinely weak.

The choice between Brier and log-loss is about how you want confident mistakes punished. Log-loss is unbounded: a single confident, wrong prediction at `p = 0.999` contributes 6.9 to the sum, while Brier contributes at most 1.0. **Use log-loss when a confident error is catastrophic (medical, safety) and Brier when it is merely expensive**, and clip probabilities away from 0 and 1 before computing log-loss or one row will define your metric.

### Recall@k, MRR and NDCG at depth — the bridge to Weeks 27–28

These three are the entire scoreboard for the retrieval half of this course, so it is worth knowing precisely what each is blind to.

**Recall@k is blind to order and to everything below k.** Both properties are deliberate and both bite. A retriever that puts the answer at rank 10 out of 10 scores the same 1.0 as one that puts it at rank 1 — which is correct if all ten chunks go into a prompt, and badly wrong if a re-ranker will only forward the top three. Week 27 Module 5 makes Recall@10 the primary metric for exactly this reason and then switches to NDCG the moment a re-ranker appears in Week 28 Module 4.

**MRR discards every hit after the first.** For a query with five relevant documents ranked 1, 2, 3, 4, 5, MRR is 1.0 — the same as for a query with one relevant document at rank 1. It is the right metric when the consumer reads one result and the wrong one whenever recall matters.

**NDCG's discount is a modelling choice, not a law.** The `1/log2(i+2)` curve is conventional, from Järvelin and Kekäläinen (2002), chosen because it decays slowly enough to keep the tail relevant. It is *not* a measured model of user attention: real click-through decays faster than logarithmically at the top of a search results page. If your product has measured position bias, substitute it — the metric is still normalised and still comparable across queries, and it now matches your users. Two things you must fix and document: the discount function and whether `ideal` is capped at k.

There is a fourth number that Weeks 27 and 28 need and that this module cannot give you: **the size of the labelled eval set determines whether a difference is real.** A change from 0.84 to 0.87 Recall@10 on 100 queries is roughly 3 queries, and a paired bootstrap over those 100 queries will show an interval that comfortably contains zero. Module 5 supplies the machinery; Week 27's ablation table applies it and reports three of its six rows as not significant.

### Conformal prediction: intervals with a guarantee

Quantile regression gives an interval by fitting a model per quantile. It is easy and it does **not** come with a coverage guarantee. Measured on California housing, `GradientBoostingRegressor(loss="quantile")` at alpha 0.05 and 0.95, 200 estimators, 4,128 test rows:

```
quantile GBM 5–95 interval:  coverage 0.8653  (target 0.90)   mean width 1.7422
```

It **under-covers by 3.5 points**. Nothing is broken — the quantile estimates are themselves fitted quantities with error, and their errors do not cancel.

**Split conformal prediction** fixes this with a guarantee that requires only exchangeability — no distributional assumption, no assumption that the model is any good:

```python
# pip install "numpy==2.5.2" "scikit-learn==1.9.0"
import numpy as np
from sklearn.model_selection import train_test_split
from sklearn.ensemble import RandomForestRegressor

X_fit, X_cal, y_fit, y_cal = train_test_split(X_train, y_train, test_size=0.25, random_state=1)
model = RandomForestRegressor(n_estimators=200, min_samples_leaf=5,
                              random_state=0, n_jobs=-1).fit(X_fit, y_fit)

residuals = np.abs(y_cal - model.predict(X_cal))          # conformity scores
n = len(residuals)
level = np.ceil((n + 1) * 0.90) / n                       # the finite-sample correction
q = np.quantile(residuals, level, method="higher")

pred = model.predict(X_test)
lower, upper = pred - q, pred + q
print(f"q={q:.4f}  coverage {((y_test >= lower) & (y_test <= upper)).mean():.4f}  width {2*q:.4f}")
```

```
q=0.7587  coverage 0.8886 (target 0.90)  width 1.5174
```

**0.8886 against a target of 0.90**, and *narrower* than the quantile-regression interval (1.5174 versus 1.7422). The guarantee is marginal coverage of at least `1 - alpha` in expectation over the calibration draw, and the `ceil((n+1)*(1-alpha))/n` term is exactly the finite-sample correction that makes it hold — using a plain `np.quantile(residuals, 0.90)` loses the guarantee, by a little at large `n` and by a lot at small `n`.

The honest limitation, and it is a big one: split conformal with absolute residuals produces a **constant-width** interval. Every prediction gets ±0.7587 whether the model is confident or not. Real uncertainty is heteroscedastic, and the fix is a normalised conformity score, `|y - yhat| / sigma(x)`, where `sigma(x)` is a second model fitted to predict the residual magnitude — this is **conformalised quantile regression** (Romano, Patterson and Candès, 2019), which keeps the coverage guarantee *and* varies the width.

### Failure modes

| Failure | Signature | Detector |
| --- | --- | --- |
| MAPE optimised, forecast biased low | persistent stock-outs while MAPE looks fine | report **mean signed error** beside MAPE; it will be clearly negative |
| MAPE infinite or enormous | a `y` at or near zero | assert `y.min() > 0` before computing; switch to weighted MAPE |
| R-squared climbing with every feature | R² cannot fall on training data | adjusted R² on train, plain R² on held-out; measured +0.0245 from pure noise |
| NDCG can never reach 1.0 | `ideal` not capped at k when a query has more than k relevant items | assert `ndcg_at_k(ideal_ranking, relevant, k) == 1.0` in a unit test |
| Recall@k above 1.0 | duplicate IDs in the retrieved list after fusion | intersect **sets**, and assert `len(set(retrieved)) == len(retrieved)` |
| Retrieval metrics drifting down over releases | unlabelled queries scored as 0 instead of excluded | count and report the excluded queries as a separate number |
| Expected-value calculations consistently wrong in one direction | miscalibration, invisible to AUC | per-decile predicted-versus-observed, alerting at 0.05 absolute gap |
| Calibration "fixed" but ranking got worse | isotonic's step function ties scores together | measured AUC 0.8061 → 0.8029; use Platt when the ranking is the product |
| Conformal interval under-covers badly | plain `np.quantile` without the `(n+1)/n` correction, or a calibration set reused for fitting | assert the calibration split is disjoint; use `method="higher"` |

### Papers

- **Järvelin, K. & Kekäläinen, J. (2002), "Cumulated Gain-Based Evaluation of IR Techniques," *ACM TOIS* 20(4).** *Takeaway:* the log discount and the normalisation by ideal DCG were introduced to make graded relevance comparable across queries of different difficulty — everything in Week 27's retrieval scoreboard descends from Section 4 of this paper.
- **Gneiting, T. & Raftery, A. E. (2007), "Strictly Proper Scoring Rules, Prediction, and Estimation," *JASA* 102(477).** *Takeaway:* only a strictly proper rule such as Brier or log-loss is uniquely minimised by reporting your true belief, which is the formal reason accuracy and F1 cannot be used to grade probabilities.
- **Murphy, A. H. (1973), "A New Vector Partition of the Probability Score," *Journal of Applied Meteorology* 12(4).** *Takeaway:* Brier decomposes into reliability minus resolution plus uncertainty, which tells you whether your model needs calibrating or needs to be better — the distinction that made the 0.15538-versus-0.13424 result above interpretable.
- **Niculescu-Mizil, A. & Caruana, R. (2005), "Predicting Good Probabilities with Supervised Learning," *ICML*.** *Takeaway:* boosted trees and SVMs are systematically over-confident in a sigmoid-shaped way while bagged trees are nearly calibrated, and Platt scaling wins on small calibration sets while isotonic wins above roughly 1,000 examples.
- **Romano, Y., Patterson, E. & Candès, E. (2019), "Conformalized Quantile Regression," *NeurIPS*.** *Takeaway:* combining conformal calibration with quantile regression keeps the finite-sample coverage guarantee while letting the interval width vary with the input, which fixes the constant-width limitation demonstrated above.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Forecast consistently short, MAPE looks fine | MAPE's minimiser sits well below the mean — measured at 38.7% of it | report mean signed error; optimise pinball loss at the cost-derived `q` |
| MAPE is `inf` or in the thousands | a label at or near zero | assert `y.min() > 0`; use weighted MAPE (`sum\|e\|/sum\|y\|`) |
| RMSE and MAE tell different stories | a few large errors; RMSE/MAE ratio is a free outlier detector | report both plus the 95th percentile of absolute error |
| Training R-squared always improves | R² cannot fall on training data, even with noise features | adjusted R² on train; held-out R² for decisions |
| NDCG never reaches 1.0 | `ideal` not capped at `k` for queries with more than `k` relevant items | `min(len(relevant), k)`; unit-test the ideal ranking |
| Recall@k above 1.0 | duplicate IDs in the retrieved list | intersect sets and assert the retrieved list has no duplicates |
| Retrieval scores drift downward each release | queries with no labels scored 0 rather than excluded | exclude them and report the count separately |
| AUC good, expected-value maths wrong | AUC cannot see miscalibration; it is invariant to monotone transforms | Brier + reliability diagram + per-decile monitor |
| Calibration helped Brier but hurt AUC | isotonic creates ties by construction — measured 0.8061 → 0.8029 | Platt when ranking is the product, isotonic when the probability is |
| Calibration barely helped | the model is weak, not miscalibrated | check Brier's decomposition: you need resolution, not reliability. Tuning got 0.1752 → 0.1342 |
| Conformal interval under-covers | plain quantile without `ceil((n+1)*(1-a))/n`, or a reused calibration split | use the correction and `method="higher"`; assert disjoint splits |
