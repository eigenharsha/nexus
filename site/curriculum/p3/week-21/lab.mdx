## Tracks

<Tabs>
<Tab title="basic">

**2–3 hours.** A 2-layer network in NumPy with hand-written backprop, matching provided reference gradients to 1e-6.

About 60% of the code is written for you and every gap is marked `TODO` with a one-line hint above it. You fill in:

- `forward()` — the two matmuls, the ReLU, the logits.
- `backward()` — `dZ2` (the fused softmax-cross-entropy gradient), `dW2`, `db2`, `dH`, `dZ1`, `dW1`, `db1`.
- `sgd_step()` — the update.

**What you must make true**

- `make verify TRACK=basic` is green: every backward matches the reference gradients to 1e-6.
- You can state the shape of every intermediate without running the code.

<Info>Hints are not cheating on this track — the point is to see the shape of a correct solution while typing it. If you finish in under half the time box, throw it away and do `standard` from an empty file. That is where the learning is.</Info>

</Tab>
<Tab title="standard">

**7–9 hours.** A reverse-mode autograd engine, layers, optimizers, MNIST to ≥95%, no framework.

Spec and tests only. You write everything from an empty file.

**Acceptance criteria**

1. A `Value` (scalar) or `Tensor` type that records a computation graph, with `backward()` doing a **topological-order** reverse pass over the nodes reachable from the output, each visited once.
2. Correct gradients for `+ - * / **`, `exp`, `log`, `tanh`, `relu`, `sum`, `mean`, and matmul.
3. **Gradient accumulation done right.** A value used twice receives both contributions. There is a test for exactly the `grad = ...` versus `grad += ...` bug, because it is the one everybody writes.
4. Modules: `Linear`, `ReLU`, `Softmax`, `CrossEntropyLoss`, `Sequential` — each with a `parameters()` method.
5. Optimizers: `SGD` (with momentum) and `Adam`, matching the reference update rules.
6. `zero_grad()` that actually zeroes, verified by running two steps and asserting the second step's gradients do not contain the first's.
7. A `gradcheck(f, inputs)` using **central** differences, relative error below **1e-6** on every operation.
8. Trained on MNIST to **≥95% test accuracy**, training curve committed.
9. No PyTorch, TensorFlow or JAX anywhere in the implementation. (You may use PyTorch in a *test*, on the `hard` track.)

**Two things that will cost you an afternoon if nobody tells you**

- **The topological sort must use a visited set.** A diamond-shaped graph without one gives you exponential traversal time and, worse, doubled gradients — which looks exactly like a math error.
- **Fuse softmax and cross-entropy.** Separately they are numerically unstable and the gradient is a `K×K` Jacobian. Fused, the gradient is `(p − y)` and it is three lines. Module 2 derives it.

<Info>Spec and tests only. You write the implementation. `make verify TRACK=standard`.</Info>

</Tab>
<Tab title="hard">

**5–8 hours.** Tensor autograd with broadcasting, PyTorch parity, and measured gradient checkpointing.

**The constraint the `standard` solution fails:** scalar autograd is 1,730× slower than NumPy (Module 2, Layer 3), so it cannot train anything real, and it has no notion of broadcasting at all.

**Acceptance criteria**

1. **Tensor-valued autograd with NumPy broadcasting**, including correct gradient *reduction* when a broadcast axis was expanded. The test broadcasts `(3,1)` against `(3,4)` and checks both the shape and the values of the resulting gradient. Write one `unbroadcast(grad, target_shape)` helper and use it in every binary op.
2. **A PyTorch parity test.** Same seed, same data, same architecture; after 100 steps every parameter matches `torch.allclose(..., atol=1e-6)`. When this fails — and it will, once — the failing parameter tells you which operation you got wrong. This test is worth more than the engine.
3. **A speed comparison** against PyTorch CPU on the same workload, with the ratio and an honest explanation of where the difference comes from. "Slower" is not an answer; "3.4× slower because our matmul calls `np.dot` per sample rather than batching, and framework overhead is per-operation not per-element" is.
4. **Gradient checkpointing with the measured peak-memory saving** on a deep network. Report memory and step time at 1, `√L` and `L` segments.

<Warning>
**No number, no credit.** That is the rule for every `hard` track in this course. The deliverable
is a short write-up containing what the standard approach measured, what yours measures, and the
sentence explaining why.
</Warning>

</Tab>
</Tabs>

## Milestones, in order

Do them in this order. Each one is independently committable, which means each one is a place
you can stop.

<Steps>
<Step title="The paper derivation (30 min, no computer)">
The 2-2-1 network from Module 2 Layer 1, forward and backward by hand. Target: `L = 0.40319`, `dL/dW1 = [[-0.33181, 0], [0.33181, 0]]`. Everything below is checked against these numbers, so getting them right first is not optional.
</Step>
<Step title="Value with + and * only (45 min)">
Just those two ops and `backward()`. Verify `y = x*x` gives `dy/dx = 2x` — this is the test that catches the `+=` bug immediately, because with `=` you get `x` instead of `2x`.
</Step>
<Step title="The rest of the ops (60 min)">
`**`, `exp`, `log`, `tanh`, `relu`, and the reflected dunders (`__radd__`, `__rmul__`, `__rsub__`, `__rtruediv__`). Reproduce the full 2-2-1 numbers from milestone 1.
</Step>
<Step title="gradcheck (45 min)">
Central differences, `ε = 1e-5`, float64. Run it on every op with random inputs. **This is the milestone that makes everything after it trustworthy** — do not proceed until every op is under 1e-6.
</Step>
<Step title="Neuron / Layer / MLP (60 min)">
Three small classes with `parameters()`. Train on `make_moons` to over 95% with plain SGD. First real training run.
</Step>
<Step title="SGD and Adam (60 min)">
Momentum and the four-line Adam from Module 4. Verify Adam against the reference update on a fixed gradient sequence — this catches bias-correction errors, which otherwise only show up as "converges a bit slower".
</Step>
<Step title="Batching, Linear, and MNIST (2-3 h)">
The scalar engine will be too slow for full MNIST — this is the moment you find that out for yourself, which is the point. Options: use a subset, use a small network, or (better) move to array-valued `Value` where `data` is a NumPy array. Reach 95%.
</Step>
<Step title="The write-up (60 min)">
The part everybody skips and the part that gets you hired. See below.
</Step>
</Steps>

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
A public repo plus a "how backprop actually works" explainer. One of the two strongest portfolio
pieces in the course.
</Card>

Your README must contain, in this order:

1. **One sentence saying what it is**, and one saying what it is not (it is not fast, and you should say so before a reader discovers it).
2. **The 2-2-1 worked example** with the hand-computed numbers next to your engine's output. This proves the engine is correct in a way no test badge does.
3. **The `gradcheck` result table** — every op, its relative error. Numbers, not "all tests pass".
4. **The MNIST curve and final accuracy.**
5. **The speed comparison with an explanation.** Your engine versus NumPy versus PyTorch on the same problem, with the ratio and *why*. This paragraph is the single strongest signal in the repo, because it shows you understand where the cost is rather than just having followed a tutorial.
6. **What you'd do differently**, honestly. Two or three sentences.

<Tip>
**The explainer.** Write the backprop explanation you wish you'd read in week one — 800–1,200
words, one worked example, one diagram. Post it. Half the value of this lab is having a public
artifact that demonstrates you can explain a hard thing clearly, which is most of what a senior
engineer is paid for.
</Tip>

## Rubric

Score yourself **before** you open `solution/`. Four dimensions, 0–3 each, 12 points total.
`make verify` decides Correctness; you grade the other three honestly.

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Correctness | `make verify` fails | happy path only | edge cases handled (diamond graphs, reused values, zero gradients) | adversarial inputs handled (deep chains without stack overflow, `log(0)`, broadcasting) |
| Code quality | works | readable | tested + typed | a reviewer would approve unchanged |
| Performance | untested | measured once | meets the budget | beats it, with evidence and an explanation |
| Explanation | none | a README | reasoning documented | trade-offs defended in writing |

**What a 3 looks like on this specific lab.** Correctness 3 means your engine survives a 2,000-deep
chain (iterative topological sort), a value consumed by five different downstream nodes, and a
gradient check on every op. Explanation 3 means your README explains *why* the scalar engine is
three orders of magnitude slower, not just that it is.

## If you get stuck

<AccordionGroup>
<Accordion title="gradcheck relative error is about 0.5 on every op">
You have `grad = ...` where you need `grad += ...` in your backward closures, and some value in your test is used twice. Exactly-0.5 error is the signature of receiving one of two contributions.
</Accordion>
<Accordion title="gradcheck error is 1e-3 and you cannot find the bug">
Check you are in float64, not float32, and that `ε = 1e-5` rather than 1e-8. Sweep `ε` over 1e-4, 1e-5, 1e-6 — if the "error" moves a lot, your *check* is broken and your gradient is probably fine. Module 2 Layer 2 covers this.
</Accordion>
<Accordion title="RecursionError once you try a real batch">
Your topological sort is recursive. A 784-term dot product built from `__add__` is a 784-deep chain. Rewrite the sort with an explicit stack — Module 2 Layer 3 has the code. Do not raise `sys.setrecursionlimit`; the C stack overflows and you get a segfault with no traceback.
</Accordion>
<Accordion title="MNIST trains but plateaus around 88%">
Three usual causes, in order of likelihood: (1) your learning rate is wrong for the optimizer you're using — SGD wants ~0.5 here, Adam ~1e-3; (2) you're using sigmoid in the hidden layers, so gradients are vanishing; (3) you didn't normalize the pixels to roughly unit scale. Module 3 covers all three.
</Accordion>
<Accordion title="It's correct but so slow you can't finish an epoch">
Expected, and it is the lesson. A scalar engine allocates a Python object per arithmetic operation — about 2.8 µs of interpreter overhead per node, and a 784-32-10 network is 25,738 nodes per example. Either shrink the problem (a 200-example subset, 8×8 downsampled digits) or make `Value.data` a NumPy array so one node covers a whole tensor. The second is the `hard` track.
</Accordion>
</AccordionGroup>
