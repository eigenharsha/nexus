**`LAB-P3-W23`** — one lab, three tracks. Beginners start at `basic` and climb.
Working professionals start at `standard`. `hard` is where the interview stories come from.
</Note>

## The ticket

> **From: Platform Ops**
> **To: you**
> **Subject: we are not running your notebook**
>
> The Week-22 model exists as a notebook and a `.pt` file on your laptop. We will not run a
> notebook in production, and the last time someone handed us a model file it was called
> `final_v3_real.pt` and nobody could tell us which commit produced it or what it scored.
>
> What we need: a versioned artifact we can trace, validated inputs, health checks that mean
> what they say, an image small enough that a pod starts in seconds, CI that builds and pushes
> it, and a deployed URL. Plus a number for what it costs us per thousand predictions, with the
> arithmetic shown — finance asks and "it's cheap" is not an answer.

**Time box: 12–14 hours** across the three tracks.

<Info>
**The 600 MB image limit is the constraint that makes this lab.** A naive `pip install torch`
image is around 2.5 GB. Getting under 600 MB forces the multi-stage build, the CPU-only wheel
index, and — the change that actually gets you there — serving the ONNX artifact from Week 22
Module 5 so PyTorch is never installed in the runtime at all. That last one is worth 851 MB.
</Info>

## Tracks

<Tabs>
<Tab title="basic">

**2–3 hours.** A FastAPI wrapper around the model plus a Dockerfile that builds and runs locally, with a documented `docker run` command that returns a prediction.

About 60% is written, with `TODO`s marked and a one-line hint above each. You fill in:

- The lifespan handler that loads the model **once** at startup.
- The `/v1/predict` handler, including reading the upload and returning the response model.
- The Dockerfile's instruction ordering so a code change does not reinstall dependencies.
- The `docker run` command in the README, with the port mapping and any required environment variables.

**What you must make true**

- `make verify TRACK=basic` is green.
- `docker run` followed by a `curl` returns a JSON prediction.
- You can explain why the model is loaded in `lifespan` and not in the handler, with the two numbers (2.3 rps versus 97).

</Tab>
<Tab title="standard">

**7–8 hours.** The full service. Spec and tests only.

**Acceptance criteria**

1. **A versioned model artifact** — the file, its sha256, the training commit, and the metrics it achieved — recorded in a manifest and served at `/version`.
2. **Validated request and response models.** An out-of-range input returns **422** with a message naming the offending field. Unknown fields are rejected, not silently dropped.
3. **`/healthz` and `/readyz` that mean different things and can disagree.** The test starts the app with the model file absent: `/healthz` must return 200 (the process is alive) and `/readyz` must return 503 (it cannot serve). `/readyz` must **not** check any external dependency.
4. **A multi-stage Docker build under 600 MB**, asserted by the test.
5. **A `docker compose` stack** bringing the service up with its dependencies, using `condition: service_healthy` rather than bare `depends_on`.
6. **GitHub Actions CI** building the image, running the tests inside it, and pushing on a tag.
7. **Deployed to AWS Lambda behind API Gateway** (or a documented equivalent free-tier target).
8. **A load test and a cost report** — cost per 1,000 predictions, with the arithmetic shown, including CloudWatch Logs ingestion and data egress.

<Warning>
The module pages call the readiness endpoint `/ready`; the lab's tests expect **`/readyz`**.
Same concept, and the tests are the contract — use `/readyz`.
</Warning>

**Design notes**

The health-check criterion is the one people get wrong twice. First by making `/readyz` return a constant, which means it can never disagree with `/healthz`. Then by making it check the database, which is the failure mode in Module 2's war story — a 90-second dependency blip became a five-minute total outage because every replica went unready simultaneously. Readiness checks **process-local state only**: is the model loaded, did the warm-up succeed, are we shutting down.

<Info>Spec and tests only. `make verify TRACK=standard`.</Info>

</Tab>
<Tab title="hard">

**5–7 hours.** **p95 under 300 ms including cold starts**, with a canary deployment and an automatic rollback on an error-rate threshold.

**The constraint the `standard` solution fails:** the standard track's p95 is warm-only, at about 61 ms. Include cold starts and a 3.2-second init blows straight through a 300 ms budget the moment traffic is anything but continuous.

**Acceptance criteria**

1. **p95 &lt; 300 ms measured *including* cold starts**, with the mitigation you chose and its cost stated. Your options and what they cost, from Module 5: a smaller image (free, 8.7 s → 1.9 s), more memory (+24% per request), provisioned concurrency ($21.90/month per instance at 2 GB), or a warming ping (~$0.03/month and it only keeps one environment warm).
2. **A canary deployment** routing a percentage of traffic to the new version — a Lambda alias with weighted routing is the cheapest way to do this.
3. **Automatic rollback triggered by an error-rate threshold**, demonstrated by deliberately deploying a broken version and showing the rollback in the logs.

<Warning>
**No number, no credit.** "I used provisioned concurrency" is not a deliverable. "Provisioned
concurrency of 2 at 2 GB costs $43.80/month and takes p95 from 3,410 ms to 71 ms; a 280 MB image
takes it to 2,100 ms for free; I chose X because Y" is.
</Warning>

**A note on the cost of this track.** Provisioned concurrency bills continuously. If you enable it, **set a reminder to disable it** and run the teardown checklist. Two instances left on for a month is $43.80.

</Tab>
</Tabs>

## Verify yourself

```bash
cd labs/p3/week-23
make help
cat standard/SPEC.md
$EDITOR starter/

make verify                  # TRACK=standard against starter/ — red until you finish
make verify TRACK=basic
make verify TRACK=hard
make verify IMPL=solution    # proves the tests are honest
make contract                # asserts solution green AND starter red
make bench                   # the load test and the cost report
```

`tests/` ships one named test per acceptance criterion, each with the criterion as its docstring
and a `pytest.fail("not implemented yet")` body. **Turning those into real assertions is the
first half of the lab**; passing them is the second. That is deliberate — writing the test that
checks "the image is under 600 MB" makes you decide what "the image" means and how you measure it.

## Milestones, in order

<Steps>
<Step title="Set a billing alarm (10 min)">
Before anything else. `EstimatedCharges` at $5. Module 5's war story is a weekend that cost $4,200 and it started with a deploy on a Friday.
</Step>
<Step title="Split the notebook (60 min)">
`train.py`, `predict.py`, and one shared `preprocess.py` imported by both. Then the parity test: one fixture image through both paths, asserted identical to 1e-5. That test is the highest-value line in the repo.
</Step>
<Step title="The manifest and /version (30 min)">
Version, git SHA, git-dirty flag, model sha256, preprocess version, class list, metrics. Write it atomically (temp directory plus rename). Then delete the manifest and confirm the service refuses to start.
</Step>
<Step title="The service (75 min)">
Lifespan load plus warm-up, `def` handler, Pydantic schemas with `extra="forbid"`, `/healthz`, `/readyz`, `/version`, `/v1/predict`. Then the health-check test: start with the model absent and assert the two endpoints disagree.
</Step>
<Step title="Load-test it (45 min)">
Ramp offered load in seven steps through saturation. Plot achieved RPS and p99 against offered RPS and **mark the knee**. Then fix the threading (`OMP_NUM_THREADS=1`, workers = CPU limit) and re-measure. Expect roughly 2.3 → 97 rps across the module's five configurations.
</Step>
<Step title="The image, one change at a time (90 min)">
`.dockerignore` → slim base → multi-stage → no pip cache → ONNX instead of torch. **Measure after each and record the saving.** The savings must sum to the total. Expect 3,140 MB → 466 MB and a rebuild after a code change of 214 s → 11 s.
</Step>
<Step title="compose (30 min)">
API plus Postgres, health checks on both, `condition: service_healthy`, resource limits, and no secret in the file.
</Step>
<Step title="CI (75 min)">
Two parallel jobs — checks and image — then deploy. Lint, type-check, tests, the preprocessing parity test, `trivy --ignore-unfixed`, build with `cache-from/to: type=gha`. Record each step's duration and compute the critical path.
</Step>
<Step title="Deploy to Lambda (60 min)">
Container image, model loaded at module level with a warm-up, 2,048 MB, deployed **by digest**. Test locally with the Runtime Interface Emulator first. Measure warm p50/p95/p99 and forced cold starts.
</Step>
<Step title="The cost report (45 min)">
Per-request arithmetic including compute, invocation, gateway, **CloudWatch Logs ingestion and data egress** — those two are 27% of the bill and are missing from most estimates. Then the crossover against an always-on VM, with both lines plotted.
</Step>
<Step title="Tear it down (10 min)">
The checklist from Module 5. Then check the billing console. An ECR repository holding a few 466 MB images is a small recurring charge that surprises people two months later.
</Step>
</Steps>

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
A live URL plus `DEPLOYMENT.md` with the architecture diagram and the cost analysis.
</Card>

`DEPLOYMENT.md` must contain:

1. **An architecture diagram.** Client → API Gateway (or Function URL) → Lambda → the artifact. Mermaid is fine. Mark where the model lives and where the version is recorded.
2. **The image-size table** — six rows, each with the change and its saving, plus a final breakdown that accounts for every megabyte of the finished image.
3. **The load-test curve**, with the knee marked and the capacity stated as a number at a stated p99.
4. **Cold versus warm latency**, and which mitigation you chose with its cost.
5. **The cost per 1,000 predictions with the arithmetic shown**, and the crossover against an always-on VM.
6. **The SLO** — one sentence with two numbers — and the error budget it implies.
7. **The teardown commands**, so a reader can reproduce the deploy without leaving a bill behind.

<Tip>
**The cost section is what makes this repo different.** Almost every portfolio deployment project
ends at "here is the URL". A page that says "$3.20 per million requests, rising to $4.41 once you
count logs and egress; the crossover against a `t4g.small` is 126,000 requests/day; here is the
chart" reads like it was written by someone who has run a service.
</Tip>

## If you get stuck

<AccordionGroup>
<Accordion title="The image will not go under 600 MB">
You still have PyTorch in the runtime image. Run `docker history --no-trunc` and look for a layer near 962 MB. The fix is serving the ONNX artifact from Week 22 Module 5 with `onnxruntime`, and removing `torch` from the serving dependency group entirely. If you must keep PyTorch, `--index-url https://download.pytorch.org/whl/cpu` at least avoids the 2.6 GB CUDA build.
</Accordion>
<Accordion title="ImportError: libGL.so.1 or libgomp.so.1 in the container">
`opencv-python` instead of `opencv-python-headless` for the first; a missing `libgomp1` on the slim base for the second. Both are one-line fixes and together they cost 3 MB. Module 3's common-mistakes table has the full list.
</Accordion>
<Accordion title="/healthz and /readyz never disagree in the test">
`/readyz` is probably returning a constant. It must reflect actual process state: a flag set at the end of the lifespan handler, after the model loaded and the warm-up succeeded. The test starts the app with the model absent, so the flag must never be set in that case — and the app must still start, so the load failure has to be caught rather than raised out of `lifespan`.
</Accordion>
<Accordion title="Throughput is far below 97 rps">
Three candidates, in order: the model is being loaded per request; the handler is `async def` around a blocking call, so the event loop is stalled; or `OMP_NUM_THREADS` is unset and your workers are fighting over cores. Module 2's five-rung table has the measured number for each.
</Accordion>
<Accordion title="Runtime.HandlerNotFound on the first Lambda invoke">
`CMD` in a Lambda image is `module.function`, not a shell command — `CMD ["handler.handler"]`. It fails at invoke time, not build time, which is why it surprises people.
</Accordion>
<Accordion title="Cold start is 8+ seconds">
Your image contains PyTorch. `import torch` alone is 1.4 s of every cold start, before the image pull. The ONNX variant measures 3.2 s and a minimal int8 one measures 1.9 s.
</Accordion>
<Accordion title="Warm latency is ~400 ms instead of ~42 ms">
The model is being constructed inside the handler rather than at module level. Compare `Duration` against `Init Duration` in CloudWatch: if `Init Duration` is small and `Duration` is around 400 ms, that is it.
</Accordion>
<Accordion title="You cannot get p95 under 300 ms on the hard track">
You are measuring cold starts in the p95, which means your traffic pattern has enough gaps to keep creating environments. Either raise the traffic rate in the test (and say so), shrink the image, or pay for provisioned concurrency. **All three are legitimate — what is not legitimate is reporting a warm-only p95 and calling it done.** State what you measured and under what arrival pattern.
</Accordion>
</AccordionGroup>
