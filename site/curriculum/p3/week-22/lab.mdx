## The ticket

> **From: Pathology lab, regional hospital group**
> **To: you**
> **Subject: pre-screen for white-cell differentials**
>
> Our technicians count and classify white blood cells manually. It is slow and it is the
> bottleneck in our turnaround time. We want a pre-screen that classifies cells into four
> types so a human only reviews the ones the model is unsure about.
>
> Two hard constraints, neither negotiable:
>
> 1. **We will not deploy anything below 90% test accuracy.** Our current inter-technician
>    agreement is around 92%, so below 90% we are adding noise rather than removing work.
> 2. **Our hardware is a CPU box in a room with no GPU** and no plans for one. Whatever you
>    train, it has to run there.
>
> Give us the latency and size table for the model you would actually ship — not the one that
> scored best on your machine.

**Time box: 12–14 hours** across the three tracks.

<Info>
Read the second constraint again. It changes the answer. The highest-accuracy backbone in this
week's comparison table (EfficientNet-B0, 94.9%) is **1.5× slower on CPU than ResNet-18**
despite having half the parameters, and ViT-B/16 has the best ImageNet score, the worst accuracy
here, and 7.6× the latency. A lab that reports only accuracy has not done the job.
</Info>

<Tab title="standard">

**7–8 hours.** The full project. Spec and tests only.

**Acceptance criteria**

1. **A dataset audit, done first and reported before you train anything.** Class balance, corrupt files, label spot-checks, and — the one that matters — **near-duplicates across the train/test split.** This dataset is augmented from a smaller set of source images; a naive per-file random split leaks and reports about 3.6 points of accuracy that does not exist.
2. **An augmentation policy chosen for this domain and justified**, plus **one you rejected with the reason.** Vertical flip is fine for cells and wrong for street photos; random grayscale is catastrophic here because stain colour carries the label (measured: −4.2 points).
3. **A from-scratch CNN baseline**, then **transfer learning** from ResNet-18 or EfficientNet-B0, with the freeze/unfreeze schedule documented.
4. **≥ 90% accuracy on the held-out test split** — touched once, at the end.
5. **Mixed precision (AMP) where a GPU is present**, with the CPU path still correct. Watch the `scaler.unscale_()` ordering; getting it wrong costs 1.9 points silently.
6. **Checkpointing that resumes correctly mid-epoch** (Week 21 Module 5).
7. **Per-class precision / recall / F1 and a confusion matrix.**
8. **Error analysis of the 20 worst misclassifications**, with a written pattern. Categorize each by hand: ambiguous / label error / image quality / real model error.
9. **A model card** — intended use, training data, metrics by class, known limitations, and what would make it unsafe to deploy.

**Design notes**

The dataset audit is not a formality. Near-duplicate leakage across a split is the single most common reason a medical-imaging model reports 97% and delivers 70%. Do the check before you spend an evening training.

Freeze the BatchNorm **statistics**, not just `requires_grad` — a "frozen" backbone in `train()` mode is still moving. Worth about a point of accuracy and a 4.7× reduction in run-to-run variance.

<Info>Spec and tests only. `make verify TRACK=standard`.</Info>

</Tab>
<Tab title="hard">

**5–7 hours.** ≥93% accuracy **under a CPU inference-latency budget**, with ONNX export and a measured latency/size table.

**The budget: p95 ≤ 60 ms at batch 1 on 4 vCPU**, single request in flight. (`hard/targets.md` is the authoritative source if your copy of the lab has it; use this figure otherwise.) That number is chosen to bite: at 200 cells per slide it is 12 s of processing, which the lab can staff. It **excludes EfficientNet-B0 (p95 91 ms), ResNet-50 (147 ms) and ViT-B/16 (401 ms)** — including the most accurate model in the week's comparison table.

**The constraint the `standard` solution fails:** the `standard` track optimizes accuracy on a GPU. The lab's box is CPU-only, and the highest-accuracy model is not the one that fits.

**Acceptance criteria**

1. **≥ 93% test accuracy under the stated CPU p95 latency budget**, measured on 4 vCPU with a single request in flight. Both numbers or neither.
2. **ONNX export with output parity to the PyTorch model within 1e-4**, verified at **two batch sizes** so the dynamic axes are actually exercised.
3. **A latency and size table**: PyTorch eager, TorchScript, ONNX Runtime fp32, and a quantized variant — p50 and p95 latency plus file size for each. The reference gets 41 / 38 / 23 / 14 ms and 44.7 / 44.9 / 44.7 / 11.3 MB.
4. **Grad-CAM explanations for five predictions, including at least one the model got wrong.** The wrong one is the interesting one — a Grad-CAM that highlights the image border or a staining artifact tells you something a confusion matrix cannot.

<Warning>
**No number, no credit.** The deliverable is a write-up containing what the straightforward
approach measured, what yours measures, and the sentence explaining why. A model that hits 93%
with no latency measurement fails this track.
</Warning>

</Tab>

## Milestones, in order

<Steps>
<Step title="Audit before you train (60 min)">
Class counts. Corrupt files (`PIL.Image.open` in a try/except over everything). Perceptual hashes to find near-duplicates. Group the augmented copies by source image. Open 20 random images and check the labels yourself. **Write the findings down before you build a model** — this document is a graded deliverable and it is the one that separates a project from a notebook.
</Step>
<Step title="Build the grouped split (30 min)">
By source image, not by file. Then, for the write-up, build the naive per-file split too and report the accuracy difference. Roughly 3.6 points of phantom accuracy is a persuasive number to have measured yourself.
</Step>
<Step title="From-scratch baseline (45 min)">
`BloodCellNet` from Module 2, or your own. Expect 84–87%. You need this number to say what transfer learning bought you.
</Step>
<Step title="Transfer learning to the bar (90 min)">
Frozen backbone + head first (≈89.6%), then staged unfreezing with discriminative LRs (≈94.4%). Freeze the BatchNorm statistics. You should clear 90% comfortably.
</Step>
<Step title="Backbone comparison on the real constraint (75 min)">
At minimum MobileNetV3-Small, ResNet-18 and EfficientNet-B0. For each: test accuracy, CPU p50 and p95 at batch 1, and file size. **The recommendation is the deliverable**, and it should not be "the most accurate one".
</Step>
<Step title="Per-class metrics and error analysis (60 min)">
Classification report, confusion matrix, and the 20 highest-loss examples displayed with true label, prediction and confidence. Categorize each by hand. The reference run found 5 label errors, 8 genuinely ambiguous, 4 quality problems and only 3 real model errors — write down your split.
</Step>
<Step title="Export, quantize, measure (60 min)">
ONNX with `dynamic_axes`, parity at two batch sizes, then `quantize_dynamic`. Build the four-row latency/size table. Report the accuracy delta from quantization — usually about 0.2 points, but report *your* number.
</Step>
<Step title="Model card and write-up (60 min)">
The deliverable the lab actually asked for. See below.
</Step>
</Steps>

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
A public repo plus a deployed demo. The API comes next week — this week, ship the model card and
the numbers.
</Card>

Your **model card** must contain:

1. **Intended use, and explicitly out-of-scope use.** "Pre-screen to route slides for human review" is in scope. "Autonomous diagnosis" is not, and saying so is part of the job.
2. **Training data** — source, size, splits, how the split was made, and the near-duplicate finding.
3. **Metrics, per class, with a confidence interval.** On a 1,879-image test set, the 95% Wilson interval on 93.8% is about [92.6, 94.8]. Quote it.
4. **The confusion matrix**, and the sentence naming which two class pairs are most of the errors.
5. **Known limitations** — the 5 label errors you found put a ceiling on any measured number; performance on out-of-focus images; behaviour on stains from a different protocol, which you have not tested.
6. **The deployment recommendation** with the latency table, and why it is not the highest-accuracy model.
7. **What would make this unsafe to ship** — the honest paragraph. Distribution shift from a new stain batch or a new microscope is the realistic one, and you cannot detect it from accuracy alone (Week 24 Module 5).

It demonstrates that you looked at your data, which is the thing almost no portfolio project

## Stuck? Open these in order

Each reveals a little more than the last. Try the level above before opening the next — a hint you
did not need costs you nothing, but an answer taken too early costs you the lesson.

<AccordionGroup>
<Accordion title="Nudge — I don't know where to start" icon="lightbulb">
Find the **first** failing test and implement only what that one test needs. Ignore the rest of the
lab until it is green. If you cannot tell which test fails first, run
`make verify TRACK=basic` and read the top of the output, not the bottom.
</Accordion>

<Accordion title="Hint — my model hits 99% on training data and 60% on test" icon="lightbulb">
Overfitting, and with a small image set it happens fast. The model is memorising, not generalising.

**What to do instead:** Add augmentation (flips, rotations, colour jitter), then weight decay, then early stopping on validation loss. If train and validation diverge in the first two epochs, your dataset is too small for training from scratch — use transfer learning instead.
</Accordion>

<Accordion title="Hint — my GPU utilisation is low and training is slow" icon="lightbulb">
The input pipeline is starving the model. The GPU waits on the CPU to decode and augment images.

**What to do instead:** Raise `num_workers` on the DataLoader, enable `pin_memory`, and check utilisation while training. The week's own measurement takes a loop from 30% to above 85% by fixing only the data path.
</Accordion>

<Accordion title="Hint — my transfer-learning accuracy is worse than training from scratch" icon="lightbulb">
Usually the normalization. A pretrained backbone expects the exact mean and standard deviation its original dataset used; feed it differently-scaled inputs and the learned features do not apply.

**What to do instead:** Use the documented normalization constants for your chosen backbone, and freeze the backbone for the first few epochs so the randomly-initialized head does not destroy pretrained weights with large early gradients.
</Accordion>

<Accordion title="I have a real attempt that fails — show me the full solution" icon="lock">
Open the [reference solution](/solutions/p3/week-22/lab).

Use it properly: read only far enough to get unstuck, then close it and return to your own code.
Afterwards, diff your version against it — the differences are the lesson, and yours is not
automatically the worse one.

If you have not yet written code that fails, do not open it. Reading a solution before struggling
with the problem feels exactly like learning, and is the most reliable way to finish this course
having learned nothing.
</Accordion>
</AccordionGroup>

## If you get stuck

<AccordionGroup>
<Accordion title="Test accuracy is 97% and you are suspicious">
Good instinct. Check for near-duplicate leakage — this dataset is augmented from a smaller set of sources, and a per-file random split puts rotations of the same image on both sides. Group by source ID. Expect the honest number to be around 3.6 points lower.
</Accordion>
<Accordion title="Transfer learning is barely beating from-scratch">
Three usual causes: (1) you skipped the head-only stage, so a random head sent large gradients into the pretrained backbone — costs 1.7 points; (2) you used your dataset's normalization statistics instead of ImageNet's — costs 1.1; (3) you froze `requires_grad` but left BatchNorm in `train()` mode. Module 4 covers all three.
</Accordion>
<Accordion title="AMP run is worse than the FP32 run">
Almost certainly `clip_grad_norm_` before `scaler.unscale_()`. Log the pre-clip norm — if it reads in the tens of thousands rather than 0.4–2.0, that's it. Costs about 1.9 points and produces no warning.
</Accordion>
<Accordion title="ONNX export raises UnsupportedOperatorError">
Check the opset first — many operators were added in 16 or 17. If raising the opset doesn't help, find the operator in the ONNX operator schema list and either rewrite it with supported primitives or `torch.jit.script` that module. Adaptive pooling with a non-1 output size is a common offender; `AdaptiveAvgPool2d(1)` exports fine.
</Accordion>
<Accordion title="ONNX parity test fails at 1e-4">
Try `rtol=1e-3, atol=1e-5`. The two runtimes fuse and reorder floating-point operations differently, so bitwise agreement is not achievable and demanding it fails on correct exports. If it still fails at 1e-3, you have a real problem — most likely a traced-away branch or a shape assumption.
</Accordion>
<Accordion title="CPU latency is far worse under load than in your benchmark">
Thread oversubscription. If you're serving with multiple workers, each one is probably spawning threads equal to your core count. Set `OMP_NUM_THREADS=1` **before importing** torch or onnxruntime, and `intra_op_num_threads=1`. Module 5 measures this at p99 340 ms → 61 ms.
</Accordion>
</AccordionGroup>
