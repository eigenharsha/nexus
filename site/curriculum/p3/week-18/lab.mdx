## The ticket

> **NEX-1803 — Who do we call, and is it worth calling them?**
> **Reporter:** Dan, Retention
> **Priority:** P1
>
> We lose about 26% of the base a year. Retention has capacity for **300 outbound calls a week**
> and a save offer that costs us **£90** when accepted. An average saved customer is worth
> **£840** in the following twelve months.
>
> Right now the call list is "month-to-month contract, sorted by monthly charges descending".
> Nobody has ever measured whether it beats picking at random.
>
> I need three things. A number for how good the current list is. A model that beats it, with
> the improvement stated in pounds per week. And a one-pager I can take to the CFO that does
> not contain the word AUC.

Note what the ticket does *not* ask for: the best possible model. It asks for a measured baseline, a defensible improvement, and a translation into money. That ordering is the lab.

<Warning>
There is a data-quality trap in this file and finding it is part of the lab. `TotalCharges` is stored as a string; `pd.to_numeric(..., errors="coerce")` turns 11 of them into `NaN`. All 11 have `tenure == 0` — they are customers who signed up and have not yet been billed. That is not a missing value to impute with the median; it is a genuine zero, and a `tenure_is_zero` indicator carries real signal. Imputing the median here puts a £1,400 lifetime spend on a customer who has spent nothing.
</Warning>

### The progression, in order

Every step must be measured before you move to the next. This is the deliverable — the *progression*, not the final model.

| Step | What | AUC | Average precision | Brier | **precision@75** |
| --- | --- | --- | --- | --- | --- |
| 0 | majority-class baseline | 0.5000 | 0.2652 | 0.1949 | 0.2652 |
| 0b | the heuristic from the ticket, as a score | 0.8031 | 0.5606 | 0.2105 | **0.7200** |
| 1 | logistic regression in a leak-free `Pipeline` | 0.8466 | 0.6381 | 0.1363 | 0.7733 |
| 2 | random forest, 500 trees, `min_samples_leaf=5` | 0.8445 | 0.6444 | 0.1362 | — |
| 3 | XGBoost, `max_depth=3`, early-stopped | **0.8490** | **0.6560** | **0.1345** | **0.8533** |

(Reference numbers: 75/25 stratified split, `random_state=42`, 1,761 test rows, scikit-learn 1.9.0, XGBoost 2.1.4, measured on an M3 Pro. Yours will differ in the third decimal. `precision@75` is the top 4.26% of the test set, which is what 300 calls a week out of a 7,043-customer base works out to.)

**Look hard at the last two columns, because between them they contain the lab's whole lesson.**

Read the AUC column and the models are indistinguishable: 0.8031 for three business rules, 0.8466 for logistic regression, 0.8490 for a tuned XGBoost. The gap from logistic regression to XGBoost is **0.0024**, which on 1,761 test rows is nothing. You would reasonably conclude that the modelling was not worth doing.

Now read the `precision@75` column — the metric that matches what the retention team actually does. The heuristic's call list is **72.0%** churners. XGBoost's is **85.3%**. That is 13 extra real churners in every 100 calls.

Bootstrapped over 3,000 resamples of the test set:

```
precision@75, XGBoost minus heuristic : +0.1210   95% CI [+0.0133, +0.2267]   <- real
precision@75, XGBoost minus logreg    : +0.0598   95% CI [-0.0267, +0.1467]   <- not established
```

Two conclusions, and both belong in your write-up. **The aggregate metric hid the entire value of the project**, because AUC averages over every threshold including the 95% of the score range nobody will ever operate at. And **the difference between logistic regression and XGBoost is not established** on this data — the interval crosses zero, so claiming XGBoost as the win would be overclaiming.

Week 19 makes both of these rigorous. Here, notice that the ticket told you the capacity in its second paragraph and the metric followed from it.

### Acceptance criteria

| # | Criterion | How it is checked |
| --- | --- | --- |
| A1 | No leakage | every fitted transformer is inside a `Pipeline`; the leakage test in `tests/` must pass |
| A2 | The full progression | all five rows of the table above, with AUC, average precision **and** Brier for each |
| A3 | Proper validation | 5-fold `StratifiedKFold` for model comparison; a separate held-out test set touched once |
| A4 | Early stopping done correctly | a three-way split: XGBoost's `eval_set` must not be the test set |
| A5 | Permutation importance | on held-out data, `n_repeats>=15`, reported with its standard deviation. `feature_importances_` must not appear in the report |
| A6 | Calibration check | reliability curve, 10 bins, plus the Brier score. State whether calibration is adequate for the cost calculation |
| A7 | Threshold from the cost matrix | not 0.5, and not the F1 maximiser. Derive it from the ticket's £90 and £840 |
| A8 | Segmentation | K-Means on the predicted churners, passing the two tests from Module 4 Layer 2 |
| A9 | The one-pager | expected weekly value in pounds, no ML jargon, one page |

### The threshold calculation

This is the step that turns the model into the deliverable, and it is the one most submissions get wrong by reaching for F1.

Retention calls the top 300 by score each week. For a customer you call:

- If they *would* have churned and the offer saves them: you gain **£840** and spend **£90**.
- If they *would not* have churned: you spend **£90** on someone who was staying.
- If you do not call a customer who churns: you lose the **£840**.

So the decision is not a threshold at all — it is a **capacity constraint**. The metric is **precision at 300**, and the expected weekly value is:

```
value_per_week = 300 * precision@300 * save_rate * 840  -  300 * 90
```

You do not know `save_rate` — nobody has run the experiment. State that explicitly, present the answer as a function of it, and find the break-even. That honesty is worth more marks than a single confident number.

<Warning>
If your report contains a threshold chosen by maximising F1, you have optimised a quantity nobody in the ticket cares about. F1 weights precision and recall equally, and the ticket weights them 840 to 90. Week 19 Module 1 and Week 20 Module 4 make this rigorous; here, just notice that the ticket gave you the numbers and F1 ignores them.
</Warning>

### The model card

A one-page markdown file with these sections, following the Mitchell et al. (2019) structure:

```
# Model card: telco churn scorer v1
## Intended use          who calls it, how often, for what decision, capacity 300/week
## Out of scope          what this must NOT be used for (pricing, credit, anything per-individual
                         and consequential without a human)
## Training data         source, date range, 7,043 rows, 26.54% positive, known quality issues
                         (the 11 tenure-0 rows)
## Metrics               AUC, AP, Brier, precision@300 — on a held-out set touched once
## Slices                performance by contract type, tenure band, and internet service.
                         Report the WORST slice, not the average
## Ethical considerations proxies for protected attributes; who is harmed by a false positive
## Caveats               save_rate is unmeasured; the model is trained on a single snapshot
## Version / owner       pinned library versions, git SHA, who to page
```

  <Tab title="hard">

**Beat a target under a training-time budget, explain five individuals, and write the card.**

| # | Criterion | Budget |
| --- | --- | --- |
| H1 | **`precision@75` at or above 0.8200** on the held-out set | with a stated, reproducible split |
| H2 | **Total training time under 120 seconds** | wall clock for the entire final pipeline fit including any search, measured with `time.perf_counter` |
| H3 | SHAP explanations for 5 individual customers | in the correct units, with the base value stated |
| H4 | Model card | complete, including a slice table |
| H5 | **A written ceiling analysis** | bootstrap the `precision@75` difference against *both* the heuristic and logistic regression, 2,000+ resamples, and report both intervals — including the one that crosses zero |

**H1 is the achievable target and H5 is the hard one.** Note carefully that H1 is *not* an AUC target. Setting one would have been a trap: this dataset has a hard ceiling around **0.85 AUC** and no amount of tuning or feature engineering gets past it. Measured, with twelve engineered features (spend ratios, service counts, tenure bins, the `tenure == 0` indicator) and a 12-configuration search:

```
engineered XGBoost   test AUC 0.8461
engineered logreg    test AUC 0.8461
baseline logreg      test AUC 0.8466        <- the RAW features
bootstrap AUC improvement over baseline: -0.0005   95% CI [-0.0073, +0.0065]
```

**Feature engineering bought nothing measurable on this dataset.** That is a real result, it is worth reporting, and a lab that demanded 0.86 AUC would have been asking you to fake it. Any submission that claims to have reached 0.86 by legitimate means should be re-checked for leakage against `tests/test_no_leak.py` first.

So `hard` is not "get a bigger number". It is **establish where the ceiling is and prove you are at it**. Concretely:

- Hit `precision@75 >= 0.82`, which the reference XGBoost reaches at 0.8533 and logistic regression does not (0.7733).
- Show, with bootstrap intervals, that the model beats the heuristic (reference: `+0.1210, 95% CI [+0.0133, +0.2267]`) and that the gap to logistic regression is **not** established (reference: `+0.0598, 95% CI [-0.0267, +0.1467]`).
- Try feature engineering anyway — the ratios, the service counts, the tenure bins — and report honestly whether it moved anything. Reporting a null result correctly is the criterion.

You still need the features to explore, so here they are, in rough order of plausibility:

- **Ratios and interactions.** `TotalCharges / tenure` (average monthly spend to date) versus `MonthlyCharges` — the gap between them is a price-increase detector, and Module 1 Layer 3 explains why a tree needs that written down rather than being able to discover it.
- **Service counts.** The nine service columns (`OnlineSecurity` through `StreamingMovies`) collapse into a count of subscribed services and a "no internet" flag. One strong ordinal feature instead of nine weak categorical ones.
- **The `tenure == 0` indicator**, and a `tenure` binning that separates the first three months from the rest, because churn is far from linear in tenure.

<Warning>
Do not chase H1 by fitting on the test set, by tuning against it, or by fitting the reducer or encoder outside the pipeline. The `tests/test_no_leak.py` harness re-runs your pipeline on a shuffled-label copy of the data and asserts that AUC lands within `0.50 ± 0.03`. Every form of leakage in Week 19 Module 4 fails that test.
</Warning>

The one-pager is the artifact that will get you promoted, and it is the one nobody practises. Constraints:

- **One page.** If it is two pages, the CFO reads the first paragraph.
- **No ML vocabulary.** No AUC, no precision, no model names. "Of the 300 people we call, about 120 would have left, against about 75 under the current list."
- **Money, with the assumption stated.** "At a 25% save rate this is worth about £2,300 a week; at 10% it breaks even. Nobody has measured the save rate, and measuring it is a two-week experiment I would run before scaling this."
- **One picture.** A bar chart of expected weekly value against `save_rate`, with the break-even marked.
- **What you would do next**, in three bullets, ranked.

Tag `v1.0.0`, push, and link it. A repo with a model card in it reads very differently from a repo with a notebook in it.

## Common ways this lab goes wrong

| Symptom | Cause | Fix |
| --- | --- | --- |
| Accuracy 0.80 reported as a success | no baseline; majority class is 0.7346 | always report the baseline in the same table |
| AUC 0.94 | leakage — usually the encoder or scaler fitted on all data, or a target-derived column | run `tests/test_no_leak.py`; the measured ceiling on this dataset is about **0.85** |
| XGBoost "beats" logistic regression by 0.0024 AUC | that is inside the noise on 1,761 test rows | bootstrap the difference; the measured `precision@75` interval is [-0.0267, +0.1467], which crosses zero |
| "The model is no better than the rules" | you compared on AUC, which averages over thresholds nobody operates at | compare at the operating capacity: 0.7200 versus 0.8533 at `precision@75` |
| Feature engineering reported as a win | on this dataset it measured at -0.0005 AUC, CI crossing zero | bootstrap it; a null result reported honestly scores better than an unsupported claim |
| 11 `NaN` in `TotalCharges` imputed with the median | those rows have `tenure == 0` and genuinely spent nothing | set to 0 and add a `tenure_is_zero` indicator |
| `feature_importances_` in the report | impurity importance, biased and computed on training data | held-out permutation importance with its standard deviation |
| Threshold chosen by maximising F1 | F1 weights the two errors equally; the ticket weights them 840 to 90 | use the capacity constraint: precision at 300 |
| Model card has no slice table | averages hide the failure | report per-contract-type and per-tenure-band metrics, and name the worst |
| One-pager mentions AUC | wrong audience | rewrite in customers, calls and pounds |
