<Note>
By Sunday you have a checkout service that sells exactly ten items when ten are in stock, under 200
concurrent buyers, with a written comparison of four concurrency strategies and their measured
throughput. This is the strongest single artifact in Phase 1.
</Note>

This is the week that separates "it works on my laptop" from production. Week 7 gave you a schema
and queries. This week makes them correct when many people use them at once, and fast when there is
real data in them.

Everything here is measured on a live PostgreSQL 16.14 instance. The two-session transcripts are
verbatim output from two `psql` sessions run side by side; the throughput tables come from a 200-
thread harness you will rebuild yourself.

## The numbers this week produced

Every one was **measured** on a live PostgreSQL 16.14 instance running in Docker on an Apple
Silicon laptop — including the anomaly transcripts, which are verbatim server output rather than
illustrations. Each is explained in the module that produced it. The reproduction log, with the
psql sessions and the deadlock and SSI errors as PostgreSQL emitted them, is committed at
`evidence/phase-1-w05-08-measurements.md`; see [About the numbers](/start/about-the-numbers) for what "measured" commits us to. Throughput numbers scale with your
machine; the ordering of the five concurrency strategies, and which anomalies each isolation level
permits, do not.

| Fact | Number | Module |
| --- | --- | --- |
| Uncommitted transfer after `SIGKILL` and recovery | fully rolled back; redo done in 1.26 s | M1 |
| Naive read-then-write, 200 buyers, 10 in stock | **sold 200** — 190 oversells | M2 |
| `SERIALIZABLE` throughput cost under contention | 2.8× / 11.3× / 5.4× at 1 / 10 / 100 hot rows | M2 |
| SSI retries to complete 2,000 transactions | 27,261 | M2 |
| Point lookup on 1M rows, index versus none | 0.033 ms versus 86.8 ms — **1,970×** | M3 |
| Write cost of five indexes | 50,000 inserts 788.9 → 1,591.8 ms (**2.02×**) | M3 |
| N+1 versus eager loading | 501 queries / 1,321.5 ms versus 1 query / 44.2 ms | M4 |
| Bulk insert: ORM versus `COPY` | 5,448 ms versus 518 ms (**10.5×**) | M4 |
| Cache stampede, 40 cold readers | 40 DB calls / 1,784 ms → 1 call / 85 ms | M5 |
| Connection pool under-sized | `pool_size=5`: **20 of 40** requests failed | M4, M5 |

## What you should be able to say out loud by Sunday

1. "Both sessions read 10 before either wrote — after that point, nothing can save you without one being aborted."
2. "`REPEATABLE READ` does not prevent write skew; the doctors both went off call and both committed."
3. "The index is there, but the query has no leftmost prefix, so it is a sequential scan."
4. "Latency is high and the database is idle — count the queries, it is an N+1."
5. "The cache did nothing because every cold key produced 40 concurrent misses."

## Prerequisites check

You need the Week 7 database still running, or the ability to reseed it. You should be able to read
an `EXPLAIN ANALYZE` plan (`P1-W07-M3`) and write a FastAPI dependency (`P1-W06-M2`). Two `psql`
sessions side by side is the whole toolkit for module 2 — no framework required.

## Phase 1 exit checkpoint

After this week you should be able to do all four of these unaided, in one sitting:

1. Explain what happens from `malloc` to a Python object to an HTTP response.
2. Ship a small FastAPI + PostgreSQL feature with tests, migrations and an index, from a written ticket.
3. Prove correctness under concurrent load.
4. Present a five-minute walkthrough of your Week 8 repo, answering "why" at each layer.

**Portfolio after Phase 1:** 8 public repos, 1 deployed frontend, 1 deployed API — and one
`CONCURRENCY.md` that is better interview material than all the rest combined.
