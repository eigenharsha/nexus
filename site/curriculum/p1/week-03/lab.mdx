## The ticket

> **NEXUS-341 · The expenses splitter is losing cents, and we cannot swap the storage**
>
> Reported by: internal tools
>
> The team expenses tool has two problems. First, when a bill is split unevenly the totals do
> not reconcile — finance found a group whose shares summed to £199.98 against a £200.00 bill,
> and another where one person owed the entire rounding remainder. Second, it writes to a JSON
> file, and we now need it to write to SQLite for the reporting team, but the storage calls are
> spread through the domain logic so it cannot be swapped without touching everything.
>
> Rewrite it as a proper library. It must be installable, typed, and tested well enough that we
> can trust the arithmetic. And it must be possible to add a third storage backend later
> **without modifying any existing file** — we will need Postgres next quarter.

**Time box.** `basic` 2–3 h · `standard` 6–8 h · `hard` 4–6 h on top of `standard`.

<Tabs>
<Tab title="basic">

**Roughly 60% is written for you.** The test suite, the `pyproject.toml` and the CLI exist. You implement two classes.

```python
# starter/basic/ledger/models.py
@dataclass(frozen=True, slots=True)
class Transaction:
    """An immutable record of money moving. TODO: fields and validation."""

class Account:
    """Holds a balance and a transaction history. TODO."""
```

**Acceptance criteria — all five:**

1. `pytest` passes the 22 provided tests, which cover: deposits, withdrawals, insufficient funds, zero and negative amounts, and an empty account's balance.
2. `Transaction` is `@dataclass(frozen=True, slots=True)` and raises `ValueError` in `__post_init__` for a non-positive amount or an empty description.
3. `Account.balance` is a **read-only `@property`**. `account.balance = 500` must raise `AttributeError`, and there is a provided test for exactly that.
4. Every amount is an **integer number of minor units** (pence/cents). The harness asserts that no float ever reaches a balance — floats are rejected at construction with a clear message. Module 1 of Week 1 explains why.
5. `ruff check` and `mypy` (non-strict) are both clean.

<Info>
Criterion 4 is the one people argue with. `0.1 + 0.2 != 0.3` — Week 1 measured the error at
5.55 × 10⁻¹⁷ per operation, and a ledger accumulating thousands of operations drifts visibly.
Every real accounting system stores integer minor units. So does yours.
</Info>

</Tab>
<Tab title="standard">

**Spec and tests only.** You write the library.

```
ledger/
  __init__.py
  models.py       Transaction, Account — validated, typed, immutable where possible
  exceptions.py   LedgerError and its subclasses
  splitting.py    split_evenly and split_by_weight
  storage/
    __init__.py   the Storage Protocol
    memory.py     in-memory backend
    jsonfile.py   JSON file backend
  cli.py
```

**Acceptance criteria — all nine:**

1. **Validation via properties.** Balances and amounts cannot be set to invalid values from anywhere. Every mutation goes through a method that checks its precondition first.
2. **A custom exception hierarchy** rooted at `LedgerError`, with at least `InsufficientFunds` (carrying `required` and `available` as attributes, not just a message), `AccountNotFound`, and `StorageError`. The harness catches by type and reads the attributes.
3. **A `Protocol`-based storage backend** with two implementations (memory and JSON file). The `Protocol` lives in `storage/__init__.py`; **neither implementation imports it or inherits from it**. `mypy` must verify both satisfy it structurally.
4. **`split_evenly(total, parts)`** returns shares that sum exactly to the total and differ by at most one minor unit. **`split_by_weight(total, weights)`** does the same with weights, using largest-remainder allocation so the shares still sum exactly.
5. **90%+ branch coverage** (`--cov-branch`), and you must be able to defend it: the harness also runs `mutmut` and reports a mutation score. Coverage alone does not pass this row.
6. **`mypy --strict` clean.** No bare `# type: ignore`; any ignore must carry an error code.
7. **`ruff check` clean** with `select = ["E","F","W","I","UP","B","SIM","C4","G","RUF","ARG","PTH"]`.
8. **Installable with `uv pip install -e .`**, and `python -m ledger --help` works from a clean venv.
9. **A `uv.lock` committed**, and `uv sync --frozen` reproduces the environment in CI.

<Info>
Criterion 4 is where the ticket's bug lives. The naive implementation puts the whole remainder
on one share: `split_evenly(2, 3)` returns `[2, 0, 0]` instead of `[1, 1, 0]`. It sums correctly,
so a sum-only test passes. `divmod` plus distributing the remainder is the fix, and the `hard`
track proves it with a property.
</Info>

</Tab>
<Tab title="hard">

**The constraints the `standard` solution fails: prove Open/Closed, and prove the invariant.**

**Acceptance criteria — all six:**

1. **A third backend with zero changes to existing files.** Add `storage/sqlite.py` implementing the same `Protocol`. The harness runs `git diff --stat` against your `standard` commit and **fails if any file other than the new one and its test is modified**. Registration must happen through a mechanism that already exists — an entry point, `__init_subclass__`, or a factory keyed by name — not by editing an `if` in the core.
2. **`hypothesis` invariant tests.** Generate arbitrary sequences of deposits, withdrawals, transfers and splits, and assert after every operation that: the sum of all account balances equals the sum of all deposits minus all withdrawals; no balance is ever negative; and replaying the transaction log from zero reproduces the current state exactly. Use a `RuleBasedStateMachine`.
3. **Splitting properties.** `split_evenly` and `split_by_weight` must satisfy, for all valid inputs: shares sum exactly to the total; shares differ by at most one minor unit (`split_evenly`); no share is negative for a non-negative total; and the result is deterministic. **Report the shrunk counterexample** hypothesis produces on a deliberately broken implementation — ours shrank to `split_evenly(total=2, parts=3)`.
4. **The same test suite passes against all three backends**, parametrised over a fixture so adding a fourth backend adds zero test code.
5. **Round-trip property.** For any sequence of operations, `load(save(state)) == state` for every backend, including edge cases hypothesis will find: empty ledgers, unicode account names, amounts at `sys.maxsize`, and descriptions containing the storage format's delimiters.
6. **Published to TestPyPI**, installable into a clean venv, with a README rendering correctly on the package page.

<Warning>
Two traps are deliberately in this track.

**The Protocol that is not actually satisfied.** `mypy` checks structurally, so a backend whose
`get` returns `dict` where the Protocol says `dict[str, int] | None` fails — but only if the
Protocol is *used* in an annotated position. If nothing is annotated `Storage`, mypy never
checks. The harness verifies that at least one function parameter is annotated with the Protocol.

**The state machine that tests the implementation.** If your invariant is computed the same way
the code computes it, the property is vacuous and will pass on broken code. The balance
invariant must be derived **independently** — sum the transaction log, do not read the cached
balance. The harness injects a mutation that breaks the cached balance while leaving the log
correct; your state machine must catch it.
</Warning>

</Tab>
</Tabs>

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
Published to TestPyPI, installable by a stranger, with a README that documents the API.
</Card>

```bash
uv build                                    # builds sdist + wheel into dist/
unzip -l dist/*.whl                         # CHECK: is every submodule in there?
uv publish --publish-url https://test.pypi.org/legacy/

# then, in a clean venv on another machine or in a container:
uv pip install -i https://test.pypi.org/simple/ --extra-index-url https://pypi.org/simple ledger
python -c "from ledger import Account; print(Account('a').balance)"
```

The README must contain:

1. **Install and 60-second usage**, copy-pasteable, that a stranger can run.
2. **The API surface**: every public class and function with its signature and one line on what it guarantees.
3. **The splitting guarantee stated precisely** — "shares sum exactly to the total and differ by at most one minor unit" — because that is the property your tests check and the ticket's actual requirement.
4. **The Open/Closed proof**: the `git diff --stat` from adding the SQLite backend, showing one new file and nothing else touched.
5. **What hypothesis found**, including the shrunk counterexample and the property that caught it.
6. **One thing you got wrong first.** Graded.

## Verify yourself

```bash
cd labs/p1/week-03
make verify              # ruff + mypy --strict + pytest with branch coverage
make verify-mutation     # mutmut; reports the mutation score, not just coverage
make verify-openclosed   # git diff --stat gate for the hard track
make verify-backends     # runs the full suite against all registered backends
```

`make verify` fails on any ruff finding, any mypy error, coverage below 90% branch, or any test failure. There is no partial credit inside `verify`.

## Start here — your first 30 minutes

The requirements above are the *finished* picture. Do not try to hold all of it at once. Do these in
order; each step ends somewhere you can stop and still be making progress.

<Steps>
<Step title="Run the starter and expect RED (5 min)">
```bash
cd labs/p1/week-03
make verify TRACK=basic
```
A red result is success here — it means the harness runs and the tests can see your code. If you get
something that is *not* a test failure (a missing command, an import error), fix that first; it is an
environment problem, not a lab problem.
</Step>

<Step title="Read one test before writing any code (5 min)">
The tests are the real specification — everything written above is prose describing them. Where the
prose and a test disagree, **the test wins**. Open the first one and read it properly.
</Step>

<Step title="Make ONE test pass (15 min)">
Implement the smallest thing the first failing test needs. Run `make verify` again. One more test
passing is the whole goal of your first half hour.

That is the loop for the entire lab: one test, one function, run, repeat. Do not write five functions
and then run for the first time — when it fails you will not know which one broke it.
</Step>

<Step title="Finish the basic track">
Work the `TODO`s in the order they appear. They are in dependency order, not alphabetical.
</Step>

<Step title="Only then read the standard requirements">
With `basic` green you have something that works. `standard` extends it; it does not replace it.
</Step>

<Step title="Ship it">
Push to a public repo with the README. That artifact is what you link from a CV — it outlasts the grade.
</Step>
</Steps>

## Stuck? Open these in order

Each reveals a little more than the last. Try the level above before opening the next — a hint you
did not need costs you nothing, but an answer taken too early costs you the lesson.

<AccordionGroup>
<Accordion title="Nudge — I don't know where to start" icon="lightbulb">
Find the **first** failing test and implement only what that one test needs. Ignore the rest of the
lab until it is green. If you cannot tell which test fails first, run
`make verify TRACK=basic` and read the top of the output, not the bottom.
</Accordion>

<Accordion title="Hint — my tests pass individually but fail when run together" icon="lightbulb">
Shared state between tests. The usual cause in this lab is a mutable default argument or a class attribute used where an instance attribute was meant — both are created once, at definition time, and then survive across every test in the session.

**What to do instead:** Change any `def f(x, items=[])` to `def f(x, items=None)` and build the list inside. For classes, check that everything mutable is assigned in `__init__`, not in the class body.
</Accordion>

<Accordion title="Hint — mypy --strict fails on code that obviously works" icon="lightbulb">
`--strict` refuses anything it cannot prove, which is the point — it catches the `None` you did not consider. Most failures here are a function that can return `None` on one path but is annotated as returning a value.

**What to do instead:** Read the error's line number and ask: what is the type on *every* path out of this function? Then either annotate it `-> X | None` and handle the `None` at the call site, or make the function raise instead of returning `None`.
</Accordion>

<Accordion title="I have a real attempt that fails — show me the full solution" icon="lock">
Open the [reference solution](/solutions/p1/week-03/lab).

Use it properly: read only far enough to get unstuck, then close it and return to your own code.
Afterwards, diff your version against it — the differences are the lesson, and yours is not
automatically the worse one.

If you have not yet written code that fails, do not open it. Reading a solution before struggling
with the problem feels exactly like learning, and is the most reliable way to finish this course
having learned nothing.
</Accordion>
</AccordionGroup>

## Rubric

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Correctness | tests fail | happy path only | all provided edge cases pass; integer minor units throughout | hypothesis invariants hold over arbitrary operation sequences, including the injected mutation |
| Code quality | works | readable | `mypy --strict` and `ruff` clean; validation in properties; custom exception hierarchy with attributes | a reviewer would approve unchanged; the Protocol boundary is real and annotated |
| Extensibility | storage calls scattered through the domain | one storage class, swapped by editing an import | Protocol-based, two backends, tests parametrised over them | a third backend added with **zero** changes to existing files, proven by diff |
| Explanation | no README | describes usage | documents the API and the splitting guarantee | reports what hypothesis found, the shrunk case, the Open/Closed diff, and one wrong turn |

**Passing bar:** 2 or better on every row. **Portfolio bar:** 3 on Extensibility and Explanation — the zero-line diff and the shrunk counterexample are the two things that make this repo worth linking, and they are the two most people skip.
