**For Aarav (student).** No assumptions. Every term is defined where it first appears.

### The one idea

In Python, `a = b` never copies anything. It makes the name `a` refer to whatever `b` already refers to. There is now one object with two names. If that object can be changed, changing it through one name changes what you see through the other — because there was only ever one thing.

Every aliasing bug in Python is a failure to keep names and objects separate in your head.

### The analogy

An **object** is a box on a shelf. A **name** is a sticky note with an arrow, stuck to the shelf edge, pointing at a box.

- `a = [1, 2, 3]` — make a box containing 1, 2, 3, and stick a note labelled `a` pointing at it.
- `b = a` — stick a *second* note labelled `b` pointing at the *same* box. No new box.
- `a.append(4)` — reach into the box and add something. Both notes still point at that box, so both `a` and `b` show four items.
- `a = a + [4]` — this is different. It builds a **new** box, then peels the note `a` off and re-sticks it on the new box. `b` still points at the old one.

The difference between "reach into the box" and "make a new box and move the note" is the whole subject.

### The vocabulary, defined

- **Object** — a thing in memory with a value, a type, and an identity. Everything in Python is one: numbers, strings, functions, classes, modules.
- **Name (variable)** — a label bound to an object. Names have no type; objects do.
- **Binding** — attaching a name to an object. `=` binds. It does not copy.
- **Identity** — the object's address in memory, returned by `id(obj)`. Two names for one object have the same `id`.
- **`is`** — identity comparison: "are these the same object?"
- **`==`** — value comparison: "do these have equal contents?"
- **Mutable** — can be changed in place. `list`, `dict`, `set`, and most classes you write.
- **Immutable** — cannot be changed. `int`, `float`, `str`, `tuple`, `frozenset`, `bytes`. "Changing" one always makes a new object.
- **Aliasing** — two or more names bound to one object.
- **Reference count** — how many references point at an object. When it drops to zero, CPython frees the object immediately.
- **Shallow copy** — a new outer container holding references to the *same* inner objects.
- **Deep copy** — a new outer container holding new copies of the inner objects, recursively.

### Smallest working example

```python
a = [1, 2, 3]
b = a                    # NOT a copy — a second name for the same list

print(a is b)            # True  — same object
print(id(a) == id(b))    # True

a.append(4)              # mutate the object
print(b)                 # [1, 2, 3, 4]   <- b changed, though we never mentioned b

a = a + [5]              # REBIND a to a brand-new list
print(a)                 # [1, 2, 3, 4, 5]
print(b)                 # [1, 2, 3, 4]   <- b still points at the old object
print(a is b)            # False
```

```bash
python3 aliasing.py
```

Run it. Then run it again with `a += [5]` instead of `a = a + [5]` and watch `b` change too — because `+=` on a list calls `list.__iadd__`, which mutates in place, while `+` calls `__add__`, which builds a new list. Same-looking syntax, opposite behaviour.

### Line-by-line walkthrough

- `a = [1, 2, 3]` — build a list object; bind the name `a` to it. The object's reference count is 1.
- `b = a` — bind `b` to the same object. Reference count is now 2. **No list was created.**
- `a is b` → `True` — `is` asks about identity, and there is one object.
- `a.append(4)` — a **method call on the object**. Nothing is rebound; the object itself changes.
- `print(b)` — `b` still points at that object, so you see the change. This is the line that surprises people, and it should stop surprising you now.
- `a = a + [5]` — `+` on lists creates a **new** list. Then `=` rebinds `a` to it. `b` is untouched.
- `a is b` → `False` — two objects now.

### Guided practice: ten aliasing puzzles

Predict each output on paper **before** running. Answers below.

```python
# 1
x = [1, 2]; y = x; y.append(3); print(x)

# 2
x = [1, 2]; y = x[:]; y.append(3); print(x)

# 3
x = (1, 2); y = x; y += (3,); print(x)

# 4
grid = [[0] * 3] * 3; grid[0][0] = 9; print(grid)

# 5
def f(lst): lst.append(1)
a = []; f(a); print(a)

# 6
def g(lst): lst = lst + [1]
a = []; g(a); print(a)

# 7
def h(items=[]): items.append(1); return items
print(h()); print(h())

# 8
s = "abc"; t = s; t += "d"; print(s)

# 9
d = {"k": [1]}; e = dict(d); e["k"].append(2); print(d)

# 10
import copy
d = {"k": [1]}; e = copy.deepcopy(d); e["k"].append(2); print(d)
```

<Accordion title="Answers, with the reason for each">

1. `[1, 2, 3]` — `y = x` aliases; `append` mutates the shared object.
2. `[1, 2]` — `x[:]` makes a new list (a shallow copy), so `y` is a different object.
3. `(1, 2)` — tuples are immutable, so `+=` builds a new tuple and rebinds `y`. `x` is untouched.
4. `[[9, 0, 0], [9, 0, 0], [9, 0, 0]]` — **the classic.** `[[0]*3]*3` repeats the *same inner list* three times. Use `[[0]*3 for _ in range(3)]`, which evaluates the inner expression three times.
5. `[1]` — the parameter `lst` is a new name bound to the same object; `append` mutates it.
6. `[]` — `lst = lst + [1]` rebinds the *local* name only. The caller's binding is unaffected.
7. `[1]` then `[1, 1]` — **the mutable default trap.** The default list is created **once**, when the `def` executes, and shared by every call.
8. `abc` — strings are immutable; `+=` made a new string and rebound `t`.
9. `{"k": [1, 2]}` — `dict(d)` is a *shallow* copy: a new dict, the same inner list.
10. `{"k": [1]}` — `deepcopy` copies recursively, so the inner list is a separate object.
</Accordion>

### `is` versus `==`

```python
a = [1, 2, 3]
b = [1, 2, 3]
print(a == b)    # True  — equal contents
print(a is b)    # False — different objects
```

**Use `==` for values. Use `is` only for `None`, `True` and `False`**, which are singletons — there is exactly one `None` object in a running program, so `x is None` is both correct and fast.

Never write `if x == None`. And never use `is` on numbers or strings, even when it appears to work — Layer 2 explains why it sometimes does, which is worse than if it never did.

### Guided practice: fix the mutable default

```python
# BROKEN
def add_item(item, basket=[]):
    basket.append(item)
    return basket

print(add_item("apple"))     # ['apple']
print(add_item("pear"))      # ['apple', 'pear']   <- the same list!

# FIXED
def add_item(item, basket=None):
    if basket is None:
        basket = []          # a fresh list PER CALL
    basket.append(item)
    return basket

print(add_item("apple"))     # ['apple']
print(add_item("pear"))      # ['pear']
```

The rule: **default argument values are evaluated once, when the `def` statement runs.** If the default is mutable, every call shares it. Use `None` as the sentinel and build the real default inside the function.

<Accordion title="Checkpoint — 5 questions before you continue">

1. **Does `b = a` copy the object?** — no. It binds a second name to the same object.
2. **Why does `[[0]*3]*3` misbehave?** — `*` repeats the *reference* to one inner list, so all three rows are the same object.
3. **When is `is` the right operator?** — for `None`, `True`, `False`, and genuine "same object?" questions. Never for numbers or strings.
4. **Why does a mutable default persist between calls?** — it is created once, when `def` runs, not on each call.
5. **`dict(d)` versus `copy.deepcopy(d)`?** — the first makes a new dict pointing at the same values; the second copies recursively.
</Accordion>

### Object sizes, measured

`sys.getsizeof` reports the object's own size, excluding what it refers to:

| Object | `getsizeof` |
|---|---|
| `0`, `1` (small int) | **28 B** |
| `2**30` | 32 B |
| `2**100` | 40 B |
| `1.0` (float) | 24 B |
| `True` | 28 B |
| `""` | 41 B |
| `"a"` | 42 B |
| `[]` | 56 B |
| `list(range(10))` | 136 B |
| `{}` | 64 B |
| `{"a": 1}` | 184 B |
| `()` | 40 B |
| `(1, 2, 3)` | 64 B |
| `set()` | 216 B |

The number that reframes everything: **an integer costs 28 bytes.** A C `int64_t` is 8. The other 20 are the object header — 8 bytes of reference count, 8 bytes of type pointer — plus the digit array's length and payload. A Python list of a million integers is not 8 MB; it is 8 MB of pointers *plus* up to 28 MB of integer objects.

Note also that an empty dict is 64 bytes but a one-item dict is **184** — the first insertion allocates a table with room for 5 entries. That 120-byte jump is why "just use a dict per record" is expensive at scale, as the next table shows.

### The million-record question, measured

One million records, each with an integer id, a name (drawn from a shared pool of 1,000 strings, so string storage is identical across all variants) and a float score. Peak RSS measured with `resource.getrusage`, baseline subtracted:

| Representation | Total | **Bytes per record** | vs dict |
|---|---|---|---|
| `dict` per record | 255.3 MB | **268 B** | 1.00× |
| plain class | 162.9 MB | **171 B** | 1.57× smaller |
| `@dataclass` | 163.1 MB | 171 B | 1.57× |
| `NamedTuple` | 145.0 MB | 152 B | 1.76× |
| plain `tuple` | 132.5 MB | 139 B | 1.93× |
| class with `__slots__` | 132.3 MB | **139 B** | **1.93×** |
| `@dataclass(slots=True)` | 132.3 MB | 139 B | 1.93× |
| columnar (`array.array` + list) | 27.2 MB | **28 B** | **9.6×** |

Four conclusions worth carrying:

1. **`@dataclass` costs exactly what a hand-written class costs** — 171 B either way. It generates `__init__`, `__repr__` and `__eq__`; it changes nothing about layout. Use it freely.
2. **`slots=True` is the single highest-value flag**, taking 171 B to 139 B — a 19% cut for one keyword. `@dataclass(slots=True)` has been available since Python 3.10.
3. **`dict` per record costs 1.93× a slotted class.** The instance `__dict__` is a full hash table; `__slots__` replaces it with a fixed array of pointers.
4. **Columnar is 9.6× smaller than dict**, and the reason is not the container — it is that `array.array('q', ...)` stores raw 8-byte integers with **no per-value Python objects at all**. The 28 B/record is 8 bytes of int + 8 bytes of float + 8 bytes of list pointer to a shared string + overhead. This is exactly why `numpy`, `polars` and `pyarrow` exist, and it is the same insight as Week 26's tensor layouts.

### Mutable defaults, shallow copies, and the `__hash__`/`__eq__` contract

**Mutable default arguments** are the trap from Layer 1. Ruff's `B006` (flake8-bugbear) catches every instance; turn it on and the class of bug disappears from your codebase permanently.

**Shallow versus deep copy:**

```python
import copy
original = {"tags": ["a"], "meta": {"n": 1}}
shallow  = dict(original)          # or original.copy(), or copy.copy(original)
deep     = copy.deepcopy(original)

shallow["tags"].append("b")        # mutates the SHARED inner list
print(original["tags"])            # ['a', 'b']
deep["tags"].append("c")
print(original["tags"])            # ['a', 'b']  — unaffected
```

`copy.deepcopy` handles cycles correctly (it memoises objects it has already copied) and is therefore slow — it walks the entire object graph. For hot paths, prefer designing so you do not need it: make the shared data immutable (`tuple`, `frozenset`, `@dataclass(frozen=True)`), which removes the question.

**The `__hash__`/`__eq__` contract**, which Python enforces only partially and which you must get right:

- If `a == b` then `hash(a) == hash(b)`. **Always.** The reverse need not hold (collisions are fine).
- Both must be based on the same fields, and those fields **must not change** while the object is in a set or used as a dict key.
- Defining `__eq__` in a class sets `__hash__ = None`, making instances unhashable. That is deliberate: a mutable object with value equality is a footgun as a dict key. To opt back in, define `__hash__` explicitly — and only if the fields it uses are immutable.

```python
from dataclasses import dataclass

@dataclass(frozen=True, slots=True)     # frozen -> hashable, immutable, 139 B/instance
class Point:
    x: int
    y: int

s = {Point(1, 2), Point(1, 2)}
print(len(s))       # 1 — equal and equally-hashed, so one element
```

`@dataclass(frozen=True)` generates `__hash__` from the fields and blocks attribute assignment. It is the right default for value objects: keys, coordinates, currency amounts, configuration.

The failure mode when you get it wrong:

```python
@dataclass(slots=True)          # NOT frozen, but eq=True by default -> __hash__ is None
class Mutable:
    x: int

# {Mutable(1)}  ->  TypeError: unhashable type: 'Mutable'
# @dataclass(eq=False) would keep the default identity hash — usually not what you want either
```

### Trade-offs table

| Decision | Choose X when… | Choose Y when… |
|---|---|---|
| `dict` vs `@dataclass` for a record | **`dict`** for genuinely dynamic keys, or data crossing a JSON boundary where the schema is not yours | **`@dataclass(slots=True)`** for anything with a fixed shape: 1.93× less memory, attribute access instead of string keys, and `mypy` can check it |
| `__slots__` vs default `__dict__` | **`__slots__`** whenever you will have more than ~10,000 instances, or the class is a value object | **`__dict__`** when instances need dynamic attributes, or the class is a mixin/base with multiple inheritance where slots conflict |
| Row objects vs columnar | **Row objects** below ~100,000 records, or when access is "one whole record at a time" | **Columnar** (`array`, `numpy`, `polars`) above that, or when access is "one field across all records" — measured **9.6× less memory**, plus vectorised operations |
| `frozen=True` vs mutable | **`frozen=True`** for value objects, dict keys, set members and anything shared across threads (Week 4) — you get `__hash__` for free and aliasing bugs become impossible | **Mutable** for entities with identity and lifecycle (a `User` whose email changes), where copying on every edit is the wrong model |

### Reference implementation — measuring it yourself

```python
"""memcmp.py — per-record memory for six representations. Run each in a fresh process."""
from __future__ import annotations

import array
import gc
import resource
import sys
from dataclasses import dataclass
from typing import NamedTuple

N = 1_000_000


def rss_mb() -> float:
    """Peak RSS in MB. ru_maxrss is BYTES on macOS and KILOBYTES on Linux."""
    r = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss
    return r / (1024 * 1024) if sys.platform == "darwin" else r / 1024


class Plain:
    def __init__(self, uid: int, name: str, score: float) -> None:
        self.uid, self.name, self.score = uid, name, score


class Slotted:
    __slots__ = ("uid", "name", "score")

    def __init__(self, uid: int, name: str, score: float) -> None:
        self.uid, self.name, self.score = uid, name, score


@dataclass(slots=True)
class DCSlots:
    uid: int
    name: str
    score: float


class NT(NamedTuple):
    uid: int
    name: str
    score: float


def build(kind: str, names: list[str]):
    if kind == "dict":
        return [{"uid": i, "name": names[i % 1000], "score": i * 0.5} for i in range(N)]
    if kind == "class":
        return [Plain(i, names[i % 1000], i * 0.5) for i in range(N)]
    if kind == "slots":
        return [Slotted(i, names[i % 1000], i * 0.5) for i in range(N)]
    if kind == "dataclass_slots":
        return [DCSlots(i, names[i % 1000], i * 0.5) for i in range(N)]
    if kind == "namedtuple":
        return [NT(i, names[i % 1000], i * 0.5) for i in range(N)]
    if kind == "columnar":
        uids = array.array("q", range(N))
        scores = array.array("d", (i * 0.5 for i in range(N)))
        nm = [names[i % 1000] for i in range(N)]
        return uids, scores, nm
    raise ValueError(kind)


def main() -> None:
    kind = sys.argv[1]
    names = [f"user{i:07d}" for i in range(1000)]   # shared pool: identical across variants
    gc.collect()
    base = rss_mb()
    data = build(kind, names)
    gc.collect()
    peak = rss_mb()
    per = (peak - base) * 1024 * 1024 / N
    print(f"{kind:16s} delta={peak - base:7.1f} MB  per-record={per:6.0f} B")
    del data


if __name__ == "__main__":
    main()
```

Two details that make the measurement trustworthy: the **name pool is shared across all variants**, so string storage is identical and the comparison isolates the container cost; and **`ru_maxrss` is bytes on macOS and kilobytes on Linux**, which is the single most common error in Python memory measurement and silently reports numbers 1,024× off.

### What breaks in the real world

A recommendation service loaded a user-feature table into memory at startup: 4.2 million users, each a dict of 11 fields. It worked in staging with a 500,000-row sample. In production the pod was OOM-killed during startup, every time, at a 4 GB memory limit.

The arithmetic that nobody did beforehand: at the measured **268 bytes per three-field dict**, an 11-field dict is roughly 550 bytes, so 4.2 M records is about 2.3 GB of records — plus the interned field-name strings, plus the list of pointers, plus the JSON parser's peak during load, which briefly doubles it. The 4 GB limit was never going to hold.

Three fixes were applied, in increasing order of effort and payoff:

1. **`@dataclass(slots=True)`** instead of dicts: 268 → 139 B/record in the three-field benchmark, so roughly 2.3 GB → 1.2 GB. One line, no call-site changes beyond `r["uid"]` → `r.uid`.
2. **Streaming the load** with a generator instead of `json.load` of the whole file, which removed the transient doubling. Module 2 measures this: **10,499 MB peak → effectively zero** for the same aggregation over a 2 GB file.
3. **Columnar** for the seven numeric fields via `numpy` arrays, keeping only the two string fields as Python objects. Final resident size 380 MB, comfortably inside the limit, and the scoring loop got faster because it became a vectorised operation.

The generalisable lesson: **"we'll load it into memory" needs an arithmetic check, and the per-record cost in Python is 5–50× the size of the underlying data.** Do the multiplication before writing the code, not after the third OOM kill.

<Accordion title="Design checkpoint — one question, with a model answer">

**Question.** A colleague's cache stores `dict` objects keyed by a tuple, and reports intermittent "wrong data returned" bugs that nobody can reproduce. Reviewing the code, you see the cached dicts are returned directly to callers. What is the likely bug and what do you change?

**Model answer.** The cache is handing out **references to its own mutable state**, and some caller is mutating what it received.

The mechanism is Layer 1's first lesson at production scale: `return self._cache[key]` does not copy. Caller A gets the dict, adds a field or edits one for its own purposes, and now every future cache hit — for every other caller — sees the modified version. It is intermittent because it depends on which caller ran first and whether that particular request happened to mutate.

Three fixes, and the choice between them is a real trade-off:

**Return a copy.** `return dict(self._cache[key])` is a shallow copy and it is not enough — nested lists and dicts are still shared, which is puzzle 9 from Layer 1. `copy.deepcopy` is correct and expensive: it walks the whole object graph on every cache hit, which for a cache is exactly the cost you were trying to avoid.

**Store immutable values.** Cache `@dataclass(frozen=True, slots=True)` instances instead of dicts. Mutation raises `FrozenInstanceError` at the call site — the bug becomes a loud, immediate error in the offending code rather than silent corruption elsewhere. It also gets you `__hash__` and, measured, **139 bytes per record instead of 268**, halving the cache's memory. This is the fix I would make.

**Store the serialised form.** Cache `bytes` (JSON or pickle) and deserialise per hit. Guarantees isolation and costs CPU per hit; it is the right answer only when the cache is shared across processes anyway.

The general principle worth stating in the review: **a cache that returns mutable objects has no ownership rule**, which is Week 1's `malloc` question in a garbage-collected language. Either the cache owns the object and hands out copies, or the caller owns it and the cache must not keep it. Immutability makes the question disappear, which is why it is the right default.

One more thing to check while you are there: if the cache key is a tuple containing a mutable object, or the objects are used as dict keys and their fields change, the `__hash__` contract is broken and lookups will silently miss. `frozen=True` fixes that too.
</Accordion>

### The object header, and why an `int` is 28 bytes

Every CPython object begins with `PyObject`:

```c
typedef struct _object {
    Py_ssize_t ob_refcnt;      /* 8 bytes  */
    PyTypeObject *ob_type;     /* 8 bytes  */
} PyObject;
```

Sixteen bytes before any payload. Variable-sized objects add `ob_size` (8 more). An `int` is a `PyLongObject`: header, size, then an array of 30-bit "digits". So:

- `0` and `1`: 16 (header) + 8 (size) + 4 (one digit, padded) = **28 bytes** ✓ measured.
- `2**30` needs two digits: **32 bytes** ✓.
- `2**100` needs four: **40 bytes** ✓.

A `float` skips the size field: 16 + 8 (a C `double`) = **24 bytes** ✓.

The consequence to internalise: **a Python integer costs 3.5× what a C `int64_t` costs, and every arithmetic operation allocates a new one.** `sum(range(10**6))` creates and destroys a million integer objects. This is the entire reason NumPy exists, and it is why the columnar representation measured 28 B/record against dict's 268 B — `array.array('q')` stores raw machine integers with no object headers at all.

CPython 3.12+ has begun shrinking this: immortal objects (PEP 683) avoid refcount writes on `None`, `True`, `False` and small ints, which matters mainly for the free-threaded build.

### Interning: why `is` sometimes works, which is worse than never

```python
a = 256; b = 256; print(a is b)      # True
x = 257; y = 257; print(x is y)      # True   <- on 3.13, at module level
```

CPython pre-allocates the integers **−5 to 256** and reuses those objects forever. That is documented and stable. But the second line is `True` for a *different* reason: the compiler constant-folds and de-duplicates constants within a single **code object**, so two literal `257`s in the same module become one object.

Break the code-object sharing and the behaviour changes:

```python
x = int("257")
y = int("257")
print(x is y)        # False — computed at runtime, two objects
```

**This is why `is` on numbers is a bug even when it works.** The behaviour depends on the small-int cache, on constant folding, on whether the values are in the same code object, and on the CPython version. `==` is always correct.

Strings behave the same way. Identifier-like literals (`"hello"`) are interned automatically; runtime-constructed strings generally are not:

```python
s1 = "hello"; s2 = "hello"; print(s1 is s2)                   # True  (literals, interned)
s3 = "hel" + input_that_returns("lo"); print(s1 is s3)        # False (built at runtime)
```

`sys.intern(s)` forces interning. It is a real optimisation when you have millions of repeated strings — the JSON key names in Module 2's 12.2 M-record file, for instance — because it turns string comparison into pointer comparison and deduplicates storage. It is also a memory leak in the classic sense: interned strings live until interpreter shutdown, so never intern user-controlled data.

### Reference counting, cycles, and the generational collector

CPython frees an object the instant its reference count reaches zero. That is deterministic and it is why `with open(...)` is *usually* unnecessary in CPython — and why relying on it is still wrong, because PyPy and other implementations do not refcount.

```python
import sys
lst = [1, 2, 3]
print(sys.getrefcount(lst) - 1)   # 1   (minus 1 for getrefcount's own argument)
alias = lst
print(sys.getrefcount(lst) - 1)   # 2
```

Refcounting cannot free cycles:

```python
a = {}; b = {}
a["b"] = b; b["a"] = a
del a, b        # both still have refcount 1, from each other. Leaked, as far as refcounting goes.
```

Hence the **cyclic garbage collector**, which is generational with three generations. Thresholds (`gc.get_threshold()`) default to `(700, 10, 10)`: a gen-0 collection runs after 700 more allocations than deallocations; a gen-1 after 10 gen-0 collections; a gen-2 after 10 gen-1 collections. Objects that survive a collection are promoted.

Two production consequences:

- **A gen-2 collection walks every tracked container object in the process.** In a service holding millions of long-lived objects, that pause is proportional to the live set and can reach hundreds of milliseconds. Instagram's well-documented fix was to disable the cyclic GC entirely (`gc.freeze()` after startup, then `gc.disable()`), accepting cycle leaks in exchange for predictable latency and better copy-on-write behaviour across forked workers — the same copy-on-write issue we measure in Week 4 Module 3.
- **`gc.freeze()`** (Python 3.7+) moves everything currently alive into a permanent generation that is never collected. Called after loading a large read-only dataset, it removes that data from every subsequent collection's scan.

Objects with no containers — ints, floats, strings — are **not tracked** by the cyclic collector at all, because they cannot participate in a cycle. `gc.is_tracked(1)` is `False`. That is why the columnar representation is also gentler on GC pause times, not just on memory.

### `__slots__`, measured and explained

| Representation | Bytes/record | Attribute read |
|---|---|---|
| plain class (`__dict__`) | **171 B** | **4.6 ns** |
| `__slots__` | **139 B** | **4.4 ns** |
| `@property` over a slot | 139 B | **12.8 ns** |
| custom descriptor | 139 B | **49.6 ns** |

`__slots__` replaces the per-instance `__dict__` with a fixed array of pointers in the object itself, and stores the attribute *names* once on the class as descriptors. The saving is the dict: **32 bytes per instance here**, 19%.

Three costs you must know before recommending it:

1. **No new attributes at runtime.** `obj.typo = 1` raises `AttributeError` — usually a feature.
2. **Multiple inheritance conflicts.** Two base classes with non-empty `__slots__` cannot be combined. Bases intended for mixing should declare `__slots__ = ()`.
3. **No `__weakref__` unless you add it.** `__slots__ = ("x", "__weakref__")` restores weak-reference support, which some caching and observer patterns need.

Note from the table that `__slots__` does **not** speed up attribute access measurably (4.4 vs 4.6 ns) — the dict lookup was already fast because CPython 3.11+ uses key-sharing dicts and inline caches. The win is memory, and memory alone.

Note also that a `@property` costs **2.8×** a plain attribute and a hand-written descriptor **10.8×**. That matters in a hot loop over millions of records and nowhere else — but "nowhere else" includes almost all code, so do not let it stop you using properties.

### Measuring memory honestly: RSS lies on macOS

This is the methodological point that makes the rest of the numbers trustworthy.

Reading a 2 GB JSONL file three ways (Module 2 covers the streaming case in full):

| Approach | `tracemalloc` peak | `ru_maxrss` peak |
|---|---|---|
| generator | **0.03 MB** | 14.9 MB |
| `f.readlines()` then parse | **2,600.9 MB** | 698.5 MB |
| list of parsed dicts | **10,499.0 MB** | 2,070.8 MB |

The `readlines` row is the tell: Python genuinely allocated 2.6 GB of string objects, and `ru_maxrss` reported 698 MB — **3.7× low**. macOS's memory compressor compresses inactive pages, and highly repetitive JSON text compresses extremely well, so the resident set never reflects the allocation.

The rules that follow:

- **`tracemalloc` measures what Python allocated**, portably and precisely. Use it for comparing representations.
- **`ru_maxrss` measures physical residency**, which is what an OOM killer and a container limit actually enforce — and it is **bytes on macOS, kilobytes on Linux**.
- **Report both, and say which you used.** A number without its measurement method is not reproducible.
- `tracemalloc` costs roughly 3× runtime (the generator run went from 23.5 s to 74.8 s), so measure with it and benchmark without it.

### Production failure modes and how you detect them

| Failure | Signature | Detection |
|---|---|---|
| OOM at startup loading a table | pod killed before serving traffic, every time | multiply rows × per-record bytes *before* writing the loader; `@dataclass(slots=True)`; stream the parse |
| Cache returns mutated data | intermittent, unreproducible wrong values | store `frozen=True` dataclasses; a mutation attempt then raises at the offending line |
| Mutable default accumulates | a list that grows across requests; memory creeps | ruff `B006`; use `None` as the sentinel |
| GC pause spikes | p99 latency spikes uncorrelated with load | `gc.callbacks` to log collection durations; `gc.freeze()` after startup; consider `gc.disable()` with care |
| Forked workers use 3× expected memory | RSS per worker approaches the parent's, defeating copy-on-write | refcount writes dirty shared pages; `gc.freeze()` before forking (Week 4 Module 3) |
| `is` comparison works locally, fails in production | different code path, different interpreter version, or runtime-constructed values | use `==`; reserve `is` for `None`/`True`/`False` |
| Memory numbers disagree between macOS and Linux | `ru_maxrss` units differ by 1,024× | branch on `sys.platform`; prefer `tracemalloc` for portable comparisons |

### Frontier and research pointers

- **Van Rossum, G. — PEP 683, "Immortal Objects, Using a Fixed Refcount" (2022).** One-sentence takeaway: making `None`, small ints and interned strings immortal removes refcount writes to shared pages, which is what makes forked workers and free-threaded Python viable.
- **PEP 703, "Making the Global Interpreter Lock Optional in CPython" (Gross, 2023).** One-sentence takeaway: removing the GIL requires biased reference counting and deferred reference counting because atomic refcount updates on every object access would be catastrophically slow — the object model is the hard part, not the lock.
- **Bacon, D. F. & Rajan, V. T. (2001). "Concurrent Cycle Collection in Reference Counted Systems." *ECOOP*.** One-sentence takeaway: reference counting plus a trial-deletion cycle collector is a complete garbage collector, and this is the design CPython implements.
- **Jones, R., Hosking, A. & Moss, E. (2011). *The Garbage Collection Handbook*, Chapters 5 and 9.** One-sentence takeaway: generational collection works because most objects die young, and the cost of a major collection is proportional to the *live* set, not the garbage — which is why a large in-memory cache makes GC pauses worse, not better.
- **Instagram Engineering, "Dismissing Python Garbage Collection at Instagram" (2017).** One-sentence takeaway: disabling the cyclic GC in forked web workers cut memory use by around 10% by preventing refcount and GC-header writes from dirtying copy-on-write pages.
- **Abadi, D. et al. (2013). "The Design and Implementation of Modern Column-Oriented Database Systems." *Foundations and Trends in Databases*.** One-sentence takeaway: storing values by column rather than by row removes per-value overhead and enables vectorised execution — the same 9.6× we measured, in database form.

### Stretch challenge

Build the memory profile of a real workload and make a defensible recommendation.

1. Take a real JSON or CSV dataset of at least 500,000 rows with 8+ fields (a public dataset is fine). Load it six ways: dict, plain class, `@dataclass`, `@dataclass(slots=True)`, `NamedTuple`, and columnar with `array`/`numpy`.
2. Measure **both** `tracemalloc` peak and `ru_maxrss` for each, in a fresh process each time. Report both, and explain any discrepancy larger than 1.5× on your platform.
3. Now measure *access* cost, not just storage: time (a) reading one field across all records, and (b) reading all fields of one random record, for each representation. The winner is different for the two access patterns — show it.
4. Add `sys.intern` to the string fields and re-measure. How much did it save, and at what fraction of duplicate values does it stop being worth it?
5. Instrument GC: register a `gc.callbacks` hook that logs generation and duration, then measure collection pause times for the dict version versus the columnar version under a synthetic allocation load.

The open question with no single right answer: columnar wins on memory by 9.6× and on field-wise access, and loses on "give me this one record" and on code readability. At what data size, and at what read/write ratio, would you actually make that trade in a service your team maintains — and does your answer change if the alternative is "put it in Postgres and query it"? Argue it with your own numbers from steps 2 and 3.

**The interview angle.** "What's the difference between `is` and `==`?" is a standard screen and the definition alone scores nothing. The answer that lands: *`is` compares identity, `==` compares value. `is` is correct for `None`, `True` and `False` because they are singletons. It appears to work for small integers and string literals because CPython caches −5 to 256 and interns literals within a code object — which makes it worse than if it never worked, because the bug hides until the values come from input.*

Then be ready for the follow-up nobody prepares for: "why is a Python integer 28 bytes?" — 8 bytes refcount, 8 bytes type pointer, 8 bytes size, then the digits. And that is why NumPy exists.

<Accordion title="If you're working" icon="briefcase">

Three places this shows up in a normal engineering week:

1. **Before writing "load it all into memory".** Multiply rows by per-record cost first. The measured floor for a three-field record is 139 bytes with `slots=True` and 268 as a dict; an eleven-field record is roughly 2× that. Ten million records is 3–6 GB before you have parsed anything, and the parse itself peaks higher.

2. **Any cache or registry that returns objects.** If callers can mutate what they receive, you have shared mutable state with no ownership rule. Store `@dataclass(frozen=True, slots=True)` values and the bug class disappears — plus you halve the memory.

3. **Turning on one linter rule.** Ruff's `B006` (mutable default argument) and `B008` (function call in a default) between them eliminate a bug that every Python codebase has at least one of. It is a two-line change to `pyproject.toml` and it is permanent.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| A function's "default" list keeps growing between calls | mutable default evaluated once at `def` time | use `None` as the sentinel; enable ruff `B006` |
| `[[0]*3]*3` — changing one row changes all three | `*` repeats the reference to one inner list | `[[0]*3 for _ in range(3)]` |
| Copying a dict still shares the nested lists | `dict(d)` / `.copy()` is shallow | `copy.deepcopy`, or make the nested values immutable |
| `x is y` is True locally and False in production | small-int cache and literal interning are implementation details | use `==`; reserve `is` for `None`/`True`/`False` |
| `TypeError: unhashable type` after adding `__eq__` | defining `__eq__` sets `__hash__ = None` | `@dataclass(frozen=True)`, or define `__hash__` over immutable fields |
| Set/dict lookups silently miss | a key's fields changed after insertion, so its hash moved | use immutable keys; `frozen=True` |
| Pod OOM-killed loading a table | per-record cost is 5–50× the raw data size | multiply before coding; `slots=True`; stream; columnar |
| Memory numbers 1,024× off between macOS and Linux | `ru_maxrss` is bytes on macOS, KB on Linux | branch on `sys.platform`; prefer `tracemalloc` |
| RSS much lower than `tracemalloc` on macOS | the OS memory compressor compressed inactive pages | report both; use `tracemalloc` for allocation comparisons |
| p99 latency spikes with no load correlation | gen-2 GC walking a large live set | log `gc.callbacks`; `gc.freeze()` after loading read-only data |
