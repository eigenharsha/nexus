## The ticket

> **NEX-204 · Backend · P1**
>
> **Reporter:** Dev (Product) · **Assignee:** you
>
> We are launching "Resume Tailor": a user pastes their resume and a job description, and we return
> a tailored, formatted version highlighting the overlap and flagging the gaps.
>
> Version 1 is **rule-based** — no LLM. Keyword extraction, overlap scoring, and a markdown
> template. We are validating demand, not model quality. (The LLM version is Week 26; design so
> that swapping the generator is a one-file change.)
>
> Requirements from the launch review:
> - Users sign up and log in. Their tailoring history is private to them.
> - Free tier: 20 tailorings per day. Enforce it.
> - Resume upload accepts `.txt` and `.md` up to 200 KB. Nothing else.
> - Support asked for a reference number on every error so they can find it in the logs.
> - The Week 5 front end must work against this with no proxy hacks.
> - Legal wants the ability to delete a user's data on request.
>
> Public URL by Friday, with the OpenAPI docs reachable.

**Time box.** `basic` 4 h · `standard` 12 h · `hard` 8 h more. If `standard` is past 18 hours you
have started building a job queue; stop and re-read the acceptance criteria.

  <Tab title="basic">
    `POST` resume text plus a job description, get a formatted markdown response. Rule-based, no
    auth, no database. Wire it to your Week 5 front end.

    <Info>~60% of the code is written for you. TODOs are marked. Answers in the solution page.</Info>

    **Acceptance criteria**

    1. `POST /v1/tailor` accepts `{"resume": "...", "job_description": "..."}` and returns `{"markdown": "...", "matched_skills": [...], "missing_skills": [...]}`.
    2. Both fields are required, each between 50 and 20,000 characters, enforced by Pydantic — a short resume returns `422` naming the field.
    3. `GET /healthz` returns `{"status":"ok"}`.
    4. `/docs` renders and the `POST` can be executed from it successfully.
    5. CORS is configured so the Week 5 page can call it from a different origin — verified in a browser, not just with `curl`.
    6. Five tests pass in under two seconds: happy path, too-short resume, missing field, health, and the OpenAPI document containing the route.

    **Verify**

    ```bash

    ```
  </Tab>

  <Tab title="standard">
    A full FastAPI service: Pydantic request/response models, file upload with size and type limits,
    auth, rate limiting, structured errors, 25+ tests, OpenAPI docs, async I/O and a load-test
    report.

    <Info>Spec and tests only. You write the implementation.</Info>

    **Acceptance criteria**

    1. **Auth.** `POST /v1/auth/register`, `POST /v1/auth/token`, `POST /v1/auth/refresh`. Passwords hashed with argon2id. Access tokens expire in 15 minutes; refresh tokens are stored server-side, hashed at rest, rotate on use, and a reused refresh token revokes the whole family.
    2. **Tenant isolation.** `GET /v1/tailorings/{id}` returns `404` — not `403` — when the tailoring belongs to another user. There is a test for this on **every** route with a path parameter.
    3. **Upload.** `POST /v1/tailor/upload` accepts `multipart/form-data` with a `.txt` or `.md` file at most 200 KB. Wrong type → `415`. Too large → `413` **without** reading the whole body into memory.
    4. **Rate limiting.** 20 tailorings per user per rolling 24 hours; the 21st returns `429` with `Retry-After` and a body explaining the limit and the reset time. Login is separately limited to 10 attempts per account per minute.
    5. **Error envelope.** Every error response — validation, auth, rate limit, not-found, server error — has the same shape with `type`, `title`, `status`, `detail`, `request_id`, and `errors[]` when field-level. `request_id` also appears as a response header and in the logs.
    6. **Async throughout.** No blocking call inside any `async def`. Password hashing runs off the event loop. A CI lint rule forbids importing `requests`, `time.sleep` and any sync database driver under `app/api/`.
    7. **Deletion.** `DELETE /v1/me` removes the user and all their tailorings in one transaction and returns `204`. A test proves nothing of theirs remains.
    8. **Tests.** 25 or more, running in under 30 seconds, passing in randomised order. Must include: auth happy path and every failure, cross-tenant 404, upload limits, rate-limit boundary (the 20th succeeds, the 21st does not), refresh rotation and reuse detection, and the error envelope shape.
    9. **Docs.** `/docs` shows every endpoint with example requests and documented error responses. `openapi.json` is committed and diffed in CI.
    10. **Load-test report.** `LOADTEST.md` with RPS against p50/p95/p99 at concurrency 10, 25, 50, 100 and 200; the knee identified; the saturated resource named with evidence; one fix applied and re-measured.

    **Verify**

    ```bash
    cd labs/p1/week-06
    make verify TRACK=standard    # tests, lint, types, OpenAPI diff, cross-tenant sweep
    make loadtest                 # writes reports/loadtest.json
    ```
  </Tab>

  <Tab title="hard">
    Add idempotency keys, background job processing with status polling, and a p95 under 200 ms
    target at 50 concurrent users.

    <Warning>
      There is a constraint here the `standard` solution fails: tailoring a 20,000-character resume
      takes long enough that doing it inside the request breaks the p95 target under concurrency.
      Moving it out of the request path changes the API's shape, and that is the point.
    </Warning>

    **Acceptance criteria**

    1. **Idempotency.** `POST /v1/tailor` honours an `Idempotency-Key` header: a replay with the same key and the same body returns the **stored** response with an `Idempotency-Replayed: true` header and creates nothing new. The same key with a different body returns `422`. A replay while the original is still running returns `409`. Keys expire after 24 hours. The key row and the effect must commit in the same transaction — there is a test that kills the process between them and asserts no orphan.
    2. **Background processing.** `POST /v1/tailor` returns `202` with a `Location` pointing at `GET /v1/jobs/{job_id}`, which returns `pending`, `running`, `succeeded` (with the result) or `failed` (with the error envelope). A job that fails is retried at most twice with backoff; the third failure is terminal and visible.
    3. **Performance target.** At 50 concurrent users mixing 70% status polls and 30% submissions, **p95 under 200 ms** and zero errors over a 60-second run. Report the numbers.
    4. **Backpressure.** With the queue depth over a configured threshold, `POST /v1/tailor` returns `503` with `Retry-After` instead of accepting work it cannot do. Prove it by submitting faster than the workers drain.
    5. **Graceful shutdown.** `SIGTERM` finishes in-flight requests, stops accepting new ones, and either completes or re-queues running jobs — no job is silently lost. A test sends `SIGTERM` mid-job and asserts the job still reaches a terminal state.
    6. **Write-up.** `ARCHITECTURE.md` with a diagram, the request path, the job lifecycle including every failure edge, and a paragraph on what you would change to add the LLM in Week 26.

    **Verify**

    ```bash
    cd labs/p1/week-06
    make verify TRACK=hard
    make loadtest MIX=hard        # asserts the p95 target
    ```
  </Tab>
</Tabs>

## Stuck? Open these in order

Each reveals a little more than the last. Try the level above before opening the next — a hint you
did not need costs you nothing, but an answer taken too early costs you the lesson.

<AccordionGroup>
<Accordion title="Nudge — I don't know where to start" icon="lightbulb">
Find the **first** failing test and implement only what that one test needs. Ignore the rest of the
lab until it is green. If you cannot tell which test fails first, run
`make verify TRACK=basic` and read the top of the output, not the bottom.
</Accordion>

<Accordion title="Hint — my endpoint is slow under load even though the handler is fast" icon="lightbulb">
A blocking call inside an `async def` stops the whole event loop. One synchronous database driver or `requests` call and every concurrent request queues behind it.

**What to do instead:** Either make the handler `def` (FastAPI runs it in a threadpool) or use async libraries throughout. The week's own measurement is a 27.8x throughput collapse from this single mistake — reproduce it before you fix it.
</Accordion>

<Accordion title="Hint — Pydantic rejects input I think is valid" icon="lightbulb">
That is the contract doing its job. Pydantic v2 is stricter than v1 about coercion, and the error body names the exact field and rule.

**What to do instead:** Read `exc.errors()` rather than the string. If the rule is wrong, change the model deliberately; do not reach for `model_config` to loosen validation globally, which turns off the protection everywhere.
</Accordion>

<Accordion title="Hint — my auth works but the tests leak state between cases" icon="lightbulb">
A module-level client or a real database shared across tests. State from one test survives into the next and the failures look random.

**What to do instead:** Use `dependency_overrides` to swap the DB session, and wrap each test in a transaction that rolls back. Tests should pass in any order and in isolation — run with `-p no:randomly` off to confirm.
</Accordion>

<Accordion title="I have a real attempt that fails — show me the full solution" icon="lock">
Open the [reference solution](/solutions/p1/week-06/lab).

Use it properly: read only far enough to get unstuck, then close it and return to your own code.
Afterwards, diff your version against it — the differences are the lesson, and yours is not
automatically the worse one.

If you have not yet written code that fails, do not open it. Reading a solution before struggling

## Common ways this lab goes wrong

- **Blocking calls in `async def`.** Password hashing at 65 ms and file parsing are both CPU work. On the event loop they cap you near 15 rps regardless of the machine. The load test will show it as high latency with idle CPU.
- **Reading the upload to check its size.** `413` must be decided from `Content-Length` and by streaming with a running byte count, not by `await file.read()` and then measuring. A 2 GB upload must never reach memory.
- **Rate limiting in process memory.** It works in tests and evaporates on restart and on a second instance. Store counters where all instances can see them, and say in the README what happens when that store is down.
- **Idempotency stored in a separate transaction.** The most common serious defect in this lab. If the key and the effect can commit separately, a crash between them produces either a double effect or a permanently stuck key.
- **`403` instead of `404` for another tenant's object.** It leaks existence. The verifier tests for `404` specifically.
- **A load test that measures the client.** If your numbers plateau at a suspiciously round value and your laptop's fans are loud, you are measuring the generator. Use `ab`, `k6` or `wrk`.
