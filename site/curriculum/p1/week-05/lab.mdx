## The ticket

> **NEX-118 · Frontend · P2**
>
> **Reporter:** Priya (Support Lead) · **Assignee:** you
>
> Our public "Country Explorer" page is the top result when people search for us and it is
> embarrassing. Three complaints this week:
>
> 1. On a phone it scrolls sideways and the search box is off screen.
> 2. When the API is slow, the page shows nothing at all for several seconds, then everything at
>    once. One user assumed it was broken and filed a bug.
> 3. A user with a screen reader could not use it — "the search field has no name".
>
> Rebuild it. It must work at 360 px, be usable with a keyboard only, show something honest while
> loading, and not fall over when the API returns an error. Ship it on a public URL by Friday.
>
> Data source: `https://restcountries.com/v3.1/all?fields=name,capital,region,population,flags,cca3`
> (free, no key, ~250 records, CORS enabled). If it is down, the repo includes `data/countries.json`
> as a fixture — your code must work against both without changes.

**Time box.** `basic` 3 h · `standard` 8 h · `hard` 6 h more. If `standard` takes you 14 hours you
are building a framework; stop and read the acceptance criteria again.

  <Tab title="standard">
    A responsive, accessible page — search with debounce, pagination, dark mode, all four UI
    states, no framework, Lighthouse ≥ 90 across the board.

    <Info>Spec and tests only. You write the implementation.</Info>

    **Acceptance criteria**

    1. **Responsive.** No horizontal scroll at any viewport width from 320 px to 2560 px. The checker sweeps in 20 px steps and asserts `document.documentElement.scrollWidth <= clientWidth` at every step.
    2. **Four states, all reachable.** Loading, empty (search matches nothing), error (bad URL or offline), success. Each has distinct, human-readable copy. The empty state for "no results for your search" differs from "the API returned no data".
    3. **Search** filters as you type, debounced at 200–300 ms, and cancels the previous in-flight request with `AbortController` when the source is remote. Typing `zim` then `zimb` must never render `zim`'s results last.
    4. **Pagination** — 24 rows per page, with working Previous/Next, a current-page indicator, and the page reflected in the URL (`?page=3`) so a reload keeps position.
    5. **Dark mode** follows `prefers-color-scheme` and can be overridden by an in-page toggle whose choice survives a reload. Both directions must work: an explicit "light" choice on a dark OS must stay light.
    6. **Accessibility.** Lighthouse accessibility ≥ 95; every input has a programmatic label; focus is visible on every interactive element; the results count is announced in a live region when it changes; the whole flow is operable with keyboard only.
    7. **Performance.** Lighthouse performance ≥ 90 on a throttled mid-tier mobile profile. No parser-blocking script. All images have `width` and `height`.
    8. **No framework.** No React, Vue, Svelte, jQuery. A CSS reset is fine. Total shipped JS under 15 KB gzipped.
    9. **Tests.** At least 8 assertions in `tests/` covering: the four states, debounce timing, abort behaviour, pagination boundaries (page 1 Previous disabled; last page Next disabled), and theme persistence.

    **Verify**

    ```bash
    cd labs/p1/week-05
    make verify TRACK=standard     # runs the resize sweep, the state machine tests and Lighthouse
    ```
  </Tab>

  <Tab title="hard">
    Add offline caching, request cancellation under rapid typing, and a virtualized list for
    50,000 items.

    <Warning>
      There is a constraint here that the `standard` solution fails: rendering 50,000 rows the
      normal way takes a measured 252.8 ms of layout and blows through fifteen frame budgets. Your
      `standard` implementation will hang the tab. That is the point.
    </Warning>

    **Acceptance criteria**

    1. **Virtualization.** The dataset is expanded to 50,000 synthetic rows (`make seed-50k`). At any scroll position the DOM contains **fewer than 200 rendered row nodes** (checked by `document.querySelectorAll('[data-row]').length`). Initial render completes in **under 50 ms** measured with `performance.mark`.
    2. **Scroll quality.** During a scripted scroll of 10,000 px, **no frame exceeds 32 ms** and the median frame is **under 16.7 ms**, measured with `PerformanceObserver` on `long-animation-frame` or a rAF timestamp delta log. Report the histogram in your README.
    3. **Correct virtualization, not fake.** `Home`, `End` and `PageDown` jump correctly; the scrollbar length is proportional to the full dataset; a row selected before a jump is still selected after scrolling back.
    4. **Offline.** A service worker caches the app shell and the last successful API response. With DevTools set to Offline, a reload renders the cached data plus a visible "showing cached data from HH:MM" banner. A failed background refresh must not blank the cached view.
    5. **Cancellation under load.** A scripted typist enters 12 characters at 40 ms intervals. At the end, exactly **one** request may be outstanding, every earlier one must be `AbortError`, and the rendered results must match the final query. The checker asserts this from the network log.
    6. **Measured write-up.** `PERFORMANCE.md` containing: naive versus virtualized render time with your own numbers, the frame-time histogram, DOM node counts, and one paragraph on what you tried that did **not** work.

    **Verify**

    ```bash
    cd labs/p1/week-05
    make seed-50k
    make verify TRACK=hard
    ```

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
Deploy to GitHub Pages, Netlify or Cloudflare Pages — all free, all under ten minutes. Put the live
URL in the repo's About field and at the top of the README. A link a stranger can click is worth
more than the code behind it, because it proves the code runs somewhere other than your laptop.
</Card>

**The README must contain**, in this order: a screenshot at 360 px and at 1440 px; the live URL;
the Lighthouse scores with the date; a two-sentence description of the architecture; the four UI
states as four screenshots; and one paragraph titled "What I would do differently".

## Rubric

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Correctness | fails tests | happy path only | all four states, pagination boundaries correct | survives adversarial input: 12-char burst typing, offline mid-request, API returning HTML instead of JSON |
| Code quality | works | readable | one state machine owns UI state; no `innerHTML` with data; delegated events | a reviewer would approve unchanged; the four states are impossible to get into an inconsistent combination |
| Performance | untested | measured | meets the budget (Lighthouse ≥ 90, no horizontal scroll) | beats it with evidence: virtualized render under 50 ms and a frame-time histogram |
| Explanation | none | a README | reasoning documented, numbers included | trade-offs defended, including one thing that did not work and why |

## Common ways this lab goes wrong

- **Building a framework.** If you have written a reactive binding system, stop. The lab tests behaviour, not architecture, and the time box assumes direct DOM code.
- **Debounce instead of cancellation.** Debouncing reduces requests; only `AbortController` guarantees the last render matches the last query. The `hard` checker specifically tests for this.
- **`overflow-x: hidden` on `body`.** This hides the resize-sweep failure instead of fixing it, and it breaks `position: sticky`. The checker measures `scrollWidth`, so it will still fail.
- **Dark mode by duplicating rules.** Re-declare custom properties instead. If your dark stylesheet is longer than 20 lines, restructure.
- **Virtualizing with `display: none`.** Hiding rows does skip their layout, but the nodes still exist, still cost memory, and still had to be created. The checker counts nodes, not visible rows. Create only what is visible.
