Working professionals start at `standard`. `hard` is where the interview stories come from.

## The ticket

> **NEXUS-114 · Analytics ingest is timing out on the nightly rollup**
>
> Reported by: data platform on-call
>
> The nightly job sorts each customer's event-id file and then answers ~40,000 "does this id
> exist" lookups against it. It has been fine for two years. Last night the largest customer's
> file crossed 50 million ids and the job was killed at the 30-minute timeout. The box has
> 16 GB but the job is boxed to a 512 MB cgroup and we are not raising it.
>
> We need three things, in this order: (1) a sort we can actually reason about, (2) evidence
> of how it scales — not an opinion, a curve — and (3) a version that completes inside the
> memory limit no matter how large the file gets.
>
> Do not just call `qsort` and close the ticket. The next person needs to know *why* it is
> fast enough, and at what n it stops being.

**Time box.** `basic` 2–3 h · `standard` 5–7 h · `hard` 4–6 h on top of `standard`. Honest estimates for someone who has read the modules; double them if you are new to C.

<Tabs>
<Tab title="basic">

**Roughly 60% is written for you.** The array plumbing, the test harness, the random-data generator and the CSV writer all exist. You write two functions marked `/* TODO */`.

```c
/* starter/basic/sorts.c */
void selection_sort(int *a, size_t n);          /* TODO */
long binary_search(const int *a, size_t n, int key);  /* TODO */
```

**Acceptance criteria — all four must pass:**

1. `make -C basic verify` is green. It runs 18 provided cases including empty array, single element, all-equal elements, already sorted, reverse sorted, and a key that is smaller than every element.
2. Your `selection_sort` sets the provided global `comparisons` counter, and for n = 8, 80 and 800 it reports exactly **28**, **3,160** and **319,600**. If it does not, your inner loop bounds are wrong. The formula is n(n−1)/2.
3. `binary_search` returns −1 for absent keys and never loops forever. The harness runs each search under a 1-second alarm; an infinite loop is a test failure, not a hang.
4. Compiles clean under `-std=c17 -Wall -Wextra -Werror` and runs clean under `-fsanitize=address,undefined`.

<Info>
Stuck on binary search? Write the invariant as a comment on the line above the loop before
you write the loop: *the answer, if present, has an index in `[lo, hi)`*. Every `+ 1` and
every missing `- 1` follows from it mechanically.
</Info>

</Tab>
<Tab title="standard">

**Spec and tests only.** You write `sorts.c`, `search.c` and `bench.c` from scratch.

**Deliverables:**

```c
/* sorts.h */
void selection_sort(int *a, size_t n);
int  nx_merge_sort(int *a, size_t n);              /* returns -1 if allocation fails */
long binary_search(const int *a, size_t n, int key);
extern long long nx_comparisons;                    /* instrumented by all three */
```

Plus `bench` — a harness that, for each n in a configurable list, generates random data with a fixed seed, runs each algorithm `R` times, and writes one CSV row per (algorithm, n).

**Acceptance criteria — all seven:**

1. All `basic` tests pass, plus the provided `standard` property tests: sorting is idempotent, the output is a permutation of the input (verified with a multiset check, not just a sum), and merge sort is **stable** (verified on an array of structs with a payload field).
2. `nx_comparisons` for selection sort equals n(n−1)/2 exactly, and for merge sort is within 5% of n·log₂n − n + 1. At n = 1,000,000 the reference implementation reports **18,673,546** against a theoretical 18,931,570 — 1.4% under.
3. `nx_merge_sort` performs **exactly one** allocation for the whole sort, verified by the test's `malloc` interposer. Allocating inside the recursion is an automatic fail on this criterion; at n = 1,000,000 it costs about 63 ms of pure allocator time.
4. `nx_merge_sort` returns −1 and leaves the array untouched when allocation fails. The test forces this by injecting a failing allocator.
5. The benchmark uses `CLOCK_PROCESS_CPUTIME_ID`, not wall clock, and reports the **minimum** of R runs. It must print the load average it observed alongside the results.
6. CSV output has the header `algorithm,n,cpu_ms,comparisons` and is consumed by the provided `plot.py` without editing.
7. Zero findings under `-fsanitize=address,undefined`. On Linux additionally zero errors from `valgrind --leak-check=full --error-exitcode=1`; on Apple Silicon that step is skipped automatically and `leaks -atExit` runs instead.

<Info>
The measurement discipline is graded, not incidental. Wall-clock timing on a loaded machine
gave us 1.0 s, 9.2 s, 12.6 s, 19.3 s and 27.2 s for the *same binary and input*. CPU time
plus minimum-of-N is the difference between a benchmark and a rumour.
</Info>

</Tab>
<Tab title="hard">

**The constraint the `standard` solution fails: a hard memory ceiling.**

Sort a 200 MB binary file of 50,000,000 little-endian `int32` values under a **16 MB** resident-memory budget, enforced. Your `standard` merge sort needs 400 MB (the array plus its scratch buffer) and will be killed.

```bash
make -C hard verify      # runs under a 16 MB RSS limit and fails the build if exceeded
```

**Acceptance criteria — all six:**

1. Output file is byte-identical to the reference sorted file (`cmp` exits 0), for a 50,000,000-element input.
2. **Peak RSS stays under 16 MB × 2.2 = 35 MB**, measured with `getrusage(RUSAGE_SELF).ru_maxrss` and cross-checked with `/usr/bin/time -l` (macOS) or `-v` (Linux). The 2.2 factor is honest slack for the runtime and I/O buffers; the reference solution measures **33.1 MB** and the README must explain where every megabyte went.
3. The program prints run count, split-phase time, merge-phase time and peak RSS to stderr in one line.
4. It works for a file whose size you did not know at compile time, including a file that is not a multiple of the chunk size, and including an empty file.
5. Temporary run files are cleaned up on **every** exit path, including `SIGINT`. Kill it mid-merge and there must be no orphaned `run_*.bin`.
6. Your README reports the measured crossover: at what memory budget does the external sort become slower than the in-memory sort, and by how much? The reference numbers are below — beat them or explain why you cannot.

**Reference measurements** (Apple M3 Pro, macOS 15, clang 15 `-O2`, 50,000,000 int32 = 200 MB, machine under load):

| Approach | Memory budget | Runs | Split | Merge | Total | Peak RSS |
|---|---|---|---|---|---|---|
| In-memory `qsort` | none | — | — | — | **5,460 ms** | **192.0 MB** |
| External merge sort | 64 MB | 3 | 5,091 ms | 617 ms | **5,709 ms** | 127.8 MB |
| External merge sort | 16 MB | 12 | 5,611 ms | 1,132 ms | **6,742 ms** | **33.1 MB** |

Read those rows before you start. The external sort at a **5.8× smaller footprint costs 23% more time.** That is the entire argument for this technique, and it is the paragraph your README needs.

<Warning>
Two traps are deliberately in this track.

**The budget accounting trap.** The 64 MB run measured 127.8 MB peak RSS — twice its
"budget" — because the split-phase buffer and the merge-phase per-run buffers were sized
independently against the same number. Your budget must cover the *maximum over phases*,
not each phase separately. This is the single most common failure on this track.

**The k-way merge trap.** With 12 runs, a linear scan over run heads costs O(k) per output
element — measured at 1,132 ms versus 617 ms for 3 runs, a 1.8× penalty for 4× the runs.
At 100+ runs it dominates. Replace the scan with a binary min-heap (O(log k)) and re-measure.
Report both numbers.
</Warning>

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
A public GitHub repo containing the code, the CSV, the log-log plot, and a README a stranger can read.
</Card>

The README must contain, at minimum:

1. **Your machine and toolchain**, exactly: CPU, OS version, compiler version, and the load average during measurement.
2. **The log-log plot** with the fitted slope annotated on each line. Reference values: **1.95** for selection sort, **1.06** for merge sort, **1.11** for `qsort`.
3. **One paragraph explaining the fitted exponent.** Why is merge sort's slope 1.06 and not 1.00? (Because n log n on a log-log plot is not a straight line — its local slope is 1 + 1/ln n, which at n between 10³ and 10⁶ averages about 1.06. If your write-up says "measurement noise", it is wrong and the grader will say so.)
4. **The `qsort` result and why.** Your hand-written merge sort should beat the C library by roughly 1.75× at n = 1,000,000. Name the mechanism: an indirect call through a function pointer per comparison, which cannot be inlined.
5. **One thing you got wrong first**, and how you found it. This is graded. A lab with no wrong turns was not attempted honestly.

## Verify yourself

```bash
cd labs/p1/week-01
make verify           # green on a correct solution, red on the starter
make verify TRACK=hard # adds the RSS ceiling and the 200 MB fixture
make bench            # writes results.csv
python3 bench/plot.py results.csv -o runtime.png   # log-log with fitted slopes
```

`make verify` runs, in order: `-Werror` compile of every source file, the full test suite under `-fsanitize=address,undefined`, the platform-appropriate leak check, and a byte-comparison of the sorted output against the reference. Any red is a fail; there is no partial credit inside `verify`.

## Rubric

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Correctness | tests fail | happy path only | all provided edge cases pass (empty, single, all-equal, sorted, reverse) | passes property tests too: permutation check, stability, injected allocation failure |
| Memory | leaks or sanitizer findings | clean under ASan | clean under ASan+UBSan and the platform leak checker | `hard` track holds the RSS ceiling with the budget accounting explained |
| Performance | no measurement | timed with wall clock, single run | CPU time, minimum of N, load average reported | exponents fitted and matching theory; the `qsort` gap explained by mechanism |
| Explanation | no README | README describes what the code does | README explains the trade-offs and the measurement method | README defends the exponent, the `qsort` result and one wrong turn, with numbers |

**Passing bar:** 2 or better on every row. **Portfolio bar:** 3 on Explanation — that is the row that makes the repo worth linking from a resume, and it is the row most people leave at 1.
