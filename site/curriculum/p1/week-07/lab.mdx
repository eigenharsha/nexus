## The ticket

> **NEX-311 · Data · P1**
>
> **Reporter:** Nisha (Head of Growth) · **Assignee:** you
>
> We are eight months in and I cannot get a straight answer to any of these:
>
> - How many customers who bought in January bought again in February? In March?
> - What are the top 3 products in each category, by units and by revenue?
> - Which customers have not ordered in 90 days but ordered twice before that?
> - What is our refund rate by product category, month over month?
>
> Analytics currently exports a CSV and someone does it in a spreadsheet. Last month two people
> produced different revenue numbers for the same period and we spent a day finding out why.
>
> I want a real schema, real data, and a `queries/` directory I can run. And I want to know these
> queries will still be fast when we are ten times bigger — we are growing about 15% a month.

**Time box.** `basic` 4 h · `standard` 12 h · `hard` 8 h more. If you are past 20 hours on
`standard` you are probably seeding data row by row; read the `COPY` section of `P1-W07-M5`.

    Complete a partial schema and write 15 supplied queries.

    <Info>~60% of the schema is written for you. The `TODO` comments mark what is missing. Answers in the solution page.</Info>

    **Acceptance criteria**

    1. The schema completes: `customers`, `products`, `orders`, `order_items` with correct primary keys, foreign keys, `NOT NULL`s and a `CHECK` on `status`.
    2. Money is stored as `bigint` minor units or `numeric(12,2)` — never `float`. The checker inspects `information_schema.columns`.
    3. Every timestamp column is `timestamptz`, not `timestamp`.
    4. `make seed` loads the provided CSVs with `COPY` (not `INSERT`) and completes in under 30 seconds.
    5. All 15 queries return the exact expected result sets. Three of them are designed so that a careless join gives a plausible but wrong answer.
    6. `EXPLAIN ANALYZE` output is committed for any query taking over 100 ms.


  <Tab title="standard">
    Design the full normalized schema, seed 1,000,000 rows, and write 20 analytical queries with
    `EXPLAIN ANALYZE` evidence.

    <Info>Spec and expected results only. You design the schema and write the queries.</Info>

    **Acceptance criteria**

    1. **Schema.** `users`, `products`, `inventory`, `carts`, `cart_items`, `orders`, `order_items`, `payments`, `refunds`, `reviews`. In 3NF, with a written justification for any deliberate denormalization. Every table has `created_at`/`updated_at`.
    2. **Constraints as correctness.** At minimum: a partial unique index enforcing one open cart per user; a `CHECK` that a refund never exceeds its payment; `ON DELETE RESTRICT` on anything financial; `unit_cents` captured on the order line at sale time, not joined from the product.
    3. **Seed.** `make seed` produces at least 1,000,000 orders with realistic repeat-purchase behaviour — customers must have multiple orders spread over months, or the cohort query is meaningless. It completes in under 3 minutes using `COPY`.
    4. **Twenty queries** in `queries/`, each in its own file with a header comment stating the question, **the grain of the result**, and the expected row count. Must include: monthly cohort retention, top-N per group, refund rate by category by month, a customer RFM segmentation, a gaps-and-islands streak query, and a 7-day moving average.
    5. **Plan evidence.** For every query, committed `EXPLAIN (ANALYZE, BUFFERS)` output with a note on the dominant node.
    6. **Correctness harness.** `make check-grain` runs every query and asserts its declared row count, and asserts the retention matrix is monotonically non-increasing across months.
    7. **Reproducible.** A fresh clone plus `make db-up seed verify` works with no manual steps.

    **Verify**

    ```bash
    cd labs/p1/week-07
    make verify TRACK=standard   # schema checks, result sets, grain assertions, plan presence
    ```
  </Tab>

  <Tab title="hard">
    Hit stated latency targets on 10,000,000 rows using indexing and query rewrites, and document
    every index with the query it serves and its write cost.

    <Warning>
      The `standard` solution will miss these targets. Several queries that run in 300 ms on 1M rows
      take over 4 seconds on 10M, and at least one degrades non-linearly because a sort starts
      spilling to disk.
    </Warning>

    **Acceptance criteria**

    1. **Scale.** `make seed SCALE=10` produces 10,000,000 orders and roughly 30,000,000 order items.
    2. **Latency targets**, measured warm, median of five runs: point lookup by customer under **5 ms**; the top-N-per-category query under **1.5 s**; the cohort matrix under **8 s**; the customer order history page (20 rows, keyset paginated) under **10 ms at any depth**.
    3. **Index register.** `INDEXES.md` with one row per index: its definition, the exact query it serves, the measured before and after, its size, and its measured write cost. An index with no named query fails the review.
    4. **Write-cost measurement.** Measure insert throughput with and without your index set — the reference measured 50,000 inserts at 788.9 ms with none and 1,591.8 ms with five, a 2.02× penalty. Report yours.
    5. **Pagination.** The order history must use keyset pagination. The checker requests page 1 and a page at depth 500,000 and asserts both are under 10 ms — offset pagination measured 693.9 ms at that depth and will fail.
    6. **No index left unjustified.** `make verify` fails if `pg_stat_user_indexes.idx_scan` is zero for any index you created, after the benchmark suite has run.
    7. **Write-up.** `PERFORMANCE.md`: for each target, the plan before, the change, the plan after, and one thing you tried that did not help.

    **Verify**

    ```bash
    cd labs/p1/week-07
    make seed SCALE=10
    make verify TRACK=hard
    make bench            # median-of-five warm timings against every target
    ```
  </Tab>

## Rubric

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Correctness | queries fail | correct on the happy path | correct grain declared and asserted for every query; NULL semantics handled | survives adversarial data: duplicate emails, refunds exceeding payments, orders with no items, ties in every ranking |
| Code quality | works | readable | constraints express the business rules; queries use CTEs and are commented with their grain | a reviewer would approve unchanged; the wrong query is hard to write because the schema forbids the wrong data |
| Performance | untested | timings recorded | all targets met | every index justified by a named query with before/after evidence and a measured write cost |
| Explanation | none | a README | grain and plan reasoning documented | trade-offs defended, including a denormalization decision with its stated cost and one thing that did not work |

## Common ways this lab goes wrong

- **Seeding with `INSERT`.** Measured, 100,000 rows took 83.8 s that way and 0.295 s with `COPY`. At a million rows the difference is the whole afternoon.
- **A seed with no repeat purchases.** If every customer has exactly one order, the cohort query returns a column of zeros and looks broken. The reference seed gives each customer a geometric number of orders with 12–52 day gaps.
- **The fan-out bug in at least one query.** Every cohort produces it. Declare the grain in each query's header comment and assert the row count — that is what `make check-grain` is for.
- **Indexes added speculatively.** `make verify` fails on any index with zero scans after the benchmark. An index you cannot attach to a query is write cost with no read benefit.
- **Offset pagination on the history page.** It passes at page 1 and fails at depth. Measured 693.9 ms versus 1.7 ms for keyset.
- **`float` for money.** The schema checker reads `information_schema.columns` and fails the track outright.
