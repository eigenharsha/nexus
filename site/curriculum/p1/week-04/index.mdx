## Outcome

<Note>By Sunday you can look at a workload, decide in one measurement whether it needs threads, processes or asyncio, and build an async pipeline that is fast, bounded in memory and concurrency, and does not make an upstream outage worse.</Note>

Five things you cannot do today and will be able to do by Sunday night:

1. Produce the full benchmark matrix and defend every cell — including the two that surprise people: threads make CPU-bound Python **0.86×** as fast, and processes give **3.57×** on I/O where threads give **14.09×**.
2. Reproduce a race that loses **64.86% of 16 million increments**, and explain why the textbook version of the same demo loses nothing on CPython 3.13.
3. Find the task size at which a process pool starts paying — measured between **10⁴ and 10⁵** iterations — and separate pool startup from pickling cost.
4. Write a **151-line event loop** over `selectors` that runs your own coroutines: 20 concurrent HTTP requests in **0.064 s** on one thread.
5. Take a client against a flaky, rate-limited server from **71% success** to **100% with zero server-side 429s**, and say what that cost.

## Why this week

Every system you build after this one waits on something: a database, an API, a GPU, another service. Week 4 is where you learn that "make it faster" almost always means "make it wait less", and that the three tools for doing so are not interchangeable.

It is also the week with the most folklore per square inch. "Python can't do concurrency", "the GIL makes threads useless", "always use asyncio", "`counter += 1` is atomic" — all four are wrong in interesting ways, and this week replaces each with a measurement.

<Note>
**Measured.** Every figure in this week was produced on an Apple M3 Pro (11 cores, 18 GB),
macOS 15, CPython 3.13.2, with `aiohttp` 3.14.3, `httpx` 0.28.1 and `uvloop` 0.22.1 — the exact
versions pinned below, on the machine this course was written on. The pages note where the machine
was under load, because process-pool speedups would be higher on an idle one.

Three results here contradict the folklore and were kept as they came out: **`asyncio` measured
slowest** of the three socket models at 1,000 connections, **`uvloop` was worth 2.1%** here rather than
the 2–4× of Selivanov's magic.io benchmarks (a **cited finding**, measuring a different workload), and the classic lost-update race **does not reproduce** on CPython 3.13.
Amdahl's law and the Little's-law predictions are **derived** — arithmetic that holds on any
machine. See [About the numbers](/start/about-the-numbers).
</Note>

## Set up before Monday

```bash
uv venv --python 3.13 && source .venv/bin/activate
uv pip install aiohttp httpx uvloop py-spy pytest pytest-asyncio

python3 -c "import aiohttp, httpx; print(aiohttp.__version__, httpx.__version__)"   # 3.14+, 0.28+
py-spy --version
```

Start the fixture servers the labs use — one with a fixed 50 ms delay, one flaky:

```bash
python3 labs/p1/week-04/fixtures/slow_server.py   &   # 127.0.0.1:8099, fixed 50 ms
python3 labs/p1/week-04/fixtures/flaky_server.py  &   # 127.0.0.1:8098, 30% fail, 500/min
curl -s localhost:8099/slow/1
```

<Warning>
**Benchmark against a local fixture server, never a public API.** Every measurement this week
depends on the server's latency being fixed and known; a public endpoint adds variable network
latency, its own rate limits, and the possibility that you are the reason someone's dashboard
went red. The fixture servers exist so the numbers mean something.

Also: **`py-spy` is the tool to install before you need it.** `py-spy dump --pid` gives every
thread's stack from a wedged production process without a restart and without prior
instrumentation. Learning it on a lab is much better than learning it during an incident.
</Warning>

## What "done" looks like

- A public repo with the downloader and a benchmark README comparing **sync, threaded and async on the identical workload**, with speedup, worker count, efficiency and machine load for each.
- Your own benchmark matrix, eight cells, every one defended in a sentence.
- An event loop you wrote, with the measurement proving it runs 20 requests concurrently on one thread.
- The flaky-server tuning table: success rate, wall time, retries, server 429s and p99 for at least three client configurations.
- Zero corrupted or double-written files across the `hard` track's 10,000 URLs, proven by checksum.
- One diagram redrawn from memory and committed.
