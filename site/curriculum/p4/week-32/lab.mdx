## The ticket

> **OPS-77 · Platform Engineering · P1**
>
> Two things happened this quarter. Finance asked what the assistant costs per resolved ticket and
> nobody could answer — we have an invoice and a request count and no link between them. And an
> intermittent quality problem took four days to notice and three more to diagnose, because the only
> evidence was a support lead's impression.
>
> We need to be able to answer three questions on any given day: what did this specific run do, what
> did it cost, and is quality where it was last week. Then we need the cost down — the invoice is
> growing faster than usage.
>
> Deliverable: instrumentation, dashboards, alerts, a documented cost-reduction experiment with
> before-and-after numbers, and `OPERATIONS.md` that an engineer joining next month could work from.

**Time box, honestly:** `basic` 4 hours · `standard` 14–18 hours · `hard` a further 10–12 hours.

<Tabs>
<Tab title="basic">

### What you build

OpenTelemetry spans around every LLM call, exported to a local collector.

**Given to you** (`labs/p4/week-32/starter/basic/`): the Week-30 agent, a collector config, a
Docker Compose file, and `test_basic.py`.

**You write:**

<Steps>
<Step title="A span per model call">
Using the GenAI semantic conventions verbatim: `gen_ai.system`, `gen_ai.operation.name`, `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.response.finish_reasons`.
</Step>
<Step title="A cost attribute">
Under your own prefix, not `gen_ai.` — and including cache creation at 1.25× and cache read at 0.1×.
</Step>
<Step title="A root span per run">
So all spans of one run share a trace id. Then verify it: count the spans in one trace.
</Step>
<Step title="Error recording">
`record_exception` plus `set_status(ERROR)`, then re-raise. A span that swallows the exception is worse than no span.
</Step>
</Steps>

**Acceptance:** `make verify TRACK=basic` — 10 tests against an in-memory exporter, no API calls,
under 3 seconds. Two of them assert that all spans in a run share one trace id, which is the
subtlety of this track.

<Info>~60% of the code is written for you. TODOs are marked.</Info>

</Tab>
<Tab title="standard">

### What you build

**Part A — instrumentation**

<Steps>
<Step title="Full graph instrumentation">
Span per node, per tool, per retrieval, per model call. Correct nesting including across any thread pool or queue — and a test that proves the nesting rather than assuming it.
</Step>
<Step title="Langfuse, self-hosted">
Docker Compose, sessions from your domain id, pseudonymous user ids, environment tags from the first trace.
</Step>
<Step title="Prompt versioning">
Prompts as labelled objects fetched at runtime, with a local fallback and a cache TTL. Practise a rollback and time it.
</Step>
<Step title="Redaction and sampling">
PII redaction in a SpanProcessor with attribute-length caps; collector-side tail sampling keeping 100% of errors and the latency tail.
</Step>
</Steps>

**Part B — cost**

Per-step cost attribution from trace attributes, with a p95 column. Then the experiment: at least
three levers applied cumulatively, each with a before/after row and an eval-suite check, reported as
**cost per successful task**. Prompt caching with `cache_read_input_tokens` asserted non-zero.

**Part C — operations**

<Steps>
<Step title="Scheduled evals">
Every six hours against production configuration, alerting on a drop from the trailing baseline, with the frozen canary subset alongside the full suite.
</Step>
<Step title="Dashboards">
Success rate, TTFT p50/p95, cost per successful task, groundedness p10, offline/online gap, unreviewed eval candidates. Six tiles, no more.
</Step>
<Step title="Alerts">
Routed by urgency: pages for fast-moving failures, tickets for slow-moving trends. An alert that pages on a quality trend gets muted within a month, and takes the real ones with it.
</Step>
<Step title="OPERATIONS.md">
SLOs and the error-budget policy, the runbook for "the model is producing garbage", the fallback's measured quality delta, and who is paged for what.
</Step>
</Steps>

<Info>Spec and tests only. `make verify TRACK=standard` runs 36 tests in under 12 seconds with no API calls.</Info>

</Tab>
<Tab title="hard">

### The constraints the standard solution fails

<Steps>
<Step title="At least 50% off cost per successful task, no quality regression">
The waterfall must include one lever that **increases** cost per run and decreases cost per successful task, and one measured counter-example — a configuration that is cheaper per call and worse per outcome. Both rows are required; they are how you prove you optimized the right quantity.
</Step>
<Step title="A documented game day">
Four conditions — provider outage, rate limiting, a silently degraded model, a prompt-injection attempt — diagnosed from telemetry alone, with detection times. Then run it once **blind**, with a colleague choosing the condition and the time, and publish both sets of times.
</Step>
<Step title="Tail sampling under load">
Load-test at 3× normal traffic with tail sampling active. Report traces retained, error traces retained, collector memory, and prove that a run longer than `decision_wait` is not truncated.
</Step>
<Step title="A published TCO analysis">
Every line including engineer-days. Then the model-deprecation plan with a per-migration estimate, and the answer to "who decides to turn this off, and on what condition".
</Step>
</Steps>

<Warning>
There is a constraint here that the `standard` solution fails: a `decision_wait` set below your p99
run duration silently truncates long traces under load, and a cost programme that optimizes cost per
call will produce a waterfall whose bottom row is worse per successful task than a row above it. Both
have to be engineered rather than discovered.
</Warning>

</Tab>
</Tabs>

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
Dashboards (six tiles, screenshotted), `OPERATIONS.md` (SLOs, error-budget policy, the
garbage-output runbook, the fallback's measured quality delta, the on-call contract), and **the
architecture poster** — one page, every component, your own measured numbers written on the
components they belong to.
</Card>

The poster is the capstone's first slide and the thing people will actually look at. A component
with no number next to it is a component nobody measured, and that is the most useful thing the
exercise will tell you.

## Verify yourself

```bash
cd labs/p4/week-32
make verify TRACK=basic       # 10 tests, in-memory exporter, ~3 s
make verify TRACK=standard    # 36 tests, no API calls, ~12 s
make verify TRACK=hard        # 36 + load test + game-day assertions

make trace-one                # runs one task, prints the trace url and the span tree
make cost-report              # per-node cost with p95; writes cost/report.md
make cost-experiment          # the full waterfall with eval checks at every step
make gameday CONDITION=random # injects one of the four; you diagnose from telemetry
make loadtest RATE=3x         # tail sampling under load; writes ops/loadtest.md
```

`make cost-experiment` must print cost per **successful** task on every row, and must fail if any
row's eval-suite result is a newly-failing case. A cost reduction that regresses quality is not a
result.

## Rubric

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Instrumentation | none | spans around model calls | full graph, correct nesting proven by test, GenAI conventions | tail sampling, boundary redaction, cardinality audit, overhead measured |
| Cost | invoice only | cost per run | per-step attribution with p95, ≥50% reduction | the waterfall including the row that costs more per run, plus the counter-example |
| Operations | nothing | some dashboards | SLOs with an error budget, alerts routed by urgency, runbook | game day with detection times, run once blind |
| Maintainability | none | a README | `OPERATIONS.md` an engineer could work from | TCO including engineer-days, deprecation plan, and who decides to switch it off |
| Communication | none | a diagram | the poster with components and boundaries | the poster with your own measured numbers on the components, presented in 5 minutes |

Score 12+/15 before you call it done. **Cost below 2 is a fail regardless of total** if the report
uses cost per call anywhere as the headline — this is the week whose one non-negotiable unit is cost
per successful task.
