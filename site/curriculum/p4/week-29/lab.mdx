## The ticket

> **SUP-4412 · Platform Engineering · P2**
>
> Support engineers spend roughly 40 minutes per escalated ticket doing the same three things:
> looking the order up in Postgres, grepping the service logs for the order reference, and reading
> the relevant runbook. We want an assistant that does the lookup part so the engineer starts from
> evidence instead of from a blank page.
>
> Constraints from the security review, non-negotiable:
> the assistant gets **read-only** database access; shell access must be **sandboxed and
> allow-listed**; every command it runs must be in an audit log we can query by ticket; and it must
> not be possible for text inside a customer ticket to cause a command to run.
>
> Deliverable: a working assistant, a benchmark showing it actually helps, and a `SECURITY.md` the
> security team will sign.

That is the whole brief. Note what it does *not* say: it does not ask for an agent. Part of your job
is deciding how much agency this needs, and defending it.

**Time box, honestly:** `basic` 3 hours · `standard` 10–14 hours · `hard` a further 8–10 hours.

<Tabs>
<Tab title="basic">

### What you build

A ReAct loop with two tools and a max-iteration guard. No framework, no MCP yet.

**Given to you** (in `labs/p4/week-29/starter/basic/`): a seeded SQLite database with 500 orders, a
20 MB log file, the tool schemas, and `test_basic.py`. About 60% of the code, with `TODO` markers.

**You write:**

<Steps>
<Step title="The loop">
`run(task, max_steps)` — call the model, append the assistant turn, dispatch tool calls, append results, repeat. Return when the model stops calling tools.
</Step>
<Step title="Two tools">
`order_lookup(order_id)` against SQLite, and `search_logs(pattern)` over the log file. Both return strings. Both return readable errors instead of raising.
</Step>
<Step title="The guard">
`max_steps=6`. On exhaustion, return a `Result` whose `stop_reason` is `"step_limit"` — not an exception, not `None`.
</Step>
<Step title="Truncation">
Cap every tool result at 4,000 characters and tell the model it was capped.
</Step>
</Steps>

**Acceptance:** `make verify TRACK=basic` runs 9 tests against a mocked model. All must pass. Two of
them assert on the `stop_reason`, because "it worked on my question" is not evidence.

<Info>~60% of the code is written for you. TODOs are marked. Answers provided in the solution page — after you have a failing attempt.</Info>

</Tab>
<Tab title="standard">

### What you build

The real thing: a from-scratch agent plus a custom MCP server, benchmarked.

**Part A — the agent** (`agent/`)

<Steps>
<Step title="Typed tool registry">
Pydantic argument models, generated JSON Schema, deterministic ordering, per-tool result caps, validation errors returned as feedback.
</Step>
<Step title="Budgets and stop conditions">
Steps, dollars and wall-clock, all enforced. Four stop reasons: `done`, `step_limit`, `budget`, `no_progress`. The `no_progress` detector fires on three identical call signatures in a row.
</Step>
<Step title="Memory">
Sliding window plus a rolling summary, under a 60,000-token budget counted with `messages.count_tokens`. Prompt caching on the stable prefix, with a test asserting `cache_read_input_tokens` is non-zero by turn three.
</Step>
<Step title="Retries">
Idempotent tools retry on timeout with jittered backoff. Non-idempotent tools do not retry — ever. Mark them in the registry and assert on it in a test.
</Step>
</Steps>

**Part B — the MCP server** (`mcp_server/`)

<Steps>
<Step title="Database tools">
`order_lookup` and `search_orders` against a Postgres role that has `SELECT` and nothing else. Prove the restriction with a test that attempts an `UPDATE` and expects a permission error from the database, not from your code.
</Step>
<Step title="Sandboxed terminal">
One `run` tool. Program allow-list, per-program flag allow-list, `shlex.split` and argv (never `shell=True`), resolve-then-contain on every path argument, 5-second timeout, 64,000-character output cap, no network, scrubbed environment, append-only JSONL audit log with a call id echoed in the result.
</Step>
<Step title="Standalone tests">
The server must be testable with no agent and no model: pytest against the tool functions directly, plus a session-level test through `stdio_client`.
</Step>
</Steps>

**Part C — the benchmark**

30 tasks from the ticket queue, each with a written acceptance criterion authored *before* you run
anything. Report: success rate, mean steps, derived per-step reliability, cost per run, cost per
successful task, p50 and p95 latency, and a `stop_reason` histogram. One table, in the README.

**Part D — the test suite**

Mocked model throughout (`models.ALLOW_MODEL_REQUESTS = False` or your own equivalent). Under 10
seconds. Must include one safety-property test: a read-only question never reaches a write tool.

<Info>Spec and tests only. You write the implementation. `make verify TRACK=standard` runs 31 tests.</Info>

</Tab>
<Tab title="hard">

### The constraints the standard solution fails

<Steps>
<Step title="30 tools, accuracy maintained">
Grow the tool surface to 30 (add ticketing, deploy history, metrics, more of the database). Measure selection accuracy on a 120-prompt labelled set. **The bar: 90% or better.** A naive 30-tool surface lands near 82%. Get there with namespacing, enum-collapsed near-neighbours and four-clause descriptions — then also report the deferred-loading variant with its schema-token and cost delta.
</Step>
<Step title="Adversarial testing of the sandbox">
Fifteen documented attack attempts minimum, each with: the command, the version it was run against, the outcome, the control that stopped it (or why nothing did), and the fix. Include at least one attack that succeeded against your own v1 or v2 — a report where nothing ever worked is a report that stopped early.
</Step>
<Step title="Injection through tool results">
Plant a hostile instruction inside a log line and inside a runbook file. Show what the agent does. Then show what your design does about it. The correct answer is not "the model refused" — it is "no tool downstream could have done the damage".
</Step>
<Step title="Cost ceiling">
The 30-task benchmark must complete for under $4.00 total, with the success rate no worse than your standard-track run. Prompt caching, tool deferral and a smaller model for mechanical steps are the levers.
</Step>
</Steps>

<Warning>
There is a constraint here that the `standard` solution fails: at 30 tools, the standard tool surface
loses roughly 8 points of selection accuracy, and its schema tokens push the benchmark over the cost
ceiling. Both have to be engineered, not wished away.
</Warning>

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
A public repository with a README that leads with the benchmark table, and a `SECURITY.md`
documenting the MCP server's trust boundary: what the server can reach, what identity it acts as,
every control mapped to the attack it blocks, the fifteen attack attempts with outcomes, at least
two honest accepted risks, and the exact audit-log query that answers "what did this server do for
this user in this window".
</Card>

Rare and highly credible artifact. Most people who claim agent experience have never written the
second document, and a reviewer can tell in thirty seconds.

## Verify yourself

```bash
cd labs/p4/week-29
make verify TRACK=basic       # 9 tests,  mocked model, ~2 s
make verify TRACK=standard    # 31 tests, mocked model, ~8 s
make verify TRACK=hard        # 31 + selection benchmark + sandbox attack suite

make bench                    # runs the 30-task benchmark, writes bench/results.md
make attack                   # runs the 15 documented attacks against your server
```

`make verify` is green on a correct solution and red on the starter. `make attack` prints a table
per attack per server version; every row must be `blocked` or carry a written justification in
`SECURITY.md`.

## Rubric

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Correctness | fails tests | happy path only | four stop conditions, errors fed back, results capped | adversarial inputs handled; the `no_progress` and budget paths proven by test |
| Code quality | works | readable | typed, tested, dependencies injected | a reviewer would approve unchanged; safety-property test present |
| Performance | untested | measured | benchmark table with cost per successful task | cost ceiling met with no quality regression, levers explained |
| Security | shell tool with `shell=True` | allow-list only | argv, containment, timeout, output cap, audit log | isolation, flag allow-lists, scrubbed env, 15 documented attacks, accepted risks stated |
| Explanation | none | a README | design decisions documented | trade-offs defended, including where you chose *not* to use an agent |

Score 12+/15 before you call it done. Anything below 2 on Security is a fail regardless of the
total — this is the one row where the average does not save you.
