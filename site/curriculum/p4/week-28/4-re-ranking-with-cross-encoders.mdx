## The mental model

A bi-encoder must embed the document *before it knows the query*, so its representation must be
useful for every possible query. A cross-encoder reads the query and the document **together** and
can attend across them — every document token can look at every query token. That is far more
accurate and impossible to precompute, which is why it runs on 50 candidates and not on 47,300.

    ### Bi-encoder versus cross-encoder

    Week 27 Module 3 drew a dotted line between two model boxes and labelled it "they never meet".
    That is a **bi-encoder**: the query goes through the model, the document goes through the model,
    and the two resulting vectors are compared with a dot product. The model never sees them
    together.

    A **cross-encoder** removes the line. It takes `[query] [SEP] [document]` as one input, runs one
    forward pass, and outputs a single relevance score. Because it is one sequence, attention
    (Week 25 M3) lets every document token look at every query token — the model can notice that the
    document's "45 days" is the answer to the query's "how long", which a bi-encoder can only hope
    it encoded in advance.

    | | Bi-encoder | Cross-encoder |
    | --- | --- | --- |
    | Input | query and document separately | query and document concatenated |
    | Output | two vectors | one score |
    | Precomputable? | **Yes** — document vectors at ingest | **No** — depends on the query |
    | Cost per query | one encode, then dot products | one full forward pass **per document** |
    | Accuracy | good | **better** |

    ### The arithmetic that decides the architecture

    The reference reranker, `BAAI/bge-reranker-base`, scores about **520 query-document pairs per
    second** on an A10G at 512 tokens — a reference figure, modelled (see [About the numbers](/start/about-the-numbers)). The corpus is
    47,300 chunks.

    ```
    47,300 pairs ÷ 520 pairs/sec = 91 seconds per query
    ```

    **Ninety-one seconds.** That is the whole reason cross-encoders are not retrievers. There is no
    tuning that fixes it, because the cost is intrinsically linear in corpus size and every pair
    needs a full transformer forward pass.

    So: **two stages.** A cheap retriever finds 50 plausible candidates from 47,300 in 8.9 ms, and
    the expensive model reorders those 50 in 96 ms. You get most of the cross-encoder's accuracy for
    0.1% of its cost.

    ### The analogy

    Hiring. You have 47,300 applications and one job.

    **Stage 1** is a keyword-and-CV filter. Cheap, crude, and it will let through some bad
    candidates and reject some good ones — but it runs over everyone in seconds and leaves you 50.

    **Stage 2** is a one-hour interview. Far more accurate, because you can ask follow-up questions
    and the candidate can respond to *you* rather than having written their CV in advance for
    everybody. You cannot interview 47,300 people, so you interview 50.

    And the property that matters: **stage 2 can only choose among what stage 1 passed through.** If
    the best candidate was rejected at CV screening, no amount of interviewing recovers them. This
    is why rerank depth matters and why Recall@50 is the ceiling on everything reranking can do.

    ### Smallest working example

    ```bash
    pip install sentence-transformers==3.0.1
    ```

    ```python
    # rerank_demo.py
    from sentence_transformers import CrossEncoder

    ce = CrossEncoder("BAAI/bge-reranker-base", max_length=512)

    query = "How long do I have to return non-defective goods?"
    candidates = [
        "Warehouse operations run Monday to Friday, 08:00 to 18:00.",
        "Returns of defective goods must be reported within 14 days of delivery.",
        "Non-defective goods may be returned within forty-five (45) days, unopened.",
        "Shipping costs for returns are borne by the supplier in all cases.",
        "The returns process is described in Section 8 of the supplier agreement.",
    ]

    scores = ce.predict([(query, c) for c in candidates])
    for score, text in sorted(zip(scores, candidates), reverse=True):
        print(f"{score:7.3f}  {text[:70]}")
    ```

    ```
      8.412  Non-defective goods may be returned within forty-five (45) days, unopened.
      1.905  Returns of defective goods must be reported within 14 days of delivery.
     -1.244  The returns process is described in Section 8 of the supplier agreement.
     -3.871  Shipping costs for returns are borne by the supplier in all cases.
     -7.102  Warehouse operations run Monday to Friday, 08:00 to 18:00.
    ```

    Compare that spread with the bi-encoder's. In Week 27 Module 3, the correct answer scored 0.78
    and the near-miss scored 0.71 — **a gap of 0.07 on a scale where unrelated text scores 0.3**.
    Here the correct answer scores 8.41 and the near-miss 1.91: the cross-encoder is *confident*,
    because it could read the query's "non-defective" against the document's "non-defective" rather
    than hoping both were encoded compatibly.

    ### Line-by-line walkthrough

    - `CrossEncoder(...)` — a 278M-parameter model, about 1.1 GB in fp32 or 560 MB in fp16. It runs
      on CPU (slowly) and on any GPU.
    - `max_length=512` — the query and the document share this budget. A 512-token chunk plus a
      12-token query gets truncated, and **the truncation silently drops the end of your chunk**.
      Layer 2 measures the cost.
    - `ce.predict([(query, c) for c in candidates])` — a list of pairs. The same query is repeated in
      every pair, which feels wasteful and is unavoidable: the whole point is that the model sees
      them together.
    - **The scores are unbounded logits, not probabilities.** They are comparable *within* one
      query's candidate list and meaningless *across* queries. A score of 8.4 on one query and 3.1
      on another does not mean the first is a better match — which matters for Module 5, where you
      might be tempted to threshold on them.

    ### The two-stage pipeline

    ```python
    # rerank.py — sentence-transformers 3.0.1, torch 2.4.1
    import torch
    from sentence_transformers import CrossEncoder

    class Reranker:
        def __init__(self, model: str = "BAAI/bge-reranker-base",
                     max_length: int = 512, batch_size: int = 32, device: str = "cuda"):
            self.ce = CrossEncoder(model, max_length=max_length, device=device,
                                   automodel_args={"torch_dtype": torch.float16})
            self.batch_size = batch_size

        def rerank(self, query: str, candidates: list, top_k: int = 10) -> list:
            if not candidates:
                return []
            # sort by text length so batches pad less; remember the original order
            order = sorted(range(len(candidates)), key=lambda i: len(candidates[i].text))
            pairs = [(query, candidates[i].text) for i in order]
            scores = self.ce.predict(pairs, batch_size=self.batch_size,
                                     show_progress_bar=False)
            for i, s in zip(order, scores):
                candidates[i].rerank_score = float(s)
            return sorted(candidates, key=lambda c: -c.rerank_score)[:top_k]


    async def search(query: str, k: int = 10, rerank_depth: int = 50):
        candidates = await hybrid_search(query, k=rerank_depth)     # Module 2
        return reranker.rerank(query, candidates, top_k=k)
    ```

    ### The depth curve — this is the decision

    Reference corpus, 100-query eval set, baseline is Module 2's hybrid RRF at NDCG 0.79 /
    Recall@10 0.91. Two rerankers over the same candidate sets.

    | Depth `N` | NDCG@10 | Recall@10 | `bge-reranker-base` p50 / p95 | `MiniLM-L-6` p50 / p95 |
    | --- | --- | --- | --- | --- |
    | 0 (no rerank) | 0.79 | 0.91 | — | — |
    | 10 | 0.82 | 0.91 | 19 / 26 ms | 3 / 5 ms |
    | 20 | 0.84 | 0.91 | 38 / 50 ms | 5 / 8 ms |
    | **50** | **0.85** | **0.92** | **96 / 125 ms** | **12 / 18 ms** |
    | 100 | 0.855 | 0.93 | 192 / 247 ms | 25 / 34 ms |
    | 200 | 0.856 | 0.93 | 385 / 491 ms | 49 / 65 ms |

    Paired bootstrap, `N=50` versus no reranking: **ΔNDCG +0.06, 95% CI [+0.03, +0.09]** —
    comfortably significant, and roughly three times any query-transformation gain in Module 3.

    Three readings.

    **NDCG rises steeply then flattens.** 0.79 → 0.85 by `N=50`, then +0.005 for doubling to 100 and
    +0.001 for doubling again. The candidate set's own quality is the ceiling: hybrid Recall@50 is
    0.97 and Recall@200 is 0.98, so there is almost nothing new to find past 50.

    **Recall@10 barely moves.** 0.91 → 0.92. Reranking does not find things; it *reorders*. Its value
    is in NDCG and — via Week 27 Module 5's position curve — in answer accuracy, not in retrieval
    recall. **If you report only Recall@10, reranking looks worthless.** That is a real reporting
    trap and it has killed reranking proposals.

    **Model choice is a 8× latency decision for 0.02 NDCG.** `MiniLM-L-6` at `N=50` gives 0.83 in
    12 ms; `bge-reranker-base` gives 0.85 in 96 ms.

    ### Choosing `N` against an SLO

    This is the whole exercise, and it is arithmetic. Suppose the p95 time-to-first-token budget is
    **400 ms**, and the pipeline already costs:

    ```
    router (Module 3)        90 ms p95 ...  240 ms
    hybrid retrieval          8.9 ms p50 ... 10.2 ms p95
    generation first token   180 ms p95
    ------------------------------------------------
    subtotal                 430 ms p95   <- already over!
    ```

    So the router does not fit, and the honest first move is to drop it (Module 3 measured it at
    +0.02) rather than to squeeze reranking. Without the router:

    ```
    hybrid retrieval          10.2 ms
    generation first token   180 ms
    ------------------------------------------------
    subtotal                 190 ms, leaving 210 ms for reranking
    ```

    From the table: `bge-reranker-base` at `N=50` is 125 ms p95 — fits, with 85 ms of headroom.
    `N=100` is 247 ms — does not fit. **Choose `N=50` with `bge-reranker-base`: NDCG 0.85 at 315 ms
    p95 total.**

    And notice what the arithmetic just told you: given a 400 ms budget, **reranking at +0.06 is a
    far better use of 125 ms than the router at +0.02 for 240 ms.** Module 3's scatter plot and this
    table belong on the same axes, and the decision is visible the moment they are.

    ### Batching across concurrent requests

    At production concurrency, each request reranks 50 pairs — but a batch of 50 does not saturate a
    GPU. Batching across requests does:

    | Concurrency | Naive (batch per request) | Cross-request batching |
    | --- | --- | --- |
    | 1 | 96 ms | 96 ms |
    | 8 | 96 ms each, 83 req/s | 118 ms each, **271 req/s** |
    | 32 | queued, p95 402 ms | 174 ms each, **736 req/s** |

    **8.9× the throughput at concurrency 32**, for 78 ms of added per-request latency. The
    implementation is a small batching queue with a short window:

    ```python
    class BatchedReranker:
        """Collect pairs for up to `window_ms`, then score them in one GPU call."""
        def __init__(self, ce, window_ms: int = 8, max_batch: int = 256):
            self.ce, self.window, self.max_batch = ce, window_ms / 1000, max_batch
            self.queue: list[tuple] = []
            self.lock = asyncio.Lock()

        async def score(self, pairs: list[tuple[str, str]]) -> list[float]:
            fut = asyncio.get_running_loop().create_future()
            async with self.lock:
                self.queue.append((pairs, fut))
                if len(self.queue) == 1:
                    asyncio.create_task(self._flush_after_window())
            return await fut

        async def _flush_after_window(self):
            await asyncio.sleep(self.window)
            async with self.lock:
                batch, self.queue = self.queue, []
            flat = [p for pairs, _ in batch for p in pairs]
            scores = await asyncio.to_thread(self.ce.predict, flat,
                                             batch_size=self.max_batch)
            i = 0
            for pairs, fut in batch:
                fut.set_result(list(scores[i:i + len(pairs)]))
                i += len(pairs)
    ```

    This is exactly the continuous-batching idea from Week 26 Module 5, applied to a much smaller
    model. The 8 ms window is the tunable: longer windows batch better and add latency to every
    request.

    ### Trade-offs

    | Decision | Choose this when… | Choose the other when… |
    | --- | --- | --- |
    | **`MiniLM-L-6` vs `bge-reranker-base`** | MiniLM (22.7M): tight latency budget. 0.83 NDCG at 12 ms for `N=50`. | `bge-reranker-base` (278M): +0.02 NDCG for 8× the latency. The default when you have 125 ms. |
    | **`N=20` vs `N=50` vs `N=100`** | 20: very tight budget — 0.84 at 50 ms p95. | 50: the knee. 100 buys +0.005 for double the latency and is rarely justified. |
    | **Cross-encoder vs LLM reranker** | Cross-encoder: 96 ms, $0, deterministic, no external dependency. | LLM listwise reranker: +0.02 NDCG over the cross-encoder (Layer 3) for 1,250 ms and $0.0009/query. Only for offline or low-volume, high-value queries. |
    | **Rerank vs distil into the bi-encoder** | Rerank: immediate, +0.06 NDCG, no training. | Distillation (Layer 3): +0.03 NDCG at **zero** query-time cost, but requires a training run and a full re-embed. Do both — they compose. |

    ### War story

    A team added a cross-encoder reranker, measured Recall@10 before and after — **0.89 to 0.90** —
    concluded it was not worth 96 ms, and removed it.

    Six weeks later, in an unrelated investigation of answer quality, someone measured end-to-end
    answer accuracy with and without the reranker that had been deleted:

    | Configuration | Recall@10 | NDCG@10 | Mean gold rank | **Answer accuracy** |
    | --- | --- | --- | --- | --- |
    | No reranking | 0.89 | 0.76 | 4.6 | 0.74 |
    | Reranking, `N=50` | 0.90 | 0.83 | 1.8 | **0.85** |

    **Eleven points of answer accuracy from a change that moved Recall@10 by 0.01.** The mechanism is
    Week 27 Module 5's lost-in-the-middle curve: reranking moved the gold chunk from a mean rank of
    4.6 to 1.8, and the position curve says position 1 is worth about 0.13 over position 5.

    They had measured the wrong metric. Recall@10 asks "is the answer in the prompt at all", and by
    construction reranking cannot improve it much — it reorders what is already there. The metrics
    that see reranking are NDCG (which discounts by rank) and end-to-end answer accuracy.

    **The permanent change: any evaluation of a reordering component must report NDCG and answer
    accuracy, and Recall@k is explicitly the wrong primary metric for it.** This is Week 27 Module
    5's "choose the metric for the question" arriving with a six-week delay and a deleted feature.

    **Question.** Your candidate set is Recall@50 = 0.97. Someone proposes raising rerank depth to
    500 to "catch more". Evaluate.

    **Model answer.** Recall@500 is 0.98 on our corpus, so the extra 450 candidates contain the gold
    chunk for one query in a hundred more than the top 50 did. Reranking 500 pairs costs 960 ms p50

    optimises the wrong stage: **the ceiling is set by stage 1, and stage 1's Recall@50 is already
    0.97.** If you want a higher ceiling, improve retrieval (Module 2's fusion is where that gain
    lives) rather than reranking deeper. The productive version of the question is the inverse:
    given that Recall@50 is 0.97 and reranked NDCG@10 is 0.85, **how much of the remaining gap is
    the reranker failing to promote a chunk it was shown?** Measure it — for each query where the
    gold chunk was in the candidate set but not in the reranked top-10, inspect the pair. On our
    corpus that was 8 queries, and 5 of them were chunks truncated at `max_length=512` such that the
    relevant sentence was cut off. That is a fixable bug and it is worth more than depth 500.

    ### The `O(N)` cost, computed properly

    `bge-reranker-base` is BERT-base shaped: 12 layers, `d_model` 768, about 86M non-embedding
    parameters. A forward pass over a `T`-token sequence costs roughly `2 × params × T` FLOPs, so at
    `T = 512`:

    ```
    2 × 86e6 × 512 = 8.8e10 FLOPs = 88 GFLOP per pair
    ```

    A throughput of 520 pairs/s implies `520 × 88e9 = 45.8 TFLOP/s`, which is 37% of the
    A10G's 125 TFLOP/s fp16 peak — a plausible MFU for a small model with short sequences and
    padding overhead. Scoring the corpus:

    ```
    47,300 × 88 GFLOP = 4.16 PFLOP per query
    4.16e15 ÷ 45.8e12 = 91 seconds per query
    ```

    Compare the bi-encoder's query-time cost: one 768-dimensional encode (3 ms, amortisable) plus
    `47,300 × 768 × 2 = 7.3e7` FLOPs of dot products — **57,000× less arithmetic**. The document
    encodes were paid once at ingest.

    That ratio is the architecture. It does not improve with a bigger GPU, because both sides scale;
    it improves only by shrinking the second stage's `N`.

    ### LLM re-rankers

    Give a language model the query and 20 candidates and ask it to output the best order. Three
    variants, modelled on the reference eval set over the same hybrid top-20 candidates:

    | Reranker | NDCG@10 | p50 latency | $/query | Notes |
    | --- | --- | --- | --- | --- |
    | None (hybrid) | 0.79 | 0 | $0 | |
    | `MiniLM-L-6` cross-encoder | 0.83 | 5 ms | $0 | |
    | `bge-reranker-base` | 0.85 | 38 ms | $0 | at `N=20` |
    | **LLM listwise** (Llama 3.2 3B, self-hosted) | **0.87** | 1,250 ms | $0.0009 | outputs a permutation |
    | LLM pointwise (score each 0–10) | 0.84 | 2,900 ms | $0.0021 | 20 separate calls |

    **Listwise beats pointwise** and is cheaper, which is the non-obvious result: seeing all
    candidates together lets the model compare them, and one call is cheaper than twenty. It is also
    where the failure modes live — the model can omit a candidate, duplicate one, or hallucinate an
    index. Constrain the output (Week 26 M4) to a permutation of exactly the input indices, and
    validate:

    ```python
    def apply_permutation(perm: list[int], candidates: list) -> list:
        seen, out = set(), []
        for i in perm:
            if 0 <= i < len(candidates) and i not in seen:
                seen.add(i); out.append(candidates[i])
        out.extend(c for j, c in enumerate(candidates) if j not in seen)  # append the rest
        return out
    ```

    Reference figure without that guard: 6.5% of LLM rerank calls produce an invalid permutation (a missing
    or duplicated index), and the naive implementation silently dropped candidates.

    **The position of the LLM reranker on the cost/quality curve:** +0.02 NDCG over the cross-encoder
    for 33× the latency and a real dollar cost. It is right for offline reranking of a golden
    evaluation set, for low-volume high-value queries, and for generating training labels — which is
    the next section.

    ### Distillation: moving the cross-encoder's knowledge into the bi-encoder

    You cannot afford a cross-encoder at retrieval time. You *can* afford to train your bi-encoder to
    imitate it, offline, and get some of the quality at zero query cost.

    The method is **margin-MSE**: for a query with a positive and a negative passage, the student
    bi-encoder should reproduce the *teacher's margin* between them.

    ```python
    # distil.py — sentence-transformers 3.0.1
    from sentence_transformers import SentenceTransformer, losses, InputExample
    from torch.utils.data import DataLoader

    student = SentenceTransformer("BAAI/bge-base-en-v1.5")
    teacher = CrossEncoder("BAAI/bge-reranker-base")

    examples = []
    for q in queries:                                 # 20k queries from logs, unlabelled
        cands = hybrid_search(q, k=20)
        scores = teacher.predict([(q, c.text) for c in cands])
        pos, neg = cands[scores.argmax()], cands[scores.argsort()[len(scores) // 2]]
        margin = float(scores.max() - scores[scores.argsort()[len(scores) // 2]])
        examples.append(InputExample(texts=[q, pos.text, neg.text], label=margin))

    loader = DataLoader(examples, batch_size=32, shuffle=True)
    student.fit(train_objectives=[(loader, losses.MarginMSELoss(student))],
                epochs=2, warmup_steps=500, use_amp=True)
    ```

    Reference figure — 20,000 unlabelled queries from the log, teacher-scored, 2 epochs:

    | Retriever | Recall@10 | NDCG@10 | Query-time cost |
    | --- | --- | --- | --- |
    | `bge-base` (baseline) | 0.88 | 0.75 | 3 ms |
    | **`bge-base` distilled** | **0.90** | **0.78** | **3 ms** |
    | + hybrid fusion | 0.92 | 0.81 | 8.9 ms |
    | + reranking `N=50` | **0.93** | **0.87** | 105 ms |

    **+0.03 NDCG for free at query time**, and it *composes* with reranking rather than replacing it
    (0.85 → 0.87 in the final row, because a better candidate set gives the reranker better material).
    The costs are real: 4 hours of teacher scoring on 20k × 20 pairs, a 40-minute training run, and
    a **full re-embed and index rebuild** — which for a large corpus is the expensive part
    (Week 27 M3's migration checkpoint).

    Note what makes this affordable: **the training data is unlabelled.** You need queries, which
    your logs have, and the teacher supplies the labels. This is the cheapest way to adapt an
    embedding model to a domain and it is strictly better than the naive fine-tuning in Week 27
    Module 3's stretch section, because the teacher's judgements are better than LLM-generated
    question-chunk pairs.

    ### MMR: when diversity beats relevance

    Reranking optimises relevance per item, which produces top-10 lists full of near-duplicates —
    exactly what Week 27 Module 2 warned about with overlapping chunks. **Maximal Marginal
    Relevance** trades a little relevance for coverage:

    ```
    MMR = argmax_{d ∉ S} [ λ · rel(d, q) − (1 − λ) · max_{s ∈ S} sim(d, s) ]
    ```

    Select greedily: each pick maximises relevance minus its similarity to what you have already
    picked. `λ = 1` is pure relevance; `λ = 0` is pure diversity.

    ```python
    def mmr(query_vec, candidates, lam: float = 0.7, k: int = 10):
        selected, pool = [], list(candidates)
        while pool and len(selected) < k:
            best, best_score = None, -1e9
            for c in pool:
                redundancy = max((c.vec @ s.vec for s in selected), default=0.0)
                score = lam * c.rerank_score_norm - (1 - lam) * redundancy
                if score > best_score:
                    best, best_score = c, score
            selected.append(best); pool.remove(best)
        return selected
    ```

    Reference figure — modelled on the reference eval set, split by whether the gold answer needs one chunk or several.
    "Coverage" is the fraction of required gold chunks present in the top-5.

    | | Single-chunk queries (76) | Multi-source queries (24) |
    | --- | --- | --- |
    | Reranked, no MMR | **NDCG 0.85** | coverage 0.62 |
    | MMR `λ=0.7` | NDCG 0.81 | **coverage 0.78** |
    | MMR `λ=0.9` | NDCG 0.84 | coverage 0.69 |
    | **MMR only on router-flagged multi-hop** | **NDCG 0.85** | **coverage 0.78** |

    **MMR helps one segment by 0.16 and hurts the other by 0.04.** Applied globally it is roughly
    neutral; applied selectively — using Module 3's router to flag multi-source queries — it is a
    clean gain on both. This is the same lesson as Module 3's routing, arriving from a different
    direction: **techniques with segment-dependent effects should be routed, not switched on.**

    `c.rerank_score_norm` in the code is not decoration: MMR mixes a relevance score with a cosine
    similarity, and the cross-encoder's unbounded logits are not on the cosine scale. Min-max
    normalise the rerank scores within the candidate list first, or `λ` means nothing.

    ### Failure modes

    | Failure | Signature | Detection |
    | --- | --- | --- |
    | Evaluated on Recall@k | Reranking looks worthless (+0.01) and gets removed | Report NDCG and answer accuracy; Recall@k is the wrong primary metric for a reordering stage |
    | Chunk truncated at `max_length` | Long chunks systematically under-ranked | Log the fraction of pairs hitting `max_length`; 5 of 8 residual failures were this |
    | Cross-encoder scores thresholded across queries | Inconsistent filtering; some queries return nothing | Scores are per-query logits; normalise within the list or use rank-based rules |
    | Rerank depth raised past the candidate ceiling | Latency doubles, quality moves 0.005 | Measure Recall@N of stage 1; that is the ceiling |
    | No cross-request batching | GPU idle, throughput caps at 83 req/s | Batching queue with a short window — 8.9× at concurrency 32 |
    | LLM reranker permutation invalid | Candidates silently dropped from results | Validate the permutation and append unlisted candidates; 6.5% invalid without it |
    | MMR applied globally | Single-fact queries regress 0.04 | Route it; or tune `λ` to 0.9 where the effect is smaller |
    | Distilled model served against the old index | Meaningless similarity scores | Re-embed and rebuild; assert the model version on the index (Week 27 M3) |

    ### Papers and primary sources

    - **Nogueira & Cho 2019, "Passage Re-ranking with BERT".** *Takeaway:* a BERT cross-encoder over
      the top-1000 BM25 candidates improved MS MARCO MRR@10 by 27% relative over the previous best,
      establishing retrieve-then-rerank as the standard architecture. **Read §3** — it is three
      pages and it is the founding result for this module.
    - **Hofstätter et al. 2020, "Improving Efficient Neural Ranking Models with Cross-Architecture
      Knowledge Distillation".** *Takeaway:* margin-MSE distillation from a cross-encoder teacher
      into a bi-encoder student transfers much of the quality at zero query-time cost, using
      unlabelled queries. **Read §3.2** for the margin formulation used in the code above.
    - **Carbonell & Goldstein 1998, "The Use of MMR, Diversity-Based Reranking for Reordering
      Documents and Producing Summaries".** *Takeaway:* trading a controlled amount of relevance for
      novelty produces better result *sets* when the user needs coverage rather than a single answer.
      **Read §2** for the λ formulation — it is one equation and it has not changed in 27 years.
    - **Sun et al. 2023, "Is ChatGPT Good at Search? Investigating Large Language Models as
      Re-Ranking Agents" (RankGPT).** *Takeaway:* listwise LLM reranking with a sliding window beats
      supervised cross-encoders on several BEIR datasets, and permutation distillation transfers it
      into a small model. **Read §3** for the sliding-window listwise procedure, which is how you
      rerank more than fits in one context.
    - **`sentence-transformers` CrossEncoder documentation.** *Takeaway:* `max_length` truncates the
      *pair*, and the default of 512 silently cuts long chunks. **Read the `CrossEncoder` API page**
      and note there is no warning on truncation — you must log it yourself.

    ### Stretch challenge

    Plot NDCG and p95 latency against rerank depth `N ∈ 10, 20, 50, 100, 200` and pick an operating
    point against a stated latency SLO. That is the lab, and Module 3's scatter belongs on the same
    axes.

    The stretch is **adaptive depth**. Rerank depth is currently a constant, but the queries differ:
    a query whose hybrid top-3 are already clearly correct needs no reranking, and a query whose top
    50 are all mediocre might need 200. Build a predictor of "how much will reranking help this
    query" from stage-1 signals alone — the RRF score gap between rank 1 and rank 5, the number of
    candidates found by both retrievers, the query's max IDF, the candidate score variance — and set
    `N` per query to hit a *mean* latency target rather than a per-query one.

    Then the open question, which is genuinely open. This is a budget-allocation problem: you have a
    fixed total reranking compute per second and a stream of queries with different marginal returns.
    The optimal policy is not "spend more on the queries that benefit most" in isolation — it depends
    on the arrival distribution and on whether unspent budget can be banked. Formulate it, implement
    a simple policy (say, threshold on the predicted benefit), and measure aggregate NDCG at a fixed
    mean latency against the constant-`N` baseline. My prior is that adaptive depth wins by a small
    amount at a fixed mean and wins *substantially* at a fixed p95, because the constant-`N` policy
    pays the full cost on the many easy queries. If you find that, it is a genuinely useful result
    and it generalises to every stage of this pipeline.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Reranking "does nothing" | Evaluated on Recall@k, which reranking cannot move | Report NDCG@10 and end-to-end answer accuracy |
| Long chunks consistently under-ranked | Silent truncation at `max_length=512` | Log the truncation rate; chunk to fit, or use a longer-context reranker |
| Filtering by score is inconsistent across queries | Cross-encoder logits are per-query, not calibrated | Normalise within the candidate list, or use rank-based rules |
| Latency doubled for +0.005 NDCG | Rerank depth beyond stage 1's recall ceiling | Measure Recall@N of the candidate set first |
| Throughput caps far below GPU capacity | One small batch per request | Cross-request batching queue with a short window |
| Results silently missing candidates | Invalid LLM permutation not validated | Validate and append unlisted candidates |
| Single-fact queries regressed after adding MMR | MMR applied globally | Route it to multi-source queries, or raise `λ` |
| Distilled model returns nonsense | Served against an index built by the old model | Re-embed and rebuild; assert model version on the index |
