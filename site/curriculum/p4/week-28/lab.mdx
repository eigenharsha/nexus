## The ticket

> **NEX-4511 · Knowledge platform · P1**
>
> Week 27's retrieval layer went live and agents are using it. Two things came back from the first
> month.
>
> First, the wins are real for questions but not for codes: agents still grep the docs repository
> when they have an error string. Second, and this is now the bigger problem, **finance wants a
> number.** We are spending roughly $4,100 a month on this and nobody can say what a query costs or
> what we would give up by halving it.
>
> Take the system to production quality. Every improvement must come with what it cost — quality,
> p95 latency, and dollars per query. If something we already do is not earning its latency, remove
> it and say so. We would rather ship four changes we can defend than eight we cannot.
>
> Deliverable: the working system and `RAG-REPORT.md`.

**Time box, honestly:** `basic` 4–5 hours. `standard` 16–20 hours. `hard` a further 12–14 hours, of
which the false-hit labelling is 2 and cannot be automated.

**Hardware:** everything except reranking runs on a laptop. Reranking with `MiniLM-L-6` is fine on
CPU (roughly 190 pairs/s, so `N=50` is 260 ms — usable for evaluation, too slow for the SLO work).
The `hard` track's latency measurements want a GPU for about 2 hours (~$2 on `g5.xlarge`); a
documented CPU fallback reports the same *quality* numbers with latency measured on MiniLM instead.

<Tabs>
  <Tab title="basic">
    **Scaffolded. About 60% is written for you; every gap is marked `# TODO`.**

    1. **Add BM25.** `starter/sparse.py` provides the analyzer and the index wrapper; you write
       `search()`. Measure Recall@10 on the Week 27 eval set for BM25 alone and compare it against
       dense alone.
    2. **Segment the eval.** Tag each of the 100 queries as `identifier`, `factual`, `paraphrase` or
       `conceptual` (a starter tagging is provided; review it). Report both retrievers per segment.
       **You are looking for the segment where dense scores below 0.5 and BM25 scores above 0.9.**
    3. **Fuse with RRF.** Implement `rrf()` from the formula. Verify by hand against the worked
       example in Module 2 Layer 1 — the two documents found by both retrievers must come out on
       top. Report the fused Recall@10 and NDCG@10.
    4. **One paragraph** on what fusion bought, per segment, and what it cost on the segments where
       one retriever was already dominant.

    <Info>
    Acceptance: `make verify TRACK=basic` green, including the hand-computed RRF fixture. Roughly
    50 lines of your own code.
    </Info>

  <Tab title="standard">
    **Spec and tests only. You write the implementation.**

    <Steps>
      <Step title="Sparse retrieval, tuned">
        Dual-field index (stemmed for prose, raw for identifiers), `k1`/`b` grid search on the eval
        set, and the analyzer comparison. Report the identifier segment separately — an analyzer that
        splits on hyphens will show it immediately.
      </Step>
      <Step title="Hybrid fusion with paired CIs">
        RRF over both retrievers, run in parallel. Report the three-way comparison — dense, sparse,
        hybrid — with **paired** bootstrap confidence intervals on every difference, plus the
        per-segment breakdown.
      </Step>
      <Step title="Query transformation, measured not adopted">
        Implement at least four of: rewrite, HyDE, multi-query, step-back, router. Every one needs a
        deadline and a raw-query fallback, and every prompt must preserve codes and IDs verbatim.
        Produce the gain-versus-latency scatter with added **p95**, not p50. **At least one
        technique must be reported as not earning its cost** — if all four helped, check whether your
        eval set contains identifier queries.
      </Step>
      <Step title="Cross-encoder reranking with a depth curve">
        Sweep `N` = 10, 20, 50, 100, 200. Report NDCG@10, Recall@10 *and* end-to-end answer accuracy
        — the last one is what makes reranking's value visible. Choose an operating point against a
        latency SLO you state before you look at the numbers.
      </Step>
      <Step title="Caching with a measured false-hit rate">
        Exact cache first, then semantic with an entity gate. Sweep at least four thresholds and
        **hand-label 200 semantic hits** to get the false-hit rate. Implement citation-based
        invalidation via a reverse index and prove it with a test.
      </Step>
      <Step title="The report">
        `RAG-REPORT.md`: the full ablation with quality, p95 latency and $/query on every row, the
        cost waterfall, and a section naming what you removed and why.
      </Step>
    </Steps>

    <Info>
    Acceptance: `make verify` green, and `RAG-REPORT.md` containing an ablation where at least one
    row is a **removal** with its justification.
    </Info>
  </Tab>

  <Tab title="hard">
    **A constraint the `standard` solution fails.**

    Hit a stated quality target under a stated latency and cost budget, and prove cache correctness
    after a document update.

    1. **The budget.** NDCG@10 ≥ 0.85, p95 end-to-end (retrieval through first token) ≤ 400 ms, and
       ≤ $0.0005 per query. The `standard` pipeline with everything switched on misses the latency
       budget — the router alone is 240 ms p95. **Show the failing measurement**, then build a
       configuration that meets all three and explain each thing you dropped.
    2. **Incremental re-indexing.** Content-hashed chunk IDs, diff-based insert and delete. Measure
       full re-ingest against incremental on a day where 20–30 documents changed. Report both.
    3. **Cache correctness after an update, proven.** Change a document so that the correct answer to
       a specific eval query changes. Then demonstrate, with a test that fails on the `standard`
       implementation, that: the cached answer for that query is evicted; answers citing *other*
       chunks of the same document are also evicted; answers citing unrelated documents are **not**
       evicted; and the next query returns the new answer.
    4. **Load behaviour.** Demonstrate cache stampede with 200 concurrent identical uncached requests
       — record pipeline executions, cost and the p95 latency of *other* queries during the burst —
       then fix it with single-flight coalescing and show all three recover.

    <Warning>
    Point 3 is the gate. TTL-based expiry passes a naive "is it eventually fresh" test and fails the
    "not evicted" clause and the immediacy clause. If your invalidation is a TTL, you have not
    attempted this track.
    </Warning>
  </Tab>
</Tabs>

## Ship it

<Card title="This is the part people skip" icon="rocket" horizontal>
A public repo plus **`RAG-REPORT.md`** — the ablation table with quality, p95 latency and $/query on
every row, paired confidence intervals throughout, the cost waterfall, the false-hit measurement,
and a section headed **"What we removed and why"**.
</Card>

The removal section is what makes the report credible. Anyone can list improvements; a report saying
*"query rewriting measured +0.00 NDCG (CI [−0.02, +0.02]) for 180 ms p50, so we removed it"* proves
you evaluated rather than accumulated. On this corpus at least two of Module 3's six techniques
should not survive, and the report is better for saying so.

Write it for the person who filed the ticket. They asked two questions — take it to production
quality, and tell us what a query costs — so the document opens with the ablation and the cost
waterfall, and the methodology follows.

## Stuck? Open these in order

Each reveals a little more than the last. Try the level above before opening the next — a hint you
did not need costs you nothing, but an answer taken too early costs you the lesson.

<AccordionGroup>
<Accordion title="Nudge — I don't know where to start" icon="lightbulb">
Find the **first** failing test and implement only what that one test needs. Ignore the rest of the
lab until it is green. If you cannot tell which test fails first, run
`make verify TRACK=basic` and read the top of the output, not the bottom.
</Accordion>

<Accordion title="Hint — hybrid search performs worse than dense alone" icon="lightbulb">
Score scales. BM25 scores are unbounded and dense cosine scores sit in [-1, 1], so naive addition lets BM25 dominate entirely.

**What to do instead:** Use Reciprocal Rank Fusion, which combines ranks rather than scores and needs no calibration. If you must weight scores, normalise each retriever's scores within the result set first.
</Accordion>

<Accordion title="Hint — my re-ranker made things slower without improving quality" icon="lightbulb">
Then say so — that is a legitimate finding, and the week requires at least one removal row. Re-ranking a top-50 costs real latency and only helps when the first stage actually buries good results.

**What to do instead:** Measure NDCG and p95 latency at rerank depths of 10, 20, 50 and 100. If the curve is flat, the first stage is already good and the re-ranker is cost without benefit.
</Accordion>

<Accordion title="Hint — my semantic cache returns wrong answers" icon="lightbulb">
The similarity threshold is too loose. Two questions can be 0.92 similar and have completely different correct answers — 'how do I cancel' and 'how do I renew' are close in embedding space.

**What to do instead:** Measure the false-hit rate, not just the hit rate. A wrong cached answer is worse than a slow correct one, so tune the threshold against false hits and accept a lower hit rate.
</Accordion>

<Accordion title="I have a real attempt that fails — show me the full solution" icon="lock">
Open the [reference solution](/solutions/p4/week-28/lab).

Use it properly: read only far enough to get unstuck, then close it and return to your own code.
Afterwards, diff your version against it — the differences are the lesson, and yours is not
automatically the worse one.

If you have not yet written code that fails, do not open it. Reading a solution before struggling
with the problem feels exactly like learning, and is the most reliable way to finish this course
having learned nothing.
</Accordion>
</AccordionGroup>

## Rubric

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| **Correctness** | tests fail | `basic` passes | `standard` passes: hybrid, transforms, reranking and caching all measured on the Week 27 eval | `hard` passes: all three budgets met, incremental re-indexing, and invalidation proven with the eviction test |
| **Code quality** | works | readable | deadlines and fallbacks on every LLM call, parallel retrieval, deterministic tiebreaks, pinned versions | a reviewer would approve unchanged; single-flight with token-checked release; telemetry on every stage |
| **Performance** | untested | timed once | p95 measured per stage against a stated SLO | operating points chosen against a named binding constraint, with the rejected alternatives priced |
| **Explanation** | none | a README | ablation with deltas | every delta paired-CI'd; a removal section; the false-hit rate hand-labelled with a risk statement in product terms |

**What a 3/3 on Explanation looks like:** the report contains a sentence a product manager can act
on. *"At threshold 0.97 approximately 0.16% of all answers will be wrong for the question asked. For
support search with visible citations we judge this acceptable; semantic caching is disabled for any
query mentioning an account, a price or an identifier."* That is a risk statement. "We use a 0.97
similarity threshold" is a configuration note.

## If you get stuck

<AccordionGroup>
  <Accordion title="Hybrid is no better than dense alone">
    Check the join first — an `INNER JOIN` between the two candidate lists discards every
    single-retriever hit, which is the entire contribution of BM25. Then check the segments: if your
    eval set has no identifier queries, hybrid genuinely has little to add and the honest report says
    so.
  </Accordion>
  <Accordion title="Adding HyDE made things worse">
    Almost certainly the hypothetical is reaching BM25. Send it to the dense retriever only and the
    original query to sparse. If it is still worse, check the identifier segment — HyDE dropped it
    from 0.93 to 0.66 on the reference corpus, and if identifiers are a large share of your eval that
    will dominate the aggregate.
  </Accordion>
  <Accordion title="Reranking barely moves my numbers">
    Check which metric you are reading. Recall@10 moves about 0.01 by construction; NDCG@10 moves
    about 0.06 and answer accuracy about 0.11. If NDCG is also flat, look at the truncation counter —
    chunks cut at `max_length=512` were 5 of 8 residual failures on the reference corpus.
  </Accordion>
  <Accordion title="My false-hit rate is 0%">
    Either your threshold is very high (0.99+, in which case say so and report the hit rate), or you
    are not labelling the risky band. Stratify the sample: most hits are at 0.99+ where the error rate
    is 0.2%, and nearly all the risk is in the 12% of hits closest to your threshold.
  </Accordion>
  <Accordion title="I cannot meet the 400 ms budget on the hard track">
    That is the intended discovery. Something has to go, and the arithmetic says which: the router is
    240 ms p95 for +0.02 NDCG while reranking is 125 ms for +0.06. Drop the router, keep reranking,
    and show the measurement that made the decision. A submission that meets the budget by dropping
    reranking has optimised the wrong thing and should say why it chose differently.
  </Accordion>
</AccordionGroup>
