## Reference solution — `P2-W15-M3`

A scraper with a snapshot test suite, so a layout change fails in CI rather than producing nulls.

### The one line that decides the mark

```python
# The bug. It looks like defensive programming.
el = row.select_one(".px")
price = float(el.get_text(strip=True)) if el else None

# The fix.
el = row.select_one(".px")
if el is None:
    raise ExtractionError(f"price element not found; tried '.px' in: {row}")
price = float(el.get_text(strip=True))
```

`if el else None` converts a loud, immediate failure into a silent, permanent one. The module's war
story: a null price column, `AVG(price)` silently excluding the source, an apparent 4% drop in
competitor pricing, and **eleven days of reduced margin** before anyone questioned the number.

```python
def test_missing_price_raises_rather_than_returning_none():
    html = "<html><body><h1 data-testid='title'>Widget</h1></body></html>"
    with pytest.raises(ExtractionError, match="price"):
        parse_product_page(BeautifulSoup(html, "lxml"))
```

**Write this test before the parser.** Everything else in this module is downstream of it.

### The two CI jobs

```yaml
# On every pull request — fast, offline, deterministic. Catches PARSER regressions.
- run: pytest tests/test_parser_snapshots.py

# Weekly — refetches the live pages into the snapshot directory, then runs the same tests.
# A failure here means THE SITE CHANGED.
- run: python tools/refresh_snapshots.py && pytest tests/test_parser_snapshots.py
```

**The weekly job is the change detector.** It converts an unbounded maintenance burden into a red
build with an HTML diff, on a Tuesday morning, instead of a null column discovered in a month.

### Selector strategy, in preference order

| Strategy | Survives a redesign? |
| --- | --- |
| **JSON-LD** (`script[type="application/ld+json"]`) | best — it exists for machines |
| **The underlying XHR API** | best — no HTML at all |
| `__NEXT_DATA__` / hydration payload | very good — the page's own data, as JSON |
| `[data-testid="..."]`, `[itemprop="..."]` | very good — front-end tests depend on these too |
| Label-anchored (the `td` after a `th` reading "Price") | good — anchors on meaning |
| `.product-price` | okay |
| `.css-1x7ab2`, `.jsx-40293` | **no** — changes on any *rebuild* |
| `div > div:nth-child(3) > span` | **no** — changes on any layout edit |

**Check the top three before writing a single CSS selector.** A very large fraction of commercial
pages embed schema.org JSON-LD because Google's rich snippets depend on it, and a scraper that reads
it is a JSON parser rather than an HTML parser. This one check has saved more scraping projects than
every other technique in the module.

### The parser measurement, and its surprise

A 2.3 MB page with a 20,000-row table, extracting two fields per row:

| Approach | Time | vs fastest |
| --- | --- | --- |
| BeautifulSoup + `html.parser` | 2.721 s | 17.1× |
| BeautifulSoup + `lxml` | 2.252 s | 14.2× |
| **`lxml` XPath directly** | **0.159 s** | **1.0×** |

**Switching BeautifulSoup's parser gains only 1.21×** — far less than the folklore claims. The 14×
comes from **leaving BeautifulSoup entirely**. The parsing is C either way; BeautifulSoup's cost is
building a Python `Tag` object per element, and 20,000 rows × 4 cells is 80,000+ objects.

Guidance: **under ~1,000 elements use BeautifulSoup** (the API is far nicer and both are under
20 ms); **over ~10,000 use `lxml` directly**. Always pass the parser explicitly, so behaviour does
not depend on what happens to be installed.

## Why this solution and not the obvious one

**Why a disk cache during development.** You will edit the parser and re-run fifty times. Without a
cache that is fifty fetches, which is slow, rude, and gets you blocked in an afternoon. Note that
the rate-limiting sleep belongs **inside the cache-miss branch** — a cache hit should be instant.

**Why `r.content` and not `r.text`.** When a server sends no charset, `requests` defaults to
ISO-8859-1 for `text/*` per RFC 2616 — wrong for most of the modern web, turning `£` into `Â£`.
Passing bytes to `lxml` lets it read the document's own `<meta charset>`, which is authoritative.

**Why strip non-breaking spaces explicitly.** `&nbsp;` is endemic in scraped HTML, is not matched by
`\s` in some regex flavours, and breaks every `float()` and every exact-match comparison. Alongside
NFC normalisation and dropping category `Cf` (zero-width joiners, bidi overrides), it is the standard
three-line canonicalisation from week 13 module 2.

**Why the null-rate monitor rather than "did the job succeed".** The scraper in the war story
succeeded every night. **"Did the job run" and "did the job produce data" are different questions**,
and only the second one would have caught it.

## Grading notes

**3/3 on Correctness** — at least three snapshot fixtures with expected outputs; a test asserting a
missing required field **raises**; selectors anchored on JSON-LD, `data-testid` or label text.

**3/3 on Code quality** — a cache with rate limiting on misses only; an honest `User-Agent` with
contact details; `robots.txt` checked per URL with `crawl_delay` honoured.

**3/3 on Explanation** — the null-rate monitoring argument, and a stated position on the legal
boundary rather than silence.

**The three most common ways submissions lose points:**

1. **`or None` at the extraction boundary.** The single failure this module exists to prevent.
2. **Selectors copied from the browser's "Copy selector".** They are positional and generated-class
   based, which is exactly the pair that does not survive a rebuild.
3. **No weekly snapshot refresh.** The pull-request tests catch parser regressions. Only the refresh
   catches *site* changes, which is the failure mode that actually happens.

**A fourth:** `r.text` rather than `r.content`, producing `Â£` and `Ã©` in the output. It looks like a
scraping bug and is an encoding bug.

**On the legal section.** A submission that ignores it is incomplete. The expected content:
`robots.txt` honoured, an honest UA, a rate that does not degrade the service, and **a stated
position on anti-bot measures** — my recommendation is that rate-based blocking is a reasonable
request to comply with, while defeating TLS fingerprinting or CAPTCHAs is a business and legal
decision that belongs with someone accountable for it, not with the engineer.
