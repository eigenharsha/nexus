## Reference solution — `P2-W10-M3`

### The two functions everything depends on

```python
import struct
HDR = struct.Struct("!I")
MAX_MESSAGE = 1 << 20

def recv_exactly(sock, n):
    buf = bytearray()
    while len(buf) < n:
        chunk = sock.recv(n - len(buf))
        if not chunk:
            return None                      # clean close, distinct from an error
        buf += chunk
    return bytes(buf)

def send_msg(sock, payload: bytes):
    if len(payload) > MAX_MESSAGE:
        raise ValueError(f"message too large: {len(payload)}")
    sock.sendall(HDR.pack(len(payload)) + payload)     # ONE write

def recv_msg(sock):
    h = recv_exactly(sock, 4)
    if h is None:
        return None
    (n,) = HDR.unpack(h)
    if n > MAX_MESSAGE:                                 # bound BEFORE allocating
        raise ValueError(f"declared length {n} exceeds limit")
    body = recv_exactly(sock, n)
    if body is None:
        raise ConnectionError("peer closed mid-message")
    return body
```

### The selector server's drain loop

The part that is free with blocking reads and must be written by hand in an event loop:

```python
b = bufs[conn]; b += data
while len(b) >= 4:
    n, = HDR.unpack(b[:4])
    if n > MAX_MESSAGE: raise ValueError(n)
    if len(b) < 4 + n: break              # incomplete frame: wait for more
    frame = bytes(b[4:4 + n]); del b[:4 + n]
    handle(conn, frame)
```

Two invariants: the buffer is only consumed when a complete frame is present, and the length is
bounded before it is used. Getting either wrong is the standard event-loop framing bug.

## Why this solution and not the obvious one

**`recv_exactly` returns `None` rather than raising on a clean close.** A closed connection is normal
traffic; an exception is not. Distinguishing "peer finished" from "peer vanished mid-message" means
your logs stop filling with errors every time a user closes a laptop, and a real truncation becomes
visible instead of being buried.

**The length is bounded before allocation, not after.** Checking after `recv_exactly` has already
read `n` bytes defeats the entire purpose. This is one line in the right place versus one line in the
wrong place, and it is the difference between a bounded server and a one-packet denial of service.

**One `sendall` for header and payload.** Two writes trigger the Nagle × delayed-ACK interaction from
Module 2 and double the syscall count.

**Wrong turns worth knowing about.**

1. *Using `struct.Struct("I")` without `!`.* Works on your machine, breaks between architectures.
   The `!` is not optional.
2. *Calling `recv` once and assuming a full frame.* Passes every local test with small messages;
   fails the moment a message straddles a read.
3. *Letting `ECONNRESET` escape to the accept loop.* One misbehaving client takes down the server.
4. *Concluding `asyncio` must be fastest.* It measured slowest of the three here. Chosen for
   writability, not speed.

## Measured numbers this solution produces

Python 3.13.2, macOS 26.2, Apple M3 Pro, 1,000 connections, machine under load:

| Model | OS threads | Peak RSS / conn | Throughput @500 | p50 | p99 |
|---|---|---|---|---|---|
| threads | 1,002 | 35.7 KiB | 26,531 msg/s | 24.1 µs | 180.7 µs |
| selectors | 2 | 0.9 KiB | **41,250 msg/s** | **21.5 µs** | **79.7 µs** |
| asyncio | 2 | 6.0 KiB | 15,194 msg/s | 47.5 µs | 266.7 µs |

Note that *current* RSS growth for threads was only ~4 KiB/connection while *peak* was 35.7 KiB —
thread stacks are lazily committed. Peak is the number your container's memory limit sees.

## Grading notes

**What 3/3 looks like**

- *Correctness* — the chaos suite passes: SIGKILL mid-message, header-then-disconnect, a 4 GB
  declared length, a slow reader, 1,000 reconnects.
- *Code quality* — framing, transport and application logic are separate modules, so the same framing
  code serves all three concurrency implementations.
- *Performance* — all three models measured on the same load, with memory *and* latency, at more than
  one concurrency level.
- *Explanation* — a recommendation with a threshold in it ("threads below ~2,000 connections; event
  loop above"), and an honest note if the student's ordering differs from the reference.

**The three most common ways submissions lose points**

1. **Only throughput measured.** Memory per connection is the number that actually decides the
   architecture, and it is the one usually missing.
2. **`recv_exactly` reimplemented per model.** Three copies means three chances to get the bound
   wrong. Write it once.
3. **Reference numbers reproduced instead of measured.** These were taken on a loaded machine and are
   noisy; a submission that reports them exactly did not run anything.
