## Reference solution — `P2-W10-M5`

### The four cases, and what each proves

```
1) default verification:
   URLError -> [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: self-signed certificate
2) verification disabled:
   b'secret\n'
3) correct: trust THIS certificate explicitly:
   b'secret\n'
4) what was negotiated:
   TLSv1.3 ('TLS_AES_256_GCM_SHA384', 'TLSv1.3', 256)
```

Case 2 is the one to sit with. The connection succeeded. It used AES-256-GCM. It was completely
insecure, because nobody checked who was on the other end. Encryption without authentication is a
private conversation with an unknown party.

### Correct client verification, by language

```python
ctx = ssl.create_default_context(cafile="corporate-ca.pem")   # private CA
requests.get(url, verify="/etc/ssl/certs/corporate-ca.pem")
```

```go
pool := x509.NewCertPool()
pool.AppendCertsFromPEM(caPEM)
cfg := &tls.Config{RootCAs: pool}          // never InsecureSkipVerify
```

```javascript
new https.Agent({ ca: fs.readFileSync('corporate-ca.pem') })  // never NODE_TLS_REJECT_UNAUTHORIZED
```

### The certificate that actually works

```bash
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 365 -nodes \
  -subj "/CN=localhost" -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

The `-addext subjectAltName` is not optional. Modern clients ignore `CN` entirely.

## Why this solution and not the obvious one

**Case 3 uses an explicit `cafile` rather than adding the certificate to the system trust store.**
Both work. Adding to the system store changes trust for every program on the machine, permanently,
and is very easy to forget about. Scoping trust to the one client that needs it is the correct
default, and it is also the pattern for a private internal CA in production.

**`openssl s_client` is always invoked with `-servername`.** Without it, no SNI is sent, a multi-site
server returns its default certificate, and you debug a hostname mismatch that your own command
created.

**Wrong turns worth knowing about.**

1. *Making a certificate error go away with `verify=False`.* This is the war story. The error meant
   an inspection proxy was on the path; the correct fix was adding its CA to the bundle. The
   `verify=False` then propagates by copy-paste.
2. *A cert with only a `CN` and no SAN.* Rejected by every modern client, with an error that does not
   obviously say "add a SAN".
3. *Serving `cert.pem` instead of `fullchain.pem`.* Works in browsers, fails in `curl`, Java and Go.
   The most common TLS misconfiguration in production.
4. *Setting the app's idle timeout shorter than the load balancer's.* Produces sporadic,
   unreproducible 502s. App keep-alive must exceed the proxy's (65–75 s against an ALB's 60 s).

## Measured numbers this solution produces

- Self-signed certificate generation: **0.075 s** for RSA-2048.
- TLS 1.3 handshake **32.5 ms** versus TLS 1.2 **53.3 ms** on the same ~22 ms path — one round trip
  saved, about 39%.
- Negotiated suite on the local server: `TLS_AES_256_GCM_SHA384`, 256-bit.
- Default verification rejects a self-signed certificate; an explicit `cafile` accepts it and
  verifies the hostname against the SAN.

## Grading notes

**What 3/3 looks like**

- *Correctness* — all four cases reproduced, plus a working interception with mitmproxy and a client
  that correctly refuses it.
- *Code quality* — verification is never disabled anywhere; private CAs are handled with an explicit
  bundle; a lint rule or CI grep is committed.
- *Performance* — the TLS 1.2 versus 1.3 handshake measured on the student's own path, with the round
  trips counted.
- *Explanation* — states clearly that encryption without authentication is worse than plaintext
  because of the false confidence, and identifies at least two legitimate uses of
  `verify=False` (a fixture test, an interactive debug session) so the rule is understood rather than
  chanted.

**The three most common ways submissions lose points**

1. **The interception demonstrated but not defeated.** Part 2 — a client that correctly refuses — is
   where the learning is.
2. **`s_client` run without `-servername`.** Produces a phantom hostname mismatch, and then a
   confident but wrong diagnosis.
3. **No mention of the reverse-proxy consequences.** Client IP, the timeout ladder, and the
   keep-alive ordering are the operational half of the module, and they cause more incidents than
   certificate problems do.
