## Reference solution — `P2-W10-M1`

### The latency budget, done correctly

```bash
curl -s -o /dev/null -w \
 'dns=%{time_namelookup} conn=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
 https://example.com
```

The values are **cumulative**. The phase durations are the differences:

| Phase | Cumulative | Duration | Interpretation |
|---|---|---|---|
| DNS | 1.9 ms | 1.9 ms | resolver cache hit |
| TCP connect | 24.5 ms | 22.6 ms | one RTT — this *is* your RTT |
| TLS | 57.0 ms | 32.5 ms | TLS 1.3, about 1.4 RTT |
| First byte | 88.7 ms | 31.7 ms | request out, one RTT, first byte back |
| Total | 88.8 ms | | 98% round trips |

The reason this is the right way to present it: it makes the conclusion unavoidable. Server
processing is 2 ms of 89. Nothing you do to the server code matters here.

### The `.pcap` annotation

The deliverable is byte offsets, not a screenshot. Structure it like this:

```
Frame 1, 74 bytes on the wire
  0x0000  a4 83 e7 ... 08 00        Ethernet: dst MAC, src MAC, ethertype 0x0800 (IPv4)   [14 B]
  0x000e  45 00 00 3c ...           IPv4: version 4, IHL 5 (=20 B), total length 60
  0x0016  40                        TTL 64
  0x0017  06                        Protocol 6 = TCP
  0x001a  c0 a8 01 25               Source 192.168.1.37
  0x001e  68 14 17 9a               Dest   104.20.23.154
  0x0022  d4 31 01 bb               TCP: src port 54321, dst port 443
  0x002e  02                        Flags = SYN
...
Frame 4 (first TLS record)
  offset +5   16 03 01              TLS record: handshake, legacy version 3.1
  offset +9   01                    ClientHello
  ...         00 00                 extension 0 = server_name (SNI)
                                    "example.com" -- IN PLAINTEXT
```

Then the two sentences the lab asks for: *the SNI is readable because the client must tell the server
which certificate to present before any key has been agreed — it is the first message, and there is
no shared secret yet. Everything after the ServerHello is encrypted under the derived keys.*

## Why this solution and not the obvious one

**Reporting phase durations, not cumulative times.** Almost every student pastes `curl`'s raw output.
It is correct and it is unreadable — nobody can subtract in their head fast enough to see that TLS
cost 32.5 ms. The table with a duration column is the analysis; the raw output is the data.

**Only the final traceroute hop is treated as a measurement.** The capture above showed hop 3 at
96.9 ms and hop 7 at 20.3 ms. A submission that concludes "hop 3 is the bottleneck" has
misunderstood the tool: routers rate-limit ICMP generation, so intermediate times measure the
router's control plane, not the forwarding path.

**Wrong turns worth knowing about.**

1. *Concluding that a 20 ms RTT to `example.com` from India is impossible, and doubting the
   measurement.* It is anycast. The instinct to distrust a surprising number is good; the next step
   is to explain it, not discard it.
2. *Running `openssl s_client` without `-servername`.* No SNI means the server returns its default
   certificate, and you spend an hour on a hostname mismatch that does not exist.
3. *Capturing without `-s 0` on older `tcpdump`.* Truncated packets, and then the TLS handshake
   cannot be parsed. Modern versions default to full capture, but check.

## Measured numbers this solution produces

- Header overhead: 14 + 20 + 20 = **54 bytes** (3.6% of a 1500-byte MTU).
- DNS: cold **87 ms**, warm **4–6 ms**, novel subdomain **26 ms** — a 21× cache effect.
- `traceroute example.com`: **7 hops, 20.3 ms** to a Cloudflare anycast edge from an Indian
  residential connection.
- Full request: DNS 1.9 / TCP 22.6 / TLS 32.5 / request 31.7 ms = **88.8 ms**, of which ~2 ms is
  server work.

## Grading notes

**What 3/3 looks like**

- *Correctness* — the phase table sums to the total, and the student's own numbers, not these.
- *Code quality* — the capture command is reproducible and committed, with the filter shown.
- *Performance* — the round-trip count is derived (`total ≈ DNS + 3 × RTT`) and compared against the
  measured RTT, so the budget is *explained*, not just tabulated.
- *Explanation* — states which phase is removable and by what mechanism (keep-alive removes TCP and
  TLS; a CDN reduces RTT; session resumption reduces TLS to 0-RTT).

**The three most common ways submissions lose points**

1. **Cumulative `curl` output pasted without differencing.** The measurement was taken; the analysis
   was not done.
2. **An intermediate traceroute hop blamed for latency.** A specific, teachable misreading.
3. **No explanation of the 20 ms anycast result.** The most interesting number in the exercise, left
   unremarked.
