## Reference solution — `P2-W13-M3`

The full `LRUCache` is in Layer 2 of the module page. What follows is the part that is not in the
module: **the invariant checker**, why it is the whole assignment, and what the benchmark should
show.

### The invariant checker

```python
def check_invariants(c: LRUCache) -> None:
    """Call this at the end of EVERY test. Five lines; catches everything."""
    # 1. Walk forward from head to tail.
    forward, node = [], c._head.next
    while node is not c._tail:
        forward.append(node.key)
        node = node.next

    # 2. Walk BACKWARD from tail to head. This is the half people omit.
    backward, node = [], c._tail.prev
    while node is not c._head:
        backward.append(node.key)
        node = node.prev

    # 3. The two walks must be exact reverses.
    assert backward == list(reversed(forward)), "prev/next pointers disagree"

    # 4. The list-reachable set must equal the map's key set — no orphans, no ghosts.
    assert set(forward) == set(c._map), "list and map have diverged"
    assert len(forward) == len(c._map) == len(set(forward)), "duplicate or missing node"

    # 5. Every map value is the node stored under that key.
    for k, n in c._map.items():
        assert n.key == k, f"map key {k!r} points at node {n.key!r}"
```

**Step 2 is the one that earns its keep.** A half-updated `prev` pointer produces a list that
traverses correctly forward and is corrupt backward. Every forward-only check passes; the corruption
surfaces later as a lost eviction or an infinite loop, in a completely unrelated test.

**Step 4 is what would have caught the module's war story.** The orphaned-node bug kept `len(_map)`
at exactly capacity while nodes accumulated off-list. The map looked healthy; the reachable set did
not match it.

### The benchmark, and what it should show

```python
def zipf_ops(n=500_000, hot=2_000, cold=40_000, hot_share=0.8, seed=3):
    """80% of accesses to 20% of keys. A uniform pattern gives a flattering
    hit rate that no real cache ever sees."""
    rng = random.Random(seed)
    return [rng.randrange(hot) if rng.random() < hot_share else rng.randrange(cold)
            for _ in range(n)]
```

Measured on the reference machine, 500,000 operations, capacity 10,000:

| Implementation | Total | Per op | Hit rate |
| --- | --- | --- | --- |
| Hand-rolled `dict` + doubly linked list, `__slots__` | 323.0 ms | 646 ns | 84.4% |
| `collections.OrderedDict` + `move_to_end` | 105.3 ms | **211 ns** | 84.4% |

**`OrderedDict` is 3.07× faster, running the identical algorithm.** If your write-up does not
mention this, you did not benchmark against the standard library — which is the point of the
exercise.

## Why this solution and not the obvious one

**Why sentinels, from the first line.** Without them, `_unlink` needs three branches (node is head,
node is tail, node is both) and `_push_front` needs two. With them, both are unconditional two-line
functions. Roughly half the bugs in hand-written linked-list code live in those branches.

**Why a Zipf-like access pattern.** A uniform random pattern over a key space larger than capacity
gives a hit rate near zero and makes every implementation look the same. Real caches see skew; the
80/20 pattern produces a realistic 84% hit rate, and **asserting that both implementations achieve
the *same* hit rate is what proves you are benchmarking two implementations of one algorithm rather
than two different caches.**

**Why the report should recommend not shipping your own.** The honest conclusion is: write it to
understand the structure, then use `OrderedDict` or `functools.lru_cache`. A submission that
concludes "my implementation is good, ship it" has measured something and not read it.

## Grading notes

**3/3 on Correctness** — `check_invariants` called at the end of every test, including the backward
walk; the capacity-1 case; the "membership must not count as a use" case; and a 10,000-insert
no-leak test.

**3/3 on Performance** — both implementations measured on an identical operation sequence with the
hit rate asserted equal, best-of-3, with machine and version stated.

**3/3 on Explanation** — the 3.07× gap explained mechanically (C pointer writes against Python
attribute assignments, ~25–40 ns each) and a stated recommendation not to ship the hand-rolled
version.

**The three most common ways submissions lose points:**

1. **Forward-only invariant checking.** Misses every `prev`-pointer bug. The backward walk is three
   lines.
2. **`__contains__` implemented as `self.get(key) is not None`.** Silently makes every existence
   check a *use*, changing the eviction order and the hit rate. Test it explicitly.
3. **Benchmarking with a uniform access pattern.** Hit rate near zero, all implementations look
   identical, and the benchmark says nothing.

**On the stretch challenge (W-TinyLFU).** If someone submits it, the thing to look for is whether
they computed the **break-even miss cost** — "this costs 8 bytes per entry more and buys 2 points of
hit rate; that is worth it only if a miss costs more than X". A hit-rate curve without that
arithmetic is a chart, not a recommendation.
