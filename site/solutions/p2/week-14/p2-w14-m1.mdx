## Reference solution — `P2-W14-M1`

Two deliverables: the autocomplete comparison, and the BST degeneration measurement.

### The autocomplete result

100,000 words from `/usr/share/dict/words`, 20,000 prefix queries of 1–3 characters, limit 10:

| Structure | Total | Per query | Resident memory |
| --- | --- | --- | --- |
| Trie (`__slots__` nodes, dict children) | 433.4 ms | **21.7 µs** | **65.1 MB** |
| Sorted list + `bisect.bisect_left` | 68.0 ms | **3.4 µs** | **5.9 MB** |
| | | **trie 6.4× slower** | **trie 11.0× larger** |

**The trie loses on both axes**, and if your write-up does not say so, you did not measure it.

The explanation, which is the graded part:

- The trie's *descent* is 1–3 dict lookups and is genuinely faster than `bisect`'s ~17 comparisons.
- The trie's *enumeration* is not. Collecting ten completions costs a stack push and pop, a
  `sorted()` over the children dict, and a string concatenation `so_far + ch` per level, per result.
  The array version does `out.append(words[i])` ten times.
- **Autocomplete spends its time enumerating, not descending**, so the trie's advantage is in the
  wrong half of the operation.
- Memory: ~250,000 trie nodes, each a Python object with `__slots__` (~56 bytes) plus a `dict` for
  children (~232 bytes once populated). Roughly 260 bytes per node against ~64 for a 9-character
  `str`.

**What would change the answer**, and a good write-up says this too: a systems language with an
arena and fixed-size child arrays; a vocabulary with heavy prefix sharing (URLs, file paths) where a
radix tree collapses the chains; or a query the array cannot express at all, which is fuzzy matching
within a bounded edit distance.

### Measuring the trie's memory correctly

```python
import sys

def deep_size(obj, seen=None) -> int:
    """sys.getsizeof on a trie root returns ~56 bytes — it does not follow
    references. You must walk it, with an id()-based seen-set for cycles."""
    seen = seen if seen is not None else set()
    if id(obj) in seen:
        return 0
    seen.add(id(obj))
    size = sys.getsizeof(obj)
    if isinstance(obj, dict):
        for k, v in obj.items():
            size += deep_size(k, seen) + deep_size(v, seen)
    elif isinstance(obj, (list, tuple, set, frozenset)):
        for i in obj:
            size += deep_size(i, seen)
    elif hasattr(obj, "__slots__"):
        for s in obj.__slots__:
            if hasattr(obj, s):
                size += deep_size(getattr(obj, s), seen)
    return size
```

**`sys.getsizeof(root)` returns 56 and people report it.** It measures one object, not the
structure. The alternative to the walk is `ru_maxrss` in a subprocess that builds only the trie.

### The BST degeneration result

100,000 integer keys, two insertion orders:

| Insert order | Height | Build | 5,000 lookups | Avg comparisons |
| --- | --- | --- | --- | --- |
| Random shuffled | **41** | 0.10 s | 6.4 ms | **21.4** |
| Strictly ascending | **100,000** | **162.80 s** | **7,265.4 ms** | **50,418.8** |
| Ratio | 2,439× | **1,628×** | **1,135×** | **2,356×** |

Two details worth more than the headline:

1. **Height 41 for random insertion, when `log₂(100,000) ≈ 16.6`.** A randomly-built BST has expected
   height `≈ 4.311 · ln n ≈ 49.6` (Reed, 2003). **A random BST is ~2.5× deeper than optimal**, so
   the failure mode is not "random is fine, sorted is bad" — it is "random is worse than you think
   and sorted is catastrophic".
2. **50,418.8 average comparisons is exactly `n/2`.** That is the signature of a linear scan, and it
   is how you detect degeneration from telemetry without inspecting the structure: instrument the
   comparison count and watch whether it tracks `log n` or `n/2`.

**Use an iterative `depth()`.** A recursive one raises `RecursionError` on the degenerate tree at
depth 100,000, which is exactly the tree you are trying to measure.

## Why this solution and not the obvious one

**Why cross-check the two implementations before benchmarking.** Two implementations that disagree
are two implementations, one of which is wrong, and benchmarking a buggy one tells you nothing. The
`@pytest.fixture(params=[TrieAutocomplete, SortedArrayAutocomplete])` pattern runs one test suite
against both, and `test_both_implementations_agree` compares them across a few thousand prefixes.

**Why the "prefix that is also a word" case is the fixture that matters.** `car` is both a word and a
prefix of `card`. The trie gets this wrong if you conflate `is_word` with "is a leaf"; the array
version gets it wrong if you use `bisect_right` instead of `bisect_left`. **One test case catches
two independent bugs in two independent implementations.**

**Why report expansions of the search rather than only latency.** Latency is machine-dependent;
per-query cost and memory both scale predictably and can be compared to someone else's numbers.

## Grading notes

**3/3 on Correctness** — both structures behind one interface, cross-validated across thousands of
prefixes, with the prefix-is-a-word, empty-prefix, and missing-prefix cases tested.

**3/3 on Performance** — per-query latency and resident memory for both, memory measured by a
recursive walk or `ru_maxrss` rather than bare `sys.getsizeof`.

**3/3 on Explanation** — the trie's loss explained by *where* the time goes (enumeration, not
descent), and a stated condition under which the trie would win.

**The three most common ways submissions lose points:**

1. **`sys.getsizeof(trie_root)` reported as the trie's memory.** Returns ~56 bytes. It is the single
   most common error in this lab.
2. **Recursive `depth()` on the degenerate tree.** `RecursionError` at 100,000 deep, and the
   temptation is to raise the recursion limit — which risks a segfault, because the real limit is
   the C stack.
3. **Concluding "tries are better" from theory without reporting the measurement.** The measurement
   says otherwise, and reporting the result that contradicts the expectation is the whole exercise.

**On the B-Tree arithmetic.** A strong submission includes it: 4 KB page ÷ 16 bytes per entry =
256-way fan-out, so `log₂₅₆(10⁸) ≈ 3.3` — four levels for a hundred million rows, against 27 for a
balanced BST. Being able to produce that in ten seconds is what distinguishes understanding an index
from having memorised that indexes are fast.
