## Reference solution — `P2-W12-M1`

### The design decision that matters

```python
class NaiveBayes:
    def log_ratio(self, text):
        """log P(x|spam) - log P(x|ham). The EVIDENCE, with no prior in it."""
        V = len(self.vocab); s = 0.0
        for t in set(tokenise(text)):
            if t not in self.vocab:
                continue
            p_spam = (self.counts[1][t] + self.alpha) / (self.total[1] + self.alpha * V)
            p_ham  = (self.counts[0][t] + self.alpha) / (self.total[0] + self.alpha * V)
            s += math.log(p_spam) - math.log(p_ham)
        return s

    def predict_logodds(self, text, prior_log_odds=None):
        if prior_log_odds is None:
            prior_log_odds = self.log_prior[1] - self.log_prior[0]
        return prior_log_odds + self.log_ratio(text)
```

Separating the prior from the evidence is the whole design. It means you can train on a 13% spam corpus
and serve against 0.5% production traffic by substituting one number, with no retraining — which is
Bayes' theorem in odds form, implemented.

### Precision at any base rate

```python
def precision_at(tpr, fpr, prevalence):
    return tpr * prevalence / (tpr * prevalence + fpr * (1 - prevalence))
```

That one line converts a classifier's measured sensitivity and specificity into the number the
operations team will actually experience.

## Why this solution and not the obvious one

**Token *presence*, not count.** Counting repeated tokens in a short SMS message over-weights repetition
and multiplies dependent evidence. `set(tokenise(text))` is one character and it measurably improves F1
on short text.

**Unseen tokens are skipped, not smoothed into the score.** A token absent from the training vocabulary
carries no information about either class, so including it with a smoothed probability adds noise. Skip
it.

**Log space, always.** A 200-token message multiplies 200 probabilities each around 1e-4. In float64
that underflows to exactly zero after about 80 terms, and every message then scores identically. This
is not a theoretical concern — it happens on the second document you test.

**Wrong turns worth knowing about.**

1. *Answering "about 99%" to the medical-test question.* Almost everyone does. The correct answer is 9%,
   and the way to get there is to **count people** — 99 true positives against 999 false positives per
   100,000 — not to manipulate percentages.
2. *Confusing specificity with the false-positive rate.* `FPR = 1 − specificity`. Getting this backwards
   inverts the whole base-rate table and is the most common bug in the guided practice.
3. *Reporting accuracy on an imbalanced problem.* The measured classifier is 97.9% accurate. A classifier
   that always predicts "ham" is 85.7% accurate on the same data. Accuracy is nearly uninformative here.
4. *Evaluating on a rebalanced set.* This is the war story, and it produces a validation precision that
   is off by an order of magnitude in production.

## Grading notes

**What 3/3 looks like**

- *Correctness* — F1 above 0.90; the base-rate table matches the Bayes formula; no underflow on a long
  document.
- *Code quality* — the prior is a separate argument, not baked into the score; smoothing is a parameter.
- *Performance* — the base-rate table computed analytically **and** verified by Monte Carlo simulation.
- *Explanation* — the paragraph for a non-technical stakeholder actually reads as though a
  non-technical stakeholder could follow it, and states the false-alarm rate rather than the precision.

**The three most common ways submissions lose points**

1. **Precision reported only at the dataset's base rate.** The whole module is about what happens when
   it changes.
2. **Specificity used where the false-positive rate was needed**, inverting the table.
3. **The stakeholder paragraph written in statistics.** "Precision falls to 0.29" means nothing to an
   operations lead. "You would see two false alarms for every real one" does.
