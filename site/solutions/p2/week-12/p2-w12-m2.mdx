## Reference solution — `P2-W12-M2`

### The two derived numbers nobody computes

```python
def describe(a):
    a = np.asarray(a, float); a = a[np.isfinite(a)]
    q = lambda p: float(np.percentile(a, p))
    mean, sd = float(a.mean()), float(a.std(ddof=1))
    srt = np.sort(a)
    return {
        "p50": q(50), "p95": q(95), "p99": q(99), "max": float(a.max()),
        "p99_over_p50": q(99) / q(50),
        "frac_above_mean": float((a > mean).mean()),                       # <- this one
        "skewness": float(((a - mean) ** 3).mean() / sd ** 3),
        "slowest_1pct_share_of_total": float(srt[int(0.99*len(srt)):].sum() / a.sum()),  # <- and this
    }
```

`frac_above_mean` converts "the distribution is skewed" into a sentence a non-statistician can act on:
*only 19.8% of requests are slower than the average*. `slowest_1pct_share_of_total` tells you whether
tail optimisation is worth doing at all.

### Fan-out amplification

```python
def fanout_slow_probability(p_slow, k):
    return 1 - (1 - p_slow) ** k
```

## Why this solution and not the obvious one

**Measure real latency rather than simulating it.** A simulated log-normal is clean and teaches the
shape; real data teaches that the tail comes from a *different mechanism* than the bulk (scheduler
preemption, GC, retries), which is why the log transform reduced skewness from 20.56 to 3.57 rather
than to zero.

**Report `p99/p50` rather than `p99` alone.** The ratio is comparable across services and across time,
while the absolute p99 is not.

**Compute the tail's share of total time.** It answers the question "should I work on the tail?"
directly. Measured here at 5.44% — real but not dominant. On a service with database calls it is
routinely 20–40%, and then the tail is where your capacity goes.

**Wrong turns worth knowing about.**

1. *Trimming outliers before analysis.* On latency data the outliers are the subject. Trimming them is
   deleting the finding.
2. *Averaging percentiles across hosts or time buckets.* Percentiles are not linear; the result always
   understates the true tail. Prometheus histograms aggregate correctly; summaries do not.
3. *Believing the `n ≥ 30` rule for the CLT.* Measured on this data, the sample mean's skewness was still
   **3.33 at n = 30** and only reached 0.62 at n = 1000. The required `n` scales roughly with the square
   of the population's skewness.
4. *Closed-loop load generation.* When the system stalls, the generator stops issuing requests, so the
   stall is under-sampled and the reported tail is optimistic. This is coordinated omission.

## Grading notes

**What 3/3 looks like**

- *Correctness* — the student's own measurements, not these; percentiles match `np.percentile`; NaN and
  infinity handled.
- *Code quality* — one `describe` function returning a dict, reusable on any timing data.
- *Performance* — measured open-loop, with coordinated omission explicitly addressed.
- *Explanation* — the SLA argument made with `frac_above_mean`, and the CLT's `n ≥ 30` rule tested and
  reported as failing on this data.

**The three most common ways submissions lose points**

1. **Simulated data presented as measured.** The point of the exercise is your own machine's tail.
2. **The `n ≥ 30` rule repeated rather than tested.** The measured skewness at n=30 is the finding.
3. **`frac_above_mean` omitted.** It is the number that makes the argument to a non-statistician, and it
   is one line.
