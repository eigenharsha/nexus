## Reference solution — `LAB-P2-W09`

The per-module solution pages carry the chip implementations. This page covers what the lab asks for
beyond them: the report, the hard-track constraint, and the benchmark analysis.

### `REPORT.md` — the shape that earns 3/3

```markdown
# Week 9 datapath — area and critical path

Measured with nandsim.py (NAND-only, depth = max(input depths) + 1).
All chips verified: gates exhaustively, adders and ALU by randomised testing.

## Area and depth

| Block        | NANDs | Depth |
|--------------|-------|-------|
| Not/And/Or   | 1/2/3 | 1/2/2 |
| Xor/Mux/DMux | 4/4/5 | 3/3/3 |
| Add16 ripple |   240 |    67 |
| Add16 KS     |   503 |    20 |
| Inc16        |    96 |    34 |
| ALU (ripple) |   718 |    81 |
| ALU (KS)     |   981 |    34 |
| Register     |   ~96 |     3 |
| RAM16K       | ~1.6M |    ~9 |

## f_max

t_gate = 10 ps, setup + skew = 20 ps.

  ripple ALU: 81 x 10 ps + 20 ps = 830 ps -> 1.20 GHz
  KS ALU:     34 x 10 ps + 20 ps = 360 ps -> 2.78 GHz

## Critical path

The longest path is x[0] -> input conditioning -> Add16 carry chain -> function
MUX -> output MUX -> zr tree. 67 of the 81 levels are the ripple carry chain.
Replacing it with Kogge-Stone costs 263 extra NANDs (+37% ALU area) and buys
2.3x the clock. The next bottleneck after that is the input conditioning at
7 levels, which cannot be reduced without merging the four MUX stages into
compound cells.
```

That last paragraph is what separates a report from a table: it names the *next* bottleneck.

### The `hard` constraint: ALU depth under 40

The `standard` ALU measures 81. The decomposition:

| Segment | Levels |
|---|---|
| Input conditioning (2 MUX + NOT stages) | 7 |
| Adder | 67 |
| Function MUX | 3 |
| Output NOT + MUX | 4 |
| (`zr` is parallel to `out`, adding 5 beyond the MUX) | — |

Only the adder can move. Swapping in Kogge-Stone at depth 20 gives `7 + 20 + 3 + 4 = 34`, comfortably
under 40. There is no way to reach 40 by tuning gates — you have to change the adder algorithm. That
is the entire point of the constraint, and any submission that reaches it another way should be read
carefully, because it probably measured depth wrongly.

### Analysing the locality curve

The three regimes to identify, using your own machine's cache sizes:

1. **Working set fits in L2** (N = 256, 0.2 MiB here): both loops are served from cache; the
   column-major version still pays for poor line utilisation and extra loads, giving ~9×.
2. **Working set exceeds L2 but the column stride stays within a page** (N = 512–1024): the stride
   prefetcher still partially works; the gap grows to ~13–28×.
3. **Working set far exceeds all caches and every column step crosses a page** (N = 2048–4096): every
   access is a DRAM round trip plus a TLB miss; the gap reaches 38–67×.

A 3/3 explanation names the line size (64 B on x86-64, 128 B on Apple silicon), computes the useful
fraction (1 of 16 floats, or 1 of 32), and identifies TLB pressure as a *separate* contributor from
data cache misses. It also reports the negative control: without `-ffast-math` both loops run at
about 1.17 ns/element and the gap vanishes, because the row-major loop is limited by the serial FP
add chain rather than by memory.

## Why this solution and not the obvious one

**The report is generated, not hand-written.** `tools/report.py` re-derives every number from the
simulator, and `make verify` diffs it against the committed `REPORT.md`. Hand-typed performance
numbers rot within a week; regenerated ones cannot. This is a habit worth carrying into real work —
it is the same reason benchmark results belong in CI.

**The prefix adder is dropped in behind the same interface.** `Add16` keeps its pins, so the ALU does
not change at all; only the implementation file is swapped. If changing the adder required editing
`ALU.hdl`, the abstraction boundary was in the wrong place.

## Grading notes

**What 3/3 looks like on each rubric row**

- *Correctness* — all official tests green, plus the randomised ALU harness reporting 0 failures over
  36,000 operand pairs, plus a multi-thousand-cycle randomised RAM test.
- *Code quality* — a strict hierarchy: nothing 16-bit contains a `Nand`, nothing at RAM level `k`
  contains a chip from level `k−2`.
- *Performance* — the prefix ALU meets the sub-40-level constraint, with the area cost stated as a
  percentage and the trade defended.
- *Explanation* — the critical path is named, the *next* bottleneck is named, and the locality curve
  is explained by cache capacity and line utilisation, including the negative control.

**The three most common ways submissions lose points**

1. **All tests green, no numbers.** The ticket asked for a frequency and a responsible block. Green
   tests are the entry fee, not the deliverable.
2. **Numbers copied from the course rather than measured.** Easy to spot: the depths match this page
   exactly, including on a machine or simulator that could not have produced them. Measure your own.
3. **The benchmark reported as a single ratio.** One number cannot distinguish "cache misses" from
   "TLB misses" from "prefetcher defeat", and the whole analytical value of the exercise is in the
   curve.
