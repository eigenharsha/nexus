## Reference solution — `P2-W16-M3`

Reproduce the four leakage measurements and explain them with a rule.

### The expected results

**1. Imputation before the split — no measurable inflation.**

| Imputer | n | Leaky AUC | Correct AUC | Inflation |
| --- | --- | --- | --- | --- |
| mean | 100 | 0.6210 | 0.6277 | **−0.0067** |
| mean | 1,000 | 0.7555 | 0.7568 | **−0.0013** |
| mean | 5,000 | 0.7635 | 0.7639 | **−0.0004** |
| KNN (k=5) | 100 | 0.7131 | 0.7333 | **−0.0201** |
| KNN (k=5) | 1,000 | 0.7823 | 0.7797 | +0.0026 |
| Iterative (MICE) | 300 | 0.7399 | 0.7428 | −0.0029 |

**Every value within ±0.02 AUC, most negative, shrinking toward zero as n grows** — the signature of
measurement noise, not an effect. This holds even with the missingness deliberately made MNAR by
depending on the label, which is the condition most favourable to leakage.

**2. Target encoding a pure-noise categorical — +0.275.**

| Approach | AUC |
| --- | --- |
| Encode using the whole dataset's target means | **0.7846** |
| Encode using train target means only | 0.5094 |
| **Truth** | **0.5000** |

A 500-level categorical assigned completely at random. Each level has ~4 rows, so its "encoded value"
is the mean of those four labels — **including the test rows' labels**. The model is being told the
answer through a category code.

**3. Feature selection before CV — up to +0.356, and it scales.**

| Candidate features | Leaky CV | Correct CV | Inflation |
| --- | --- | --- | --- |
| 200 | 0.6750 | 0.4910 | +0.184 |
| 1,000 | 0.7270 | 0.4860 | +0.241 |
| 5,000 | 0.7800 | 0.4810 | +0.299 |
| 20,000 | **0.8250** | 0.4690 | **+0.356** |

200 samples, **entirely random features and random labels**. The truth is 0.500 in every row. **The
inflation grows with the number of candidates searched** — that is the mechanism made visible.

**4. Duplicate rows spanning the split — up to +0.200.**

| Duplication | Random split | `GroupShuffleSplit` | Inflation |
| --- | --- | --- | --- |
| 0% | 0.7222 | 0.7151 | +0.007 (noise) |
| 10% | 0.7805 | 0.7176 | **+0.063** |
| 30% | 0.8605 | 0.7126 | **+0.148** |
| 50% | 0.9116 | 0.7116 | **+0.200** |

### The rule that predicts all four

> **Leak size scales with how much the transform's parameters depend on `y`, multiplied by how many
> candidates the transform searched.**

| Transform | Uses `y`? | Candidates | Measured |
| --- | --- | --- | --- |
| Mean/median imputation | no | 1 per column | **≈ 0** |
| StandardScaler | no | 2 per column | ≈ 0 |
| KNN / iterative imputation | no (uses other rows) | few per column | ≈ 0 |
| Target encoding | **yes** | one per category level | **+0.275** |
| Feature selection | **yes** | one per candidate feature | **+0.184 → +0.356** |

**A mean imputer fits one number per column, from the same distribution, carrying almost no
information about any individual test row's label.** At n = 5,000, the mean of all rows and the mean
of the train rows agree to several decimal places.

**And the correct practice does not change.** Put every fitted transform inside a `Pipeline` — not
because imputation leaks, but because some things leak enormously, you do not want to adjudicate case
by case, `Pipeline` makes cross-validation automatically correct, and it costs nothing. **Do the right
thing for the right reason.**

## Why this solution and not the obvious one

**Why report the negative result.** The week's specification asked for a demonstration that imputing
before splitting inflates test accuracy. It does not, measurably. **Manufacturing a scenario that
produces the expected number would be dishonest and would teach a rule that misdirects attention** —
people check imputation order carefully and leave a target-encoded feature in place, which is exactly
backwards.

**Why 20–30 repetitions.** The effect is within noise. A single run shows a difference in one
direction and you will believe it. Twenty seeds show the mean is zero and the sign is random.

**Why pure noise for experiments 2 and 3.** With random features and random labels the correct answer
is exactly 0.500, so every point above it is leakage with no ambiguity about whether the model "found
something".

**Why the folklore exists.** "Never transform before splitting" is a *safe* rule — never harmful —
generalised from cases where it genuinely matters, and it is easier to teach than the real one. It is
fine as a practice and wrong as an explanation.

### The leaks a pipeline cannot fix

```python
# 1. TIME TRAVEL — no pipeline detects this.
df["roll"] = df.value.rolling(7, center=True).mean()   # uses the FUTURE
df["roll"] = df.value.rolling(7).mean().shift(1)       # correct

# 2. A feature populated after the outcome — only a temporal audit finds this.
# 3. GROUP leakage — needs the right SPLITTER, not the right pipeline.
GroupKFold(n_splits=5).split(X, y, groups=df.patient_id)
# 4. A target derived from a feature — `is_active` and `churned` are one column twice.
```

**The definitive diagnostic, and it takes ten minutes:**

```python
scores = cross_val_score(model, X, rng.permutation(y), cv=5, scoring="roc_auc")
assert scores.mean() < 0.55, f"structural leakage: {scores.mean():.3f} on shuffled labels"
```

**Permute the target. It must score chance.** If it does not, the leak is in your splitting or your
data, and no feature-by-feature audit will find it.

## Grading notes

**3/3 on Correctness** — all four experiments, ≥20 repetitions each, with data whose true answer is
known.

**3/3 on Explanation** — the negative result reported, the rule stated, and the rule shown to predict
all four measured magnitudes.

**3/3 on Code quality** — every fitted transform inside a `Pipeline`, with a test that poisons the
test set and confirms the fitted parameters do not move.

**The three most common ways submissions lose points:**

1. **Running each configuration once.** The imputation effect is within noise, and one run always
   shows a difference.
2. **Not reporting the negative result.** A benchmark that only reports the effects it hoped to find
   is not a benchmark. **This is the graded finding of the module.**
3. **Reporting inflation without the true answer.** "The leaky version scored 0.78" is
   uninterpretable unless you say the truth was 0.50.

**A fourth:** concluding "so imputation order does not matter, I will stop using pipelines". The
measurement says the *leak* is negligible; it says nothing about the other three reasons for the
discipline (test-time consistency, automatic CV correctness, and not having to adjudicate each
transform). A submission that draws the wrong operational conclusion from a correct measurement has
made a worse error than one that measured nothing.

**On the stretch challenge (leakage detector).** The number to look for is the **false-positive rate
on clean data**. A detector that flags every dataset is muted within a week, and then it is not there
when something real happens — the same failure as module 4's drift alert. Precision and recall
against a labelled corpus, or it is a heuristic rather than a tool.
