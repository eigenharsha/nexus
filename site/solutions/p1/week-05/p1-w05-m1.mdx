## Reference solution — `P1-W05-M1`

The module exercise is: instrument a request, then prove the cost of connection reuse.

### The complete `httptrace` script

```bash
#!/usr/bin/env bash
# httptrace — phase-by-phase timing for any URL. Usage: ./httptrace <url> [runs]
set -euo pipefail
URL="${1:?usage: httptrace <url> [runs]}"; N="${2:-5}"
FMT='%{time_namelookup} %{time_connect} %{time_appconnect} %{time_starttransfer} %{time_total} %{http_code} %{size_download} %{http_version}\n'

printf "%-8s %-8s %-8s %-8s %-8s %-5s %-9s %s\n" dns tcp tls ttfb total code bytes proto
for _ in $(seq "$N"); do
  curl -sS -o /dev/null -w "$FMT" "$URL" | awk '{
    printf "%-8.1f %-8.1f %-8.1f %-8.1f %-8.1f %-5s %-9s %s\n",
      $1*1000, ($2-$1)*1000, ($3-$2)*1000, ($4-$3)*1000, $5*1000, $6, $7, $8 }'
done
```

The only subtle part is the `awk` line. `curl`'s timing variables are **cumulative offsets from
the start of the request**, not phase durations, so `time_connect` already includes DNS. Printing
them raw is the single most common mistake in this exercise and it makes TLS look free. Subtract
consecutive values to get phases.

### The measured result

Against `https://developer.mozilla.org/en-US/docs/Web/HTTP` on home broadband:

| Phase | Cumulative | Phase cost |
| --- | --- | --- |
| DNS | 6.9 ms | 6.9 ms |
| TCP | 17.4 ms | 10.5 ms |
| TLS | 32.3 ms | 14.9 ms |
| Server think + first byte | 45.2 ms | 12.9 ms |
| Transfer of 221,912 bytes | 71.8 ms | 26.6 ms |

Connection reuse, six requests each way:

```
fresh connection each: 780 ms
one keep-alive connection: 204 ms
```

3.8×, or about 96 ms saved per avoided setup.

## Why this solution and not the obvious one

**Wrong turn 1: measuring once.** A single run is dominated by whatever your machine and the
nearest DNS resolver were doing at that instant. My own runs of the same URL ranged from 64 ms to
189 ms total. The script runs N times for a reason, and the *second and later* rows are the ones
that tell you about the server rather than about your resolver cache — on run 2 onward, `dns` and
`tls` are typically 0.0, which is itself the evidence that reuse is happening.

**Wrong turn 2: concluding that HTTP/2 is faster because it is newer.** The honest measurement in
Layer 3 shows HTTP/2 *losing* on 12 parallel requests over a 20 ms link: 66–93 ms versus 55–103 ms
for HTTP/1.1. Learners who report "h2 was faster" without running it are pattern-matching, not
measuring. The correct write-up says: at this request count and this latency the difference is
inside the noise, and the arithmetic shows the crossover is at high request counts and high RTT.
A grader should reward the learner who reports a null result honestly over the one who reports the
expected result.

**Wrong turn 3: using `-L` (follow redirects) without noticing.** Several public URLs answer 301.
If you follow redirects, `time_total` covers two requests and the phase breakdown becomes
meaningless because the second request reuses the connection. Check `%{http_code}` is 200 before
you trust any of the numbers — that column is in the script for exactly this reason.

## Measured numbers this solution produces

| Claim | Number | How to reproduce |
| --- | --- | --- |
| Setup is a large fraction of a cold request | 32.3 of 71.8 ms = 45% | `httptrace <url> 1` on a cold DNS cache |
| Connection reuse saving | ~96 ms per avoided setup | the two `time` commands in Layer 1 |
| Keep-alive speedup, 6 requests | 780 ms → 204 ms (3.8×) | same |
| HTTP/2 vs 1.1, 12 parallel, 20 ms RTT | no significant difference | `curl --parallel --parallel-max 12` with each protocol flag |

## Grading notes

**A 3/3 on correctness** subtracts the cumulative timings into phases, runs multiple times, checks
the status code, and states the machine and network conditions alongside the numbers. A 2 gets the
numbers but reports cumulative values as if they were phases.

**A 3/3 on explanation** contains a sentence of the form "X% of this request was setup, so the
highest-leverage change is Y", and, if HTTP/2 did not win, says so plainly with the arithmetic for
when it would.

**The three most common ways submissions lose points**

1. Reporting `time_connect` as "TCP time" when it includes DNS. Costs a point on correctness every cohort.
2. No mention of failure or variance — a single run presented as a fact.
3. Claiming HTTP/2 is faster with no measurement, or with a measurement that contradicts the claim and is not addressed.
