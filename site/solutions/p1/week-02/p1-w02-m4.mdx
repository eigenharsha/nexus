## Reference solution — `P1-W02-M4`

The task: find a defect introduced somewhere in 200 commits, using `git bisect run`.

**The test script — and exit code 125 is the whole point.**

```bash
#!/bin/sh
# bisect-test.sh — exit 0 good, 1 bad, 125 skip (cannot evaluate this commit)
set -u

# 1. Can this commit even be evaluated? If not, SKIP — do not guess.
if ! make -s build >/dev/null 2>&1; then
  exit 125
fi
if [ ! -f data.txt ]; then
  exit 125                      # file did not exist yet at this point in history
fi

# 2. The actual predicate. Deterministic, no network, no clock.
if grep -q 'BUG' data.txt; then
  exit 1                        # bad
fi
exit 0                          # good
```

**The run.**

```bash
chmod +x bisect-test.sh
# ALWAYS verify the endpoints first — bisect assumes monotonicity
git checkout -q HEAD      && ./bisect-test.sh; echo "HEAD      -> $?"   # expect 1
git checkout -q HEAD~200  && ./bisect-test.sh; echo "HEAD~200  -> $?"   # expect 0
git checkout -q -

git bisect start HEAD HEAD~200
git bisect run ./bisect-test.sh
```

## Why this solution and not the obvious one

**Wrong turn 1: no exit 125, so unbuildable commits score "bad".**

This is the failure that makes people distrust bisect. In any real 200-commit range, some commits do not build — a dependency was added in the next commit, a generated file was not yet checked in, a rename landed in two parts. A test script that returns 1 for "make failed" tells bisect those commits are **bad**, and bisect dutifully converges on the earliest of them, which is not your bug.

The symptom is characteristic: bisect names a commit whose diff has nothing to do with the behaviour you are chasing. When that happens, the first thing to check is whether your script can distinguish "the predicate is false" from "I could not evaluate the predicate".

Exit 125 means skip. Git then picks a neighbouring commit instead. If too many commits in the range are unskippable, bisect reports the remaining candidate set rather than lying to you.

**Wrong turn 2: not verifying the endpoints.**

`git bisect` is binary search, and binary search has a precondition: the predicate must be **monotone** over the range — good everywhere before the transition, bad everywhere after. If `HEAD~200` is *also* bad (the bug is older than you thought) bisect will still converge, confidently, on a commit inside your range that has nothing to do with it.

Two commands prevent an afternoon of confusion:

```bash
git checkout HEAD~200 && ./bisect-test.sh; echo $?   # must be 0
git checkout HEAD     && ./bisect-test.sh; echo $?   # must be 1
```

For a *performance* regression the monotonicity assumption is much weaker, because noise makes the predicate flap near the threshold. The fix is the Week 1 measurement discipline: run the benchmark N times, take the **minimum**, and set the threshold with real margin — 250 ms when good commits measure 180 ms and bad ones 400 ms, not 200 ms. A flaky predicate converges on a random commit, which is worse than not bisecting because it comes with a confident answer.

**A third thing worth knowing: `git bisect run` leaves you detached.**

Always finish with `git bisect reset`, which returns you to the branch you started on. Scripts that automate bisect should do it in a `trap ... EXIT`, because a bisect abandoned halfway leaves the repository in a confusing state for the next person — and `git bisect log` plus `git bisect replay` is how you resume one deliberately.

## Grading notes

**3/3 on correctness** means bisect converged in 8 or fewer runs, exit 125 is used and *demonstrated* (show a commit that got skipped), and both endpoints were verified before starting.

**3/3 on explanation** means the write-up names the monotonicity precondition and explains what happens when it does not hold.

The three most common ways submissions lose points:

1. **The test script has a side effect.** A script that writes into the working tree, or leaves build artifacts that change the next commit's behaviour, makes the predicate depend on history. Clean between runs, or test in a `git worktree`.
2. **`git bisect reset` never run.** The repository is left detached at an arbitrary commit and the next person's `git status` is alarming.
3. **The blob hash "verified" by comparing two `git` commands.** `git hash-object` and `git rev-parse HEAD:file` agreeing proves nothing — they are the same implementation. The exercise is to reproduce it *outside* Git with `printf` and `shasum`, which is what demonstrates you understand the `<type> <size>\0<content>` framing.
