## Reference solution — `P1-W02-M1`

The task: reconstruct what an unknown binary does using only `strace`/`fs_usage`, `lsof` and `ps`.

The method, in the order that produces answers fastest:

```bash
# 1. What kind of thing is it, before running anything
file ./mystery
otool -L ./mystery       # macOS: what it links against  (Linux: ldd)
strings -n 8 ./mystery | grep -iE 'http|/etc/|/var/|\.json|\.db' | head -40

# 2. Syscall histogram first — one number tells you where it spends its time
strace -f -c ./mystery                                   # Linux
sudo fs_usage -w -f filesys ./mystery                    # macOS: file activity only

# 3. Then the detail, filtered to the interesting families
strace -f -e trace=openat,connect,execve,unlink ./mystery 2>trace.txt

# 4. Live state while it runs
./mystery & pid=$!
lsof -p "$pid"                                   # open files, sockets, libraries
ps -o pid,ppid,stat,etime,rss,command -p "$pid"
cat /proc/"$pid"/environ | tr '\0' '\n'          # Linux only
wait "$pid"; echo "exit=$?"
```

A worked report for a small unknown binary looks like this:

```
FILES READ      /etc/resolv.conf, ~/.config/mystery/config.toml, /usr/share/zoneinfo/UTC
FILES WRITTEN   /tmp/mystery-cache.db (created, 40 KB), ~/.config/mystery/state.json (rewritten)
NETWORK         connect() to 93.184.216.34:443 (resolved from api.example.com)
CHILDREN        one: /usr/bin/git rev-parse HEAD
SIGNALS         installs a SIGTERM handler
EXIT            0

Could NOT determine: what it sent over TLS (encrypted), and whether the cache is
ever read on a subsequent run — needed a second run to answer, which changed behaviour.
```

## Why this solution and not the obvious one

**Wrong turn 1: starting with the full `strace` output.**

An unfiltered `strace -f` on anything real produces tens of thousands of lines, most of them `mmap`, `brk` and `futex` from the dynamic loader and the allocator. People scroll for ten minutes and learn nothing.

`strace -c` first is the correct order. The histogram is twenty lines and it tells you the shape immediately: 400,000 `stat` calls means a filesystem search problem; 3 `connect` calls means the network is not the story; heavy `futex` means lock contention. *Then* you filter to the family that matters. Diagnosis before detail, exactly as in Week 1 Module 5.

**Wrong turn 2: assuming `dtruss` works on macOS.**

Every tutorial says "the macOS equivalent of strace is dtruss". In practice, on a modern macOS with System Integrity Protection enabled, `sudo dtruss` on an Apple-signed binary produces nothing useful, and even on your own binaries it is unreliable. There is no `/proc`, so `cat /proc/PID/environ` and `cat /proc/PID/limits` — two of the most useful commands in the Linux toolkit — simply do not exist.

The honest macOS toolkit is `sudo fs_usage -w -f filesys` (which does work and covers file activity), `lsof` sampled in a loop, `nettop` for network, and `sample`/`spindump` for what the process is doing on-CPU. Everything else means running it in a Linux container.

**Naming what you could not determine is part of the deliverable**, not an admission of failure. An analysis that claims certainty about encrypted payload contents is wrong; one that says "TLS, so I could not read the body, but the SNI was `api.example.com` and the request pattern was one connection per run" is correct and useful.

## Grading notes

**3/3 on correctness** means the report lists every file opened for writing, every network endpoint (address and port, plus the hostname if you caught the DNS lookup), every child process with its arguments, and the exit code.

**3/3 on explanation** means you state at least one question you could not answer *and why the tool could not answer it* — encrypted payload, SIP restriction, no `/proc`, or behaviour that changed between the first and second run.

The three most common ways submissions lose points:

1. **A wall of raw `strace` output pasted into the report.** The deliverable is the conclusion and the evidence for it, not the log. Two hundred lines of `mmap` prove nothing.
2. **Running it once and generalising.** Many programs behave differently on first run (creating a config, warming a cache) versus subsequent runs. Run it three times and note what changed; that difference is often the most informative observation available.
3. **Claiming certainty about a TLS payload.** If it is encrypted, you did not see it. Say so. A report that infers content from timing and size is doing something legitimate but must label it as inference.
