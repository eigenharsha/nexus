## Reference solution — `P1-W01-M4`

Three algorithms, instrumented, benchmarked, plotted, and fitted.

```c
long long nx_comparisons;

void selection_sort(int *a, size_t n) {
    for (size_t i = 0; i + 1 < n; i++) {
        size_t m = i;
        for (size_t j = i + 1; j < n; j++) { nx_comparisons++; if (a[j] < a[m]) m = j; }
        int t = a[i]; a[i] = a[m]; a[m] = t;
    }
}

static void merge_run(int *a, int *tmp, size_t lo, size_t mid, size_t hi) {
    size_t i = lo, j = mid, k = lo;
    while (i < mid && j < hi) { nx_comparisons++; tmp[k++] = (a[j] < a[i]) ? a[j++] : a[i++]; }
    while (i < mid) tmp[k++] = a[i++];
    while (j < hi)  tmp[k++] = a[j++];
    memcpy(a + lo, tmp + lo, (hi - lo) * sizeof *a);
}
static void msort_rec(int *a, int *tmp, size_t lo, size_t hi) {
    if (hi - lo < 2) return;
    size_t mid = lo + (hi - lo) / 2;
    msort_rec(a, tmp, lo, mid);
    msort_rec(a, tmp, mid, hi);
    if (a[mid - 1] <= a[mid]) return;          /* already ordered: skip the merge */
    merge_run(a, tmp, lo, mid, hi);
}
int nx_merge_sort(int *a, size_t n) {
    if (n < 2) return 0;
    int *tmp = malloc(n * sizeof *tmp);
    if (!tmp) return -1;
    msort_rec(a, tmp, 0, n);
    free(tmp);
    return 0;
}

long binary_search(const int *a, size_t n, int key) {
    size_t lo = 0, hi = n;                     /* invariant: answer in [lo, hi) */
    while (lo < hi) {
        size_t mid = lo + (hi - lo) / 2;
        if (a[mid] == key) return (long)mid;
        if (a[mid] < key) lo = mid + 1; else hi = mid;
    }
    return -1;
}
```

Fitting the exponent from two endpoints is enough and is what the README should show:

```python
# plot.py, the part that matters
import math
def fit(n1, t1, n2, t2):
    return math.log(t2 / t1) / math.log(n2 / n1)

print(fit(1000, 1.039, 32000, 890.347))     # selection -> 1.95
print(fit(1000, 0.043, 1000000, 63.053))    # merge     -> 1.06
print(fit(1000, 0.051, 1000000, 110.055))   # qsort     -> 1.11
```

## Why this solution and not the obvious one

**Wrong turn 1: allocating `tmp` inside the recursion.**

The natural translation of "merge sort allocates a temporary array" puts the `malloc` in `merge_run` or in `msort_rec`. It is correct and it roughly doubles the runtime: the recursion makes 2n−1 calls, and at the 31.85 ns per `malloc`/`free` pair measured in Module 3, n = 1,000,000 pays about **63 ms** of pure allocator time on top of a 63 ms sort.

Allocating once in the wrapper and threading `tmp` through the recursion costs one extra parameter and halves the runtime. It also makes the failure path a single, testable place — which is criterion 4 of the lab.

**Wrong turn 2: `<=` instead of `<` in the merge comparison.**

`tmp[k++] = (a[j] <= a[i]) ? a[j++] : a[i++];` sorts correctly. Every test passes. It is also **not stable**: on a tie it takes from the right run, so equal elements come out in reverse of their input order.

Nothing catches this unless you test for it deliberately, which is why the lab's property tests sort an array of structs with a payload field and assert the payloads of equal keys are still in input order. Instability is invisible until someone sorts by department, then by name, and the names come out scrambled — the classic bug report that reads "sorting is random".

The stability rule for a merge is: **on a tie, take from the left run.** One character.

**A third wrong turn worth naming: the `a[mid-1] <= a[mid]` early exit is not free of consequence.**

It makes already-sorted input O(n) and costs one comparison per internal node otherwise — about n comparisons total, under 0.1% of the total at n = 10⁶. Worth it. But if you also count that comparison into `nx_comparisons`, your count will exceed the theoretical formula and the lab's ±5% check will fail on nearly-sorted input. The reference deliberately does not count it, and the README should say so. Instrumentation that changes the number you are validating against is its own bug class.

**Fitted exponents: selection 1.95, merge 1.06, `qsort` 1.11.**

Checks that must line up:

- Selection sort comparisons = n(n−1)/2 exactly: 32000 × 31999 / 2 = 511,984,000 ✓
- Merge sort comparisons versus n·log₂n − n + 1 = 18,931,570 at n = 10⁶: measured 18,673,546, **1.4% under** ✓
- Information-theoretic lower bound log₂(n!) ≈ 18,488,865 at n = 10⁶: we are **1.0% above optimal** ✓
- Selection versus merge at n = 32,000: **471× slower**
- Insertion/merge crossover: **n ≈ 96** (1,699.7 ns vs 1,643.8 ns)
- Linear vs binary search at n = 10⁷: 2,002,740 ns vs 870 ns — **2,302×**; binary search's per-probe cost rises from 2.8 ns to **36.3 ns** as the array outgrows cache

## Grading notes

**3/3 on correctness** means the property tests pass: idempotence, multiset permutation check (not a checksum — a sum-preserving corruption is easy to write by accident), stability on structs, and the injected-allocation-failure path.

**3/3 on performance** means CPU time, min-of-N, load average reported, and both exponents fitted and stated.

**3/3 on explanation** means the README correctly explains why merge sort's fitted exponent is 1.06 rather than 1.00 — n log n is not a power law, and its local log-log slope is 1 + 1/ln n, which averages about 1.06 across n = 10³ to 10⁶ — and names the mechanism behind the `qsort` gap (an un-inlinable indirect call per comparison).

The three most common ways submissions lose points:

1. **"The 1.06 is measurement noise."** It is not; it is the log factor, and it is predictable to two decimal places. This single sentence is the difference between a 2 and a 3 on Explanation.
2. **Verifying the sort with a checksum.** `sum(output) == sum(input)` passes for a sort that duplicates one element and drops another. Use a multiset comparison — sort a copy with `qsort` and `memcmp`, or count occurrences.
3. **Not counting comparisons, or counting them inconsistently.** The comparison count is the *only* machine-independent evidence in the whole lab. A submission with timings but no counts cannot demonstrate that its merge sort is actually a merge sort rather than an accidental O(n²).
