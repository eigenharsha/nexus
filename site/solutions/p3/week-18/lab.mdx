## Reference solution — `LAB-P3-W18`

## The result the lab is built around

Every reference number below: Telco churn, 7,043 rows, 26.54% positive, 75/25 stratified split at `random_state=42` (1,761 test rows), scikit-learn 1.9.0, XGBoost 2.1.4, Apple M3 Pro.

| Model | AUC | Average precision | Brier | **precision@75** |
| --- | --- | --- | --- | --- |
| majority baseline | 0.5000 | 0.2652 | 0.1949 | 0.2652 |
| the ticket's 3-rule heuristic | 0.8031 | 0.5606 | 0.2105 | **0.7200** |
| logistic regression | 0.8466 | 0.6381 | 0.1363 | 0.7733 |
| random forest, 500 trees | 0.8445 | 0.6444 | 0.1362 | — |
| XGBoost, `max_depth=3`, early-stopped | **0.8490** | **0.6560** | 0.1345 | **0.8533** |

And the full `precision@k` curve, because the choice of `k` changes the story:

| k | heuristic | logreg | XGBoost |
| --- | --- | --- | --- |
| 50 | 0.7000 | 0.7600 | **0.8600** |
| **75** | 0.7200 | 0.7733 | **0.8533** |
| 100 | 0.6900 | 0.7600 | 0.8100 |
| 150 | 0.6800 | 0.7200 | 0.7533 |
| 300 | 0.6033 | 0.6833 | 0.6867 |

**The model's advantage is concentrated at the top of the ranking and disappears by k=300.** At the ticket's actual capacity (300 calls a week out of 7,043 customers, which is the top 4.26%, which on 1,761 test rows is 75) the gap is 13.3 points. At k=300 on the test set it is 8.3 points over the heuristic and **0.3 points** over logistic regression. If retention doubled its capacity, most of this project's value would evaporate — and saying that in the one-pager is what makes it a recommendation rather than a result.

## The bootstrap, which is the honest part

3,000 resamples of the test set:

```
precision@75, XGBoost minus heuristic : +0.1210   95% CI [+0.0133, +0.2267]   REAL
precision@75, XGBoost minus logreg    : +0.0598   95% CI [-0.0267, +0.1467]   NOT ESTABLISHED
```

Two claims, and the write-up must make exactly these two and no more. The model beats the rules. The choice of model family is not supported by this data. A submission that leads with "XGBoost improved performance" has stated something its own interval does not support.

## The ceiling

Twelve engineered features — `TotalCharges/tenure` versus `MonthlyCharges`, the price delta and ratio, a count of subscribed services, a "no internet" flag, tenure bins, the `tenure == 0` indicator, charges per service — plus a 12-configuration search over `max_depth` and `min_child_weight`:

```
engineered XGBoost   test AUC 0.8461
engineered logreg    test AUC 0.8461
baseline logreg (RAW features)  test AUC 0.8466
bootstrap AUC improvement over the baseline: -0.0005   95% CI [-0.0073, +0.0065]
```

**Feature engineering moved nothing.** That is the correct result on this dataset and it must be reported as such. The consequence for the write-up is a genuinely useful sentence: "the model is at the ceiling this data supports; further gains need different data — usage logs, support-contact history, competitor pricing — not further modelling."

## The threshold, done from the cost matrix

The ticket gives £90 per offer and £840 per saved customer, and a hard capacity of 300 calls a week. That capacity makes it a **top-k** decision, not a threshold decision, so:

```
expected weekly value = 300 * precision@300 * save_rate * 840  -  300 * 90
```

With `precision@300 = 0.6867` from the model and `0.6033` from the heuristic:

```
model     : value = 300 * 0.6867 * save_rate * 840 - 300 * 90 = 173,048 * save_rate - 27,000
heuristic : value = 300 * 0.6033 * save_rate * 840 - 300 * 90 = 152,032 * save_rate - 27,000
```

| `save_rate` | model | heuristic | model advantage |
| --- | --- | --- | --- |
| 0.10 | −£9,700 | −£11,800 | £2,100 |
| **0.1560** | **£0** | −£3,300 | break-even for the model |
| **0.1776** | +£3,700 | **£0** | break-even for the heuristic |
| 0.20 | £7,600 | £3,400 | £4,200 |
| 0.30 | £24,900 | £18,600 | £6,300 |

The honest headline: **the model is worth about £2,100 more per week than the current list for every 10 percentage points of save rate, and the whole programme is under water below a 15.6% save rate — against 17.8% for the current list.** Nobody has measured the save rate. Naming that as the largest single uncertainty, and proposing the two-week randomised holdout that measures it, is the strongest thing in the one-pager.

<Warning>
A threshold chosen by maximising F1 gives roughly 0.35 here and selects far more than 300 customers. It optimises a quantity that weights the two errors equally when the ticket weights them 840 to 90, and it ignores the capacity constraint entirely. If F1 appears anywhere in a submission's threshold logic, that is a correctness deduction.
</Warning>

## The data-quality trap

`TotalCharges` is stored as a string; `pd.to_numeric(..., errors="coerce")` produces 11 `NaN`. All 11 have `tenure == 0` — brand-new customers who have not been billed. Imputing the median assigns a customer who has spent nothing a lifetime spend of about £1,400.

```python
df["TotalCharges"] = pd.to_numeric(df["TotalCharges"], errors="coerce")
assert (df.loc[df.TotalCharges.isna(), "tenure"] == 0).all()   # check before deciding
df["tenure_is_zero"] = (df["tenure"] == 0).astype(int)
df["TotalCharges"] = df["TotalCharges"].fillna(0.0)
```

Eleven rows out of 7,043 will not move a metric. It is in the lab because **the habit of checking what a missing value means before filling it** is what separates a working data scientist from a notebook, and because it is exactly the mistake `SimpleImputer(strategy="median")` inside a pipeline makes silently.

## Why this solution and not the obvious one

**The obvious solution trains four models, reports AUC for each, declares XGBoost the winner, and stops.** Everything in that sentence is defensible in isolation and the whole is wrong. AUC says the four models are indistinguishable (0.803 / 0.847 / 0.845 / 0.849), so the obvious write-up concludes the project was not worth doing — while `precision@75` says the model finds 13 more real churners per 100 calls than the rules the company uses today. The metric hid the value.

Three more wrong turns:

1. **Early stopping on the test set.** With only 7,043 rows the temptation to skip the three-way split is strong. It inflates every number and it is invisible.
2. **Reporting `feature_importances_`.** Module 2 measured a random ID column taking 81.8% of it. Held-out permutation importance on this dataset gives `Contract +0.0472`, `tenure +0.0226`, `InternetService +0.0163` — a ranking a retention manager can act on and defend.
3. **Writing a one-pager containing the word AUC.** The ticket explicitly asked for it not to. Half the value of this lab is practising the translation, and it is the half that generalises to every job.

## Grading notes

**3/3 on each rubric row:**

- **Correctness (3):** leak-free pipeline passing the shuffled-label test at 0.50 ± 0.03; three-way split; bootstrap intervals on *every* claimed improvement, with the ones crossing zero reported as not established.
- **Code quality (3):** one `Pipeline` object end to end; `mypy --strict` clean; the feature-engineering step is a transformer, not a notebook cell, so the null result is reproducible.
- **Performance (3):** the full fit under 120 s **with a breakdown** — the reference search is 3.3 s for 12 XGBoost configurations, so anything near the budget deserves an explanation.
- **Explanation (3):** the one-pager states the expected weekly value as a function of the unmeasured `save_rate`, names the break-even at 15.6%, and proposes the experiment that would measure it. A single confident number scores a 2; the function plus the experiment scores a 3.

**The three most common ways submissions lose points:**

1. **Comparing on AUC only**, and therefore concluding the modelling was pointless.
2. **Claiming the XGBoost-over-logistic-regression improvement.** The interval is [−0.0267, +0.1467]. It crosses zero.
3. **An unqualified money figure.** "£7,600 a week" without the `save_rate` assumption attached is a number the CFO will hold you to and that you cannot defend.
