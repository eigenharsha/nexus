## Reference solution — `P3-W22-M5`

The hands-on was: build an image similarity search over 50,000 images and report index build time, query latency and recall.

### The self-retrieval evaluation, which is the part people skip

You cannot report recall without ground truth, and hand-labelling is expensive. The cheap, strong signal: **augment a held-out image and check that it retrieves its own original at rank 1.**

```python
"""selfretrieval.py — ground truth for free."""
from __future__ import annotations
import numpy as np, torch, faiss
from torchvision.transforms import v2

PERTURB = v2.Compose([
    v2.RandomResizedCrop(224, scale=(0.8, 1.0), antialias=True),
    v2.RandomHorizontalFlip(p=1.0),
    v2.ColorJitter(brightness=0.15, contrast=0.15),
])

def self_retrieval_at_k(index, encoder, dataset, probe_ids, k=1) -> float:
    """Fraction of perturbed probes that retrieve their own original within top-k."""
    hits = 0
    for i in probe_ids:
        img, _ = dataset[i]
        v = encoder(PERTURB(img).unsqueeze(0).cuda())
        v = torch.nn.functional.normalize(v, dim=1).cpu().numpy().astype("float32")
        _, ids = index.search(v, k)
        hits += int(i in ids[0])
    return hits / len(probe_ids)
```

**Reference result on the healthy system: self-retrieval@1 = 0.947, @10 = 0.991** over 500 probes. That single number is what turns every experiment below from an opinion into a measurement.

### The deliberate breakages

This is part three of the stretch challenge and the most useful table on the page. Each row breaks one thing and reports what the metrics did.

| Breakage | recall@10 vs exact | self-retrieval@1 | Caught? |
| --- | --- | --- | --- |
| Healthy baseline | 0.982 | 0.947 | — |
| **1. No L2 normalization** | 0.982 | **0.611** | **yes, loudly** |
| **2. Index at `Resize(224)`, query at `Resize(256)+CenterCrop(224)`** | 0.980 | **0.734** | **yes** |
| **3. `efSearch=8`** | **0.812** | 0.859 | yes |
| **4. Index with ResNet-18, query with ResNet-34** | 0.004 | 0.002 | **yes, catastrophically** |
| **5. int8 encoder for query, fp32 for index** | 0.979 | **0.931** | **barely — 1.6 points** |

Two findings worth writing up:

- **Breakage 1 is invisible to recall@10 and obvious to self-retrieval.** Recall is measured *against the same broken index*, so a systematically wrong ranking that is consistently wrong still "recalls" its own neighbours. This is the trap: **an ANN recall metric validates the index, not the embeddings.** Only an external ground truth catches an embedding-level bug.
- **Breakage 5 is the dangerous one.** A 1.6-point drop from quantizing one side of the pipeline is within the range a team would shrug at, and it compounds silently across a catalogue. The answer is not a better metric; it is an **encoder fingerprint stored in the index metadata and asserted at query time** — the single check that catches breakages 4 and 5 outright and makes 2 detectable.

```python
# The one automated check that catches the most
import hashlib, json, faiss

def encoder_fingerprint(model, preprocess_version: str) -> str:
    h = hashlib.sha256()
    for p in model.state_dict().values():
        h.update(p.detach().cpu().numpy().tobytes())
    h.update(preprocess_version.encode())
    return h.hexdigest()[:16]

# at build time
faiss.write_index(index, "img.index")
open("img.index.meta.json", "w").write(json.dumps(
    {"fingerprint": fp, "dim": 512, "n": 50_000, "metric": "ip", "normalized": True}))

# at query time, once at startup
meta = json.load(open("img.index.meta.json"))
assert meta["fingerprint"] == encoder_fingerprint(query_encoder, PREPROC_VERSION), \
    "encoder/index mismatch — rebuild the index"
```

## Why this solution and not the obvious one

**Why self-retrieval rather than same-class precision@10.** Same-class precision is easy to compute and measures the wrong thing — with four classes and 12,500 images, a random result gets 25% precision@10 and a merely-adequate embedding gets 90%, so the metric saturates and cannot detect a normalization bug. Self-retrieval is a hard task with a clear correct answer, so it has headroom to fall.

**Why the recall column is reported *and* labelled as insufficient.** recall@10 against exact search is the standard ANN metric and it is genuinely useful for tuning `efSearch`. It just does not test the embeddings. Reporting both and explaining what each one can and cannot see is the actual insight.

**Why the fingerprint includes the preprocessing version.** Breakage 2 — different resize between indexing and querying — is a preprocessing bug, not a weights bug, so a weights-only hash misses it. Concatenating a preprocessing version string is one line and closes the gap.

**Why exact search is the default recommendation under a million vectors.** 2.1 ms at 50k and 42 ms at 1M on four vCPUs, with perfect recall and zero tuning. ANN's failure mode is silently worse results, and taking on a silent failure mode to save 40 ms is a bad trade until you have measured that you need it.

## The two wrong turns worth knowing about

**1. Reporting recall@10 as though it validated the system.** It validates the index against exact search over the same vectors. If the vectors are wrong, both are wrong together and recall is 1.000. This is the single most common mistake in retrieval evaluation, and it carries over unchanged into RAG systems in Week 27.

**2. Tuning `efSearch` upward until results "look right".** Past the knee you pay multiples of latency for fractions of a point, and at `efSearch=512` this index is slower than brute force with worse recall. Plot the curve, pick a point on it, and write down why.

## Grading notes

**3/3 on Correctness** — all three index types built, recall measured against exact search, `efSearch` swept, and the norms asserted to be 1.0.

**3/3 on Performance** — the full export table with p50 *and* p95, the quantization accuracy delta, and the oversubscription measurement.

**3/3 on Explanation** — the breakage table, with the observation that recall@10 cannot see an embedding-level bug, and a defended recommendation for the one CI check.

**The three most common ways submissions lose points**

1. **No external evaluation.** Recall against exact search only. The submission then cannot detect the normalization bug, which is the module's whole war story.
2. **`efSearch` left at the default and reported as "HNSW's performance".** It is a runtime knob with a 17× latency range and an 11-point recall range on this data. Report the curve.
3. **Quantized model benchmarked for latency but not accuracy.** Half the result. 1.64× for an unmeasured accuracy cost is not a finding.
