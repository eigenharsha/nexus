## Reference solution — `P3-W17-M2`

The task: implement both solvers, find the dataset size where gradient descent beats the normal equation, and plot the crossover.

## The answer in one sentence

**On dense data that fits in memory, the crossover is almost never about time — it is about the `8*p^2` bytes of `X^T X`.** If your submission concluded "gradient descent wins above about `p = 500`", you measured the wrong thing; if it concluded "the exact solve wins until you run out of RAM at `p ≈ 40,000`, and separately SGD wins on very large `n` because of statistics not arithmetic", you got it.

## The measurement

```python
# numpy 2.5.2 — Apple M3 Pro, 18 GB, float64, single process
import numpy as np, time
rng = np.random.default_rng(0)

def bench(n, p, reps=2, gdsteps=30):
    X = rng.normal(size=(n, p)); y = X @ np.ones(p) + rng.normal(size=n)
    tg, ts = [], []
    for _ in range(reps):
        t = time.perf_counter(); G = X.T @ X; b = X.T @ y; tg.append(time.perf_counter() - t)
        t = time.perf_counter(); np.linalg.solve(G, b);     ts.append(time.perf_counter() - t)
    th = np.zeros(p); t = time.perf_counter()
    for _ in range(gdsteps):
        th -= 1e-6 * (2 / n) * (X.T @ (X @ th - y))
    return min(tg) * 1000, min(ts) * 1000, (time.perf_counter() - t) / gdsteps * 1000
```

| 20,000 | 10 | 0.2 ms | 0.08 ms | 0.3 ms | 1.12 ms | 0 | 800 B |
| 20,000 | 100 | 3.2 ms | 0.17 ms | 3.4 ms | 1.94 ms | 1 | 80 KB |
| 20,000 | 500 | 68.6 ms | 7.5 ms | 76.1 ms | 6.8 ms | 11 | 2 MB |
| 20,000 | 1,000 | 251.9 ms | 16.1 ms | 268.0 ms | 13.1 ms | 20 | 8 MB |
| 20,000 | 2,000 | 1,077 ms | 182 ms | 1,259 ms | 57.0 ms | 22 | 32 MB |
| 20,000 | 4,000 | — | — | 17,610 ms | — | — | 128 MB |

Read the "GD steps affordable" column: it never exceeds 22. Gradient descent on ill-conditioned data needs hundreds to thousands of steps. **The exact solve wins every one of these cells.**

## Where gradient descent actually wins

Two places, and neither is on this table.

**1. Memory.** `8*p^2` bytes:

| p | `X^T X` |
| --- | --- |
| 1,000 | 8 MB |
| 10,000 | 800 MB |
| 30,000 | 7.2 GB |
| **50,000** | **20 GB** |
| 100,000 | 80 GB |

Somewhere between 20,000 and 40,000 features, on a normal machine, the exact solve stops being an option regardless of how long you are willing to wait. That is the crossover, and it is a cliff, not a curve. Note also that forming `X^T X` costs `n*p^2` multiply-adds, so the time cost hits the same wall from the other side: at `p = 4,000` and `n = 20,000` the measured total is 17.6 s, 14x the `p = 2,000` time for a 2x increase in `p`.

**2. Statistics, on very large `n`.** Measured on 10,000,000 rows x 10 float32 features, true noise floor MSE `0.01`:

| Method | Wall clock | Final MSE |
| --- | --- | --- |
| Normal equation | 0.65 s | 0.009992 |
| Full-batch GD, 5 steps | 0.34 s | 0.009992 |
| Full-batch GD, 30 steps | 2.39 s | 0.009992 |
| SGD, 1 epoch, batch 1024 | 0.98 s | 0.009992 |
| **SGD, 10% of one epoch** | **0.03 s** | 0.009995 |

Peak RSS: 0.56 GB for 400 MB of data. SGD reached the optimum to five decimals after 976 of 9,766 mini-batches — one million rows out of ten million — and was **21.7x faster than the exact solve**.

The correct explanation is Bottou and Bousquet's: the statistical error of an estimate from `n` samples scales as `1/sqrt(n)`, so driving the *optimisation* error far below that is wasted work. This is not "GD is faster than linear algebra". It is "you did not need the extra digits".

## The plot

Log-log axes, `p` on x, milliseconds on y. Two lines: exact-solve total, and SGD wall clock to reach within 1% of the exact solution's test MSE. Then — this is the part most submissions omit — **a third line on a secondary axis showing `8*p^2` in bytes, with a horizontal rule at your machine's RAM.** The intersection of that rule with the memory line is the real crossover, and it should be annotated with the number.

## Why this solution and not the obvious one

**The obvious solution times both methods and reports where the lines cross.** It gives an answer around `p = 500–2,000` depending on the learning rate chosen, and it is meaningless, because the number of GD steps needed is a free parameter the author picked. Anyone can move the crossover anywhere by changing `lr` or `n_iter`.

Two wrong turns worth knowing about:

1. **Timing GD for a fixed number of steps.** A fixed step count is not a comparison — the two methods are not producing the same answer. The only honest protocol is "time to reach a specified accuracy", which forces you to state the accuracy.
2. **Benchmarking on well-conditioned random Gaussian data only.** `rng.normal(size=(n,p))` has a condition number near 1, so GD converges in a handful of steps and looks fantastic. Real design matrices — one-hot columns, correlated features, unstandardised units — have condition numbers of `1e6` upwards, and GD's step count scales with the square root of the condition number. Repeat the benchmark on a matrix with `cond = 1e6` and GD's affordable-step budget stops being anywhere near enough. A submission that only tests on `randn` has measured the easiest possible case.

## Grading notes

**3/3 looks like:** the crossover is identified as memory-bound with the `8*p^2` number written on the plot; the GD comparison is "time to a stated accuracy", not a fixed step count; at least one badly-conditioned design matrix is included and its effect on the step count is reported; peak RSS is measured with `resource.getrusage`, not estimated.

**The three most common ways submissions lose points:**

1. **Reporting a time crossover without the memory analysis.** The time crossover is real but secondary and highly tunable. The memory wall is not tunable.
2. **Only benchmarking on `randn`.** Condition number 1 is the best case for iterative methods and it flatters them by an order of magnitude or more.
3. **`np.linalg.inv(X.T @ X) @ X.T @ y`.** Never invert. It is slower than `solve` and numerically worse: `inv` computes a full inverse you immediately throw away, and squares the condition number for free. Any submission containing `inv` loses a point on correctness even if the numbers happen to match.
