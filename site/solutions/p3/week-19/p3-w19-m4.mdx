## Reference solution — `P3-W19-M4`

The task: five datasets, each with a different hidden leak. Find and quantify each — accuracy before and after the fix.

## The five, with their measured inflations

| # | Leak | Leaky | Correct | Inflation |
| --- | --- | --- | --- | --- |
| 1 | feature selection using every row's label (200 x 10,000 noise) | 0.8650 | 0.5300 | **+33.50 pts** |
| 2 | SMOTE applied before the split | 0.9969 AUC | 0.8445 AUC | **+15.24 AUC pts** |
| 3 | target encoding computed on the full dataset | 0.7282 | 0.5950 | **+13.32 pts** |
| 4 | `StandardScaler` fitted on all data (n=60, p=200) | 0.5667 | 0.5000 | **+6.67 pts** |
| 5 | 20% duplicate rows spanning the split | 0.9375 | 0.9147 | **+2.28 pts** |

And the two that no `Pipeline` prevents, from the module body:

| | Leaky | Correct | Inflation |
| --- | --- | --- | --- |
| target leakage, obvious (`days_to_close`) | 1.0000 | 0.7381 | +26.19 pts |
| target leakage, laundered (`lifetime_tickets`) | 0.9863 | 0.7381 | +24.82 pts |

## The order to find them in

Not the order they are listed. The efficient order is:

**1. Look at the score against a prior.** Dataset 1 at 0.8650 and dataset 2 at 0.9969 AUC are outside any plausible range, and you know that before running a single diagnostic. This step takes zero seconds and narrows the search to two datasets.

**2. Permutation importance on held-out data.** Catches both target leaks immediately. On the obvious one every real feature scores exactly 0.0000 while `days_to_close` scores 0.3858 — a single feature explaining everything is not a modelling result.

**3. The shuffled-label test, wrapping the whole pipeline.** Catches 1, 3 and 4. This is where most of the marks are and where most submissions go wrong; see below.

**4. Structural assertions.** Group overlap between folds; `max(train_time) < min(test_time)`; hashed feature vectors for duplicates. Catches 5, and catches the group and temporal leaks from Module 3.

## The trap in the shuffled-label test

This is the single most important thing on this page, and it catches almost everyone.

```python
# WRONG — this passes, and the leak is still there
X_sel = SelectKBest(f_classif, k=20).fit_transform(X, y)     # selected using the REAL y
shuffled_label_test(model, X_sel, y, cv)                     # then shuffles y
```

By the time the test shuffles the labels, the selection has already happened using the real ones — so the selected features are now uncorrelated with the shuffled target and the model correctly scores chance. **The test passes and the leak is untouched.**

```python
# RIGHT — the shuffle happens before every fitted step
pipe = make_pipeline(SelectKBest(f_classif, k=20), LogisticRegression(max_iter=5000))
shuffled_label_test(pipe, X, y, cv)
```

The rule: **the test must take an unfitted estimator and raw `X`, never a pre-transformed matrix.** Any submission that reports "the shuffled-label test passed" on all five datasets has made this mistake, because it cannot pass on datasets 1, 3 and 4 when applied correctly.

## The one that must be identified as unfixable by structure

The acceptance criterion asks for at least one leak that no structural fix prevents. That is the target leak. A `Pipeline` controls *when* `fit` is called; it has no opinion about *what is in a column*. Every fold is contaminated equally, the cross-validation is technically correct, and the answer is wrong.

The fix for `lifetime_tickets` is not deletion — it is **re-windowing**: `tickets_in_the_90_days_before_the_prediction_date`. Same source data, a window that ends at the prediction moment, and the legitimate signal is retained. Measured, that returns the score to 0.7381, which is the honest number.

## Why the sizes vary by 15x

Worth a paragraph in the write-up, because it is what tells you where to hunt on your own data.

**Inflation scales with how many independent chances the leak had to fit noise.** The scaler leak leaks two numbers per feature estimated from the test rows, so each test row contributes `O(1/n)` — measured at +6.67 points at n=60 and **+0.00 at n=5,000**. The selection leak leaks *which of `p` features correlate with the labels*, and the selector gets `p` chances — measured at +33.50 points when `p/n = 50` and +1.25 when `p/n = 0.25`.

So: wide data (genomics, text features, one-hot explosions, small `n`) should audit selection and encoding first. Tall data with few features should audit feature *availability* first, because its preprocessing leaks are worth nothing and its target leaks are worth everything.

## Why this solution and not the obvious one

**The obvious solution finds the leaks by reading the dataset construction code.** It works and it teaches nothing, because in production nobody hands you the construction code. Run the diagnostics blind, record what each one caught, and only then confirm against the answer key.

Two more wrong turns:

1. **Fixing dataset 4 and concluding leakage is overrated.** The scaler leak is the mildest member of the family and it is the one every textbook uses as the example. A submission that generalises from +0.00 at n=5,000 has drawn exactly the wrong lesson from the smallest number in the table.
2. **Reporting the leaky score without the corrected one.** The deliverable is the *difference*. "Dataset 3 had a target-encoding leak" is an observation; "+13.32 accuracy points, and here is the out-of-fold version" is a finding.

## Grading notes

**3/3 looks like:** all five found, each with a before/after and the mechanism named in one sentence; at least one identified as target leakage that no structural fix prevents, with a re-windowing fix rather than a deletion; the shuffled-label test applied to unfitted pipelines throughout; and a written note on why the inflations differ by an order of magnitude.

**The three most common ways submissions lose points:**

1. **The shuffled-label test applied to a pre-transformed matrix.** It passes, and three leaks go unfound.
2. **Deleting the leaky feature instead of re-windowing it.** Correct but wasteful; the legitimate signal was recoverable and a reviewer will ask.
3. **No prior.** Starting the search with diagnostics rather than with "0.9969 AUC on this problem is impossible" turns a ten-minute job into an afternoon.
