## Reference solution — `P4-W26-M4`

### The task

Raise JSON validity from a measured baseline to above 99% by three methods, and report the
compliance/latency trade-off for each.

### The solution that works

One interface, four backends, telemetry on every call — that structure is what makes the comparison
possible:

```python
from dataclasses import dataclass

@dataclass
class Result:
    value: object | None
    schema_valid: bool
    retries: int
    tokens_in: int
    tokens_out: int
    latency_ms: float
    grounded: float          # fraction of extracted strings found verbatim in the source

def grounded_fraction(obj, source: str) -> float:
    vals = [str(v) for v in flatten(obj) if isinstance(v, (str, int, float))]
    if not vals:
        return 1.0
    return sum(str(v) in source for v in vals) / len(vals)
```

`grounded` is the field that makes this a 3/3 rather than a 2/3, and it is the one nobody adds
until they have been burned.

### Measured numbers this produces

200 held-out invoices, Llama 3.2 3B Instruct:

| Mechanism | Schema-valid | Field F1 | Grounded | p50 | p95 | Prompt tok |
| --- | --- | --- | --- | --- | --- | --- |
| Zero-shot | 58.5% | 0.61 | 0.91 | 620 ms | 1,410 ms | 180 |
| Few-shot + prefill | 81.5% | 0.71 | 0.93 | 790 ms | 1,680 ms | 1,410 |
| + repair (≤2) | 96.5% | 0.74 | 0.93 | 1,200 ms | 3,900 ms | 1,410 |
| Constrained | **100%** | 0.74 | 0.89 | 930 ms | 1,510 ms | 180 |
| Fine-tuned | 99.5% | **0.89** | 0.97 | 640 ms | 1,180 ms | 120 |
| Fine-tuned + constrained | **100%** | **0.90** | 0.97 | 750 ms | 1,290 ms | 120 |

With `reasoning` added as the first schema field, the constrained row moves from F1 0.74 to **0.81**
for 40 extra output tokens.

Note the groundedness column on the constrained row: **0.89, lower than the unconstrained
baseline's 0.91.** Constraining forced values into fields that had no support in the source. That
is the war story arriving as a number, and it is the finding that justifies tracking the metric.

### Why this solution and not the obvious one

**The obvious report has one column: schema-valid.** It shows constrained decoding at 100% and
concludes the problem is solved. Two columns — validity and F1 — show that syntax and semantics are
independent, and a third (groundedness) shows constraining can make one of them *worse*. The report
is the deliverable, and a single-column report cannot support any decision except "did it parse".

**Latency should be reported at p95, not p50.** The repair loop's p50 is 1,200 ms and its p95 is
3,900 ms, because p95 is where the retries live. A p50-only comparison makes the repair loop look
almost competitive with constrained decoding; the p95 column is where the 2.6× difference lives.

### The two wrong turns worth knowing about

**Wrong turn 1: rebuilding the outlines generator per request.** `outlines.generate.json(model,
Schema)` compiles the FSM and indexes the vocabulary — 2.14 s for the nested invoice schema. Called
inside the request handler, every request pays it. Measured p50 goes from 930 ms to 3,070 ms with no
other change. Build generators at startup, keyed by (schema, tokenizer).

**Wrong turn 2: a repair loop with a generic retry message.** "That was invalid, try again"
recovered 61% of failures; feeding Pydantic's actual error text (`total: Input should be a valid
number`) recovered 89%. The model needs to know *what* was wrong, and Pydantic already wrote that
sentence for you.

### Grading notes

**3/3** requires all four mechanisms on the same eval, both validity and F1 reported side by side,
p95 latency, and a paragraph correctly classifying the remaining failures as syntactic or semantic.
Groundedness earns the top mark on Explanation. **The three most common point losses:** reporting
only schema validity and declaring victory; p50-only latency, which hides the repair loop's real
cost; and concluding that constrained decoding "improved quality" when the F1 column says it moved
0.03 and the groundedness column says it moved backwards.
