## Reference solution — `LAB-P4-W26`

### What a finished `standard` submission looks like

```
repo/
├── README.md              # ticket, approach, results table, the honest conclusion
├── MODEL_CARD.md          # base + revision, data, rubric, lift with CIs, REGRESSIONS
├── RESULTS.md             # baseline vs final on the same 100 items, paired bootstrap
├── schema.py  build_dataset.py  train_qlora.py  extract.py  bench.py
├── tests/                 # 13 tests, all green
└── figures/               # funnel, rank sweep, Pareto, concurrency curve, cost curve
```

### The decisions that make it a 3/3

**Eval before dataset, baseline before training.** Everything in `RESULTS.md` is a delta against a
number you measured on day one. A submission whose eval set was built after the fine-tune cannot be
trusted and cannot be fixed retrospectively.

**The schema encodes the failure modes.** `Optional` on everything the world permits to be absent;
a `reasoning` field first; `Field` patterns on formatted fields; at least one cross-field validator
that proves you understand the grammar boundary.

**Every number has a confidence interval, and you say what the eval cannot resolve.** This is the
single highest-signal habit in the whole week.

celebrating.

### Why this solution and not the obvious one

**The obvious submission trains a model and reports that it is better.** The ticket asked two
questions and the second one was "tell us honestly whether we should have just paid for the API".
A submission that answers only the first is incomplete regardless of how good the model is. The
artifact that gets read is `README.md`'s final section: the accuracy gap, the cost position, the
utilisation assumption, and a recommendation.

**On the model card:** the temptation is to report the lift and stop. The card that is actually
useful reports the MMLU drop, the fabrication rate on absent fields, and the document shapes where
the model still fails — because that is what a colleague needs in order to decide whether to use
your adapter.

### The two wrong turns worth knowing about

**Wrong turn 1: building the eval set from the same pool as the training set, after deduplication
but before checking cross-split similarity.** Near-duplicates at 0.94 cosine survive a 0.95
threshold and three epochs is enough to memorise them. Symptom: test F1 above 0.95 and production
behaviour matching the base model. Check the threshold, and eyeball the ten most-similar cross-split
pairs by hand.

**Wrong turn 2 (on `hard`): concluding that self-hosting wins by assuming full utilisation.** The
ticket's workload is invoice intake, which is bursty and low volume. At a realistic 8% utilisation
the honest answer is that the API is roughly five times cheaper, and the only reason to self-host is
the finance constraint in the ticket — which is a *requirement*, not an economic argument. A
submission that states this clearly, with the arithmetic and the accuracy gap that the constraint is
buying, scores higher than one that manufactures a favourable utilisation assumption.

### Grading notes

**A 3/3 across all four rows** is: `hard` complete with the rank sweep, the quantization Pareto plot
and the cost analysis; a pinned, config-driven implementation with the pre-flight checks; a capacity
plan derived from the KV formula and validated against a real vLLM run with the prediction error
reported; and a model card that names the regressions.

**The three most common ways submissions lose points.** First, a results table with no confidence
intervals — at n=100 the CI is roughly ±0.09 and most reported deltas are inside it. Second, a model
card that reports only improvements; the MMLU column and the fabrication rate are what make it a
document rather than an advertisement. Third, answering only the first half of the ticket. The
recommendation is the deliverable; the model is the evidence for it.
