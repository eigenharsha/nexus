## Reference solution — `LAB-P4-W25`

### What a finished `standard` submission looks like

```
repo/
├── README.md                 # the explainer, with your own diagrams
├── MEASUREMENTS.md           # machine specs at the top, every number reproducible
├── bpe.py  model.py  generate.py  measure.py
├── tests/                    # 13 tests, all green
└── figures/                  # merge table, attention grid, loss curve, prefill-decode timeline
```

### The decisions that make it a 3/3

**One config object, no magic numbers.** Every dimension flows from a `Config` dataclass with
validation in `__post_init__` — `d_model % n_heads == 0`, `d_ff % 8 == 0`, `block_size > 0`. When a
reviewer asks "what happens at `n_heads=7`", the answer should be an assertion with a helpful
message, not a stride error 40 lines deeper.

**Verification against a reference, not against nothing.** Three comparisons carry the whole
submission: attention against `nn.MultiheadAttention` (4.8e-7), analytic parameter count against
the instantiated model (exact), and KV-cache bytes against the formula (exact). If any of the three
is approximate, something is wrong and you should find out what.

**The perturbation test.** Six lines, catches every causal-mask bug. It belongs in the repo before
the training script does.

### Measured numbers a correct solution produces

| Deliverable | Expected value |
| --- | --- |
| BPE bytes/token at vocab 1,024, tinyshakespeare held-out | 3.11 |
| `gpt2` bytes/token on the same text | 4.02 |
| Attention max abs diff vs reference | &lt; 1e-5 (typically 4.8e-7) |
| Parameter count, default config | 10,750,080 exactly |
| Val loss at 5,000 steps | 1.48 ± 0.03 |
| KV cache speedup at 256 output tokens | 6–7× |
| Roofline achieved (your own model, own machine) | 55–95% depending on framework |

If your val loss is below 1.20, your causal mask leaks. If it is above 1.70, check gradient
clipping and that you are decaying only matrices.

### Why this solution and not the obvious one

**The obvious repo trains a model and prints samples.** It demonstrates that the code ran. The
ticket asked for something the team can *reason against*, which means the test suite is the primary
artifact and the model is secondary. A submission with a mediocre model and a test suite that
catches an inverted mask is worth more than a good model with no tests, and it is graded that way.

**On the explainer:** the temptation is to write it after everything works, describing the clean
final state. Do not. The version that lands keeps the too-good loss curve from when the mask
leaked, names the bug, and shows the test that would have caught it. That is house style and it is
also simply the more useful document.

### The two wrong turns worth knowing about

**Wrong turn 1: training before testing.** Every hour spent training an unverified model is an hour
you may have to repeat. The order that works is: BPE round-trip → attention reference match →
causality perturbation → parameter count → *then* train. Three of those four take under a second to
run.

**Wrong turn 2 (on `hard`): claiming FlashAttention without proving it.** `F.scaled_dot_product_attention`
silently falls back to the math backend on an unsupported dtype, head dimension or mask shape, and
the fallback materialises the `(B,H,T,T)` matrix — which is exactly what you were trying to avoid.
Prove it with `torch.cuda.max_memory_allocated` scaling sub-quadratically in `T`, or with an
explicit `sdp_kernel` context manager that raises when the flash backend is unavailable.

### Grading notes

**A 3/3 across all four rows** is: `hard` track complete including the 16,384-context run *with the
baseline failure demonstrated*; a config-driven implementation with diagnostic assertions; the
roofline percentage computed and the gap explained; and an explainer that teaches the material with
your own diagrams and keeps at least one mistake visible.

**The three most common ways submissions lose points.** First, measurements with no machine
specification — "94 tokens/sec" is not a number without a GPU, dtype, batch size and context
length. Second, the `hard` track's constraint asserted rather than demonstrated: if you cannot show
the `standard` implementation failing at 16,384, you have not shown that yours succeeds at anything
meaningful. Third, an explainer that is a README — a list of files and a usage example is
documentation, not an explainer, and it earns 1/3 on the Explanation row.
