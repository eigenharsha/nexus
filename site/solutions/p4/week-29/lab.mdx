## Reference solution — `LAB-P4-W29`

### Shape of the repository

```
week-29-agent/
├── README.md              # leads with the benchmark table, not with "an AI agent that..."
├── SECURITY.md            # the trust boundary. The document that makes this credible.
├── agent/
│   ├── loop.py            # Agent, Budget, Result — four stop reasons
│   ├── registry.py        # Tool, Registry — Pydantic schemas, feedback errors, caps
│   ├── memory.py          # window + rolling summary + token budget
│   └── prompts/           # versioned. system_v3.txt, with a CHANGELOG.
├── mcp_server/
│   ├── server.py          # order_lookup, search_orders (read-only role)
│   ├── safe_terminal.py   # the sandbox, v3
│   └── audit.py           # append-only JSONL
├── bench/
│   ├── tasks.yaml         # 30 tasks + acceptance criteria, committed BEFORE first run
│   ├── selection.yaml     # 120 labelled prompts incl. 20 "none of these"
│   └── results.md         # generated by `make bench`
└── tests/                 # 31 tests, mocked model, <10 s
```

Two structural decisions that reviewers notice. **Prompts are files, versioned, with a changelog** —
because in Week 32 you will need to attribute a quality change to a prompt version, and a prompt
embedded in a Python string cannot be attributed. **`bench/tasks.yaml` is committed before the first
run** and the commit date proves it, which is the only defence against unconsciously grading yourself
generously.

### The benchmark table that belongs at the top of your README

| | Agent, 30 tools | Agent, tuned surface | Chain for the top 2 task types |
| --- | --- | --- | --- |
| Success (30 tasks) | 19/30 | 22/30 | 26/30 |
| Mean steps | 7.1 | 6.2 | 3.0 |
| Derived per-step | 93.7% | 95.1% | 97.4% |
| Cost per run | $0.243 | $0.176 | $0.031 |
| **Cost per successful task** | **$0.384** | **$0.239** | **$0.036** |
| p95 latency | 88 s | 71 s | 19 s |

The last column is the point of the whole lab. The strongest submissions conclude that the agent
was the wrong shape for two-thirds of the queue, and say so. That conclusion is worth more marks
than a better agent.

### The five things that separate a 3/3 from a 2/3

1. **Four stop reasons, all observed.** Not just implemented — present in `results.md` with counts. A `stop_reason` histogram is the artifact.
2. **The database refuses the write, not your code.** A test that runs `UPDATE orders ...` through the MCP server's connection and asserts on Postgres's `permission denied for table orders`. Defence in code is a defence; defence in the database is a control.
3. **A safety-property test.** Read-only question, assert no write tool appears in the trajectory. Nine lines, highest value in the suite.
4. **An attack that succeeded.** Your `SECURITY.md` must contain at least one attack that worked against your own v1 or v2, with the fix. Every clean-sheet report is either dishonest or incurious.
5. **Cost per successful task, everywhere.** Never cost per call. Every table, every claim.

## Why this solution and not the obvious one

**Obvious:** more tools makes a more capable assistant. It makes a less accurate one. Going from 12
to 30 tools cost us 8 points of selection accuracy and 1,900 schema tokens per step. Capability and
reliability trade against each other, and the ticket asked for something that helps, not something
that can do everything.

**Obvious:** put the sandbox behind a "are you sure?" prompt and call that human-in-the-loop. A
confirmation that does not show the *resolved arguments* is theatre — the attack lives in the
argument, not in the verb. `Run: grep -n ERROR /work/app.log — approve?` is a control.
`The agent wants to run a command — approve?` is not.

**Obvious:** benchmark on tasks you wrote while building the tools. They will be the tasks your tools
happen to fit. Sample from the real queue, before you design the surface, and accept the ones you
cannot serve as failures rather than editing them out.

## Grading notes

**Automatic caps.** No benchmark table → maximum 60. No `SECURITY.md` → maximum 60. Any claim in the
README without a number → maximum 75. `shell=True` anywhere in the repository → the Security row is 0
and the lab does not pass.

**A 3/3 submission** reads like an engineering report: the ticket, what you decided to build and why
(including where you chose *not* to use an agent), the measurement, the security boundary, and an
honest section on what you would fix next. It is roughly two pages of README and it will take you
longer than the code.

**The three most common losses:** benchmark written after the fact; a security document that lists
controls but never states the blast radius; and a `hard` track submission that reports 30-tool
accuracy without the confusion matrix that justifies the fix.
