## Reference solution — `P4-W29-M4`

### The three versions, and why you must build all three

The pedagogical point of the lab is the *sequence*. If you build v3 first you will have a secure
server and no understanding of which control does what.

- **v1** — program allow-list, `subprocess.run(cmd, shell=True)`. Attacks 1, 2, 3, 5, 8 succeed. Seeing `ls; cat /etc/passwd` return a password file through your own "allow-listed" tool is the moment the module lands.
- **v2** — `shlex.split`, argv, resolve-then-contain, timeout, output cap. Attacks 1, 2, 3, 6, 7, 9, 11 blocked. Attacks 4 (symlink), 5 (`/proc/self/environ`), 8 (`grep -f`), 10 (`PATH` poisoning) still succeed.
- **v3** — bubblewrap isolation, `--clearenv`, absolute `PATH`, per-program flag allow-list. Everything blocked except the two accepted risks.

The four attacks that survive v2 are the interesting ones because they all share a shape: **the
control checked the input the model gave, and the attack changed something the control was not
looking at** — the target of a symlink, the process environment, the file a flag reads, the
directory a program name resolves from. That is the generalizable lesson, and it is the sentence to
put in your `SECURITY.md`.

### The two accepted risks, written honestly

> **AR-1 — timing side channel.** `grep -c` on a large file leaks approximate content through
> response time. Mitigation would require constant-time execution, which is not achievable for a
> shell tool. Accepted: the sandbox contains only project files already readable by the requesting
> user, so the channel leaks nothing the requester could not read directly.
>
> **AR-2 — denial of wallet.** The server caps a single call at 64 KB and 5 s, but cannot prevent a
> client from issuing 200 calls. Mitigation lives in the agent's per-run dollar budget (Module 1),
> not in the server. Accepted, with the control named and its owner recorded.

A report with zero accepted risks is a report that stopped when the author ran out of ideas. Two
honest entries score higher than a clean sheet.

### The audit query that closes the loop

```sql
-- "What did the sandbox do for this user during the incident window?"
SELECT ts, id, argv, exit, bytes
FROM   sandbox_audit
WHERE  user_id = $1 AND ts BETWEEN $2 AND $3
ORDER  BY ts;
```

If you cannot run that query, your controls are unverifiable in the only moment they matter. Ship
the audit log before you ship the second tool.

## Why this solution and not the obvious one

**Obvious:** block dangerous strings with a deny-list (`rm`, `curl`, `sudo`, `;`). Deny-lists lose.
Ours was defeated in eleven minutes by `cat` plus a symlink — no listed string appeared. Allow-list
the small set you need and reject everything else, including flags.

**Obvious:** run as a less-privileged user and call it sandboxed. Necessary, not sufficient. A
non-root user still reads `/etc/passwd`, still reaches the network, still sees the environment. The
namespace isolation is doing the work; the uid is a backstop.

**Obvious:** ask the model not to run dangerous commands. This is not a control. Attack 13 is the
demonstration: the model complied with a hostile instruction from a file, and only the *server*
stopped the damage. Prompts are not a security boundary. Write that sentence in your README.

## The two wrong turns worth knowing about

1. **Checking the path before resolving it.** `if ".." in rel: raise` looks correct and blocks nothing that matters. `resolve()` then `is_relative_to(root)` is the whole defence, and the symlink test is the one that proves you got it right.
2. **Allow-listing programs but not flags.** We shipped `grep` with no flag restriction and `grep -f /etc/shadow x` read a file outside the sandbox through an allow-listed program. Every flag that names a file, changes lifetime, or shells out is an execution surface.

## Grading notes

**3/3 on Security** requires: allow-lists at both program and flag level; resolve-then-contain with a
symlink test; namespace or container isolation; `--clearenv`; a timeout and an output cap; an
append-only audit log with a call id echoed to the model; and 15 documented attacks with at least
one that succeeded against an earlier version.

**Anything below 2 on Security fails the lab regardless of total score.** This is the one row where
a good average does not save you, because the artifact you are producing claims safety.

**Common losses:**
- A red-team report where every attack was blocked. Not credible; ask what you did not think of.
- No audit log, or an audit log without arguments and user identity.
- `SECURITY.md` that lists controls but never states what an attacker gets if they win. The blast radius is the document's purpose.
