## Reference solution — `LAB-P4-W27`

### What a finished `standard` submission looks like

```
repo/
├── README.md                 # how to run it
├── RETRIEVAL.md              # THE deliverable: quality per doc type, failure modes named
├── docker-compose.yml
├── ingest.py chunk.py embed.py index.py retrieve.py evaluate.py
├── data/eval/eval_100.json   # gold as (doc_id, char_start, char_end) + corpus_hash
├── tests/                    # 13 tests, all green
└── figures/                  # scorecard, chunk sweep, model comparison, recall-vs-QPS
```

### The decisions that make it a 3/3

**Eval set first, frozen, versioned with the corpus hash.** Everything else is a delta against it.
A submission whose eval set was built after the pipeline cannot be trusted and cannot be repaired
retrospectively.

**Ingestion that reports on itself.** The scorecard is not documentation, it is a CI assertion:
zero-text-document fraction under 2%, thin-parse fraction under 5%, with the offending paths in the
message.

**Every delta has a paired confidence interval, and non-significant rows say so.**

### Why this solution and not the obvious one

**The obvious submission builds the pipeline and reports one number.** The ticket asked how good it
is *per document type, with the failure modes named*, and it explicitly said that "it works for
manuals and not contracts" would be a useful answer. A submission that reports 0.88 aggregate and
nothing else has not answered the question that was asked, regardless of how good 0.88 is.

**On `RETRIEVAL.md`:** the section headed "What this system does badly" is the one that gets read
twice. Name the document types with low recall, the exact-identifier query class that scores 0.40
for every dense model, and the filter selectivities where recall collapses. Those are not
admissions of failure — they are the scope for Week 28, and stating them is what makes the rest of
the report credible.

### The two wrong turns worth knowing about

**Wrong turn 1: building the index before it is needed.** At 47,300 chunks, exact search is 3.6 ms
and has no recall to monitor. Teams add HNSW immediately, then spend an afternoon debugging why
their index is not being used (operator-class mismatch) for a latency saving that does not matter
against a 900 ms generation step. Add the index at the point where brute force stops being fast
enough, and measure its recall when you do.

**Wrong turn 2 (on `hard`): reporting 10M-scale numbers without showing the failure first.** The
constraint is that the `standard` configuration cannot hold recall and latency at 10M vectors in
32 GB. If your report shows only your working solution, you have demonstrated that something works
without demonstrating that the problem was real. Include the p95 cliff — 1.7 ms to 340 ms as the
index outgrows `shared_buffers` — because that 200× discontinuity is the most instructive
measurement in the whole lab.

### Grading notes

**A 3/3 across all four rows** is: `hard` complete with the 10M index inside both budgets and
filtered recall ≥ 0.95 proven across the twenty-cell benchmark; idempotent ingestion with
per-document error isolation and deterministic chunk IDs; an operating point chosen against a named
binding constraint; and a `RETRIEVAL.md` that answers the ticket's actual question with per-type
numbers and a named failure list.

**The three most common ways submissions lose points.** First, an eval set built after the system or
never reviewed — this invalidates every other number in the report, so it is the most expensive
mistake available. Second, no filtered-recall measurement, which means the single most dangerous
production failure in this week is undetected. Third, a `RETRIEVAL.md` that reports only aggregate
quality; the per-document-type breakdown is what the ticket asked for and it is what makes the
document useful to anyone other than the author.
