## Reference solution — `P4-W30-M2`

### Building the 120-prompt benchmark properly

The experiment is worth more than the registry code, and it is where submissions go wrong.

**Write prompts from user language, not tool names.** If your prompt is "search the orders" and your
tool is `search_orders`, you are measuring string matching. Ours came from real support tickets:
*"can you find the thing Asha ordered last month, she thinks it was a router"*. Twenty of the 120
deliberately do not name any entity your tools handle, and the correct label is "none of these" —
if your harness has no such label, you cannot measure the failure mode where the model invents a
tool call for a task it should have declined.

**Three runs, report the spread.** Single-run differences under about 3 points are noise on 120
prompts. Ours varied ±1.7 points across three runs; a "4-point improvement" from one run each is not
a result.

```python
# bench/selection.py — the core of it
from collections import Counter
def evaluate(prompts, tools) -> dict:
    conf = Counter()
    for p in prompts:
        r = client.messages.create(model="claude-opus-5", max_tokens=1000,
                                   tools=tools, messages=[{"role":"user","content":p.text}])
        calls = [b for b in r.content if b.type == "tool_use"]
        got = calls[0].name if calls else "NONE"
        conf[(p.label, got)] += 1
    correct = sum(v for (want, got), v in conf.items() if want == got)
    return {"accuracy": correct / len(prompts), "confusion": conf}
```

The `confusion` counter is the deliverable. Accuracy tells you there is a problem; the confusion
matrix tells you it is three pairs of tools, which turns a research project into an afternoon.

## Why this solution and not the obvious one

**Obvious:** raise the model's effort or switch to a bigger model. On our set this bought 1.9 points
at 30 tools and roughly doubled cost. Rewriting six descriptions bought 8 points for free. Always
exhaust the text before you spend on the model.

**Obvious:** give the model all 30 tools and a better system prompt telling it to choose carefully.
Measured: +0.8 points, inside noise. The system prompt cannot disambiguate two tools whose
descriptions do not distinguish them — the information is not there to reason from.

**Obvious:** collapse everything into one `query(action, params)` tool. This does fix selection —
there is only one tool — but it moves the problem into an untyped `params` blob, so argument
validity collapses instead. We measured 34% malformed-argument rate on a collapsed 30-operation
tool versus 4% across 30 typed tools. Collapse *near-neighbours*, not everything.

## The two wrong turns worth knowing about

1. **Measuring on the happy path only.** Our first benchmark had no "should not call any tool" cases. It reported 94% at 30 tools. Adding 20 such cases dropped it to 81.7% — the model was inventing tool calls for out-of-scope questions and we had built a harness that could not see it.
2. **Tool order.** We shuffled the tool list between runs to "avoid position bias" and destroyed the prompt cache, which quadrupled the benchmark's cost and hid a real ordering effect. Sort deterministically; if you want to test position sensitivity, do it as a deliberate separate experiment.

## Grading notes

**3/3 on Correctness:** the registry returns readable feedback for unknown tool, invalid arguments,
tool exception and oversized output, and never raises out of `call()`.

**3/3 on Performance:** the before/after table has three tool-surface sizes, a spread across runs,
schema-token counts, and dollars per run.

**Common losses:**
- No confusion matrix. Accuracy alone is not a diagnosis, and the fix cannot be justified.
- Prompts written from tool names. The result is inflated and the reviewer will spot it immediately.
- Non-idempotent tools that auto-retry. This is an automatic point off on Security in the lab rubric, because it is the double-charge bug.
