## Reference solution — `P4-W30-M5`

### The suite that matters, in order of value

Not all tests are worth the same. Ours, ranked by how often each has caught a real regression over
four months:

| Rank | Test kind | Caught | Example |
| --- | --- | --- | --- |
| 1 | Safety property | 6 regressions | "no destructive tool for a read-only question" — caught two prompt edits and one tool-registry change |
| 2 | Scripted retry (`FunctionModel`) | 4 | a validator rewrite that made the retry message unactionable, so the model repeated the same error |
| 3 | Replay cassette | 3 | a framework bump that changed `None` tool-result serialization |
| 4 | Trajectory assertion | 2 | the agent answering without calling the log tool at all |
| 5 | `TestModel` wiring | 1 | a tool that failed to register after a refactor |

Write them in that order. The safety-property test is nine lines and has paid for the whole suite.

```python
# conftest.py — the two lines that make the rest possible
from pydantic_ai import models
models.ALLOW_MODEL_REQUESTS = False
```

## Why this solution and not the obvious one

**Obvious:** test against the real model with a low temperature "for realism". This is an
integration test wearing a unit test's clothes. It is slow, costs money, and — the part that kills
it — it cannot provoke the failures you most need to test. You cannot ask a real model to reliably
return malformed output on demand. `FunctionModel` can.

**Obvious:** assert on the final answer's text. Text assertions on model output are either too
strict (exact match fails on rewording) or too loose (substring match passes on a wrong answer
containing the right word). Assert on the *typed output object's fields* and on the *trajectory*.
Both are stable under rewording and sensitive to real regressions.

**Obvious:** skip the from-scratch loop and start with the framework. You would then have no model
of what `output_type` does, and the first time `final_result` competes with your tools for
selection you would have nowhere to start. `capture_run_messages()` is only illuminating if you know
what you expected to see.

## The two wrong turns worth knowing about

1. **A `ModelRetry` message that describes the problem but not the fix.** Our first version said `"evidence lines not found in logs"`. The model retried with *different invented* lines, three times, then failed. Rewritten to say what to do — quote verbatim from the tool output, or lower your confidence and say the evidence is indirect — it succeeded on the first retry in 84% of cases. The retry message is a prompt; write it like one.
2. **Cassettes with no model version in the filename.** After moving models, twelve replay tests were green and testing nothing but history. Name them `inc_10231_disk_full__opus-5__2026-08-20.json` and treat a re-record as a reviewable diff.

## Grading notes

**3/3 on Code quality** requires injected dependencies throughout (no module-level clients reachable
from a tool), `ALLOW_MODEL_REQUESTS = False` in `conftest.py`, and at least one safety-property test.

**3/3 on Explanation** requires a written answer to "what did adopting this framework cost you", with
the token and latency overhead measured rather than assumed.

**Common losses:**
- A suite that is fast because it tests nothing — `TestModel` only, no scripted failures. `TestModel` proves wiring; it does not prove behaviour.
- Replay cassettes presented as protection against model regression. They are the opposite by design: they freeze model behaviour. Say so, and pair them with a scheduled live eval.
- No measurement of the retry policy's cost. "It improved reliability" without the +7% token figure is exactly the unmeasured claim this course rejects.
