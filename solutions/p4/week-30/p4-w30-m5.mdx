## Reference solution — `P4-W30-M5`

### The blast-radius table is the deliverable

Six columns, one row per action kind, and two rules that decide the grade:

- **"What stops it" must name a mechanism in code.** A hard `max_replicas` in the tool is a control. "The system prompt says to be careful" is not; write "nothing" in that cell and see how it reads.
- **"What detects it" must name an alert that already exists.** If nothing detects it, the action cannot be at auto level, whatever its blast radius.

And the table must include the rows for what you deliberately excluded. Ours has `rollback_deploy`
(suggest only — a code rollback past a migration is a new untested state, not a previous one) and
`rotate_credential` (not in the system at all). A table that only covers what you built is a
description; one that names the exclusions is an argument.

### The rollout, with gates set in advance

| Phase | Gate to advance | Our result |
| --- | --- | --- |
| Shadow, 4 weeks | Agreement above 70%, zero harmful proposals | 1,240 proposals, 71% agreement, 3 harmful (all `scale_deployment` with absurd targets — which produced the hard ceiling) |
| Suggest, 6 weeks | Suggestion used in more than 60% of incidents | 68%; MTTR 41 → 33 min |
| Approve, 8 weeks | Approval rate above 90% per action kind, at least 50 instances | 890 proposals, 94% approved; 52 of 53 declines became eval cases |
| Auto, per kind | Rollback armed and tested weekly | 3 of 11 kinds; MTTR 26 min |

**The biggest win was at suggest level.** 41 to 33 minutes, from the agent doing the reading.
Autonomy over actions bought a further 7 minutes and carried almost all of the risk. If a submission
argues for autonomy without noticing this, it has missed the module.

## Why this solution and not the obvious one

**Obvious:** one MCP server with all the tools. Splitting read and write into separate servers with
separate credentials is what makes a prompt injection in a log line harmless — the context that sees
untrusted text cannot reach a write verb. This is Week 29 M4's least-privilege argument made
structural, and it costs nothing.

**Obvious:** ask for autonomy in the design review. You will not get it, and you will burn the
credibility you need later. Ask for shadow mode: it is unarguable, costs nothing, and produces the
data every subsequent conversation requires.

**Obvious:** dense retrieval is enough for runbooks. It is not — 0.68 recall@5 against 0.91 for
hybrid plus re-rank. Runbooks are full of exact service names and error strings, which is precisely
what BM25 is good at and embeddings smear.

## The two wrong turns worth knowing about

1. **We classified `clear_cache` as harmless.** The person who owned that cache pointed out that clearing it during a traffic peak causes a thundering herd against an already-saturated database. The review by the system's actual owner is the exercise, not a formality.
2. **Nobody owned the prompts.** The first version of this system was switched off after five weeks — not because it was wrong, but because when it *was* wrong nobody could fix it. Ownership by the on-call rota, with a pull-request flow, is the change that made the second version survive.

## Grading notes

**3/3 on Design** requires: autonomy level per node with justification; the six-column blast-radius
table with code-named controls; the never-automate list; numeric rollout gates set before launch;
and section 9 — who owns the prompts, who is paged, how a human says "that was wrong", and what it
costs per month including engineer time.

**Common losses:** a blast-radius table where the controls are prompt instructions; a rollout plan
with no numbers; and — the most common — a design document with no operations section, which is the
section that decides whether the system is still running in six months.
