## Reference solution — `P4-W31-M4`

### Report compliance and consequence in separate columns

This is the whole submission. Ours, 15 attacks, 10 trials each:

| Configuration | Complied | Catastrophic |
| --- | --- | --- |
| No defence | 12/15 | 9/15 |
| + delimiters and a data-not-instruction rule | 5/15 | 4/15 |
| + spotlighting | 4/15 | 3/15 |
| + injection classifier | 3/15 | 2/15 |
| + **write tools scoped out of the untrusted context** | 3/15 | **0/15** |

The last row changed nothing about compliance — the model still followed injected instructions one
time in five — and took harmful effect to zero. A report that shows only one column has missed the
module. Label every mitigation: does it reduce probability, or consequence? If none of yours reduces
consequence, the design is unfinished.

### The dual-LLM boundary, and its honest cost

```python
class TicketFacts(BaseModel):
    order_reference: str | None = Field(default=None, pattern=r"^ORD-\d{6}$")
    reported_problem: Literal["not_delivered", "damaged", "wrong_item", "other"]
    customer_sentiment: Literal["calm", "frustrated", "angry"]
    # No free-text field. There is nowhere for an instruction to ride.
```

The privileged model never sees the ticket, only this object. 0 of 15 attacks complied — and **29%
of tasks became impossible**, because some genuinely need the nuance in the free text. Our
resolution: dual-LLM on paths that touch write tools, single agent with text defences on read-only
paths where the worst outcome is a peculiar answer. Privilege separation applied where privilege
exists.

A submission that presents dual-LLM without the 29% is not being honest about the trade.

### Reference numbers

| | Value |
| --- | --- |
| Injection classifier | 85.5% recall, 1.2% FPR on 2,000 benign documents |
| Markdown-image exfiltration | 100% success wherever images auto-load |
| Egress-capable tools discovered in audit | 4 of 11, none previously recognised as such |
| Delimiter escape (`</untrusted>` in content) | Works until you escape it |

## Why this solution and not the obvious one

**Obvious:** a second model checks the first model's output for signs of manipulation. It reads the
same untrusted text and can be instructed by it; it runs *after* the tool call that did the damage;
and its recall is unmeasured until you measure it. Useful as detection, never as the safety argument.

**Obvious:** better delimiters and a stronger system instruction. Worth 80% → 33% compliance, which
is a large improvement and is not a boundary. Against an adversary with unlimited retries, a 33%
per-attempt rate is a certainty.

**Obvious:** block the attack. You cannot. Plan for it succeeding and make that survivable — that is
the only framing with a clean argument behind it.

## The two wrong turns worth knowing about

1. **Not escaping the closing delimiter.** An attacker writes `</untrusted>` in their ticket and everything after it appears trusted. This is Week 10's XML injection and it is the first thing a red teamer tries.
2. **Auditing tools by what they do rather than where they can reach.** Four of eleven of our tools could carry data outside the network through a free-text argument. None had been thought of as egress. Inventory by *reach*, not by verb.

## Grading notes

**3/3 on Security:** fifteen attacks across at least eight categories, ten trials each, compliance and
consequence reported separately, every mitigation labelled, an attack tree with partial and accepted
leaves, and an egress inventory.

**Common losses:** fifteen variants of one attack; a mitigation list that is entirely filters; no
markdown-rendering check (this is nearly always an open channel); and an attack tree where every leaf
is mitigated, which means the author stopped when they ran out of ideas rather than out of attacks.

**The sentence a 3/3 submission contains:** "compliance stayed at 20% and harm went to zero, because
we removed the capability rather than the temptation."
