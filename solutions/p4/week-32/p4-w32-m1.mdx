## Reference solution — `P4-W32-M1`

### Design the state first, and here is the checklist

Most submissions build nodes and grow the state as they go. That produces a state you cannot debug,
because the fields exist for the convenience of whichever node added them. Do it the other way:

1. **List every decision the system makes.** Each becomes a field. Ours: `severity`, `hypothesis`, `confidence`, `remediation`, `approved_by`.
2. **List everything that accumulates.** Each needs a reducer and a comment saying which. Ours: `evidence` (merge with de-duplication), `node_trail` (plain append).
3. **List the control variables.** `attempts`, `tokens_used`, `usd_spent`, `halt_reason`, `budgets.started_at`. Every one must be in the state or it will not survive resume.
4. **Ask: could a human read this JSON at 3 a.m. and know what happened?** If not, something is missing or something is raw model prose that should have been an extracted field.

### The reducer that is actually correct

```python
def merge_evidence(left: list[Evidence], right: list[Evidence]) -> list[Evidence]:
    seen = {(e.source, e.query) for e in left}
    return left + [e for e in right if (e.source, e.query) not in seen]
```

Plain `operator.add` passes every test you will write on the happy path and fails silently the first
time a node is retried or resumed. **Reducers are where idempotency lives in a graph** — that is the
sentence that connects this module to Module 3, and it is the thing most submissions miss.

## Why this solution and not the obvious one

**Obvious:** one node containing the whole ReAct loop. That is a from-scratch agent with extra
imports — no per-decision checkpoints, no routing you can see, no per-node telemetry. The line to
draw: nodes are decisions the *system* makes; tools are actions the *model* chooses.

**Obvious:** a node per tool. This hard-codes tool selection into edges and throws away the one
thing the model is genuinely good at. Six to ten nodes for a real workflow, with a tool-using node
where free choice is appropriate.

**Obvious:** put the model call in the router so routing can be "smart". Routers must be pure
functions of state — otherwise routing is non-deterministic on resume, untestable without a model,
and unreproducible from a checkpoint. If a routing decision needs judgement, make it a node that
writes a decision field, then route on that field.

## The two wrong turns worth knowing about

1. **The counter in a closure.** Compiled once, served many concurrent runs, shared a variable. Some runs terminated after one attempt, one ran to `recursion_limit`. One line to fix, and the general rule is: anything that shapes the run lives in the state.
2. **A hand-maintained architecture diagram.** It was wrong within three weeks. Generate it with `draw_mermaid()`, commit the output, regenerate in CI, and fail on diff — then an architecture change shows up in code review.

## Grading notes

**3/3 on Code quality:** every accumulating field has an explicit reducer with a comment; the graph
diagram is generated and snapshot-tested; routers have `Literal` return types.

**3/3 on Explanation:** a written justification of the node granularity — why these six and not
three or twelve.

**Common losses:** plain `add` on a field that a retried node can write twice; control variables
outside the state; and a state carrying full message history, which is a 13× checkpoint size penalty
and shows up in Module 3's storage bill.
