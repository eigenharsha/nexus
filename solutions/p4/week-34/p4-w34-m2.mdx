## Reference solution — `P4-W34-M2`

### The loop only closes if a person is in it

The tooling in this module is a Docker Compose file and about forty lines of code. The reason teams
still fail to close the loop is that candidate eval cases accumulate with nobody reviewing them.

Our fix was not technical: a **30-minute weekly review owned by the on-call rota**, and an
**"unreviewed candidate cases" tile** on the dashboard next to the eval score, treated like an
unattended alert queue — above 20, someone is paged. Within a month the suite grew by 47 cases and
the online score moved 78% → 88%. The tooling had been right for two months.

If your submission has a promotion job and no named reviewer with a recurring slot, it will not work,
and the write-up should say so honestly rather than describing the pipeline as complete.

### Reference numbers

| | Value |
| --- | --- |
| Failure → candidate eval case | 9 days → 4 minutes |
| Suite growth over 8 weeks | 120 → 167 cases (47 promoted, 39 accepted) |
| Online judged score | 78% → 88% |
| Offline/online gap | 13 points → 4 points |
| Prompt rollback | 42 s (label change) vs 14 min (deploy) |
| Online scoring split | mechanical on 100% ($0), judge on 5% ($3.78/day at platform volume) |

### The eight-week table, and the row people misread

The offline score **falls** in two of the eight weeks, each time because fresh production failures
entered the suite. A team watching only the offline number would read that as a regression and
possibly revert a good change. Watch the **gap**, and warn people about this effect before it
happens rather than after.

## Why this solution and not the obvious one

**Obvious:** let the promotion job fill in `expected_output` automatically so no human is needed. We
tested it: a proposed expected output cut review from 90 s to 35 s per case, and humans accepted a
*wrong* proposal 9% of the time. Whether that is acceptable is a real question with a real answer for
your domain — but silently skipping the human is not.

**Obvious:** hosted, because self-hosting is work. Decide on data first: traces contain customer
text. For us, a data-residency commitment settled it before cost was considered — and cost was close
to a wash at 1.9 M observations a month either way.

**Obvious:** keep prompts in the repository because that is where code lives. The rollback speed
(42 s versus 14 minutes) is the argument, and the counter-argument — that the prompt becomes a
runtime dependency — is answered by a local fallback and a 60-second cache, which makes frozen
prompts the failure mode.

## The two wrong turns worth knowing about

1. **No environment tags on the first month of traces.** Production, staging and eval runs were indistinguishable, so a month of historical data could not be used for any comparison. Tag from the first trace.
2. **Deletion that did not cascade to promoted dataset items.** A promoted eval case is a copy of customer content in a different table with a different lifecycle. A subject-erasure request covers it, and discovering that in month nine is expensive.

## Grading notes

**3/3 on the flywheel:** one failure traced end to end with timestamps at every stage, a named
reviewer with a recurring slot, deduplication on failure signature, and `source_trace_id` plus
`prompt_version` on every promoted case.

**Common losses:** a pipeline with no reviewer; no environment tags; cost columns empty because
`usage` was never reported; and a retention policy invented after the database reached 41 GB.
