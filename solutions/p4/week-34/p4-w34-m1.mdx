## Reference solution — `P4-W34-M1`

### Check the shape before you check anything else

The failure that wastes weeks is not missing instrumentation — it is instrumentation that produces a
*forest* of single-span traces instead of a tree. Dashboards look correct: counts right, durations
right, shape entirely wrong. Assert on it:

```python
def test_run_produces_one_tree():
    exporter = InMemorySpanExporter()
    run_agent("INC-10231")
    spans = exporter.get_finished_spans()
    assert len({s.context.trace_id for s in spans}) == 1, "forest, not a tree"
    roots = [s for s in spans if s.parent is None]
    assert len(roots) == 1, f"{len(roots)} roots — context lost at a boundary"
    assert len(spans) >= 8, "too few spans to be useful"
```

Nine lines, and it catches the bug this module exists to prevent. The cause is almost always a
thread pool: OpenTelemetry context lives in `contextvars`, which follow `await` and are **not**
inherited by pool threads. `otel_context.attach(ctx)` inside the worker fixes it.

### Reference numbers

| | Value |
| --- | --- |
| Overhead per span (BatchSpanProcessor) | 0.4 ms |
| Overhead per run (15 spans) | 60 ms, 0.18% of a 34 s run |
| `SimpleSpanProcessor` instead | 1.83 s per run, 5.4% — never use it |
| Head sampling 10% vs tail sampling | 10% of errors vs **100%**, at 8.1% of volume |
| Storage, platform volume | 55 GB/yr → 4.5 GB/yr with tail sampling |
| `user_id` as a metric label | 39.6 M series, ≈$7,920/month |

## Why this solution and not the obvious one

**Obvious:** invent your own attribute names because they read better. Using `gen_ai.*` cost nothing
and removed a mapping layer we had been maintaining; Langfuse ingested our OTLP with zero
configuration, and a Grafana GenAI dashboard worked immediately. Standard names for standard things,
your own prefix for the rest, and never invent under `gen_ai.`

**Obvious:** head sampling, because it is one config line. It throws away 90% of errors, and errors
are the entire reason the traces exist. Tail sampling stores *less* and keeps everything you would
ever open.

**Obvious:** put `user_id` on the metrics so you can slice by user. That multiplies into permanent
time series. High cardinality belongs on spans, which are individual records; then "which users hit
the most errors" is a query rather than a bill.

## The two wrong turns worth knowing about

1. **`decision_wait` of 10 seconds against a 71-second p99.** Long traces were sampled on their first few spans and the rest dropped, producing truncated traces that looked like the agent had stopped early. A day to diagnose. Set it above p99.
2. **Recording prompt and response text on every span by default.** That is customer content in a trace store, and it is also a storage bill. We record text for 5% of traces plus 100% of error traces, redacted in a SpanProcessor with a 2,000-character cap.

## Grading notes

**3/3 on Instrumentation:** correct nesting proven by test (not asserted in prose), the GenAI
conventions used verbatim, cost including cache fields, redaction structural rather than
call-site, and measured overhead.

**Common losses:** a forest of single-span traces; cost computed from `input_tokens` alone, which
under-reports a cached workload by 40–80%; a high-cardinality metric label; and no measurement of
the overhead, which is the objection everyone raises and nobody answers with a number.
