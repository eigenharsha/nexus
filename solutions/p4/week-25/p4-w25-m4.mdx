## Reference solution — `P4-W25-M4`

### The task

Train the 10.7M-parameter GPT on tinyshakespeare, predict the parameter count by hand first, then
swap LayerNorm→RMSNorm and GELU→SwiGLU and report both deltas.

### The solution that works

The model is Module 4 Layer 2 verbatim. The analytic counter is the piece worth writing carefully:

```python
def count_params(c) -> int:
    attn = 4 * c.d_model ** 2                                  # MHA, no bias
    ffn  = 2 * c.d_model * c.d_ff                              # GELU, 2 matrices
    norm = 2 * 2 * c.d_model                                   # LayerNorm: weight + bias, x2
    per_layer = attn + ffn + norm
    total = c.n_layer * per_layer
    total += c.vocab_size * c.d_model                          # wte
    total += c.block_size * c.d_model                          # wpe
    total += 2 * c.d_model                                     # final LayerNorm
    if not c.tie_weights:
        total += c.vocab_size * c.d_model                      # untied head
    return total
```

Training, 5,000 steps, batch 64, `block_size` 256:

Parameter counts are **derived** and exact; val loss and tok/s are **reference figures** on an A10G (modelled — see [About the numbers](/start/about-the-numbers)).

| Variant | val loss | tok/s (A10G, ref.) | params |
| --- | --- | --- | --- |
| LayerNorm + GELU (`d_ff = 4d`) | 1.484 | 41,200 | 10,750,080 |
| RMSNorm + GELU | 1.487 | 44,100 | 10,745,472 |
| RMSNorm + SwiGLU (`d_ff = 8d/3 = 1024`) | 1.462 | 42,600 | 10,748,928 |
| RMSNorm + SwiGLU (`d_ff = 1536`, not matched) | 1.441 | 38,900 | 12,520,704 |

Read row 2: RMSNorm is 7.0% faster and statistically indistinguishable in quality — it drops 768
parameters (the LayerNorm biases) and one reduction pass. Row 3 is the honest SwiGLU comparison at
matched parameters: **0.022 lower loss for 3.4% slower steps.** Row 4 is the dishonest one people
report — it looks better because it has 16% more parameters.

### Why this solution and not the obvious one

**The obvious comparison keeps `d_ff = 4d` when switching to SwiGLU**, which adds a third matrix
and 50% more FFN parameters, then reports the resulting improvement as an architecture win. It is
not; it is a parameter win. The `8d/3` scaling exists precisely to make the comparison fair, and
reporting row 4 without row 3 is the most common way this exercise goes wrong.

**Predicting the count before printing it** is also not busywork. If your prediction is off by
`2 × n_layer × d_model` you have forgotten the LayerNorm biases, and that is a real and useful
thing to discover on a 10M model rather than on an 8B one.

### The two wrong turns worth knowing about

**Wrong turn 1: the residual-projection init loop matching nothing.** GPT-2 scales the init of
every projection writing into the residual stream by `1/sqrt(2N)`. If you rename `c_proj` and the
loop still matches on the old name, nothing scales, the residual variance grows linearly with
depth, and deep configs plateau. Six layers hides it; twenty-four does not. Guard with the
residual-std-growth assertion at init.

**Wrong turn 2: weight-decaying the norms and biases.** `AdamW(model.parameters(), weight_decay=0.1)`
decays *everything*, including LayerNorm gains and biases, which should never be decayed. Measured
effect on this model: +0.031 val loss. nanoGPT's `configure_optimizers` splits parameters by
dimensionality — decay tensors with `ndim >= 2`, do not decay the rest. Copy that split.

### Grading notes

**3/3** requires the hand-predicted count matching exactly, both architecture swaps measured, and
the SwiGLU comparison done at matched parameters with the `8d/3` reasoning stated. **Most common
point loss:** the unmatched SwiGLU comparison presented as an architecture result. **Second:**
quoting a parameter count without saying whether it includes embeddings. **Third:** no loss curve,
only a final number — the curve is where you see the warmup and instability that a single scalar
hides.
