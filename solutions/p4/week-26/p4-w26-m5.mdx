## Reference solution — `P4-W26-M5`

### The task

Produce the self-host versus API cost model for your own workload, with measured throughput as the
input, and state the crossover volume.

### The solution that works

The concurrency sweep is Module 5 Layer 2's `bench.py`. The cost model is the part that has to be
written honestly:

```python
GPU_HOURLY = 1.006
HOURS_PER_MONTH = 730
API_PER_M_OUT = 0.60          # list price, checked 2026-08

def self_host_cost_per_million(tok_per_sec: float, utilisation: float) -> float:
    monthly_tokens = tok_per_sec * 3600 * HOURS_PER_MONTH * utilisation
    return GPU_HOURLY * HOURS_PER_MONTH / (monthly_tokens / 1e6)

def breakeven_utilisation(tok_per_sec: float) -> float:
    monthly_cost = GPU_HOURLY * HOURS_PER_MONTH
    tokens_needed = monthly_cost / API_PER_M_OUT * 1e6
    seconds_needed = tokens_needed / tok_per_sec
    return seconds_needed / (HOURS_PER_MONTH * 3600)
```

### Measured numbers this produces

Llama 3.2 3B Instruct + rank-8 adapter, A10G, vLLM 0.6.2, 512-token prompts, 128-token outputs — **reference figures**, modelled rather than run (see [About the numbers](/start/about-the-numbers)). The shape of the throughput-versus-concurrency curve is what you are being graded on reproducing:

| Concurrency | Total tok/s | Per-request tok/s | TTFT p50 | TTFT p95 |
| --- | --- | --- | --- | --- |
| 1 | 62 | 62.0 | 0.14 s | 0.17 s |
| 8 | 432 | 54.0 | 0.24 s | 0.38 s |
| 32 | 1,248 | 39.0 | 0.61 s | 1.14 s |
| 128 | 2,176 | 17.0 | 3.04 s | 5.87 s |
| 256 | 2,278 | 8.9 | 7.11 s | 9.42 s |

At a stated p95 TTFT SLO of 1.5 s, the operating point is **concurrency 32, 1,248 output tok/s**.

```
break-even = 734.38 / 0.60 = 1,224M output tokens/month
           = 1,224e6 / 1,248 = 980,769 s = 272 GPU-hours = 37.3% utilisation
```

**Below 1.22 billion output tokens a month — 37% sustained utilisation — the hosted API is
cheaper.** Spot pricing at $0.30/hr moves that to 11%; a one-year reservation to 23%.

### Why this solution and not the obvious one

**The obvious model uses peak throughput at maximum concurrency.** 2,176 tok/s gives a break-even
of 21% and looks much more favourable. But concurrency 128 has a p95 TTFT of 5.87 s, which violates
the SLO — so it is capacity you cannot actually sell. **Compute the cost model at the concurrency
that meets your SLO, not at the concurrency that maximises the number.** This single substitution
changes the break-even by 16 percentage points and is the difference between a correct
recommendation and the war story.

**The obvious model also omits idle hours.** A GPU rented monthly and used for 90 minutes a night
is at 6% utilisation, which the model above prices at $3.73 per million output tokens — six times
the API. Report `$/M` at your *realistic* utilisation, and put the utilisation assumption in bold
where a reviewer will see it.

### The two wrong turns worth knowing about

**Wrong turn 1: `--max-model-len 131072` "for flexibility".** KV cache is reserved per sequence
against that length. Measured: max cached tokens 122,073, so `max_model_len` 8,192 permits 14
concurrent sequences and 1,100 permits 111. Setting a generous value costs 8× your concurrency and
therefore 8× your cost per token — it is the single most expensive default in the file.

**Wrong turn 2: benchmarking with the client's default retry policy.** The OpenAI SDK retries twice
by default. Under load-test conditions your timeouts become retries, your retries become extra load,
and the throughput number you record is lower than the server's real capacity while the latency
number is a fiction. `max_retries=0` in every benchmark client.

### Grading notes

**3/3** requires the full concurrency sweep from your own hardware, an SLO stated *before* the
operating point is chosen, the `$/M` curve as a function of utilisation, the break-even percentage,
and a recommendation that names the assumption most likely to be wrong. **The three most common
point losses:** cost modelled at peak concurrency rather than at the SLO-meeting one; utilisation
assumed at 100% with no justification; and a recommendation to self-host with no accuracy comparison
attached, since the only reason to accept a worse cost position is a better quality position and
that trade has to be shown.
