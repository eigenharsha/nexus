## Reference solution — `P1-W05-M4`

### The ordering puzzle, with the reasoning

```js
console.log('1 sync start');
setTimeout(() => console.log('7 setTimeout 0'), 0);
queueMicrotask(() => console.log('4 queueMicrotask'));
Promise.resolve().then(() => console.log('5 promise.then'));
(async () => {
  console.log('2 async fn body (sync until first await)');
  await null;
  console.log('6 after await');
})();
console.log('3 sync end');
```

Verified output on Node 24.19:

```
1 sync start
2 async fn body (sync until first await)
3 sync end
4 queueMicrotask
5 promise.then
6 after await
7 setTimeout 0
```

Trace it as a table, which is how to answer this in an interview without hand-waving:

| Step | What runs | Why |
| --- | --- | --- |
| 1 | `1 sync start` | synchronous |
| 2 | `setTimeout` scheduled | macrotask queued |
| 3 | `queueMicrotask` scheduled | microtask queued (position 1) |
| 4 | `.then` scheduled | microtask queued (position 2) |
| 5 | `2 async fn body` | async body runs synchronously up to the first `await` |
| 6 | continuation after `await null` scheduled | microtask queued (position 3) |
| 7 | `3 sync end` | synchronous |
| 8 | stack empties → **microtask checkpoint** | drain queue in FIFO order: 4, 5, 6 |
| 9 | one macrotask | 7 |

### The harder puzzle

```js
const out = [];
setTimeout(() => { out.push('T1'); Promise.resolve().then(() => out.push('T1-micro')); }, 0);
setTimeout(() => { out.push('T2'); }, 0);
Promise.resolve().then(() => { out.push('P1'); return Promise.resolve(); })
                 .then(() => out.push('P2'));
(async () => { out.push('A-sync'); await Promise.resolve(); out.push('A-after-await'); })();
out.push('MAIN');
```

Verified: `A-sync -> MAIN -> P1 -> A-after-await -> P2 -> T1 -> T1-micro -> T2`

Two things surprise almost everyone. `P2` runs *after* `A-after-await` even though `P1` was
queued first, because returning a promise from `.then` costs two extra microtask ticks while the
runtime adopts the thenable. And `T1-micro` runs between `T1` and `T2`, because the microtask
queue is drained after **each** macrotask, not once at the end.

### The measured combinators

```
sequential awaits : 315 ms      (100 + 120 + 90 — the sum)
Promise.all       : 122 ms      (the max)
Promise.allSettled: 102 ms      (the max of the survivors; the rejection settled instantly)
Promise.race      :  93 ms      (the min — the other two are still running)
AbortController   :  51 ms      -> AbortError, for an abort scheduled at 50 ms
```

## Why this solution and not the obvious one

**Wrong turn 1: assuming `setTimeout(fn, 0)` runs first because it was scheduled first.** It is
scheduled first and runs last. The microtask queue is drained completely before any macrotask
gets a turn — that is the entire rule, and everything else in this module follows from it.

**Wrong turn 2: using `Promise.race` for cancellation.** `race` gives you the first result; the
losers keep running, keep holding sockets, and keep being able to write to your state. Measured:
`race` returned at 93 ms while two other tasks were still in flight. If a loser writes to the DOM
when it eventually finishes, you have a stale-render bug that reproduces once in twenty. Real
cancellation requires `AbortController`, which stopped a 500 ms task at 51 ms.

**Wrong turn 3: `array.forEach(async x => await f(x))`.** `forEach` ignores the returned promise,
so the loop finishes immediately, nothing is awaited, and errors become unhandled rejections. The
tell is that a "loop over 100 API calls" completes in 0 ms. Use `for...of` with `await` for
sequential, or `Promise.all(items.map(f))` for parallel — and `mapLimit` when the set is large.

## Measured numbers this solution produces

| Claim | Number |
| --- | --- |
| Independent work serialised by sequential `await` | 315 ms vs 122 ms — 2.6× |
| `Promise.all` floor is the slowest task | 122 ms for tasks of 100/120/90 ms |
| `race` does not cancel | returns at 93 ms; the 120 ms task still completes |
| Cancellation latency | abort at 50 ms → rejection at 51 ms |
| Ordering | seven-step order verified on Node 24.19, identical in Chrome 134 |

## Grading notes

**A 3/3 on correctness** predicts both puzzles exactly *before* running them and can explain the
`P2`-after-`A-after-await` ordering by naming thenable adoption.

**A 3/3 on the `mapLimit` challenge** preserves input order, never exceeds the limit (proved with
a concurrency counter, not by inspection), captures per-item errors rather than rejecting the
batch, checks the abort signal at the top of each iteration, and loops rather than recursing so
100,000 items do not blow the stack.

**The three most common ways submissions lose points**

1. `mapLimit` implemented with recursion; it passes the small tests and blows the stack on the large one.
2. Concurrency limited by chunking (`Promise.all` over slices of 8). It never exceeds the limit but it also idles — every chunk waits for its slowest member. The measured symptom is a wall time near `chunks × max(chunk)` instead of `total / limit`.
3. Aborts logged as errors. An `AbortError` is the expected outcome of cancellation and must not reach the user's error UI.
