## Reference solution — `P1-W05-M2`

Two deliverables: an accessible page scoring ≥ 95, and the measured `defer` experiment.

### The `defer` measurement, reproduced

Create four pages that differ only in one script tag, where `slow.js` busy-waits 120 ms:

```html
<!-- a.html -->  <script src="slow.js"></script>
<!-- b.html -->  <script defer src="slow.js"></script>
<!-- c.html -->  <script async src="slow.js"></script>
<!-- d.html -->  (no script)
```

Each page reads its own navigation timings on `load`:

```html
<script>
addEventListener('load', function () {
  var n = performance.getEntriesByType('navigation')[0];
  document.title = 'domInteractive=' + n.domInteractive.toFixed(1) +
                   ' DCL=' + n.domContentLoadedEventEnd.toFixed(1);
});
</script>
```

Measured in headless Chrome 134:

| Variant | `domInteractive` | `domContentLoadedEventEnd` |
| --- | --- | --- |
| blocking in `head` | 137.4 ms | 137.4 ms |
| `defer` | **2.4 ms** | 122.4 ms |
| `async` | 2.3 ms | 2.4 ms |
| no script | 2.0 ms | 2.0 ms |

**57× on `domInteractive`** from one attribute.

### The accessibility fixes that actually move the score

In order of how often they appear in submissions:

1. **Inputs without programmatic labels.** Add `<label for>`/`id`. Placeholder text is not a label — it disappears on focus and is not reliably announced.
2. **Insufficient contrast.** The 4.5:1 ratio for body text is arithmetic, not taste. Fix the token, not the individual rule.
3. **Missing `lang` on `<html>`.** One attribute; changes pronunciation for every screen-reader user.
4. **Non-sequential headings.** An `h4` chosen for its size. Use the right level and style it.
5. **Icon buttons with no accessible name.** Add visually hidden text or `aria-label`.
6. **`outline: none` with no replacement.** Restore a visible focus style; `:focus-visible` gives you one that does not appear on mouse clicks.

## Why this solution and not the obvious one

**Wrong turn 1: fixing Lighthouse instead of the page.** Adding `aria-label="button"` to every
button silences the rule and helps nobody — the screen reader now says "button, button". The
grading criterion is the sentence you write about the *user impact* of each fix, precisely to
catch this. Lighthouse is a smoke detector, not a fire inspector; it catches roughly a third of
WCAG criteria and cannot judge whether a name is meaningful.

**Wrong turn 2: reaching for ARIA first.** A very common submission replaces a `<div>` with
`<div role="button" tabindex="0">` plus a keydown handler for Enter — and forgets Space, forgets
`aria-disabled`, and forgets that the handler fires on keydown for Enter but on keyup for Space in
native buttons. `<button type="button">` is eleven characters and correct. The First Rule of ARIA
exists because this specific mistake is so common.

**Wrong turn 3: using `async` because it "sounds faster".** In the table above, `async` shows the
best `DOMContentLoaded` — but only because the script had not finished downloading when the event
fired. It runs later, at an unpredictable point, in unpredictable order relative to other scripts.
Any script that touches the DOM or depends on another script must use `defer`.

## Measured numbers this solution produces

| Claim | Number |
| --- | --- |
| Blocking script delays interactivity | `domInteractive` 137.4 ms vs 2.4 ms with `defer` (57×) |
| A 120 ms script costs its full duration | 137.4 − 2.0 = 135.4 ms of pure parser stall |
| CLS from an unsized 120 px shift in a 600 px viewport | ~0.16, above the 0.1 budget on its own |
| Core Web Vitals thresholds (p75) | LCP 2.5 s · INP 200 ms · CLS 0.1 |

## Grading notes

**A 3/3 on correctness**: accessibility ≥ 95 with every fix justified by user impact, keyboard
traversal verified by hand, and both `defer` numbers measured on the learner's own machine.

**A 3/3 on explanation**: names *which* users each fix serves — keyboard-only, screen reader,
low vision, motor impairment — rather than citing the rule ID.

**The three most common ways submissions lose points**

1. `aria-label` sprayed onto elements that already had accessible names, to silence warnings.
2. A score of 100 with a page that cannot be operated with the keyboard, because the automated tool cannot check that and the learner did not try.
3. Reporting the `defer` result without the blocking baseline, so there is no ratio to defend.
