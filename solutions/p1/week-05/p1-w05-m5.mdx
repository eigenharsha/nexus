## Reference solution — `P1-W05-M5`

The exercise: render 50,000 rows without freezing the tab, and measure before and after.

### The measurement harness

```html
<!doctype html><meta charset=utf-8><title>bench</title>
<style>#list{contain:content}.row{padding:4px;border-bottom:1px solid #ddd}</style>
<div id="list"></div><pre id="out"></pre>
<script>
const N = 50000, out = [];
const rows = Array.from({length:N}, (_,i)=>({id:i, name:'Item '+i}));
const list = document.getElementById('list');
const clear = () => list.innerHTML = '';
const force = () => list.offsetHeight;                 // forces layout

function t(label, fn) {
  clear();
  const s = performance.now(); fn(); const built = performance.now() - s;
  force();  const laid = performance.now() - s;
  out.push({strategy: label, build_ms: +built.toFixed(1),
            build_plus_layout_ms: +laid.toFixed(1), nodes: list.childElementCount});
}

// the quadratic disaster — only 1,000 rows, or it never finishes
clear();
{ const s = performance.now();
  for (let i = 0; i < 1000; i++) list.innerHTML += '<div class="row">Item ' + i + '</div>';
  const d = performance.now() - s;
  out.push({strategy: 'innerHTML += per row (1,000 only)', build_ms: +d.toFixed(1),
            extrapolated_50k_ms: +(d * 50 * 50).toFixed(0)}); }

t('appendChild per row (50,000)', () => {
  for (const r of rows) { const d = document.createElement('div');
    d.className='row'; d.textContent=r.name; list.appendChild(d); } });

t('layout THRASH: read offsetHeight per row (5,000)', () => {
  for (let i = 0; i < 5000; i++) { const d = document.createElement('div');
    d.className='row'; d.textContent=rows[i].name; list.appendChild(d); void list.offsetHeight; } });

t('DocumentFragment, single append (50,000)', () => {
  const f = document.createDocumentFragment();
  for (const r of rows) { const d = document.createElement('div');
    d.className='row'; d.textContent=r.name; f.appendChild(d); }
  list.appendChild(f); });

t('one innerHTML assignment (50,000)', () => {
  let s = ''; for (const r of rows) s += '<div class="row">' + r.name + '</div>';
  list.innerHTML = s; });

t('virtualized window (30 of 50,000)', () => {
  const f = document.createDocumentFragment();
  for (let i = 0; i < 30; i++) { const d = document.createElement('div');
    d.className='row'; d.textContent=rows[i].name; f.appendChild(d); }
  list.appendChild(f); });

document.getElementById('out').textContent = JSON.stringify(out, null, 1);
</script>
```

### The results

Chrome 134 headless, Apple Silicon:

| Strategy | Build | Build + layout | Nodes |
| --- | --- | --- | --- |
| `innerHTML +=` per row (1,000) | 123.6 ms | — | 1,000 |
| ↳ extrapolated to 50,000 (O(n²)) | ~309,000 ms | — | — |
| `appendChild` per row | 15.2 ms | 230.7 ms | 50,000 |
| **Layout thrash, 5,000 rows** | **2,406.3 ms** | 2,406.4 ms | 5,000 |
| `DocumentFragment` | 36.9 ms | 264.2 ms | 50,000 |
| single `innerHTML` assignment | 17.7 ms | 252.8 ms | 50,000 |
| **virtualized, 30 rows** | **0.1 ms** | **0.3 ms** | 30 |

## Why this solution and not the obvious one

**Wrong turn 1: believing `DocumentFragment` is the answer.** It is the answer everyone has read
about, and here it measured 264.2 ms against 230.7 ms for a plain `appendChild` loop — slightly
*worse*. The reason is that modern engines already defer layout, so the fragment saves nothing
when no layout is being forced between insertions. The fragment matters when something *else* in
the loop reads layout. Learners who present a fragment as a 10× win have not measured it.

**Wrong turn 2: optimising the build when layout is the cost.** Build times across the three
correct strategies are 15.2, 17.7 and 36.9 ms; the layout that follows is 215–230 ms in every
case. Any effort spent shaving the build phase is optimising 7% of the problem. This is the
general lesson: measure the whole pipeline before choosing what to improve.

**Wrong turn 3: "virtualizing" by hiding rows.** `display: none` or `visibility: hidden` on
off-screen rows still requires 50,000 nodes to exist, which is most of the memory and all of the
creation cost. The measured win comes from *not creating* them: 30 nodes, 0.3 ms, an **843×**
improvement over 252.8 ms. The checker counts DOM nodes for exactly this reason.

The one honourable middle path is `content-visibility: auto` with `contain-intrinsic-size`, which
keeps all nodes but lets the engine skip their layout and paint. A learner who chooses it and
explains the trade-off — simpler code and working browser find, at the cost of scrollbar jitter
when the intrinsic size estimate is wrong — should score full marks.

### The layout-thrash fix

```js
// BAD: alternating writes and reads forces synchronous layout every iteration
for (const el of items) el.style.height = el.offsetHeight + 10 + 'px';

// GOOD: all reads, then all writes
const heights = items.map(el => el.offsetHeight);
items.forEach((el, i) => { el.style.height = heights[i] + 10 + 'px'; });
```

Measured: 5,000 rows interleaved took 2,406.3 ms; 50,000 rows batched took 230.7 ms. Ten times
fewer rows, ten times more time — about a 100× per-row penalty.

## Measured numbers this solution produces

| Claim | Number |
| --- | --- |
| `innerHTML +=` is quadratic | 123.6 ms at 1,000 rows → ~309 s extrapolated at 50,000 |
| Virtualization is the only order-of-magnitude win | 252.8 ms → 0.3 ms (843×) |
| Layout thrash penalty | ~100× per row |
| DOM node count, virtualized | 30 vs 50,000 |
| Frame budget context | full render burns ~15 frames of 16.7 ms; virtualized burns 2% of one |

## Grading notes

**A 3/3 on performance** reports its own numbers for at least four strategies, states the machine
and browser version, and identifies layout rather than node creation as the dominant cost.

**A 3/3 on correctness** keeps the virtualized list genuinely usable: `Home`/`End`/`PageDown`
work, the scrollbar is proportional to the full dataset, and selection survives scrolling away
and back.

**The three most common ways submissions lose points**

1. A "virtualized" list that still creates all 50,000 nodes and hides them. Node count gives it away instantly.
2. No baseline. A fast number with nothing to compare it to is not a measurement.
3. Rendering with `innerHTML` and interpolated data — fast *and* an XSS hole. The automated check greps for it.
