## Reference solution — `P1-W03-M5`

Find a bug with `hypothesis` that the example tests miss.

**The code under test**, with four passing example tests and 100% branch coverage:

```python
def split_evenly(total_cents: int, parts: int) -> list[int]:
    """Split `total_cents` into `parts` shares that sum to the total."""
    if parts <= 0:
        raise ValueError("parts must be positive")
    share = total_cents // parts
    result = [share] * parts
    result[0] += total_cents - share * parts     # the whole remainder onto share 0
    return result
```

```python

def test_one_part():   assert split_evenly(7, 1) == [7]
def test_zero_parts(): 
    with pytest.raises(ValueError, match="positive"):
        split_evenly(100, 0)
```

**The properties, taken from the docstring rather than the implementation:**

```python
from hypothesis import given, settings, strategies as st, example
from money import split_evenly

INTS = st.integers(min_value=-10**9, max_value=10**9)
PARTS = st.integers(min_value=1, max_value=1000)


@given(total=INTS, parts=PARTS)
@settings(max_examples=500)
def test_sum_is_preserved(total: int, parts: int) -> None:
    """Conservation: the parts sum to the whole."""
    assert sum(split_evenly(total, parts)) == total


@given(total=st.integers(min_value=0, max_value=10**9), parts=PARTS)
@settings(max_examples=500)
@example(total=2, parts=3)                       # pin the shrunk case forever
def test_shares_differ_by_at_most_one(total: int, parts: int) -> None:
    """Fairness: 'evenly' means no share is more than one unit above another."""
    shares = split_evenly(total, parts)
    assert max(shares) - min(shares) <= 1


@given(total=st.integers(min_value=0, max_value=10**9), parts=PARTS)
def test_no_negative_shares(total: int, parts: int) -> None:
    assert all(s >= 0 for s in split_evenly(total, parts))
```

**The fix:**

```python
def split_evenly(total_cents: int, parts: int) -> list[int]:
    """Split into `parts` shares differing by at most one minor unit, summing to the total."""
    if parts <= 0:
        raise ValueError("parts must be positive")
    share, remainder = divmod(total_cents, parts)      # floor division; 0 <= remainder < parts
    return [share + 1] * remainder + [share] * (parts - remainder)
```

## Why this solution and not the obvious one

**Wrong turn 1: writing properties from the implementation instead of the docstring.**

The tempting property is "the result equals what the function returns for these inputs", which is a tautology. The subtler and more common version is reimplementing the algorithm in the test:

```python
@given(total=INTS, parts=PARTS)
def test_split(total, parts):
    share = total // parts
    expected = [share] * parts
    expected[0] += total - share * parts
    assert split_evenly(total, parts) == expected      # VACUOUS: same bug, twice
```

This passes on the broken code, because it *is* the broken code. It will keep passing after you fix the function, at which point it fails and you "fix" the test.

Properties must come from the **contract**, not the mechanism. The docstring said "split evenly" and "sum to the total"; those are two independent, checkable statements, and the first one is what the four example tests never encoded. Writing the property forced someone to say what "evenly" means — which is the real work, and it is why property testing improves designs as well as finding bugs.

**Wrong turn 2: trusting 100% coverage.**

The example suite achieved **100% line and 100% branch coverage** on a function that returns `[2, 0, 0]` for `split_evenly(2, 3)`. Every line ran. Both branches of the `if` ran. Coverage was structurally complete and behaviourally blind.

Coverage answers "did this line execute", never "was the result checked". A test suite of `assert True` after calling every function reaches 100%.

The metric that actually answers the question is **mutation score**: inject small changes (flip a comparison, change a constant, drop a statement) and measure what fraction your tests detect. `mutmut run` on this module kills far more mutants with the property suite than with the example suite, and that difference is the number to report. Use coverage as a **floor** — it reliably finds code with *no* test — and mutation score as the quality signal.

**A third thing worth knowing: `@example` pins the shrunk case.**

Hypothesis stores failures in `.hypothesis/examples/` and replays them first, but that directory is usually gitignored and CI starts fresh. Adding `@example(total=2, parts=3)` turns the discovered case into a deterministic regression test that runs on every machine, forever, in 40 microseconds. **Every hypothesis-found bug should end with an `@example`.**

## Grading notes

**3/3 on correctness** means at least one property fails on the original code and all pass after the fix, and the negative-total behaviour is verified by hand rather than assumed.

**3/3 on code quality** means the properties are derived from the contract, not the implementation — a grader will check by asking whether the property would still be meaningful if the function were rewritten from scratch.

**3/3 on explanation** means the write-up reports the **shrunk** case (not the first failure), shows the example suite's coverage number, and adds the shrunk case as an `@example`.

The five most common ways submissions lose points:

1. **A vacuous property that reimplements the function.** Passes on broken code. The test: could this property be written by someone who has only read the docstring? If not, it is not a property.
2. **The first failing case reported instead of the shrunk one.** Shrinking is the feature; `(872341, 617)` is not actionable and `(2, 3)` is.
3. **No `@example` added.** The bug is fixed and unpinned; the next refactor can reintroduce it and CI will only catch it probabilistically.
4. **`deadline` errors dismissed by disabling hypothesis in CI.** The right fix is `@settings(deadline=None)` on genuinely slow tests, not turning off the tool that found the bug.
5. **Coverage reported as evidence of quality.** The whole point of this module is that 100% branch coverage coexisted with the bug. Report mutation score, or report coverage explicitly as a floor.
