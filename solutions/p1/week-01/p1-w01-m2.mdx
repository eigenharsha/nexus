## Reference solution — `P1-W01-M2`

The deliverable is the four artifacts plus a Makefile with debug/release targets and working header dependency tracking.

```bash
cc -E hello.c -o hello.i && cc -S hello.c -o hello.s && cc -c hello.c -o hello.o && cc hello.o -o hello
wc -l hello.c hello.i hello.s
ls -l hello.c hello.i hello.s hello.o hello
cc -E -H hello.c -o /dev/null 2>&1 | grep -c '^\.'
nm hello.o && otool -L hello && size -m hello
```

The Makefile:

```makefile
CC       := cc
SRC      := $(wildcard src/*.c)
CFLAGS   := -std=c17 -Wall -Wextra -Wpedantic -Wshadow -MMD -MP -g3
LDFLAGS  :=

BUILD    ?= debug
ifeq ($(BUILD),debug)
  CFLAGS  += -O0 -fsanitize=address,undefined -fno-omit-frame-pointer
  LDFLAGS += -fsanitize=address,undefined
else
  CFLAGS  += -O2 -DNDEBUG
endif

OUT := build/$(BUILD)
OBJ := $(SRC:src/%.c=$(OUT)/%.o)
DEP := $(OBJ:.o=.d)

.PHONY: all clean verify
all: $(OUT)/app

$(OUT)/app: $(OBJ)
	$(CC) $(OBJ) $(LDFLAGS) -o $@

$(OUT)/%.o: src/%.c | $(OUT)
	$(CC) $(CFLAGS) -c $< -o $@

$(OUT):
	mkdir -p $@

verify: all
	./$(OUT)/app --selftest

clean:
	rm -rf build

-include $(DEP)
```

Proof that dependency tracking works — this is the graded step:

```bash
make && make            # second run: "make: 'build/debug/app' is up to date."
touch src/session.h
make -n                 # must list ONLY the .o files that include session.h
cat build/debug/main.d  # the generated dependency list
```

## Why this solution and not the obvious one

**Wrong turn 1: one output directory for both builds.**

The natural Makefile writes `main.o` next to `main.c` regardless of flags. Then `make` followed by `make BUILD=release` reuses the sanitized `main.o` in an unsanitized link, or vice versa. The result is a binary where some translation units expect ASan's runtime interposition and some do not — you get link errors if you are lucky and bizarre crashes inside `malloc` if you are not.

`build/$(BUILD)/` costs one variable and makes the two configurations genuinely independent. The order-only prerequisite `| $(OUT)` creates the directory without making its mtime a rebuild trigger; using a normal prerequisite there causes a full rebuild every time anything in the directory changes, which is every build.

**Wrong turn 2: `-MD` instead of `-MMD`, or omitting `-MP`.**

`-MD` records dependencies on system headers too, so every `stdio.h` in the SDK ends up in your `.d` files — 37 of them for a single `#include <stdio.h>` — and an Xcode or glibc update rebuilds everything. `-MMD` records only your own headers, which is what you want.

Omitting `-MP` is subtler and bites exactly once: you delete a header, `make` reads a stale `.d` file that still lists it as a prerequisite, cannot find a rule to build it, and stops with `No rule to make target 'src/old.h'`. `-MP` emits a phony target for each header so the missing file is silently ignored and the `.o` simply rebuilds. Four characters that save an hour of confusion.

## The measured numbers this solution produces

| Stage | File | Lines | Bytes |
|---|---|---|---|
| source | `hello.c` | 3 | 105 |
| preprocessed | `hello.i` | 557 | 25,076 |
| assembly | `hello.s` | 38 | 1,088 |
| object | `hello.o` | — | 808 |
| executable | `hello` | — | 33,432 |

- Headers pulled in transitively by one `#include <stdio.h>`: **37**.
- `nm hello.o`: `T _main` (defined), `U _printf` (undefined until link).
- `size -m hello`: `__text` is **68 bytes**; `__PAGEZERO` is **4,294,967,296 bytes** of deliberately unmapped space so null dereferences fault.
- Compile time, same file: `-O0` **0.04 s** user, `-O2` **0.08 s** user.
- `sum_to(1e9)` at `-O0`: ~1.0 s idle (9.2–27.2 s under load average 44). At `-O1` and `-O2`: **0.000 ms** — the loop is replaced by nine instructions computing n(n+1)/2.

## Grading notes

**3/3 on correctness** means `make -n` after touching a header lists exactly the objects that include it — no more, no fewer. Graders run this.

**3/3 on explanation** means the README explains *why* 105 bytes became 25,076 (37 headers, all for one declaration) and *why* the binary is 33 KB when the code is 68 bytes (load commands, symbol table, unwind info, 16 KB page alignment).

The three most common ways submissions lose points:

1. **Dependency tracking present but not verified.** `-MMD -MP` in `CFLAGS` and no `-include $(DEP)` at the bottom. The flags generate the `.d` files; the `-include` is what makes `make` read them. Both are required and only one is memorable.
2. **Benchmarking `sum_to` and reporting 0 ms as a result.** If your write-up says "the optimised version runs in under a millisecond" rather than "the optimiser replaced the loop with a closed form, here is the assembly", you have measured nothing and learned the wrong lesson.
3. **Claiming a static build on macOS.** `clang -static` fails on Darwin because Apple ships no static `libSystem`. A submission that reports static-link byte counts on a Mac either did not run the command or is reporting numbers from somewhere else.
