## Reference solution — `LAB-P2-W12`

The module solution pages carry the implementations. This page covers the lab's own three things: the
tool's structure, the sequential-boundary verification that the `hard` track turns on, and the
one-pager.

### Structure: checks are a gate, not a report section

```
abtest/
  checks.py     srm, covariate_balance, outlier_filter  -> raise ExperimentInvalid
  design.py     n_per_arm, mde_for_n, obrien_fleming_boundaries
  analyse.py    bootstrap_diff_ci, cuped, guardrails, decide
  cli.py        orchestration: checks FIRST, and they can abort
tests/
  test_*.py
tools/
  broken_experiment.py   the SRM dataset
  sequential_sim.py      family-wise error verification
  cuped_sim.py           variance-reduction verification
```

`cli.py` runs `checks` before `analyse` is imported into scope at all. That ordering is the design:
there is no code path that produces a primary metric from an invalid experiment.

```python
def main(args):
    df = load(args.data)
    try:
        run_all_checks(df, args.config)                 # raises on failure
    except ExperimentInvalid as e:
        print(f"EXPERIMENT INVALID\n{e}\n\nNo metrics will be reported.")
        return 2                                         # non-zero exit: CI can gate on it
    report(analyse(df, args.config))
    return 0
```

### Verifying the sequential boundaries

This is the `hard` track's real difficulty. Implementing O'Brien-Fleming is a formula; showing that it
controls the error rate is an experiment.

```python
def verify_boundaries(boundaries, n_final, trials=20_000, seed=0):
    """Simulate under the NULL. The fraction of trials crossing any boundary must be ~alpha."""
    rng = np.random.default_rng(seed)
    checks = np.linspace(n_final // len(boundaries), n_final, len(boundaries)).astype(int)
    crossed = 0
    for _ in range(trials):
        a = rng.normal(0, 1, n_final); b = rng.normal(0, 1, n_final)   # no effect
        for n, thresh in zip(checks, boundaries):
            if stats.ttest_ind(a[:n], b[:n], equal_var=False)[1] < thresh:
                crossed += 1
                break
    return crossed / trials        # must be 0.05 +/- 0.01
```

Run the same harness with a **flat 0.05 threshold** at every look and you reproduce the module's
measured numbers: 0.0512 at one look rising to **0.2507** at twenty. Printing both in the report is what
demonstrates the correction works.

### The one-pager that gets read

```markdown
# How to read an A/B test

## Before you launch (fill this in, or the result means nothing)
- Primary metric:                    (exactly one)
- Minimum effect worth shipping:     (%)
- Users needed per arm:              (from the calculator)
- Guardrails that must not degrade:
- Decision rule:
- Stop date:

## Before you believe a result
1. Did the split come out as intended? (SRM check. If it failed, stop. The result is not
   "slightly off", it is uninterpretable.)
2. Was the sample size fixed before launch, and did anyone stop early because it looked good?
   (Checking daily and stopping when significant turns a 5% false-alarm rate into 25%.)
3. Is the metric being reported the one declared before launch?
4. Do the guardrails hold?

## Reading it
Look at the effect size and its confidence interval, not the p-value.
Ask: "is the LOWER end of this interval still worth shipping for?"
If the interval includes zero, you have not measured an effect - but if the test could
only detect a 9% change and the true effect is 4%, "no effect" is also not what you found.

## Traps
- Peeking: 5% -> 25% false alarms with 20 looks.
- Segment fishing: "it worked for iOS users in Germany" is a hypothesis, not a result.
- Novelty: a big day-1 lift that fades. Plot the effect by day.
- Interference: in a marketplace, treatment can harm control, so the test overstates the effect.

## When to distrust a win
Too good to be true usually is. Check SRM first, then check what changed in logging.
```

## Why this solution and not the obvious one

**Non-zero exit code on an invalid experiment.** It lets CI or a scheduled job gate on it, which is how
the check becomes organisational rather than personal.

**The one-pager contains no statistics vocabulary.** It is for a product manager. Every sentence is
either a thing to write down or a thing to check, and the numbers are consequences, not parameters.

**Both the broken and the corrected numbers are reported.** Showing 0.2507 alongside 0.05 is what makes
the sequential correction convincing; the boundary values alone are not.

## Grading notes

**What 3/3 looks like on each rubric row**

- *Correctness* — the tool refuses on the SRM dataset; F1 above 0.90; paired bootstrap correct; boundary
  verification at 0.05 ± 0.01; CUPED matching `ρ²` within 2 percentage points.
- *Code quality* — checks live in their own module and run first; the classifier's prior is separable;
  no analysis code path is reachable from an invalid experiment.
- *Performance* — the bootstrap is vectorised enough that the coverage simulation runs in under a
  minute.
- *Explanation* — the one-pager is genuinely usable by a non-statistician, and the report shows both the
  inflated and the corrected false-positive rates.

**The three most common ways submissions lose points**

1. **SRM as a warning.** The single most important requirement, and the one most often softened.
2. **Sequential boundaries unverified.** The simulation is the deliverable. Without it there is no
   evidence the implementation is correct, and it usually is not on the first attempt.
3. **A one-pager written for statisticians.** If it contains "null hypothesis", "type I error" or
   "significance level", it will not be read by the people it is for, and it has failed at its job.
