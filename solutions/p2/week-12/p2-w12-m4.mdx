## Reference solution — `P2-W12-M4`

### Assignment that actually works across processes

```python
import hashlib

def assign(user_id: str, experiment_id: str, split=0.5) -> str:
    h = hashlib.sha256(f"{experiment_id}:{user_id}".encode()).digest()
    x = int.from_bytes(h[:8], "big") / 2**64
    return "treatment" if x < split else "control"
```

Three requirements, all satisfied by this one function: **deterministic** (the same user always gets
the same variant), **independent across experiments** (the experiment id is in the hash, so experiment
2's split does not correlate with experiment 1's), and **stable across processes** (SHA-256, not
Python's `hash()`, which is salted per process).

Measured on 100,000 ids: `Counter({'control': 50241, 'treatment': 49759})` — within 0.5% of even.

### The gate, not the warning

```python
def analyse(df, config):
    chi2, p = srm_check(df.groupby("variant").size().tolist())
    if p < 0.001:
        raise ExperimentInvalid(
            f"SRM: chi2={chi2:.2f}, p={p:.2e}. Randomisation is broken; "
            f"the groups are not comparable and the primary metric will not be reported."
        )
    ...
```

Raising rather than warning is the entire design. A warning is read once and ignored thereafter.

## Why this solution and not the obvious one

**SRM at `p < 0.001`, not 0.05.** You will run hundreds of experiments. At 0.05 you would investigate
one in twenty healthy ones and stop taking the alert seriously. At 0.001 a firing alert is almost
always real.

**CUPED's `θ` estimated from the pooled data, not per arm.** Estimating separately introduces a
dependence on the treatment and biases the estimate. `θ = Cov(Y, X) / Var(X)` over everyone.

**The covariate must predate assignment entirely.** This is the one way to get CUPED wrong and it is
silent: any covariate measured during the experiment can itself be affected by the treatment.

**Wrong turns worth knowing about.**

1. *Python's built-in `hash()` for assignment.* String hashing is randomly salted per process, so the
   same user gets different variants on different servers and after every restart. Extremely common and
   very hard to debug from the metrics alone.
2. *Randomising by session or request.* Contaminates users and over-represents heavy ones, which breaks
   the independence assumption behind every test and narrows intervals illegitimately.
3. *Logging assignment at render time rather than assignment time.* This is the war story: a client-side
   timeout fell back to control **and logged the user as control**, which systematically removed the
   slowest sessions from treatment and manufactured a 3.2% "lift".
4. *Checking the dashboard daily with a fixed 0.05 threshold.* Measured: 20 looks gives a 25%
   false-positive rate. This is not a hypothetical practice; it is what everybody does.

## Grading notes

**What 3/3 looks like**

- *Correctness* — `assign` is stable across processes and splits within 0.5%; SRM blocks reporting;
  CUPED's reduction matches `ρ²` within 2 percentage points.
- *Code quality* — checks are separated from analysis and run first; the tool raises rather than warns.
- *Performance* — sequential boundaries implemented **and verified by simulation** to keep the
  family-wise error at 0.05 ± 0.01.
- *Explanation* — the one-pager is written for a product manager, not a statistician, and states the
  peeking number.

**The three most common ways submissions lose points**

1. **SRM implemented as a warning.** The ticket asked for a refusal, and the difference is the entire
   lesson of the incident.
2. **Sequential boundaries implemented but not simulated.** The formula is easy; verifying that the
   error rate is actually controlled is where the bugs are.
3. **CUPED's covariate taken from the experiment period.** Silent bias, and the submission usually
   reports a suspiciously large variance reduction as a success.
