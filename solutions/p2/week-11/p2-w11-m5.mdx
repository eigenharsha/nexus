## Reference solution — `P2-W11-M5`

### Adam, with the bias correction that people omit

```python
def adam(p, g, t, s, lr=1e-2, b1=0.9, b2=0.999, eps=1e-8):
    s['m'] = b1 * s.get('m', 0) + (1 - b1) * g
    s['v'] = b2 * s.get('v', 0) + (1 - b2) * g * g
    mh = s['m'] / (1 - b1 ** t)          # without this, step 1 is 10x too small
    vh = s['v'] / (1 - b2 ** t)
    return p - lr * mh / (np.sqrt(vh) + eps)
```

Note `t` starts at **1**, not 0. At `t = 0` the bias correction divides by zero.

### Global-norm clipping

```python
def clip_global_norm(grads, max_norm=1.0):
    total = np.sqrt(sum((g ** 2).sum() for g in grads))
    if total > max_norm:
        scale = max_norm / (total + 1e-6)
        grads = [g * scale for g in grads]
    return grads, total                   # return the PRE-clip norm: log it
```

### The Hessian, which turns the race into an explanation

```python
def hessian_rosen(p):
    x, y = p
    return np.array([[2 - 400 * (y - 3 * x * x), -400 * x], [-400 * x, 200.0]])
```

## Why this solution and not the obvious one

**`clip_global_norm` returns the pre-clip norm.** That value is the single most informative training
diagnostic there is, and if the function does not return it nobody logs it. The war story in the module
is four days of debugging that one log line would have ended in ten minutes.

**Global norm, not per-parameter.** Scaling all gradients by one factor preserves the descent
direction; clipping each parameter independently changes it, so you are no longer stepping downhill.

**The Hessian is computed and reported alongside the race.** Without it you have observed that Adam
wins; with it you can say the condition number is 2,508 and the stability limit is 2.00e-3, and then
*predict* that plain GD's best learning rate will be 2e-3 — which it is.

**Wrong turns worth knowing about.**

1. *Omitting bias correction.* `m` and `v` start at zero, so early estimates are biased towards zero
   and the first steps are far too small. Symptom: Adam appears to do nothing for the first hundred
   steps.
2. *Starting `t` at 0.* `1 − β^0 = 0`, so the correction divides by zero on the first step.
3. *Using `Adam` with `weight_decay` and calling it weight decay.* Adam divides the L2 gradient by
   `sqrt(v)`, so parameters with large gradients get *less* regularisation — backwards. Use `AdamW`.
4. *Tuning the learning rate without knowing `L`.* The threshold is `2/L` exactly; measured, `1.99/L`
   converges, `2.0/L` oscillates forever and `2.01/L` diverges. Everything above that is not
   "instability", it is arithmetic.
5. *Reporting Adam's win without the memory cost.* The 8 bytes per parameter is the reason Week 26
   exists, and a solution that omits it has missed the module's purpose.

## Grading notes

**What 3/3 looks like**

- *Correctness* — every optimizer converges below `2/L` and diverges above `2.01/L`; Adam reaches
  `f < 1e-3` on Rosenbrock; bias correction verified by checking the first step's magnitude.
- *Code quality* — one `run` harness driving all five optimizers; clipping returns the pre-clip norm.
- *Performance* — the Hessian spectrum reported alongside the race, and the predicted `2/L` compared
  against the empirically best learning rate.
- *Explanation* — the memory table computed for a model the student cares about, with a stated
  conclusion about what hardware it needs.

**The three most common ways submissions lose points**

1. **The race reported without the Hessian.** Adam wins; nobody can say why or by how much the problem
   was ill-conditioned.
2. **Bias correction missing or `t` starting at 0.** Either produces a visibly wrong first hundred
   steps, and it is the detail most often dropped when Adam is written from memory.
3. **No memory table.** It is the deliverable that connects Week 11 to Week 26, and it takes four lines
   of arithmetic.
