## Reference solution — `P2-W11-M2`

### Gauss-Jordan inverse with partial pivoting

```python
def inverse(M):
    n = len(M)
    A = [list(row) + [1.0 if i == j else 0.0 for j in range(n)] for i, row in enumerate(M)]
    for col in range(n):
        # partial pivoting: pick the row with the largest |value| in this column
        piv = max(range(col, n), key=lambda r: abs(A[r][col]))
        if abs(A[piv][col]) < 1e-12:
            raise ValueError(f"matrix is singular (pivot {col} is {A[piv][col]:.3e})")
        A[col], A[piv] = A[piv], A[col]
        p = A[col][col]
        A[col] = [x / p for x in A[col]]
        for r in range(n):
            if r == col:
                continue
            f = A[r][col]
            if f != 0.0:
                A[r] = [a - f * b for a, b in zip(A[r], A[col])]
    return [row[n:] for row in A]
```

### The tiled matmul

```python
def tiled(A, B, T=64):
    n, k = A.shape; m = B.shape[1]
    C = np.zeros((n, m))
    for i0 in range(0, n, T):
        for j0 in range(0, m, T):
            acc = C[i0:i0+T, j0:j0+T]
            for p0 in range(0, k, T):
                acc += A[i0:i0+T, p0:p0+T] @ B[p0:p0+T, j0:j0+T]
    return C
```

## Why this solution and not the obvious one

**Partial pivoting is not optional.** Without it, Gauss-Jordan divides by whatever happens to be on the
diagonal, which can be arbitrarily small even on a well-conditioned matrix, and the result is
catastrophic cancellation. Choosing the largest available pivot bounds the growth of the multipliers.
The measured consequence is visible in any ill-conditioned test: without pivoting the error grows by
orders of magnitude on matrices that invert fine with it.

**The singularity check uses a threshold, not equality.** `if A[piv][col] == 0` almost never fires in
floating point; a nearly-singular matrix produces a pivot around 1e-17 and the "inverse" is noise. The
threshold turns a silent wrong answer into an exception.

**The tiled matmul accumulates into a view (`acc = C[...]`), not a copy.** `acc += ...` on a NumPy
slice writes through to `C`. Writing `acc = acc + ...` would rebind the name to a new array and the
result would be silently discarded — a classic and completely invisible bug.

**Wrong turns worth knowing about.**

1. *Solving by computing the inverse.* Measured on a 12×12 Hilbert matrix: `solve` gives a maximum
   error of 0.143 while `inv(H) @ b` gives 8.656 — **60× worse** on identical input. Never invert to
   solve.
2. *Using `reshape` where `permute`/`transpose` was meant.* `reshape` reinterprets memory in-place
   order; `transpose` reorders axes. Confusing them raises no error and scrambles the data. This is the
   module's war story.
3. *Reductions without `keepdims=True` feeding a broadcast.* `scores / scores.sum(axis=1)` broadcasts
   along the wrong axis, produces the right shape and the wrong numbers, and raises nothing.
4. *Benchmarking at one matrix size.* The naive loop's GFLOP/s is essentially constant (interpreter-
   bound) while BLAS's falls with `n` (memory-bound). One data point hides both facts.

## Grading notes

**What 3/3 looks like**

- *Correctness* — inverse verified as `A @ inv(A) ≈ I` to 1e-9 on well-conditioned matrices, and a
  clear exception on singular ones; all three matmul readings agree.
- *Code quality* — one `matmul`, used everywhere; tiled version accumulates into views correctly.
- *Performance* — the full table across at least three sizes, with fp32 versus fp64 measured.
- *Explanation* — the 28,000× gap decomposed into four named factors with a number for each, and the
  observation that naive GFLOP/s is flat in `n` while BLAS's falls.

**The three most common ways submissions lose points**

1. **No partial pivoting.** The inverse "works" on random matrices and fails on anything structured.
2. **`acc = acc + ...` in the tiled loop.** Produces zeros, and the bug is invisible because the shapes
   are right.
3. **The benchmark gap asserted rather than decomposed.** "NumPy is faster because it's C" is one of
   four factors and the least interesting one.
