## Reference solution — `P2-W13-M2`

Six problems, each with the complexity stated before the code, a brute-force oracle kept as a test,
and the measured ratio at n = 10⁵.

### 1. Two-sum, unsorted

```python
def two_sum(nums: list[int], target: int) -> tuple[int, int] | None:
    """O(n) time, O(n) space. One pass: check for the complement BEFORE inserting,
    so an element cannot pair with itself."""
    seen: dict[int, int] = {}
    for i, x in enumerate(nums):
        if (j := seen.get(target - x)) is not None:
            return (j, i)
        seen[x] = i
    return None
```

**The ordering is the whole solution.** Looking up before inserting is what makes `two_sum([3, 2], 6)`
return `None` rather than `(0, 0)`. Insert first and the bug only appears when `target == 2 * x`,
which no hand-written test contains.

### 2. Longest substring without repeating characters

```python
def longest_unique(s: str) -> int:
    """O(n) time, O(min(n, alphabet)) space."""
    last: dict[str, int] = {}
    left = best = 0
    for right, ch in enumerate(s):
        if ch in last and last[ch] >= left:      # the guard everyone drops
            left = last[ch] + 1
        last[ch] = right
        best = max(best, right - left + 1)
    return best
```

**`last[ch] >= left` is the guard.** Without it, a character seen *before* the current window drags
`left` backwards, which both gives wrong answers and destroys the O(n) argument. `"abba"` returns 3
instead of 2 — and every simpler test still passes.

### 3. Container with most water

```python
def max_area(h: list[int]) -> int:
    """O(n) time, O(1) space. Two pointers moving inward."""
    i, j, best = 0, len(h) - 1, 0
    while i < j:
        best = max(best, (j - i) * min(h[i], h[j]))
        if h[i] < h[j]:
            i += 1
        else:
            j -= 1
    return best
```

**The correctness argument, which is what an interviewer wants:** moving the *taller* wall inward can
never help. Width strictly decreases, and the area is bounded by the shorter wall, so any pair
formed by keeping the taller wall and a narrower width is no better. Therefore discarding the
shorter wall discards nothing that could be optimal.

### 4. Product of array except self

```python
def product_except_self(nums: list[int]) -> list[int]:
    """O(n) time, O(1) extra space (the output does not count). No division —
    division fails on a zero, and on two zeros it fails differently."""
    n = len(nums)
    out = [1] * n
    prefix = 1
    for i in range(n):
        out[i] = prefix
        prefix *= nums[i]
    suffix = 1
    for i in range(n - 1, -1, -1):
        out[i] *= suffix
        suffix *= nums[i]
    return out
```

Two passes, each accumulating one side. The obvious solution — total product divided by each element
— is O(n) too, and it breaks on zeros. Handling zeros with special cases takes more code than this
version.

### 5. Minimum window substring

```python
from collections import Counter

def min_window(s: str, t: str) -> str:
    """O(|s| + |t|) time. Variable-size window: expand right, contract left while valid."""
    if not t or len(s) < len(t):
        return ""
    need = Counter(t)
    missing = len(t)               # counts DUPLICATES, which is why it is len(t) not len(need)
    best = (0, 0)
    left = 0
    for right, ch in enumerate(s, 1):
        if need[s[right - 1]] > 0:
            missing -= 1
        need[s[right - 1]] -= 1
        if missing == 0:
            while need[s[left]] < 0:      # shrink past characters we have spare
                need[s[left]] += 1
                left += 1
            if not best[1] or right - left < best[1] - best[0]:
                best = (left, right)
    return s[best[0]:best[1]]
```

**`missing = len(t)`, not `len(need)`.** If `t` is `"AABC"` you need two `A`s, and counting distinct
characters declares the window valid one `A` early. This is the single most common bug in this
problem.

### 6. Trapping rain water

```python
def trap(h: list[int]) -> int:
    """O(n) time, O(1) space. Two pointers, each carrying its side's running maximum."""
    if not h:
        return 0
    i, j = 0, len(h) - 1
    left_max = right_max = total = 0
    while i < j:
        if h[i] < h[j]:
            left_max = max(left_max, h[i])
            total += left_max - h[i]
            i += 1
        else:
            right_max = max(right_max, h[j])
            total += right_max - h[j]
            j -= 1
    return total
```

**Why you may commit to `left_max` without knowing `right_max`:** you only move the pointer on the
shorter side, so whenever you process position `i`, you know `h[j] > h[i]` — which guarantees some
wall at least as tall as `left_max` exists to the right. The water level at `i` is therefore
determined by `left_max` alone.

## Why this solution and not the obvious one

**Why keep the brute force.** Every one of these has a five-line O(n²) version. Keep it as a test
oracle and property-test the fast version against it on a few thousand random inputs. Five
hand-written cases will not contain `"abba"`, `"AABC"`, `[0, 0]`, or an empty string; random testing
finds all four in seconds.

**Why report ratios rather than times.** "37× faster at n = 10⁵" survives being run on a different
machine. "12 ms" does not.

**Where the measurements surprise you.** Two rows from the module's benchmarks are worth
reproducing, because both contradict the textbook:

| Comparison | Result |
| --- | --- |
| Prefix sums vs recomputing, n = 10⁵, 2,000 queries | 503.8 ms → 2.16 ms, **233×** |
| Sliding-window max vs `max()` per window, n = 10⁶, k = 1,000 | 9,108.5 ms → 134.5 ms, **68×** |
| Pure-Python KMP vs naive slice-compare, adversarial input | 391.5 ms vs 374.4 ms — **KMP is 4% slower** |
| `str.find` (C, two-way) vs pure-Python KMP | 2.301 ms vs 391.5 ms, **170×** |

The KMP result is the one to write up. The naive version's inner comparison is a C-level `memcmp` on
a slice; KMP's is a Python-level loop. **The asymptotically superior algorithm loses because of which
language its inner loop runs in**, and that is a more useful lesson than KMP itself.

## Grading notes

**3/3 on Correctness** — all six correct, property-tested against a brute force, and the four edge
cases handled: empty input, single element, all-identical elements, and the duplicate-character case
in problem 5.

**3/3 on Explanation** — the complexity stated *before* the code in each docstring, plus a
correctness argument for the two-pointer problems (3 and 6). Those two are the ones where "it works
on my tests" is not evidence, because the algorithm discards candidates and you must say why that is
safe.

**The three most common ways submissions lose points:**

1. **Missing the `last[ch] >= left` guard in problem 2.** Passes every test that does not contain a
   repeated character outside the current window. Test `"abba"`.
2. **`missing = len(need)` in problem 5.** Passes whenever `t` has no repeated characters. Test with
   `t = "AABC"`.
3. **Reporting absolute times with no machine specification.** Uninterpretable and unreproducible.
   Every result table opens with CPU, RAM, OS, Python version and timing method.

**A note on the stretch challenge.** If someone submits the PDF-extractor normalization study, the
thing to check is whether they measured the *downstream* consequence — the dedup rate before and
after normalization — rather than only counting invisible characters. The character counts are
interesting; the dedup-rate delta is the number that makes the case.
