## Reference solution — `P2-W13-M5`

Find the top 100 of a 10,000,000-element stream using at most 1 MB of working memory for the
algorithm's own state.

### The measurement harness

```python
# w13m5.py — one process per approach, so ru_maxrss is honest.
import gc, heapq, random, resource, sys, time

N, K = 10_000_000, 100

def stream():
    r = random.Random(5)                     # seeded: all three see identical data
    for _ in range(N):
        yield r.random()

def full_sort():
    xs = list(stream()); xs.sort(); return xs[-K:]

def nlargest():
    return heapq.nlargest(K, stream())

def bounded():
    h = []
    push, rep = heapq.heappush, heapq.heapreplace
    for v in stream():
        if len(h) < K:
            push(h, v)
        elif v > h[0]:                       # ONE comparison for the common case
            rep(h, v)
    return sorted(h)

if __name__ == "__main__":
    fn = {"sort": full_sort, "nlargest": nlargest, "bounded": bounded}[sys.argv[1]]
    gc.collect()
    t = time.perf_counter(); r = fn(); el = time.perf_counter() - t
    rss = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss
    mb = rss / 1e6 if sys.platform == "darwin" else rss / 1e3
    print(f"{sys.argv[1]},{el:.2f}s,{mb:.1f}MB,checksum={sum(r):.6f}")
```

### The result

| Approach | Time | Peak process RSS | vs sort |
| --- | --- | --- | --- |
| `list(stream())` then `.sort()` | 22.37 s | 411.6 MB | 1.0× |
| Bounded min-heap, pure Python | 2.00 s | **14.8 MB** | 11.2× faster, 27.8× less memory |
| `heapq.nlargest(100, stream())` | **1.27 s** | **14.8 MB** | **17.6× faster, 27.8× less memory** |

All three checksums identical: `99.999473`.

<Warning>
**Do not use `tracemalloc` for the memory figure.** My first attempt did, and the benchmark ran for
25 minutes without finishing — `tracemalloc` hooks every allocation and costs roughly 30× on an
allocation-heavy loop. Measure time and memory in separate runs, or use `ru_maxrss`, which is free.
This mistake is easy to make and it silently produces a benchmark of `tracemalloc`.
</Warning>

### The admission-rate derivation

The number that makes the result explicable. For a uniform random stream, element `i` is admitted
only if it lands in the top `k` of the first `i` seen — probability `k/i`. So:

```
E[admissions] = k + Σ(i=k+1..n) k/i  ≈  k + k·ln(n/k)
              = 100 + 100·ln(100,000)
              ≈ 100 + 1,151  =  1,251
```

**About 1,251 sift operations out of 10,000,000 elements — 0.0125%.** The `log k` factor applies to
a vanishing fraction of the input, which is why the measured cost is so close to a linear scan.

**Instrument this.** A submission that reports the admission rate and compares it to the prediction
has understood the algorithm; one that reports only the time has measured it.

### Then break it

```python
def sorted_stream():
    return iter(sorted(random.Random(5).random() for _ in range(N)))
```

Ascending input admits **every** element, so you pay `n log k` for real and the admission rate goes
to 100%. **Finding your own algorithm's worst case experimentally is the most valuable part of this
exercise**, and naming it unprompted in an interview is what a senior interviewer is listening for.

## Why this solution and not the obvious one

**Why a generator, not a list.** If you materialise the stream you have already lost — the memory
figure then measures the list, not the algorithm, and the whole point was `O(k)` memory.

**Why one process per approach.** `ru_maxrss` is the process's high-water mark and never decreases.
Running all three in one process means the second and third both report the first one's 411 MB peak.

**Why `heapreplace` rather than `heappop` + `heappush`.** One sift-down instead of a sift-down
followed by a sift-up. Roughly half the work on the admitted path.

**Why `nlargest` beats the hand-written bounded heap by 1.57×.** Same algorithm; `Modules/_heapqmodule.c`
does the comparison and replacement in C, while the Python version pays interpreter overhead per
element on the `if v > h[0]` test — which executes 10 million times. **This is the same lesson as
module 3's LRU (3.07×) and module 2's KMP (170×): write it to understand it, then use theirs.**

## Grading notes

**3/3 on Correctness** — all three approaches return the identical set, verified by checksum rather
than by inspection. The bounded heap handles the case where the stream is shorter than `k`.

**3/3 on Performance** — one process per approach, `ru_maxrss` for memory, wall time and memory
reported separately, machine and version stated.

**3/3 on Explanation** — the `k + k·ln(n/k)` derivation, the measured admission rate compared
against it, and the ascending-input worst case demonstrated rather than described.

**The three most common ways submissions lose points:**

1. **Using `tracemalloc` around the timed region.** Produces a 30× slowdown and a benchmark of the
   profiler. If your bounded-heap run takes minutes, this is why.
2. **Measuring all three in one process.** The memory figures become identical and meaningless.
3. **Not instrumenting the admission rate.** Without it, the `O(n log k)` claim is repeated rather
   than demonstrated, and the ascending-input worst case is invisible.

**A fourth, subtler one:** a heap of `(score, item)` tuples with no tiebreaker. It works until two
scores are exactly equal, at which point Python compares the items and raises `TypeError` if they
are not orderable. With random floats this fires rarely; with integer scores it fires immediately.
`next(itertools.count())` as the middle element, always.

**On the stretch challenge (streaming top-K service).** The thing to check is whether they compared
against **Space-Saving** as well as a count-min sketch. Space-Saving gives deterministic guarantees
for exactly the heavy-hitters problem in `O(k)` counters and frequently beats a sketch. A submission
that only implemented the sketch has not answered "is this the right structure?".
