## Reference solution — `P2-W13-M4`

Both implementations are in Layer 2 of the module page. The deliverable is the **two measurement
tables**, and this page is about getting them right.

### Table 1: probe counts (deterministic — must match)

Count probes, do not time them. Probe counts depend only on the keys and the table size, so **your
numbers should match these to within rounding**, on any machine, every run.

| α | Chaining avg | Chaining max | Open avg | Open **max** | Theory: chaining `1+α/2` | Theory: open `(1+1/(1−α))/2` |
| --- | --- | --- | --- | --- | --- | --- |
| 0.30 | 1.15 | 6 | 1.22 | 12 | 1.15 | 1.21 |
| 0.50 | 1.25 | 6 | 1.51 | 26 | 1.25 | 1.50 |
| 0.70 | 1.35 | 7 | 2.17 | 66 | 1.35 | 2.17 |
| 0.80 | 1.40 | 8 | 3.04 | 136 | 1.40 | 3.00 |
| 0.90 | 1.45 | 8 | 5.65 | 462 | 1.45 | 5.50 |
| 0.95 | 1.48 | 7 | 10.39 | **1,435** | 1.48 | 10.50 |
| 0.99 | 1.50 | 8 | **40.99** | **15,832** | 1.50 | 50.50 |

**If your chaining column does not match `1 + α/2` to two decimal places, you have a bug** — almost
certainly a hash function with poor low-bit avalanche, combined with power-of-two masking. That is
the diagnostic value of this table.

**The `max` columns are the finding.** Chaining's worst probe stays between 6 and 8 across the whole
sweep. Open addressing's goes from 12 to 15,832. The averages hide this completely, and a submission
that reports only averages has missed the failure mode.

**The crossover is at α ≈ 0.75.** Your value may differ by a few hundredths; the *existence* and

<Warning>
My first attempt at this table was unusable — the `dict` column ranged from 52 ns to 307 ns with no
pattern, and `open ÷ chain` was non-monotonic. The cause was other processes competing for the
machine. **Timing benchmarks need a quiet machine; probe counts do not.** That is why the probe
table comes first: it is correct regardless, so you can debug your implementation against it before
timing anything.
</Warning>

### The tombstone test

```python
def test_delete_heavy_workload_does_not_degrade(m):
    """Churn 10,000 entries through a table that never exceeds 200 live keys."""
    for cycle in range(50):
        for i in range(200):
            m[(cycle, i)] = i
        for i in range(200):
            del m[(cycle, i)]
    assert len(m) == 0
    m["after"] = 1
    assert m["after"] == 1
```

Without counting tombstones toward the load factor, this fills the table with tombstones, never
triggers a rebuild, and every subsequent lookup scans the entire array — **while `len(m)` reports 0
and the table looks perfectly healthy.** No other metric notices.

## Why this solution and not the obvious one

**Why probe counts before timings.** They are deterministic and they have a closed-form prediction.
If they match Knuth's 1963 formulas your implementation is correct; if they do not, you have a bug
that timing would never have revealed. **Debug against theory, then measure reality.**

**Why the resize is conditional.** The module's war story is a table that grew to 67 million slots
holding 200 live keys, because a tombstone-triggered threshold always doubled. The correct form:

```python
if (self._n + self._tombs) > self.max_load * self._cap:
    self._resize(self._cap * 2 if self._n > self._cap // 2 else self._cap)
```

Grow only if the *live* count justifies it; otherwise rebuild at the same size, which compacts
tombstones away. **One threshold decides when to act; a separate decision decides what action.**

**Why `hash(key) & (cap - 1)` and not `% cap`.** Masking is faster, and it forces power-of-two
capacity — which is what real tables do. The cost is that masking keeps only the *low* bits, so a
hash with poor low-bit avalanche produces clustering. That is a trade-off to state in the write-up,
not a detail to hide.

## Grading notes

**3/3 on Correctness** — both strategies; tombstones counted toward the load factor; the
delete-heavy churn test; property-tested against `dict` with `hypothesis`; and a test that all keys
survive two forced resizes.

**3/3 on Performance** — both tables, with the max-probe column, and the crossover identified from
the submitter's own data.

**3/3 on Explanation** — the crossover explained mechanically (contiguous probing versus a
dereferenced list object below α ≈ 0.75; primary clustering above it), and the `dict` column
acknowledged: CPython is 5–12× faster than either hand-rolled version.

**The three most common ways submissions lose points:**

1. **Open-addressing delete writing `_EMPTY` instead of a tombstone.** Breaks the probe chain for
   every key stored past it. The bug is data-dependent and intermittent, so it passes small tests.
2. **Reporting only average probe counts.** The 15,832 max at α = 0.99 is the entire tail-latency
   story and the averages hide it.
3. **Timing on a busy machine and reporting the result anyway.** If `dict` lookups measure above
   ~60 ns, or if `open ÷ chain` is non-monotonic, close everything and re-run. Publishing noise as a
   result is worse than publishing nothing.

**On the `hard` track (beating `dict`).** Pure Python will almost certainly lose, because `dict`'s
probe loop is C. **An honest loss with a profile showing where the time went earns full marks.** A
claimed win without a committed benchmark script earns zero. If someone does win, check they stated
what generality they gave up and wrote a test demonstrating the failure mode they accepted.
