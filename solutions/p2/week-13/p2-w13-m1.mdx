## Reference solution — `P2-W13-M1`

The hands-on asked for six operations benchmarked across four sizes, with the fitted exponent and
a written reconciliation for every row that disagrees with theory.

### The harness

```python
# bench_ops.py — CPython 3.12
from __future__ import annotations
import gc, math, random, time
from collections import deque

def best_of(fn, reps: int = 5) -> float:
    b = math.inf
    for _ in range(reps):
        gc.collect()
        t = time.perf_counter(); fn(); b = min(b, time.perf_counter() - t)
    return b

def fit_exponent(sizes, times) -> float:
    xs = [math.log(n) for n in sizes]; ys = [math.log(t) for t in times]
    k = len(xs); mx, my = sum(xs)/k, sum(ys)/k
    num = sum((x-mx)*(y-my) for x, y in zip(xs, ys))
    den = sum((x-mx)**2 for x in xs)
    return num/den

SIZES = (1_000, 10_000, 100_000, 1_000_000)

def op_list_append(n):
    xs = []
    for i in range(n): xs.append(i)

def op_list_pop0(n):
    xs = list(range(n))
    while xs: xs.pop(0)

def op_deque_popleft(n):
    q = deque(range(n))
    while q: q.popleft()

def op_dict_get(n):
    d = {i: i for i in range(n)}
    for i in range(n): d[i]

def op_list_membership(n):
    xs = list(range(n)); probes = range(0, n, max(1, n // 1000))
    for p in probes: p in xs

def op_set_membership(n):
    s = set(range(n)); probes = range(0, n, max(1, n // 1000))
    for p in probes: p in s

OPS = [("list.append", op_list_append), ("list.pop(0)", op_list_pop0),
       ("deque.popleft", op_deque_popleft), ("dict[k] get", op_dict_get),
       ("x in list (1k probes)", op_list_membership),
       ("x in set (1k probes)", op_set_membership)]

for name, fn in OPS:
    sizes = SIZES if "pop(0)" not in name else SIZES[:3]   # pop(0) at 1M takes minutes
    times = [best_of(lambda n=n: fn(n), 3) for n in sizes]
    print(f"{name:<24} exponent={fit_exponent(sizes, times):5.2f}")
    for n, t in zip(sizes, times):
        print(f"    n={n:>9,}  {t*1e3:10.3f} ms")
```

### The expected shape of the answer

| Operation | Theory | Typical measured exponent | Agrees? |
| --- | --- | --- | --- |
| `list.append` × n | O(n) amortized | ~1.00 | yes |
| `list.pop(0)` × n | O(n²) | ~1.95–2.00 | yes |
| `deque.popleft` × n | O(n) | ~1.00 | yes |
| `dict[k]` × n | O(n) | ~1.00–1.10 | yes |
| `x in list`, fixed 1,000 probes | O(n) | ~1.00 | yes |
| `x in set`, fixed 1,000 probes | O(1) | **~0.00–0.15** | yes, and this is the interesting one |

## Why this solution and not the obvious one

**Why a fixed probe count for the membership rows.** If you probe `n` times into a structure of
size `n`, list membership is O(n²) and set membership is O(n) — you are measuring two things at
once and cannot see the per-operation cost. Holding the probe count fixed at 1,000 isolates the
cost of *one* lookup as `n` grows, which is the question. The set row then comes back with an
exponent near zero, which is what O(1) looks like on a log-log plot: a flat line.

**Why best-of and not mean.** A mean includes every context switch, page fault and background
process. The minimum is the closest available estimate of the work itself, and it is the number
that reproduces on someone else's machine.

**Why `gc.collect()` before each rep and not `gc.disable()` throughout.** Disabling the collector
across a benchmark that allocates a million objects changes the allocator's behaviour and can
make the *last* measured case pay for everything that came before. Collecting before each timed
region gives every rep the same starting state. (For the module-1 locality benchmark, where the
structures are built and freed in isolation, `gc.disable()` inside each timed section is correct
and is what was used — the difference is that there the allocation happens outside the timer.)

**Why `pop(0)` is capped at 100,000.** At n = 1,000,000 it is roughly 5 × 10¹¹ pointer moves,
several minutes. Three points is enough to establish an exponent of 2, and a benchmark nobody
will wait for is a benchmark nobody runs.

## The two rows that should disagree, and the explanations

A submission that reports six clean agreements has not looked hard enough. Two things reliably
misbehave:

**1. `dict[k]` measures an exponent slightly above 1.0** (typically 1.05–1.15) rather than exactly
1.0. Theory says `n` lookups of O(1) each is O(n). The excess is cache behaviour: a dict of 1,000
entries fits in L1; a dict of 1,000,000 entries is roughly 40 MB of table plus key and value
objects scattered across the heap, so a large fraction of lookups miss cache. The *algorithm* is
still O(1); the *machine* is not. This is exactly Lie 1 from Layer 3, showing up on the most
common operation in Python.

**2. `list.append` shows visible steps rather than a smooth line** if you plot per-append cost
against `n`. Those are the reallocations. The amortized average is constant, but individual
appends at capacity boundaries copy the entire backing array. If a submission plots per-operation
cost and the plot is smooth, they averaged over too many operations to see it.

A third, if the sweep is wide enough: **`x in list` with 1,000 probes may show an exponent
slightly *below* 1.0** at small `n`, because at n = 1,000 the whole list is in L1 and the scan
runs at a different speed per element than at n = 1,000,000. Same mechanism, opposite direction.

## Grading notes

**3/3 on Correctness** — all six operations measured, sizes swept geometrically over at least
three orders of magnitude, exponents fitted rather than eyeballed, and the probe count held fixed
for the membership rows.

**3/3 on Explanation** — at least two disagreements identified *and correctly attributed*.
"Measurement noise" is not an explanation unless accompanied by a variance figure showing the
spread exceeds the effect. The correct attributions are cache behaviour (dict, and the membership
rows at small n) and amortization (append).

**The three most common ways submissions lose points:**

1. **Probing `n` times in the membership rows.** Produces exponents of 2.0 and 1.0 and a
   conclusion that sets are "O(n)". The measurement is not wrong; the experimental design is.
2. **Reporting the mean, or `time.time()`.** Both make results unreproducible. `time.time()` on
   some platforms has ~15 ms resolution, which is larger than several of the measurements here.
3. **No machine or version stated.** The numbers become uninterpretable. Every `RESULTS.md` opens
   with CPU, RAM, OS, Python build and timing method, or it is an anecdote.

**A note on the stretch challenge.** If someone submits the CI complexity-regression plugin, the
thing to check is whether they handled the `O(n)` versus `O(n log n)` indistinguishability
honestly. The correct answer is that a single power-law fit cannot separate them over a narrow
range, and the options are a much wider sweep, fitting competing models and comparing residuals,
or switching to deterministic operation counts. A submission that claims to detect `n log n`
regressions from a 64× sweep of wall time has not tested it.
