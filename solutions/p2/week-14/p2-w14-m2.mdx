### `sift_down`, which is where the bug is

```python
def sift_down(heap: list, i: int) -> None:
    n = len(heap)
    while True:
        smallest = i
        left, right = 2 * i + 1, 2 * i + 2
        if left < n and heap[left] < heap[smallest]:
            smallest = left
        if right < n and heap[right] < heap[smallest]:      # compare to SMALLEST, not to i
            smallest = right
        if smallest == i:
            return
        heap[i], heap[smallest] = heap[smallest], heap[i]
        i = smallest
```

**Two bugs live in those eight lines**, and both pass casual testing:

1. **`heap[right] < heap[i]` instead of `heap[right] < heap[smallest]`.** Then when both children are
   smaller than the parent you may swap with the *larger* one, placing a bigger value above a
   smaller sibling and breaking the property on that side. It only fires when both children beat the
   parent, which is common in a random heap and absent from a five-element hand test.
2. **Missing the `left < n` / `right < n` bounds checks.** `IndexError` on every leaf.

### The test that catches everything

```python
def assert_heap_property(h: list) -> None:
    for i in range(len(h)):
        for c in (2 * i + 1, 2 * i + 2):
            if c < len(h):
                assert h[i] <= h[c], f"violated at parent {i} child {c}"

def test_randomised_operations():
    import random
    rng = random.Random(0)
    h, ref = [], []
    for _ in range(10_000):
        if h and rng.random() < 0.4:
            assert pop(h) == min(ref); ref.remove(min(ref))
        else:
            v = rng.random(); push(h, v); ref.append(v)
        assert_heap_property(h)          # after EVERY operation
        assert len(h) == len(ref)
```

Checking the invariant after every one of 10,000 random operations finds bugs that a hand-written
sequence never will. It is six lines and it is the only test this structure needs.

## Why this solution and not the obvious one

**Why `heapify` rather than n pushes, and why the win is smaller than theory says.**

| n | `heapq.heapify` | n successive `heappush` | Speedup |
| --- | --- | --- | --- |
| 100,000 | 2.0 ms | 6.5 ms | **3.23×** |
| 1,000,000 | 22.7 ms | 42.0 ms | **1.85×** |

Theory predicts `log₂(10⁶) ≈ 20×`. The measurement says 1.85×. **Both are right and they answer
different questions.** `heapify` is O(n) in *comparisons*, but both versions must touch all n
elements, and at a million elements memory bandwidth dominates the comparison count. The 3.23× at
100,000 (fits in L2) against 1.85× at 1,000,000 (does not) shows the effect directly. **A submission
that reports 20× has not measured it.**

**Why the tiebreaker in the heap tuple.** `(score, next(counter), item)`. Without it, two equal
scores make Python compare the payloads, raising `TypeError` on anything without `__lt__`. It also
gives FIFO ordering within a priority level, which is almost always what you want.

**Why `threshold` returns `-inf` until the queue is full.** In week 27, HNSW stops expanding when the
nearest unexplored candidate is worse than the result set's threshold. If `threshold` returned a real
value before the set was full, the search would terminate early and silently return fewer than `k`
neighbours — a **recall** bug, not a crash, and therefore only findable by measuring recall.
