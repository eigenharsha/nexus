## Reference solution — `P2-W14-M5`

Edit distance with backtracking, then a mini `diff`.

### The five recipe lines, written before any code

1. **State.** `dp[i][j]` = minimum edits to turn `a[:i]` into `b[:j]`.
2. **Transition.** What was the last operation? Delete `a[i-1]`: `dp[i-1][j] + 1`. Insert `b[j-1]`:
   `dp[i][j-1] + 1`. Substitute or match: `dp[i-1][j-1] + (a[i-1] != b[j-1])`. Take the minimum.
3. **Base.** `dp[i][0] = i`, `dp[0][j] = j`.
4. **Order.** Row-major — each cell needs up, left and up-left, all already filled.
5. **Answer.** `dp[n][m]`.

**If a submission cannot produce those five lines, the code is guesswork that happened to work.**

### The backtrack, and the test that validates it

```python
edits, i, j = [], n, m
while i > 0 or j > 0:
    if i > 0 and j > 0 and a[i-1] == b[j-1] and dp[i][j] == dp[i-1][j-1]:
        edits.append(Edit(Op.EQUAL, i-1, j-1, a[i-1])); i, j = i-1, j-1
    elif i > 0 and j > 0 and dp[i][j] == dp[i-1][j-1] + 1:
        edits.append(Edit(Op.REPLACE, i-1, j-1, b[j-1])); i, j = i-1, j-1
    elif i > 0 and dp[i][j] == dp[i-1][j] + 1:
        edits.append(Edit(Op.DELETE, i-1, None, a[i-1])); i -= 1
    else:
        edits.append(Edit(Op.INSERT, None, j-1, b[j-1])); j -= 1
edits.reverse()
```

**The order of the four branches matters** — several may be true at once when there are ties, and
checking EQUAL first produces the alignment a human expects (matches preferred over substitutions).

```python
def test_alignment_reconstructs_the_target():
    """The only test that catches a plausible-but-wrong alignment."""
    for a, b in [("kitten", "sitting"), ("abcdef", "azced"), ("", "xyz"), ("xyz", "")]:
        _, edits = align(list(a), list(b))
        rebuilt = [e.text for e in edits if e.op in (Op.EQUAL, Op.REPLACE, Op.INSERT)]
        assert "".join(rebuilt) == b
```

**The distance is easy to get right and the path is easy to get wrong.** An off-by-one in the walk,
or the branches in the wrong order, produces an edit list of the correct *length* that does not
transform `a` into `b`. Applying the edits and comparing is the only check that catches it, and it
catches every variant.

### The space optimisation, measured

Random DNA-like strings, alphabet `acgt`:

| Length | Full matrix time | Two-row time | Full peak | Two-row peak | Memory ratio |
| --- | --- | --- | --- | --- | --- |
| 500 | 490.6 ms | 410.2 ms | 4.41 MB | 0.045 MB | **97×** |
| 2,000 | 17,749.1 ms | 14,837.4 ms | 154.54 MB | 0.165 MB | **936×** |
| 4,000 | 81,741.1 ms | **87,132.6 ms** | **634.67 MB** | **0.325 MB** | **1,952×** |

Three things to report:

1. **The memory reduction is 1,952× at length 4,000 and grows with n.** `O(nm)` versus `O(m)`. At
   length 10,000 the full matrix is ~4 GB. **The space optimisation is what makes the algorithm
   usable, not a micro-optimisation.**
2. **The time is essentially unchanged, and at 4,000 the two-row version is slightly *slower*** —
   87.1 s against 81.7 s. Both do the same `n×m` cell computations; the two-row version allocates a
   list per row, the full-matrix version pays more cache misses on 634 MB. They roughly cancel, and
   which wins depends on the size.
3. **Pure Python is 5 µs per cell.** 16 million cells in 82 seconds. In C it is roughly 20 ns.
   **For real work use `rapidfuzz` (3.10.1)**, which implements bit-parallel Myers in C++.

**And the trade the two-row version makes:** it cannot backtrack. Backtracking needs the full table,
and you threw the rows away. Need the number → two rows. Need the alignment → keep the matrix, or
use Hirschberg (`O(min(n,m))` space, exactly 2× the time).

### The Fibonacci call counts

| n | Naive calls | Memoized calls | Table steps | Naive wall time |
| --- | --- | --- | --- | --- |
| 10 | 177 | 19 | 11 | 0.0000 s |
| 20 | 21,891 | 39 | 21 | 0.0012 s |
| 30 | 2,692,537 | 59 | 31 | 0.1566 s |
| 35 | **29,860,703** | **69** | 36 | **2.6146 s** |

**432,764× fewer calls at n = 35**, and memoized calls are almost exactly `2n − 1`. Extrapolating at
the golden ratio, `fib(50)` naive is ~40 billion calls (about an hour) against 99 memoized.

## Why this solution and not the obvious one

**Why line-level rather than character-level for the `diff`.** Hashing each line to an integer makes
`n` and `m` the line counts rather than the character counts, and each comparison `O(1)` rather than
`O(line length)`. On a 1,000-line file that is 10⁶ cells instead of ~10⁹.

**Why `git` does not use this algorithm.** `git diff` runs Myers (1986), which indexes by
`(edit count, diagonal)` rather than `(i, j)` and runs in `O((n+m)·D)` where `D` is the edit-script
size. Real diffs are small, so `D` is small and Myers is nearly linear. On 10,000-line files with 10
lines changed that is ~2 × 10⁵ operations against 10⁸ — **500× less**. It is worth knowing that the
algorithm you implemented is not the one in the tool you use every day, and why.

**Why the `Edit` dataclass carries both indices.** `old_index` and `new_index` are what let a
consumer map an edit back to a line number in either file, which is what unified-diff hunk headers
need. An edit list of bare strings cannot produce a usable diff.

## Grading notes

**3/3 on Correctness** — the five recipe lines written down; distance validated against known values
(`kitten`/`sitting` = 3); **the alignment validated by applying it**; empty strings on both sides.

**3/3 on Performance** — full-matrix and two-row measured at three sizes, both time and peak memory,
with the observation that the time is essentially unchanged.

**3/3 on Explanation** — what the two-row version costs (no backtracking), and how Hirschberg gets
both at 2× the time.

**The three most common ways submissions lose points:**

1. **Testing only the distance, not the alignment.** A plausible-but-wrong edit list has the right
   length and does not reconstruct the target.
2. **Reporting only the memory reduction and not that the time is unchanged.** The surprising half
   is that the two-row version is not faster — and at 4,000 is slightly slower.
3. **Not stating what the space optimisation costs.** "1,952× less memory" without "and it cannot
   produce the alignment" is half a result.

**On the stretch challenge (diff on real commits).** The interesting deliverable is the **`D` versus
`n` scatter across thousands of real commits**. Everyone assumes diffs are small; measuring it is the
contribution. Check whether they separated source files from lockfiles and generated assets — my
expectation is the assumption holds overwhelmingly for source and fails badly for the rest, and a
survey that pools them reports a mean that describes neither.
