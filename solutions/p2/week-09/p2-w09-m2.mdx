## Reference solution — `P2-W09-M2`

### Adders

```python
def half_adder(a, b):
    return XOR(a, b), AND(a, b)                    # 6 NANDs, depth 3

def full_adder(a, b, c_in):
    s1, c1 = half_adder(a, b)
    s2, c2 = half_adder(s1, c_in)
    return s2, OR(c1, c2)                          # 15 NANDs, depth 7

def ripple(n, A, B):
    c, out = Wire(0), []
    for i in range(n):
        s, c = full_adder(A[i], B[i], c)
        out.append(s)
    return out, c                                  # 15n NANDs, depth ~4n+3

def increment(n, A):
    """Add 1. B is constant 0, so every full adder collapses to a half adder."""
    carry, out = Wire(1), []
    for i in range(n):
        out.append(XOR(A[i], carry))
        carry = AND(A[i], carry)
    return out, carry                              # 6n NANDs — 2.5x cheaper than ripple
```

### Kogge-Stone

```python
def kogge_stone(n, A, B):
    g = [AND(A[i], B[i]) for i in range(n)]        # generate — all parallel
    p = [XOR(A[i], B[i]) for i in range(n)]        # propagate — all parallel
    G, P, d = g[:], p[:], 1
    while d < n:                                    # ceil(log2 n) levels
        nG, nP = G[:], P[:]                         # fresh lists: see wrong turn 2
        for i in range(n - 1, d - 1, -1):
            nG[i] = OR(G[i], AND(P[i], G[i - d]))
            nP[i] = AND(P[i], P[i - d])
        G, P, d = nG, nP, d * 2
    carries = [Wire(0)] + G[:-1]
    return [XOR(p[i], carries[i]) for i in range(n)], G[-1]
```

## Why this solution and not the obvious one

**The full adder as two half adders, not as a sum-of-products.** From the 8-row truth table you can
write `sum = a'b'c + a'bc' + ab'c' + abc` and `c_out = ab + bc + ac`, which is correct and costs
roughly 25–30 NANDs. Two half adders plus an OR is 15. The saving comes from reusing `a XOR b`,
which appears in both the sum and (implicitly) the carry logic. **Reuse of a shared sub-expression
is the single highest-leverage move in combinational design**, and it is the same move that fixed
the FPGA timing failure in Module 1's war story.

**`Inc16` as half adders.** The full adder's `b` input is a constant 0, so `sum = a XOR 0 XOR c` =
`a XOR c` and `c_out = (a AND 0) OR ((a XOR 0) AND c)` = `a AND c`. 6 NANDs per bit against 15.
Getting this wrong costs 144 gates on `Inc16` alone and is the second most common miss on this lab.

**Wrong turns worth knowing about.**

1. *Cascading 4-bit carry-lookahead blocks and calling it `O(log n)`.* Block CLA with a ripple
   between blocks is still `O(n)` in the number of blocks. Measured, it gives 16-bit depth 32 versus
   ripple's 67 — a 2.09× win, not the 3.35× that a true prefix network gives, and the gap widens
   with width. If your "lookahead" adder's depth grows linearly, this is what you built.
2. *Updating `G` and `P` in place inside a prefix level.* Position `i` reads position `i-d`, which
   may already have been overwritten at this level. The adder then produces correct results for
   small operands and wrong ones for large ones — a maddening bug. Either build fresh lists per
   level (as above) or iterate `i` strictly downwards.
3. *Testing only with small operands.* `add(16, 3, 5)` works with a broken carry chain. Test with
   random 16-bit values and with the boundary set `{0, 1, 0x7FFF, 0x8000, 0xFFFF}`.

## Grading notes

**What 3/3 looks like**

- *Correctness* — random testing at every width plus explicit boundary values, and the carry-out
  checked (not just the low `n` bits).
- *Code quality* — one `full_adder`, used by everything. `Add16` is a loop, not sixteen lines.
- *Performance* — the full depth-versus-width table for both architectures, and the growth rates
  identified explicitly as `O(n)` and `O(log n)` from the data rather than asserted from theory.
- *Explanation* — converts depth into `f_max` and states the conclusion: a 64-bit ripple adder caps a
  single-cycle machine at about 380 MHz, so no shipping CPU can use one.

**The three most common ways submissions lose points**

1. **Depth doesn't double for ripple.** Almost always because the simulator's `Wire` depth is not
   `max(inputs) + 1`, or because Python's `+` leaked into the carry path.
2. **The prefix adder is a block-CLA in disguise.** Check the growth rate: +4 per doubling means a
   true prefix network; ×1.5 or more means blocks with a ripple between them.
3. **No conversion from depth to frequency.** The table is data; the frequency is the conclusion.
   A submission that stops at the table has done the measurement but not the analysis.
