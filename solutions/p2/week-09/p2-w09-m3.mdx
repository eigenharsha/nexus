## Reference solution — `P2-W09-M3`

### The HDL

```
CHIP ALU {
    IN  x[16], y[16], zx, nx, zy, ny, f, no;
    OUT out[16], zr, ng;
    PARTS:
    // ---- condition x ----
    Mux16(a=x,   b=false, sel=zx, out=x0);
    Not16(in=x0, out=notx0);
    Mux16(a=x0,  b=notx0, sel=nx, out=x1);
    // ---- condition y ----
    Mux16(a=y,   b=false, sel=zy, out=y0);
    Not16(in=y0, out=noty0);
    Mux16(a=y0,  b=noty0, sel=ny, out=y1);
    // ---- compute both, select one ----
    Add16(a=x1, b=y1, out=sum);
    And16(a=x1, b=y1, out=conj);
    Mux16(a=conj, b=sum, sel=f, out=fout);
    // ---- condition the output; fan out the taps on the SAME line ----
    Not16(in=fout, out=notfout);
    Mux16(a=fout, b=notfout, sel=no,
          out=out, out[15]=ng, out[0..7]=lo, out[8..15]=hi);
    // ---- zr: balanced OR tree, then invert ----
    Or8Way(in=lo, out=orlo);
    Or8Way(in=hi, out=orhi);
    Or(a=orlo, b=orhi, out=nonzero);
    Not(in=nonzero, out=zr);
}
```

### The reference model and its harness

```python
MASK = 0xFFFF
def u16(x): return x & MASK
def s16(x): return x - 0x10000 if x & 0x8000 else x

def alu(x, y, zx, nx, zy, ny, f, no):
    if zx: x = 0
    if nx: x = u16(~x)
    if zy: y = 0
    if ny: y = u16(~y)
    out = u16(x + y) if f else u16(x & y)
    if no: out = u16(~out)
    return out, (1 if out == 0 else 0), (1 if out & 0x8000 else 0)
```

```
18 functions x 2000 random 16-bit pairs: 0 failures
```

## Why this solution and not the obvious one

**Fanning the output taps out on the final `Mux16` line.** Nand2Tetris HDL forbids reading a
sub-bus of an internal pin, so `out2[15]` after the fact is a syntax error. The idiomatic fix is to
declare all four names — `out`, `out[15]=ng`, `out[0..7]=lo`, `out[8..15]=hi` — on the producing
line. Students lose 30–60 minutes here more often than on any other line in Week 9.

**`zr` as two `Or8Way`s plus one `Or`, not a 16-long chain.** Depth 5 versus depth 17. The `zr`
signal is on the ALU's output path, so its depth adds directly to the critical path, and a chain
here silently costs you 12 levels — enough to change the reported `f_max` by 15%.

**Both `Add16` and `And16` always instantiated.** Beginners try to "skip" the adder when `f = 0`.
There is no skipping in combinational logic; the hardware exists and evaluates. The MUX discards the
unwanted result. Understanding this is the difference between thinking in code and thinking in
circuits.

**Wrong turns worth knowing about.**

1. *Tapping `zr` and `ng` off `fout` instead of `out`.* Everything passes until an operation with
   `no = 1` produces zero — for instance `x - y` where `x == y`, which is `NOT(NOT x + y)` and is
   zero only *after* the final inversion. This bug specifically breaks equality comparison, which is
   the single most common branch in real programs.
2. *Applying the conditioning switches out of order.* Negate-then-zero gives `-1` where you wanted
   `0`. The order is fixed: zero, negate, combine, negate output.
3. *Using Python's `~` without masking in the reference model.* `~5` is `-6`, an arbitrary-precision
   negative integer, and every subsequent comparison is wrong. Mask after every step.

## Measured numbers this solution produces

| Block | NANDs | Depth |
|---|---|---|
| Input conditioning (both operands) | ~256 | 7 |
| Add16 (ripple) | 240 | 67 |
| And16 | 32 | 2 |
| Function MUX16 | 64 | 3 |
| Output Not16 + Mux16 | 80 | 4 |
| `zr` (two Or8Way + Or + Not) | 46 | 5 |
| **Total, ripple adder** | **~718** | **~81** |
| **Total, Kogge-Stone adder** | **~981** | **~34** |

At `t_gate = 10 ps` plus 20 ps of setup and skew: 830 ps → **1.20 GHz** with the ripple adder,
360 ps → **2.78 GHz** with the prefix adder. Swapping one block gives **2.3×**.

Verification: 18 operations × 2,000 random 16-bit operand pairs = 36,000 checks of `out`, `zr` and
`ng`. 0 failures. Exhaustive testing of one operation would require `2^32` pairs — at the harness's
measured ~1.5 M evaluations/second on CPython 3.13.2 that is about 48 minutes per operation, roughly
14 hours for all 18.

## Grading notes

**What 3/3 looks like**

- *Correctness* — the randomised harness, not just the supplied `.tst`. Flags checked on every call,
  not only on the operations where they seem interesting.
- *Code quality* — the ALU is built entirely from Module 1 and 2 chips. No `Nand` appears in
  `ALU.hdl`.
- *Performance* — area and depth reported for both adder variants, with the `f_max` arithmetic shown.
- *Explanation* — identifies the adder as the critical path and derives `NOT(NOT x + y) = x - y`
  rather than quoting the control table.

**The three most common ways submissions lose points**

1. **Flags tapped off the wrong signal.** Passes the supplied tests, fails the randomised harness on
   `x - y` with equal operands. This is the single most instructive bug in Week 9 — it is caught by
   random testing and missed by fixture testing, which is the module's whole verification argument.
2. **`zr` as an OR chain.** Functionally perfect, 12 levels of unnecessary depth, and then the
   `f_max` analysis is wrong and the student cannot see why.
3. **No derivation of the control patterns.** The table is reproduced from the book. Ask the student
   to derive `x + 1` from `zy=1, ny=1, nx=1, f=1, no=1` and the gap shows immediately.
