## Reference solution — `P2-W09-M5`

### `RAM[2] = RAM[0] * RAM[1]` by repeated addition

Handles zero and negative multipliers by taking the absolute value of the counter and fixing the
sign at the end.

```asm
// R2 = R0 * R1, correct for negative and zero inputs.
    @R2
    M=0
    @R0
    D=M
    @END
    D;JEQ           // R0 == 0 -> product is 0, done
    @R1
    D=M
    @END
    D;JEQ           // R1 == 0 -> product is 0, done

// Work with |R1| as the loop count; remember whether to negate at the end.
    @neg
    M=0
    @R1
    D=M
    @count
    M=D
    @POSITIVE
    D;JGT
    @count
    M=-M            // count = |R1|
    @neg
    M=1
(POSITIVE)

(LOOP)
    @count
    D=M
    @FIXSIGN
    D;JEQ           // counted down to zero -> finish
    @R0
    D=M
    @R2
    M=M+D           // total += R0
    @count
    M=M-1
    @LOOP
    0;JMP

(FIXSIGN)
    @neg
    D=M
    @END
    D;JEQ
    @R2
    M=-M            // R1 was negative -> negate the product
(END)
    @END
    0;JMP
```

Hand-trace for `R0 = 3, R1 = 4`: `count` = 4, and `R2` goes 3, 6, 9, 12 over four iterations; `neg`
is 0 so no sign fix. Result 12. For `R0 = 3, R1 = -4`: `count` becomes 4, `neg` = 1, `R2` reaches 12,
then `M=-M` gives −12.

Cycle cost: 2 cycles of setup per guard plus roughly **8 instructions per iteration**, so about
`8 × |R1| + 20` cycles. That is `O(|R1|)`, which is why no real machine multiplies this way — a
hardware multiplier is a tree of adders with depth `O(log n)`.

### The vectorisation result

```c
float dot(const float *a, const float *b, int n) {
    float s = 0;
    for (int i = 0; i < n; i++) s += a[i] * b[i];
    return s;
}
```

| Build | Time (best of 15) | Throughput | ns/element |
|---|---|---|---|
| `clang -O2` | 61.4 ms | 1.71 GFLOP/s | 1.172 |
| `clang -O2 -ffast-math` | 12.8 ms | 8.17 GFLOP/s | 0.245 |

**4.79×**, Apple M3 Pro, `n = 1,048,576`, 50 repetitions per timing.

## Why this solution and not the obvious one

**Counting down, not up.** `@count / M=M-1` and testing against zero uses one ALU operation and one
jump. Counting up requires loading the limit and subtracting every iteration — two extra
instructions per pass, a 25% increase in this loop. Compilers do this transformation automatically
(it is called strength reduction on the induction variable); doing it by hand in assembly is where
you first see why.

**Guarding both zero cases first.** Without the `R1 == 0` guard the loop still terminates correctly,
but the `R0 == 0` guard saves `|R1|` iterations of adding zero. More importantly, writing the guards
first makes the sign handling tractable — the general case then only has to deal with non-zero
values.

**Wrong turns worth knowing about.**

1. *Assuming `-ffast-math` is the answer rather than the diagnosis.* The 4.79× comes specifically
   from reassociation permitting a vectorised reduction. The safe version is multiple accumulators or
   a per-loop `#pragma clang loop vectorize(enable)`, which gets most of the win without disabling
   NaN semantics globally. A submission that ships `-ffast-math` project-wide has learned the number
   and not the lesson.
2. *Reporting the sorted-vs-unsorted branch benchmark as a speedup.* On arm64 at `-O2` clang emits
   `csel` and there is no branch to mispredict — measured 0.11 vs 0.12 ns/element, i.e. no effect.
   The correct submission reports the null result *with the assembly*.
3. *Forgetting that `D` is clobbered.* In Hack, computing a comparison and then loading an address
   before jumping destroys the flags' relevance. The compute must immediately precede the jump.

## Measured numbers this solution produces

- `sum_to(n)` at `-O0`: 12 instructions per iteration, all through the stack.
- `sum_to(n)` at `-O2`: **8 instructions total, no loop** — clang replaced it with `(n−1)n/2` using
  `umull` and `lsr`, plus a `csel` for `n < 1`.
- Dot product: 1.71 → 8.17 GFLOP/s, **4.79×**.
- Branchy sum over random vs sorted data at `-O2` on arm64: 0.11 vs 0.12 ns/element — **no
  difference**, because of `csel`.
- Multiply-by-addition: ~`8 × |R1| + 20` cycles.

## Grading notes

**What 3/3 looks like**

- *Correctness* — the multiply program handles zero, negatives on either operand, and both; 200
  randomised pairs pass; the program terminates for every input.
- *Code quality* — labels are meaningful, the loop counts down, guards come first, and there is a
  comment explaining the sign fix.
- *Performance* — a speedup of at least 3× demonstrated, with the mechanism identified from the
  assembly rather than assumed.
- *Explanation* — states that the dependency chain, not the work, was the limit; proposes the safe
  alternative to global `-ffast-math`; and reports at least one thing that did *not* reproduce.

**The three most common ways submissions lose points**

1. **The benchmark got optimised away.** Time is independent of `n`, the number is implausible, and
   nobody checked. Sink the result into a `volatile` and sanity-check ns/element against the memory
   bandwidth the machine can actually deliver.
2. **Speedup claimed without reading the assembly.** Half of these are real and half are dead-code
   elimination; without the assembly you cannot tell which you have.
3. **No negative result reported.** The strongest submissions include the branch benchmark that
   failed to reproduce and explain why. It demonstrates the student ran the experiment instead of
   restating the course.
