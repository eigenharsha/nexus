## Reference solution — `P3-W18-M4`

The task: cluster customers, then produce a one-page segment description a marketing team could act on.

## The two acceptance tests, and why they come before the clustering

Almost every submission produces clusters. The difference between a 2 and a 3 is whether the submission can *defend* them. Two tests, both cheap, both run before the write-up.

**Test 1 — single-feature dominance.** Cluster on each feature alone, and compare each single-feature clustering to your full clustering by adjusted Rand index. If any single feature reproduces your segmentation at ARI above 0.5, your segmentation *is* that feature, dressed up.

```python
from sklearn.metrics import adjusted_rand_score
from sklearn.cluster import KMeans
full = KMeans(k, n_init=10, random_state=0).fit_predict(Xs)
for j, name in enumerate(feature_names):
    solo = KMeans(k, n_init=10, random_state=0).fit_predict(Xs[:, [j]])
    ari = adjusted_rand_score(full, solo)
    if ari > 0.5:
        print(f"FAIL: '{name}' alone reproduces the clustering at ARI {ari:.3f}")
```

This is the war story from Layer 2, caught. In that case the answer was **ARI 0.87** for `total_spend` alone, against a 14-feature clustering.

**Test 2 — cross-seed stability.** Refit with 20 different `random_state` values and report the mean pairwise adjusted Rand index between runs. Below about 0.8, the segments are not reproducible and any name you give them is a name for noise.

## Choosing k

Three signals, on the reference synthetic data (three true blobs):

| k | inertia | silhouette | Calinski-Harabasz |
| --- | --- | --- | --- |
| 2 | 5763.46 | 0.7049 | 756.9 |
| **3** | **566.86** | **0.8480** | **5196.3** |
| 4 | 496.82 | 0.6604 | 3953.1 |
| 5 | 426.32 | 0.4924 | 3455.7 |
| 6 | 361.11 | 0.3306 | 3263.3 |

All three agree at `k = 3`, which is the truth. On real customer data they usually will not, and that disagreement is information: it means the data does not have a clean `k`.

**Then override them on actionability.** If the retention team can run four campaigns, `k = 12` is unusable however it scores. Saying "the metrics preferred 7, I am delivering 4 because that is what can be operated, and here is what the extra three would have split" is a stronger deliverable than either number alone.

## The two preprocessing facts

**Scaling changes the answer, and the internal metric will mislead you about it.** Measured on `load_breast_cancer` against the true diagnosis:

```
raw           ARI 0.4914   silhouette 0.6973
standardised  ARI 0.6536   silhouette 0.3434
```

Standardising made the clustering **33% better in relative ARI** and **halved the silhouette**. On raw data, `worst area` (values in the thousands) dominates every distance, so the "clusters" are a threshold on one column — geometrically beautiful, and unrelated to the diagnosis. **Any submission that selects a preprocessing choice by silhouette has selected the wrong one.**

**Initialisation changes the answer too.** On 3,000 points with 12 true clusters, single initialisation, 30 seeds:

```
init="random"     inertia mean 5429.7  sd 2999.4  best 3368.4  worst 20751.8
init="k-means++"  inertia mean 3691.3  sd  332.9  best 3368.2  worst  4616.0
```

A 9x reduction in run-to-run variance and a 4.5x better worst case, for the cost of `k` extra passes. `n_init >= 10` on top of that.

## The one-pager

The deliverable, per segment, in this order:

1. **A name from the top three feature ratios**, never a cluster index. Indices are not stable across refits; "high-frequency, low-basket, discount-led" is.
2. **Share of customers and share of revenue.** These differ, and the difference is usually the finding.
3. **The three features whose cluster mean most exceeds the population mean**, with the ratio.
4. **One action.** If you cannot write it, the segment is not actionable and should be merged.
5. **The stability number** for the whole segmentation, once, in a footnote.

No cluster indices, no inertia, no silhouette, no `k`. Those belong in the appendix.

## Why this solution and not the obvious one

**The obvious solution runs `KMeans(n_clusters=5)` on every numeric column, prints the cluster means, and calls the result a segmentation.** It will look fine. It is untestable, unstable across seeds, and — if any feature has a much larger range than the others — a rename of that feature.

Two more wrong turns:

1. **Clustering on everything, including tenure proxies.** If `days_since_signup` (or anything correlated with it) is in the feature set, one segment will be "new customers" and one will be "old customers", which nobody needed a model to discover. Cluster on *behaviour you can act on*, and exclude the rest deliberately, in writing.
2. **One-hot encoding a high-cardinality categorical into the distance.** A 5,000-level column contributes 5,000 dimensions in which almost every pair of rows differs by exactly `sqrt(2)`, which is a nearly constant offset added to every pairwise distance and drowns the ten behavioural features you cared about. Reduce it, hash it, or leave it out.

## Grading notes

**3/3 looks like:** both acceptance tests run and reported with numbers; `k` chosen with three metrics and then overridden on actionability with the override stated; `k-means++` with `n_init>=10`; a one-page document with named segments, revenue shares and one action each, containing no cluster indices and no ML vocabulary; and an explicit list of features excluded and why.

**The three most common ways submissions lose points:**

1. **No scaling**, so the segmentation is one feature's bands. The single-feature ARI test catches it in twenty minutes.
2. **Selecting preprocessing by silhouette.** Measured above, that picks the worse clustering.
3. **Segments named "Cluster 0" through "Cluster 4".** Indices are not stable across refits, so the deliverable stops meaning anything the first time somebody reruns it.
